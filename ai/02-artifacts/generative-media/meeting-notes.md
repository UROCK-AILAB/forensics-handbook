# AI 회의록 앱 (클로바노트·Otter 등)

AI 회의록 앱은 회의 녹음을 받아 글로 옮기고 정리하며, Otter 는 녹음·받아쓴 기록·회의 화면 캡처를 클라우드에 두어서 원본은 서버에 있고, 기기에는 앱과 로컬 받아쓰기 도구의 흔적이 남습니다.

## 무엇을 기록하나 · 왜 생기나

회의록 앱은 회의를 녹음하거나 녹음 파일을 받아 받아쓰기(transcript)를 만들고 요약을 붙이는 서비스라서, 한 회의에 녹음, 받아쓴 기록, 요약, 회의 자료가 함께 쌓입니다. 개인 대화형 AI 와 달리 여러 사람의 목소리와 화면이 한 기록에 들어간다는 점이 조사에서 가장 먼저 눈여겨볼 부분입니다.

Otter 가 모으는 항목은 오디오 녹음("Audio Recordings"), OtterPilot 의 자동 스크린샷, 사용자가 올린 글·이미지·영상입니다[1]. 자동 스크린샷은 온라인 회의에서만 찍고("The automatic screenshots will only take place in virtual meetings.") 회의의 받아쓴 기록에 붙습니다[1]. 외부 서비스를 연동하면 캘린더 정보와 연락처 정보도 받습니다[1]. OtterPilot 이 어느 회의 플랫폼에 들어가는지는 분석 대상 계정의 연동 설정에서 확인합니다.

Otter 는 비식별화한 오디오 녹음과 받아쓴 기록으로 자체 AI 를 학습시키고, 이 기록에는 개인정보가 들어 있을 수 있습니다[1].

클로바노트(네이버)는 녹음 파일과 음성 기록을 서버에 두는지, 얼마나 보관하는지, 기기에 무엇이 남는지는 실제 기기와 계정 화면으로 직접 확인해야 합니다.

## 위치와 버전별 차이

| 앱 | 원본이 있는 곳 | 보관 | 기기에 남는 것 | 근거 |
|---|---|---|---|---|
| Otter | 클라우드(Amazon Web Services, 미국 기반)에서 저장·처리 | "as long as necessary to fulfill the purposes set out in this Policy, or for as long as we are required to do so by law", 구체 기간과 휴지통 기간은 공개되지 않음 | 기기의 앱 데이터 폴더에서 확인 | 처리방침[1] |
| 클로바노트 | 계정 화면에서 확인 | 계정 화면에서 확인 | 기기의 앱 데이터 폴더에서 확인 | 공개 분석 자료 없음 |
| 로컬 받아쓰기 도구 | PC | 도구마다 다름 | 스크립트, 모델 파일, 결과 파일 | 실제 기기에서 확인 |

Otter 는 녹음과 받아쓴 기록을 클라우드에서 저장·처리하므로[1], 회의 원본은 서버에 있다고 보고 수집을 계획합니다. 내보낼 수 있는 형식은 계정의 내보내기 메뉴에서 확인하고, 계정에서 받는 방법은 [계정 데이터 내보내기로 수집](../../03-techniques/acquisition/export-collection.md)을, 서비스 회사에 직접 요청하는 방법은 [서비스 회사에 대한 데이터 요청](../../03-techniques/acquisition/legal-requests.md)을 따릅니다. 데스크톱 앱이 웹뷰로 만든 앱이면 캐시는 [Electron·웹뷰 앱의 저장 구조](../../01-foundations/storage-model/electron-webview.md)의 원리대로 찾고, Android·iOS 앱은 [앱 데이터 폴더 구조](https://urock-ailab.github.io/forensics-handbook/android/01-foundations/storage/app-data-layout.html)와 [데이터 보호](https://urock-ailab.github.io/forensics-handbook/ios/01-foundations/storage/data-protection/index.html)를 따릅니다.

### 로컬 받아쓰기 스크립트

회의록 앱을 쓰지 않고 PC 에서 음성 인식 모델로 직접 받아쓰는 경우도 있고, 이런 스크립트는 AI 개발 도구의 플러그인 안에도 들어 있습니다. 예를 들어 Claude Code 에 영상 받아쓰기용 플러그인을 설치하면 플러그인 폴더에 `transcribe.py` 와 `whisper.py` 같은 스크립트가 생기고, 같은 스크립트가 내려받은 캐시 폴더와 마켓 폴더 두 곳에 있을 수 있습니다.

```
%USERPROFILE%\.claude\plugins\cache\(마켓 이름)\watch\(버전)\scripts\transcribe.py
%USERPROFILE%\.claude\plugins\cache\(마켓 이름)\watch\(버전)\scripts\whisper.py
%USERPROFILE%\.claude\plugins\marketplaces\(마켓 이름)\scripts\transcribe.py
```

이 두 파일은 회의록 앱이 아니라 플러그인의 스크립트이고, 받아쓴 결과를 어디에 저장하는지는 스크립트 본문에서 출력 경로를 찾아 확인합니다. 스크립트가 있다는 사실은 받아쓰기를 할 수 있는 환경이었다는 뜻이고, 실제로 돌렸는지는 [세션 기록 구조](../dev-agents/claude-code/transcripts.md)의 도구 호출 줄에서 찾습니다.

## 구조

Otter 의 회의 한 건에 모일 수 있는 기록을 나누면 다음과 같습니다[1].

| 기록 | 뜻 | 조건 |
|---|---|---|
| 오디오 녹음 | 회의 소리 | 녹음하거나 올린 경우 |
| 받아쓴 기록 | 녹음을 글로 옮긴 것 | 녹음이 있는 경우 |
| 자동 스크린샷 | OtterPilot 이 회의 화면을 찍은 것 | 온라인 회의에서만, 받아쓴 기록에 붙음 |
| 올린 콘텐츠 | 사용자가 올린 글·이미지·영상 | 올린 경우 |
| 연동 정보 | 캘린더 정보, 연락처 정보 | 외부 서비스를 연동한 경우 |

요약의 저장 형식과 화자 이름을 붙이는 방식은 공개 자료에 없어서, 내보낸 파일에서 확인합니다.

## 증거로서 의미

**증명하는 것.** 계정에 회의 기록이 있으면 그 계정으로 그 회의의 녹음과 받아쓴 기록을 만들었거나 올렸다는 뜻이고, 자동 스크린샷이 있으면 온라인 회의 중 어떤 화면이 떠 있었는지 보여 줍니다. 스크린샷에는 다른 참석자가 공유한 화면도 찍힐 수 있어서, 회의 자료가 회사 밖 서비스로 나갔는지 따지는 사건에서는 받아쓴 글보다 스크린샷이 더 직접적인 단서가 됩니다. 보고서에는 "이 계정에 이 날짜의 회의 기록이 있고, 녹음과 받아쓴 기록, 스크린샷 몇 장이 붙어 있다" 처럼 기록으로 확인되는 만큼만 씁니다.

**증명하지 못하는 것.** 사용자가 녹음 파일을 올릴 수도 있어서, 회의 기록이 있다고 계정 주인이 그 회의에 참석했다고 볼 수는 없습니다. 받아쓴 기록은 소리를 글로 바꾼 결과라 잘못 받아쓴 말이 섞일 수 있고, 누가 그 말을 했는지는 녹음과 참석자 정보로 따로 확인해야 합니다([그 대화를 한 사람이 누구인가](../../04-scenarios/attribution/user-attribution.md)). 기록이 없다는 사실도 앱을 쓰지 않았다는 증거가 되지 않는데, 사용자가 지웠거나 다른 계정·다른 앱을 썼을 수 있습니다.

## 시각 해석

서버 기록의 회의 시각이 녹음 시작 시각인지, 올린 시각인지, 어느 시간대로 보여 주는지는 공개 문서에 없어서 실제 계정과 내보내기 파일에서 먼저 봅니다. 캘린더를 연동했다면 일정 정보와 회의 기록 시각을 나란히 놓고 맞춰 볼 수 있고, Otter 가 기록과 일정을 어떻게 잇는지는 시험용 계정으로 확인합니다.

기기 쪽에서는 내려받은 녹음·받아쓰기 파일의 파일 시스템 시각이 다운로드나 저장 시각을 가리키고, 로컬 받아쓰기 결과 파일의 만든 시각은 받아쓰기를 돌린 때일 가능성이 있지만, 복사하거나 옮기면 바뀌므로 도구 호출 기록과 맞춰 봅니다. 여러 출처를 시간순으로 합치는 방법은 [AI 사용 타임라인](../../03-techniques/analysis/timeline.md)에 있습니다.

## 함정과 한계

Otter 의 보관 기간은 "목적에 필요한 동안, 또는 법이 요구하는 동안" 으로만 정해져 있어 언제 지워지는지 기준이 없고[1], 필요한 기록은 일찍 보존을 요청합니다. 기록이 미국의 클라우드에 있어서 요청 절차가 국내 서비스와 다를 수 있고, 그 절차는 [서비스 회사에 대한 데이터 요청](../../03-techniques/acquisition/legal-requests.md)에서 다룹니다. 보관 설정과 삭제의 일반 원리는 [대화 기록 보관 설정과 삭제](../../01-foundations/storage-model/retention-deletion.md)에 있습니다.

회의록 앱은 한 사람의 AI 사용이 아니라 회의 참석자 모두의 발언과 화면을 담아서, 조사 범위를 정할 때 조사 대상이 아닌 참석자의 정보가 함께 들어온다는 점을 미리 정리해 둡니다. 클로바노트는 공개된 분석 자료가 없어서, 다른 앱의 저장 방식을 그대로 옮겨 적용하지 않고 실제 기기로 확인합니다.

## 직접 분석해 보기

**헥스로 한 번.** 녹음 파일의 형식을 첫 바이트로 판별하는 방법은 [음성 대화 기능](voice-mode.md)의 시작 바이트 표와 같습니다. 여기서는 내보낸 받아쓰기 글 파일의 인코딩을 봅니다. 아래는 UTF-8 명세로 만든 예시이고, 실제 파일에서 뜬 바이트가 아닙니다.

```
만든 예시(UTF-8 명세로 만든 바이트, 글 "회의")
00000000  EF BB BF ED 9A 8C EC 9D 98                        .........
```

처음 3바이트 `EF BB BF` 는 UTF-8 BOM 이고, 그 뒤 `ED 9A 8C` 가 "회", `EC 9D 98` 이 "의" 입니다. 파일이 `FF FE` 로 시작하면 UTF-16 LE 라서 한글 한 글자가 2바이트로 들어가고("회" 는 `8C D6`), 영문·숫자 뒤에는 `00` 이 붙습니다. 인코딩을 잘못 고르면 키워드 검색에서 한글 문장이 걸리지 않습니다.

**공개 도구로 한 번.** 내보낸 받아쓰기 파일이 여럿이면 사본 폴더에서 ripgrep 으로 키워드를 찾습니다. 폴더 이름과 키워드는 만든 예시입니다.

```sh
rg -n -i "가짜프로젝트|toy-shop" ./made-example-export/
```

녹음 파일의 길이와 코덱은 음성 대화 기능 페이지에서처럼 ffprobe 로 읽고, 녹음 길이를 받아쓴 기록의 마지막 시각과 맞춰 기록이 잘렸는지 봅니다.

## 교차 검증

회의 기록이 있는 시간대에 서비스와 통신했는지는 [AI 서비스 도메인과 네트워크 기록](../network-enterprise/network-traces.md)과 [보안 제품이 남기는 AI 사용 기록](../network-enterprise/dlp-casb.md)으로 맞춰 봅니다. 같은 네이버 서비스의 흔적은 [클로바X](../chat-services/clova-x.md) 페이지에, 협업 도구에 들어간 요약 기능은 [협업 도구의 AI 기능](../office-integrations/workspace-ai-features.md)에 있습니다. 회의 자료를 회사 밖 AI 로 보냈는지 따지는 흐름은 [기밀 자료를 AI에 넣었나](../../04-scenarios/data-leak/confidential-input.md)와 [회사가 허용하지 않은 AI를 썼나](../../04-scenarios/data-leak/shadow-ai.md)에 있고, 기기에서 흔적을 모으는 순서는 [기기에서 AI 흔적 모으기](../../03-techniques/acquisition/endpoint-triage.md)에 있습니다.

## 실습

회의록 앱의 흔적이 든 공개 시험 데이터가 없으므로, 시험용 계정과 가짜 회의로 풀어 봅니다.

1. 시험용 계정으로 가짜 회의를 녹음하고, 내보낼 수 있는 형식을 모두 받아 파일 형식과 인코딩을 확인합니다.
2. 온라인 회의에서 화면을 공유한 뒤, 받아쓴 기록에 스크린샷이 몇 장, 어느 자리에 붙었는지 봅니다.
3. 데스크톱 앱이나 모바일 앱을 쓴 뒤 앱 데이터 폴더에 녹음이나 받아쓴 글의 사본이 남는지 찾습니다.
4. 로컬 받아쓰기 스크립트로 가짜 녹음을 받아쓰고, 결과 파일이 어디에 생기는지와 파일 시각을 기록합니다.
