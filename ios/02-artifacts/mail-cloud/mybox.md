# 네이버 MYBOX (MYBOX)

## 한 줄 요약

네이버 MYBOX 는 사진 자동 올리기가 있는 국내 클라우드 저장 앱이고, 앱 안의 저장 구조가 공개 자료로 확인되지 않아서 로컬 백업의 앱 영역을 검체에서 직접 풀고 사진·네트워크 기록과 맞춰 보는 방식으로 분석합니다.

## 무엇을 기록하나 · 왜 생기나

MYBOX 는 NAVER Corp. 가 내는 앱이고 App Store 에는 "네이버 MYBOX - NAVER MYBOX" 라는 이름으로 유틸리티 분류에 올라 있습니다(id585173084) [1]. App Store 설명에 따르면 무료로 30GB 를 쓰고 유료로 최대 20TB 까지 늘릴 수 있으며, 사진 자동 올리기(조건 설정 가능), 사진 정리와 중복 파일 정리, 날짜·장소·주제로 찾기, 네이버 블로그·메일·카페로 파일과 폴더 공유를 지원합니다 [1].

분석에서 눈여겨볼 기능은 사진 자동 올리기입니다. 사용자가 올리기 버튼을 누르지 않아도 사진이 서버로 나갈 수 있어서, "이 사진이 밖으로 나갔나" 라는 질문에 이 앱이 끼어들 수 있습니다. 다만 어떤 사진을 언제 올렸는지를 앱이 기기 안에 남기는지, 남긴다면 어느 파일에 남기는지는 공개 출처에서 확인하지 못했습니다. 앱 컨테이너 안의 DB·plist·캐시 경로와 표·칸 이름, 시각 형식도 마찬가지라서 이 페이지는 그 부분을 검체에서 직접 확인할 항목으로 남깁니다.

App Store 개인정보 라벨에는 사용자와 연결된 데이터로 식별자(사용자 ID·기기 ID), 구입 항목, 위치(정확·대략), 연락처 정보(이메일·이름·전화번호), 사용자 콘텐츠(사진·비디오·오디오·고객 지원), 사용 데이터, 진단이 적혀 있고, 추적에 식별자를 쓴다고 적혀 있습니다 [1]. 이 라벨은 개발사가 수집해 처리하는 데이터 종류를 밝힌 것이고, 기기 안에 그 데이터가 남는다는 뜻은 아닙니다.

## 위치와 버전별 차이

| 무엇 | 위치 | 확인 정도 |
|---|---|---|
| 앱 설치 여부와 번들 ID | 백업 최상위 `Info.plist` 의 `Installed Applications`·`Applications` 키, `Manifest.db` 의 도메인 이름 | 키 이름 관찰 |
| 번들 ID | 공개 출처에서 확인 못 함 | 검체의 설치 앱 목록에서 확인 |
| 앱 컨테이너 안의 DB·plist·캐시 | 앱 도메인(`AppDomain-` 로 시작) 안 | 확인 못 함, 검체에서 직접 확인 |
| 자동 올리기 기록 | 확인 못 함 | 기기 안에 남는지부터 확인 못 함 |
| Files 앱 쪽 흔적 | `HomeDomain` 의 `Library/Application Support/FileProvider/` 아래 | 앱이 Files 앱 공급자로 등록되었을 때만 해당, MYBOX 로 관찰한 것은 아님 |

관찰한 백업에는 도메인이 1428개 있었고 그중 다른 회사 앱 161개는 메모에서 이름을 가렸기 때문에, MYBOX 앱 도메인의 존재와 내용은 관찰하지 않았습니다.

| 항목 | 내용 | 근거 |
|---|---|---|
| 앱이 요구하는 최소 iOS | iOS 17.0(2026-09 조회 시점) | [1] |
| 조회 시점 앱 버전 | 5.5.3 | [1] |

지금 App Store 버전은 iOS 17.0 을 요구하므로 iOS 15·16 기기에서 발견한 앱은 그보다 예전 버전일 수 있고, 예전 버전의 저장 구조도 확인하지 못했습니다.

## 구조

앱 내부 구조는 확인하지 못했으므로, 검체에서 아래 순서로 구조를 밝힙니다.

1. 백업 `Info.plist` 의 설치 앱 목록에서 MYBOX 번들 ID 를 찾습니다. 번들 ID 와 앱 그룹 읽는 법은 [번들 ID와 앱 그룹](../../01-foundations/value-decoding/bundle-id-app-group.md) 에 있습니다.
2. `Manifest.db` 의 `Files` 표에서 그 번들 ID 가 들어간 `AppDomain-`·`AppDomainGroup-`·`AppDomainPlugin-` 도메인을 모두 찾습니다. 백업 안에서 파일을 꺼내는 방법은 [로컬 백업](../../01-foundations/backups/local-backup/index.md) 에 있습니다.
3. 찾은 도메인 안의 파일을 머리말로 SQLite·plist·그 밖의 형식으로 나눕니다.
4. SQLite 파일마다 표 이름과 칸 이름을 적고, 파일 이름·경로·크기·시각처럼 보이는 칸이 있는 표를 고릅니다.
5. 앱에서 알고 있는 동작(사진 한 장 올리기, 폴더 하나 공유하기)을 시험 기기에서 해 보고, 어느 표의 어느 칸이 바뀌는지 봅니다. 이 절차는 [앱 데이터 분석](../../03-techniques/analysis/app-data-analysis/index.md) 에서 자세히 다룹니다.

MYBOX 가 Files 앱에 저장 위치로 연결되는 경우에는 `Domains.plist` 와 Files 앱 설정 파일에 공급자 흔적이 남을 수 있습니다. 이 구조와 관찰한 키는 [구글 드라이브](google-drive.md) 페이지의 "파일 공급자 도메인 설정" 과 "Files 앱 설정" 에서 설명하고, 여기서는 되풀이하지 않습니다. MYBOX 가 파일 공급자 도메인을 등록하는지는 확인하지 못했습니다.

## 증거로서 의미

### 증명하는 것

백업의 설치 앱 목록과 앱 도메인에 MYBOX 가 있으면, 백업을 만든 시점에 그 앱이 기기에 설치되어 있었다는 기록이 됩니다. 앱 영역에서 파일 목록이나 올리기 대기열로 보이는 표를 찾고 시험 기기로 그 뜻을 밝혔다면, 그 표에 적힌 파일을 앱이 다룬 기록이 있다고 말할 수 있습니다.

### 증명하지 못하는 것

앱이 설치되어 있다는 사실만으로는 사진이 올라갔다고 말할 수 없습니다. 자동 올리기는 조건을 정해 쓰는 기능이라서, 설정 값과 실제로 올린 기록을 따로 확인해야 합니다. 개인정보 라벨에 적힌 데이터 종류는 기기 안의 기록이 아니라서 증거로 쓰지 않습니다. 기기에서 찾지 못한 파일이 MYBOX 서버에도 없었다고 쓰지 않습니다.

보고서에는 "MYBOX 로 사진을 유출했다" 대신 "이 시간대에 MYBOX 앱이 이만큼 송신한 기록이 있고, 앱 영역에 이런 파일 목록이 남아 있다" 처럼 기록이 말하는 만큼만 씁니다.

## 시각 해석

앱이 시각을 어떤 형식으로 저장하는지, UTC 인지 현지 시각인지는 확인하지 못했습니다. 시각으로 보이는 칸을 찾으면 자릿수로 초·밀리초를 가늠하고, Unix 시각과 Mac 절대 시각 등으로 바꿔 본 뒤 시험 기기에서 한 동작의 시각과 견주어 형식을 정합니다. 형식별 변환은 [시각 값](../../01-foundations/value-decoding/time-values.md) 에 있습니다.

자동 올리기는 사진을 찍은 시각과 서버로 올라간 시각이 다를 수 있습니다. 사진 쪽 시각은 [카메라 사진과 메타데이터](../media/dcim-exif.md) 에서, 앱이 데이터를 주고받은 쪽은 [앱별 데이터 사용량](../network/data-usage.md) 에서 따로 읽고, 두 시각을 하나로 섞지 않습니다.

## 함정과 한계

공개 iOS 포렌식 참고 목록(RealityNet iOS-Forensics-References, 2023-04 갱신 기준)에는 NAVER·MYBOX 항목이 없습니다 [2]. 분석 도구에 이 앱을 읽는 기능이 없을 수 있고, 도구가 아무것도 보여 주지 않는다고 기록이 없는 것은 아닙니다. 도구 결과는 [도구 검증](../../03-techniques/reporting/tool-validation.md) 방식으로 확인합니다.

MYBOX 에는 네이버 블로그·메일·카페로 파일을 공유하는 기능이 있고 [1], 공유 흔적이 MYBOX 앱 영역이 아니라 [네이버 앱](../browsers/naver.md) 이나 메일 쪽에 남을 수도 있지만 이 부분은 확인하지 못했습니다. 한 앱만 보고 공유가 없었다고 결론 내리지 않습니다.

Android 판이나 PC 판에서 알려진 파일 이름을 아이폰 백업에서 그대로 찾지 않습니다. 이 페이지에서 확인한 iOS 쪽 구조는 앱 바깥의 설치 기록뿐입니다.

## 직접 분석해 보기

### 헥스로 한 번

앱 영역의 파일은 이름만으로 형식을 알 수 없는 경우가 많아서 머리말을 봅니다. SQLite 파일은 맨 앞 16바이트가 `SQLite format 3` 과 널 바이트 하나라서 헥스 편집기로 열면 아래처럼 보입니다. 아래는 명세로 만든 예시이고 검체에서 나온 값이 아닙니다.

```
00000000  53 51 4C 69 74 65 20 66  6F 72 6D 61 74 20 33 00  SQLite format 3.
```

이 머리말이 보이는 파일은 확장자와 상관없이 SQLite 로 열어 표 목록을 봅니다. 머리말 뒤의 페이지 크기와 WAL 파일 처리는 [SQLite 데이터베이스](../../01-foundations/data-formats/sqlite/index.md) 에서 따라갑니다.

### 공개 도구로 한 번

1. 백업의 `Manifest.db` 사본을 sqlite3 로 열어, 설치 앱 목록에서 확인한 번들 ID 로 앱 도메인과 파일 목록을 뽑습니다(`번들ID` 자리에 실제 값을 넣습니다).

   ```sql
   SELECT fileID, domain, relativePath FROM Files
   WHERE domain LIKE 'AppDomain%번들ID%'
   ORDER BY domain, relativePath;
   ```

2. 뽑은 파일 가운데 SQLite 로 확인한 파일을 sqlite3 로 열어 표와 칸을 적습니다.

   ```sql
   SELECT name, sql FROM sqlite_master WHERE type = 'table';
   ```

3. plist 파일은 Python 표준 라이브러리 `plistlib` 으로 읽어, 자동 올리기 설정으로 보이는 키가 있는지 봅니다. 키 이름은 확인하지 못했으므로 시험 기기에서 설정을 바꿔 보며 어느 키가 바뀌는지 확인합니다.

## 실습

NIST CFReDS 같은 공개 검체 가운데 MYBOX 앱이 설치된 iOS 검체가 있는지 먼저 확인하고, 있으면 아래 질문을 풀어 봅니다. 공개 검체가 없으면 시험용 계정과 시험 기기로 직접 만든 백업에서 풉니다.

1. 설치 앱 목록에서 MYBOX 의 번들 ID 를 찾고, 그 번들 ID 가 들어간 도메인이 `Manifest.db` 에 몇 개 있는지 셉니다.
2. 앱 도메인 안의 파일을 머리말로 나누고, SQLite 파일의 표 이름을 모두 적습니다.
3. 시험 기기에서 사진 한 장을 올린 뒤 다시 백업하고, 두 백업 사이에 바뀐 표와 칸을 찾습니다.
4. 3번에서 찾은 시각 칸의 형식을 정하고, 앱별 데이터 사용량의 기록과 시간대가 맞는지 봅니다.
5. 자동 올리기를 끈 상태와 켠 상태로 백업을 하나씩 만들어, 설정이 어느 파일의 어느 키에 남는지 찾습니다.
