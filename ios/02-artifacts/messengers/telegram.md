# 텔레그램 (Telegram)

텔레그램 iOS 앱은 앱 그룹 공유 폴더 아래 `telegram-data` 폴더에 계정마다 메시지 DB 와 미디어를 따로 두고, 메시지 DB 는 SQLite 파일이지만 값이 앱 자체 이진 형식이라 일반 SQLite 뷰어로는 내용이 읽히지 않습니다.

## 무엇을 기록하나 · 왜 생기나

텔레그램은 대화 목록을 빨리 띄우고 받은 미디어를 다시 내려받지 않으려고 기기에 캐시를 둡니다. 이 캐시가 포스트박스 (Postbox) 라는 저장소이고, 메시지·대화 상대·채팅 목록·읽음 상태·연락처·접속 상태·계정 설정이 모두 여기에 들어갑니다 [1][2].

텔레그램 대화는 두 종류라서 기기에 남는 기록의 무게도 다릅니다. 일반 대화인 클라우드 대화는 텔레그램 클라우드에 암호화해 저장하고 여러 기기에서 동기화하지만, 비밀 대화 (Secret Chat) 는 클라우드에 없고 처음 만든 기기에서만 볼 수 있습니다 [3]. 비밀 대화의 내용을 찾는다면 그 대화를 만든 기기에서 추출한 데이터가 유일한 출처일 수 있습니다.

## 위치와 버전별 차이

아래 경로는 전체 파일 시스템 추출 기준이고, 모두 앱 그룹 공유 폴더 아래에 있습니다 [1][2]. 앱 그룹 개념은 [번들 ID와 앱 그룹](../../01-foundations/value-decoding/bundle-id-app-group.md) 에서 다룹니다.

| 경로(`telegram-data/` 아래) | 내용 |
|---|---|
| `account-*/postbox/db/db_sqlite` | 계정별 메시지 DB. 파일 이름에 확장자가 없다 [1] |
| `account-*/postbox/media/` | 계정별 미디어 [1] |
| `account-*/postbox/media/telegram-peer-photo-size-*` | 프로필 사진 캐시 [2] |
| `accounts-metadata/atomic-state` | 기기에 등록된 계정 ID 와 활성 계정 [2] |
| `accounts-metadata/db/db_sqlite` | 계정 공용 설정 DB [2] |
| `accounts-metadata/spotlight/p*/data.json`, `avatar.png` | Spotlight 에 넘기는 연락처 캐시 [2] |

계정마다 `account-` 뒤에 ID 가 붙은 폴더가 따로 생겨서, 한 기기에서 여러 계정을 썼다면 폴더도 여러 개입니다 [1][2].

번들 ID·앱 그룹 ID 와 로컬 백업의 도메인 이름, 텔레그램 파일이 로컬 백업에 들어가는지는 실제 데이터로 확인해야 합니다. 로컬 백업에서는 앱 그룹 공유 폴더가 `AppDomainGroup-` 으로 시작하는 도메인으로 따로 나뉩니다. 백업 도메인 읽는 법은 [로컬 백업](../../01-foundations/backups/local-backup/index.md) 에 있습니다.

이 경로와 구조는 iOS 13.3.1(텔레그램 6.0)부터 iOS 18.7.8(텔레그램 12.6.3)까지의 iLEAPP 시험 표본에서 나온 것입니다 [1].

| 항목 | 확인된 범위 |
|---|---|
| iOS | 13.3.1 ~ 18.7.8 [1] |
| 텔레그램 앱 | 6.0 ~ 12.6.3 [1] |

## 구조

`db_sqlite` 안의 표 이름은 `t0`, `t2`, `t6`, `t7` 처럼 숫자로만 붙어 있고, 각 표는 `key`·`value` 두 열입니다 [1][2]. `value` 는 텔레그램 자체 이진 형식이라서 SQLite 뷰어로 열면 열 이름과 바이트 덩어리만 보입니다. 각 표의 역할은 텔레그램 iOS 공개 소스의 표 정의(Postbox.swift 의 tableSpec 번호)와 맞춘 것입니다 [1][2].

| 표 | 역할 |
|---|---|
| `t0` | 메타데이터. 키 2 가 계정 상태(state.date) [2] |
| `t2` | 대화 상대: 사용자·봇·그룹·채널·비밀 대화 [2] |
| `t6` | 메시지가 가리키는 미디어 [1] |
| `t7` | 메시지 [1] |
| `t9` | 채팅 목록 [2] |
| `t12` | 메시지 분류 색인(사진·영상·파일·음악·음성·링크·고정 등) [2] |
| `t14` | 읽음 상태 [2] |
| `t16` | 연락처 목록 [2] |
| `t18` | 상대 상세 캐시 [2] |
| `t20` | 접속 상태 [2] |
| `t35` | 계정 설정 [2] |
| `t54` | 기기 주소록을 가져온 기록 [2] |

`t7` 의 키에는 상대 ID·namespace·시각·메시지 ID 가 빅엔디언으로 들어 있고, 시각은 Unix 초(int32)입니다 [1]. 이 계정이 보낸 메시지의 작성자 ID 는 로그인한 계정의 사용자 ID 이고, 전달한 메시지에는 원래 작성자와 원래 시각이 따로 남습니다 [1].

`t9` 의 키에는 그룹 ID·고정 값·마지막 메시지 시각·상대 ID 가 들어 있습니다 [2]. 그룹 ID 0 은 기본 목록, 1 은 보관함이고, 고정 값 0 은 고정하지 않은 대화입니다 [2].

`t20` 의 접속 상태는 `v` 값으로 종류를 나눕니다 [2].

| `v` | 뜻 |
|---|---|
| 0 | 정보 없음 |
| 1 | 접속 중 표시가 끝나는 시각이 `t` 에 있음 |
| 2 | 최근 |
| 3 | 지난주 |
| 4 | 지난달 |

같은 행의 `h` 는 숨김 표시이고, `la` 는 앱이 저장한 마지막 활동 값입니다 [2].

`t18` 에는 소개글, 차단 여부(`b`, 사용자만), 공통 그룹 수, 생일, 자동 삭제 타이머 상태, 채널 초대자가 들어 있습니다 [2]. 앱 자체 암호 잠금(passcode)을 켰는지는 계정별 DB 가 아니라 공용 설정 DB(`accounts-metadata/db/db_sqlite`)와 `atomic-state` 에서 알 수 있습니다 [2].

미디어 폴더의 사진은 받은 크기마다 다른 파일 이름으로 따로 저장되고, 이름이 `_partial` 로 끝나는 파일만 있으면 완전한 사본을 받지 못했다는 뜻입니다 [1].

`db_sqlite` 는 일반 SQLite 로 바로 열립니다 [1]. 열리지 않으면 파일 맨 앞 16바이트가 `SQLite format 3` 문자열인지 먼저 확인합니다. 저장 형식 자체는 [SQLite 데이터베이스](../../01-foundations/data-formats/sqlite/index.md) 를 봅니다.

## 증거로서 의미

**증명하는 것.** `t7` 에 메시지 행이 있으면 이 계정이 그 대화에서 해당 메시지를 주고받은 기록이 기기에 남아 있다는 뜻이고, 작성자 ID 가 계정 자신의 ID 이면 이 계정에서 보낸 메시지입니다 [1]. `accounts-metadata/atomic-state` 는 기기에 등록된 계정과 활성 계정을 알려 주고 [2], `t54` 는 기기 주소록의 번호를 텔레그램으로 가져온 기록이라서 텔레그램 사용자가 아닌 번호도 남습니다 [2]. 따라서 `t54` 는 텔레그램 연락처보다 기기 주소록 쪽을 보여 줍니다.

**증명하지 못하는 것.** `t2` 와 `t18` 에 행이 있어도 그 상대와 대화했다는 뜻은 아닙니다. 메시지를 주고받지 않았고 연락처에도 저장하지 않은 상대가 행으로 남을 수 있습니다 [2]. `t12` 의 분류는 앱이 붙인 것이라서 내용을 따로 검사한 결과가 아닙니다 [2]. 접속 상태 `v` 가 2~4 인 값은 정확한 시각이 아니라 "최근", "지난주" 같은 범위입니다 [2]. 클라우드 대화는 다른 기기와 동기화되니, 이 기기에 메시지가 있다는 사실만으로 이 기기에서 입력했다고 말할 수는 없습니다 [3].

보고서에는 "이 계정 데이터에 이 시각의 메시지 행이 있고 작성자 ID 가 계정 자신이다" 처럼 기록으로 확인되는 만큼만 씁니다.

## 시각 해석

`t7` 과 `t9` 키의 시각, 전달 메시지의 원래 시각은 모두 Unix 초이고 UTC 기준입니다 [1][2]. `t7` 의 시각은 메시지 하나의 시각이고, `t9` 의 시각은 그 대화의 마지막 메시지 시각이라서 새 메시지가 오면 바뀝니다 [2]. 전달 메시지는 전달한 시각(키 안의 시각)과 원래 시각이 따로 있으니 둘을 섞지 않습니다 [1]. 시각 값 변환은 [시각 값](../../01-foundations/value-decoding/time-values.md) 에서 다룹니다.

## 함정과 한계

지운 메시지는 흔적이 남지 않을 수 있습니다. 1:1 대화에서는 보낸 메시지와 받은 메시지를 양쪽 모두에서 지울 수 있고, 지운 메시지는 대화에 흔적을 남기지 않습니다 [3]. 자동 삭제 타이머는 비밀 대화의 모든 메시지와 1:1 클라우드 대화의 미디어에 쓸 수 있고, 받는 쪽 화면에 표시된 순간부터 시간이 흘러 끝나면 양쪽 기기에서 사라집니다 [3]. 그래서 메시지가 없다는 사실만으로 대화가 없었다고 판단하지 않고, SQLite 파일의 빈 공간을 [삭제 데이터 복구](../../03-techniques/analysis/data-recovery/index.md) 방법으로 함께 봅니다.

표 역할(`t7` 등)은 앱 공개 소스의 번호로 맞춘 것이라서, 시험 표본보다 새 버전에서는 달라질 수 있습니다. 새 버전 기기에서는 도구 결과를 표 내용과 한 번 맞춰 봅니다([도구 검증](../../03-techniques/reporting/tool-validation.md)).

사진은 받은 크기마다 파일이 따로 있어서 같은 사진이 여러 파일로 보일 수 있고, `_partial` 파일만 있으면 원본 전체가 기기에 없었던 것입니다 [1].

## 직접 분석해 보기

**헥스로 한 번.** 아래는 명세로 만든 예시이고 실제 기기에서 나온 값이 아닙니다. `t7` 키 안에서 시각 자리의 4바이트가 다음과 같다고 합니다.

```
66 00 00 00
```

빅엔디언 int32 로 읽으면 0x66000000 = 1,711,276,032 이고, Unix 초라서 UTC 2024-03-24 10:27:12 입니다. 같은 값을 리틀엔디언으로 잘못 읽으면 102 가 되어 1970년 1월 1일로 나오므로, 1970년 근처 시각이 보이면 바이트 순서부터 의심합니다.

**공개 도구로 한 번.** iLEAPP 의 텔레그램 분석기는 `db_sqlite` 의 키와 값을 풀어 메시지·계정·연락처 보고서를 만듭니다 [1][2]. SQLite 뷰어로 같은 파일을 열어 `t7` 의 행 수와 도구 보고서의 메시지 수를 맞춰 보면, 도구가 행을 빠뜨렸는지 확인할 수 있습니다.
