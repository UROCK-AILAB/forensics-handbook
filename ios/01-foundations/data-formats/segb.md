# SEGB 형식 (SEGB)

## 한 줄 요약

SEGB 는 [바이옴](../../02-artifacts/app-usage/biome/index.md) 기록을 담는 이진 파일 형식이고, 기록 하나하나는 짧은 헤더 뒤에 [프로토콜 버퍼](protobuf.md) 페이로드가 붙은 모양이며, iOS 17 에서 파일 구조가 v2 로 바뀌었습니다.

Apple 은 이 형식의 공식 문서를 내지 않았습니다.

## 이 형식을 쓰는 아티팩트

SEGB 데이터는 예전에 'Biome' 데이터로 불렀고, iOS·macOS 등에서 쓰입니다[1]. SEGB 파일은 바이옴 스트림 폴더 안에서 만나고, 폴더 위치와 스트림 종류는 [바이옴](../../02-artifacts/app-usage/biome/index.md)에서 다룹니다.

아이폰 로컬 백업에는 바이옴과 관련된 설정 plist 가 있습니다. `HomeDomain` 의 `Library/Preferences/com.apple.biomed.plist`, `com.apple.biomesyncd.plist`, `com.apple.lighthouse.dill.BiomeSELFIngestor.plist` 와 `SysSharedContainerDomain-systemgroup.com.apple.safetyalerts` 의 `apsd_biome_collection.plist` 가 그 예입니다. SEGB 파일이 백업에 들어 있는지는 실제 백업으로 확인합니다.

## 버전별 차이

| 항목 | SEGB v1 | SEGB v2 |
|---|---|---|
| iOS 버전 | iOS 15–16[2] | iOS 17 이후[2] |
| 파일 헤더 | 56바이트, 헤더 끝 부분에 ASCII `SEGB`[3] | 32바이트, 맨 앞에 ASCII `SEGB`[2] |
| 기록 헤더 | 32바이트[3] | 8바이트[2] |
| 기록 목록 | 없음(기록을 앞에서부터 차례로 읽음) | 파일 끝의 트레일러가 기록마다 끝 위치·상태·시각을 적음[2] |
| 채움 단위 | 8의 배수[2][3] | 4의 배수[2] |

v1 이 쓰이기 시작한 버전은 자료마다 다르고, 표의 iOS 15–16 은 Cellebrite 글 기준입니다[2]. 페이로드는 두 버전 모두 대개 protobuf 이고, iOS 16(v1) 에서 쓰던 protobuf 구조를 iOS 17(v2) 에서도 그대로 쓰는 스트림이 많습니다[2].

## 구조

### SEGB v1

파일은 56바이트 헤더로 시작하고, `SEGB` 글자는 파일 맨 앞이 아니라 헤더의 끝 부분에 있습니다[3]. 헤더 뒤로 기록이 이어지고, 기록 하나는 32바이트 기록 헤더와 길이가 바뀌는 protobuf 페이로드로 이루어집니다[3].

| 기록 헤더 오프셋 | 크기 | 내용 |
|---|---|---|
| 0 | 4 | protobuf 페이로드 길이, 리틀 엔디언[3] |
| 8 | 8 | 시각 1 — 기록을 파일에 쓴 시각, Mac 절대 시각(2001-01-01 00:00 UTC 기준)[3] |
| 16 | 8 | 시각 2 — 기록을 만든 시각, Mac 절대 시각[3] |

ccl-segb 는 오프셋 8 과 16 의 두 시각을 `timestamp1`·`timestamp2` 로 부릅니다[1]. 표에 없는 나머지 바이트의 뜻을 설명한 공개 자료는 없습니다. 기록 사이는 `0x00` 으로 채우고, 다음 기록 헤더는 8의 배수 오프셋에서 시작합니다[2][3].

### SEGB v2

v2 파일 헤더는 32바이트이고 필드 배치는 아래와 같습니다[2].

| 오프셋 | 크기 | 내용 |
|---|---|---|
| 0 | 4 | 매직 ASCII `SEGB` |
| 4 | 4 | 항목 수, 리틀 엔디언 |
| 8 | 8 | 파일을 만든 시각 |
| 16 | 12 | 내부용 |
| 28 | 4 | 채움 |

파일을 해석하는 데 필요한 필드는 "항목 수" 하나뿐입니다[2].

v2 에서 새로 생긴 트레일러는 파일 뒤쪽에서 앞쪽으로 자라며, 항목마다 16바이트 기록이 하나씩 붙습니다[2].

| 트레일러 기록 오프셋 | 크기 | 내용 |
|---|---|---|
| 0 | 4 | 항목 끝 오프셋, 리틀 엔디언, 파일 헤더 끝을 기준으로 셈 |
| 4 | 4 | 항목 상태, 리틀 엔디언 — 1 = Written, 3 = Deleted |
| 8 | 8 | 항목을 만든 시각 |

항목 자체는 8바이트 항목 헤더와 페이로드로 이루어지고, 페이로드는 트레일러가 적은 항목 끝 오프셋까지입니다[2]. 항목 헤더 8바이트 안의 필드 뜻을 설명한 공개 자료는 없고, v2 에 나오는 시각이 어느 시점을 기준으로 센 값인지도 알려져 있지 않습니다[2]. ccl-segb 는 v2 기록을 `data_start_offset`, `metadata_offset`, `state`, `data`, `metadata.creation`, `metadata.state.name` 필드로 내보냅니다[1].

## 읽는 법

1. 파일 맨 앞 4바이트가 `SEGB` 이면 v2 로, 맨 앞이 아니라 56바이트 헤더 끝 부분에 `SEGB` 가 있으면 v1 로 봅니다. ccl-segb 에는 헤더를 보고 두 버전을 스스로 가려내는 공통 모듈이 있습니다[1].
2. v1 은 헤더 뒤부터 기록 헤더의 앞 4바이트(페이로드 길이)를 읽고, 헤더 32바이트와 페이로드를 건너뛴 뒤 8의 배수 경계로 맞춰 다음 기록으로 갑니다.
3. v2 는 파일 헤더의 항목 수만큼 파일 끝에서부터 16바이트 트레일러 기록을 읽고, 앞 항목의 끝(첫 항목은 헤더 끝)부터 이번 항목 끝 오프셋까지를 항목으로 잘라 냅니다. 이어지는 항목 사이의 채움은 4의 배수 단위입니다[2].
4. 잘라 낸 페이로드를 protobuf 로 풉니다. 스키마 없이 필드 번호로 읽는 법은 [프로토콜 버퍼](protobuf.md)에서 다룹니다.
5. Mac 절대 시각 값은 [시각 값](../value-decoding/time-values.md)의 방법으로 UTC 로 바꿉니다.

아래는 v2 파일 헤더 설명대로 만든 헥스 예시이고, 특정 파일에서 나온 값이 아닙니다. 항목 수 필드만 뜻을 넣고 시각·내부용 필드는 비워 두었습니다.

```
오프셋  바이트                                    뜻
0x00    53 45 47 42                               "SEGB"
0x04    03 00 00 00                               항목 수 3 (리틀 엔디언)
0x08    .. .. .. .. .. .. .. ..                   파일을 만든 시각
0x10    .. .. .. .. .. .. .. .. .. .. .. ..       내부용
0x1C    00 00 00 00                               채움
```

같은 방식으로 만든 트레일러 기록 하나는 이렇습니다.

```
오프셋  바이트                                    뜻
+0x00   40 00 00 00                               항목 끝 오프셋 0x40 (헤더 끝 기준)
+0x04   03 00 00 00                               상태 3 = Deleted
+0x08   .. .. .. .. .. .. .. ..                   항목을 만든 시각
```

## 포렌식에서 중요한 점

v2 트레일러의 상태 값이 3(Deleted)인 항목은 삭제 표시가 된 기록입니다[2]. 그래서 v2 파일에서는 지워진 기록이 있었다는 사실 자체를 트레일러로 셀 수 있습니다. 다만 삭제 표시가 된 항목의 페이로드가 파일에 그대로 남는지는 실제 파일로 확인해야 합니다. 페이로드가 읽히더라도 원래 내용인지 다른 값으로 덮인 것인지 페이로드를 풀어 따로 확인한 뒤에 보고서에 씁니다.

v1 에는 트레일러가 없어서 기록을 앞에서부터 길이 필드로 이어 읽습니다. 길이 필드 하나가 망가지면 그 뒤 기록의 경계를 잃게 되므로, 이런 때는 8의 배수 오프셋마다 기록 헤더 모양이 맞는지 보며 다음 기록을 찾아야 합니다. 이 방법은 위 구조에서 따라 나오는 읽기 요령이고, 검증된 복구 절차는 아닙니다.

v1 의 두 시각과 v2 의 항목 생성 시각은 SEGB 파일에 기록을 쓰고 만든 시각입니다[2][3]. 페이로드 안에도 행위의 시작·끝 같은 시각이 따로 들어 있는 스트림이 있을 수 있어서, 어떤 시각을 쓰는지 보고서에 필드 이름까지 적습니다. 스트림마다 페이로드 안의 시각은 [바이옴](../../02-artifacts/app-usage/biome/index.md)과 [타임라인 작성](../../03-techniques/analysis/timeline/index.md)에서 다룹니다.

## 함정

v1 파일에서 `SEGB` 를 파일 맨 앞에서만 찾으면 v1 파일을 놓칩니다. 매직 위치가 버전마다 다르다는 점을 먼저 확인합니다.

채움 단위가 v1 은 8의 배수, v2 는 4의 배수라서[2], 한 버전의 규칙으로 다른 버전 파일을 읽으면 기록 경계가 어긋납니다.

v2 의 시각은 기준 시점이 알려져 있지 않습니다[2]. v1 과 같은 Mac 절대 시각이라고 짐작해 바로 바꾸지 말고, 같은 기기의 다른 아티팩트 시각과 맞춰 본 뒤에 씁니다.

페이로드는 스키마 없이 필드 번호로만 읽히는 경우가 많습니다. 같은 필드 번호라도 스트림이 다르면 뜻이 다를 수 있으므로, 한 스트림에서 알아낸 뜻을 다른 스트림에 옮겨 쓰지 않습니다.

## 도구

CCL Group 의 파이썬 도구 ccl-segb 가 v1·v2 를 모두 읽습니다[1]. 도구가 내보낸 `state` 와 시각 값은 위 헥스 예시처럼 트레일러 16바이트를 직접 읽어 맞춰 볼 수 있고, 도구 결과를 검증하는 절차는 [도구 검증](../../03-techniques/reporting/tool-validation.md)에서 다룹니다.
