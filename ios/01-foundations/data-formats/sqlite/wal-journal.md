# WAL과 저널 (WAL·Journal)

SQLite 는 쓰는 도중 문제가 생겨도 DB 가 깨지지 않도록 본 파일 곁에 롤백 저널(`-journal`)이나 WAL(`-wal`)을 두고, 이 곁 파일에는 본 파일에 아직 합쳐지지 않은 변경이나 바뀌기 전 페이지가 남습니다. 이 페이지는 두 방식의 구조와, 곁 파일을 증거로 다룰 때 지킬 점을 다룹니다.

## 이 형식을 쓰는 아티팩트

곁 파일은 본 파일과 같은 폴더에 본 파일 이름 뒤에 `-journal`, `-wal`, `-shm` 을 붙인 이름으로 생깁니다. Apple 은 iOS 7 과 OS X Mavericks 부터 Core Data SQLite 저장소의 기본 저널 방식을 WAL 로 바꿨고, 이때부터 Core Data 는 본 저장소 파일을 건드리지 않고 같은 위치의 `-wal` 에 트랜잭션을 덧붙입니다[3]. 본 파일만 복사하면 데이터가 빠지거나 어긋날 수 있으니, 본 파일과 `-wal` 을 한 묶음으로 다룹니다[3].

| 대상 | 기본 저널 방식 | 근거 |
|---|---|---|
| Core Data SQLite 저장소, iOS 7 이후 | WAL | [3] |
| Core Data 를 쓰지 않는 SQLite DB | 앱이 정하고, SQLite 자체 기본값은 DELETE | [4] |
| 로컬 백업의 `Manifest.db` | 최상위에 `Manifest.db-wal`, `Manifest.db-shm` 이 함께 있음 | |

iOS 앱 DB 가 모두 WAL 방식이라고 단정할 수는 없으니, 앱 DB 의 저널 방식과 로컬 백업에 앱 DB 의 `-wal` 이 따로 들어가는지는 검체에서 확인합니다.

## 저널 방식 (journal_mode)

| 값 | 동작 |
|---|---|
| DELETE | 기본값이다. 트랜잭션이 끝날 때 저널 파일을 지우고, 지우는 순간이 커밋이다 |
| TRUNCATE | 저널을 지우지 않고 0바이트로 자른다 |
| PERSIST | 저널 파일은 두고 헤더를 0 으로 덮는다 |
| MEMORY | 저널을 메모리에만 둔다 |
| WAL | 바뀐 페이지를 `-wal` 에 덧붙인다 |
| OFF | 저널을 쓰지 않는다 |

WAL 은 다른 방식과 달리 DB 를 닫았다 다시 열어도 유지되고, 파일 헤더 오프셋 18·19 값이 2 이면 WAL 방식 DB 입니다(헤더 칸은 [페이지와 레코드](b-tree-record.md) 참고).

## 구조

### 롤백 저널 (-journal)

롤백 저널 방식은 페이지를 고치기 전에 원래 페이지 내용을 저널에 옮겨 적습니다. 그래서 저널에는 변경 "후"가 아니라 변경 "전" 내용이 남습니다.

| 오프셋 | 크기 | 뜻 |
|---|---|---|
| 0 | 8 | 매직 `d9 d5 05 f9 20 a1 63 d7` |
| 8 | 4 | 페이지 기록 수(-1 이면 파일 끝까지) |
| 12 | 4 | 체크섬 계산용 난수(nonce) |
| 16 | 4 | 트랜잭션을 시작할 때의 DB 크기(페이지 수) |
| 20 | 4 | 섹터 크기 |
| 24 | 4 | 페이지 크기 |

헤더는 섹터 크기만큼 채우고, 그 뒤에 페이지 기록이 이어집니다. 페이지 기록 하나는 페이지 번호(4바이트), 바뀌기 전 원래 페이지 내용, 체크섬(4바이트) 순서입니다.

커밋은 저널을 지우거나, 0바이트로 자르거나, 헤더를 무효한 값으로 덮는 세 가지 방법으로 끝납니다. 비정상 종료 뒤에 남은 유효한 저널을 hot journal 이라고 하고, 다음에 DB 를 열 때 SQLite 가 이 저널로 변경을 자동으로 되돌립니다.

### WAL (-wal)

WAL 은 SQLite 3.7.0(2010-07-21)부터 있습니다. 원래 DB 파일은 그대로 두고 바뀐 페이지를 WAL 파일 뒤에 덧붙이며, 커밋 기록이 WAL 에 붙는 순간 커밋이 끝납니다. 읽는 쪽은 페이지가 필요하면 먼저 WAL 에 그 페이지가 있는지 보기 때문에, 본 파일만 열면 최신 내용이 빠질 수 있습니다.

WAL 헤더는 32바이트입니다.

| 오프셋 | 크기 | 뜻 |
|---|---|---|
| 0 | 4 | 매직 0x377f0682(체크섬 리틀엔디언) 또는 0x377f0683(체크섬 빅엔디언) |
| 4 | 4 | 형식 버전 3007000 |
| 8 | 4 | 페이지 크기 |
| 12 | 4 | 체크포인트 순번 |
| 16 | 4 | salt-1 |
| 20 | 4 | salt-2 |
| 24 | 4 | 체크섬 1 |
| 28 | 4 | 체크섬 2 |

salt-1 은 체크포인트마다 1 씩 늘고, salt-2 는 체크포인트마다 새 난수로 바뀝니다. 헤더 뒤에는 프레임이 이어지고, 프레임 하나는 24바이트 프레임 헤더와 페이지 내용 한 장으로 되어 있습니다.

| 오프셋 | 크기 | 뜻 |
|---|---|---|
| 0 | 4 | 페이지 번호 |
| 4 | 4 | 커밋 크기(커밋 프레임이면 커밋 뒤 DB 페이지 수, 아니면 0) |
| 8 | 4 | salt-1 |
| 12 | 4 | salt-2 |
| 16 | 4 | 누적 체크섬 1 |
| 20 | 4 | 누적 체크섬 2 |

프레임은 salt 두 개가 WAL 헤더와 같고 누적 체크섬이 맞을 때만 유효합니다. 같은 페이지가 WAL 에 여러 번 들어 있을 수 있어서, SQLite 는 WAL 색인으로 "페이지 P 에 대해 프레임 M 이하 중 가장 큰 프레임"을 찾아 읽습니다.

### WAL 색인 (-shm)

`-shm` 은 여러 연결이 공유 메모리처럼 쓰려고 mmap 하는 일반 파일입니다. 기기의 바이트 순서를 그대로 써서 다른 기기로 옮기면 맞지 않을 수 있고, 충돌 뒤에는 SQLite 가 WAL 에서 다시 만들며, 마지막 연결이 닫힐 때 잘리거나 0 으로 채워집니다.

### 체크포인트

체크포인트는 WAL 의 페이지를 본 파일에 옮겨 적는 작업입니다. 기본 설정에서는 WAL 이 1000페이지 이상이 되면 자동으로 일어나고, 방식은 PASSIVE(기본, 다른 연결을 방해하지 않음), FULL, RESTART, TRUNCATE 가 있습니다. 체크포인트 뒤에도 WAL 은 보통 잘리지 않고 처음부터 다시 덮어쓰이지만, `journal_size_limit` 가 설정되어 있으면 남는 WAL·롤백 저널의 크기를 그 값으로 제한합니다(0 이면 늘 최소 크기로 자르고, 음수면 제한이 없습니다). 마지막 연결이 닫히면 WAL 파일은 보통 자동으로 지워집니다.

## 읽는 법

1. 본 파일, `-wal`, `-shm` 을 함께 복사하고 원본의 해시를 남긴 뒤, 복사본만 엽니다.
2. 본 파일 헤더 오프셋 18·19 로 WAL 방식인지 확인합니다.
3. `-wal` 앞 4바이트가 `37 7f 06 82` 나 `37 7f 06 83` 인지 보고, 헤더의 페이지 크기·salt-1·salt-2 를 적어 둡니다. `-journal` 이라면 앞 8바이트가 `d9 d5 05 f9 20 a1 63 d7` 인지 봅니다. 두 값은 규격에 적힌 매직이고, 특정 기기에서 뽑은 값이 아닙니다.
4. WAL 헤더 뒤부터 (24 + 페이지 크기)바이트씩 끊어 프레임을 읽고, 프레임마다 페이지 번호·커밋 크기·salt 를 표로 만듭니다. salt 가 헤더와 같은 프레임과 다른 프레임을 나눠 둡니다.
5. 관심 있는 페이지의 프레임 내용을 [페이지와 레코드](b-tree-record.md)의 방법으로 풀어, 본 파일의 같은 번호 페이지와 비교합니다.
6. `sqlite3` 셸로 세 파일을 둔 복사본과 본 파일만 둔 복사본을 각각 열어 같은 질의 결과를 비교하면, WAL 에만 있는 변경이 드러납니다. 셸이 연결을 닫을 때 복사본의 WAL 을 본 파일에 합칠 수 있으니, 4·5번의 프레임 분석은 이 단계 전에 따로 떠 둔 복사본으로 합니다.

SQLite 3.22.0 이전은 쓰기 권한 없이 WAL 방식 DB 를 읽지 못했습니다. 3.22.0 부터는 `-shm`·`-wal` 이 이미 있고 읽을 수 있거나, 폴더에 쓰기 권한이 있거나, immutable 로 열면 읽을 수 있습니다.

## 포렌식에서 중요한 점

분석 도구가 WAL 방식 DB 를 쓰기 가능하게 열면 체크포인트가 일어나 WAL 내용이 본 파일에 합쳐지고, WAL 도 바뀔 수 있습니다. 1번 단계에서 원본 대신 복사본을 여는 까닭이 여기에 있습니다.

규격의 유효 조건에 비추어 보면, 체크포인트 뒤 아직 덮어쓰이지 않은 옛 프레임은 salt 가 달라 SQLite 가 무효로 처리하지만 바이트는 파일에 남습니다. 이 해석은 규격의 유효 조건과 WAL 재사용 방식을 합친 것이고, 규격이 직접 서술한 내용은 아닙니다. 옛 프레임이나 롤백 저널의 변경 전 페이지에는 지금은 지운 행이 들어 있을 수 있어서, 이 자리는 [지운 레코드 되살리기](freelist-freeblock.md)의 탐색 범위에 들어갑니다.

마지막 연결이 닫히면 WAL 은 보통 지워지고, `-wal` 이 없다는 사실만으로 누가 곁 파일을 지웠다고 보지 않습니다. 롤백 저널 방식 DB 에서 유효한 저널이 남아 있다면 트랜잭션이 끝나지 못한 흔적이고, 이 저널에는 되돌리기 전의 원래 페이지가 들어 있습니다.

## 함정

`-shm` 은 기기 바이트 순서를 쓰고 WAL 에서 다시 만들 수 있는 파일이라, 다른 컴퓨터에서 열 때 `-shm` 의 색인보다 WAL 프레임 자체를 기준으로 삼습니다. WAL 은 체크포인트 뒤에도 잘리지 않고 덮어쓰여서 `-wal` 크기가 최근 변경량을 뜻한다고 볼 수 없고, 같은 페이지가 여러 프레임에 있으면 어느 커밋 뒤의 모습인지 커밋 프레임을 기준으로 가려야 합니다.

## 도구

`sqlite3` 셸로 PRAGMA 와 질의 결과를 보고(`PRAGMA journal_mode;`), 프레임 단위 해석은 헥스 편집기나 짧은 스크립트로 헤더 표를 따라 읽습니다.
