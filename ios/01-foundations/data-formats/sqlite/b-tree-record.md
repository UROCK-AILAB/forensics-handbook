# 페이지와 레코드 (B-tree·Record)

SQLite 파일은 크기가 같은 페이지로 나뉘고, 표와 색인은 이 페이지들을 b-tree 로 엮어 저장하며, 행 하나는 셀 안에 레코드 형식으로 들어갑니다. 이 페이지는 파일 헤더에서 출발해 셀 안의 값 한 칸까지 내려가는 길을 다룹니다.

## 이 형식을 쓰는 아티팩트

iOS 에서 SQLite 로 된 아티팩트는 모두 이 구조를 따릅니다. 메시지의 `sms.db` 처럼 `ROWID` 칸을 쓰는 일반 DB 도, 메모의 `NoteStore.sqlite` 처럼 Core Data 가 만든 저장소도 바이트로 내려가면 같은 페이지·셀·레코드로 되어 있습니다(확인 범위: iOS 27.0). 파일 형식은 iOS 와 상관없는 SQLite 공통 규격이고, iOS 버전에 따라 달라지는 점은 확인하지 못했습니다. 어떤 DB 가 있는지와 파일 식별법은 [SQLite 데이터베이스](index.md) 허브에 정리했습니다.

## 구조

### 파일 헤더

1번 페이지 맨 앞 100바이트가 파일 헤더입니다. 분석에서 자주 보는 칸은 아래와 같습니다.

| 오프셋 | 크기 | 뜻 | 포렌식에서 보는 점 |
|---|---|---|---|
| 0 | 16 | 매직 문자열 `SQLite format 3\000` | SQLite 파일인지 가른다 |
| 16 | 2 | 페이지 크기 | 512~32768 사이 2의 거듭제곱이고, 값 1은 65536 이다 |
| 18 | 1 | 쓰기 버전 | 1 은 레거시(롤백 저널), 2 는 WAL |
| 19 | 1 | 읽기 버전 | 18 과 같은 뜻 |
| 24 | 4 | 파일 변경 카운터 | 92 의 값과 비교한다 |
| 28 | 4 | DB 크기(페이지 수) | 아래 조건을 만족할 때만 믿는다 |
| 32 | 4 | 첫 freelist 트렁크 페이지 번호 | [지운 레코드 되살리기](freelist-freeblock.md) |
| 36 | 4 | freelist 페이지 총수 | 같은 곳 |
| 40 | 4 | 스키마 쿠키 | |
| 44 | 4 | 스키마 형식 번호(1~4) | serial type 8·9 를 쓸 수 있는지 정한다 |
| 52 | 4 | 가장 큰 루트 b-tree 페이지 | 0 이 아니면 auto vacuum 이나 incremental vacuum DB 다 |
| 56 | 4 | 글자 인코딩 | 1 은 UTF-8, 2 는 UTF-16le, 3 은 UTF-16be |
| 60 | 4 | user_version | |
| 64 | 4 | incremental vacuum 여부 | 0 이 아니면 incremental |
| 68 | 4 | application_id | |
| 72 | 20 | 예약 | 0 으로 채운다 |
| 92 | 4 | version-valid-for | |
| 96 | 4 | 마지막으로 파일을 고친 SQLite 의 버전 번호 | |

오프셋 28 의 DB 크기는 값이 0 이 아니고 변경 카운터(24)와 version-valid-for(92)가 같을 때만 믿습니다. 페이지 크기 기본값은 SQLite 3.12.0 부터 4096 이고, 페이지 크기를 바꾸면 다음 VACUUM 때 적용됩니다. 규격상 페이지 수는 최대 4,294,967,294 개이고, 쓸 수 있는 페이지 크기는 최소 480바이트입니다.

1번 페이지는 언제나 스키마 표(`sqlite_schema`)의 루트 페이지이고, 이 표의 `type`, `name`, `tbl_name`, `rootpage`, `sql` 칸에 모든 표와 색인이 어느 페이지에서 시작하는지 적혀 있습니다.

### 페이지 종류와 페이지 헤더

b-tree 페이지는 페이지 헤더의 첫 바이트로 종류를 가릅니다.

| 첫 바이트 | 종류 | 셀에 든 것 |
|---|---|---|
| 0x02 | 인덱스 내부 페이지 | 왼쪽 자식 페이지 번호와 키 |
| 0x05 | 테이블 내부 페이지 | 왼쪽 자식 페이지 번호와 정수 키 |
| 0x0a | 인덱스 잎 페이지 | 키 |
| 0x0d | 테이블 잎 페이지 | 행 데이터 |

페이지 헤더는 잎 페이지가 8바이트, 내부 페이지가 12바이트이고, 1번 페이지만 100바이트 파일 헤더 다음에 페이지 헤더가 옵니다.

| 오프셋 | 크기 | 뜻 |
|---|---|---|
| 0 | 1 | 페이지 종류 |
| 1 | 2 | 첫 freeblock 위치(없으면 0) |
| 3 | 2 | 셀 개수 |
| 5 | 2 | 셀 내용 영역이 시작하는 위치(0 이면 65536) |
| 7 | 1 | 조각난 빈 바이트 수 |
| 8 | 4 | 가장 오른쪽 자식 페이지 번호(내부 페이지만) |

페이지 헤더 바로 뒤에는 셀 포인터 배열이 옵니다. 2바이트 빅엔디언 오프셋이 셀 개수만큼 키가 작은 순서로 늘어서 있고, 오프셋마다 페이지 안의 셀 하나를 가리킵니다. 셀 포인터 배열 끝과 셀 내용 영역 시작 사이는 할당되지 않은 영역이고, 지운 레코드 조각이 이 자리와 freeblock 에 남는 방식은 [지운 레코드 되살리기](freelist-freeblock.md)에서 다룹니다.

### 셀

행 데이터는 테이블 잎 셀(0x0d)에 들어갑니다. 셀은 페이로드 전체 길이(varint), rowid(varint), 페이로드 앞부분 순서로 이어지고, 페이로드가 페이지에 다 들어가지 않으면 끝에 첫 오버플로 페이지 번호(4바이트)가 붙습니다. 오버플로 페이지는 앞 4바이트가 다음 오버플로 페이지 번호(마지막이면 0)이고, 나머지가 이어지는 내용입니다.

테이블 내부 셀(0x05)은 왼쪽 자식 페이지 번호(4바이트)와 정수 키(varint)만 담아서, 행을 찾아 내려가는 길잡이 구실만 합니다. 인덱스 셀은 rowid 대신 키 페이로드를 담습니다.

### varint

varint 는 1~9바이트 길이의 빅엔디언 정수입니다. 앞 8바이트는 최상위 비트가 "다음 바이트가 이어진다"는 표시라서 바이트마다 7비트씩만 값에 쓰고, 9번째 바이트는 8비트를 모두 씁니다. 예를 들어 `81 00` 은 첫 바이트 최상위 비트가 1 이라 한 바이트 더 읽고, (0x01 × 128) + 0x00 = 128 이 됩니다.

### 레코드

페이로드 안의 레코드는 헤더와 본문으로 나뉩니다. 헤더는 헤더 길이(varint, 자기 자신 포함)로 시작하고 칸마다 serial type(varint)이 하나씩 이어지며, 본문에는 그 순서대로 값이 붙습니다.

| serial type | 값 | 본문 크기 |
|---|---|---|
| 0 | NULL | 0 |
| 1~6 | 부호 있는 정수 | 1, 2, 3, 4, 6, 8바이트 |
| 7 | IEEE 754 64비트 실수 | 8 |
| 8 | 정수 0(스키마 형식 4 이상) | 0 |
| 9 | 정수 1(스키마 형식 4 이상) | 0 |
| 10, 11 | 내부 예약 | |
| 12 이상 짝수 | BLOB | (N−12)/2 |
| 13 이상 홀수 | TEXT(끝에 NUL 없음) | (N−13)/2 |

## 읽는 법

### 헥스로 한 번 따라가기

아래 바이트는 규격을 보고 만든 예시이고, 실제 기기에서 뽑은 값이 아닙니다. 파일 헤더 오프셋 16 에서 `10 00` 을 읽으면 페이지 크기가 4096 이고, 오프셋 18·19 가 `02 02` 이면 WAL 방식 DB 라서 [WAL과 저널](wal-journal.md)의 곁 파일도 함께 봐야 합니다.

테이블 잎 페이지 하나가 다음과 같다고 해 봅니다.

```
페이지 시작:
0d 00 00 00 02 0f f0 00     페이지 헤더: 종류 0x0d, freeblock 없음, 셀 2개,
                            셀 내용 영역 시작 0x0ff0, 조각 0
0f f8 0f f0                 셀 포인터 배열: 0x0ff8, 0x0ff0

페이지 안 0x0ff0:
06 08 03 01 11 07 6f 6b     셀 (rowid 8)
페이지 안 0x0ff8:
06 07 03 01 11 05 68 69     셀 (rowid 7)
```

0x0ff8 의 셀을 풀어 보면, `06` 은 페이로드 길이 6바이트이고 `07` 은 rowid 7 입니다. 이어지는 레코드에서 `03` 은 헤더 길이 3바이트이고, `01` 은 첫 칸이 1바이트 정수라는 뜻이며, `11`(17)은 둘째 칸이 길이 (17−13)/2 = 2 인 TEXT 라는 뜻입니다. 본문 `05` 는 정수 5, `68 69` 는 헤더 오프셋 56 의 인코딩이 UTF-8 이라면 "hi" 가 됩니다. 셀 포인터 배열은 rowid 7 인 셀을 먼저 가리키는데, 배열이 키 순서로 늘어서기 때문입니다.

### 공개 도구로 한 번

SQLite 프로젝트가 배포하는 `sqlite3` 명령줄 셸로 같은 값을 확인할 수 있습니다. 원본이 아닌 복사본을 열고, WAL 방식 DB 라면 `-wal`·`-shm` 도 같은 폴더에 함께 복사합니다.

```
sqlite3 copy.db "PRAGMA page_size;"
sqlite3 copy.db "SELECT type, name, tbl_name, rootpage FROM sqlite_schema;"
```

오래된 `sqlite3` 셸에서 `sqlite_schema` 라는 이름이 통하지 않으면 예전 이름인 `sqlite_master` 로 질의합니다. `rootpage` 값에서 표의 루트 페이지 번호를 얻고, 헥스 편집기로 그 페이지부터 내부 페이지를 따라 잎 페이지까지 내려가면 SQL 결과와 바이트를 한 줄씩 맞춰 볼 수 있습니다.

## 포렌식에서 중요한 점

SQLite 에는 날짜·시각 전용 자료형이 없어서, 시각은 정수나 실수로 저장되고 기준 시점과 단위는 앱마다 다릅니다. Core Data 저장소의 기준은 [Core Data 저장소](core-data.md)에, 여러 기준을 바꾸는 법은 [시각 값](../../value-decoding/time-values.md)에 정리했고, 어느 DB 의 어느 칸이 초인지 나노초인지는 이 페이지에서 확인하지 않았으니 아티팩트 페이지를 따릅니다.

SQL 질의는 셀 포인터 배열이 가리키는 살아 있는 셀만 보여 줍니다. 지운 행의 흔적은 freeblock·할당 안 된 영역·freelist 페이지에 남고, 커밋 전후의 페이지는 곁 파일에 남습니다. SQL 결과만 보고 DB 안의 내용을 다 봤다고 말할 수 없는 이유입니다. iOS 시스템에 들어 있는 SQLite 의 버전과 컴파일 옵션은 확인하지 못했고, 파일마다 헤더 오프셋 96 에서 마지막으로 파일을 고친 SQLite 의 버전 번호만 읽을 수 있습니다.

## 함정

긴 값은 셀 안에 앞부분만 있고 나머지는 오버플로 페이지로 이어져서, 셀만 잘라 읽으면 값이 중간에 끊깁니다. 지운 레코드의 오버플로 페이지가 다른 용도로 다시 쓰였을 때 생기는 문제는 [지운 레코드 되살리기](freelist-freeblock.md)에서 다룹니다. TEXT 값은 끝에 NUL 이 없어서 문자열 검색으로 레코드를 찾을 때 경계를 serial type 이 알려 주는 길이로 잘라야 하고, serial type 8·9 는 스키마 형식 번호가 4 이상일 때만 뜻이 있습니다.

## 도구

`sqlite3` 셸은 SQL 결과와 PRAGMA 값을, 헥스 편집기는 페이지와 셀 바이트를 보여 줍니다. 지운 레코드까지 읽는 도구는 [지운 레코드 되살리기](freelist-freeblock.md)에서 다룹니다.
