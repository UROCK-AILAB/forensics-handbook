# 압축·희소 파일 (Compressed·Sparse)

## 한 줄 요약

NTFS 압축 파일·희소 파일·WOF 압축 파일은 디스크에 놓인 바이트와 파일을 열었을 때 보이는 바이트가 다르므로, 속성 플래그와 데이터 런을 보고 풀어서 읽어야 합니다.

## 세 가지 방식 한눈에 보기

NTFS 에서 파일 내용을 디스크에 그대로 두지 않는 방식은 세 가지입니다.

| 방식 | 알아보는 표시 | 실제 바이트가 있는 곳 | 압축 방식 | 쓸 수 있는 Windows |
|---|---|---|---|---|
| NTFS 압축 (NTFS Compression) | `$DATA` 속성 플래그 0x0001, 압축 단위 값이 0보다 큼 | 이름 없는 `$DATA` 의 클러스터 | LZNT1 | NTFS 초기부터. 클러스터 4 KB 이하 볼륨만 |
| 희소 파일 (Sparse File) | `$DATA` 속성 플래그 0x8000 | 0 이 아닌 구간의 클러스터만 | 없음 | Windows 2000(NTFS 3.0)부터 |
| WOF 압축 (Windows Overlay Filter) | 리파스 포인트 태그 0x80000017 | `WofCompressedData` 스트림 | XPRESS Huffman 4K·8K·16K, LZX | Windows 10부터 |

Windows 8.1 의 WIMBoot 도 WOF 를 쓰지만, 파일 내용을 별도 WIM 파일에 두는 방식이라 이 페이지에서는 다루지 않습니다.

`$STANDARD_INFORMATION` 의 파일 특성 값에도 표시가 남는데, 희소는 0x00000200, 리파스 포인트는 0x00000400, 압축은 0x00000800 입니다. 두 시각 속성의 전체 구조는 [두 벌의 시각 ($STANDARD_INFORMATION·$FILE_NAME)](standard-information-file-name.md) 에 있습니다.

## 이 형식을 쓰는 아티팩트

- **USN 변경 저널** — `$UsnJrnl:$J` 는 희소 스트림입니다. 오래된 레코드가 있던 앞부분이 비어 있습니다. [USN 변경 저널 ($UsnJrnl)](../../../02-artifacts/filesystem/usnjrnl.md) 을 봅니다.
- **사용자가 압축한 파일·폴더** — 탐색기의 압축 설정이나 `compact /c` 로 만듭니다. 폴더에 압축 표시를 하면 그 뒤에 그 폴더에 새로 만드는 파일이 압축됩니다.
- **Windows 10 이후 시스템 실행 파일** — Compact OS 를 켜면 OS 실행 파일이 WOF 로 압축됩니다. `compact /EXE` 로 사용자가 아무 파일이나 WOF 로 압축할 수도 있습니다.
- **앱이 만든 큰 파일** — 대부분이 0 인 데이터베이스 파일 등을 앱이 희소 파일로 만들기도 합니다.

## 구조

### 속성 헤더에서 볼 곳

속성 헤더 전체와 데이터 런 인코딩은 [MFT 레코드와 속성](file-record-attribute.md) 과 [데이터 런과 상주·비상주 데이터](data-run-resident-non-resident.md) 에 있고, 여기서는 압축·희소와 관련된 필드만 봅니다. 오프셋은 속성 시작 기준입니다.

| 오프셋 | 크기 | 필드 | 뜻 |
|---|---|---|---|
| 0x0C | 2 | 속성 플래그 | 0x0001 압축, 0x4000 암호화, 0x8000 희소 |
| 0x20 | 2 | 데이터 런 오프셋 | 런 목록이 시작하는 위치 |
| 0x22 | 2 | 압축 단위 크기 | 2의 거듭제곱 지수입니다. 4면 2⁴ = 16 클러스터입니다. 0이면 압축 단위가 없습니다 |
| 0x28 | 8 | 할당 크기 (Allocated Size) | |
| 0x30 | 8 | 데이터 크기 (Data Size) | 파일을 열었을 때 보이는 크기입니다 |
| 0x38 | 8 | 유효 데이터 크기 (Valid Data Length) | |
| 0x40 | 8 | 전체 할당 크기 (Total Allocated Size) | 압축 단위 값이 0보다 클 때만 있습니다. 실제로 잡힌 클러스터 양입니다 |

암호화 플래그(0x4000)는 [EFS 암호화 파일](../../../03-techniques/analysis/encrypted-evidence/encrypting-file-system.md) 에서 다룹니다.

### 압축 단위와 데이터 런

NTFS 압축은 파일을 압축 단위 (Compression Unit) 로 잘라서 따로따로 압축합니다. 압축 단위는 보통 16 클러스터이므로 클러스터가 4 KB 면 64 KB 입니다. 클러스터가 4 KB 보다 큰 볼륨에서는 NTFS 압축을 쓸 수 없지만, 희소 파일은 클러스터 크기와 상관없이 쓸 수 있습니다.

압축 단위 하나는 세 가지 중 하나로 저장됩니다.

| 저장 모양 | 데이터 런에서 보이는 모습 | 읽는 법 |
|---|---|---|
| 압축됨 | 16 개보다 적은 실제 클러스터 + 나머지를 채우는 빈 구간 | 실제 클러스터를 LZNT1 로 풉니다 |
| 압축 안 됨 | 실제 클러스터 16 개 | 그대로 읽습니다 |
| 전부 0 | 빈 구간 16 개 | 0 으로 채웁니다 |

압축해서 한 클러스터 이상 줄지 않으면 NTFS 는 그 단위를 압축하지 않고 씁니다. 빈 구간 (Sparse Run) 은 위치 칸이 없는 데이터 런이며, 런 헤더 바이트의 위쪽 4비트가 0 이면 빈 구간입니다. 빈 구간에는 디스크 클러스터가 없고, 읽으면 0 이 나옵니다.

> 그림 자리: 가상 클러스터 번호(VCN) 0x00\~0x2F 를 16 개씩 세 칸으로 나누고, 첫 칸은 실제 5 개 + 빈 구간 11 개, 둘째 칸은 실제 16 개, 셋째 칸은 빈 구간 16 개로 칠한 막대

압축된 단위의 실제 클러스터에는 LZNT1 조각이 이어져 있고, 조각 하나는 원본을 최대 4 KB 까지 담습니다. 조각은 2바이트 헤더로 시작하며, 헤더의 15번 비트는 압축 여부, 12\~14번 비트는 서명 값 3, 0\~11번 비트는 "조각 크기 − 3" 입니다. 헤더 뒤에는 플래그 바이트 1개와 원소 8개가 되풀이됩니다.
LZNT1 의 자세한 풀이법은 [윈도 압축 형식 (LZNT1·Xpress·Xpress Huffman)](../../value-decoding/lznt1-xpress-xpress-huffman.md) 에 있습니다.

### 희소 파일

희소 파일은 0 이 아닌 구간에만 클러스터를 잡고, 0 인 구간은 빈 구간 런으로만 남습니다. 그래서 희소 파일의 데이터 크기는 볼륨 크기보다 클 수도 있습니다. Microsoft NTDebugging 블로그의 2008년 글에 따르면, 희소 파일에 바이트를 쓰면 그 바이트가 든 압축 단위 전체에 클러스터를 잡고 나머지를 0 으로 채웁니다.

### WOF 압축 파일

WOF 압축 파일은 속성 세 개로 이루어집니다.

| 속성 | 내용 |
|---|---|
| 이름 없는 `$DATA` | 희소입니다. 전부 0 이고, 데이터 크기는 원래 파일 크기입니다 |
| `$REPARSE_POINT` | 태그 0x80000017. 뒤따르는 16바이트는 버전(1)·공급자(2)·파일 정보 버전(1)·압축 방식 순의 4바이트 값입니다 |
| `$DATA` 스트림 `WofCompressedData` | 앞에 조각 위치 표, 뒤에 압축 조각들이 있습니다 |

압축 방식 값은 다음과 같습니다.

| 값 | 압축 방식 | `compact /EXE` 이름 |
|---|---|---|
| 0 | XPRESS Huffman, 4 KB 조각 | XPRESS4K |
| 1 | LZX, 32 KB 조각 | LZX |
| 2 | XPRESS Huffman, 8 KB 조각 | XPRESS8K |
| 3 | XPRESS Huffman, 16 KB 조각 | XPRESS16K |

조각 위치 표는 32비트 또는 64비트 값의 배열이고, 첫 조각의 위치는 표 바로 뒤라서 표에 적지 않습니다. 조각 크기가 원래 크기와 같으면 그 조각은 압축하지 않은 그대로입니다. 리파스 포인트 자체는 [링크와 리파스 포인트](hard-link-junction-reparse-point.md) 에서, 이름 있는 스트림은 [대체 데이터 스트림 (ADS)](ads.md) 에서 다룹니다.

WOF 압축 파일을 쓰기 모드로 열면 파일이 압축 안 된 상태로 돌아갑니다.

## 읽는 법

### 순서

1. `$DATA` 속성 헤더의 플래그(0x0C)와 압축 단위 크기(0x22)를 봅니다.
2. 0x20 의 데이터 런 오프셋을 따라가 런 목록을 VCN 순서로 펼칩니다.
3. 속성이 여러 MFT 레코드에 나뉘어 있으면 조각을 모두 모아 VCN 순으로 잇습니다.
4. VCN 을 16 개씩 끊어 압축 단위마다 위 표의 세 모양 중 어느 것인지 가립니다.
5. 압축된 단위는 LZNT1 로 풀고, 빈 단위는 0 으로 채웁니다.
6. 이어 붙인 결과를 데이터 크기(0x30)에서 자릅니다.
7. 리파스 포인트 태그가 0x80000017 이면 이름 없는 `$DATA` 대신 `WofCompressedData` 를 풉니다.

### 헥스로 따라가기

아래 속성 헤더와 런 목록은 **명세로 만든 예시**이고, 클러스터 크기는 4 KB 로 잡았습니다.

```
오프셋 0x0C: 01 00                     ← 플래그 0x0001 (압축)
오프셋 0x22: 04 00                     ← 압축 단위 2^4 = 16 클러스터
오프셋 0x30: 00 00 03 00 00 00 00 00   ← 데이터 크기 0x30000 (196,608 바이트)
오프셋 0x40: 00 50 01 00 00 00 00 00   ← 전체 할당 크기 0x15000 (21 클러스터)
런 목록:     21 05 00 10  01 0B  11 10 05  01 10  00
```

| 바이트 | 헤더 풀이 | 길이 | 위치 (LCN) | VCN | 뜻 |
|---|---|---|---|---|---|
| `21 05 00 10` | 길이 1바이트, 위치 2바이트 | 5 | 0x1000 | 0x00\~0x04 | 1번째 단위의 압축 데이터 |
| `01 0B` | 길이 1바이트, 위치 없음 | 11 | 없음 | 0x05\~0x0F | 1번째 단위를 16 칸으로 채우는 빈 구간 |
| `11 10 05` | 길이 1바이트, 위치 1바이트 | 16 | 0x1000 + 5 = 0x1005 | 0x10\~0x1F | 2번째 단위, 압축 안 됨 |
| `01 10` | 길이 1바이트, 위치 없음 | 16 | 없음 | 0x20\~0x2F | 3번째 단위, 전부 0 |
| `00` | 끝 | | | | |

빈 구간은 다음 런의 상대 위치 계산에 끼지 않으므로, 세 번째 런의 +5 는 첫 런의 0x1000 에서 셉니다. 실제 클러스터는 5 + 16 = 21 개이고, 전체 할당 크기(0x15000)가 데이터 크기(0x30000)보다 작은 것도 이 때문입니다.

LCN 0x1000 의 첫머리가 아래와 같다고 해 봅니다. 이 바이트는 Microsoft 명세 [MS-XCA] 의 LZNT1 예시를 그대로 가져온 것입니다.

```
38 B0 88 46 23 20 00 20 47 20 41 00 10 ...
```

- `38 B0` 은 16비트 값 0xB038 입니다. 15번 비트가 1 이라 압축 조각입니다. 서명은 3 이고, 조각 크기는 56 + 3 = 59 바이트입니다.
- `88` 은 플래그 바이트입니다. 0\~2번 비트가 0 이라 다음 3바이트는 글자 그대로입니다.
- `46 23 20` 은 "F# " 입니다.
- `00 20` 은 앞의 3바이트를 다시 복사하라는 복사 값입니다.

원문은 "F# F# G A A ..." 로 시작하는데, 디스크에는 "F# " 다음에 복사 값이 끼어 있어 "F# F# G" 라는 문자열이 이어져 있지 않습니다.

## 포렌식에서 중요한 점

### 디스크 전체 키워드 검색과 카빙에 잘 걸리지 않습니다

압축된 단위의 원문은 디스크에 그대로 있지 않아서, 디스크를 바이트 그대로 훑는 [키워드 검색](../../../03-techniques/analysis/content-search/keyword-search.md) 은 압축된 단위의 내용을 놓칩니다. 압축 안 된 단위는 그대로 있으므로 한 파일에서 일부만 걸리기도 합니다. 파일 시스템을 해석해 압축을 푼 뒤 검색하면 이 문제가 없습니다.

명세를 따르면 LZNT1 조각의 첫 원소는 앞에 복사해 올 데이터가 없기 때문에 반드시 글자 그대로입니다. 그래서 파일 앞머리의 시그니처는 클러스터 시작이 아니라 조각 헤더 뒤에 보이는 경우가 많습니다. 압축 조각이면 3바이트 뒤(헤더 2 + 플래그 1), 압축 안 한 조각이면 2바이트 뒤입니다.
클러스터 시작만 보는 [파일 카빙](../../../03-techniques/analysis/data-recovery/file-carving.md) 은 이런 파일을 놓칩니다.

### 지운 압축 파일은 MFT 레코드가 있어야 제대로 풉니다

MFT 레코드가 남아 있으면 런 목록으로 압축 단위 경계를 알 수 있지만, 레코드가 덮어써졌으면 경계를 알 수 없습니다. 이때는 조각 헤더의 서명 값 3 을 단서로 조각을 찾고, 단위 경계는 추정해야 합니다. 추정으로 복원한 내용은 보고서에 추정이라고 밝힙니다. 파일 시스템 정보로 되살리는 방법은 [파일시스템 기반 복구](../../../03-techniques/analysis/data-recovery/undelete-ntfs-fat.md) 에 있습니다.

### 빈 구간에는 되살릴 것이 없습니다

빈 구간에는 클러스터가 없지만, 그 구간에 예전에 있던 데이터는 해제된 클러스터, 곧 비할당 영역에 남아 있을 수 있습니다. `$UsnJrnl:$J` 의 앞부분에서 풀려난 클러스터에도 옛 USN 레코드가 남아 있을 수 있습니다. 이런 레코드는 [레코드 카빙](../../../03-techniques/analysis/data-recovery/record-carving.md) 으로 찾습니다.

### 뽑는 방식에 따라 크기와 해시가 다릅니다

현장 관찰로는 `$UsnJrnl:$J` 를 뽑을 때 빈 구간을 0 으로 채우면 수 GB 의 논리 크기가 되고, 빈 구간을 건너뛰면 실제 데이터만 남습니다. 두 결과는 크기와 해시가 다릅니다. 일반 파일도 희소 표시가 있으면, 빈 구간을 건너뛰고 뽑을 때 뒤쪽 내용이 앞으로 밀려 파일 안의 오프셋이 원래와 달라집니다. 그래서 뽑은 방식(0 채움 또는 건너뜀)과 크기·해시를 함께 기록합니다.
해시 기록 방법은 [해시로 무결성 검증](../../../03-techniques/process-acquisition/evidence-acquisition/hash-verification.md) 을 봅니다.

희소 파일을 다른 볼륨으로 보통 방식으로 복사하면 0 구간이 실제 0 바이트로 채워집니다.
Microsoft NTDebugging 글은 볼륨보다 큰 희소 파일을 `COPY` 로 복사하다 실패한 예를 보여 줍니다.
[선별 수집](../../../03-techniques/process-acquisition/evidence-acquisition/triage-collection.md) 에서 희소 파일을 받을 때 이 점을 미리 봅니다.

### WOF 를 모르는 도구는 0 을 봅니다

WOF 압축 파일의 이름 없는 `$DATA` 는 전부 0 이라서, WOF 를 모르는 도구가 이것만 읽으면 다음 일이 생깁니다.

- 파일 해시가 0 뭉치의 해시가 됩니다. 그래서 알려진 파일 [해시셋 대조](../../../03-techniques/analysis/hash-set-fuzzy-hash.md) 에서 빠집니다.
- 키워드 검색과 [파일 형식 식별](../../../03-techniques/analysis/content-search/file-signature.md) 이 내용을 못 봅니다.

Khatri 의 2016년 글 시점에는 널리 쓰는 포렌식 도구 여러 개가 WOF 를 자동으로 풀지 못했습니다. 지금 쓰는 도구가 WOF 를 푸는지는 직접 확인해야 합니다. `WofCompressedData` 스트림이 있는 파일 목록을 먼저 뽑아 두면 영향 범위를 알 수 있습니다.

### 압축 표시가 증명하는 것과 증명하지 못하는 것

- **증명하는 것**: 수집 시점에 그 파일이 NTFS 압축·희소·WOF 상태였다는 것입니다.
- **증명하지 못하는 것**: 누가 언제 압축했는지입니다. 압축된 폴더에 만들어진 파일은 저절로 압축됩니다. Compact OS 상태에서는 OS 실행 파일이 사용자 조작 없이 압축됩니다.
- 압축 상태가 바뀐 시점은 [USN 변경 저널](../../../02-artifacts/filesystem/usnjrnl.md) 의 이유 값 `COMPRESSION_CHANGE` 로 찾아볼 수 있습니다. 저널이 그 시점까지 남아 있을 때만 가능합니다.

## 함정

- **런 하나에 여러 단위가 섞입니다.** 압축 안 된 단위 둘과 압축된 단위 하나가 실제 클러스터 런 하나로 이어질 수 있습니다. 런 단위가 아니라 VCN 16 개 단위로 판단해야 합니다.
- **0x40 필드는 늘 있지 않습니다.** 압축 단위 값이 0 이면 0x40 에 다른 값이 올 수 있습니다. 런 목록 위치는 늘 0x20 의 오프셋 값으로 찾습니다.
- **크기 필드마다 뜻이 다릅니다.** 데이터 크기를 더해서 디스크 사용량을 계산하면 압축·희소 파일에서 틀립니다. 실제 사용량은 전체 할당 크기나 실제 클러스터 수로 봅니다.
- **화면 표시가 실제 상태와 다릅니다.** Microsoft NTDebugging 글에 따르면 탐색기 속성 창은 희소 비트를 보지 않아 아무 표시도 하지 않고, `compact` 는 희소 파일을 압축된 파일로 보여 줍니다. 화면 표시 대신 속성 플래그를 봅니다.

## 도구

- **Windows 기본 명령**: `compact` 는 파일·폴더의 압축 상태를, `fsutil sparse` 는 희소 표시와 할당 구간을 보여 줍니다. 둘 다 살아 있는 볼륨에서 씁니다.
- **The Sleuth Kit**: 이미지에서 속성과 클러스터 목록을 보고 파일 내용을 뽑을 수 있습니다. WOF 를 푸는지는 쓰는 판에서 확인합니다.
- **libfsntfs**: NTFS 읽기 라이브러리입니다. 함께 있는 형식 문서가 압축·희소·WOF 구조를 설명합니다.
- **헥스 편집기**: 위의 헥스 따라가기를 직접 해 볼 때 씁니다.

도구 결과는 시험용 가상 머신에서 확인합니다. NTFS 압축·희소·WOF 파일을 하나씩 만들고, 살아 있는 시스템에서 구한 해시와 도구가 뽑은 파일의 해시를 비교합니다. 방법은 [도구 결과 교차 검증](../../../03-techniques/reporting/tool-validation.md) 에 있습니다.
