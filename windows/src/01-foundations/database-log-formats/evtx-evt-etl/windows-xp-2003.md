# 구형 EVT 형식 (Windows XP·2003)

## 한 줄 요약

EVT 는 Windows Vista 전에 쓰던 이벤트 로그 형식으로, 48바이트 헤더 뒤에 레코드가 원형 버퍼처럼 이어집니다. 파일 끝 레코드 (EOF Record) 에는 헤더와 같은 위치 정보가 한 벌 더 들어 있고, 시각은 32비트 유닉스 시각(UTC)입니다. 레코드 본문은 XML 이 아니라 고정 칸과 문자열입니다.

이 페이지는 [이벤트 로그 형식 (EVTX·EVT·ETL)](index.md) 의 하위 주제입니다. Vista 이후 형식은 [EVTX 파일 구조 (File Header·Chunk·Record)](file-header-chunk-record.md) 에서 다룹니다.

## 이 형식을 쓰는 아티팩트

libevt 명세는 Windows NT 4·2000·XP·Server 2003 의 파일로 이 형식을 시험했습니다. Vista 에서 EVTX 로 바뀌면서 이 형식은 쓰지 않게 됐습니다.

| Windows | 위치 (libevt 명세) |
|---|---|
| NT 4 | `C:\WINNT\System32\config` |
| 2000 이후 | `C:\Windows\System32\config` |

Windows 2000 의 SystemRoot 값은 `C:\WINNT` 로도 적혀 있으므로([공급자와 메시지 파일](provider-message-table.md) 의 표), 실제 폴더는 이미지의 SystemRoot 값으로 확인합니다.

기본 파일 이름은 AppEvent.Evt(응용 프로그램), SecEvent.Evt(보안), SysEvent.Evt(시스템) 입니다. 그 밖에 DFSR.Evt·DNSEvent.Evt·FwdEvents.Evt·HrwEvents.Evt·Internet.Evt·NTDS.Evt·NtFrs.Evt·ODiag.Evt·WindowsPowerShell.evt 등이 있습니다. 도메인 컨트롤러에는 Directory service 로그와 File Replication service 로그가, DNS 서버에는 DNS server 로그가 더 있습니다.

이 위키의 확인 PC(Windows 11)에는 EVT 파일이 없어 직접 보지 못했으며, 이 페이지의 값은 모두 명세와 Microsoft 문서 기준입니다.

## 구조

> 그림 자리: wrap 하지 않은 파일(헤더 → 가장 오래된 레코드 … 가장 새 레코드 → EOF 레코드)과 wrap 한 파일(헤더 → 쪼개진 레코드 뒷부분 → … → EOF 레코드 → 빈 틈 → 가장 오래된 레코드 … → 쪼개진 레코드 앞부분)을 나란히 그린 그림

### 파일 전체 배치

파일은 파일 헤더, 이벤트 레코드, 파일 끝 레코드, 뒤쪽 빈 값 순서로 놓이고, 순환하면 이 순서가 바뀝니다(아래 "순환 동작"). 정수는 리틀 엔디언, 시각은 UTC 의 32비트 POSIX(유닉스) 시각, 문자열은 UTF-16LE 입니다.

### 파일 헤더 (ELF_LOGFILE_HEADER, 48바이트)

| 오프셋 | 크기 | 내용 |
|---|---|---|
| 0 | 4 | 헤더 크기. 값 48 |
| 4 | 4 | 서명 `LfLe` (0x654c664c) |
| 8 | 4 | 주 버전. 값 1 |
| 12 | 4 | 부 버전. 값 1 |
| 16 | 4 | 가장 오래된 레코드의 오프셋 |
| 20 | 4 | 파일 끝 레코드의 오프셋 |
| 24 | 4 | 가장 새 레코드 번호 |
| 28 | 4 | 가장 오래된 레코드 번호 |
| 32 | 4 | 최대 파일 크기 |
| 36 | 4 | 파일 플래그 |
| 40 | 4 | 알 수 없음. Retention 으로 추정합니다 |
| 44 | 4 | 크기 사본. 값 48 |

| 플래그 | 이름 | 뜻 |
|---|---|---|
| `0x1` | DIRTY | 정상적으로 닫히지 않았습니다 |
| `0x2` | WRAP | 한 바퀴 돌았습니다 |
| `0x4` | LOGFULL_WRITTEN | 공간이 모자라 마지막 쓰기가 실패했습니다 |
| `0x8` | ARCHIVE_SET | 보관해야 하는 로그입니다 |

헤더와 파일 끝 레코드는 로그를 만들 때 생깁니다. 이벤트를 쓸 때마다 두 곳의 값이 바뀝니다.

### 이벤트 레코드 (EVENTLOGRECORD)

| 오프셋 | 크기 | 내용 |
|---|---|---|
| 0 | 4 | 레코드 크기 |
| 4 | 4 | 서명 `LfLe` |
| 8 | 4 | 레코드 번호 |
| 12 | 4 | 생성 시각. 레코드가 만들어진 UTC 시각(유닉스 초) |
| 16 | 4 | 기록 시각. 파일에 쓰인 UTC 시각(유닉스 초) |
| 20 | 4 | 이벤트 식별자 |
| 24 | 2 | 이벤트 종류 |
| 26 | 2 | 문자열 개수 |
| 28 | 2 | 분류 |
| 30 | 2 | 이벤트 플래그. 보통 0 |
| 32 | 4 | closing record number. 밖에서 고치지 않았으면 0 |
| 36 | 4 | 문자열 오프셋. 2의 배수 |
| 40 | 4 | 사용자 SID 크기 |
| 44 | 4 | 사용자 SID 오프셋 |
| 48 | 4 | 데이터 크기 |
| 52 | 4 | 데이터 오프셋 |
| 56 | 가변 | 원본 이름, 컴퓨터 이름, 사용자 SID, 이벤트 문자열 배열, 이벤트 데이터, 4바이트 맞춤 채움, 크기 사본(4) 순서 |

고정 부분은 0x38(56)바이트입니다. 원본 이름은 끝 문자가 붙은 UTF-16 문자열이고 그 뒤에 컴퓨터 이름이 옵니다. 문자열·SID·데이터 오프셋은 레코드 안의 위치이며, 레코드 범위를 넘는 오프셋은 무시해야 합니다.
- SID 를 푸는 법은 [윈도 식별자 형식](../../value-decoding/sid-guid-clsid-known-folder-id.md) 에 있습니다.

| 이벤트 종류 | 뜻 |
|---|---|
| `0x1` | 오류 |
| `0x2` | 경고 |
| `0x4` | 정보 |
| `0x8` | 감사 성공 |
| `0x10` | 감사 실패 |

- 이벤트 식별자의 비트 구조는 EVTX 와 같습니다. 표는 [EVTX 파일 구조](file-header-chunk-record.md) 의 "이벤트 식별자와 수준" 에 있습니다.
- 이 형식에서는 이벤트 식별자가 곧 메시지 식별자입니다. 설명 문장을 만드는 법은 [공급자와 메시지 파일](provider-message-table.md) 에 있습니다.

### 파일 끝 레코드 (ELF_EOF_RECORD, 40바이트)

| 오프셋 | 크기 | 내용 |
|---|---|---|
| 0 | 4 | 크기. 값 0x28 |
| 4 | 16 | 서명 0x11111111·0x22222222·0x33333333·0x44444444 |
| 20 | 4 | 가장 오래된 레코드의 오프셋 |
| 24 | 4 | 파일 끝 레코드의 오프셋 |
| 28 | 4 | 가장 새 레코드 번호 |
| 32 | 4 | 가장 오래된 레코드 번호 |
| 36 | 4 | 크기 사본. 값 0x28 |

### 순환 동작 (Wrap)

아래는 Microsoft 문서의 설명입니다.

쓰는 방식은 두 가지입니다. wrap 하지 않는 로그는 헤더 바로 뒤가 가장 오래된 레코드이고, 새 레코드는 파일 끝 레코드 앞에 붙습니다. wrap 하는 로그는 파일을 원형 버퍼로 쓰며, Microsoft 문서의 예에서는 1\~101번 자리가 덮여 가장 오래된 레코드가 102번이 됐습니다.

로그를 새로 만들거나 지운 뒤에는 wrap 하지 않는 상태일 수 있고, 크기 한도(MaxSize 또는 시스템 자원)에 닿으면 wrap 할 수 있습니다. wrap 여부는 Retention 값이 정합니다. wrap 하면 새 레코드가 가장 오래된 레코드를 덮어서 가장 오래된 레코드와 가장 새 레코드의 위치가 바뀝니다.

새 레코드 자리를 만들 때는 오래된 레코드를 통째로 몇 개 지웁니다. 그래서 파일 끝 레코드와 가장 오래된 레코드 사이에 빈 틈이 생깁니다. 예를 들어 100바이트 레코드를 쓰려고 75바이트 레코드 두 개를 지우면 50바이트가 남는데, Microsoft 문서는 이 남은 자리를 다음 레코드를 쓸 때 쓴다고 적습니다.

파일 끝에 자리가 모자라면 레코드를 둘로 나누어 앞부분은 파일 끝에, 나머지는 헤더 바로 뒤에 씁니다. 파일 끝의 남은 자리가 고정 부분(0x38바이트)보다 작으면 레코드 전체를 헤더 바로 뒤에 쓰고, 이때 파일 끝의 빈 바이트는 0x00000027 로 채웁니다.

## 읽는 법

1. 원본의 해시를 구하고 사본에서 작업합니다.
2. 헤더의 크기 48, 서명 `LfLe`, 버전 1.1, 크기 사본 48 을 확인합니다.
3. 플래그를 봅니다. DIRTY 면 헤더의 오프셋을 그대로 믿지 않습니다.
4. 가장 오래된 레코드의 오프셋에서 읽기 시작합니다. 레코드마다 서명과 크기를 확인하고, 크기만큼 건너 다음 레코드로 갑니다.
5. 레코드 끝의 크기 사본이 앞의 크기와 같은지 확인합니다.
6. 파일 끝에 닿으면 헤더 바로 뒤(오프셋 48)로 돌아가 이어 읽습니다. 나뉜 레코드는 두 조각을 이어 붙입니다. 0x00000027 로 채운 바이트는 건너뜁니다.
7. 파일 끝 레코드(서명 0x11111111 …)에 닿으면 멈춥니다. 파일 끝 레코드의 네 값을 헤더와 비교합니다.
8. 헤더 오프셋이 틀린 dirty 파일은 헤더가 말한 EOF 오프셋 뒤에서 파일 끝 레코드를 찾아 읽습니다.
9. 문자열·SID·데이터는 레코드 안 오프셋으로 읽습니다. 레코드 범위를 넘는 오프셋은 무시합니다.

### 헥스로 한 번 따라가기

아래는 명세로 만든 예시입니다. 실제 검체에서 떠낸 바이트가 아닙니다. 이벤트 식별자 3260 은 명세의 예를 따랐습니다. 이벤트 종류, 시각, 오프셋은 설명을 위해 정한 값입니다. `??` 는 이 설명에 쓰지 않는 바이트입니다.

**파일 헤더**

```
오프셋    00 01 02 03 04 05 06 07  08 09 0A 0B 0C 0D 0E 0F
00000000  30 00 00 00 4C 66 4C 65  01 00 00 00 01 00 00 00
00000010  30 00 00 00 00 02 00 00  ?? ?? ?? ?? 01 00 00 00
00000020  ?? ?? ?? ?? 01 00 00 00  ?? ?? ?? ?? 30 00 00 00
```

- 0x00 은 헤더 크기 48 입니다. 0x04 `4C 66 4C 65` 는 서명 `LfLe` 입니다.
- 0x08 과 0x0C 는 버전 1.1 입니다.
- 0x10 은 가장 오래된 레코드의 오프셋 0x30 입니다. 헤더 바로 뒤이므로 아직 wrap 하지 않은 모양입니다.
- 0x14 는 파일 끝 레코드의 오프셋 0x200 입니다.
- 0x1C 는 가장 오래된 레코드 번호 1 입니다.
- 0x24 는 플래그 0x1(DIRTY) 입니다. 헤더 값을 파일 끝 레코드와 맞춰 봐야 합니다.
- 0x2C 는 크기 사본 48 입니다.

**첫 레코드 (오프셋 0x30)**

```
오프셋    00 01 02 03 04 05 06 07  08 09 0A 0B 0C 0D 0E 0F
00000030  ?? ?? ?? ?? 4C 66 4C 65  01 00 00 00 80 07 5C 49
00000040  80 07 5C 49 BC 0C 00 00  04 00 02 00 00 00 00 00
00000050  00 00 00 00 ?? ?? ?? ??  00 00 00 00 ?? ?? ?? ??
00000060  00 00 00 00 ?? ?? ?? ??  ...
```

- 0x30 은 레코드 크기, 0x34 는 서명 `LfLe`, 0x38 은 레코드 번호 1 입니다.
- 0x3C 는 생성 시각, 0x40 은 기록 시각입니다. `80 07 5C 49` 는 0x495C0780 = 1,230,768,000 초이고, 2009-01-01 00:00:00 UTC 입니다.
- 0x44 `BC 0C 00 00` 은 이벤트 식별자 3260(0x00000cbc) 입니다.
- 0x48 `04 00` 은 이벤트 종류 0x4(정보) 입니다.
- 0x4A `02 00` 은 문자열 2개입니다. 명세 예의 문장 "…joined to %1 '%2'." 의 자리 표시자 수와 맞습니다.
- 0x50 은 closing record number 0 입니다.
- 0x58 은 SID 크기 0 입니다. 사용자 SID 가 없는 레코드입니다.
- 0x60 은 데이터 크기 0 입니다. 이때는 데이터 오프셋이 레코드 크기를 넘어도 무시해도 됩니다.
- 0x68 부터 원본 이름이 시작합니다.

**파일 끝 레코드 (오프셋 0x200)**

```
오프셋    00 01 02 03 04 05 06 07  08 09 0A 0B 0C 0D 0E 0F
00000200  28 00 00 00 11 11 11 11  22 22 22 22 33 33 33 33
00000210  44 44 44 44 30 00 00 00  00 02 00 00 ?? ?? ?? ??
00000220  01 00 00 00 28 00 00 00
```

- 0x200 은 크기 0x28 입니다. 0x204 부터 16바이트가 서명입니다.
- 0x214 의 가장 오래된 레코드 오프셋 0x30 과 0x218 의 파일 끝 레코드 오프셋 0x200 이 헤더의 0x10·0x14 값과 같습니다.
- 헤더가 DIRTY 여도 두 곳의 값이 같으므로 이 예에서는 헤더 오프셋을 쓸 수 있습니다.
- 0x220 은 가장 오래된 레코드 번호 1, 0x224 는 크기 사본 0x28 입니다.

## 포렌식에서 중요한 점

### 시각

레코드마다 생성 시각과 기록 시각이 있고, 둘 다 UTC 이며 초 단위입니다. 생성 시각은 레코드가 만들어진 때이고 기록 시각은 파일에 쓰인 때입니다. 정수 초 값이므로 1초보다 작은 단위는 없습니다. 변환은 [시각 값 형식](../../value-decoding/filetime-unix-webkit-dos-ole.md) 을 봅니다.

### wrap 과 빈 틈

wrap 한 로그에서는 가장 오래된 레코드가 덮여 사라지고, 파일 끝 레코드와 가장 오래된 레코드 사이에는 빈 틈이 생깁니다. 이 틈에 지운 옛 레코드의 바이트가 남는지는 이 위키가 참고한 자료로 확인하지 못했습니다. 틈을 헥스로 직접 보고, 서명 `LfLe` 와 크기 사본으로 조각인지 확인합니다.


### 손상 사례 (libevt 명세)

- dirty 로 표시됐는데 가장 오래된 레코드와 파일 끝 레코드의 오프셋이 틀린 파일이 있습니다. 쓰는 중에 헤더가 갱신되지 않은 것이 흔한 원인입니다. EOF 오프셋 뒤에서 파일 끝 레코드를 찾아 읽습니다.
- 이런 파일이 wrap 된 경우, wrap 직전 마지막 이벤트 뒤에 이벤트가 아닌 데이터가 남을 수 있습니다. 이 데이터는 무시합니다.
- 잘린 레코드는 일부가 0 으로 채워지고 크기 사본이 0 입니다. 문자열 부분에서 잘렸다면 앞쪽 문자열은 읽힙니다.
- 데이터 크기가 0 이면, 레코드 크기를 넘는 데이터 오프셋은 무시해도 됩니다.

### 설정

- 로그 크기와 덮어쓰기 설정은 EVTX 와 같은 `HKLM\SYSTEM\CurrentControlSet\Services\Eventlog\<로그>` 키에 있습니다. 값의 뜻은 [EVTX 파일 구조](file-header-chunk-record.md) 의 "로그 크기·덮어쓰기 설정" 을 봅니다.
- Windows Server 2003 에서 AutoBackupLogFiles 가 동작하려면 Retention 이 -1 또는 1 이어야 합니다.
- libevt 명세는 헤더 40 오프셋의 알 수 없는 값을 Retention 으로 짐작합니다. 레지스트리의 Retention 값과 견줘 볼 수 있습니다.

## 함정

- DIRTY 헤더의 오프셋을 그대로 믿으면 레코드를 놓칩니다.
- 파일 앞쪽부터 차례로 읽으면 순서가 틀립니다. wrap 한 파일은 가장 오래된 레코드의 오프셋부터 읽습니다.
- 나뉜 레코드를 한 덩어리로 읽으면 크기 사본이 맞지 않습니다. 파일 끝 조각과 헤더 뒤 조각을 이어 붙입니다.
- 0x00000027 로 채운 바이트는 레코드가 아닙니다.
- EVT 의 시각은 FILETIME 이 아니라 32비트 유닉스 초입니다. EVTX 해석 코드를 그대로 쓰면 틀립니다.
- 레코드 본문은 이진 XML 이 아닙니다. 원본 이름부터 크기 사본까지 정해진 순서로 읽습니다.

## 도구

- libevt: 형식 명세와 함께 공개된 라이브러리입니다. 명세에 손상 사례가 적혀 있습니다.
- 도구 결과는 헥스로 본 헤더·파일 끝 레코드 값과 [도구 결과 교차 검증](../../../03-techniques/reporting/tool-validation.md) 의 방식으로 비교합니다.
