# 마스터 파일 테이블 ($MFT)

## 한 줄 요약

마스터 파일 테이블 (Master File Table, MFT) 은 NTFS 볼륨의 파일과 폴더 정보를 한곳에 모은 파일입니다. NTFS 에서는 볼륨 안의 모든 것이 파일이고, 그 정보가 MFT 에 모입니다(참고 1). 파일마다 이름, 부모 폴더, 시각, 크기, 데이터 위치가 MFT 항목에 적힙니다. 지운 파일의 항목도 다른 파일이 그 자리를 다시 쓰기 전까지 남을 수 있습니다.

## 무엇을 기록하나 · 왜 생기나

### 파일시스템이 쓰는 목록입니다

MFT 는 로그가 아닙니다. NTFS 가 파일을 찾고 여는 데 쓰는 목록입니다. 그래서 파일을 만들 때마다 항목이 생기고, 파일이 바뀔 때마다 항목의 값이 바뀝니다. 항목의 칸마다 지금 값 하나만 남습니다. 예전 값은 [USN 변경 저널](usnjrnl.md)과 [NTFS 트랜잭션 로그](logfile.md)에서 찾습니다.

### 항목 하나에 남는 값

| 값 | 들어 있는 곳 (속성 번호) |
|---|---|
| 파일 이름, 부모 폴더 참조 | `$FILE_NAME` (0x30) |
| 시각 네 개 (생성·내용 수정·MFT 항목 수정·접근) | `$STANDARD_INFORMATION` (0x10). `$FILE_NAME` 에도 이름마다 네 개가 따로 있습니다 |
| 할당 크기, 파일 크기 | `$FILE_NAME`, `$DATA` |
| 파일 속성 플래그 | `$STANDARD_INFORMATION` 오프셋 32 |
| 소유자 ID, 보안 설명자 ID, USN | `$STANDARD_INFORMATION` (NTFS 3.0 이상) |
| 파일 내용, 또는 내용이 있는 클러스터 위치 | `$DATA` (0x80) |
| 대체 데이터 스트림 | 이름 있는 `$DATA` |
| 폴더 안 파일 목록 | `$INDEX_ROOT` (0x90), `$INDEX_ALLOCATION` (0xA0) |
| 사용 중인지, 폴더인지 | 항목 머리의 플래그 |
| 순번, `$LogFile` 순번 (LSN) | 항목 머리 |

속성 종류 전체와 바이트 구조는 [MFT 레코드와 속성](../../01-foundations/disk-volume/ntfs/file-record-attribute.md)에서 다룹니다. 이 페이지는 이 값들을 증거로 읽는 법을 다룹니다.

### 앞 번호는 NTFS 가 씁니다

0번부터 11번까지는 번호가 정해진 메타 파일입니다(참고 1). 분석에서 자주 여는 항목은 아래와 같습니다.

| 번호 | 이름 | 분석에서 쓰는 곳 |
|---|---|---|
| 0 | `$MFT` | MFT 자신입니다. 이 항목의 데이터 런으로 MFT 전체 위치를 구합니다 |
| 1 | `$MFTMirr` | MFT 앞 항목 4개의 사본입니다 |
| 2 | `$LogFile` | [NTFS 트랜잭션 로그](logfile.md) |
| 5 | 루트 폴더 (`.`) | 경로를 세울 때 끝점입니다 |
| 6 | `$Bitmap` | 클러스터마다 할당 여부를 적습니다 |
| 11 | `$Extend` | `$UsnJrnl` 같은 확장 메타 파일이 들어 있는 폴더입니다 |

- 12\~15번은 사용 중으로 표시돼 있지만 비어 있습니다. 16\~23번은 미사용으로 표시돼 있습니다(참고 1).
- `$Extend\$UsnJrnl` 은 흔히 쓰는 번호가 있지만 번호가 고정되지 않습니다(참고 1). 그래서 `$Extend` 폴더 안에서 이름으로 찾습니다.
- 나머지 메타 파일은 [NTFS 메타 파일](../../01-foundations/disk-volume/ntfs/bitmap-secure-extend.md)에서 다룹니다.

## 위치와 버전별 차이

### MFT 가 있는 곳

MFT 시작 위치는 볼륨 헤더(부트 섹터)에 적혀 있고, 계산식은 "볼륨 시작 + MFT 시작 클러스터 번호 × 클러스터 크기" 입니다(참고 1). MFT 는 한 덩어리가 아닐 수 있어서 0번 항목의 데이터 런이 여러 조각을 가리키는데(참고 1), 시작 위치부터 연달아 읽으면 뒤쪽 항목을 놓칠 수 있습니다. 조각은 [데이터 런과 상주·비상주 데이터](../../01-foundations/disk-volume/ntfs/data-run-resident-non-resident.md)의 방법으로 따라갑니다.

볼륨 헤더의 칸 전체는 [부트 섹터와 클러스터](../../01-foundations/disk-volume/ntfs/boot-sector-cluster.md)에서 다루고, 아래 "직접 분석해 보기" 에서 한 번 따라갑니다.

### 항목 크기

MFT 항목은 흔히 1024바이트이지만(참고 1) 4096바이트 항목도 있어서, 해석 도구 가운데는 1024 와 4096 을 고르게 하는 것이 있습니다(참고 2). 항목 크기는 볼륨 헤더 오프셋 64 에서 읽습니다(참고 1).

### NTFS 버전별 차이

| NTFS 버전 | Windows | MFT 에서 달라지는 점 |
|---|---|---|
| 1.2 | NT 3.51 | 9번이 `$Quota` 입니다. `$STANDARD_INFORMATION` 에 소유자 ID 이후 칸이 없습니다 |
| 3.0 | Windows 2000 | 9번이 `$Secure` 가 됩니다. `$STANDARD_INFORMATION` 에 소유자 ID·보안 설명자 ID·할당량·USN 칸이 붙습니다. `$Extend` 아래 24번 `$Quota`, 25번 `$ObjId`, 26번 `$Reparse` 가 생깁니다 |
| 3.1 | XP 이후 | 항목 머리 오프셋 44 에 자기 항목 번호가 들어갑니다 |

libyal 문서는 Windows 11 21H2 까지 NTFS 3.1 로 시험했다고 적었고, Windows 10 1809 가 클러스터 64KB 볼륨에 NTFS 1.2 를 쓴 사례도 적었습니다(참고 1). 그래서 버전 번호만 보고 Windows 버전을 짐작하지 않습니다.


- "NTFS 5.0" 같은 이름은 Windows 버전을 따라 부른 호칭입니다. NTFS 자체 번호로는 3.1 입니다(참고 1).
- Vista 무렵부터 `$Extend` 아래 27번 이후에 `$RmMetadata`(트랜잭션 NTFS)가 생깁니다(참고 1).
- Windows 10 부터 29번 `$Extend\$Deleted` 가 생깁니다. 핸들이 열린 채 삭제 요청을 받은 파일이 잠시 머무는 곳입니다(참고 1).

### 실제 PC 한 대에서 본 값

`fsutil fsinfo ntfsinfo C:` 로 확인한 값입니다. (확인 범위: Windows 11 25H2, 1.8TB 볼륨 한 대)

| 항목 | 값 |
|---|---|
| NTFS 버전 | 3.1 |
| 섹터 | 512바이트 (물리 4096바이트) |
| 클러스터 | 4096바이트 |
| MFT 항목 크기 (FileRecord Segment) | 1024바이트 |
| MFT 유효 데이터 길이 (Mft Valid Data Length) | 2.41GB |
| MFT 예약 영역 (MFT Zone) | 200MB |

한 대의 값이라 모든 PC 에 맞는다고 보장하지 못합니다. 검체에서는 볼륨 헤더와 0번 항목을 직접 읽습니다.

## 구조

바이트 구조는 [MFT 레코드와 속성](../../01-foundations/disk-volume/ntfs/file-record-attribute.md)에서 다룹니다. 여기서는 분석에 쓰는 칸이 어디 있는지만 모읍니다.

| 있는 곳 | 오프셋 | 칸 | 분석에서 쓰는 곳 |
|---|---|---|---|
| 항목 머리 | 0 | 서명 `FILE` 또는 `BAAD` | 손상된 항목 가리기 |
| 항목 머리 | 8 | `$LogFile` 순번 (LSN) | `$LogFile` 기록과 잇기 |
| 항목 머리 | 16 | 순번 (Sequence) | 다른 기록의 참조가 지금 파일을 가리키는지 가리기 |
| 항목 머리 | 22 | 플래그 (0x0001 사용 중, 0x0002 폴더) | 지운 항목과 폴더 가리기 |
| 항목 머리 | 32 | 기본 레코드 참조 | 확장 레코드를 기본 레코드에 묶기 |
| 항목 머리 | 44 | 자기 항목 번호 (NTFS 3.1) | 떨어져 나온 항목의 원래 번호 찾기 |
| `$STANDARD_INFORMATION` | 0·8·16·24 | 시각 네 개 | 타임라인 |
| `$STANDARD_INFORMATION` | 64 | USN (8바이트) | [USN 변경 저널](usnjrnl.md) 레코드와 맞춰 보기 |
| `$FILE_NAME` | 0 | 부모 폴더 참조 | 경로 세우기 |
| `$FILE_NAME` | 8·16·24·32 | 시각 네 개 | `$STANDARD_INFORMATION` 시각과 비교 |
| `$FILE_NAME` | 65 | 이름공간 (0 POSIX, 1 Win32, 2 DOS, 3 DOS 와 Win32 가 같음) | 긴 이름과 짧은 이름 가리기 |

### 파일 참조와 순번

다른 기록이 MFT 항목을 가리킬 때는 8바이트 파일 참조를 쓰며, 앞 6바이트는 항목 번호이고 뒤 2바이트는 순번입니다(참고 1). libyal 문서가 옮긴 Microsoft 설명으로는 항목이 해제될 때마다 순번이 1 늘어나고(참고 1), 해석 도구 설명서는 지운 항목을 다시 쓸 때 1 늘어난다고 적었습니다(참고 2). 이름만 바꿀 때는 순번이 늘지 않고(참고 2), 한 번도 쓰지 않은 항목의 순번은 0 입니다(참고 1).

폴더 색인, USN 레코드, `$FILE_NAME` 의 부모 참조가 모두 이 형식이며, 참조의 순번과 지금 항목의 순번이 다르면 그 참조는 옛 파일을 가리킵니다. 비교표는 [MFT 레코드와 속성](../../01-foundations/disk-volume/ntfs/file-record-attribute.md)의 "지운 파일의 레코드" 절에 있습니다.

### 항목의 할당 표시

`$MFT` 의 `$BITMAP` 속성에서는 비트 하나가 MFT 항목 하나를 뜻합니다(참고 1). 비트가 1 이면 할당, 0 이면 비할당이며, 바이트 안에서는 최하위 비트가 앞 번호 항목입니다(참고 1). 클러스터의 할당 여부는 따로 6번 `$Bitmap` 파일에 적습니다(참고 1).

### 항목 안에 남는 내용

작은 데이터는 MFT 항목 안에 상주로 들어가고, 큰 데이터는 항목 밖 클러스터에 두고 데이터 런으로 가리킵니다(참고 1). 1024바이트 항목에 들어가는 상주 `$DATA` 는 최대 744바이트 정도이고, 보통은 그보다 작습니다(참고 2). 속성 목록은 0xFFFFFFFF 로 끝나며(참고 1), 그 뒤부터 항목 끝까지를 레코드 슬랙이라고 부릅니다(참고 2). 속성 뒤 8바이트 맞춤 여백에도 옛 데이터가 남을 수 있습니다(참고 1).

레코드 슬랙에 무엇이 남는지는 Windows 버전마다 다르다는 시험 결과가 있습니다. [MFT 레코드와 속성](../../01-foundations/disk-volume/ntfs/file-record-attribute.md)의 "레코드 슬랙" 절을 봅니다.

> 그림 자리: MFT 를 항목 번호 순서의 칸으로 그리고, 한 항목 안의 머리·`$STANDARD_INFORMATION`·`$FILE_NAME`·`$DATA`·끝 표시·슬랙을 펼친 그림. 옆에 `$BITMAP` 의 비트 하나가 항목 하나에 이어지는 화살표를 붙인다

## 증거로서 의미

| 증명하는 것 | 증명하지 못하는 것 |
|---|---|
| 이 볼륨에 이 이름의 파일이나 폴더 항목이 있습니다. 비할당 항목이면 한때 있었습니다 | 누가 파일을 만들었는지, 누가 열었는지 |
| 부모 참조를 따라 세운 경로 (부모 항목이 다시 쓰이지 않았을 때) | 칸의 예전 값. 칸마다 마지막 값 하나만 남습니다 |
| 칸마다 지금 적힌 시각과 크기 | 시각 하나가 어떤 사용자 행동을 뜻하는지. 변화 규칙을 따로 따져야 합니다 |
| 상주 파일이면 그 내용 | 비상주 파일의 클러스터 내용이 지금도 그 파일의 것인지 |
| 다른 기록의 파일 참조가 지금 이 파일을 가리키는지 (순번 비교) | 파일을 밖으로 복사하거나 보냈는지 |

### 보고서 문장

아래 이름과 시각은 설명을 위해 만든 예입니다.

- 쓸 수 있는 문장: "C: 볼륨 MFT 77,372번 항목은 비할당 상태입니다. 이 항목의 `$FILE_NAME` 에는 이름 `계약서.docx` 와 부모 폴더 참조(5번 항목)가 남아 있습니다. `$STANDARD_INFORMATION` 의 내용 수정 시각은 2025-02-03 01:20:30 UTC 입니다."
- 쓰면 안 되는 문장: "사용자가 2025-02-03 에 계약서.docx 를 고친 뒤 지웠다."

## 시각 해석

- MFT 의 시각은 모두 FILETIME 이고 UTC 입니다(참고 1). 계산법은 [시각 값 형식](../../01-foundations/value-decoding/filetime-unix-webkit-dos-ole.md)에서 다룹니다.
- `$STANDARD_INFORMATION` 에서는 오프셋 0 이 생성, 8 이 내용 수정, 16 이 MFT 항목 수정, 24 가 접근 시각입니다(참고 1).
- `$FILE_NAME` 에서는 오프셋 8 이 생성, 16 이 내용 수정, 24 가 MFT 항목 수정, 32 가 접근 시각입니다(참고 1).
- 한 항목에 `$FILE_NAME` 이 여러 개일 수 있습니다. 긴 이름과 짧은 이름이 따로 있고, 하드 링크마다 부모 참조가 다른 `$FILE_NAME` 이 더 붙습니다(참고 1). 보고서에는 어느 이름의 시각인지 적습니다.
- `$STANDARD_INFORMATION` 은 없고 `$FILE_NAME`·`$I30` 색인 같은 다른 속성만 있는 항목을 본 사례가 있습니다(참고 1). 이런 항목에는 첫 번째 시각 묶음이 없습니다.
- 두 벌의 시각이 어떤 동작에 바뀌는지는 이 페이지에서 확인하지 않았습니다. [두 벌의 시각](../../01-foundations/disk-volume/ntfs/standard-information-file-name.md)과 [파일 시각 네 가지와 변화 규칙](../../03-techniques/analysis/timeline/macb-timestamp-rules.md)을 봅니다.
- 현지 시각으로 바꿀 때는 그 PC 의 [시간대 설정](../system-account/time-zone.md)을 씁니다.
- MFT 로 시간표를 만드는 절차는 [파일시스템 타임라인](../../03-techniques/analysis/timeline/filesystem-timeline-mft-usnjrnl-logfile.md)에서 다룹니다.

## 함정과 한계

1. **`$MFT` 파일만 떼어 보면 빠지는 것이 있습니다.** 폴더 색인의 `$INDEX_ALLOCATION` 은 `$MFT` 밖에 있고(참고 1), 비상주 속성 목록의 내용도 `$MFT` 밖 클러스터에 있습니다. 이런 내용이 필요하면 볼륨 이미지에서 읽습니다.
2. **경로가 틀어질 수 있습니다.** 부모 폴더 항목이 다른 폴더에 다시 쓰였으면 부모 연결이 틀어집니다(참고 1). 부모 참조의 순번과 부모 항목의 지금 순번을 비교합니다.
3. **긴 이름이 확장 레코드에만 있을 수 있습니다.** 확장 레코드를 쓰는 항목은 Win32 긴 이름이 확장 레코드에만 있을 수 있어서, 기본 레코드만 보면 8.3 짧은 이름만 보입니다. 확장 레코드는 대개 기본 레코드와 멀리 떨어져 있습니다. (현장 관찰)
4. **항목 크기를 1024바이트로 못박지 않습니다.** 4096바이트 항목도 있습니다(참고 2). 볼륨 헤더 값으로 확인합니다.
5. **fix-up 을 빠뜨리지 않습니다.** 디스크에서는 512바이트마다 마지막 2바이트가 fix-up 표시 값으로 바뀌어 있습니다. 원래 값은 fix-up 배열에 있습니다(참고 1).
6. **`BAAD` 항목을 만날 수 있습니다.** chkdsk 가 fix-up 이 맞지 않는 항목을 찾으면 `BAAD` 로 표시하고, 첫 섹터 끝의 fix-up 값만 빼고 0 으로 채운다는 설명이 있습니다. `BAAD` 는 NT4·XP 에서 보였습니다(참고 1).
7. **`$FILE_NAME` 의 크기 값을 그대로 쓰지 않습니다.** MFT 안 `$FILE_NAME` 의 크기 값은 정확하지 않을 때가 있습니다(참고 1). 크기는 `$DATA` 에서 읽습니다.
8. **순번이 같다고 이름까지 같지는 않습니다.** 이름을 바꿔도 순번은 그대로입니다(참고 2). 옛 이름은 [USN 변경 저널](usnjrnl.md)에서 찾습니다.
9. **비할당 항목이 모두 지운 파일은 아닙니다.** 16\~23번처럼 미사용으로 표시된 항목도 있습니다(참고 1). 이름 속성이 남아 있는지 함께 봅니다.

### 지우기와 조작

- **파일 삭제**: 항목은 비할당으로 바뀌고, 다른 파일이 다시 쓸 때까지 값이 남을 수 있습니다. 되살리는 절차는 [파일시스템 기반 복구](../../03-techniques/analysis/data-recovery/undelete-ntfs-fat.md)에서 다룹니다. 항목이 이미 덮였으면 `$LogFile` 과 `$UsnJrnl`, 폴더 색인 슬랙에서 이름을 찾습니다([지운 파일의 흔적 찾기](../../04-scenarios/activity/deleted-file-traces.md)).
- **시각 조작**: 시각 칸은 마지막 값만 남으므로 조작한 값도 그대로 남습니다. `$STANDARD_INFORMATION` 과 `$FILE_NAME`, USN 레코드의 기본 정보 변경 표시를 함께 봅니다. 판단 방법은 [시각 조작 탐지](../../03-techniques/analysis/timeline/timestomping.md)에서 다룹니다.
- **변경 저널 끄기**: 저널을 끄면 MFT 레코드의 값도 바뀝니다. [USN 변경 저널](usnjrnl.md)의 "지우기와 조작" 절을 봅니다.
- **완전삭제 도구**: [완전삭제 도구를 썼나](../../04-scenarios/activity/anti-forensics/wiping-tools.md)를 봅니다.

## 직접 분석해 보기

### 헥스로 한 번

아래 바이트는 libyal 명세를 보고 만든 예시입니다. 실제 검체에서 뽑은 값이 아닙니다. `..` 은 이 예시에서 읽지 않는 바이트입니다.

**1단계: 볼륨 헤더에서 MFT 위치와 항목 크기 읽기**

```
오프셋  00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F
0x30    00 00 0C 00 00 00 00 00 02 00 00 00 00 00 00 00
0x40    F6 .. .. .. 01 .. .. .. .. .. .. .. .. .. .. ..
```

1. 오프셋 48(0x30)의 8바이트 `00 00 0C 00 00 00 00 00` 은 MFT 시작 클러스터 번호입니다(참고 1). 리틀 엔디언으로 0x000C0000, 10진으로 786,432 입니다.
2. 오프셋 56(0x38)의 8바이트 `02 00 00 00 00 00 00 00` 은 `$MFTMirr` 시작 클러스터 번호 2 입니다(참고 1).
3. 오프셋 64(0x40)의 1바이트 `F6` 은 MFT 항목 크기입니다(참고 1).
4. 크기 값이 0\~127 이면 클러스터 개수, 128\~255 면 2^(256−값) 바이트입니다(참고 1). 0xF6 은 246 이므로 2^(256−246) = 2^10 = 1024바이트입니다.
5. 오프셋 68(0x44)의 1바이트 `01` 은 폴더 색인 항목 크기입니다(참고 1). 1 은 127 이하이므로 클러스터 1개입니다.
6. 클러스터 크기가 4096바이트라면 MFT 는 볼륨 시작에서 786,432 × 4096 = 3,221,225,472바이트(0xC0000000) 떨어진 곳에서 시작합니다. 클러스터 크기 읽는 법은 [부트 섹터와 클러스터](../../01-foundations/disk-volume/ntfs/boot-sector-cluster.md)에서 다룹니다.

**2단계: `$BITMAP` 에서 할당 여부 읽기**

`$MFT` 의 `$BITMAP` 속성 값에서 여섯 번째 바이트(오프셋 5)가 `5F` 라고 합니다. 이 바이트는 40\~47번 항목을 뜻합니다.

| 비트 (최하위부터) | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| 항목 번호 | 40 | 41 | 42 | 43 | 44 | 45 | 46 | 47 |
| 값 (0x5F = 0101 1111) | 1 | 1 | 1 | 1 | 1 | 0 | 1 | 0 |

45번과 47번은 비할당입니다. 이 두 항목을 열어 서명과 `$FILE_NAME` 이 남아 있는지 봅니다.

**3단계: 파일 참조 풀기**

어떤 USN 레코드의 파일 참조 칸이 `3C 2E 01 00 00 00 03 00` 이라고 합니다.

1. 앞 6바이트 `3C 2E 01 00 00 00` 은 항목 번호 0x012E3C, 10진으로 77,372 입니다.
2. 뒤 2바이트 `03 00` 은 순번 3 입니다.
3. MFT 77,372번 항목 머리 오프셋 16 의 순번이 3 이면 같은 파일입니다. 4 이상이면 그 항목은 그 뒤에 해제된 적이 있습니다.

### 실행 중인 시스템에서

- `fsutil fsinfo ntfsinfo C:` 는 NTFS 버전, 클러스터 크기, MFT 항목 크기, MFT 유효 데이터 길이를 보여 줍니다(위 "실제 PC 한 대에서 본 값").
- 실행 중인 볼륨에서 `$MFT` 를 뽑는 방법은 [증거 획득](../../03-techniques/process-acquisition/evidence-acquisition/index.md)과 [라이브 응답](../../03-techniques/process-acquisition/live-response/index.md)을 봅니다.

### 공개 도구로 한 번

The Sleuth Kit, libfsntfs 같은 공개 도구와 라이브러리가 MFT 를 풀어 줍니다. 어느 도구를 쓰든 아래를 확인합니다.

- 항목 크기를 볼륨에 맞게 1024 또는 4096 으로 두는지 확인합니다.
- 확장 레코드를 따라가 긴 이름을 찾는지 확인합니다.
- `$FILE_NAME` 을 어느 이름공간의 것으로 보여 주는지 확인합니다.
- 비할당 항목과 순번을 칸으로 보여 주는지 확인합니다.
- 시각을 UTC 로 내는지, 분석 PC 의 현지 시각으로 바꿔 내는지 확인합니다.
- 항목 몇 개는 헥스로 읽은 값과 맞춰 봅니다. 방법은 [도구 결과 교차 검증](../../03-techniques/reporting/tool-validation.md)을 봅니다.

## 실습

**NIST CFReDS 같은 공개 검체의 Windows 디스크 이미지**로 풀어 봅니다.

1. 볼륨 헤더에서 MFT 시작 클러스터와 항목 크기를 헥스로 직접 읽어 보십시오. 도구가 보여 주는 값과 같습니까?
2. 0번 항목의 데이터 런은 몇 조각입니까? 조각이 여럿이면 두 번째 조각이 시작하는 항목 번호를 계산해 보십시오.
3. 사용자 문서 폴더 아래에서 비할당 항목을 찾아보십시오. 이름·부모 참조·순번을 적고, 부모 항목의 지금 순번과 비교해 보십시오.
4. `$FILE_NAME` 이 두 개 이상인 항목을 하나 골라 이름공간 값과 시각을 나란히 적어 보십시오.

**직접 만든 Windows 10·11 가상 머신**에서도 해 봅니다.

1. 작은 텍스트 파일과 큰 파일을 하나씩 만들고 이미지를 뜹니다. 작은 파일의 내용이 MFT 항목 안에 있는지 확인합니다.
2. 파일 이름만 바꾸고 다시 이미지를 뜹니다. 순번이 그대로인지 확인합니다.
3. 파일을 지운 뒤 새 파일을 여러 개 만들고 이미지를 뜹니다. 지운 파일의 항목이 다시 쓰였는지, 순번이 몇 늘었는지 봅니다.
