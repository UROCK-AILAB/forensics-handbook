# 증거 이미지·가상 디스크 형식 (E01·RAW·AFF4·VHDX·VMDK)

> 위치: 기반 구조 > 디스크·볼륨

디스크를 통째로 뜬 증거 이미지와 가상 머신의 가상 디스크는 섹터 데이터를 파일에 담습니다. E01·VHDX·VMDK 파일에는 섹터 데이터 말고도 조각 목록, 체크섬, 사건 정보, 부모 파일 정보 같은 관리 정보가 함께 들어 있습니다. 이 관리 정보를 먼저 풀어야 안쪽의 [파티션 표](mbr-gpt.md)와 파일시스템을 읽을 수 있습니다.

## 이 형식을 쓰는 아티팩트

이 형식들은 사용자 행동을 기록하지 않습니다. 증거를 담는 그릇입니다. 디스크 분석은 대부분 이 그릇을 여는 데서 시작합니다.

| 만나는 곳 | 형식 | 이 페이지에서 볼 값 |
|---|---|---|
| 디스크·파티션을 뜬 결과 ([증거 획득](../../03-techniques/process-acquisition/evidence-acquisition/index.md)) | E01 (EWF) | 조각 파일, 사건 정보, 매체 해시, 읽기 오류 구간 |
| 논리 증거 파일 | L01 (EWF) | 서명 `LVF`, 매체 종류 0x0e |
| 메모리를 뜬 결과 ([메모리 분석](../../03-techniques/analysis/memory-forensics/index.md)) | EWF | 매체 종류 0x10 (물리 메모리) |
| Microsoft 가상화 제품의 가상 머신 | VHDX | BAT, 부모 위치 |
| VMware 가상화 제품의 가상 머신 | VMDK | 설명 파일, 그레인 표, 부모 CID |

- 이미지를 뜨고 넘겨받는 절차와 해시 검증 절차는 [증거 획득](../../03-techniques/process-acquisition/evidence-acquisition/index.md)에서 다룹니다. 이 페이지는 파일 안의 구조만 봅니다.
- 이미지를 푼 뒤 첫 섹터부터 읽는 법은 [파티션 구조](mbr-gpt.md)로 이어집니다.

## 구조

### 형식 한눈에 보기

| 형식 | 쓰는 곳 | 파일 구성 | 맨 앞 서명 | 이 페이지에서 다루는 범위 |
|---|---|---|---|---|
| EWF (E01·L01·S01) | EnCase·FTK 같은 포렌식 도구 | 조각 파일 여러 개 | `EVF` (E01), `LVF` (L01) | 파일 헤더, 섹션, 청크, 해시 |
| EWF2 (Ex01·Lx01) | EnCase 7 부터 | — | — | 다루지 않음 |
| RAW | — | — | — | VMDK flat 조각과의 관계만 |
| AFF4 | — | — | — | 다루지 않음 |
| VHDX | Microsoft 가상화 제품 | 파일 하나 (차등이면 부모 파일도) | `vhdxfile` | 헤더, 영역 표, 메타데이터, BAT |
| VMDK | VMware 가상화 제품 | 설명 파일 + 조각 파일 | `KDMV`, `COWD` (sparse 조각) | 설명 파일, sparse 헤더, 그레인 |

- RAW 이미지 파일, AFF4, EWF2, VHD(1판)는 이 페이지에서 구조 표를 싣지 않습니다.
- 여러 바이트 정수는 모두 리틀 엔디언 (little-endian) 입니다. 작은 쪽 바이트가 앞에 옵니다.

### EWF (E01)

EWF (Expert Witness Compression Format) 는 포렌식용 매체 이미지를 담는 형식입니다.

원래 명세는 ASRDATA 가 SMART 프로그램용으로 냈고, 지금은 EnCase·FTK 같은 도구에서 널리 씁니다. 디스크 이미지와 파티션 이미지를 담으며, 데이터는 압축해도 되고 압축하지 않아도 됩니다.

EWF 는 확장자에 따라 세 종류로 나뉩니다. SMART 의 EWF-S01, EnCase 계열의 EWF-E01, EnCase 5 가 들여온 논리 증거 파일 EWF-L01 입니다. EnCase 7 에서 뒤를 잇는 형식 EWF2 (Ex01·Lx01) 가 나왔습니다. libewf 문서는 FTK Imager 2.3~3.0, EnCase 1.35~7.04, linen 5~7 이 만든 파일로 시험했습니다.

#### 조각 파일

이미지 하나를 조각 파일 (Segment File) 여러 개에 나눠 담을 수 있습니다. 섹션 하나는 두 파일에 걸치지 않습니다.

| 종류 | 첫 파일 | 이어지는 이름 |
|---|---|---|
| EWF-E01 | .E01 | .E02~.E99 → .EAA~.EAZ → .EBA~.EZZ → .FAA → … → .ZZZ |
| EWF-S01 | .s01 | E01 과 같은 규칙 |
| EWF-L01 | .L01 | E01 과 같은 규칙 |

- .ZZZ 다음에 오는 이름은 공개된 자료가 없습니다.

#### 파일 헤더 (13바이트)

조각 파일은 모두 13바이트 파일 헤더로 시작합니다.

| 오프셋 | 크기 | 값 | 뜻 |
|---|---|---|---|
| 0 | 8 | `45 56 46 09 0D 0A FF 00` | 서명 "EVF\x09\x0d\x0a\xff\x00". L01 은 "LVF\x09\x0d\x0a\xff\x00" 입니다. |
| 8 | 1 | `01` | 필드 시작 |
| 9 | 2 | | 조각 번호. 첫 파일이 1 입니다. |
| 11 | 2 | `00 00` | 필드 끝 |

#### 섹션 설명자 (76바이트)

파일 헤더 뒤로 섹션 (Section) 이 이어 붙습니다. 섹션은 76바이트 섹션 설명자 (Section Descriptor) 로 시작합니다.

| 오프셋 | 크기 | 필드 | 설명 |
|---|---|---|---|
| 0 | 16 | 섹션 종류 | "header", "volume" 같은 문자열입니다. |
| 16 | 8 | 다음 섹션 오프셋 | 조각 파일 시작에서 잰 위치입니다. |
| 24 | 8 | 섹션 크기 | |
| 32 | 40 | 빈 영역 | |
| 72 | 4 | 체크섬 | Adler-32 입니다. |

#### 섹션 종류

| 섹션 | 담는 것 | 놓이는 자리 |
|---|---|---|
| header2 | 사건 정보. zlib 으로 압축한 UTF-16 텍스트입니다. EnCase 4~7 이 씁니다. | 첫 조각 파일 맨 앞. 같은 내용이 두 번 나옵니다. |
| header | 사건 정보. zlib 으로 압축한 ASCII 텍스트입니다. | 첫 조각 파일에만 있습니다. |
| volume | 매체 종류, 섹터 수, 청크 크기 (1,052바이트) | |
| disk | volume 과 같은 구조 | FTK Imager 2.3 으로 물리 디스크를 뜬 이미지에서 나옵니다. |
| data | volume 과 같은 내용 | 조각 파일이 여럿이면 둘째 파일부터 맨 앞에 있습니다. |
| sectors | 매체 데이터 청크 | |
| table | 청크 위치 표 | |
| table2 | table 의 사본 | EWF-E01 에는 늘 있습니다. |
| hash | 매체 데이터의 MD5 | 넣지 않아도 됩니다. 넣으면 마지막 조각 파일의 done 앞에 둡니다. |
| digest | 매체 데이터의 MD5 와 SHA1 | EnCase 6.12·linen 6.12 부터 있습니다. |
| error2 | 읽기 오류가 난 섹터 범위 | 오류가 있을 때만 마지막 조각 파일에 붙습니다. |
| next | 이 조각 파일이 끝났다는 표시 | 마지막이 아닌 조각 파일의 끝 |
| done | 이미지가 끝났다는 표시 | 마지막 조각 파일의 끝 |
| incomplete | 드문 섹션입니다. 원격 수집으로 끝까지 뜨지 못한 이미지라는 해석이 있습니다. | |

이 밖에 session·ltree·ltypes 섹션도 있습니다.

#### header·header2 의 사건 정보

압축을 풀면 셋째 줄에 항목 기호가 있고 넷째 줄에 값이 있으며, 두 줄 모두 탭으로 필드를 나눕니다.

| 기호 | 뜻 | 기호 | 뜻 |
|---|---|---|---|
| c | 사건 번호 | md | 매체 모델 |
| n | 증거 번호 | sn | 매체 일련번호 |
| a | 설명 | av | 도구 버전 |
| e | 분석관 이름 | ov | 수집한 OS |
| t | 메모 | m | 수집 일시 |
| p | 비밀번호 해시 | u | 시스템 일시 |

비밀번호 해시 (p) 는 도구가 비밀번호를 확인하는 데만 쓰며, 이미지 데이터를 보호하지 않습니다.

#### volume 섹션 (1,052바이트)

| 오프셋 | 필드 | 설명 |
|---|---|---|
| 0 | 매체 종류 | 아래 표 |
| 4 | 청크 개수 | |
| 8 | 청크당 섹터 수 | 기본 64 |
| 12 | 섹터당 바이트 수 | |
| 16 | 전체 섹터 수 | 8바이트 |
| 36 | 매체 플래그 | 아래 표 |
| 52 | 압축 수준 | |
| 56 | 오류 단위 | |
| 64 | 조각 파일 묶음 GUID | 16바이트 |
| 1048 | 체크섬 | Adler-32 |

| 매체 종류 값 | 뜻 |
|---|---|
| 0x00 | 이동식 저장장치 |
| 0x01 | 고정식 저장장치 |
| 0x03 | 광학 디스크 |
| 0x0e | 논리 증거 파일 (L01) |
| 0x10 | 물리 메모리 |

| 매체 플래그 비트 | 뜻 |
|---|---|
| 0x01 | 이미지 파일 |
| 0x02 | 물리 장치 |
| 0x04 | Fastbloc 쓰기 방지 장치를 씀 |
| 0x08 | Tableau 쓰기 방지 장치를 씀 (EnCase 6.13 부터) |

- 조각 파일 묶음에는 고유 ID 필드가 따로 없습니다. volume 섹션의 GUID 로 같은 묶음인지 판별합니다.

#### 청크와 table 섹션

sectors 섹션에는 매체 데이터가 청크 (Chunk) 단위로 들어 있습니다. 청크 기본 크기는 32,768바이트로, 512바이트 섹터 64개입니다. 압축하지 않은 청크는 데이터 뒤에 4바이트 Adler-32 체크섬이 붙고, 압축한 청크는 zlib 형식입니다. 압축한 결과가 원래보다 크면 그 청크는 압축하지 않고 저장합니다.

| 만든 도구 | 청크당 섹터 수 |
|---|---|
| EnCase 5·6, linen 5·6 | 64~32,768 가운데 고릅니다. |
| EnCase 7, linen 7 | 64·128·256·1,024 가운데 하나입니다. |

table 섹션 (EnCase 6~7) 은 청크마다 위치를 적습니다.

| 부분 | 크기 | 내용 |
|---|---|---|
| 표 머리 | 24바이트 | 항목 수, 기준 오프셋, 체크섬 |
| 항목 배열 | 항목마다 4바이트 | 청크 위치와 압축 여부 |
| 끝 체크섬 | 4바이트 | |

항목의 최상위 비트가 1 이면 압축한 청크이고, 나머지 31비트는 기준 오프셋에서 잰 청크 위치입니다. 위치 필드가 31비트라서 EnCase 는 조각 파일 크기를 2000 MiB 로 묶었는데, EnCase 6.7 에서 기준 오프셋이 들어와 이 제한이 풀렸습니다.

#### 해시와 읽기 오류

hash 섹션에는 MD5 (16바이트) 가 있고, digest 섹션에는 MD5 와 SHA1 이 함께 있습니다. 두 섹션의 해시는 청크 안의 데이터, 곧 매체 데이터로 낸 값입니다. error2 섹션은 읽기 오류 범위마다 시작 섹터 (4바이트) 와 섹터 수 (4바이트) 를 적고, EnCase 는 읽기 오류가 난 섹터를 0 으로 채웁니다.

#### 시각

수집 일시 (m) 와 시스템 일시 (u) 를 적는 방식은 도구마다 다릅니다.

| 자리 | 적는 방식 |
|---|---|
| header2 | 32비트 POSIX 시각을 숫자 문자열로 적습니다. 예: "1142163845" |
| EnCase 의 header | "2002 3 4 10 19 59" 같은 날짜 문자열입니다. UTC 인지 현지 시각인지는 실제 데이터로 확인해야 합니다. |

| 만든 도구 | 수집 일시 (m) | 시스템 일시 (u) |
|---|---|---|
| linen 6.19 전 | 현지 시각 | 현지 시각 |
| linen 6.19 부터 | UTC | 현지 시각 |

- L01 에서 EnCase 5 는 두 일시를 0 으로 적습니다.
- EnCase 6~7 은 L01 의 두 일시를 1970-01-01 00:00:00 으로 적습니다.
- 이 값은 보는 도구의 시간대에 따라 다른 날짜로 보입니다.
- POSIX 시각을 바꾸는 법은 [시각 값 형식](../value-decoding/filetime-unix-webkit-dos-ole.md)에 있습니다.

### RAW 와 AFF4

- VMDK 의 flat 조각 파일은 RAW 데이터입니다. "Simple extent" 나 "Flat extent" 라고도 부릅니다.
- RAW 이미지 파일의 이름 규칙과 나눠 저장하는 방식은 이 페이지에서 다루지 않습니다.
- AFF4 의 구조도 이 페이지에서 다루지 않습니다.

### VHDX

VHDX 는 Microsoft 가상화 제품이 쓰는 가상 디스크 형식입니다.

파일은 파일 식별자, 이미지 헤더 2개, 영역 표 (Region Table) 2개, 로그, BAT 영역, 메타데이터 영역, 디스크 내용으로 이뤄지고, 요소는 64 KiB 경계에 맞춰 놓입니다. 문자열은 BOM 없는 UTF-16LE 이며, 인코딩은 [문자 인코딩](../value-decoding/utf-16le-utf-8-cp949.md)을 봅니다. libvhdi 문서는 Windows 10 2004 의 Diskpart 로 만든 이미지로 시험했습니다.

공식 명세는 Microsoft 의 MS-VHDX 입니다(4.0판, 2018-09-12).

#### 파일 식별자 (64 KiB)

| 오프셋 | 크기 | 필드 |
|---|---|---|
| 0 | 8 | 서명 `vhdxfile` |
| 8 | 512 | 만든 프로그램 이름 (UTF-16LE) |

#### 이미지 헤더 (4 KiB)

| 오프셋 | 크기 | 필드 |
|---|---|---|
| 0 | 4 | 서명 `head` |
| 4 | 4 | CRC-32C 체크섬 |
| 8 | 8 | 순번 (Sequence Number) |
| 16 | 16 | 파일 쓰기 GUID |
| 32 | 16 | 데이터 쓰기 GUID |
| 48 | 16 | 로그 GUID |
| 64 | 2 | 로그 형식 판 |
| 66 | 2 | 형식 판 (1) |
| 68 | 4 | 로그 크기 |
| 72 | 8 | 로그 오프셋 |

이미지 헤더는 두 벌입니다. 두 헤더 가운데 순번이 큰 쪽이 최신인지는 실제 데이터로 확인해야 합니다.

#### 영역 표

- 영역 표는 서명 `regi` 로 시작합니다. 서명 뒤에 CRC-32C 와 항목 수 (2,047 이하) 가 옵니다.
- 항목은 32바이트입니다. 영역 GUID, 오프셋, 크기, 필수 여부를 담습니다.

| 영역 | GUID |
|---|---|
| BAT | 2dc27766-f623-4200-9d64-115e9bfd4a08 |
| 메타데이터 | 8b7ca206-4790-4b9a-b8fe-575f050f886e |

#### 메타데이터

메타데이터 표는 서명 `metadata` 로 시작합니다. 항목은 GUID 로 구분합니다. 아래 표의 GUID 는 앞 8자리만 적었습니다.

| 항목 | GUID 앞부분 | 내용 |
|---|---|---|
| 파일 매개변수 | caa16737-… | 블록 크기, 고정·차등 표시 |
| 가상 디스크 크기 | 2fa54224-… | |
| 논리 섹터 크기 | 8141bf1d-… | 512 또는 4096 |
| 물리 섹터 크기 | cda348c7-… | 512 또는 4096 |
| 가상 디스크 ID | beca12ab-… | |
| 부모 위치 | a8d35f2d-… | 차등 이미지가 가리키는 부모 |

파일 매개변수에는 세 값이 있습니다.

- 블록 크기: 1 MiB~256 MiB 사이의 2의 거듭제곱입니다.
- "블록을 계속 할당" 비트: 켜져 있으면 고정 크기 이미지입니다.
- "부모 있음" 비트: 켜져 있으면 차등 이미지입니다.

부모 위치에는 아래 키가 있습니다.

| 키 | 값의 형식 |
|---|---|
| absolute_win32_path | `\\?\c:\file.vhdx` |
| relative_path | `..\file.vhdx` |
| volume_path | `\\?\Volume{GUID}\file.vhdx` |
| parent_linkage | 부모의 데이터 쓰기 GUID |

- 차등 이미지와 부모의 가상 디스크 ID 는 바뀌지 않습니다. VHD(1판)와 다른 점입니다.
- 부모를 가리키는 데는 데이터 쓰기 GUID 를 쓴다는 해석이 있습니다. 그래서 부모와 짝을 맞출 때는 가상 디스크 ID 가 아니라 부모의 데이터 쓰기 GUID 를 봅니다.

#### BAT

BAT (블록 할당 표) 항목은 64비트이며, 하위 3비트가 블록 상태이고 44비트 필드가 블록의 파일 안 위치를 1 MiB 단위로 적습니다.

| 상태 값 | 이름 | 뜻 |
|---|---|---|
| 0 | NOT_PRESENT | 블록이 없음 |
| 1 | UNDEFINED | 정해지지 않음 |
| 2 | ZERO | 0 으로 채운 블록 |
| 3 | UNMAPPED | 매핑 해제 |
| 6 | FULLY_PRESENT | 이 파일에 있음 |
| 7 | PARTIALLY_PRESENT | 부모에 있음. 차등 이미지에서 섹터마다 이 파일에 있는지 부모에 있는지는 섹터 비트맵으로 판별합니다. |

섹터 비트맵 블록은 1 MiB 이고, 그 BAT 항목 상태는 0 (SB_BLOCK_NOT_PRESENT) 과 6 (SB_BLOCK_PRESENT) 두 가지입니다. 차등 이미지의 섹터 비트맵에서 비트 1 은 이 파일에 있는 섹터이고, 0 은 부모에 있는 섹터입니다. 고정 크기 이미지의 BAT 에는 섹터 비트맵 항목이 없고, 동적·차등 이미지의 BAT 에는 있습니다.

#### 로그

로그는 원형 버퍼 모양의 메타데이터 저널이고 로그 항목은 4 KiB 입니다. 로그 항목의 세부 구조는 이 페이지에서 다루지 않습니다.

### VMDK

VMDK 는 VMware 가상화 제품이 쓰는 가상 디스크 형식입니다.

설명 파일 (Descriptor) 하나와 데이터 조각 (Extent) 파일 여럿으로 이뤄지며, 조각 종류는 RAW, VMDK sparse, COWD sparse 셋입니다. 섹터는 512바이트로 봅니다.

#### 설명 파일

설명 파일은 대소문자를 가리지 않는 텍스트이고, 첫 줄은 `# Disk DescriptorFile` 입니다.

| 값 | 뜻 |
|---|---|
| version | 1~3 |
| CID | 내용 식별자 (32비트) |
| parentCID | 부모의 CID. `ffffffff` 이면 부모가 없습니다. |
| createType | 디스크 종류 |
| parentFileNameHint | 차등 이미지의 부모 경로 |

- CID 는 디스크를 연 뒤 처음 내용이 바뀔 때 새 난수로 바뀝니다.
- 조각 줄은 접근 방식, 섹터 수, 조각 종류, 파일 이름, (있으면) 시작 섹터 순서로 적습니다. 예: `RW 4192256 SPARSE "test-s001.vmdk"`

| createType | 파일 |
|---|---|
| monolithicSparse | `<이름>.vmdk` 하나. 설명도 그 안에 들어 있습니다. |
| monolithicFlat | 설명 파일 + `<이름>-f001.vmdk` (RAW) |
| twoGbMaxExtentSparse | 설명 파일 + `<이름>-s###.vmdk` (2 GB 이하 조각) |
| twoGbMaxExtentFlat | 설명 파일 + `<이름>-f###.vmdk` |
| vmfs | 설명 파일 + `<이름>-flat.vmdk` (RAW) |
| vmfsSparse | 설명 파일 + `<이름>-delta.vmdk` (COWD) |
| streamOptimized | 압축한 sparse 조각 하나 |

- 차등 (delta) 이미지는 다른 차등 이미지에 이어질 수 있습니다.

#### sparse 조각 헤더 (512바이트)

| 오프셋 | 필드 |
|---|---|
| 0 | 서명 `KDMV` |
| 4 | 판 (1~3) |
| 8 | 플래그 |
| 12 | 용량 (섹터 수) |
| 20 | 그레인 (Grain) 크기 (섹터 수) |
| 28 | 내장 설명 위치 |
| 36 | 내장 설명 크기 |
| 44 | 그레인 표 항목 수 (512) |
| 48 | 보조 그레인 디렉터리 위치 |
| 56 | 그레인 디렉터리 위치 |
| 64 | 메타데이터 크기 |
| 72 | 깨끗이 닫히지 않음 (dirty) 표시 |
| 73~76 | 줄바꿈 문자 `\n`, 공백, `\r`, `\n` |
| 77 | 압축 방식 |

- 28·36·48·56·64 의 위치와 크기는 바이트가 아니라 섹터 (512바이트) 수로 적습니다.
- 73~76 의 줄바꿈 문자는 파일을 옮기다 줄바꿈이 바뀐 손상을 찾는 데 씁니다.
- 판 3 부터 조각 파일 크기의 2 GiB 제한이 없어졌습니다. 바뀐 블록 추적 (CBT, Changed Block Tracking) 도 판 3 에서 생겼습니다.

#### 그레인 찾기

주소는 그레인 디렉터리 → 그레인 표 → 그레인 데이터 순서로 두 단계를 거쳐 찾습니다. 그레인 표 하나에는 항목이 512개 있고 크기는 2,048바이트입니다. 그레인 표 항목이 0 이면 비어 있거나 부모에서 읽어야 하는 그레인이며, 판 2 부터는 플래그에 따라 항목 값 1 도 빈 그레인을 뜻합니다.

#### streamOptimized 와 COWD

- streamOptimized 는 그레인을 deflate 로 압축합니다.
- 헤더의 그레인 디렉터리 위치가 -1 이면 실제 값은 파일 끝에서 1,024바이트 앞에 있는 보조 헤더 (꼬리) 에 있습니다.
- streamOptimized 는 512바이트 표지 (Marker) 를 씁니다. 표지 종류는 0 끝, 1 그레인 표, 2 그레인 디렉터리, 3 꼬리입니다.
- COWD 조각 (ESX 서버의 sparse 조각) 은 헤더가 2,048바이트이고 서명이 `COWD` 입니다. 오프셋 1648 에 dirty 값이 있습니다.

## 읽는 법

### E01 첫 조각 파일 따라가기

> 아래 바이트는 명세(libewf 문서)대로 만든 예시입니다. 실제 데이터에서 뽑은 값이 아닙니다. 체크섬 자리는 `xx` 로 비워 두었습니다.

```
오프셋    00 01 02 03 04 05 06 07  08 09 0A 0B 0C 0D 0E 0F
00000000  45 56 46 09 0D 0A FF 00  01 01 00 00 00 68 65 61   EVF..........hea
00000010  64 65 72 32 00 00 00 00  00 00 00 00 00 D1 01 00   der2............
00000020  00 00 00 00 00 C4 01 00  00 00 00 00 00 00 00 00   ................
00000030  00 00 00 00 00 00 00 00  00 00 00 00 00 00 00 00   ................
00000040  00 00 00 00 00 00 00 00  00 00 00 00 00 00 00 00   ................
00000050  00 00 00 00 00 xx xx xx  xx (0x59 부터 섹션 데이터)
```

| 오프셋 | 바이트 | 값 | 뜻 |
|---|---|---|---|
| 0x00 | `45 56 46 09 0D 0A FF 00` | "EVF…" | EWF-E01 조각 파일입니다. |
| 0x09 | `01 00` | 1 | 첫 조각 파일입니다. |
| 0x0D | `68 65 61 64 65 72 32 00 …` | "header2" | 첫 섹션은 header2 입니다. 섹션 설명자는 0x0D 에서 시작합니다. |
| 0x1D | `D1 01 00 00 00 00 00 00` | 0x1D1 | 다음 섹션 설명자는 이 파일의 0x1D1 에 있습니다. |
| 0x25 | `C4 01 00 00 00 00 00 00` | 0x1C4 (452) | 이 섹션의 크기입니다. |
| 0x55 | `xx xx xx xx` | | 섹션 설명자의 Adler-32 체크섬입니다. |

순서는 이렇습니다.

1. 조각 파일을 모두 모읍니다. 이름이 .E01 부터 빠짐없이 이어지는지 봅니다.
2. 조각 파일마다 서명과 조각 번호를 확인합니다. 조각 번호가 이름 순서와 맞아야 합니다.
3. 섹션 설명자를 사슬처럼 따라갑니다. 종류를 읽고, 다음 섹션 오프셋으로 건너뜁니다.
4. 조각 파일이 next 로 끝나면 다음 조각 파일로 넘어갑니다. 마지막 조각 파일은 done 으로 끝나야 합니다.
5. header 와 header2 의 zlib 데이터를 풀어 사건 번호, 증거 번호, 수집 일시를 읽습니다.
6. volume 섹션에서 매체 종류, 섹터당 바이트 수, 전체 섹터 수, 청크당 섹터 수를 읽습니다.
7. table 섹션의 항목으로 청크 위치를 구합니다. 최상위 비트로 압축 여부를 판별합니다.
8. 청크를 풀어 이어 붙인 매체 데이터로 해시를 다시 계산합니다. hash·digest 섹션의 값과 비교합니다.
9. error2 섹션이 있으면 읽기 오류 구간을 따로 적어 둡니다.

### VHDX

1. 오프셋 0 에서 `vhdxfile` 을 확인합니다.
2. 서명 `head` 로 이미지 헤더 두 벌을 찾습니다. 두 헤더의 순번과 GUID 를 모두 적어 둡니다.
3. 서명 `regi` 로 영역 표를 찾습니다. BAT 와 메타데이터 영역의 GUID 로 두 영역의 위치를 구합니다.
4. 메타데이터에서 파일 매개변수를 읽습니다. 블록 크기와 고정·동적·차등 여부를 정합니다.
5. 차등 이미지라면 부모 위치 키로 부모 파일을 찾습니다. 부모 헤더의 데이터 쓰기 GUID 가 parent_linkage 와 같은지 봅니다.
6. BAT 항목에서 블록 상태와 위치를 읽습니다. 동적·차등 이미지의 BAT 에는 섹터 비트맵 항목도 들어 있습니다. 그래서 블록 번호를 BAT 항목 번호로 바로 쓰지 않습니다.
7. 상태가 6 이면 이 파일에서 읽습니다. 차등 이미지에서 부모에 있는 섹터는 섹터 비트맵으로 구분해 부모에서 읽습니다.

### VMDK

1. 설명 파일을 엽니다. monolithicSparse 라면 sparse 헤더의 내장 설명 위치 (28) 와 크기 (36) 로 설명을 찾습니다. 두 값은 섹터 단위이므로 512 를 곱해 바이트로 바꿉니다.
2. createType 과 조각 줄을 읽어 조각 파일 목록을 만듭니다. 조각 줄의 섹터 수를 더하면 디스크 크기입니다.
3. parentCID 가 `ffffffff` 가 아니면 parentFileNameHint 로 부모를 찾습니다. 부모도 같은 방법으로 끝까지 따라갑니다.
4. sparse 조각마다 서명 `KDMV`, 판, 그레인 크기, 그레인 디렉터리 위치를 읽습니다.
5. 조각 안의 섹터 번호를 그레인 크기로 나눠 그레인 번호를 구합니다.
6. 그레인 번호를 512 로 나눈 몫이 그레인 디렉터리 항목 번호이고, 나머지가 그레인 표 안의 항목 번호입니다.
7. 그레인 표 항목이 빈 그레인을 뜻하면 부모 이미지에서 같은 섹터를 읽습니다. 부모가 없으면 빈 그레인입니다.
8. streamOptimized 에서 그레인 디렉터리 위치가 -1 이면 파일 끝의 꼬리를 먼저 읽습니다.

## 포렌식에서 중요한 점

### 매체 해시와 파일 해시

EWF 의 hash·digest 값은 매체 데이터의 해시입니다. 조각 파일에는 섹션 설명자, 체크섬, 압축한 청크가 섞여 있어서 조각 파일 자체의 해시는 매체 해시와 다릅니다. 압축하지 않은 청크의 Adler-32 는 청크 하나가 손상됐는지 보는 값이라 이미지 전체의 해시를 대신하지 못합니다.
- 해시를 비교하는 절차는 [증거 획득](../../03-techniques/process-acquisition/evidence-acquisition/index.md)에서 다룹니다.

### 읽기 오류로 채운 구간

EnCase 는 읽기 오류가 난 섹터를 0 으로 채우므로, error2 섹션에 적힌 구간의 0 은 원래 매체의 내용이 아닙니다. 이 구간을 "비어 있던 곳" 으로 해석하지 않습니다.

### EWF 손상·조작 사례

알려진 사례는 아래와 같습니다.

- **두 이미지 숨기기 (dual image).** 섹션 설명자에는 "다음 섹션 오프셋" 과 "섹션 크기" 가 둘 다 있습니다. 한쪽만 읽는 도구에게는 이미지 두 개를 한 파일에 숨길 수 있습니다. 최신 libewf 는 이런 파일을 손상으로 봅니다.
- **표 오프셋 넘침.** EnCase 6.7.1 은 sectors 섹션이 2048 MiB 를 넘으면 표 오프셋이 32비트를 다 써서 넘칩니다. 6.8 에서 사라진 버그로 보입니다.
- **묶음 GUID 가 바뀐 이미지.** 원격 수집 이미지에서 조각 파일 묶음 GUID 가 중간에 바뀐 사례가 있습니다. EnCase 는 그 이미지를 무효로 봅니다.
- **수집 장비 펌웨어.** 어떤 Tableau TD3 펌웨어는 DEFLATE 비압축 블록의 길이 보수 값을 0 으로 적습니다. libewf 는 이 경우를 처리하지 못합니다.
- **끝까지 뜨지 못한 이미지.** incomplete 섹션이 있으면 원격 수집이 중간에 끊긴 이미지일 수 있습니다.

### 가상 디스크의 비정상 종료와 손상

- VMDK sparse 헤더의 72 에는 "깨끗이 닫히지 않음" 표시가 있습니다. COWD 조각은 1648 에 같은 값이 있습니다. 가상 머신이 정상으로 닫히지 않은 채 복사한 디스크인지 이 값으로 봅니다.
- VHDX 의 로그는 메타데이터 저널입니다. 로그가 남은 VHDX 를 도구가 어떻게 처리했는지 기록합니다.
- VMDK sparse 헤더의 73~76 줄바꿈 문자가 `0A 20 0D 0A` 가 아니면 파일을 옮기다 줄바꿈이 바뀐 손상을 의심합니다.
- 잘린 streamOptimized 파일도 512바이트 표지를 검색하면 일부 그레인을 되살릴 수 있습니다.
- qemu-img 가 만든 VMDK 에서 그레인 표 전체 크기가 용량보다 큰 사례가 있습니다. 표 크기와 용량이 맞지 않는다는 이유만으로 조작이라고 보지 않습니다.

### 차등 사슬

VHDX 차등 이미지는 부모에 있는 블록과 섹터를 담지 않고, VMDK 차등 이미지도 빈 그레인을 부모에서 읽습니다. 사슬의 파일 하나라도 빠지면 그 구간은 읽을 수 없습니다.

VMDK 의 CID 는 디스크를 연 뒤 처음 내용이 바뀔 때 새 값으로 바뀝니다. 부모 디스크 사본을 열어 내용이 바뀌면 부모의 CID 도 바뀝니다. 그래서 사슬의 파일은 사본으로만 엽니다.

### 사본에서 작업하기

- 이미지에서 꺼낸 파일은 원본을 열면 바뀔 수 있습니다. ESE 데이터베이스가 그런 예입니다. 늘 사본에서 작업합니다.
- 희소 스트림을 꺼낼 때 빈 구간을 0 으로 채우는지 건너뛰는지에 따라 크기와 해시가 달라집니다. `$UsnJrnl:$J` 가 그런 예입니다. 어떻게 뽑았는지 기록합니다.

## 함정

1. **조각 파일의 해시를 매체 해시로 적습니다.** 비교할 값은 hash·digest 섹션의 매체 해시입니다.
2. **조각 파일 일부만 받습니다.** 마지막으로 받은 조각 파일이 done 으로 끝나는지 확인합니다. next 로 끝나면 뒤 조각이 빠졌습니다.
3. **매체 종류 값을 그대로 믿습니다.** FTK Imager 2.9 전 버전은 이동식 매체도 고정식 (0x01) 으로 적었습니다.
4. **수집 일시를 UTC 로 가정합니다.** 도구와 버전에 따라 현지 시각입니다. EnCase 날짜 문자열의 시간대는 실제 데이터로 확인합니다.
5. **L01 의 1970-01-01 을 실제 수집 일시로 읽습니다.** EnCase 6~7 이 채운 값입니다.
6. **비밀번호 해시 (p) 가 있으니 이미지가 암호화됐다고 봅니다.** 도구가 확인하는 데만 쓰는 값입니다.
7. **VHDX 차등 이미지를 가상 디스크 ID 로 부모와 짝짓습니다.** 차등과 부모는 ID 가 같습니다. 데이터 쓰기 GUID 로 짝짓습니다.
8. **VHDX 두 헤더 가운데 하나만 봅니다.** 두 헤더가 다를 수 있습니다. 둘 다 적어 둡니다.
9. **VMDK 설명 파일을 빼고 조각 파일만 받습니다.** monolithicSparse 가 아니면 설명 파일이 따로 있어야 조각 순서와 부모를 알 수 있습니다.
10. **VMDK 그레인 표 항목 1 을 위치로 읽습니다.** 판 2 부터는 플래그에 따라 빈 그레인일 수 있습니다.

## 도구

- 헥스 편집기로 위 순서를 직접 따라갈 수 있습니다. 서명 `EVF`, `vhdxfile`, `head`, `regi`, `metadata`, `KDMV`, `COWD` 를 찾는 데서 시작합니다.
- libyal 의 libewf·libvhdi·libvmdk 는 이 형식들의 문서를 공개한 오픈 소스 라이브러리입니다. 한 도구로 만든 이미지를 다른 구현으로 다시 읽어 볼 때 예로 들 수 있습니다.
- 시험용 VHDX 는 Windows 의 Diskpart 로 만들 수 있습니다.
- 두 도구의 결과가 다르면 [도구 결과 교차 검증](../../03-techniques/reporting/tool-validation.md)의 방법으로 헥스와 맞춰 봅니다.
