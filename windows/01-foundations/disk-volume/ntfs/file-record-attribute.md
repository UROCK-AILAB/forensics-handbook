# MFT 레코드와 속성 (FILE Record·Attribute)

상위 페이지: [NTFS 구조 (NTFS)](index.md)

## 한 줄 요약

NTFS 는 파일마다 MFT 안에 크기가 정해진 칸을 하나 이상 둡니다. 이 칸을 MFT 레코드 (MFT Entry·File Record Segment) 라고 하며, 레코드 하나에는 헤더 하나와 속성 (Attribute) 여러 개가 들어 있습니다. 파일 이름·시각·내용 위치는 모두 속성에 담깁니다.

## 이 형식을 쓰는 아티팩트

Microsoft 문서에 따르면 NTFS 볼륨의 모든 파일은 MFT 에 항목이 적어도 하나 있고 MFT 자신도 여기에 들어갑니다. 아래 아티팩트와 기법은 레코드 구조나 레코드를 가리키는 번호를 그대로 씁니다.

| 아티팩트·기법 | 이 페이지와 닿는 부분 |
|---|---|
| [마스터 파일 테이블 ($MFT)](../../../02-artifacts/filesystem/mft.md) | 레코드를 모두 모아 둔 파일입니다. |
| [폴더 인덱스와 슬랙 ($I30)](../../../02-artifacts/filesystem/i30.md) | 폴더 레코드의 인덱스 속성(0x90·0xA0)에 들어 있습니다. 인덱스 항목마다 파일 참조 (File Reference) 가 있습니다. |
| [USN 변경 저널 ($UsnJrnl)](../../../02-artifacts/filesystem/usnjrnl.md) | 기록마다 바뀐 파일과 부모 폴더의 파일 참조를 담습니다. |
| [NTFS 트랜잭션 로그 ($LogFile)](../../../02-artifacts/filesystem/logfile.md) | 레코드 헤더의 LSN 이 이 로그의 기록 번호입니다. |

| [파일시스템 기반 복구 (Undelete)](../../../03-techniques/analysis/data-recovery/undelete-ntfs-fat.md) | 사용 중 표시가 꺼진 레코드에서 파일을 되살립니다. |
| [레코드 카빙 (Record Carving)](../../../03-techniques/analysis/data-recovery/record-carving.md) | `FILE` 서명으로 비할당 영역이나 페이지 파일에서 레코드를 찾습니다. |

## 구조

### 레코드가 놓이는 자리

MFT 는 `$MFT` 라는 파일이고 0번 레코드가 `$MFT` 자신을 기록합니다. `$MFT` 의 시작 위치와 레코드 크기는 부트 섹터에 적혀 있으며, 읽는 법은 [부트 섹터와 클러스터](boot-sector-cluster.md) 에서 다룹니다. 레코드 크기는 보통 1,024바이트이지만 4K 네이티브 섹터 디스크처럼 4,096바이트인 볼륨도 있습니다. 레코드 번호 N 은 `$MFT` 내용 안에서 "N × 레코드 크기" 위치에 있습니다.

`$MFT` 도 조각날 수 있으므로 디스크 위 실제 위치는 0번 레코드의 `$DATA` 데이터 런으로 구합니다. 데이터 런은 [데이터 런과 상주·비상주 데이터](data-run-resident-non-resident.md) 에서 다룹니다. 파일을 지우면 그 레코드는 빈 칸으로 표시되고 나중에 다시 쓰이며, 한번 늘어난 `$MFT` 는 파일을 지워도 줄어들지 않습니다.

0번부터 11번까지는 정해진 메타 파일이 차지합니다. 0번은 `$MFT`, 1번은 `$MFTMirr`, 2번은 `$LogFile`, 5번은 루트 폴더입니다. `$MFTMirr` 는 앞 레코드 4개의 백업이며, 나머지 메타 파일은 [NTFS 메타 파일](bitmap-secure-extend.md) 에서 다룹니다.

> 그림 자리: 1,024바이트 레코드 한 개 안에 헤더 → 고침 값 배열 → 속성 여러 개 → 끝 표시(0xFFFFFFFF) → 슬랙이 차례로 놓인 모습

### 레코드 헤더

아래 표는 NTFS 3.1(Windows XP 이후) 기준입니다. 값은 모두 리틀 엔디언입니다.

| 오프셋 | 크기 | 필드 | 뜻 |
|---|---|---|---|
| 0x00 | 4 | 서명 | 정상이면 `FILE` 입니다. 손상된 레코드에는 `BAAD` 가 적힙니다. |
| 0x04 | 2 | 고침 값 배열 위치 | 레코드 시작에서 잰 거리입니다. |
| 0x06 | 2 | 고침 값 개수 | 표시 값 1개를 포함한 개수입니다. |
| 0x08 | 8 | LSN | 이 레코드와 이어진 `$LogFile` 기록 번호입니다. |
| 0x10 | 2 | 순번 (Sequence Number) | 레코드가 해제될 때마다 1 늘어납니다. |
| 0x12 | 2 | 링크 수 | 하드 링크 수입니다. |
| 0x14 | 2 | 첫 속성 위치 | 레코드 시작에서 잰 거리입니다. |
| 0x16 | 2 | 플래그 | 아래 표를 봅니다. |
| 0x18 | 4 | 사용 크기 | 레코드에서 실제로 쓰는 바이트 수입니다. |
| 0x1C | 4 | 전체 크기 | 레코드 크기입니다. |
| 0x20 | 8 | 기본 레코드 참조 | 기본 레코드면 0 입니다. 확장 레코드면 기본 레코드의 파일 참조가 들어 있습니다. |
| 0x28 | 2 | 다음 속성 번호 | 새 속성에 줄 번호입니다. |
| 0x2A | 2 | (문서화되지 않음) | libyal 문서도 쓰임을 모른다고 적습니다. |
| 0x2C | 4 | 레코드 번호 | 이 레코드 자신의 번호입니다. NTFS 3.1 에만 있습니다. |

| 플래그 값 | 뜻 |
|---|---|
| 0x0001 | 사용 중입니다. |
| 0x0002 | 파일 이름 인덱스(`$I30`)가 있습니다. 곧 폴더입니다. |
| 0x0004 | 이름은 `MFT_RECORD_IN_EXTEND` 입니다. libyal 문서는 뜻을 모른다고 적습니다. |
| 0x0008 | 이름은 `MFT_RECORD_IS_VIEW_INDEX` 입니다. `$I30` 이 아닌 다른 인덱스(뷰 인덱스)가 있습니다. |

### 고침 값 (Fixup·Update Sequence Array)

NTFS 는 레코드를 디스크에 쓸 때 512바이트 블록마다 끝 2바이트를 같은 "표시 값"으로 바꿔 쓰고, 원래 있던 2바이트는 헤더 뒤의 고침 값 배열에 따로 적습니다. 배열의 첫 2바이트가 표시 값이고 그 뒤로 블록마다 원래 값 2바이트가 이어집니다. 1,024바이트 레코드는 블록이 2개이므로 개수가 3이며, 블록 크기는 "레코드 크기 ÷ (개수 − 1)" 로 맞춰 볼 수 있습니다.

Microsoft 문서는 이 배열이 여러 섹터에 걸친 쓰기를 보호한다고 설명합니다. 블록 끝 2바이트가 표시 값과 다르면 그 블록은 같은 쓰기에서 온전히 기록되지 않은 것입니다.

### 파일 참조 (File Reference)

파일 참조는 레코드 하나를 가리키는 8바이트 값입니다.

| 오프셋 | 크기 | 필드 |
|---|---|---|
| 0 | 6 | 레코드 번호 (48비트) |
| 6 | 2 | 순번 |

파일 참조는 기본 레코드 참조, `$FILE_NAME` 의 부모 폴더 참조, `$I30` 인덱스 항목, USN 기록, `$ATTRIBUTE_LIST` 항목에 쓰이고, 참조 안의 순번 0 은 예약된 값입니다. Microsoft 문서에 따르면 참조의 순번은 레코드 헤더의 순번과 같아야 하며, 두 값이 다르면 그 참조는 틀렸고 대개 낡은 것입니다.

### 속성 헤더

모든 속성은 16바이트 공통 헤더로 시작합니다. 오프셋은 속성 시작에서 잰 값입니다.

| 오프셋 | 크기 | 필드 | 뜻 |
|---|---|---|---|
| 0 | 4 | 형식 번호 | 아래 "속성 종류" 표를 봅니다. |
| 4 | 4 | 속성 길이 | 헤더를 포함한 길이입니다. 8의 배수입니다. |
| 8 | 1 | 비상주 표시 | 0 이면 상주, 1 이면 비상주입니다. |
| 9 | 1 | 이름 길이 | UTF-16 글자 수입니다. 이름이 없으면 0 입니다. 최대 255자입니다. |
| 10 | 2 | 이름 위치 | 속성 시작에서 잰 거리입니다. |
| 12 | 2 | 데이터 플래그 | 0x0001 압축, 0x4000 암호화, 0x8000 희소입니다. |
| 14 | 2 | 속성 번호 | 레코드 안에서 속성마다 다른 번호입니다. |

값이 레코드 안에 있으면 상주 (Resident) 속성입니다. 공통 헤더 뒤에 8바이트가 붙습니다.

| 오프셋 | 크기 | 필드 |
|---|---|---|
| 16 | 4 | 값 크기 |
| 20 | 2 | 값 위치 (속성 시작에서 잰 거리) |
| 22 | 1 | 인덱스 표시 |
| 23 | 1 | 채움 |

값이 레코드 밖 클러스터에 있으면 비상주 (Non-resident) 속성입니다. 공통 헤더 뒤에 아래 칸이 붙습니다.

| 오프셋 | 크기 | 필드 |
|---|---|---|
| 16 | 8 | 첫 VCN |
| 24 | 8 | 마지막 VCN |
| 32 | 2 | 데이터 런 위치 |
| 34 | 2 | 압축 단위 (2의 n승 클러스터) |
| 40 | 8 | 할당 크기 |
| 48 | 8 | 파일 크기 |
| 56 | 8 | 유효 데이터 크기 |
| 64 | 8 | 실제 할당 합계 (압축 속성에 있음) |

Microsoft 문서에 따르면 세 크기 칸(40·48·56)은 첫 VCN 이 0 인 조각에서만 믿을 수 있습니다. 데이터 런의 풀이는 [데이터 런과 상주·비상주 데이터](data-run-resident-non-resident.md) 에서 다룹니다.

### 속성 종류

| 형식 번호 | 이름 | 내용 | 자세히 |
|---|---|---|---|
| 0x10 | `$STANDARD_INFORMATION` | 시각 4개, 파일 특성, 보안 번호 등입니다. 48 또는 72바이트입니다. | [두 벌의 시각](standard-information-file-name.md) |
| 0x20 | `$ATTRIBUTE_LIST` | 속성이 여러 레코드에 흩어졌을 때의 목록입니다. | 아래 절 |
| 0x30 | `$FILE_NAME` | 이름, 부모 폴더 참조, 시각 4개입니다. | [두 벌의 시각](standard-information-file-name.md) |
| 0x40 | `$OBJECT_ID` | 링크 추적 서비스가 붙인 개체 식별자입니다. | [바로가기 파일](../../../02-artifacts/file-folder-usage/lnk.md) |
| 0x50 | `$SECURITY_DESCRIPTOR` | 보안 설명자입니다. NTFS 3.0 이후에는 보통 `$Secure` 에 모아 둡니다. | [NTFS 메타 파일](bitmap-secure-extend.md) |
| 0x60 | `$VOLUME_NAME` | 볼륨 이름입니다. `$Volume` 에만 있습니다. | |
| 0x70 | `$VOLUME_INFORMATION` | 볼륨 정보입니다. `$Volume` 에만 있습니다. | |
| 0x80 | `$DATA` | 파일 내용입니다. 이름이 붙은 `$DATA` 는 대체 데이터 스트림입니다. | [ADS](ads.md) |
| 0x90 | `$INDEX_ROOT` | 인덱스의 뿌리입니다. 작은 폴더는 항목이 모두 여기에 들어갑니다. | [$I30](../../../02-artifacts/filesystem/i30.md) |
| 0xA0 | `$INDEX_ALLOCATION` | 큰 폴더의 인덱스 블록입니다. | [$I30](../../../02-artifacts/filesystem/i30.md) |
| 0xB0 | `$BITMAP` | 인덱스 블록의 사용 표시입니다. | |
| 0xC0 | `$REPARSE_POINT` | 리파스 포인트 데이터입니다. | [링크와 리파스 포인트](hard-link-junction-reparse-point.md) |
| 0xD0 | `$EA_INFORMATION` | 확장 속성 정보입니다. | |
| 0xE0 | `$EA` | 확장 속성입니다. | |
| 0x100 | `$LOGGED_UTILITY_STREAM` | EFS 암호화 정보 등이 들어갑니다. | [EFS 암호화 파일](../../../03-techniques/analysis/encrypted-evidence/encrypting-file-system.md) |
| 0xFFFFFFFF | 끝 표시 | 속성 목록이 여기서 끝납니다. | |

`$FILE_NAME` 의 이름공간 값은 0 POSIX, 1 Win32, 2 DOS(8.3 짧은 이름), 3 DOS 와 Win32 겸용입니다. 압축·희소 플래그의 뜻은 [압축·희소 파일](compressed-sparse.md) 에서 다룹니다.

### 속성 목록 ($ATTRIBUTE_LIST) 과 확장 레코드

속성이 한 레코드에 다 들어가지 않으면 NTFS 는 레코드를 더 쓰는데, 심하게 조각난 파일이나 하드 링크가 많은 파일에서 생깁니다. 처음 레코드를 기본 레코드 (Base Record), 더 쓴 레코드를 확장 레코드 (Extension Record) 라고 합니다. 기본 레코드에는 `$ATTRIBUTE_LIST` 가 생기며 이 목록은 속성마다 어느 레코드에 있는지 적습니다. 확장 레코드의 헤더 0x20 에는 기본 레코드의 파일 참조가 들어 있습니다. `$ATTRIBUTE_LIST` 자체도 비상주가 될 수 있고, 그러면 목록 내용은 `$MFT` 밖 클러스터에 있습니다.

목록 항목 하나의 구조는 다음과 같습니다.

| 오프셋 | 크기 | 필드 |
|---|---|---|
| 0 | 4 | 속성 형식 번호 |
| 4 | 2 | 항목 길이 |
| 6 | 1 | 이름 길이 |
| 7 | 1 | 이름 위치 |
| 8 | 8 | 이 조각의 첫 VCN |
| 16 | 8 | 속성이 있는 레코드의 파일 참조 |
| 24 | 2 | 속성 번호 |

26바이트 뒤에 UTF-16LE 속성 이름과 채움 바이트가 옵니다.

### 버전별 차이

| 항목 | 차이 |
|---|---|
| 헤더 0x2C | NTFS 3.1(Windows XP 이후)에는 레코드 자신의 번호가 들어갑니다. NTFS 3.0(Windows 2000)에서는 쓰임이 알려지지 않았습니다. |
| 속성 0x40·0xC0·0x100, 메타 파일 `$Secure` | libyal 문서는 NTFS 3.0 부터 있다고 적습니다. |
| `$STANDARD_INFORMATION` 크기 | libyal 문서는 48 또는 72바이트라고 적습니다. 자세한 차이는 [두 벌의 시각](standard-information-file-name.md) 에서 다룹니다. |
| 레코드 슬랙 처리 | Windows 버전마다 다르다는 시험 결과가 있습니다. 아래 "레코드 슬랙" 절을 봅니다. |

## 읽는 법

1. 부트 섹터에서 `$MFT` 시작 클러스터와 레코드 크기를 읽습니다.
2. 0번 레코드를 읽고 `$DATA` 데이터 런으로 `$MFT` 전체의 위치를 구합니다.
3. 원하는 번호의 레코드를 "번호 × 레코드 크기" 위치에서 읽습니다.
4. 서명을 봅니다. `FILE` 이 아니면 해석을 멈추고 까닭을 따로 봅니다. `BAAD` 는 손상된 레코드입니다.
5. 고침 값을 적용합니다. 블록마다 끝 2바이트가 표시 값과 같은지 확인하고 원래 값으로 되돌립니다.
6. 헤더에서 플래그, 순번, 기본 레코드 참조를 읽습니다.
7. 첫 속성 위치에서 출발해 속성 길이만큼 건너뛰며 속성을 읽습니다.
8. 형식 번호 0xFFFFFFFF 를 만나면 멈춥니다. 속성 길이가 0 이거나 사용 크기를 넘으면 손상으로 보고 멈춥니다.
9. 기본 레코드 참조가 0 이 아니면 확장 레코드입니다. 기본 레코드와 합쳐서 해석합니다.

### 헥스로 한 번 따라가기

아래 바이트는 libyal 명세와 Microsoft 구조체 문서에 맞춰 만든 예시입니다. 실제 검체에서 뽑은 값이 아닙니다.

```
오프셋  00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F
0000    46 49 4C 45 30 00 03 00 5A 3C 21 04 00 00 00 00   FILE0...Z<!.....
0010    05 00 01 00 38 00 01 00 30 01 00 00 00 04 00 00   ....8...0.......
0020    00 00 00 00 00 00 00 00 03 00 00 00 2A 1B 00 00   ............*...
0030    0A 00 00 00 00 00 00 00 10 00 00 00 60 00 00 00   ............`...
0040    00 00 18 00 00 00 00 00 48 00 00 00 18 00 00 00   ........H.......
```

| 오프셋 | 바이트 | 읽은 값 | 뜻 |
|---|---|---|---|
| 0x00 | `46 49 4C 45` | `FILE` | 정상 서명입니다. |
| 0x04 | `30 00` | 0x30 | 고침 값 배열이 0x30 에서 시작합니다. |
| 0x06 | `03 00` | 3 | 표시 값 1개와 원래 값 2개입니다. |
| 0x08 | `5A 3C 21 04 00 00 00 00` | 0x04213C5A | LSN 입니다. |
| 0x10 | `05 00` | 5 | 순번입니다. |
| 0x12 | `01 00` | 1 | 링크 수입니다. |
| 0x14 | `38 00` | 0x38 | 첫 속성이 0x38 에 있습니다. |
| 0x16 | `01 00` | 0x0001 | 사용 중이고 폴더가 아닙니다. |
| 0x18 | `30 01 00 00` | 0x130 (304) | 사용 크기입니다. |
| 0x1C | `00 04 00 00` | 0x400 (1,024) | 레코드 크기입니다. |
| 0x20 | `00` × 8 | 0 | 기본 레코드입니다. |
| 0x28 | `03 00` | 3 | 다음에 줄 속성 번호입니다. |
| 0x2C | `2A 1B 00 00` | 0x1B2A (6,954) | 이 레코드의 번호입니다. |
| 0x30 | `0A 00` | 0x000A | 표시 값입니다. |
| 0x32 | `00 00 00 00` | | 블록 두 개의 원래 끝 2바이트입니다. |

고침 값은 이렇게 적용합니다. 오프셋 0x1FE 와 0x3FE 의 2바이트가 `0A 00` 인지 봅니다. 같으면 둘 다 배열에 적힌 원래 값 `00 00` 으로 되돌립니다.

이 파일의 파일 참조는 레코드 번호 6,954 와 순번 5 를 합친 값입니다. 디스크에는 `2A 1B 00 00 00 00 05 00` 로 적힙니다.

0x38 의 첫 속성은 형식 0x10(`$STANDARD_INFORMATION`)이고 길이는 0x60 입니다. 0x40 의 비상주 표시가 0 이므로 상주 속성입니다. 값 크기는 0x48(72바이트)이고 값 위치는 속성 시작에서 0x18 이므로 값은 레코드의 0x50 에서 시작합니다. 이 예시 레코드의 속성을 끝까지 따라가면 다음과 같습니다.

| 속성 위치 | 형식 | 길이 | 다음 속성 위치 |
|---|---|---|---|
| 0x38 | 0x10 `$STANDARD_INFORMATION` (상주) | 0x60 | 0x98 |
| 0x98 | 0x30 `$FILE_NAME` (상주, 8글자 이름) | 0x70 | 0x108 |
| 0x108 | 0x80 `$DATA` (상주, 내용 5바이트) | 0x20 | 0x128 |
| 0x128 | 0xFFFFFFFF 끝 표시 | | |

같은 파일을 지운 뒤 레코드가 아직 재사용되지 않았다면 두 칸이 바뀌어, 0x16 의 플래그는 `00 00` 이 되고 0x10 의 순번은 해제 규칙에 따라 `06 00` 이 됩니다. USN 기록 같은 곳에 남은 옛 참조에는 여전히 순번 5 가 적혀 있습니다.

## 포렌식에서 중요한 점

### 지운 파일의 레코드

파일을 지우면 헤더의 사용 중 플래그(0x0001)가 꺼지지만, 레코드가 다시 쓰이기 전까지 이름·시각·크기·데이터 런은 그대로 남습니다. 순번은 레코드가 해제될 때 1 늘어나므로 옛 참조의 순번과 지금 순번을 비교하면 재사용 여부를 가릴 수 있습니다.

| 옛 참조와 비교한 지금 레코드 | 해석 |
|---|---|
| 순번이 같고 사용 중 | 같은 파일이 아직 있습니다. |
| 순번이 1 크고 사용 중이 아님 | 그 파일이 지워진 뒤 아직 재사용되지 않았을 가능성이 높습니다. |
| 순번이 1 크고 사용 중 | 레코드가 다른 파일에 다시 쓰였습니다. |
| 순번이 2 이상 큼 | 해제가 두 번 이상 있었습니다. 그 사이에 레코드가 다른 파일에 쓰였으므로 옛 파일의 속성은 덮였습니다. 슬랙에 조각만 남을 수 있습니다. |

- 파일의 `$FILE_NAME` 에 적힌 부모 참조의 순번이 부모 레코드의 지금 순번과 다를 수 있습니다. 이때는 부모 폴더가 지워졌고 그 레코드가 재사용된 것입니다. 이런 파일은 경로를 끝까지 잇지 못하는 고아 파일로 다룹니다.

### 레코드 안에 든 작은 파일 내용

작은 파일은 내용이 상주 `$DATA` 로 레코드 안에 들어갑니다. 이런 파일은 지워진 뒤 비할당 클러스터가 덮여도 레코드가 남아 있으면 내용을 되살릴 수 있고, 반대로 레코드가 재사용되면 클러스터와 상관없이 내용이 사라질 수 있습니다.

### 레코드 슬랙 (MFT Slack)

레코드의 사용 크기부터 전체 크기까지를 레코드 슬랙이라고 하며, 이 자리에는 예전에 쓰던 속성의 조각이 남을 수 있습니다. Sygnia 의 2025년 시험 결과는 다음과 같습니다.

| 상황 | 남는 것 | 확인 범위 |
|---|---|---|
| 상주 파일이 커져 비상주로 바뀜 | 예전 내용 일부가 슬랙에 남습니다. | Windows XP·7 |
| 상주 파일이 커져 비상주로 바뀜 | 슬랙이 0 으로 채워져 남는 것이 없습니다. | Windows 10 가상 머신 |
| 작은 폴더에서 파일을 지우거나 옮김 | 폴더 레코드 슬랙에 인덱스 항목이 남습니다. 이름·크기·시각 4개를 읽을 수 있습니다. | Windows 10·11 을 포함한 시험한 모든 버전 |

폴더 인덱스 항목의 해석은 [폴더 인덱스와 슬랙 ($I30)](../../../02-artifacts/filesystem/i30.md) 에서 다룹니다.

### 손상된 레코드

고침 값이 맞지 않는 블록은 같은 쓰기에서 끝까지 기록되지 않은 것이며, 이런 레코드는 서명 자리에 `BAAD` 가 적혀 있을 수 있습니다. `$MFTMirr` 는 앞 레코드 4개만 백업하는데, 0번 레코드가 손상되면 여기서 `$MFT` 의 위치를 다시 얻을 수 있습니다.

### 비정상 종료

헤더의 LSN 은 레코드와 `$LogFile` 기록을 이어 주는데, 라이브 시스템이나 비정상 종료 뒤 확보한 이미지에서는 레코드와 `$LogFile` 이 서로 다른 시점을 보여 줄 수 있습니다. 두 자료를 맞춰 보는 법은 [NTFS 트랜잭션 로그 ($LogFile)](../../../02-artifacts/filesystem/logfile.md) 에서 다룹니다.

### 흩어진 레코드 조각

- `FILE` 서명은 비할당 영역, 페이지 파일, 섀도 복사본에서도 찾을 수 있습니다.
- NTFS 3.1 레코드는 헤더 0x2C 에 자기 번호를 담고 있어서 떨어져 나온 레코드도 원래 몇 번이었는지 알 수 있습니다.
- `$FILE_NAME` 의 부모 참조를 따라가면 경로 일부를 다시 세울 수 있습니다.
- 섀도 복사본 안의 `$MFT` 는 [섀도 복사본 활용](../../../03-techniques/analysis/volume-shadow-copy-analysis.md) 에서 다룹니다.

## 함정

- **레코드 크기를 1,024바이트로 못박지 않습니다.** 크기는 부트 섹터 값과 헤더 0x1C 로 확인합니다.
- **고침 값을 빠뜨리지 않습니다.** 적용하지 않으면 각 512바이트 블록의 끝 2바이트가 틀립니다. 이름이나 데이터 런이 그 자리를 지나면 값이 조용히 망가집니다.
- **긴 이름이 확장 레코드에만 있을 수 있습니다.** `$ATTRIBUTE_LIST` 를 쓰는 레코드에서 Win32 긴 이름의 `$FILE_NAME` 이 확장 레코드에만 있는 경우를 봤는데, 이때 기본 레코드만 보면 8.3 짧은 이름만 보이고 확장 레코드는 대개 기본 레코드와 멀리 떨어져 있습니다. (현장 관찰)
- **`$ATTRIBUTE_LIST` 만 믿고 확장 레코드를 찾지 않습니다.** 목록이 비상주이면 `$MFT` 파일만으로는 목록을 읽을 수 없습니다. 이때는 확장 레코드 헤더의 기본 레코드 참조를 거꾸로 따라가 묶습니다.
- **`$FILE_NAME` 은 여러 개일 수 있습니다.** DOS 짧은 이름과 Win32 긴 이름이 따로 있을 수 있고 하드 링크마다 `$FILE_NAME` 이 하나씩 있습니다. 링크마다 부모 폴더가 다를 수 있으므로 경로도 따로 세웁니다.
- **지운 레코드의 순번은 이미 1 늘어나 있습니다.** 도구가 지금 순번을 보여 주는지 확인하고 옛 참조와 비교합니다.
- **비상주 조각의 크기 칸을 그대로 쓰지 않습니다.** 첫 VCN 이 0 이 아닌 조각의 할당·파일·유효 크기 칸은 뜻이 없습니다.
- **사용 중이 아닌 레코드가 모두 지운 파일은 아닙니다.** 한 번도 쓰이지 않은 레코드도 있습니다. 이름 속성이 있는지 함께 봅니다.

## 도구

아래는 공개 도구의 예입니다. 확장 레코드와 슬랙을 다루는 방식은 도구마다 다릅니다. 중요한 레코드는 헥스로 한 번 확인하고 [도구 결과 교차 검증](../../../03-techniques/reporting/tool-validation.md) 의 방법으로 맞춰 봅니다.

- The Sleuth Kit 의 `istat`: 레코드 하나의 헤더와 속성 목록을 보여 줍니다.
- libfsntfs: 참고 문헌 1 의 형식 문서와 함께 배포되는 라이브러리입니다.
- MFTECmd, analyzeMFT: `$MFT` 파일 전체를 표로 풀어 줍니다. Sygnia 는 MFTECmd 가 슬랙의 인덱스 항목을 표시한다고 적습니다.
- dfir_ntfs: Sygnia 는 이 도구가 슬랙 인덱스 항목에서 이름·시각·크기를 되살린다고 적습니다.
- 헥스 편집기: 고침 값 적용 전후를 직접 비교할 때 씁니다.
