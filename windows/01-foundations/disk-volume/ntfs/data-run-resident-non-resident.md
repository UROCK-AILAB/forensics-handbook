# 데이터 런과 상주·비상주 데이터 (Data Run·Resident·Non-resident)

> 위치: 기반 구조 > 디스크·볼륨 > [NTFS 구조](index.md)

## 한 줄 요약

NTFS 속성의 내용은 MFT 레코드 안에 바로 들어가거나 (상주, Resident) 레코드 밖의 클러스터에 놓입니다 (비상주, Non-resident). 비상주일 때 레코드에는 내용 대신 클러스터 위치를 적은 데이터 런 (Data Run) 이 들어갑니다.

## 이 형식을 쓰는 아티팩트

NTFS 의 모든 파일과 폴더가 이 두 형태 중 하나로 내용을 저장합니다. 분석에서 자주 부딪히는 곳은 아래와 같습니다.

| 쓰는 곳 | 이 페이지와 관련된 점 |
|---|---|
| [마스터 파일 테이블 ($MFT)](../../../02-artifacts/filesystem/mft.md) | 작은 파일은 내용이 MFT 레코드 안에 있습니다. |
| [$MFT 자신](boot-sector-cluster.md) | 부트 섹터에는 $MFT 의 첫 클러스터만 있습니다. $MFT 가 조각났으면 레코드 0번의 데이터 런을 따라가야 뒤쪽 레코드를 찾습니다. |
| [대체 데이터 스트림 (ADS)](ads.md)·[Zone.Identifier](../../../02-artifacts/filesystem/zone-identifier.md) | 이름 있는 $DATA 도 크기가 작으면 상주로 들어갈 수 있습니다. |
| [폴더 인덱스 ($I30)](../../../02-artifacts/filesystem/i30.md) | $INDEX_ROOT 는 상주, $INDEX_ALLOCATION 은 비상주입니다. |
| [USN 변경 저널 ($UsnJrnl)](../../../02-artifacts/filesystem/usnjrnl.md) | $J 스트림의 앞부분은 디스크 자리가 없는 희소 런입니다. |
| [파일시스템 기반 복구](../../../03-techniques/analysis/data-recovery/undelete-ntfs-fat.md) | 지운 레코드에 남은 데이터 런으로 옛 클러스터를 찾습니다. |

## 구조

### 두 형태를 가르는 값

속성 헤더의 오프셋 0x08 한 바이트가 형태를 정하며, 0 이면 상주, 1 이면 비상주입니다. 앞 16바이트 공통 헤더(종류·길이·이름·플래그)는 [MFT 레코드와 속성](file-record-attribute.md)에서 다루고, 이 페이지는 오프셋 0x10 부터 달라지는 부분만 다룹니다.

$AttrDef 에는 속성 종류마다 상주로만 둘 수 있는지가 적혀 있습니다. $STANDARD_INFORMATION·$FILE_NAME·$INDEX_ROOT 는 상주로만 저장되고, $DATA 는 두 형태 모두 됩니다. 이 헤더 구조는 NTFS 3.0·3.1 에서 유효합니다[1]. Windows XP 부터 지금까지의 NTFS 는 3.1 이므로 버전에 따른 차이는 없습니다.

> 그림 자리: 1,024바이트 MFT 레코드 두 개를 나란히 놓은 그림. 왼쪽은 $DATA 헤더 바로 뒤에 파일 내용이 있는 상주 레코드. 오른쪽은 $DATA 헤더 뒤에 데이터 런만 있고, 화살표가 볼륨의 떨어진 클러스터 묶음 두 곳을 가리키는 비상주 레코드.

### 상주 형태

오프셋은 속성 첫 바이트 기준입니다.

| 오프셋 | 크기 | 필드 | 설명 |
|---|---|---|---|
| 0x10 | 4 | 값 길이 (ValueLength) | 내용의 바이트 수입니다. |
| 0x14 | 2 | 값 위치 (ValueOffset) | 내용이 속성 첫 바이트에서 몇 바이트 뒤에 있는지입니다. |
| 0x16 | 1 | 색인 플래그 | 색인에 쓰이는 속성인지 표시합니다. |
| 0x17 | 1 | 채움 | 0 입니다. |

상주 헤더는 24바이트 (0x18) 입니다. 이름 없는 $DATA 는 대개 0x18 에서 내용이 바로 시작하지만, 이름 있는 속성은 헤더와 내용 사이에 이름이 들어가므로 값 위치 필드를 꼭 읽어야 합니다. 속성 전체 길이는 8바이트 배수로 맞춥니다.

상주 $DATA 가 몇 바이트까지 들어가는지는 정해진 값이 없습니다. 내용이 대략 700바이트를 넘으면 비상주가 됩니다[6]. 이때 MFT 레코드는 보통 1,024바이트입니다. 실제 경계는 레코드 크기와 파일 이름 길이처럼 다른 속성이 차지한 자리에 따라 달라집니다.

### 비상주 형태

| 오프셋 | 크기 | 필드 | 설명 |
|---|---|---|---|
| 0x10 | 8 | 시작 VCN (LowestVcn) | 이 속성이 맡은 첫 VCN 입니다. |
| 0x18 | 8 | 끝 VCN (HighestVcn) | 이 속성이 맡은 마지막 VCN 입니다. |
| 0x20 | 2 | 런 목록 위치 (MappingPairsOffset) | 데이터 런이 속성 첫 바이트에서 몇 바이트 뒤에 있는지입니다. |
| 0x22 | 2 | 압축 단위 | 2^n 클러스터입니다. 0 이면 압축하지 않은 속성입니다. |
| 0x24 | 4 | 예약 | 0 입니다. |
| 0x28 | 8 | 할당 크기 (AllocatedLength) | 잡아 둔 공간의 바이트 수입니다. 클러스터 크기의 배수입니다. |
| 0x30 | 8 | 데이터 크기 (FileSize) | 파일 크기입니다. 읽을 수 있는 마지막 바이트 + 1 입니다. |
| 0x38 | 8 | 유효 데이터 길이 (ValidDataLength) | 실제로 써 넣은 마지막 바이트 + 1 입니다. |
| 0x40 | 8 | 전체 할당 (TotalAllocated) | 압축 단위가 0 보다 클 때만 있습니다[3]. |

비상주 헤더는 64바이트 또는 72바이트입니다. 0x28·0x30·0x38 의 세 크기 값은 시작 VCN 이 0 인 속성에서만 뜻이 있습니다. 유효 데이터 길이 너머를 읽으면 Windows 는 0 을 돌려주고, 데이터 크기는 그대로입니다.

### 데이터 런

가상 클러스터 번호 (VCN) 와 논리 클러스터 번호 (LCN) 의 뜻은 [부트 섹터와 클러스터](boot-sector-cluster.md)에 있습니다. 데이터 런 하나는 "VCN 몇 개가 어느 LCN 부터 이어서 놓였는지" 를 적은 덩어리이고, 데이터 런을 이어 적은 것이 런 목록 (Runlist) 입니다. 매핑 쌍 (Mapping Pairs) 이라고도 합니다[1].

런 하나는 이렇게 생겼습니다.

| 위치 | 크기 | 뜻 |
|---|---|---|
| 첫 바이트 아래 4비트 | 4비트 | 길이 필드가 몇 바이트인지 |
| 첫 바이트 위 4비트 | 4비트 | 위치 필드가 몇 바이트인지. 0 이면 희소 런입니다. |
| 그다음 | 길이 필드 크기 | 클러스터 개수 |
| 그다음 | 위치 필드 크기 | 앞 런의 LCN 에서 옮겨 간 양 |

읽는 규칙은 다섯 가지입니다.

1. 길이와 위치는 작은 쪽 바이트가 앞에 옵니다 (리틀 엔디언).
2. 위치 값은 부호 있는 수입니다. 가장 높은 바이트의 맨 위 비트가 1 이면 음수입니다.
3. 위치 값은 바로 앞 런의 LCN 에 더하는 변화량입니다. 첫 런은 0 에 더하므로 사실상 절대 위치입니다.
4. 위치 필드 크기가 0 인 런은 희소 런 (Sparse Run) 입니다. 이 구간은 디스크 자리가 없고 0 으로 읽습니다.
5. 첫 바이트가 0x00 이면 목록이 끝납니다.

## 읽는 법

> 아래 바이트는 모두 명세(Microsoft Learn·libfsntfs)대로 만든 예시입니다. 실제 데이터에서 뽑은 값이 아닙니다.

### 상주 데이터 한 번 따라가기

5바이트짜리 파일 "Hello" 의 $DATA 속성입니다.

```
오프셋  00 01 02 03 04 05 06 07  08 09 0A 0B 0C 0D 0E 0F
0x00    80 00 00 00 20 00 00 00  00 00 18 00 00 00 01 00
0x10    05 00 00 00 18 00 00 00  48 65 6C 6C 6F 00 00 00
```

1. 0x00 의 `80 00 00 00` 은 속성 종류 $DATA (0x80) 입니다.
2. 0x04 의 `20 00 00 00` 은 속성 전체 길이 32바이트입니다.
3. 0x08 의 `00` 은 상주라는 뜻입니다.
4. 0x10 의 `05 00 00 00` 은 내용이 5바이트라는 뜻입니다.
5. 0x14 의 `18 00` 은 내용이 속성 첫 바이트에서 0x18 뒤에 있다는 뜻입니다.
6. 0x18 부터 5바이트 `48 65 6C 6C 6F` 가 파일 내용 "Hello" 입니다.
7. 뒤의 `00 00 00` 은 8바이트 배수를 맞춘 채움입니다.

### 비상주 헤더와 런 따라가기

클러스터가 4,096바이트인 볼륨에 있는 160,000바이트 파일입니다. 파일은 두 조각으로 나뉘어 있습니다.

```
오프셋  00 01 02 03 04 05 06 07  08 09 0A 0B 0C 0D 0E 0F
0x00    80 00 00 00 50 00 00 00  01 00 40 00 00 00 02 00
0x10    00 00 00 00 00 00 00 00  27 00 00 00 00 00 00 00
0x20    40 00 00 00 00 00 00 00  00 80 02 00 00 00 00 00
0x30    00 71 02 00 00 00 00 00  00 71 02 00 00 00 00 00
0x40    31 20 00 60 01 11 08 F0  00 00 00 00 00 00 00 00
```

| 오프셋 | 값 | 뜻 |
|---|---|---|
| 0x08 | `01` | 비상주입니다. |
| 0x10 | 0 | 시작 VCN 은 0 입니다. |
| 0x18 | 0x27 = 39 | 끝 VCN 은 39 입니다. 모두 40클러스터입니다. |
| 0x20 | 0x40 | 런 목록이 0x40 에서 시작합니다. |
| 0x22 | 0 | 압축하지 않았습니다. |
| 0x28 | 0x28000 = 163,840 | 할당 크기는 40 × 4,096 바이트입니다. |
| 0x30 | 0x27100 = 160,000 | 데이터 크기입니다. |
| 0x38 | 0x27100 = 160,000 | 유효 데이터 길이입니다. 데이터 크기와 같으므로 끝까지 써 넣은 파일입니다. |

런 목록 `31 20 00 60 01 | 11 08 F0 | 00` 을 풉니다.

| 런 | 첫 바이트 | 길이 | 위치 바이트 | 변화량 | LCN | VCN |
|---|---|---|---|---|---|---|
| 1 | `31` (길이 1바이트, 위치 3바이트) | `20` = 32 | `00 60 01` | +90,112 | 90,112~90,143 | 0~31 |
| 2 | `11` (길이 1바이트, 위치 1바이트) | `08` = 8 | `F0` | −16 | 90,096~90,103 | 32~39 |
| 끝 | `00` | | | | | |

두 번째 런의 `F0` 은 부호 있는 1바이트라서 −16 이며, 파일 뒷부분이 앞부분보다 볼륨 앞쪽에 놓여 있다는 뜻입니다.

- 첫 런의 볼륨 안 바이트 위치는 90,112 × 4,096 = 369,098,752 입니다. 디스크 전체 이미지라면 파티션 시작 위치를 더합니다 ([부트 섹터와 클러스터](boot-sector-cluster.md)).
- 마지막 클러스터에는 163,840 − 160,000 = 3,840 바이트가 파일 끝 뒤에 남습니다. 이 자리가 파일 슬랙입니다 ([비할당 영역과 슬랙](../../../03-techniques/analysis/data-recovery/unallocated-slack-space.md)).

> 그림 자리: 위 예시의 VCN 0~39 를 위쪽 막대로, 볼륨의 LCN 90,096~90,143 을 아래쪽 막대로 그리고, VCN 0~31 은 LCN 90,112 로, VCN 32~39 는 그보다 앞쪽인 LCN 90,096 으로 가는 화살표를 그린다.

### 희소 런이 낀 경우

희소 플래그 (0x8000) 가 켜진 속성의 런 목록이라고 가정합니다.

`31 20 00 60 01 11 08 F0 01 10 21 04 00 01 00`

| 런 | 첫 바이트 | 길이 | 변화량 | LCN | VCN |
|---|---|---|---|---|---|
| 1 | `31` | 32 | +90,112 | 90,112~90,143 | 0~31 |
| 2 | `11` | 8 | −16 | 90,096~90,103 | 32~39 |
| 3 | `01` (위치 필드 없음) | 16 | 없음 | 디스크 자리 없음 | 40~55 |
| 4 | `21` | 4 | +256 | 90,352~90,355 | 56~59 |

네 번째 런의 위치는 두 번째 런의 LCN (90,096) 에 256 을 더한 값인데, 희소 런은 LCN 을 바꾸지 않기 때문입니다. 압축 속성도 런 목록에 희소 런을 씁니다. 압축·희소 속성을 푸는 법은 [압축·희소 파일](compressed-sparse.md)에 있습니다.

### 위치 값 부호 확인하기

LCN 128 에서 시작하는 8클러스터 런 하나를 바이트로 적으면 `21 08 80 00 00` 입니다[1]. 128 은 1바이트로 `80` 이지만 부호 있는 1바이트 `80` 은 −128 이라서 위치 필드가 2바이트 `80 00` 이 됩니다.

위치 값을 부호 없는 수로 읽는 코드는 음수 변화량을 큰 양수로 읽습니다. 뒤로 가는 조각이 있는 파일에서 그 뒤 모든 런이 엉뚱한 클러스터를 가리킵니다.

### 속성이 여러 레코드로 나뉜 경우

조각이 아주 많으면 런 목록이 레코드 하나에 다 들어가지 않습니다. 이때 $DATA 는 여러 속성으로 나뉘어 확장 레코드 (Extension Record) 에 들어가고, 나뉜 속성은 저마다 시작 VCN·끝 VCN 으로 자기가 맡은 구간을 밝힙니다. 어느 레코드에 어느 구간이 있는지는 $ATTRIBUTE_LIST 가 알려 줍니다 ([MFT 레코드와 속성](file-record-attribute.md)). 세 크기 값은 시작 VCN 이 0 인 첫 속성에서만 뜻이 있으므로 나머지 속성의 크기 값은 읽지 않습니다.

확장 레코드는 기본 레코드와 멀리 떨어져 있는 경우가 많습니다. 기본 레코드 주변만 보면 뒤쪽 런을 놓칩니다.

## 포렌식에서 중요한 점

### 지운 상주 파일

파일을 지우면 MFT 레코드에는 "비어 있음" 표시만 남습니다. 상주 내용은 레코드 안에 있으므로, 레코드가 다른 파일에 다시 쓰이기 전까지 남습니다. 상주 파일은 클러스터를 받지 않아서 비할당 클러스터만 덮는 방식으로는 상주 내용이 지워지지 않습니다.

- 완전삭제 흔적은 [완전삭제 도구를 썼나](../../../04-scenarios/activity/anti-forensics/wiping-tools.md)를 봅니다.
- 조각난 MFT 레코드를 비할당 영역에서 찾는 방법은 [레코드 카빙](../../../03-techniques/analysis/data-recovery/record-carving.md)에 있습니다.

### 커진 파일에 남는 옛 상주 내용

Pomeranz 의 시험에서는 469바이트 상주 파일에 1KB 넘게 덧붙여 비상주로 바꾸자, 새 속성 목록의 끝 표시 (0xFFFFFFFF) 뒤 다음 섹터 경계부터 옛 상주 내용이 그대로 남았습니다[4]. 실제 사건에서 지금 파일에는 없는 문자열이 이 잔재에서 검색된 사례도 있습니다[4]. 시험한 Windows 버전은 밝혀져 있지 않으므로 실제 데이터로 확인합니다.

이 잔재는 섀도 복사본에도 없을 수 있는 옛 내용입니다. 잔재에는 따로 시각이 없어서 언제의 내용인지는 [$LogFile](../../../02-artifacts/filesystem/logfile.md)·[$UsnJrnl](../../../02-artifacts/filesystem/usnjrnl.md) 기록과 맞춰 봐야 합니다. 보고서에는 "이 파일의 MFT 레코드 중 쓰이지 않는 부분에 이런 내용이 남아 있다" 까지만 씁니다.

속성 끝의 채움 바이트에는 옛 데이터가 남을 수 있고, 런 목록 뒤의 바이트도 늘 0 은 아닙니다[3].

### 지운 비상주 파일

지운 레코드의 런 목록도 레코드가 다시 쓰이기 전까지 남습니다. 런이 가리키는 클러스터는 풀려나서 다른 파일이 쓸 수 있으므로, 그 클러스터가 지금 다른 파일에 할당됐는지 [$Bitmap](bitmap-secure-extend.md)으로 확인합니다. 할당된 클러스터라면 런을 따라 뽑은 내용은 원래 파일이 아닐 수 있습니다.

- SSD 에서는 풀린 클러스터가 TRIM 으로 비워졌을 수 있습니다 ([SSD TRIM과 복구 한계](../../../03-techniques/analysis/data-recovery/ssd-trim.md)).

### 유효 데이터 길이 너머

유효 데이터 길이가 데이터 크기보다 작으면, 그 사이 구간은 Windows 가 0 으로 채워 돌려줍니다. 디스크의 그 클러스터는 0 으로 덮이지 않았을 수 있고, 이 자리에는 예전 파일의 데이터가 있을 수 있습니다[2]. 그래서 파일을 복사한 결과와 런을 따라 클러스터를 그대로 뽑은 결과가 다를 수 있습니다.

원시 클러스터에서 나온 그 구간의 내용은 이 파일의 내용이 아니라 그 자리에 전에 있던 데이터로 다룹니다.

### 손상된 런 목록

런의 위치는 앞 런을 기준으로 한 변화량이라서, 런 목록 중간의 바이트 하나가 깨지면 그 뒤 모든 런의 위치가 어긋납니다. 첫 바이트의 크기 값이 깨지면 뒤의 바이트를 모두 잘못 끊어 읽습니다. 그래서 도구가 오류 없이 엉뚱한 내용을 내놓을 수 있습니다.

뽑은 결과의 파일 형식 시그니처를 확인하고, 필요하면 [파일 카빙](../../../03-techniques/analysis/data-recovery/file-carving.md) 결과와 대조합니다.

## 함정

1. **크기만 보고 상주라고 판단합니다.** 작은 파일도 비상주일 수 있습니다. 데이터 크기가 0 인 비상주 속성도 있습니다[3]. 헤더 0x08 을 봅니다.
2. **섹터 끝 2바이트를 되돌리지 않습니다.** MFT 레코드의 각 섹터 마지막 2바이트는 디스크에서 고정값 (Fixup) 으로 바뀌어 있습니다. 상주 내용이 섹터 경계를 넘으면 되돌리지 않은 2바이트가 틀립니다. 방법은 [MFT 레코드와 속성](file-record-attribute.md)에 있습니다.
3. **희소 런 뒤에서 기준을 0 으로 되돌립니다.** 다음 런의 기준은 마지막 보통 런의 LCN 입니다.
4. **런을 모두 이어 붙여 파일로 씁니다.** 마지막 클러스터의 슬랙까지 붙습니다. 데이터 크기에서 잘라야 파일 해시가 맞습니다.
5. **희소 구간을 어떻게 뽑았는지 적지 않습니다.** 구멍을 0 으로 채우면 논리 크기가 되고, 건너뛰면 실제 데이터만 남습니다. 둘은 크기와 해시가 다릅니다. $UsnJrnl:$J 는 0 으로 채우면 수 GB 가 됩니다.
6. **런 단위를 섹터로 봅니다.** 런의 길이와 위치는 클러스터 단위입니다. 클러스터 크기는 부트 섹터에서 읽습니다.

## 도구

- 헥스 편집기로 위 예시처럼 한 번 직접 풀어 두면 도구 결과를 검산하는 기준이 됩니다.
- The Sleuth Kit 의 `istat` 는 MFT 항목의 속성마다 상주 여부와 크기를 보여 주고, 비상주면 클러스터 번호를 늘어놓습니다. `icat` 은 그 런을 따라 내용을 뽑습니다.
- libyal 의 libfsntfs 도 MFT 항목과 속성을 읽습니다.
- 도구마다 희소 구간, 유효 데이터 길이 너머, 슬랙을 다루는 방식이 다를 수 있습니다. 두 가지 이상으로 뽑아 크기와 해시를 비교합니다 ([도구 결과 교차 검증](../../../03-techniques/reporting/tool-validation.md)).
