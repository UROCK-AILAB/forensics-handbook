# 문자 인코딩 (UTF-16LE·UTF-8·CP949)

## 한 줄 요약

Windows 가 저장하는 문자열은 대부분 BOM 없는 UTF-16LE 입니다.
8비트 문자열은 UTF-8 이거나 그 PC 의 코드 페이지 (Code Page) 를 따릅니다.
한국어 Windows 11 PC 에서 확인한 코드 페이지는 949(CP949) 였습니다.
같은 글자도 인코딩마다 바이트가 다릅니다.
그래서 인코딩을 잘못 고르면 글자가 깨지고, 키워드 검색에서도 빠집니다.

## 이 형식을 쓰는 아티팩트

| 쓰는 곳 | 인코딩 | 자세한 내용 |
|---|---|---|
| Windows 형식 전반의 유니코드 문자열 | 따로 정하지 않았으면 BOM 없는 UTF-16LE | 아래 "Windows 쪽 기본 규칙" |
| NTFS 의 유니코드 문자열·파일 이름 | BOM 없는 UTF-16LE | [NTFS 구조](/01-foundations/disk-volume/ntfs/index.md) |
| SECURITY 하이브의 작업그룹·도메인 이름 | 길이 칸 뒤의 UTF-16 (현장 관찰) | 아래 "길이 칸이 붙은 문자열", [레지스트리 속 비밀번호 정보](/02-artifacts/credentials/sam-security/index.md) |
| 8비트 문자열 (LPSTR) | 코드 페이지 또는 UTF-8. 쓰는 쪽이 정함 | 코드 페이지 문자열이 남는 예는 [바로가기 파일](/02-artifacts/file-folder-usage/lnk.md) |

## 구조

### Windows 쪽 기본 규칙

Windows 데이터 형식 명세 [MS-DTYP] 는 다음과 같이 정합니다.

- 유니코드 문자 하나는 따로 정하지 않았으면 UTF-16 코드 단위 (Code Unit) 16비트 하나입니다.
- 유니코드 문자열은 따로 정하지 않았으면 BOM 없는 UTF-16LE 입니다.
- WCHAR 는 16비트 유니코드 문자입니다.
- 8비트 문자열 (LPSTR) 의 형식은 쓰는 쪽이 정해야 합니다. 흔한 두 가지는 ANSI 와 UTF-8 입니다.

"ANSI" 는 Windows 코드 페이지를 가리키는 옛 이름이고, 정확한 이름이 아닙니다.
Windows 의 ANSI 문자 집합은 1252·1250·…·932·936·949·950 가운데 하나입니다.
Microsoft 는 옛 프로그램과 맞출 때가 아니면 ANSI 문자 집합을 쓰지 말라고 권합니다.
ANSI 코드 페이지는 컴퓨터마다 다를 수 있습니다.
한 컴퓨터 안에서도 바뀔 수 있어서 데이터가 깨질 수 있습니다.
그래서 Microsoft 는 일관된 결과가 필요하면 UTF-8 이나 UTF-16 을 쓰라고 권합니다.

### 세 인코딩 비교

| | UTF-16LE | UTF-8 | CP949 |
|---|---|---|---|
| 기본 단위 | 16비트 코드 단위 | 1바이트 | 1바이트 |
| ASCII 글자 | 2바이트. 뒤 바이트가 00 | 1바이트. ASCII 와 같음 | 1바이트. ASCII 와 같음 |
| 한글 음절 | 2바이트 | 3바이트 | 2바이트 |
| BMP 밖 글자 | 서로게이트 쌍 (Surrogate Pair), 4바이트 | 4바이트 | — |
| BOM | `FF FE` | `EF BB BF` | — |
| Windows 코드 페이지 번호 | 1200 (관리 코드 (Managed Code) 전용) | 65001 | 949 |

### 같은 글자의 바이트

아래 바이트는 Python 표준 코덱으로 인코딩해 본 예시입니다.

| 글자 | UTF-16LE | UTF-8 | CP949 |
|---|---|---|---|
| A | `41 00` | `41` | `41` |
| 가 (U+AC00) | `00 AC` | `EA B0 80` | `B0 A1` |
| 한글 | `5C D5 00 AE` | `ED 95 9C EA B8 80` | `C7 D1 B1 DB` |
| U+1F600 (BMP 밖 글자) | `3D D8 00 DE` | `F0 9F 98 80` | — |

영문·숫자만 있는 UTF-16LE 문자열은 한 바이트 걸러 `00` 이 끼어 보입니다.
헥스 화면에서는 이 모양으로 UTF-16LE 를 알아볼 수 있습니다.

### CP949 바이트 범위

아래 범위는 Python `cp949` 코덱이 받아들이는 바이트를 모두 조사해 얻은 값입니다.
Windows 변환표와 세부가 다를 수 있으므로 대략의 범위로 봅니다.
예를 들어 Python 코덱은 첫 바이트 `0xC9`·`0xFE` 로 시작하는 2바이트를 받지 않았습니다.

| 구분 | 바이트 범위 |
|---|---|
| 1바이트 글자 | `0x00`~`0x7F`. ASCII 와 같음 |
| 2바이트 글자의 첫 바이트 | `0x81`~`0xC8`, `0xCA`~`0xFD` |
| 2바이트 글자의 둘째 바이트 | `0x41`~`0x5A`, `0x61`~`0x7A`, `0x81`~`0xFE` |

- 2바이트 글자는 17,048개이고, 한글 음절 11,172자가 모두 들어 있습니다.
- 그중 EUC-KR 영역(첫 바이트 `0xB0`~`0xC8`, 둘째 바이트 `0xA1`~`0xFE`)에 든 한글은 2,350자입니다.
- 나머지 한글 8,822자는 CP949 가 덧붙인 영역에 있습니다.

### 길이 칸이 붙은 문자열

Windows 형식에는 끝 NUL 대신 길이 칸으로 문자열 끝을 정하는 구조가 많습니다.
[MS-DTYP] 의 RPC_UNICODE_STRING 이 대표 예입니다.

| 순서 | 크기 | 칸 | 뜻 |
|---|---|---|---|
| 1 | 2 | Length | 문자열 길이. 바이트 수이고 2의 배수 |
| 2 | 2 | MaximumLength | 최대 길이. 바이트 수이고 2의 배수 |
| 3 | — | Buffer | UTF-16 문자열. 끝 NUL 이 없음 |

두 길이 칸은 글자 수가 아니라 바이트 수입니다.

SECURITY 하이브 `Policy\PolPrDmN` 의 기본값도 비슷한 모양입니다(확인 범위: 압수 이미지에서 꺼낸 SECURITY 하이브, 현장 관찰).

- 앞 8바이트는 길이 2바이트, 최대 길이 2바이트, 자리 4바이트입니다.
- 그 뒤에 UTF-16 이름이 옵니다.
- 도메인에 가입한 PC 는 이름 뒤에 도메인 SID 가 붙습니다.
- 그래서 길이 칸만큼만 이름으로 읽어야 합니다.

붙어 있는 SID 를 푸는 법은 [윈도 식별자 형식](/01-foundations/value-decoding/sid-guid-clsid-known-folder-id.md) 에 있습니다.

NTFS `$FILE_NAME` 의 이름 길이 칸은 바이트 수가 아니라 글자 수입니다.
끝 문자는 세지 않고, 이름 뒤에 끝 문자도 없습니다.
칸의 오프셋은 [NTFS 구조](/01-foundations/disk-volume/ntfs/index.md) 에서 봅니다.

## 읽는 법

### 순서

1. 형식 명세가 인코딩을 정해 두었는지 먼저 봅니다. Windows 형식의 유니코드 문자열은 따로 정하지 않았으면 UTF-16LE 입니다.
2. 앞머리에 BOM 이 있는지 봅니다. `FF FE` 면 UTF-16LE, `EF BB BF` 면 UTF-8 입니다.
3. 영문·숫자 구간에 한 바이트 걸러 `00` 이 있으면 UTF-16LE 로 읽어 봅니다.
4. 8비트 문자열이면 압수 PC 의 코드 페이지를 확인합니다. `Control\Nls\CodePage` 의 `ACP`·`OEMCP` 값입니다. 이미지에서 어느 제어 집합을 볼지는 [레지스트리 하이브 구조](/01-foundations/database-log-formats/registry-hive/index.md) 에서 다룹니다.
5. 길이 칸이 있으면 바이트 수인지 글자 수인지 명세로 확인합니다. 그다음 그 길이만큼만 읽습니다.
6. 결과가 깨져 보이면 다른 인코딩으로 다시 읽습니다.

### 헥스로 한 번 — CP949

아래 바이트는 "한글" 을 CP949 로 인코딩해 만든 예시입니다.

```
C7 D1 B1 DB
```

1. `C7` 은 `0x81`~`0xC8` 범위라서 2바이트 글자의 첫 바이트입니다.
2. 둘째 바이트 `D1` 과 묶은 `C7 D1` 이 "한" 입니다.
3. `B1` 도 같은 범위라서 2바이트 글자의 첫 바이트입니다.
4. `B1 DB` 가 "글" 입니다.

같은 두 글자를 UTF-16LE 로 쓰면 `5C D5 00 AE`, UTF-8 로 쓰면 `ED 95 9C EA B8 80` 입니다.
세 바이트열에 겹치는 부분이 없습니다.

## 포렌식에서 중요한 점

### 한국어 키워드는 세 바이트열로 찾습니다

"한글" 한 단어도 세 인코딩의 바이트가 모두 다릅니다.
그래서 한국어 키워드는 UTF-16LE·UTF-8·CP949 바이트열로 모두 찾아야 합니다.
검색 절차는 [파일 내용 검색](/03-techniques/analysis/content-search/index.md) 에서 다룹니다.

### CP949 데이터에서 영문 검색은 헛걸릴 수 있습니다

CP949 2바이트 글자의 둘째 바이트는 영문 대소문자 범위(`0x41`~`0x5A`, `0x61`~`0x7A`)와 겹칩니다.
그래서 CP949 바이트열을 ASCII 로 검색하면 영문 키워드가 한글 글자 가운데에 걸릴 수 있습니다.
걸린 자리의 앞 바이트를 보고 한글 글자의 일부인지 확인합니다.

### 조각의 시작을 잘못 잡으면 다른 글자가 됩니다

UTF-16LE 는 2바이트가 한 단위입니다.
카빙한 조각이나 슬랙에서 시작을 한 바이트 어긋나게 잡으면 모든 글자가 다른 글자로 읽힙니다.
글자가 깨져 보이면 한 바이트 옮겨서 다시 읽어 봅니다.

### NTFS 이름은 엄밀한 UTF-16 이 아닙니다

NTFS 파일 이름에는 짝 없는 서로게이트가 들어갈 수 있습니다.
U+D800, U+DC00 같은 값이 홀로 들어가는 경우입니다.
엄격한 UTF-16 디코더는 이런 이름에서 오류를 내거나 글자를 바꿀 수 있습니다.
그래서 같은 파일 목록도 도구에 따라 이름이 다르게 보일 수 있습니다.
이름을 비교하거나 보고서에 옮길 때는 원시 바이트를 함께 남깁니다.

### 길이 칸을 무시하면 뒤의 데이터가 섞입니다

길이 칸이 있는 문자열을 끝 NUL 까지 읽으면 뒤에 붙은 데이터가 이름에 섞입니다.
`PolPrDmN` 이라면 도메인 SID 바이트가 이름 끝에 깨진 글자로 붙어 보일 수 있습니다.

## 함정

- **분석 PC 의 코드 페이지로 읽지 않습니다.** ANSI 코드 페이지는 컴퓨터마다 다르고 바뀔 수도 있습니다. 압수 PC 의 `Nls\CodePage` 값을 먼저 확인합니다.
- **길이 칸의 단위는 형식마다 다릅니다.** RPC_UNICODE_STRING 은 바이트 수, NTFS `$FILE_NAME` 은 글자 수입니다.
- **949 와 51949 는 다른 번호입니다.** 51949 는 euc-kr 입니다. EUC-KR 영역 밖의 한글 8,822자는 CP949 가 덧붙인 영역에 있습니다. 그래서 도구에서 EUC-KR 을 고르면 이 글자들을 못 읽을 수 있습니다.
- **1200·1201·12000 은 관리 코드 전용 번호입니다.**
- **"ANSI" 는 특정 인코딩 이름이 아닙니다.** 한국어 PC 에서는 CP949 를, 다른 언어 PC 에서는 그 언어의 코드 페이지를 뜻합니다.

## 도구

**Python 표준 코덱** 으로 바이트를 직접 풀어 볼 수 있습니다.

```python
bytes.fromhex('C7D1B1DB').decode('cp949')      # '한글'
'한글'.encode('utf-16-le').hex(' ')             # '5c d5 00 ae'
'한글'.encode('utf-8').hex(' ')                 # 'ed 95 9c ea b8 80'
```

- **헥스 편집기** — 문자 표시 인코딩을 바꿔 가며 볼 수 있으면 편합니다. UTF-16LE 로 볼 때는 시작 위치의 짝·홀도 확인합니다.
- **Microsoft 코드 페이지 번호 문서** — 도구가 요구하는 코드 페이지 번호나 이름을 찾을 때 씁니다.
- **문자열 추출·키워드 검색 도구** — 여러 인코딩을 한 번에 찾는 방법은 [파일 내용 검색](/03-techniques/analysis/content-search/index.md) 에서 다룹니다.
