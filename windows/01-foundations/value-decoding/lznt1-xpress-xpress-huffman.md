# 윈도 압축 형식 (LZNT1·Xpress·Xpress Huffman)

## 한 줄 요약

Windows 는 LZ77 계열 압축 세 가지, 곧 LZNT1, Xpress, Xpress Huffman 을 씁니다.
NTFS 파일 압축은 LZNT1 을 쓰고 WOF 압축은 Xpress Huffman 이나 LZX 를 쓰는데, 압축된 데이터 안에서는 원래 바이트가 그대로 보이지 않습니다.
그래서 검색하거나 해시를 구하기 전에 풀어서 읽어야 합니다.

## 이 형식을 쓰는 아티팩트

| 쓰는 곳 | 압축 형식 | 자세한 내용 |
|---|---|---|
| NTFS 파일 압축 | LZNT1 | [NTFS 구조](../disk-volume/ntfs/index.md) |
| WOF 압축 (Windows Overlay Filter, Windows 10 부터) | Xpress Huffman 4K·8K·16K, 또는 LZX | [NTFS 구조](../disk-volume/ntfs/index.md) |
| ESE 데이터베이스의 긴 값 압축 | XPRESS 등 여러 방식 (현장 관찰) | [ESE 데이터베이스](../database-log-formats/extensible-storage-engine/index.md) |

libfsntfs 문서는 NTFS 속성 데이터 플래그의 압축 방식 값 1 이 LZNT1 이라고 적고, WOF 압축 파일의 실제 데이터가 `WofCompressedData` 라는 대체 데이터 스트림에 있다고도 적습니다.
LZX 는 이 페이지의 세 형식과 다른 알고리즘이라 여기서 다루지 않습니다.

아래 아티팩트도 Xpress 계열 압축을 쓴다고 알려져 있으며, 어느 변형을 쓰는지는 각 페이지에서 근거와 함께 다룹니다.

- Windows 10 이후의 [프리페치](../../02-artifacts/execution/prefetch/index.md)
- 최대 절전 파일 (hiberfil.sys) — [메모리 분석](../../03-techniques/analysis/memory-forensics/index.md)

## 구조

### 이름과 세 변형

Microsoft 명세 [MS-XCA] 는 Xpress 압축 알고리즘에 변형이 셋 있다고 적습니다.
셋 모두 속도를 중시해 만든 방식이라, 반복되는 바이트열이 많은 데이터를 CPU 부담 적게 누르는 용도이며 그림·소리·영상을 누르는 용도가 아닙니다.
명세가 적용 제품으로 적은 범위는 Windows 2000 ~ Windows 11, Windows Server 2003 ~ 2025 입니다.

| 명세 이름 | 흔히 부르는 이름 | 특징 |
|---|---|---|
| Plain LZ77 | Xpress | 셋 중 가장 빠릅니다 |
| LZ77+Huffman | Xpress Huffman | 더 느립니다. LZ77 결과에 허프만 부호화 (Huffman Coding) 를 한 번 더 합니다 |
| LZNT1 | LZNT1 | 허프만 단계가 없습니다. 부호화가 Plain LZ77 보다 단순합니다 |

libyal 문서는 Xpress Huffman 을 "LZXPRESS Huffman" 이라고 부릅니다.

명세 이름과 흔히 부르는 이름의 대응은 한국어 Windows 11 PC 에서 확인했습니다.
ntdll 의 `RtlCompressBuffer` 에 형식 번호를 넘겨 눌러 본 결과는 다음과 같습니다.

| 형식 번호 | 결과 |
|---|---|
| 2 | LZNT1 로 동작 |
| 3 | Plain LZ77 로 동작. 명세의 Plain LZ77 예시 두 개와 바이트까지 같음 |
| 4 | LZ77+Huffman 으로 동작. 명세 예시와 끝부분이 같음 |

### 세 형식 한눈에 비교

| | LZNT1 | Plain LZ77 (Xpress) | LZ77+Huffman (Xpress Huffman) |
|---|---|---|---|
| 처리 단위 | 입력 4,096바이트마다 청크 하나 | 32비트 플래그 하나에 요소 32개 | 입력 64KB 블록 |
| 리터럴·매치 구분 | 플래그 바이트. 낮은 비트부터 읽음 | 32비트 플래그. 높은 비트부터 읽음 | 허프만 기호. 0~255 리터럴, 256~511 매치 |
| 매치 표현 | 2바이트 압축 단어. 거리와 길이의 비트 수가 바뀜 | 16비트. 거리 13비트, 길이 3비트 | 기호 + 거리 아래 비트 |
| 최대 거리 | 같은 청크 안 | 8,192 | 65,535 |
| 허프만 부호 | 없음 | 없음 | 있음 |

### LZNT1

입력을 4,096바이트 단위로 눌러, 따로따로 풀 수 있는 청크 (Chunk) 가 이어진 결과를 만듭니다.
청크마다 2바이트(16비트) 머리가 있습니다.

| 비트 | 뜻 |
|---|---|
| 15 | 1 이면 압축된 청크 |
| 14~12 | 서명. 늘 3 |
| 11~0 | 청크 크기 − 3. 청크 크기는 머리 2바이트를 포함 |

- 머리가 `0x0000` 이면 버퍼 끝 표시 (End_of_buffer) 입니다. 하지만 공간이 모자라면 이 표시를 쓰지 않으므로 풀려면 압축된 크기를 미리 알아야 합니다.
- 압축 안 된 청크는 머리 뒤에 원래 데이터가 그대로 있습니다. 길이는 비트 11~0 의 값에 1 을 더한 바이트 수입니다.
- 압축된 청크는 머리 뒤에 "플래그 바이트 1개 + 데이터 요소 최대 8개" 묶음이 이어집니다.

플래그 바이트는 낮은 비트부터 읽습니다.
비트가 0 이면 그 요소는 1바이트 원래 값, 곧 리터럴 (Literal) 이고, 1 이면 2바이트 압축 단어 (Compressed Word) 입니다.

압축 단어는 위쪽 D비트가 거리 (Displacement), 아래쪽 L비트가 길이입니다.
D + L = 16 이고 D 는 4 이상 12 이하이며, 저장값에 거리는 1 을, 길이는 3 을 더해야 실제 값입니다.

D 는 그 청크 안에서 지금까지 풀린 바이트 수 U 에 따라 바뀝니다.
2^(M−1) < U 를 만족하는 4~12 중 가장 큰 M 이 D 이고, 그런 M 이 없으면 D 는 4 입니다.
U 는 청크마다 0 부터 다시 세며, 아래 표는 이 규칙으로 계산한 것입니다.

| 지금까지 풀린 바이트 수 U | D (거리 비트) | L (길이 비트) |
|---|---|---|
| 16 이하 | 4 | 12 |
| 17~32 | 5 | 11 |
| 33~64 | 6 | 10 |
| 65~128 | 7 | 9 |
| 129~256 | 8 | 8 |
| 257~512 | 9 | 7 |
| 513~1,024 | 10 | 6 |
| 1,025~2,048 | 11 | 5 |
| 2,049 이상 | 12 | 4 |

복사할 영역이 아직 풀리지 않은 부분과 겹칠 수 있어서 한 바이트씩 앞에서부터 복사해야 합니다.
청크의 끝은 머리의 크기 값으로 정하고, 플래그 비트 가운데 청크 밖을 가리키는 것은 무시합니다.

> 그림 자리: LZNT1 청크 하나를 가로 막대로 그리고, 머리 2바이트 → 플래그 바이트 → 요소 8개(리터럴 1바이트·압축 단어 2바이트가 섞인 칸) → 다음 플래그 바이트 순서로 칸을 나눈 그림

### Plain LZ77 (Xpress)

리터럴인지 매치인지 알리는 플래그를 32비트 단위로 묶고, 높은 비트부터 씁니다.
비트 1 은 매치, 0 은 리터럴입니다.

- 리터럴은 1바이트 그대로입니다.
- 매치는 16비트입니다. 위 13비트가 "거리 − 1", 아래 3비트가 "길이 − 3" 입니다. 그래서 거리는 최대 8,192 입니다.
- 3비트 길이 값이 7 이면 길이가 더 길어서 추가로 4비트(반 바이트)를 읽는데, 이 반 바이트는 다음 긴 매치와 한 바이트를 나눠 씁니다.
- 4비트 값이 15 면 1바이트를 더 읽습니다. 그 값이 255 면 2바이트를 더 읽습니다. 그 값이 0 이면 4바이트를 더 읽습니다.
- 마지막 플래그 묶음의 남는 비트는 1 로 채웁니다.

### LZ77+Huffman (Xpress Huffman)

입력을 64KB 블록 단위로 처리하고, 결과를 순서대로 잇습니다.

| 위치 | 내용 |
|---|---|
| 블록 앞 256바이트 | 허프만 기호 512개의 부호 길이. 기호마다 4비트. 짝수 기호는 낮은 4비트, 홀수 기호는 높은 4비트. 0 은 쓰지 않는 기호 |
| 그 뒤 | 16비트 단위로 읽는 비트 스트림 |

- 기호 0~255 는 리터럴 바이트이고, 256~511 은 매치입니다.
- 매치 기호 = 256 + min(길이 − 3, 15) + 16 × (거리의 최상위 비트 위치) 입니다.
- 거리의 나머지 아래 비트는 기호 뒤에 그대로 적습니다.
- 길이가 18 이상이면 1바이트를 더 읽습니다. 그 값이 255 면 2바이트를, 거기서도 0 이면 4바이트를 더 읽습니다.
- 부호 길이는 최대 15비트입니다. 풀 때는 2^15 칸짜리 표를 만들어 찾습니다.
- 끝 표시로 기호 256(EOF)을 붙입니다. 일부 구현은 이 표시가 없으면 실패합니다.

매치 길이가 거리보다 클 수 있습니다.
예를 들어 "a" 뒤에 거리 1·길이 5 매치가 오면 "aaaaaa" 가 되므로 한 바이트씩 복사해야 하고, memcpy·memmove 로 한꺼번에 복사하면 안 됩니다.

## 읽는 법

### 헥스로 한 번 — LZNT1

아래 바이트는 "abc" 를 100번 이은 300바이트를 LZNT1 으로 누른 예시입니다.
한국어 Windows 11 PC 의 `RtlCompressBuffer`(형식 번호 2)로 만들었고, 풀이는 명세 규칙을 따랐습니다.

```
05 B0 08 61 62 63 26 21
```

1. `05 B0` 은 머리 0xB005 입니다. 비트 15 가 1 이라 압축된 청크입니다.
2. 비트 14~12 는 3 이라 서명이 맞습니다.
3. 비트 11~0 은 5 입니다. 청크 크기는 5 + 3 = 8바이트입니다.
4. `08` 은 플래그 바이트입니다. 이진수로 00001000 입니다.
5. 비트 0~2 가 0 이라 다음 3바이트 `61 62 63` 은 리터럴 "abc" 입니다. 이제 U = 3 입니다.
6. 비트 3 이 1 이라 다음 2바이트 `26 21` 은 압축 단어 0x2126 입니다.
7. U = 3 이므로 D = 4, L = 12 입니다.
8. 위 4비트는 2 입니다. 1 을 더해 거리 3 입니다.
9. 아래 12비트는 0x126, 곧 294 입니다. 3 을 더해 길이 297 입니다.
10. 3바이트 앞에서부터 297바이트를 한 바이트씩 복사합니다. "abc" 가 되풀이되어 모두 300바이트가 됩니다.
11. 청크가 8바이트에서 끝나므로 플래그 비트 4~7 은 무시합니다.

### 헥스로 한 번 — Plain LZ77

아래 바이트는 명세 [MS-XCA] 의 예시입니다.
"abc" 를 100번 이은 300바이트를 누른 결과입니다.

```
FF FF FF 1F 61 62 63 17 00 0F FF 26 01
```

1. 앞 4바이트는 플래그 묶음입니다. 리틀 엔디언으로 0x1FFFFFFF 입니다.
2. 높은 비트부터 세 비트가 0 이라 `61 62 63` 은 리터럴 "abc" 입니다.
3. 넷째 비트가 1 이라 `17 00` 은 매치 0x0017 입니다.
4. 위 13비트는 2 입니다. 1 을 더해 거리 3 입니다.
5. 아래 3비트는 7 이라 길이를 더 읽습니다.
6. `0F` 의 아래 4비트는 15 라서 1바이트를 더 읽습니다. 위 4비트는 다음 긴 매치 몫으로 남겨 둡니다.
7. `FF` 는 255 라서 2바이트를 더 읽습니다.
8. `26 01` 은 0x0126, 곧 294 입니다. 길이에서 3 을 뺀 값이라 길이는 297 입니다.
9. 남은 플래그 비트는 모두 1 이고, 채움 비트입니다.

명세의 다른 예시는 알파벳 26자 "abcdefghijklmnopqrstuvwxyz" 입니다.
결과는 `3F 00 00 00 61 62 … 7A` 입니다.
앞 4바이트 플래그는 리터럴 26개의 0 비트와 남는 6비트의 1 로 이루어집니다.

### LZ77+Huffman 예시

명세는 같은 "abc" × 100 을 LZ77+Huffman 으로 누른 결과도 보여 줍니다.
256바이트 부호 길이 표 뒤에 `A8 DC 00 00 FF 26 01` 이 옵니다.
끝의 `FF 26 01` 은 길이 연장입니다. 0x126 = 294 = 297 − 3 입니다.
한국어 Windows 11 PC 의 `RtlCompressBuffer`(형식 번호 4) 결과도 끝부분이 이와 같았습니다.

### LZNT1 청크를 알아보는 표지

LZNT1 청크 머리의 비트 14~12 는 늘 3 이라서 `(머리 & 0x7000) == 0x3000` 을 LZNT1 청크를 알아보는 표지로 쓸 수 있습니다.
이것은 명세에서 끌어낸 추론이고, 2바이트짜리 조건이라 우연히 맞는 바이트도 많으므로 후보를 고르는 데만 씁니다.

## 포렌식에서 중요한 점

### 손상된 입력을 안전하게 풀어야 합니다

명세는 푸는 쪽이 잘못된 입력에서 버퍼 밖을 읽거나 쓰지 말고 실패해야 한다고 적습니다.
입력은 손상됐거나 악의로 만든 것일 수 있어서, 긴 매치 길이에서 정수나 포인터가 넘치지 않도록 특히 막아야 합니다.
명세의 풀기 의사 코드도 버퍼 밖에 접근하면 오류로 끝내도록 적혀 있습니다.

### LZNT1 은 끝 표시가 없을 수 있습니다

End_of_buffer 표시는 공간이 모자라면 빠지므로, 압축된 크기를 모르고 풀면 끝을 잘못 잡아 뒤의 쓰레기 바이트까지 풀 수 있습니다.
카빙한 조각처럼 크기를 모를 때는 풀린 결과의 끝부분을 따로 확인합니다.

### NTFS 의 손상 사례는 도구마다 다르게 풉니다

libfsntfs 문서는 NTFS 압축 파일의 경계 사례를 적어 두었습니다.
NTFS 는 압축 단위 안의 블록마다 2바이트 머리를 두는데, 이 머리는 LZNT1 청크 머리와 배치가 같습니다.

| 사례 | 관찰된 동작 | Windows 동작 |
|---|---|---|
| 머리가 `0x0000` 인 빈 블록 | 서로 다른 NTFS 구현 두 개가 모두 블록 전체를 0 으로 채움 | 확인되지 않음 |
| 16,384 오프셋에서 잘린 블록 | 한 구현은 읽은 만큼 풀고 나머지를 0 으로 채움. 다른 구현은 버퍼에 남아 있던 이전 데이터를 내놓음 | 확인되지 않음 |
| `$ATTRIBUTE_LIST` 로 여러 `$DATA` 속성에 나뉜 스트림 | 첫 `$DATA` 에만 압축 플래그가 있었음 | 손상인지 정상인지 불분명 |

그래서 손상된 압축 파일은 도구마다 다른 내용을 낼 수 있으므로, 두 가지 이상의 방식으로 풀어 결과를 비교하고 어떤 도구와 방식으로 뽑았는지 기록에 남깁니다.
비교 방법은 [도구 결과 교차 검증](../../03-techniques/reporting/tool-validation.md) 에 있습니다.

### 압축된 내용은 디스크 검색에 보이지 않습니다

압축된 데이터 안에서는 키워드가 원래 바이트로 보이지 않아서 원시 디스크 검색만으로는 압축 파일의 내용을 찾지 못합니다.
파일 시스템을 해석해 압축을 푼 뒤 검색해야 합니다.
검색 방법은 [파일 내용 검색](../../03-techniques/analysis/content-search/index.md) 에서, 지운 파일을 되살리는 방법은 [삭제 데이터 복구](../../03-techniques/analysis/data-recovery/index.md) 에서 다룹니다.
NTFS 압축 파일의 희소 구간과 뽑는 방식에 따른 해시 차이는 [NTFS 구조](../disk-volume/ntfs/index.md) 에서 다룹니다.

## 함정

- **이름이 비슷해 헷갈립니다.** Xpress 는 허프만 단계가 없는 Plain LZ77 이고, Xpress Huffman 은 LZ77+Huffman 입니다. 문서에 따라 LZXPRESS 같은 이름도 씁니다. LZX 는 또 다른 알고리즘입니다.
- **플래그 읽는 방향이 다릅니다.** LZNT1 플래그 바이트는 낮은 비트부터, Plain LZ77 플래그 묶음은 높은 비트부터 읽습니다.
- **LZNT1 의 거리 비트 수는 청크 안에서 바뀝니다.** 풀린 바이트 수 U 에 따라 D 가 4 에서 12 까지 늘어납니다. 청크가 바뀌면 U 를 0 으로 되돌립니다.
- **한꺼번에 복사하면 틀립니다.** 매치 길이가 거리보다 길 수 있으므로 한 바이트씩 복사합니다.
- **Xpress Huffman 의 끝 기호에 기대는 구현이 있습니다.** 끝 기호 256 이 없으면 실패하는 구현이 있습니다. 한 도구가 실패하면 다른 구현으로도 풀어 봅니다.

## 도구

- **Windows 압축 API** — ntdll 의 `RtlCompressBuffer` 계열 함수입니다. 형식 번호 2·3·4 로 세 형식을 누를 수 있습니다(Windows 11 기준). 알고 있는 입력을 눌러 명세 예시와 비교하면 파서를 시험할 수 있습니다.
- **libfwnt** — libfsntfs 문서가 압축 방식 설명으로 가리키는 libyal 라이브러리입니다. LZNT1·Xpress Huffman 등을 다룹니다.
- **헥스 편집기** — 위 따라가기처럼 청크 머리와 플래그를 직접 확인할 때 씁니다.
