# 시각 값 형식 (FILETIME·Unix·WebKit·DOS·OLE)

## 한 줄 요약

시각 값은 기준 시각 (Epoch) 에서 정한 단위가 몇 개 지났는지를 적은 수이고, 형식마다 기준 시각·단위·크기·시간대가 다릅니다. 형식을 잘못 고르면 오류 없이 엉뚱한 날짜가 나옵니다. 그래서 값의 생김새로 형식을 짐작하지 말고, 그 아티팩트의 명세를 따릅니다.

## 이 형식을 쓰는 아티팩트

| 형식 | 쓰는 곳 | 시간대 | 자세한 내용 |
|---|---|---|---|
| FILETIME | NTFS 의 날짜·시각 값 | UTC | [NTFS 구조](../disk-volume/ntfs/index.md) |
| DOS 날짜·시각 | FAT 의 날짜·시각 | 대개 현지 시각 | [FAT·exFAT 구조](../disk-volume/fat-exfat.md) |
| WebKit 시각 | Chromium 계열 프로그램 | 대개 UTC | [크롬 계열 브라우저](../../02-artifacts/browsers/chrome-edge-whale/index.md) |

WebKit 시각의 정의는 Chromium 소스의 `time.h` 에 있습니다[1].

## 구조

### 한눈에 보기

| 형식 | 기준 시각 | 단위 | 크기 | 시간대 |
|---|---|---|---|---|
| FILETIME | 1601-01-01 00:00 UTC | 100나노초 | 8바이트 | 값에 적혀 있지 않음. 대개 UTC |
| POSIX 시각 (Unix time) | 1970-01-01 00:00:00 | 초 | 4 또는 8바이트 | — |
| Java 시각 | 1970-01-01 | 밀리초 | 8바이트 | — |
| WebKit 시각 | 1601-01-01 00:00:00 | 마이크로초 | 8바이트, 부호 있는 정수 | 대개 UTC |
| DOS 날짜·시각 (FAT date and time) | 1980년부터 햇수를 셈 | 2초 | 날짜 2바이트 + 시각 2바이트 | 대개 현지 시각 |
| OLE 자동화 날짜 (OLE Automation DATE) | 1899-12-30 자정 | 날. 소수부는 하루 중 지난 비율 | 8바이트 부동소수점 | 현지 시각 |
| SYSTEMTIME | 없음. 연·월·일을 필드마다 따로 적음 | 1밀리초 | 16바이트 | — |

"—" 는 공개 자료에 시간대가 정해져 있지 않다는 뜻이고, POSIX 시각이 음수이면 1970-01-01 보다 앞선 시각입니다.

> 그림 자리: 가로 시간 축에 1582-10-15, 1601-01-01, 1899-12-30, 1970-01-01, 1980-01-01 을 찍고, 각 점에서 시작하는 형식 이름(FILETIME·WebKit, OLE DATE, POSIX·Java, DOS)을 붙인 그림

### FILETIME

| 오프셋 | 크기 | 필드 | 뜻 |
|---|---|---|---|
| 0 | 4 | dwLowDateTime | 하위 32비트 |
| 4 | 4 | dwHighDateTime | 상위 32비트 |

두 필드를 합쳐 64비트 정수 하나로 읽을 수 있습니다. NTFS 는 바이트 순서가 리틀 엔디언이라서 디스크의 8바이트를 뒤에서부터 이어 읽으면 64비트 값이 됩니다.

값 0 의 뜻은 쓰인 곳마다 달라서 1601-01-01 을 뜻할 수도 있고 "설정 안 됨" 을 뜻할 수도 있습니다. SetFileTime API 에서는 `{ 0xffffffff, 0xffffffff }` 같은 값에 특별한 뜻이 붙습니다. FILETIME 이 실제로 담을 수 있는 날짜의 상한은 분명하지 않습니다.

### DOS 날짜·시각

날짜 워드 (wFatDate) 의 비트 배치입니다.

| 비트 | 뜻 |
|---|---|
| 0~4 | 일 (1~31) |
| 5~8 | 월 (1 = 1월) |
| 9~15 | 1980년부터 지난 햇수. 1980 을 더해 연도를 구합니다 |

시각 워드 (wFatTime) 의 비트 배치입니다.

| 비트 | 뜻 |
|---|---|
| 0~4 | 초를 2로 나눈 값 |
| 5~10 | 분 (0~59) |
| 11~15 | 시 (0~23, 24시간제) |

초 필드에 2로 나눈 값을 넣으므로 초는 짝수만 남습니다. 범위는 1980-01-01 00:00:00 부터 2107-12-31 23:59:58 까지이고, 상한을 2099-12-31 23:59:58 로 보는 경우도 있습니다. Windows 에서는 kernel32 의 `DosDateTimeToFileTime` 함수로 FILETIME 으로 바꾸며, 이 함수는 Windows 2000 부터 있습니다.

시각 워드와 날짜 워드 중 어느 쪽이 먼저 오는지는 파일 형식마다 다르고, FAT 디렉터리 항목 안의 배치는 [FAT·exFAT 구조](../disk-volume/fat-exfat.md) 에서 봅니다.

### OLE 자동화 날짜

8바이트 부동소수점(double) 값이고, 정수부는 1899-12-30 자정부터 지난 날 수, 소수부는 그날 자정부터 하루가 얼마나 지났는지를 비율로 적은 것입니다. 값과 날짜·시각의 대응 예는 다음과 같습니다[3].

| 값 | 날짜·시각 |
|---|---|
| 0.00 | 1899-12-30 자정 |
| 2.00 | 1900-01-01 자정 |
| 5.25 | 1900-01-04 오전 6시 |
| 5.50 | 1900-01-04 정오 |
| 5.875 | 1900-01-04 오후 9시 |

1899-12-30 보다 앞선 날짜는 정수부에만 부호가 붙고 소수부는 늘 더합니다. 그래서 -0.25 와 0.25 는 둘 다 1899-12-30 오전 6시입니다. 0 아래에서는 시간 축이 끊기므로 1899-12-30 보다 앞선 날짜를 부동소수점 크기로 정렬하면 순서가 틀립니다.

자동화 (Automation) 에서 DATE 는 현지 시각입니다[3]. 시간대 변환은 쓰는 쪽이 직접 해야 하고, 일광 절약 시간 (Daylight Saving Time) 도 반영하지 않습니다. Delphi 의 TDateTime 도 1899-12-30 을 기준으로 하는 부동소수점 날 수입니다.

### SYSTEMTIME

| 오프셋 | 필드 |
|---|---|
| 0 | wYear |
| 2 | wMonth |
| 4 | wDayOfWeek |
| 6 | wDay |
| 8 | wHour |
| 10 | wMinute |
| 12 | wSecond |
| 14 | wMilliseconds |

필드 8개가 모두 WORD(2바이트)라서 전체는 16바이트입니다. 범위는 1601년부터 30827년까지이고 1밀리초 단위이며, 연·월·일을 필드마다 따로 적으므로 기준 시각이 없습니다.

### 저장 단위와 실제 정밀도

시각 값의 정밀도는 두 가지로 나눠 봅니다[1]. 하나는 저장 단위 (Storage Granularity) 로, FILETIME 이면 100나노초입니다. 다른 하나는 실제로 기록한 값의 정밀도 (Value Granularity) 로, FAT 의 접근 시각은 하루 단위 정밀도입니다. 100나노초 단위 필드에 적혀 있다고 해서 그 값이 100나노초까지 정확하다는 뜻은 아닙니다.

## 읽는 법

### 기준 시각 사이 거리

아래 상수는 Python 표준 라이브러리 `datetime` 으로 계산한 값입니다.

| 구간 | 거리 |
|---|---|
| 1601-01-01 → 1970-01-01 | 11,644,473,600초 |
| 1899-12-30 → 1970-01-01 | 25,569일 |

이 상수와 형식 정의를 합치면 변환식이 나옵니다.

- FILETIME = (Unix 초 + 11,644,473,600) × 10,000,000
- WebKit = FILETIME ÷ 10
- Unix 초 = (DATE − 25,569) × 86,400

### 같은 순간을 형식별로 적은 예

아래 값은 형식 정의대로 계산해 만든 예시이고, 실제 데이터에서 나온 값이 아닙니다. DOS 를 뺀 나머지는 2024-01-01 00:00:00 UTC 를 적은 것이며, DOS 는 현지 시각 2024-01-01 12:34:56 을 적은 것입니다.

| 형식 | 값 | 디스크 바이트 (리틀 엔디언) |
|---|---|---|
| FILETIME | 133485408000000000 (0x01DA3C457689C000) | `00 C0 89 76 45 3C DA 01` |
| Unix 초 (32비트) | 1704067200 | `80 00 92 65` |
| WebKit | 13348540800000000 | — |
| OLE DATE | 45292.0 | `00 00 00 00 80 1D E6 40` |
| DOS | 날짜 0x5821, 시각 0x645C | `5C 64 21 58` (시각 워드가 앞에 올 때) |

### 헥스로 한 번 — FILETIME

1. 디스크 바이트 `00 C0 89 76 45 3C DA 01` 을 리틀 엔디언으로 읽습니다. 0x01DA3C457689C000 입니다.
2. 10진으로 바꾸면 133,485,408,000,000,000 입니다.
3. 10,000,000 으로 나누면 1601-01-01 부터 13,348,540,800초가 지났다는 뜻입니다.
4. 11,644,473,600 을 빼면 Unix 초 1,704,067,200 입니다.
5. 날짜로는 2024-01-01 00:00:00 UTC 입니다.
6. 한국 시각(UTC+9)으로는 같은 날 09:00:00 입니다.

### 헥스로 한 번 — DOS 날짜·시각

1. 앞 2바이트 `5C 64` 는 시각 워드 0x645C 입니다.
2. 비트 11~15 는 12 입니다. 12시입니다.
3. 비트 5~10 은 34 입니다. 34분입니다.
4. 비트 0~4 는 28 입니다. 2를 곱해 56초입니다.
5. 뒤 2바이트 `21 58` 은 날짜 워드 0x5821 입니다.
6. 비트 9~15 는 44 입니다. 1980 을 더해 2024년입니다.
7. 비트 5~8 은 1, 비트 0~4 도 1 입니다. 1월 1일입니다.
8. 결과는 2024-01-01 12:34:56 입니다.
9. 현지 시각이므로 UTC 로 바꾸려면 그 기기의 시간대를 알아야 합니다.

### 헥스로 한 번 — OLE 자동화 날짜

1. `00 00 00 00 80 1D E6 40` 을 리틀 엔디언 double 로 읽으면 45292.0 입니다.
2. 25,569 를 빼면 19,723 입니다. 1970-01-01 부터 지난 날 수입니다.
3. 86,400 을 곱하면 Unix 초 1,704,067,200 입니다.
4. 날짜로는 2024-01-01 00:00:00 입니다.
5. 이 값이 현지 시각인지 UTC 인지는 아티팩트마다 확인합니다.

### 시간대 맞추기

현지 시각 값을 UTC 로 맞추는 방법은 [타임라인 작성](../../03-techniques/analysis/timeline/index.md) 에서 다루고, 압수 PC 의 시간대 설정은 [시간대 설정](../../02-artifacts/system-account/time-zone.md) 에서 읽습니다.

## 포렌식에서 중요한 점

### 0 은 "설정 안 됨" 일 수 있습니다

FILETIME 0 을 그대로 날짜로 바꾸면 1601-01-01 이고, 그 0 이 "설정 안 됨" 이었다면 타임라인에 1601년 사건이 끼어듭니다. 0 의 뜻은 그 값이 쓰인 곳의 명세를 보고 정합니다.

### 정밀도가 낮은 기록을 시간 범위에서 빼지 않습니다

FAT 접근 시각처럼 날짜만 남는 값이 있습니다. 특정 한 시간 안의 사건만 추릴 때도 그날의 접근 기록은 그 시간에 일어났을 수 있습니다. 그래서 이런 기록을 시간 범위 밖이라고 빼면 안 됩니다.

### 바꿔 옮기면 정보가 줄 수 있습니다

시각을 다른 형식으로 옮기거나 문자열로 바꾸면 정밀도가 바뀔 수 있고, "0 = 설정 안 됨" 같은 뜻도 사라질 수 있습니다. 그래서 작업 기록과 보고서에는 바꾼 날짜와 함께 원시 값을 남깁니다.

### 문맥 없는 조각에서 찾은 값

카빙으로 찾은 레코드처럼 앞뒤 문맥이 없는 값은 형식을 짐작하기 쉽지만, 그럴듯한 날짜가 나왔다고 형식이 맞았다는 뜻은 아닙니다. FILETIME 과 WebKit 은 기준 시각이 같고 단위만 10배 다릅니다. 요즘 시각의 WebKit 값을 FILETIME 으로 읽으면 17세기 날짜가 나오고, 거꾸로 FILETIME 값을 WebKit 으로 읽으면 수천 년 뒤의 날짜가 나옵니다. 형식은 그 레코드의 명세로 정하고, 날짜가 그럴듯한지는 검산에만 씁니다.

## 함정

- **시간대 Bias 는 부호 있게 읽습니다.** `SYSTEM\ControlSet00X\Control\TimeZoneInformation\Bias` 는 REG_DWORD 로 저장합니다. 그러나 부호 있는 32비트로 읽어야 합니다. UTC+9 는 -540 이고, 부호 없이 읽으면 4294966756 입니다. 자세한 내용은 [시간대 설정](../../02-artifacts/system-account/time-zone.md) 에 있습니다.
- **도구가 보여 주는 10진수를 그대로 믿지 않습니다.** 하이브의 REG_DWORD 를 문자열로 받는 도구는 부호 없는 10진으로 보여 주는 경우가 많습니다. 부호에 뜻이 있는 값은 원시 바이트로 확인합니다.
- **32비트 POSIX 시각은 2038-01-19 03:14:07 에서 끝납니다.**
- **DOS 시각의 초는 짝수뿐입니다.** 같은 사건을 적은 다른 출처의 시각과 1초 차이가 나면 이 때문일 수 있습니다.
- **OLE 자동화 날짜의 기준일을 잘못 적은 문서가 있습니다.** dfDateTime 문서는 기준일을 1889-12-30 으로 적었지만[1], Microsoft 문서는 1899-12-30 으로 적습니다[3]. dfDateTime 문서 안의 Delphi 항목도 1899-12-30 입니다. 계산은 1899-12-30 으로 합니다.
- **GUID 안의 시각은 기준 시각이 다릅니다.** 읽는 법은 [윈도 식별자 형식](sid-guid-clsid-known-folder-id.md) 에 있습니다.

## 도구

**Python 표준 라이브러리** 로 기준 시각에 지난 시간을 더해 직접 확인할 수 있습니다.

```python
from datetime import datetime, timedelta

datetime(1601, 1, 1) + timedelta(microseconds=133485408000000000 // 10)  # FILETIME
datetime(1601, 1, 1) + timedelta(microseconds=13348540800000000)         # WebKit
datetime(1899, 12, 30) + timedelta(days=45292.0)                          # OLE DATE
```

세 줄 모두 2024-01-01 00:00:00 을 돌려주며, 결과에는 시간대가 붙지 않으므로 UTC 인지 현지 시각인지는 아티팩트를 보고 정합니다. OLE DATE 줄은 1899-12-30 보다 앞선 음수 값을 제대로 풀지 못합니다. 이런 값은 위 "OLE 자동화 날짜" 절의 규칙대로 따로 계산합니다.

다른 도구는 다음과 같습니다.

- **dfDateTime** — 참고 문헌 1 의 문서가 딸린 Python 라이브러리입니다. 이 페이지의 형식 대부분을 문서에서 설명합니다.
- **Windows API** — `DosDateTimeToFileTime` 으로 DOS 날짜·시각을 FILETIME 으로 바꿉니다.
- **헥스 편집기** — 고른 8바이트를 리틀 엔디언 정수나 double 로 보여 주는 기능이 있으면 위 따라가기를 바로 해 볼 수 있습니다.

도구마다 표시 시간대가 다를 수 있으며, 같은 값을 두 도구로 풀어 비교하는 방법은 [도구 결과 교차 검증](../../03-techniques/reporting/tool-validation.md) 에 있습니다.
