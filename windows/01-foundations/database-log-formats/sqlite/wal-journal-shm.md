# WAL과 롤백 저널 (-wal·-journal·-shm)

SQLite 는 주 파일을 고칠 때 같은 폴더에 보조 파일을 함께 씁니다.
롤백 저널 (Rollback Journal) 인 `-journal` 에는 바뀌기 **전** 페이지를 적고, 쓰기 전 로그 (Write-Ahead Log, WAL) 인 `-wal` 에는 바뀐 **뒤** 페이지를 적습니다.
그래서 주 파일만 읽으면 최근 기록을 놓치고, 이미 지운 기록을 유효한 기록으로 잘못 볼 수도 있습니다.

## 이 형식을 쓰는 아티팩트

DB 하나는 롤백 저널과 WAL 가운데 하나만 쓰고 둘을 동시에 쓰지 않습니다.
보조 파일은 늘 주 파일과 같은 폴더에 있으며, 이름은 주 파일 이름 뒤에 `-journal`·`-wal`·`-shm` 을 붙인 것입니다.
주 파일 머리의 오프셋 18·19 값이 1 이면 롤백 저널 방식이고, 2 이면 WAL 방식입니다. 머리 전체는 [파일·페이지 구조](b-tree-record-format.md) 에 있습니다.

| 파일 | 쓰는 방식 | 담는 것 | 복구에 필요한가 |
|---|---|---|---|
| `이름-journal` | 롤백 저널 | 트랜잭션이 바꾸기 전의 페이지 | 필요합니다. 끝나지 않은 트랜잭션을 되돌릴 때 씁니다 |
| `이름-wal` | WAL | 커밋했지만 아직 주 파일로 옮기지 않았을 수 있는 새 페이지 | 필요합니다. DB 상태의 일부입니다 |
| `이름-shm` | WAL | `-wal` 안의 프레임을 빨리 찾는 색인과 잠금 자리 | 필요하지 않습니다. `-wal` 을 읽어 다시 만듭니다 |

Windows 에서 만나는 예는 아래와 같습니다(Windows 11 빌드 26200 기준).

- [윈도 알림 기록 (wpndatabase.db)](../../../02-artifacts/execution/wpndatabase-db.md) 옆에 `-wal`·`-shm` 이 있습니다.
- [윈도 타임라인 (ActivitiesCache.db)](../../../02-artifacts/file-folder-usage/activitiescache-db.md) 옆에도 `-wal`·`-shm` 이 있습니다.
- 크롬·엣지 프로필의 `History`·`Web Data`·`Login Data` 옆에는 `-journal` 이 있고, 대부분 0바이트입니다. 같은 폴더의 `DIPS` 는 `-wal` 을 씁니다. ([방문·다운로드 기록 (History)](../../../02-artifacts/browsers/chrome-edge-whale/history.md))

어느 방식을 쓰는지는 앱과 앱 버전이 정하므로 분석 대상마다 폴더의 보조 파일과 주 파일 머리를 확인합니다.
이 형식은 Windows 버전과 상관이 없지만, SQLite 버전에 따라서는 아래가 달라집니다.

| SQLite 버전 | 달라진 점 |
|---|---|
| 3.7.0 (2010-07-21) | WAL 방식이 생겼습니다. WAL 방식 DB 는 이 버전 이상만 열 수 있습니다 |
| 3.22.0 (2018-01-22) | 쓰기 권한이 없는 WAL 방식 DB 도 조건이 맞으면 읽을 수 있게 되었습니다 |

롤백 저널 방식은 커밋할 때 저널을 치우는 방법이 여러 가지입니다. `journal_mode` 설정이 이것을 정합니다.

| journal_mode | 커밋할 때 하는 일 | 디스크에 남는 모습 |
|---|---|---|
| DELETE (기본값) | 저널 파일을 지웁니다 | 파일이 없습니다. 내용은 비할당 영역에 남을 수 있습니다 |
| TRUNCATE | 저널 길이를 0 으로 자릅니다 | 0바이트 파일이 남습니다 |
| PERSIST | 저널 머리를 0 으로 덮어씁니다 | 페이지 기록이 파일에 남습니다 |
| MEMORY | 저널을 메모리에만 둡니다 | 저널 파일이 없습니다 |
| OFF | 저널을 쓰지 않습니다 | 저널 파일이 없습니다 |
| WAL | 롤백 저널 대신 `-wal` 을 씁니다 | `-wal`·`-shm` |

WAL 설정만 DB 에 남고 다른 설정은 DB 를 다시 열면 기본값 DELETE 로 돌아갑니다.
PERSIST 에서 `journal_size_limit` 를 정했으면 커밋 뒤 그 크기를 넘는 부분을 잘라 냅니다.

같은 생각으로 만든 다른 형식으로 [레지스트리 .LOG1·.LOG2](../registry-hive/log1-log2.md) 와 [ESE 트랜잭션 로그](../extensible-storage-engine/edb-log-dirty-shutdown.md) 가 있습니다.

## 구조

### 롤백 저널 (`-journal`)

숫자는 모두 빅 엔디언입니다. (pager.c)

| 오프셋 | 크기 | 필드 | 뜻 |
|---|---|---|---|
| 0 | 8 | 매직 (Magic) | `D9 D5 05 F9 20 A1 63 D7` |
| 8 | 4 | 페이지 수 (Page Count) | 이 머리 뒤에 오는 페이지 기록 개수. −1(`FF FF FF FF`)이면 파일 끝까지 |
| 12 | 4 | 난수 (Nonce) | 검사합의 시작값. 트랜잭션마다 새로 뽑습니다 |
| 16 | 4 | 처음 DB 크기 | 트랜잭션 전 DB 크기 (페이지 수) |
| 20 | 4 | 섹터 크기 | 저널을 쓴 프로그램이 가정한 섹터 크기 |
| 24 | 4 | 페이지 크기 | DB 페이지 크기 |

머리는 섹터 하나를 혼자 쓰고 나머지 자리는 0 으로 채우므로, 첫 페이지 기록은 섹터 크기만큼 떨어진 위치에서 시작합니다.
페이지 수가 0 보다 크면 그 개수의 기록 뒤에 머리가 한 번 더 올 수 있습니다.

페이지 기록 하나는 아래와 같습니다. N 은 페이지 크기입니다.

| 오프셋 | 크기 | 뜻 |
|---|---|---|
| 0 | 4 | 주 파일 안의 페이지 번호 |
| 4 | N | 트랜잭션 전 페이지 내용 |
| N+4 | 4 | 검사합 (Checksum) |

기록 하나의 크기는 N + 8 바이트이고, 한 저널 안에 같은 페이지는 한 번만 나옵니다.
빈 페이지 목록의 잎 페이지 (Freelist Leaf Page) 는 되돌릴 정보가 없는 페이지로 보기 때문에 저널에 적지 않습니다.
- 검사합은 난수에 페이지 안 바이트 몇 개를 더한 값입니다. 오프셋 N−200 부터 200바이트씩 앞으로 가며 한 바이트씩 더합니다. 페이지가 4,096바이트면 20바이트만 더합니다.
- 동기화를 끄지 않은 보통 설정에서, SQLite 는 페이지 기록을 디스크에 확실히 쓴 다음 매직과 페이지 수를 채웁니다. 그 전까지 두 필드는 0 입니다. (pager.c)

Windows 11 빌드 26200 의 엣지는 브라우저를 닫은 뒤에도 `History-journal` 을 남길 수 있습니다. 한 예는 8,720바이트입니다.
이 파일은 앞 12바이트(매직·페이지 수)가 0 이고, 크기는 512바이트 머리와 4,104바이트 페이지 기록 2개를 더한 값과 같습니다.
두 기록의 검사합은 명세의 계산법으로 맞습니다.

### 핫 저널 (Hot Journal)

되돌리기에 필요한 내용이 든 저널을 핫 저널이라고 부릅니다. SQLite 는 아래 네 조건이 모두 맞으면 핫 저널로 봅니다.

- 저널 파일이 있습니다.
- 어떤 프로세스도 DB 에 RESERVED 이상의 잠금을 걸지 않았습니다.
- 주 파일 크기가 0 보다 큽니다.
- 저널의 첫 바이트가 있고, 그 값이 0x00 이 아닙니다.

SQLite 는 DB 를 열다가 핫 저널을 찾으면 저널의 페이지를 주 파일에 도로 쓰고, 그러면 주 파일은 끝나지 않은 트랜잭션이 시작되기 전 상태로 돌아갑니다.

### WAL (`-wal`)

WAL 은 32바이트 머리 뒤에 프레임 (Frame) 이 이어지는 구조입니다. 프레임 하나에는 바뀐 페이지 하나가 들어갑니다.
머리와 프레임 머리의 숫자는 모두 빅 엔디언입니다.

| 오프셋 | 크기 | 필드 | 뜻 |
|---|---|---|---|
| 0 | 4 | 매직 | `0x377F0682` 또는 `0x377F0683` |
| 4 | 4 | 형식 버전 | 3007000 (`0x002DE218`) |
| 8 | 4 | 페이지 크기 | DB 페이지 크기 |
| 12 | 4 | 체크포인트 순번 (Checkpoint sequence number) | WAL 을 처음부터 다시 쓸 때마다 1 오릅니다 (wal.c) |
| 16 | 4 | 솔트-1 (Salt-1) | 다시 쓸 때마다 1 오릅니다 |
| 20 | 4 | 솔트-2 (Salt-2) | 다시 쓸 때마다 새 난수로 바뀝니다 |
| 24 | 8 | 검사합-1·2 | 머리 앞 24바이트의 검사합 |

프레임 머리는 24바이트입니다. 바로 뒤에 페이지 내용이 옵니다.

| 오프셋 | 크기 | 필드 | 뜻 |
|---|---|---|---|
| 0 | 4 | 페이지 번호 | 이 프레임이 담은 페이지 |
| 4 | 4 | 커밋 크기 | 커밋 프레임이면 커밋 뒤 DB 크기 (페이지 수). 아니면 0 |
| 8 | 4 | 솔트-1 | WAL 머리에서 베낀 값 |
| 12 | 4 | 솔트-2 | WAL 머리에서 베낀 값 |
| 16 | 8 | 검사합-1·2 | 처음부터 이 프레임까지 이어서 계산한 검사합 |

프레임 i(1부터 셈)는 32 + (i − 1) × (24 + 페이지 크기) 에서 시작합니다.
커밋 크기가 0 이 아닌 프레임을 커밋 프레임 (Commit Frame) 이라고 부르며 트랜잭션 하나가 여기서 끝나는데, WAL 하나에는 보통 트랜잭션이 여럿 들어 있습니다.

프레임은 아래 두 조건이 맞을 때만 유효합니다.

- 프레임의 솔트 두 값이 WAL 머리의 솔트와 같습니다.
- 이어서 계산한 검사합이 맞습니다. 계산 범위는 WAL 머리 앞 24바이트, 그리고 이 프레임까지 모든 프레임의 머리 앞 8바이트와 페이지 내용입니다.

검사합은 입력을 32비트 정수 두 개씩 묶어 계산합니다. 넘친 자리는 버립니다.

```
s0 = s1 = 0
정수 두 개 x(i), x(i+1) 마다:
    s0 = s0 + x(i)   + s1
    s1 = s1 + x(i+1) + s0
```

- 매직이 `0x377F0682` 이면 입력을 리틀 엔디언 정수로 읽습니다.
- 매직이 `0x377F0683` 이면 입력을 빅 엔디언 정수로 읽습니다.

결과는 매직과 상관없이 빅 엔디언으로 저장합니다.
SQLite 는 WAL 을 쓰는 컴퓨터의 바이트 순서에 맞춰 매직을 고릅니다. (wal.c)

Windows 11 빌드 26200 의 `wpndatabase.db-wal` 은 매직이 `0x377F0682` 이고, 검사합을 리틀 엔디언으로 계산하면 머리와 모든 프레임에서 맞습니다.

### 읽는 규칙·체크포인트·초기화

페이지 P 를 읽을 때 SQLite 는 WAL 에서 P 의 마지막 유효 프레임을 쓰는데, 그 프레임이 커밋 프레임이거나 그 뒤에 커밋 프레임이 있어야 합니다.
그런 프레임이 없으면 주 파일의 페이지 P 를 읽습니다.
마지막 커밋 프레임 뒤에 있는 유효한 프레임은 끝나지 않은 트랜잭션이라서 SQLite 는 이 프레임을 읽지 않습니다.

체크포인트 (Checkpoint) 는 WAL 의 유효한 내용을 주 파일로 옮기는 일입니다.
기본 설정에서는 WAL 이 1,000페이지를 넘으면 트랜잭션이 끝날 때 체크포인트가 저절로 돌고, 페이지가 4,096바이트면 약 4MB 입니다. 앱이 이 기준을 바꾸거나 끌 수 있습니다.
체크포인트는 보통 WAL 을 자르지 않고 다음 쓰기가 파일 처음부터 덮어쓰는데, 이것을 WAL 초기화 (WAL Reset) 라고 부릅니다.
초기화할 때 솔트-1 은 1 오르고 솔트-2 는 새 난수가 되므로, 아직 덮이지 않은 옛 프레임은 솔트가 달라서 무효가 됩니다.
`journal_size_limit` 를 정했으면 초기화할 때 WAL 을 자르기도 합니다.

마지막 연결이 정상으로 닫히면 SQLite 는 체크포인트를 한 뒤 `-wal` 과 `-shm` 을 지우지만, 앱이 정상으로 닫히지 않았거나 마지막 연결이 읽기 전용이었으면 두 파일이 남을 수 있습니다.
새로 만든 `-wal` 은 체크포인트 순번이 0 이고 솔트도 새 난수입니다. (wal.c)

### WAL 색인 (WAL-index, `-shm`)

`-shm` 은 DB 를 여는 프로그램들이 함께 쓰는 공유 메모리를 파일로 둔 것입니다. DB 내용은 들어 있지 않습니다.

숫자는 쓰는 컴퓨터의 바이트 순서로 적으며, x86·x64·ARM64 Windows 는 모두 리틀 엔디언입니다.
SQLite 는 이 파일을 디스크에 강제로 쓰지(fsync) 않습니다.
크기는 32,768바이트의 배수이고 대개 정확히 32,768바이트입니다. 첫 32,768바이트가 프레임 4,062개를 맡으므로, WAL 이 이보다 커질 때 파일이 늘어납니다.
배타 잠금 방식 (`locking_mode=EXCLUSIVE`) 에서는 `-shm` 을 만들지 않고 메모리만 씁니다.

머리 136바이트 가운데 분석에 쓰는 필드는 아래와 같습니다.

| 오프셋 | 크기 | 필드 | 뜻 |
|---|---|---|---|
| 0 | 4 | iVersion | 3007000 |
| 12 | 1 | isInit | 1 이면 초기화된 상태 |
| 13 | 1 | bigEndCksum | WAL 검사합이 빅 엔디언이면 1 |
| 14 | 2 | szPage | 페이지 크기. 65,536 이면 1 |
| 16 | 4 | mxFrame | 유효하고 커밋된 프레임 수. 마지막 유효 커밋 프레임의 번호와 같습니다 |
| 20 | 4 | nPage | DB 크기 (페이지 수) |
| 32 | 8 | aSalt | WAL 머리의 솔트 두 값. WAL 의 바이트 순서 그대로입니다 |
| 48 | 48 | (사본) | 0~47 바이트를 한 벌 더 적은 것 |
| 96 | 4 | nBackfill | 체크포인트로 주 파일에 이미 옮긴 프레임 수 |
| 100 | 20 | read-mark[0~4] | 읽는 연결들이 쓰는 표시 다섯 개 |
| 128 | 4 | nBackfillAttempted | 옮기려 했지만 다 옮겼는지 모르는 프레임 수 |

머리 뒤에는 프레임마다 페이지 번호를 적은 배열(aPgno)과 해시 표(aHash)가 옵니다.
mxFrame 과 nBackfill 로 WAL 을 셋으로 나눌 수 있는데, 프레임 1~nBackfill 은 이미 주 파일에 옮겼고 그 뒤 mxFrame 까지는 WAL 에만 있으며 mxFrame 뒤는 SQLite 가 쓰지 않는 프레임입니다.
같은 `wpndatabase.db` 의 `-shm` 에서 aSalt 는 `-wal` 머리의 솔트와 같습니다.

> 그림 자리: 주 파일, `-wal`(머리 → 프레임 … → 커밋 프레임 → 옛 솔트 프레임), `-shm`(nBackfill·mxFrame 이 가리키는 프레임 범위) 세 파일의 관계

## 읽는 법 — 헥스로 한 번 따라가기

아래 바이트는 **명세로 만든 예시**입니다. 실제 데이터에서 나온 값이 아닙니다. `..` 은 설명에 필요 없는 바이트입니다.

**1단계. 주 파일 머리에서 방식을 봅니다.**

```
주 파일, 오프셋 0x10 (명세로 만든 예시)
00000010  10 00 02 02 .. .. .. ..  .. .. .. .. .. .. .. ..
```

- 오프셋 16~17 의 페이지 크기는 0x1000(4,096바이트) 입니다.
- 오프셋 18·19 가 모두 2 입니다. WAL 방식이므로 같은 폴더의 `-wal` 을 찾습니다.

**2단계. WAL 머리를 읽습니다.**

```
이름-wal, 오프셋 0x00 (명세로 만든 예시)
00000000  37 7F 06 82 00 2D E2 18  00 00 10 00 00 00 00 03
00000010  5A 1B 3C 4D 11 22 33 44  .. .. .. .. .. .. .. ..
```

- 매직이 `0x377F0682` 입니다. 검사합은 리틀 엔디언 정수로 계산합니다.
- 형식 버전은 3007000 입니다.
- 페이지 크기는 4,096바이트입니다.
- 체크포인트 순번은 3 입니다. 이 `-wal` 은 만든 뒤 세 번 초기화되었습니다.
- 솔트-1 은 0x5A1B3C4D, 솔트-2 는 0x11223344 입니다.
- 프레임 하나는 24 + 4,096 = 4,120(0x1018) 바이트입니다.

**3단계. 프레임 머리를 차례로 읽습니다.** (검사합 8바이트는 줄였습니다.)

```
프레임  위치     페이지 번호   커밋 크기     솔트-1        솔트-2        (명세로 만든 예시)
1       0x0020   00 00 00 05   00 00 00 00   5A 1B 3C 4D   11 22 33 44
2       0x1038   00 00 00 02   00 00 00 0C   5A 1B 3C 4D   11 22 33 44
3       0x2050   00 00 00 05   00 00 00 0C   5A 1B 3C 4D   11 22 33 44
4       0x3068   00 00 00 07   00 00 00 00   5A 1B 3C 4C   9E 8D 7C 6B
```

- 프레임 1 은 페이지 5 입니다. 커밋 프레임이 아닙니다.
- 프레임 2 는 페이지 2 이고 커밋 크기가 12 입니다. 첫 트랜잭션은 프레임 1~2 이고, 커밋 뒤 DB 는 12페이지입니다.
- 프레임 3 은 페이지 5 를 다시 담은 커밋 프레임입니다. 둘째 트랜잭션입니다.
- 프레임 4 는 솔트-1 이 머리보다 1 작고 솔트-2 도 다릅니다. 초기화 전 세대의 프레임입니다. SQLite 는 이 프레임을 쓰지 않습니다. 내용은 그대로 읽을 수 있습니다.
- 머리부터 프레임 1·2·3 까지 검사합을 이어서 계산해 맞춰 봅니다. 중간에 틀리면 그 프레임부터 무효입니다.
- `-shm` 이 있으면 mxFrame 이 3 인지 봅니다.

**4단계. 페이지마다 판을 정리합니다.**

| 페이지 | 판 (옛 → 새) |
|---|---|
| 5 | 주 파일의 페이지 5 → 프레임 1 → 프레임 3 (지금 상태) |
| 2 | 주 파일의 페이지 2 → 프레임 2 (지금 상태) |
| 7 | 프레임 4 (주 파일의 페이지 7 과 같거나 더 옛 판) → 주 파일의 페이지 7 (지금 상태) |

- 페이지 7 이 이렇게 되는 이유가 있습니다. 초기화는 앞 세대 프레임을 주 파일에 모두 옮긴 뒤에만 일어납니다.
- 주 파일의 판이 가장 옛 판이라는 것은 이 프레임들이 아직 옮겨지지 않았을 때만 맞습니다. `-shm` 의 nBackfill 이 0 보다 크면 그만큼은 주 파일에 이미 들어가 있습니다.
- 주 파일에서 페이지 5 는 (5 − 1) × 4,096 = 0x4000 에서 시작합니다.
- 판마다 셀을 비교하면 레코드가 생기고, 바뀌고, 지워진 순서를 알 수 있습니다. 페이지 안 셀을 읽는 법은 [파일·페이지 구조](b-tree-record-format.md) 에 있습니다.

**5단계. 롤백 저널이면 이렇게 읽습니다.**

```
이름-journal (명세로 만든 예시)
00000000  D9 D5 05 F9 20 A1 63 D7  00 00 00 01 1F 2E 3D 4C
00000010  00 00 00 0C 00 00 02 00  00 00 10 00 00 00 00 00
...
00000200  00 00 00 05 0D .. .. ..  .. .. .. .. .. .. .. ..
```

- 매직이 맞습니다. 페이지 수는 1 이고, 난수는 0x1F2E3D4C 입니다.
- 처음 DB 크기는 12페이지, 섹터 크기는 0x200(512), 페이지 크기는 0x1000(4,096) 입니다.
- 첫 기록은 오프셋 0x200 에서 시작합니다. 페이지 번호는 5 입니다.
- 0x204 부터 4,096바이트가 트랜잭션 전의 페이지 5 입니다. 첫 바이트 0x0D 는 테이블 B-트리의 잎 페이지라는 뜻입니다.
- 검사합은 0x1204 에 있습니다. 다음 기록은 0x1208 에서 시작합니다.
- 이 저널이 핫 저널이면 SQLite 는 이 내용을 주 파일 오프셋 0x4000 에 도로 씁니다.

## 포렌식에서 중요한 점

### 주 파일만 읽으면 두 가지를 틀립니다

WAL 방식에서 최근 변경은 체크포인트 전까지 `-wal` 에만 있으므로, 주 파일만 읽으면 새로 생긴 레코드가 빠집니다.
삭제도 `-wal` 에 먼저 적히기 때문에 지운 레코드가 주 파일에는 아직 살아 있을 수 있고, 주 파일만 읽으면 이 레코드를 지금 있는 레코드로 잘못 봅니다.
주 파일만 연 모습은 마지막 체크포인트 때의 상태이고 `-wal` 을 함께 연 모습은 마지막 커밋 때의 상태이므로, 두 결과가 다른 것은 정상입니다.

### 한 페이지의 여러 판

`-wal` 에는 같은 페이지의 프레임이 여럿 있을 수 있고 판마다 레코드 내용이 다릅니다.
같은 `-wal` 안에서는 솔트-1 이 클수록 새 세대이고, 솔트-1 이 같으면 파일 뒤쪽에 있는 프레임이 더 새것입니다.
서로 다른 `-wal` 파일 사이의 순서는 새 파일이 솔트를 새 난수로 시작하므로 솔트로 정할 수 없습니다.
보안 삭제 (`secure_delete`) 가 켜진 앱이라도 옛 프레임과 저널에는 지우기 전 페이지가 남을 수 있습니다. 실험 결과는 [파일 안에 남은 지운 레코드](freelist-freeblock.md) 에 있습니다.

### 남는 옛 기록

- 초기화 뒤에도 새 프레임이 닿지 않은 뒤쪽 프레임은 파일에 남습니다. SQLite 는 쓰지 않지만 내용은 읽을 수 있습니다.
- PERSIST 방식 저널과 매직이 0 인 저널에는 마지막 트랜잭션 전의 페이지가 남을 수 있습니다. SQLite 는 첫 바이트가 0x00 인 저널을 되돌리기에 쓰지 않습니다.
- DELETE 방식은 쓰기 트랜잭션마다 `-journal` 을 만들고 지웁니다. 그래서 [USN 변경 저널 ($UsnJrnl)](../../../02-artifacts/filesystem/usnjrnl.md) 에 이 파일의 생성·삭제 기록이 남을 수 있습니다.
- 지운 `-wal`·`-journal` 의 내용은 비할당 영역에 남을 수 있습니다. WAL 매직 `37 7F 06 82`·`37 7F 06 83` 과 저널 매직 `D9 D5 05 F9 20 A1 63 D7` 을 찾아봅니다. 방법은 [파일 카빙](../../../03-techniques/analysis/data-recovery/file-carving.md) 과 [레코드 카빙](../../../03-techniques/analysis/data-recovery/record-carving.md) 에 있습니다.
- [섀도 복사본](../../../03-techniques/analysis/volume-shadow-copy-analysis.md) 에는 예전 시점의 주 파일과 `-wal` 이 함께 들어 있을 수 있습니다.

### 비정상 종료

마지막 커밋 프레임 뒤에 솔트와 검사합이 맞는 프레임이 있으면 커밋되지 않은 트랜잭션이며, 수집 순간에 쓰던 중이었거나 앱이 갑자기 꺼진 경우입니다.
핫 저널이 있으면 주 파일에는 끝나지 않은 트랜잭션이 쓴 페이지가 섞여 있을 수 있고 저널에는 그 전 페이지가 있으므로, 둘 다 따로 봐 둡니다.

### 여는 순간 파일이 바뀝니다

일반 SQLite 프로그램으로 열면 핫 저널은 주 파일로 되돌려집니다.
WAL 방식 DB 를 열었다 닫으면 체크포인트가 돌고 `-wal`·`-shm` 이 지워질 수 있는데, 이때 주 파일 안의 옛 판이 덮이고 `-wal` 의 옛 프레임도 사라집니다.
주 파일을 `-wal` 과 떼어 놓으면 커밋한 트랜잭션을 잃거나 DB 가 깨질 수 있습니다.
그래서 주 파일, `-journal`, `-wal`, `-shm` 을 같은 이름 그대로 함께 모으고, 파일마다 해시를 남기며 사본에서만 작업합니다. 방법은 [선별 수집](../../../03-techniques/process-acquisition/evidence-acquisition/triage-collection.md) 과 [해시로 무결성 검증](../../../03-techniques/process-acquisition/evidence-acquisition/hash-verification.md) 에 있습니다.
디스크 이미지 속 `-shm` 은 SQLite 가 이 파일을 디스크에 강제로 쓰지 않기 때문에 마지막 상태와 다를 수 있으므로, mxFrame·nBackfill 은 참고로만 쓰고 `-wal` 로 다시 확인합니다.

### 증거로 쓸 때

- **알 수 있는 것**: 유효한 커밋 프레임까지의 페이지 내용이 DB 의 어느 한 시점에 커밋되었다는 것.
- **알 수 있는 것**: 솔트와 프레임 위치로 본 판의 앞뒤 순서.
- **알 수 없는 것**: 프레임이나 저널 기록을 쓴 시각. 머리에 시각 필드가 없습니다. 시각은 레코드 안의 값([시각 값 형식](../../value-decoding/filetime-unix-webkit-dos-ole.md))과 파일 시스템 시각([파일 시각 네 가지와 변화 규칙](../../../03-techniques/analysis/timeline/macb-timestamp-rules.md))으로만 추정합니다.
- **알 수 없는 것**: 누가 지웠는지. 앱이 오래된 기록을 스스로 정리했을 수도 있습니다.

보고서에는 "주 파일에는 없고, `-wal` 의 프레임 3(둘째 트랜잭션의 커밋 프레임)에 담긴 페이지 5 에 이 레코드가 있다" 처럼 기록으로 확인되는 만큼만 씁니다.

## 함정

- **주 파일만 복사하거나 파싱합니다.** 최근 변경을 놓치고, 지운 레코드를 살아 있다고 봅니다.
- **`immutable=1` 로 연 결과를 최신 상태로 봅니다.** 이 방식으로 연 사본은 `-wal` 을 읽지 않습니다 (pager.c). 주 파일만의 상태를 보는 데는 알맞지만 최신 상태는 아닙니다.
- **`-wal` 이 없으면 최근 활동이 없었다고 봅니다.** 정상으로 닫히면 SQLite 가 `-wal` 을 지웁니다.
- **파일 뒤쪽 프레임이 가장 새것이라고 봅니다.** 초기화 뒤에는 뒤쪽에 가장 옛 세대가 남습니다. 솔트부터 비교합니다.
- **0바이트 `-journal` 을 이상한 흔적으로 봅니다.** TRUNCATE 방식이 커밋할 때 남기는 정상 모습입니다.
- **매직이 0 인 저널을 빈 파일로 봅니다.** 머리만 0 이고 페이지 기록은 남아 있을 수 있습니다.
- **저널 검사합이 맞으면 페이지 전체가 온전하다고 봅니다.** 4,096바이트 페이지에서 20바이트만 봅니다.
- **`-shm` 을 빅 엔디언으로 읽습니다.** 주 파일·`-wal` 과 달리 `-shm` 의 숫자는 쓰는 컴퓨터의 바이트 순서를 따릅니다. Windows 에서는 리틀 엔디언입니다. aSalt 두 값만 WAL 의 바이트 순서 그대로입니다.
- **nBackfill 위치를 잘못 잡습니다.** SQLite 의 WAL 형식 문서 본문 한 곳은 nBackfill 을 오프셋 128 이라고 적습니다. 같은 문서의 표와 wal.c 구조체로는 96 입니다. 128 은 nBackfillAttempted 입니다.
- **WAL 방식 DB 의 파일 변경 카운터(오프셋 24)로 트랜잭션 수를 셉니다.** WAL 방식에서는 이 값이 트랜잭션마다 오르지 않을 수 있습니다.
- **암호화된 DB 의 프레임을 그대로 읽습니다.** 프레임 머리는 읽히지만 페이지 내용은 풀어야 합니다. [암호화된 SQLite (SQLCipher)](sqlcipher.md) 를 봅니다.

## 도구

아래 공개 도구는 예로만 듭니다. 한 도구의 결과에만 기대지 않습니다.

| 도구 | 쓰임 |
|---|---|
| sqlite3 명령줄 셸 (SQLite 공식) | 사본에서만 씁니다. `-wal` 을 함께 둔 사본과 뺀 사본을 따로 열어 두 상태를 비교합니다 |
| FQLite (Apache-2.0) | 롤백 저널과 WAL 을 읽습니다 |
| bring2lite | 주 파일·WAL·저널의 구조를 분석해 지운 레코드를 찾습니다 |
| 헥스 편집기와 짧은 스크립트 | 위 표대로 프레임을 나누고 검사합을 다시 계산합니다 |

두 도구의 결과가 다르면 먼저 WAL 을 넣었는지, 어느 프레임까지 썼는지, 옛 세대 프레임을 넣었는지를 비교하며, 검증 방법은 [도구 결과 교차 검증](../../../03-techniques/reporting/tool-validation.md) 에 있습니다.
