# 파일 안에 남은 지운 레코드 (Freelist·Freeblock)

## 한 줄 요약

SQLite 는 행을 지워도 그 바이트를 곧바로 0 으로 채우지 않고, 그 자리를 빈 공간으로 표시해 두었다가 나중에 다시 씁니다. 페이지 전체가 비면 프리리스트 (Freelist) 에 올라가고, 페이지 일부가 비면 프리블록 (Freeblock) 이나 비할당 영역 (Unallocated Region) 이 됩니다. 이 세 곳이 파일 안에서 지운 레코드를 찾는 자리입니다. 다만 앱이 보안 삭제 (secure_delete) 를 켜 두었으면 대부분 0 으로 바뀌어 있습니다.

페이지·셀·레코드 형식 자체는 [파일·페이지 구조 (B-tree·Record Format)](b-tree-record-format.md) 에서 다룹니다. 이 글은 빈 공간만 봅니다.

## 이 형식을 쓰는 아티팩트

Windows 에서 만나는 SQLite 파일은 모두 해당합니다. 크롬 계열 [방문·다운로드 기록 (History)](../../../02-artifacts/browsers/chrome-edge-whale/history.md), 파이어폭스 [places.sqlite](../../../02-artifacts/browsers/firefox/places-sqlite.md), [윈도 타임라인 (ActivitiesCache.db)](../../../02-artifacts/file-folder-usage/activitiescache-db.md), [윈도 알림 기록 (wpndatabase.db)](../../../02-artifacts/execution/wpndatabase-db.md) 이 그 예입니다.

지운 레코드가 남는 정도는 Windows 버전보다 앱 설정에 달려 있습니다. 앱이 SQLite 를 직접 넣어 배포하는 경우가 많기 때문입니다. 보안 삭제 설정은 DB 파일 헤더에 적히지 않고 연결마다 정하는 값이며, 기본값은 앱을 빌드할 때 정합니다. 앱별 설정은 아래와 같습니다.

| 앱 | 빌드 설정 (2026년 9월 공개 소스 기준) | 뜻 |
|---|---|---|
| 크롬 계열 (Chromium 소스) | 공통 빌드 설정에 `SQLITE_SECURE_DELETE` 가 있습니다. 코드도 이 값이 1 이라고 가정합니다[5]. | 본 파일의 프리블록·프리리스트는 대부분 0 입니다. |
| 파이어폭스 | 빌드 설정(moz.build)에서 `SQLITE_SECURE_DELETE` 를 1 로 정합니다[6]. | 위와 같습니다. |
| 그 밖의 앱·Windows 기본 DB | 공개 자료 없음 | 빈 공간을 직접 열어 보고 판단합니다. |

보안 삭제가 켜진 앱이라도 `-wal` 파일의 옛 프레임이나 롤백 저널에는 지우기 전 페이지가 남을 수 있습니다. secure_delete 를 켠 DB 에서도 WAL 파일로 지운 레코드를 되살릴 수 있습니다[4]. 자세한 내용은 [WAL과 롤백 저널 (-wal·-journal·-shm)](wal-journal-shm.md) 에 있습니다.

## 구조

모든 정수는 빅엔디언입니다. 페이지 번호는 1 부터 셉니다. N번 페이지는 파일의 (N−1) × 페이지 크기 위치에서 시작합니다.

### 파일 헤더에서 볼 필드

| 오프셋 | 크기 | 뜻 |
|---|---|---|
| 16 | 2 | 페이지 크기. 값 1 은 65536 입니다. |
| 20 | 1 | 페이지 끝 예약 바이트 수. 페이지 크기에서 이 값을 뺀 것이 사용 가능 크기입니다. |
| 32 | 4 | 첫 프리리스트 트렁크 페이지 번호. 0 이면 프리리스트가 비어 있습니다. |
| 36 | 4 | 프리리스트 페이지 전체 수 (트렁크 + 리프) |
| 52 | 4 | 0 이 아니면 자동 정리 (auto_vacuum) 나 단계 정리 (incremental_vacuum) 모드입니다. |
| 64 | 4 | 52 가 0 이 아닐 때, 참이면 단계 정리 모드이고 거짓이면 자동 정리 모드입니다. |

### 프리리스트: 통째로 빈 페이지

프리리스트는 트렁크 페이지 (Trunk Page) 가 사슬로 이어진 목록입니다. 트렁크 페이지마다 리프 페이지 (Leaf Page) 번호가 적혀 있습니다.

| 트렁크 페이지 오프셋 | 크기 | 뜻 |
|---|---|---|
| 0 | 4 | 다음 트렁크 페이지 번호. 0 이면 마지막 트렁크입니다. |
| 4 | 4 | 이 트렁크에 적힌 리프 페이지 수 (L) |
| 8 | 4 × L | 리프 페이지 번호 목록 |

리프 페이지에는 아무 구조도 적지 않습니다. SQLite 는 리프 페이지를 되도록 읽지도 쓰지도 않으므로[1], 리프 페이지에는 비기 전에 마지막으로 파일에 쓰인 내용이 그대로 남고 옛 b-트리 페이지였다면 페이지 머리말과 셀까지 남습니다.
트렁크가 된 페이지는 앞 8바이트가 덮이고, 리프 번호가 늘수록 오프셋 8 부터 차례로 덮입니다. 옛 페이지 머리말과 셀 포인터 배열이 먼저 사라지고, 페이지 끝쪽 셀은 남는 경우가 많습니다.
트렁크 하나에는 리프를 (사용 가능 크기 ÷ 4) − 8 개까지만 넣는데, 3.6.0 이전 버전과 맞추려고 마지막 6칸을 비워 두기 때문입니다. 4096바이트 페이지라면 1016개입니다.
지운 레코드가 쓰던 오버플로 페이지 (Overflow Page) 도 프리리스트로 가고, `DROP TABLE` 로 지운 표의 페이지도 마찬가지입니다.

### 페이지 안의 빈 공간

사용 중인 b-트리 페이지 안에도 빈 곳이 있습니다. 페이지 머리말에서 볼 필드는 아래와 같습니다. 1번 페이지는 머리말이 오프셋 100 에서 시작하지만, 머리말 안의 위치 값은 모두 페이지 첫 바이트를 기준으로 셉니다.

| 머리말 오프셋 | 크기 | 뜻 |
|---|---|---|
| 0 | 1 | 페이지 종류 (0x02·0x05·0x0A·0x0D) |
| 1 | 2 | 첫 프리블록 위치. 0 이면 프리블록이 없습니다. |
| 3 | 2 | 셀 수 |
| 5 | 2 | 셀 내용 영역 시작 위치. 0 은 65536 입니다. |
| 7 | 1 | 조각 바이트 합계 |

빈 곳은 세 가지입니다.

| 종류 | 자리 | 모양 | 지운 레코드가 남는 정도 |
|---|---|---|---|
| 비할당 영역 | 셀 포인터 배열 끝부터 셀 내용 영역 시작까지 | 머리말이 없습니다. | 셀 내용 영역 맨 앞 셀을 지우면 SQLite 는 시작 위치만 옮깁니다. 이때 셀이 통째로 남습니다. |
| 프리블록 | 셀 내용 영역 안 | 앞 2바이트는 다음 프리블록 위치, 다음 2바이트는 이 블록 크기(4바이트 머리말 포함)입니다. | 셀의 앞 4바이트가 덮이고 나머지는 남습니다. |
| 조각 (Fragment) | 셀 사이 1~3바이트 | 머리말이 없습니다. 합계만 머리말 오프셋 7 에 적힙니다. | 레코드로 쓸 만한 내용이 거의 없습니다. 합계는 60 을 넘지 않습니다. |

프리블록은 늘 위치가 커지는 순서로 이어지고, 새로 빈 곳이 이웃 프리블록과 3바이트 이하로 떨어져 있으면 SQLite 는 둘을 하나로 합칩니다. 그래서 붙어 있던 레코드 여러 개를 함께 지우면 큰 프리블록 하나가 되는데, 이때 앞 4바이트가 덮이는 것은 첫 레코드뿐이고 뒤 레코드는 통째로 남습니다.

> 그림 자리: b-트리 페이지 한 장의 배치(머리말 → 셀 포인터 배열 → 비할당 영역 → 셀·프리블록·조각이 섞인 셀 내용 영역)와 머리말 오프셋 1 에서 시작하는 프리블록 사슬. 옆에 파일 헤더 오프셋 32 에서 시작하는 트렁크 → 리프 사슬.

## 읽는 법

1. 사본을 만듭니다. 같은 폴더의 `-wal`·`-journal` 도 함께 복사합니다. SQLite 라이브러리로 열고 닫으면 WAL 체크포인트나 저널 되돌리기가 일어나 빈 공간이 덮일 수 있습니다. 라이브러리로 열 때는 사본을 `immutable=1` URI 로 엽니다.
2. 헤더 오프셋 16·20 에서 페이지 크기와 사용 가능 크기를 구합니다.
3. 헤더 오프셋 52·64 에서 정리 모드를 확인합니다. 오프셋 32·36 에서 프리리스트 시작과 개수를 읽습니다.
4. 트렁크 사슬을 따라가며 리프 번호를 모읍니다. 트렁크 수와 리프 수의 합이 오프셋 36 값과 맞는지 봅니다. 맞지 않으면 사슬이 끊겼거나 파일이 손상된 것입니다.
5. 리프 페이지의 첫 바이트가 0x0D 같은 b-트리 페이지 종류 값이면 옛 b-트리 페이지로 해석해 봅니다. 트렁크 페이지는 리프 번호 목록 뒤쪽을 봅니다.
6. 사용 중인 b-트리 페이지마다 머리말 오프셋 1 에서 프리블록 사슬을 따라갑니다. 비할당 영역도 함께 봅니다.
7. `sqlite_schema` 표의 `CREATE` 문으로 표마다 열 개수와 형을 알아냅니다. 빈 공간의 바이트를 각 표의 serial type 모양에 맞춰 봅니다.

### 헥스로 따라가기: 프리리스트

아래는 명세로 만든 예시입니다. 페이지 크기는 4096 (오프셋 16 = `10 00`) 으로 둡니다.

```
헤더 0x20: 00 00 00 07    첫 트렁크 = 7번 페이지
헤더 0x24: 00 00 00 03    프리리스트 페이지 3개

7번 페이지 (파일 위치 0x6000 = 6 × 4096):
0x6000: 00 00 00 00  00 00 00 02  00 00 00 09  00 00 00 0C
        다음 트렁크 없음 | 리프 2개 | 9번 페이지 | 12번 페이지
```

트렁크 1개와 리프 2개를 더하면 3 이고, 헤더 값과 맞습니다. 9번 페이지는 0x8000, 12번 페이지는 0xB000 에서 시작합니다. 이 두 페이지의 첫 바이트가 0x0D 이면 옛 표 리프 페이지로 읽어 봅니다.

### 헥스로 따라가기: 프리블록

이것도 명세로 만든 예시입니다. 표는 `CREATE TABLE t(id INTEGER PRIMARY KEY, url TEXT, cnt INTEGER)` 입니다. rowid 5, url "a.kr", cnt 3 인 행의 셀은 11바이트입니다.

```
지우기 전: 09 05 04 00 15 01 61 2E 6B 72 03
```

| 바이트 | 뜻 |
|---|---|
| `09` | payload 길이 9 |
| `05` | rowid 5 |
| `04` | 레코드 머리말 길이 4 |
| `00` | id 열: NULL. rowid 별칭인 열은 본문에 NULL 로 적히고 실제 값은 rowid 에 있습니다. |
| `15` | url 열: 텍스트. 0x15 = 21 이므로 (21 − 13) ÷ 2 = 4바이트입니다. |
| `01` | cnt 열: 1바이트 정수 |
| `61 2E 6B 72` | "a.kr" |
| `03` | 3 |

이 행을 지우고 셀이 셀 내용 영역 중간에 있었다면, 앞 4바이트가 프리블록 머리말로 바뀝니다.

```
지운 뒤:   00 00 00 0B 15 01 61 2E 6B 72 03
           다음 없음 | 크기 11 | 이하 그대로
```

- 남은 것: url 과 cnt 의 serial type(`15 01`), 값 "a.kr" 과 3 입니다.
- 잃은 것: payload 길이, rowid, 머리말 길이, 첫 serial type 입니다.
- 스키마로 열이 셋이고 첫 열이 rowid 별칭임을 알면 남은 바이트를 풀 수 있습니다.
- id 값 5 는 되살릴 수 없습니다. 이 값이 다른 표와 잇는 열쇠였다면 이 레코드를 어느 행과 이어야 할지 알 수 없습니다.

덮이는 4바이트에 무엇이 드는지는 varint 길이에 따라 다릅니다. varint 는 128 미만이면 1바이트이고, rowid 가 300 이면 `82 2C` 두 바이트입니다. payload 길이가 1바이트라면 덮이는 것은 payload 길이·rowid·머리말 길이까지이고, 이 경우 serial type 은 모두 남습니다.

## 포렌식에서 중요한 점

### 설정에 따라 남는 것

| 설정 | 프리블록·비할당 영역 | 프리리스트 페이지 | 근거 |
|---|---|---|---|
| secure_delete=0 (SQLite 기본값), auto_vacuum=NONE | 남습니다 (프리블록은 앞 4바이트 제외). | 남습니다. | [1][3] |
| secure_delete=FAST (2017년 무렵 추가) | 0 으로 채웁니다. | 남습니다. | [2] |
| secure_delete=1 | 0 으로 채웁니다. | 페이지 전체를 0 으로 채웁니다. | [2][3] |
| auto_vacuum=FULL | 보안 삭제 설정을 따릅니다. | 커밋할 때마다 파일 끝으로 옮겨 잘라 냅니다. | [2] |
| auto_vacuum=INCREMENTAL | 보안 삭제 설정을 따릅니다. | `incremental_vacuum` 을 실행하기 전까지 남습니다. | [2] |
| `VACUUM` 실행 뒤 | 파일을 새로 짜므로 남지 않습니다. | 남지 않습니다. | [2] |

- 자동 정리는 프리리스트 페이지만 잘라 내고 페이지 안은 다시 채우지 않으므로[2], auto_vacuum=FULL 인 DB 도 사용 중인 페이지의 프리블록에는 지운 레코드가 남을 수 있습니다.
- 잘려 나간 파일 끝부분은 파일 시스템의 비할당 영역에 남을 수 있습니다. 이 부분은 [레코드 카빙 (Record Carving)](../../../03-techniques/analysis/data-recovery/record-carving.md) 으로 찾습니다.
- 전문 검색 (FTS3·FTS5) 가상 표의 섀도 표에는 secure_delete 를 켜도 흔적이 남을 수 있습니다[2].
- 지운 행뿐 아니라 고친 행도 흔적을 남깁니다. 흔적을 없애려면 지우거나 고치기 전에 secure_delete 를 켜거나, 그 뒤에 `VACUUM` 을 실행합니다[2].

### 증명하는 것과 증명하지 못하는 것

- **증명하는 것:** 이 파일 안에 현재 표에 없는 레코드 바이트가 있다는 사실입니다. 레코드 모양이 스키마와 맞으면 그 값이 한때 이 DB 에 쓰였다는 사실입니다.
- **증명하지 못하는 것:** 누가, 언제 지웠는지입니다. 사용자가 직접 지웠는지도 알 수 없고, 앱이 오래된 기록을 스스로 정리해도 똑같은 흔적이 남습니다.
- **증명하지 못하는 것:** 빈 공간에 아무것도 없다고 해서 지운 일이 없었다는 뜻은 아닙니다. 보안 삭제, `VACUUM`, 재사용 가운데 어느 것이든 흔적을 없앱니다.

보고서 문장 예: "분석 대상 DB 파일의 프리블록에서 urls 표 형식과 맞는 레코드 조각 3건을 찾았다. 이 가운데 2건은 현재 urls 표에 같은 값이 없다. 조각에 rowid 가 남아 있지 않아 다른 표의 행과 이을 수 없었다."

## 함정

- **지운 레코드가 곧 지운 행은 아닙니다.** 행을 고쳐 셀 크기가 바뀌면 옛 셀이 프리블록이 됩니다. 크기가 같으면 SQLite 는 제자리에 덮어써서 옛 값이 본 파일에 남지 않습니다. 페이지가 합쳐지며 빈 페이지가 프리리스트로 가면, 그 안의 셀 일부는 다른 페이지로 옮겨져 아직 살아 있을 수 있습니다. 되살린 레코드는 현재 표와 대조해 겹치는 것을 뺍니다.
- **지운 시각은 없습니다.** 프리블록 사슬은 위치 순서이지 시간 순서가 아닙니다. 레코드 안의 시각 열은 그 행이 쓰일 때의 값입니다. 시각 값 형식은 [시각 값 형식 (FILETIME·Unix·WebKit·DOS·OLE)](../../value-decoding/filetime-unix-webkit-dos-ole.md) 에서 확인합니다.
- **어느 표의 레코드인지 적혀 있지 않습니다.** 프리리스트 페이지에는 원래 표가 적히지 않습니다. serial type 모양이 비슷한 표가 여럿이면 다른 표에 잘못 붙일 수 있습니다. 지운 표의 `CREATE` 문은 `sqlite_schema` 표(루트는 1번 페이지)의 빈 공간에 남아 있을 수 있습니다.
- **반쯤 덮인 레코드가 섞입니다.** 새 셀이 프리블록을 쓸 때는 블록의 뒤쪽부터 차지합니다[3]. 그래서 옛 레코드의 앞부분과 새 레코드가 한 블록 안에 이어져 있을 수 있습니다. 길이 값과 맞지 않는 레코드는 잘라 내고 보고합니다.
- **조각 모음이 흔적을 지웁니다.** 셀을 넣을 연속 공간이 모자라면 SQLite 는 페이지를 조각 모음 (Defragment) 합니다. 이때 비할당 영역을 0 으로 채웁니다(2026년 9월 소스 기준)[3]. 쓰기가 잦은 DB 일수록 페이지 안에 남는 것이 적습니다.
- **복호하거나 내보내면 빈 공간이 사라집니다.** `VACUUM INTO` 나 내보내기로 만든 새 파일에는 지우지 않은 행만 옮겨집니다. 암호화된 DB 에서 지운 레코드를 찾으려면 페이지 단위로 풀어야 합니다. [암호화된 SQLite (SQLCipher)](sqlcipher.md) 를 함께 봅니다.
- **도구마다 결과가 다릅니다.** 복구 도구는 레코드 경계를 추정하므로 같은 파일에서도 건수가 다를 수 있습니다. 중요한 레코드는 헥스로 한 번 더 확인합니다. [도구 결과 교차 검증 (Tool Validation)](../../../03-techniques/reporting/tool-validation.md) 을 참고합니다.

## 도구

- **sqlite3 명령줄 셸:** 사본에서 `PRAGMA freelist_count;` 로 빈 페이지 수를, `PRAGMA auto_vacuum;` 으로 정리 모드를 봅니다.
- **헥스 편집기:** 헤더와 프리블록 사슬을 직접 따라갈 때 씁니다.
- **공개 복구 도구의 예:** bring2lite, FQLite, undark 가 있습니다. 도구마다 보는 범위(프리블록·비할당 영역·프리리스트·WAL)와 출력 방식이 다릅니다. undark 처럼 현재 행과 지운 행을 함께 내보내는 도구는 현재 표와 대조해 나눠야 합니다.
- **검증용 데이터:** Nemetz·Schmitt·Freiling(2018)이 만든 [SQLite Forensic Corpus](https://digitalcorpora.org/corpora/sql/sqlite-forensic-corpus/) 에 지운 레코드가 든 DB 가 있습니다. 도구가 무엇을 되살리고 무엇을 놓치는지 먼저 이 데이터로 확인해 볼 수 있습니다.

같은 문제를 ESE 형식에서 다룬 글은 [파일 안에 남은 지운 레코드 (Deleted Records)](../extensible-storage-engine/deleted-records.md) 입니다. 상위 허브는 [SQLite 데이터베이스 (SQLite)](index.md) 입니다.
