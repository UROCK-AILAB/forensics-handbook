# 파일·페이지 구조 (B-tree·Record Format)

상위 허브: [SQLite 데이터베이스 (SQLite)](index.md)

## 한 줄 요약

SQLite 파일은 크기가 같은 페이지를 차례로 이어 붙인 것이고, 표 하나와 색인 하나는 각각 B-트리 (B-tree) 하나를 이룹니다.
행 하나는 잎 페이지의 셀 (Cell) 하나에 레코드 (Record) 로 들어가므로, 1번 페이지의 스키마 표에서 시작하면 모든 표의 행을 따라갈 수 있습니다.

## 이 형식을 쓰는 아티팩트

암호화하지 않은 SQLite 파일은 모두 이 구조를 따릅니다.
크롬 계열 [방문 기록](../../../02-artifacts/browsers/chrome-edge-whale/history.md), 파이어폭스 [places.sqlite](../../../02-artifacts/browsers/firefox/places-sqlite.md), [윈도 타임라인](../../../02-artifacts/file-folder-usage/activitiescache-db.md), [윈도 알림 기록](../../../02-artifacts/execution/wpndatabase-db.md), Windows 11 [검색 색인](../../../02-artifacts/file-folder-usage/windows-search/windows-edb-windows-db.md) 이 그 예입니다.
파일별 위치와 버전은 [SQLite 허브](index.md) 의 표에 있습니다.
SQLite 파일 형식은 Windows 버전과 상관없고, 달라지는 것은 앱에 들어 있는 SQLite 라이브러리의 판입니다.
암호화된 파일은 먼저 풀어야 이 구조로 읽을 수 있으며, 자세한 내용은 [암호화된 SQLite](sqlcipher.md) 를 봅니다.

## 구조

### 전체 배치

파일은 크기가 같은 페이지 (Page) 로 나뉘며, 페이지 크기는 512~65536바이트 사이의 2의 거듭제곱입니다.
페이지 번호는 1 부터 세고, 페이지 N 의 파일 오프셋은 `(N − 1) × 페이지 크기` 입니다.
1번 페이지 맨 앞 100바이트는 파일 머리 (Database Header) 입니다.
여러 바이트로 된 정수는 모두 **빅 엔디언 (Big-endian)** 이며, 레지스트리·NTFS·ESE 와 반대입니다.

페이지마다 쓰임새가 하나씩 정해져 있습니다.

| 종류 | 알아보는 법 | 설명 |
|---|---|---|
| 표 B-트리 내부 페이지 | 첫 바이트 0x05 | 자식 페이지 번호와 rowid 만 담습니다. |
| 표 B-트리 잎 페이지 | 첫 바이트 0x0D | 행 데이터가 들어갑니다. |
| 색인 B-트리 내부 페이지 | 첫 바이트 0x02 | 자식 페이지 번호와 색인 키를 담습니다. |
| 색인 B-트리 잎 페이지 | 첫 바이트 0x0A | 색인 키가 들어갑니다. |
| 넘침 페이지 (Overflow Page) | 서명 없음 | 셀에 다 못 넣은 레코드 뒷부분이 들어갑니다. |
| 빈 페이지 목록 (Freelist) 의 줄기·잎 페이지 | 서명 없음 | 지금 안 쓰는 페이지입니다. [지운 레코드](freelist-freeblock.md) 에서 다룹니다. |
| 포인터 맵 페이지 (Pointer Map) | 서명 없음 | 자동 정리(auto_vacuum)·증분 정리 모드 파일에만 있습니다. 자식에서 부모 쪽으로 가는 연결 정보를 담습니다. |
| 잠금 바이트 페이지 (Lock-byte Page) | 위치로 정해짐 | 파일 오프셋 1,073,741,824~1,073,742,335 를 포함하는 페이지입니다. 1 GiB 보다 큰 파일에만 있습니다. SQLite 는 이 페이지를 읽지도 쓰지도 않습니다. |

> 그림 자리: 1번 페이지(파일 머리 + 스키마 표 루트) → 표 루트 페이지 → 내부 페이지 → 잎 페이지 → 넘침 페이지로 이어지는 포인터 흐름

### 파일 머리 (Database Header)

| 오프셋 | 크기 | 칸 | 뜻 |
|---|---|---|---|
| 0 (0x00) | 16 | 서명 | ASCII `SQLite format 3` 과 0x00 |
| 16 (0x10) | 2 | 페이지 크기 | 바이트 수. 값 1 은 65536 입니다. |
| 18 (0x12) | 1 | 쓰기 형식 버전 | 1 = 롤백 저널 모드, 2 = WAL 모드 |
| 19 (0x13) | 1 | 읽기 형식 버전 | 1 = 롤백 저널 모드, 2 = WAL 모드 |
| 20 (0x14) | 1 | 예약 바이트 수 | 페이지마다 끝에 비워 두는 바이트 수. 보통 0 입니다. |
| 21~23 (0x15~0x17) | 1씩 | 페이로드 비율 | 반드시 64·32·32 입니다. |
| 24 (0x18) | 4 | 파일 변경 카운터 | 파일을 고친 뒤 잠금을 풀 때마다 1 늘어납니다. |
| 28 (0x1C) | 4 | 페이지 수 | 머리에 적힌 DB 크기입니다. |
| 32 (0x20) | 4 | 첫 빈 목록 줄기 페이지 번호 | 없으면 0 |
| 36 (0x24) | 4 | 빈 목록 페이지 총수 | |
| 40 (0x28) | 4 | 스키마 쿠키 (Schema Cookie) | 스키마가 바뀔 때마다 늘어납니다. |
| 44 (0x2C) | 4 | 스키마 형식 번호 | 1~4. 새 파일은 4 입니다. |
| 48 (0x30) | 4 | 기본 페이지 캐시 크기 | |
| 52 (0x34) | 4 | 가장 큰 루트 페이지 번호 | 자동 정리·증분 정리 모드일 때만 0 이 아닙니다. |
| 56 (0x38) | 4 | 글자 인코딩 | 1 = UTF-8, 2 = UTF-16LE, 3 = UTF-16BE |
| 60 (0x3C) | 4 | 사용자 버전 (user_version) | SQLite 는 쓰지 않습니다. 앱이 원하는 대로 씁니다. |
| 64 (0x40) | 4 | 증분 정리 모드 | 0 이 아니면 증분 정리 모드입니다. |
| 68 (0x44) | 4 | 응용 ID (Application ID) | 앱이 파일 종류를 표시하려고 정하는 값 |
| 72 (0x48) | 20 | 예약 | 0 |
| 92 (0x5C) | 4 | 유효 판 번호 (Version-valid-for) | 96 의 버전 번호를 적을 때의 변경 카운터 값 |
| 96 (0x60) | 4 | 라이브러리 버전 번호 | 이 파일을 마지막으로 고친 SQLite 라이브러리의 `SQLITE_VERSION_NUMBER` |

페이지 크기에서 예약 바이트 수를 뺀 값을 **쓸 수 있는 크기 (Usable Size, U)** 라고 합니다.
U 는 480 보다 작을 수 없습니다.
예약 영역은 암호화 확장 같은 확장 기능이 페이지마다 정보를 두는 곳입니다.

28 의 페이지 수는 다음 두 조건을 모두 채울 때만 믿습니다.

- 값이 0 이 아닙니다.
- 24 의 변경 카운터와 92 의 유효 판 번호가 같습니다.

SQLite 3.7.0 보다 오래된 라이브러리는 이 칸도 92 도 고치지 않습니다.
그래서 두 값이 다르면 페이지 수를 버리고 실제 파일 크기로 계산합니다.

### B-트리 페이지

B-트리 페이지 하나는 아래 순서로 나뉩니다.

1. 파일 머리 100바이트 (1번 페이지에만 있음)
2. 페이지 머리 8바이트(잎) 또는 12바이트(내부)
3. 셀 포인터 배열 (Cell Pointer Array)
4. 비할당 공간 (Unallocated Space)
5. 셀 내용 영역 (Cell Content Area)
6. 예약 영역 (Reserved Region)

| 오프셋 | 크기 | 칸 | 뜻 |
|---|---|---|---|
| 0 | 1 | 페이지 종류 | 0x02·0x05·0x0A·0x0D. 다른 값은 오류입니다. |
| 1 | 2 | 첫 빈 블록 위치 | 빈 블록이 없으면 0 |
| 3 | 2 | 셀 수 | |
| 5 | 2 | 셀 내용 영역 시작 | 0 이면 65536 입니다. |
| 7 | 1 | 조각 바이트 수 | 셀 내용 영역 안 1~3바이트짜리 빈틈의 합 |
| 8 | 4 | 오른쪽 끝 포인터 | 내부 페이지에만 있습니다. |

셀 포인터 배열은 페이지 머리 바로 뒤에 오며, 셀 하나마다 2바이트 오프셋이 하나씩 있고 키가 작은 셀부터 큰 셀 순서로 놓입니다.
셀 자체는 페이지 끝 쪽부터 채워 나가므로 셀의 실제 위치 순서는 키 순서와 다를 수 있습니다.

셀 내용 영역 안의 빈 곳은 빈 블록 (Freeblock) 사슬로 이어집니다.
빈 블록 구조와 그 안에 남는 지운 레코드는 [파일 안에 남은 지운 레코드](freelist-freeblock.md) 에서 다룹니다.

### 셀 (Cell)

셀에 담긴 레코드 바이트를 페이로드 (Payload) 라고 합니다.
페이지 종류마다 셀에 들어가는 칸이 다릅니다.

| 칸 | 표 잎 (0x0D) | 표 내부 (0x05) | 색인 잎 (0x0A) | 색인 내부 (0x02) |
|---|---|---|---|---|
| 왼쪽 자식 페이지 번호 (4바이트) | | ✔ | | ✔ |
| 페이로드 크기 (varint) | ✔ | | ✔ | ✔ |
| rowid (varint) | ✔ | ✔ | | |
| 페이로드 (레코드) | ✔ | | ✔ | ✔ |
| 첫 넘침 페이지 번호 (4바이트, 넘칠 때만) | ✔ | | ✔ | ✔ |

표 B-트리의 키는 64비트 부호 있는 정수 rowid 이고, 행 데이터는 잎 페이지에만 둡니다.
내부 페이지의 셀은 `왼쪽 자식 페이지 번호 + 키` 로 되어 있으며, 왼쪽 자식 쪽 페이지의 키는 모두 그 셀의 키보다 작거나 같습니다.
가장 큰 키보다 큰 쪽은 페이지 머리의 오른쪽 끝 포인터가 가리킵니다.

색인 B-트리의 키는 `색인한 열 값 + 표의 rowid` 로 된 레코드이고, 따로 데이터는 없습니다.
`WITHOUT ROWID` 로 만든 표는 색인 B-트리에 저장되는데, 이때 키는 기본 키 열이 앞에 오고 나머지 열이 뒤따르는 레코드입니다.

### 가변 길이 정수 (Varint)

셀과 레코드 머리의 숫자는 대부분 가변 길이 정수입니다.

- 길이는 1~9바이트입니다.
- 최상위 비트가 1 인 바이트는 뒤에 바이트가 더 있다는 뜻입니다.
- 각 바이트의 아래 7비트를 앞에서부터 이어 붙입니다.
- 9번째 바이트는 8비트를 모두 씁니다.

예를 들어 `81 0D` 는 `(0x01 × 128) + 0x0D = 141` 입니다.
`81 9C 24` 는 `(0x01 × 16384) + (0x1C × 128) + 0x24 = 20004` 입니다.

### 레코드 형식 (Record Format)

레코드는 머리와 본문으로 되어 있습니다.
머리 첫 varint 는 머리 전체의 바이트 수입니다. 이 varint 자신도 포함합니다.
그 뒤에 열마다 형식 번호 (Serial Type) varint 가 하나씩 옵니다.
본문에는 열 값이 같은 순서로 붙어 있습니다.
레코드에는 열 이름이 없습니다. 이름은 스키마 표의 `CREATE` 문에서 얻습니다.

| 형식 번호 | 값 크기 | 뜻 |
|---|---|---|
| 0 | 0 | NULL |
| 1 / 2 / 3 / 4 | 1 / 2 / 3 / 4 | 부호 있는 정수 (빅 엔디언) |
| 5 / 6 | 6 / 8 | 부호 있는 정수 (빅 엔디언) |
| 7 | 8 | IEEE 754 64비트 실수 (빅 엔디언) |
| 8 / 9 | 0 | 정수 0 / 정수 1. 스키마 형식 4 부터 씁니다. |
| 10 / 11 | — | SQLite 내부용. 정상 파일에는 나오지 않습니다. |
| 12 이상 짝수 N | (N − 12) / 2 | BLOB |
| 13 이상 홀수 N | (N − 13) / 2 | 텍스트. 파일 머리 56 의 인코딩을 따릅니다. 끝의 0x00 은 적지 않습니다. |

텍스트 길이는 글자 수가 아니라 바이트 수입니다.
UTF-16 파일에서는 한 글자가 2바이트 이상입니다([문자 인코딩](../../value-decoding/utf-16le-utf-8-cp949.md)).

형식은 열이 아니라 값마다 정해집니다.
SQLite 는 `INTEGER PRIMARY KEY` 열을 빼면 어느 열에나 어떤 형식의 값이든 넣을 수 있습니다.
그래서 같은 열에 정수와 텍스트가 섞여 있을 수 있습니다.
`STRICT` 로 만든 표는 예외로 선언한 형식을 지킵니다.

`INTEGER PRIMARY KEY` 열은 rowid 의 다른 이름입니다.
이 열은 레코드에 NULL(형식 번호 0)로 적힙니다.
실제 값은 셀의 rowid 칸에 있습니다.

`ALTER TABLE ... ADD COLUMN` 으로 열을 늘리면 기존 레코드는 그대로 둡니다.
그래서 레코드의 열 수가 스키마보다 적을 수 있습니다.
빠진 뒤쪽 열은 스키마의 기본값으로 채워 읽습니다.

### 넘침 페이지 (Overflow Page)

페이로드가 크면 앞부분만 셀에 두고 나머지는 넘침 페이지로 보냅니다.
넘침 페이지 첫 4바이트는 다음 넘침 페이지 번호입니다. 마지막 페이지는 0 입니다.
5번째 바이트부터 쓸 수 있는 크기 끝까지가 내용입니다. 그래서 한 페이지에 `U − 4` 바이트가 들어갑니다.

셀에 얼마를 두는지는 아래 식으로 정합니다. P 는 페이로드 크기입니다.

| 기호 | 표 잎 셀 | 색인 셀 |
|---|---|---|
| X (셀에 다 둘 수 있는 최대) | U − 35 | ((U − 12) × 64 / 255) − 23 |
| M (셀에 최소로 두는 양) | ((U − 12) × 32 / 255) − 23 | 같음 |
| K | M + ((P − M) mod (U − 4)) | 같음 |

- P ≤ X 이면 페이로드 전체가 셀에 있습니다.
- P > X 이고 K ≤ X 이면 앞 K 바이트가 셀에 있습니다.
- P > X 이고 K > X 이면 앞 M 바이트가 셀에 있습니다.
- 나눗셈은 모두 정수 나눗셈입니다.

U 가 4096 이면 표 잎 셀의 X 는 4061, M 은 489 입니다. 색인 셀의 X 는 1002 입니다.

### 스키마 표 (sqlite_schema)

1번 페이지는 스키마 표의 루트 페이지입니다.
스키마 표에는 표·색인·뷰·트리거마다 행이 하나씩 있습니다.
열은 다섯 개입니다.

| 열 | 뜻 |
|---|---|
| type | `table`·`index`·`view`·`trigger` |
| name | 객체 이름 |
| tbl_name | 색인·트리거가 딸린 표 이름 |
| rootpage | 표·색인의 루트 페이지 번호. 뷰·트리거·가상 표는 0 또는 NULL 입니다. |
| sql | 객체를 만든 SQL 문 |

`sqlite_schema` 라는 이름은 파일 안에 적혀 있지 않습니다.
옛 문서와 도구는 같은 표를 `sqlite_master` 라고 부릅니다.
이름이 `sqlite_` 로 시작하는 객체는 SQLite 내부 객체입니다.
`AUTOINCREMENT` 를 쓰는 표가 있으면 `sqlite_sequence` 표가 생깁니다.

### 버전별 차이

파일 형식은 Windows 버전이 아니라 SQLite 판과 설정에 따라 다릅니다.

| 항목 | 차이 |
|---|---|
| 스키마 형식 1 | SQLite 3.0.0 부터 모든 판이 읽습니다. |
| 스키마 형식 2 | 같은 표의 행마다 열 수가 다를 수 있습니다(`ADD COLUMN`). 3.1.3 부터. |
| 스키마 형식 3 | 늘린 열에 NULL 이 아닌 기본값을 줄 수 있습니다. 3.1.4 부터. |
| 스키마 형식 4 | 색인의 `DESC` 를 따르고 형식 번호 8·9 를 씁니다. 3.3.0 부터. 새 파일의 기본값입니다. |
| 파일 머리 28 의 페이지 수 | 3.7.0 이후 판만 고친 파일에서 늘 믿을 수 있습니다. |
| 파일 머리 18·19 = 2 | WAL 모드입니다. [WAL과 롤백 저널](wal-journal-shm.md) 을 함께 봅니다. |

## 읽는 법 — 헥스로 한 번 따라가기

아래 헥스는 **명세의 칸 배치대로 만든 작은 예시 파일**입니다.
실제 검체에서 나온 값이 아닙니다.
예시 파일은 페이지 크기 4096 에 표 하나, 행 하나만 있습니다.

```sql
CREATE TABLE t(id INTEGER PRIMARY KEY, url TEXT, visits INTEGER);
INSERT INTO t VALUES(5, 'a.kr', 3);
```

**1단계. 파일 머리 확인**

```
오프셋    00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F
00000000  53 51 4C 69 74 65 20 66 6F 72 6D 61 74 20 33 00   SQLite format 3.
00000010  10 00 01 01 00 40 20 20 00 00 00 02 00 00 00 02
00000020  00 00 00 00 00 00 00 00 00 00 00 01 00 00 00 04
00000030  00 00 00 00 00 00 00 00 00 00 00 01 00 00 00 00
00000040  00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
00000050  00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 02
00000060  00 2E 86 29 0D 00 00 00 01 0F AF 00 0F AF 00 00
```

- 0x10 의 `10 00` 은 빅 엔디언 0x1000, 곧 페이지 크기 4096 입니다.
- 0x12·0x13 이 둘 다 1 입니다. 롤백 저널 모드 파일입니다.
- 0x14 가 0 이므로 예약 영역이 없습니다. 쓸 수 있는 크기 U 는 4096 입니다.
- 0x18 의 변경 카운터와 0x5C 의 유효 판 번호가 둘 다 2 입니다. 그래서 0x1C 의 페이지 수 2 를 믿을 수 있습니다.
- 페이지 수 2 × 4096 = 8192 입니다. 실제 파일 크기와 맞는지 확인합니다.
- 0x20·0x24 가 0 입니다. 빈 목록 페이지가 없습니다.
- 0x2C 는 스키마 형식 4, 0x38 은 UTF-8 입니다.
- 0x60 의 0x002E8629 는 3049001 입니다. 이 값은 `주 × 1000000 + 부 × 1000 + 패치` 로 읽습니다. 이 파일을 마지막으로 고친 라이브러리는 3.49.1 입니다.

**2단계. 1번 페이지의 페이지 머리**

1번 페이지의 페이지 머리는 파일 머리 뒤 0x64 에서 시작합니다.

- 0x64 의 `0D` 는 표 잎 페이지입니다. 잎이므로 머리는 8바이트입니다.
- 0x65 의 `00 00` 은 빈 블록이 없다는 뜻입니다.
- 0x67 의 `00 01` 은 셀이 1개라는 뜻입니다.
- 0x69 의 `0F AF` 는 셀 내용 영역이 0x0FAF 에서 시작한다는 뜻입니다.
- 0x6C 의 `0F AF` 가 셀 포인터 배열의 첫 값입니다.
- 셀 포인터는 페이지 시작이 기준입니다. 1번 페이지는 파일 0 에서 시작하므로 셀은 파일 0x0FAF 에 있습니다.

**3단계. 스키마 표 셀 읽기**

```
00000FA0  00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 4F
00000FB0  01 07 17 0F 0F 01 81 0D 74 61 62 6C 65 74 74 02   ........tablett.
00000FC0  43 52 45 41 54 45 20 54 41 42 4C 45 20 74 28 69   CREATE TABLE t(i
00000FD0  64 20 49 4E 54 45 47 45 52 20 50 52 49 4D 41 52   d INTEGER PRIMAR
00000FE0  59 20 4B 45 59 2C 20 75 72 6C 20 54 45 58 54 2C   Y KEY, url TEXT,
00000FF0  20 76 69 73 69 74 73 20 49 4E 54 45 47 45 52 29    visits INTEGER)
```

- 0xFAF 의 `4F` 는 페이로드 크기 79 입니다.
- 0xFB0 의 `01` 은 rowid 1 입니다.
- 0xFB1 의 `07` 은 레코드 머리가 7바이트라는 뜻입니다. 머리는 0xFB1~0xFB7 입니다.
- 형식 번호는 `17`(23 → 텍스트 5바이트), `0F`(텍스트 1바이트), `0F`(텍스트 1바이트), `01`(1바이트 정수), `81 0D`(141 → 텍스트 64바이트) 입니다.
- 본문은 `table`, `t`, `t`, `02`, `CREATE TABLE ...` 순서입니다.
- 머리 7 + 본문 5 + 1 + 1 + 1 + 64 = 79 입니다. 페이로드 크기와 맞습니다.
- 이 행에서 표 `t` 의 루트 페이지가 2번이라는 것을 알 수 있습니다.

**4단계. 표 t 의 행 읽기**

2번 페이지는 파일 `(2 − 1) × 4096 = 0x1000` 에서 시작합니다.

```
00001000  0D 00 00 00 01 0F F5 00 0F F5 00 00 00 00 00 00
   ...
00001FF0  00 00 00 00 00 09 05 04 00 15 01 61 2E 6B 72 03   ...........a.kr.
```

- 표 잎 페이지이고 셀이 1개입니다.
- 셀 포인터 0x0FF5 는 페이지 기준입니다. 파일 오프셋은 0x1000 + 0x0FF5 = 0x1FF5 입니다.
- `09` 는 페이로드 크기 9, `05` 는 rowid 5 입니다.
- `04` 는 레코드 머리 크기 4 입니다.
- 형식 번호는 `00`(NULL), `15`(21 → 텍스트 4바이트), `01`(1바이트 정수) 입니다.
- 본문 `61 2E 6B 72` 는 `a.kr`, `03` 은 3 입니다.
- 첫 열 `id` 는 `INTEGER PRIMARY KEY` 라서 NULL 로 적혔습니다. 값은 rowid 5 입니다.
- 읽은 행은 `(5, 'a.kr', 3)` 입니다.

**5단계. 넘침 페이지가 있는 셀**

페이로드가 10,000바이트인 BLOB 한 개를 넣은 예시 파일을 봅니다(U = 4096).
잎 페이지의 셀은 아래 바이트로 시작합니다.

```
CE 10 01 04 81 9C 24 AB AB AB ...
```

- `CE 10` 은 `(0x4E × 128) + 0x10 = 10000` 입니다. 페이로드 크기 P 입니다.
- `01` 은 rowid 1 입니다.
- `04` 는 레코드 머리 크기 4 입니다.
- `81 9C 24` 는 20004 입니다. (20004 − 12) / 2 = 9996바이트짜리 BLOB 입니다. 머리 4 + 본문 9996 = 10000 입니다.
- X = 4061 이므로 P 가 X 보다 큽니다.
- K = 489 + ((10000 − 489) mod 4092) = 489 + 1327 = 1816 입니다. K ≤ X 입니다.
- 그래서 페이로드 앞 1,816바이트가 셀에 있습니다. 바로 뒤 4바이트가 첫 넘침 페이지 번호입니다.
- 나머지 8,184바이트는 넘침 페이지 두 장(4,092 × 2)에 들어갑니다.
- 두 번째 넘침 페이지의 첫 4바이트는 0 입니다.

## 포렌식에서 중요한 점

### 구조 안에는 시각이 없습니다

파일 머리·페이지 머리·셀·레코드 어디에도 시각 칸이 없고, 파일 변경 카운터는 횟수일 뿐 시각이 아닙니다.
화면에 보이는 시각은 모두 앱이 열 값으로 적은 것입니다.
SQLite 에는 날짜 전용 저장 형식이 없으므로 열마다 기준 시점과 단위를 앱 기준으로 따로 확인합니다([시각 값 형식](../../value-decoding/filetime-unix-webkit-dos-ole.md)).
파일 자체가 언제 바뀌었는지는 파일 시스템 시각으로 봅니다.

### 지운 행을 읽을 때 구조에서 알아 둘 점

SQL 로 조회하면 지금 살아 있는 행만 나오며, 지운 행이 남는 자리와 설정별 차이는 [파일 안에 남은 지운 레코드](freelist-freeblock.md) 에서 다룹니다.
여기서는 이 페이지의 구조와 이어지는 점만 적습니다.

- 지운 셀이 빈 블록이 되면 첫 4바이트가 빈 블록 머리로 덮입니다. 표 잎 셀의 첫 부분은 페이로드 크기·rowid·레코드 머리 크기입니다. 그래서 남은 형식 번호 배열을 스키마의 열 구성과 맞춰 어느 표의 행인지 좁힙니다.
- 색인 B-트리는 색인한 열 값과 rowid 를 한 벌 더 담습니다. 표 쪽 잔여 데이터가 덮였으면 색인 페이지의 빈 공간도 함께 봅니다.
- 파일 머리 32·36 은 빈 목록 페이지가 얼마나 있는지 알려 줍니다. 52·64 는 자동 정리·증분 정리 모드인지 알려 줍니다. 복구할 거리가 있는지 가늠하는 첫 단서입니다.

### 최신 내용이 본 파일에 없을 수 있습니다

파일 머리 18·19 가 2 이면 WAL 모드이고, 이 모드에서는 커밋한 페이지가 `-wal` 파일에만 있을 수 있으며 변경 카운터가 트랜잭션마다 늘지 않을 수도 있습니다.
수집과 해석은 [WAL과 롤백 저널](wal-journal-shm.md) 을 봅니다.

### rowid 로 보는 삭제 흔적

`AUTOINCREMENT` 가 없으면 새 행의 rowid 는 그때 가장 큰 rowid 에 1 을 더한 값이라서 지운 행의 rowid 를 다시 쓸 수 있습니다.
`AUTOINCREMENT` 가 있으면 한 번 쓴 rowid 를 다시 쓰지 않으며, 지금까지 가장 컸던 rowid 는 `sqlite_sequence` 표의 `seq` 열에 있습니다.

- **알려 주는 것**: `seq` 가 지금 가장 큰 rowid 보다 크면 그보다 큰 rowid 의 행이 한때 있었습니다.
- **알려 주는 것**: `AUTOINCREMENT` 표에서 rowid 사이 빈 번호는 그 번호의 행이 한때 있었을 수 있다는 단서입니다.
- **알려 주지 않는 것**: 누가 지웠는지 알려 주지 않습니다. 앱이 오래된 기록을 스스로 정리했을 수 있습니다.
- **알려 주지 않는 것**: 앱이 rowid 를 직접 정해 넣을 수 있습니다. 위 예시의 rowid 5 가 그런 경우입니다. 그래서 빈 번호가 꼭 삭제를 뜻하지는 않습니다.

### 잘리거나 손상된 파일

- 페이지 수를 믿을 수 있는데 파일이 `페이지 수 × 페이지 크기` 보다 짧으면 뒤쪽이 빠진 사본일 수 있습니다.
- 페이지 종류 바이트가 네 값 가운데 하나가 아니면 B-트리 페이지가 아닙니다. 넘침·빈 목록·포인터 맵 페이지이거나 손상된 페이지입니다.
- 스키마 표 페이지가 망가지면 어느 페이지가 어느 표인지 알 수 없습니다. 이때는 레코드의 형식 번호 배열을 알려진 스키마와 맞춰 봅니다.
- 페이지 머리와 레코드 머리의 규칙은 디스크 비할당 영역에서 조각을 찾는 데에도 씁니다([레코드 카빙](../../../03-techniques/analysis/data-recovery/record-carving.md)).

## 함정

- **리틀 엔디언으로 읽음.** SQLite 의 여러 바이트 정수는 빅 엔디언입니다. 레지스트리·NTFS·ESE 는 리틀 엔디언이라 헷갈리기 쉽습니다.
- **1번 페이지 오프셋 기준을 헷갈림.** 1번 페이지의 페이지 머리는 100 에서 시작합니다. 하지만 셀 포인터와 빈 블록 위치는 페이지 시작(파일 0)이 기준입니다.
- **값 0 과 1 을 그대로 씀.** 셀 내용 영역 시작 0 은 65536 입니다. 페이지 크기 1 은 65536 입니다.
- **U 대신 페이지 크기로 계산함.** 예약 바이트가 있으면 넘침 계산과 페이지 끝 위치가 달라집니다.
- **`INTEGER PRIMARY KEY` 열을 NULL 로 봄.** 값은 셀의 rowid 에 있습니다. 레코드만 떼어 읽으면 이 값을 잃습니다.
- **열 수가 스키마와 같다고 가정함.** `ADD COLUMN` 전에 쓴 레코드는 열이 적습니다.
- **열 형식을 선언대로 가정함.** 같은 열에 다른 형식 값이 섞일 수 있습니다. 형식 번호를 값마다 봅니다.
- **넘침 사슬을 따라가지 않음.** 긴 URL·JSON·BLOB 은 앞부분만 잎 페이지에 있습니다. 잎 페이지만 카빙하면 값이 잘립니다. 넘침 페이지가 다른 용도로 다시 쓰였으면 사슬이 끊겨 있습니다.
- **잠금 바이트 페이지를 손상으로 봄.** 1 GiB 보다 큰 파일에서 이 페이지가 비어 있는 것은 정상입니다.
- **서명이 없다고 SQLite 가 아니라고 판단함.** 파일 전체를 암호화하면 첫 16바이트도 바뀝니다([암호화된 SQLite](sqlcipher.md)).
- **원본을 SQLite 라이브러리로 바로 엶.** 라이브러리가 저널을 되돌리거나 WAL 을 본 파일에 반영하면서 파일이 바뀔 수 있습니다. 해시를 남긴 사본에서 작업합니다.

## 도구

SQLite 공식 명령줄 셸(`sqlite3`)과 `sqlite3_analyzer` 로 파일 머리 값과 페이지 쓰임새를 볼 수 있지만, DB Browser for SQLite 같은 조회 도구는 살아 있는 행만 보여 줍니다.
잔여 레코드를 찾는 공개 도구로는 sqlparse(SQLite Deleted Records Parser), undark, bring2lite 등이 있습니다.
Kaitai Struct 의 sqlite3 형식 정의나 헥스 편집기 템플릿을 쓰면 칸 단위로 헥스를 볼 수 있습니다.
도구마다 넘침 사슬·UTF-16·지운 레코드를 다루는 방식이 다릅니다.
Nemetz·Schmitt·Freiling 이 공개한 SQLite Forensic Corpus 는 이런 특이 사례를 일부러 넣은 검사용 파일 모음입니다.
도구 결과를 맞춰 보는 방법은 [도구 결과 교차 검증](../../../03-techniques/reporting/tool-validation.md) 을 봅니다.
