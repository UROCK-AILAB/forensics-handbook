# 트랜잭션 로그와 반영 안 된 변경 (.LOG1·.LOG2)

> 위치: [레지스트리 하이브 구조 (Registry Hive)](index.md) > 트랜잭션 로그

윈도는 하이브를 고치기 전에 바뀐 내용을 먼저 옆의 .LOG1·.LOG2 파일에 적는데, Windows 8.1 부터는 로그에 적은 내용이 하이브 파일에 옮겨지기까지 한 시간쯤 걸릴 수 있어서 하이브 파일만 읽으면 가장 최근의 변경을 놓칠 수 있습니다.

## 이 형식을 쓰는 아티팩트

트랜잭션 로그 (Transaction Log) 는 하이브의 주 파일 (Primary File) 곁에 붙는 보조 파일로, 하이브의 키와 값 변경을 적습니다.
로그 파일은 주 파일과 같은 폴더에 있고, 이름은 주 파일 이름 뒤에 .LOG1·.LOG2 를 붙인 것입니다.

- `C:\Windows\System32\config\SOFTWARE` → `SOFTWARE.LOG1`, `SOFTWARE.LOG2`
- `C:\Users\<사용자>\NTUSER.DAT` → `NTUSER.DAT.LOG1`, `NTUSER.DAT.LOG2`

SYSTEM·SOFTWARE·SAM·SECURITY·DEFAULT·NTUSER.DAT·UsrClass.dat 가 모두 이 방식을 씁니다.
하이브 형식을 빌려 쓰는 파일도 같습니다. [AmCache (Amcache.hve)](../../../02-artifacts/execution/amcache-hve/index.md) 와 부팅 설정 파일 BCD 가 그 예입니다.
하이브별 위치는 [하이브 파일 종류와 위치](system-software-sam-security-ntuser-dat-usrclass.md) 에 있습니다.

| Windows | 로그 파일 | 로그 형식 | 로그의 File type 값 |
|---|---|---|---|
| NT 3.51·NT 4.0·2000 | .LOG | 옛 형식 | 2 |
| XP·Server 2003 | .LOG 하나 | 옛 형식 (더티 벡터) | 1 |
| Vista·7·8 | .LOG1·.LOG2 | 옛 형식 (더티 벡터) | 1 |
| 8.1·Server 2012 R2·10 | .LOG1·.LOG2 | 새 형식 (로그 항목) | 6 |

- 로그 파일 두 개를 쓰는 방식을 이중 기록 (Dual Logging) 이라고 합니다. Vista 에서 처음 나왔습니다.
- Vista 이후에도 .LOG 파일이 함께 보일 수 있습니다. 설치 이미지에서 따라온, 쓰지 않는 파일일 수 있습니다.
- 공개된 형식 명세는 Windows 10 까지를 다룹니다. Windows 11 도 새 형식을 쓰는 것으로 알려져 있으므로, 실제 데이터에서 로그의 File type 값을 확인합니다.

같은 생각으로 만든 다른 형식으로 [ESE 트랜잭션 로그](../extensible-storage-engine/edb-log-dirty-shutdown.md), [SQLite WAL](../sqlite/wal-journal-shm.md), [NTFS $LogFile](../../../02-artifacts/filesystem/logfile.md) 이 있으며, 세 가지 모두 하이브 로그와는 서로 다른 파일입니다.

## 로그를 먼저 쓰는 이유와 "반영 안 된 변경"

윈도는 바뀐 데이터를 주 파일에 쓰기 전에 로그에 먼저 씁니다.
로그를 쓰다가 전원이 나가도 주 파일은 그대로 멀쩡하고, 주 파일을 쓰다가 전원이 나가면 로그로 주 파일을 되살립니다.

옛 형식에서는 "디스크에 썼다" 는 말이 주 파일까지 썼다는 뜻이지만, 새 형식에서는 로그에만 적어도 디스크에 쓴 것으로 칩니다.
주 파일 기록은 최대 한 시간까지 미뤄질 수 있는데, 이 한 시간에는 절전·최대 절전 시간이 들어가지 않습니다. 그래서 PC 를 띄엄띄엄 쓰면 실제로는 더 오래 미뤄질 수 있습니다.
레지스트리는 일정한 간격으로, 그리고 시스템 종료 때 변경을 디스크에 씁니다. 이것을 지연 기록 (Lazy Flush) 이라고 부릅니다.

로그에만 있고 주 파일에는 아직 들어가지 않은 데이터를 반영 안 된 데이터 (Unreconciled Data) 라고 부르며, 전원을 갑자기 끊거나 켜진 상태에서 하이브를 복사하면 이 데이터는 로그에만 남습니다.

## 구조

### 주 파일이 복구가 필요한지 판별하기

주 파일 머리 블록 (Base Block) 의 전체 구조는 [하이브 내부 구조 (regf·hbin·Cell)](regf-hbin-cell.md) 에 있고, 여기서는 로그와 관련된 필드만 봅니다. 숫자는 모두 리틀 엔디언입니다.

| 오프셋 | 크기 | 필드 | 쓰임 |
|---|---|---|---|
| 4 | 4 | 첫째 순번 (Primary sequence number) | 주 파일 쓰기를 시작할 때 1 올립니다 |
| 8 | 4 | 둘째 순번 (Secondary sequence number) | 주 파일 쓰기를 마칠 때 1 올립니다 |
| 28 | 4 | 파일 종류 (File type) | 주 파일은 0, 로그는 1·2·6 입니다 |
| 40 | 4 | 하이브 빈 데이터 크기 (Hive bins data size) | 복구할 때 주 파일 크기를 정합니다 |
| 508 | 4 | 검사합 (Checksum) | 앞 508바이트의 XOR-32 값입니다 |

- 두 순번이 다르면 복구가 필요한 하이브입니다. 도구는 이것을 더티 하이브 (Dirty Hive) 라고 표시합니다.
- 검사합이 틀려도 더티 하이브입니다.
- 주 파일이 깨끗하면 새 형식 로그 안에 뒤 순번 항목이 있어도 커널은 적용하지 않습니다.

### 로그 파일의 첫 512바이트

로그 파일의 첫 섹터에는 주 파일 머리 블록의 앞부분 사본이 들어가며, Windows 8 부터 이 사본은 늘 512바이트입니다.
사본에서는 파일 종류 필드가 1·2·6 가운데 하나로 바뀌고 검사합도 바뀐 내용으로 다시 계산합니다.
로그 사본의 두 순번이 서로 같아야 유효한 로그 파일입니다.

### 옛 형식 (Windows 8 까지)

| 로그 파일 위치 | 내용 |
|---|---|
| 0 | 머리 블록 사본 |
| 512 | 서명 `DIRT` (4바이트) 와 비트맵 |
| 비트맵이 끝난 다음 섹터 | 바뀐 페이지 (Dirty Page) 들. 512바이트씩 빈틈없이 놓입니다 |

- 이 서명과 비트맵을 합쳐 더티 벡터 (Dirty Vector) 라고 부릅니다.
- 비트 하나는 하이브 빈 데이터의 512바이트 페이지 하나를 뜻합니다.
- 비트가 1 이면 그 페이지가 바뀐 것입니다.
- 비트맵 길이(비트 수)는 하이브 빈 데이터 크기 ÷ 512 입니다.
- 한 바이트 안에서는 가장 낮은 비트부터 셉니다.
- 0부터 센 n 번째 비트가 1 이면, 그 페이지는 주 파일 오프셋 4096 + 512 × n 에 들어갑니다.
- 바뀐 페이지는 1 인 비트 순서대로 놓입니다.
- 윈도는 4096바이트 단위로 바뀜을 추적합니다. 그래서 비트맵 바이트는 보통 0x00 이나 0xFF 입니다.
- 마지막 페이지 뒤에 예전 페이지의 잔재가 남아 있을 수 있습니다.

### 새 형식 (Windows 8.1 부터)

두 번째 섹터(오프셋 512)부터 로그 항목 (Log Entry) 이 이어집니다.
각 항목은 512바이트 경계에서 시작하고 크기도 512의 배수이며, 항목 사이에는 빈틈이 없습니다.

| 오프셋 | 크기 | 필드 | 뜻 |
|---|---|---|---|
| 0 | 4 | 서명 | `HvLE` |
| 4 | 4 | 크기 | 이 항목 전체 바이트 수 |
| 8 | 4 | 플래그 | 머리 블록 플래그의 일부 사본 (0x1 비트만 저장) |
| 12 | 4 | 순번 | 이 항목을 적용한 뒤 머리 블록이 가질 순번 |
| 16 | 4 | 하이브 빈 데이터 크기 | 항목을 만들 때의 값. 4096의 배수여야 합니다 |
| 20 | 4 | 페이지 수 | 이 항목에 붙은 바뀐 페이지 개수 |
| 24 | 8 | 해시-1 | 오프셋 40부터 (크기 − 40) 바이트의 Marvin32 해시 |
| 32 | 8 | 해시-2 | 항목 앞 32바이트의 Marvin32 해시 |
| 40 | 8 × 페이지 수 | 페이지 참조 | 아래 표 |
| 그 뒤 | | 바뀐 페이지 | 참조 순서대로 빈틈없이 |

페이지 참조 하나는 8바이트입니다.

| 오프셋 | 크기 | 뜻 |
|---|---|---|
| 0 | 4 | 페이지 위치. 하이브 빈 데이터 시작 기준입니다 |
| 4 | 4 | 페이지 크기 (바이트) |

- 주 파일 안 위치는 4096 + 페이지 위치 입니다.
- 두 해시의 씨앗값은 `82 EF 4D 88 7A 4E 55 C5` 입니다.
- 항목 머리에는 시각 필드가 없습니다.
- 로그 파일에는 이미 적용된 옛 항목이 함께 남아 있을 수 있습니다.

> 그림 자리: 옛 형식(머리 블록 → DIRT 비트맵 → 페이지)과 새 형식(머리 블록 → HvLE 항목 → HvLE 항목 …)의 파일 배치를 나란히 비교

### .LOG1 과 .LOG2 를 쓰는 순서

| | 옛 형식 | 새 형식 |
|---|---|---|
| 평소 | .LOG1 만 씁니다 | .LOG1 과 .LOG2 를 주기적으로 바꿔 가며 씁니다 |
| .LOG2 를 쓰는 때 | 주 파일 쓰기에 오류가 났을 때 | 늘 번갈아 씁니다 |
| 복구할 때 | 대개 .LOG1 을 씁니다 | 주 파일 머리 블록이 멀쩡하면 두 파일의 항목을 순번대로 이어 씁니다 |
| 머리 블록이 망가졌을 때 | 조건에 맞으면 .LOG2 를 씁니다 | 가장 최근 항목이 든 파일 하나만 씁니다 |

- 새 형식에서는 .LOG1 이 더 옛 항목을 담는다는 보장이 없습니다.
- 옛 형식에서 복구에 .LOG2 를 쓰는 조건은 Windows 8 에서 넓어졌습니다.
- Windows 7 은 2016년 3월 커널 업데이트(KB3140410)로 Windows 8 과 비슷한 방식을 쓰게 되었습니다.

## 읽는 법 — 헥스로 한 번 따라가기

아래 바이트는 **명세로 만든 예시**입니다. 실제 데이터에서 나온 값이 아닙니다. `..` 은 이 설명에 필요 없는 바이트입니다.

**1단계. 주 파일이 더티인지 봅니다.**

```
주 파일 SOFTWARE, 오프셋 0x000 (명세로 만든 예시)
00000000  72 65 67 66 2A 00 00 00  29 00 00 00 .. .. .. ..   regf*...).......
```

- 오프셋 4 의 첫째 순번은 0x2A(42) 입니다.
- 오프셋 8 의 둘째 순번은 0x29(41) 입니다.
- 두 값이 다르므로 더티 하이브입니다.
- 오프셋 508(0x1FC)의 검사합도 다시 계산해 맞춰 봅니다.

**2단계. 로그 파일의 형식을 봅니다.**

```
SOFTWARE.LOG1, 오프셋 0x000 (명세로 만든 예시)
00000000  72 65 67 66 2A 00 00 00  2A 00 00 00 .. .. .. ..   regf*...*.......
00000010  .. .. .. .. 01 00 00 00  .. .. .. .. 06 00 00 00
00000020  01 00 00 00 .. .. .. ..  00 A0 00 00 01 00 00 00
```

- 두 순번이 모두 0x2A(42)로 같습니다. 유효한 로그입니다.
- 오프셋 28(0x1C)의 파일 종류가 6 입니다. 새 형식입니다.
- 오프셋 40(0x28)의 하이브 빈 데이터 크기는 0xA000(40,960바이트) 입니다.

**3단계. 첫 로그 항목을 읽습니다.**

```
SOFTWARE.LOG1, 오프셋 0x200 (명세로 만든 예시, 해시 자리는 ..)
00000200  48 76 4C 45 00 12 00 00  00 00 00 00 2A 00 00 00   HvLE........*...
00000210  00 A0 00 00 01 00 00 00  .. .. .. .. .. .. .. ..
00000220  .. .. .. .. .. .. .. ..  00 30 00 00 00 10 00 00
00000230  (여기부터 4,096바이트 페이지 내용)
```

- 서명은 `HvLE` 입니다.
- 크기는 0x1200(4,608바이트) 입니다. 머리 40 + 참조 8 + 페이지 4,096 = 4,144바이트를 512의 배수로 올린 값입니다.
- 순번은 0x2A(42) 입니다. 로그 머리 블록의 첫째 순번(42)과 같습니다. 주 파일의 둘째 순번(41)보다 작지 않습니다. 그래서 첫 항목으로 받아들입니다.
- 페이지 수는 1 입니다.
- 페이지 참조는 위치 0x3000, 크기 0x1000 입니다.
- 이 페이지는 주 파일 사본의 4096 + 0x3000 = 0x4000 위치에 4,096바이트로 덮어씁니다.
- 덮어쓰기 전에 해시-1·해시-2 를 계산해 맞춰 봅니다. 해시-1 범위는 0x228 부터 0x11D8(4,568)바이트입니다.

**4단계. 다음 항목으로 넘어갑니다.**

- 다음 항목은 0x200 + 0x1200 = 0x1400 에서 시작합니다.
- 다음 항목의 순번은 43 이어야 이어서 적용합니다.
- 순번이 끊기거나, 해시가 틀리거나, 하이브 빈 데이터 크기가 4096의 배수가 아니면 거기서 멈춥니다.
- .LOG1 에서 멈추면 .LOG2 로 넘어갑니다. .LOG2 의 첫 항목은 마지막으로 적용한 순번 + 1 이어야 합니다.
- 항목이 커진 하이브 빈 데이터 크기를 담고 있으면 주 파일 사본도 그만큼 늘립니다.

**5단계. 결과 사본을 읽습니다.**

모든 항목을 적용한 사본은 보통 하이브처럼 읽습니다. 읽는 법은 [하이브 내부 구조](regf-hbin-cell.md) 에 있습니다.

## 포렌식에서 중요한 점

### 최근 변경은 로그에만 있을 수 있습니다

새 형식에서는 주 파일 기록이 한 시간쯤 미뤄질 수 있어서 압수 직전에 생긴 변경이 주 파일에는 없을 수 있으며, 자동실행 키 추가나 실행 기록 갱신이 그런 예입니다.
주 파일만 읽은 결과로 "그 키가 없었다" 고 쓰면 안 됩니다.

### 한 키의 여러 판을 볼 수 있습니다

로그 항목을 하나씩 적용하면 하이브의 중간 상태 (Intermediate State) 를 차례로 볼 수 있으며, 중간 상태는 로그 항목 하나를 적용한 뒤 복구가 끝나기 전의 하이브 모습입니다.
이 방법으로 UserAssist 키 하나의 마지막 기록 시각을 세 개 얻은 예가 있습니다. 주 파일만 보면 그 키의 마지막 기록 시각은 하나뿐입니다.
중간 상태에서 얻은 시각은 [타임라인](../../../03-techniques/analysis/timeline/super-timeline.md) 의 재료가 됩니다.

### 지운 데이터와 옛 잔재

로그 파일에는 이미 적용된 옛 항목이 남을 수 있고, 옛 형식 로그에도 마지막 페이지 뒤에 예전 페이지 잔재가 남을 수 있습니다.
이런 부분에는 주 파일에서 이미 덮어쓴 옛 셀이 들어 있을 수 있습니다.
주 파일 안의 지운 셀을 찾는 법은 [지워진 키·값 복구](deleted-keys-values.md) 에 있습니다.

### 수집 방법에 따라 로그 내용이 달라집니다

- 하이브를 모을 때는 .LOG1·.LOG2(있으면 .LOG 도)를 함께 모읍니다. 로그를 빼면 반영 안 된 변경을 잃습니다.
- 섀도 복사본을 만들 때 커널은 모든 하이브를 잠시 멈추고 로그를 주 파일에 적용합니다. 적용한 로그 파일은 비워질 수 있습니다.
- 그래서 섀도 복사본 속 하이브는 로그를 적용한 "뒤" 상태만 보여 줍니다. 적용 "전" 상태는 사라집니다.
- 켜진 PC 에서 수집 도구가 섀도 복사본을 만들면, 원래 PC 의 로그 내용도 이때 바뀔 수 있습니다.
- `reg save` 같은 내보내기는 형식 옵션에 따라 할당된 키와 값만 옮깁니다. 이 경우 지운 데이터가 사라집니다.

수집 절차는 [선별 수집](../../../03-techniques/process-acquisition/evidence-acquisition/triage-collection.md) 과 [실행 중 시스템 이미징](../../../03-techniques/process-acquisition/live-response/live-imaging.md) 에서 다룹니다.
섀도 복사본 자체는 [볼륨 섀도 복사본 구조](../../disk-volume/volume-shadow-copy.md) 와 [섀도 복사본 활용](../../../03-techniques/analysis/volume-shadow-copy-analysis.md) 을 봅니다.

### 로그에서 나온 값을 증거로 쓸 때

- **알 수 있는 것**: 그 페이지 내용이 하이브의 어느 한 시점에 실제로 기록되었다는 것.
- **알 수 있는 것**: 항목 순번으로 본 기록의 앞뒤 순서.
- **알 수 없는 것**: 항목이 기록된 정확한 시각. 항목 머리에는 시각 필드가 없습니다. 시각은 페이지 안 키의 [마지막 기록 시각](last-write-time.md)(FILETIME, UTC)으로만 추정합니다.
- **알 수 없는 것**: 누가 그 값을 바꿨는지.

보고서에는 "주 파일에는 없고, 트랜잭션 로그의 순번 N 항목을 적용한 상태에 이 값이 있다" 처럼 기록으로 확인되는 만큼만 씁니다.

## 함정

- **주 파일만 파싱합니다.** 가장 최근 변경을 놓칩니다.
- **도구마다 로그 처리가 다릅니다.** 어떤 도구는 로그를 자동으로 적용합니다. 어떤 도구는 로그를 무시하거나 적용 여부를 선택하게 합니다. 어느 쪽으로 읽었는지 기록합니다.
- **.LOG1 이 먼저라고 가정합니다.** 새 형식에서는 .LOG2 에 더 옛 항목이 있을 수 있습니다.
- **복구가 멈춘 뒤를 보지 않습니다.** 순번이 끊기거나 해시가 틀리면 복구는 멈춥니다. 그 뒤 항목은 적용되지 않았을 뿐 파일에는 남아 있습니다.
- **"깨끗한 하이브" 를 로그가 비었다는 뜻으로 읽습니다.** 주 파일이 깨끗해도 로그에는 옛 항목과 잔재가 남을 수 있습니다.
- **원본에 로그를 적용합니다.** 로그를 적용하면 새 하이브가 생깁니다. 원본 주 파일과 로그는 그대로 두고 사본에서 작업합니다. 원본과 결과 파일의 해시를 모두 적습니다.
- **Vista 이후의 .LOG 만 봅니다.** 설치 이미지에서 따라온 쓰지 않는 파일일 수 있습니다.
- **머리 블록 시각을 하이브의 마지막 기록 시각으로 씁니다.** Windows 8.1 부터 머리 블록의 마지막 기록 시각 (Last written timestamp) 필드는 갱신되지 않습니다.
- **다른 로그와 헷갈립니다.** NTFS 의 [$LogFile](../../../02-artifacts/filesystem/logfile.md) 은 파일 시스템 로그입니다. 트랜잭션 레지스트리 (TxR) 는 CLFS 파일에 따로 기록합니다. 둘 다 .LOG1·.LOG2 와 다른 것입니다.

## 도구

아래 공개 도구는 예로만 듭니다. 한 도구의 결과에만 기대지 않습니다.

| 도구 | 로그와 관련된 기능 |
|---|---|
| Registry Explorer·RECmd (Eric Zimmerman) | 더티 하이브에 로그를 적용해 읽습니다. RECmd 는 로그를 무시하는 선택지도 둡니다 |
| RLA (Eric Zimmerman) | 로그를 적용한 새 하이브 파일을 만듭니다. 로그를 모르는 도구에 넘길 때 씁니다 |
| regipy (Python) | 로그를 적용해 복구한 하이브를 만듭니다 |
| yarp (Python, Suhanov) | 로그 항목을 하나씩 적용하며 중간 상태를 살펴볼 수 있습니다 |
| 헥스 편집기 | 서명 `DIRT`·`HvLE` 를 찾아 위의 표대로 직접 읽습니다 |

두 도구의 결과가 다르면 먼저 로그 적용 여부와 멈춘 순번을 비교합니다.
검증 방법은 [도구 결과 교차 검증](../../../03-techniques/reporting/tool-validation.md) 에 있습니다.
