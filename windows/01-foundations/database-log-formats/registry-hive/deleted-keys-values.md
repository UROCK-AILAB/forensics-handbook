# 지워진 키·값 복구 (Deleted Keys·Values)

키나 값을 지워도 셀(Cell) 크기 필드의 부호만 바뀌고, 내용은 새 데이터가 덮을 때까지 하이브 파일에 남습니다.

레지스트리 키나 값을 지우면 Windows 는 그 셀을 "빈 셀"로 표시만 합니다. 이 페이지는 지운 키·값이 어디에 어떤 모양으로 남는지, 어떻게 찾고 검증하는지를 설명합니다.

셀과 하이브 빈(Hive Bin)의 기본 구조는 [하이브 내부 구조 (regf·hbin·Cell)](regf-hbin-cell.md) 에서 설명하고, 이 페이지는 지우기와 관련된 필드만 다룹니다.

## 이 원리가 쓰이는 곳

지운 키·값 복구는 레지스트리에 남는 모든 아티팩트에 쓸 수 있습니다. 특히 "지워졌다는 사실" 자체가 단서가 될 때 자주 씁니다.

| 상황 | 지워진 것 | 함께 볼 페이지 |
|---|---|---|
| 한 번만 실행되도록 등록된 프로그램 | RunOnce 값. Windows 는 기본적으로 명령을 실행하기 **전에** 이 값을 지웁니다[6]. | [로그온 자동실행 (Run·RunOnce·Startup Folder)](../../../02-artifacts/persistence/run-runonce-startup-folder.md) |
| 자동실행을 등록했다가 지운 경우 | Run 값, 서비스 키 | [서비스·드라이버 (Services·Drivers)](../../../02-artifacts/persistence/services-drivers.md) |
| 예약 작업을 목록에서 숨긴 경우 | TaskCache Tree 아래 SD 값 | [숨긴 예약 작업 찾기 (SD 값 삭제)](../../../02-artifacts/persistence/scheduled-tasks/sd.md) |
| 장치 연결 기록을 지운 경우 | USBSTOR 아래 장치 키 | [USB 저장장치 목록 (USBSTOR)](../../../02-artifacts/external-devices/usb-storage-artifacts/usbstor.md) |
| 흔적을 없애려 한 정황 조사 | 여러 키·값 | [증거를 없애려 했나 (Anti-Forensics)](../../../04-scenarios/activity/anti-forensics/index.md) |

## 구조: 지울 때 바뀌는 필드

### 셀과 레코드별 변화

아래 표는 2008년에 Windows 2000·XP·Server 2003·Vista 에서 지우기 동작을 시험한 결과입니다[2]. Windows 10·11 하이브에서는 복구 결과를 헥스로 한 번 더 확인합니다.

| 대상 | 지울 때 바뀌는 것 | 남는 것 |
|---|---|---|
| 셀 | 크기 필드가 음수에서 양수로 바뀝니다. 옆에 빈 셀이 있으면 하나로 합쳐집니다. | 셀 안의 내용은 대체로 그대로입니다. |
| 키 노드 (Key Node, `nk`) | 하위 키 목록 오프셋(키 노드 기준 28)과 보안 항목 오프셋(44)이 `0xFFFFFFFF` 로 덮입니다. 하위 키 수(20)가 0 이 됩니다. | 부모 오프셋(16), 값 수(36), 값 목록 오프셋(40), 이름 |
| 값 목록 (Key Values List) | 값을 하나 지울 때마다 목록을 다시 씁니다. 마지막 값이 빠지면 목록 셀이 해제됩니다. | 목록 뒤쪽 남는 공간은 지우지 않습니다. 부모 키를 지우면 목록이 그대로 남습니다. |
| 하위 키 목록 (Subkeys List) | 항목이 빠질 때마다 뒤 항목을 앞으로 당겨 씁니다. 부모 키를 지우면 하위 키를 차례로 지우면서 목록이 뒤섞입니다. | 목록 끝에 옛 항목이 겹친 채 남습니다. |
| 값 레코드 (Key Value, `vk`)와 값 데이터 | 대체로 바뀌지 않습니다. | 이름, 형식, 크기, 데이터 오프셋, 데이터 |

### Windows 버전별 차이

| 버전 | 차이 | 출처 |
|---|---|---|
| Windows 2000 | 빈 셀 데이터의 첫 4바이트에 빈 셀 목록의 다음 셀 오프셋(없으면 `0xFFFFFFFF`)을 적습니다. 그래서 지운 `vk` 의 서명·이름 길이나 데이터 앞 4바이트가 덮인 경우가 있었습니다. 하위 키가 있던 키를 지워도 그 키의 시각이 바뀌지 않았습니다. | 명세, Morgan |
| Windows XP 이후 | 빈 셀 첫머리에 기록을 적는 것은 Windows 2000(과 NT 3.1)의 동작입니다[1]. `vk` 앞 4바이트가 덮이는 일도 Windows 2000 에서만 나타났습니다[2]. | 명세, Morgan |
| Windows 8·Server 2012 이후 | 하이브 재구성(Reorganization)이 생겼습니다. 아래 "지운 데이터가 사라지는 경우"를 봅니다. | 명세 |
| Windows 10 일부 릴리스 | 키 이름을 바꿀 때 옛 키 노드 셀이 빈 셀로 표시되지 않았습니다. 이 셀은 부모의 하위 키 목록에서만 빠졌습니다. | Suhanov |

### 지운 데이터가 남는 자리

| 자리 | 모양 | 놓치기 쉬운 점 |
|---|---|---|
| 빈 셀 (Unallocated Cell) | 크기 필드가 양수인 셀입니다. 지운 `nk`·`vk`·값 목록·데이터가 들어 있습니다. | 합쳐진 빈 셀에는 레코드가 여러 개 들어 있습니다. 셀 첫머리만 보면 두 번째부터 놓칩니다. |
| 할당된 셀의 남는 공간 (Slack) | 목록이 줄어든 뒤 남은 옛 항목입니다. 목록은 커질 때 여유 있는 큰 셀로 옮겨지기도 합니다. 값 데이터 셀에서 데이터 크기 뒤에 남은 바이트도 여기에 들어갑니다. | 할당된 셀이라서 빈 셀만 살펴보면 안 보입니다. |
| 마지막 하이브 빈 뒤 (Remnant Data) | 기본 파일(Primary File)은 마지막 하이브 빈 뒤에 임의 크기의 남은 데이터를 가질 수 있습니다. 시작 위치는 4096 + 기본 블록(Base Block) 오프셋 40 의 "하이브 빈 데이터 크기" 입니다. | 하이브 빈 안만 보는 도구는 이 부분을 건너뜁니다. |
| 할당됐지만 아무도 가리키지 않는 셀 | 위 Windows 10 이름 바꾸기 버그처럼 트리에서 끊긴 셀입니다. | 빈 셀이 아니라서 대부분의 도구가 찾지 않습니다. |
| 트랜잭션 로그 (.LOG1·.LOG2) | 기본 파일에 아직 들어가지 않은 변경입니다. 지우기 직전 상태가 남아 있을 수 있습니다. | [트랜잭션 로그와 반영 안 된 변경 (.LOG1·.LOG2)](log1-log2.md) |
| 볼륨 섀도 복사본의 옛 하이브 | 지우기 전 시점의 하이브 전체입니다. | [섀도 복사본 활용 (Volume Shadow Copy Analysis)](../../../03-techniques/analysis/volume-shadow-copy-analysis.md) |

> 그림 자리: 합쳐진 빈 셀 하나 안에 옛 `nk`·값 목록·`vk`·데이터가 이어 붙어 있고, `nk` 의 부모 오프셋과 값 목록 오프셋이 각각 다른 셀을 가리키는 모습

## 읽는 법

### 복구 순서

믿을 만한 구조부터, 연결 정보가 많은 구조부터 되살립니다[2]. 순서는 다음과 같습니다.

1. 하이브를 사본으로 떠서 작업합니다. 트랜잭션 로그를 반영하면 페이지 내용이 바뀝니다. 반영 전 사본과 반영 후 사본을 따로 두고 둘 다 검사합니다.
2. 루트 키부터 현재 트리를 따라가며 참조되는 셀을 모두 표시합니다.
3. 하이브 빈마다 셀 크기 필드를 따라 셀을 차례로 넘깁니다. 크기가 양수인 셀을 모읍니다. 마지막 하이브 빈 뒤의 남은 데이터도 모읍니다.
4. 빈 셀 전체를 검색해 `nk` 서명을 찾습니다. 셀 첫머리만 보지 않습니다.
5. 찾은 키 노드를 검증합니다. 이름 길이가 셀 안에 들어가는지 봅니다. 부모 오프셋이 하이브 빈 범위 안의 키 노드를 가리키는지 봅니다.
6. 부모 오프셋을 따라 올라가 경로를 만듭니다. 지워지지 않은 키에 닿으면 그 아래에 붙입니다. 닿지 않으면 "부모를 모르는 키"로 따로 둡니다.
7. 값 수와 값 목록 오프셋으로 값 레코드와 데이터를 찾습니다.
8. 남은 빈 셀에서 `vk` 서명을 찾아 데이터를 따라갑니다. 이 값들은 어느 키의 것인지 모를 수 있습니다.
9. 할당된 셀의 남는 공간(목록 뒤쪽, 값 데이터 뒤쪽)과 아무도 가리키지 않는 할당 셀을 검사합니다.
10. 되살린 항목마다 나온 자리(빈 셀·남는 공간·남은 데이터·로그)를 적어 둡니다.

### 헥스로 한 번 따라가기

아래는 **명세로 만든 예시**입니다. 실제 데이터에서 나온 바이트가 아닙니다. 이름이 `Test` 인 지운 키의 키 노드 셀입니다. 왼쪽 위치는 셀 시작 기준입니다. 명세의 키 노드 오프셋은 여기서 4 를 뺀 값입니다.

```
셀 기준  00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F
0000     58 00 00 00 6E 6B 20 00 00 9C 1C 08 BB 6B DA 01
0010     00 00 00 00 20 10 00 00 00 00 00 00 00 00 00 00
0020     FF FF FF FF FF FF FF FF 01 00 00 00 48 23 00 00
0030     FF FF FF FF FF FF FF FF 00 00 00 00 00 00 00 00
0040     08 00 00 00 3A 00 00 00 00 00 00 00 04 00 00 00
0050     54 65 73 74 00 00 00 00
```

| 셀 기준 | 키 노드 기준 | 바이트 | 뜻 |
|---|---|---|---|
| 0x00 | – | `58 00 00 00` | 셀 크기 +88 입니다. 양수라서 빈 셀입니다. 살아 있을 때는 `A8 FF FF FF`(−88)입니다. |
| 0x04 | 0 | `6E 6B` | 서명 `nk` |
| 0x06 | 2 | `20 00` | 플래그 0x0020. 키 이름이 ASCII 라는 뜻입니다. |
| 0x08 | 4 | `00 9C 1C 08 BB 6B DA 01` | 마지막 기록 시각. FILETIME, UTC 로 2024-03-01 09:30:00 입니다. |
| 0x14 | 16 | `20 10 00 00` | 부모 키 노드 오프셋 0x1020 입니다. |
| 0x18 | 20 | `00 00 00 00` | 하위 키 수입니다. 지울 때 0 이 됩니다. |
| 0x20 | 28 | `FF FF FF FF` | 하위 키 목록 오프셋입니다. 지울 때 덮입니다. |
| 0x28 | 36 | `01 00 00 00` | 값 수 1. 지워도 남습니다. |
| 0x2C | 40 | `48 23 00 00` | 값 목록 오프셋 0x2348. 지워도 남습니다. |
| 0x30 | 44 | `FF FF FF FF` | 보안 항목 오프셋입니다. 지울 때 덮입니다. |
| 0x4C | 72 | `04 00` | 키 이름 길이 4바이트 |
| 0x50 | 76 | `54 65 73 74` | 키 이름 `Test` |

이어서 이렇게 따라갑니다.

1. 오프셋은 하이브 빈 데이터 시작 기준입니다. 파일 위치는 4096(0x1000)을 더한 값입니다.
2. 부모 오프셋 0x1020 은 파일 위치 0x2020 입니다. 그 셀의 크기 필드 뒤에 `nk` 가 있는지 봅니다. 그 셀이 지워지지 않은 키라면 경로를 잇습니다.
3. 값 목록 오프셋 0x2348 은 파일 위치 0x3348 입니다. 그 셀의 크기 필드 뒤 첫 4바이트가 값 레코드 오프셋입니다. 그 자리에 `vk` 가 있는지 봅니다.

하위 키 수 0 과 하위 키 목록 `0xFFFFFFFF` 는 하위 키가 없는 정상 키에서도 흔합니다. 지운 키라는 판단은 크기 필드가 양수라는 점과, 현재 트리에서 이 셀을 가리키는 곳이 없다는 점으로 합니다. 지워지지 않은 키 노드는 보안 항목을 가리키므로, 보안 항목 오프셋이 `0xFFFFFFFF` 인 것은 보조 단서가 됩니다.

## 포렌식에서 중요한 점

### 지운 시각

하이브에는 "지운 시각" 필드가 없고, 되살린 키 노드에는 마지막 기록 시각(FILETIME, UTC)이 남아 있습니다.

- 하위 키가 있던 키를 지우면 그 키의 시각이 갱신됩니다(Windows 2000 제외)[2]. 이 경우 그 시각은 지운 시각에 가깝습니다.
- 하위 키가 없던 키는 지울 때 시각이 바뀌지 않습니다. 이 경우 그 시각은 지우기 전 마지막으로 바뀐 시각입니다.
- 값 레코드에는 시각 필드가 없습니다.
- 시각이 바뀌는 규칙은 [키 마지막 기록 시각 (Last Write Time)](last-write-time.md) 을 봅니다. 부모 키 시각, 트랜잭션 로그, 섀도 복사본을 함께 보고 범위를 좁힙니다.

### 되살린 결과가 증명하는 것 / 증명하지 못하는 것

증명하는 것:

- 그 이름의 키나 값이 이 하이브에 한때 있었습니다.
- 데이터가 덮이지 않았다면 그때 값의 내용을 알 수 있습니다.
- 키 노드의 마지막 기록 시각에 그 키가 마지막으로 바뀌었습니다.

증명하지 못하는 것:

- 누가 지웠는지 알 수 없습니다. 사람이 지웠는지, Windows 나 프로그램이 지웠는지도 알 수 없습니다.
- 정확히 언제 지웠는지 알 수 없습니다.
- 되살린 경로가 맞다고 보장하지 않습니다. 부모 오프셋은 숫자일 뿐이라서, 그 자리에 다른 키가 새로 들어섰다면 엉뚱한 경로가 붙습니다.
- 되살리지 못한 키가 없었다는 뜻은 아닙니다. 덮였거나 재구성으로 사라졌을 수 있습니다.

지운 키가 있다는 사실만으로 사람이 지웠다고 볼 수 없습니다. 적게 쓴 Vista 시험 PC 의 SYSTEM 하이브에서는 하이브의 30% 가 빈 공간이었고 그중 83% 가 지운 구조로 되살아났습니다[2]. 키 5,669개(부모와 연결된 것 4,101개), 값 16,748개(키와 연결된 것 6,470개)가 나왔으며, 방화벽 정책, 이벤트 로그 설정, 하드웨어 설정 같은 시스템 항목이 많았습니다. 다른 하이브 표본들은 빈 공간 비율이 0~30%, 그중 되살린 비율이 0~83% 로 크게 달랐습니다.

보고서에는 기록으로 확인되는 만큼만 씁니다. 예: "SOFTWARE 하이브의 빈 셀에서 `…\CurrentVersion\Run` 키에 연결되는 값 레코드 1개가 발견됐습니다. 이 값은 현재 키 트리에서 참조되지 않습니다. 하이브에는 삭제 시각이 기록되지 않습니다."

### 지운 데이터가 사라지는 경우

- **셀 재사용**: 새 키·값이 빈 셀을 다시 씁니다. 자주 바뀌는 하이브일수록 빨리 덮일 수 있습니다.
- **하이브 재구성** (Windows 8·Server 2012 이후): 하이브가 잠겨 있지 않을 때 일주일에 한 번쯤 일어납니다. 재구성은 조각 모음(Defragmentation)을 하거나 키 접근 기록만 지웁니다. 조각 모음은 할당된 데이터만 기본 파일에 촘촘히 다시 씁니다. 그래서 그 전에 지운 데이터는 기본 파일에 남기 어렵습니다.
- **재구성 확인**: 기본 블록 오프셋 168 의 "마지막 재구성 시각"(8바이트, FILETIME, UTC)을 봅니다. 가장 아래 비트가 1 이면 마지막 재구성 때 조각 모음을 했다는 뜻입니다. 둘째 비트가 1 이면 키 접근 기록을 지웠다는 뜻입니다. 이 두 비트는 시각의 가장 작은 단위라서 시각을 읽는 데는 거의 영향이 없습니다. 이 시각이 조사 대상 시점보다 뒤이고 조각 모음 비트가 1 이면, 그 시점의 지운 데이터를 거의 되살리지 못해도 이상하지 않습니다.
- **정리·조각 모음 도구**: 레지스트리 조각 모음 도구가 빈 셀 대부분을 없앨 것이라는 추정이 있습니다[2].
- **일부러 덮기**: 모든 키에 값을 하나씩 만들었다 지우면 되살릴 레코드 대부분이 덮일 것이라는 추정이 있습니다[2]. 이 방법은 키 시각도 함께 바꿉니다.

하이브 파일 자체가 지워졌다면 디스크에서 하이브 빈을 찾아 모읍니다. [레코드 카빙 (Record Carving)](../../../03-techniques/analysis/data-recovery/record-carving.md) 을 봅니다.

## 함정

- **합쳐진 셀**: 빈 셀 첫머리만 보는 도구는 합쳐진 셀의 나머지 레코드를 놓칩니다.
- **재사용된 셀**: 값 목록 오프셋이 가리키는 셀이 이미 다른 용도로 쓰였을 수 있습니다. 이때 엉뚱한 값이 붙습니다. 옛 데이터 조각을 옛 레코드로 잘못 읽을 수도 있습니다.
- **이름만 바꾼 키**: Windows 10 일부 릴리스에서는 이름을 바꾼 키의 옛 셀이 트리에서 끊긴 채 할당 상태로 남습니다. 지운 키처럼 보이지만 지운 것이 아닙니다.
- **꾸며 넣은 구조**: 부모에서 자식으로 가는 확정된 연결이 없어서 낮은 권한 사용자도 지운 구조를 꾸며 넣을 수 있습니다[2]. 예를 들어 값 데이터에 `nk` 모양 바이트를 넣고 그 값을 지우면, 도구가 그것을 지운 키로 보여 줄 수 있습니다.
- **숨긴 데이터**: 빈 셀을 할당 상태로 바꾸면 데이터를 숨길 수 있습니다. 이런 셀은 트리에도 없고 빈 셀도 아닙니다. 아무도 가리키지 않는 할당 셀을 따로 검사해야 찾습니다.
- **로그 반영 여부**: 로그를 반영하지 않은 하이브에는 가장 최근의 지우기가 아직 들어가지 않았을 수 있습니다. 로그를 반영하면 빈 셀이 새 내용으로 덮일 수 있습니다. 두 상태를 모두 봅니다.
- **도구마다 다른 결과**: 남은 데이터를 건너뛰는 도구, 남는 공간을 보지 않는 도구, 부모를 모르는 값을 보여 주지 않는 도구가 있습니다. 두 가지 이상의 도구로 비교합니다. [도구 결과 교차 검증 (Tool Validation)](../../../03-techniques/reporting/tool-validation.md) 을 봅니다.

## 도구

아래는 공개 도구의 예이며, 도구마다 살펴보는 자리가 다르므로 결과를 서로 비교합니다.

| 도구 | 지운 데이터와 관련된 기능 |
|---|---|
| RegLookup 의 reglookup-recover | Morgan 이 발표한 복구 방법을 구현한 명령줄 도구입니다. |
| Registry Explorer·RECmd | 지운 키·값을 되살리고 값 데이터 뒤의 남는 공간을 보여 줍니다. 지워지지 않은 부모 키에 붙인 것(Associated deleted records)과 부모를 못 찾은 것(Unassociated deleted records)을 나눠 보여 줍니다. |
| yarp | 지운 키·값을 출력합니다. 트랜잭션 로그를 반영하거나 건너뛸 수 있습니다. 잘린 하이브와 따로 떨어진 하이브 빈도 읽습니다. |

도구가 지운 데이터를 어디까지 찾는지는 아래 공개 시험 데이터로 확인할 수 있습니다[3].

| 시험 데이터 | 하이브 | 찾아야 할 것 | 확인하는 능력 |
|---|---|---|---|
| NIST CFReDS Hacking Case | `\WINDOWS\system32\config\system` | 지운 `DhcpSubnetMaskOpt` 값 2개 | 빈 셀 하나에 든 여러 레코드 |
| Digital Corpora M57-Patents (`terry-2009-12-11-001.E01`) | `\Windows\System32\config\SYSTEM` | 지운 `AcceptOfficeAndTahoeServers` 값 2개 | 마지막 하이브 빈 뒤의 남은 데이터 |
| NIST CFReDS Hacking Case | `\WINDOWS\system32\config\software` | 지운 키 2개와 값 4개 | 할당된 셀의 남는 공간 |
