# 하이브 내부 구조 (regf·hbin·Cell)

상위 허브: [레지스트리 하이브 구조 (Registry Hive)](/01-foundations/database-log-formats/registry-hive/index.md)

## 한 줄 요약

하이브 파일은 머리 블록 하나와 그 뒤에 이어지는 hbin 블록 여러 개로 되어 있습니다.
키·값·보안 정보는 모두 hbin 안의 셀(Cell)에 들어 있습니다.

## 이 형식을 쓰는 파일

아래 파일은 모두 같은 regf 형식입니다.
그래서 이 페이지의 읽는 법이 그대로 통합니다.

| 파일 | 설명 | 자세히 |
|---|---|---|
| SYSTEM·SOFTWARE·SAM·SECURITY·DEFAULT·NTUSER.DAT·UsrClass.dat | 시스템 하이브와 사용자 하이브 | [하이브 파일 종류와 위치](/01-foundations/database-log-formats/registry-hive/system-software-sam-security-ntuser-dat-usrclass.md) |
| Amcache.hve | 프로그램·파일 목록을 담은 하이브 | [AmCache](/02-artifacts/execution/amcache-hve/index.md) |
| settings.dat | UWP 앱 설정 하이브 | [UWP 앱 데이터 구조](/01-foundations/app-mail-data/packages-settings-dat.md) |
| BCD | 부팅 설정 하이브입니다. 명세는 Windows 8.1 예로 `\Boot\BCD` 를 듭니다. | — |
| 백업 사본·저장 파일 | RegBack 사본, RegSaveKey 계열 함수로 저장한 파일 | 명세는 백업 사본이 기본 파일과 같은 형식이라고 적습니다. |

## 구조

### 전체 배치

하이브 파일은 기본 블록(Base Block) 4096바이트로 시작합니다.
그 뒤에 하이브 빈(Hive Bin, 이하 hbin)이 차례로 이어집니다.
hbin 하나는 32바이트 머리와 셀 여러 개로 되어 있습니다.
마지막 hbin 뒤에는 쓰레기 값이나 잔여 데이터가 붙어 있을 수 있습니다.

```
파일 오프셋 0x0000   기본 블록 (서명 "regf", 4096바이트)
파일 오프셋 0x1000   hbin #1  = 머리 32바이트 + 셀 + 셀 + ...
                     hbin #2
                     ...
                     (마지막 hbin 뒤: 잔여 데이터가 있을 수 있음)
```

> 그림 자리: 기본 블록 → 루트 키 셀 → 하위 키 목록 → 하위 키 셀, 그리고 키 셀 → 값 목록 → 값 셀 → 데이터 셀로 이어지는 포인터 흐름

모든 숫자는 리틀 엔디언입니다.
하이브 안의 오프셋은 대부분 파일 시작이 아니라 **hbin 데이터 시작(파일 오프셋 4096)** 을 기준으로 합니다.
그래서 파일 오프셋은 `4096 + 적힌 오프셋` 으로 구합니다.
오프셋 값이 0xFFFFFFFF 이면 아무 곳도 가리키지 않는다는 뜻입니다.

### 기본 블록 (Base Block, "regf")

| 오프셋 | 크기 | 칸 | 뜻 |
|---|---|---|---|
| 0 | 4 | 서명 | ASCII `regf` |
| 4 | 4 | 1차 순서 번호 (Primary Sequence Number) | 기본 파일에 쓰기 시작할 때 1 늘어납니다. |
| 8 | 4 | 2차 순서 번호 (Secondary Sequence Number) | 쓰기가 끝날 때 1 늘어납니다. 정상 종료면 1차와 같습니다. |
| 12 | 8 | 마지막 기록 시각 | FILETIME (UTC) |
| 20 | 4 | 주 버전 | 1 |
| 24 | 4 | 부 버전 | 3·4·5·6 |
| 28 | 4 | 파일 종류 | 0 = 기본 파일. 로그 파일 속 사본은 다른 값을 씁니다. |
| 32 | 4 | 파일 형식 | 1 |
| 36 | 4 | 루트 셀 오프셋 | 루트 키가 든 셀의 위치 (hbin 데이터 기준) |
| 40 | 4 | hbin 데이터 크기 | hbin 전체의 바이트 수 |
| 44 | 4 | 클러스터 계수 (Clustering Factor) | 논리 섹터 크기 ÷ 512. Windows 8 부터는 늘 1 입니다. |
| 48 | 64 | 파일 이름 | UTF-16LE. 경로 일부나 파일 이름이 들어갑니다. 디버깅용입니다. |
| 168 | 8 | 마지막 재구성 시각 | FILETIME (UTC). Windows 8 부터 씁니다. |
| 508 | 4 | 체크섬 | 앞 508바이트의 XOR-32 |

체크섬은 앞 508바이트를 4바이트씩 끊어 차례로 XOR 해서 구합니다.
결과가 0xFFFFFFFF 이면 0xFFFFFFFE 로 바꿉니다.
결과가 0 이면 1 로 바꿉니다.

112~167 사이 예약 칸에는 트랜잭션 관리용 GUID 와 `rmtm` 서명이 들어갑니다.
명세는 이 칸들이 Windows Vista 부터 쓰였다고 적습니다.
오프라인 레지스트리 라이브러리(offreg.dll)로 저장한 하이브에는 176 에 `OfRg` 서명이 들어갑니다.
이 경우 512 에는 저장 시각(FILETIME, UTC)이 들어갑니다.
옛 라이브러리(6.1)는 `OfRg` 를 168 에 씁니다.

### 하이브 빈 (Hive Bin, "hbin")

| 오프셋 | 크기 | 칸 | 뜻 |
|---|---|---|---|
| 0 | 4 | 서명 | ASCII `hbin` |
| 4 | 4 | 오프셋 | 이 hbin 자신의 위치 (hbin 데이터 기준) |
| 8 | 4 | 크기 | 이 hbin 의 바이트 수. 4096 의 배수입니다. |
| 12 | 8 | 예약 | |
| 20 | 8 | 시각 | 첫 hbin 에만 뜻이 있습니다. 기본 블록 마지막 기록 시각의 백업 사본입니다. |
| 28 | 4 | 여분 | 디스크에서는 뜻이 없습니다. |

hbin 크기는 4096 으로 고정되지 않습니다.
큰 셀이 필요하면 4096 의 몇 배인 hbin 이 생깁니다.
libyal 문서는 두 번째 hbin 부터 시각 칸이 대개 0 이거나 잔여 값이라고 적습니다.

### 셀 (Cell)

셀은 hbin 머리 뒤를 빈틈없이 채웁니다.
셀 하나는 4바이트 크기 칸과 셀 데이터로 되어 있습니다.

| 오프셋 | 크기 | 칸 | 뜻 |
|---|---|---|---|
| 0 | 4 | 크기 | 크기 칸 자신을 포함한 셀 크기. 8 의 배수입니다. |
| 4 | … | 셀 데이터 | 아래 레코드 가운데 하나, 또는 값 데이터 같은 날것의 바이트 |

크기 칸은 **부호 있는 32비트 정수**로 읽습니다.
음수이면 쓰고 있는 셀(할당된 셀)입니다.
양수이면 비어 있는 셀(비할당 셀, Unallocated Cell)입니다.
실제 크기는 절댓값입니다.
셀 끝에는 8바이트 맞춤용 여분이 붙을 수 있습니다.

셀 데이터 첫 2바이트 서명으로 레코드 종류를 가립니다.

| 서명 | 이름 | 담는 것 |
|---|---|---|
| `nk` | 키 노드 (Key Node) | 키 하나 |
| `vk` | 키 값 (Key Value) | 값 하나 |
| `sk` | 키 보안 (Key Security) | 보안 설명자 (Security Descriptor) |
| `li` `lf` `lh` | 하위 키 목록 (Subkey List) | 하위 키 nk 셀의 오프셋 목록 |
| `ri` | 인덱스 루트 (Index Root) | 하위 키 목록 여러 개의 오프셋 목록 |
| `db` | 큰 데이터 (Big Data) | 큰 값 데이터 조각들의 목록 |
| (서명 없음) | 값 목록 (Key Values List) | vk 셀 오프셋 배열 |

아래 표의 오프셋은 모두 **셀 데이터 기준**입니다.
셀 시작에서 따지면 4를 더해야 합니다.

### 키 노드 (nk)

| 오프셋 | 크기 | 칸 | 뜻 |
|---|---|---|---|
| 0 | 2 | 서명 | `nk` |
| 2 | 2 | 플래그 | 아래 표 |
| 4 | 8 | 마지막 기록 시각 | FILETIME (UTC). 해석은 [키 마지막 기록 시각](/01-foundations/database-log-formats/registry-hive/last-write-time.md) 참고 |
| 12 | 4 | 접근 비트 (Access Bits) | Windows 8 부터 씁니다. 그 전에는 예약 칸입니다. |
| 16 | 4 | 부모 | 부모 nk 셀 오프셋. 루트 키에서는 뜻이 없습니다. |
| 20 | 4 | 하위 키 수 | |
| 28 | 4 | 하위 키 목록 오프셋 | `li`·`lf`·`lh`·`ri` 셀 |
| 36 | 4 | 값 개수 | |
| 40 | 4 | 값 목록 오프셋 | |
| 44 | 4 | 보안 오프셋 | `sk` 셀 |
| 48 | 4 | 클래스 이름 오프셋 | |
| 72 | 2 | 키 이름 길이 | 바이트 수 |
| 74 | 2 | 클래스 이름 길이 | 바이트 수 |
| 76 | … | 키 이름 | 확장 ASCII 또는 UTF-16LE |

나머지 칸(휘발성 하위 키 수, 가장 긴 이름 길이 등)은 명세를 봅니다.

자주 보는 플래그는 다음과 같습니다.

| 값 | 이름 | 뜻 |
|---|---|---|
| 0x0004 | KEY_HIVE_ENTRY | 이 하이브의 루트 키 |
| 0x0008 | KEY_NO_DELETE | 지울 수 없는 키 |
| 0x0010 | KEY_SYM_LINK | 심볼릭 링크 키. 대상은 `SymbolicLinkValue` 값에 있습니다. |
| 0x0020 | KEY_COMP_NAME | 이름이 확장 ASCII 입니다. 이 비트가 없으면 UTF-16LE 입니다. |

클래스 이름 (Class Name)은 키에 붙는 UTF-16LE 문자열입니다.
대개 뜻이 없습니다.
다만 명세는 Microsoft 가 Syskey 암호화 키를 클래스 이름에 넣었다고 적습니다([부트키 구하기](/02-artifacts/credentials/sam-security/system-boot-key.md)).

### 하위 키 목록 (li·lf·lh·ri)

네 목록은 모두 `서명(2) + 요소 개수(2)` 뒤에 요소가 이어집니다.

| 서명 | 요소 크기 | 요소 내용 | 쓰는 버전 |
|---|---|---|---|
| `li` | 4 | nk 오프셋 | 모든 버전 |
| `lf` | 8 | nk 오프셋 + 이름 앞 4글자 (Name Hint) | 1.3 부터 |
| `lh` | 8 | nk 오프셋 + 이름 해시 (Name Hash) | 부 버전 5 이상 |
| `ri` | 4 | 하위 키 목록 오프셋 | 모든 버전 |

요소는 키 이름을 대문자로 바꾼 순서로 정렬되어 있습니다.
`ri` 는 다른 `ri` 를 가리킬 수 없습니다.
`lh` 의 이름 해시는 대문자 이름의 글자마다 `H = 37 × H + 글자 코드` 를 되풀이해 구합니다(32비트, 시작값 0).

### 키 값 (vk)과 값 데이터

| 오프셋 | 크기 | 칸 | 뜻 |
|---|---|---|---|
| 0 | 2 | 서명 | `vk` |
| 2 | 2 | 이름 길이 | 0 이면 이름 없는 값(기본값)입니다. |
| 4 | 4 | 데이터 크기 | 최상위 비트가 1 이면 데이터가 바로 다음 칸에 들어 있습니다. |
| 8 | 4 | 데이터 오프셋 | 데이터 셀 오프셋, 또는 데이터 자체 |
| 12 | 4 | 데이터 형식 | 1 = REG_SZ, 3 = REG_BINARY, 4 = REG_DWORD, 7 = REG_MULTI_SZ, 0x0B = REG_QWORD 등 |
| 16 | 2 | 플래그 | 0x0001 = 이름이 확장 ASCII |
| 18 | 2 | 여분 | |
| 20 | … | 값 이름 | |

값 데이터는 세 곳 가운데 한 곳에 있습니다.

1. **4바이트 이하**: 데이터 크기 칸의 최상위 비트가 1 입니다. 데이터는 데이터 오프셋 칸에 바로 들어 있습니다. 크기를 셀 때는 최상위 비트를 뺍니다.
2. **보통 크기**: 데이터 오프셋이 가리키는 셀 하나에 들어 있습니다.
3. **16,344바이트 초과**: 부 버전이 4 이상이면 데이터 오프셋이 `db` 셀을 가리킵니다.

`db` 셀은 `db`(2) + 조각 수(2) + 조각 목록 오프셋(4)으로 되어 있습니다.
조각은 마지막 것을 빼고 모두 16,344바이트입니다.

### 보안 레코드 (sk)

| 오프셋 | 크기 | 칸 | 뜻 |
|---|---|---|---|
| 0 | 2 | 서명 | `sk` |
| 4 | 4 | 다음 (Flink) | 다음 `sk` 셀 오프셋 |
| 8 | 4 | 이전 (Blink) | 이전 `sk` 셀 오프셋 |
| 12 | 4 | 참조 수 | 이 `sk` 를 가리키는 키 수 |
| 16 | 4 | 설명자 크기 | |
| 20 | … | 보안 설명자 | 소유자 SID 등. SID 읽는 법은 [윈도 식별자 형식](/01-foundations/value-decoding/sid-guid-clsid-known-folder-id.md) 참고 |

`sk` 레코드는 서로 앞뒤로 이어진 목록을 이룹니다.
권한이 같은 키 여러 개가 `sk` 하나를 함께 씁니다.

### 버전별 차이

| 부 버전 | 구조 차이 | 흔히 보이는 곳 |
|---|---|---|
| 1.3 | `lf` 를 씁니다. `db` 가 없어 큰 값도 셀 하나에 들어갑니다. | NT 4.0 이후, 주로 NTUSER.DAT (libyal) |
| 1.4 | `db` 를 쓸 수 있습니다. | libyal 문서는 아직 관찰하지 못했다고 적습니다 |
| 1.5 | `lh` 를 씁니다. | XP SP2 이후, 주로 SOFTWARE·SYSTEM (libyal) |
| 1.6 | 명세는 1.3~1.6 을 같은 배치로 설명합니다. | Windows 10 2004 의 컨테이너용 차등 하이브 (libyal) |

Windows NT 3.x 의 1.1·1.2 는 셀 배치가 달라 이 글에서 다루지 않습니다.

Microsoft 문서는 하이브 파일 형식을 "표준(standard)" 과 "최신(latest)" 둘로 나눕니다.
표준 형식은 Windows 2000 이 지원하는 유일한 형식입니다.
최신 형식은 Windows XP 부터 지원합니다.
최신 형식을 지원하는 버전에서도 HKCU·SAM·SECURITY·.DEFAULT 는 표준 형식을 씁니다.
값 하나의 크기 한도는 표준 형식이 1MB 이고 최신 형식은 메모리 한도까지입니다.
Microsoft 문서는 두 형식의 버전 번호를 적지 않습니다.
libyal 문서는 Windows 10 2004 에서 `RegSaveKeyEx` 로 저장할 때 표준 형식이 1.3, 최신 형식이 1.5 라고 적습니다.

## 읽는 법 — 헥스로 한 번 따라가기

아래 헥스는 **명세의 칸 배치대로 만든 예시**입니다.
실제 검체에서 나온 값이 아닙니다.
`..` 는 설명에 필요 없는 바이트입니다.

**1단계. 기본 블록 확인**

```
오프셋    00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F
00000000  72 65 67 66 D2 04 00 00 D2 04 00 00 .. .. .. ..   regf
00000010  .. .. .. .. 01 00 00 00 05 00 00 00 00 00 00 00
00000020  01 00 00 00 20 00 00 00 00 E0 7F 00 01 00 00 00
```

- 0x00 의 `72 65 67 66` 은 `regf` 입니다.
- 0x04 와 0x08 이 둘 다 0x4D2 입니다. 두 순서 번호가 같으므로 기본 파일에 대한 마지막 쓰기는 끝까지 마무리됐습니다. 로그에만 있는 변경은 따로 확인합니다.
- 0x14 는 1, 0x18 은 5 입니다. 형식 버전은 1.5 입니다.
- 0x24 의 루트 셀 오프셋은 0x20 입니다. 파일 오프셋은 0x1000 + 0x20 = 0x1020 입니다.
- 0x28 의 hbin 데이터 크기는 0x7FE000 입니다. 파일 크기가 0x1000 + 0x7FE000 보다 크면 끝에 잔여 데이터가 있습니다.
- 마지막으로 앞 508바이트의 XOR-32 를 계산해 0x1FC 의 체크섬과 맞춰 봅니다.

**2단계. 첫 hbin 확인**

```
00001000  68 62 69 6E 00 00 00 00 00 10 00 00 00 00 00 00   hbin
00001010  00 00 00 00 .. .. .. .. .. .. .. .. 00 00 00 00
```

- 서명은 `hbin` 이고 자기 오프셋은 0, 크기는 0x1000 입니다.
- 다음 hbin 은 파일 0x2000 에 있어야 합니다. 그 hbin 의 오프셋 칸은 0x1000 이어야 합니다.

**3단계. 루트 키 셀 읽기**

```
00001020  A8 FF FF FF 6E 6B 2C 00 .. .. .. .. .. .. .. ..
```

- `A8 FF FF FF` 를 부호 있게 읽으면 -88 입니다. 88바이트짜리 할당된 셀입니다.
- `6E 6B` 는 `nk` 입니다.
- 플래그 0x002C 는 0x0004(루트) + 0x0008(지울 수 없음) + 0x0020(이름이 ASCII)입니다.
- 셀 데이터는 0x1024 에서 시작합니다. 각 칸은 0x1024 + 칸 오프셋에 있습니다.
- 하위 키 목록 오프셋은 0x1040(+28), 값 목록 오프셋은 0x104C(+40), 이름 길이는 0x106C(+72), 이름은 0x1070(+76)에 있습니다.
- 이름이 4바이트라면 셀 크기는 4 + 76 + 4 = 84 입니다. 8 의 배수로 올리면 88 입니다. 크기 칸과 맞습니다.

**4단계. 하위 키 목록의 해시 맞춰 보기**

하위 키 목록이 `lh` 이고 그 안에 `Select` 키가 있다고 합시다.
대문자 `SELECT` 로 해시를 구하면 0x5F0024A0 입니다.
파일에는 리틀 엔디언으로 `A0 24 00 5F` 가 적힙니다.
요소의 해시가 가리키는 nk 이름과 맞지 않으면 목록이나 셀이 손상됐을 수 있습니다.
`Select` 키의 뜻은 [컨트롤셋 고르기](/01-foundations/database-log-formats/registry-hive/controlset-select.md) 를 봅니다.

**5단계. 값 셀과 인라인 데이터 읽기**

```
E0 FF FF FF 76 6B 04 00 04 00 00 80 E4 FD FF FF
04 00 00 00 01 00 00 00 42 69 61 73 00 00 00 00
```

- `E0 FF FF FF` 는 -32 입니다. 32바이트짜리 할당된 셀입니다.
- `76 6B` 는 `vk` 이고 이름 길이는 4 입니다.
- 데이터 크기 칸은 0x80000004 입니다. 최상위 비트가 1 이므로 데이터가 다음 칸에 바로 들어 있습니다. 크기는 4바이트입니다.
- 데이터 `E4 FD FF FF` 를 부호 없이 읽으면 4294966756 이고, 부호 있게 읽으면 -540 입니다.
- 데이터 형식은 4(REG_DWORD)이고 플래그 1 은 이름이 ASCII 라는 뜻입니다.
- 이름은 `42 69 61 73`, 곧 `Bias` 입니다.
- 셀 데이터는 24바이트이고 크기 칸을 더하면 28바이트입니다. 8 의 배수인 32바이트를 맞추려고 마지막 4바이트가 여분으로 붙었습니다.

이 예의 값은 시간대 설정 `Bias` 를 흉내 낸 것입니다.
`Bias` 는 부호 있는 32비트로 읽어야 합니다(확인 범위: 압수 이미지에서 꺼낸 SYSTEM 하이브, 현장 관찰).
UTC+9 는 -540 입니다.
자세한 해석은 [시간대 설정](/02-artifacts/system-account/time-zone.md) 을 봅니다.

## 포렌식에서 중요한 점

### 비할당 셀에 남는 것

키나 값을 지우면 그 셀의 크기 칸이 양수가 됩니다.
셀 내용이 곧바로 지워진다는 보장은 없습니다.
그래서 비할당 셀 안에 옛 `nk`·`vk` 레코드가 남아 있을 수 있습니다.
붙어 있는 비할당 셀은 하나로 합쳐집니다.
그래서 비할당 셀 하나에 옛 레코드 여러 개가 들어 있을 수 있습니다.
되살리는 방법은 [지워진 키·값 복구](/01-foundations/database-log-formats/registry-hive/deleted-keys-values.md) 에서 다룹니다.

### 비정상 종료와 반영 안 된 변경

명세는 다음 두 경우에 하이브를 "더러운(dirty)" 상태로 봅니다.

- 기본 블록 체크섬이 틀린 경우
- 1차 순서 번호와 2차 순서 번호가 다른 경우

이런 하이브는 기본 파일만 읽으면 중간까지만 쓰인 상태일 수 있습니다.
Windows 8.1 부터 쓰는 새 로그 형식에서는 변경이 로그 파일에 먼저 쓰입니다.
명세에 따르면 기본 파일 반영은 최대 1시간까지 미뤄질 수 있습니다.
그래서 기본 파일만 읽으면 최근 변경을 놓칠 수 있습니다.
하이브를 수집할 때는 `.LOG1`·`.LOG2` 를 함께 가져옵니다.
로그 구조와 적용 방법은 [트랜잭션 로그와 반영 안 된 변경](/01-foundations/database-log-formats/registry-hive/log1-log2.md) 에서 다룹니다.

### 구조 안의 시각 칸

모든 시각 칸은 FILETIME (UTC) 입니다([시각 값 형식](/01-foundations/value-decoding/filetime-unix-webkit-dos-ole.md)).

| 위치 | 뜻 | 주의 |
|---|---|---|
| 기본 블록 +12 | 마지막 기록 시각 | 명세에 따르면 Windows 8.1 부터는 갱신되지 않습니다. 하이브를 만들 때만 적힐 수 있습니다. |
| 첫 hbin +20 | 위 시각의 백업 사본 | 두 번째 hbin 부터는 대개 뜻이 없습니다. |
| 기본 블록 +168 | 마지막 재구성 시각 | Windows 8 부터. 재구성은 하이브가 잠겨 있지 않을 때 주 1회 일어납니다. 낮은 2비트는 재구성 종류를 나타냅니다. |
| 기본 블록 +512 | offreg 저장 시각 | 176(옛 라이브러리는 168)에 `OfRg` 가 있을 때만 뜻이 있습니다. |
| nk +4 | 키 마지막 기록 시각 | [키 마지막 기록 시각](/01-foundations/database-log-formats/registry-hive/last-write-time.md) 참고 |

Windows 8 부터 nk 의 접근 비트는 키가 열린 적이 있는지 기록합니다.
0x1 은 부팅 중 레지스트리 초기화 전에 열렸다는 뜻입니다.
0x2 는 초기화 뒤에 열렸다는 뜻입니다.
이 기록은 재구성 때 지워질 수 있습니다.
그래서 0 이라고 해서 한 번도 열린 적이 없다고 말할 수는 없습니다.

### 조각 찾기

hbin 머리에는 서명, 자기 오프셋, 4096 배수 크기가 함께 들어 있습니다.
이 세 가지로 디스크 비할당 영역이나 사본에서 찾은 hbin 조각의 순서를 맞춰 볼 수 있습니다.
방법은 [레코드 카빙](/03-techniques/analysis/data-recovery/record-carving.md) 을 봅니다.
예전 시점의 하이브 전체가 필요하면 [볼륨 섀도 복사본](/01-foundations/disk-volume/volume-shadow-copy.md) 을 먼저 찾습니다.

## 함정

- **오프셋 기준을 헷갈림.** 하이브 안 오프셋은 hbin 데이터 기준입니다. 파일 오프셋으로 쓰려면 4096 을 더합니다.
- **셀 표 오프셋을 셀 시작에서 셈.** nk·vk 표의 오프셋은 크기 칸 4바이트 뒤부터 셉니다.
- **셀 크기를 부호 없이 읽음.** 부호 없이 읽으면 할당된 셀이 4GB 가까운 크기로 보입니다.
- **확장 ASCII 이름을 코드 페이지로 읽음.** KEY_COMP_NAME 이름의 한 바이트는 U+0000~U+00FF 글자 하나입니다. CP949 로 읽으면 0x80 이상 글자가 깨집니다. 한글이 든 이름은 UTF-16LE 로 저장됩니다([문자 인코딩](/01-foundations/value-decoding/utf-16le-utf-8-cp949.md)).
- **인라인 데이터를 오프셋으로 착각함.** 데이터 크기 칸의 최상위 비트를 먼저 확인합니다.
- **REG_DWORD 부호.** 레지스트리 값을 문자열로 받는 도구는 REG_DWORD 를 부호 없는 10진으로 보여 주는 경우가 많습니다(확인 범위: 압수 이미지에서 꺼낸 하이브, 현장 관찰). 부호에 뜻이 있는 값은 원시 바이트로 확인합니다.
- **정해진 형식 번호만 있다고 가정함.** 명세는 미리 정한 형식 밖의 번호도 허용한다고 적습니다. 도구가 모르는 형식 번호는 원시 바이트로 봅니다.
- **기본 블록 시각을 하이브 수정 시각으로 씀.** Windows 8.1 부터 이 칸은 갱신되지 않습니다. 하이브가 언제 바뀌었는지는 키 시각과 파일 시스템 시각으로 따로 봅니다.
- **hbin 영역 중간에서 멈춤.** libyal 문서는 Windows 8.1 SYSTEM 하이브의 hbin 데이터 끝부분이 0 으로 채워진 사례를 적습니다. 파서가 이 구간에서 오류로 멈추면 뒤 내용을 놓칠 수 있습니다.
- **사용 중에 복사한 하이브.** libyal 문서는 사용 중에 복사한 하이브에서 값 레코드가 깨진 사례를 적습니다. 이런 값은 믿기 어렵습니다. 수집 방법은 [선별 수집](/03-techniques/process-acquisition/evidence-acquisition/triage-collection.md) 을 봅니다.

## 도구

하이브 구조를 직접 읽는 공개 도구와 라이브러리로는 libregf(libyal), yarp, regipy, python-registry, Registry Explorer 등이 있습니다.
도구마다 더러운 하이브, 로그 적용, 비할당 셀을 다루는 방식이 다릅니다.
결과 수가 다르면 헥스로 셀 몇 개를 직접 따라가 봅니다.
여러 도구 결과를 맞춰 보는 방법은 [도구 결과 교차 검증](/03-techniques/reporting/tool-validation.md) 을 봅니다.
