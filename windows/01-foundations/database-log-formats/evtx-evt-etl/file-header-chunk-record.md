# EVTX 파일 구조 (File Header·Chunk·Record)

## 한 줄 요약

EVTX 파일은 4096바이트 파일 헤더 (File Header) 뒤에 65536바이트 청크 (Chunk) 를 이어 붙인 파일입니다. 이벤트 레코드 (Event Record) 는 청크 안에 차례로 들어 있습니다. 파일 헤더와 청크 헤더에는 서명과 CRC32 체크섬이 있습니다. 레코드에는 서명과 크기 사본이 있습니다. 이 값들을 따라가면 헥스만으로 레코드 경계를 찾고 손상을 가려낼 수 있습니다.

이 페이지는 [이벤트 로그 형식 (EVTX·EVT·ETL)](index.md) 의 하위 주제입니다. 레코드 본문을 푸는 법은 [이진 XML 해석 (Binary XML·Template)](binary-xml-template.md) 에 있습니다. 설명 문장을 찾는 법은 [공급자와 메시지 파일 (Provider·Message Table)](provider-message-table.md) 에 있습니다. 빈 공간과 손상은 [파일 안에 남은 지운·손상 레코드 (Chunk Slack·Corrupted EVTX)](chunk-slack-corrupted-evtx.md) 에서 다룹니다.

## 이 형식을 쓰는 아티팩트

- Windows Vista 부터 이벤트 로그는 EVTX 형식입니다. XP 까지 쓰던 형식은 [구형 EVT 형식 (Windows XP·2003)](windows-xp-2003.md) 에서 다룹니다.
- 파일은 `C:\Windows\System32\winevt\Logs\` 에 있습니다. 로그마다 파일이 따로 있습니다.
- [로그온·로그오프](../../../02-artifacts/event-logs/logon-events/index.md), [서비스 설치](../../../02-artifacts/event-logs/7045-4697.md), [프로세스 생성](../../../02-artifacts/event-logs/4688.md), [PowerShell 실행 기록](../../../02-artifacts/event-logs/powershell-event-logs-4103-4104.md) 같은 이벤트 아티팩트는 모두 이 파일에서 읽습니다.

## 구조

> 그림 자리: 파일 헤더(4 KiB) 뒤에 64 KiB 청크가 이어지는 파일 전체 모습과, 청크 하나를 확대해 청크 헤더(512바이트)·레코드 배열·빈 공간 오프셋·안 쓴 공간을 보여 주는 그림

### 전체 배치

- 파일은 파일 헤더, 청크 여러 개, 뒤쪽 빈 값 순서로 놓입니다.
- 정수는 모두 리틀 엔디언입니다.
- 날짜와 시각은 UTC 기준 FILETIME 입니다. 푸는 법은 [시각 값 형식](../../value-decoding/filetime-unix-webkit-dos-ole.md) 에 있습니다.
- 문자열은 BOM 없는 UTF-16LE 입니다. [문자 인코딩](../../value-decoding/utf-16le-utf-8-cp949.md) 을 봅니다.
- 첫 청크는 파일 오프셋 4096 에서 시작합니다. 그 뒤로 청크가 65536바이트씩 이어집니다.
- 아래 오프셋은 libevtx 명세 기준의 10진 바이트입니다. 괄호 안은 16진입니다.

### 파일 헤더 (4096바이트)

| 오프셋 | 크기 | 내용 |
|---|---|---|
| 0 (0x00) | 8 | 서명 `ElfFile\x00` |
| 8 (0x08) | 8 | 첫 청크 번호 |
| 16 (0x10) | 8 | 마지막 청크 번호 |
| 24 (0x18) | 8 | 다음 레코드 식별자 |
| 32 (0x20) | 4 | 헤더 크기. 값은 128 입니다 |
| 36 (0x24) | 2 | 부 버전 |
| 38 (0x26) | 2 | 주 버전 |
| 40 (0x28) | 2 | 헤더 블록 크기. 값은 4096 이고, 청크 데이터가 시작하는 오프셋입니다 |
| 42 (0x2A) | 4 | 청크 개수 |
| 46 (0x2E) | 74 | 알 수 없음(빈 값) |
| 120 (0x78) | 4 | 파일 플래그 |
| 124 (0x7C) | 4 | 체크섬. 앞 120바이트의 CRC32 입니다(RFC 1952 방식, 초깃값 0) |
| 128 ~ 4095 | — | 알 수 없음(빈 값) |

| 파일 플래그 | 뜻 |
|---|---|
| `0x0001` | dirty. 파일이 정상적으로 닫히지 않았습니다 |
| `0x0002` | full. 로그가 가득 찼습니다 |

| 형식 버전 | 보이는 곳 |
|---|---|
| 3.1 | Windows Vista 이후 |
| 3.2 | Windows 10 2004 이후 |

확인 PC 에서 본 값입니다(확인 범위: Windows 11 25H2 PC 한 대, 쓰는 중인 로그 파일 225개).

- 225개 파일이 모두 버전 3.2 였습니다.
- 225개 파일 모두 헤더 체크섬이 맞았습니다.
- 헤더의 다음 레코드 식별자는 파일 안 가장 큰 레코드 식별자에 1 을 더한 값이었습니다. Application.evtx 는 헤더 값이 63,689 이고, 가장 큰 식별자가 63,688 이었습니다.

### 청크 (65536바이트)

청크는 청크 헤더(512바이트), 이벤트 레코드 배열, 안 쓴 공간 순서로 놓입니다. 아래 오프셋은 청크 시작 기준입니다.

| 오프셋 | 크기 | 내용 |
|---|---|---|
| 0 (0x00) | 8 | 서명 `ElfChnk\x00` |
| 8 (0x08) | 8 | 첫 이벤트 레코드 번호 |
| 16 (0x10) | 8 | 마지막 이벤트 레코드 번호 |
| 24 (0x18) | 8 | 첫 이벤트 레코드 식별자 |
| 32 (0x20) | 8 | 마지막 이벤트 레코드 식별자 |
| 40 (0x28) | 4 | 헤더 크기. 값은 128 입니다 |
| 44 (0x2C) | 4 | 마지막 레코드의 오프셋 |
| 48 (0x30) | 4 | 빈 공간 오프셋 |
| 52 (0x34) | 4 | 이벤트 레코드 데이터의 CRC32 |
| 56 (0x38) | 64 | 알 수 없음(빈 값) |
| 120 (0x78) | 4 | 알 수 없음. 명세는 플래그로 추정합니다 |
| 124 (0x7C) | 4 | 청크 헤더 체크섬. 0~119 바이트와 128~511 바이트를 이어 계산한 CRC32 입니다 |
| 128 (0x80) | 256 | 공통 문자열 오프셋 64개(각 4바이트) |
| 384 (0x180) | 128 | 템플릿 포인터 (TemplatePtr) 32개(각 4바이트) |

- 한 청크의 레코드 수는 "마지막 레코드 번호 − 첫 레코드 번호 + 1" 입니다.
- 정상 파일에서는 뒤 청크의 레코드 번호가 앞 청크에서 이어집니다. 명세의 예에서는 첫 청크가 1~117번, 둘째 청크가 118~232번입니다.
- 명세는 공통 문자열 오프셋 배열이 청크 안 레코드들이 함께 쓰는 문자열을 가리킨다고 봅니다. 다만 이 설명에 "확인 안 됨" 표시를 붙였습니다.
- 보관(archive)된 EVTX 에서는 빈 공간 오프셋이 레코드 끝이 아니라 청크 끝을 가리키는 경우가 있었습니다. 그 사이는 0 으로 채워져 있었습니다.

확인 PC 에서 본 값입니다(확인 범위: 위와 같은 PC, 청크 3,870개).

- 3,870개 모두 청크 헤더 체크섬이 맞았습니다.
- 레코드 데이터 CRC32 는 청크의 512 바이트부터 빈 공간 오프셋 앞까지를 계산했을 때 3,870개 모두 맞았습니다.
- 오프셋 120 의 값은 3,870개 모두 1 이었습니다.
- 첫 레코드는 청크 시작 + 512(0x200) 에 있었습니다.

### 이벤트 레코드

아래 오프셋은 레코드 시작 기준입니다.

| 오프셋 | 크기 | 내용 |
|---|---|---|
| 0 (0x00) | 4 | 서명 `2A 2A 00 00` (`**`) |
| 4 (0x04) | 4 | 레코드 크기. 서명과 이 칸을 포함한 전체 크기입니다 |
| 8 (0x08) | 8 | 이벤트 레코드 식별자 |
| 16 (0x10) | 8 | 기록 시각 (FILETIME). 레코드가 파일에 쓰인 시각입니다 |
| 24 (0x18) | 가변 | 이벤트 본문(이진 XML) |
| 끝 − 4 | 4 | 크기 사본. 4 오프셋의 크기와 같아야 합니다 |

- 본문을 푸는 법은 [이진 XML 해석](binary-xml-template.md) 에 있습니다.
- 확인 PC 의 System.evtx 첫 레코드는 크기가 1,624, 식별자가 1 이었습니다. 끝 4바이트도 1,624 였습니다.

### 이벤트 식별자와 수준

두 값은 레코드 본문(XML) 안에 들어 있습니다. EVT 와 메시지 파일에서도 같은 틀을 쓰므로 여기에 한 번 정리합니다.

이벤트 식별자는 32비트입니다.

| 비트 | 뜻 |
|---|---|
| 0 ~ 15 | 코드 |
| 16 ~ 27 | facility (12비트) |
| 28 | 예약 |
| 29 | customer |
| 30 ~ 31 | severity. `00` 성공, `01` 정보, `10` 경고, `11` 오류 |

| 수준 (Level) | 이름 | 비고 |
|---|---|---|
| 0 | LogAlways | 이벤트 뷰어는 "정보" 로 보여 줍니다 |
| 1 | Critical | |
| 2 | Error | |
| 3 | Warning | |
| 4 | Informational | |
| 5 | Verbose | |

### 로그 크기·덮어쓰기 설정

로그 설정은 `HKLM\SYSTEM\CurrentControlSet\Services\Eventlog\<로그 이름>` 키에 있습니다. 하이브를 읽는 법은 [레지스트리 하이브 구조](../registry-hive/index.md) 에 있습니다. 감사 정책 쪽 설정은 [감사 정책과 로그 설정](../../../02-artifacts/event-logs/audit-policy-log-settings.md) 에서 다룹니다.

| 값 | 형식 | 뜻 |
|---|---|---|
| File | REG_SZ 또는 REG_EXPAND_SZ | 로그 파일 전체 경로 |
| MaxSize | REG_DWORD | 최대 크기(바이트). System·Application·Security 는 64K 의 배수여야 합니다. 기본은 1MB 입니다 |
| Retention | REG_DWORD | 기본값은 0 입니다. 0 이면 늘 덮어씁니다. 0 이 아니면(0xFFFFFFFF 포함) 덮어쓰지 않고, 가득 차면 새 이벤트를 버립니다 |
| AutoBackupLogFiles | REG_DWORD | 기본값 0 은 자동 백업을 끕니다. Retention 이 -1(0xFFFFFFFF) 일 때만 자동 백업합니다 |

- Microsoft 문서는 DisplayNameFile·DisplayNameID·PrimaryModule·Sources·RestrictGuestAccess 를 "쓰지 않는 값" 으로 적습니다.

확인 PC 에서 본 값입니다(확인 범위: Windows 11 25H2 PC 한 대).

- System 키에는 File=`%SystemRoot%\system32\winevt\Logs\System.evtx`, MaxSize=0x1400000, Retention=0 이 있었습니다.
- Application 키도 같은 모양이었고, AutoBackupLogFiles=0 이 더 있었습니다.
- `…/Operational` 같은 채널 로그는 `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\WINEVT\Channels\<채널>` 키에 MaxSize 가 따로 있었습니다.
- Application.evtx 크기는 20,975,616바이트였습니다. 4,096 + 320 × 65,536 과 같습니다.
- Application.evtx 헤더의 청크 개수도 320 이었습니다.
- 같은 로그의 MaxSize 0x1400000 은 20,971,520 = 320 × 65,536 입니다. 로그가 최대 크기까지 차면 파일 크기가 "MaxSize + 헤더 4 KiB" 였습니다.

## 읽는 법

1. 원본의 해시를 구하고 사본에서 작업합니다.
2. 파일 헤더의 서명 `ElfFile\x00` 을 확인합니다. 앞 120바이트의 CRC32 를 계산해 124 오프셋의 값과 비교합니다.
3. 형식 버전, 파일 플래그, 첫·마지막 청크 번호, 청크 개수, 다음 레코드 식별자를 적어 둡니다.
4. 파일 오프셋 4096 부터 65536바이트씩 잘라 청크 서명 `ElfChnk\x00` 을 확인합니다. 헤더의 청크 개수보다 칸이 많을 수 있으므로 파일 끝까지 봅니다.
5. 청크 헤더 체크섬과 레코드 데이터 CRC32 를 확인합니다. 맞지 않는 청크는 따로 표시합니다.
6. 청크 시작 + 512 에서 첫 레코드를 읽습니다. 서명과 크기를 읽고, 크기만큼 건너 다음 레코드로 갑니다. 마지막 레코드 오프셋의 레코드까지 읽습니다.
7. 레코드마다 끝 4바이트의 크기 사본이 앞의 크기와 같은지 확인합니다.
8. 24 오프셋부터의 본문을 이진 XML 로 풉니다. 요소 이름과 템플릿은 청크 시작 기준 오프셋으로 가리키므로, 레코드를 청크에서 떼어 내면 풀 수 없습니다.
9. 모은 레코드를 식별자 순서로 늘어놓습니다. 한 바퀴 돈 로그는 파일 안 순서와 시간 순서가 다릅니다.

### 헥스로 한 번 따라가기

아래는 명세로 만든 예시입니다. 실제 검체에서 떠낸 바이트가 아닙니다. `??` 는 이 설명에 쓰지 않는 바이트입니다. 청크 2개짜리 파일이고, 레코드 번호는 명세의 예(첫 청크 1~117번)를 따랐습니다.

**파일 헤더**

```
오프셋    00 01 02 03 04 05 06 07  08 09 0A 0B 0C 0D 0E 0F
00000000  45 6C 66 46 69 6C 65 00  ?? ?? ?? ?? ?? ?? ?? ??
00000010  ?? ?? ?? ?? ?? ?? ?? ??  E9 00 00 00 00 00 00 00
00000020  80 00 00 00 02 00 03 00  00 10 02 00 00 00 00 00
  ...
00000070  00 00 00 00 00 00 00 00  00 00 00 00 ?? ?? ?? ??
```

- 0x00 `ElfFile\x00` 은 서명입니다.
- 0x08 과 0x10 은 첫·마지막 청크 번호입니다. 이 예에서는 비워 두었습니다.
- 0x18 `E9 00 …` 은 다음 레코드 식별자 233 입니다.
- 0x20 `80 00 00 00` 은 헤더 크기 128 입니다.
- 0x24 `02 00` 은 부 버전 2, 0x26 `03 00` 은 주 버전 3 입니다. 형식 3.2 입니다.
- 0x28 `00 10` 은 헤더 블록 크기 4096 입니다.
- 0x2A `02 00 00 00` 은 청크 2개입니다.
- 0x78 `00 00 00 00` 은 파일 플래그 0 입니다. dirty 도 full 도 아닙니다.
- 0x7C 의 체크섬은 0x00 ~ 0x77 을 CRC32 로 계산한 값과 같아야 합니다.

**첫 청크 (파일 오프셋 0x1000)**

```
오프셋    00 01 02 03 04 05 06 07  08 09 0A 0B 0C 0D 0E 0F
00001000  45 6C 66 43 68 6E 6B 00  01 00 00 00 00 00 00 00
00001010  75 00 00 00 00 00 00 00  01 00 00 00 00 00 00 00
00001020  75 00 00 00 00 00 00 00  80 00 00 00 ?? ?? 00 00
00001030  00 E0 00 00 ?? ?? ?? ??  00 00 00 00 00 00 00 00
  ...
00001070  00 00 00 00 00 00 00 00  01 00 00 00 ?? ?? ?? ??
```

- 0x1008 과 0x1010 은 첫·마지막 레코드 번호 1 과 117(0x75) 입니다. 이 청크의 레코드는 117 − 1 + 1 = 117개입니다.
- 0x1018 과 0x1020 은 첫·마지막 레코드 식별자입니다.
- 0x1028 `80 00 00 00` 은 헤더 크기 128 입니다.
- 0x102C 는 마지막 레코드의 오프셋입니다.
- 0x1030 `00 E0 00 00` 은 빈 공간 오프셋 0xE000 입니다. 파일 오프셋으로는 0x1000 + 0xE000 = 0xF000 입니다. 여기부터 청크 끝(0x11000) 앞까지는 레코드 목록 밖입니다.
- 0x1078 의 값 1 은 확인 PC 의 청크에서 늘 보이던 값을 넣은 것입니다.
- 0x107C 의 체크섬은 0x1000 ~ 0x1077 과 0x1080 ~ 0x11FF 를 이어서 계산합니다.

**첫 레코드 (파일 오프셋 0x1200)**

```
오프셋    00 01 02 03 04 05 06 07  08 09 0A 0B 0C 0D 0E 0F
00001200  2A 2A 00 00 58 06 00 00  01 00 00 00 00 00 00 00
00001210  ?? ?? ?? ?? ?? ?? ?? ??  0F 01 01 00 0C ?? ?? ??
  ...
00001850  ?? ?? ?? ?? 58 06 00 00
```

- 0x1200 `2A 2A 00 00` 은 레코드 서명입니다.
- 0x1204 `58 06 00 00` 은 크기 0x658(1,624) 입니다.
- 0x1208 은 식별자 1 입니다.
- 0x1210 의 8바이트는 기록 시각(FILETIME) 입니다.
- 0x1218 `0F 01 01 00` 부터가 이진 XML 입니다. 뒤의 `0C` 는 템플릿 인스턴스 토큰입니다.
- 크기 사본은 0x1200 + 0x658 − 4 = 0x1854 에 있습니다. 앞의 크기와 같습니다.
- 다음 레코드는 0x1200 + 0x658 = 0x1858 에서 시작합니다.
- 크기 1,624 와 본문 앞 5바이트는 확인 PC 의 System.evtx 첫 레코드에서 본 값과 같게 넣었습니다.

## 포렌식에서 중요한 점

### 비정상 종료 표시 (dirty)

- 파일 플래그 0x0001 은 파일이 정상적으로 닫히지 않았다는 표시입니다.
- 켜져 있는 PC 에서 쓰는 중인 파일을 읽으면 dirty 가 보일 수 있습니다. 확인 PC 에서는 225개 가운데 211개가 플래그 0, 14개가 dirty 였습니다(확인 범위: Windows 11 25H2 PC 한 대).
- dirty 파일은 헤더 값이 실제 청크와 어긋날 수 있습니다. 사례와 읽는 법은 [파일 안에 남은 지운·손상 레코드](chunk-slack-corrupted-evtx.md) 에 있습니다.

### 한 바퀴 돈 로그

아래는 확인 PC 에서 본 모습입니다(확인 범위: Windows 11 25H2 PC 한 대, 쓰는 중인 로그 225개).

- Application.evtx 는 첫 청크 번호가 122, 마지막 청크 번호가 121 이었습니다.
- 파일 맨 앞 칸의 청크에는 레코드 56,091번부터 들어 있었습니다. 한 바퀴 돌아 앞쪽 칸을 다시 쓰는 중이었습니다.
- 이 파일은 크기가 MaxSize 에 닿아 있었고, 로그의 Retention 은 0 이었습니다.
- 225개 가운데 45개 파일이 이렇게 "첫 청크 번호 > 마지막 청크 번호" 였습니다.

이 모양은 정상 순환입니다. 이것만으로 손상이라고 판단하지 않습니다. 덮인 레코드의 조각은 청크 빈 공간에 남을 수 있습니다.

### 헤더 값과 실제 파일 비교

- libevtx 명세는 "파일 크기 = 청크 수 × 65536 + 4096" 이 늘 맞는지 확인하지 못했다고 적었습니다.
- 확인 PC 의 System.evtx 는 헤더의 청크 개수가 171 이었고, 파일 크기로 센 칸은 177 이었습니다. 뒤 6칸은 서명까지 전부 0 이었습니다. 아직 쓰지 않은 칸을 미리 늘려 둔 것으로 보입니다.
- 확인 PC 의 Setup.evtx 도 헤더는 15, 칸은 16 이었고, 마지막 1칸이 0 이었습니다.
- 청크 개수는 헤더와 파일 크기 두 쪽으로 셉니다. 남는 칸은 서명이 있는지 직접 확인합니다.
- 다음 레코드 식별자가 "가장 큰 식별자 + 1" 과 다르면 끝쪽 레코드가 빠졌는지 확인합니다.

### 시각

- 레코드 헤더의 기록 시각은 레코드가 파일에 쓰인 시각입니다. UTC 입니다.
- 본문 XML 안의 TimeCreated 는 헤더의 기록 시각과 다를 수 있습니다.
- 일부 wevtutil 버전이 내보낸 파일에 헤더 시각을 잘못 쓴 사례가 명세에 있습니다.
- 두 값이 다르면 둘 다 적고, 보고서에는 어느 값을 썼는지 밝힙니다. 시간순 정리는 [타임라인 작성](../../../03-techniques/analysis/timeline/index.md) 을 봅니다.

### 로그를 지운 경우

로그 지우기(Clear) 가 파일을 어떻게 바꾸는지는 이 위키가 참고한 자료로 확인하지 못했습니다. 지운 흔적을 찾는 법은 [이벤트 로그 삭제](../../../02-artifacts/event-logs/1102-104.md) 에서 다룹니다.

## 함정

- 첫 청크 번호가 마지막 청크 번호보다 크다고 손상은 아닙니다. 한 바퀴 돈 정상 로그에서 흔히 보입니다.
- 헤더의 청크 개수만 믿고 읽으면 뒤쪽 칸을 놓칠 수 있습니다.
- 체크섬마다 계산 범위가 다릅니다. 파일 헤더는 앞 120바이트, 청크 헤더는 0~119 바이트와 128~511 바이트, 레코드 데이터는 512 바이트부터 빈 공간 오프셋 앞까지입니다. 마지막 범위는 확인 PC 에서 맞춰 본 것입니다.
- 청크 헤더에는 레코드 번호 한 쌍과 레코드 식별자 한 쌍이 따로 있습니다. 두 쌍을 섞어 쓰지 않습니다.
- 레코드 하나만 떼어 XML 로 풀 수는 없습니다. 이름과 템플릿이 같은 청크의 다른 자리에 있습니다.
- 설명 문장은 파일 안에 없습니다. [공급자와 메시지 파일 (Provider·Message Table)](provider-message-table.md) 을 봅니다.

## 도구

- libevtx: 형식 명세와 함께 공개된 라이브러리입니다. 헤더·청크·레코드를 파일에서 직접 읽습니다.
- wevtutil: Windows 명령줄 도구입니다. 명세에는 일부 버전이 내보낸 파일의 헤더 시각을 잘못 쓴 사례가 있습니다.
- 이벤트 뷰어: 살아 있는 시스템이나 사본 파일을 열어 결과를 견줘 볼 때 씁니다.
- 한 도구의 결과만 믿지 않습니다. 헥스로 본 헤더 값과 도구 결과를 [도구 결과 교차 검증](../../../03-techniques/reporting/tool-validation.md) 의 방식으로 비교합니다.
