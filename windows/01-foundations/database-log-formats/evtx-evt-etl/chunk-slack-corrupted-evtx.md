# 파일 안에 남은 지운·손상 레코드 (Chunk Slack·Corrupted EVTX)

## 한 줄 요약

EVTX 청크의 빈 공간 (Chunk Slack) 에는 정상 레코드 목록에서 빠진 옛 레코드가 남을 수 있고, 손상된 파일은 도구마다 읽어 내는 건수가 다릅니다. 레코드 서명, 크기 사본, 시각, 이진 XML 머리를 함께 봐야 진짜 레코드를 골라낼 수 있으며, 되살린 레코드를 XML 로 풀 때는 템플릿이 맞는지도 확인합니다.

이 페이지는 [이벤트 로그 형식 (EVTX·EVT·ETL)](index.md) 의 하위 주제입니다. 청크와 레코드의 기본 구조는 [EVTX 파일 구조 (File Header·Chunk·Record)](file-header-chunk-record.md) 에 있습니다. 템플릿은 [이진 XML 해석 (Binary XML·Template)](binary-xml-template.md) 에 있습니다. 옛 EVT 형식의 손상 사례는 [구형 EVT 형식 (Windows XP·2003)](windows-xp-2003.md) 에서 다룹니다.

## 이 내용이 쓰이는 때

- 필요한 시간대의 레코드가 정상 목록에 없을 때 씁니다. 로그가 한 바퀴 돌아 덮였거나 지워졌을 수 있습니다. 로그를 지운 흔적은 [이벤트 로그 삭제](../../../02-artifacts/event-logs/1102-104.md) 에서, 증거를 없애려 한 정황은 [증거를 없애려 했나](../../../04-scenarios/activity/anti-forensics/index.md) 에서 다룹니다.
- dirty 파일이나 쓰는 중에 복사한 파일을 읽을 때 씁니다.
- 도구마다 이벤트 건수가 다를 때 씁니다.
- 디스크 비할당 영역이나 메모리 이미지에서 EVTX 조각을 찾을 때 씁니다. [삭제 데이터 복구](../../../03-techniques/analysis/data-recovery/index.md) 와 [메모리 분석](../../../03-techniques/analysis/memory-forensics/index.md) 을 함께 봅니다.

## 구조 — 레코드가 남는 자리

> 그림 자리: 청크 하나에서 빈 공간 오프셋 앞의 살아 있는 레코드들과, 그 뒤 빈 공간에 남은 옛 레코드·0 덩어리를 색으로 나눠 보여 주는 그림

| 자리 | 모습 | 다루는 곳 |
|---|---|---|
| 청크 빈 공간 | 빈 공간 오프셋 뒤에 레코드 서명 `**\0\0` 이 있는 바이트 | 아래 "읽는 법" |
| 헤더가 말한 마지막 청크 뒤 | dirty 파일에서 헤더의 청크 수가 실제보다 적은 경우 | 아래 "libevtx 명세의 손상 사례" |
| 손상 구간 뒤 | 0 덩어리 뒤에 이어지는 레코드·청크 | 같은 절 |
| 파일 밖 | 비할당 영역·메모리 이미지의 청크·레코드 조각 | 아래 "템플릿을 잃은 레코드" |

빈 공간의 레코드는 두 가지입니다.

- 정상 목록에서 사라진 레코드: 식별자가 파일의 살아 있는 레코드에 없습니다.
- 지금 있는 레코드의 예전 모습: 식별자가 살아 있는 레코드와 같습니다. 빈 공간에는 이런 사본이 자주 들어 있습니다[1].

## 읽는 법

### 절차

1. 원본의 해시를 구하고 사본에서 작업합니다.
2. 정상 레코드를 모두 읽고 식별자 목록을 만듭니다.
3. 청크마다 빈 공간 오프셋부터 청크 끝까지 레코드 서명 `2A 2A 00 00` 을 찾습니다.
4. 후보마다 크기와 끝 4바이트의 크기 사본이 같은지 봅니다.
5. 이진 XML 머리가 다음 셋 가운데 하나인지 봅니다[1]. `0x0a`(PI, 5바이트 이상), `0x0f 0x01 0x01 0x00`(조각 헤더, 4바이트 이상), `0x00`(이진 XML 없음) 입니다.
6. 기록 시각이 말이 되는 범위인지 봅니다. 아래 사례의 범위는 2000~2027년입니다.
7. 식별자를 2단계 목록과 비교합니다. 같으면 옛 사본이고, 없으면 사라진 레코드입니다. libevtx 는 식별자가 같은 레코드를 무시합니다.
8. 템플릿을 확인합니다. 인스턴스가 가리키는 정의 자리의 GUID 앞 4바이트가 템플릿 식별자와 같아야 합니다. 다르면 그 자리가 다른 데이터로 덮인 것으로 봅니다.
9. 결과에는 "되살린 레코드" 표시와 파일 오프셋을 붙여 정상 레코드와 나눕니다.

### 헥스로 한 번 따라가기

아래는 명세로 만든 예시입니다. 실제 검체에서 떠낸 바이트가 아닙니다. `??` 는 이 설명에 쓰지 않는 바이트입니다. 청크는 파일 오프셋 0x1000 에서 시작하고, 빈 공간 오프셋은 0xE000 이라고 가정합니다.

```
오프셋    00 01 02 03 04 05 06 07  08 09 0A 0B 0C 0D 0E 0F
00001030  00 E0 00 00 ?? ?? ?? ??  ?? ?? ?? ?? ?? ?? ?? ??
  ...
0000F100  2A 2A 00 00 50 01 00 00  ?? ?? ?? ?? ?? ?? ?? ??
0000F110  ?? ?? ?? ?? ?? ?? ?? ??  0F 01 01 00 0C 01 ?? ??
  ...
0000F240  ?? ?? ?? ?? ?? ?? ?? ??  ?? ?? ?? ?? 50 01 00 00
```

- 0x1030 의 빈 공간 오프셋이 0xE000 이므로 빈 공간은 파일 오프셋 0xF000 부터입니다.
- 0xF100 에 레코드 서명 `2A 2A 00 00` 이 있습니다. 빈 공간 안이므로 정상 목록 밖입니다.
- 0xF104 의 크기는 0x150(336) 입니다. 크기 사본은 0xF100 + 0x150 − 4 = 0xF24C 에 있고, 값이 같습니다.
- 0xF108 의 8바이트가 식별자입니다. 정상 레코드 목록에 있는지 봅니다.
- 0xF110 의 8바이트가 기록 시각입니다. 범위 안인지 봅니다.
- 0xF118 이 `0F 01 01 00` 으로 시작합니다. 조각 헤더이므로 5단계를 통과합니다.
- 0xF11C 의 `0C` 는 템플릿 인스턴스입니다. 뒤의 정의 데이터 오프셋을 따라가 템플릿 식별자를 맞춰 봅니다.

### Windows 11 25H2 의 빈 공간 사례

쓰는 중인 로그 225개를 센 결과입니다. 로그가 계속 쓰이는 동안에는 셀 때마다 숫자가 조금씩 달라집니다.

- 판정 조건은 빈 공간 오프셋 뒤의 `**\0\0` 서명, 크기 = 크기 사본, 기록 시각 2000~2027년, 본문 `0f 01 01 00` 시작이었습니다.
- 225개 가운데 58개 파일의 빈 공간에서 조건에 맞는 레코드가 나왔고, 두 번 세어 2,923개와 3,018개였습니다.
- 첫 번째 셈의 2,923개 가운데 2,289개는 식별자가 파일의 살아 있는 레코드에 없어서 정상 목록에서는 사라진 레코드였습니다.
- Microsoft-Windows-Known Folders API Service.evtx 는 살아 있는 식별자가 7,665~9,699 였습니다. 빈 공간 레코드 132개는 식별자가 7,533~7,664 였고, 날짜는 2026-08-31~09-02 였습니다. 바로 앞 번호들이 빈 공간에만 남아 있었습니다.
- Microsoft-Windows-PowerShell%4Operational.evtx 는 빈 공간 레코드 대부분이 다른 청크에 살아 있는 식별자와 같았습니다. 예전 모습의 사본입니다.
- 시각과 본문 검사를 빼고 서명과 크기만 보면 1617년·7338년 같은 엉뚱한 시각의 가짜 일치가 섞였습니다.
- 빈 공간 레코드 3,018개의 템플릿 참조는 이랬습니다.
  - 5개는 템플릿 정의를 스스로 담고 있었습니다.
  - 2,762개는 가리킨 자리의 템플릿 식별자가 맞았습니다.
  - 251개(약 8%)는 맞지 않았습니다. 그 자리가 다른 데이터로 덮인 것으로 보입니다.
- 같은 검사에서 살아 있는 레코드 333,872개는 모두 맞았습니다.

### 템플릿을 잃은 레코드

레코드에는 템플릿 참조와 치환 값 목록이 들어 있어서, XML 로 바꾸려면 템플릿을 찾아 자리 표시자를 채웁니다. 템플릿이 망가지면 그 64KB 청크 안의 많은 레코드를 되살릴 수 없지만, 치환 값 배열은 남아 있을 수 있습니다.

- [프로세스 생성](../../../02-artifacts/event-logs/4688.md) 이나 [로그온](../../../02-artifacts/event-logs/logon-events/index.md) 같은 흔한 이벤트는 템플릿이 거의 바뀌지 않습니다. 그래서 다른 청크의 템플릿을 빌려 다시 만들 수 있습니다.

EVTXtract 는 디스크 이미지의 비할당 영역이나 메모리 이미지 같은 원시 데이터에서 EVTX 조각을 되살립니다. 순서는 다음과 같습니다.

1. `ElfChnk` 서명을 찾습니다. 헤더 크기가 0x80~0x200 인지, 체크섬이 맞는지 확인합니다.
2. 정상 청크에서 레코드를 뽑습니다.
3. 정상 청크에서 템플릿을 뽑습니다.
4. 레코드 서명을 찾습니다. 헤더 값·시각·치환 값을 풀고, 이벤트 ID 등을 뽑습니다.
5. 옛 템플릿과 치환 값으로 레코드를 다시 만듭니다.

끝내 템플릿을 찾지 못한 레코드는 오프셋, 이벤트 ID, 치환 값(번호·종류·값)만 적어 냅니다.

## 포렌식에서 중요한 점

### libevtx 명세의 손상 사례

**헤더 값이 이상한 파일**

체크섬은 맞는데 첫 청크 번호 206 이 마지막 청크 번호 205 보다 큰 파일 사례가 있습니다(청크 1,024개)[1]. 한 바퀴 돈 정상 로그도 이 모양이므로([EVTX 파일 구조](file-header-chunk-record.md) 의 "한 바퀴 돈 로그") 이 모양만으로 손상이라고 보지 않습니다.

dirty 파일에서는 헤더의 청크 수가 실제보다 적은 경우가 있고, 이벤트 뷰어는 이런 파일을 "고쳐서" 읽는 것 같습니다. libevtx(20130713 판)는 헤더가 말한 마지막 청크 뒤로도 청크를 계속 찾으며, 거기서 나온 레코드는 "되살린 레코드" 로 표시하지 않습니다.
- 헤더보다 칸이 많아도 남는 칸이 모두 0 일 수 있습니다. Windows 11 25H2 의 System.evtx 가 그랬습니다([EVTX 파일 구조](file-header-chunk-record.md) 의 "헤더 값과 실제 파일 비교").

**레코드·청크 손상**

레코드 손상은 청크 중간에서 레코드 바로 뒤로 큰 0 덩어리가 나오거나 크기와 크기 사본이 다른 모습이며, 청크 나머지를 훑어 찾은 레코드는 "되살린 것" 으로 봅니다.
청크 손상은 0 덩어리가 다음 청크 헤더 자리까지 이어지는 모습이라서 정상 청크 헤더나 파일 끝이 나올 때까지 훑습니다.
컴퓨터 이름이 빈 레코드도 형식상 있을 수 있으므로 이것만으로 손상이라고 보지 않습니다.

**명세에 실린 두 사례**

| | 사례 1 | 사례 2 |
|---|---|---|
| 파일 | dirty Security.evtx | dirty Security.evtx |
| 이벤트 뷰어 표시 | 4,001건 | 102,019건 |
| wevtutil | 손상을 알리지 않음 | `qe` 가 19,660건에서 "Failed to read events. The event log file is corrupted." 로 멈춤 |
| 손상 모습 | 청크 하나의 레코드 CRC 불일치. 레코드 크기 664, 크기 사본 1,694,526,976 | 크기 사본 0. 청크 헤더 자리가 0 |
| 끝까지 훑은 결과 | 청크 나머지에서 되살릴 수 있는 레코드 5개 | 98,927건과 되살린 1,043건 |

- 사례 1 에서 레코드 번호가 끊긴 것은 레코드를 쓰는 도중에 파일을 복사했기 때문으로 보입니다.
- 정상 파일에서도 이벤트 뷰어의 "모든 이벤트를 다른 이름으로 저장(XML)" 결과가 화면 건수보다 적었습니다(20,568건 → 4,168건).
- wevtutil 로 내보낸 파일의 헤더 시각 문제는 [EVTX 파일 구조](file-header-chunk-record.md) 의 "시각" 을 봅니다.

### 원본 다루기

원본을 열면 바뀔 수 있으므로 늘 사본에서 작업합니다. [ESE 데이터베이스](../extensible-storage-engine/index.md) 도 마찬가지입니다.
손상된 ESE 데이터베이스는 읽는 방식에 따라 결과 행 수가 달라지고, EVTX 도 위 사례처럼 도구마다 건수가 다르므로 두 가지 이상의 방식으로 읽어 비교합니다. 비교 방법은 [도구 결과 교차 검증](../../../03-techniques/reporting/tool-validation.md) 에 있습니다.

### 증거로서 의미

**증명하는 것**

- 이 로그 파일에 한때 이런 식별자·기록 시각·값의 레코드가 쓰였다는 것.
- 사라진 레코드라면, 그 식별자가 지금 정상 목록에 없다는 것.

**증명하지 못하는 것**

- 언제 정상 목록에서 빠졌는지. 빠진 때를 적는 칸은 없습니다.
- 왜 빠졌는지. 순환 덮어쓰기인지 로그 지우기인지 레코드만으로는 가를 수 없습니다.
- 값이 온전한지. 템플릿 자리가 덮였을 수 있습니다(위 사례에서 약 8%).
- 빠진 레코드가 더는 없다는 것. 도구가 0건을 내도 빈 공간을 훑지 않았거나 이미 덮였을 수 있습니다.

보고서에는 기록이 말하는 만큼만 씁니다. 예: "System.evtx 의 한 청크 빈 공간(파일 오프셋 X)에서 식별자 N, 기록 시각 T 의 레코드가 나왔다. 이 식별자는 파일의 정상 레코드 목록에 없다. 이 레코드가 언제, 어떤 이유로 목록에서 빠졌는지는 파일에 기록이 없다."

## 함정

- 서명과 크기만으로 판정하면 가짜 일치가 섞입니다. 시각과 이진 XML 머리까지 봅니다.
- 식별자가 같은 빈 공간 레코드는 사라진 레코드가 아니라 옛 사본입니다. 건수를 셀 때 빼거나 따로 셉니다.
- 템플릿 식별자가 맞지 않는 레코드를 그대로 풀면 엉뚱한 XML 이 나옵니다. 치환 값만 적거나, 같은 템플릿을 다른 청크에서 찾습니다.
- 첫 청크 번호가 마지막 청크 번호보다 크다고 손상은 아닙니다.
- 헤더의 청크 수 뒤에도 청크가 있을 수 있습니다. 파일 끝까지 훑습니다.
- 도구마다 건수가 다릅니다. 위 두 사례에서 wevtutil 은 한 번은 손상을 알렸고 한 번은 알리지 않았습니다.
- 로그를 지운 뒤 옛 청크가 파일에 남는지는 공개된 분석 자료가 없어 검체로 확인해야 합니다.

## 도구

- libevtx: 청크 빈 공간을 훑어 레코드를 되살립니다. 20130713 판은 헤더가 말한 마지막 청크 뒤도 찾습니다.
- EVTXtract: 원시 데이터에서 청크와 레코드를 찾고, 다른 청크의 템플릿으로 레코드를 다시 만듭니다.
- 이벤트 뷰어·wevtutil: 비교 기준으로 씁니다. 손상 파일에서 둘의 건수가 달랐던 사례가 위에 있습니다.
