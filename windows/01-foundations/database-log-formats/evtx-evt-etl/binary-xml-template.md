# 이진 XML 해석 (Binary XML·Template)

## 한 줄 요약

EVTX 레코드 본문은 글자로 쓴 XML 이 아니라 토큰으로 줄인 이진 XML (Binary XML) 입니다. 요소 이름과 이벤트의 틀인 템플릿 (Template) 은 청크 안에 한 번만 들어 있습니다. 레코드는 그 자리를 가리키고 값만 담습니다. 그래서 레코드를 XML 로 되살리려면 같은 청크의 이름과 템플릿이 함께 있어야 합니다.

이 페이지는 [이벤트 로그 형식 (EVTX·EVT·ETL)](index.md) 의 하위 주제입니다. 레코드가 파일 어디에 있는지는 [EVTX 파일 구조 (File Header·Chunk·Record)](file-header-chunk-record.md) 에서 다룹니다.

## 이 형식을 쓰는 곳

- EVTX 이벤트 레코드의 본문입니다. 레코드 시작에서 24바이트 뒤부터입니다.
- 메시지 파일의 WEVT_TEMPLATE 리소스에도 이진 XML 로 된 템플릿이 있습니다. 모양이 조금 다릅니다(아래 "함정"). 리소스 자체는 [공급자와 메시지 파일 (Provider·Message Table)](provider-message-table.md) 에서 다룹니다.
- libevtx 명세는 MS-EVEN6(EventLog Remoting Protocol 6.0) 을 원 명세로 따릅니다.

## 구조

> 그림 자리: 청크 앞쪽의 템플릿 정의 하나를 여러 레코드의 템플릿 인스턴스가 화살표로 가리키고, 각 레코드는 값 목록만 담는 모습

### 문서와 조각

- 이진 XML 문서는 처리 지시 (Processing Instruction, PI) 0~1개, 조각 (Fragment) 0개 이상, PI 0~1개, 파일 끝 토큰 순서로 놓입니다.
- 조각은 조각 헤더 뒤에 요소 하나나 템플릿 인스턴스 하나가 오는 모양입니다.
- 조각 헤더는 4바이트입니다. `0x0f`(토큰), `0x01`(주 버전), `0x01`(부 버전), `0x00`(플래그) 순서입니다.
- 확인 PC 의 System.evtx 첫 레코드는 24바이트 뒤가 `0f 01 01 00 0c …` 로 시작했습니다. 조각 헤더 바로 뒤에 템플릿 인스턴스가 온 모양입니다(확인 범위: Windows 11 25H2 PC 한 대).

### 토큰

| 토큰 | 뜻 |
|---|---|
| `0x00` | 파일 끝 (EOF) |
| `0x01` / `0x41` | 요소 시작 태그 열기 (`<Event`). `0x41` 은 속성 목록이 뒤따른다는 뜻입니다 |
| `0x02` | 시작 태그 닫기 (`>`) |
| `0x03` | 빈 요소 닫기 (`/>`) |
| `0x04` | 끝 태그 (`</Event>`) |
| `0x05` / `0x45` | 값 |
| `0x06` / `0x46` | 속성 |
| `0x07` / `0x47` | CDATA |
| `0x08` / `0x48` | 문자 참조 |
| `0x09` / `0x49` | 엔티티 참조 |
| `0x0a` | PI 대상 |
| `0x0b` | PI 데이터 |
| `0x0c` | 템플릿 인스턴스 |
| `0x0d` | 일반 치환 |
| `0x0e` | 선택 치환 |
| `0x0f` | 조각 헤더 |

`0x40` 비트는 "뒤에 데이터가 더 있다" 는 표시입니다.

### 요소·이름·속성

요소 시작은 아래 순서입니다.

| 크기 | 내용 |
|---|---|
| 1 | 토큰 `0x01` 또는 `0x41` |
| 2 | 의존 식별자. `0xffff` 면 없음입니다. 명세는 이 칸을 선택 항목으로 적습니다 |
| 4 | 데이터 크기 |
| 4 | 이름 오프셋. 청크 시작 기준입니다 |
| 가변 | 속성 목록(`0x41` 일 때) |

- 이름은 알 수 없는 4바이트, 이름 해시 2바이트, 글자 수 2바이트, UTF-16LE 문자열 순서입니다. 문자열 끝에는 끝 문자가 붙습니다.
- 이름은 청크 시작 기준 오프셋으로 가리킵니다. 그래서 한 청크에서 한 번 저장한 이름을 여러 요소가 다시 씁니다.
- 요소 이름이 속성 목록 앞에 바로 놓이는 경우도 있습니다.
- 속성 목록은 크기 4바이트 뒤에 속성이 이어지는 모양입니다.
- 속성 토큰 `0x46` 은 뒤에 속성이 더 있다는 뜻입니다. `0x06` 은 마지막 속성입니다.
- 값 텍스트는 토큰 `0x05`·`0x45`, 값 종류 `0x01`(문자열), 글자 수 2바이트, UTF-16LE 문자열 순서입니다. 이 문자열에는 끝 문자가 없습니다.
- 엔티티 참조는 `lt`·`gt`·`amp`·`quot`·`apos` 를 쓰는 것으로 봅니다.

### 템플릿

템플릿 인스턴스는 토큰 `0x0c`, 템플릿 정의, 템플릿 인스턴스 데이터 순서입니다.

**템플릿 정의**

| 크기 | 내용 |
|---|---|
| 1 | 알 수 없음. `0x01` 이 보입니다 |
| 4 | 알 수 없음. 템플릿 식별자로 추정합니다 |
| 4 | 정의 데이터 오프셋. 청크 안의 위치입니다 |
| 4 | 다음 정의 오프셋. 없으면 0 입니다 |
| 16 | 템플릿 GUID |
| 4 | 데이터 크기 |
| 가변 | 조각 헤더, 요소, EOF |

- 정의 데이터 오프셋은 바로 뒤를 가리키거나, 같은 청크의 앞쪽을 가리킵니다.
- 앞쪽을 가리키면 정의는 그 자리에 있습니다. 이 레코드에는 정의가 들어 있지 않습니다.
- 정의 데이터 오프셋이 가리키는 자리에는 다음 정의 오프셋, GUID, 데이터 크기, 본문이 차례로 있습니다.

확인 PC 에서 본 모습입니다(확인 범위: Windows 11 25H2 PC 한 대, 쓰는 중인 로그 225개).

- 인스턴스의 4바이트 템플릿 식별자는 "정의 데이터 오프셋 + 4" 자리의 값, 곧 GUID 앞 4바이트와 같았습니다. 살아 있는 레코드 333,872개가 모두 그랬습니다.
- 템플릿 정의를 바로 뒤에 담은 레코드는 5,270개였습니다. 나머지 대부분은 같은 청크 앞쪽의 정의를 가리켰습니다.
- 청크 하나에 쓰인 서로 다른 템플릿은 평균 1.4개였습니다(청크 3,870개).

**템플릿 인스턴스 데이터**

| 크기 | 내용 |
|---|---|
| 4 | 값 개수 |
| 4 × 값 개수 | 값 설명자. 하나에 크기 2바이트, 값 종류 1바이트, 빈 값 1바이트 |
| 가변 | 값 데이터. 설명자 순서대로 이어집니다 |

**치환 토큰** (템플릿 정의 안에 있습니다)

| 토큰 | 모양 | 동작 |
|---|---|---|
| `0x0d` 일반 치환 | 토큰 1바이트, 치환 번호 2바이트(0부터), 값 종류 1바이트 | 번호에 맞는 값을 그 자리에 넣습니다 |
| `0x0e` 선택 치환 | 같은 모양 | 대응 값의 종류가 NULL(`0x00`) 이면 그 요소를 만들지 않습니다 |

- 값 종류에 배열 비트(`0x80`)가 켜져 있으면 원소마다 치환을 되풀이합니다. 배열 크기가 0 이면 빈 요소 하나를 만듭니다.
- 값 종류가 `0x21`(이진 XML) 이면 값 안에 요소 시작·조각·템플릿 인스턴스가 다시 들어 있습니다. 같은 방법으로 한 번 더 풉니다.

### 값 종류

| 값 | 종류 |
|---|---|
| `0x00` | NULL |
| `0x01` | UTF-16 문자열 |
| `0x02` | ANSI 문자열 |
| `0x03` ~ `0x0a` | 부호 있는·없는 8·16·32·64비트 정수 |
| `0x0b` · `0x0c` | 32·64비트 실수 |
| `0x0d` | 불리언 (32비트) |
| `0x0e` | 이진 |
| `0x0f` | GUID |
| `0x10` | size_t. 32비트 또는 64비트이고, `0x14`·`0x15` 와 짝을 이룹니다 |
| `0x11` | FILETIME |
| `0x12` | SYSTEMTIME (16바이트) |
| `0x13` | SID |
| `0x14` | 16진으로 보여 주는 32비트 정수 |
| `0x15` | 16진으로 보여 주는 64비트 정수 |
| `0x21` | 이진 XML |
| `0x80` 비트 | 배열. `0x81` 은 끝 문자로 나눈 UTF-16 문자열 배열입니다 |

- SYSTEMTIME 은 연·월·요일·일·시·분·초·밀리초가 2바이트씩 들어 있습니다.
- FILETIME 과 SYSTEMTIME 을 푸는 법은 [시각 값 형식](../../value-decoding/filetime-unix-webkit-dos-ole.md) 에 있습니다. GUID 와 SID 는 [윈도 식별자 형식](../../value-decoding/sid-guid-clsid-known-folder-id.md) 을 봅니다.

### 이벤트 데이터 모양

- 문자열과 이진 값은 보통 `EventData` 아래 `Data` 요소에 들어갑니다. `Data` 에 `Name` 속성이 붙을 수 있습니다.
- 일부 이벤트는 `EventData` 대신 `UserData` 아래에 공급자가 정한 XML 로 값을 넣습니다.
- `ProcessingErrorData`(`ErrorCode`·`DataItemName`·`EventPayload`) 는 `EventData` 의 변형입니다.
- `Binary` 요소 값은 16진 문자열로 보입니다.
- 템플릿 정의의 치환 토큰은 레코드의 치환 값과 번호로 짝을 이룹니다. libevtx 는 20130208 판부터 이 방식으로 이벤트 문자열을 뽑습니다.
- 이렇게 뽑은 문자열이 설명 문장의 `%1`·`%2` 자리에 들어갑니다. 문장을 만드는 법은 [공급자와 메시지 파일](provider-message-table.md) 에 있습니다.

### 특수 문자 처리

- 문자열 속 `<` `>` `&` `"` `'` 는 XML 로 쓸 때 `&lt;` `&gt;` `&amp;` `&quot;` `&apos;` 로 바꿔야 합니다.
- 문자 참조나 엔티티 참조로 저장된 것은 바꾸지 않습니다.
- 이벤트 뷰어는 XML 보기에서는 이스케이프하지 않습니다. XML 로 내보낼 때는 이스케이프합니다.

## 읽는 법

1. 레코드 24 오프셋에서 조각 헤더 `0F 01 01 00` 을 확인합니다.
2. 다음 토큰을 봅니다. `0x0c` 면 템플릿 인스턴스입니다. `0x01`·`0x41` 이면 요소가 바로 옵니다.
3. 템플릿 인스턴스면 템플릿 식별자와 정의 데이터 오프셋을 읽습니다.
4. 정의 데이터 오프셋이 바로 뒤 위치와 같으면 정의가 이 자리에 들어 있습니다. 정의를 다 읽은 뒤에 인스턴스 데이터가 옵니다.
5. 오프셋이 앞쪽을 가리키면 그 자리에서 정의를 읽습니다. 인스턴스 데이터는 정의 데이터 오프셋 칸 바로 뒤에서 시작합니다.
6. 정의 자리의 GUID 앞 4바이트가 인스턴스의 템플릿 식별자와 같은지 확인합니다. 다르면 그 자리가 덮였을 수 있습니다.
7. 인스턴스 데이터에서 값 개수, 설명자, 값을 차례로 읽습니다.
8. 정의의 토큰을 따라가며 XML 을 씁니다. 요소 이름은 이름 오프셋(청크 시작 기준)에서 읽습니다. 치환 토큰을 만나면 번호에 맞는 값을 종류대로 풀어 넣습니다.
9. `0x21` 값은 같은 방법으로 다시 풉니다.
10. 글로 내보낼 때는 특수 문자를 이스케이프합니다.

### 헥스로 한 번 따라가기

아래는 명세로 만든 예시입니다. 실제 검체에서 떠낸 바이트가 아닙니다. 템플릿 식별자 `A1 B2 C3 D4`, 오프셋, 값은 설명을 위해 정했습니다. `??` 는 이 설명에 쓰지 않는 바이트입니다. 오프셋은 모두 청크 시작 기준입니다.

**① 템플릿 정의를 담은 레코드** (청크 0x0200 의 레코드, 본문은 0x0218)

```
오프셋    00 01 02 03 04 05 06 07  08 09 0A 0B 0C 0D 0E 0F
00000210                           0F 01 01 00 0C 01 A1 B2
00000220  C3 D4 26 02 00 00 00 00  00 00 A1 B2 C3 D4 ?? ??
00000230  ?? ?? ?? ?? ?? ?? ?? ??  ?? ?? ?? ?? ?? ?? 0F 01
00000240  01 00 ...
```

- 0x218 `0F 01 01 00` 은 조각 헤더입니다.
- 0x21C `0C` 는 템플릿 인스턴스 토큰입니다. 0x21D `01` 은 알 수 없는 1바이트입니다.
- 0x21E `A1 B2 C3 D4` 는 템플릿 식별자입니다.
- 0x222 `26 02 00 00` 은 정의 데이터 오프셋 0x226 입니다. 바로 뒤 위치이므로 정의가 여기 들어 있습니다.
- 0x226 은 다음 정의 오프셋 0 입니다.
- 0x22A 부터 16바이트가 템플릿 GUID 입니다. 앞 4바이트가 템플릿 식별자와 같습니다.
- 0x23A 는 데이터 크기입니다. 0x23E 부터 정의 본문(조각 헤더·요소·EOF)이 이어집니다.

정의 본문 안에 아래 치환 토큰 두 개가 있다고 가정합니다.

```
0D 00 00 01    일반 치환: 0번 값, 종류 0x01 (UTF-16 문자열)
0E 01 00 14    선택 치환: 1번 값, 종류 0x14 (16진 표시 32비트)
```

**② 앞쪽 정의를 빌려 쓰는 레코드** (청크 0x1000 의 레코드, 본문은 0x1018)

```
오프셋    00 01 02 03 04 05 06 07  08 09 0A 0B 0C 0D 0E 0F
00001010                           0F 01 01 00 0C 01 A1 B2
00001020  C3 D4 26 02 00 00 02 00  00 00 08 00 01 00 04 00
00001030  14 00 74 00 65 00 73 00  74 00 05 00 00 00
```

- 0x1022 의 정의 데이터 오프셋은 0x226 입니다. 바로 뒤(0x1026)가 아니므로 ① 의 정의를 빌려 씁니다.
- 0x226 + 4 = 0x22A 의 GUID 앞 4바이트가 이 레코드의 식별자 `A1 B2 C3 D4` 와 같습니다.
- 인스턴스 데이터는 0x1026 에서 시작합니다. 값 개수는 2 입니다.
- 0x102A `08 00 01 00` 은 첫 값의 설명자입니다. 크기 8바이트, 종류 0x01 입니다.
- 0x102E `04 00 14 00` 은 둘째 값의 설명자입니다. 크기 4바이트, 종류 0x14 입니다.
- 0x1032 의 8바이트는 UTF-16LE 문자열 `test` 입니다.
- 0x103A 의 4바이트는 정수 5 입니다. 종류가 0x14 이므로 16진으로 보여 줍니다.

정의의 0번 치환 자리에는 `test` 가, 1번 치환 자리에는 5 가 16진으로 들어갑니다. 1번 값의 종류가 NULL 이었다면 선택 치환이므로 그 요소는 생기지 않습니다.

## 포렌식에서 중요한 점

- 레코드 하나만으로는 XML 을 만들 수 없습니다. 이름과 템플릿 정의가 같은 청크의 다른 자리에 있습니다. 확인 PC 에서는 살아 있는 레코드 대부분이 앞쪽 정의를 빌려 썼습니다.
- 템플릿 정의가 있는 자리가 망가지면, 그 정의를 빌려 쓰는 레코드가 함께 풀리지 않습니다. 대처법은 [파일 안에 남은 지운·손상 레코드 (Chunk Slack·Corrupted EVTX)](chunk-slack-corrupted-evtx.md) 에 있습니다.
- 인스턴스 데이터에는 값마다 크기와 종류가 붙어 있습니다. 템플릿이 없어도 값 목록은 읽을 수 있습니다.
- 이름 오프셋과 정의 데이터 오프셋은 청크 시작 기준입니다. 청크 시작 위치를 잘못 잡으면 이름과 템플릿을 모두 잘못 읽습니다.

## 함정

- 이름 오프셋과 정의 데이터 오프셋을 레코드 시작 기준으로 계산하면 틀립니다.
- 이름 문자열에는 끝 문자가 붙습니다. 값 텍스트에는 붙지 않습니다.
- `0x10`(size_t) 은 32비트일 수도 64비트일 수도 있습니다. 폭은 설명자의 크기 칸으로 판단합니다.
- SYSTEMTIME(`0x12`) 은 FILETIME 과 모양이 다릅니다. 8바이트 정수로 읽으면 틀립니다.
- XML 에 요소가 없다고 해서 템플릿에 그 요소가 없던 것은 아닙니다. 선택 치환의 값이 NULL 이면 요소가 생기지 않습니다.
- 이벤트 뷰어의 XML 보기와 XML 내보내기는 이스케이프가 다릅니다. 도구끼리 문자열을 비교할 때 이 차이부터 맞춥니다.
- WEVT_TEMPLATE 안의 이진 XML 은 EVTX 와 조금 다릅니다. 이름 오프셋을 쓰지 않고, 이름 앞 4바이트가 없습니다. 템플릿 항목은 템플릿 밖에 따로 있습니다. EVTX 해석 코드를 그대로 쓰면 틀립니다.

## 도구

- libevtx: 이진 XML 과 템플릿을 직접 풉니다. 형식 명세도 함께 공개했습니다.
- 이벤트 뷰어: XML 보기와 XML 내보내기로 결과를 견줘 볼 수 있습니다.
- EVTXtract: 템플릿을 잃은 레코드를 다른 청크의 템플릿으로 다시 만듭니다.
- 도구마다 결과가 다르면 [도구 결과 교차 검증](../../../03-techniques/reporting/tool-validation.md) 의 방식으로 비교합니다.
