# 파일 안에 남은 지운 레코드 (Deleted Records)

ESE 데이터베이스에서 지운 행은 곧바로 사라지지 않고, 지움 표시, 페이지 안 빈 공간, B-트리에서 빠진 페이지의 모습으로 파일 안에 한동안 남습니다.

이 페이지는 [ESE 데이터베이스](index.md)의 하위 주제입니다. 지운 행이 남는 자리, 찾는 방법, 믿을 수 있는 범위를 다룹니다. 페이지·태그·카탈로그의 기본 구조는 [파일 구조 (Page·B+Tree·Catalog)](page-b-tree-catalog.md)에 있습니다. SQLite 에서 같은 주제는 [파일 안에 남은 지운 레코드 (Freelist·Freeblock)](../sqlite/freelist-freeblock.md)에서 다룹니다.

## 이 내용이 쓰이는 아티팩트

지운 행이 조사에서 뜻하는 바는 DB 마다 다릅니다.

| 파일 | 행이 지워지는 때 | 자세히 |
|---|---|---|
| WebCacheV01.dat | 사용자가 브라우저 방문 기록을 지울 때 | [웹캐시 DB (WebCacheV01.dat)](../../../02-artifacts/browsers/ie-edgehtml/webcachev01-dat.md) |
| Windows.edb | 색인에 들어 있던 파일을 지울 때 | [지운 파일·옛 파일 흔적 찾기](../../../02-artifacts/file-folder-usage/windows-search/deleted-file-traces.md) |
| SRUDB.dat 등 그 밖의 ESE 파일 | 앱이 행을 지울 때. 언제 지우는지는 앱마다 다릅니다 | [SRUM](../../../02-artifacts/execution/system-resource-usage-monitor/index.md) |

IE 방문 기록을 지운 뒤에도 WebCacheV01.dat 의 지운 행에서 웹 페이지 제목, HTTP 응답 헤더, 다운로드 정보를 되살릴 수 있습니다[6]. Windows Search 는 파일을 지우면 그 파일의 색인 행도 지웁니다[5]. 그 행은 DB 안 빈 공간에 남을 수 있습니다.

## 구조 — 지운 행이 남는 자리

### 행 하나가 지워지는 순서

Microsoft 가 공개한 ESE 소스 코드 기준의 순서는 다음과 같습니다[3]. 공개 소스는 Windows 에 들어 있는 esent.dll 과 판이 다를 수 있습니다.

1. 앱이 JetDelete 를 부르면 엔진은 행을 바로 빼지 않습니다. 그 행에 지움 표시(0x2)를 붙이고, 보통 버전 표시(0x1)도 함께 붙입니다.
2. 엔진은 이 변경을 버전 저장소 (Version Store) 에 적습니다. 진행 중인 다른 트랜잭션은 이 기록으로 지우기 전의 행을 봅니다.
3. 뒤에서 도는 정리 작업이 표시된 행을 페이지에서 실제로 뺍니다. 태그 배열에서 그 행의 태그를 없애고, 뒤쪽 태그를 한 칸씩 당겨 빈자리를 메웁니다.
4. 행이 쓰던 바이트는 빈 공간으로 셈만 바뀌고 그대로 남습니다.
5. 페이지를 다시 정리하거나 새 행을 넣을 때 그 바이트가 덮어써집니다.
6. 페이지가 비거나 옆 페이지와 합쳐지면 페이지 전체가 공간 트리 (Space Tree) 로 돌아갑니다. 테이블을 지우면 그 테이블의 페이지가 모두 돌아갑니다.

소스에는 4단계에서 지운 바이트를 다른 값으로 채우는 기능(런타임 스크러빙)도 있는데, Windows 구성 요소가 이 기능을 켜는지는 공개 문서가 없으므로 파일마다 빈 공간을 직접 보고 판단합니다.

> 그림 자리: 한 행이 "지움 표시 → 태그 삭제 → 빈 공간 → 덮어쓰기" 로 바뀌는 과정을 페이지 그림 네 장으로 보여 준다.

### 남는 자리 다섯 곳

| 자리 | 파일 안 모습 | 보통 파서에 보이나 | 언제까지 남나 |
|---|---|---|---|
| 지움 표시만 된 행 | 태그가 그대로 있고 태그 플래그 0x2 가 켜져 있음 | 안 보임 | 정리 작업이 돌 때까지 |
| 페이지 안 빈 공간 | 유효한 값 사이의 틈, 또는 데이터 끝과 태그 배열 사이 | 안 보임 | 페이지 재정리·새 행 삽입 전까지 |
| 남는 태그 자리 | 쓰는 태그 개수 밖에 남은 옛 4바이트 태그 | 안 보임 | 새 태그가 그 자리를 쓸 때까지 |
| B-트리에서 빠진 페이지 | 빈 페이지 플래그(0x0008)가 켜진 페이지, 공간 트리로 돌아간 페이지, 분할 뒤 옛 복사본 | 안 보임 | 그 페이지를 다시 쓸 때까지 |
| 지운 테이블 | 카탈로그 행은 지워지고 페이지 헤더의 FDP 개체 ID 는 남음 | 안 보임 | 그 페이지를 다시 쓸 때까지 |

Chivers 와 Hargreaves 의 실험에서 중간 번호의 행이 지워진 자리는 트리를 다시 맞출 때까지 다시 쓰이지 않았습니다[5]. 페이지를 나눌 때 옛 행 몇 개가 부모 페이지에 그대로 남기도 합니다[5].

### 페이지 헤더에서 볼 값

페이지 번호 N 의 파일 안 위치는 (N + 1) × 페이지 크기입니다. 아래 오프셋은 페이지 시작 기준이며, 작은 페이지와 큰 페이지에 공통입니다.

| 오프셋 | 크기 | 값 | 지운 행과 관련된 뜻 |
|---|---|---|---|
| 8 | 8 | 데이터베이스 시각 (dbtime) | 페이지를 마지막으로 바꾼 때의 카운터 값입니다. 시스템 시계 시각이 아닙니다 |
| 24 | 4 | FDP 개체 ID | 이 페이지가 속한 테이블·인덱스입니다. 카탈로그에서 지워져도 남습니다 |
| 28 | 2 | 빈 바이트 수 (cbFree) | 틈까지 합친 빈 공간입니다 |
| 30 | 2 | 커밋 안 된 빈 바이트 수 | 비었지만 롤백하면 다시 쓰일 바이트입니다 |
| 32 | 2 | 첫 빈 데이터 오프셋 (ibMicFree) | 헤더 끝 기준입니다. 여기부터 태그 배열 앞까지가 이어진 빈 공간입니다 |
| 34 | 2 | 쓰는 태그 개수 | 이 개수 밖의 태그 자리는 옛 값입니다. 형식 개정 0x122 부터는 위쪽 4비트를 빼고 읽습니다 |
| 36 | 4 | 페이지 플래그 | 0x0002 잎, 0x0008 빈 페이지, 0x0020 공간 트리, 0x0080 긴 값, 0x4000 스크럽됨 |

태그 플래그는 3비트입니다.

| 값 | 뜻 |
|---|---|
| 0x1 | 버전 표시. 버전 저장소에 걸린 변경이 있습니다. libyal 문서[4]는 이 비트의 뜻을 확정하지 않았고, 공개 소스[3]의 이름은 fNDVersion 입니다 |
| 0x2 | 지움 표시. 지운 행입니다. defunct 라고도 부릅니다[4] |
| 0x4 | 공통 키. 값 첫머리에 공통 키 길이 필드가 붙습니다 |

플래그가 놓이는 자리는 페이지 크기에 따라 다릅니다.

| 페이지 크기 | 페이지 헤더 | 태그 플래그 자리 |
|---|---|---|
| 8 KiB 이하 | 40 바이트 | 태그의 위치 필드(16비트) 위쪽 3비트 |
| 16·32 KiB (형식 개정 0x11, Windows 7 부터) | 80 바이트 | 값 첫 16비트의 위쪽 3비트 |

두 경우 모두 마스크는 0xE000 입니다. 지움 표시 0x2 는 그 16비트 값에서 0x4000 비트로 보입니다.

파일 헤더에서는 네 필드를 봅니다. 오프셋 232 는 형식 개정, 236 은 페이지 크기입니다. 오프셋 280 과 288 에는 스크러빙을 한 때의 데이터베이스 시각과 날짜·시각이 들어갑니다.

## 읽는 법

### 절차

1. 원본의 해시를 구하고 사본에서 작업합니다. 쓰기 모드로 열면 엔진이 파일을 바꿀 수 있습니다.
2. 트랜잭션 로그를 재생하기 전의 사본을 따로 남깁니다. 재생은 페이지를 다시 쓰므로 빈 공간의 내용이 바뀔 수 있습니다. 로그와 비정상 종료는 [트랜잭션 로그와 비정상 종료 상태](edb-log-dirty-shutdown.md)를 봅니다.
3. 파일 헤더에서 페이지 크기와 형식 개정을 읽습니다. 헤더 크기와 플래그 자리가 여기서 정해집니다.
4. 카탈로그(MSysObjects)에서 테이블 이름, FDP 개체 ID, 열 정의를 얻습니다. 지운 테이블은 카탈로그 페이지의 빈 공간을 같은 방법으로 뒤져 찾습니다.
5. B-트리를 따라가지 않고 파일의 모든 페이지를 차례로 읽습니다. 헤더의 FDP 개체 ID 로 페이지를 테이블별로 묶습니다. B-트리에서 빠진 페이지도 이 단계에서 잡힙니다.
6. 페이지마다 세 곳을 봅니다. 쓰는 태그 가운데 지움 표시가 켜진 값, 유효한 태그가 가리키지 않는 바이트, 쓰는 태그 개수 밖의 태그 자리입니다.
7. 빈 공간에서 레코드 머리 후보를 찾고 열 정의로 거릅니다. 레코드 머리는 마지막 고정 열 ID(1바이트), 마지막 가변 열 ID(1바이트), 가변 데이터 시작 오프셋(2바이트)으로 시작합니다. 두 ID 가 스키마의 열 범위 안에 있는지, 오프셋이 페이지 크기보다 작은지로 후보를 거릅니다[6].
8. 남아 있는 행과 키를 맞춰 봅니다. 같은 키의 행이 남아 있으면 지운 행이 아니라 고치기 전의 옛 판일 수 있습니다.

빈 공간에서 레코드를 골라내는 일반 기법은 [레코드 카빙 (Record Carving)](../../../03-techniques/analysis/data-recovery/record-carving.md)에 있습니다.

### 헥스로 한 번 따라가기

아래 바이트는 명세와 공개 소스로 만든 예시입니다. 실제 파일에서 나온 값이 아닙니다. 4 KiB 페이지(헤더 40바이트) 하나에서 행 D 가 지워지는 과정을 두 시점으로 나눠 보여 줍니다. 체크섬과 행 내용은 생략했습니다.

**① 지움 표시만 된 상태**

```
오프셋    00 01 02 03 04 05 06 07  08 09 0A 0B 0C 0D 0E 0F
00000010  1A 00 00 00 1C 00 00 00  21 00 00 00 24 01 00 00
00000020  A0 0E 05 00 02 28 00 00
  ...
00000FE0                                       78 03 28 0B
00000FF0  00 04 28 07 28 00 00 67  00 07 00 00 00 00 00 00
```

- 0x10 과 0x14 는 앞·뒤 잎 페이지 번호(0x1A·0x1C)입니다.
- 0x18 `21 00 00 00` 은 FDP 개체 ID 0x21 이며, 카탈로그에서 이 ID 의 테이블을 찾습니다.
- 0x1C `24 01` 은 빈 바이트 0x124(292)입니다.
- 0x20 `A0 0E` 는 첫 빈 데이터 오프셋 0xEA0 이고, 헤더 끝(0x28)에 더하면 파일 안 0xEC8 입니다.
- 0x22 `05 00` 은 태그 5개를 쓴다는 뜻입니다.
- 0x24 `02 28 00 00` 은 페이지 플래그 0x2802 로, 0x0002 가 켜져 있어 잎 페이지입니다. 0x0800 은 새 레코드 형식, 0x2000 은 새 체크섬 형식입니다[3].

태그는 페이지 끝에서 앞쪽으로 4바이트씩 놓입니다. 태그 하나의 앞 2바이트는 크기, 뒤 2바이트는 위치입니다.

| 태그 | 파일 위치 | 바이트 | 크기 | 위치 필드 | 플래그 |
|---|---|---|---|---|---|
| 0 | 0xFFC | `00 00 00 00` | 0 | 0x0000 | 없음 (행이 아닌 페이지용 머리값) |
| 1 (행 A) | 0xFF8 | `00 07 00 00` | 0x700 | 0x0000 | 없음 |
| 2 (행 D) | 0xFF4 | `28 00 00 67` | 0x28 | 0x6700 | 0x3 |
| 3 (행 B) | 0xFF0 | `00 04 28 07` | 0x400 | 0x0728 | 없음 |
| 4 (행 C) | 0xFEC | `78 03 28 0B` | 0x378 | 0x0B28 | 없음 |

태그 2 의 위치 필드 0x6700 에서 위쪽 3비트를 떼면 플래그 0x3 입니다. 버전 표시와 지움 표시가 함께 켜졌습니다. 남은 0x0700 이 실제 위치입니다. 이 상태에서는 D 가 태그로 아직 이어져 있습니다. 지움 표시가 붙은 값을 건너뛰는 파서에서는 D 가 보이지 않습니다.

**② 정리 작업이 행을 뺀 뒤**

```
오프셋    00 01 02 03 04 05 06 07  08 09 0A 0B 0C 0D 0E 0F
00000010  1A 00 00 00 1C 00 00 00  21 00 00 00 50 01 00 00
00000020  A0 0E 04 00 02 28 00 00
  ...
00000FE0                                       78 03 28 0B
00000FF0  78 03 28 0B 00 04 28 07  00 07 00 00 00 00 00 00
```

쓰는 태그 개수가 5에서 4로 줄었고, 빈 바이트가 0x124 에서 0x150(336)으로 늘었습니다. D 의 0x28 바이트와 태그 4바이트가 더해진 값입니다. 첫 빈 데이터 오프셋은 D 가 데이터 끝에 있지 않았기 때문에 그대로입니다.

태그 2 자리에 B 가, 태그 3 자리에 C 가 당겨 들어왔고 D 를 가리키던 태그는 사라졌습니다. 0xFEC 는 이제 쓰는 태그 밖이며, 이 자리에는 C 의 태그가 옛 값으로 남아 D 가 아니라 C 를 가리킵니다.

유효한 태그를 위치순으로 늘어놓으면 A 는 0x000–0x700, B 는 0x728–0xB28, C 는 0xB28–0xEA0 이고, 0x700–0x728 의 0x28 바이트를 가리키는 태그는 없습니다. 파일 안 위치는 0x28 + 0x700 = 0x728 이며, 이 40바이트가 D 의 후보입니다. 여기서 키 길이와 레코드 머리를 읽고 열 정의로 검증합니다.

## 포렌식에서 중요한 점

### 증거로서 의미

**증명하는 것**

- 이 DB 의 이 테이블에 한때 이런 값을 담은 행이 있었다는 것.
- 되살린 행의 시각 열에 적힌 사건의 시각. 단, 그 열의 뜻은 아티팩트마다 다릅니다.

**증명하지 못하는 것**

- 언제 지웠는지. 지운 시각을 적는 필드는 없습니다.
- 누가 왜 지웠는지. 사용자가 지운 것과 앱이 스스로 정리한 것을 구분할 필드가 없습니다.
- 지운 행인지 옛 판인지. 행을 고치거나 페이지를 나눌 때도 옛 복사본이 빈 공간에 남습니다.
- 값이 온전한지. 행의 일부가 덮어써졌을 수 있습니다.

보고서에는 기록으로 확인되는 만큼만 씁니다. 예: "WebCacheV01.dat 의 한 페이지 빈 공간에서 URL 열이 X 인 행 조각이 나왔다. 이 행이 언제 지워졌는지는 파일에 기록이 없다."

### 시각 해석

- 되살린 행의 시각 열은 행이 살아 있을 때 앱이 쓴 값 그대로입니다. UTC 인지 현지 시각인지는 열마다 다르므로 해당 아티팩트 페이지를 따릅니다. 값 형식은 [시각 값 형식](../../value-decoding/filetime-unix-webkit-dos-ole.md)을 봅니다.
- 데이터베이스 시각(dbtime)은 바뀔 때마다 커지는 카운터입니다. 어느 페이지가 나중에 바뀌었는지 비교하는 데만 쓸 수 있고, 날짜로 바꿀 수 없습니다.

### 지우기·조작이 남기는 모습

- 방문 기록 지우기: 앱이 행을 지워도 페이지 빈 공간에 행이 남을 수 있습니다. 위 WebCacheV01.dat 방문 기록의 예가 그렇습니다[6].
- 색인 다시 만들기: Windows Search 색인을 다시 만들면 0 으로 채운 새 파일이 생겨 옛 행이 DB 안에 남지 않습니다[5]. 옛 내용은 파일시스템 비할당 영역에서 찾아야 합니다.
- 오프라인 압축: esentutl /d 는 임시 DB 를 새로 만들어 옮겨 적은 뒤 원래 자리에 놓습니다. 새 파일에는 옮겨 적은 행만 들어가므로 옛 빈 공간은 따라오지 않습니다.
- 스크러빙: 페이지 플래그 0x4000 이 켜진 페이지는 스크러빙으로 지워진 뒤 아직 바뀌지 않은 페이지입니다. 다른 변경이 생기면 이 플래그는 꺼집니다[3]. Exchange 는 백업 과정에서 스크러빙을 씁니다. Windows Search 가 스크러빙을 쓴다는 근거는 알려져 있지 않습니다[5].

### 파일 밖에 남는 사본

같은 행이 DB 파일 밖에도 남을 수 있습니다. Windows Search 행은 로그 파일, 섀도 복사본, 파일시스템 비할당 영역, 메모리·pagefile 에서도 나옵니다[5].

- 트랜잭션 로그: [트랜잭션 로그와 비정상 종료 상태](edb-log-dirty-shutdown.md)
- 섀도 복사본: [볼륨 섀도 복사본 구조](../../disk-volume/volume-shadow-copy.md)
- 비할당 영역: [비할당 영역과 슬랙](../../../03-techniques/analysis/data-recovery/unallocated-slack-space.md)
- 페이지 파일: [페이지 파일 (pagefile.sys·swapfile.sys)](../../../03-techniques/analysis/memory-forensics/pagefile-sys-swapfile-sys.md)

## 함정

- **B-트리를 끝까지 못 따라간 행을 지운 행으로 세면 안 됩니다.** 손상된 페이지 너머의 지우지 않은 행도 "B-트리 밖" 목록에 섞일 수 있습니다. 손상된 SRUDB.dat 의 앱 사용량 표가 읽는 방식에 따라 1,612 행과 1,742 행으로 다르게 나온 사례가 있습니다. 먼저 두 가지 방식으로 지우지 않은 행 수를 맞춰 봅니다.
- **로그를 재생한 파일만 보면 안 됩니다.** 압수 이미지의 ESE 파일은 비정상 종료 상태인 경우가 많고, 오래된 로그가 지워져 재생이 안 되기도 합니다. 페이지를 직접 읽는 방식은 로그 없이도 됩니다.
- **같은 키의 행이 여러 벌 나옵니다.** 고치기 전의 옛 판이나 페이지 분할의 복사본일 수 있습니다.
- **ID 가 다시 쓰입니다.** Chivers 와 Hargreaves 의 실험에서는 가장 큰 번호의 행을 지우면 다음 새 행이 그 번호를 다시 썼습니다[5]. 되살린 행의 ID 가 남아 있는 다른 행과 같을 수 있습니다.
- **긴 값은 따로 저장됩니다.** 행에는 긴 값의 ID 만 들어 있습니다. ID 가 다시 쓰일 수 있어 지운 행과 긴 값 조각을 믿을 만하게 잇기 어렵습니다. 조각 경계를 잘못 계산하면 오류 없이 값이 망가집니다(6,000바이트 값이 11,158바이트로 나온 사례가 있습니다). 되살린 값이 압축되어 있을 수도 있습니다. 둘 다 [긴 값과 압축 열](long-value-compressed-column.md)을 봅니다.
- **큰 페이지에서 태그 위쪽 비트를 플래그로 읽으면 틀립니다.** 16·32 KiB 페이지는 플래그가 값 안에 있습니다.
- **도구가 0건을 내도 없다는 뜻이 아닙니다.** libesedb 는 지움 표시가 붙은 값을 건너뜁니다[4]. JET API 로 여는 도구는 지우지 않은 행만 돌려줍니다.
- **빈 공간에는 쓰레기 바이트가 많습니다.** 열 정의로 거르지 않은 후보는 잘못 잡은 것이 섞입니다. 레코드 머리가 망가진 행은 이 방법으로 찾지 못합니다.

## 도구

아래는 예시입니다. 한 도구의 결과만 믿지 말고 [도구 결과 교차 검증](../../../03-techniques/reporting/tool-validation.md)의 방식으로 견줘 봅니다.

- **libesedb (esedbinfo·esedbexport)**: 지우지 않은 행을 페이지 단위로 읽습니다. 형식 문서가 함께 공개되어 있습니다. 지움 표시가 붙은 값은 건너뜁니다.
- **esentutl**: Windows 에 들어 있습니다. 헤더 덤프(/m), 로그 재생(/r), 오프라인 압축(/d)을 합니다. 재생과 압축은 파일을 바꾸므로 사본에서만 씁니다.
- **논문에서 소개한 카버**: wdsCarve 는 Windows Search 를 대상으로 합니다[5]. 테이블 스키마를 써서 모든 ESE 파일의 지운 행을 찾는 방법도 발표됐습니다[6].

도구가 낸 후보는 위 예시처럼 헥스로 헤더와 태그를 직접 확인합니다.
