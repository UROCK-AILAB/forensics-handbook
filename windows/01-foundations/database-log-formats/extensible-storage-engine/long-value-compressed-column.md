# 긴 값과 압축 열 (Long Value·Compressed Column)

ESE 는 긴 문자열·바이너리 값을 레코드 밖의 별도 B+트리에 조각으로 나눠 저장합니다.
Windows 7 부터는 이런 값을 압축해서 저장할 수도 있습니다.
그래서 조각을 잘못 이어 붙이거나 압축 방식을 잘못 고르면, 오류 없이 망가진 값을 얻습니다.

## 이 형식을 쓰는 아티팩트

긴 값 (Long Value, LV) 은 ESE 의 두 가지 열 형식에 들어가는 값입니다.

| 열 형식 코드 | 이름 | 담는 것 | 최대 크기 |
|---|---|---|---|
| 11 | JET_coltypLongBinary | 바이너리 | 2,147,483,647 바이트 |
| 12 | JET_coltypLongText | 문자열 (ASCII 또는 UTF-16) | 2,147,483,647 바이트 |

열 형식 코드는 카탈로그 (MSysObjects) 의 열 정의에 있으며, 카탈로그를 읽는 법은 [파일 구조 (Page·B+Tree·Catalog)](page-b-tree-catalog.md) 에 있습니다. SRUDB.dat·WebCacheV01.dat·Windows.edb·qmgr.db·ntds.dit 처럼 ESE 로 된 파일이라면 모두 이 규칙으로 읽고, 파일 목록과 위치는 [ESE 허브](index.md) 에 있습니다. 어느 표의 어느 열이 긴 값인지는 앱이 정합니다. 그래서 파일마다 카탈로그에서 열 형식이 11·12 인 열을 먼저 찾습니다.

| 형식 (버전, 리비전) | Windows | 이 글과 관련된 점 | 근거 |
|---|---|---|---|
| 0x620, 0x09 | XP SP3 | 긴 값을 따로 저장합니다. 압축은 없습니다 | libyal 명세 |
| 0x620, 0x0C | Vista | 같습니다 | libyal 명세 |
| 0x620, 0x11 | 7 | 열 압축(7비트·XPRESS)이 들어옵니다 | libyal 명세, Microsoft Learn |
| 0x620, 0xD2 이상 | 공개 자료 없음 | LZ4 압축을 쓸 수 있는 형식입니다 | ESE 공개 소스 |
| — | 10·11 | LZ4 로 압축한 값이 보입니다 | 실제 DB 파일 |

값을 저장할 때 압축을 요청하는 옵션(JET_bitSetCompressed)은 Windows 7 에서 들어왔습니다. LZ4 기능은 DB 형식 버전 0x620, 갱신 번호 210(0xD2) 이상에서만 쓸 수 있고, 이 기능은 2021년 3월에 추가됐습니다. 갱신 번호는 헤더의 "형식 리비전" 필드와 같은 값이며, 헤더 읽는 법은 [파일 구조](page-b-tree-catalog.md) 에 있습니다.

Windows 의 어느 빌드부터 이 조건을 채우는지는 공개 자료가 없습니다. 그래서 헤더의 리비전과 실제 값의 첫 바이트를 함께 봅니다. 8바이트 긴 값 식별자(아래)가 어느 Windows 부터 쓰였는지도 실제 파일로 확인해야 합니다.

## 구조

### 레코드 안에 두기와 따로 두기

긴 값은 레코드 안에 들어갈 수도 있고, 레코드 밖에 따로 놓일 수도 있습니다.
레코드 안에 든 값을 안에 둔 긴 값 (Intrinsic Long Value) 이라고 합니다.
밖에 놓인 값을 따로 둔 긴 값 (Separated Long Value) 이라고 합니다.

레코드 크기에는 페이지 크기에 따른 한도가 있고, 레코드가 한도를 넘으면 엔진이 5바이트보다 큰 긴 값을 레코드 밖으로 옮깁니다. 앱이 값을 밖에 두도록 강제할 수도 있지만 4바이트 이하 값은 밖에 둘 수 없고, 안에 두도록 강제하면 1,024바이트까지만 됩니다. 밖에 둔 값도 레코드 안에서 연결 정보로 5바이트를 씁니다. 그래서 같은 열이라도 레코드마다 저장 방식이 다를 수 있습니다.

> 그림 자리: 레코드의 태그 열 → LID → 긴 값 트리의 뿌리 노드와 조각 노드로 이어지는 모습

### 태그 열의 머리 바이트

긴 값 열은 늘 태그 열 (Tagged Column) 번호를 받습니다. 그래서 긴 값은 레코드의 태그 열 영역에 들어가며, 압축 옵션과 암호화 옵션은 긴 값 열에만 쓸 수 있습니다.

태그 열 값 앞에는 플래그 바이트 하나가 붙을 수 있는데, 이 바이트는 오프셋 배열 항목의 0x4000 비트가 켜져 있을 때 붙고 Windows 7(리비전 0x11) 이후의 16·32 KiB 페이지에서는 늘 붙습니다. 태그 열 영역의 전체 배치는 [파일 구조](page-b-tree-catalog.md) 에 있습니다.

| 비트 | ESE 소스의 이름 | 뜻 |
|---|---|---|
| 0x01 | fLongValue | 긴 값 형식 열의 값입니다 |
| 0x02 | fCompressed | 레코드 안에 든 값이 압축되어 있습니다 |
| 0x04 | fSeparated | 값은 긴 값 트리에 있습니다. 여기에는 식별자만 있습니다 |
| 0x08 | fMultiValues | 값이 여러 개입니다 |
| 0x10 | fTwoValues | 값이 두 개입니다 |
| 0x20 | fNull | 빈 값입니다 |
| 0x40 | fEncrypted | 암호화된 값입니다 |

0x02 와 0x04 는 함께 켜지지 않으며, 밖에 둔 값의 압축은 조각마다 따로 알아봅니다(아래). libyal 명세는 0x01 을 "가변 크기 값" 이라고 추정해 적었지만 Microsoft 가 공개한 ESE 소스의 이름은 fLongValue 입니다. 0x05 는 "밖에 둔 긴 값" 이고, 0x03 은 "안에 둔 압축된 긴 값" 입니다.

### 긴 값 식별자 (LID)

밖에 둔 값이면 레코드에는 긴 값 식별자 (Long Value ID, LID) 만 남습니다.

LID 는 4바이트(옛 형식) 또는 8바이트(새 형식)이고, 레코드 안에서는 리틀 엔디언입니다. 긴 값 트리의 키에는 같은 LID 가 빅 엔디언으로 들어가는데, 레코드 쪽 바이트를 거꾸로 놓으면 키가 됩니다. 8바이트 LID 는 가장 높은 비트(bit 63)가 켜져 있습니다. 그래서 키의 첫 바이트가 0x80 이면 8바이트 LID 이고, 4바이트 LID 의 첫 바이트는 0x7F 이하입니다.

### 긴 값 트리 (Long Value Tree)

긴 값은 표마다 하나씩 있는 B+트리에 저장됩니다.
카탈로그에서 종류가 4(긴 값)인 항목이 이 트리의 시작 페이지 번호를 가리킵니다.
이 트리의 페이지는 페이지 플래그 0x0080(긴 값 페이지)으로 알아봅니다.

트리의 노드는 두 종류입니다. 키 길이로 구별합니다.

| 키 길이 | 노드 | 키 내용 (빅 엔디언) |
|---|---|---|
| 4바이트 | 옛 형식 뿌리 노드 | LID (4바이트) |
| 8바이트 | 첫 바이트가 0x80 이면 새 형식 뿌리 노드, 아니면 옛 형식 조각 노드 | LID (8바이트), 또는 LID (4바이트) + 자리 (4바이트) |
| 12바이트 | 새 형식 조각 노드 | LID (8바이트) + 자리 (4바이트) |

**뿌리 노드 (LVROOT)** 의 데이터는 8바이트 또는 9바이트입니다. 숫자는 리틀 엔디언입니다.

| 오프셋 | 크기 | 필드 | 뜻 |
|---|---|---|---|
| 0 | 4 | 참조 수 (Reference Count) | 이 값을 가리키는 레코드 수 |
| 4 | 4 | 크기 | 압축을 풀었을 때 값 전체의 바이트 수 |
| 8 | 1 | 플래그 | 9바이트일 때만 있습니다. 0x01 = 암호화 |

- 9바이트 형식은 2015년 9월 암호화 기능과 함께 들어왔습니다.
- 참조 수가 0xFFFFFFFF 이면 지우던 도중인 값입니다. 엔진은 이 상태를 "일부만 지운 값 (Partially Deleted LV)" 으로 처리합니다.

**조각 노드 (Chunk)** 의 키는 LID 뒤에 자리 (Offset) 4바이트를 붙인 것입니다.

자리는 압축을 풀었을 때 값 전체에서 이 조각이 시작하는 바이트 위치이고, 첫 조각의 자리는 0 이며 늘 조각 최대 크기의 배수입니다. 마지막 조각을 빼면 모든 조각은 압축을 푼 기준으로 조각 최대 크기만큼 담습니다.

조각 최대 크기는 표마다 정해지며, 카탈로그의 LVChunkMax 필드에 값이 있으면 그 값을 쓰고 없으면 엔진 기본값을 씁니다. libyal 명세는 LVChunkMax 필드의 뜻을 "알 수 없음" 으로 적었지만 ESE 소스에서는 조각 최대 크기로 쓰입니다. 엔진 기본값은 공개 자료가 없으므로, 실제 값은 둘째 조각 키의 자리로 확인합니다.

### 압축 값의 첫 바이트

압축된 값은 첫 바이트가 압축 방식을 알려 줍니다.
첫 바이트의 위 5비트가 방식 번호입니다. 그래서 첫 바이트를 8로 나눈 몫이 방식 번호입니다.

| 첫 바이트 | 방식 번호 | 이름 | 첫 바이트 뒤에 오는 것 |
|---|---|---|---|
| 0x08~0x0F | 1 | 7비트 ASCII | 7비트씩 이어 붙인 글자 |
| 0x10~0x17 | 2 | 7비트 유니코드 | 7비트씩 이어 붙인 글자. 풀면 UTF-16LE 가 됩니다 |
| 0x18 | 3 | XPRESS | 원래 크기 2바이트 + XPRESS 데이터 |
| 0x20 | 4 | 덮어 지우기 (Scrub) | 같은 채움 바이트의 반복. 압축이 아닙니다 |
| 0x28 | 5 | XPRESS9 | 검사합 4바이트 + XPRESS9 데이터 |
| 0x30 | 6 | XPRESS10 | 원래 크기 2바이트 + CRC 4바이트 + 검사합 8바이트 + 데이터 |
| 0x38 | 7 | LZ4 | 원래 크기 2바이트 + LZ4 블록 |

7비트 방식의 아래 3비트는 "마지막 바이트에서 쓴 비트 수 − 1" 입니다. 원래 크기 필드는 리틀 엔디언 2바이트입니다. 그래서 한 번에 65,535바이트까지만 압축합니다.

XPRESS 는 허프만 부호가 없는 LZ77 방식이며 libyal 은 이것을 LZXPRESS 라고 부르고, 형식은 [윈도 압축 형식 (LZNT1·Xpress·Xpress Huffman)](../../value-decoding/lznt1-xpress-xpress-huffman.md) 에 있습니다. LZ4 는 프레임 머리가 없는 LZ4 블록 형식입니다. XPRESS9·XPRESS10 은 ESE 에 조건부로 들어가는 방식이며, Windows 아티팩트 DB 에서 쓰이는지는 실제 파일로 확인해야 합니다.

**7비트 방식 푸는 법**

1. 첫 바이트의 아래 3비트에 1을 더합니다. 마지막 바이트에서 쓴 비트 수입니다.
2. 전체 비트 수 = (압축 값 길이 − 2) × 8 + 1단계 값 입니다.
3. 글자 수 = 전체 비트 수 ÷ 7 입니다.
4. 둘째 바이트부터 가장 낮은 비트 쪽에서 7비트씩 꺼냅니다. 한 번 꺼낸 값이 글자 하나입니다.
5. 방식 2(7비트 유니코드)면 글자마다 뒤에 0x00 을 붙입니다. 그러면 UTF-16LE 문자열이 됩니다.

### 엔진이 압축을 고르는 규칙

압축은 앱이 열이나 값에 요청했을 때만 하며, 엔진은 XPRESS 계열을 먼저 해 봅니다. 밖에 둔 값의 조각은 앱이 XPRESS 를 요청해도 DB 형식이 LZ4 를 허용하면 LZ4 를 씁니다. 그 결과가 7비트 유니코드로 줄인 크기보다 크면 7비트 방식을 해 보고, 어느 방식으로도 원래보다 작아지지 않으면 압축하지 않고 그대로 저장합니다.

밖에 둔 값은 조각마다 따로 압축합니다. 128바이트 이상인 조각은 앞부분(최대 1,024바이트)의 바이트 분포를 먼저 보고, 분포가 무작위에 가까우면 압축을 시도하지 않습니다. 조각에는 압축 여부를 알리는 비트가 없고, 저장된 길이가 기대 길이보다 짧으면 압축된 조각입니다. 기대 길이는 조각 최대 크기이며 마지막 조각만 "값 전체 크기 − 자리" 입니다. Windows 10·11 의 ESENT 가 만든 DB 에서는 잘 줄어드는 값에 LZ4 가 쓰입니다.

## 읽는 법 — 헥스로 한 번 따라가기

아래 바이트는 모두 **명세와 ESE 공개 소스로 만든 예시**입니다. 실제 파일에서 나온 값이 아닙니다.

**1단계. 카탈로그에서 열 형식을 봅니다.**
형식 코드가 11 이나 12 이면 긴 값 열입니다.
12(LongText)면 열 정의의 코드 페이지도 적어 둡니다. 1252 는 ASCII 계열, 1200 은 UTF-16 입니다.

**2단계. 레코드 안에 든 압축 값을 풉니다.**

```
태그 열 값 (명세로 만든 예시)
03 10 E3 36 D9 55 C6 97 01
```

- `03` 은 머리 바이트입니다. 0x01(긴 값) 과 0x02(압축) 가 켜져 있습니다.
- `10` 은 압축 값의 첫 바이트입니다. 0x10 ÷ 8 = 2 이므로 7비트 유니코드입니다.
- 아래 3비트는 0 입니다. 마지막 바이트에서 1비트를 썼습니다.
- 압축 값 길이는 `10` 부터 8바이트입니다. 전체 비트 수는 (8 − 2) × 8 + 1 = 49 입니다.
- 글자 수는 49 ÷ 7 = 7 입니다.
- `E3` 의 아래 7비트는 0x63 입니다. 첫 글자 `c` 입니다.
- `E3` 의 남은 1비트와 `36` 의 아래 6비트를 합치면 0x6D 입니다. 둘째 글자 `m` 입니다.
- 끝까지 풀면 `63 00 6D 00 64 00 2E 00 65 00 78 00 65 00`, 곧 UTF-16LE 로 `cmd.exe` 입니다.
- 압축 전 14바이트가 8바이트로 줄었습니다. 이 파일을 `cmd.exe` 로 검색해도 이 값은 걸리지 않습니다.

**3단계. 밖에 둔 값이면 LID 를 읽습니다.**

```
태그 열 값 (명세로 만든 예시)
05 A7 00 00 00
```

- `05` 는 머리 바이트입니다. 0x01(긴 값) 과 0x04(밖에 둠) 가 켜져 있습니다.
- 뒤의 4바이트 `A7 00 00 00` 이 LID 입니다. 리틀 엔디언으로 0x000000A7 입니다.

**4단계. 긴 값 트리에서 뿌리 노드를 찾습니다.**

```
긴 값 트리 잎 노드 (명세로 만든 예시)
키:    00 00 00 A7
데이터: 01 00 00 00  70 17 00 00
```

- 키는 LID 를 빅 엔디언으로 적은 4바이트입니다. 옛 형식 뿌리 노드입니다.
- 참조 수는 1 입니다.
- 크기는 0x1770, 곧 6,000바이트입니다.

**5단계. 같은 LID 의 조각 노드를 자리 순서대로 모읍니다.**

이 예시는 조각 최대 크기를 2,048바이트로 가정합니다. 실제 값은 둘째 조각 키의 자리로 확인합니다.

| 키 | 자리 | 저장된 길이 | 기대 길이 | 판단 |
|---|---|---|---|---|
| `00 00 00 A7 00 00 00 00` | 0 | 2,048 | 2,048 | 같으므로 그대로 씁니다 |
| `00 00 00 A7 00 00 08 00` | 2,048 | 755 | 2,048 | 짧으므로 압축된 조각입니다 |
| `00 00 00 A7 00 00 10 00` | 4,096 | 1,904 | 6,000 − 4,096 = 1,904 | 같으므로 그대로 씁니다 |

- 둘째 조각의 데이터는 `38 00 08 …` 로 시작합니다.
- 0x38 ÷ 8 = 7 이므로 LZ4 입니다. 뒤의 `00 08` 은 원래 크기 0x0800(2,048)입니다.
- 셋째 바이트부터를 LZ4 블록으로 풀면 2,048바이트가 나옵니다.
- 각 조각을 키의 자리에 놓습니다. 결과 길이는 2,048 + 2,048 + 1,904 = 6,000 입니다.
- 뿌리 노드의 크기 6,000 과 같으므로 조각이 빠지지 않았습니다.
- 저장된 길이를 그대로 더하면 4,707 이 됩니다. 압축을 풀지 않고 이어 붙이면 이렇게 짧고 깨진 값이 나옵니다.

**6단계. 결과를 글자로 바꿉니다.**
LongText 열이면 1단계의 코드 페이지로 글자를 해석합니다.
코드 페이지가 1200 이어도 실제로는 ASCII 인 값이 있습니다. 길이가 짝수면 UTF-16 으로 먼저 읽어 보고, 깨지면 ASCII 로 읽습니다.
인코딩 판별은 [문자 인코딩 (UTF-16LE·UTF-8·CP949)](../../value-decoding/utf-16le-utf-8-cp949.md) 에서 다룹니다.

## 포렌식에서 중요한 점

### 파일 전체를 문자열로 검색하면 놓칩니다

7비트 압축 값에는 글자가 7비트씩 밀려 있기 때문에 원래 문자열의 바이트가 없습니다. XPRESS·LZ4 는 되풀이되는 부분을 앞 위치 참조로 바꿉니다. 그래서 문자열의 일부만 보이거나 전혀 안 보입니다. ESE 파일이나 비할당 영역을 [키워드 검색](../../../03-techniques/analysis/content-search/keyword-search.md) 이나 [레코드 카빙](../../../03-techniques/analysis/data-recovery/record-carving.md) 으로 검색할 때 이 한계를 보고서에 적습니다.

반대로 바이트 분포가 고른 값은 엔진이 분포를 보고 압축을 건너뛰기 때문에 압축되지 않은 채 남는 경우가 많고, 암호화된 데이터나 이미 압축된 데이터가 여기에 들어갑니다.

### 지운 레코드와 긴 값은 따로 남습니다

레코드와 긴 값은 서로 다른 B+트리, 서로 다른 페이지에 있습니다. 레코드를 지우면 긴 값의 참조 수가 1 줄어들고, 참조 수가 0 이 되면 엔진은 뿌리 노드와 조각 노드에 지움 표시를 하며 실제 정리는 그 뒤에 따로 합니다. 그래서 지운 레코드를 되살려도 LID 가 가리키는 뿌리·조각이 없을 수 있고, 거꾸로 레코드는 없고 긴 값 조각만 남을 수도 있는데 이때 어느 레코드의 값인지는 LID 로만 이을 수 있습니다.

참조 수가 0xFFFFFFFF 인 뿌리는 지우던 도중에 멈춘 값입니다. 첫 바이트가 0x20 이고 뒤가 같은 바이트로 채워진 값은 엔진이 덮어 지운 값이며 원래 내용은 되살릴 수 없습니다. 이 값으로는 "그 자리에 지운 데이터가 있었다" 는 사실만 알 수 있습니다. 페이지 안에서 지운 레코드를 찾는 법은 [파일 안에 남은 지운 레코드 (Deleted Records)](deleted-records.md) 에 있습니다.

### 비정상 종료 DB

JET API 로 DB 를 열면 엔진이 조각을 잇고 압축을 풀어 주지만, 비정상 종료 DB 는 먼저 로그로 복구해야 열립니다. 이미지 안의 로그 사슬이 끊겨 복구가 안 되는 경우도 있습니다. 페이지를 직접 해석하면 로그 없이 읽을 수 있는 대신, 이 글의 규칙대로 조각을 잇고 압축을 직접 풀어야 합니다.

비정상 종료 DB(Vista 검색 DB, Exchange 2013)에서 가지 노드가 가리킨 잎 페이지에 긴 값 뿌리 노드가 없고 그다음 잎 페이지에 있던 사례가 있습니다. 잎 페이지 하나만 보고 "값 없음" 으로 판단하지 않습니다. 복구와 로그는 [트랜잭션 로그와 비정상 종료 상태 (edb.log·Dirty Shutdown)](edb-log-dirty-shutdown.md) 에서 다룹니다. 어느 쪽이든 원본이 아닌 사본에서 작업합니다.

### 시각과 증거의 범위

긴 값 구조에는 뿌리 노드에도 조각 노드에도 시각 필드가 없고, 값이 언제 기록됐는지는 같은 레코드의 시각 열로만 추정합니다. 풀어 낸 값으로는 "이 LID 의 긴 값에 이 내용이 저장되어 있다" 는 것까지만 알 수 있습니다. 보고서에는 값을 어떤 방식으로 풀었는지(압축 방식, 조각 수, 뿌리 크기와 결과 길이가 같은지)를 함께 적습니다.

## 함정

- **첫 바이트만 보고 조각이 압축됐다고 판단합니다.** 압축되지 않은 조각도 우연히 0x18·0x38 로 시작할 수 있습니다. 조각의 압축 여부는 저장된 길이와 기대 길이를 비교해 정합니다.
- **조각 위치를 저장된 길이로 계산합니다.** 조각의 위치는 키의 자리 값(압축 전 기준)으로 정합니다. 조각 경계를 잘못 계산한 파서가 6,000바이트 값을 11,158바이트로 내놓고도 오류를 내지 않은 사례가 있습니다.
- **결과 길이를 확인하지 않습니다.** 이어 붙인 결과 길이는 뿌리 노드의 크기와 같아야 합니다. 다르면 조각이 빠졌거나 경계를 잘못 계산한 것입니다.
- **도구가 아는 압축 방식을 확인하지 않습니다.** libesedb 의 공개 소스(2026년 5월 커밋 기준)는 첫 바이트 0x18 만 XPRESS 로 풉니다. 나머지는 모두 7비트 방식으로 풉니다. 이런 도구에 LZ4(0x38) 값을 넣으면 오류 없이 깨진 글자가 나올 수 있습니다.
- **7비트 유니코드 결과를 ASCII 로 읽습니다.** 방식 2 를 풀면 UTF-16LE 입니다.
- **ESE 압축만 풀면 끝이라고 생각합니다.** 앱이 값을 자기 방식으로 한 번 더 인코딩하기도 합니다. 예를 들어 공개 도구 esedbexport 에는 Windows Search 값만을 위한 별도 디코딩 코드가 있습니다. 앱별 처리는 [윈도 검색 색인 DB](../../../02-artifacts/file-folder-usage/windows-search/index.md) 같은 아티팩트 페이지를 봅니다.
- **페이지에 적힌 키를 그대로 비교합니다.** ESE 는 페이지 안에서 키의 공통 앞부분을 줄여 저장합니다. 전체 키를 되살린 뒤에 LID 를 비교합니다. 방법은 [파일 구조](page-b-tree-catalog.md) 에 있습니다.
- **8바이트 키를 한 가지로만 읽습니다.** 8바이트 키는 새 형식 뿌리일 수도 있고 옛 형식 조각일 수도 있습니다. 첫 바이트의 가장 높은 비트로 구분합니다.
- **암호화 플래그를 지나칩니다.** 머리 바이트 0x40 이나 뿌리 플래그 0x01 이 켜져 있으면 압축을 풀기 전에 복호해야 합니다. 키가 없으면 풀 수 없습니다.
- **여러 값 열의 모든 값이 같은 방식이라고 가정합니다.** 압축 플래그가 켜진 여러 값 열에서 첫 값만 압축된 사례가 있습니다.

## 도구

아래 공개 도구는 예로만 듭니다. 한 도구의 결과에만 기대지 않습니다.

| 방식 | 예 | 긴 값·압축 처리 |
|---|---|---|
| JET API 로 여는 도구 | Windows 의 ESENT.dll 을 쓰는 도구 | 엔진이 조각을 잇고 압축을 풀어 줍니다. 비정상 종료 DB 는 먼저 복구해야 합니다 |
| 페이지를 직접 읽는 도구 | libesedb (esedbexport) | 로그 없이 읽습니다. 소스 기준으로 7비트·XPRESS 만 풉니다 |
| 다른 파이썬 파서 | dissect.esedb, Impacket ese.py 등 | 지원하는 압축 방식이 버전마다 다를 수 있습니다. 쓰기 전에 표본 값으로 확인합니다 |
| 헥스 편집기와 짧은 스크립트 | — | 이 글의 표대로 뿌리·조각·첫 바이트를 직접 읽습니다. LZ4·XPRESS 는 공개 라이브러리로 풉니다 |

두 도구의 결과가 다르면 먼저 같은 LID 의 조각 수, 뿌리 크기, 압축 방식을 비교합니다.
검증 방법은 [도구 결과 교차 검증 (Tool Validation)](../../../03-techniques/reporting/tool-validation.md) 에 있습니다.
