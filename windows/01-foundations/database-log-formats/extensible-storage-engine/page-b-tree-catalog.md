# 파일 구조 (Page·B+Tree·Catalog)

## 한 줄 요약

ESE 파일은 크기가 같은 페이지 (Page) 를 이어 붙인 파일입니다. 표와 인덱스는 저마다 페이지로 된 B+트리 (B+ Tree) 하나입니다. 어느 표가 어느 페이지에서 시작하는지는 카탈로그 (Catalog) 라는 시스템 표에 적혀 있습니다. 이 셋을 알면 엔진 없이 헥스만으로 레코드까지 따라갈 수 있습니다.

## 이 형식을 쓰는 아티팩트

SRUDB.dat·WebCacheV01.dat·Windows.edb·qmgr.db·ntds.dit 가 모두 이 구조를 씁니다. 파일마다 표와 열의 정의가 다릅니다. 파일 목록과 위치는 [ESE 데이터베이스](index.md) 허브에 있습니다.

## 구조

> 그림 자리: 파일 앞의 헤더 두 장과 그 뒤의 페이지 1·4·24 를 그리고, 카탈로그(페이지 4) 행의 FDP 페이지 번호를 따라 각 표의 B+트리 루트로 내려가는 화살표

### 파일 전체 배치

헤더와 레코드의 정수는 리틀 엔디언이고 트리의 키만 예외입니다(아래 B+트리 절). 첫 페이지는 파일 헤더 (File Header), 두 번째 페이지는 헤더 사본 (Shadow Header) 입니다. 헤더 두 장에는 페이지 번호가 붙지 않고, 그 뒤 페이지부터 1, 2, 3 … 번입니다. 파일 오프셋은 `(페이지 번호 + 1) × 페이지 크기` 입니다.

페이지 크기는 헤더의 236 오프셋에서 읽으며, 파일마다 다르므로 짐작하지 않습니다.

### 파일 헤더

아래 표는 분석에 쓰는 칸만 담습니다. 시각 칸의 형식은 아래 "시각 값" 절에서 다룹니다.

| 오프셋 | 크기 | 내용 |
|---|---|---|
| 0 | 4 | 체크섬. 4 오프셋부터 32비트씩 XOR 한 값이고, 시작값은 `0x89ABCDEF` 입니다. |
| 4 | 4 | 서명 `EF CD AB 89` |
| 8 | 4 | 형식 버전 (예: `0x620`) |
| 12 | 4 | 파일 종류. 0 은 데이터베이스, 1 은 스트리밍 파일입니다. |
| 16 | 8 | 데이터베이스 시각 (DBTIME). 작업 순번입니다. |
| 24 | 28 | 데이터베이스 서명. 난수 4바이트, 만든 시각 8바이트(28 오프셋), 컴퓨터 이름 16바이트(36 오프셋)입니다. 컴퓨터 이름은 비어 있을 수 있습니다. |
| 52 | 4 | 상태. 1 방금 만듦, 2 비정상 종료, 3 정상 종료, 4 변환 중, 5 강제 분리입니다. |
| 64 | 8 | 마지막 정상 종료 시각. 비정상 종료 상태면 비어 있습니다. |
| 72 | 8 | 마지막 연결 (Attach) 시각. 엔진이 DB 를 열어 붙인 때입니다. |
| 88 | 8 | 마지막 분리 (Detach) 시각. 엔진이 DB 를 떼어 낸 때입니다. |
| 216 ~ 228 | 4 × 4 | 인덱스를 갱신할 때의 Windows 주·부 버전, 빌드 번호, 서비스 팩 번호 |
| 232 | 4 | 형식 개정 (Format Revision) |
| 236 | 4 | 페이지 크기(바이트) |
| 340 · 344 | 4 · 4 | 처음 만들 때의 형식 버전과 형식 개정 |

### 페이지 헤더

페이지 크기가 8 KiB 이하면 헤더가 40바이트입니다. 16·32 KiB 면 80바이트입니다. 앞 8바이트는 형식에 따라 다릅니다.

| 형식 | 0 ~ 7 오프셋 |
|---|---|
| 옛 체크섬 형식 (플래그 `0x2000` 꺼짐) | XOR 체크섬 4바이트 뒤에 이 페이지 번호 4바이트가 있습니다. |
| 새 체크섬 형식 (플래그 `0x2000` 켜짐) | XOR 체크섬 4바이트 뒤에 ECC 체크섬 4바이트가 있습니다. 페이지 번호는 체크섬 시작값으로만 쓰고 저장하지 않습니다. |
| 16·32 KiB 페이지 | 체크섬 8바이트입니다. 페이지 번호는 64 오프셋에 따로 있습니다. |

그 뒤는 모든 형식이 같습니다.

| 오프셋 | 크기 | 내용 |
|---|---|---|
| 8 | 8 | 이 페이지가 마지막으로 바뀐 때의 DBTIME |
| 16 | 4 | 이전 페이지 번호 (잎끼리 잇는 왼쪽 페이지) |
| 20 | 4 | 다음 페이지 번호 (잎끼리 잇는 오른쪽 페이지) |
| 24 | 4 | FDP 개체 ID. 이 페이지가 속한 트리의 번호입니다. |
| 28 | 2 | 남은 바이트 수 |
| 30 | 2 | 비었지만 롤백하면 다시 쓰일 수 있는 바이트 수 |
| 32 | 2 | 빈 자리가 시작하는 오프셋 (헤더 끝 기준) |
| 34 | 2 | 쓰는 태그 개수 (낮은 12비트) |
| 36 | 4 | 페이지 플래그 |
| 40 | 24 | (16·32 KiB 만) 추가 체크섬 8바이트 세 개 |
| 64 | 4 | (16·32 KiB 만) 이 페이지 번호 |
| 68 | 12 | (16·32 KiB 만) 예약 |

FDP 는 Father Data Page 의 줄임말입니다. 트리마다 개체 ID 가 하나 있습니다. 그 트리의 루트 페이지를 FDP 페이지라고 부릅니다.

### 페이지 플래그

| 값 | 이름 | 뜻 |
|---|---|---|
| `0x0001` | Root | 트리의 루트 페이지입니다. |
| `0x0002` | Leaf | 잎 페이지입니다. 레코드나 인덱스 값이 들어 있습니다. |
| `0x0004` | ParentOfLeaf | 잎 바로 위의 가지 페이지입니다. |
| `0x0008` | Empty | 빈 페이지입니다. |
| `0x0020` | SpaceTree | 공간 트리 페이지입니다. |
| `0x0040` | Index | 보조 인덱스 트리 페이지입니다. |
| `0x0080` | LongValue | 긴 값 트리 페이지입니다. |
| `0x0400` | NonUniqueKeys | 키가 겹칠 수 있는 인덱스의 페이지입니다. |
| `0x0800` | NewRecordFormat | 새 레코드 형식입니다. |
| `0x2000` | NewChecksumFormat | 새 체크섬 형식입니다. |
| `0x4000` | Scrubbed | 스크럽 (Scrub) 작업을 거친 페이지입니다. 다른 변경이 생기면 꺼집니다. libyal 명세는 0 으로 덮인 페이지로 봅니다. |
| `0x20000` | PreInit | 새로 잡았지만 아직 쓰지 않은 페이지입니다. 데이터 부분이 모두 0 입니다. |

`0x0020`·`0x0040`·`0x0080` 이 모두 꺼져 있으면 표 레코드가 든 페이지입니다.

### 페이지 태그

페이지 태그 (Page Tag) 는 페이지 안 값의 목차이며 태그 하나가 4바이트입니다. 태그는 페이지 맨 끝에서 앞쪽으로 쌓이고, 태그 0 이 맨 끝 4바이트입니다. 파일 순서로 읽으면 앞 2바이트가 값의 크기이고 뒤 2바이트가 값의 오프셋이며, 오프셋은 페이지 시작이 아니라 페이지 헤더 끝(40 또는 80)부터 셉니다.

8 KiB 이하 페이지에서는 크기와 오프셋이 낮은 13비트이고 오프셋 칸의 위 3비트가 태그 플래그입니다. 16·32 KiB 페이지에서는 크기와 오프셋이 낮은 15비트이고, 태그 플래그는 값 자체의 첫 2바이트 위 3비트로 옮겨 갑니다.

| 태그 플래그 | 이름 | 뜻 |
|---|---|---|
| `0x1` | Version | 트랜잭션 처리와 관련된 표시입니다. |
| `0x2` | Deleted | 지움 표시만 하고 아직 정리하지 않은 값입니다. [파일 안에 남은 지운 레코드](deleted-records.md) 에서 다룹니다. |
| `0x4` | Compressed | 키 앞부분을 공통 키에서 빌려 씁니다. |

### B+트리: 루트·가지·잎

트리 맨 위 페이지가 루트 (Root) 입니다. 데이터가 든 맨 아래 페이지가 잎 (Leaf) 입니다. 그 사이에서 자식 페이지 번호만 적는 페이지가 가지 (Branch) 입니다. 트리가 작으면 루트 하나가 잎을 겸합니다.

- 태그 0 의 값은 페이지 종류에 따라 다릅니다.
  - 루트 페이지의 태그 0 은 루트 헤더입니다. 처음 잡은 페이지 수, 부모 FDP 페이지 번호, 공간 관리 방식(한 페이지·여러 페이지), 공간 트리 페이지 번호가 4바이트씩 들어 있습니다. 개정 `0x14` 에서는 25바이트짜리 루트 헤더도 보입니다.
  - 루트가 아닌 페이지의 태그 0 은 공통 키입니다. 그 페이지의 엔트리들이 함께 쓰는 키 앞부분입니다.
- 태그 1 부터가 엔트리입니다. 가지 엔트리와 잎 엔트리는 앞부분이 같습니다.

| 순서 | 크기 | 가지 엔트리 | 잎 엔트리 |
|---|---|---|---|
| 1 | 2 | (태그 플래그 `0x4` 일 때만) 공통 키에서 빌릴 바이트 수 | 같음 |
| 2 | 2 | 이 엔트리의 키 길이 | 같음 |
| 3 | 가변 | 키 | 키 |
| 4 | 4 / 가변 | 자식 페이지 번호 | 데이터 |

- 잎끼리는 페이지 헤더의 이전·다음 페이지 번호로 이어집니다. 첫 잎을 찾으면 옆으로 차례대로 읽을 수 있습니다.
- 표 트리는 기본 인덱스 (Primary Index) 순서로 레코드를 담습니다. 기본 인덱스를 따로 두지 않은 표는 넣은 순서대로 담습니다.
- 보조 인덱스 (Secondary Index) 는 트리가 따로 있습니다. 보조 인덱스 잎의 데이터는 레코드의 기본 키입니다.
- 긴 값은 표마다 트리가 따로 있습니다. 자세한 내용은 [긴 값과 압축 열](long-value-compressed-column.md) 에 있습니다.
- 공간 트리 (Space Tree) 는 트리가 쓰는 페이지를 관리합니다. 루트 헤더가 가리키는 페이지는 이 트리에 속한 페이지 구간을 적습니다. 그다음 번호의 페이지는 그중 비어 있는 구간을 적습니다.
- 키는 바이트 단위로 비교해도 순서가 맞도록 바꿔서 저장합니다. 키의 예는 `7F 80 00 00 02 7F 80 01 7F 80 00 00 02` 입니다. 이 예를 보면 열마다 `7F` 로 시작합니다. 정수는 빅 엔디언이고 맨 위 비트가 뒤집혀 있습니다. 카탈로그 기본 키의 짜임(4바이트·2바이트·4바이트)에 맞춰 읽으면 (2, 1, 2) 가 됩니다.

### 고정 페이지 번호

카탈로그와 그 인덱스는 늘 같은 페이지에서 시작합니다.

| 페이지 번호 | FDP 개체 ID | 내용 |
|---|---|---|
| 1 | 1 | 데이터베이스 루트. 파일 전체의 공간을 관리합니다. |
| 4 | 2 | 카탈로그 `MSysObjects` (기본 인덱스 `Id`) |
| 7 | 4 | `MSysObjects` 의 `Name` 인덱스 |
| 10 | 5 | `MSysObjects` 의 `RootObjects` 인덱스 |
| 24 | 3 | 카탈로그 사본 `MSysObjectsShadow` |

4 KiB 페이지라면 페이지 4 는 파일 오프셋 `0x5000` 이고, 페이지 24 는 `0x19000` 입니다. 32 KiB 페이지라면 각각 `0x28000`, `0xC8000` 입니다.

### 카탈로그 (MSysObjects)

카탈로그의 행 하나가 개체 하나이며 개체 종류는 표·열·인덱스·긴 값·콜백입니다. 기본 키는 `ObjidTable` → `Type` → `Id` 순서입니다. 그래서 한 표에 딸린 행이 표 → 열 → 인덱스 → 긴 값 순서로 붙어 나옵니다. 카탈로그는 자기 자신의 정의도 담습니다.

| `Type` 값 | 종류 |
|---|---|
| 1 | 표 |
| 2 | 열 |
| 3 | 인덱스 |
| 4 | 긴 값 |
| 5 | 콜백 |

자주 보는 열은 아래와 같습니다. "위치" 는 레코드 머리 4바이트 뒤부터 센 바이트 위치입니다(카탈로그 레코드의 한 예).

| 열 ID | 이름 | 크기 | 위치 | 뜻 |
|---|---|---|---|---|
| 1 | ObjidTable | 4 | 0 | 이 행이 속한 표의 개체 ID |
| 2 | Type | 2 | 4 | 개체 종류 |
| 3 | Id | 4 | 6 | 열이면 열 ID, 나머지는 그 개체의 ID |
| 4 | ColtypOrPgnoFDP | 4 | 10 | 열이면 열 형식, 나머지는 그 트리의 FDP 페이지 번호 |
| 7 | PagesOrLocale | 4 | 22 | 표는 처음 페이지 수, 열은 코드페이지, 인덱스는 로캘 ID |
| 9 | RecordOffset | 2 | 27 | 고정 열이 레코드 안에서 놓이는 위치 |
| 128 | Name | 가변 | — | 이름 |
| 132 | KeyFldIDs | 가변 | — | 인덱스를 이루는 열 ID |

- 개정이 오르면서 카탈로그 열이 늘었습니다. 예를 들어 11번 `KeyMost` 는 개정 `0x0C` 에서, 12번 `LVChunkMax` 는 개정 `0x14` 에서 생겼습니다.
- 인덱스 행의 FDP 페이지는 그 인덱스 트리의 루트입니다. 다만 기본 인덱스 행은 표 트리 자체를 가리킵니다.
- 열 형식 번호 가운데 자주 보는 것은 4 (32비트 정수), 8 (DateTime), 9 (Binary), 10 (Text), 11 (LongBinary), 12 (LongText), 15 (64비트 정수), 16 (GUID) 입니다.

### 표 레코드의 짜임

- 열 ID 범위가 저장 방식을 정합니다. 1 ~ 127 은 고정 길이 열, 128 ~ 255 는 가변 길이 열, 256 이상은 태그 열 (Tagged Column) 입니다.
- 레코드 머리는 4바이트입니다. 마지막 고정 열 ID (1바이트), 마지막 가변 열 ID (1바이트), 가변 열 영역의 오프셋 (2바이트, 레코드 시작 기준) 순서입니다.
- 고정 열 값은 ID 순서대로 이어집니다. 크기는 카탈로그의 열 형식으로 정합니다. 고정 열 뒤에 짧은 추가 바이트가 올 수 있으므로 가변 열 위치는 머리의 오프셋으로 찾습니다.
- 가변 열 영역은 2바이트짜리 끝 위치 배열로 시작합니다. 끝 위치는 누적값입니다. 맨 위 비트가 켜진 칸은 빈 값입니다.
- 태그 열은 가변 열 뒤에 옵니다. 4바이트 항목(열 ID 2바이트, 오프셋 2바이트)의 배열 뒤에 값이 이어집니다. 값이 없는 태그 열은 레코드에 아무것도 남기지 않습니다.
- 태그 열 값에는 압축·긴 값·다중 값 표시가 붙을 수 있습니다. 푸는 법은 [긴 값과 압축 열](long-value-compressed-column.md) 에서 다룹니다.

### 버전에 따라 달라지는 점

표의 Windows 개정은 모두 형식 버전 `0x620` 입니다.

| 형식 개정 | 쓰인 곳 | 구조에서 바뀐 점 |
|---|---|---|
| `0x09` | Windows XP SP3 | — |
| `0x0B` | Exchange 2003 SP1 | ECC 체크섬이 든 페이지 헤더가 들어옵니다. |
| `0x0C` | Windows Vista | 카탈로그에 `KeyMost` 열이 생깁니다. |
| `0x11` | Windows 7 | 2·16·32 KiB 페이지를 씁니다. 16·32 KiB 는 80바이트 헤더와 15비트 태그를 씁니다. 열 압축이 들어옵니다. |
| `0x14` | Exchange 2013·Active Directory 2016 | 카탈로그에 `LVChunkMax` 열이 생깁니다. |
| `0xC8` | Windows 11 21H2 | — |
| `0xE6` | Windows 11 | 카탈로그에 `SortID` 열이 생깁니다. |
| `0x122` | — | 페이지 헤더 34 오프셋 값의 위 4비트가 예약됩니다. |

## 읽는 법

1. 사본에서 작업합니다. 원본 해시를 먼저 구해 둡니다.
2. 파일 헤더에서 서명, 페이지 크기, 형식 개정, 상태를 읽습니다. 헤더 체크섬이 맞지 않으면 두 번째 페이지의 사본과 비교합니다.
3. 페이지 크기로 형식을 고릅니다. 8 KiB 이하면 40바이트 헤더와 13비트 태그입니다. 16·32 KiB 면 80바이트 헤더와 15비트 태그입니다.
4. 페이지 4 로 가서 헤더의 FDP 개체 ID 가 2 인지 확인합니다.
5. 카탈로그 트리를 잎까지 내려가 행을 모두 읽습니다. 표 이름과 FDP 페이지, 열 ID·형식·이름, 인덱스와 긴 값 트리의 페이지를 목록으로 만듭니다.
6. 읽을 표의 FDP 페이지로 갑니다. 가지 엔트리의 자식 페이지 번호를 따라 첫 잎까지 내려갑니다.
7. 잎의 엔트리를 읽고, 다음 페이지 번호로 옆 잎으로 넘어갑니다. 다음 페이지 번호가 0 이면 끝입니다.
8. 레코드를 카탈로그의 열 정의로 풉니다. 긴 값과 압축 열은 따로 풉니다.

### 헥스로 한 번 따라가기

아래는 명세로 만든 예시입니다. 실제 검체에서 나온 값이 아닙니다. `??` 는 이 설명에 쓰지 않는 바이트입니다. 페이지 크기는 4 KiB 로 가정합니다.

파일 헤더에서 서명, 상태, 개정, 페이지 크기를 읽습니다.

```
0000: ?? ?? ?? ?? EF CD AB 89 20 06 00 00 00 00 00 00   체크섬 / 서명 / 형식 0x620 / 종류 0
0030: ?? ?? ?? ?? 02 00 00 00 ?? ?? ?? ?? ?? ?? ?? ??   상태 2 (비정상 종료)
00E0: ?? ?? ?? ?? ?? ?? ?? ?? 11 00 00 00 00 10 00 00   개정 0x11 / 페이지 크기 0x1000
```

페이지 4 는 `(4 + 1) × 0x1000 = 0x5000` 에 있습니다.

```
5010: 00 00 00 00 00 00 00 00 02 00 00 00 ?? ?? ?? ??   이전 0 / 다음 0 / FDP 개체 ID 2
5020: ?? ?? ?? ?? 03 28 00 00                           플래그 0x00002803
```

- FDP 개체 ID 가 2 이므로 카탈로그 페이지가 맞습니다.
- 플래그 `0x2803` 은 `0x2000` (새 체크섬) + `0x0800` (새 레코드 형식) + `0x0002` (잎) + `0x0001` (루트) 입니다. 카탈로그가 페이지 하나에 다 들어간 경우입니다.

페이지 끝(`0x6000`) 바로 앞 8바이트가 태그 1 과 태그 0 입니다.

```
5FF8: 50 00 10 00 10 00 00 00   태그 1 (크기 0x0050, 오프셋 0x0010) / 태그 0 (크기 0x0010, 오프셋 0x0000)
```

- 태그 0 의 값은 `0x5000 + 40 = 0x5028` 부터 16바이트입니다. 루트 헤더입니다.
- 태그 1 의 값은 `0x5028 + 0x10 = 0x5038` 부터 80바이트입니다. 첫 카탈로그 행입니다.
- 오프셋 칸이 `10 40` (`0x4010`) 이었다면 위 3비트 값은 2 입니다. 곧 지움 표시가 된 값이고, 실제 오프셋은 `0x0010` 입니다.

첫 행이 카탈로그 자신의 표 행이라고 가정하면 엔트리는 아래와 같습니다.

```
5038: 0D 00 7F 80 00 00 02 7F 80 01 7F 80 00 00 02      키 길이 13 / 키 (ObjidTable 2, Type 1, Id 2)
5047: ?? ?? ?? ??                                       레코드 머리 4바이트
504B: 02 00 00 00 01 00 02 00 00 00 04 00 00 00         ObjidTable 2 / Type 1 / Id 2 / FDP 페이지 4
```

- 레코드는 키 뒤 `0x5047` 에서 시작합니다.
- `ColtypOrPgnoFDP` 는 고정 열 시작에서 10바이트 뒤인 `0x5055` 에 있습니다. 값 4 는 이 표의 트리가 페이지 4 에서 시작한다는 뜻입니다.
- 다른 표의 행에서도 같은 자리의 값을 읽습니다. 그 값이 그 표의 FDP 페이지이므로 6단계로 넘어갑니다.

## 포렌식에서 중요한 점

### 비정상 종료 파일을 페이지로 읽을 때

헤더 52 오프셋이 2 면 비정상 종료 (Dirty Shutdown) 상태입니다. 페이지를 직접 읽으면 로그 없이 파일에 적힌 것만 보므로 로그에만 있는 변경은 보이지 않고, 로그로 복구할지 고르는 기준은 [트랜잭션 로그와 비정상 종료 상태](edb-log-dirty-shutdown.md) 에서 다룹니다.

비정상 종료 DB 의 긴 값 트리에서는 트리가 어긋난 사례가 있습니다. 가지 엔트리가 가리킨 잎에 찾는 키가 없고 다음 잎이나 다음 가지에 있었습니다. 키로 찾다가 없으면 옆 페이지까지 확인합니다.

### 트리 밖에 남는 데이터

트리에서 빠진 페이지, 빈 페이지, 지움 표시가 붙은 태그에 옛 레코드가 남을 수 있습니다. 레코드를 지워도 태그와 데이터 영역은 그대로 남고, 레코드 수와 페이지 플래그만 바뀝니다.

한 표의 페이지는 루트에서 트리를 따라 모을 수도 있고, 파일 전체에서 헤더의 FDP 개체 ID 가 같은 페이지를 골라 모을 수도 있습니다. 두 번째 방법은 트리에서 빠진 페이지까지 모으므로 같은 레코드가 겹치거나 지운 레코드가 섞입니다. 찾는 절차와 스크럽 (`0x4000`) 의 한계는 [파일 안에 남은 지운 레코드](deleted-records.md) 에서 다룹니다.

### 손상된 파일

- 손상된 DB 는 읽는 방식에 따라 행 수가 다를 수 있고, 트리를 끝까지 못 따라간 쪽이 적게 냅니다(사례는 [허브](index.md) 참고). 트리 따라가기와 FDP 개체 ID 모으기를 둘 다 해 보고 결과를 맞춰 봅니다. [도구 결과 교차 검증](../../../03-techniques/reporting/tool-validation.md) 도 함께 봅니다.
- 카탈로그 페이지가 망가졌다면 페이지 24 의 카탈로그 사본 `MSysObjectsShadow` 를 읽어 봅니다.
- 페이지 체크섬이 맞지 않으면 그 페이지는 손상됐거나 다른 자리에서 왔을 수 있습니다.
- DB 가 아예 열리지 않으면 페이지에서 레코드를 직접 찾습니다. [레코드 카빙](../../../03-techniques/analysis/data-recovery/record-carving.md) 을 봅니다.

### 시각 값

파일 구조 안의 시각은 두 종류입니다. 둘 다 FILETIME 이 아닙니다.

| 값 | 위치 | 형식 | 뜻 |
|---|---|---|---|
| DBTIME | 파일 헤더 16, 페이지 헤더 8 | 64비트 정수 | DB 작업마다 늘어나는 순번입니다. 벽시계 시각이 아닙니다. 페이지끼리 어느 쪽이 나중에 바뀌었는지 견줄 때만 씁니다. |
| 만든 시각 | 파일 헤더 28 | JET_LOGTIME | DB 를 처음 만든 때 |
| 정상 종료 시각 | 파일 헤더 64 | JET_LOGTIME | 마지막으로 깨끗이 닫힌 때 |
| 연결·분리 시각 | 파일 헤더 72·88 | JET_LOGTIME | 엔진이 DB 를 마지막으로 붙인 때와 떼어 낸 때 |

JET_LOGTIME 은 8바이트이며 초·분·시·일·월·연이 1바이트씩 들어 있고, 연에는 1900 을 더합니다. 7번째 바이트(6 오프셋)의 맨 아래 비트가 UTC 표시 (fTimeIsUTC) 이며, 이 비트가 켜져 있으면 UTC 이고 꺼져 있으면 UTC 라고 단정하지 않고 다른 시각과 맞춰 봅니다. 헤더 시각은 엔진이 DB 를 열고 닫은 때를 알려 줄 뿐, 사용자가 그 앱으로 무엇을 했는지는 알려 주지 않습니다.

레코드 속 시각은 구조가 아니라 열 값입니다. DateTime 열의 설명은 자료마다 다릅니다. libyal 명세는 FILETIME 으로 적습니다. 1899년 12월 30일부터 센 날수를 실수로 적는 형식(OLE 날짜)으로 설명하는 자료도 있습니다. 앱이 시각을 정수 열에 넣기도 합니다. 여러 형식으로 풀어 보고 앞뒤가 맞는 쪽을 고릅니다. 형식별 변환은 [시각 값 형식](../../value-decoding/filetime-unix-webkit-dos-ole.md) 에 있습니다.

## 함정

- 위치 계산은 두 군데에서 자주 틀립니다. 헤더 두 장 때문에 페이지 n 은 `(n + 1) × 페이지 크기` 에 있습니다. 태그 오프셋에는 헤더 길이(40 또는 80)를 더해야 합니다.
- 페이지 크기를 4 KiB 로 가정하면 안 됩니다. 헤더의 값을 씁니다. 페이지 크기 값이 0 이면 4 KiB 입니다.
- 한 파일에 옛 체크섬 형식과 새 형식이 섞일 수 있습니다. 새 엔진은 고쳐 쓴 페이지만 새 형식으로 바꿉니다. 그래서 형식은 페이지마다 플래그 `0x2000` 으로 판단합니다.
- 8 KiB 이하의 새 형식 페이지는 헤더에 자기 페이지 번호가 없습니다. 파일에서 떼어 낸 페이지는 원래 위치를 알아야 번호를 셀 수 있습니다.
- 16·32 KiB 페이지에서는 엔트리 첫 2바이트의 위 3비트가 태그 플래그입니다. 이 비트를 지우지 않고 읽으면 키 길이가 틀립니다.
- 표와 열 이름은 카탈로그에 적힌 그대로 씁니다. 같은 아티팩트라도 버전에 따라 열 이름이 다를 수 있습니다. 예는 [허브](index.md) 와 [파일 속성 되살리기 (PropertyStore)](../../../02-artifacts/file-folder-usage/windows-search/propertystore.md) 에 있습니다.
- Text 열의 코드페이지가 1200 이어도 값이 ASCII 로 들어 있을 수 있습니다. 길이가 짝수면 UTF-16LE 로 먼저 풀어 봅니다. 인코딩은 [문자 인코딩](../../value-decoding/utf-16le-utf-8-cp949.md) 을 봅니다.
- 긴 값은 조각 경계를 잘못 계산해도 오류 없이 값이 망가집니다. [긴 값과 압축 열](long-value-compressed-column.md) 을 봅니다.

## 도구

- 페이지를 직접 해석하는 공개 구현으로 libesedb(`esedbinfo`·`esedbexport`), Python 의 dissect.esedb, Impacket 의 ESE 모듈이 있습니다. 로그 없이 파일만 읽습니다.
- Windows 에 들어 있는 esentutl 은 Windows 의 ESE 엔진으로 파일을 다룹니다. 헤더 정보를 보여 주는 기능이 있습니다. 복구 기능은 파일을 고치므로 사본에서만 씁니다.
- 한 도구의 결과를 그대로 믿지 않습니다. 엔진으로 여는 쪽과 페이지를 직접 읽는 쪽을 하나씩 골라 결과를 비교합니다.
