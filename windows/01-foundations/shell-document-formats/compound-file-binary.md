# OLE 복합 파일 (Compound File Binary)

## 한 줄 요약

OLE 복합 파일 (Compound File Binary) 은 파일 하나 안에 작은 파일 시스템을 넣은 컨테이너 형식입니다. OLE2, Compound Binary File, Compound Document File 이라고도 부르고, libyal 은 OLECF 라고 부릅니다. 파일 머리 뒤에 같은 크기의 섹터가 이어지고, 할당 표가 섹터를 사슬로 묶습니다. 디렉터리 항목은 저장소 (Storage) 와 스트림 (Stream) 을 나무 모양으로 묶습니다. libolecf 문서는 이 구조가 FAT 파일 시스템과 비슷하다고 적습니다.

## 이 형식을 쓰는 아티팩트

| 아티팩트 | 이 형식이 들어가는 곳 | 페이지 |
|---|---|---|
| Office 97–2003 문서 | 파일 전체. 이 형식을 쓰는 파일로 널리 알려져 있습니다 | [문서 메타데이터](/02-artifacts/embedded-metadata/document-metadata/index.md) |
| 점프리스트 자동 목록 | `.automaticDestinations-ms` 파일 전체. 안에 `DestList` 스트림과 16진수 이름 스트림이 있습니다 | [점프리스트](/02-artifacts/file-folder-usage/jump-lists.md) |

- 점프리스트의 16진수 이름 스트림은 이름이 정규식 `^[1-9a-f][0-9a-f]*$` 에 맞습니다.
- 번호 스트림에 든 LNK 데이터의 형식은 [바로가기 형식](/01-foundations/shell-document-formats/shell-link-lnk.md) 에서 다룹니다.

### 형식 버전

| 주 버전 | 섹터 크기 | 다른 점 |
|---|---|---|
| 3 | 512바이트 (섹터 시프트 0x0009) | 디렉터리 섹터 수 칸은 반드시 0 입니다. 스트림 크기는 0x80000000 (2GB) 이하입니다 |
| 4 | 4,096바이트 (섹터 시프트 0x000C) | 512바이트 머리 뒤 3,584바이트를 반드시 0 으로 채웁니다 |

- libyal 문서가 본 주·부 버전 조합은 3/33, 3/62 (Office 2010), 4/62 입니다. 4/62 의 예로는 `msninfo.dat` 를 적었습니다.
- Windows 11 PC 한 대의 `AutomaticDestinations` 폴더에 있던 22개 파일은 모두 주 버전 3 이었습니다 (확인 범위: Windows 11 Home 10.0.26200, PC 한 대).

## 구조

### 전체 모양

- 파일은 파일 머리와 여러 종류의 섹터로 이루어집니다.
- 섹터는 할당 표, 디렉터리, 스트림 가운데 하나를 담습니다.
- 할당 표는 섹터를 어떻게 쓰는지 적습니다.
- 디렉터리는 스트림 사이의 계층을 적습니다.
- 스트림은 실제 내용을 담습니다.
- 날짜·시각은 UTC 기준 FILETIME 입니다. 푸는 법은 [시각 값 형식](/01-foundations/value-decoding/filetime-unix-webkit-dos-ole.md) 에서 다룹니다.
- 유니코드 문자열은 BOM 없는 UTF-16LE 입니다.

Microsoft MS-CFB 명세와 libyal 문서는 같은 것을 다른 이름으로 부릅니다.

| MS-CFB 이름 | libyal 이름 | 뜻 |
|---|---|---|
| FAT | SAT | 섹터 할당 표 |
| 미니 FAT (Mini FAT) | SSAT | 미니 섹터 할당 표 |
| DIFAT (Double Indirect FAT) | MSAT | FAT 섹터의 위치 목록 |

이 글은 MS-CFB 이름을 씁니다.

### 파일 머리 (512바이트)

파일 머리는 반드시 파일 오프셋 0 에 있습니다.

| 오프셋 | 16진 | 크기 | 뜻 |
|---|---|---|---|
| 0 | 0x00 | 8 | 서명 `D0 CF 11 E0 A1 B1 1A E1` |
| 8 | 0x08 | 16 | Header CLSID. 예약 칸이며 반드시 모두 0 입니다 |
| 24 | 0x18 | 2 | 부 버전. 주 버전이 3·4 면 0x003E 여야 합니다 (SHOULD) |
| 26 | 0x1A | 2 | 주 버전. 반드시 0x0003 이나 0x0004 입니다 |
| 28 | 0x1C | 2 | 바이트 순서. 반드시 0xFFFE 입니다. 리틀 엔디언이라는 표시이고, 파일 바이트로는 `FE FF` 입니다 |
| 30 | 0x1E | 2 | 섹터 시프트. 버전 3 은 0x0009, 버전 4 는 0x000C 입니다 |
| 32 | 0x20 | 2 | 미니 섹터 시프트. 반드시 0x0006 입니다. 미니 섹터는 64바이트입니다 |
| 34 | 0x22 | 6 | 예약 (0) |
| 40 | 0x28 | 4 | 디렉터리 섹터 수. 버전 3 에서는 반드시 0 입니다 |
| 44 | 0x2C | 4 | FAT 섹터 수 |
| 48 | 0x30 | 4 | 첫 디렉터리 섹터 번호 |
| 52 | 0x34 | 4 | 트랜잭션 서명 번호 (Transaction Signature Number) |
| 56 | 0x38 | 4 | 미니 스트림 기준 크기. 반드시 0x00001000 (4,096) 입니다 |
| 60 | 0x3C | 4 | 첫 미니 FAT 섹터 번호 |
| 64 | 0x40 | 4 | 미니 FAT 섹터 수 |
| 68 | 0x44 | 4 | 첫 DIFAT 섹터 번호 |
| 72 | 0x48 | 4 | DIFAT 섹터 수 |
| 76 | 0x4C | 436 | DIFAT. 처음 109개 FAT 섹터의 번호입니다 |

- 옛 OLE2 베타 버전은 서명으로 `0E 11 FC 0D D0 CF 11 0E` 를 썼습니다.
- 트랜잭션 서명 번호는 트랜잭션을 지원하는 구현이 저장할 때마다 올릴 수 있습니다 (MAY). 지원하지 않는 구현은 0 을 적습니다.

### 섹터 번호와 특수 값

- 섹터 번호 (Sector ID) 로 파일 오프셋을 구하는 식은 (섹터 번호 + 1) × 섹터 크기입니다.
- 1 을 더하는 까닭은 첫 섹터 자리를 파일 머리가 차지하기 때문입니다.

할당 표 칸에는 다음 특수 값이 들어갈 수 있습니다. 값은 libolecf 문서 본문의 표를 따릅니다.

| 값 | 뜻 |
|---|---|
| 0xFFFFFFFC | DIFAT 섹터 |
| 0xFFFFFFFD | FAT 섹터 |
| 0xFFFFFFFE | 사슬 끝 |
| 0xFFFFFFFF | 빈 (Free) 섹터 |

### FAT 와 DIFAT

- FAT 는 사슬 방식입니다. 칸마다 다음 섹터 번호나 사슬 끝 값이 들어 있습니다.
- 스트림 하나는 섹터 사슬 하나입니다.
- FAT 섹터 하나에는 (섹터 크기 ÷ 4) 개 칸이 있습니다.
- 파일 머리의 DIFAT 는 109칸입니다. 더 필요하면 DIFAT 섹터를 씁니다.
- DIFAT 섹터마다 마지막 칸은 다음 DIFAT 섹터를 가리킵니다. 그래서 DIFAT 섹터 하나에는 FAT 섹터 번호가 (섹터 크기 ÷ 4) − 1 개 들어갑니다.
- 파일 머리의 DIFAT 칸에는 사슬 끝 값이 없습니다. 쓰지 않는 칸은 빈 값 (0xFFFFFFFF) 입니다.
- 추가 DIFAT 섹터가 없으면 파일 머리 오프셋 68 의 값은 0xFFFFFFFE 입니다.

### 미니 스트림

- 크기가 4,096바이트보다 작은 사용자 스트림은 미니 FAT 와 미니 스트림 (Mini Stream) 에 둡니다.
- 4,096바이트와 같거나 큰 스트림은 일반 섹터에 두고 FAT 로 따라갑니다.
- 미니 스트림은 작은 스트림들을 64바이트 미니 섹터로 나눠 담는 스트림입니다.
- 미니 스트림 자체의 자리는 뿌리 항목 (Root Entry) 의 시작 섹터와 크기로 찾습니다.
- 미니 섹터 번호의 위치는 미니 스트림 안에서 (미니 섹터 번호 × 64) 입니다.
- 미니 스트림도 FAT 사슬입니다. 그래서 실제 파일 위치는 미니 스트림의 사슬을 따라가 구합니다.

### 디렉터리 항목 (128바이트)

- 디렉터리 항목은 128바이트로 크기가 정해져 있습니다.
- 512바이트 섹터 (버전 3) 하나에 4개, 4,096바이트 섹터 (버전 4) 하나에 32개가 들어갑니다.
- 할당되지 않은 항목이 있어서, 항목 수가 실제 저장소·스트림 수보다 많을 수 있습니다.

| 오프셋 | 16진 | 크기 | 뜻 |
|---|---|---|---|
| 0 | 0x00 | 64 | 이름. UTF-16 이고 끝 NULL 을 포함해 최대 32글자입니다. `/`, `\`, `:`, `!` 는 쓸 수 없습니다 |
| 64 | 0x40 | 2 | 이름 길이. 끝 NULL 을 포함한 바이트 수이고, 2의 배수이며 64 이하입니다 |
| 66 | 0x42 | 1 | 종류 |
| 67 | 0x43 | 1 | 색. 0x00 빨강, 0x01 검정 (레드-블랙 트리) |
| 68 | 0x44 | 4 | 왼쪽 형제 ID |
| 72 | 0x48 | 4 | 오른쪽 형제 ID |
| 76 | 0x4C | 4 | 자식 ID |
| 80 | 0x50 | 16 | CLSID. 저장소와 뿌리만 씁니다. 스트림은 반드시 0 입니다 |
| 96 | 0x60 | 4 | 상태 비트 (State Bits). 사용자 플래그입니다. 스트림은 0 이어야 합니다 (SHOULD) |
| 100 | 0x64 | 8 | 만든 시각 (FILETIME, UTC) |
| 108 | 0x6C | 8 | 수정 시각 (FILETIME, UTC) |
| 116 | 0x74 | 4 | 시작 섹터 |
| 120 | 0x78 | 8 | 스트림 크기 |

**종류**

| 값 | 뜻 |
|---|---|
| 0x00 | 알 수 없음 또는 할당 안 됨 |
| 0x01 | 저장소 |
| 0x02 | 스트림 |
| 0x05 | 뿌리 저장소 |

- MS-CFB 는 위 네 값만 유효하다고 봅니다.
- libolecf 문서의 표에는 0x03 (lock bytes) 과 0x04 (property) 도 있습니다.

**형제·자식 ID**

- 항목이 없으면 NOSTREAM (0xFFFFFFFF) 입니다.
- 일반 ID 는 0 부터 0xFFFFFFF9 까지이고, 최대값 MAXREGSID 는 0xFFFFFFFA 입니다.
- 스트림 항목에는 자식이 없습니다. 그래서 스트림의 자식 ID 는 늘 NOSTREAM 입니다.
- 이름으로 항목을 찾을 때는 (뿌리 제외) 대소문자를 가리지 않는 특별한 대문자 변환 규칙으로 비교합니다.

**시각·시작 섹터·크기**

| 칸 | 저장소 | 스트림 | 뿌리 |
|---|---|---|---|
| 만든 시각 | 기록합니다 | 반드시 0 | 반드시 0 |
| 수정 시각 | 기록합니다 | 반드시 0 | 0 이어도 됩니다 (MAY) |
| 시작 섹터 | 0 | 스트림의 첫 섹터 | 미니 스트림의 첫 섹터 |
| 스트림 크기 | 0 | 스트림 크기 | 미니 스트림 크기 |

- 두 시각이 모두 0 이면 "기록되지 않음" 을 뜻합니다.
- 뿌리의 만든 시각은 복합 파일 자체의 시각입니다. 그래서 파일 시스템 쪽에서 얻습니다.
- 버전 3 에서는 스트림 크기가 0x80000000 이하여야 하고, 상위 32비트는 0 이어야 합니다.
- libolecf 문서는 오프셋 120 을 4바이트 크기와 4바이트 예약 칸 (124) 으로 적습니다. 버전 3 기준 해석입니다.

**뿌리 항목**

- 뿌리 항목은 디렉터리 사슬의 첫 항목이고 종류는 0x05 입니다.
- 오래된 구현은 뿌리 이름을 "R" 한 글자만 적기도 합니다.

### 속성 집합 스트림

- 공유 속성 집합 (Property Set) 스트림은 이름이 "\005" (0x05) 로 시작합니다. `\005SummaryInformation`, `\005DocumentSummaryInformation` 이 그 예입니다.
- 요약 정보의 형식 ID (FMTID) 는 `f29f85e0-4ff9-1068-ab91-08002b27b3d9` 입니다.
- 문서 요약 정보의 형식 ID 는 `d5cdd502-2e9c-101b-9397-08002b2cf9ae` 입니다.
- `\1CompObj` 스트림은 포함 객체의 클립보드 형식과 표시 이름을 담습니다.

속성 집합 머리 (28바이트):

| 오프셋 | 크기 | 뜻 |
|---|---|---|
| 0 | 2 | 바이트 순서 |
| 2 | 2 | 형식 |
| 4 | 4 | 시스템 버전. 상위 16비트가 플랫폼입니다 (0 Win16, 1 Mac, 2 Win32). libolecf 문서에 불확실 표시가 있습니다 |
| 8 | 16 | 클래스 ID |
| 24 | 4 | 섹션 수 |

- 섹션 목록 항목은 20바이트입니다. 16바이트 형식 ID 와 4바이트 위치로 이루어집니다.
- 섹션 머리는 8바이트입니다. 데이터 크기와 속성 수로 이루어집니다.
- 속성 목록 항목은 8바이트입니다. 속성 ID 와 위치로 이루어집니다.
- 속성 값은 4바이트 값 종류 (VARIANT 형) 뒤에 데이터가 옵니다.
- VT_LPWSTR 문자열의 크기는 글자 수로 적습니다.
- 속성 ID 가 무엇을 뜻하는지는 [문서 메타데이터](/02-artifacts/embedded-metadata/document-metadata/index.md) 에서 다룹니다.

## 읽는 법

1. 오프셋 0 의 서명, 오프셋 28 의 바이트 순서, 오프셋 26 의 주 버전을 확인합니다. 섹터 시프트로 섹터 크기를 정합니다.
2. 파일 머리의 DIFAT 109칸에서 FAT 섹터 번호를 모읍니다. 추가 DIFAT 섹터가 있으면 마지막 칸을 따라가며 더 모읍니다.
3. FAT 섹터들을 이어 붙여 FAT 를 만듭니다.
4. 오프셋 48 의 첫 디렉터리 섹터에서 시작해 FAT 사슬을 따라 디렉터리를 모두 읽습니다.
5. 0번 항목인 뿌리 항목에서 미니 스트림의 시작 섹터와 크기를 읽습니다. 미니 스트림도 FAT 사슬로 모읍니다.
6. 오프셋 60 의 첫 미니 FAT 섹터에서 시작해 미니 FAT 를 모읍니다.
7. 뿌리 항목의 자식 ID 부터 나무를 내려갑니다. 같은 층의 다른 항목은 왼쪽·오른쪽 형제 ID 로 찾습니다. 저장소 아래 항목은 그 저장소의 자식 ID 로 찾습니다.
8. 스트림마다 크기를 봅니다. 4,096바이트보다 작으면 미니 FAT 로, 아니면 FAT 로 사슬을 따라 내용을 읽습니다.

### 헥스로 한 번

아래는 MS-CFB 명세와 libolecf 문서를 보고 만든 예시입니다. 실제 검체에서 뽑은 값이 아닙니다. 버전 3 파일이고, 스트림 `Data` 하나만 담았습니다.

**파일 머리 (파일 오프셋 0x000)**

```
오프셋  00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F
0x000   D0 CF 11 E0 A1 B1 1A E1 00 00 00 00 00 00 00 00
0x010   00 00 00 00 00 00 00 00 3E 00 03 00 FE FF 09 00
0x020   06 00 00 00 00 00 00 00 00 00 00 00 01 00 00 00
0x030   01 00 00 00 00 00 00 00 00 10 00 00 02 00 00 00
0x040   01 00 00 00 FE FF FF FF 00 00 00 00 00 00 00 00
0x050   FF FF FF FF FF FF FF FF FF FF FF FF FF FF FF FF
(0x060~0x1FF 모두 FF)
```

1. 0x000 의 8바이트는 복합 파일 서명입니다.
2. 0x018 의 `3E 00` 은 부 버전 0x003E 입니다. 0x01A 의 `03 00` 은 주 버전 3 입니다.
3. 0x01C 의 `FE FF` 는 바이트 순서 0xFFFE 입니다.
4. 0x01E 의 `09 00` 은 섹터 시프트 9 입니다. 섹터는 512바이트입니다.
5. 0x020 의 `06 00` 은 미니 섹터 시프트 6 입니다. 미니 섹터는 64바이트입니다.
6. 0x02C 의 `01 00 00 00` 은 FAT 섹터 수 1 입니다.
7. 0x030 의 `01 00 00 00` 은 첫 디렉터리 섹터 번호 1 입니다. 파일 오프셋은 (1 + 1) × 512 = 0x400 입니다.
8. 0x038 의 `00 10 00 00` 은 미니 스트림 기준 크기 4,096 입니다.
9. 0x03C 의 `02 00 00 00` 은 첫 미니 FAT 섹터 번호 2 입니다. 파일 오프셋은 0x600 입니다.
10. 0x040 의 `01 00 00 00` 은 미니 FAT 섹터 수 1 입니다.
11. 0x044 의 `FE FF FF FF` 는 추가 DIFAT 섹터가 없을 때의 값입니다. 0x048 의 DIFAT 섹터 수도 0 입니다.
12. 0x04C 의 `00 00 00 00` 은 DIFAT 첫 칸입니다. FAT 는 섹터 0, 곧 파일 오프셋 0x200 에 있습니다.
13. 0x050 부터 끝까지는 쓰지 않는 DIFAT 칸이라 0xFFFFFFFF 입니다.

**FAT (섹터 0, 파일 오프셋 0x200)**

```
오프셋  00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F
0x200   FD FF FF FF FE FF FF FF FE FF FF FF FE FF FF FF
0x210   FF FF FF FF FF FF FF FF FF FF FF FF FF FF FF FF
(0x220~0x3FF 모두 FF)
```

14. 0번 칸 `FD FF FF FF` 는 섹터 0 이 FAT 섹터라는 뜻입니다.
15. 1번 칸 `FE FF FF FF` 는 디렉터리 사슬이 섹터 1 하나로 끝난다는 뜻입니다.
16. 2번 칸은 미니 FAT 사슬, 3번 칸은 미니 스트림 사슬입니다. 둘 다 섹터 하나로 끝납니다.
17. 4번 칸부터는 빈 섹터입니다.

**디렉터리 (섹터 1, 파일 오프셋 0x400) — 뿌리 항목**

```
오프셋  00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F
0x400   52 00 6F 00 6F 00 74 00 20 00 45 00 6E 00 74 00
0x410   72 00 79 00 00 00 00 00 00 00 00 00 00 00 00 00
0x420   00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
0x430   00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
0x440   16 00 05 01 FF FF FF FF FF FF FF FF 01 00 00 00
0x450   00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
0x460   00 00 00 00 00 00 00 00 00 00 00 00 00 0C D0 22
0x470   51 91 DB 01 03 00 00 00 40 00 00 00 00 00 00 00
```

18. 0x400 부터 이름 `Root Entry` 가 UTF-16LE 로 있습니다.
19. 0x440 의 `16 00` 은 이름 길이 22바이트입니다. 10글자와 끝 NULL 을 합친 값입니다.
20. 0x442 의 `05` 는 뿌리 저장소입니다. 0x443 의 `01` 은 검정입니다.
21. 0x444 와 0x448 의 `FF FF FF FF` 는 형제가 없다는 뜻입니다.
22. 0x44C 의 `01 00 00 00` 은 자식 ID 1 입니다.
23. 0x464 (항목 +100) 의 만든 시각은 0 입니다. 뿌리는 반드시 0 입니다.
24. 0x46C (항목 +108) 의 `00 0C D0 22 51 91 DB 01` 은 수정 시각입니다. FILETIME 0x01DB915122D00C00 이고, 2025-03-10 00:12:40 UTC 입니다.
25. 0x474 (항목 +116) 의 `03 00 00 00` 은 미니 스트림의 첫 섹터 3 입니다. 파일 오프셋은 (3 + 1) × 512 = 0x800 입니다.
26. 0x478 (항목 +120) 의 `40 00 00 00 00 00 00 00` 은 미니 스트림 크기 64 입니다.

**디렉터리 — 1번 항목 (파일 오프셋 0x480)**

1번 항목의 칸 값은 아래와 같습니다. 헥스는 줄였습니다.

| 칸 | 값 | 뜻 |
|---|---|---|
| 이름 (+0) | `44 00 61 00 74 00 61 00 00 00` | `Data` |
| 이름 길이 (+64) | `0A 00` | 10바이트 |
| 종류 (+66) | `02` | 스트림 |
| 형제·자식 ID (+68·+72·+76) | 모두 `FF FF FF FF` | 없음 |
| 두 시각 (+100·+108) | 모두 0 | 스트림은 반드시 0 |
| 시작 섹터 (+116) | `00 00 00 00` | 미니 섹터 0 |
| 크기 (+120) | `30 00 00 00 00 00 00 00` | 48바이트 |

27. 크기 48 은 4,096 보다 작습니다. 그래서 시작 섹터 0 은 미니 섹터 번호입니다.
28. 미니 FAT (파일 오프셋 0x600) 의 0번 칸이 `FE FF FF FF` 라고 둡니다. 이 스트림은 미니 섹터 하나로 끝납니다.
29. 미니 섹터 0 은 미니 스트림 안에서 0 × 64 = 0 에 있습니다. 미니 스트림이 파일 오프셋 0x800 에서 시작하므로, 내용은 0x800 부터 48바이트입니다.
30. 같은 섹터의 2번·3번 항목 (0x500·0x580) 은 종류 0x00 인 빈 항목입니다.

> 그림 자리: 위 예시에서 파일 머리 → DIFAT 첫 칸 → FAT 섹터 → 디렉터리 섹터 → 뿌리 항목 → 미니 스트림 섹터 → 1번 항목의 미니 섹터 0 으로 이어지는 길을 화살표로 보여 주고, 섹터 번호와 파일 오프셋을 나란히 적은 그림

## 포렌식에서 중요한 점

### 시각

- 디렉터리 항목의 두 시각은 저장소 객체만 기록합니다.
- 스트림 항목의 두 시각은 반드시 0 입니다. 그래서 복합 파일 구조만으로는 스트림 하나하나가 언제 생겼는지 알 수 없습니다.
- 뿌리의 만든 시각은 반드시 0 입니다. 복합 파일이 언제 생겼는지는 파일 시스템의 시각에서 봅니다([마스터 파일 테이블](/02-artifacts/filesystem/mft.md)).
- 뿌리의 수정 시각은 0 이어도 됩니다.
- Windows 11 PC 한 대의 점프리스트 자동 목록 22개는 모두 뿌리의 만든 시각이 0 이고 수정 시각은 채워져 있었습니다. 가장 큰 파일의 스트림 항목 (`DestList`·`1`·`2`·`3` …) 은 두 시각이 모두 0 이었습니다 (확인 범위: Windows 11 Home 10.0.26200, PC 한 대). 명세와 맞습니다.
- Office 서식 파일 (템플릿) 에서 만든 시각이 -1 (0xFFFFFFFFFFFFFFFF) 인 사례가 있습니다. 뜻은 알려져 있지 않습니다.
- 스트림 안쪽에 시각을 따로 적는 형식도 있습니다. 점프리스트의 `DestList` 스트림이 그 예입니다([점프리스트](/02-artifacts/file-folder-usage/jump-lists.md)). Office 문서의 속성은 [문서 메타데이터](/02-artifacts/embedded-metadata/document-metadata/index.md) 에서 다룹니다.

### 지운 데이터

- 종류가 0x00 인 디렉터리 항목은 할당되지 않은 항목입니다.
- FAT 에서 빈 섹터 (0xFFFFFFFF) 로 표시된 섹터는 어느 스트림에도 속하지 않습니다.
- 두 곳에 지운 스트림의 흔적이 남는지는 이번에 연 자료로 확인하지 못했습니다. 아래는 PC 한 대에서 본 결과입니다 (확인 범위: Windows 11 Home 10.0.26200, PC 한 대).
  - 가장 큰 점프리스트 파일 (약 1.8MB) 의 디렉터리 항목 576개 가운데 248개가 종류 0x00 이었습니다. 248개 모두 이름 칸과 이름 길이가 0 이었습니다. 이 파일에서는 지운 항목의 이름이 남아 있지 않았습니다.
  - 22개 파일의 FAT 에서 빈 섹터로 표시된 섹터는 모두 256개였습니다. 256개 모두 0 이 아닌 바이트를 담고 있었습니다. 이전 데이터가 남은 것으로 보이지만 내용은 해석하지 않았습니다.
- 빈 섹터를 살펴볼 때는 섹터 번호로 파일 오프셋을 구해 직접 꺼냅니다. 복구 방법 일반은 [삭제 데이터 복구](/03-techniques/analysis/data-recovery/index.md) 에서 다룹니다.

### 손상과 낯선 값

libolecf 문서와 MS-CFB 명세에 적힌 사례입니다.

- 버전 3 에서 스트림 크기의 상위 32비트를 초기화하지 않은 예전 구현이 있습니다. 그래서 상위 32비트에 쓰레기 값이 들어 있을 수 있습니다. MS-CFB 는 버전 3 에서 상위 32비트를 무시하라고 권고합니다.
- "하위 항목 없음" 을 −1 (0xFFFFFFFF) 대신 0 으로 적은 파일이 있습니다.
- 디렉터리 항목이 아예 없는 파일이 있습니다.
- 뿌리 항목이 미사용으로 표시된 파일이 있습니다.
- libolecf 문서가 든 빈 디렉터리 항목의 예는 이름 칸 0, 형제·자식 ID 0xFFFFFFFF, 시작 섹터 0xFFFFFFFE 로 채운 128바이트입니다.

## 함정

1. **특수 값을 거꾸로 읽습니다.** libolecf 문서 끝의 "Notes" 절은 0xFFFFFFFC 와 0xFFFFFFFD 를 거꾸로 적었습니다. 본문 표 (0xFFFFFFFC = DIFAT 섹터, 0xFFFFFFFD = FAT 섹터) 를 따릅니다.
2. **버전 3 스트림 크기를 8바이트 그대로 씁니다.** 상위 32비트에 쓰레기 값이 있을 수 있습니다. 버전 3 에서는 하위 32비트만 씁니다.
3. **"없음" 을 뜻하는 0 을 항목 번호로 따라갑니다.** 0번 항목은 뿌리입니다. 형제 ID 0 을 그대로 따라가면 뿌리로 돌아가 같은 자리를 맴돕니다. 방문한 항목을 기억해 두고 되돌아오면 멈춥니다.
4. **디렉터리 항목 수를 스트림 수로 씁니다.** 할당되지 않은 항목이 섞여 있습니다. 종류가 0x01·0x02·0x05 인 항목만 셉니다.
5. **작은 스트림을 일반 섹터에서 읽습니다.** 4,096바이트보다 작은 스트림의 시작 섹터는 미니 섹터 번호입니다. 일반 섹터 번호로 읽으면 엉뚱한 내용이 나옵니다.
6. **이름의 제어 문자를 놓칩니다.** `\005SummaryInformation` 의 첫 글자는 0x05 입니다. 화면에 보이지 않는 글자라서 도구가 다른 모양으로 바꿔 보여 줄 수 있습니다. 이름을 비교할 때는 바이트로 비교합니다.
7. **스트림 시각이 0 이라서 조작을 의심합니다.** 명세상 스트림 시각은 반드시 0 입니다.
8. **컨테이너 버전으로 스트림 내용의 버전을 짐작합니다.** 복합 파일 형식은 그대로여도 스트림 안의 형식은 따로 바뀝니다. 위 Windows 11 PC 의 점프리스트 22개는 모두 주 버전 3 이었습니다. 그런데 `DestList` 머리의 형식 버전은 모두 6 이었습니다. libyal 점프리스트 문서에는 1 (Windows 7), 3·4 (Windows 10) 만 있습니다. 22개 모두 libyal 문서에 없는 `DestListPropertyStore` 스트림도 담고 있었습니다.
9. **libolecf 표의 종류 값을 그대로 받아들입니다.** libolecf 표에는 0x03·0x04 가 있지만 MS-CFB 는 0x00·0x01·0x02·0x05 만 유효하다고 봅니다. 다른 값이 나오면 손상이나 비표준 구현을 먼저 의심합니다.

## 도구

- 이 글이 따른 형식 문서는 libyal 의 libolecf 저장소에 있는 문서와 Microsoft MS-CFB 명세의 파일 머리·디렉터리 항목 절입니다.
- 점프리스트를 읽는 도구 예는 [점프리스트](/02-artifacts/file-folder-usage/jump-lists.md) 페이지에 있습니다.

도구를 쓸 때는 다음을 확인합니다.

- 할당되지 않은 디렉터리 항목과 빈 섹터를 보여 주는지 확인합니다.
- 저장소 항목의 시각을 UTC 로 보여 주는지, 0 과 -1 을 어떻게 표시하는지 확인합니다.
- 스트림을 꺼낼 때 미니 스트림과 일반 섹터를 제대로 가르는지 확인합니다. 작은 스트림 하나를 헥스로 따라가 결과와 맞춰 봅니다.
- 손상된 파일 (형제 ID 0, 뿌리 미사용) 에서 멈추거나 같은 자리를 맴돌지 않는지 확인합니다.
- 방법은 [도구 결과 교차 검증](/03-techniques/reporting/tool-validation.md) 을 봅니다.
