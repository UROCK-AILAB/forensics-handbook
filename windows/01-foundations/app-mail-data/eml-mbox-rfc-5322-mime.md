# 인터넷 메일 형식 (EML·MBOX·RFC 5322·MIME)

## 한 줄 요약

인터넷 메일 한 통은 헤더 칸 여러 개와 본문으로 된 글자 데이터입니다.
헤더와 본문의 문법은 RFC 5322 가 정합니다.
본문의 형식과 인코딩은 MIME(RFC 2045~2049)이 정합니다.
MBOX 는 메일 여러 통을 한 파일에 차례로 이어 붙인 형식입니다.
메일 한 통에는 시각이 여러 개 있고, 뜻이 저마다 다릅니다.
`Date` 칸은 보낸 시각이 아니라 작성자가 보낼 준비를 마친 시각입니다.

## 이 형식을 쓰는 아티팩트

- 메일 프로그램이 받은 메일을 어떤 형식으로 두는지는 프로그램마다 다릅니다. 프로그램별 저장 방식은 아래 페이지에서 다룹니다.
  - [아웃룩](../../02-artifacts/mail/outlook/index.md)
  - [새 Outlook](../../02-artifacts/mail/new-outlook.md)
  - [썬더버드](../../02-artifacts/mail/thunderbird.md)
  - [옛 윈도 메일 프로그램](../../02-artifacts/mail/outlook-express-windows-live-mail.md)
  - [Windows 메일 앱](../../02-artifacts/mail/hxstore.md)
- 아웃룩 저장소 안에도 원래 인터넷 헤더가 속성 하나로 남습니다. [MAPI 속성](mapi-property.md) 을 봅니다.
- `Received` 칸을 따라 전달 경로를 되짚는 방법은 [메일 헤더 분석](../../03-techniques/analysis/email-header-analysis.md) 에서 다룹니다.
- 이 페이지는 파일 안의 글자를 어떻게 나눠 읽는지만 다룹니다.

## 구조

> 그림 자리: 메일 한 통(헤더 칸들 → 빈 줄 → 본문)과, 그런 메일 여러 통이 구분 줄로 이어진 MBOX 파일을 나란히 놓은 그림

### 메시지 한 통 (RFC 5322)

RFC 5322 "Internet Message Format" 은 2008년 10월에 나온 표준 문서입니다.
이 문서가 RFC 2822 를 대체합니다.

- 메시지는 헤더 칸들 (Header Section) 뒤에 본문 (Body) 이 오는 구조입니다. 본문은 없어도 됩니다 (§2.1).
- 헤더와 본문 사이는 빈 줄로 나눕니다. 빈 줄은 CRLF 만 있는 줄입니다.
- 한 줄은 998자를 넘으면 안 됩니다. 78자 이하가 좋습니다. CRLF 는 세지 않습니다 (§2.1.1).
- 긴 헤더는 공백 앞에 CRLF 를 넣어 여러 줄로 접습니다 (Folding, §2.2.3).
- 해석할 때는 공백 바로 앞의 CRLF 를 지워 한 줄로 폅니다 (Unfolding).
- 헤더 칸의 순서는 보장되지 않습니다. 전송 중에 순서가 바뀐 사례도 있습니다 (§3.6).
- 다만 trace 칸과 resent 칸은 순서를 바꾸면 안 됩니다. 이 칸들은 메시지 앞에 블록으로 붙입니다.
- 이름이 정해지지 않은 칸도 문법만 맞으면 쓸 수 있습니다 (§3.6.8). 표준에 없는 이름의 칸이 보여도 형식 오류가 아닙니다.

### 헤더 칸과 개수 (§3.6)

꼭 있어야 하는 칸은 `Date` 와 `From` 둘뿐입니다.
아래 개수는 헤더 칸의 개수입니다.

| 칸 | 개수 | 비고 |
|---|---|---|
| `Date` | 1 | 필수 |
| `From` | 1 | 필수 |
| `Sender` | 0~1 | `From` 에 주소가 여럿이면 필수 |
| `Reply-To` | 0~1 | |
| `To`, `Cc`, `Bcc` | 각 0~1 | |
| `Message-ID` | 0~1 | 있어야 좋습니다 |
| `In-Reply-To`, `References` | 각 0~1 | 답장에는 있어야 좋습니다 |
| `Subject` | 0~1 | |
| `Comments`, `Keywords` | 제한 없음 | |
| trace 칸 | 제한 없음 | 메시지 앞에 블록으로 붙습니다 |
| resent 칸 (`Resent-*`) | 블록마다 1 | |

### Date 와 시간대 (§3.3, §3.6.1)

- `Date` 는 작성자가 메시지를 다 쓰고 배달 시스템에 넣을 준비가 됐다고 한 시각입니다.
- RFC 는 "보내기" 버튼을 누른 때를 예로 듭니다.
- 실제로 전송된 시각이 아닙니다.
- RFC 의 예: 네트워크에 붙지 않은 노트북에서 메일을 대기열에 넣었다면 `Date` 는 대기열에 넣은 시각입니다. 나중에 접속해 보낸 시각이 아닙니다.
- 날짜·시각은 요일(없어도 됨), 날짜, 시각, 시간대 순서로 적습니다.
- 시간대는 `+hhmm` 또는 `-hhmm` 꼴입니다. UTC 와의 차이입니다.
- 날짜와 시각은 현지 시각으로 적는 것이 좋습니다.

| 시간대 표기 | 뜻 |
|---|---|
| `+0000` | UTC |
| `-0000` | UTC 입니다. 다만 현지 시간대가 따로 있을 수 있는 시스템에서 만들었고, 그 현지 시간대 정보가 없다는 뜻입니다 |
| 한 글자 군사 시간대(A~Z), 뜻을 모르는 문자 시간대 | 따로 확인할 근거가 없으면 `-0000` 으로 봅니다 |

### Message-ID (§3.6.4)

- 문법은 `"<" id-left "@" id-right ">"` 입니다.
- 만드는 쪽이 유일함을 보장해야 합니다.
- RFC 는 현재 날짜·시각과 시스템의 다른 유일한 값을 섞는 방법을 예로 듭니다.
- 전송 시스템을 지나며 trace 칸이나 resent 칸이 앞에 붙어도 같은 메시지입니다. 원래 `Message-ID` 를 그대로 둡니다.

### Bcc (§3.6.3)

- `Bcc` 에는 다른 수신자에게 드러나지 않을 주소를 적습니다.
- RFC 는 쓰는 방식을 세 가지 적습니다.
- 첫째 방식은 보낼 때 `Bcc` 줄을 지웁니다.

### resent 칸 (§3.6.6)

- 메시지를 다시 보낼 때마다 resent 칸 한 묶음을 앞에 붙입니다.
- 가장 최근 묶음이 가장 앞에 옵니다.

### trace 칸 (§3.6.7, 부록 A.4)

- trace 칸은 `Return-Path` 하나(없어도 됨)와 `Received` 하나 이상입니다.
- `Received` 의 문법은 `"Received:"` 뒤에 토큰 목록, `";"`, 날짜·시각이 오는 꼴입니다.
- 메시지가 전송 시스템을 지날 때 trace 칸이 앞에 붙습니다.
- 앞에 붙는 규칙이므로 위쪽 `Received` 가 나중에 붙은 칸입니다.
- trace 칸의 자세한 해석은 RFC 5321 몫입니다. RFC 5322 에서는 참고용 정보로만 다룹니다.

### MIME (RFC 2045~2049)

MIME 은 다섯 문서로 되어 있습니다.

| 문서 | 다루는 것 |
|---|---|
| RFC 2045 | 본문 형식과 MIME 헤더 칸 (1996년 11월) |
| RFC 2046 | 미디어 타입 |
| RFC 2047 | 헤더 안의 비ASCII 글자 |
| RFC 2048 | 등록 절차 |
| RFC 2049 | 적합성 기준과 예 |

RFC 2045 가 정한 내용은 아래와 같습니다.

| 칸 | 내용 | 칸이 없을 때 |
|---|---|---|
| `MIME-Version` | `MIME-Version: 1.0` | — |
| `Content-Type` | 본문의 미디어 타입과 문자 집합 | `text/plain; charset=us-ascii` 로 봅니다 |
| `Content-Transfer-Encoding` | `7bit`, `8bit`, `binary`, `quoted-printable`, `base64` 가운데 하나(확장 토큰도 가능). 대소문자를 가리지 않습니다 | `7BIT` 로 봅니다 |
| `Content-ID` | `msg-id` 문법을 따르고 유일해야 합니다. 대체로 선택이지만 `message/external-body` 에서는 필수입니다 | — |

- base64 로 바꾼 글은 한 줄이 76자 이하입니다.
- quoted-printable 로 바꾼 글도 한 줄이 76자 이하입니다.
- quoted-printable 에서 줄 끝의 `=` 는 소프트 줄바꿈 (Soft Line Break) 입니다. 원래 글에는 그 자리에 줄바꿈이 없습니다.
- 이 페이지를 쓰며 RFC 2046·2047 은 열어 보지 않았습니다. 여러 부분 (multipart) 을 나누는 경계 문법과 헤더 안 비ASCII 글자의 인코딩 꼴은 그 RFC 에서 확인합니다.
- 첨부 파일 이름이 어느 칸에 들어가는지도 이 페이지에서는 다루지 않습니다.

### MBOX (RFC 4155)

RFC 4155 "The application/mbox Media Type" 은 2005년 9월에 나온 정보용 (Informational) 문서입니다.
이 RFC 는 mbox 에 권위 있는 명세가 없다고 적습니다.
잘 알려진 출력 형식일 뿐이라는 것입니다 (§2).

- 메일 여러 통이 한 파일에 차례로 이어집니다.
- 메일마다 구분 줄로 시작하고, 보통 빈 줄로 끝납니다.
- 구분 줄은 대개 `From` + 공백(0x20) + 주소 + 공백 + 시각 + 줄 끝입니다.
- 하지만 주소 형식, 시각 형식, 줄 끝은 모두 구현마다 크게 다릅니다.
- 여러 mbox 를 이어 붙였거나 여러 메일 프로그램이 한 파일에 썼다면 구분 줄 형식이 한 파일 안에 섞일 수 있습니다.
- 구분 줄의 시각은 최종 수신자가 받은 시각입니다. 마지막 홉 시스템이나 수신자 메일 저장소를 기준으로 합니다.
- 본문이나 헤더에 표시 없는 8비트 글자, 인코딩하지 않은 바이너리, BINHEX·UUENCODE 가 들어 있을 수 있습니다.

본문의 `From ` 줄은 구현마다 다르게 다룹니다 (§2).

| 구현 | 본문에서 `From ` 으로 시작하는 줄 |
|---|---|
| 많은 구현 | `>From ` 으로 바꿉니다 |
| 일부 구현 | 조건이 맞을 때만 바꿉니다 |
| 일부 구현 | 이미 바꾼 줄을 한 번 더 바꿉니다 |
| 일부 구현 | 바꾸지 않습니다 |

- RFC 4155 는 이 바꾸기 방식을 정하지 않습니다.
- 받는 쪽이 구분 줄 전체를 보고 판단하라고 합니다.

RFC 4155 는 "default" 형식을 따로 정합니다.

| 항목 | "default" 형식 |
|---|---|
| 구분 줄 | `From` + 공백 + 보낸이 주소(addr-spec) + 공백 + 처음 받은 시각 + 줄 끝 |
| 구분 줄 시각 | UTC. UNIX ctime 꼴이고 시간대 표시가 없습니다 |
| 줄 끝 | LF(0x0A) 하나. CRLF 는 쓰면 안 됩니다 |
| 적용 범위 | 전송하는 표준 mbox 에만 해당합니다 |
| 메일 사이 | 첫 메일 앞에는 구분 줄만 있습니다. 둘째 메일부터는 줄 끝 두 개(앞 메일의 끝 + 구분용)와 구분 줄이 옵니다 |

- UNIX 계열 변형은 RFC 가 qmail 의 mbox(5) 설명서를 가리킵니다.

### EML

- 이 페이지를 쓰며 연 자료에는 `.eml` 확장자 설명이 없었습니다.
- 그래서 `.eml` 파일이 어떤 형식인지는 확장자가 아니라 내용으로 가립니다.
- 첫 줄이 `이름: 값` 꼴 헤더 칸이고 빈 줄 뒤에 본문이 오면 RFC 5322 메시지 한 통으로 읽습니다.
- 첫 줄이 `From ` 으로 시작하면 mbox 구분 줄일 수 있습니다. 파일 안에 구분 줄이 더 있는지 봅니다.

## 읽는 법

1. **사본으로 작업합니다.** 원본 파일의 해시를 먼저 적습니다.
2. **형식을 가립니다.** 첫 줄과 줄 끝(CRLF 인지 LF 인지)을 헥스로 봅니다.
3. **mbox 면 메일 단위로 나눕니다.** 구분 줄 후보를 찾되 줄 전체 모양(`From` + 공백 + 주소 + 공백 + 시각)을 봅니다. 본문의 `From ` 줄과 헷갈리지 않게 합니다.
4. **헤더와 본문을 나눕니다.** 첫 빈 줄이 경계입니다.
5. **헤더를 폅니다.** 공백 앞의 줄 끝을 지워 접힌 칸을 한 줄로 만듭니다.
6. **칸을 뽑습니다.** `Date`, `From`, `Sender`, `To`, `Cc`, `Bcc`, `Message-ID`, `In-Reply-To`, `References`, `Subject`, resent 블록, `Received` 목록을 따로 적습니다. `Received` 는 적힌 순서도 함께 적습니다.
7. **MIME 을 풉니다.** `Content-Type` 과 `Content-Transfer-Encoding` 을 보고 base64·quoted-printable 을 풀어 원래 바이트로 돌립니다. 칸이 없으면 위 기본값을 적용합니다.
8. **시각을 정리합니다.** 아래 "시각 여러 개" 표대로 시각마다 뜻과 시간대를 붙여 적습니다.

### 헥스로 한 번 따라가기

아래 바이트는 RFC 문법대로 만든 예시입니다.
실제 메일에서 옮긴 바이트가 아닙니다.
`..` 는 설명에 필요 없는 바이트입니다.

**헤더와 본문의 경계 (RFC 5322)**

```
.. .. 0D 0A 0D 0A .. ..
```

- 첫 `0D 0A` 는 마지막 헤더 줄의 줄 끝입니다.
- 둘째 `0D 0A` 는 빈 줄입니다.
- 그 뒤가 본문입니다.
- mbox "default" 형식은 줄 끝이 LF 하나입니다. 그런 파일 안에서는 같은 경계가 `0A 0A` 로 보입니다.

**mbox 에서 둘째 메일이 시작하는 자리 ("default" 형식)**

```
.. .. 0A 0A 46 72 6F 6D 20 .. ..   ....From ...
```

- 첫 `0A` 는 앞 메일의 마지막 줄 끝입니다.
- 둘째 `0A` 는 구분용 줄 끝입니다.
- `46 72 6F 6D 20` 은 `From` 과 공백입니다.
- 그 뒤로 보낸이 주소, 공백, 시각, `0A` 가 이어집니다.

**quoted-printable 의 소프트 줄바꿈**

```
abc=
def
```

- 첫 줄 끝의 `=` 는 소프트 줄바꿈입니다.
- 풀면 줄바꿈 없는 `abcdef` 가 됩니다.

**헤더 뼈대 (값 자리만 표시)**

```
Received: <토큰 목록>; <날짜·시각>        ← 나중에 붙은 칸
Received: <토큰 목록>; <날짜·시각>        ← 먼저 붙은 칸
Date: <요일,> <날짜> <시각> +0900
From: <주소>
Message-ID: <id-left@id-right>          ← 이 꺾쇠는 문법의 일부
MIME-Version: 1.0
Content-Type: <미디어 타입>
Content-Transfer-Encoding: base64
(빈 줄)
<본문>
```

`Message-ID` 줄을 빼면 `<…>` 는 값 자리를 표시한 것이고, 실제 값이 아닙니다.

## 포렌식에서 중요한 점

### 시각 여러 개

| 시각 | 자리 | 뜻 | 시간대 |
|---|---|---|---|
| `Date` | 헤더 | 작성자가 보낼 준비를 마친 시각 | 칸에 적힌 차이값. 현지 시각이 권장입니다 |
| `Received` 끝 날짜·시각 | trace 칸마다 | 각 시스템이 적은 날짜·시각. 자세한 뜻은 RFC 5321 몫입니다 | 칸마다 적힌 차이값 |
| mbox 구분 줄 시각 | 구분 줄 | 최종 수신자가 받은 시각 | "default" 형식은 UTC, 시간대 표시 없음. 구현마다 다를 수 있습니다 |
| 파일 시스템 시각 | NTFS 등 | 파일을 만들거나 바꾼 시각 | [시각 값 형식](../value-decoding/filetime-unix-webkit-dos-ole.md) |

- 네 시각이 같은 사건을 가리킨다고 가정하지 않습니다.
- 보고서에는 "`Date` 칸에 이 시각이 적혀 있다" 처럼 시각마다 출처를 붙입니다.
- 시각을 한 줄로 늘어놓는 법은 [타임라인 작성](../../03-techniques/analysis/timeline/index.md) 을 봅니다.

### 위조와 조작

- EML·MBOX 는 글자 파일입니다. 편집기로 헤더를 고쳐도 형식이 깨지지 않습니다.
- 그래서 헤더 값 하나만으로 진위를 판단하지 않습니다. 다른 사람의 사본, 서버 쪽 기록과 비교합니다.
- `Message-ID` 는 만드는 쪽이 유일하게 만들어야 합니다. 여러 사본에서 같은 `Message-ID` 가 보이면 같은 메시지의 사본으로 보고 묶습니다.
- 같은 `Message-ID` 인데 내용이 다르면 따로 조사합니다.
- 아래쪽 `Received` 일수록 먼저 붙은 칸입니다. 어느 칸부터 믿을지 정하는 법은 [메일 헤더 분석](../../03-techniques/analysis/email-header-analysis.md) 에서 다룹니다.

### 지운 메일과 조각

- mbox 는 메일 여러 통을 한 파일에 잇습니다.
- 파일 안이나 빈 공간에서 구분 줄과 헤더 칸 이름을 찾으면 메일 조각을 찾을 수 있습니다. [파일 내용 검색](../../03-techniques/analysis/content-search/index.md) 과 [삭제 데이터 복구](../../03-techniques/analysis/data-recovery/index.md) 를 봅니다.
- 본문의 `From ` 줄을 바꾸지 않는 구현도 있습니다. 그래서 `From ` 줄마다 메일을 자르면 한 통이 둘로 갈릴 수 있습니다.

### 손상과 섞인 형식

- 한 mbox 안에 구분 줄 형식이 섞일 수 있습니다.
- 본문에 인코딩하지 않은 바이너리가 들어 있을 수 있습니다. 도구가 나눈 경계를 헥스로 한 번 더 확인합니다.

## 함정

- **`Date` 를 보낸 시각으로 적습니다.** `Date` 는 작성자가 보낼 준비를 마친 시각입니다. 오프라인에서 대기열에 넣은 메일은 실제 전송이 그보다 늦을 수 있습니다.
- **`-0000` 을 그냥 UTC 로만 적습니다.** 값은 UTC 가 맞습니다. 다만 현지 시간대 정보가 빠졌다는 표시이기도 합니다.
- **한 글자 군사 시간대를 글자대로 풉니다.** 다른 근거가 없으면 `-0000` 으로 봅니다.
- **`Bcc` 줄이 없어 숨은 수신자가 없었다고 봅니다.** 보낼 때 `Bcc` 줄을 지우는 방식이 있습니다.
- **헤더 순서로 사건 순서를 읽습니다.** 헤더 칸의 순서는 보장되지 않습니다. 순서에 뜻이 있는 칸은 trace 칸과 resent 칸뿐입니다.
- **mbox 구분 줄 시각을 보낸 시각으로 봅니다.** 최종 수신자가 받은 시각입니다.
- **구분 줄 시각의 시간대를 가정합니다.** "default" 형식은 UTC 입니다. 하지만 RFC 는 구현마다 시각 형식이 다르다고 적습니다. 같은 메일의 `Received` 시각과 맞춰 봅니다.
- **접힌 헤더를 편지 않고 검색합니다.** 긴 `Subject` 나 주소 목록이 여러 줄에 걸쳐 있으면 키워드를 놓칩니다.
- **인코딩을 풀지 않고 본문을 검색합니다.** base64·quoted-printable 본문은 풀기 전에는 글자 검색에 걸리지 않습니다.
- **확장자로 형식을 정합니다.** 이 페이지의 자료로는 `.eml` 형식을 확인하지 못했습니다. 첫 줄과 구분 줄을 보고 내용으로 가립니다.

## 도구

아래 도구는 예로만 듭니다.

| 도구 | 쓰임 |
|---|---|
| 텍스트 편집기 | 헤더와 본문을 사람이 읽습니다. 원본이 아닌 사본으로 엽니다 |
| 헥스 편집기 | 줄 끝(CRLF·LF), 빈 줄 경계, 구분 줄을 봅니다 |
| Python 표준 라이브러리 (`email`, `mailbox` 모듈) | 헤더 펴기, MIME 풀기, mbox 나누기를 스크립트로 합니다. 결과는 헥스로 몇 통 대조합니다 |

도구마다 메일 수나 시각이 다르면 [도구 결과 교차 검증](../../03-techniques/reporting/tool-validation.md) 을 봅니다.
