# 캐시 형식 (Blockfile·Simple Cache)

> 위치: [크롬 계열 앱 공통 구조 (Chromium·Electron·WebView2)](index.md) > 캐시 형식

## 한 줄 요약

Chromium 의 디스크 캐시 (Disk Cache) 는 저장 방식이 두 가지입니다. 블록 파일 방식 (Blockfile) 은 `index` 파일 하나와 `data_0`~`data_3` 파일 넷에 항목을 나눠 담고, 심플 캐시 (Simple Cache) 는 항목 하나를 파일 하나에 담습니다. Windows 한 PC 안에서도 폴더에 따라 두 형식이 섞여 있습니다.

## 이 형식을 쓰는 아티팩트

Chromium 설계 문서에 적힌 기본값은 이렇습니다.

- 블록 파일 방식 설계 문서: Android 는 이 구현을 쓰지 않고 Simple Cache 를 씁니다.
- Simple Cache 설계 문서: Simple Cache 는 Windows 를 뺀 모든 플랫폼에서 기본으로 켜져 있습니다. 문서를 쓴 시점 기준입니다.

지금 Windows 에서 어떻게 쓰는지는 아래 관찰로 보충합니다.
관찰은 Windows 11(빌드 26200) PC 한 대에서 Chrome 153·Edge 151·WebView2 앱·Electron 앱을 보고 확인한 것입니다.

| 폴더 (프로필 기준) | 형식 (관찰) | 알아보는 법 |
|---|---|---|
| `Cache\Cache_Data` — Chrome·Edge·WebView2·Electron 의 HTTP 캐시 | 블록 파일 방식 | `index`, `data_0`~`data_3`, `f_xxxxxx` |
| `Code Cache\js`, `Code Cache\wasm` | Simple Cache | `<16자리 16진수>_0` 파일들, `index`, `index-dir\the-real-index` |

두 형식 모두 `index` 라는 이름의 파일이 있어서 `index` 파일만 보고 형식을 가리지 않습니다. `data_0` 이 있으면 블록 파일 방식이고, `index-dir` 폴더와 `_0` 으로 끝나는 파일이 있으면 Simple Cache 입니다.

- 캐시 폴더가 어디 있는지는 [프로필 폴더와 계열 브라우저 구분](user-data-profile-local-state.md) 과 [Electron·WebView2 앱 데이터 위치](teams-discord-slack.md) 에서 다룹니다.
- 캐시 항목이 사용자 행위로 무엇을 뜻하는지는 [크롬 계열 브라우저](../../../02-artifacts/browsers/chrome-edge-whale/index.md) 에서 다룹니다. 이 페이지는 저장 형식만 다룹니다.

## 구조 — 블록 파일 방식

> 그림 자리: `index` 가 캐시 주소로 `data_1` 의 항목 블록을 가리키고, 항목 블록의 스트림 주소가 다시 `data_2`·`data_3` 의 블록이나 `f_xxxxxx` 파일을 가리키는 흐름

### 파일 구성

파일은 적어도 다섯 개로, `index` 파일 하나와 데이터 파일 넷입니다 (설계 문서). 데이터 파일은 크기가 같은 블록으로 나뉘고 파일마다 블록 크기가 다릅니다. 데이터가 16KB(`kMaxBlockSize`)를 넘으면 블록 파일에 넣지 않고 별도 파일 `f_xxxxxx` 에 저장합니다 (설계 문서).

| 파일 | 블록 크기 |
|---|---|
| `data_0` | 36바이트 |
| `data_1` | 256바이트 |
| `data_2` | 1KB |
| `data_3` | 4KB |
| `f_xxxxxx` | 블록 없음. 16KB 를 넘는 데이터 하나를 담습니다 |

블록 크기는 설계 문서와 dtformats 문서가 같습니다. `data_0` 의 36바이트 블록은 순위 노드 (Rankings Node) 이고 순위 노드는 늘 36바이트입니다 (설계 문서). 관찰한 PC 에서도 각 `data_N` 파일 헤더 오프셋 12 의 값이 36·256·1024·4096 이었습니다.

캐시 항목 (Entry Store) 은 키 길이에 따라 256바이트 블록을 1~4개 씁니다 (설계 문서). 데이터 스트림은 블록 파일 안이나 `f_` 파일에 있습니다 (dtformats). 한 항목의 데이터는 HTTP 헤더용과 실제 내용용처럼 여러 스트림 (Stream) 으로 나뉘고 (설계 문서), 항목마다 스트림 크기 칸과 스트림 주소 칸이 네 개씩 있습니다 (dtformats).

### 캐시 주소 (Cache Address)

파일 사이의 연결은 32비트 캐시 주소로 적습니다.
주소 하나가 파일 종류와 파일 번호, 블록 위치를 함께 가리킵니다.

설계 문서의 예는 둘입니다.

| 주소 | 가리키는 곳 (설계 문서) |
|---|---|
| `0x8000002A` | 별도 파일 `f_00002A` |
| `0xA0010003` | `data_1` 의 3번 블록부터 1블록 |

dtformats 문서의 파일 종류 값은 아래와 같습니다.

| 값 | 파일 종류 |
|---|---|
| 0 | 별도 파일 (`f_xxxxxx`) |
| 1 | 36바이트 블록 (`data_0`) |
| 2 | 256바이트 블록 (`data_1`) |
| 3 | 1KB 블록 (`data_2`) |
| 4 | 4KB 블록 (`data_3`) |

Chromium 소스(`addr.h`)의 비트 배치는 아래와 같습니다.

| 비트 | 뜻 |
|---|---|
| 31 | 초기화 표시 |
| 28~30 | 파일 종류 |
| 26~27 | 예약 (블록 파일일 때) |
| 24~25 | 이어진 블록 수 1~4 (블록 파일일 때) |
| 16~23 | 파일 번호 0~255 (블록 파일일 때) |
| 0~15 | 시작 블록 번호 0~65,535 (블록 파일일 때) |

이 배치는 위 두 예와 맞습니다. `0x8…` 은 이진수로 `1000` 이라 파일 종류가 0 이고, `0xA…` 는 `1010` 이라 파일 종류가 2 입니다. `0xA0010003` 은 블록 수 칸이 0 인데 1블록을 가리켜서, 이 칸에는 블록 수에서 1 을 뺀 값이 들어간다고 봅니다 (해석). 소스의 파일 종류 값에는 5~7 도 있지만 위 표에는 캐시 항목을 따라갈 때 만나는 값만 적었습니다.

### index 파일 헤더

아래는 dtformats 문서의 배치입니다.
이 문서는 Chrome 8~51 로 시험했습니다.
오프셋 48 칸은 Chromium 소스(`disk_format.h`)에서 가져왔습니다.

| 오프셋 | 크기 | 내용 |
|---|---|---|
| 0 | 4 | 시그니처 `C3 CA 03 C1` |
| 4 | 2 | 부 버전 |
| 6 | 2 | 주 버전 |
| 8 | 4 | 항목 수 |
| 12 | 4 | 저장된 데이터 크기 (버전 2.x) |
| 16 | 4 | 마지막으로 만든 파일 번호 |
| 20 | 4 | 더티 (Dirty) 표시 |
| 40 | 8 | 만든 시각 |
| 48 | 8 | 저장된 데이터 크기 (버전 3.0) |

헤더는 256바이트이고, 표에 없는 오프셋은 이 페이지에서 다루지 않습니다. dtformats 문서의 버전 2.0·2.1 부분은 아직 TODO 로 남아 있습니다.

관찰한 Chrome 153 의 `index` 는 첫 8바이트가 `C3 CA 03 C1 00 00 03 00` 이어서 주 버전 3, 부 버전 0 입니다. 같은 파일의 오프셋 12 값은 0 이었습니다. Chromium 소스는 오프셋 12 칸을 버전 2.x 의 데이터 크기로, 오프셋 48 칸을 버전 3.0 의 데이터 크기로 적기 때문에 버전 3.0 파일에서 오프셋 12 가 0 인 것은 소스와 맞습니다. 소스의 현재 버전 값 `0x30000` 도 관찰한 버전 3.0 과 같습니다.

- 오프셋 20 칸은 소스 주석에 "바뀌는 중인 항목의 ID (더티 표시)" 로 적혀 있습니다.
- 만든 시각 칸의 시각 형식은 이번에 연 자료로 확인하지 못했습니다.

### 데이터 블록 파일 (data_N) 헤더

| 오프셋 | 내용 | 근거 |
|---|---|---|
| 0 | 시그니처 `C3 CA 04 C1` | dtformats |
| 4 | 버전. `data_0` 에서 `00 00 02 00` (버전 2.0) 이었습니다 | 관찰 |
| 8 | 파일 번호. `data_0` 은 0, `data_1` 은 1 … | 관찰 |
| 12 | 블록 크기 | 관찰 |
| 80 | 블록 할당 비트맵 시작 | dtformats |

헤더는 8192바이트입니다 (dtformats). 관찰한 `data_0` 의 크기는 598,016바이트로 8,192 + 36 × 16,384 와 같아서, 헤더 8192바이트 뒤에 36바이트 블록 16,384개가 있는 크기입니다.

### 캐시 항목 (Entry Store, 256바이트)

아래는 dtformats 문서의 배치입니다.
칸 순서는 Chromium 소스(`disk_format.h`)의 `EntryStore` 와도 같습니다.

| 오프셋 | 크기 | 내용 |
|---|---|---|
| 0 | 4 | 해시 |
| 8 | 4 | 순위 노드 주소 |
| 12 | 4 | 재사용 횟수 |
| 20 | 4 | 항목 상태 |
| 24 | 8 | 만든 시각. 1601-01-01 00:00:00 UTC 부터 센 마이크로초 |
| 32 | 4 | 키 크기 |
| 36 | 4 | 긴 키의 주소 |
| 40 | 4 × 4 | 데이터 스트림 크기 네 개 |
| 56 | 4 × 4 | 데이터 스트림 주소 네 개 |
| 96 | 160 | 키 (UTF-8). 더 길면 이어진 블록이나 오프셋 36 이 가리키는 곳에 둡니다 |

해시는 SuperFastHash 로 계산한다고 적혀 있습니다 (dtformats). 표에 없는 오프셋은 이 페이지에서 다루지 않습니다.

## 구조 — Simple Cache

### 설계 문서에 적힌 구조

항목 하나를 파일 하나에 저장하고, 파일 이름은 "항목 해시(16진수) + 밑줄 + 스트림 번호" 입니다. 항목 해시는 URL 의 SHA-1 값에서 64비트를 씁니다. 파일 안에는 매직 번호와 버전, 길이를 앞에 붙인 전체 URL, 데이터, EOF 레코드가 들어 있습니다. 관찰한 파일 이름의 16자리 16진수는 64비트라서 설계 문서의 64비트 해시와 길이가 맞습니다.

### 색인 파일

설계 문서는 색인 파일 이름을 `00index` 로 적었지만 관찰한 폴더에는 `index` 파일과 `index-dir\the-real-index` 파일이 있었습니다. 그래서 설계 문서는 초기 설계를 적은 것으로 봅니다 (해석).

- `the-real-index` 의 오프셋 8 에는 `6F 79 20 72 65 74 6E 65` (리틀 엔디언 `0x656E74657220796F`) 가 있었습니다 (관찰).
- 같은 파일의 오프셋 16 에는 `09 00 00 00` 이 있었습니다 (관찰).
- 두 칸의 이름과 뜻은 확인하지 못했습니다.

### 항목 파일 머리

칸 이름은 Chromium 소스(`simple_entry_format.h`)의 `SimpleFileHeader` 입니다.
본 값은 `Code Cache\js` 의 `_0` 파일 앞 24바이트에서 봤습니다 (관찰).

| 오프셋 | 크기 | 칸 (소스) | 본 값 (관찰) |
|---|---|---|---|
| 0 | 8 | 시작 매직 번호 | `30 5C 72 A7 1B 6D FB FC` (리틀 엔디언 `0xFCFB6D1BA7725C30`). 소스의 값과 같습니다 |
| 8 | 4 | 버전 | `05 00 00 00` (5) |
| 12 | 4 | 키 길이 | 4바이트 값 |
| 16 | 4 | 키 해시 | 4바이트 값 |
| 20 | 4 | 채움 | — |

소스 주석에 적힌 `_0` 파일의 순서는 머리, 키, 스트림 1 데이터, 스트림 1 의 EOF 레코드, 스트림 0 데이터, (있으면) 키의 SHA-256, 스트림 0 의 EOF 레코드입니다. 스트림 2 는 따로 파일 하나에 머리, 키, 데이터, EOF 레코드 순으로 들어가는데 (소스 주석), 관찰 폴더에는 `_0` 파일만 있었습니다.

스트림 2 파일이 `_1` 로 끝나는지, 희소 (sparse) 데이터 파일이 `_s` 로 끝나는지는 이번에 연 자료로 확인하지 못했습니다. 버전 값 5 가 소스의 현재 버전과 같은지도 확인하지 못했습니다.

## 읽는 법

1. **사본을 만듭니다.** 앱이 켜져 있으면 캐시 파일이 바뀔 수 있습니다. 폴더 전체를 사본으로 떠서 읽습니다.
2. **형식을 가립니다.** `data_0` 이 있으면 블록 파일 방식입니다. `index-dir` 와 `_0` 파일이 있으면 Simple Cache 입니다.
3. **블록 파일 방식이면 헤더부터 봅니다.** `index` 첫 4바이트가 `C3 CA 03 C1` 인지, `data_N` 첫 4바이트가 `C3 CA 04 C1` 인지 봅니다. `index` 의 주 버전·부 버전을 적어 둡니다.
4. **항목 블록을 읽습니다.** `data_1` 의 256바이트 블록에서 캐시 항목을 읽습니다. 오프셋 96 의 키와 오프셋 32 의 키 크기를 먼저 봅니다. 키 크기가 160 을 넘으면 나머지 키는 이어진 블록에 있거나, 오프셋 36 의 긴 키 주소가 가리키는 곳에 있습니다.
5. **스트림을 따라갑니다.** 오프셋 56 의 스트림 주소 네 개를 풉니다. 주소가 가리키는 `data_N` 블록이나 `f_xxxxxx` 파일에서 스트림 크기만큼 읽습니다. 어느 칸이 HTTP 헤더이고 어느 칸이 내용인지는 이번 자료로 확인하지 못했습니다. 읽은 내용으로 가립니다.
6. **Simple Cache 면 파일 하나씩 읽습니다.** 파일 이름에서 항목 해시를 읽습니다. 파일 안에서 URL 과 데이터를 찾습니다. 색인 파일에 없는 항목 파일도 읽습니다.
7. **시각을 바꿉니다.** 캐시 항목의 만든 시각은 1601-01-01 UTC 부터 센 마이크로초입니다. 변환은 [시각 값 형식](../../value-decoding/filetime-unix-webkit-dos-ole.md) 에서 다룹니다.

이 페이지의 정수는 리틀 엔디언으로 읽습니다.
관찰한 `index` 버전 칸 `03 00` 을 3 으로 읽을 때와 같은 방식입니다.

### 헥스로 한 번 따라가기 — 블록 파일 방식

아래 바이트는 **명세로 만든 예시**입니다.
실제 검체에서 나온 값이 아닙니다.
`??` 는 이 예시에서 다루지 않는 바이트입니다.

```
index 파일 첫 16바이트 (명세로 만든 예시. 버전 값은 관찰한 값)
오프셋    00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F
00000000  C3 CA 03 C1 00 00 03 00 ?? ?? ?? ?? ?? ?? ?? ??
```

- 오프셋 0 의 `C3 CA 03 C1` 은 `index` 시그니처입니다.
- 오프셋 4 의 `00 00` 은 부 버전 0 입니다.
- 오프셋 6 의 `03 00` 은 주 버전 3 입니다.
- 오프셋 8 부터 항목 수, 저장된 데이터 크기, 마지막 파일 번호, 더티 표시가 4바이트씩 이어집니다.

```
data_1 의 256바이트 블록 하나 = 캐시 항목 (명세로 만든 예시)
오프셋    00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F
00000000  ?? ?? ?? ?? ?? ?? ?? ?? ?? ?? ?? ?? ?? ?? ?? ??
00000010  ?? ?? ?? ?? ?? ?? ?? ?? 00 80 A6 8E DE A5 2F 00
00000020  14 00 00 00 ?? ?? ?? ?? ?? ?? ?? ?? ?? ?? ?? ??
00000030  ?? ?? ?? ?? ?? ?? ?? ?? 03 00 01 A0 2A 00 00 80
   ...
00000060  68 74 74 70 73 3A 2F 2F 65 78 61 6D 70 6C 65 2E   https://example.
00000070  63 6F 6D 2F                                       com/
```

- 이 예시는 설계 문서의 주소 예 두 개를 스트림 주소 칸에 넣어 만들었습니다.
- 오프셋 0x18(24) 의 8바이트는 만든 시각입니다. 값은 `0x002FA5DE8EA68000` = 13,411,699,200,000,000 마이크로초입니다.
- 이 값을 1601-01-01 UTC 에 더하면 2026-01-01 00:00:00 UTC 입니다. 예시를 위해 고른 시각입니다.
- 오프셋 0x20(32) 의 `14 00 00 00` 은 키 크기 20 입니다.
- 오프셋 0x60(96) 부터 키 20바이트 `https://example.com/` 이 있습니다.
- 오프셋 0x38(56) 의 `03 00 01 A0` 은 첫 스트림 주소 `0xA0010003` 입니다. 설계 문서의 예대로 `data_1` 의 3번 블록부터 1블록을 가리킵니다.
- 오프셋 0x3C(60) 의 `2A 00 00 80` 은 둘째 스트림 주소 `0x8000002A` 입니다. 별도 파일 `f_00002A` 를 가리킵니다.

`data_1` 의 3번 블록이 파일 어디에 있는지는 아래처럼 셈합니다.
헤더 8192바이트 바로 뒤에 블록이 0번부터 차례로 놓인다고 보면 8,192 + 3 × 256 = 8,960(0x2300) 입니다.
이 셈은 헤더 크기와 관찰한 `data_0` 파일 크기에서 나온 해석입니다.
블록 번호를 0 부터 세는지는 확인하지 못했으므로 도구 결과와 대조합니다.

### 헥스로 한 번 따라가기 — Simple Cache

```
Code Cache\js 의 <16자리 16진수>_0 파일 앞 16바이트 (관찰한 값으로 만든 예시)
오프셋    00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F
00000000  30 5C 72 A7 1B 6D FB FC 05 00 00 00 ?? ?? ?? ??
```

- 앞 8바이트는 관찰한 파일의 매직 번호로 보이는 값입니다.
- 오프셋 8 의 `05 00 00 00` 은 버전 칸입니다. 값은 5 입니다.
- 오프셋 12 의 4바이트가 키 길이입니다.
- 키는 머리 24바이트 바로 뒤, 곧 오프셋 24 부터 키 길이만큼 이어집니다 (소스 주석). `Code Cache` 의 키가 URL 만으로 이뤄졌는지는 확인하지 못했습니다. 키 앞부분을 직접 봅니다.

## 포렌식에서 중요한 점

### 비정상 종료

블록 파일 방식은 파일 헤더에 갱신 중 (updating) 표시를 두고, 캐시를 열 때 이 표시가 켜져 있으면 헤더가 서로 맞는지 검사합니다 (설계 문서). 비정상 종료 때는 그 순간 열려 있던 항목만 버리도록 설계했으므로 (설계 문서) 앱이 갑자기 꺼져도 대부분의 항목은 남는다고 봅니다 (해석). `index` 헤더 오프셋 20 에 더티 표시가 있으니 (dtformats) 사본을 뜬 시점의 상태를 적어 둡니다.

Simple Cache 는 비정상 종료 뒤에 색인이 오래된 상태가 되므로 폴더를 다시 훑어 색인에 없는 항목을 찾습니다 (설계 문서). 분석할 때도 색인만 믿지 말고 폴더 안 항목 파일을 모두 읽습니다 (해석).

### 지운 항목

블록 파일 방식에서 항목을 지울 때는 Doom 계열 메서드가 먼저 표시하고, 그 항목을 쓰는 곳이 모두 닫은 뒤에 실제로 지웁니다 (설계 문서). 지운 항목의 블록이 덮어쓰기 전까지 남는지는 확인하지 못했습니다. 그래서 `data_N` 헤더의 블록 할당 비트맵(오프셋 80)에서 빈 블록으로 표시한 자리도 내용을 한 번 보고, 옛 항목이 남았는지는 검체마다 확인합니다.

`f_xxxxxx` 파일과 Simple Cache 항목 파일은 파일 하나가 데이터 하나라서, 이런 파일이 지워졌으면 파일 시스템 수준에서 찾습니다 (해석). [삭제 데이터 복구](../../../03-techniques/analysis/data-recovery/index.md) 를 봅니다.

### 시각

캐시 항목의 만든 시각은 1601-01-01 UTC 부터 센 마이크로초이고 (dtformats), UTC 값이므로 현지 시각으로 바꿀 때 시간대를 밝힙니다. 이 값은 항목을 만든 시각이라서 사용자가 그 페이지를 마지막으로 본 시각과 같다고 보지 않습니다.

- `f_xxxxxx` 파일과 Simple Cache 파일은 파일 시스템 시각도 있습니다. [마스터 파일 테이블](../../../02-artifacts/filesystem/mft.md) 의 시각과 함께 봅니다.

## 함정

- **Windows 는 Simple Cache 라고 단정합니다.** 설계 문서의 기본값 설명은 문서를 쓴 시점 기준입니다. 관찰한 PC 에서는 HTTP 캐시가 블록 파일 방식, `Code Cache` 가 Simple Cache 였습니다.
- **dtformats 오프셋을 그대로 믿습니다.** 이 문서는 Chrome 8~51 로 시험했습니다. 관찰한 Chrome 153 의 `index` 는 주 버전이 3 이었습니다. 버전 3.0 은 저장된 데이터 크기를 오프셋 12 가 아니라 오프셋 48 에 적습니다 (Chromium 소스). 요즘 버전에서는 칸 뜻을 소스와 다시 맞춰 봅니다.
- **`data_N` 만 읽습니다.** 16KB 를 넘는 데이터는 `f_xxxxxx` 파일에 있습니다.
- **키를 160바이트에서 자릅니다.** 키가 더 길면 나머지는 별도 블록에 있습니다.
- **키를 곧 URL 로 봅니다.** 키 앞에 다른 값이 붙는 경우가 있다고 알려져 있으나 이번에 확인하지 못했습니다. 키 앞부분을 직접 봅니다.
- **설계 문서의 파일 이름으로 찾습니다.** Simple Cache 설계 문서의 `00index` 는 관찰한 폴더에 없었습니다.
- **`index` 파일 이름으로 형식을 가립니다.** 두 형식 모두 `index` 파일이 있습니다.
