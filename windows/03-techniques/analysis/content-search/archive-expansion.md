# 압축·복합 파일 펼치기 (Archive Expansion)

## 한 줄 요약

ZIP·OLE 복합 파일처럼 다른 파일을 담는 형식에서 안쪽 항목을 꺼내고, 꺼낸 항목을 다시 형식 식별과 본문 추출로 보냅니다.

이 글은 [파일 내용 검색 (Content Search)](/03-techniques/analysis/content-search/index.md) 묶음의 한 편입니다.
각 형식의 시그니처 값은 [파일 형식 식별](/03-techniques/analysis/content-search/file-signature.md) 에 모아 두었습니다.

## 언제 쓰나

- **문서 파일을 검색할 때** 씁니다. DOCX·XLSX·PPTX 는 ZIP 입니다. ODT·EPUB·JAR·APK·XPS 도 ZIP 을 바탕으로 한 형식입니다.
- **예전 오피스 문서를 볼 때** 씁니다. DOC·XLS·PPT 는 OLE 복합 파일 (Compound File Binary, CFB) 입니다. CFB 는 파일 안에 FAT 과 디렉터리를 두고 여러 스트림을 담습니다. 파일 속에 작은 파일 시스템이 있는 구조입니다.
- **압축된 글을 찾을 때** 씁니다. ZIP 항목은 대개 압축돼 있습니다. 펼치지 않고 원시 바이트로 찾으면 안쪽 글을 놓칠 수 있습니다. 검색 쪽 이야기는 [키워드 검색](/03-techniques/analysis/content-search/keyword-search.md) 에 있습니다.

## 컨테이너 한눈에 보기

| 형식 | 안쪽 구조 | 항목 목록이 있는 곳 | 이 페이지에서 |
|---|---|---|---|
| ZIP (OOXML·ODT·EPUB 등 포함) | 항목마다 로컬 파일 헤더, 끝에 중앙 디렉터리와 끝 레코드 | 파일 끝의 중앙 디렉터리 | 구조까지 다룹니다 |
| OLE 복합 파일 (CFB) | FAT·디렉터리·스트림. 섹터 512 또는 4,096바이트 | 디렉터리 섹터 | 요점만 다룹니다 |
| RAR·7z·GZIP·BZIP2·XZ·CAB | 형식마다 다름 | 형식마다 다름 | 시그니처만 [파일 형식 식별](/03-techniques/analysis/content-search/file-signature.md) 에 있습니다 |

## ZIP 구조

근거는 PKWARE 의 ZIP 명세 APPNOTE 6.3.10(2022-11-01) 입니다.

### 세 가지 레코드

| 레코드 | 시그니처 (값) | 디스크 바이트 | 내용 |
|---|---|---|---|
| 로컬 파일 헤더 (Local File Header) | 0x04034b50 | 50 4B 03 04 | 항목 하나의 압축 방식·시각·CRC-32·크기·이름 |
| 중앙 디렉터리 파일 헤더 (Central Directory File Header) | 0x02014b50 | 50 4B 01 02 | 중앙 디렉터리에 모인 항목 정보 |
| 중앙 디렉터리 끝 레코드 (End of Central Directory, EOCD) | 0x06054b50 | 50 4B 05 06 | 항목 수, 중앙 디렉터리 크기와 시작 오프셋, 주석 |

시그니처 값은 리틀 엔디언이라 디스크에는 바이트 순서가 뒤집혀 적힙니다.
[파일 형식 식별](/03-techniques/analysis/content-search/file-signature.md) 의 "빈 압축 파일" 시그니처 `50 4B 05 06` 은 EOCD 시그니처와 같은 바이트입니다.

ZIP 파일에는 EOCD 가 반드시 있습니다.
EOCD 는 파일 끝에 있습니다.
EOCD 의 칸은 이 디스크 번호, 중앙 디렉터리가 시작하는 디스크 번호, 이 디스크의 항목 수, 전체 항목 수, 중앙 디렉터리 크기, 중앙 디렉터리 시작 오프셋, ZIP 주석 길이, 주석 순서입니다.
주석은 길이가 정해지지 않았습니다.
그래서 EOCD 는 파일 끝에서 주석 길이만큼 앞에 있습니다.

항목 목록은 이 순서로 읽습니다.

1. 파일 끝에서부터 거꾸로 EOCD 시그니처를 찾습니다.
2. EOCD 의 중앙 디렉터리 시작 오프셋으로 갑니다.
3. 중앙 디렉터리 파일 헤더를 차례로 읽어 항목 목록을 만듭니다.

Zip64 형식에는 따로 Zip64 중앙 디렉터리 끝 레코드(시그니처 0x06064b50)가 있습니다.

> 그림 자리: ZIP 파일을 가로 막대로 그리고, 앞쪽에 "로컬 헤더 + 데이터" 칸이 되풀이되고 뒤쪽에 중앙 디렉터리와 EOCD 가 붙은 모습. EOCD 의 "중앙 디렉터리 시작 오프셋" 에서 중앙 디렉터리 첫 칸으로 화살표

### 로컬 파일 헤더

| 오프셋 | 크기 | 칸 |
|---|---|---|
| 0x00 | 4 | 시그니처 (50 4B 03 04) |
| 0x04 | 2 | 추출에 필요한 버전 |
| 0x06 | 2 | 일반 목적 비트 플래그 |
| 0x08 | 2 | 압축 방식 |
| 0x0A | 2 | 마지막 수정 시각 (MS-DOS) |
| 0x0C | 2 | 마지막 수정 날짜 (MS-DOS) |
| 0x0E | 4 | CRC-32 |
| 0x12 | 4 | 압축 크기 |
| 0x16 | 4 | 원래 크기 |
| 0x1A | 2 | 파일 이름 길이 |
| 0x1C | 2 | 추가 필드 길이 |
| 0x1E | 가변 | 파일 이름 |

오프셋은 명세의 칸 크기를 차례로 더해 얻은 값입니다.

아래는 명세로 만든 예시입니다.
특정 파일에서 뽑은 바이트가 아닙니다.
시각·날짜·CRC-32·크기는 값 대신 글자(tt·dd·cc·ss·uu)로 두었습니다.

```
오프셋    00 01 02 03 04 05 06 07  08 09 0A 0B 0C 0D 0E 0F
00000000  50 4B 03 04 14 00 00 08  08 00 tt tt dd dd cc cc
00000010  cc cc ss ss ss ss uu uu  uu uu 07 00 00 00 EA B0
00000020  80 2E 74 78 74
```

- 0x04 의 `14 00` 은 추출에 필요한 버전 0x0014 입니다.
- 0x06 의 `00 08` 은 플래그 0x0800 입니다. 비트 11 이 켜져 있어 파일 이름이 UTF-8 입니다.
- 0x08 의 `08 00` 은 압축 방식 8, Deflate 입니다.
- 0x1A 의 `07 00` 은 파일 이름 길이 7바이트입니다.
- 0x1C 의 `00 00` 은 추가 필드가 없다는 뜻입니다.
- 0x1E 부터 7바이트 `EA B0 80 2E 74 78 74` 는 UTF-8 로 적은 이름 "가.txt" 입니다.

### 일반 목적 비트 플래그

| 비트 | 켜졌을 때 뜻 |
|---|---|
| 0 | 항목이 암호화돼 있습니다 |
| 3 | 로컬 헤더의 CRC-32·압축 크기·원래 크기가 0 입니다. 실제 값은 뒤따르는 데이터 기술자 (Data Descriptor) 에 있습니다 |
| 6 | 강한 암호화 (Strong Encryption) 입니다. 추출에 필요한 버전이 50 이상이어야 합니다 |
| 11 | 언어 인코딩 플래그 (EFS) 입니다. 파일 이름과 주석이 UTF-8 입니다 |

### 압축 방식

| 값 | 방식 |
|---|---|
| 0 | 저장 (압축 안 함) |
| 8 | Deflate |
| 9 | Deflate64 |
| 12 | BZIP2 |
| 14 | LZMA |
| 93 | Zstandard |
| 99 | AE-x 암호화 표시 |

### 항목 시각

ZIP 항목의 시각과 날짜는 MS-DOS 형식입니다.
연도는 1980년부터 셉니다.
정밀도는 2초입니다.
값을 푸는 법은 [시각 값 형식](/01-foundations/value-decoding/filetime-unix-webkit-dos-ole.md) 에 있습니다.

이 MS-DOS 시각이 현지 시각인지 UTC 인지는 이 페이지의 근거 자료로 확인하지 못했습니다.
명세에는 확장 타임스탬프 추가 필드(0x5455)와 NTFS 추가 필드(0x000a)도 있습니다.
두 필드의 칸 배치는 명세 원문에서 확인한 뒤 씁니다.

## OLE 복합 파일 펼치기

CFB 는 섹터 단위로 나뉩니다.
[MS-CFB] 명세에 따르면 섹터는 버전 3 에서 512바이트, 버전 4 에서 4,096바이트입니다.
4,096바이트보다 작은 스트림은 미니 FAT 과 미니 스트림에 놓입니다.
미니 스트림의 섹터는 64바이트입니다.
4,096바이트 이상인 스트림은 일반 FAT 섹터에 놓입니다.
이 경계 크기는 헤더 0x38 칸에 0x00001000 으로 적혀 있습니다.

펼치기는 디렉터리에서 스트림 목록을 읽고, 스트림마다 섹터 사슬을 따라가 이어 붙이는 일입니다.
디렉터리와 FAT 을 따라가는 방법은 [OLE 복합 파일](/01-foundations/shell-document-formats/compound-file-binary.md) 에 있습니다.
꺼낸 스트림은 ZIP 항목과 마찬가지로 형식 식별부터 다시 거칩니다.

## 절차

1. [파일 형식 식별](/03-techniques/analysis/content-search/file-signature.md) 결과에서 컨테이너 형식을 고릅니다.
2. 항목 목록을 읽습니다. ZIP 은 EOCD 에서 중앙 디렉터리로 가고, CFB 는 디렉터리를 읽습니다.
3. 암호화 표시를 봅니다. ZIP 이면 플래그 비트 0·비트 6 과 압축 방식 99 를 확인합니다. 암호화된 항목은 [암호화 증거 다루기](/03-techniques/analysis/encrypted-evidence/index.md) 로 넘깁니다.
4. 항목을 꺼냅니다. 꺼낸 항목은 형식 식별부터 다시 거칩니다. 안에 또 컨테이너가 있으면 이 단계를 되풀이합니다.
5. 되풀이 깊이와 풀어낸 전체 크기에 상한을 둡니다. 상한에 걸린 파일은 따로 목록으로 남깁니다.
6. 꺼낸 항목마다 바깥 경로를 적습니다. 예를 들어 "보관.zip 안의 보고서.docx 안의 항목" 처럼 바깥에서 안쪽까지 차례로 적습니다.
7. 꺼낸 항목마다 해시를 구합니다. 이미 아는 파일을 거를 때는 [해시셋 대조와 유사 해시](/03-techniques/analysis/hash-set-fuzzy-hash.md) 를 씁니다.
8. 꺼낸 항목을 [본문 추출과 글자 인식](/03-techniques/analysis/content-search/text-extraction-ocr.md) 으로 보냅니다.

## 도구

- **공개 압축 해제 도구와 프로그래밍 언어의 ZIP 라이브러리**: 예를 들어 Python 표준 `zipfile` 모듈로 항목 목록·플래그·압축 방식을 볼 수 있습니다.
- **bulk_extractor** (README 기준 2.2.0): 파일 시스템을 해석하지 않고 디스크 이미지·파일·폴더를 훑습니다. 모든 바이트 위치에서 압축을 풀거나 디코딩할 수 있는 데이터가 시작되는지 살핍니다. 풀리면 푼 데이터를 처음부터 다시 검사합니다. 그래서 비할당 영역 속 압축 조각도 대상이 됩니다.
- **헥스 편집기**: 도구가 항목을 못 읽을 때 로컬 헤더와 EOCD 를 직접 봅니다.

## 함정과 한계

- **로컬 헤더의 크기가 0 일 수 있습니다.** 플래그 비트 3 이 켜진 항목은 로컬 헤더의 CRC-32·크기가 0 입니다. 로컬 헤더만 읽는 도구는 이런 항목에서 데이터 끝을 알 수 없습니다.
- **EOCD 는 맨 끝 고정 위치에 있지 않습니다.** 주석이 붙으면 그만큼 앞으로 옵니다. 끝에서 거꾸로 찾아야 합니다.
- **파일 끝이 잘린 ZIP 은 중앙 디렉터리를 찾지 못합니다.** 카빙으로 되살린 ZIP 이 이런 경우입니다. 도구가 로컬 헤더를 앞에서부터 훑어 항목을 읽는지 확인합니다.
- **이름이 깨질 수 있습니다.** 비트 11 이 꺼진 이름에는 UTF-8 이라는 표시가 없습니다. 도구가 이름을 어떤 코드 페이지로 읽었는지 확인합니다. 깨진 이름은 원시 바이트로 다시 봅니다. 코드 페이지는 [문자 인코딩](/01-foundations/value-decoding/utf-16le-utf-8-cp949.md) 에서 다룹니다.
- **Zip64 를 읽는지 확인합니다.** 쓰는 도구가 Zip64 중앙 디렉터리 끝 레코드(0x06064b50)도 읽는지 시험 파일로 확인합니다.
- **국내 압축 형식은 따로 확인합니다.** ALZ·EGG 의 구조는 이 페이지의 근거 자료에 없습니다. 쓰는 도구가 이 형식을 펼치는지 시험 파일로 먼저 확인합니다.
- **풀어 쓴 파일의 시각을 항목 시각으로 쓰지 않습니다.** 항목 시각은 ZIP 헤더에서 읽어 따로 적습니다.

## 결과를 어떻게 해석하나

- 펼친 항목의 위치는 "바깥 파일 경로 + 안쪽 항목 경로" 로 적습니다. 안쪽 항목만 적으면 같은 이름의 항목끼리 구분되지 않습니다.
- ZIP 항목 시각은 2초 단위입니다. NTFS 시각과 초 아래 자리까지 맞추려 하지 않습니다.
- 펼치지 못한 항목도 결과입니다. 암호화·손상·미지원 형식으로 못 펼친 목록은 "검색하지 못한 범위" 로 보고서에 남깁니다.
- 컨테이너 안에 있었다는 사실은 그 항목이 언제 컨테이너에 들어갔는지 알려 주지 않습니다. 압축 프로그램을 쓴 흔적은 [압축 프로그램 사용 기록](/02-artifacts/file-folder-usage/7-zip-winrar-bandizip.md) 에서 봅니다.
