# 키워드 검색 (Keyword Search)

## 한 줄 요약

찾을 낱말을 인코딩마다 바이트열로 바꿔 파일·원시 영역·색인에서 찾고, 걸린 곳마다 위치·인코딩·앞뒤 글을 적습니다.

이 글은 [파일 내용 검색 (Content Search)](index.md) 묶음의 한 편입니다. 압축된 파일과 문서 파일은 [압축·복합 파일 펼치기](archive-expansion.md) 와 [본문 추출과 글자 인식](text-extraction-ocr.md) 을 거친 결과에서도 찾습니다.

## 언제 쓰나

- **사건과 관련된 낱말을 이미 알 때** 씁니다. 사람 이름, 회사 이름, 프로젝트 이름, 파일 이름이 예입니다.
- **파일 시스템 밖을 뒤질 때** 씁니다. 비할당 영역과 슬랙은 파일로 열리지 않아서 원시 검색으로만 볼 수 있습니다.
- **다른 분석의 실마리를 찾을 때** 씁니다. 걸린 곳 주변 글에서 새 낱말을 얻어 목록을 늘립니다.

## 세 가지 검색 방식

| 방식 | 보는 것 | 강한 곳 | 놓치기 쉬운 것 |
|---|---|---|---|
| 파일 단위 검색 (논리 검색) | 파일 시스템으로 연 파일 내용. 펼치고 본문을 뽑은 글도 포함 | 문서·압축 파일 속 글 | 비할당 영역·슬랙 |
| 원시 검색 (물리 검색) | 디스크 이미지 바이트 전체. 파일 시스템을 해석하지 않음 | 비할당 영역 속 글 | 압축된 글, 조각난 파일에서 경계에 걸친 낱말 |
| 색인 검색 | 미리 만든 낱말 색인 | 빠르게 낱말을 찾음 | 낱말 중간 문자열, 색인에 본문이 안 들어간 파일 |

세 방식은 서로 빈 곳을 메우므로 중요한 낱말은 둘 이상의 방식으로 찾습니다.

원시 검색에서 압축된 글을 놓치는 이유는 간단합니다. ZIP 항목은 대개 Deflate(압축 방식 8)로 압축돼 있고 디스크에는 압축된 바이트만 있으므로, 원래 글의 바이트열이 나타나지 않을 수 있습니다[4]. 공개 도구 bulk_extractor 는 모든 바이트 위치에서 압축 해제를 시도하고, 풀린 데이터를 다시 검사합니다[3].

색인 검색은 색인을 만든 방식에 묶입니다. Windows Search 는 필터가 뽑은 글을 낱말로 끊고 정규화해 색인에 넣는데, 낱말 끊기와 언어(LCID)의 관계는 [본문 추출과 글자 인식](text-extraction-ocr.md) 에 있습니다. 색인이 낱말 단위라서 낱말 중간 문자열이나 정규식은 원문 검색과 결과가 다를 수 있습니다. 색인 파일 자체는 [윈도 검색 색인 DB](../../../02-artifacts/file-folder-usage/windows-search/index.md) 에서 다룹니다.

## 인코딩: 같은 글자, 다른 바이트

같은 글자라도 인코딩이 다르면 디스크에 적힌 바이트가 다릅니다. 아래는 "가"(U+AC00) 한 글자를 세 가지로 적은 바이트입니다. Python 표준 코덱(utf-8·utf-16-le·cp949)으로 인코딩하면 같은 값이 나옵니다.

| 인코딩 | "가" 의 바이트 |
|---|---|
| UTF-8 | EA B0 80 |
| UTF-16 LE | 00 AC |
| CP949 | B0 A1 |

세 바이트열은 서로 다릅니다.
그래서 한 인코딩으로만 찾으면 다른 인코딩으로 적힌 글은 걸리지 않습니다.

Windows 코드 페이지 식별자 가운데 한국어와 유니코드 관련 값은 다음과 같습니다[1].

| 코드 페이지 | 이름 | 설명 |
|---|---|---|
| 949 | ks_c_5601-1987 | ANSI/OEM Korean (Unified Hangul Code) |
| 51949 | euc-kr | EUC Korean |
| 20949 | x-cp20949 | Korean Wansung |
| 1361 | Johab | Korean (Johab) |
| 50225 | iso-2022-kr | ISO 2022 Korean |
| 10003 | x-mac-korean | Korean (Mac) |
| 1200 | utf-16 | UTF-16 리틀 엔디언 (관리 코드 전용) |
| 1201 | unicodeFFFE | UTF-16 빅 엔디언 (관리 코드 전용) |
| 12000 | utf-32 | UTF-32 리틀 엔디언 (관리 코드 전용) |
| 65001 | utf-8 | UTF-8 |

ANSI 코드 페이지는 컴퓨터마다 다를 수 있고 한 컴퓨터에서도 설정이 바뀔 수 있습니다. 이 차이로 데이터가 깨질 수 있어서 UTF-8·UTF-16 같은 유니코드를 쓰는 편이 안전합니다[1].

그래서 한국어 키워드는 적어도 UTF-16 LE·UTF-8·CP949 세 가지 바이트열로 찾고, 오래된 파일이나 다른 운영체제에서 온 파일이 있으면 표의 다른 인코딩도 더합니다.
인코딩 자체의 구조는 [문자 인코딩](../../../01-foundations/value-decoding/utf-16le-utf-8-cp949.md) 에서 다룹니다.

## 절차

1. 키워드 목록을 만듭니다. 띄어쓰기·영문 표기·줄임말 같은 표기 차이를 함께 넣습니다.
2. 키워드마다 인코딩별 바이트열을 만듭니다.
3. 검색 범위를 정하고 적습니다. 파일 단위·원시·색인 가운데 무엇을 쓸지, 비할당 영역과 슬랙을 넣을지 정합니다. 비할당 영역과 슬랙은 [삭제 데이터 복구](../data-recovery/index.md) 에서 다룹니다.
4. 압축·복합 파일을 펼치고 본문을 뽑은 결과에서도 찾습니다.
5. 걸린 곳마다 위치를 적습니다. 파일이면 경로와 파일 안 오프셋을, 원시 영역이면 이미지 오프셋을 적습니다. 인코딩과 앞뒤 글도 함께 적습니다.
6. 걸린 곳을 원본에서 헥스로 다시 확인합니다.
7. 색인 검색으로 찾은 결과는 원문 검색으로 한 번 더 확인합니다. 색인 검색에서 걸리지 않은 낱말도 원문 검색으로 확인합니다.

## 뽑은 파일에서 찾을 때: 오프셋이 어긋나는 경우

희소 (Sparse) 속성이 있는 파일을 빈 구간을 건너뛰고 뽑으면 뒤쪽 내용이 앞으로 밀리고, 그러면 뽑은 파일 속 오프셋이 원래 파일의 논리 오프셋과 달라집니다. 이런 파일에서 찾은 오프셋을 보고서에 쓸 때는 어떤 방식으로 뽑았는지 함께 적습니다.

NTFS 변경 저널 `$UsnJrnl:$J` 도 앞부분이 빈 희소 스트림입니다. 희소 파일의 구조는 [NTFS 구조](../../../01-foundations/disk-volume/ntfs/index.md) 에서, 변경 저널은 [USN 변경 저널](../../../02-artifacts/filesystem/usnjrnl.md) 에서 다룹니다.

## 도구

- **bulk_extractor** (2.2.0): 파일 시스템을 해석하지 않고 디스크 이미지·파일·폴더를 차례로 읽습니다. 전자우편 주소·신용카드 번호·JPEG·JSON 조각처럼 형식이 정해진 정보를 뽑습니다. 결과는 텍스트 파일과 히스토그램(빈도표)으로 남기며, 구글 검색어·전자우편 주소 히스토그램이 그 예입니다[3].
- **헥스 편집기**: 인코딩별 바이트열을 직접 찾고, 걸린 곳을 확인합니다.
- **윈도 검색 색인**: 대상 PC 에 남은 색인을 읽어 낱말을 찾습니다. 원문 검색과 결과를 비교하는 데 씁니다.

## 함정과 한계

- **인코딩 하나만 찾으면 놓칩니다.** "가" 의 세 바이트열처럼 인코딩마다 바이트열이 다릅니다.
- **짧은 키워드는 우연히 걸립니다.** 한 글자는 UTF-16 LE 로 2바이트뿐입니다. 짧은 바이트열은 관계없는 데이터에서도 자주 나옵니다.
- **ANSI 코드 페이지는 컴퓨터마다 다를 수 있습니다.** 다른 PC 에서 만든 파일은 다른 코드 페이지로 적혔을 수 있습니다. 한국어로 보이지 않는 결과도 다른 코드 페이지로 다시 읽어 봅니다.
- **압축된 글은 원시 검색에 잘 안 걸립니다.** 펼친 결과에서 한 번 더 찾습니다.
- **조사가 붙은 한국어 낱말은 색인 검색 결과가 달라질 수 있습니다.** "홍길동" 으로 "홍길동이" 를 찾는지는 색인의 낱말 끊기에 달려 있습니다. 대상 색인과 같은 조건에서 시험해 봅니다.
- **걸린 것이 없다고 낱말이 없었다는 뜻이 아닙니다.** 인코딩·범위·압축·추출 실패 가운데 무엇이 원인인지 먼저 따집니다.

## 결과를 어떻게 해석하나

- 결과는 기록으로 확인되는 만큼만 씁니다. 예를 들어 "키워드 X 가 UTF-16 LE 바이트열로 이미지 오프셋 Y 에 있다" 처럼 씁니다. "사용자가 X 를 입력했다" 는 이 결과만으로 쓸 수 없습니다.
- 비할당 영역에서 걸린 결과는 어느 파일에 속했는지, 언제 쓰였는지 알려 주지 않습니다. 파일을 되살려 볼 수 있으면 [삭제 데이터 복구](../data-recovery/index.md) 로 넘깁니다.
- 원시 오프셋이 어느 파일의 클러스터인지는 파일 시스템 정보로 거슬러 올라가 찾습니다. [NTFS 구조](../../../01-foundations/disk-volume/ntfs/index.md) 와 [마스터 파일 테이블](../../../02-artifacts/filesystem/mft.md) 을 봅니다.
- 개인정보처럼 형식이 정해진 값을 찾는 일은 [개인정보 탐지](pii-detection.md) 에서 다룹니다.
