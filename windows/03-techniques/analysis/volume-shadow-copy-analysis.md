# 섀도 복사본 활용 (Volume Shadow Copy Analysis)

> 위치: 분석 기법 > 분석

볼륨 섀도 복사본 서비스 (Volume Shadow Copy Service, VSS) 는 볼륨의 한 시점 사본인 섀도 복사본을 만듭니다.
섀도 복사본을 찾아 지금 볼륨과 비교하면, 지금은 지웠거나 바뀐 파일의 예전 내용을 볼 수 있습니다.
이 페이지는 섀도 복사본을 찾아 쓰고 해석하는 방법을 다룹니다.
디스크 위의 저장 구조와 헥스 풀이는 [볼륨 섀도 복사본 구조](../../01-foundations/disk-volume/volume-shadow-copy.md) 에 있습니다.

## 언제 쓰나

- **지금 볼륨에서 지운 파일의 예전 내용이 필요할 때** 씁니다. 파일 시스템에서 되살리는 방법은 [삭제 데이터 복구](data-recovery/index.md) 에 있습니다. 두 방법은 서로 보완합니다.
- **레지스트리 하이브·이벤트 로그·데이터베이스 파일의 예전 판을 볼 때** 씁니다. 지금 판과 비교하면 그사이에 무엇이 바뀌었는지 드러납니다.
- **랜섬웨어 사건에서 암호화되기 전 파일 모습을 찾을 때** 씁니다. 사건 흐름은 [랜섬웨어는 언제 어떻게 퍼졌나](../../04-scenarios/incident/ransomware.md) 에서 다룹니다.
- **같은 파일이 시점마다 어떻게 바뀌었는지 볼 때** 씁니다. 스냅숏이 여러 개면 시점도 여러 개입니다.

## 섀도 복사본이 담는 것

### 쓰기 시 복사

VSS 는 백업할 데이터의 일관된 섀도 복사본 (Shadow Copy) 을 만드는 일을 조율합니다.
VSS 를 쓰는 Windows 기능에는 Windows Server Backup, 공유 폴더 섀도 복사본 (Shadow Copies of Shared Folders), System Center DPM, 시스템 복원 (System Restore) 이 있습니다.

Windows 에 들어 있는 기본 공급자 (System Provider) 는 swprv.dll 과 volsnap.sys 두 파일로 이뤄지며 쓰기 시 복사 (Copy-on-Write) 방식으로 동작합니다.
원본 볼륨의 블록이 바뀌려 하면 기본 공급자가 쓰기를 마치기 전에 그 블록을 읽어 저장 영역 (Diff Area) 에 먼저 써 둡니다.
그래서 저장 영역에는 스냅숏 뒤에 바뀐 블록의 바뀌기 전 내용만 들어 있고, 바뀌지 않은 블록은 지금 볼륨에서 읽습니다.
저장 영역의 블록과 지금 볼륨을 합치면 스냅숏 시점의 볼륨을 다시 만들 수 있는데, 합치는 순서는 [볼륨 섀도 복사본 구조](../../01-foundations/disk-volume/volume-shadow-copy.md) 의 "예전 시점 다시 만들기" 에 있습니다.
섀도 복사본은 읽기 전용입니다.

> 그림 자리: 스냅숏 시각 T 뒤에 볼륨 블록 B 가 바뀌려 할 때, B 의 옛 내용이 먼저 저장 영역으로 복사되고 그다음 새 내용이 볼륨에 쓰이는 흐름. 옆에 "스냅숏 T 의 볼륨 = 저장 영역의 옛 블록 + 지금 볼륨의 나머지 블록" 을 그린 그림

### 만드는 순간

VSS 는 섀도 복사본을 만들 때 쓰기를 잠깐 멈춥니다.
응용 프로그램이 쓰기를 멈추는 시간은 60초를 넘을 수 없고, 공급자가 섀도 복사본을 만드는 단계는 10초를 넘지 않습니다.
그래서 섀도 복사본 하나는 한 순간의 볼륨 모습으로 봅니다.

### 도입 시점과 크기

- Microsoft 문서의 본문은 VSS 를 Windows Server 2003 에서 도입했다고 적습니다.
- 같은 문서의 FAQ 는 Windows XP 에서 도입했다고 적습니다.
- VSS 가 다루는 볼륨은 최대 64 TB 입니다.

## 저장 위치·개수·지우는 조건

해석에서 가장 자주 틀리는 부분입니다.

| 항목 | 값 | 분석에서 뜻하는 것 |
|---|---|---|
| 저장 영역 위치 | 같은 볼륨일 수도, 다른 볼륨일 수도 있습니다 | 다른 볼륨이면 그 볼륨의 이미지도 있어야 읽을 수 있습니다 |
| 저장 영역 볼륨 | NTFS 볼륨이어야 합니다 | FAT 계열 볼륨에는 저장 영역이 없습니다 |
| 영구 섀도 복사본 | NTFS 볼륨에만 만들 수 있습니다 | 재부팅 뒤에도 남는 스냅숏은 NTFS 볼륨에서 찾습니다 |
| 볼륨 하나의 개수 | 기본 공급자는 최대 512개 | |
| 공유 폴더 섀도 복사본의 개수 | 기본 64개까지. MaxShadowCopies 로 바꿉니다 | 설정에 따라 남는 개수가 다릅니다 |
| 세트 하나에 넣는 볼륨 | 최대 64개 | 섀도 복사본 개수와 다른 값입니다 |
| 공간이 모자랄 때 | 가장 오래된 섀도 복사본부터 지웁니다 | 오래된 스냅숏이 없다는 것만으로 누가 지웠다고 볼 수 없습니다 |

- 저장 영역이 어느 볼륨에 있는지는 VSS 볼륨 헤더의 "섀도 복사본 저장 볼륨 GUID" 필드로 봅니다. 필드의 오프셋은 [볼륨 섀도 복사본 구조](../../01-foundations/disk-volume/volume-shadow-copy.md) 의 볼륨 헤더 표에 있습니다.
- 이 필드가 가리키는 볼륨이 이미지에 없으면 섀도 복사본을 다시 만들 수 없습니다. 이 판단은 헤더 필드와 저장 위치 규칙 두 사실을 합친 해석입니다.

### 빠지는 파일

페이징 파일 같은 임시 파일은 자동으로 섀도 복사본에서 빠집니다.
응용 프로그램은 FilesNotToSnapshot 레지스트리 키로 특정 파일을 빼 달라고 할 수 있는데, 이 키는 클라이언트는 Windows Vista, 서버는 Windows Server 2008 부터 있습니다.
이 제외는 최선 노력 (Best-effort) 방식이라 늘 빠진다는 보장이 없습니다.
그래서 스냅숏에 파일이 없다고 해서 그 시점에 파일이 없었다고 볼 수 없습니다.

### 관련 레지스트리 값

VSS 와 관련된 레지스트리 값 이름은 아래와 같습니다.
정확한 레지스트리 경로는 실제 데이터로 확인한 뒤 보고서에 씁니다.

| 이름 | 설명 |
|---|---|
| FilesNotToSnapshot | 섀도 복사본에서 뺄 파일 |
| MaxShadowCopies | 공유 폴더 섀도 복사본의 최대 개수 |
| MinDiffAreaFileSize | 저장 영역의 최소 초기 크기 (MB 단위) |

- VssAccessControl 이라는 키 이름도 있습니다.

## 절차

1. **원본은 건드리지 않습니다.** 증거 이미지의 사본에서 작업합니다.
2. **섀도 복사본이 있는지 봅니다.** 이미지라면 VSS 볼륨 헤더와 카탈로그 위치를 읽습니다. 카탈로그 위치가 0 이면 스냅숏이 없습니다. 읽는 법은 [볼륨 섀도 복사본 구조](../../01-foundations/disk-volume/volume-shadow-copy.md) 의 "섀도 복사본이 있는지 보기" 에 있습니다.
3. **저장 영역의 볼륨을 확인합니다.** 저장 볼륨 GUID 가 다른 볼륨을 가리키면 그 볼륨 이미지도 확보합니다.
4. **스냅숏마다 만든 시각을 적습니다.** 카탈로그 항목에 FILETIME 으로 들어 있습니다. 스냅숏의 순서는 이 시각으로 정합니다. 카탈로그에 적힌 순서가 만든 순서와 같다고 가정하지 않습니다.
5. **스냅숏의 정보를 적습니다.** 저장소 정보에는 섀도 복사본 ID, 세트 ID, 속성 플래그, 작업한 컴퓨터 이름 (Operating Machine), 서비스 컴퓨터 이름 (Service Machine) 이 있습니다.
6. **보려는 시점의 볼륨을 다시 만듭니다.** 다시 만든 볼륨은 파일 시스템으로 열어 읽습니다. NTFS 로 읽는 법은 [NTFS 구조](../../01-foundations/disk-volume/ntfs/index.md) 에 있습니다.
7. **지금 볼륨과 비교합니다.** 파일 목록, 크기, 해시를 비교합니다. 해시로 같은 파일을 찾는 방법은 [해시셋 대조와 유사 해시](hash-set-fuzzy-hash.md) 에 있습니다.
8. **필요한 아티팩트의 예전 판을 꺼냅니다.** 꺼낸 파일은 각 아티팩트의 분석 방법을 그대로 따릅니다. 예로 [레지스트리 하이브 구조](../../01-foundations/database-log-formats/registry-hive/index.md), [이벤트 로그 형식](../../01-foundations/database-log-formats/evtx-evt-etl/index.md), [마스터 파일 테이블](../../02-artifacts/filesystem/mft.md) 이 있습니다.
9. **타임라인에 넣습니다.** 꺼낸 기록마다 어느 스냅숏에서 나왔는지 붙입니다. 방법은 [타임라인 작성](timeline/index.md) 에 있습니다.

## 켜진 시스템에서 보기

켜진 시스템에서는 Windows 에 들어 있는 명령줄 도구로 섀도 복사본을 봅니다.
조사 대상 시스템에서 명령을 실행하는 원칙은 [라이브 응답](../process-acquisition/live-response/index.md) 에 있습니다.

| 도구 | 있는 곳 | 명령 |
|---|---|---|
| VssAdmin | 클라이언트·서버 Windows 모두 | create shadow, delete shadows, list providers, list writers, resize shadowstorage |
| DiskShadow | 서버 Windows 에만 | list, create, import, expose, revert |

VssAdmin 은 섀도 복사본을 만들고, 지우고, 정보를 보여 주며 저장 영역의 크기도 바꿉니다.
다만 기본 공급자가 만든 섀도 복사본만 다루므로, 다른 공급자가 만든 섀도 복사본은 VssAdmin 결과에 나오지 않을 수 있습니다.
DiskShadow 의 expose 는 섀도 복사본을 드라이브 문자 같은 이름으로 드러내는 명령입니다.
create, delete, resize, revert 는 섀도 복사본을 만들거나 지우거나 되돌리는 명령이라서 조사 중에는 정보를 보는 명령만 씁니다.
명령을 실행했다면 실행한 명령과 시각을 기록에 남깁니다.

## 도구

- **헥스 편집기**: 볼륨 헤더, 카탈로그, 저장소 정보를 직접 읽습니다. 도구 결과가 갈리면 여기로 돌아옵니다.
- **libvshadow (libyal)**: VSS 형식 문서를 공개한 오픈 소스 라이브러리입니다.
- **VssAdmin·DiskShadow**: Windows 에 들어 있는 도구입니다. 켜진 시스템에서만 씁니다.
- 두 도구의 결과가 다르면 [도구 결과 교차 검증](../reporting/tool-validation.md) 의 방법으로 헥스와 맞춰 봅니다.

## 함정과 한계

- **오래된 스냅숏이 없다고 누가 지웠다고 씁니다.** 공간이 모자라면 VSS 가 가장 오래된 것부터 지웁니다. 지운 행위는 다른 기록으로 확인합니다. [증거를 없애려 했나](../../04-scenarios/activity/anti-forensics/index.md) 를 봅니다.
- **스냅숏에 없는 파일을 그때 없던 파일로 봅니다.** 페이징 파일 같은 임시 파일과 FilesNotToSnapshot 제외 목록의 파일은 빠집니다. 제외는 최선 노력이라 빠진 파일과 남은 파일이 섞일 수 있습니다.
- **저장 영역이 같은 볼륨에 있다고 가정합니다.** 다른 볼륨일 수 있습니다. 그 볼륨 이미지가 없으면 다시 만들 수 없습니다.
- **VssAdmin 결과에 없으면 섀도 복사본이 없다고 봅니다.** VssAdmin 은 기본 공급자의 섀도 복사본만 다룹니다.
- **만든 시각을 사용자 행위 시각으로 씁니다.** 만든 시각으로 알 수 있는 것은 그 시점의 볼륨 모습이 남아 있다는 사실뿐입니다.
- **최신 Windows 결과를 그대로 믿습니다.** libvshadow 문서가 시험한 판은 Windows 2003 R2 SP2, Vista, 2008, 7, 8 Consumer Preview 입니다. 2012 와 10 은 할 일로 남아 있어, Windows 10·11 이미지는 두 도구로 맞춰 봅니다.
- **조사 중에 섀도 복사본을 새로 만듭니다.** 새 스냅숏이 저장 공간을 쓰면 오래된 스냅숏이 밀려 지워질 수 있습니다. 이 판단은 공간 부족 때 오래된 것부터 지운다는 규칙에서 나온 해석입니다.

## 결과를 어떻게 해석하나

| 알 수 있는 것 | 알 수 없는 것 |
|---|---|
| 스냅숏을 만든 시각에 볼륨이 이런 모습이었다는 것 | 스냅숏 사이에 파일이 몇 번 바뀌었는지 |
| 지금은 없거나 바뀐 파일이 그 시점에 어떤 내용이었는지 | 누가 파일을 만들거나 바꿨는지 |
| 스냅숏 여러 개를 비교해 두 시점 사이에 바뀐 파일 | 스냅숏에 없는 파일이 그 시점에 없었는지 |
| 저장소 정보에 적힌 컴퓨터 이름 | 두 컴퓨터 이름이 각각 무엇을 뜻하는지 |

두 스냅숏 사이에 파일이 바뀌었다면 바뀐 때는 두 스냅숏을 만든 시각 사이라고만 말할 수 있고, 정확한 때는 [USN 변경 저널](../../02-artifacts/filesystem/usnjrnl.md) 이나 [NTFS 트랜잭션 로그](../../02-artifacts/filesystem/logfile.md) 처럼 변경을 기록하는 아티팩트에서 찾습니다.

보고서에는 어느 스냅숏에서 꺼냈는지를 함께 씁니다.

> `<볼륨>` 의 섀도 복사본(만든 시각 `<UTC 시각>`, 섀도 복사본 ID `<값>`)으로 다시 만든 볼륨에 `<경로>` 파일이 있었다. 지금 볼륨의 같은 경로에는 파일이 없다. 두 파일의 해시는 `<알고리즘>` 으로 계산했다.
