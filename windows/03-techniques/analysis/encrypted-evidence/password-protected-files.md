# 암호 걸린 문서·압축 파일 (Password-Protected Files)

> 위치: [암호화 증거 다루기 (Encrypted Evidence)](index.md) > 암호 걸린 문서·압축 파일

## 한 줄 요약

문서와 압축 파일의 암호는 그 파일 형식 안에 표시됩니다.
ZIP 은 일반 비트 플래그의 bit 0 으로 표시합니다.
암호 걸린 오피스 OOXML 문서는 OLE 파일 안의 `EncryptedPackage` 스트림에 들어갑니다.
한글(HWP) 문서는 `FileHeader` 스트림의 속성 bit 1 로 표시합니다.
이 표시를 읽으면 비밀번호 없이도 암호가 걸렸는지 알 수 있고 어떤 방식인지도 좁힐 수 있습니다.

## 언제 쓰나

- 파일 내용 검색에서 본문이 나오지 않는 문서가 있을 때
- 확장자는 `.docx` 인데 ZIP 으로 열리지 않을 때
- 비밀번호 복구에 들어가기 전에 암호 방식을 가려야 할 때
- 한글 문서가 암호 문서인지 배포용 문서인지 가려야 할 때

## 절차

1. **실제 형식을 확인합니다.** 확장자가 아니라 파일 앞머리의 서명으로 형식을 가립니다. 방법은 [파일 내용 검색](../content-search/index.md) 에 있습니다.
2. **형식별 암호 표시를 읽습니다.** 아래 오피스·ZIP·한글 절을 봅니다.
3. **암호 방식을 적습니다.** 방식에 따라 복구할 수 있는지와 걸리는 시간이 다릅니다.
4. **DRM 표시가 있는지도 봅니다.** 암호 표시가 없는데 열리지 않으면 [DRM 문서 판별](enterprise-drm.md) 로 넘어갑니다.
5. **복구가 필요하면 넘깁니다.** 비밀번호를 찾아야 하면 [비밀번호 복구](password-recovery.md) 를 봅니다.
6. **기록합니다.** 파일마다 실제 형식, 암호 표시, 암호 방식, 복호 여부를 적습니다.

### 오피스 문서

아래 표는 Apache POI 문서의 지원 표를 옮긴 것입니다.
POI 가 어느 형식에서 어떤 방식을 읽을 수 있는지를 보여 줍니다.
빈 칸은 POI 가 지원하지 않거나 표에 없다는 뜻입니다. 그 형식이 그 방식을 쓰지 않는다는 뜻은 아닙니다.

| 방식 | `.xls` | `.doc` | `.ppt` | `.xlsx`·`.docx`·`.pptx` |
|---|---|---|---|---|
| XOR 난독화 (XOR Obfuscation) | ○ | | | |
| 40비트 RC4 | ○ | ○ | | |
| RC4 CryptoAPI | ○ | ○ | ○ | |
| RC4 (CryptoAPI 없이, 컨테이너 방식) | | | | ○ |
| ECMA-376 Standard | | | | ○ |
| ECMA-376 Agile | | | | ○ |

- Apache POI 문서는 XOR 난독화 행에 "결함이 있고 아주 작은 파일에만 동작한다" 는 주석을 붙였습니다. POI 버그 보고(#59857)를 가리키는 주석이라, 방식 자체가 아니라 POI 가 처리할 수 있는 범위를 말합니다.
- POI 문서는 OOXML 의 RC4 행에 "명세(MS-OFFCRYPTO)는 이 방식을 제자리 암호화로만 설명하지만 컨테이너 방식도 있는 듯하다" 는 주석을 붙였습니다.
암호 걸린 OOXML(`.docx`·`.xlsx`·`.pptx`)은 ZIP 파일이 통째로 OLE 파일 안의 `EncryptedPackage` 스트림에 들어갑니다. 그래서 확장자는 `.docx` 인데 파일은 ZIP 이 아니라 OLE 복합 파일로 시작합니다. OLE 파일 안의 스트림 목록을 보는 법은 [OLE 복합 파일](../../../01-foundations/shell-document-formats/compound-file-binary.md) 에 있습니다.

- 일부 "쓰기 보호" 파일은 내장 비밀번호 `VelvetSweatshop` 으로 암호화되어 있습니다.

### ZIP

기준 문서는 PKWARE 의 APPNOTE.TXT 6.3.10(2022-11-01)입니다.

| 자리 | 값 | 뜻 |
|---|---|---|
| 일반 비트 플래그 (General Purpose Bit Flag) bit 0 | 1 | 파일이 암호화됨 |
| 일반 비트 플래그 bit 6 | 1 | 강한 암호화 (Strong Encryption). "압축 해제에 필요한 버전" 을 50 이상으로 하고 bit 0 도 1 로 해야 함 |
| 일반 비트 플래그 bit 13 | 1 | 중앙 디렉터리 (Central Directory) 를 암호화하면서 로컬 헤더의 일부 값을 가렸음 |
| 추가 필드 ID 0x0017 | — | 강한 암호화 헤더. 칸은 Format(2)·AlgID(2)·Bitlen(2)·Flags(2)·CertData(가변) |
| 추가 필드 ID 0x9901 | — | AE-x 암호화 구조 (APPNOTE 부록 E) |
| 압축 방법 99 | — | AE-x 암호화 표시 |

- 일반 비트 플래그는 ZIP 안의 항목마다 따로 붙습니다. 그래서 한 ZIP 안에 암호화한 항목과 하지 않은 항목이 섞일 수 있습니다.
- 로컬 파일 헤더, 암호화 헤더, 중앙 디렉터리 끝 레코드에는 압축을 적용하지 않습니다.
- 강한 암호화 헤더의 `AlgID`·`Bitlen` 칸에서 알고리즘과 키 길이를 읽습니다.

### 한글 문서 (HWP 5.0)

한컴의 HWP 5.0 명세(revision 1.3, 2018-11-08)는 한글 2002 이후 제품이 쓰는 파일 형식 5.0 을 다룹니다.
배포용 문서, HWPML, 파일 형식 3.0 은 별도 문서에서 설명한다고 적혀 있습니다.

HWP 5.0 은 스토리지와 스트림으로 나뉘는 복합 파일 (Compound File) 구조이고, 스트림에 따라 압축하거나 암호화합니다.
`FileHeader` 스트림은 파일 인식 정보이며 전체 크기는 256바이트입니다.

`FileHeader` 스트림의 구성은 아래와 같습니다. 오프셋은 명세 표의 길이를 차례로 더해 계산한 값입니다.

| 오프셋 | 형식 | 내용 |
|---|---|---|
| 0 | BYTE[32] | 서명. 문서 파일은 `HWP Document File` |
| 32 | DWORD | 파일 버전. `0xMMnnPPrr` 꼴 (예: 5.0.3.0) |
| 36 | DWORD | 속성 (아래 비트 표) |
| 40 | DWORD | 두 번째 속성. bit 0 CCL·공공누리 라이선스 정보, bit 1 복제 제한 여부, bit 2 동일 조건 하에 복제 허가 여부 |
| 44 | DWORD | EncryptVersion (아래 값 표) |
| 48 | BYTE | 공공누리(KOGL) 라이선스 지원 국가. 6 은 KOR, 15 는 US |
| 49 | BYTE[207] | 예약 |

첫 번째 속성(오프셋 36)에서 암호와 관련된 비트는 아래와 같습니다.

| 비트 | 뜻 |
|---|---|
| bit 0 | 압축 여부 |
| bit 1 | 암호 설정 여부 |
| bit 2 | 배포용 문서 여부 |

- DRM 과 공인 인증서에 관련된 비트는 [DRM 문서 판별](enterprise-drm.md) 에 있습니다.
- 나머지 비트의 뜻은 명세의 속성 표를 봅니다. 한글 문서의 메타데이터 전반은 [문서 메타데이터](../../../02-artifacts/embedded-metadata/document-metadata/index.md) 에 있습니다.

EncryptVersion 값은 아래와 같습니다.

| 값 | 뜻 |
|---|---|
| 0 | None |
| 1 | 한글 2.5 버전 이하 |
| 2 | 한글 3.0 버전 Enhanced |
| 3 | 한글 3.0 버전 Old |
| 4 | 한글 7.0 버전 이후 |

배포용 문서는 모든 스트림에 배포용 문서 데이터 레코드가 들어갑니다.

레코드의 Tag ID 는 `HWPTAG_DISTRIBUTE_DOC_DATA`(`HWPTAG_BEGIN+12`)이고 크기는 256바이트입니다.
배포용 문서 본문을 어디에 어떤 알고리즘으로 넣는지는 이 명세에 없습니다.

XML 로 된 HWPX 형식의 암호 표시는 이 페이지에서 다루지 않습니다.

### PDF·7-Zip·RAR

- 이 세 형식의 암호 표시는 이 페이지에서 다루지 않습니다.
- 복구 방식은 [비밀번호 복구](password-recovery.md) 를 봅니다.
- 어떤 압축 프로그램을 썼는지는 [압축 프로그램 사용 기록](../../../02-artifacts/file-folder-usage/7-zip-winrar-bandizip.md) 에서 찾습니다.

### 헥스로 한 번 따라가기

아래 값은 **명세로 만든 예시**입니다. 실제 검체에서 나온 값이 아닙니다. `??` 는 이 예시에서 정하지 않은 바이트입니다.

```
HWP 문서의 FileHeader 스트림 앞부분 (명세로 만든 예시)
00000000  48 57 50 20 44 6F 63 75  6D 65 6E 74 20 46 69 6C   HWP Document Fil
00000010  65 ?? ?? ?? ?? ?? ?? ??  ?? ?? ?? ?? ?? ?? ?? ??   e...............
```

- 첫 17바이트가 ASCII `HWP Document File` 입니다. 서명 칸은 32바이트입니다.

서명 뒤의 칸을 값으로 읽으면 아래와 같습니다(명세로 만든 예시).

| 오프셋 | 예시 값 | 읽는 법 |
|---|---|---|
| 32 | 0x05000300 | 파일 버전 5.0.3.0 |
| 36 | 0x00000003 | bit 0(압축)과 bit 1(암호 설정)이 켜짐 |
| 44 | 4 | 한글 7.0 버전 이후 방식으로 암호화 |

- 오프셋 36 의 값이 0x00000005 였다면 bit 0 과 bit 2 가 켜진 것입니다. 암호 문서가 아니라 배포용 문서입니다.

## 도구

아래 공개 도구는 예로만 듭니다. 한 도구의 결과에만 기대지 않습니다.

| 도구 | 쓰임 |
|---|---|
| Apache POI (Java 라이브러리) | 오피스 문서의 암호 방식을 가리고, 비밀번호를 알면 복호합니다 |
| OLE 스트림 보기 도구 (Python `olefile` 등) | `EncryptedPackage` 스트림과 HWP 의 `FileHeader` 스트림을 꺼내 봅니다 |
| ZIP 목록 보기 도구 (`zipinfo` 등) | 항목마다 일반 비트 플래그와 압축 방법을 봅니다 |
| 헥스 편집기 | 서명과 플래그 값을 직접 봅니다 |

## 함정과 한계

- **확장자로 형식을 정합니다.** 암호 걸린 `.docx` 는 ZIP 이 아니라 OLE 파일입니다. ZIP 도구로 열리지 않는다고 손상된 파일로 보지 않습니다.
- **암호 표시가 있으면 사용자가 비밀번호를 걸었다고 봅니다.** 일부 "쓰기 보호" 파일은 내장 비밀번호 `VelvetSweatshop` 으로 암호화되어 있습니다. 이 비밀번호부터 넣어 봅니다.
- **배포용 문서를 암호 문서로 적습니다.** HWP 는 암호 설정(bit 1)과 배포용 문서(bit 2)가 다른 비트입니다.
- **ZIP 로컬 헤더 값을 그대로 믿습니다.** bit 13 이 켜져 있으면 로컬 헤더의 일부 값이 가려져 있습니다.
- **bit 6 만 켜진 ZIP 항목을 강한 암호화로 봅니다.** 명세는 bit 6 을 켜면 bit 0 도 켜야 한다고 정합니다. 둘이 어긋나면 파일이 손상되었거나 명세를 따르지 않은 도구가 만든 것일 수 있습니다. 다시 확인합니다.
- **PDF·7-Zip·RAR 도 같은 방법으로 가린다고 봅니다.** 이 페이지의 표시는 오피스·ZIP·HWP 에만 해당합니다.

## 결과를 어떻게 해석하나

- **암호 표시**: 파일을 저장한 때 암호가 걸려 있었다는 뜻입니다. 누가 걸었는지, 비밀번호가 무엇인지는 말하지 않습니다.
- **암호 방식**: 복구할 수 있는지를 가늠하는 근거입니다. 판단은 [비밀번호 복구](password-recovery.md) 에서 합니다.
- **암호 걸린 OOXML 의 문서 속성**: ZIP 전체가 `EncryptedPackage` 안에 들어가므로, ZIP 안에 있던 문서 속성도 암호문 속에 있습니다. 풀기 전에는 작성자·수정 시각 같은 메타데이터를 읽을 수 없습니다(구조에서 끌어낸 판단). 메타데이터 해석은 [문서 메타데이터](../../../02-artifacts/embedded-metadata/document-metadata/index.md) 를 봅니다.
- **`VelvetSweatshop` 으로 풀린 파일**: 사용자가 따로 비밀번호를 걸었다는 근거가 되지 않습니다.
- **`EncryptedPackage` 만 보고 비밀번호 방식이라고 단정하지 않습니다.** 이유는 [DRM 문서 판별](enterprise-drm.md) 에 있습니다.

보고서 문장 예:

- "파일 X 는 확장자가 `.docx` 이지만 OLE 복합 파일이고, 안에 `EncryptedPackage` 스트림이 있다. 암호화한 OOXML 문서로 판단했다."
- "한글 문서 Y 의 `FileHeader` 속성 값은 0x00000003 이고 EncryptVersion 은 4 이다. 암호를 설정한 문서이며, 비밀번호를 찾지 못해 본문을 확인하지 못했다."
