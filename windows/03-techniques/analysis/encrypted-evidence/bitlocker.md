# BitLocker 볼륨 구조와 풀기 (BitLocker)

> 위치: [암호화 증거 다루기 (Encrypted Evidence)](index.md) > BitLocker 볼륨 구조와 풀기

## 한 줄 요약

BitLocker 는 볼륨 전체를 암호화하는 Windows 기능입니다.
볼륨 헤더에는 FVE 메타데이터 블록이 어디 있는지 적혀 있고, 그 메타데이터를 읽으면 이 볼륨에 어떤 키 보호기가 걸렸는지 알 수 있습니다.
볼륨을 풀려면 그 보호기에 맞는 비밀을 구해야 하는데, 압수한 디스크라면 대개 복구 비밀번호를 찾는 일이 됩니다.

## 언제 쓰나

- [암호화 컨테이너 찾기](encrypted-container-detection.md) 에서 BitLocker 볼륨을 찾은 뒤
- 압수한 디스크를 분석 장비에 붙여 읽어야 할 때
- 복구 비밀번호를 어디서 구할지 정해야 할 때
- 볼륨 일부가 손상되어 보통 방법으로 풀리지 않을 때

BitLocker 드라이브를 새 컴퓨터로 옮기면 복구 모드에 들어갑니다.
그래서 압수한 디스크를 다른 장비에 붙이면 TPM 자동 잠금 해제가 되지 않습니다.
이때는 복구 비밀번호나 다른 보호기가 있어야 합니다.

## 절차

### 1. 볼륨과 버전을 가립니다

- 볼륨 헤더의 서명과 점프 코드로 BitLocker 볼륨인지, Vista 인지 Windows 7 이상인지 가립니다.
- 값은 [암호화 컨테이너 찾기](encrypted-container-detection.md) 에 있습니다.

### 2. FVE 메타데이터 블록을 찾습니다

볼륨 헤더에는 FVE 메타데이터 (Full Volume Encryption Metadata) 블록의 위치를 적은 칸이 있습니다.
칸의 자리는 볼륨 종류마다 다릅니다.

| 볼륨 종류 | 위치 칸 (볼륨 헤더 오프셋) | 가리키는 블록 |
|---|---|---|
| Vista | 56 (0x38), 8바이트. 클러스터 블록 번호 | 블록 1 |
| Windows 7 이상 | 176 (0xB0)·184 (0xB8)·192 (0xC0), 각 8바이트 | 블록 1·2·3 |
| BitLocker To Go | 440 (0x1B8)·448 (0x1C0)·456 (0x1C8), 각 8바이트 | 블록 1·2·3 |

메타데이터 블록은 볼륨마다 3벌이고, Vista 볼륨 헤더에는 블록 1 의 위치 칸만 있습니다.
블록은 오프셋 0 의 서명 `-FVE-FS-`(8바이트)로 시작하고, 블록 오프셋 10 의 2바이트는 메타데이터 버전입니다. 1 이면 Vista, 2 면 Windows 7 이상입니다.
블록 1 이 깨졌으면 2·3 번 칸이 가리키는 블록을 읽습니다.

Windows 7 이상과 BitLocker To Go 는 원래 볼륨 헤더(볼륨 맨 앞 섹터들)를 암호화해 다른 자리에 옮겨 두고, 옮긴 자리는 FVE 메타데이터에 적힙니다.
옮긴 헤더는 흔히 8,192바이트(16섹터)입니다.
그래서 BitLocker 볼륨의 첫 섹터를 NTFS 부트 섹터로 읽으면 안 됩니다.
NTFS 부트 섹터의 구조는 [NTFS 구조](../../../01-foundations/disk-volume/ntfs/index.md) 를 봅니다.

### 3. 키 보호기를 확인합니다

FVE 메타데이터의 볼륨 마스터 키 (Volume Master Key, VMK) 항목에는 보호 종류 값이 있습니다.
이 값이 그 VMK 를 무엇으로 보호했는지 알려 줍니다.

| 값 | 보호 방식 |
|---|---|
| 0x0000 | 보호 없음 (Clear Key) |
| 0x0100 | TPM |
| 0x0200 | 시작 키 (Startup Key) |
| 0x0500 | TPM + PIN |
| 0x0800 | 복구 비밀번호 (Recovery Password) |
| 0x2000 | 비밀번호 (Password) |

보호기 목록을 먼저 적어 두면 어떤 비밀을 찾아야 하는지가 정해집니다. TPM 보호기만 보고 포기하지 않으며, 복구 비밀번호 보호기가 함께 걸려 있으면 그것으로 풉니다.

BitLocker 를 일시 중지 (Suspend) 해도 드라이브는 완전히 암호화된 채로 남고, 일시 중지한 볼륨은 재부팅 때 보호가 자동으로 다시 켜집니다.
PowerShell 이나 `manage-bde.exe` 로 재부팅 횟수를 정해 두었다면 예외입니다.

### 4. 복구 수단을 찾습니다

| 수단 | 모습 | 저장할 수 있는 곳 | 알아 둘 점 |
|---|---|---|---|
| 복구 비밀번호 | 48자리 숫자. 6자리씩 8묶음을 하이픈으로 이음 | 텍스트 파일, 인쇄물, Microsoft Entra ID, Active Directory | 묶음마다 11로 나누어떨어짐 |
| 복구 키 (Recovery Key) | 이동식 매체에 저장한 키 파일 `<protector_id>.bek` | 이동식 매체 | 암호화 키를 파일로 저장한 것 |
| 키 패키지 (Key Package) | `BitLocker Key Package {<id>}.KPG` | 파일, AD DS | 자동으로 만들어지지 않음. Entra ID 에는 저장 불가. 복구 비밀번호나 복구 키와 함께 써야 함 |
| 데이터 복구 에이전트 (Data Recovery Agent, DRA) 인증서 | 인증서 | — | 공개 키가 맞는 BitLocker 드라이브를 모두 풀 수 있음 |

- 복구 비밀번호는 묶음마다 11로 나누어떨어져야 합니다. 11로 나눈 몫은 16비트 값(65,535 이하)이고, 몫 8개가 모여 128비트 키가 됩니다. 그래서 문서나 메모에서 찾은 48자리 숫자가 복구 비밀번호 형식에 맞는지 먼저 걸러 낼 수 있습니다.
- 키 패키지는 BitLocker Repair 도구로 손상된 드라이브의 중요한 부분을 되살릴 때 쓰는 복호 키입니다. 복구 비밀번호나 복구 키가 함께 있어야 손상된 부분을 풀 수 있습니다.
- 키 패키지는 드라이브 식별자가 맞는 드라이브에만 쓸 수 있습니다.
- 키 패키지를 새로 만들려면 잠금이 풀린 볼륨과 로컬 관리자 권한이 있어야 합니다. 켜진 시스템에서 `manage-bde.exe -KeyPackage C: -id <id> -path <path>` 로 만듭니다.
- 이 명령을 실행하면 `<path>` 에 `BitLocker Key Package {<id>}.KPG` 파일이 생깁니다. 증거 볼륨이 아닌 외부 매체를 `<path>` 로 줍니다.
- DRA 로 운영체제 드라이브를 풀려면 그 드라이브를 다른 장치에 데이터 드라이브로 붙여야 합니다.
- DRA 인증서의 기본 EKU 는 `1.3.6.1.4.1.311.67.1.1` 입니다.

### 5. 복구 비밀번호가 보관된 곳을 확인합니다

풀기 전에 보관처부터 확인합니다. 장치가 어디에 가입했는지에 따라 보관처가 다릅니다.

| 장치 | 보관처 | 찾는 방법 |
|---|---|---|
| Microsoft Entra 가입 | Entra ID. 자료 형식 이름 `bitlockerRecoveryKey` | Entra 관리 센터, Intune 관리 센터, PowerShell, Microsoft Graph |
| Active Directory 가입 | AD DS. 컴퓨터 개체의 자식 개체 (cn `ms-FVE-RecoveryInformation`) | 아래 속성 표 |
| 가입하지 않고 Microsoft 계정을 쓰는 장치 | 사용자의 Microsoft 계정 | 사용자 계정 |

- Entra·AD 에 가입하지 않은 장치는 Microsoft 계정에 저장하는 방법을 기본으로 권합니다.
- 이동식 저장장치의 복구 키는 Entra ID 와 AD DS 에 자동으로 저장되지 않습니다. PowerShell 이나 `manage-bde` 로 따로 저장했을 때만 있습니다.

AD DS 의 복구 정보 개체에는 아래 속성이 있습니다.

| 속성 | 내용 |
|---|---|
| `ms-FVE-RecoveryPassword` | 48자리 복구 비밀번호 |
| `ms-FVE-RecoveryGuid` | 복구 비밀번호에 딸린 GUID. 복구 화면에 이 GUID 가 나오므로 맞는 비밀번호를 고를 때 씁니다 |
| `ms-FVE-VolumeGuid` | 볼륨마다 다른 GUID |
| `ms-FVE-KeyPackage` | 키 패키지 |

개체 이름은 `<Object Creation Date and Time><Recovery GUID>` 꼴이고 길이는 63자로 정해져 있습니다.
AD 는 컴퓨터 개체의 복구 비밀번호 이력을 모두 남기고 컴퓨터 개체를 지우지 않으면 옛 키도 자동으로 지워지지 않으므로, 한 컴퓨터에 복구 정보 개체가 여러 개 있을 수 있습니다. 복구 화면에 나오는 GUID 와 `ms-FVE-RecoveryGuid` 가 같은 개체를 고릅니다.

- 도메인 컨트롤러를 오프라인으로 분석한다면 [액티브 디렉터리 DB](../../../02-artifacts/credentials/ntds-dit.md) 를 봅니다.

### 6. 풀고 기록합니다

복구 비밀번호로 키를 만들 때는 솔트를 섞어 SHA-256 을 1,048,576번 반복하므로, 복구 비밀번호를 대입으로 찾는 일은 느립니다. 대입이 필요하면 [비밀번호 복구](password-recovery.md) 를 봅니다.
복호는 증거 이미지의 사본이나 읽기 전용 연결에서 하고, 풀린 볼륨은 그 안의 파일 시스템에 맞춰 분석합니다.
쓴 보호기, 비밀의 출처, 도구와 그 버전을 적습니다.

암호화 방식 값은 아래와 같습니다. 도구가 방식을 보여 주면 이 값과 맞춰 봅니다.

| 값 | 암호화 방식 |
|---|---|
| 0x8000 | AES-128-CBC + Elephant Diffuser |
| 0x8001 | AES-256-CBC + Elephant Diffuser |
| 0x8002 | AES-128-CBC |
| 0x8003 | AES-256-CBC |
| 0x8004 | AES-128-XTS |
| 0x8005 | AES-256-XTS |

### 헥스로 한 번 따라가기

아래 내용은 **명세로 만든 예시**입니다. 실제 검체에서 나온 값이 아닙니다.

```
볼륨 헤더 (Windows 7 이상) 의 메타데이터 위치 칸 (명세로 만든 예시)
000000B0  ?? ?? ?? ?? ?? ?? ?? ??   오프셋 176: FVE 메타데이터 블록 1 위치
000000B8  ?? ?? ?? ?? ?? ?? ?? ??   오프셋 184: 블록 2 위치
000000C0  ?? ?? ?? ?? ?? ?? ?? ??   오프셋 192: 블록 3 위치
```

```
FVE 메타데이터 블록 앞부분 (명세로 만든 예시)
00000000  2D 46 56 45 2D 46 53 2D  ?? ?? vv vv               -FVE-FS-....
```

- 칸 세 개가 가리키는 자리마다 이 모양의 블록이 있어야 합니다.
- 첫 8바이트 `2D 46 56 45 2D 46 53 2D` 는 ASCII `-FVE-FS-` 입니다.
- `vv vv` 는 오프셋 10 의 2바이트 버전입니다. Windows 7 이상이면 값이 2 입니다.

복구 비밀번호 형식을 확인하는 예도 한 번 봅니다.

```
111111-222222-333333-444444-555555-666666-000000-110011
```

- 이 값은 형식만 맞춘 **만든 예시**이고 실제 키가 아닙니다.
- 6자리씩 8묶음이며, 묶음마다 11로 나누어떨어집니다. 예를 들어 111111 = 11 × 10101 입니다.
- 몫은 65,535 이하여야 합니다. 666666 ÷ 11 = 60606 이라 괜찮지만, 777777 ÷ 11 = 70707 은 16비트를 넘으므로 복구 비밀번호 묶음이 될 수 없습니다.
- `123456` 같은 묶음이 섞여 있으면 11로 나누어떨어지지 않으므로 복구 비밀번호가 아닙니다.

## 도구

아래 공개 도구는 예로만 듭니다. 한 도구의 결과에만 기대지 않습니다.

| 도구 | 쓰임 |
|---|---|
| libbde (`bdeinfo`, `bdemount`) | 메타데이터와 보호기 종류를 읽고, 복구 비밀번호로 볼륨을 읽기 전용으로 붙입니다 |
| `manage-bde.exe` (Windows 기본) | 켜진 시스템에서 키 패키지를 만듭니다 |
| BitLocker Repair 도구 | 키 패키지로 손상된 드라이브의 중요한 부분을 되살립니다 |
| 헥스 편집기 | 위치 칸과 메타데이터 블록 서명을 직접 봅니다 |

풀린 결과가 도구마다 다르면 [도구 결과 교차 검증](../../reporting/tool-validation.md) 을 봅니다.

## 함정과 한계

- **일시 중지 상태면 평문이라고 봅니다.** 일시 중지해도 드라이브는 암호화된 채로 남습니다. 이미지는 여전히 복호해야 합니다.
- **원래 PC 에 디스크를 다시 끼우고 켜 봅니다.** 메인보드 교체, BIOS/UEFI 펌웨어 업그레이드, 부트 관리자 변경, NTFS 파티션 표 변경, PXE 부팅 같은 일이 있었으면 복구 모드로 들어갑니다. PIN 을 여러 번 틀리거나 TPM 을 끄거나 지운 경우도 같습니다. 원본을 부팅하는 일 자체도 증거를 바꿉니다.
- **복구 비밀번호가 하나뿐이라고 봅니다.** AD 는 옛 복구 비밀번호도 남깁니다. GUID 로 맞는 것을 고릅니다.
- **이동식 드라이브의 복구 키도 AD 에 있다고 봅니다.** 이동식 저장장치의 복구 키는 자동으로 저장되지 않습니다.
- **키 패키지가 늘 있다고 봅니다.** 키 패키지는 자동으로 만들어지지 않습니다. Entra ID 에는 저장할 수도 없습니다.
- **전원을 끈 뒤 키 패키지를 만들려 합니다.** 키 패키지는 잠금이 풀린 볼륨에서만 새로 만들 수 있습니다. 볼륨이 손상될 걱정이 있으면 켜진 상태에서 먼저 만듭니다.
- **첫 섹터를 NTFS 부트 섹터로 읽습니다.** Windows 7 이상은 원래 볼륨 헤더를 다른 자리에 옮겨 둡니다.

## 결과를 어떻게 해석하나

- **보호기 목록**: 이 볼륨을 여는 방법이 무엇으로 설정되어 있었는지를 보여 줍니다. 누가 언제 설정했는지는 보여 주지 않습니다.
- **AD 의 복구 정보 개체**: 개체 이름 앞부분은 개체를 만든 날짜와 시각입니다. 복구 비밀번호가 AD 에 올라간 때를 가늠하는 단서가 됩니다. 이 시각이 UTC 인지 현지 시각인지는 공개 문서에 나와 있지 않아 검체에서 확인해야 합니다.
- **개체가 여러 개**: 한 컴퓨터의 복구 비밀번호가 여러 번 새로 올라갔다는 뜻입니다. AD 는 복구 비밀번호 이력을 모두 남깁니다.
- **풀린 볼륨의 내용**: 암호화하지 않은 볼륨과 같은 방법으로 분석합니다. 어느 비밀로 풀었는지를 보고서에 함께 씁니다.

보고서 문장 예:

- "볼륨 X 의 FVE 메타데이터에는 TPM(0x0100) 보호기와 복구 비밀번호(0x0800) 보호기가 있다."
- "AD DS 에서 `ms-FVE-RecoveryGuid` 가 복구 화면의 GUID 와 같은 개체를 찾았다. 이 개체의 복구 비밀번호로 볼륨 X 를 읽기 전용으로 풀었다."
