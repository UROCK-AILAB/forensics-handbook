# 파일 카빙 (File Carving)

파일 카빙 (File Carving) 은 파일시스템의 메타정보 없이 원시 데이터만 분석해 파일을 되살리는 방법입니다. 파일 형식마다 정해진 서명으로 시작점을 찾고, 끝 표시나 파일 머리에 적힌 크기로 끝을 정하며, 결과에는 파일 이름·시각·원래 경로가 없습니다.

이 페이지는 [삭제 데이터 복구 (Data Recovery)](index.md) 의 하위 주제입니다. 이름과 시각까지 되살릴 수 있는지는 먼저 [파일시스템 기반 복구 (Undelete: NTFS·FAT)](undelete-ntfs-fat.md) 로 봅니다. 카빙할 데이터를 어디서 뽑는지는 [비할당 영역과 슬랙 (Unallocated·Slack Space)](unallocated-slack-space.md) 에 있습니다. 파일보다 작은 레코드 단위로 찾는 방법은 [레코드 카빙 (Record Carving)](record-carving.md) 에서 다룹니다.

## 언제 쓰나

- 디렉터리 자료가 없거나 망가져서 파일시스템 기반 복구를 쓸 수 없을 때 씁니다.
- 비할당 영역과 슬랙에서 뽑은 데이터에서 파일을 찾을 때 씁니다.
- 메모리 덤프에서 파일을 찾을 때 씁니다. 최근 본 그림이나 대화처럼 디스크에 남지 않는 데이터를 얻을 수 있습니다. 메모리 이미지 다루는 법은 [메모리 분석](../memory-forensics/index.md) 에 있습니다.

## 원리

### 서명과 끝 표시

가장 단순한 방법은 파일 형식마다 정해진 서명 (매직 넘버) 으로 시작점을 찾는 것입니다. 예를 들어 Java class 파일은 첫 4바이트가 `CA FE BA BE` 입니다. 일부 형식에는 끝 표시 (Footer) 가 있어 파일 끝도 찾을 수 있고, 일부 형식은 파일 머리에 원래 크기가 적혀 있어 그 크기로 끝을 자를 수 있습니다.

### 조각화

대부분의 파일시스템은 크기가 같은 클러스터 단위로 저장하는데, 클러스터보다 큰 파일은 여러 조각으로 흩어질 수 있고 조각난 파일은 서명과 끝 표시만으로 되살리기 어렵습니다.

Garfinkel(2007) 연구에서 형식별로 조각난 비율은 이렇습니다[1].

| 형식 | 조각난 비율 |
|---|---|
| JPEG | 16% |
| Word 문서 | 17% |
| AVI | 22% |
| PST | 58% |

조각난 파일을 다루는 방법은 이렇습니다.

두 조각으로 나뉜 파일은 bifragment gap carving 으로 다루는데, 앞 조각과 뒤 조각을 이어 붙여 올바른 파일이 되는지 빠르게 검사하며 되살립니다. SmartCarving 은 두 조각보다 많이 나뉜 파일을 다루며, 전처리·모으기·다시 잇기 단계를 거치고 알려진 파일시스템의 조각화 습성을 씁니다.

## 절차

아래 2·3단계는 공개 도구 PhotoRec 이 일하는 방식을 예로 든 것입니다.

1. 대상 데이터를 정합니다. 비할당 영역에서 뽑은 데이터, 이미지 전체, 메모리 덤프 가운데 무엇을 볼지 적습니다.
2. 블록(클러스터) 크기를 정합니다. 파일시스템이 멀쩡하면 superblock(FAT·NTFS 는 부트 섹터)에서 읽습니다. 멀쩡하지 않으면 섹터 단위로 읽으며 처음 10개 파일을 찾고, 그 위치로 블록 크기를 계산합니다.
3. 블록 단위로 읽으며 각 블록을 서명 목록과 비교합니다.
4. 끝을 정합니다. 끝 표시가 있으면 끝 표시까지, 파일 머리에 크기가 있으면 그 크기까지 자릅니다.
5. 되살린 파일마다 이미지 안 시작 오프셋과 끝을 정한 방법을 적습니다.
6. 되살린 파일이 형식대로 열리는지 확인합니다. 서명만 맞고 파일이 아닌 결과를 여기서 거릅니다.
7. 해시를 구해 알려진 파일과 맞춰 봅니다. 방법은 [해시셋 대조와 유사 해시](../hash-set-fuzzy-hash.md) 에 있습니다.

## 헥스로 한 번 따라가기

아래는 설명용으로 만든 예시입니다. 실제 데이터에서 떠낸 바이트가 아닙니다. `??` 는 이 설명에 쓰지 않는 바이트입니다. 블록 크기는 4,096바이트(0x1000)라고 가정합니다.

```
오프셋    00 01 02 03 04 05 06 07  08 09 0A 0B 0C 0D 0E 0F
00039FF0  ?? ?? ?? ?? ?? ?? ?? ??  ?? ?? ?? ?? ?? ?? ?? ??
0003A000  CA FE BA BE ?? ?? ?? ??  ?? ?? ?? ?? ?? ?? ?? ??
```

0x3A000 은 0x1000 의 배수이고 0x3A000 ÷ 0x1000 = 0x3A 이므로 블록 58번의 시작입니다. 블록 시작에 Java class 서명 `CA FE BA BE` 가 있어서 이 블록을 Java class 파일의 시작 후보로 잡습니다. 끝을 정하는 방법은 형식마다 다릅니다. 끝을 정한 방법과 시작 오프셋 0x3A000 을 결과에 함께 적습니다.

## 도구

공개 도구의 예입니다.

- PhotoRec: 파일시스템을 무시하고 밑의 데이터를 직접 읽습니다. 그래서 파일시스템이 심하게 망가졌거나 다시 포맷한 매체에서도 동작합니다.
  - 지원하는 파일시스템은 FAT, NTFS, exFAT, ext2/3/4, HFS+ 입니다.
  - 480개가 넘는 확장자(약 300개 형식 묶음)를 지원합니다.
  - GNU GPL v2 이상으로 배포합니다.
- Foremost
- Scalpel: 2005년에 나온 오픈소스 도구입니다.

도구마다 서명 목록과 끝을 정하는 방식이 다릅니다. 결과가 다르면 [도구 결과 교차 검증](../../reporting/tool-validation.md) 을 따릅니다.

## 함정과 한계

- 지운 파일의 메타정보는 잃습니다. 파일 이름, 날짜·시각, 크기, 원래 위치가 없습니다.
- 조각나지 않은 파일은 되살린 결과가 원본과 같거나 더 큽니다. 끝을 정확히 모르면 원본보다 클 수 있고, 크기가 다르면 해시도 원본과 다릅니다.
- 조각난 파일도 일부는 되살릴 수 있습니다. 다만 뒷부분에 다른 파일의 내용이 섞여 나올 수 있습니다.
- 서명이 맞아도 파일이 아닐 수 있습니다. 되살린 파일이 형식대로 열리는지 확인합니다.
- 빈 공간과 슬랙에는 조각이 수천 개 들어 있을 수 있습니다. 도구 없이 손으로 뽑기 어렵습니다.
- SSD 에서는 지운 데이터가 이미 비워졌을 수 있습니다. [SSD TRIM과 복구 한계 (SSD·TRIM)](ssd-trim.md) 를 봅니다.

## 결과를 어떻게 해석하나

**증명하는 것**

- 이미지의 그 오프셋에 그 형식의 데이터가 있었다는 것
- 그 데이터의 내용

**증명하지 못하는 것**

- 원래 파일 이름과 경로
- 파일시스템 시각(만든·수정·접근 시각)과 지운 시각
- 누가 만들었고 누가 지웠는지
- 되살린 결과가 원래 파일 전체와 같은지. 조각난 파일은 뒷부분이 다른 데이터일 수 있습니다.

파일 안에 적힌 메타데이터는 내용과 함께 나옵니다. 사진이면 [사진 EXIF](../../../02-artifacts/embedded-metadata/exif.md), 문서면 [문서 메타데이터](../../../02-artifacts/embedded-metadata/document-metadata/index.md) 로 읽습니다. 이 값은 파일 안에 적힌 값이고 파일시스템 시각이 아닙니다.

보고서 문장 예: "이미지 오프셋 X 에서 시작하는 JPEG 형식 데이터를 카빙으로 되살렸다. 이 데이터에는 파일 이름과 파일시스템 시각이 없다. 되살린 파일 안의 EXIF 에는 시각 T 가 적혀 있다."
