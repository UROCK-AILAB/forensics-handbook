# 도구 결과 교차 검증 (Tool Validation)

## 한 줄 요약

도구가 보여 주는 값은 원시 데이터를 그 도구 방식대로 해석한 결과라서, 보고서에 쓸 값은 해석 경로가 다른 방법으로 한 번 더 읽어 맞춰 보고 두 결과가 다르면 원시 바이트를 직접 읽어 가립니다.

이 페이지는 도구 결과를 서로 맞춰 보는 방법을 다룹니다. 조사 전체 흐름은 [포렌식 조사 절차](../process-acquisition/investigation-process.md)에, 원본과 사본의 해시를 맞추는 방법은 [증거 획득](../process-acquisition/evidence-acquisition/index.md)에 있습니다.

## 언제 쓰나

- 보고서에 들어갈 값을 확정할 때 씁니다. 시각, 건수, 경로, 해시가 그 예입니다.
- 두 도구가 같은 파일에서 다른 값을 낼 때 씁니다.
- 도구가 0건을 냈을 때 씁니다. "기록이 없다" 고 쓰기 전에 확인합니다.
- 손상됐거나 비정상 종료된 파일을 읽었을 때 씁니다.
- 새 도구를 들이거나 쓰던 도구의 판을 올렸을 때 씁니다.

모든 값을 두 번 읽을 필요는 없습니다. 결론을 떠받치는 값부터 확인합니다.

### 도구 결과가 갈리는 곳

## 절차

1. **확인할 값을 고릅니다.** 결론을 떠받치는 값과 보고서에 숫자로 들어갈 값부터 고릅니다. 0건이 나온 결과와 예상과 크게 다른 값도 넣습니다.
2. **입력을 고정합니다.** 원본이 아니라 해시를 확인한 사본에서 작업합니다. 그러면 두 방법이 같은 사본을 읽었다는 것을 해시로 보일 수 있습니다. 원본을 도구로 열면 바뀌는 경우는 [포렌식 조사 절차](../process-acquisition/investigation-process.md)의 "함정과 한계" 에 있습니다.
3. **도구 정보를 적습니다.** 도구 이름, 판, 설정, 실제로 입력한 명령줄 인자를 적습니다.
    - SP 800-86 은 라이브 수집 도구마다 해시값, 라이선스, 판과 실제로 입력한 명령줄 인자를 기록하라고 권합니다 (5.2.1.1).
    - 이미징 소프트웨어·하드웨어의 이름, 판, 라이선스 정보도 적으라고 합니다 (4.2.1).
    - 출력 시간대 같은 표시 설정도 함께 적습니다. 같은 도구도 설정에 따라 다른 값을 보여 줍니다.
4. **해석 경로가 다른 두 번째 방법을 고릅니다.** 두 번째 방법은 첫 도구와 다른 경로로 원시 데이터를 읽어야 합니다. 같은 라이브러리로 해석하는 두 도구는 같은 곳에서 함께 틀릴 수 있습니다. ESE 데이터베이스라면 JET API 로 여는 방법과 페이지를 직접 해석하는 방법이 서로 다른 경로입니다. 페이지를 직접 해석하는 방법은 트랜잭션 로그 없이 읽습니다(현장 관찰 사례).
5. **비교할 조건을 맞춥니다.** 시각은 UTC 인지 현지 시각인지와 정밀도가 어느 자리까지인지를 맞추고, 건수는 지운 레코드를 넣었는지와 중복을 뺐는지를 맞춥니다. 시각 기준을 맞추는 방법은 [타임라인 작성](../analysis/timeline/index.md)에 있습니다.
6. **결과를 맞춰 봅니다.** 건수가 같아도 값까지 같은지 몇 건을 골라 대조합니다. 뽑아낸 파일은 해시로 비교합니다.
7. **다르면 원시 바이트로 가립니다.** 형식 문서를 보고 그 값이 저장된 자리를 헥스로 읽습니다. 어느 도구가 어느 단계에서 달라졌는지 찾습니다. 아래 "직접 따라가 보기" 가 한 예입니다.
8. **차이와 판정을 기록합니다.** 두 도구의 값, 원시 바이트에서 읽은 값, 보고서에 쓴 값과 그 까닭을 적습니다. 원인을 찾지 못했으면 두 값을 모두 적습니다. 보고서에 쓰는 방법은 [분석 보고서 작성](forensic-report.md)에 있습니다.
9. **도구를 들이거나 판을 올릴 때 미리 시험합니다.** 답을 아는 데이터로 먼저 돌려 봅니다. SP 800-86 은 NIST CFTT(Computer Forensics Tool Testing) 프로젝트가 디스크 이미징 도구를 검증하는 절차를 만들었다고 적었습니다 (4.2.1).

### 직접 따라가 보기 — 이벤트 ID 의 두 가지 표기

관찰한 PC 한 대에서 서비스 설치 이벤트는 이벤트 XML 에 `<EventID Qualifiers='16384'>7045</EventID>` 로 들어 있었습니다. 공급자 메타데이터에 적힌 이 이벤트의 원시 ID 는 1073748869 였습니다. 그래서 도구에 따라 이 이벤트가 7045 로도, 1073748869 로도 보일 수 있습니다(현장 관찰 사례).

두 값이 같은 이벤트를 가리키는지는 16진수로 바꿔 나눠 보면 알 수 있습니다. 아래 계산은 관찰한 값으로 만든 예시입니다.

| 단계 | 값 | 뜻 |
|---|---|---|
| 10진 원시 값 | 1073748869 | 한 도구가 보여 준 값 |
| 16진으로 바꾼 값 | 0x40001B85 | |
| 위 16비트 | 0x4000 = 16384 | XML 의 Qualifiers 값과 같습니다 |
| 아래 16비트 | 0x1B85 = 7045 | XML 의 EventID 값과 같습니다 |

두 도구는 같은 이벤트를 다르게 보여 준 것이므로 이벤트 ID 로 걸러 찾을 때는 두 표기를 모두 넣습니다. 이벤트 로그의 저장 구조는 [이벤트 로그 형식](../../01-foundations/database-log-formats/evtx-evt-etl/index.md)에 있습니다.

## 도구

교차 검증에서는 특정 프로그램보다 해석 경로가 서로 다른지가 중요합니다. 아래 도구는 예입니다.

| 쓰임 | 예 | 메모 |
|---|---|---|
| 뽑은 파일 비교 | PowerShell `Get-FileHash` | -Algorithm 에 SHA1, SHA256, SHA384, SHA512, MD5 를 줄 수 있습니다. 기본값은 SHA256 입니다 [5]. |
| 원시 바이트 확인 | 헥스 편집기와 형식 문서 | 형식 문서는 오프셋과 값의 뜻을 알려 줍니다. 이 페이지의 압축·이미지 사례는 libyal 프로젝트의 형식 문서에서 가져왔습니다 [2][3]. |
| 레지스트리 값 확인 | 공개 레지스트리 분석 플러그인(예: RegRipper) | 플러그인이 시각을 어떻게 바꿔 보여 주는지 소스에서 확인합니다 [4]. |
| 시험용 데이터 | 답을 아는 데이터 | 도구를 들이거나 판을 올릴 때 먼저 돌려 봅니다. |

## 함정과 한계

- **두 도구가 같은 값을 내도 맞다는 보장은 없습니다.** 같은 라이브러리나 같은 해석 규칙을 쓰면 함께 틀립니다. 두 번째 방법이 정말 다른 경로로 읽는지 확인합니다.
- **오류 메시지가 없다고 값이 맞는 것은 아닙니다.** 앞 표의 긴 값 사례처럼 도구는 오류 없이 틀린 값을 낼 수 있습니다.
- **0건은 "기록이 없다" 와 다릅니다.** 앞 표의 Windows Search 사례처럼 도구가 찾는 이름과 실제 이름이 다르면 0건이 나옵니다.
- **많이 낸 쪽이 늘 맞지는 않습니다.** 앞 표의 손상 데이터베이스 사례에서는 적게 낸 쪽이 B-트리를 끝까지 따라가지 못했습니다. 반대로 카빙은 조각난 파일의 뒷부분을 다른 파일 내용으로 채워 낼 수 있습니다. 카빙은 [삭제 데이터 복구](../analysis/data-recovery/index.md)에서 다룹니다. 어느 쪽이 맞는지는 원시 바이트로 가립니다.
- **라이브 수집 결과는 다시 뽑아 비교하기 어렵습니다.** 켜진 시스템에서는 파일과 메모리가 계속 바뀌는데, SP 800-86 은 라이브 시스템의 물리 장치 전체를 비트 단위로 뜨면 검증할 수 없다고 봅니다 (4.2.1). 라이브 결과는 수집 시각과 명령을 함께 남기고 그 뒤 디스크 이미지에 남은 기록과 맞춰 봅니다.
- **수집 도구도 흔적을 남깁니다.** SP 800-86 은 도구마다 시스템을 어떻게 바꾸는지 미리 알아 두라고 권합니다 (5.2.1.1). 자세한 내용은 [라이브 응답](../process-acquisition/live-response/index.md)에 있습니다.
- **원시 바이트로도 뜻을 정하지 못할 때가 있습니다.** 형식 문서가 다루지 않는 경우가 그렇습니다. 앞 표의 LZNT1 사례에서도 Windows 의 동작은 확인하지 못했습니다.

## 결과를 어떻게 해석하나

| 결과 | 판단 | 보고서에 적을 것 |
|---|---|---|
| 해석 경로가 다른 두 방법이 같은 값을 냄 | 값을 씁니다. | 두 방법의 이름과 판 |
| 값이 다르고, 원시 바이트로 원인을 찾음 | 원시 바이트와 맞는 값을 씁니다. | 두 값, 원인, 판정 근거 |
| 값이 다르고, 원인을 찾지 못함 | 한 값으로 정하지 않습니다. | 두 값과 "정할 수 없음" |
| 한 방법으로만 읽을 수 있음 | 검증하지 못한 값으로 다룹니다. | 검증하지 못했다는 사실 |

- 같은 값이 나와도 뜻까지 정해지지는 않습니다. 앞 표의 네트워크 목록 사례에서 두 도구가 같은 숫자를 보여 줘도, 그 숫자가 UTC 인지 현지 시각인지는 다른 기록과 맞춰 봐야 정할 수 있습니다.
- 결론을 낼 수 없다는 판단도 알맞은 결과입니다. 근거는 [포렌식 조사 절차](../process-acquisition/investigation-process.md)의 "결과를 어떻게 해석하나" 에 있습니다.
