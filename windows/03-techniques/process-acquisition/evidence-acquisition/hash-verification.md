# 해시로 무결성 검증 (Hash Verification)

> 상위 허브: [증거 획득 (Evidence Acquisition)](index.md)

## 한 줄 요약

해시 검증은 원본과 사본의 메시지 다이제스트 (Message Digest) 를 계산해 같은지 비교하는 일입니다.
다이제스트는 해시 함수로 계산한 값이고, 흔히 해시 값이라고 부릅니다.
이 무결성 검증은 데이터 획득의 마지막 단계입니다.

## 언제 쓰나

- 비트 스트림 이미지를 뜰 때 씁니다. 이미징 전후로 원본과 사본을 비교합니다.
- 논리 백업이나 선별 수집으로 파일을 가져올 때 씁니다. 이때는 파일마다 비교합니다.
- 포렌식 활동에서 얻은 모든 데이터에 씁니다. 로그 파일과 논리 백업도 여기에 들어갑니다.
- 가능하면 수집한 증거의 체크섬을 만들고 암호 서명을 합니다.
- 증거 자체는 바꾸지 않습니다.

## 절차

### 비트 스트림 이미지

1. 이미지를 뜨기 전에 원본 매체의 다이제스트를 계산해 기록합니다.
2. 이미징 뒤에 사본의 다이제스트를 계산합니다.
3. 사본 값을 원본 값과 비교합니다.
4. 원본의 다이제스트를 다시 계산합니다. 이미징이 원본을 바꾸지 않았는지 확인하는 단계입니다.
5. 모든 결과를 기록합니다.
6. 다이제스트는 읽기 전용이나 한 번 쓰기 (Write-Once) 매체에 저장합니다. 인쇄해서 안전한 곳에 두어도 됩니다.

> 그림 자리: 원본 해시(이미징 전) → 이미징 → 사본 해시 → 비교 → 원본 해시(이미징 후) 로 이어지는 흐름

이미징 절차 전체는 [디스크 이미징](disk-imaging.md) 에 있습니다.

### 논리 백업과 선별 수집물

같은 절차를 따릅니다.
다만 다이제스트를 데이터 파일마다 계산해 비교합니다.
어떤 파일을 모을지 고르는 법은 [선별 수집](triage-collection.md) 에 있습니다.

## 알고리즘 고르기

| 알고리즘 | 다이제스트 길이 | 승인·사용 범위 |
|---|---|---|
| MD5 | 16바이트 (128비트) | FIPS 승인 알고리즘이 아닙니다 |
| SHA-1 | 20바이트 (160비트) | 충돌 저항이 필요한 용도에는 그만 써야 합니다 |
| SHA-2 계열 (SHA-224·SHA-256 등) | 알고리즘마다 다릅니다 | 보안 해시가 필요한 모든 용도에 쓸 수 있습니다 |
| SHA-3 (SHA3-224·256·384·512) | 알고리즘마다 다릅니다 | 모든 용도에 승인됐습니다 |

### SP 800-86 (2006) 이 적은 것

- SP 800-86 은 가장 흔한 알고리즘으로 MD5 와 SHA-1 을 듭니다.
- SHA-1 은 FIPS 승인 알고리즘이고 MD5 는 아니어서, 연방 기관에는 SHA-1 을 쓰라고 했습니다.
- 각주에서는 연방 기관이 2010년까지 SHA-1 에서 SHA-224·SHA-256 같은 더 강한 SHA 로 옮겨야 한다고 적었습니다.
- 본문에는 두 알고리즘이 모두 128비트 다이제스트를 낸다고 적혀 있습니다. 이 문장은 틀렸습니다.
- SHA-1 다이제스트는 20바이트(160비트)입니다. EWF 의 digest 섹션도 SHA1 칸을 20바이트로 둡니다.

### NIST 해시 정책 (마지막 갱신 2024-09-09)

- SHA-2 계열은 보안 해시가 필요한 모든 용도에 쓸 수 있습니다.
- SHA-3 고정 길이 함수(SHA3-224·256·384·512)는 모든 용도에 승인됐습니다.
- 연방 기관은 디지털 서명, 타임스탬프, 충돌 저항이 필요한 용도에 SHA-1 을 그만 써야 합니다.
- SHA-1 은 옛 서명·타임스탬프 검증, HMAC, 키 유도 함수 (KDF), 난수 생성에는 계속 쓸 수 있습니다.
- 2030-12-31 이후에는 SHA-1 을 승인 알고리즘으로 둔 FIPS 140 검증 모듈이 이력 목록 (Historical List) 으로 옮겨 갑니다.
- 이 정책 페이지에는 MD5 가 나오지 않습니다.

### 어떻게 고르나

해시 비교는 "해시가 같으면 내용도 같다" 는 전제에 기대는데, 이 전제는 서로 다른 내용이 같은 해시를 내는 충돌 (Collision) 을 만들 수 없어야 성립합니다.
MD5 와 SHA1 은 더는 안전하지 않아서 단순한 변경 확인에만 씁니다. 공격이나 조작에서 보호해야 하는 파일에는 쓰지 않습니다.
그래서 누군가 증거를 조작했을 가능성까지 따져야 하면 SHA-2 계열이나 SHA-3 을 씁니다.
옛 기록과 맞춰 봐야 해서 MD5 나 SHA-1 을 계산할 때도 SHA-256 값을 함께 적어 둡니다.

해시셋으로 알려진 파일을 걸러 내는 일은 목적이 다릅니다. [해시셋 대조와 유사 해시](../../analysis/hash-set-fuzzy-hash.md) 에서 다룹니다.

## Windows 에서 계산하기

PowerShell 의 `Get-FileHash` 로 파일 해시를 계산합니다.

```powershell
Get-FileHash -Path <파일 경로> -Algorithm SHA256
```

`-Algorithm` 에는 SHA1, SHA256, SHA384, SHA512, MD5 를 줄 수 있고(PowerShell 7.6 기준), 주지 않으면 SHA256 으로 계산합니다.
결과 객체에는 Algorithm, Hash, Path 속성이 있습니다.
`-InputStream` 을 쓰면 파일이 아닌 스트림의 해시도 계산할 수 있습니다.
결과를 기록할 때는 알고리즘 이름과 경로를 해시 값과 함께 적습니다.

## E01 안에 적힌 해시

E01 세그먼트 파일은 청크 데이터와 머리 정보를 함께 담은 그릇입니다.
청크는 zlib 으로 압축할 수 있습니다.
그래서 세그먼트 파일 자체의 해시는 원본 매체의 해시와 다릅니다.
원본과 비교할 값은 이미지 안의 매체 데이터로 계산한 해시입니다.

EWF 는 이미지 전체의 해시를 hash 섹션과 digest 섹션에 적습니다.
형식 전체는 [증거 이미지·가상 디스크 형식](../../../01-foundations/disk-volume/e01-raw-aff4-vhdx-vmdk.md) 에서 다룹니다.

**hash 섹션 (36바이트)**

| 오프셋 | 크기 | 내용 |
|---|---|---|
| 0 | 16 | MD5 |
| 16 | 16 | 알려지지 않은 값 |
| 32 | 4 | Adler-32 |

**digest 섹션 (80바이트, EnCase 6.12 부터)**

| 오프셋 | 크기 | 내용 |
|---|---|---|
| 0 | 16 | MD5 |
| 16 | 20 | SHA1 |
| 36 | 40 | 채움 |
| 76 | 4 | Adler-32 |

압축하지 않은 청크에는 데이터 뒤에 4바이트 Adler-32 체크섬이 붙는데, 이 값은 청크가 손상됐는지 확인하는 값입니다.
청크 체크섬은 이미지 전체 해시와 다르므로 청크 체크섬이 모두 맞아도 이미지 전체 해시를 대신하지 못합니다.
도구가 "검증 성공" 이라고 보여 주면 이미지에 적힌 해시와 다시 계산한 해시를 비교한 것인지 확인하고, 그 값을 획득 때 원본 매체에서 따로 기록한 해시와도 맞춰 봅니다.

## 해시가 달라지는 경우

| 경우 | 까닭 | 기록할 것 |
|---|---|---|
| 켜진 시스템에서 한 백업 | 백업을 시작한 때와 검증한 때 사이에 일부 파일이 바뀔 수 있습니다 | 시작·검증 시각 |
| 희소 스트림 추출 (예: `$UsnJrnl:$J`) | 구멍을 0 으로 채워 뽑으면 논리 크기가 됩니다. 구멍을 건너뛰면 실제 데이터만 남습니다 | 추출 방식, 뽑은 크기 |
| 희소 속성이 있는 일반 파일 | 구멍을 건너뛰고 뽑으면 내용이 앞으로 밀립니다 | 추출 방식 |
| E01 세그먼트 파일끼리 비교 | 그릇 파일과 매체 데이터는 다른 바이트열입니다 | 무엇의 해시인지 |

- 희소 (Sparse) 스트림은 비어 있는 구간(구멍)을 디스크에 실제로 두지 않는 스트림입니다. NTFS 의 희소 속성은 [NTFS 구조](../../../01-foundations/disk-volume/ntfs/index.md) 에서 다룹니다.
- `$UsnJrnl:$J` 는 앞부분이 비어 있는 희소 스트림이고, 두 방식으로 뽑은 결과는 크기도 해시도 다릅니다(현장 관찰).
- 두 방식 모두 틀린 방법은 아니며, 어떻게 뽑았는지 기록해야 다른 분석가가 같은 해시를 다시 얻습니다.
- `$UsnJrnl:$J` 자체는 [USN 변경 저널](../../../02-artifacts/filesystem/usnjrnl.md) 에서 다룹니다.
- 켜진 시스템의 물리 장치 전체 이미지는 애초에 검증할 수 없습니다. 이 내용은 [디스크 이미징](disk-imaging.md) 의 "켜진 시스템에서" 절에 있습니다.
- 읽기 오류가 난 구간은 [디스크 이미징](disk-imaging.md) 의 error2 설명을 함께 봅니다.

## 함정과 한계

- **이미징 뒤에 원본 해시를 다시 계산하지 않습니다.** 이미징이 원본을 바꾸지 않았다는 근거가 사라집니다.
- **다이제스트를 증거와 같은 쓰기 가능한 곳에만 둡니다.** 읽기 전용이나 한 번 쓰기 매체, 또는 인쇄물로 따로 보관합니다.
- **MD5 나 SHA-1 하나만 적습니다.** 조작 가능성을 따져야 하는 사건에서 근거가 약해집니다.
- **SP 800-86 의 "둘 다 128비트" 문장을 그대로 옮깁니다.** SHA-1 은 160비트입니다.
- **추출 방식을 적지 않습니다.** 희소 스트림은 뽑는 방식에 따라 해시가 달라집니다.
- **세그먼트 파일 해시를 원본 매체 해시와 비교합니다.** 비교할 대상이 다릅니다.

## 결과를 어떻게 해석하나

- **말해 주는 것**: 두 해시가 같으면 사본이 해시를 계산한 시점의 원본과 같은 내용이라는 것.
- **말해 주는 것**: 이미징 전후 원본 해시가 같으면 이미징이 원본을 바꾸지 않았다는 것.
- **말해 주지 못하는 것**: 첫 해시를 계산하기 전에 원본이 어떻게 바뀌었는지.
- **말해 주지 못하는 것**: 데이터가 사건과 관련 있는지, 누가 만들었는지.

보고서에는 무엇의 해시를 어떤 알고리즘으로 언제 계산했는지 씁니다.

> 원본 매체 해시(`<알고리즘>`)를 이미징 전 `<시각>` 과 이미징 후 `<시각>` 에 계산했고 두 값이 같았다. 사본 이미지 안의 매체 데이터로 계산한 해시도 같은 값이었다. 해시 값은 `<보관 위치>` 에 따로 보관했다.
