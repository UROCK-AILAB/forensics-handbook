# 쓰기 방지 (Write Blocker)

> 상위 허브: [증거 획득 (Evidence Acquisition)](index.md)

## 한 줄 요약

쓰기 방지 장치 (Write Blocker) 는 연결한 저장 매체에 컴퓨터가 쓰지 못하게 막는 하드웨어나 소프트웨어입니다.
원본 매체를 이미징할 때와 이미지를 분석할 때 증거가 바뀌지 않게 하려고 쓰며, 쓰기 방지를 걸었더라도 원본이 그대로인지는 해시로 따로 확인합니다.

## 언제 쓰나

원본 매체를 이미징 컴퓨터에 연결할 때 씁니다. 이미징 절차 전체는 [디스크 이미징](disk-imaging.md) 에 있습니다.
분석 단계에서도 써서, 매체에 복원한 이미지에 쓰기가 일어나지 않게 막습니다. 이미지 파일이든 복원한 이미지든 읽기 전용으로만 접근합니다.

## 종류

| | 하드웨어 쓰기 방지 | 소프트웨어 쓰기 방지 |
|---|---|---|
| 놓는 곳 | 컴퓨터와 저장 매체 사이에 물리적으로 연결합니다 | 분석용 시스템에 설치합니다 |
| 연결 순서 | 매체를 쓰기 방지 장치에, 쓰기 방지 장치를 컴퓨터에 연결합니다 | 소프트웨어를 먼저 올리고 매체를 연결합니다 |

소프트웨어 쓰기 방지는 운영체제마다 막는 방법이 다릅니다.

MS-DOS 용은 Interrupt 13 과 확장 Interrupt 13 의 디스크 쓰기를 가로채고, Windows 용은 장치로 가는 요청을 필터로 걸러 쓰기를 막습니다.
SP 800-86 이 나온 2006년에는 소프트웨어 쓰기 방지 도구가 MS-DOS 용과 Windows 용만 있었다고 적었습니다.

Mac OS X 나 Linux 같은 운영체제는 보조 장치를 마운트하지 않고 부팅하도록 설정할 수 있어서 소프트웨어 쓰기 방지가 필요 없을 수 있지만, SP 800-86 은 하드웨어 쓰기 방지 장치를 붙이면 무결성이 보장된다고 적었습니다.

## 절차

### 하드웨어 쓰기 방지

1. 저장 매체(또는 매체를 읽는 장치)를 쓰기 방지 장치에 바로 연결합니다.
2. 쓰기 방지 장치를 이미징 컴퓨터에 연결합니다.
3. 장치에 쓰기 방지를 켜고 끄는 기능이 있으면, 연결한 모든 장치에서 켜져 있는지 확인합니다.
4. 쓴 장치의 이름과 설정을 기록합니다.

### 소프트웨어 쓰기 방지

1. 매체를 연결하기 전에 쓰기 방지 소프트웨어를 먼저 올립니다.
2. 연결할 모든 장치에 쓰기 방지를 켭니다.
3. 매체를 연결합니다.
4. 쓴 소프트웨어의 이름, 버전, 설정을 기록합니다.

### 새 장치는 주기적으로 시험합니다

쓰기 방지 도구가 새 장치를 제대로 지원하는지 주기적으로 시험합니다. 새 장치는 예약된 기능을 써서 장치에 쓰는 명령을 만들 수 있기 때문입니다.
시험한 날짜와 결과를 남깁니다. 도구 검증 기록을 남기는 법은 [도구 결과 교차 검증](../../reporting/tool-validation.md) 에 있습니다.

## Windows 의 diskpart 읽기 전용 속성

Windows 의 diskpart 에는 디스크에 읽기 전용 속성을 설정하거나 해제하는 명령이 있습니다.

```
select disk <디스크 번호>
attributes disk set readonly
```

명령 형식은 `attributes disk [{set | clear}] [readonly] [noerr]` 이고, 쓰려면 먼저 `select disk` 로 디스크를 골라야 합니다.
`clear` 를 쓰면 속성을 해제하며, `noerr` 는 스크립트용이라 오류가 나도 diskpart 가 멈추지 않고 다음 명령을 처리합니다.

이 속성을 쓰기 방지 장치 대신 쓰려면 아래를 먼저 따져 봅니다.

Microsoft 문서(ms.date 2017-10-16)에는 이 속성이 파일 시스템 메타데이터를 포함한 모든 쓰기를 막는지 나오지 않고, 이 글의 참고 자료 가운데 이 속성을 포렌식 쓰기 방지로 검증한 공식 자료도 없습니다.
- `select disk` 로 고르려면 디스크가 이미 연결돼 있어야 합니다. 소프트웨어 쓰기 방지를 매체 연결 전에 먼저 올리라는 SP 800-86 의 순서와 맞지 않습니다.

그래서 이 속성만 믿지 않습니다.
연결 전후에 원본 해시를 비교해 매체가 그대로인지 확인합니다.
비교 절차는 [해시로 무결성 검증](hash-verification.md) 에 있습니다.

## 분석 단계에서

이미지에서 꺼낸 파일도 원본으로 여기고 사본에서 작업합니다.
파일을 여는 방식에 따라 파일 내용이 바뀔 수 있기 때문입니다.

비정상 종료 (Dirty Shutdown) 상태의 ESE 데이터베이스는 JET API 로 열려면 같은 폴더의 트랜잭션 로그로 먼저 복구해야 하고, 이 복구가 파일 내용을 바꿀 수 있습니다.
압수 이미지에서 꺼낸 ESE 데이터베이스는 대부분 비정상 종료 상태였습니다(현장 관찰).

ESE 파일을 로그와 함께 다루는 법은 [ESE 데이터베이스](../../../01-foundations/database-log-formats/extensible-storage-engine/index.md) 에 있습니다.

## 함정과 한계

- **쓰기 방지를 건 매체의 파일 시각을 화면에서 그대로 옮깁니다.** 쓰기 방지 장치는 매체의 MAC 시각이 바뀌는 것을 막지만 운영체제가 바뀐 시각을 메모리에 캐시하는 것은 막지 못해서, 운영체제는 매체에 적힌 실제 값 대신 캐시한 값을 보여 줄 수 있습니다.
- **일부 장치에만 쓰기 방지를 켭니다.** 쓰기 방지를 쓸 때는 연결한 모든 장치에 켭니다.
- **매체를 연결한 뒤에 소프트웨어를 올립니다.** 소프트웨어 쓰기 방지는 매체를 연결하기 전에 먼저 올립니다.
- **새 장치를 시험하지 않고 씁니다.** 새 장치는 예약된 기능으로 쓰기 명령을 만들 수 있습니다.
- **쓰기 방지를 썼으니 원본이 그대로라고 단정합니다.** 원본이 바뀌지 않았다는 근거는 이미징 전후의 해시 비교입니다.

## 결과를 어떻게 해석하나

- **말해 주는 것**: 쓰기 방지 기록은 원본에 쓰지 못하게 막는 조치를 했다는 사실을 보여 줍니다.
- **말해 주지 못하는 것**: 원본이 실제로 바뀌지 않았는지. 이것은 해시 비교로 보입니다.
- **말해 주지 못하는 것**: 연결 전에 원본에 일어난 일.

보고서에는 쓴 장치와 확인 결과를 함께 씁니다.

> 원본 매체를 하드웨어 쓰기 방지 장치(`<장치 이름>`)에 연결한 상태로 이미지를 만들었다. 이미징 전후에 계산한 원본 해시(`<알고리즘>`)가 같았다.
