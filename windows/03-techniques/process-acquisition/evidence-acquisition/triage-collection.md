# 선별 수집 (Triage Collection)

> 상위 허브: [증거 획득 (Evidence Acquisition)](index.md)

## 한 줄 요약

선별 수집은 디스크 전체 대신 미리 고른 파일과 데이터만 모으는 일이며, 데이터 출처가 너무 많거나 시스템을 멈출 수 없을 때 씁니다.
고른 것만 모으므로, 무엇을 왜 골랐는지와 어떻게 모았는지를 함께 기록합니다.

## 언제 쓰나

데이터 출처가 너무 많아서 모두 얻기 어려울 때가 있는데, 이때를 대비해 우선순위를 정하는 계획과 절차를 미리 만들어 둡니다.
중요한 서버를 멈추지 않고 사용자 한 명의 홈 폴더만 가져오는 것처럼, 필요한 파일만 켜진 시스템에서 복사할 수도 있습니다.
증거로 쓸 가능성이 크거나 지운 파일과 슬랙 공간까지 봐야 하면 [디스크 이미징](disk-imaging.md) 을 씁니다.

## 우선순위 정하기

우선순위를 정할 때는 세 가지를 따집니다.

| 요소 | 따질 것 |
|---|---|
| 예상 가치 (Likely Value) | 그 출처가 조사에 얼마나 쓸모 있을지 |
| 휘발성 (Volatility) | 전원이 꺼지거나 시간이 지나면 얼마나 빨리 사라지는지 |
| 드는 노력 (Amount of Effort Required) | 그 데이터를 얻는 데 얼마나 수고가 드는지 |

휘발성 데이터는 전원이 꺼지거나 시간이 지나면 사라지는 켜진 시스템의 데이터이고, 로그처럼 덮어쓰이는 비휘발성 데이터도 시간이 지나면 어느 정도 바뀝니다.
매체 종류 사이의 휘발성 순서는 [증거 획득](index.md) 허브에 있습니다.

### 휘발성 데이터를 모으는 순서

휘발성 데이터는 아래 순서로 모읍니다.

1. 네트워크 연결
2. 로그인 세션
3. 메모리 내용
4. 실행 중인 프로세스
5. 열린 파일
6. 네트워크 설정
7. 운영체제 시각

네트워크 연결을 먼저 모으는 것은 연결이 끊기거나 시간이 지나 사라지기 때문이고, 로그인 세션을 일찍 모으는 것은 접속한 사용자 목록이 바뀌기 때문입니다.
메모리를 뜨고 분석하는 법은 [메모리 분석](../../analysis/memory-forensics/index.md) 에 있고, 켜진 시스템에서 모으는 일 전반은 [라이브 응답](../live-response/index.md) 에서 다룹니다.

## 절차

선별 수집의 절차는 아래와 같습니다.

1. **증거가 있을 만한 곳을 적습니다.** 관련 시스템과 수집할 출처를 적습니다.
2. **무엇이 관련 있고 증거로 인정될지 정합니다.** 이 판단이 수집 목록이 됩니다.
3. **시스템마다 휘발성 순서를 정합니다.**
4. **외부에서 시스템을 바꿀 수 있는 경로를 끊습니다.**
5. **수집 프로그램을 보호된 매체에서 돌립니다.** 시스템에 있는 프로그램은 믿지 않습니다.
6. **휘발성 순서에 따라 알맞은 도구로 모읍니다.** 일관성을 위해 툴킷 CD 의 자동 스크립트로 모을 수도 있습니다.
7. **시스템 시계가 얼마나 어긋났는지 기록합니다.**
8. **그 밖에 증거가 될 만한 것이 없는지 다시 따져 봅니다.**
9. **단계마다 기록합니다.** 현장에 누가 있었고 무엇을 했는지도 적습니다. 기록 항목은 [증거 보관 연속성](chain-of-custody.md) 에 있습니다.
10. **모은 파일마다 해시를 계산합니다.** 절차는 [해시로 무결성 검증](hash-verification.md) 에 있습니다.

## 무엇을 모을지 고를 때

모을 파일은 조사 질문에서 거꾸로 고릅니다.
아래 표는 질문마다 먼저 볼 아티팩트 페이지이며, 파일 위치는 각 페이지에서 확인합니다.

| 알고 싶은 것 | 볼 페이지 |
|---|---|
| 어떤 프로그램을 실행했나 | [프리페치](../../../02-artifacts/execution/prefetch/index.md), [AmCache](../../../02-artifacts/execution/amcache-hve/index.md), [SRUM](../../../02-artifacts/execution/system-resource-usage-monitor/index.md) |
| 어떤 파일과 폴더를 열었나 | [바로가기 파일](../../../02-artifacts/file-folder-usage/lnk.md), [점프리스트](../../../02-artifacts/file-folder-usage/jump-lists.md), [셸백](../../../02-artifacts/file-folder-usage/shellbags/index.md) |
| 파일 시스템이 어떻게 바뀌었나 | [마스터 파일 테이블](../../../02-artifacts/filesystem/mft.md), [USN 변경 저널](../../../02-artifacts/filesystem/usnjrnl.md) |
| 누가 언제 로그온했나 | [로그온·로그오프](../../../02-artifacts/event-logs/logon-events/index.md) |
| 웹에서 무엇을 했나 | [크롬 계열 브라우저](../../../02-artifacts/browsers/chrome-edge-whale/index.md) |
| 어떤 USB 를 꽂았나 | [USB 저장장치 흔적](../../../02-artifacts/external-devices/usb-storage-artifacts/index.md) |

주 파일 곁에 트랜잭션 로그를 두는 형식은 로그도 함께 모읍니다.

ESE 데이터베이스를 JET API 로 열려면 같은 폴더의 트랜잭션 로그로 먼저 복구해야 하므로(현장 관찰), 로그를 빼고 데이터베이스 파일만 가져오면 이 복구를 할 수 없습니다.
로그를 함께 모아도 오래된 로그가 지워져 사슬이 끊겨 있으면 복구가 안 될 수 있습니다(현장 관찰).
ESE 는 [ESE 데이터베이스](../../../01-foundations/database-log-formats/extensible-storage-engine/index.md), 레지스트리는 [레지스트리 하이브 구조](../../../01-foundations/database-log-formats/registry-hive/index.md) 에서 함께 모을 파일을 확인합니다.

## 도구

아래는 공개 도구를 예로 든 것이며, 어떤 도구를 쓰든 같은 점을 확인합니다.

### 예: Velociraptor 오프라인 수집기

오프라인 수집기는 설정과 고른 아티팩트를 넣어 만든 Velociraptor 실행 파일로, 서버에 연결하지 않고 끝점에서 미리 정한 수집을 돌립니다.
결과는 정해진 구조로 정리한 zip 보관 파일로 나오며, 보통 암호화하거나 암호를 걸지만 반드시 그래야 하는 것은 아닙니다.
KAPE 대상 목록을 옮긴 `Windows.KapeFiles.Targets` 아티팩트를 쓸 수 있습니다.

결과 파일을 보호하는 방식은 세 가지입니다.

| 방식 | 하는 일 |
|---|---|
| 고정 암호 | 미리 정한 암호를 겁니다 |
| X.509 (권장) | 임의 암호를 만들고, 그 암호를 서버 인증서로 암호화합니다 |
| PGP | 임의 암호를 만들고, 그 암호를 PGP 공개 키로 암호화합니다 |

zip 하나에 암호만 걸면 파일 이름과 크기 같은 메타데이터가 그대로 보여서, 안쪽 zip 을 바깥 컨테이너로 한 번 더 감싸서 암호화합니다.

### 도구마다 따로 확인할 것

어떤 도구를 쓰든 아래 점은 그 도구에서 직접 확인하고 기록합니다.

- 쓰는 중이라 잠긴 파일을 원시 NTFS 로 읽는지
- 모은 파일마다 해시를 기록하는지
- 관리자 권한이 필요한지

두 도구의 결과를 맞춰 보는 법은 [도구 결과 교차 검증](../../reporting/tool-validation.md) 에 있습니다.

## 함정과 한계

- **복사하는 동안 파일이 바뀝니다.** 켜진 시스템에서 복사하면 복사 중에 파일이 바뀔 수 있습니다.
- **열린 파일을 놓칩니다.** 프로세스가 열어 둔 파일은 복사하기 쉽지 않습니다.
- **시스템에 부담을 줍니다.** 켜진 시스템에서 모으면 시스템 성능과 네트워크 대역폭에 영향을 줄 수 있습니다.
- **루트킷이 거짓 정보를 돌려줍니다.** 켜진 시스템에서 수집하면 이런 위험이 있습니다.
- **복사한 파일의 시각을 원래 시각으로 씁니다.** 복사하면 파일 생성 시각이 바뀔 수 있어서 원래 시각을 수집할 때 따로 기록해 두어야 합니다.
- **접근 시각을 바꾸는 프로그램으로 모읍니다.** 모든 파일의 접근 시각을 바꾸는 프로그램(예: tar, xcopy)은 돌리지 않습니다.
- **선별 수집물에서 지운 파일을 찾습니다.** 파일 단위로 복사한 결과에는 지운 파일과 슬랙 공간의 잔여 데이터가 들어가지 않습니다.

## 결과를 어떻게 해석하나

- **알 수 있는 것**: 수집한 시점에 그 파일이 그 경로에 그 내용으로 있었다는 것.
- **알 수 없는 것**: 수집 목록에 없던 곳의 상태. 모으지 않은 곳에 흔적이 없었다고 말할 수 없습니다.
- **알 수 없는 것**: 복사하면서 바뀌었을 수 있는 파일 시각. 원래 시각은 따로 기록한 값으로 확인합니다.
- **알 수 없는 것**: 루트킷이 숨긴 것. 가능하면 디스크 이미지나 메모리와 맞춰 봅니다.

보고서에는 수집 범위를 먼저 밝힙니다.

> `<날짜 시각, 시간대>` 에 켜져 있던 시스템에서 미리 정한 목록(`<목록 이름·버전>`)의 파일만 복사했다. 목록에 없는 위치는 살피지 않았다. 모은 파일마다 해시(`<알고리즘>`)를 계산해 기록했다.
