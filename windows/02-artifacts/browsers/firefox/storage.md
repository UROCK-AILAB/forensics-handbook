# 웹 저장소 (storage 폴더)

웹 저장소 (Web Storage) 는 웹사이트가 브라우저 안에 데이터를 넣어 두는 자리입니다. 파이어폭스는 이 데이터를 프로필 안의 `storage` 폴더에 두는 것으로 알려져 있습니다. 이 폴더의 정확한 위치와 구조는 실제 데이터로 확인합니다. 이 페이지는 알려진 사실과 실제 데이터로 구조를 확인하는 절차를 적습니다.

## 무엇을 기록하나 · 왜 생기나

웹사이트는 쿠키 말고도 브라우저에 데이터를 넣어 둘 수 있고, 웹 표준이 정한 저장 방식이 몇 가지 있습니다.

- 로컬 저장소 (Local Storage) 에는 사이트가 이름과 값을 쌍으로 넣어 둡니다.
- IndexedDB 에는 사이트가 더 크고 복잡한 데이터를 넣어 둡니다.
- 캐시 API (Cache API) 로는 사이트의 스크립트가 서버 응답을 통째로 저장해 둡니다.

브라우저는 이 데이터를 사이트의 출처 (origin) 마다 나눠 두어서, 한 사이트가 넣은 값을 다른 사이트는 읽지 못합니다. 웹메일·웹 메신저·문서 편집 서비스는 이 자리에 설정, 임시 저장본, 오프라인용 데이터를 넣기도 합니다. 이 데이터가 파이어폭스 프로필 안에서 어떤 파일로 남는지는 아래 "구조" 에서 다룹니다.

## 위치와 버전별 차이

- 파이어폭스 프로필은 본 폴더와 로컬 폴더로 나뉩니다. 두 폴더의 위치는 [프로필 구조 (profiles.ini·prefs.js)](profiles-ini-prefs-js.md) 에서 다룹니다.
- `storage` 폴더가 두 폴더 중 어디에 있는지는 실제 데이터로 확인해야 하므로, 두 폴더를 모두 살펴봅니다.
- 파이어폭스 판에 따라 웹 저장소를 담는 방식이 달라졌을 수 있습니다. 오래된 데이터와 최근 데이터의 폴더 모양이 다르면 판 차이를 먼저 의심합니다.

## 구조

### 실제 데이터로 확인할 것

아래 항목은 파이어폭스 소스나 실제 데이터로 확인해야 합니다.

- `storage` 폴더 아래의 층 구성입니다. 사이트별 폴더가 있는지, 그 아래가 저장 방식별로 나뉘는지 봅니다.
- `storage` 폴더 바로 아래 있는 파일과 폴더의 역할입니다.
- 로컬 저장소·IndexedDB·캐시 API 의 데이터가 각각 어떤 이름의 파일에 담기는지입니다.
- 사이트 주소를 폴더 이름으로 바꿀 때 특수 문자를 어떻게 바꾸는지입니다.
- 값을 압축해서 저장하는지입니다.
- 예전 판의 로컬 저장소 파일이 무엇이었고, 몇 번 판에서 지금 방식으로 바뀌었는지입니다.
- [쿠키 (cookies.sqlite)](cookies-sqlite.md) 의 `originAttributes` 처럼 컨테이너·분할 정보가 폴더나 파일 이름에 붙는지입니다.

### 알려진 것

- 파이어폭스의 저장 공간 관리 코드(quota manager)는 `.metadata`, `.metadata-v2` 라는 파일에 출처 (origin) 의 마지막 접근 시각을 적습니다[2].
- 이 파일이 폴더 안 어디에 놓이는지, 시각을 어떤 단위와 바이트 배치로 적는지는 실제 데이터로 확인합니다.

구조를 모르는 채로 도구 결과만 옮겨 적지 않습니다. 아래 "직접 분석해 보기" 의 순서로 실제 데이터에서 먼저 확인합니다.

## 증거로서 의미

### 증명하는 것

- 한 사이트의 저장소 데이터가 있으면, 그 사이트의 페이지가 이 프로필의 브라우저에서 데이터를 저장한 적이 있습니다.
- 저장된 값 자체가 증거가 될 수 있습니다. 사이트가 넣어 둔 계정 식별자, 설정, 임시 저장본이 남기도 합니다.

### 증명하지 못하는 것

- 사용자가 그 사이트를 주소창에 직접 열었다는 것은 증명하지 못합니다. 페이지 안에 끼워 넣은 다른 사이트의 내용도 저장소를 쓸 수 있습니다.
- 값 하나를 언제 넣었는지는 단정하지 못합니다. `.metadata` 파일의 마지막 접근 시각도 출처 단위이므로 값 하나를 넣은 시각이 아닙니다.
- 값의 뜻은 그 사이트가 정합니다. 이름만 보고 뜻을 단정하지 않습니다.
- 키보드 앞의 사람이 누구인지는 알 수 없습니다.
- 데이터가 없다고 방문하지 않은 것은 아닙니다. 사이트가 저장소를 쓰지 않았거나, 사용자가 사이트 데이터를 지웠을 수 있습니다.

보고서에는 "그 서비스를 썼다" 대신 "이 프로필의 `storage` 폴더 아래에 그 사이트 이름이 든 폴더가 있고, 그 안 파일에 이 값이 있다. 파일의 마지막 수정 시각은 X(UTC) 이다" 처럼 씁니다.

## 시각 해석

- 저장소 파일 안에 시각 필드가 있는지, 있다면 단위가 무엇인지는 실제 데이터로 확인합니다.
- `.metadata`·`.metadata-v2` 파일에는 출처의 마지막 접근 시각이 들어 있습니다. 값을 풀었다면 단위를 단정하지 말고 방문 기록의 시각과 맞춰 본 뒤에 씁니다.
- 폴더와 파일의 생성·수정 시각은 [$MFT](../../filesystem/mft.md) 에서 봅니다.
- 사이트 폴더가 생긴 시각은 그 사이트가 처음 데이터를 넣은 때와 가까울 수 있으므로, 방문 기록의 시각과 맞춰 본 뒤에 씁니다.
- 파일을 만들고 고친 차례는 [$UsnJrnl](../../filesystem/usnjrnl.md) 에서 봅니다.
- 여러 시각을 한 시간 축에 놓을 때는 [타임라인 작성](../../../03-techniques/analysis/timeline/index.md) 을 따릅니다.

## 함정과 한계

- **원본 프로필로 브라우저를 켜지 않습니다.** 브라우저를 켜고 사이트가 다시 열리면 저장소 파일이 바뀔 수 있으므로 해시를 기록한 사본으로 분석합니다.
- **구조를 단정하지 않습니다.** 공개 도구가 보여 주는 표 이름과 열 이름을 원본 파일과 맞춰 봅니다.
- **두 폴더를 모두 봅니다.** `storage` 폴더의 위치는 분석 대상마다 확인해야 하므로 본 폴더와 로컬 폴더를 함께 살펴봅니다.
- **SQLite 파일이면 `-wal` 파일도 뜹니다.** 최근 변경이 본 파일에 아직 합쳐지지 않았을 수 있습니다. [SQLite 데이터베이스](../../../01-foundations/database-log-formats/sqlite/index.md) 를 참고합니다.
- **읽히지 않는 값은 따로 표시합니다.** 사람이 읽을 수 없는 바이트 덩어리는 압축·직렬화한 값일 수 있습니다. 푸는 법을 확인하기 전에는 키워드 검색에 걸리지 않을 수 있습니다. [파일 내용 검색](../../../03-techniques/analysis/content-search/index.md) 을 참고합니다.
- **크롬 계열의 읽는 법을 그대로 쓰지 않습니다.** 파이어폭스와 크롬 계열은 웹 저장소를 담는 방식이 다릅니다. [크롬 계열 브라우저](../chrome-edge-whale/index.md) 와 섞어 읽지 않습니다.
- **지운 사이트 데이터는 따로 찾습니다.** [삭제 데이터 복구](../../../03-techniques/analysis/data-recovery/index.md) 와 [섀도 복사본 활용](../../../03-techniques/analysis/volume-shadow-copy-analysis.md) 을 봅니다.

## 직접 분석해 보기

### 헥스로 한 번

실제 파일의 종류부터 판별합니다.

1. `storage` 폴더를 찾아 그 아래 모든 파일의 목록과 크기를 뽑습니다.
2. 각 파일을 헥스로 열어 머리 16바이트를 봅니다. SQLite 파일인지는 이 머리로 구분합니다. 머리 모양은 [SQLite 데이터베이스](../../../01-foundations/database-log-formats/sqlite/index.md) 에서 다룹니다.
3. SQLite 가 아닌 파일은 머리 바이트를 적어 두고 종류를 따로 확인합니다. 이름이 `.metadata`·`.metadata-v2` 인 파일은 출처의 마지막 접근 시각을 담은 파일입니다.

### 공개 도구로 한 번

1. SQLite 파일은 같은 폴더의 `-wal` 파일과 함께 사본으로 뜹니다.
2. SQLite 명령줄 도구를 읽기 전용으로 열어 표 목록을 봅니다.

```sql
SELECT type, name, sql FROM sqlite_master;
```

3. 표 이름과 열 이름을 적어 둡니다. 값이 글자로 읽히는 열과 바이트 덩어리인 열을 나눕니다.
4. 폴더 이름에 사이트 주소가 드러나면, 방문 기록·쿠키의 도메인과 맞춰 봅니다.
5. 웹 저장소를 풀어 주는 공개 도구를 쓸 때는 그 결과를 위에서 직접 읽은 표와 맞춰 봅니다. [도구 결과 교차 검증](../../../03-techniques/reporting/tool-validation.md) 을 참고합니다.

## 실습

파이어폭스를 쓴 공개 시험 데이터(NIST CFReDS 등)에서 프로필 본 폴더와 로컬 폴더를 꺼내 아래 질문을 풀어 봅니다.

1. `storage` 폴더는 본 폴더와 로컬 폴더 중 어디에 있습니까?
2. `storage` 아래 폴더 이름에 사이트 주소가 드러납니까? 그 사이트들은 방문 기록에 있습니까?
3. SQLite 파일을 하나 골라 표 이름과 열 이름을 적습니다. 그 파일은 로컬 저장소와 IndexedDB 중 어느 쪽으로 보입니까? 무엇을 근거로 그렇게 봅니까?
4. 쿠키 DB 에는 없고 `storage` 에만 있는 사이트가 있습니까?
