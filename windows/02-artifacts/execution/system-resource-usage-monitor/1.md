# SRUM 해석 함정 (1시간 단위 기록·레지스트리 임시 저장)

## 한 줄 요약

SRUM 은 모은 값을 한 시간 안팎 쥐고 있다가 한꺼번에 DB 에 씁니다. 그래서 `TimeStamp` 는 활동한 시각이 아니라 DB 에 쓴 시각입니다. 수집 직전 한 시간 안팎의 활동은 SRUDB.dat 에 아직 없을 수 있습니다.

## 왜 이 주제를 따로 보나

SRUM (System Resource Usage Monitor) 의 표는 여러 개입니다. 표마다 무엇을 남기는지는 각 하위 페이지에서 다룹니다. 이 페이지는 어느 표를 읽든 똑같이 걸리는 함정만 다룹니다.

1. `TimeStamp` 를 활동 시각으로 읽는 경우
2. DB 에 아직 들어가지 않은 값을 놓치는 경우
3. 보존 기간이 지나 지운 행을 "없었다" 로 읽는 경우
4. 손상된 DB 를 한 가지 방식으로만 읽는 경우
5. 짧게 돈 프로세스와 VPN 통신을 잘못 읽는 경우

위치, 표 목록, 버전별 차이의 개요는 [SRUM 허브](index.md)에 있습니다. `AppId`·`UserId` 를 푸는 법은 [구조와 ID 매핑](srudbidmaptable.md)을 봅니다. ESE 형식 자체는 [ESE 데이터베이스](../../../01-foundations/database-log-formats/extensible-storage-engine/index.md)를 봅니다.

> 그림 자리: 가로축을 시간으로 두고, 60초마다 쌓이는 1단계 저장소(메모리)와 1시간마다 찍히는 `TimeStamp` 를 나란히 그린 그림. 한 행이 덮는 구간(앞 `TimeStamp` 다음부터 이번 `TimeStamp` 까지)과, 수집 시각 직전에 아직 DB 에 안 들어간 구간을 색으로 구분한다.

## 함정 1 — 1시간 단위 기록

### 어떻게 쌓이나

WithSecure 연구(2023)는 SRUM 이 값을 두 단계로 쌓는다고 설명합니다.

| 단계 | 저장 위치 | 갱신 주기 (기본값) |
|---|---|---|
| 1단계 저장소 (Tier1) | 메모리 | 60초 (`Tier1Period`) |
| 2단계 저장소 (Tier2) | 디스크의 SRUDB.dat | 1시간 (`Tier2Period`) |

1단계 저장소는 60초마다 갱신됩니다. SRUM 은 한 시간마다 그 내용을 SRUDB.dat 로 옮깁니다. 그래서 앱 사용량·네트워크 사용량 표의 한 행은 한 시간 안팎의 구간을 모은 값입니다. 1시간은 기본값입니다. 검체의 실제 간격은 `TimeStamp` 를 늘어놓고 직접 확인합니다.

### `TimeStamp` 는 DB 에 쓴 시각입니다

대부분의 표에 `TimeStamp` 열이 있습니다. Velociraptor 문서는 이 값이 ESE 레코드를 쓴 시각이라고 설명합니다. 실제 실행보다 한참 늦을 수 있다는 설명도 붙어 있습니다.

이 사실에서 아래 해석이 따라 나옵니다.

- 한 행의 활동은 `TimeStamp` 앞 구간 어딘가에서 있었습니다. 구간 안의 정확한 시각은 행에 없습니다.
- 한 번에 옮긴 행들은 `TimeStamp` 가 같습니다. 같은 `TimeStamp` 의 두 앱이 같은 순간에 돌았다는 뜻이 아닙니다.
- 한 행이 덮는 구간은 "같은 표에서 바로 앞 `TimeStamp` 다음부터 이번 `TimeStamp` 까지" 로 추정합니다. 이 추정은 동작 방식에서 끌어낸 것이고, 명세가 보장하지 않습니다.
- PC 가 꺼져 있던 동안에는 행이 생기지 않습니다. 그래서 전원을 켠 뒤 첫 행은 앞 행과 간격이 크게 벌어집니다. 이 첫 행이 꺼지기 전의 활동까지 담았는지는 알 수 없습니다. 꺼진 구간은 [켜짐·꺼짐 이벤트](../../event-logs/power-on-off-events.md)로 확인합니다.
- 1분 단위, 초 단위 순서가 필요하면 SRUM 으로 정하지 않습니다. 초 단위 기록은 아래 교차 검증 표의 아티팩트에서 찾습니다.

### 열마다 시각의 뜻이 다릅니다

`TimeStamp` 말고도 시각을 담는 열이 있습니다. 형식은 libyal 문서를 따릅니다.

| 열 | 있는 표 | 저장 형식 | 뜻 |
|---|---|---|---|
| `TimeStamp` | 대부분의 표 | OLE 자동화 날짜 (OLE Automation Date) | 행을 DB 에 쓴 시각 |
| `ConnectStartTime` | 네트워크 연결 `{DD6636C4-…}` | FILETIME | 연결을 시작한 시각. `TimeStamp` 보다 훨씬 이를 수 있습니다. [네트워크 연결 기록](network-connectivity.md) |
| `EndTime` | App Timeline `{5C8CF1C7-…}` | 64비트 정수 | Velociraptor 문서는 실행 시점을 `TimeStamp` 가 아니라 `EndTime` 과 `DurationMS` 로 정한다고 설명합니다. |
| `EventTimestamp` | 전원 사용 `{FEE4E14F-…}` | 64비트 정수 | [전원·배터리 사용](energy-usage.md)에서 다룹니다. |

한 행 안의 두 시각이 서로 다른 사건을 가리킬 수 있습니다. 타임라인에 올릴 때는 열 이름을 함께 적습니다.

### 시각의 기준

- OLE 자동화 날짜는 1899-12-30 0시부터 센 날 수를 8바이트 실수로 적은 값입니다. 변환은 [시각 값 형식](../../../01-foundations/value-decoding/filetime-unix-webkit-dos-ole.md)을 봅니다.
- libyal 문서는 `TimeStamp` 가 UTC 인지 현지 시각인지 밝히지 않습니다. SANS ISC 에 실린 공개 도구 설명은 이 값을 UTC 로 보여 줍니다. 쓰는 도구가 결과를 현지 시각으로 바꿔 보여 주는지 확인합니다.
- `TimeStamp` 는 DB 에 쓰던 때의 시스템 시계를 따릅니다. 시계를 되돌리면 `TimeStamp` 순서가 뒤집힌 구간이 생길 수 있습니다. 행을 저장 순서대로 읽으며 시각이 뒤로 가는 곳을 찾습니다. 시계 변경은 [시스템 시각을 바꿨나](../../../04-scenarios/activity/anti-forensics/system-time-change.md)와 [시간대·시계 오차 보정](../../../03-techniques/analysis/timeline/time-normalization.md)을 봅니다.

## 함정 2 — DB 에 아직 안 들어간 값

### 값이 머무는 곳은 버전마다 다릅니다

| 시기 | DB 에 쓰기 전 머무는 곳 | 근거 |
|---|---|---|
| 옛 버전 (Windows 8 무렵) | SOFTWARE 하이브 | Kashiwaba 정리 |
| 2019년 무렵의 Windows 10 | 레지스트리에 먼저 캐시한다는 설명 | Velociraptor (2019) |
| 최근 Windows 10·11 | 메모리의 1단계 저장소. 레지스트리에 임시 값을 두지 않습니다. | WithSecure (2023), Kashiwaba 정리 |

어느 빌드부터 레지스트리를 쓰지 않게 바뀌었는지는 확인하지 못했습니다. 그래서 검체마다 직접 확인합니다.

레지스트리 위치는 SOFTWARE 하이브의 `Microsoft\Windows NT\CurrentVersion\SRUM\Extensions` 입니다. 라이브 시스템에서는 `HKLM\SOFTWARE\` 아래에 있습니다. 이 키 아래에는 확장별 GUID 하위 키가 있습니다. Harrison (2019) 은 임시 값이 `RecordSets` 라는 하위 키에 있다고 적었습니다. 다만 그가 시험한 Windows Server 2019 에서는 `RecordSets` 하위 키가 비어 있었습니다. 최근 버전에서 이 키는 표 이름(GUID)이 어느 확장인지 알려 주는 용도로 남습니다.

### 무엇을 잃나

- 값이 메모리에만 있는 버전에서 전원을 바로 끊으면, 마지막으로 DB 에 쓴 뒤의 값은 사라집니다. 최대 한 시간 안팎의 활동이 SRUM 에 남지 않을 수 있습니다.
- 정상 종료나 재시작 때도 DB 에 쓴다는 분석 자료가 많습니다. 종료 때 반드시 쓴다는 공식 문서는 확인하지 못했습니다. 종료 직전 몇 분의 기록이 있다고 가정하지 않습니다.
- 켜져 있는 PC 에서 SRUDB.dat 를 복사하면, 복사한 뒤에 쓴 행은 사본에 없습니다. 이 경우 1단계 저장소의 값은 메모리 덤프에만 있습니다. 메모리에서 이 값을 되살리는 공개된 방법은 확인하지 못했습니다.

### 확인 순서

1. OS 버전과 빌드를 확인합니다. [시스템 기본 정보](../../system-account/os-version-computer-name-install-date-shutdown-t.md)를 봅니다.
2. SOFTWARE 하이브의 `SRUM\Extensions` 아래에 `RecordSets` 하위 키가 있는지 봅니다.
3. 있으면 그 안의 값도 읽습니다. 하이브 본체에 아직 반영하지 않은 변경은 [트랜잭션 로그 (.LOG1·.LOG2)](../../../01-foundations/database-log-formats/registry-hive/log1-log2.md)에 있을 수 있습니다. 하이브 파일만 보지 말고 로그를 함께 모읍니다.
4. 없으면 SRUDB.dat 의 마지막 `TimeStamp` 를 표마다 적습니다.
5. 수집 시각(또는 전원을 끊은 시각)을 적습니다. 4번과 5번 사이를 "SRUM 기록 공백" 으로 보고서에 밝힙니다.

## 함정 3 — 보존 기간과 "기록 없음"

보존 기간은 자료마다 다르게 적혀 있습니다. 숫자는 [SRUM 허브](index.md)의 표를 봅니다. 표마다 기간이 다릅니다. App Timeline 은 대개 7일로, 다른 표보다 훨씬 짧습니다(WithSecure). Velociraptor 문서는 실제 검체에서 60일 넘는 기록을 자주 본다고 적었습니다. 그래서 기간을 숫자로 가정하지 말고 검체에서 잽니다.

1. 표마다 가장 이른 `TimeStamp` 와 가장 늦은 `TimeStamp` 를 적습니다.
2. 가장 이른 시각보다 앞선 활동은 "SRUM 으로 판단할 수 없음" 으로 적습니다. "기록 없음" 으로 적지 않습니다.
3. 지운 행은 파일 안에 남아 있을 수 있습니다. [파일 안에 남은 지운 레코드](../../../01-foundations/database-log-formats/extensible-storage-engine/deleted-records.md)를 봅니다.
4. 옛 SRUDB.dat 는 섀도 복사본에 남아 있을 수 있습니다. [섀도 복사본 활용](../../../03-techniques/analysis/volume-shadow-copy-analysis.md)을 봅니다.

## 함정 4 — 손상된 DB 와 읽는 방식

압수 이미지에서 꺼낸 SRUDB.dat 는 대부분 비정상 종료 (dirty shutdown) 상태였습니다(현장 관찰). 손상된 파일은 읽는 방식에 따라 행 수가 달랐습니다(현장 관찰). 자세한 사례는 [SRUM 허브](index.md)의 수집 항목에 있습니다. 여기서는 읽는 순서만 정리합니다.

1. 원본은 열지 않습니다. 사본에서 작업합니다. JET API 로 열면 파일 내용이 바뀔 수 있습니다.
2. SRUDB.dat 와 같은 폴더의 트랜잭션 로그·체크포인트 파일을 함께 모읍니다.
3. 로그로 복구해 보고, 복구 전후 행 수를 적습니다. 이미지 안의 로그 사슬이 끊겨 복구가 안 되는 경우도 있었습니다(현장 관찰). 복구 원리는 [트랜잭션 로그와 비정상 종료 상태](../../../01-foundations/database-log-formats/extensible-storage-engine/edb-log-dirty-shutdown.md)를 봅니다.
4. 페이지를 직접 해석하는 방식으로도 읽습니다. 이 방식은 로그 없이 읽습니다. 구조는 [파일 구조 (Page·B+Tree·Catalog)](../../../01-foundations/database-log-formats/extensible-storage-engine/page-b-tree-catalog.md)를 봅니다.
5. 두 결과의 표별 행 수와 `TimeStamp` 범위를 비교합니다. 한쪽에만 있는 행은 따로 표시합니다. 방법은 [도구 결과 교차 검증](../../../03-techniques/reporting/tool-validation.md)을 봅니다.

## 함정 5 — 짧게 돈 프로세스와 VPN

- App Timeline 에는 1단계 저장소를 갱신하는 순간에 돌고 있던 프로세스만 들어갑니다(WithSecure). 갱신 주기는 기본 60초입니다. 1분 안에 시작해서 끝난 프로세스는 이 표에 없을 수 있습니다.
- VPN 을 거친 통신의 송수신 바이트는 모두 VPN 프로세스나 서비스 몫으로 잡힙니다(WithSecure). 앱별 송신량이 적다고 그 앱이 통신하지 않았다고 볼 수 없습니다. [네트워크 사용량](network-data-usage.md)과 [VPN 연결 기록](../../network/vpn-connections.md)을 봅니다.

## 증거로서 의미

**증명하는 것**

- 한 행이 있으면, 그 `TimeStamp` 앞 구간에 그 앱 ID 가 자원을 쓴 기록이 있습니다.
- `UserId` 가 붙은 행은 그 계정의 몫으로 잡힌 사용량입니다.
- 한 표의 `TimeStamp` 가 이어지는 구간에는 SRUM 이 돌고 있었습니다.

**증명하지 못하는 것**

- 구간 안의 정확한 활동 시각
- 사용자가 직접 실행했다는 것. 백그라운드로 돈 앱도 행이 생깁니다.
- 행이 없으니 실행하지 않았다는 것. 보존 기간, DB 에 아직 안 들어간 값, 짧은 실행, 손상된 페이지가 모두 행을 없앱니다.
- 송신 바이트로 어떤 파일을 보냈는지

## 끄기·지우기가 남기는 흔적

- 분석가 자료는 SRUM 이 진단 정책 서비스 (Diagnostic Policy Service) 안에서 돈다고 설명합니다. 이 서비스의 이름은 `DPS` 입니다. 오프라인 SYSTEM 하이브의 `ControlSet00X\Services\DPS` 에서 `Start` 값을 봅니다. 값이 4 이면 사용 안 함입니다. 서비스 키는 [서비스·드라이버](../../persistence/services-drivers.md), ControlSet 선택은 [컨트롤셋 고르기](../../../01-foundations/database-log-formats/registry-hive/controlset-select.md)를 봅니다.
- 서비스를 끄면 그 뒤로 행이 생기지 않는다고 봅니다. PC 는 켜져 있었는데(이벤트 로그의 켜짐 기록, 다른 실행 흔적) `TimeStamp` 가 끊긴 구간은 수집이 멈춘 구간일 수 있습니다. 서비스 키의 [마지막 기록 시각](../../../01-foundations/database-log-formats/registry-hive/last-write-time.md)을 그 구간과 비교합니다.
- SRUDB.dat 를 지우거나 새 파일로 바꾸면 [$MFT](../../filesystem/mft.md)와 [$UsnJrnl](../../filesystem/usnjrnl.md)에 흔적이 남을 수 있습니다. 새로 만든 DB 는 가장 이른 `TimeStamp` 가 교체 시점 근처입니다. 보존 기간보다 훨씬 짧은 기록만 있으면 교체를 의심합니다.
- 전체 흐름은 [보안 프로그램을 끄거나 지웠나](../../../04-scenarios/activity/anti-forensics/defense-evasion.md)와 [증거를 없애려 했나](../../../04-scenarios/activity/anti-forensics/index.md)를 봅니다.

## 직접 분석해 보기

### 헥스로 한 번

아래 바이트는 명세로 만든 예시입니다. 특정 검체에서 나온 값이 아닙니다.

`TimeStamp` 는 8바이트 리틀 엔디언 실수(double)입니다.

```
55 55 55 55 91 1D E6 40
```

1. 바이트를 뒤집으면 `0x40E61D9155555555` 입니다.
2. 실수로 읽으면 45292.541666… 입니다.
3. 1899-12-30 0시에 45,292일을 더하면 2024-01-01 입니다.
4. 0.541666… 일은 13시간입니다. 결과는 2024-01-01 13:00:00 입니다.

같은 표에서 바로 앞 `TimeStamp` 가 12:00:00 이면, 이 행은 12:00 다음부터 13:00 까지의 사용량으로 추정합니다.

네트워크 연결 표의 `ConnectStartTime` 은 FILETIME 입니다.

```
00 46 B6 6B AC 3C DA 01
```

1. 바이트를 뒤집으면 `0x01DA3CAC6BB64600` 입니다.
2. 10진으로 133,485,850,200,000,000 입니다. 1601-01-01 부터 센 100나노초 단위 수입니다.
3. 변환하면 2024-01-01 12:17:00 입니다.

이 연결은 12:17 에 시작했고, 13:00 에 DB 에 기록됐습니다. 두 시각 가운데 연결 시작을 뜻하는 쪽은 `ConnectStartTime` 입니다. 이 행을 쓸 때 연결이 이어지고 있었는지는 [네트워크 연결 기록](network-connectivity.md)의 방법으로 가립니다.

### 공개 도구로 한 번

공개 도구 가운데 libesedb 의 esedbexport, srum-dump, SrumECmd, Velociraptor, Chainsaw 가 SRUDB.dat 를 읽습니다. 도구 하나의 결과만 믿지 않습니다.

1. 사본에서 두 가지 이상 방식으로 엽니다. 표별 행 수를 비교합니다.
2. 표마다 서로 다른 `TimeStamp` 값을 뽑아 순서대로 늘어놓습니다. 간격이 1시간에서 크게 벗어나는 곳과 시각이 뒤로 가는 곳을 표시합니다.
3. 도구가 보여 주는 시각이 UTC 인지 현지 시각인지 확인합니다.
4. SOFTWARE 하이브의 `SRUM\Extensions` 아래를 레지스트리 뷰어로 열어 `RecordSets` 가 있는지 봅니다.

## 보고서 문장 예

- 쓰지 말 것: "A.exe 는 (시각)에 실행됐다."
- 쓸 것: "SRUM 앱 사용량 표에 A.exe 의 행이 있다. 이 행의 `TimeStamp` 는 (시각, UTC)이고, 같은 표의 바로 앞 기록 시각은 (시각, UTC)이다. 이 구간 안에 A.exe 가 자원을 쓴 기록이 있다."
- 쓰지 말 것: "수집 당일 A.exe 는 네트워크를 쓰지 않았다."
- 쓸 것: "SRUDB.dat 의 네트워크 사용량 표에서 마지막 `TimeStamp` 는 (시각, UTC)이다. 이 시각부터 수집 시각 (시각, UTC)까지의 사용량은 DB 에 아직 기록되지 않았을 수 있다."
- 쓰지 말 것: "(날짜) 이전에는 A.exe 를 쓴 적이 없다."
- 쓸 것: "SRUM 앱 사용량 표의 가장 이른 기록은 (시각, UTC)이다. 그 이전 사용 여부는 SRUM 으로 판단할 수 없다."

## 실습

NIST CFReDS 같은 공개 검체에서 Windows 10 이나 11 이미지를 하나 골라 아래 질문을 풀어 봅니다.

1. 앱 사용량 표의 `TimeStamp` 값은 몇 가지입니까? 이웃한 값 사이의 간격은 대개 얼마입니까?
2. 간격이 크게 벌어진 곳이 있습니까? 그 구간에 켜짐·꺼짐 이벤트가 있습니까?
3. SOFTWARE 하이브의 `SRUM\Extensions` 아래에 `RecordSets` 하위 키가 있습니까? 이 결과는 OS 빌드와 맞습니까?
4. 표마다 가장 이른 `TimeStamp` 는 언제입니까? App Timeline 표와 다른 표의 기간은 얼마나 다릅니까?
5. 네트워크 연결 표에서 `ConnectStartTime` 과 `TimeStamp` 가 가장 많이 떨어진 행은 어느 것입니까?
6. SRUDB.dat 를 두 가지 방식으로 열었을 때 표별 행 수가 같습니까?
