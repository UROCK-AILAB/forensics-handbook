# 참조 파일·폴더 목록 활용 (Referenced Files)

프리페치 파일에는 프로그램이 시작 직후 읽은 파일과 폴더의 전체 경로가 남습니다. 그 경로가 있던 볼륨의 일련번호도 함께 남습니다. 이 목록으로 실제 실행 위치, 제자리가 아닌 DLL, 시작하면서 읽은 문서, 연결되어 있던 외부 저장장치를 찾을 수 있습니다.

## 무엇을 기록하나 · 왜 생기나

프리페처 (Prefetcher) 는 프로그램이 시작할 때 읽는 코드와 데이터를 시작 뒤 최대 10초 동안 지켜보고, 시작이 먼저 끝났다고 판단하면 더 일찍 멈춥니다. 다음 실행 때 Windows 는 이 기록을 보고 필요한 데이터를 한꺼번에 미리 읽습니다. 그래서 .pf 파일 안에는 "시작할 때 읽은 파일" 과 "그 파일들이 있던 폴더" 가 들어갑니다.

.pf 파일에는 한 번의 실행이 아니라 지난 실행들에서 시작할 때 읽은 페이지가 담깁니다.

.pf 파일 안에서 이 페이지가 다루는 부분은 셋입니다.

| 부분 | 명세상 이름 | 담긴 것 |
|---|---|---|
| 파일 목록 | 파일 메트릭 배열 (File Metrics Array) 과 파일 이름 문자열 (Filename Strings) | 시작할 때 읽은 파일의 전체 경로. 실행 파일 자신, DLL, 설정·데이터 파일이 섞여 있습니다. |
| 볼륨 정보 | 볼륨 정보 항목 (Volume Information Entry) | 볼륨 장치 경로, 볼륨 생성 시각, 볼륨 일련번호 |
| 폴더 목록 | 디렉터리 문자열 (Directory Strings) | 볼륨마다 시작할 때 건드린 폴더 경로 |

실행 횟수와 실행 시각은 [실행 횟수와 실행 시각 읽기](run-count-last-run-times.md) 에서 다룹니다.

## 위치와 버전별 차이

.pf 파일은 `C:\Windows\Prefetch\` 에 있습니다. 형식 버전과 압축은 [파일 구조와 버전](format-versions-mam.md) 에서 다룹니다. 아래 표는 참조 목록과 관련 있는 차이만 모았습니다.

| 형식 버전 | Windows | 파일 목록 항목 크기 | 항목의 NTFS 파일 참조 필드 | 경로 앞부분 표기 |
|---|---|---|---|---|
| 17 | XP·2003 | 20바이트 | 없음 | `\DEVICE\HARDDISKVOLUMEn` 등 |
| 23 | Vista·7 | 32바이트 | 있음 (안 채우면 0) | `\DEVICE\HARDDISKVOLUMEn` 등 |
| 26 | 8.0·8.1 | 32바이트 | 23과 같은 자리 | 실제 .pf 파일의 경로 문자열로 확인 |
| 30 | 10 | 32바이트 | 23과 같은 자리 | `\VOLUME{…}` |
| 31 | 11 | 32바이트 | 23과 같은 자리 | `\VOLUME{…}` |

- Windows 10 부터는 .pf 파일 전체가 압축되어 있습니다. 압축을 풀기 전에는 원시 파일에서 경로 문자열을 검색할 수 없습니다.
- 볼륨 정보 안에는 파일 참조 목록이 따로 있습니다. Windows 8 부터 이 목록의 순번이 채워지지 않습니다. 최근 Windows 10 에서는 목록 자체가 채워지지 않습니다.

## 구조

전체 형식은 [파일 구조와 버전](format-versions-mam.md) 에 있습니다. 여기서는 참조 목록을 따라가는 데 필요한 필드만 적습니다. 값은 모두 리틀 엔디언입니다.

**파일 정보 (File Information)** 는 파일 처음에서 84바이트(0x54) 뒤에 있습니다. 아래 위치는 파일 정보 시작 기준입니다. 필드에 담긴 오프셋 값은 파일 처음 기준입니다.

| 위치 | 크기 | 뜻 |
|---|---|---|
| +0 | 4 | 파일 메트릭 배열 오프셋 |
| +4 | 4 | 파일 메트릭 항목 수 |
| +16 | 4 | 파일 이름 문자열 오프셋 |
| +20 | 4 | 파일 이름 문자열 전체 크기 |
| +24 | 4 | 볼륨 정보 오프셋 |
| +28 | 4 | 볼륨 수 |
| +32 | 4 | 볼륨 정보 전체 크기 |

**파일 메트릭 항목** (버전 23~31, 32바이트)

| 위치 | 크기 | 뜻 |
|---|---|---|
| +0 | 4 | 트레이스 체인 (Trace Chain) 시작 번호 |
| +4 | 4 | 트레이스 항목 수 |
| +8 | 4 | 미리 읽을 블록 수 |
| +12 | 4 | 파일 이름 오프셋 (파일 이름 문자열 시작 기준, 바이트) |
| +16 | 4 | 파일 이름 글자 수 (끝 NUL 제외) |
| +20 | 4 | 플래그 |
| +24 | 8 | NTFS 파일 참조 (MFT 번호 6바이트 + 순번 2바이트). 안 채우면 0 |

버전 17 항목은 20바이트입니다. 파일 이름 오프셋이 +8, 글자 수가 +12, 플래그가 +16 에 있고 파일 참조 필드는 없습니다.

플래그 값의 뜻은 아래와 같습니다.

| 값 | 뜻 |
|---|---|
| 0x00000001 | 미리 읽지 않음 |
| 0x00000002 | 리소스로 올림 |
| 0x00000200 | 실행 코드로 올림 |

**파일 이름 문자열** 은 UTF-16LE 전체 경로가 NUL 로 끝나며 이어 붙어 있습니다.

**볼륨 정보 항목** 은 버전 17에서 40바이트, 23·26에서 104바이트, 30·31에서 96바이트입니다. 앞 36바이트는 모든 버전이 같습니다.

| 위치 | 크기 | 뜻 |
|---|---|---|
| +0 | 4 | 장치 경로 오프셋 (볼륨 정보 시작 기준) |
| +4 | 4 | 장치 경로 글자 수 |
| +8 | 8 | 볼륨 생성 시각 (FILETIME, UTC) |
| +16 | 4 | 볼륨 일련번호 |
| +20 | 4 | 파일 참조 목록 오프셋 |
| +24 | 4 | 파일 참조 목록 크기 |
| +28 | 4 | 디렉터리 문자열 오프셋 (볼륨 정보 시작 기준) |
| +32 | 4 | 디렉터리 문자열 개수 |

**디렉터리 문자열** 항목은 2바이트 글자 수(끝 NUL 제외) 뒤에 UTF-16LE 경로와 NUL 이 옵니다.

> 그림 자리: 파일 정보 → 파일 메트릭 항목 → 파일 이름 문자열, 파일 정보 → 볼륨 정보 항목 → 장치 경로·디렉터리 문자열로 이어지는 오프셋 사슬

## 읽는 법 — 목록에서 찾을 것

### 1. 실행 파일의 실제 경로

.pf 파일 이름에는 전체 경로 없이 실행 파일 이름과 경로 해시만 있습니다. 예를 들어 CMD.EXE 의 .pf 파일 목록에는 `\WINDOWS\SYSTEM32\CMD.EXE` 가 들어 있습니다. 이처럼 파일 목록에서 .pf 이름과 같은 실행 파일 항목을 찾으면 실행 위치를 알 수 있습니다.

`\USERS\…\DOWNLOADS`, `…\TEMP`, `\PROGRAMDATA`, 시스템 볼륨이 아닌 볼륨처럼 프로그램을 보통 설치하지 않는 곳이면 먼저 살핍니다. 경로 해시로 이 경로를 검증하는 법은 [경로 해시로 실행 위치 구분하기](path-hash.md) 에 있습니다.

### 2. 제자리가 아닌 DLL

시스템 DLL 과 이름이 같은데 System32·SysWOW64 가 아닌 폴더에 있는 항목을 찾습니다. 프로그램 폴더에 넣은 가짜 DLL 을 먼저 읽게 만드는 DLL 검색 순서 가로채기 (DLL Search Order Hijacking) 흔적일 수 있습니다. 공개된 사례 가운데에는 WSOCK32.DLL 이 시스템 폴더가 아니라 프로그램 폴더에서 올라온 경우가 있습니다.

플래그가 0x200 이면 실행 코드로 올린 파일입니다. 그 파일이 디스크에 남아 있으면 서명과 해시를 확인합니다 ([의심 실행 파일 선별](../../../03-techniques/analysis/code-signing-yara.md)).

### 3. 시작하면서 읽은 문서·데이터 파일

.DOCX, .PDF, .HWP, .ZIP 처럼 코드가 아닌 파일이 목록에 있을 수 있습니다. 이런 항목은 프로그램이 시작 직후 그 파일을 읽었다는 기록입니다. 외부 매체의 파일을 연 프로그램의 .pf 에는 그 매체의 흔적이 남을 수 있습니다.

### 4. 압축·전송 도구가 건드린 대상

압축 도구나 동기화 도구는 시작하자마자 대상 파일과 폴더를 읽습니다. 그래서 이런 도구의 .pf 에는 대상 이름 일부가 남을 수 있습니다. 공개된 사례에서는 7-Zip 의 .pf 에 풀어 놓은 공격 도구 이름이 남았고, rclone 의 .pf 에는 빼돌린 폴더 아래 폴더 이름이 남았습니다.

이 목록은 시작 뒤 짧은 시간의 표본이지 도구가 처리한 대상 전체가 아닙니다. 시나리오는 [퇴사 전 자료를 모으고 압축했나](../../../04-scenarios/exfiltration/data-exfiltration/staging.md) 에서 다룹니다.

### 5. 외부 저장장치

볼륨 정보 항목이 둘 이상이면 프로그램이 시작할 때 다른 볼륨의 파일도 읽었다는 뜻이고, 항목마다 볼륨 일련번호가 있습니다. 이 번호로 프로그램을 실행하거나 파일을 연 USB 메모리를 찾을 수 있습니다.

볼륨 일련번호는 포맷할 때 볼륨에 붙는 번호입니다. USB 장치 자체의 일련번호와는 다릅니다. 볼륨 일련번호를 장치와 잇는 방법은 [휴대용 장치·볼륨 이름 기록](../../external-devices/usb-storage-artifacts/wpd-emdmgmt.md) 과 [바로가기 파일](../../file-folder-usage/lnk.md) 에 있습니다.

XP~7 에서는 FAT 볼륨이면 생성 시각이 비어 있습니다. 일련번호는 늘 채워집니다.

Windows 10 의 장치 경로는 `\VOLUME{16자리-8자리}` 형식입니다. 뒤 8자리는 볼륨 일련번호와 같고, 앞 16자리는 볼륨 생성 시각을 16진으로 적은 값입니다(Windows 11 기준). 형식 명세에는 이 관계가 적혀 있지 않으므로, 보고서에 쓰려면 분석 대상마다 같은 항목의 생성 시각 필드와 맞춰 봅니다.

### 6. 사용자 폴더

폴더 목록에 `\USERS\<이름>\` 이 있으면 프로그램이 그 프로필 아래를 건드린 것이며, 실행한 계정을 가리키는 정황일 뿐입니다. 다른 계정의 폴더를 읽는 프로그램도 있습니다. 사람을 특정하는 방법은 [그 시각에 PC 를 쓴 사람이 누구인가](../../../04-scenarios/activity/user-attribution.md) 에서 다룹니다.

### 7. 지금은 없는 파일

목록 속 파일이 디스크에 없으면 나중에 지웠거나 옮겼을 수 있습니다. 버전 23 (Vista·7) 이면 항목의 NTFS 파일 참조로 $MFT 레코드를 찾습니다. 레코드의 순번이 파일 참조의 순번과 다르면 그 레코드는 이미 다른 파일이 다시 쓴 것입니다 ([MFT 레코드와 속성](../../../01-foundations/disk-volume/ntfs/file-record-attribute.md)). 파일 이름은 [$MFT](../../filesystem/mft.md)·[$UsnJrnl](../../filesystem/usnjrnl.md) 을 찾는 단서가 됩니다.

## 증거로서 의미

**증명하는 것**

- 그 .pf 의 프로그램이 실행된 적이 있고, 시작 직후 목록 속 경로의 파일·폴더를 읽었습니다.
- 프로그램이 어느 경로에서 실행되었는지 알 수 있습니다.
- 그때 목록 속 볼륨이 시스템에 연결되어 있었습니다.

**증명하지 못하는 것**

- 사용자가 그 파일을 열어 내용을 봤다는 것. 목록은 프로세스가 읽은 기록입니다.
- 몇 번째 실행 때, 몇 시에 읽었는지. 목록 항목에는 시각이 없습니다.
- 목록에 없는 파일은 안 읽었다는 것. 시작 뒤 약 10초가 지난 뒤의 접근은 남지 않습니다.
- 그 파일이 지금도 있거나 내용이 그대로라는 것.
- 누가 실행했는지.

보고서 문장은 기록으로 확인되는 만큼만 씁니다.

- 쓰지 않을 문장: "피의자가 7-Zip 으로 기밀 폴더를 압축했다."
- 쓸 문장: "7ZG.EXE 프리페치 파일의 참조 목록에 `…\PROJECT` 폴더와 그 안 파일 이름 N개가 있다. 이는 이 프리페치 파일에 기록된 실행 가운데 적어도 한 번, 7-Zip 이 시작 직후 이 경로들을 읽었다는 기록이다."

## 시각 해석

- 참조 목록의 항목에는 시각 필드가 없습니다.
- 목록 전체는 .pf 에 적힌 실행 시각들과 함께 볼 수 있습니다. 하지만 어느 실행에서 생긴 항목인지는 목록만으로 정할 수 없습니다.
- 트레이스 체인 항목에는 최근 8번 실행 각각에서 그 블록을 썼는지 표시하는 비트가 있습니다. 파일 안에 여러 번의 실행 정보가 섞여 있을 수 있다는 뜻입니다.
- 볼륨 생성 시각은 UTC FILETIME 입니다 ([시각 값 형식](../../../01-foundations/value-decoding/filetime-unix-webkit-dos-ole.md)). 볼륨을 만든(포맷한) 때로 읽습니다.
- 참조된 파일 자체의 시각($MFT·$UsnJrnl)이 .pf 의 실행 시각 가운데 하나와 몇 초 안에 붙어 있으면, 그 실행과 묶는 근거가 됩니다.

## 함정과 한계

- **짧은 창.** 시작 뒤 최대 10초만 보고 시작이 먼저 끝나면 더 짧아지며, 한참 뒤에 연 문서는 남지 않습니다.
- **드라이브 문자가 아닙니다.** 경로는 `\DEVICE\HARDDISKVOLUMEn` 이나 `\VOLUME{…}` 로 시작합니다. HARDDISKVOLUME 번호는 드라이브 문자와 다릅니다. 볼륨 일련번호를 실제 볼륨의 일련번호와 맞춰 봅니다 ([부트 섹터와 클러스터](../../../01-foundations/disk-volume/ntfs/boot-sector-cluster.md)).
- **대소문자.** 폴더·파일 이름은 대문자로 적혀 있습니다. 원래 대소문자는 알 수 없습니다.
- **엄격한 UTF-16 이 아닙니다.** 경로에는 짝 없는 대리 문자 (U+D800 같은 값) 가 들어갈 수 있습니다. 도구가 이런 글자를 바꾸거나 건너뛸 수 있으므로, 이상한 이름은 원시 바이트로 확인합니다 ([문자 인코딩](../../../01-foundations/value-decoding/utf-16le-utf-8-cp949.md)).
- **압축.** Windows 10 이후 .pf 는 압축되어 있습니다. 이미지 전체를 키워드로 검색해도 .pf 속 경로는 걸리지 않습니다. 압축을 푼 뒤 검색합니다 ([윈도 압축 형식](../../../01-foundations/value-decoding/lznt1-xpress-xpress-huffman.md)).
- **.pf 가 여러 개.** 같은 실행 파일이라도 경로에 따라 .pf 가 따로 생깁니다. 참조 목록도 .pf 마다 다릅니다 ([경로 해시](path-hash.md)).
- **안 남는 경우.** 프리페치가 꺼져 있거나 보관 개수 한도를 넘으면 목록이 없습니다 ([프리페치 해석 함정](pitfalls.md)).
- **안티포렌식.** .pf 를 지우면 목록도 함께 사라집니다. 섀도 복사본이나 비할당 영역에 옛 .pf 가 남아 있을 수 있습니다 ([섀도 복사본 활용](../../../03-techniques/analysis/volume-shadow-copy-analysis.md), [파일 카빙](../../../03-techniques/analysis/data-recovery/file-carving.md)). 실행 파일 이름을 바꾸면 .pf 이름은 바뀌지만, 목록 속 경로는 실제로 읽은 경로 그대로입니다.

## 직접 분석해 보기

### 헥스로 한 번

아래 바이트는 모두 libscca 명세로 만든 예시입니다. 실제 데이터에서 나온 값이 아닙니다. 형식 버전 30 파일의 압축을 이미 풀었다고 가정합니다.

**1단계 — 압축 풀기.** Windows 10 이후 .pf 는 `4D 41 4D 04` ("MAM\x04") 로 시작합니다. 먼저 압축을 풉니다. 푼 파일은 버전 값 뒤에 "SCCA" 서명이 옵니다.

**2단계 — 파일 정보에서 오프셋 읽기.** 파일 정보는 0x54 에서 시작합니다.

```
오프셋    00 01 02 03 04 05 06 07  08 09 0A 0B 0C 0D 0E 0F
00000050  .. .. .. .. 30 01 00 00  2C 00 00 00 B0 06 00 00
00000060  90 00 00 00 30 0B 00 00  28 1A 00 00 58 25 00 00
00000070  01 00 00 00 40 0A 00 00
```

| 파일 오프셋 | 값 | 뜻 |
|---|---|---|
| 0x54 | 0x130 | 파일 메트릭 배열 시작 |
| 0x58 | 44 | 파일 목록 44개 |
| 0x64 | 0xB30 | 파일 이름 문자열 시작 |
| 0x68 | 0x1A28 | 파일 이름 문자열 전체 크기 |
| 0x6C | 0x2558 | 볼륨 정보 시작 |
| 0x70 | 1 | 볼륨 1개 |
| 0x74 | 0xA40 | 볼륨 정보 전체 크기 |

0x5C·0x60 은 트레이스 체인 배열의 오프셋과 개수입니다.

**3단계 — 파일 메트릭 항목 하나 읽기.** 항목은 32바이트입니다. 번호 5 항목은 0x130 + 5×32 = 0x1D0 에 있습니다.

```
000001D0  11 00 00 00 01 00 00 00  01 00 00 00 E0 02 00 00
000001E0  4B 00 00 00 00 02 00 00  00 00 00 00 00 00 00 00
```

- +12 의 0x2E0 을 파일 이름 문자열 시작 0xB30 에 더합니다. 이름은 파일 오프셋 0xE10 에 있습니다.
- +16 은 75글자입니다. 끝 NUL 까지 152바이트를 읽습니다.
- +20 은 0x200 입니다. 실행 코드로 올린 파일입니다.
- +24 의 8바이트가 모두 0 입니다. 파일 참조가 채워지지 않았습니다.

0xE10 에서 읽은 이름이 아래와 같다고 합시다.

```
\VOLUME{01d9a0b1c2d3e4f5-1a2b3c4d}\USERS\USR\APPDATA\LOCAL\TEMP\VERSION.DLL
```

VERSION.DLL 은 원래 System32 에 있는 이름입니다. Temp 폴더에서 코드로 올렸으므로 "제자리가 아닌 DLL" 후보입니다.

**4단계 — 볼륨 정보 항목 읽기.** 볼륨 정보는 0x2558 에서 시작합니다.

```
00002550                           60 00 00 00 22 00 00 00
00002560  F5 E4 D3 C2 B1 A0 D9 01  4D 3C 2B 1A A8 00 00 00
00002570  10 00 00 00 B8 00 00 00  0E 00 00 00
```

| 항목 안 위치 | 값 | 뜻 |
|---|---|---|
| +0 | 0x60 | 장치 경로는 0x2558 + 0x60 = 0x25B8 에 있습니다. |
| +4 | 34 | 장치 경로 34글자: `\VOLUME{01d9a0b1c2d3e4f5-1a2b3c4d}` |
| +8 | 0x01D9A0B1C2D3E4F5 | 볼륨 생성 시각: 2023-06-17 00:22:12 UTC |
| +16 | 0x1A2B3C4D | 볼륨 일련번호: 1A2B-3C4D |
| +28 | 0xB8 | 디렉터리 문자열은 0x2558 + 0xB8 = 0x2610 에 있습니다. |
| +32 | 14 | 폴더 14개 |

이 예시의 장치 경로는 앞 16자리가 생성 시각, 뒤 8자리가 일련번호가 되도록 만들었습니다. 앞 16자리는 널리 쓰이는 설명을 따른 것입니다.

**5단계 — 디렉터리 문자열 읽기.** 첫 항목은 0x2610 에 있습니다.

```
00002610  28 00 5C 00 56 00 4F 00  4C 00 55 00 4D 00 45 00   (.\.V.O.L.U.M.E.
00002620  7B 00 30 00 31 00 64 00  39 00 61 00 30 00 62 00   {.0.1.d.9.a.0.b.
00002630  31 00 63 00 32 00 64 00  33 00 65 00 34 00 66 00   1.c.2.d.3.e.4.f.
00002640  35 00 2D 00 31 00 61 00  32 00 62 00 33 00 63 00   5.-.1.a.2.b.3.c.
00002650  34 00 64 00 7D 00 5C 00  55 00 53 00 45 00 52 00   4.d.}.\.U.S.E.R.
00002660  53 00 00 00                                        S...
```

- 앞 2바이트 0x28 은 40글자입니다.
- 40글자 뒤 NUL 까지 읽으면 `\VOLUME{01d9a0b1c2d3e4f5-1a2b3c4d}\USERS` 입니다.
- 이 항목은 2 + 41×2 = 84바이트입니다. 다음 항목은 0x2664 에서 시작합니다.

### 공개 도구로 한 번

libscca 의 sccainfo 와 PECmd 는 파일 목록, 볼륨 정보, 폴더 목록을 모두 보여 줍니다. PECmd 는 기본값으로 temp·tmp 가 든 경로를 강조합니다. 두 도구의 파일 목록 개수와 이상한 글자 처리가 같은지 맞춰 봅니다 ([도구 결과 교차 검증](../../../03-techniques/reporting/tool-validation.md)).

## 실습

NIST CFReDS 의 Data Leakage Case 는 Windows 7 SP1 PC 이미지와 USB 메모리 두 개, CD-R 하나로 이루어져 있습니다. Windows 7 이므로 .pf 는 형식 버전 23 이고 압축되어 있지 않습니다.

1. `Windows\Prefetch` 의 모든 .pf 에서 볼륨 정보 항목이 둘 이상인 파일을 찾아 봅니다. 있다면 시스템 볼륨이 아닌 볼륨의 장치 경로·일련번호·생성 시각을 적습니다.
2. 1번의 일련번호를 LNK 파일과 레지스트리의 USB 흔적과 맞춰 봅니다. 어느 장치의 볼륨인지 말할 수 있나요?
3. 문서 편집기나 뷰어 .pf 의 파일 목록에서 문서 파일 이름을 뽑습니다. LNK·점프리스트의 최근 문서 목록과 겹치는 것과 겹치지 않는 것을 나눠 봅니다.
4. 파일 메트릭 항목의 NTFS 파일 참조 하나를 골라 $MFT 레코드를 찾습니다. 순번이 같은지, 그 파일이 지금도 있는지 확인합니다.
5. 1~4번 결과로 보고서 문장을 하나 씁니다. "사용자가 옮겼다" 가 아니라 기록으로 확인되는 만큼만 씁니다.
