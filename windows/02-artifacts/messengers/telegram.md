# 텔레그램 (Telegram)

> 위치: 아티팩트 사전 > 메신저

텔레그램 데스크톱 (Telegram Desktop) 의 데이터는 `tdata` 폴더에 있습니다. `tdata` 에는 대화 기록이 들어 있지 않습니다[1]. 이 폴더에는 설정과 캐시(사진·영상·받은 파일)가 남습니다. 설정 파일은 `TDF$` 로 시작하고, 그 파일을 쓴 앱 버전과 MD5 가 함께 적힙니다. 로컬 암호 (passcode) 를 걸었는지에 따라 `tdata` 만으로 풀 수 있는지가 달라집니다. 실행 로그 `log.txt` 는 실행 시각·버전·설치 위치를 알려 줍니다.

이 페이지의 폴더 구성·파일 머리·로그 설명은 텔레그램 데스크톱 7.1.1, 시간대 KST 기준입니다.

## 무엇을 기록하나 · 왜 생기나

`tdata` 안 파일은 설정 파일과 캐시 파일이고, 대화 기록 (chat histories) 은 들어 있지 않습니다. 캐시를 풀면 JPEG, 영상, 공유된 파일이 나올 수 있습니다[1]. 데스크톱 앱은 대화를 서버에서 받아 보여 주므로, 디스크에는 설정과 화면에 띄운 사진·영상·파일의 캐시가 남는 것으로 보입니다. 앱은 실행할 때마다 로그 파일에 실행 정보를 적습니다.

이 페이지는 대화 본문이 로컬 DB 에 있다고 보지 않으며, 대화 본문을 찾는다면 다른 경로를 봅니다. 아래 "교차 검증" 을 참고합니다.

## 위치와 버전별 차이

| 판 | 위치 | 근거 |
|---|---|---|
| Windows 설치판 | `%USERPROFILE%\AppData\Roaming\Telegram Desktop` | [1] |
| 스토어 판, 포터블 판 | 공개 자료 없음 | — |

설치판은 실행 파일과 데이터를 같은 폴더에 두며, 그 폴더에는 `Telegram.exe`, `Updater.exe`, `unins000.exe`·`unins000.dat`·`unins000.msg`, `log.txt`, `log_start0.txt`, `modules`, `tdata`, `tupdates` 가 있습니다. 경로를 모를 때는 이름 `tdata` 폴더와 `Telegram.exe` 로 찾고, 설치 기록은 [설치 프로그램](../system-account/uninstall.md) 에서 확인합니다.

파일을 쓰는 방식(요즘 방식·옛 방식)에 따라 파일 이름 끝 글자가 달라집니다. 아래 "파일 이름" 을 참고합니다.

## 구조

### 설정 파일 형식 (TDF$)

`tdata` 의 설정 파일은 아래 구성입니다[2].

| 순서 | 필드 | 크기 | 뜻 |
|---|---|---|---|
| 1 | 매직 | 4바이트 | `TDF$` (`54 44 46 24`) |
| 2 | 버전 | 4바이트 (qint32) | 이 파일을 쓴 앱 버전 |
| 3 | 데이터 | 가변 | 암호화된 부분이 들어 있습니다 |
| 4 | MD5 | 16바이트 | 파일 끝에 붙습니다 |

- MD5 는 데이터, 데이터 크기(qint32), 버전, 매직을 이 순서로 이어 계산합니다[2].
- MD5 는 파일이 손상됐는지 판별하는 값입니다.
- `key_datas`, `settingss`, `D877F783D5D3EF8Cs`, `D877F783D5D3EF8C\maps`, `D877F783D5D3EF8C\configs` 가 모두 `54 44 46 24` 로 시작합니다.
- 버전 필드는 리틀 엔디언입니다. 7.1.1 에서 이 값은 7001001 이고, `log.txt` 의 `Launched version: 7001001` 과 같습니다.
- 일부 파일의 버전 필드는 7000008, 7000009 처럼 예전 값일 수 있습니다. 그 파일은 예전 버전(7.0.8·7.0.9)을 쓰던 때 마지막으로 쓰인 것으로 보입니다.

### 파일 이름

- 앱은 64비트 키를 `ToFilePart` 함수로 16글자 16진수 이름으로 바꿉니다[2].
- 이름 끝 글자는 쓰기 방식을 구분합니다[2].

| 끝 글자 | 뜻 |
|---|---|
| `s` | 요즘 방식. 안전한 원자적 쓰기 |
| `0` | 옛 방식 |
| `1` | 옛 방식의 백업 |

- 앱은 읽을 때 `s` 파일을 먼저 찾고, 없으면 `0` 과 `1` 가운데 수정 시각이 새것을 고릅니다[2].
- 옛 자료에는 `tdata/D877F783D5D3EF8C/map0` 으로 나오지만[1] 7.1.1 에서는 `maps` 이며, 끝 글자 규칙과 맞습니다.
- 폴더 이름 `D877F783D5D3EF8C` 는 MD5("data") 에서 나온 값과 같습니다. 계산은 아래 "헥스로 한 번" 에 있습니다.
- 두 번째 계정부터 폴더 이름이 어떻게 정해지는지는 공개 자료가 없습니다.

### 암호화

이 절은 무엇이 암호화됐고 키가 무엇에 묶였는지만 적습니다. 푸는 절차는 적지 않습니다.

- 암호화된 부분은 AES 로 "로컬 방식" 암호화를 합니다(`aesEncryptLocal`·`aesDecryptLocal`)[2].
- 암호 블록은 SHA1 해시 16바이트와 암호문으로 이루어지며, 암호문은 16바이트 단위로 맞추고 남는 자리는 무작위 바이트로 채웁니다[2].
- 키는 PKCS5_PBKDF2_HMAC 와 SHA-512 로 만듭니다. 반복 횟수는 100,000번(`kStrongIterationsCount`)입니다[2].
- 로컬 암호가 비어 있으면 반복 횟수는 1번입니다[2].
- 옛 키 방식은 SHA1 기반 PBKDF2(`CreateLegacyLocalKey`)입니다[2].
- `key_datas` 는 이름으로 보면 로컬 키를 담는 파일일 가능성이 있습니다.

로컬 암호를 걸지 않았으면 `tdata` 만으로 풀 수 있고, 걸었으면 그 암호가 있어야 합니다. 암호화된 증거를 다루는 방법은 [암호화 증거 다루기](../../03-techniques/analysis/encrypted-evidence/index.md) 에서 다룹니다.

### 캐시

| 항목 | 모양 |
|---|---|
| `user_data\cache\0` | `binlog` 파일과 두 자리 16진수 하위 폴더(`00`, `01` …) |
| `user_data\media_cache\0` | 위와 같음 |
| 캐시 파일 이름 | 12글자 16진수 |
| 파일 수 | 예: `user_data` 안에 825개 |

- `binlog` 와 캐시 파일은 `54 44 45 46`(`TDEF`)로 시작합니다. 설정 파일의 `TDF$` 와 다릅니다.
- 캐시 형식의 세부는 공개 자료가 없습니다.

### tdata 의 다른 항목

| 항목 | 내용 |
|---|---|
| `user_data\wvbots\EBWebView` | 봇(미니 앱)용 WebView2 데이터 폴더로 보입니다. 읽는 법은 [크롬 계열 앱 공통 구조](../../01-foundations/app-mail-data/chromium-electron-webview2/index.md) 에서 다룹니다 |
| `emoji` | `cache_42_*`, `cache_56_*` 파일 |
| `dumps`, `temp`, `tdummy`, `countries` | 공개 자료 없음 |
| `shortcuts-custom.json`, `shortcuts-default.json` | 단축키 설정 |
| `prefix` | 내용이 `https://td.telegram.org/` 로 시작합니다 |
| `usertag` | 8바이트 파일 |

### 로그

설치 폴더에 `log.txt` 와 `log_start0.txt` 가 있고, 줄마다 `[YYYY.MM.DD HH:MM:SS]` 모양의 시각이 붙습니다. 실행할 때 아래 줄들이 적힙니다.

| 줄 | 알려 주는 것 |
|---|---|
| `Launched version: 7001001 ...` | 실행한 앱 버전 |
| `Executable dir: ...` | 실행 파일 위치 |
| `Working dir: ...` | 작업 폴더 |
| `Command line: ...` | 실행 인수 |

로그를 몇 개까지 돌려 쓰는지는 공개 자료가 없습니다.

## 증거로서 의미

### 증명하는 것

- **앱 실행.** `log.txt` 의 실행 줄은 그 시각에 앱이 실행됐다는 기록입니다.
- **실행 버전과 위치.** 실행 줄에 버전, 실행 파일 폴더, 작업 폴더, 실행 인수가 남습니다.
- **파일마다 마지막으로 쓴 버전.** 설정 파일의 버전 필드는 그 파일을 마지막으로 쓴 앱 버전입니다. 여러 버전을 거쳐 썼다는 단서가 됩니다.
- **캐시에 남은 사진·영상·파일.** 풀면 앱이 받아 둔 미디어와 파일이 나올 수 있습니다[1].
- **계정 폴더.** `tdata` 아래 16글자 16진수 폴더는 로그인한 계정의 데이터 폴더로 보입니다. 폴더가 여러 개면 계정이 여럿이었는지 확인합니다.

### 증명하지 못하는 것

- **대화 본문.** `tdata` 에는 대화 기록이 없습니다[1].
- **사용자가 캐시의 사진을 봤는지.** 캐시에 있다는 것은 앱이 받아 두었다는 뜻입니다. 사용자가 화면에서 봤다는 뜻은 아닙니다.
- **누가 조작했는지.** 계정까지만 알려 줍니다. 방법은 [그 시각에 PC 를 쓴 사람이 누구인가](../../04-scenarios/activity/user-attribution.md) 에서 다룹니다.
- **로그에 없는 실행.** 로그를 돌려 쓰는 범위를 모르므로, 로그에 없다고 실행하지 않았다고 말할 수 없습니다.

보고서에는 "피의자가 텔레그램으로 대화했다" 가 아니라 이렇게 씁니다. "A 계정의 `Telegram Desktop\log.txt` 에 이 시각 앱 실행 기록이 있다. 기록된 버전은 7001001, 실행 파일 폴더는 X 이다." 시각과 폴더는 실제 데이터에서 확인한 값으로 채웁니다.

## 시각 해석

| 시각 | 무엇이 바뀔 때 | UTC·현지 |
|---|---|---|
| `log.txt` 줄 시각 | 로그 줄을 쓸 때 | 현지 시각입니다. 마지막 줄 시각이 파일 수정 시각과 같습니다 |
| 설정 파일 (`TDF$`) | — | 구조에 시각 필드가 없습니다 |
| 설정 파일의 파일 시스템 시각 | 앱이 파일을 다시 쓸 때 | UTC. `settingss` 는 마지막 실행과 가깝고, `key_datas` 는 그보다 이를 수 있습니다. 각 파일 시각의 뜻은 공개 자료가 없습니다 |
| 캐시 파일의 파일 시스템 시각 | 캐시를 쓸 때 | UTC. 받은 때의 단서로 봅니다 |

- 현지 시각인 로그와 UTC 인 파일 시각을 한 표에 놓을 때는 [시간대 설정](../system-account/time-zone.md) 으로 맞춥니다.
- 파일 시스템 시각은 [마스터 파일 테이블](../filesystem/mft.md) 에서 봅니다.

## 함정과 한계

- **`tdata` 에서 대화를 찾습니다.** 대화 기록은 `tdata` 에 없습니다.
- **예전 자료의 파일 이름을 그대로 찾습니다.** 옛 자료의 예는 `map0` 이지만 7.1.1 은 `maps` 를 씁니다. 끝 글자 `s`·`0`·`1` 을 모두 찾습니다.
- **`0`·`1` 파일을 파일 이름만으로 고릅니다.** 앱은 수정 시각이 새것을 읽습니다. 두 파일을 모두 보존합니다.
- **캐시도 `TDF$` 로 봅니다.** 캐시 파일은 `TDEF` 로 시작합니다. 형식이 다릅니다.
- **로그 시각을 UTC 로 봅니다.** `log.txt` 는 현지 시각입니다.
- **로컬 암호 유무를 짐작합니다.** 로컬 암호가 있으면 `tdata` 만으로는 풀리지 않습니다.
- **폴더를 지웠다고 흔적이 없다고 봅니다.** 지운 파일은 [삭제 데이터 복구](../../03-techniques/analysis/data-recovery/index.md) 방법으로 찾습니다. 옛 시점은 [섀도 복사본 활용](../../03-techniques/analysis/volume-shadow-copy-analysis.md) 으로 봅니다.

## 직접 분석해 보기

### 헥스로 한 번

아래는 tdesktop 소스의 형식으로 만든 예시입니다. 실제 기기에서 나온 파일이 아닙니다. 데이터 부분과 MD5 는 `..` 로 줄였습니다.

```
오프셋  00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F
0x00   54 44 46 24 A9 D3 6A 00 .. .. .. .. .. .. .. ..   TDF$..j.
...    (데이터)
끝-16  .. .. .. .. .. .. .. .. .. .. .. .. .. .. .. ..   (MD5 16바이트)
```

1. 0x00 의 `54 44 46 24` 는 매직 `TDF$` 입니다.
2. 0x04 의 `A9 D3 6A 00` 은 버전입니다. 리틀 엔디언으로 읽으면 `0x006AD3A9` = 7001001 입니다.
3. 7001001 은 앞에서부터 7·001·001 로 끊어 7.1.1 로 읽습니다. 앱 버전 7.1.1 의 로그에 `Launched version: 7001001` 이 적히므로 이 읽기와 맞습니다.
4. 0x08 부터 파일 끝 16바이트 앞까지가 데이터입니다.
5. 마지막 16바이트가 MD5 입니다.

폴더 이름도 직접 맞춰 볼 수 있습니다.

1. 문자열 `data` 의 MD5 는 `8d777f385d3dfec8815d20f7496026dc` 입니다.
2. 앞 8바이트는 `8d 77 7f 38 5d 3d fe c8` 입니다.
3. `ToFilePart` 는 64비트 값의 낮은 4비트부터 한 글자씩 적습니다[2]. 그래서 바이트마다 두 자리가 뒤집혀 `D8 77 F7 83 D5 D3 EF 8C` 가 됩니다.
4. 이어 적으면 `D877F783D5D3EF8C` 입니다. `tdata` 의 폴더 이름과 같습니다.

### 공개 도구로 한 번

공개 도구의 예로 `tdata` 의 설정과 캐시를 풀어 보는 telegram-desktop-decrypt 가 있습니다[1].

- 도구가 읽은 파일 목록과 `tdata` 의 파일 목록을 맞춰 봅니다.
- 도구가 `s`·`0`·`1` 가운데 어느 파일을 읽었는지 적습니다.
- 도구가 낸 버전 값과 헥스로 읽은 버전 필드를 맞춰 봅니다. 방법은 [도구 결과 교차 검증](../../03-techniques/reporting/tool-validation.md) 에서 다룹니다.

## 실습

Windows 11 가상 머신에 앱을 설치해 직접 시험합니다. 시험 전에 앱 버전을 적어 둡니다.

1. 로그인 전과 뒤에 `tdata` 의 파일 목록은 어떻게 달라집니까? 16글자 16진수 폴더가 생깁니까?

3. 대화방에서 사진을 연 뒤 `user_data\media_cache` 에 새 파일이 생깁니까? 파일 시스템 시각은 사진을 연 시각과 맞습니까?
