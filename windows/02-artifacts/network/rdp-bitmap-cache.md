# 원격 데스크톱 비트맵 캐시 (RDP Bitmap Cache)

## 한 줄 요약

원격 데스크톱 클라이언트는 원격 화면에서 받은 작은 그림 조각을 사용자 프로필 안 캐시 파일에 저장합니다. 이 조각을 꺼내면 그 계정이 원격 데스크톱으로 본 글자·창·아이콘의 일부를 볼 수 있습니다.

## 무엇을 기록하나 · 왜 생기나

원격 데스크톱 클라이언트는 원격 화면을 작은 사각형 조각으로 받는데, 이 조각을 이 글에서는 타일 (tile) 이라고 부릅니다. 클라이언트가 받은 타일을 저장한 파일이 비트맵 캐시 (Bitmap Cache) 이고, 이 파일은 사용자 프로필 안에 있어서 계정마다 따로 남습니다.

접속을 건 쪽(출발 PC)에 남는 흔적이며, 접속을 받은 쪽의 흔적은 [원격 데스크톱 이벤트](../event-logs/rdp-event-logs/index.md) 에서 다룹니다. 타일에는 원격 화면의 픽셀이 그대로 들어 있어서 화면에 떠 있던 글자나 창 모양이 조각으로 남습니다.

클라이언트의 "지속 비트맵 캐싱" 옵션과 캐시 파일이 생기는지의 관계는 확인하지 못했습니다. mstsc 가 아닌 다른 원격 데스크톱 클라이언트가 같은 파일을 만드는지도 확인하지 못했습니다.

## 위치와 버전별 차이

```
C:\Users\<사용자>\AppData\Local\Microsoft\Terminal Server Client\Cache\bcache<번호>.bmc
```

- 위 경로는 JPCERT/CC 의 mstsc 분석 자료를 따릅니다.
- 공개 도구 bmc-tools 의 설명서는 사용자 프로필 안의 `bcache*.bmc` 파일과 `cache????.bin` 파일을 처리한다고 적습니다.
- `.bin` 파일이 `.bmc` 와 같은 `Cache` 폴더에 있는지는 이번에 연 자료로 확인하지 못했습니다.

캐시 파일은 두 형식이 있습니다.

| 형식 | 파일 이름 | 파일 머리 | 타일 머리 크기 |
|---|---|---|---|
| `.bmc` | `bcache<번호>.bmc` | 없음 | 20바이트 (0x14) |
| `.bin` | `cache????.bin` | `RDP8bmp` + 0x00 + 버전 4바이트 | 12바이트 (0x0C) |

- `.bin` 의 머리 문자열 `RDP8bmp` 로 보아 RDP 8 이후 형식으로 보입니다. 윈도 버전과 형식의 대응을 적은 자료는 이번에 보지 못했습니다.
- `.bmc` 에서 `.bin` 으로 바뀐 윈도 버전은 확인하지 못했습니다.
- `bcache2`, `bcache22`, `bcache24` 처럼 파일 이름에 붙는 번호와 색 깊이의 관계도 확인하지 못했습니다.

원격 데스크톱 연결을 쓴 적이 없는 Windows 11 PC 한 대에는 `Terminal Server Client\Cache` 폴더가 없었습니다. (확인 범위: Win11 25H2 한 대)

## 구조

아래 구조는 bmc-tools 소스 코드가 읽는 방식을 정리한 것입니다. Microsoft 가 공개한 파일 형식 문서는 이번에 보지 못했습니다. 숫자는 모두 리틀 엔디언 (little-endian) 입니다.

### .bin 파일

**파일 머리 (12바이트)**

| 오프셋 | 크기 | 내용 |
|---|---|---|
| 0x00 | 8 | `RDP8bmp` 와 0x00 |
| 0x08 | 4 | 버전 (정수) |

**타일 머리 (12바이트)**

| 오프셋 | 크기 | 내용 |
|---|---|---|
| 0x00 | 4 | key1 |
| 0x04 | 4 | key2 |
| 0x08 | 2 | 폭 (픽셀) |
| 0x0A | 2 | 높이 (픽셀) |

- 픽셀은 32비트 BGRA 입니다. 한 픽셀이 파랑·초록·빨강·투명도 순서로 4바이트입니다.
- bmc-tools 는 픽셀 데이터를 256바이트씩 끊어 그 순서를 뒤집습니다. 도구가 이렇게 읽는 것으로 보아 아래 줄이 먼저 저장된 것으로 보입니다.
- 256바이트가 64픽셀 한 줄(64 × 4바이트)이라는 해석은 계산으로 맞춘 것입니다. 자료로 확인하지는 못했습니다.

### .bmc 파일

- 파일 전체의 머리(매직 값)가 없습니다. 첫 바이트부터 타일 머리입니다.

**타일 머리 (20바이트)**

| 오프셋 | 크기 | 내용 |
|---|---|---|
| 0x00 | 4 | key1 |
| 0x04 | 4 | key2 |
| 0x08 | 2 | 폭 (픽셀) |
| 0x0A | 2 | 높이 (픽셀) |
| 0x0C | 4 | 데이터 길이 |
| 0x10 | 4 | 매개변수 |

- 앞 12바이트는 `.bin` 의 타일 머리와 같습니다.
- 매개변수에 0x08 비트가 켜져 있으면 RLE (Run-Length Encoding) 로 압축된 타일입니다.
- bmc-tools 는 데이터 길이를 (폭 × 높이) 로 나눠 한 픽셀의 바이트 수를 정합니다.

| 나눈 값 | 색 형식 |
|---|---|
| 1 | 8비트 팔레트 색 (256색) |
| 2 | RGB565 (16비트) |
| 3 | 24비트 색 |
| 4 | 32비트 BGRA |

- bmc-tools 는 README 기준 3.05 판부터 BMCache 파일 안의 "old bitmap data" 를 뽑는 `-o` 옵션을 제공합니다. 이 데이터가 무엇인지(덮어쓴 타일인지 등)는 확인하지 못했습니다.

### 타일

- 타일은 보통 64×64 픽셀입니다.
- 타일 머리에는 시각 칸이 없습니다.
- key1·key2 가 화면 위치를 뜻하는지는 이번에 연 자료로 확인하지 못했습니다.

## 증거로서 의미

### 증명하는 것

- 이 사용자 프로필의 캐시에 이 타일이 있습니다. 곧 이 계정에서 원격 데스크톱 클라이언트가 이 화면 조각을 받았습니다.
- 타일에 보이는 글자·창·아이콘으로 원격 화면에 무엇이 떠 있었는지 일부를 알 수 있습니다. 예를 들어 창 제목, 폴더 이름, 프로그램 아이콘 같은 조각입니다.
- 출발 PC 쪽 흔적이므로, 이 PC 에서 다른 컴퓨터로 원격 데스크톱을 건 적이 있다는 근거 하나가 됩니다.

### 증명하지 못하는 것

- **어느 컴퓨터의 화면인지.** 타일 머리에는 대상 호스트가 없습니다. 대상은 [원격 데스크톱 접속 기록](rdp-client-mru.md) 과 이벤트 로그로 맞춰 봅니다.
- **언제 본 화면인지.** 타일에는 시각이 없습니다. 아래 "시각 해석" 절을 봅니다.
- **어느 접속의 화면인지.** 한 캐시 파일에 여러 접속의 타일이 섞이는지, 새 접속 때 덮어쓰는지는 확인하지 못했습니다.
- **화면 전체 모습.** 타일은 조각일 뿐입니다. 캐시에 없는 부분은 알 수 없습니다.
- **키보드 앞의 사람.** 캐시 파일이 가리키는 것은 사용자 프로필(계정)입니다. 사람을 좁히는 방법은 [그 시각에 PC 를 쓴 사람이 누구인가](../../04-scenarios/activity/user-attribution.md) 에서 다룹니다.

보고서에는 "이 계정의 원격 데스크톱 비트맵 캐시에서 이 글자가 보이는 타일이 나왔다" 처럼 씁니다. "이 시각에 이 화면을 봤다" 로 쓰지 않습니다.

## 시각 해석

타일 머리에는 시각 칸이 없어서 시각은 캐시 파일의 파일 시스템 시각으로 잡습니다. 파일 시스템 시각은 [마스터 파일 테이블](../filesystem/mft.md) 에서 읽습니다.

- 캐시 파일의 만든 시각·수정 시각이 원격 데스크톱의 어떤 동작 때 바뀌는지는 확인하지 못했습니다.
- 그래서 파일 시각은 "이 무렵에 캐시 파일이 만들어졌거나 바뀌었다" 로만 씁니다.
- 접속 시각은 [원격 데스크톱 접속 기록](rdp-client-mru.md) 과 [원격 데스크톱 이벤트](../event-logs/rdp-event-logs/index.md) 로 맞춰 봅니다.
- 시각 값의 기준(UTC·현지)은 [시각 값 형식](../../01-foundations/value-decoding/filetime-unix-webkit-dos-ole.md) 에서 다룹니다.

## 함정과 한계

- **콜라주는 화면 복원이 아닙니다.** bmc-tools 의 콜라주가 원래 화면 배치를 되살린다고 적은 자료는 이번에 보지 못했습니다. 글자나 창을 읽으려면 타일을 직접 맞춰 봐야 합니다.
- **색이 어긋날 수 있습니다.** `.bmc` 는 데이터 길이로 색 형식을 정합니다. 뽑은 그림의 색이 이상하면 타일 머리를 헥스로 직접 읽어 봅니다.
- **캐시 파일이 없다고 원격 데스크톱을 쓰지 않은 것은 아닙니다.** 캐시를 만드는 조건(클라이언트 옵션 등)은 확인하지 못했습니다.
- **"old bitmap data" 는 따로 표시합니다.** `-o` 로 뽑은 조각이 무엇인지 확인하지 못했으므로, 일반 타일과 섞어 보고하지 않습니다.
- **지운 캐시 파일.** 사용자가 캐시 폴더를 지웠다면 [삭제 데이터 복구](../../03-techniques/analysis/data-recovery/index.md) 와 [섀도 복사본 활용](../../03-techniques/analysis/volume-shadow-copy-analysis.md) 으로 찾아봅니다.
  - `.bin` 은 머리 문자열 `RDP8bmp` 로 비할당 영역을 검색할 수 있습니다.
  - `.bmc` 에는 파일 머리가 없어서 머리 문자열로 찾을 수 없습니다.
  - 조작 흔적을 찾는 흐름은 [증거를 없애려 했나](../../04-scenarios/activity/anti-forensics/index.md) 에 있습니다.
- **어느 계정의 프로필인지 먼저 확인합니다.** [사용자 프로필 목록](../system-account/profilelist.md) 으로 프로필 폴더와 계정을 잇습니다.

## 직접 분석해 보기

### 헥스로 한 번

아래 바이트는 bmc-tools 소스 코드가 읽는 구조로 만든 예시입니다. 특정 검체에서 꺼낸 값이 아닙니다. key1·key2 는 읽는 순서를 보이려고 넣은 값입니다.

**.bin 파일 앞부분 (예시).**

```
오프셋  00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F
0x00    52 44 50 38 62 6D 70 00 vv vv vv vv 11 22 33 44
0x10    55 66 77 88 40 00 40 00 ...
```

1. 0x00~0x07 의 `52 44 50 38 62 6D 70 00` 은 ASCII 로 `RDP8bmp` 와 0x00 입니다.
2. 0x08~0x0B 는 버전입니다. 실제 파일에 어떤 값이 오는지 확인하지 못해 `vv` 로 비웠습니다.
3. 0x0C 부터 첫 타일 머리입니다. `11 22 33 44` 를 리틀 엔디언으로 읽으면 key1 = 0x44332211 입니다.
4. 0x10 의 `55 66 77 88` 은 key2 = 0x88776655 입니다.
5. 0x14 의 `40 00` 은 폭 0x0040 = 64, 0x16 의 `40 00` 은 높이 64 입니다.
6. 그 뒤가 32비트 BGRA 픽셀입니다.

**.bmc 타일 머리 (예시).**

```
오프셋  00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F
0x00    11 22 33 44 55 66 77 88 40 00 40 00 00 20 00 00
0x10    00 00 00 00 ...
```

1. 파일 머리가 없으므로 0x00 부터 타일 머리입니다.
2. key1 = 0x44332211, key2 = 0x88776655 입니다.
3. 폭과 높이는 모두 64 입니다.
4. 0x0C 의 `00 20 00 00` 은 데이터 길이 0x2000 = 8192 입니다.
5. 0x10 의 매개변수는 0 입니다. 0x08 비트가 꺼져 있으므로 압축하지 않은 타일입니다.
6. 8192 ÷ (64 × 64) = 2 이므로 RGB565(16비트) 타일로 읽습니다.
7. 매개변수가 `08 00 00 00` 이었다면 RLE 로 압축된 타일입니다.

### 공개 도구로 한 번

공개 도구 bmc-tools(ANSSI) 로 따라갑니다.

1. 사용자 프로필의 캐시 폴더를 사본으로 뜹니다. 파일마다 만든 시각·수정 시각을 먼저 적어 둡니다.
2. bmc-tools 에 캐시 파일과 출력 폴더를 주고 타일을 낱장 그림으로 뽑습니다.
3. `-b` 옵션을 더해 모든 타일을 한 장에 붙인 콜라주를 만듭니다. 한 줄 타일 수는 기본 64 이고 `-w` 로 바꿉니다.
4. 3.05 판 이상이면 `-o` 로 "old bitmap data" 도 뽑되, 결과를 따로 둡니다.
5. 글자·창·아이콘이 보이는 타일을 골라 파일 이름과 함께 기록합니다.
6. 타일 머리 한두 개를 헥스 편집기로 직접 읽어, 도구가 보여 준 폭·높이와 같은지 맞춰 봅니다.

## 실습

공개 검체(NIST CFReDS 등)에서 사용자 프로필의 `Terminal Server Client\Cache` 폴더를 꺼내 아래 질문을 풀어 봅니다.

1. 캐시 폴더가 있습니까? 파일은 `.bmc` 입니까, `.bin` 입니까?
2. `.bin` 파일이면 첫 8바이트가 `RDP8bmp` 와 0x00 입니까? 버전 칸의 값은 무엇입니까?
3. 첫 타일의 폭과 높이는 얼마입니까? 64×64 입니까?
4. `.bmc` 파일이면 첫 타일의 데이터 길이와 매개변수는 무엇입니까? 압축된 타일입니까? 색 형식은 무엇입니까?
5. bmc-tools 로 뽑은 타일 중 글자가 읽히는 타일이 있습니까? 그 글자가 MRU 의 대상 호스트와 이어집니까?
6. 캐시 파일의 만든 시각·수정 시각은 언제입니까? 같은 사용자의 MRU 키 LastWrite, mstsc 프리페치 실행 시각과 비교해 봅니다.
