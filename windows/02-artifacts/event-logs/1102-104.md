# 이벤트 로그 삭제 (1102·104)

보안 로그 (Security) 를 지우면 보안 로그에 1102 가 남습니다. 다른 로그를 지웠을 때 남는 104 는 매니페스트상 System 로그에 기록됩니다. 1102 에는 지운 계정의 SID 와 로그온 ID 가 있습니다. 104 에는 계정 이름과 지운 로그의 이름이 있고, SID 와 로그온 ID 는 없습니다. 1102 는 감사 정책을 따로 켜지 않아도 남습니다.

## 무엇을 기록하나 · 왜 생기나

| 이벤트 | 남는 때 | 남는 로그 | 알려 주는 것 |
|---|---|---|---|
| 1102 "The audit log was cleared." | 보안 감사 로그가 지워질 때마다 | Security | 지운 계정의 SID·이름·도메인·로그온 ID |
| 104 "The %3 log file was cleared." | 로그 파일이 지워질 때 | System (매니페스트 기준) | 지운 계정의 이름·도메인, 지운 로그 이름 |

1102 의 하위 범주는 기타 이벤트 (Other Events) 입니다. Other Events 의 이벤트는 자동으로 생기고 기본으로 켜져 있습니다[2]. 1102 는 평소에는 보이지 않아야 하는 이벤트이므로, 보이면 왜 지웠는지 조사합니다[1]. 104 의 메시지에서 `%3` 은 Channel 필드, 곧 지운 로그의 이름입니다. (Windows 11 25H2 매니페스트 기준)

로그를 지운 흔적을 찾고 누가 어디서 지웠는지 좁히는 순서는 [이벤트 로그를 지웠나](../../04-scenarios/activity/anti-forensics/log-clearing.md)에서 다룹니다. 이 페이지는 두 이벤트의 구조와 읽는 법을 다룹니다.

## 위치와 버전별 차이

### 공급자와 로그

| 항목 | 1102 | 104 |
|---|---|---|
| 공급자 (Provider) | Microsoft-Windows-Eventlog `{fc65ddd8-d6ef-4962-83d5-6e5cfe9ce148}` | Microsoft-Windows-Eventlog |
| 로그 (채널) | Security | System |
| 수준 | Microsoft 예시에서 Level 4 | Information |
| Task | Microsoft 예시에서 104 | "Log clear" |
| Keywords | Microsoft 예시에서 `0x4020000000000000` | 실제 기록으로 확인 |
| 최소 Windows | Windows Vista · Windows Server 2008 | 공개 자료 없음 |

1102 의 공급자는 보안 감사 공급자 (Microsoft-Windows-Security-Auditing) 가 아닙니다. 104 열의 값은 Windows 11 25H2 공급자 매니페스트 기준입니다.

매니페스트로 보면 Application 이나 다른 로그를 지워도 104 는 System 로그에 남는 구조입니다. 보안 로그를 지울 때 1102 와 함께 System 로그에도 104 가 남는지는 실제 기록으로 확인해야 합니다.

### 같은 하위 범주의 이벤트

Other Events 하위 범주의 이벤트는 다음과 같습니다[2].

| ID | 뜻 |
|---|---|
| 1100 | 이벤트 로그 서비스 종료 |
| 1102 | 감사 로그 지워짐 |
| 1104 | 보안 로그 가득 참 |
| 1105 | 이벤트 로그 자동 백업 |
| 1108 | 이벤트 처리 오류 |

매니페스트에는 세 이벤트의 모양이 더 있습니다 (Windows 11 25H2 기준).

- 1100 "The event logging service has shut down." 은 Security 채널에 남고 필드가 없습니다.
- 1104 "The security log is now full." 은 Security 채널에 수준 Error 로 남습니다.
- 1105 "Event log automatic backup" 은 Security 채널에 남고, 필드는 Channel 과 BackupPath 입니다.

### 이벤트 버전

| 이벤트 | 버전 | 필드 | 출처 |
|---|---|---|---|
| 1102 | 0 | SubjectUserSid, SubjectUserName, SubjectDomainName, SubjectLogonId | Microsoft 문서 |
| 1102 | 1 | 버전 0 의 필드 + ClientProcessId (UInt32), ClientProcessStartKey (UInt64) | 매니페스트 |
| 104 | 0 | SubjectUserName, SubjectDomainName, Channel, BackupPath | 매니페스트 |
| 104 | 1 | 버전 0 의 필드 + ClientProcessId, ClientProcessStartKey | 매니페스트 |

Microsoft 문서에는 1102 버전 0 만 있습니다[1]. 버전 1 이 어느 Windows 버전부터 쓰였는지는 공개 자료가 없습니다. 옛 로그 형식은 [구형 EVT 형식 (Windows XP·2003)](../../01-foundations/database-log-formats/evtx-evt-etl/windows-xp-2003.md)에서 다룹니다.

### 로그마다 다른 보관 기간

같은 PC 에서도 로그마다 남은 기간이 크게 다를 수 있습니다. Windows 11 25H2 에서 보안 로그를 최대 20,971,520바이트, 순환 (Circular) 으로 두면 약 2일치만 남을 수 있고, 같은 PC 의 System 로그에는 약 3개월치가 남을 수 있습니다. 로그 크기와 보관 방식을 확인하는 방법은 [감사 정책과 로그 설정](audit-policy-log-settings.md)에서 다룹니다.

## 구조

### 1102

1102 의 내용은 EventData 가 아니라 UserData 아래 `LogFileCleared` 요소에 들어 있습니다. 이 요소의 이름공간은 `http://manifests.microsoft.com/win/2004/08/windows/eventlog` 입니다.

아래는 Microsoft 문서 예시의 뼈대입니다. 필드 값은 비웠습니다.

```xml
<Provider Name="Microsoft-Windows-Eventlog" Guid="{fc65ddd8-d6ef-4962-83d5-6e5cfe9ce148}" />
<EventID>1102</EventID>
<Version>0</Version>
<Level>4</Level>
<Task>104</Task>
<Keywords>0x4020000000000000</Keywords>
<Channel>Security</Channel>
...
<UserData>
  <LogFileCleared xmlns="http://manifests.microsoft.com/win/2004/08/windows/eventlog">
    <SubjectUserSid>…</SubjectUserSid>
    <SubjectUserName>…</SubjectUserName>
    <SubjectDomainName>…</SubjectDomainName>
    <SubjectLogonId>…</SubjectLogonId>
  </LogFileCleared>
</UserData>
```

| 필드 | 뜻 | 읽을 때 주의 |
|---|---|---|
| SubjectUserSid · SubjectUserName · SubjectDomainName | 로그를 지운 계정 | 계정입니다. 사람이 아닙니다 |
| SubjectLogonId | 그 계정의 로그온 ID | 4624 의 Logon ID 와 이을 수 있습니다 |
| ClientProcessId · ClientProcessStartKey | 버전 1 에만 있는 필드 | 값의 쓰임은 실제 기록으로 확인합니다 |

### 104

| 필드 | 뜻 | 읽을 때 주의 |
|---|---|---|
| SubjectUserName · SubjectDomainName | 로그를 지운 계정 | SID 필드가 없습니다 |
| Channel | 지운 로그 이름 | 메시지의 `%3` 자리에 들어갑니다 |
| BackupPath | 공개 자료 없음 | 무엇이 들어가는지는 실제 기록으로 확인합니다 |
| ClientProcessId · ClientProcessStartKey | 버전 1 에만 있는 필드 | 값의 쓰임은 실제 기록으로 확인합니다 |

104 에는 SID 와 로그온 ID 필드가 없습니다. 그래서 1102 처럼 로그온 ID 로 4624 와 바로 이을 수 없습니다. (Windows 11 25H2 매니페스트 기준)

## 증거로서 의미

| 증명하는 것 | 증명하지 못하는 것 |
|---|---|
| 기록 시각에 보안 로그가 지워졌다는 것 (1102) | 지운 레코드에 무엇이 있었는지 |
| 지운 요청이 이 계정·로그온 세션에서 왔다는 것 (1102) | 그 계정 뒤에 있던 사람이 누구인지, 왜 지웠는지 |
| 이 계정 이름으로 이 로그가 지워졌다는 것 (104) | 어떤 수단(이벤트 뷰어, 명령줄 도구, PowerShell 등)으로 지웠는지. 1102·104 만으로 구분할 수 있는지는 공개 자료가 없습니다 |
| | 1102·104 가 없으니 로그를 건드리지 않았다는 것 |
| | 오래된 기록이 없으니 로그를 지웠다는 것 |

1102·104 를 남기지 않고 레코드를 없애는 경우가 있다는 설명이 있습니다. 순환 로그는 크기 한도에 이르면 오래된 기록부터 밀려나므로 오래된 기록이 없다는 것만으로 지웠다고 볼 수 없습니다. 순환 로그가 기록을 덮어쓸 때 따로 이벤트를 남기지 않는다는 설명도 있습니다.

### 보고서 문장

- 쓸 수 있는 문장: "보안 로그에 ○○(UTC) 의 1102 가 있습니다. Subject 는 ○○\○○ (SID ○○) 이고 로그온 ID 는 ○○ 입니다. 이 기록은 이 계정의 세션에서 보안 로그를 지웠음을 보여 줍니다. 지운 레코드의 내용과 지운 이유는 이 기록만으로 알 수 없습니다."
- 쓰면 안 되는 문장: "사용자 ○○가 범행 흔적을 없애려고 로그를 지웠다."

두 번째 문장은 기록에 없는 사람과 의도를 적습니다.

## 시각 해석

- 1102 의 기록 시각은 보안 로그를 지운 때입니다. 104 의 기록 시각은 Channel 의 로그를 지운 때입니다.
- 1102·104 는 지운 뒤 새 로그의 첫 기록으로 남는다는 설명이 있습니다. JPCERT/CC 시험에서는 104 가 로그 맨 앞에 남았습니다([이벤트 로그를 지웠나](../../04-scenarios/activity/anti-forensics/log-clearing.md) 참고).
- 지운 로그의 가장 오래된 기록 시각은 지운 시각 무렵일 가능성이 큽니다. 순환으로 밀려난 로그도 가장 오래된 기록이 최근일 수 있으니, 삭제 이벤트와 함께 봅니다.
- 레코드의 기록 시각을 저장하는 형식은 [이벤트 로그 형식](../../01-foundations/database-log-formats/evtx-evt-etl/index.md)에서 다룹니다.
- 여러 로그의 시각을 한 기준으로 맞추는 방법은 [시간대·시계 오차 보정](../../03-techniques/analysis/timeline/time-normalization.md)에서 다룹니다.

## 함정과 한계

1. **보안 로그를 공급자 Security-Auditing 으로만 거릅니다.** 1102 의 공급자는 Microsoft-Windows-Eventlog 입니다. 공급자 이름으로 거르면 1102 가 빠집니다.
2. **EventData 만 읽습니다.** 1102 의 필드는 UserData 아래에 있습니다. EventData 만 읽는 스크립트나 도구에서는 필드가 비어 보일 수 있습니다.
3. **1102 의 Task 값을 이벤트 ID 104 로 읽습니다.** Microsoft 예시 XML 에서 1102 의 Task 값은 104 입니다. 이벤트 ID 104 와는 다른 값입니다.
4. **104 를 지운 로그 안에서만 찾습니다.** 매니페스트상 104 는 System 로그에 남는 구조입니다. System 로그와 지운 로그를 모두 봅니다.
5. **1102 가 없으니 System 로그도 무사하다고 봅니다.** 1102 는 보안 로그를 지웠을 때의 기록입니다. 다른 로그를 지운 흔적은 104 로 따로 찾습니다.
6. **104 의 계정 이름만으로 사람을 정합니다.** 104 에는 SID 와 로그온 ID 가 없습니다. 같은 이름의 계정이 여러 도메인에 있을 수 있으니 도메인 필드를 함께 적습니다.
7. **1104·1105 를 삭제로 읽습니다.** 1104 는 보안 로그가 가득 찬 기록이고, 1105 는 자동 백업 기록입니다. 로그가 비었거나 짧아진 이유가 삭제가 아닐 수 있다는 단서가 됩니다.
8. **ClientProcessId 로 지운 프로그램을 안다고 봅니다.** 필드 이름으로 보면 버전 1 의 ClientProcessId 로 지운 프로세스를 찾을 수 있을 가능성이 있습니다. 실제 기록에서 4688 과 맞춰 확인한 뒤에 적습니다.
9. **EventRecordID 가 건너뛴 곳을 부분 삭제로 단정합니다.** 이 방법으로 부분 삭제를 찾는다는 설명이 있지만, 공개된 검증 자료는 없습니다.

### 지운 뒤에도 남는 것

- **파일 안의 옛 레코드.** 지우거나 덮어쓴 레코드가 .evtx 파일 안에 남아 있을 수 있습니다. [파일 안에 남은 지운·손상 레코드](../../01-foundations/database-log-formats/evtx-evt-etl/chunk-slack-corrupted-evtx.md)를 봅니다.
- **섀도 복사본 속 옛 로그 파일.** 지우기 전에 만든 섀도 복사본에 .evtx 사본이 있을 수 있습니다. [섀도 복사본 활용](../../03-techniques/analysis/volume-shadow-copy-analysis.md)을 봅니다.
- **지운 도구의 실행 흔적.** 보안 로그가 남아 있다면 [프로세스 생성 (4688)](4688.md)에, 그 밖에는 [프리페치](../execution/prefetch/index.md)에 남을 수 있습니다.

## 직접 분석해 보기

### 헥스로 한 번

이벤트 필드의 값은 이진 XML 의 치환 값으로 들어 있습니다. 값 종류 번호와 배열 구조는 [이진 XML 해석](../../01-foundations/database-log-formats/evtx-evt-etl/binary-xml-template.md)에서 다룹니다. 여기서는 값 데이터 두 개만 봅니다.

아래 바이트는 명세로 만든 예시입니다. 실제 기록에서 나온 값이 아닙니다.

**1) 104 의 Channel 필드**

Application 로그를 지운 104 라고 하겠습니다. Channel 값이 UTF-16 문자열로 들어 있다고 보고 만든 예시입니다. 값 종류는 실제 기록으로 확인합니다.

```
41 00 70 00 70 00 6C 00 69 00 63 00 61 00 74 00 69 00 6F 00 6E 00
A     p     p     l     i     c     a     t     i     o     n
```

1. 한 글자가 2바이트입니다. 영문자는 뒤 바이트가 `00` 입니다.
2. 11글자이므로 22바이트입니다.
3. 이 값이 메시지의 `%3` 자리에 들어가 "The Application log file was cleared." 로 보입니다.

**2) 1102 버전 1 의 ClientProcessId**

매니페스트에서 이 필드는 UInt32 입니다. 값이 3,900 이라면 값 데이터는 4바이트입니다.

```
3C 0F 00 00
```

1. 리틀 엔디언으로 읽으면 0x00000F3C 입니다.
2. 0x0F3C 는 10진으로 3,900 입니다.
3. 4688 의 PID 는 16진으로 적힙니다. 같은 PID 의 4688 을 찾으려면 `0xf3c` 로 찾습니다.
4. 같은 PID 가 여러 번 나오면 1102 보다 앞선 기록 가운데 가장 가까운 것을 먼저 봅니다.

> 그림 자리: 1102 레코드의 UserData 구조와, ClientProcessId 4바이트를 16진 PID 로 바꿔 4688 의 New Process ID 와 잇는 흐름

### 공개 도구로 한 번

Windows 에 들어 있는 이벤트 뷰어와 PowerShell 의 `Get-WinEvent` 로 볼 수 있습니다. 분석 PC 로 옮긴 파일은 `Path` 로 엽니다. 아래 `E:\case\` 는 예시 경로입니다.

```powershell
# 보안 로그의 1102 와 그 칸 (UserData 아래)
$e = Get-WinEvent -FilterHashtable @{ Path = 'E:\case\Security.evtx'; ProviderName = 'Microsoft-Windows-Eventlog'; Id = 1102 }
$e | ForEach-Object { ([xml]$_.ToXml()).Event.UserData.LogFileCleared }

# System 로그의 104 와 지운 로그 이름
Get-WinEvent -FilterHashtable @{ Path = 'E:\case\System.evtx'; ProviderName = 'Microsoft-Windows-Eventlog'; Id = 104 } |
  ForEach-Object { $_.TimeCreated; $_.Message }

# 로그마다 가장 오래된 기록
Get-WinEvent -Path 'E:\case\Security.evtx' -Oldest -MaxEvents 1 | Select-Object TimeCreated, Id, RecordId
```

라이브 시스템에서는 `Get-WinEvent -ListLog Security, System | Select-Object LogName, LogMode, MaximumSizeInBytes, RecordCount` 로 보관 방식과 크기를 봅니다. 필드 구성은 `(Get-WinEvent -ListProvider Microsoft-Windows-Eventlog).Events | Where-Object Id -in 104, 1102` 로 확인합니다. 이 명령은 분석 PC 의 매니페스트를 읽습니다.

도구가 1102 의 UserData 필드를 보여 주는지 확인합니다. 레코드 한두 개는 XML 원문과 맞춰 봅니다. 방법은 [도구 결과 교차 검증](../../03-techniques/reporting/tool-validation.md)에서 다룹니다.

## 실습

**직접 만든 Windows 10·11 가상 머신**에서 해 봅니다. 각 단계의 시각을 적어 둡니다.

1. `Get-WinEvent -ListLog` 로 Security·System·Application 로그의 크기, 보관 방식, 가장 오래된 기록 시각을 적어 둡니다.
2. 이벤트 뷰어에서 Application 로그를 지웁니다. 104 가 System 로그에 남는지, Application 로그에도 남는지 봅니다. Channel 필드 값을 적습니다.
3. 이벤트 뷰어에서 보안 로그를 지웁니다. 1102 의 버전과 필드를 봅니다. System 로그에 104 도 남는지 봅니다.
4. 1102·104 가 지운 로그의 첫 기록인지 봅니다. EventRecordID 가 어떻게 바뀌는지도 적습니다.
5. 4688 을 켜 두었다면 1102 버전 1 의 ClientProcessId 를 16진으로 바꿔 4688 과 맞춥니다.
6. 명령줄 도구나 PowerShell 로 한 번 더 지워 봅니다. 수단마다 1102·104 의 필드 값이 다른지 비교합니다.

**NIST CFReDS 같은 공개 데이터**에서는 다음을 풀어 봅니다.

1. 보안 로그에 1102 가 있습니까? 있다면 SubjectLogonId 로 4624 를 찾습니다.
2. System 로그에 104 가 있습니까? Channel 필드에 어떤 로그 이름이 있습니까?
3. 로그마다 가장 오래된 기록 시각을 비교합니다. 유독 최근부터 시작하는 로그가 있습니까? 그 이유가 삭제인지 순환인지 무엇으로 구분하겠습니까?
