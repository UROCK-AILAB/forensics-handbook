# 공유 폴더 접근 (5140·5145)

## 한 줄 요약

5140 은 네트워크 공유에 접근한 기록입니다. 5145 는 공유 안의 파일·폴더에 요청한 권한을 줄 수 있는지 검사한 기록입니다. 두 이벤트 모두 공유를 연 컴퓨터의 보안 로그에 남습니다. 접속한 PC 에는 남지 않습니다. 5140 은 파일 공유 감사, 5145 는 세부 파일 공유 감사 하위 범주를 켜야 남습니다. 조사한 PC 에서는 둘 다 꺼져 있었습니다. 시각은 UTC 입니다.

## 무엇을 기록하나 · 왜 생기나

### 5140 — 공유에 접근했다

- 제목은 "5140(S, F) A network share object was accessed." 입니다.
- 하위 범주는 파일 공유 감사 (Audit File Share) 입니다.
- Microsoft 문서의 설명에는 두 문장이 함께 있습니다. 하나는 "공유 개체에 접근할 때마다 생긴다" 이고, 다른 하나는 "세션마다 한 번, 처음 접근을 시도할 때 생긴다" 입니다. 두 문장이 서로 맞지 않습니다.
- Subject 칸은 공유 접근을 요청한 계정입니다.
- Access Mask 는 이 이벤트에서 늘 `0x1` 이고, Accesses 는 늘 "ReadData (or ListDirectory)" 입니다. 그래서 5140 만으로는 읽었는지 썼는지 알 수 없습니다.

### 5145 — 파일·폴더 권한을 검사했다

- 제목은 "5145(S, F) A network share object was checked to see whether client can be granted desired access." 입니다.
- 하위 범주는 세부 파일 공유 감사 (Audit Detailed File Share) 입니다.
- 공유 안의 파일·폴더에 접근할 때마다 생깁니다.
- 실패 이벤트는 공유 수준에서 거부됐을 때만 생깁니다.
- NTFS 권한에서 거부되면 이벤트가 생기지 않습니다.
- 한 파일을 열 때 5145 가 몇 건 남는지는 확인하지 못했습니다.

### 어느 컴퓨터에 남나

- Microsoft 예시에서 이벤트의 Computer 는 공유를 연 쪽(DC01)입니다.
- Source Address 칸에는 접속한 쪽의 IP 주소가 들어갑니다.
- 곧 두 이벤트는 공유를 연 서버에 남습니다. 접속한 PC 쪽 흔적은 따로 찾습니다.

### 같은 공급자의 공유 관리 이벤트

같은 공급자에는 공유 자체를 바꾼 기록도 있습니다. 칸 이름은 공급자 템플릿에서 읽었습니다 (확인 범위: Win11 25H2 한 대).

| ID | 뜻 | 주요 칸 |
|---|---|---|
| 5142 | 공유 추가 | ShareName, ShareLocalPath |
| 5143 | 공유 수정 | OldRemark/NewRemark, OldMaxUsers/NewMaxUsers, OldShareFlags/NewShareFlags, OldSD/NewSD |
| 5144 | 공유 삭제 | |
| 5168 | SMB 용 SPN 확인 실패 | |

각 이벤트가 어느 감사 설정에서 남는지는 확인하지 못했습니다.

### 이벤트 버전

| 이벤트 | 버전 | 내용 |
|---|---|---|
| 5140 | 0 | 문서의 "Event Versions" 는 "0 - Windows Server 2008, Windows Vista" 하나만 적습니다 |
| 5140 | 1 | 문서의 예시 XML 은 버전 1 입니다. 공급자 템플릿에서는 ObjectType, ShareLocalPath, AccessMask, AccessList 가 더해집니다 |
| 5145 | 0 | 문서와 예시 XML 모두 버전 0 입니다 |

- 5140 은 문서의 버전 목록과 예시 XML 이 서로 맞지 않습니다.
- 5140 의 버전별 칸은 공급자 템플릿에서 읽었습니다 (확인 범위: Win11 25H2 한 대).

### 감사 설정

조사한 PC 의 설정입니다 (확인 범위: Win11 25H2 한 대).

| 하위 범주 | GUID | 설정 |
|---|---|---|
| 파일 공유 감사 (Audit File Share) | `{0CCE9224-69AE-11D9-BED3-505054503030}` | No Auditing |
| 세부 파일 공유 감사 (Audit Detailed File Share) | `{0CCE9244-69AE-11D9-BED3-505054503030}` | No Auditing |

- 이 PC 의 보안 로그에는 5140 과 5145 가 한 건도 없었습니다.
- 한국어 Windows 에서는 `auditpol /subcategory:"File Share"` 처럼 영어 이름을 쓰면 오류(0x57)가 났습니다. GUID 로 불러야 했습니다.
- Microsoft 가 정한 기본 감사 설정이 워크스테이션·서버·도메인 컨트롤러마다 어떤지는 확인하지 못했습니다.
- 오프라인 이미지에서 감사 설정을 읽는 법은 [감사 정책과 로그 설정](audit-policy-log-settings.md)에서 다룹니다.

### 칸의 뜻

| 칸 | 뜻 |
|---|---|
| Subject… | 공유 접근을 요청한 계정입니다. SubjectLogonId 로 같은 로그온 ID 의 4624 와 이을 수 있습니다 |
| ObjectType | 5140 에서는 늘 "File" 입니다 |
| IpAddress (Source Address) | 접근한 쪽의 IP 주소입니다. IPv6 또는 `::ffff:IPv4` 모양입니다. `::1` 과 `127.0.0.1` 은 자기 컴퓨터입니다 |
| IpPort (Source Port) | 접근한 쪽의 포트입니다. 로컬 접근이면 0 입니다 |
| ShareName | `\\*\공유이름` 모양입니다 |
| ShareLocalPath (Share Path) | `\??\경로` 모양입니다. `\\*\IPC$` 처럼 비어 있는 경우가 있습니다 |
| RelativeTargetName | 공유를 기준으로 한 상대 경로입니다. 공유 자체에 접근하면 `\` 입니다 |
| AccessMask | 요청한 권한 값의 합입니다. 5140 에서는 늘 `0x1` 입니다 |
| AccessList | 요청한 권한을 `%%n` 코드로 적습니다 |
| AccessReason (Access Check Results) | 요청한 권한마다 결과(Granted by / Denied by)와 허용·거부한 ACE 를 적습니다. ACE 는 SDDL 형식입니다 |

### Microsoft 예시 값

| 칸 | 5140 | 5145 |
|---|---|---|
| ObjectType | File | |
| IpAddress | `10.0.0.100` | `fe80::31ea:6c3c:f40d:1973` |
| IpPort | `49212` | `56926` |
| ShareName | `\\*\Documents` | `\\*\Documents` |
| ShareLocalPath | `\??\C:\Documents` | `\??\C:\Documents` |
| RelativeTargetName | | `Bginfo.exe` |
| AccessMask | `0x1` | `0x100081` |
| AccessList | `%%4416` | `%%1541 %%4416 %%4423` |
| AccessReason | | `%%1541: %%1801 D:(A;;FA;;;WD) %%4416: %%1801 D:(A;;FA;;;WD) %%4423: %%1801 D:(A;;FA;;;WD)` |

두 예시는 서로 다른 문서에서 왔습니다. 한 번의 접속에서 나온 기록이 아닙니다.

### 권한 코드

- AccessList 의 `%%n` 코드와 AccessMask 의 16진 값은 파일 개체의 접근 권한 표를 따릅니다. 5145 문서에 실린 표는 [파일 접근 감사](4656-4663-4660.md)의 접근 권한 표와 값이 같습니다. 표는 그 페이지에서 봅니다.
- `%%n` 을 문장으로 푸는 방법은 [이벤트 로그 형식](../../01-foundations/database-log-formats/evtx-evt-etl/index.md)에서 다룹니다.
- AccessReason 의 `%%1801` 이 "Granted" 를 뜻하는지는 확인하지 못했습니다. 문서는 형식만 적고 이 코드를 풀지 않습니다.

## 증거로서 의미

| 증명하는 것 | 증명하지 못하는 것 |
|---|---|
| 기록된 시각에 이 계정이 이 IP 주소에서 이 공유에 접근했습니다 (5140) | 공유 안에서 무엇을 읽거나 썼는지. 5140 의 AccessMask 는 늘 `0x1` 입니다 |
| 이 계정이 공유 안의 이 상대 경로에 이런 권한을 요청했습니다 (5145) | 실제로 몇 바이트를 읽고 썼는지. 5145 는 요청한 권한만 적습니다 |
| 공유 수준 검사의 결과와 근거 ACE (5145 의 AccessReason) | NTFS 권한에서 거부된 시도. 이 경우 이벤트가 생기지 않습니다 |
| 접속한 쪽의 IP 주소와 포트 | 접속한 PC 에서 누가 조작했는지 |
| | 기록이 없으니 접근도 없었다는 것. 감사 설정이 꺼져 있을 수 있습니다 |

### 보고서 문장

아래 시각과 주소는 설명을 위해 만든 예입니다.

- 쓸 수 있는 문장: "서버 ○○ 의 보안 로그에는 <시각> UTC 에 5145 가 있습니다. 계정 ○○ (로그온 ID ○○) 이 `10.0.0.100` 에서 공유 `\\*\Documents` 안의 `Bginfo.exe` 에 SYNCHRONIZE, ReadAttributes, ReadData 권한을 요청했습니다."
- 쓰면 안 되는 문장: "○○ 이 서버에서 Bginfo.exe 를 복사해 갔다."

두 번째 문장은 사람과 결과를 단정합니다. 이벤트에는 계정과 주소와 요청한 권한만 있습니다.

## 시각 해석

- 이벤트 시각은 `<TimeCreated SystemTime>` 에 들어 있습니다. 끝에 Z 가 붙은 UTC 값입니다.
- 5140 시각은 그 세션에서 공유에 처음 접근한 시각일 수 있습니다. 문서 설명이 엇갈리므로, 5140 개수를 접근 횟수로 세지 않습니다.
- 5145 시각은 파일·폴더마다 권한을 검사한 시각입니다.
- 이 기록은 서버의 시계로 남습니다. 접속한 PC 의 기록과 맞출 때는 두 컴퓨터의 시각이 어긋나지 않았는지 먼저 봅니다. 시각이 바뀐 기록은 [시간 변경](4616-kernel-general.md)에서 찾습니다.
- 현지 시각으로 바꿀 때는 서버의 [시간대 설정](../system-account/time-zone.md)을 씁니다.

## 함정과 한계

1. **접속한 PC 에서 5140 을 찾습니다.** 5140·5145 는 공유를 연 쪽에 남습니다.
2. **5140 으로 읽기와 쓰기를 가립니다.** 5140 의 AccessMask 는 늘 `0x1` 입니다. 요청한 권한은 5145 에서 봅니다.
3. **5140 개수를 접근 횟수로 셉니다.** 문서가 "접근할 때마다" 와 "세션마다 한 번" 을 함께 적습니다.
4. **5145 실패가 없으니 거부도 없었다고 봅니다.** NTFS 권한에서 거부되면 이벤트가 생기지 않습니다.
5. **AccessMask 를 실제 동작으로 읽습니다.** 5145 는 요청한 권한을 적습니다. 요청한 권한이 무엇을 하려 했는지는 보여 주지만, 끝까지 했는지는 보여 주지 않습니다.
6. **`::1`·`127.0.0.1` 을 원격 접속으로 읽습니다.** 자기 컴퓨터에서 접근한 기록입니다. 이때 IpPort 는 0 입니다.
7. **Share Path 가 비었다고 레코드가 깨졌다고 봅니다.** `\\*\IPC$` 처럼 비어 있는 경우가 있습니다.
8. **기본으로 남는다고 봅니다.** 조사한 PC 에서는 두 하위 범주가 모두 꺼져 있었고 이벤트가 0건이었습니다.
9. **5140 버전 0 에서 Share Path 를 찾습니다.** 버전 0 에는 ShareLocalPath·AccessMask·AccessList 칸이 없습니다.
10. **한국어 Windows 에서 영어 하위 범주 이름으로 설정을 봅니다.** 조사한 PC 에서는 오류가 났습니다. GUID 로 확인합니다.

### 지우기와 조작

- **보안 로그를 지웁니다.** 지운 기록은 [이벤트 로그 삭제](1102-104.md)에서 찾습니다.
- **감사 설정을 끕니다.** 하위 범주를 끄면 그 뒤로는 기록이 남지 않습니다. 설정이 언제 바뀌었는지는 [감사 정책과 로그 설정](audit-policy-log-settings.md)에서 다룹니다.
- **공유를 만들었다가 지웁니다.** 5142(추가)·5143(수정)·5144(삭제)를 찾아봅니다.

Microsoft 문서는 이렇게 지켜보라고 권합니다.

- 5140: 중요한 컴퓨터의 공유(예: 도메인 컨트롤러의 `C$`) 접근을 봅니다.
- 5140: 내부 주소 대역 밖의 Source Address 와, 그 컴퓨터에 붙으면 안 되는 주소를 봅니다.
- 5145: 쓰기 쪽 권한(WriteData, AppendData, WriteEA, DeleteChild, WriteAttributes, DELETE, WRITE_DAC, WRITE_OWNER)을 특히 실패 쪽으로 봅니다.
- 5145: 중요한 공유는 Share Name 과 Relative Target Name 으로 봅니다.

## 직접 분석해 보기

### AccessMask 풀기

5145 예시의 `0x100081` 을 권한 값으로 나누면 AccessList 의 세 코드와 하나씩 맞습니다.

```
0x100000  SYNCHRONIZE      %%1541
0x000080  ReadAttributes   %%4423
0x000001  ReadData         %%4416
--------
0x100081
```

도구가 권한 이름만 보여 줄 때는 AccessMask 를 직접 풀어 도구의 풀이와 맞춰 봅니다. 값을 헥스에서 읽는 법은 [파일 접근 감사](4656-4663-4660.md)의 "헥스로 한 번" 과 같습니다.

### 헥스로 한 번

로그 파일 안의 문자열은 UTF-16LE 로 들어 있습니다. 그래서 파일 이름이나 공유 이름을 UTF-16LE 바이트로 바꿔 보안 로그 사본 전체를 찾을 수 있습니다.

아래는 Microsoft 예시의 값을 형식대로 옮긴 예시입니다. 검체에서 뽑은 바이트가 아닙니다.

```
"Bginfo.exe"  →  42 00 67 00 69 00 6E 00 66 00 6F 00 2E 00 65 00 78 00 65 00
"IPC$"        →  49 00 50 00 43 00 24 00
```

1. 서버의 보안 로그 사본을 헥스 편집기로 엽니다.
2. 찾는 파일 이름을 UTF-16LE 바이트로 바꿔 찾습니다.
3. 찾은 자리 근처에서 ShareName(`\\*\…`)과 IP 주소 문자열을 읽습니다.
4. 도구 결과에 없는 자리에서 나왔다면, [이벤트 로그 형식](../../01-foundations/database-log-formats/evtx-evt-etl/index.md)에서 설명하는 구조로 그 자리가 레코드인지 확인합니다.

인코딩 자체는 [문자 인코딩](../../01-foundations/value-decoding/utf-16le-utf-8-cp949.md)에서 다룹니다.

### 공개 도구로 한 번

Windows 에 들어 있는 PowerShell 로 보안 로그 사본에서 두 이벤트를 뽑을 수 있습니다.

```powershell
Get-WinEvent -Path .\Security.evtx -FilterXPath "*[System[(EventID=5140 or EventID=5145)]]" -Oldest |
  ForEach-Object {
    $d = @{}
    ([xml]$_.ToXml()).Event.EventData.Data | ForEach-Object { $d[$_.Name] = $_.'#text' }
    [pscustomobject]@{
      TimeUtc    = $_.TimeCreated.ToUniversalTime()
      EventId    = $_.Id
      Account    = "$($d['SubjectDomainName'])\$($d['SubjectUserName'])"
      LogonId    = $d['SubjectLogonId']
      Ip         = $d['IpAddress']
      Share      = $d['ShareName']
      Target     = $d['RelativeTargetName']
      AccessMask = $d['AccessMask']
    }
  } | Sort-Object LogonId, TimeUtc | Format-Table
```

- 결과를 LogonId 로 묶으면 한 세션에서 어느 공유의 어느 파일에 무슨 권한을 요청했는지 늘어놓을 수 있습니다.
- 라이브 시스템에서는 auditpol 로 하위 범주 설정을 봅니다. 한국어 Windows 에서는 GUID 로 부릅니다.
- EvtxECmd 같은 공개 도구도 이 칸들을 뽑아 줍니다. 도구가 `%%n` 을 권한 이름으로 바꿔 보여 주면 XML 원문 한두 건과 맞춰 봅니다. 방법은 [도구 결과 교차 검증](../../03-techniques/reporting/tool-validation.md)에서 다룹니다.

| 함께 볼 기록 | 무엇을 맞춰 보나 | 링크 |
|---|---|---|
| 로그온 이벤트 | SubjectLogonId 가 가리키는 로그온 세션과 접속한 주소 | [로그온·로그오프](logon-events/index.md) |
| 파일 접근 감사 | 서버의 파일에 SACL 이 있을 때 남는 4656·4663 | [파일 접근 감사](4656-4663-4660.md) |
| 공유 폴더·네트워크 드라이브 | 접속한 PC 쪽에 남은 연결 흔적 | [공유 폴더·네트워크 드라이브](../network/network-shares-mapped-drives.md) |
| 감사 정책 | 그 시기에 두 하위 범주가 켜져 있었는지 | [감사 정책과 로그 설정](audit-policy-log-settings.md) |

SMB 로그에서 볼 후보도 있습니다. 조사한 PC 에서 본 것입니다 (확인 범위: Win11 25H2 한 대).

- 서버 쪽 Microsoft-Windows-SMBServer/Operational 에는 엔드포인트·설정 이벤트(1010·1011·1025·1027·1033·1034·1040 등)만 있었습니다. 개별 접근 기록은 없었습니다. SMBServer/Security 와 SMBServer/Audit 은 0건이었습니다.
- SMB 서버 공급자에는 감사 정책과 따로 쓰는 이벤트 템플릿이 있습니다. 551 "SMB Session Authentication Failure", 1006 "The share denied access to the client.", 1007 "The share denied anonymous access to the client.", 1020 "File system operation has taken longer than expected." 입니다. 어느 채널에 남는지, 기본으로 남는지는 확인하지 못했습니다.
- 접속한 PC 쪽 Microsoft-Windows-SmbClient/Connectivity 에는 30803(연결 실패), 30804(연결 끊김), 30805(세션 잃음), 30806(세션 다시 맺음) 템플릿이 있습니다. 칸에는 ServerName 과 Address 가 있습니다. 어느 서버에 붙었는지 볼 수 있는 후보입니다.
- 조사한 PC 의 Connectivity 로그에는 30810·30811·30812·30813·30830·30833 이 있었습니다. 각 ID 의 뜻은 확인하지 못했습니다.

관리 공유(`ADMIN$`·`IPC$`)를 거친 원격 실행 흔적은 [계정 탈취와 측면 이동](../../04-scenarios/incident/credential-theft-lateral-movement/index.md)에서, 공유로 자료를 옮긴 흔적은 [자료를 밖으로 빼돌렸나](../../04-scenarios/exfiltration/data-exfiltration/index.md)에서 다룹니다.

## 실습

직접 만든 Windows 가상 머신 두 대로 해 봅니다. 한 대는 공유를 열고, 다른 한 대는 접속합니다. 공유를 연 쪽에서 두 하위 범주의 성공·실패 감사를 GUID 로 켭니다. 각 단계의 시각을 UTC 로 적어 둡니다.

1. 감사를 켜기 전에 공유의 파일을 엽니다. 5140·5145 가 남는지 보십시오.
2. 감사를 켠 뒤 공유의 파일 하나를 엽니다. 5140 과 5145 가 몇 건씩 남는지 세어 보십시오. "한 파일에 5145 가 몇 건" 이라는 확인하지 못한 부분이 여기서 풀립니다.
3. 같은 세션에서 다른 파일을 엽니다. 5140 이 다시 남는지 보십시오. 문서의 엇갈린 설명 가운데 어느 쪽이 맞는지 알 수 있습니다.
4. 파일을 고쳐 저장합니다. 5145 의 AccessMask 를 풀어 2번과 비교하십시오.
5. 공유 권한으로 쓰기를 막은 경우와 NTFS 권한으로 쓰기를 막은 경우를 비교하십시오. 실패 5145 가 어느 쪽에서만 남는지 확인하십시오.
6. 접속한 PC 의 SmbClient/Connectivity 로그를 보십시오. 서버 이름이 남는 이벤트가 있는지 확인하십시오.

NIST CFReDS 같은 공개 검체에서 서버의 보안 로그를 꺼냈다면, 먼저 5140·5145 가 한 건이라도 있는지 봅니다. 없다면 감사 설정이 꺼져 있었는지부터 확인하십시오.
