# 파일 접근 감사 (4656·4663·4660)

## 한 줄 요약

4656 은 파일에 어떤 권한을 달라고 요청한 기록입니다. 4663 은 그 권한을 실제로 쓴 기록입니다. 4660 은 개체를 지운 기록입니다. 세 이벤트 모두 보안 로그 (Security) 에 남습니다. 감사 정책의 하위 범주를 켜고, 파일에도 감사 설정을 걸어야 남습니다. 둘 중 하나라도 없으면 기록이 없습니다. 시각은 UTC 입니다.

## 무엇을 기록하나 · 왜 생기나

### 두 가지 설정이 모두 있어야 남는다

파일 시스템 감사 (Audit File System) 는 고급 감사 정책 (Advanced Audit Policy) 의 하위 범주입니다. 사용자가 파일 시스템 개체에 접근하려 할 때 감사 이벤트를 만들지 이 하위 범주가 정합니다.

하위 범주를 켜는 것만으로는 부족합니다. 감사 이벤트는 개체에 시스템 액세스 제어 목록 (SACL) 이 걸려 있을 때만 생깁니다. 요청한 접근 종류(읽기·쓰기·수정 등)와 요청한 계정도 SACL 설정과 맞아야 합니다.

- 기본 파일 시스템 SACL 로는 감사 이벤트가 생기지 않습니다.
- 성공 감사를 켜면, SACL 이 맞는 개체에 성공한 접근마다 기록합니다.
- 실패 감사를 켜면, 실패한 시도마다 기록합니다.
- 이벤트 양은 SACL 을 어떻게 걸었느냐에 따라 달라집니다.

곧 "하위 범주 켜기" 와 "개체 SACL" 두 가지가 모두 있어야 이 페이지의 이벤트가 남습니다.

### 세 이벤트가 말하는 것

| 이벤트 | 제목 | 성공·실패 | 뜻 |
|---|---|---|---|
| 4656 | A handle to an object was requested. | 성공, 실패 | 개체에 어떤 접근을 요청했고 그 결과가 무엇이었는지 적습니다. 접근이 거부되면 실패 이벤트가 생깁니다 |
| 4663 | An attempt was made to access an object. | 성공만 | 개체에 어떤 작업을 실제로 했는지 적습니다. 권한을 "요청" 한 기록이 아니라 "사용" 한 기록입니다 |
| 4660 | An object was deleted. | 성공만 | 개체를 지웠다는 기록입니다 |

Microsoft 문서는 4656 이 요청과 그 결과만 보여 준다고 적습니다. 작업을 실제로 했는지는 4663 을 보라고 합니다.

### 같은 하위 범주의 다른 이벤트

파일 시스템 감사에 속한 이벤트는 여덟 개입니다.

| 이벤트 | 성공·실패 | 내용 |
|---|---|---|
| 4656 | 성공, 실패 | 핸들 (handle) 요청 |
| 4658 | 성공 | 핸들 닫힘 |
| 4660 | 성공 | 개체 삭제 |
| 4663 | 성공 | 개체 접근 시도 |
| 4664 | 성공 | 하드 링크를 만들려는 시도 |
| 4985 | 성공 | 트랜잭션 상태 변경 |
| 5051 | - | 파일 가상화 |
| 4670 | 성공 | 개체 권한 변경 |

- 이 가운데 4658 만 따로 핸들 조작 감사 (Audit Handle Manipulation) 하위 범주의 성공 감사를 켜야 생깁니다.
- 나머지는 다른 설정 없이 생깁니다.

### 어느 하위 범주에서 나왔나

같은 이벤트 ID 가 여러 하위 범주에서 나옵니다.

| 이벤트 | 파일 시스템 | 커널 개체 | 레지스트리 | 이동식 저장소 |
|---|---|---|---|---|
| 4656 | ○ | ○ | ○ | ○ |
| 4663 | ○ | ○ | ○ | ○ |
| 4660 | ○ | ○ | ○ | |

4660 의 하위 범주 목록에는 이동식 저장소 감사 (Audit Removable Storage) 가 없습니다.

레코드의 Task 값으로 하위 범주를 가를 수 있습니다. Microsoft 예시 XML 은 4656·4663·4660 모두 파일 예시이고, Task 가 모두 12800 입니다. 공급자 메타데이터의 Task 값은 아래와 같았습니다 (확인 범위: Win11 25H2 한 대).

| Task | 하위 범주 |
|---|---|
| 12800 | 파일 시스템 (File System) |
| 12801 | 레지스트리 (Registry) |
| 12802 | 커널 개체 (Kernel Object) |
| 12807 | 핸들 조작 (Handle Manipulation) |
| 12812 | 이동식 저장소 (Removable Storage) |

이동식 저장소에서 나온 실제 4663 레코드의 Task 가 12812 인지는 확인하지 못했습니다.

### 감사 설정의 기본값과 권장값

- Microsoft 권장 표는 도메인 컨트롤러·구성원 서버·워크스테이션 모두 성공·실패를 "조건부 (IF)" 로 적습니다.
- 같은 문서는 쓸 계획 없이 켜지 말라고 합니다. 효과 없는 SACL 은 지우라고 합니다.
- 조사에 쓴 PC 에서는 개체 액세스 범주의 하위 범주 14개가 모두 "No Auditing" 이었습니다. 파일 시스템 하위 범주(`{0CCE921D-69AE-11D9-BED3-505054503030}`)도 꺼져 있었습니다 (확인 범위: Win11 25H2 한 대).
- 이 PC 의 auditpol 출력에서는 하위 범주 이름이 깨져 보였습니다. 그래서 GUID 로 확인했습니다.
- 가정용 PC 의 기본값이 모두 꺼짐인지는 확인하지 못했습니다.

오프라인 이미지에서 감사 정책을 읽는 방법은 [감사 정책과 로그 설정](/02-artifacts/event-logs/audit-policy-log-settings.md)에서 다룹니다.

### 칸의 뜻

| 칸 | 뜻 |
|---|---|
| Subject… | 접근을 요청한 계정입니다. SubjectLogonId 는 4624 의 같은 로그온 ID 와 이을 수 있습니다 |
| ObjectServer | 이 이벤트에서는 "Security" 입니다 |
| ObjectType | 개체 종류입니다. 흔한 값은 File, Key, Directory, Process, Token, Device, Mutant 등입니다 |
| ObjectName | 개체 이름입니다. 파일이면 경로가 들어갑니다 |
| HandleId | 개체 핸들의 16진 값입니다. 잡히지 않으면 `0x0` 입니다 |
| TransactionId | 트랜잭션 GUID 입니다. 잡히지 않으면 `{00000000-0000-0000-0000-000000000000}` 입니다 |
| AccessList | 요청했거나 쓴 접근 권한의 목록입니다. 개체 종류에 따라 권한이 다릅니다 |
| AccessReason | 권한마다 접근 검사의 결과를 적습니다. 개체마다 형식이 다릅니다. 커널 개체에는 해당하지 않습니다 |
| AccessMask | 권한 값의 합입니다 |
| PrivilegeList | 접근 검사에 쓴 사용자 권한입니다(예: SeBackupPrivilege). 잡히지 않으면 `-` 입니다 |
| RestrictedSidCount | 토큰 안 제한 SID 의 개수입니다. 일부 개체 종류에만 해당합니다 |
| ProcessId | 접근을 요청한 프로세스의 ID 입니다. 16진으로 적힙니다 |
| ProcessName | 그 프로세스의 실행 파일 경로입니다 |

- Microsoft 의 4656 예시에서는 AccessReason 이 `%%4418: %%1802 D:(D;;LC;;;S-1-5-21-…-1104)` 처럼 적혔습니다. 권한마다 결과 코드와 근거가 된 ACE 가 붙습니다. ACE 는 SDDL 형식입니다.
- `%%1801`~`%%1811` 같은 결과 코드의 뜻은 확인하지 못했습니다.
- `%%n` 을 문장으로 푸는 방법은 [공급자와 메시지 파일](/01-foundations/database-log-formats/evtx-evt-etl/provider-message-table.md)에서 다룹니다.

### 접근 권한 표

AccessList 에는 권한 이름 대신 `%%n` 코드가 들어갑니다. AccessMask 에는 아래 16진 값의 합이 들어갑니다.

| 권한 | 값 | XML 코드 | 레지스트리에서의 뜻 |
|---|---|---|---|
| ReadData (ListDirectory) | 0x1 | `%%4416` | Query key value |
| WriteData (AddFile) | 0x2 | `%%4417` | Set key value |
| AppendData (AddSubdirectory · CreatePipeInstance) | 0x4 | `%%4418` | |
| ReadEA | 0x8 | `%%4419` | Enumerate sub-keys |
| WriteEA | 0x10 | `%%4420` | |
| Execute/Traverse | 0x20 | `%%4421` | |
| DeleteChild | 0x40 | `%%4422` | |
| ReadAttributes | 0x80 | `%%4423` | |
| WriteAttributes | 0x100 | `%%4424` | |
| DELETE | 0x10000 | `%%1537` | |
| READ_CONTROL | 0x20000 | `%%1538` | |
| WRITE_DAC | 0x40000 | `%%1539` | |
| WRITE_OWNER | 0x80000 | `%%1540` | |
| SYNCHRONIZE | 0x100000 | `%%1541` | |
| ACCESS_SYS_SEC | 0x1000000 | `%%1542` | |

- 괄호 안은 같은 값의 다른 이름입니다.
- 로컬 파일에서 AppendData 만 있고 WriteData 가 없으면 기존 데이터를 덮어쓰지 않습니다.
- Traverse(폴더 통과) 권한은 무시됩니다. 사용자에게 기본으로 BYPASS_TRAVERSE_CHECKING 권한이 주어지기 때문입니다.
- Microsoft 는 파일 개체에서 WriteData, AppendData, WriteEA, DeleteChild, WriteAttributes, DELETE, WRITE_DAC, WRITE_OWNER 를 지켜보라고 권합니다. 4656 에서는 이 권한들을 특히 실패 이벤트 위주로 보라고 합니다.

### PrivilegeList 의 두 권한

4656 의 PrivilegeList 에 아래 권한이 적히면, ACL 과 관계없이 접근을 얻었을 수 있습니다.

| 사용자 권한 | 뜻 | 허용되는 접근 |
|---|---|---|
| SeBackupPrivilege | ACL 과 관계없이 모든 파일에 읽기 접근을 줍니다 | READ_CONTROL, ACCESS_SYSTEM_SECURITY, FILE_GENERIC_READ, FILE_TRAVERSE |
| SeRestorePrivilege | ACL 과 관계없이 쓰기 접근을 줍니다 | WRITE_DAC, WRITE_OWNER, ACCESS_SYSTEM_SECURITY, FILE_GENERIC_WRITE, FILE_ADD_FILE, FILE_ADD_SUBDIRECTORY, DELETE |

### Keywords 로 성공과 실패 가르기

- 표준 이벤트 키워드에서 감사 실패 (AuditFailure) 는 `0x0010000000000000`, 감사 성공 (AuditSuccess) 은 `0x0020000000000000` 입니다 (확인 범위: Win11 25H2 한 대의 .NET StandardEventKeywords 열거값).
- 4656 예시의 `0x8010…` 에는 감사 실패 비트가 들어 있습니다.
- 4663·4660 예시의 `0x8020…` 에는 감사 성공 비트가 들어 있습니다.
- 맨 앞 `0x8000000000000000` 비트의 뜻은 확인하지 못했습니다.

## 증거로서 의미

| 증명하는 것 | 증명하지 못하는 것 |
|---|---|
| 기록된 시각에 이 계정의 이 프로세스가 이 파일에 이런 권한을 요청했습니다. 요청이 받아들여졌는지 거부됐는지도 적힙니다 (4656) | 요청한 작업을 실제로 했다는 것 (4656 만으로는 알 수 없습니다) |
| 기록된 시각에 이 프로세스가 이 파일에 이 권한을 썼습니다 (4663) | ReadData 가 있는 4663 이 파일 내용을 끝까지 읽었다는 것 (확인하지 못했습니다) |
| 이 프로세스가 이 핸들의 개체를 지웠습니다 (4660) | 4660 만으로 지운 파일의 이름 (칸이 없습니다) |
| DELETE 권한을 쓴 파일의 경로 (4663) | DELETE 가 든 4663 이면 파일이 지워졌다는 것 (이름 바꾸기에서도 남습니다) |
| 접근 검사에 특수 사용자 권한을 썼다는 것 (4656 의 PrivilegeList) | 계정 뒤의 사람이 누구인지 |
| | 기록이 없는 파일에 아무도 접근하지 않았다는 것 (SACL 이 없으면 남지 않습니다) |

### 보고서 문장

아래 시각과 경로는 설명을 위해 만든 예입니다.

- 쓸 수 있는 문장: "보안 로그에는 <시각> UTC 에 4663 이 있습니다. 계정 ○○ 의 `notepad.exe`(프로세스 ID `0x458`)가 `C:\Documents\HBI Data.txt` 에 WriteData 와 AppendData 권한을 썼습니다. 이 파일에는 쓰기 감사를 거는 SACL 이 설정돼 있었습니다."
- 쓰면 안 되는 문장: "○○ 이 파일 내용을 고쳤다."

두 번째 문장은 사람과 결과를 단정합니다. 이벤트에는 계정과 프로세스와 권한만 있습니다. 무엇을 얼마나 바꿨는지는 적히지 않습니다.

## 시각 해석

- 이벤트 시각은 `<TimeCreated SystemTime>` 에 들어 있습니다. 끝에 Z 가 붙은 UTC 값입니다. Microsoft 의 4663 예시는 `2015-09-18T22:13:54.770429700Z` 입니다.
- 현지 시각으로 바꿀 때는 조사 대상 PC 의 시간대 설정을 씁니다. 읽는 법은 [시간대 설정](/02-artifacts/system-account/time-zone.md)에서 다룹니다.
- 4656 시각은 권한을 요청한 시각입니다.
- 4663 시각은 권한을 쓴 시각입니다.
- 한 핸들로 같은 권한을 여러 번 쓸 때 4663 이 한 번만 남는지, 쓸 때마다 남는지는 확인하지 못했습니다. 4663 의 개수를 조작 횟수로 읽지 않습니다.
- 파일의 MFT 시각과 4663 시각이 가까우면 두 기록이 같은 조작을 가리킬 수 있습니다. 파일 시각은 [마스터 파일 테이블](/02-artifacts/filesystem/mft.md)에서 다룹니다.

## 함정과 한계

1. **4656 을 실제 접근으로 읽습니다.** 4656 은 요청과 결과만 보여 줍니다. 실제로 했는지는 같은 핸들의 4663 을 찾아 봅니다.
2. **4660 에서 파일 이름을 찾습니다.** 4660 에는 HandleId 만 있습니다. Microsoft 는 삭제를 추적하려면 DELETE 권한이 든 4663 을 쓰라고 권합니다.
3. **DELETE 가 든 4663 을 삭제로 단정합니다.** 4663 은 이름 바꾸기 같은 다른 동작에서도 생깁니다. 4660 은 실제로 지울 때만 생깁니다. 둘을 함께 봅니다.
4. **휴지통으로 보낸 파일도 4660 이 남는다고 봅니다.** 휴지통으로 옮길 때 어떤 이벤트가 남는지는 확인하지 못했습니다. 문서는 "4663 은 이름 바꾸기에서도 생긴다" 까지만 적습니다. 휴지통 쪽 기록은 [휴지통](/02-artifacts/file-folder-usage/recycle-bin.md)에서 따로 확인합니다.
5. **기록이 없으니 접근도 없었다고 씁니다.** 하위 범주가 꺼져 있었거나 그 파일에 SACL 이 없었을 수 있습니다. 기본 SACL 로는 이벤트가 생기지 않습니다.
6. **HandleId 하나로만 잇습니다.** 같은 HandleId 가 다른 프로세스나 다른 시각에 다시 나오는지는 확인하지 못했습니다. 잇기 전에 ProcessId 와 시각도 맞는지 봅니다.
7. **TransactionId 로 4656 과 4660 을 잇습니다.** 트랜잭션이 잡히지 않으면 모두 0 GUID 입니다. 0 GUID 끼리는 이으면 안 됩니다.
8. **이동식 저장소 기록을 파일 시스템 기록으로 읽습니다.** 같은 이벤트 ID 가 여러 하위 범주에서 나옵니다. Task 값과 ObjectType 을 함께 봅니다.
9. **커널 개체 기록에 시간을 씁니다.** Microsoft 는 커널 개체 감사 이벤트가 보안상 의미가 거의 없고 분석하기 어렵다고 적습니다.
10. **ProcessId 를 10진으로 찾습니다.** 이 칸은 16진입니다. 4688 의 New Process ID 와 맞출 때 진법을 맞춥니다.

### 지우기와 조작

- **보안 로그를 지웁니다.** 지운 기록은 [이벤트 로그 삭제](/02-artifacts/event-logs/1102-104.md)에서 찾습니다.
- **감사 설정을 끕니다.** 하위 범주를 끄거나 SACL 을 지우면 그 뒤로는 기록이 남지 않습니다. 설정이 언제 바뀌었는지는 [감사 정책과 로그 설정](/02-artifacts/event-logs/audit-policy-log-settings.md)에서 다룹니다.
- **개체 권한을 바꿉니다.** 4670 은 파일 시스템 감사 목록에 들어 있는 권한 변경 이벤트입니다. 칸에는 OldSd 와 NewSd 가 있습니다 (확인 범위: Win11 25H2 한 대의 공급자 메타데이터).
- **파쇄 도구로 지웁니다.** 흔적을 찾는 순서는 [완전삭제 도구를 썼나](/04-scenarios/activity/anti-forensics/wiping-tools.md)에서 다룹니다.

## 직접 분석해 보기

### AccessMask 풀기

AccessMask 는 권한 값의 합입니다. 위 권한 표로 되돌려 풀 수 있습니다.

4663 예시 `0x6`:

```
0x6 = 0x2 (WriteData) + 0x4 (AppendData)
AccessList: %%4417 %%4418  →  WriteData, AppendData
```

4656 예시 `0x12019f`:

```
0x100000  SYNCHRONIZE      %%1541
0x020000  READ_CONTROL     %%1538
0x000100  WriteAttributes  %%4424
0x000080  ReadAttributes   %%4423
0x000010  WriteEA          %%4420
0x000008  ReadEA           %%4419
0x000004  AppendData       %%4418
0x000002  WriteData        %%4417
0x000001  ReadData         %%4416
--------
0x12019f
```

두 예시 모두 AccessMask 를 푼 결과가 AccessList 의 코드와 하나씩 맞습니다. 도구가 권한 이름만 보여 줄 때는 AccessMask 를 직접 풀어 도구의 풀이와 맞춰 봅니다.

### 헥스로 한 번

AccessMask 는 16진으로 보여 주는 32비트 정수 (HexInt32) 칸입니다. 값은 바이트 순서를 뒤집어 저장합니다(리틀 엔디언). 값 종류와 저장 방식은 [이진 XML 해석](/01-foundations/database-log-formats/evtx-evt-etl/binary-xml-template.md)에서 다룹니다.

아래는 Microsoft 문서의 예시 값을 형식대로 옮긴 예시입니다. 검체에서 뽑은 바이트가 아닙니다.

```
AccessMask 0x12019f  →  9F 01 12 00
AccessMask 0x6       →  06 00 00 00
```

1. EVTX 파일을 헥스 편집기로 엽니다.
2. 4663 레코드의 값 영역에서 4바이트 값을 찾습니다. 값 설명자의 종류가 HexInt32 인 자리입니다.
3. 바이트를 뒤집어 읽고, 위 권한 표로 풉니다.
4. 값 영역의 AccessList 는 `%%4417` 같은 문자열입니다. 3번 풀이와 맞는지 봅니다.

### 한 조작을 잇는 순서

같은 파일 조작은 HandleId 로 4656(요청) → 4663(사용) → 4660(삭제) → 4658(닫힘) 순서로 이을 수 있습니다.

1. 보안 로그 사본에서 4656, 4663, 4660, 4658 을 뽑습니다.
2. ProcessId 와 HandleId 가 같은 기록끼리 묶습니다.
3. 묶음 안에서 시각 순으로 늘어놓습니다.
4. 4660 이 있으면 같은 묶음에서 AccessList 에 `%%1537`(DELETE) 이 든 4663 을 찾습니다. 그 4663 의 ObjectName 이 지운 파일의 경로입니다.
5. 4660 과 4656 의 TransactionId 가 0 GUID 가 아니면 이 값으로도 맞춰 봅니다.
6. SubjectLogonId 로 그 계정의 로그온 기록을 찾습니다. 방법은 [로그온 세션 잇기](/02-artifacts/event-logs/logon-events/logon-id-4624-4634-4647.md)에서 다룹니다.
7. ProcessId 로 그 프로세스를 만든 4688 을 찾습니다. 방법은 [프로세스 생성](/02-artifacts/event-logs/4688.md)에서 다룹니다.

4658 은 핸들 조작 감사를 켰을 때만 있습니다. 없으면 3번 묶음의 끝을 정할 수 없습니다.

> 그림 자리: 한 프로세스의 같은 HandleId 위에 4656(요청) → 4663(DELETE 사용, ObjectName 있음) → 4660(삭제, 이름 없음) → 4658(닫힘) 을 시간 축에 놓고, 4663 의 ObjectName 으로 4660 의 파일 이름을 채우는 모습

### 공개 도구로 한 번

- 이벤트 뷰어에서 "자세히 → XML 보기" 를 열면 AccessList, AccessMask, HandleId 를 바로 볼 수 있습니다.
- Windows 에 들어 있는 PowerShell 로 사본 파일에서 네 이벤트를 뽑아 핸들별로 늘어놓을 수 있습니다.

```powershell
Get-WinEvent -Path .\Security.evtx -FilterXPath "*[System[(EventID=4656 or EventID=4663 or EventID=4660 or EventID=4658)]]" -Oldest |
  ForEach-Object {
    $d = @{}
    ([xml]$_.ToXml()).Event.EventData.Data | ForEach-Object { $d[$_.Name] = $_.'#text' }
    [pscustomobject]@{
      TimeUtc    = $_.TimeCreated.ToUniversalTime()
      EventId    = $_.Id
      Task       = $_.Task
      ProcessId  = $d['ProcessId']
      HandleId   = $d['HandleId']
      Object     = $d['ObjectName']
      AccessMask = $d['AccessMask']
      LogonId    = $d['SubjectLogonId']
    }
  } | Sort-Object ProcessId, HandleId, TimeUtc | Format-Table
```

- python-evtx, EvtxECmd 같은 공개 도구도 이 칸들을 뽑아 줍니다. 도구가 `%%n` 을 권한 이름으로 바꿔 보여 주면 XML 원문 한두 건과 맞춰 봅니다. 방법은 [도구 결과 교차 검증](/03-techniques/reporting/tool-validation.md)에서 다룹니다.
- 라이브 시스템에서는 auditpol 로 하위 범주 설정을 봅니다. 이름이 깨져 보이면 GUID 로 확인합니다.
- EVTX 저장 구조는 [이벤트 로그 형식](/01-foundations/database-log-formats/evtx-evt-etl/index.md)에서 다룹니다.

## 실습

직접 만든 Windows 10·11 가상 머신에서 해 봅니다. 파일 시스템 하위 범주의 성공·실패 감사를 켜고, 시험 폴더에 모든 사람 (Everyone) 대상 SACL 을 겁니다. 각 단계의 시각을 적어 둡니다.

1. SACL 을 걸기 전에 시험 파일을 열고 고칩니다. 이벤트가 남는지 보십시오.
2. SACL 을 건 뒤 메모장으로 파일을 열고, 고치고, 저장합니다. 4656 과 4663 의 AccessMask 를 풀어 비교하십시오.
3. 쓰기 권한이 없는 계정으로 같은 파일을 고쳐 봅니다. 실패 4656 의 Keywords 와 AccessReason 을 확인하십시오.
4. 파일 이름을 바꿉니다. DELETE 가 든 4663 이 남는지, 4660 이 남는지 보십시오.
5. 파일 하나는 휴지통으로 보내고, 다른 하나는 Shift+Delete 로 지웁니다. 두 경우에 남는 이벤트를 비교하십시오. 함정 4번의 답이 여기서 나옵니다.
6. 파일을 한 번 열어 여러 번 저장합니다. 4663 이 몇 건 남는지 세어 보십시오. "시각 해석" 의 확인하지 못한 부분이 여기서 풀립니다.
7. 핸들 조작 감사를 켜고 2번을 다시 합니다. 4658 이 어느 시점에 남는지 보십시오.

NIST CFReDS 같은 공개 검체에서 보안 로그를 꺼냈다면, 먼저 4656·4663·4660 이 한 건이라도 있는지 봅니다. 없다면 감사 설정이 꺼져 있었는지부터 확인하십시오.
