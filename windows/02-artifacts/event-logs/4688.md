# 프로세스 생성 (4688)

## 한 줄 요약

보안 로그 (Security) 의 4688 은 새 프로세스가 시작될 때마다 남는 기록입니다. 실행 파일 경로, 새 프로세스와 부모 프로세스의 PID, 실행한 계정과 로그온 ID, 토큰 상승 유형이 남습니다. 감사 하위 범주 Audit Process Creation 을 켜야 남습니다. 명령줄은 정책을 하나 더 켜야 들어갑니다. 프로세스가 끝난 때는 4689 에서 봅니다.

## 무엇을 기록하나 · 왜 생기나

4688 의 제목은 "A new process has been created." 입니다. 새 프로세스가 시작될 때마다 생깁니다.

| 알고 싶은 것 | 볼 칸 (화면 이름 / XML 이름) |
|---|---|
| 무엇을 실행했나 | New Process Name / NewProcessName |
| 어떤 인수로 실행했나 | Process Command Line / CommandLine. 정책을 켜야 들어갑니다 |
| 어느 프로세스가 띄웠나 | Creator Process ID / ProcessId, Creator Process Name / ParentProcessName |
| 어느 계정·로그온 세션에서 띄웠나 | Creator Subject / SubjectUserSid 등 네 칸, Target Subject / TargetUserSid 등 네 칸 |
| 어떤 권한으로 실행했나 | Token Elevation Type / TokenElevationType, Mandatory Label / MandatoryLabel |

- 4688 에는 프로세스가 끝난 시각이 없습니다. 끝난 기록은 4689 "A process has exited." 로 따로 남습니다. 이 구분은 두 이벤트의 칸 구성을 보고 한 해석입니다.
- Sysmon 도 프로세스 생성을 남깁니다. Sysmon 쪽 기록은 [프로세스 생성 (이벤트 1)](/02-artifacts/event-logs/sysmon/1.md)에서 다룹니다.
- 여러 실행 흔적을 묶어 보는 순서는 [어떤 프로그램을 언제 실행했나](/04-scenarios/activity/program-execution.md)에서 다룹니다.

## 위치와 버전별 차이

### 로그와 켜는 설정

| 항목 | 값 |
|---|---|
| 공급자 (Provider) | Microsoft-Windows-Security-Auditing `{54849625-5478-4994-A5BA-3E3B0328C30D}` |
| 로그 | 보안 로그 (채널 `Security`) |
| 감사 하위 범주 | Audit Process Creation |
| 감사 정책 위치 | Computer Configuration > Policies > Windows Settings > Security Settings > Advanced Audit Configuration > Detailed Tracking |
| 감사 정책 기본값 | Not configured |
| 명령줄 정책 | Administrative Templates\System\Audit Process Creation 아래 "Include command line in process creation events" |
| 명령줄 정책 기본값 | Not Configured (꺼짐) |

- Microsoft 문서는 Audit Process Creation 정책을 "Supported on: Windows 7 and above" 로 적었습니다.
- 명령줄 정책은 Audit Process Creation 이 켜져 있을 때만 쓰입니다.
- 명령줄 정책의 적용 대상은 "At least Windows Server 2012 R2, Windows 8.1 or Windows RT 8.1" 입니다. (확인 범위: Win11 25H2 한 대의 AuditSettings.admx·Windows.adml)
- Windows 7·Server 2008 R2 에서도 업데이트를 설치하면 명령줄을 남길 수 있다는 설명이 널리 알려져 있습니다. 이번에 연 자료로는 확인하지 못했습니다.

명령줄 정책은 다음 레지스트리 값에 들어갑니다. (확인 범위: Win11 25H2 한 대의 AuditSettings.admx)

| 키 | 값 이름 | 뜻 |
|---|---|---|
| `HKLM\Software\Microsoft\Windows\CurrentVersion\Policies\System\Audit` | `ProcessCreationIncludeCmdLine_Enabled` | 1 이면 켬, 0 이면 끔 |

고급 감사 정책 설정이 기본 감사 정책 설정에 덮어쓰이면 4719 가 남습니다. 이를 막는 설정은 "Audit: Force audit policy subcategory settings (Windows Vista or later) to override audit policy category settings" 입니다. 감사 설정을 확인하는 방법은 [감사 정책과 로그 설정](/02-artifacts/event-logs/audit-policy-log-settings.md)에서 다룹니다.

### 한 PC 의 설정

한 PC 에서 읽은 결과는 다음과 같습니다. (확인 범위: Win11 25H2 한 대)

- 감사 하위 범주 Process Creation `{0CCE922B-69AE-11D9-BED3-505054503030}` 은 감사 안 함 (No Auditing) 이었습니다.
- 보안 로그에 4688 은 0건이었습니다.
- `...\Policies\System\Audit` 키는 있었습니다. 그 안에 값은 하나도 없었습니다.
- 보안 로그의 최대 크기는 20,971,520바이트였고, 보관 방식은 순환 (Circular) 이었습니다.
- 보안 로그에는 34,508건이 있었습니다. 가장 오래된 기록은 2026-09-22 08:43(+09:00) 이었습니다. 조사한 날(2026-09-24) 기준으로 약 2일치만 남아 있었습니다.

### 이벤트 버전

| 버전 | Windows | 바뀐 점 |
|---|---|---|
| 0 | Windows Vista · Windows Server 2008 | 처음 나온 형태 |
| 1 | Windows 8.1 · Windows Server 2012 R2 | Process Command Line 칸이 더해졌습니다 |
| 2 | Windows 10 | Subject 이름이 Creator Subject 로 바뀌었습니다. Target Subject 절, Mandatory Label 칸, Creator Process Name 칸이 더해졌습니다 |

버전별 XML 칸 이름은 다음과 같습니다. (확인 범위: Win11 25H2 한 대의 공급자 매니페스트)

| 버전 | 칸 |
|---|---|
| 0 | SubjectUserSid, SubjectUserName, SubjectDomainName, SubjectLogonId, NewProcessId, NewProcessName, TokenElevationType, ProcessId |
| 1 | 버전 0 의 칸 + CommandLine |
| 2 | 버전 1 의 칸 + TargetUserSid, TargetUserName, TargetDomainName, TargetLogonId, ParentProcessName, MandatoryLabel |

Windows XP · 2003 의 프로세스 생성 이벤트는 이번에 확인하지 못했습니다. 옛 로그 형식은 [구형 EVT 형식 (Windows XP·2003)](/01-foundations/database-log-formats/evtx-evt-etl/windows-xp-2003.md)에서 다룹니다.

## 구조

### 칸의 뜻

| XML 칸 | 화면 이름 | 뜻 | 읽을 때 주의 |
|---|---|---|---|
| NewProcessId | New Process ID | 새 프로세스의 PID | 16진입니다. 10진으로 바꾸면 작업 관리자의 값과 비교할 수 있습니다 |
| NewProcessName | New Process Name | 새 프로세스 실행 파일의 전체 경로와 이름 | |
| ProcessId | Creator Process ID | 새 프로세스를 띄운 프로세스의 PID | 16진입니다. 다른 4688 의 New Process ID 와 이을 수 있습니다 |
| ParentProcessName | Creator Process Name | 부모 프로세스의 전체 경로 | 버전 2 부터 있습니다 |
| CommandLine | Process Command Line | 실행 파일 이름과 인수 | 버전 1 부터 있습니다. 정책이 꺼져 있으면 비어 있습니다 |
| SubjectUserSid · SubjectUserName · SubjectDomainName · SubjectLogonId | Creator Subject | 프로세스를 만든 쪽 계정 | Logon ID 는 16진입니다. 4624 의 Logon ID 와 이을 수 있습니다 |
| TargetUserSid · TargetUserName · TargetDomainName · TargetLogonId | Target Subject | 새 프로세스의 대상 주체 | 버전 2 부터 있습니다 |
| TokenElevationType | Token Elevation Type | 토큰 상승 유형 | 아래 표 |
| MandatoryLabel | Mandatory Label | 무결성 수준 SID | 버전 2 부터 있습니다. 아래 표 |

XML 칸 이름 `ProcessId` 는 새 프로세스가 아니라 부모 프로세스의 PID 입니다. 새 프로세스의 PID 는 `NewProcessId` 에 있습니다.

### Creator Subject 와 Target Subject

- 만든 쪽과 대상 쪽이 같은 로그온 세션을 쓰지 않을 때가 있습니다. 이때 Target Subject 에 대상 주체를 함께 적습니다.
- 이런 경우 프로세스 종료 이벤트의 주체가 생성 이벤트의 주체와 다를 수 있다고 Microsoft 문서가 적었습니다.
- 로그온 ID 로 세션을 잇는 방법은 [로그온 세션 잇기](/02-artifacts/event-logs/logon-events/logon-id-4624-4634-4647.md)에서 다룹니다.

### Token Elevation Type

XML 에는 `%%1936` 꼴의 값이 들어갑니다. 이 번호는 메시지 파일의 문구를 가리킵니다. 메시지 파일을 읽는 방법은 [공급자와 메시지 파일](/01-foundations/database-log-formats/evtx-evt-etl/provider-message-table.md)에서 다룹니다.

| XML 값 | msobjs.dll 문구 | 뜻 |
|---|---|---|
| `%%1936` | TokenElevationTypeDefault (1) | 유형 1, 전체 토큰입니다. 권한을 빼지 않았습니다. UAC 가 꺼져 있거나, 기본 제공 Administrator·서비스 계정·로컬 시스템 계정일 때입니다 |
| `%%1937` | TokenElevationTypeFull (2) | 유형 2, 상승된 토큰입니다. UAC 가 켜진 상태에서 "관리자 권한으로 실행" 을 골랐을 때입니다. 항상 관리자 권한을 요구하는 앱을 Administrators 구성원이 실행할 때도 이 값입니다 |
| `%%1938` | TokenElevationTypeLimited (3) | 유형 3, 제한된 토큰입니다. UAC 가 켜져 있고 관리자 권한 없이 실행했을 때입니다 |

msobjs.dll 문구 열은 한 PC 의 메시지 표에서 읽었습니다. (확인 범위: Win11 25H2 한 대) 뜻 열은 Microsoft 문서의 설명입니다.

### Mandatory Label

| SID | 무결성 수준 |
|---|---|
| S-1-16-0 | Untrusted |
| S-1-16-4096 | Low |
| S-1-16-8192 | Medium |
| S-1-16-8448 | Medium Plus |
| S-1-16-12288 | High |
| S-1-16-16384 | System |
| S-1-16-20480 | Protected process |

### Microsoft 예시

Microsoft 문서의 버전 2 예시 가운데 일부입니다. 문서가 보여 주는 예시이며 검체에서 나온 값이 아닙니다.

```xml
<Provider Name="Microsoft-Windows-Security-Auditing" Guid="{54849625-5478-4994-A5BA-3E3B0328C30D}" />
<EventID>4688</EventID>
<Version>2</Version>
<Level>0</Level>
<Task>13312</Task>
<Keywords>0x8020000000000000</Keywords>
<Channel>Security</Channel>
...
<Data Name="SubjectUserSid">S-1-5-18</Data>
<Data Name="SubjectUserName">WIN-GG82ULGC9GO$</Data>
<Data Name="SubjectLogonId">0x3e7</Data>
<Data Name="TokenElevationType">%%1938</Data>
<Data Name="CommandLine" />
<Data Name="ParentProcessName">C:\Windows\explorer.exe</Data>
<Data Name="MandatoryLabel">S-1-16-8192</Data>
```

이 예시에서 읽을 점은 다음과 같습니다.

1. Creator Subject 는 S-1-5-18 입니다. 컴퓨터 계정 이름이 적혀 있고, Logon ID 는 0x3e7 입니다.
2. Target Subject 에는 도메인 사용자가 적혀 있습니다. 사용자 계정은 Creator Subject 가 아니라 Target Subject 에 있습니다.
3. 부모 프로세스는 `C:\Windows\explorer.exe` 입니다.
4. 토큰은 제한된 토큰(`%%1938`)이고, 무결성 수준은 Medium 입니다.
5. CommandLine 은 빈 요소입니다. 명령줄 정책이 꺼져 있을 때의 모습과 같습니다.

## 증거로서 의미

| 증명하는 것 | 증명하지 못하는 것 |
|---|---|
| 기록 시각에 이 경로의 실행 파일로 프로세스가 만들어졌다는 것 | 프로세스가 무슨 일을 했는지 |
| 새 프로세스와 부모 프로세스의 PID, 버전 2 이면 부모 경로 | 프로세스가 언제 끝났는지 (4689 에서 따로 봅니다) |
| 만든 쪽과 대상 쪽의 계정·로그온 ID | 그 계정 뒤에 있던 사람이 누구인지 |
| 명령줄 정책을 켰다면 실행할 때의 인수 | 명령줄 칸이 비었을 때 인수가 없었다는 것 (정책이 꺼져도 비어 있습니다) |
| 토큰 상승 유형과 무결성 수준 | 실행 파일의 내용. 칸 목록에 해시가 없습니다 |
| | 감사가 꺼져 있던 기간이나, 순환으로 밀려난 기간에 실행이 없었다는 것 |

### 보고서 문장

- 쓸 수 있는 문장: "보안 로그에 ○○(UTC) 의 4688 이 있습니다. New Process Name 은 `○○` 이고 Creator Process Name 은 `○○` 입니다. Target Subject 는 ○○\○○ 이고 Logon ID 는 ○○ 입니다. Token Elevation Type 은 %%1937 입니다."
- 쓰면 안 되는 문장: "사용자 ○○가 관리자 권한으로 악성 프로그램을 실행했다."

두 번째 문장은 기록에 없는 사람과 판단을 적습니다. 4688 이 말하는 것은 어느 계정 세션에서 어떤 파일이 어떤 토큰으로 시작됐는지까지입니다. 파일이 악성인지는 다른 분석으로 따로 적습니다.

## 시각 해석

- 4688 의 기록 시각은 새 프로세스가 시작된 때입니다.
- 4688 에는 끝난 시각이 없습니다. 같은 PID 의 4689 를 찾아 끝난 시각을 봅니다.
- 레코드의 기록 시각을 저장하는 형식은 [이벤트 로그 형식](/01-foundations/database-log-formats/evtx-evt-etl/index.md)에서 다룹니다.
- 여러 기록의 시각을 한 기준으로 맞추는 방법은 [시간대·시계 오차 보정](/03-techniques/analysis/timeline/time-normalization.md)에서 다룹니다.
- 보안 로그는 크기 한도에 이르면 오래된 기록부터 밀려납니다. 한 PC 에서는 약 2일치만 남아 있었습니다. (확인 범위: Win11 25H2 한 대) 그보다 오래된 실행은 [프리페치](/02-artifacts/execution/prefetch/index.md) 같은 다른 흔적에서 찾습니다.

## 함정과 한계

1. **4688 이 없으면 실행이 없었다고 봅니다.** 감사 정책 기본값은 Not configured 입니다. 한 PC 에서는 감사 안 함이었고 4688 이 0건이었습니다. 먼저 감사 설정을 확인합니다.
2. **명령줄이 비면 인수가 없었다고 봅니다.** 명령줄 정책이 꺼져 있으면 CommandLine 칸은 늘 비어 있습니다. 레지스트리 값이나 같은 로그의 다른 4688 에 명령줄이 있는지 먼저 봅니다.
3. **XML 의 `ProcessId` 를 새 프로세스 PID 로 읽습니다.** 이 칸은 부모 PID 입니다. 새 프로세스의 PID 는 `NewProcessId` 입니다.
4. **PID 를 10진 값과 그대로 맞춥니다.** 4688 의 PID 는 16진입니다. 작업 관리자의 PID 와 비교하려면 10진으로 바꿉니다. 예약 작업 이벤트 129 의 ProcessID 도 10진입니다([예약 작업 이벤트](/02-artifacts/event-logs/taskscheduler-4698.md)).
5. **PID 하나로만 부모를 잇습니다.** PID 가 다시 쓰이므로 PID 만으로 이으면 틀릴 수 있다는 설명이 있습니다. 이번에 연 자료로는 확인하지 못했습니다. Microsoft 문서는 "이을 수 있다" 고만 적었습니다. PID 와 함께 시각 순서와 부모 경로(ParentProcessName)도 맞춰 봅니다.
6. **Creator Subject 만 봅니다.** Microsoft 예시에서 Creator Subject 는 SYSTEM 이고 사용자 계정은 Target Subject 에 있습니다. 버전 2 기록은 두 절을 모두 읽습니다.
7. **명령줄을 그대로 옮겨 적습니다.** 명령줄은 보안 로그에 평문으로 남습니다. 보안 로그를 읽을 수 있는 사람은 누구나 인수를 볼 수 있습니다. 인수에 비밀번호 같은 민감 정보가 들어 있을 수 있습니다. 보고서와 공유 자료에서는 가립니다.
8. **분석 PC 의 매니페스트를 검체에 그대로 씁니다.** 검체의 Windows 버전이 다르면 이벤트 버전과 칸 구성이 다를 수 있습니다. 레코드의 Version 값을 먼저 봅니다.

### 지우기와 조작

- **로그를 지웁니다.** 보안 로그를 지우면 1102 가 남습니다. [이벤트 로그 삭제 (1102·104)](/02-artifacts/event-logs/1102-104.md)를 봅니다.
- **다른 로그만 지웁니다.** 보안 로그가 남아 있다면 로그를 지운 도구의 실행이 4688 로 남아 있을 수 있습니다. 이 판단은 4688 이 모든 새 프로세스에 생긴다는 설명에서 나온 해석입니다.
- **감사 설정을 바꿉니다.** 고급 감사 정책 설정이 기본 감사 정책 설정에 덮어쓰이면 4719 가 남습니다.
- **레코드 일부만 남아 있습니다.** 지우거나 덮어쓴 레코드가 파일 안에 남아 있을 수 있습니다. [파일 안에 남은 지운·손상 레코드](/01-foundations/database-log-formats/evtx-evt-etl/chunk-slack-corrupted-evtx.md)를 봅니다.

## 직접 분석해 보기

### 헥스로 한 번

**1) 명령줄 정책 값**

명령줄 정책이 켜져 있었는지 SOFTWARE 하이브에서 확인합니다. 하이브 안의 키 경로는 `Microsoft\Windows\CurrentVersion\Policies\System\Audit` 입니다. 하이브 구조는 [레지스트리 하이브 구조](/01-foundations/database-log-formats/registry-hive/index.md)에서 다룹니다.

아래 바이트는 명세로 만든 예시입니다. 검체에서 나온 값이 아닙니다.

`ProcessCreationIncludeCmdLine_Enabled` 가 REG_DWORD 1 이면 값 데이터는 4바이트입니다.

```
01 00 00 00
```

1. 리틀 엔디언으로 읽으면 0x00000001 입니다.
2. 1 은 켬입니다. 0 이면 끔입니다.
3. 값 자체가 없으면 이 정책을 설정하지 않은 상태로 봅니다. 한 PC 에서는 키만 있고 값이 없었습니다. (확인 범위: Win11 25H2 한 대)
4. REG_DWORD 를 문자열로 받는 도구는 부호 없는 10진으로 보여 줍니다(현장 관찰). 0 과 1 은 어느 쪽으로 읽어도 같습니다.

지금 설정은 수집 시점의 값입니다. 사건 당시에도 같은 값이었는지는 같은 시기 4688 의 CommandLine 칸이 채워져 있는지로 함께 봅니다.

**2) PID 로 부모와 자식 잇기**

아래 두 레코드는 설명을 위해 만든 예시입니다. 경로와 PID 는 지어낸 값입니다.

| 레코드 | NewProcessId | NewProcessName | ProcessId (부모) | ParentProcessName |
|---|---|---|---|---|
| A | `0x1a9c` | `C:\Example\parent.exe` | … | … |
| B | `0x2b40` | `C:\Example\child.exe` | `0x1a9c` | `C:\Example\parent.exe` |

1. B 의 ProcessId `0x1a9c` 와 같은 NewProcessId 를 찾습니다. A 입니다.
2. A 가 B 보다 먼저 기록됐는지 시각을 봅니다.
3. B 의 ParentProcessName 과 A 의 NewProcessName 이 같은지 봅니다.
4. 셋 다 맞으면 A 가 B 의 부모라고 적습니다.
5. `0x1a9c` 는 10진으로 6,812 이고, `0x2b40` 은 10진으로 11,072 입니다. 작업 관리자나 10진 PID 를 쓰는 기록과는 이 값으로 비교합니다.

> 그림 자리: 4688 레코드 여러 개를 NewProcessId 와 ProcessId 로 이어 부모·자식 나무로 그린 그림. 각 칸에 16진 PID 와 10진 값을 함께 적는다

### 공개 도구로 한 번

Windows 에 들어 있는 이벤트 뷰어와 PowerShell 의 `Get-WinEvent` 로 볼 수 있습니다. 분석 PC 로 옮긴 파일은 `Path` 로 엽니다. 아래 `E:\case\` 는 예시 경로입니다.

```powershell
# 프로세스 생성과 종료
Get-WinEvent -FilterHashtable @{ Path = 'E:\case\Security.evtx'; Id = 4688, 4689 }

# 4688 하나에서 주요 칸 꺼내기
$e = Get-WinEvent -FilterHashtable @{ Path = 'E:\case\Security.evtx'; Id = 4688 } -MaxEvents 1
([xml]$e.ToXml()).Event.EventData.Data |
  Where-Object { $_.Name -in 'NewProcessId', 'NewProcessName', 'ProcessId', 'ParentProcessName', 'CommandLine', 'TokenElevationType', 'MandatoryLabel' }

# 16진 PID 를 10진으로
[Convert]::ToInt32('1a9c', 16)
```

칸 구성은 공급자 매니페스트에서 확인할 수 있습니다.

```powershell
(Get-WinEvent -ListProvider Microsoft-Windows-Security-Auditing).Events |
  Where-Object Id -eq 4688 | Select-Object Id, Version, Template
```

이 명령은 분석 PC 의 매니페스트를 읽습니다. 라이브 시스템의 감사 설정은 `auditpol /get /subcategory:{0CCE922B-69AE-11D9-BED3-505054503030} /r` 로 확인합니다. 명령줄 정책 값은 `reg query "HKLM\Software\Microsoft\Windows\CurrentVersion\Policies\System\Audit"` 로 봅니다.

도구가 긴 명령줄을 잘라 보여 주는지 확인합니다. 레코드 한두 개는 XML 원문과 맞춰 봅니다. 방법은 [도구 결과 교차 검증](/03-techniques/reporting/tool-validation.md)에서 다룹니다.

## 교차 검증

| 함께 볼 아티팩트 | 무엇을 맞춰 보나 |
|---|---|
| 4689 (같은 보안 로그) | 같은 PID 의 프로세스가 끝난 시각과 Status |
| [프로세스 생성 (이벤트 1)](/02-artifacts/event-logs/sysmon/1.md) | 같은 실행이 Sysmon 에도 있는지, PID·시각·명령줄이 맞는지 |
| [로그온 세션 잇기](/02-artifacts/event-logs/logon-events/logon-id-4624-4634-4647.md) | SubjectLogonId·TargetLogonId 와 같은 Logon ID 의 4624 |
| [명시적 자격 증명·특수 권한 (4648·4672)](/02-artifacts/event-logs/logon-events/4648-4672.md) | 상승된 토큰으로 실행한 세션에 특수 권한 기록이 있는지 |
| [예약 작업 이벤트](/02-artifacts/event-logs/taskscheduler-4698.md) | 129 의 10진 ProcessID 를 16진으로 바꿔 New Process ID 와 맞추기 |
| [PowerShell 실행 기록](/02-artifacts/event-logs/powershell-event-logs-4103-4104.md) | PowerShell 명령줄 뒤에 실제로 실행된 스크립트 |
| [프리페치](/02-artifacts/execution/prefetch/index.md) · [AmCache](/02-artifacts/execution/amcache-hve/index.md) | 보안 로그가 밀려난 기간의 실행 흔적, 실행 파일 정보 |

Microsoft 의 명령줄 감사 문서는 AppLocker 로그(Application and Services Logs\Microsoft\Windows\AppLocker)에 실행 파일의 SHA1·SHA2 해시도 남는다고 적었습니다. 이번에는 AppLocker 로그를 따로 확인하지 않았습니다.

### 원격 작업 등록 시험 결과 (JPCERT/CC)

JPCERT/CC 는 `schtasks` 로 다른 컴퓨터에 작업을 등록하는 시험을 하고 남은 기록을 정리했습니다. 전체 표는 [예약 작업 이벤트](/02-artifacts/event-logs/taskscheduler-4698.md)에 있습니다. 4688 과 관련된 부분만 옮기면 다음과 같습니다.

- 실행한 쪽의 4688 에 Mandatory Label Medium 이 남았습니다.
- 대상 쪽에도 4688 이 남았습니다.
- 실행한 쪽의 4689 Exit Status 0x0 을 실행 성공의 근거로 삼았습니다.

## 실습

**직접 만든 Windows 10·11 가상 머신**에서 해 봅니다. 각 단계의 시각을 적어 둡니다.

1. `auditpol /get /subcategory:{0CCE922B-69AE-11D9-BED3-505054503030} /r` 로 지금 설정을 봅니다.
2. `auditpol /set /subcategory:{0CCE922B-69AE-11D9-BED3-505054503030} /success:enable` 로 감사를 켭니다.
3. 메모장을 한 번 실행합니다. 4688 의 CommandLine 칸이 비어 있는지 봅니다.
4. 명령줄 정책을 켭니다. `ProcessCreationIncludeCmdLine_Enabled` 값이 생기는지 봅니다. 메모장을 다시 실행하고 CommandLine 칸을 봅니다.
5. 명령 프롬프트를 그냥 한 번, "관리자 권한으로 실행" 으로 한 번 엽니다. 두 4688 의 TokenElevationType 과 MandatoryLabel 을 비교합니다.
6. 명령 프롬프트 안에서 다른 프로그램을 실행합니다. ProcessId 와 NewProcessId 로 부모와 자식을 잇습니다.
7. 프로그램을 닫고 4689 의 ProcessId·Status 를 봅니다.

**NIST CFReDS 같은 공개 검체**에서는 다음을 풀어 봅니다.

1. 보안 로그에 4688 이 있습니까? 없다면 감사 설정이 꺼져 있었는지, 로그가 얼마나 오래된 기록부터 남아 있는지 봅니다.
2. 4688 의 이벤트 버전은 몇입니까? 버전에 따라 어떤 칸이 없습니까?
3. CommandLine 칸이 채워진 레코드가 있습니까? 없다면 명령줄 정책 값을 레지스트리에서 찾습니다.
4. TokenElevationType 이 `%%1937` 인 레코드를 모읍니다. 어느 계정 세션에서 무엇을 실행했습니까?
