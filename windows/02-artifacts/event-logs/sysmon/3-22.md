# 네트워크 연결·DNS 질의 (이벤트 3·22)

Sysmon 이벤트 3 (NetworkConnect) 은 프로세스의 TCP·UDP 연결을 남기고, 이벤트 22 (DnsQuery) 는 프로세스의 DNS 질의를 남깁니다. 두 이벤트 모두 ProcessGuid 필드가 있어 어느 프로세스가 어느 이름을 묻고 어느 주소와 통신했는지 이을 수 있습니다. 이벤트 3 은 기본으로 꺼져 있습니다. 시각은 UTC 입니다.

## 무엇을 기록하나 · 왜 생기나

### 이벤트 3 (NetworkConnect)

컴퓨터의 TCP·UDP 연결을 기록합니다. 기본으로 꺼져 있어서 설치 명령의 `-n` 스위치나 설정 파일의 `<NetworkConnect>` 필터로 켭니다. 어느 프로세스의 연결인지는 ProcessId 와 ProcessGuid 로 잇습니다.

출발지와 목적지의 호스트 이름, IP 주소, 포트 번호, IPv6 여부가 들어 있습니다. 호스트 이름 필드는 Sysmon 이 역방향 DNS 조회 (reverse DNS lookup) 로 채우며, 이 조회는 전역 설정 DnsLookup 으로 끄고 켭니다. 기본은 켜짐(True)입니다.

### 이벤트 22 (DnsQuery)

프로세스가 DNS 질의를 하면 남습니다. 질의가 성공했는지 실패했는지, 캐시에서 답을 얻었는지와 관계없이 남습니다. Sysmon 은 이 이벤트에 Windows 8.1 에서 추가된 기록 기능을 쓰므로 Windows 7 이하에는 이 이벤트가 없습니다.

Sysmon 은 dnsapi.dll 의 DnsQuery_* API 호출을 ETW 로 받아 기록합니다[4]. 설치 명령의 `-dns` 스위치나 설정 파일의 `<DnsQuery>` 필터로 정합니다. 기록량이 설정에 따라 중간에서 많음까지라서 빼기 규칙을 함께 씁니다[4].

다음 경우는 이벤트 22 로 남지 않습니다[4].

- 자체 DNS 해석 기능으로 이름을 푸는 프로그램
- raw 소켓으로 DNS 서버에 직접 묻는 경우
- 다른 DNS 라이브러리를 쓰는 앱

DNS over HTTPS 질의가 남는지는 실제 데이터로 확인해야 합니다.

## 위치와 버전별 차이

채널, 로그 파일 위치, 스위치와 필터 규칙은 [Sysmon 개념과 설정 확인](sysmon-config.md)에서 다룹니다. 두 이벤트 모두 v15.22 가 아는 가장 오래된 스키마 4.80 에 있고, 이벤트 22 는 Windows 8.1 이후에만 있습니다.

Microsoft 의 Sysmon 설정 파일 문서 한 곳은 22번 태그를 "DNSQuery" 로 적었지만, 배포본 스키마와 도움말의 태그는 "DnsQuery" 입니다[2][3]. 설정 파일을 읽을 때는 배포본 표기를 기준으로 봅니다.

| 이벤트 | 필터 태그 | 설치 스위치 | 기본 상태 |
|---|---|---|---|
| 3 | NetworkConnect | `-n` | 꺼짐 |
| 22 | DnsQuery | `-dns` | 설정에 따릅니다 |

## 증거로서 의미

### 이벤트 3

| 증명하는 것 | 증명하지 못하는 것 |
|---|---|
| 기록된 시각에 Sysmon 이 이 프로세스의 TCP·UDP 연결을 기록했습니다 | 얼마나 주고받았는지 (바이트 수 필드가 없습니다) |
| 양쪽의 IP 주소와 포트 번호 | 무엇을 주고받았는지 |
| 연결한 프로세스의 경로와 계정 | 연결이 얼마나 이어졌는지 |
| | 호스트 이름 필드의 값이 프로세스가 물은 이름이라는 것 (역방향 조회 결과입니다) |
| | 어느 쪽이 연결을 시작했는지 (Initiated 의 뜻은 공개 자료가 없습니다) |
| | 이벤트 수가 곧 연결 수라는 것 (한 연결을 몇 번 기록하는지 알려져 있지 않습니다) |

### 이벤트 22

| 증명하는 것 | 증명하지 못하는 것 |
|---|---|
| 기록된 시각에 이 프로세스가 Windows DNS API 로 이 이름을 물었습니다 | 그 뒤에 그 주소로 실제로 연결했다는 것 |
| 질의의 결과 상태와 답 | 사람이 그 주소를 직접 입력했다는 것 |
| | 기록되지 않는 경로(자체 해석, raw 소켓, 다른 라이브러리)로 물은 이름이 없었다는 것 |
| | 네트워크로 DNS 패킷이 나갔다는 것 (캐시에서 답한 질의도 남습니다) |

### 보고서 문장

아래 이름·주소·시각은 설명을 위해 만든 예입니다. 주소는 문서용 예약 주소입니다.

- 쓸 수 있는 문장: "이 PC 의 Sysmon 로그에는 <시각> UTC 에 `C:\Tools\sync.exe` 가 `files.example.org` 를 질의한 이벤트 22 가 있습니다. 같은 ProcessGuid 로 몇 초 뒤 목적지 203.0.113.10, 포트 443 인 이벤트 3 이 있습니다."
- 쓰면 안 되는 문장: "사용자가 `sync.exe` 로 회사 자료를 `files.example.org` 에 올렸다."

두 번째 문장은 사람, 전송 방향, 전송 내용까지 적지만 이벤트 3·22 에는 이 가운데 어느 것도 없습니다. 전송량은 다른 기록에서 찾습니다(아래 교차 검증).

## 시각 해석

- 두 이벤트의 UtcTime 은 UTC 입니다. 서식은 [프로세스 생성](1.md)의 "시각 해석" 을 봅니다.
- 이벤트 22 는 질의한 때, 이벤트 3 은 연결을 기록한 때입니다.
- 같은 ProcessGuid 에서 22 가 먼저 나오고 3 이 뒤따르면, 이름을 풀고 연결한 흐름으로 읽을 수 있습니다.
- 역방향 조회 결과는 조회한 때의 DNS 답입니다. 분석하면서 같은 IP 를 다시 조회하면 다른 이름이 나올 수 있습니다. 보고서에는 이벤트에 남은 이름을 그대로 적습니다.
- 여러 기록을 한 줄로 놓는 법은 [타임라인 작성](../../../03-techniques/analysis/timeline/index.md)에서 다룹니다.

## 함정과 한계

1. **이벤트 3 이 없으니 통신도 없었다고 씁니다.** 이벤트 3 은 기본으로 꺼져 있고, 켜져 있어도 설정이 뺀 연결은 남지 않으므로 설정부터 확인합니다.
2. **DestinationHostname 을 프로세스가 찾아간 이름으로 읽습니다.** 이 필드는 Sysmon 이 IP 로 역방향 조회를 해서 채운 이름입니다. 한 IP 에 여러 이름이 붙는 경우가 흔하므로, 프로세스가 물은 이름은 같은 ProcessGuid 의 이벤트 22 QueryName 에서 찾습니다.
3. **Source 를 이 컴퓨터로 단정합니다.** Initiated 필드의 뜻은 공개 자료가 없습니다. 출발지와 목적지 가운데 어느 쪽이 이 컴퓨터인지는 IP 를 이 컴퓨터의 주소와 맞춰 판별합니다.
4. **이벤트 수를 연결 수로 셉니다.** 같은 연결을 몇 번 기록하는지는 알려져 있지 않습니다.
5. **DnsLookup 설정을 확인하지 않습니다.** DnsLookup 을 끄면 Sysmon 은 역방향 조회를 하지 않습니다. 그때 호스트 이름 필드가 어떻게 남는지는 실제 데이터로 확인해야 합니다.
6. **이벤트 22 가 모든 DNS 질의를 담는다고 봅니다.** 자체 해석 기능, raw 소켓, 다른 DNS 라이브러리로 한 질의는 남지 않습니다.
7. **이벤트 22 수를 네트워크 질의 수로 읽습니다.** 캐시에서 답한 질의도 남습니다.
8. **QueryResults·QueryStatus 를 짐작해 읽습니다.** 표기 형식과 상태 코드 뜻은 공개 자료가 없습니다. 실물 값을 먼저 여러 건 봅니다.
9. **태그 이름 표기를 잘못 옮깁니다.** 설정 파일의 22번 태그는 배포본 기준 "DnsQuery" 입니다.
10. **빼기 규칙을 지나칩니다.** 이벤트 22 는 양이 많아서 흔히 빼기 규칙을 씁니다. 설정에서 뺀 이름·프로그램은 기록에 없습니다.

기록을 지우거나 Sysmon 을 멈추는 경우는 [Sysmon 개념과 설정 확인](sysmon-config.md)의 "지우기와 조작" 에서 다룹니다.

## 직접 분석해 보기

### 한 프로세스의 통신 이어 보기

1. 이벤트 22 에서 의심스러운 QueryName 을 찾습니다.
2. 그 이벤트의 ProcessGuid 를 적습니다.
3. 같은 ProcessGuid 의 이벤트 3 을 찾습니다.
4. 이벤트 3 의 DestinationIp 가 이벤트 22 의 QueryResults 에 들어 있는지 봅니다.
5. 같은 ProcessGuid 의 이벤트 1 을 찾아 명령줄과 부모 프로세스를 봅니다.
6. 이 컴퓨터의 IP 를 [네트워크 인터페이스 설정](../../network/tcp-ip-interfaces.md)에서 확인하고, 출발지·목적지 방향을 확인합니다.

아래는 이 흐름을 보이려고 만든 예시입니다. 실제 데이터에서 나온 값이 아닙니다.

| 순서 | 이벤트 | ProcessGuid | 주요 필드 |
|---|---|---|---|
| 1 | 1 | {A…} | Image `C:\Tools\sync.exe`, ParentImage `explorer.exe` |
| 2 | 22 | {A…} | QueryName `files.example.org` |
| 3 | 3 | {A…} | DestinationIp 203.0.113.10, DestinationPort 443 |

EVTX 레코드 안에서 필드 값이 어떻게 저장되는지는 [이벤트 로그 형식](../../../01-foundations/database-log-formats/evtx-evt-etl/index.md)에서 다룹니다.

### 공개 도구로 한 번

- 이벤트 뷰어에서 Sysmon 채널을 열고 이벤트 ID 3 과 22 로 거릅니다.
- PowerShell 의 `Get-WinEvent` 로 두 ID 를 뽑아 ProcessGuid 로 묶습니다.
- 공개 EVTX 해석 도구(예: EvtxECmd, python-evtx)로 필드를 표로 뽑아 스프레드시트에서 잇습니다.
- 여러 대의 로그를 규칙으로 살펴볼 때는 [이벤트 로그 규칙 검색](../../../03-techniques/analysis/sigma-rules.md)을 봅니다.
- 도구가 IP·포트를 원래 값대로 보여 주는지 레코드 한두 개로 확인합니다. 방법은 [도구 결과 교차 검증](../../../03-techniques/reporting/tool-validation.md)에서 다룹니다.

## 실습

직접 만든 Windows 11 가상 머신에 Sysmon 을 설치하고 해 봅니다. 각 단계의 시각을 적어 둡니다.

1. `-n` 없이 설치하고 웹 페이지 하나를 엽니다. 이벤트 3 이 남는지 보십시오. 그다음 `-n` 을 켜고 같은 일을 합니다.
2. 이 가상 머신에서 밖으로 접속하고, 다른 가상 머신에서 이 가상 머신의 공유 폴더로 접속합니다. 두 경우의 Initiated 필드와 Source·Destination 방향을 비교하십시오.
3. 연결 하나를 오래 열어 둡니다. 같은 연결이 몇 번 기록되는지 세어 보십시오.
4. `Resolve-DnsName` 과 `nslookup` 으로 같은 이름을 질의합니다. 두 경우 모두 이벤트 22 가 남는지 비교하십시오.
5. 없는 이름을 질의합니다. QueryStatus 와 QueryResults 에 무엇이 남는지 적어 보십시오.
6. DnsLookup 을 끈 설정으로 바꿉니다. 이벤트 3 의 호스트 이름 필드가 어떻게 달라지는지 보십시오.
7. 브라우저에서 DNS over HTTPS 를 켜고 웹 페이지를 엽니다. 이벤트 22 가 남는지 보십시오.
