# 이미지 로드·프로세스 접근 (이벤트 7·8·10)

## 한 줄 요약

Sysmon 이벤트 7 (ImageLoad) 은 프로세스에 DLL 같은 모듈 (module) 이 올라올 때 남습니다. 이벤트 8 (CreateRemoteThread) 은 한 프로세스가 다른 프로세스 안에 스레드를 만들 때 남습니다. 이벤트 10 (ProcessAccess) 은 한 프로세스가 다른 프로세스를 열 때 남습니다. 이미지 로드는 기본으로 꺼져 있고, 프로세스 접근은 빼기 규칙과 함께 켜는 이벤트입니다. 그래서 이 세 이벤트는 설정부터 확인하고 읽습니다. 시각은 UTC 입니다.

## 무엇을 기록하나 · 왜 생기나

### 이벤트 7 (ImageLoad)

어느 프로세스에 모듈이 올라올 때 남고, 올라온 모듈의 해시와 서명 정보가 들어 있습니다. 서명 확인은 성능 때문에 로드와 따로, 나중에 합니다. 이 이벤트에는 로드 뒤에 파일이 지워졌는지도 남습니다[1]. 어느 필드에 어떤 값으로 남는지는 실제 기록으로 확인해야 합니다. 모든 로드를 기록하면 양이 매우 많아지므로 조심해서 설정합니다[1].

### 이벤트 8 (CreateRemoteThread)

한 프로세스가 다른 프로세스 안에 스레드를 만들 때 남습니다. 악성 코드는 이 방법으로 다른 프로세스에 코드를 넣어 실행하는데, 이를 코드 주입 (code injection) 이라 합니다. 새 스레드가 실행을 시작할 곳은 StartAddress, StartModule, StartFunction 필드에 적습니다.

### 이벤트 10 (ProcessAccess)

한 프로세스가 다른 프로세스를 열 때 남습니다. 프로세스를 연 뒤에는 보통 정보를 조회하거나 메모리를 읽고 씁니다. 이 이벤트는 lsass.exe 메모리를 읽어 자격 증명을 훔치는 도구를 잡는 데 씁니다[1]. Sysmon 드라이버는 ObRegisterCallbacks 로 이 동작을 잡습니다[4].

진단 도구가 프로세스를 되풀이해 열면 양이 매우 많아집니다. 그래서 예상된 접근을 빼는 필터와 함께 켭니다.

## 위치와 버전별 차이

- 채널, 로그 파일 위치, 필터 규칙은 [Sysmon 개념과 설정 확인](sysmon-config.md)에서 다룹니다.

| 이벤트 | 필터 태그 | 켜는 법 |
|---|---|---|
| 7 | ImageLoad | 기본으로 꺼져 있습니다. 설치 스위치 `-l` 로 켭니다 |
| 8 | CreateRemoteThread | 설정 파일의 필터로 정합니다 |
| 10 | ProcessAccess | 설치 스위치 `-k` 로도 켤 수 있습니다 |

- 스위치로 켠 이벤트를 설정 파일에서 어떻게 다루는지는 [Sysmon 개념과 설정 확인](sysmon-config.md)의 "기본 동작과 명령줄 스위치" 를 봅니다.
- 세 이벤트 모두 v15.22 가 아는 가장 오래된 스키마 4.80 에 있습니다. 처음 생긴 Sysmon 버전은 공개 자료가 없습니다.
- 아래 필드 목록은 v15.22 스키마 기준입니다. 예전 버전의 필드 구성은 다를 수 있으니 실제 기록으로 확인합니다.
- 이벤트 7 의 서명 확인에는 전역 설정 SigningQueueSize 와 CheckRevocation 이 걸립니다. 두 설정의 뜻과 기본값은 설정 페이지의 "전역 설정 항목" 표에 있습니다.
- `-k` 설정이 레지스트리 어디에 남는지는 공개 자료가 없습니다. Matt Graeber 의 SysmonRuleParser.ps1 이 Parameters 키에서 읽는 ProcessAccessMasks·ProcessAccessNames 값이 후보입니다[3]. 두 값이 `-k` 설정을 담는지는 실제 레지스트리에서 확인합니다.

## 구조

### 이벤트 7 필드

| 필드 | 뜻 | 읽을 때 주의 |
|---|---|---|
| RuleName | 이 이벤트가 걸린 규칙의 이름 | |
| UtcTime | 모듈이 올라온 시각 | 서식은 [프로세스 생성](1.md)의 "시각 해석" 을 봅니다 |
| ProcessGuid · ProcessId | 모듈을 불러온 프로세스 | 이벤트 1 과 이을 때 ProcessGuid 를 씁니다 |
| Image | 그 프로세스의 실행 파일 경로 | |
| ImageLoaded | 올라온 모듈의 경로 | |
| FileVersion · Description · Product · Company · OriginalFileName | 모듈 안의 버전 정보 | 각 필드의 뜻은 [프로세스 생성](1.md)과 같습니다 |
| Hashes | 모듈 파일의 해시 | 알고리즘은 설정이 정합니다 |
| Signed · Signature · SignatureStatus | 서명 정보 | 필드 이름으로 보면 서명 여부, 서명자, 확인 결과입니다. 값 표기는 실제 기록으로 확인합니다 |
| User | 모듈을 불러온 프로세스의 계정 | |

스키마 순서는 RuleName, UtcTime, ProcessGuid, ProcessId, Image, ImageLoaded, FileVersion, Description, Product, Company, OriginalFileName, Hashes, Signed, Signature, SignatureStatus, User 입니다.

### 이벤트 8 필드

| 필드 | 뜻 |
|---|---|
| RuleName | 이 이벤트가 걸린 규칙의 이름 |
| UtcTime | 스레드를 만든 시각 |
| SourceProcessGuid · SourceProcessId · SourceImage | 스레드를 만든 프로세스 |
| TargetProcessGuid · TargetProcessId · TargetImage | 스레드가 생긴 프로세스 |
| NewThreadId (UInt32) | 새 스레드의 ID |
| StartAddress | 새 스레드가 실행을 시작할 주소 |
| StartModule | 시작 주소가 속한 모듈 (추정값) |
| StartFunction | 시작 주소에 해당하는 내보낸 함수 (추정값) |
| SourceUser · TargetUser | 두 프로세스의 계정 |

StartModule·StartFunction 은 Sysmon 이 추정한 값이라서, 시작 주소가 올라온 모듈 밖에 있거나 알려진 내보낸 함수가 아니면 빈칸일 수 있습니다. 그래서 StartModule 이 비어 있으면, 시작 주소가 파일로 올라온 모듈 밖에 있었을 수 있습니다. 이 주소는 [메모리 분석](../../../03-techniques/analysis/memory-forensics/index.md)으로 따로 확인합니다.

### 이벤트 10 필드

| 필드 | 뜻 |
|---|---|
| RuleName | 이 이벤트가 걸린 규칙의 이름 |
| UtcTime | 프로세스를 연 시각 |
| SourceProcessGUID · SourceProcessId | 대상을 연 프로세스 |
| SourceThreadId | 대상을 연 프로세스 안의 스레드 ID |
| SourceImage | 대상을 연 프로세스의 실행 파일 경로 |
| TargetProcessGUID · TargetProcessId · TargetImage | 열린 프로세스 |
| GrantedAccess (HexInt32) | 접근 권한 비트마스크 |
| CallTrace | 프로세스를 연 호출 경로 |
| SourceUser · TargetUser | 두 프로세스의 계정 |

#### 필드 이름의 대소문자

이벤트 10 은 SourceProcessGUID·TargetProcessGUID 로 GUID 를 대문자로 쓰고, 이벤트 8 은 SourceProcessGuid·TargetProcessGuid 로 씁니다. 필드 이름으로 값을 찾는 쿼리나 스크립트는 이 차이를 맞춰야 합니다.

#### GrantedAccess

이 필드는 요청한 접근 권한의 비트마스크입니다[4]. 설정 파일의 필터는 이 필드를 비트 단위로 보지 않고 문자열 그대로 비교합니다. 그래서 `is` 조건에 0x1010 을 적은 규칙은 0x1410 같은 값에 걸리지 않습니다.

접근 권한 상수는 아래와 같습니다[4].

| 이름 | 값 |
|---|---|
| PROCESS_TERMINATE | 0x0001 |
| PROCESS_CREATE_THREAD | 0x0002 |
| PROCESS_VM_OPERATION | 0x0008 |
| PROCESS_VM_READ | 0x0010 |
| PROCESS_VM_WRITE | 0x0020 |
| PROCESS_DUP_HANDLE | 0x0040 |
| PROCESS_CREATE_PROCESS | 0x0080 |
| PROCESS_SET_QUOTA | 0x0100 |
| PROCESS_SET_INFORMATION | 0x0200 |
| PROCESS_QUERY_INFORMATION | 0x0400 |
| PROCESS_SUSPEND_RESUME | 0x0800 |
| PROCESS_QUERY_LIMITED_INFORMATION | 0x1000 |
| SYNCHRONIZE | 0x00100000 |

공격과 자주 함께 보이는 값은 아래와 같습니다[4]. 켜진 비트는 위 상수 표로 푼 것입니다.

| 값 | 켜진 비트 |
|---|---|
| 0x1010 | QUERY_LIMITED_INFORMATION, VM_READ |
| 0x1438 | QUERY_LIMITED_INFORMATION, QUERY_INFORMATION, VM_WRITE, VM_READ, VM_OPERATION |
| 0x143A | 0x1438 의 비트에 CREATE_THREAD 가 더해진 값 |
| 0x0810 | SUSPEND_RESUME, VM_READ |
| 0x0820 | SUSPEND_RESUME, VM_WRITE |
| 0x0800 | SUSPEND_RESUME |
| 0x1F1FFF · 0x1FFFFF | 위 상수 표의 비트가 모두 켜져 있고, 표에 없는 비트도 켜져 있습니다 |

이 목록은 현업의 경험에서 나온 값입니다. 목록에 있는 값이라고 공격으로 단정하지 않습니다. 목록에 없는 값이라고 정상으로 보지도 않습니다.

#### CallTrace

대상 프로세스를 연 호출 경로로, DLL 과 그 안의 상대 주소 (DLL+오프셋) 가 이어져 나옵니다. 이 경로에 dbghelp.dll·dbgcore.dll 이 보이면 의심스럽게 봅니다[4].

- 배포본에는 `%sUNKNOWN(%p)%s` 서식 문자열이 있습니다 (Sysmon v15.22 기준)[2]. 모듈 밖 주소를 "UNKNOWN(주소)" 형식으로 적는 데 쓰이는지는 실제 기록으로 확인합니다.

### 이웃 이벤트: 드라이버 로드 (6)

드라이버가 올라오는 것은 이벤트 7 이 아니라 이벤트 6 (DriverLoad) 에 남고, 필드에는 ImageLoaded, Hashes, Signed, Signature, SignatureStatus 가 있습니다.

- 설정 없이 설치했을 때 이 이벤트를 기록하는지는 [Sysmon 개념과 설정 확인](sysmon-config.md)의 "기본 동작과 명령줄 스위치" 에서 봅니다.
- 올라온 드라이버를 서비스 키와 맞추는 법은 [서비스·드라이버](../../persistence/services-drivers.md)에서 다룹니다.

## 증거로서 의미

| 증명하는 것 | 증명하지 못하는 것 |
|---|---|
| (7) 기록된 시각에 이 프로세스에 이 경로의 모듈이 올라왔습니다 | 모듈 안의 코드가 무엇을 했는지 |
| (7) Sysmon 이 계산한 모듈 해시와 서명 확인 결과 | 설정이 뺀 모듈 로드가 없었다는 것 |
| (8) 원본 프로세스가 대상 프로세스 안에 스레드를 만들었습니다 | 새 스레드가 악성 코드를 실행했다는 것 |
| (8) 새 스레드의 시작 주소 | StartModule·StartFunction 이 정확하다는 것 (추정값입니다) |
| (10) 원본 프로세스가 이 접근 권한으로 대상 프로세스를 열었습니다 | 메모리를 실제로 읽거나 썼다는 것 |
| (10) 어떤 호출 경로로 열었는지 | 자격 증명을 가져갔다는 것 |
| 원본·대상 프로세스의 계정 | 키보드 앞에 누가 있었는지 |
| | 핸들 복제처럼 기록되지 않는 경로로 한 접근이 없었다는 것 (어떤 경로가 기록되지 않는지는 공개 자료가 없습니다) |

### 보고서 문장

아래 경로와 시각은 설명을 위해 만든 예입니다.

- 쓸 수 있는 문장: "이 PC 의 Sysmon 로그에는 <시각> UTC 에 이벤트 10 이 있습니다. SourceImage 는 `C:\Users\Public\t.exe`, TargetImage 는 lsass.exe, GrantedAccess 는 0x1010 입니다. CallTrace 에는 dbghelp.dll 이 보입니다."
- 쓰면 안 되는 문장: "`t.exe` 가 lsass 메모리에서 관리자 비밀번호를 빼냈다."

이벤트 10 은 프로세스를 연 기록입니다. 메모리를 읽었는지, 무엇을 가져갔는지는 적혀 있지 않습니다. 두 번째 문장을 쓰려면 다른 근거가 필요합니다.

## 시각 해석

- 세 이벤트의 UtcTime 은 UTC 입니다. 서식은 [프로세스 생성](1.md)의 "시각 해석" 을 봅니다.
- 이벤트 7 의 UtcTime 은 모듈이 올라온 때입니다.
- 서명 확인은 나중에 따로 합니다. 그래서 이벤트 7 을 로그에 쓰는 때가 로드보다 늦을 수 있습니다.
- 이벤트 8 의 UtcTime 은 스레드를 만든 때입니다.
- 이벤트 10 의 UtcTime 은 프로세스를 연 때입니다. 메모리를 읽은 때가 아닙니다.
- 같은 프로세스를 되풀이해 열면 이벤트 10 도 되풀이해 남습니다. 첫 건과 마지막 건의 시각을 함께 적습니다.
- 원본 프로세스의 이벤트 1 은 그 프로세스의 7·8·10 보다 앞섭니다. 이벤트 1 이 없으면 설정이 그 실행을 뺐거나, 로그가 덮어써졌거나, 로그가 그보다 늦게 시작했을 수 있습니다.
- 시계를 바꾼 흔적은 [시간 변경](../4616-kernel-general.md)에서 봅니다.
- 여러 기록을 한 줄로 놓는 법은 [타임라인 작성](../../../03-techniques/analysis/timeline/index.md)에서 다룹니다.

## 함정과 한계

1. **이벤트 7 이 없으니 DLL 도 안 올라왔다고 씁니다.** 이벤트 7 은 기본으로 꺼져 있습니다. 켜져 있어도 필터가 뺀 로드는 남지 않습니다.
2. **드라이버 로드를 이벤트 7 에서 찾습니다.** 드라이버는 이벤트 6 에 남습니다.
3. **8 과 10 의 필드 이름을 같다고 봅니다.** 10 은 `…ProcessGUID`, 8 은 `…ProcessGuid` 입니다. 이름이 어긋나면 쿼리가 빈 결과를 낼 수 있습니다.
4. **GrantedAccess 값 하나로 공격을 단정합니다.** 공격과 자주 함께 보이는 값 목록은 경험치입니다. 원본 프로세스, CallTrace, 앞뒤 이벤트를 함께 봅니다.
5. **필터를 비트 단위로 읽습니다.** 필터는 GrantedAccess 를 문자열로 비교합니다. 값 하나를 뺀 규칙은 비트가 하나 다른 값을 빼지 않습니다.
6. **빼기 규칙을 지나칩니다.** 이벤트 10 은 양이 많아서 흔히 진단 도구의 접근을 뺍니다. 빼기 규칙이 파일 이름만 보면, 같은 이름의 다른 실행 파일도 함께 빠집니다.
7. **StartModule·StartFunction 을 사실로 읽습니다.** 두 필드는 추정값이고, 빈칸일 수 있습니다.
8. **이벤트 10 을 메모리 읽기로 읽습니다.** 이벤트 10 은 여는 동작을 기록합니다.
9. **서명 필드의 값을 짐작합니다.** 값 표기를 밝힌 공개 문서는 없습니다. 실물 값을 여러 건 먼저 봅니다.

기록을 지우거나 Sysmon 을 멈추는 경우는 [Sysmon 개념과 설정 확인](sysmon-config.md)의 "지우기와 조작" 에서 다룹니다. 로그 삭제 흔적은 [이벤트 로그 삭제](../1102-104.md)를 봅니다.

## 직접 분석해 보기

### lsass.exe 접근 한 건 읽기

1. 이벤트 10 에서 TargetImage 가 lsass.exe 인 것을 거릅니다.
2. GrantedAccess 를 비트로 풉니다 (아래 "헥스로 한 번").
3. CallTrace 에서 어떤 DLL 을 거쳐 열었는지 봅니다. dbghelp.dll·dbgcore.dll 이 있는지도 봅니다.
4. SourceProcessGUID 와 ProcessGuid 가 같은 이벤트 1 을 찾습니다. 원본 프로세스의 명령줄, 부모, 해시를 봅니다.
5. 같은 ProcessGuid 의 이벤트 7 이 있으면, 원본 프로세스가 불러온 모듈을 봅니다.
6. 같은 ProcessGuid 의 이벤트 11 에서, 비슷한 시각에 새 파일을 만들었는지 봅니다.
7. SourceImage 가 이 조직의 진단 도구인지 확인합니다. 설정의 빼기 규칙과도 맞춰 봅니다.

아래는 이 흐름을 보이려고 만든 예시입니다. 실제 기록에서 나온 값이 아닙니다.

| 순서 | 이벤트 | 잇는 값 | 주요 필드 |
|---|---|---|---|
| 1 | 1 | ProcessGuid {A…} | Image `C:\Users\Public\t.exe`, ParentImage `cmd.exe` |
| 2 | 7 | ProcessGuid {A…} | ImageLoaded 에 dbghelp.dll |
| 3 | 10 | SourceProcessGUID {A…} | TargetImage lsass.exe, GrantedAccess 0x1010 |
| 4 | 11 | ProcessGuid {A…} | TargetFilename `C:\Users\Public\out.bin` |

### 헥스로 한 번

GrantedAccess 는 스키마에서 HexInt32 형식입니다. 32비트 정수를 16진수로 보여 줍니다. 아래는 접근 권한 상수 표로 만든 예시입니다. 실제 기록에서 나온 값이 아닙니다.

```
GrantedAccess  0x1438
2진수          0001 0100 0011 1000
```

켜진 비트를 오른쪽에서부터 읽습니다.

| 비트 값 | 이름 |
|---|---|
| 0x0008 | PROCESS_VM_OPERATION |
| 0x0010 | PROCESS_VM_READ |
| 0x0020 | PROCESS_VM_WRITE |
| 0x0400 | PROCESS_QUERY_INFORMATION |
| 0x1000 | PROCESS_QUERY_LIMITED_INFORMATION |

1. 다섯 값을 더하면 0x1438 입니다.
2. 메모리 읽기 (VM_READ) 와 쓰기 (VM_WRITE) 비트가 모두 켜져 있습니다.
3. 스레드 만들기 (CREATE_THREAD, 0x0002) 비트는 꺼져 있습니다. 이 비트까지 켜면 0x143A 입니다.

PowerShell 에서는 `(0x1438 -band 0x0010) -ne 0` 이 True 면 PROCESS_VM_READ 비트가 켜져 있습니다.

EVTX 레코드 안에서 필드 값이 어떻게 저장되는지는 [이벤트 로그 형식](../../../01-foundations/database-log-formats/evtx-evt-etl/index.md)에서 다룹니다.

### 공개 도구로 한 번

- 이벤트 뷰어에서 Sysmon 채널을 열고 이벤트 ID 6, 7, 8, 10 으로 거릅니다.
- PowerShell 에서는 `Get-WinEvent -FilterHashtable @{LogName='Microsoft-Windows-Sysmon/Operational'; Id=10}` 처럼 거릅니다. 떼어 낸 EVTX 파일은 `-Path` 로 엽니다.
- 공개 EVTX 해석 도구(예: EvtxECmd, python-evtx)로 필드를 표로 뽑습니다.
- 여러 대의 로그를 규칙으로 검색할 때는 [이벤트 로그 규칙 검색](../../../03-techniques/analysis/sigma-rules.md)을 봅니다.

도구를 쓸 때 다음을 확인합니다.

- 8 과 10 의 GUID 필드를 도구가 같은 열로 합치는지, 따로 두는지 확인합니다.
- GrantedAccess 를 16진수 그대로 보여 주는지 확인합니다.
- CallTrace 를 도구가 자르지 않는지 확인합니다.
- 레코드 한두 개는 XML 원문과 맞춰 봅니다. 방법은 [도구 결과 교차 검증](../../../03-techniques/reporting/tool-validation.md)에서 다룹니다.

## 실습

직접 만든 Windows 11 가상 머신에 Sysmon 을 설치하고 해 봅니다. 각 단계의 시각을 적어 둡니다.

1. `-l` 없이 설치하고 프로그램 하나를 실행합니다. 이벤트 7 이 남는지 보십시오. 그다음 ImageLoad 필터로 그 프로그램만 넣어 켭니다.
2. 서명된 DLL 과 서명 없는 DLL 을 한 번씩 불러옵니다. Signed·Signature·SignatureStatus 값 표기를 적어 보십시오.
3. DLL 을 불러온 직후 그 파일을 지웁니다. 지워졌다는 표시가 어느 필드에 남는지 찾아 보십시오.
4. 작업 관리자에서 프로세스 하나의 덤프 파일을 만듭니다. 이벤트 10 의 GrantedAccess 와 CallTrace 를 적고, dbghelp.dll·dbgcore.dll 이 보이는지 확인하십시오.
5. GrantedAccess 에 `is` 조건으로 값 하나를 넣은 규칙을 만듭니다. 비트가 하나 다른 접근이 이 규칙에 걸리는지 보십시오.
6. 이벤트 8 과 10 의 XML 원문을 나란히 놓고 GUID 필드 이름을 비교하십시오.
7. CallTrace 에 "UNKNOWN(" 으로 시작하는 항목이 나오는지 찾아 보십시오. 나온다면 그 주소가 어느 메모리 영역인지 메모리 분석으로 확인하십시오.
