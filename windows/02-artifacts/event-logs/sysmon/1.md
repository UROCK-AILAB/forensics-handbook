# 프로세스 생성 (이벤트 1)

Sysmon 이벤트 1 (ProcessCreate) 은 새 프로세스가 만들어질 때 남습니다. 새 프로세스와 부모 프로세스의 명령줄, 실행 파일의 해시와 버전 정보, 실행한 계정과 로그온 세션이 한 이벤트에 함께 적힙니다. 프로세스마다 붙는 ProcessGuid 로 같은 프로세스의 다른 Sysmon 이벤트를 이을 수 있습니다. 시각은 UTC 입니다.

## 무엇을 기록하나 · 왜 생기나

이 이벤트는 새 프로세스가 만들어질 때 남습니다. 새 프로세스와 부모 프로세스의 전체 명령줄을 모두 적으므로 어떤 인자로 실행했는지 알 수 있습니다. Hashes 필드에는 실행 파일 전체의 해시가 들어가며, 어떤 알고리즘으로 계산할지는 설정이 정합니다. 실행 파일 (PE) 안의 버전 정보도 옮겨 적습니다.

보안 로그의 프로세스 생성 이벤트 4688 과 같은 정보를 담고, 거기에 PE 정보와 해시를 더합니다. 4688 은 [프로세스 생성 (4688)](../4688.md)에서 다룹니다.

설정 없이 설치했을 때 기록하는 이벤트와 필터 규칙은 [Sysmon 개념과 설정 확인](sysmon-config.md)에서 다룹니다.

### ProcessGuid 와 LogonGuid

PID 는 프로세스가 끝나면 다른 프로세스가 다시 쓸 수 있습니다. 그래서 Sysmon 은 PID 가 다시 쓰여도 사건을 이어 볼 수 있게 프로세스마다 ProcessGuid 를 붙입니다. 이 값은 도메인 안에서 이 프로세스에 고유합니다. 로그온 세션마다 LogonGuid 도 붙습니다.

네트워크(3)·DNS(22)·파일(11·23·26)·레지스트리(12·13·14) 이벤트에도 ProcessGuid 필드가 있어서, 이 필드로 이벤트 1 과 잇습니다. ProcessGuid·LogonGuid 를 무엇으로 조립하는지 설명한 공개 자료는 없습니다.

## 위치와 버전별 차이

채널, 로그 파일 위치, 설치 흔적은 [Sysmon 개념과 설정 확인](sysmon-config.md)에서 다룹니다. 설정 파일의 필터 태그는 ProcessCreate 이고, 이 이벤트는 v15.22 가 아는 가장 오래된 스키마 4.80 에도 있습니다. 아래 필드 목록은 v15.22 스키마 기준이며, 예전 Sysmon 버전을 쓴 기기라면 필드 구성을 로그에서 직접 확인합니다.

## 구조

### 필드 목록

v15.22 스키마의 순서대로 적었습니다. 괄호 안은 스키마가 정한 형식입니다.

| 필드 | 뜻 | 읽을 때 주의 |
|---|---|---|
| RuleName | 이 이벤트가 걸린 규칙의 이름 | 규칙에 name 을 붙였을 때 그 이름이 남습니다 |
| UtcTime | 프로세스가 만들어진 시각 | 문자열 필드입니다. 아래 "시각 해석" 을 봅니다 |
| ProcessGuid (GUID) | 새 프로세스의 GUID | 다른 이벤트와 이을 때 씁니다 |
| ProcessId (UInt32) | 새 프로세스의 PID | 다시 쓰일 수 있습니다 |
| Image | 새 프로세스의 실행 파일 경로 | |
| FileVersion | PE 버전 정보의 파일 버전 | |
| Description | PE 버전 정보의 설명 | |
| Product | PE 버전 정보의 제품 이름 | |
| Company | PE 버전 정보의 회사 이름 | |
| OriginalFileName | PE 버전 정보에 적힌 원래 파일 이름 | 이름을 바꾼 파일이면 Image 의 파일 이름과 다릅니다 |
| CommandLine | 새 프로세스의 명령줄 | FieldSizes 설정으로 잘릴 수 있습니다 |
| CurrentDirectory | 새 프로세스의 현재 폴더 | |
| User | 프로세스를 만든 계정 이름 (도메인 포함) | |
| LogonGuid (GUID) | 프로세스를 만든 사용자의 로그온 세션 GUID | |
| LogonId (HexInt64) | 프로세스를 만든 사용자의 로그온 ID | 16진수로 적힙니다 |
| TerminalSessionId (UInt32) | 세션 번호 | |
| IntegrityLevel | 프로세스의 무결성 수준 (Integrity Level) | 아래 값 후보를 봅니다 |
| Hashes | 실행 파일 전체의 해시 | 표기 형식은 실제 데이터로 확인합니다 |
| ParentProcessGuid (GUID) | 부모 프로세스의 GUID | 부모의 이벤트 1 을 찾을 때 씁니다 |
| ParentProcessId (UInt32) | 부모 프로세스의 PID | |
| ParentImage | 부모 프로세스의 실행 파일 경로 | |
| ParentCommandLine | 부모 프로세스의 명령줄 | |
| ParentUser | 부모 프로세스의 계정 이름 | |

- 배포본에는 "Low", "Medium", "High", "System", "AppContainer" 문자열이 있습니다. IntegrityLevel 값 후보로 보입니다 (Sysmon v15.22 기준).
- FileVersion·Description·Product·Company·OriginalFileName 은 실행 파일 안의 정보에서 가져옵니다. 이 정보가 어디에 어떻게 저장되는지는 [실행 파일 메타데이터](../../embedded-metadata/pe-header-version-info-digital-signature.md)에서 다룹니다.

### 짝이 되는 종료 이벤트 (5)

이벤트 5 (ProcessTerminate) 는 프로세스가 끝날 때 남습니다. 필드는 RuleName, UtcTime, ProcessGuid, ProcessId, Image, User 입니다.

이벤트 1 과 5 를 ProcessGuid 로 이으면 프로세스가 언제 시작해 언제 끝났는지 알 수 있습니다. 이벤트 5 에는 명령줄과 해시가 없으므로 무엇을 실행했는지는 이벤트 1 에서 봅니다.

### 프로세스 나무 잇기

자식 이벤트의 ParentProcessGuid 는 부모 프로세스의 ProcessGuid 입니다. 이 값으로 부모의 이벤트 1 을 찾고, 그 부모의 ParentProcessGuid 로 다시 올라갑니다.

1. 의심 프로세스의 이벤트 1 을 찾습니다.
2. ProcessGuid 가 그 ParentProcessGuid 와 같은 이벤트 1 을 찾습니다.
3. 부모 쪽 이벤트가 없어질 때까지 반복합니다.
4. 거꾸로, 의심 프로세스의 ProcessGuid 를 ParentProcessGuid 로 적은 이벤트 1 을 찾으면 자식 프로세스가 나옵니다.

부모의 이벤트 1 이 없을 수 있습니다. 설정이 그 실행을 뺐거나, 로그가 덮어써졌거나, 로그가 그보다 늦게 시작했을 수 있는데, 이때도 ParentImage 와 ParentCommandLine 은 자식 이벤트에 남아 있습니다.

## 증거로서 의미

| 증명하는 것 | 증명하지 못하는 것 |
|---|---|
| 기록된 시각에 이 실행 파일 경로로 프로세스가 만들어졌습니다 | 키보드 앞에 누가 있었는지 |
| 그때의 명령줄과 현재 폴더 | 프로세스가 무엇을 했는지 (다른 이벤트와 아티팩트로 봅니다) |
| 부모 프로세스의 경로, 명령줄, 계정 | 명령줄과 부모 PID 가 조작되지 않았다는 것 |
| 프로세스를 만든 계정, 로그온 세션, 무결성 수준 | PE 버전 정보가 진짜라는 것 (파일을 만든 쪽이 적는 값입니다) |
| Sysmon 이 계산한 실행 파일 해시 | 설정이 기록하지 않은 실행이 없었다는 것 |

### 보고서 문장

아래 경로와 시각은 설명을 위해 만든 예입니다.

- 쓸 수 있는 문장: "이 PC 의 Sysmon 로그에는 <시각> UTC 에 이벤트 1 이 있습니다. Image 는 `C:\Users\Public\a.exe`, OriginalFileName 은 다른 파일 이름입니다. 부모 프로세스는 `cmd.exe` 이고, User 는 <계정> 입니다."
- 쓰면 안 되는 문장: "<계정> 사용자가 이름을 바꾼 해킹 도구를 일부러 실행했다."

두 번째 문장은 기록에 없는 사람과 의도를 적습니다. 계정이 곧 사람이라고 판단하려면 [그 시각에 PC 를 쓴 사람이 누구인가](../../../04-scenarios/activity/user-attribution.md)의 근거를 함께 적습니다.

## 시각 해석

- UtcTime 은 UTC 이며 문자열 필드입니다. 배포본에는 `%04u-%02u-%02u %02u:%02u:%02u.%03u` 서식 문자열이 있어서 "YYYY-MM-DD hh:mm:ss.밀리초" 형식으로 보입니다 (Sysmon v15.22 기준). 다른 Sysmon 이벤트의 UtcTime 도 같은 서식으로 봅니다.
- 이벤트 로그 레코드에는 UtcTime 필드와 별도로 레코드의 기록 시각이 있습니다. 두 값이 다르면 둘 다 적습니다. 레코드 시각은 [이벤트 로그 형식](../../../01-foundations/database-log-formats/evtx-evt-etl/index.md)에서 다룹니다.
- 부팅 초기 활동은 드라이버가 모아 두었다가 서비스가 뜬 뒤 쓰는 것으로 보입니다. 그래서 부팅 직후 이벤트는 UtcTime 과 로그에 쓴 시각이 벌어질 수 있습니다.
- 이벤트 5 의 UtcTime 에서 이벤트 1 의 UtcTime 을 빼면 프로세스가 돈 시간입니다.
- 시각은 그 컴퓨터의 시계를 따릅니다. 시계를 바꾼 흔적은 [시간 변경](../4616-kernel-general.md)에서 봅니다.
- 여러 기록을 한 줄로 놓는 법은 [타임라인 작성](../../../03-techniques/analysis/timeline/index.md)에서 다룹니다.

## 함정과 한계

1. **PID 로 이벤트를 잇습니다.** PID 는 다시 쓰이므로 ProcessGuid 로 잇습니다.
2. **Image 의 파일 이름만 봅니다.** 이름을 바꾼 도구는 Image 로는 알아보기 어렵습니다. OriginalFileName 과 해시를 함께 봅니다. 두 이름이 다르다는 사실은 단서일 뿐 악성의 증거는 아닙니다.
3. **잘린 명령줄을 전체로 읽습니다.** FieldSizes 설정으로 CommandLine·Image 같은 필드 길이를 줄일 수 있습니다. 명령줄이 짧게 끊겨 있으면 설정부터 확인합니다.
4. **Hashes 필드를 한 가지 형식으로 짐작합니다.** 어떤 알고리즘이 들어가는지는 설정마다 다릅니다. 도구로 뽑을 때 실제 필드 값을 한 번 확인합니다.
5. **PE 정보를 믿습니다.** Description·Company 같은 값은 파일을 만든 쪽이 적습니다. 서명과 해시로 따로 확인합니다.
6. **부모 관계를 끝까지 믿습니다.** 명령줄과 부모 PID 를 위조할 수 있는지, Sysmon 이 시작하기 전에 뜬 프로세스를 어떻게 적는지 설명한 공개 자료는 없습니다. 부모 관계 하나로 결론을 내지 않습니다.
7. **LogonId 형식을 맞추지 않고 비교합니다.** LogonId 는 16진수입니다. 다른 로그와 맞출 때는 표기(0x 접두어, 자릿수)를 맞춥니다.
8. **기록이 없으니 실행도 없었다고 씁니다.** 설정이 뺀 실행은 남지 않습니다.

### 지우기와 조작

- 로그를 지우거나 Sysmon 드라이버를 내리는 경우는 [Sysmon 개념과 설정 확인](sysmon-config.md)의 "지우기와 조작" 에서 다룹니다.
- 로그 삭제 흔적은 [이벤트 로그 삭제](../1102-104.md)를 봅니다.
- 실행 파일 이름을 바꾸는 경우는 위 함정 2번을 봅니다.

## 직접 분석해 보기

### 헥스로 한 번

ProcessGuid·LogonGuid·ParentProcessGuid 는 스키마에서 GUID 형식입니다. 뷰어는 이 값을 `{…}` 형식 문자열로 보여 줍니다. GUID 16바이트를 문자열로 옮기는 규칙은 [윈도 식별자 형식](../../../01-foundations/value-decoding/sid-guid-clsid-known-folder-id.md)에서 다룹니다.

아래 값은 바이트 순서를 보이려고 만든 값입니다. Sysmon 이 만든 값이 아닙니다.

```
문자열  {00112233-4455-6677-8899-AABBCCDDEEFF}
바이트  33 22 11 00  55 44  77 66  88 99  AA BB CC DD EE FF
```

1. 앞의 세 덩어리(4바이트·2바이트·2바이트)는 바이트 순서가 뒤집혀 들어갑니다.
2. 뒤의 두 덩어리(2바이트·6바이트)는 적힌 순서 그대로 들어갑니다.

이벤트 로그 파일 안에서 GUID 형식 필드가 어떤 모양으로 저장되는지는 [이벤트 로그 형식](../../../01-foundations/database-log-formats/evtx-evt-etl/index.md)에서 확인합니다. 지운 레코드나 원시 데이터에서 ProcessGuid 를 찾을 때는 문자열 형식과 바이트 형식을 둘 다 찾습니다.

### 공개 도구로 한 번

- 이벤트 뷰어에서 Sysmon 채널을 열고 이벤트 ID 1 로 거릅니다. "작업 범주" 열에 태그 이름이 보입니다.
- PowerShell 에서는 `Get-WinEvent -FilterHashtable @{LogName='Microsoft-Windows-Sysmon/Operational'; Id=1}` 처럼 거릅니다. 떼어 낸 EVTX 파일은 `-Path` 로 엽니다.
- 공개 EVTX 해석 도구(예: EvtxECmd, python-evtx, libevtx 의 evtxexport)로 필드를 표로 뽑습니다.
- 규칙으로 여러 대의 로그를 살펴볼 때는 [이벤트 로그 규칙 검색](../../../03-techniques/analysis/sigma-rules.md)을 봅니다.

도구를 쓸 때 다음을 확인합니다.

- UtcTime 을 그대로 보여 주는지, 현지 시각으로 바꿔 보여 주는지 확인합니다.
- CommandLine 을 도구가 다시 자르지 않는지 확인합니다.
- 레코드 한두 개는 XML 원문과 맞춰 봅니다. 방법은 [도구 결과 교차 검증](../../../03-techniques/reporting/tool-validation.md)에서 다룹니다.

## 실습

직접 만든 Windows 11 가상 머신에 Sysmon 을 설치하고 해 봅니다. 각 단계의 시각을 적어 둡니다.

1. 시스템 실행 파일 하나를 다른 이름으로 복사해 실행합니다. Image 와 OriginalFileName 을 비교하십시오.
2. `cmd.exe` 에서 `powershell.exe` 를 띄우고, 그 안에서 다른 명령을 실행합니다. ProcessGuid 와 ParentProcessGuid 로 프로세스 나무를 그려 보십시오.
3. 프로그램 하나를 실행했다가 닫습니다. 이벤트 1 과 5 의 UtcTime 으로 돈 시간을 구하십시오.
4. FieldSizes 에 `CommandLine:100` 을 넣고 긴 명령줄을 실행합니다. 어떻게 잘려 남는지 보십시오.
5. 해시 알고리즘을 바꿔 가며 설치합니다. Hashes 필드의 표기 형식을 적어 보십시오.
6. 보안 로그의 4688 을 함께 켜 둡니다. 같은 실행에 대해 두 이벤트의 필드를 비교하십시오.
