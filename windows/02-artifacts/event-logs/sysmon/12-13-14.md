# 레지스트리 변경 (이벤트 12·13·14)

## 한 줄 요약

Sysmon 이벤트 12·13·14 는 프로세스가 레지스트리를 바꿀 때 남습니다. 12 는 키·값의 생성과 삭제, 13 은 값 수정, 14 는 키·값 이름 바꿈입니다. 세 이벤트 모두 바꾼 프로세스와 대상 경로가 적힙니다. 경로의 루트 키는 줄인 이름으로 적힙니다. 시각은 UTC 입니다.

## 무엇을 기록하나 · 왜 생기나

| 이벤트 | 남는 때 | 더 적는 것 |
|---|---|---|
| 12 | 키나 값을 만들거나 지울 때 | |
| 13 | 값을 수정할 때 | DWORD·QWORD 값이면 쓴 값 |
| 14 | 키나 값의 이름을 바꿀 때 | 바뀐 새 이름 |

- Sysinternals 문서는 자동 실행 위치의 변경이나 악성코드의 레지스트리 변경을 지켜보는 데 이 이벤트들을 쓰라고 적습니다.
- 세 이벤트는 필터 태그 RegistryEvent 를 함께 씁니다. 그래서 설정 파일에서는 세 이벤트의 규칙을 이 태그 하나로 적습니다.
- 필터 규칙 쓰는 법은 [Sysmon 개념과 설정 확인](/02-artifacts/event-logs/sysmon/sysmon-config.md)에서 다룹니다.

## 위치와 버전별 차이

- 채널과 로그 파일 위치는 [Sysmon 개념과 설정 확인](/02-artifacts/event-logs/sysmon/sysmon-config.md)에서 다룹니다.
- 세 이벤트 모두 v15.22 가 아는 가장 오래된 스키마 4.80 에 있습니다.
- 아래 칸 목록은 v15.22 스키마 기준입니다.

### 루트 키를 줄여 적는 규칙

Sysinternals 문서는 대상 경로의 앞부분을 아래처럼 줄여 적는다고 밝힙니다.

| 원래 경로 | 이벤트에 적히는 꼴 |
|---|---|
| HKEY_LOCAL_MACHINE | HKLM |
| HKEY_USERS | HKU |
| HKEY_LOCAL_MACHINE\System\ControlSet00x | HKLM\System\CurrentControlSet |
| HKEY_LOCAL_MACHINE\Classes | HKCR |

- 마지막 줄은 문서에 적힌 그대로 옮겼습니다.
- 대응표대로라면 이벤트에는 실제로 몇 번 ControlSet 이었는지가 남지 않습니다. 이 점은 대응표에서 나온 해석입니다.
- 대응표에는 HKEY_CURRENT_USER 항목이 없습니다. 현재 사용자 키에 쓴 변경이 `HKU\<SID>\…` 꼴로 남는지는 확인하지 못했습니다.

## 구조

### 칸 목록

v15.22 스키마의 순서대로 적었습니다.

| 이벤트 | 칸 |
|---|---|
| 12 | RuleName, EventType, UtcTime, ProcessGuid, ProcessId, Image, TargetObject, User |
| 13 | RuleName, EventType, UtcTime, ProcessGuid, ProcessId, Image, TargetObject, Details, User |
| 14 | RuleName, EventType, UtcTime, ProcessGuid, ProcessId, Image, TargetObject, NewName, User |

| 칸 | 뜻 | 읽을 때 주의 |
|---|---|---|
| EventType | 변경의 종류 | 아래 값 후보를 봅니다 |
| ProcessGuid · ProcessId | 레지스트리를 바꾼 프로세스 | [프로세스 생성](/02-artifacts/event-logs/sysmon/1.md)과 잇습니다 |
| Image | 그 프로세스의 실행 파일 경로 | |
| TargetObject | 바뀐 키나 값의 경로 | 루트 키를 줄여 적습니다 |
| Details (13) | 쓴 값 | 아래 서식을 봅니다 |
| NewName (14) | 바뀐 새 이름 | |
| User | 그 프로세스의 계정 | |

### EventType 값 후보

배포본에는 "CreateKey", "DeleteKey", "CreateValue", "DeleteValue", "SetValue", "RenameKey" 문자열이 있습니다. EventType 값 후보로 보입니다 (확인 범위: v15.22 배포본 실행 파일 안의 문자열). 값마다 어느 이벤트 ID 에 나오는지는 확인하지 못했습니다. 그래서 거를 때는 이벤트 ID 와 EventType 을 함께 봅니다.

### Details 칸 서식

배포본에는 아래 서식 문자열이 있습니다 (확인 범위: v15.22 배포본 실행 파일 안의 문자열).

| 서식 문자열 | 읽는 법 |
|---|---|
| `DWORD (0x%08x)` | DWORD 값을 16진수 8자리로 적습니다 |
| `QWORD (0x%08x-0x%08x)` | QWORD 값을 16진수 8자리 두 조각으로 나눠 적습니다. 어느 조각이 앞인지는 확인하지 못했습니다 |
| `Binary Data` | 이진 값에 붙는 문자열로 보입니다. 이진 값의 내용 대신 이 문자열만 남는지는 확인하지 못했습니다 |

문자열 값이 Details 에 그대로 나오는지도 확인하지 못했습니다.

## 증거로서 의미

| 증명하는 것 | 증명하지 못하는 것 |
|---|---|
| 기록된 시각에 이 프로세스가 이 키나 값을 만들었거나, 지웠거나, 바꿨거나, 이름을 바꿨습니다 | 바꾸기 전의 값 (이전 값 칸이 없습니다) |
| 바꾼 프로세스의 경로와 계정 | 그 값이 지금도 남아 있다는 것 |
| DWORD·QWORD 값이면 쓴 값 | 몇 번 ControlSet 을 바꿨는지 |
| 이름을 바꿨다면 새 이름 | 사람이 직접 바꿨는지, 프로그램이 스스로 바꿨는지 |
| | 설정이 뺀 경로의 변경이 없었다는 것 |
| | 운영체제가 돌지 않을 때 하이브 파일을 직접 고친 변경 (Sysmon 이 돌지 않으므로 남지 않습니다) |

### 보고서 문장

아래 경로와 시각은 설명을 위해 만든 예입니다.

- 쓸 수 있는 문장: "이 PC 의 Sysmon 로그에는 <시각> UTC 에 이벤트 13 이 있습니다. `C:\Users\Public\a.exe` 가 Run 키 아래 `Updater` 값을 썼습니다. TargetObject 는 <이벤트에 적힌 경로> 입니다. 같은 값이 수집한 하이브에도 남아 있습니다."
- 쓰면 안 되는 문장: "공격자가 악성코드를 자동 실행되게 등록했다."

두 번째 문장은 사람과 의도, 파일의 성격을 적습니다. 자동 실행으로 판단하려면 그 값이 실제로 쓰이는 위치인지, 그 뒤에 실행 흔적이 있는지를 함께 적습니다.

## 시각 해석

- UtcTime 은 UTC 입니다. 서식은 [프로세스 생성](/02-artifacts/event-logs/sysmon/1.md)의 "시각 해석" 을 봅니다.
- 하이브의 키에는 마지막 기록 시각이 하나만 있습니다. 그 뒤에 다른 변경이 있으면 앞선 변경의 시각은 하이브에서 사라집니다.
- Sysmon 이벤트는 변경마다 시각을 남깁니다. 그래서 하이브의 마지막 기록 시각보다 앞선 변경도 이벤트로 볼 수 있습니다.
- 두 시각을 맞출 때 하이브 쪽 시각 형식은 [시각 값 형식](/01-foundations/value-decoding/filetime-unix-webkit-dos-ole.md)에서, 마지막 기록 시각의 위치는 [레지스트리 하이브 구조](/01-foundations/database-log-formats/registry-hive/index.md)에서 다룹니다.

## 함정과 한계

1. **CurrentControlSet 을 그대로 하이브에서 찾습니다.** 오프라인 SYSTEM 하이브에는 CurrentControlSet 이 없습니다. 당시 어느 ControlSet 을 썼는지 하이브에서 따로 확인하고, 그 번호 키에서 찾습니다.
2. **현재 사용자 키 경로를 짐작합니다.** HKEY_CURRENT_USER 변경이 어떤 꼴로 남는지 확인하지 못했습니다. `HKU\<SID>` 꼴이면 SID 를 [사용자 프로필 목록](/02-artifacts/system-account/profilelist.md)으로 계정에 잇습니다.
3. **HKCR 줄임을 그대로 풉니다.** 대응표의 HKCR 줄은 문서에 적힌 그대로입니다. 실물에서 TargetObject 와 하이브 경로를 맞춰 확인합니다.
4. **Details 를 모든 값 형식에 똑같이 읽습니다.** DWORD·QWORD 는 쓴 값이 남지만, QWORD 두 조각의 순서는 확인하지 못했습니다. 문자열·이진 값이 어떻게 남는지도 확인하지 못했습니다.
5. **EventType 과 이벤트 ID 를 한쪽만 보고 거릅니다.** 둘의 대응을 확인하지 못했습니다. 둘을 함께 봅니다.
6. **기록이 없으니 변경도 없었다고 씁니다.** 레지스트리 변경은 양이 많아서 흔히 특정 경로만 넣습니다. 설정에서 넣지 않은 경로는 남지 않습니다.
7. **하이브 파일을 직접 고친 경우를 잊습니다.** 운영체제가 돌지 않을 때 하이브를 고치면 Sysmon 기록이 남지 않습니다.

### 지우기와 조작

- 기록을 지우거나 Sysmon 을 멈추는 경우, Sysmon 자신의 규칙 값을 지우는 경우는 [Sysmon 개념과 설정 확인](/02-artifacts/event-logs/sysmon/sysmon-config.md)의 "지우기와 조작" 에서 다룹니다.
- 값을 쓰고 곧바로 지우면 하이브에서는 그 값을 볼 수 없습니다. 이때 같은 TargetObject 의 12·13 이벤트가 남아 있는지 봅니다.

## 직접 분석해 보기

### 헥스로 한 번

REG_DWORD 값은 4바이트를, REG_QWORD 값은 8바이트를 리틀 엔디언으로 저장합니다. 아래는 서식 문자열로 만든 예시입니다. 검체에서 나온 값이 아니고, 실제 로그로 확인한 표기도 아닙니다.

```
REG_DWORD 값 1
  하이브의 값 데이터   01 00 00 00
  Details 예상 꼴      DWORD (0x00000001)

REG_QWORD 값 0x0000000100000002
  하이브의 값 데이터   02 00 00 00 01 00 00 00
  Details 예상 꼴      QWORD (0x00000001-0x00000002) 또는 QWORD (0x00000002-0x00000001)
```

1. DWORD 는 하이브의 `01 00 00 00` 을 뒤집어 읽은 0x00000001 이 Details 에 들어갈 것으로 보입니다.
2. QWORD 는 8바이트를 앞 4바이트와 뒤 4바이트로 나눠 적습니다. 어느 쪽이 앞에 오는지 확인하지 못해서 두 꼴을 모두 적었습니다.
3. 하이브의 값과 Details 가 다르면, 이벤트 뒤에 값이 다시 바뀌었는지 같은 TargetObject 의 뒤 이벤트를 찾습니다.

하이브 안에서 값 데이터를 찾아가는 법은 [레지스트리 하이브 구조](/01-foundations/database-log-formats/registry-hive/index.md)에서 다룹니다.

### 공개 도구로 한 번

1. 이벤트 뷰어나 PowerShell 의 `Get-WinEvent` 로 Sysmon 채널에서 이벤트 12·13·14 를 뽑습니다.
2. 공개 EVTX 해석 도구(예: EvtxECmd, python-evtx)로 칸을 표로 뽑아 TargetObject 로 묶습니다.
3. TargetObject 의 줄인 루트 키를 원래 하이브로 바꿉니다. HKLM 은 SYSTEM·SOFTWARE 같은 하이브 파일로, HKU 는 사용자별 NTUSER.DAT 로 찾아갑니다.
4. 공개 레지스트리 뷰어(예: Registry Explorer, RegRipper)로 그 키를 열어 지금 값과 마지막 기록 시각을 봅니다.
5. 이벤트의 Details·NewName·시각과 하이브 쪽 값을 맞춰 봅니다.

도구 결과는 레코드 한두 개로 원문과 맞춰 봅니다. 방법은 [도구 결과 교차 검증](/03-techniques/reporting/tool-validation.md)에서 다룹니다.

## 실습

직접 만든 Windows 11 가상 머신에 Sysmon 을 설치하고, RegistryEvent 로 실습용 키 하나를 넣는 설정을 씁니다. 각 단계의 시각을 적어 둡니다.

1. `reg add` 로 실습용 키를 만들고, DWORD·QWORD·문자열·이진 값을 하나씩 씁니다. 각 이벤트의 EventType 과 Details 를 적어 보십시오. QWORD 두 조각의 순서도 여기서 확인합니다.
2. 같은 값을 지우고, 키도 지웁니다. 어느 이벤트 ID 에 어떤 EventType 이 나오는지 표로 만드십시오.
3. 레지스트리 편집기에서 키 이름을 바꿉니다. 이벤트 14 의 TargetObject 와 NewName 을 보십시오.
4. 현재 사용자 키 아래에 값을 씁니다. TargetObject 가 어떤 꼴로 남는지 보십시오.
5. `HKLM\SYSTEM\CurrentControlSet` 아래에 값을 씁니다. TargetObject 에 ControlSet 번호가 남는지 보십시오.
6. 하이브를 수집해 실습 키의 마지막 기록 시각을 이벤트의 UtcTime 과 비교하십시오.
