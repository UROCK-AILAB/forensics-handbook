# 파일 생성·삭제 (이벤트 11·23·26)

Sysmon 이벤트 11 (FileCreate) 은 파일이 새로 만들어지거나 덮어써질 때 남습니다. 이벤트 23 (FileDelete) 은 파일 삭제를 기록하고, 지운 파일을 보관 폴더에 복사해 둡니다. 이벤트 26 (FileDeleteDetected) 은 삭제를 기록만 하고 파일은 보관하지 않습니다. 세 이벤트 모두 어느 프로세스가 어느 경로에 그 일을 했는지 적힙니다. 시각은 UTC 입니다.

## 무엇을 기록하나 · 왜 생기나

### 이벤트 11 (FileCreate)

파일이 새로 만들어질 때 남고, 있던 파일을 덮어쓸 때도 남습니다. 시작프로그램 폴더 같은 자동 실행 위치와 임시·다운로드 폴더를 지켜보는 데 이 이벤트를 씁니다.

### 이벤트 23 (FileDelete, 보관)

파일 삭제를 기록하고, 지운 파일을 보관 폴더 (ArchiveDirectory) 에 저장합니다. 어떤 파일을 보관할지는 전역 설정 CopyOnDeletePE, CopyOnDeleteSIDs, CopyOnDeleteExtensions, CopyOnDeleteProcesses 로 정하며, 각 설정의 뜻은 [Sysmon 개념과 설정 확인](sysmon-config.md)에서 다룹니다. 평소에 켜 두면 보관 폴더가 지나치게 커질 수 있어서 저장 없이 기록만 하는 이벤트 26 이 따로 있습니다.

### 이벤트 26 (FileDeleteDetected, 기록만)

파일 삭제를 기록만 하고, 지운 파일은 보관하지 않습니다.

## 위치와 버전별 차이

채널, 로그 파일 위치, 필터 규칙은 [Sysmon 개념과 설정 확인](sysmon-config.md)에서 다룹니다. 필터 태그는 FileCreate (11), FileDelete (23), FileDeleteDetected (26) 입니다. 세 이벤트 모두 v15.22 가 아는 가장 오래된 스키마 4.80 에 있습니다. 예전 Sysmon 을 쓴 기기라면 23·26 이 있는 판인지 먼저 확인합니다.

### 보관 폴더

ArchiveDirectory 는 각 볼륨 루트에 만드는 폴더의 이름이며 기본값은 "Sysmon" 입니다. C 드라이브라면 기본 위치는 `C:\Sysmon` 입니다. 이 폴더에는 SYSTEM 만 들어가도록 ACL 이 걸리므로, 라이브 시스템에서 들여다보려면 `psexec -sid cmd` 처럼 SYSTEM 권한으로 연 창이 필요합니다.

폴더 이름은 설정이나 설치 스위치 `-a` 로 바꿀 수 있어서, 실물에서는 적용된 설정에서 이름을 먼저 확인합니다.

배포본에는 보관 폴더 조건에 관한 문자열이 있습니다 (Sysmon v15.22 기준).

| 문자열 | 풀이 |
|---|---|
| Archive directory must be a single path component. | 보관 폴더 이름은 경로 한 단계여야 합니다 |
| The ArchiveDirectory must not be a reparse point and its ACL must be limited to System access. Archiving is disabled. | 보관 폴더가 재분석 지점이거나 ACL 이 SYSTEM 전용이 아니면 보관을 끕니다 |

## 구조

### 필드 비교

v15.22 스키마 기준입니다. 표의 순서는 스키마 순서가 아니라 비교하기 쉬운 순서입니다.

| 필드 | 11 | 23 | 26 | 뜻 |
|---|---|---|---|---|
| RuleName | ○ | ○ | ○ | 이 이벤트가 걸린 규칙의 이름 |
| UtcTime | ○ | ○ | ○ | 이벤트 시각 |
| ProcessGuid · ProcessId | ○ | ○ | ○ | 파일을 만들거나 지운 프로세스 |
| Image | ○ | ○ | ○ | 그 프로세스의 실행 파일 경로 |
| User | ○ | ○ | ○ | 그 프로세스의 계정 |
| TargetFilename | ○ | ○ | ○ | 만들거나 지운 파일의 경로 |
| CreationUtcTime | ○ | | | 파일의 생성 시각 |
| Hashes | | ○ | ○ | 지운 파일의 해시 |
| IsExecutable (Boolean) | | ○ | ○ | 지운 파일이 실행 파일인지 |
| Archived | | ○ | | 보관 결과 |

- 스키마 순서는 이벤트 11 이 RuleName, UtcTime, ProcessGuid, ProcessId, Image, TargetFilename, CreationUtcTime, User 입니다.
- 이벤트 23 은 RuleName, UtcTime, ProcessGuid, ProcessId, User, Image, TargetFilename, Hashes, IsExecutable, Archived 입니다.
- 이벤트 26 은 이벤트 23 에서 Archived 만 빠진 순서입니다.
- 이벤트 11 에는 해시 필드가 없습니다.

### Archived 필드

Archived 는 Boolean 이 아니라 문자열 필드이고, 배포본에는 아래 문자열이 있습니다. 이 문자열은 Archived 필드에 보관 결과와 실패 이유를 적는 데 쓰이는 것으로 보입니다 (Sysmon v15.22 기준).

| 문자열 | 풀이 |
|---|---|
| `true` | 보관했습니다 |
| `false - insufficient disk space` | 디스크 공간이 모자랐습니다 |
| `false - copy creation failed with status 0x%08x` | 사본을 만들지 못했습니다 (상태 코드가 붙습니다) |
| `false - copy read failed…` | 사본을 만들려고 읽다가 실패했습니다 |
| `false - copy write failed…` | 사본을 쓰다가 실패했습니다 |
| `false - rename failed…` | 이름 바꾸기에 실패했습니다 |
| `false - shredded file with pattern 0x%04x` | 파쇄된 파일입니다 (패턴 값이 붙습니다) |
| `false - this version does not support kernel crypto` | 이 버전은 커널 암호 기능을 지원하지 않습니다 |
| `false - failed with error %d` | 오류 번호와 함께 실패했습니다 |

보관 폴더 안에서 파일 이름을 짓는 규칙은 공개돼 있지 않습니다.

### 이웃 이벤트

파일과 관련된 Sysmon 이벤트는 더 있습니다. 번호 목록은 [Sysmon 로그](index.md) 허브에 있습니다.

| 이벤트 | 남는 때 | 읽을 때 |
|---|---|---|
| 2 (FileCreateTime) | 프로세스가 파일 생성 시각을 일부러 바꿀 때 | TargetFilename, CreationUtcTime, PreviousCreationUtcTime 필드가 있습니다. 정상 프로그램도 흔히 바꾸므로 그 자체로 악성은 아닙니다 |
| 15 (FileCreateStreamHash) | 이름 있는 스트림이 만들어질 때 (예: Zone.Identifier) | 스트림의 해시도 적습니다. [다운로드 출처 표시](../../filesystem/zone-identifier.md)와 함께 봅니다 |
| 27 (FileBlockExecutable) | 실행 파일 생성을 막았을 때 | |
| 28 (FileBlockShredding) | SDelete 같은 도구의 파일 파쇄를 막았을 때 | |
| 29 (FileExecutableDetected) | 실행 파일 생성을 감지했을 때 | |

## 증거로서 의미

| 증명하는 것 | 증명하지 못하는 것 |
|---|---|
| 기록된 시각에 이 프로세스가 이 경로에 파일을 만들었거나 덮어썼습니다 (11) | 새로 만든 것인지 덮어쓴 것인지 (11 에는 둘을 구분하는 필드가 없습니다) |
| 기록된 시각에 이 프로세스가 이 경로의 파일을 지웠습니다 (23·26) | 파일 내용 (11 에는 해시도 없습니다) |
| 지운 파일의 해시와 실행 파일 여부 (23·26) | 사람이 일부러 지웠다는 것 |
| 보관 결과 (23 의 Archived) | 보관 폴더의 사본이 지금도 그대로라는 것 (SYSTEM 권한이면 손댈 수 있습니다) |
| | 설정이 뺀 경로·프로세스의 파일 활동이 없었다는 것 |

### 보고서 문장

아래 경로와 시각은 설명을 위해 만든 예입니다.

- 쓸 수 있는 문장: "이 PC 의 Sysmon 로그에는 <시각> UTC 에 이벤트 23 이 있습니다. `cmd.exe` 가 `C:\Users\Public\a.exe` 를 지웠고, IsExecutable 은 true, Archived 는 true 입니다. `C:\Sysmon` 에서 Hashes 필드와 해시가 같은 파일을 찾았습니다."
- 쓰면 안 되는 문장: "사용자가 흔적을 없애려고 악성 파일을 지웠다."

두 번째 문장은 사람과 의도, 파일의 성격까지 적지만, 이벤트에는 프로세스와 경로와 해시만 있습니다.

## 시각 해석

- UtcTime 은 이벤트 시각이며 UTC 입니다. 서식은 [프로세스 생성](1.md)의 "시각 해석" 을 봅니다.
- 이벤트 11 의 CreationUtcTime 은 파일의 생성 시각 필드입니다. 이 값이 MFT 의 $STANDARD_INFORMATION 생성 시각과 같은지 밝힌 공개 자료가 없으므로 [마스터 파일 테이블](../../filesystem/mft.md)의 값과 직접 맞춰 봅니다.
- 이벤트 2 는 생성 시각을 바꾼 기록입니다. 바꾸기 전 값(PreviousCreationUtcTime)과 바꾼 값(CreationUtcTime)이 함께 남습니다. 파일 시각이 이상하면 같은 파일의 이벤트 2 를 찾습니다.
- 시각 값 형식은 [시각 값 형식](../../../01-foundations/value-decoding/filetime-unix-webkit-dos-ole.md)에서 다룹니다.

## 함정과 한계

1. **이벤트 11 을 "새 파일" 로만 읽습니다.** 덮어쓸 때도 남습니다.
2. **이벤트 11 로 파일 내용을 확인하려 합니다.** 이벤트 11 에는 해시가 없습니다. 파일이 남아 있으면 직접 해시를 구합니다.
3. **이벤트 23 이면 파일이 보관돼 있다고 봅니다.** Archived 필드를 먼저 봅니다. CopyOnDelete 설정에 맞지 않는 파일은 보관하지 않고, 보관 폴더가 조건에 맞지 않으면 보관 기능이 꺼집니다.
4. **보관 폴더를 기본 이름으로만 찾습니다.** 이름은 설정으로 바꿀 수 있고, 볼륨마다 루트에 폴더가 생기므로 C 드라이브만 보지 않습니다.
5. **보관 파일의 이름으로 원래 파일을 찾습니다.** 파일 이름 규칙이 공개돼 있지 않으므로 이벤트 23 의 Hashes 와 보관 파일의 해시를 맞춰 찾습니다. 해시 알고리즘은 설정을 따릅니다.
6. **이벤트 26 에서 사본을 찾습니다.** 26 은 기록만 하는 이벤트입니다.
7. **설정이 뺀 경로를 지나칩니다.** 파일 이벤트는 양이 많아서 흔히 특정 경로만 넣거나 빼므로, 기록이 없는 경로에서 활동이 없었다고 쓰지 않습니다.
8. **27·28 을 기록 이벤트로 봅니다.** 이름대로라면 두 이벤트는 파일 활동을 막은 기록이고, 이 이벤트가 있으면 그 파일은 만들어지지 않았거나 파쇄되지 않았을 수 있습니다.

### 지우기와 조작

- **파일을 파쇄합니다.** Archived 필드에 "shredded file with pattern" 문자열이 남을 수 있습니다. 설정에 따라 28 이 파쇄를 막을 수 있습니다.
- **보관 폴더를 지웁니다.** SYSTEM 권한이면 보관 폴더에 손댈 수 있습니다. 그 흔적은 [USN 변경 저널](../../filesystem/usnjrnl.md)과 [NTFS 트랜잭션 로그](../../filesystem/logfile.md)에서 찾습니다.
- **로그를 지우거나 Sysmon 을 멈춥니다.** [Sysmon 개념과 설정 확인](sysmon-config.md)의 "지우기와 조작" 을 봅니다.

## 직접 분석해 보기

### 보관 파일 찾아 맞추기

1. 적용된 설정에서 ArchiveDirectory 이름과 CopyOnDelete 설정을 확인합니다.
2. 디스크 이미지의 각 볼륨 루트에서 그 이름의 폴더를 찾습니다. 파일 시스템을 직접 해석하는 도구로 열면 ACL 과 관계없이 폴더 안을 볼 수 있습니다.
3. 이벤트 23 을 뽑아 Archived 가 `true` 인 것만 고릅니다.
4. 보관 폴더 안 파일마다 설정과 같은 알고리즘으로 해시를 구합니다.
5. 해시가 이벤트 23 의 Hashes 와 같은 파일을 짝짓습니다.
6. 짝지은 이벤트의 ProcessGuid 로 [프로세스 생성](1.md) 이벤트를 찾아, 누가 어떤 명령으로 지웠는지 봅니다.

보관 파일은 지운 파일의 사본입니다. 증거 목록에 올릴 때는 보관 폴더의 경로와 해시를 함께 적습니다.

### 공개 도구로 한 번

- 이벤트 뷰어나 PowerShell 의 `Get-WinEvent` 로 Sysmon 채널에서 이벤트 11·23·26 을 뽑습니다.
- 공개 EVTX 해석 도구(예: EvtxECmd, python-evtx)로 필드를 표로 뽑아 TargetFilename 으로 묶습니다.
- 한 파일의 삶을 보려면 같은 TargetFilename 의 11 → 2 → 23·26 을 시각 순으로 늘어놓습니다.
- EVTX 저장 구조는 [이벤트 로그 형식](../../../01-foundations/database-log-formats/evtx-evt-etl/index.md)에서 다룹니다.
- 도구 결과는 레코드 한두 개로 원문과 맞춰 봅니다. 방법은 [도구 결과 교차 검증](../../../03-techniques/reporting/tool-validation.md)에서 다룹니다.

## 실습

직접 만든 Windows 11 가상 머신에 Sysmon 을 설치하고 해 봅니다. 각 단계의 시각을 적어 둡니다.

1. 새 파일을 만들고, 같은 이름으로 한 번 더 덮어씁니다. 두 이벤트 11 을 비교하십시오. CreationUtcTime 을 MFT 의 생성 시각과도 비교하십시오.
2. CopyOnDeletePE 를 켜고 실행 파일 하나를 지웁니다. Archived 필드, 보관 폴더 안 파일 이름, 해시를 확인하십시오.
3. 파일 하나를 휴지통으로 보내고, 휴지통을 비웁니다. 다른 파일은 Shift+Delete 로 지웁니다. 각각 어떤 이벤트가 남는지 보십시오.
4. 이벤트 26 만 켠 설정으로 바꿔 같은 일을 합니다. 23 과 무엇이 다른지 적으십시오.
5. 공개 파쇄 도구(예: SDelete)로 파일을 지웁니다. 28 을 켠 경우와 끈 경우의 기록을 비교하십시오.
6. PowerShell 로 파일 생성 시각을 바꿉니다. 이벤트 2 의 두 시각 필드를 확인하십시오.
