# 서비스 설치 (7045·4697)

## 한 줄 요약

새 서비스가 설치되면 이벤트 로그 두 곳에 기록이 남을 수 있습니다. System 로그의 7045 는 기본으로 남습니다. 보안 로그 (Security) 의 4697 은 감사 하위 범주를 켜야 남습니다. 두 이벤트 모두 서비스 이름과 실행 파일 경로, 시작 방식, 실행 계정을 설치한 때의 값으로 남깁니다. 서비스 실행 파일을 나중에 지워도 이 기록은 남습니다.

## 무엇을 기록하나 · 왜 생기나

| 항목 | 7045 | 4697 |
|---|---|---|
| 로그 | System | Security |
| 공급자 | Service Control Manager | Microsoft-Windows-Security-Auditing |
| 남는 조건 | 기본으로 남습니다 | 감사 하위 범주 Audit Security System Extension 을 켜야 남습니다 |
| 설치한 계정 | 칸에는 없습니다. System 노드의 Security UserID 에 SID 만 있습니다 | Subject 칸에 SID·이름·도메인·로그온 ID 가 있습니다 |
| 서비스 종류·시작 방식 | 현지화된 글자 | 숫자 (0x10, 2 등) |
| 경로 칸 이름 | ImagePath | ServiceFileName |
| 계정 칸 이름 | AccountName | ServiceAccount |

Audit Security System Extension 은 Windows 클라이언트 기본값에서 꺼져 있습니다. 기본값 표는 [감사 정책과 로그 설정](audit-policy-log-settings.md)에서 다룹니다. 조사한 PC 도 이 하위 범주가 "감사 없음" 이었고 4697 이 한 건도 없었습니다. 그래서 감사 설정을 바꾸지 않은 PC 에서는 7045 가 서비스 설치를 알려 주는 기록입니다.

원격 실행 도구 (PsExec 등) 는 도착 PC 에 서비스를 만듭니다. 흐름은 [다른 PC 에서 원격 실행했나 (PsExec·WMI·WinRM)](../../04-scenarios/incident/credential-theft-lateral-movement/psexec-wmi-winrm.md)에서 다룹니다. 서비스가 레지스트리에 남기는 설정은 [서비스·드라이버](../persistence/services-drivers.md)에서 다루고, 이 페이지는 이벤트만 다룹니다.

## 위치와 버전별 차이

| 이벤트 | 버전 | Windows | 근거 |
|---|---|---|---|
| 4697 | 0 | 최소 OS 는 Windows 10, Windows Server 2016 | Microsoft 문서 |
| 4697 | 1 | 버전 0 칸에 ClientProcessStartKey (UInt64), ClientProcessId (UInt32), ParentProcessId (UInt32) 를 더합니다. 어느 Windows 부터인지는 확인하지 못했습니다 | 한 PC 의 공급자 메타데이터 |
| 7045 | 0 | 최소 OS 는 확인하지 못했습니다 | — |

Microsoft 문서는 4697 의 버전 0 만 적지만 조사한 PC 의 메타데이터에는 버전 1 도 있었습니다. 이 문서는 Windows 10 판 문서 묶음에 들어 있으므로, 문서가 적은 최소 OS 를 "그 전 Windows 에는 4697 이 없다" 는 뜻으로 읽지 않습니다. 그 전 Windows 에서 남는지는 확인하지 못했습니다.

## 구조

### 7045

한 PC 의 공급자 메타데이터와 실제 이벤트에서 읽었습니다.

| 항목 | 값 |
|---|---|
| 공급자 | Service Control Manager `{555908d1-a6d7-4695-8e1e-26931d2012f4}` |
| 메시지 파일 | `%SystemRoot%\system32\services.exe` |
| 채널 | System |
| 메시지 | A service was installed in the system. Service Name: %1 Service File Name: %2 Service Type: %3 Service Start Type: %4 Service Account: %5 |
| 칸 | ServiceName, ImagePath, ServiceType, StartType, AccountName (모두 문자열) |

조사한 PC 의 7045 한 건을 줄여 옮기면 다음과 같습니다. 서비스 이름과 경로는 가렸습니다.

```xml
<Provider … EventSourceName="Service Control Manager" />
<EventID Qualifiers="16384">7045</EventID>
<Version>0</Version>
<Level>4</Level>
<Task>0</Task>
<Keywords>0x8080000000000000</Keywords>
<Security UserID="S-1-5-18" />
...
<Data Name="ServiceName">[서비스 이름]</Data>
<Data Name="ImagePath">"[실행 파일 경로]"</Data>
<Data Name="ServiceType">사용자 모드 서비스</Data>
<Data Name="StartType">자동 시작</Data>
<Data Name="AccountName">LocalSystem</Data>
```

ImagePath 는 따옴표로 감싼 경로였습니다. 메타데이터의 원시 ID 는 1073748869 (0x40001B85) 인데, 실제 이벤트 XML 에는 `Qualifiers='16384'` 와 7045 로 나뉘어 들어 있었습니다. 16384 는 0x4000 입니다. 설치한 계정은 EventData 에 없고, System 노드의 Security UserID 에 SID 가 있습니다.

같은 공급자의 다른 이벤트도 서비스 흔적을 볼 때 씁니다. 칸은 param1 ~ param5 입니다.

| ID | 원시 ID | 메시지 |
|---|---|---|
| 7036 | 0x40001B7C | The %1 service entered the %2 state. |
| 7040 | 0x40001B80 | The start type of the %1 service was changed from %2 to %3. |
| 7034 | 0xC0001B7A | The %1 service terminated unexpectedly. It has done this %2 time(s). |
| 7031 | 0xC0001B77 | 예기치 않은 종료와 복구 동작 |
| 7000 | 0xC0001B58 | The %1 service failed to start due to the following error: %2 |
| 7009 | 0xC0001B61 | 연결 대기 시간 초과 |

### 4697

Microsoft 문서의 제목은 "4697(S) A service was installed in the system." 입니다. 새 서비스가 설치될 때 생깁니다.

Microsoft 문서의 예시 이벤트 가운데 일부입니다. 문서가 보여 주는 예시이며 검체에서 나온 값이 아닙니다.

```xml
<Provider Name="Microsoft-Windows-Security-Auditing" Guid="{54849625-5478-4994-A5BA-3E3B0328C30D}" />
<EventID>4697</EventID>
<Version>0</Version>
<Level>0</Level>
<Task>12289</Task>
<Keywords>0x8020000000000000</Keywords>
<Channel>Security</Channel>
```

같은 예시의 칸 값은 다음과 같습니다.

| 칸 | 예시 값 | 뜻 |
|---|---|---|
| SubjectUserSid · SubjectUserName · SubjectLogonId | S-1-5-18, WIN-GG82ULGC9GO$, 0x3e7 | 서비스를 설치한 계정과 로그온 ID |
| ServiceName | AppHostSvc | 서비스 이름 |
| ServiceFileName | `%windir%\\system32\\svchost.exe -k apphost` | SCM 이 실행할 파일의 전체 경로. 명령줄 인자가 있으면 같이 남습니다 |
| ServiceType | 0x20 | 서비스 종류 |
| ServiceStartType | 2 | 시작 방식 |
| ServiceAccount | localSystem | 설치 때 설정한 실행 계정 |

설치를 수행한 토큰에 SID 가 있으면 System/Security 노드에 그 SID 가 들어가고, Subject 의 로그온 ID 로 4624 등과 이을 수 있습니다. ServiceAccount 는 사용자 모드 서비스 (0x10·0x20) 일 때만 채워지며 커널 드라이버는 비어 있습니다. 계정 없이 설치한 Win32 서비스는 LocalSystem 으로 돕니다.

Microsoft 문서의 ServiceType 표입니다.

| 값 | 뜻 |
|---|---|
| 0x1 | Kernel Driver |
| 0x2 | File System Driver |
| 0x8 | Recognizer Driver |
| 0x10 | Win32 Own Process |
| 0x20 | Win32 Share Process |
| 0x110 | Interactive Own Process |
| 0x120 | Interactive Share Process |

Microsoft 문서의 ServiceStartType 표입니다.

| 값 | 뜻 |
|---|---|
| 0 | Boot |
| 1 | System |
| 2 | Automatic |
| 2 | Automatic Delayed |
| 3 | Manual |
| 4 | Disabled |

문서는 Automatic 과 Automatic Delayed 를 둘 다 2 로 적었으므로, 4697 의 ServiceStartType 만으로는 둘을 가를 수 없습니다. 칸 형식도 문서와 메타데이터에서 달랐습니다. 문서는 ServiceStartType 을 HexInt32 로 적고, 예시 값은 "2" 입니다. 조사한 PC 의 메타데이터는 ServiceType 이 HexInt32, ServiceStartType 이 UInt32 였습니다.

## 증거로서 의미

| 증명하는 것 | 증명하지 못하는 것 |
|---|---|
| 기록 시각에 이 이름의 서비스가 설치됐다는 것 | 그 서비스가 실제로 실행됐는지 |
| 설치할 때의 실행 파일 경로, 종류, 시작 방식, 실행 계정 | 설치한 뒤에 바뀐 경로·계정 (두 이벤트 모두 남기지 않습니다) |
| 설치 요청이 이 계정·로그온 세션에서 왔다는 것 (4697 의 Subject) | 그 계정 뒤에 있던 사람이 누구인지 |
| 설치 요청의 SID (7045 의 Security UserID) | 7045 만으로 계정 이름과 로그온 세션 |
| | 로그가 밀려난 기간에 설치가 없었다는 것 |

Microsoft 는 서비스 설치가 계획된 일이어야 한다고 적었습니다. 그래서 예상하지 못한 설치는 경고로 다루라고 권합니다. 탐지할 때 볼 것은 다음과 같습니다.

- ServiceFileName 이 `%windir%`·Program Files·Program Files (x86) 밖에 있습니다.
- ServiceType 이 0x1·0x2·0x8 입니다. 이 종류는 부팅 초기부터 거의 제한 없는 권한으로 돌고, 드물게 설치됩니다.
- ServiceStartType 이 0·1 입니다. 드라이버용 값입니다.
- ServiceStartType 이 4 입니다. 사용 안 함으로 설치하는 일은 드뭅니다.
- ServiceAccount 가 localSystem·localService·networkService 가 아닙니다.

### 보고서 문장

- 쓸 수 있는 문장: "System 로그에 ○○(UTC) 의 7045 가 있습니다. ServiceName 은 ○○, ImagePath 는 `○○`, StartType 은 '요청 시 시작' 입니다. Security UserID 는 ○○ 입니다."
- 쓰면 안 되는 문장: "공격자가 악성 서비스를 설치해 실행했다."

두 번째 문장은 사람과 의도, 실행을 적지만 7045 는 설치 기록입니다. 실행 여부는 7036·프리페치·4688 로 따로 확인합니다. 이 판단 방법은 해석입니다.

## 시각 해석

두 이벤트의 시각은 서비스가 설치된 때이고, 두 이벤트 모두 설치 시점 값을 남깁니다. 지금 레지스트리 (`SYSTEM\ControlSet00X\Services\<이름>`) 의 ImagePath·ObjectName 과 다르면 설치 뒤에 바뀐 것입니다. 이 판단은 해석입니다.

같은 서비스 이름이 여러 번 설치된 기록이 흔했습니다. 조사한 PC 에서 한 이름은 46번, 다른 이름은 7번 설치 기록이 있었습니다. 같은 이름의 반복 설치는 앱 업데이트일 수 있으므로 첫 설치 시각과 마지막 설치 시각을 따로 봅니다. 이 판단은 해석입니다.

System 로그가 덮는 기간을 먼저 봅니다. 조사한 PC 의 System 로그 (20MB) 는 약 3개월 치였습니다.

- 시각 값 저장 형식은 [이벤트 로그 형식](../../01-foundations/database-log-formats/evtx-evt-etl/index.md)에서 다룹니다.

## 함정과 한계

1. **4697 이 없으니 설치가 없었다고 봅니다.** 4697 은 기본으로 꺼져 있습니다. 7045 를 봅니다.
2. **7045 를 원시 값으로 찾지 못합니다.** 도구에 따라 7045 가 아니라 원시 값 1073748869 로 보일 수 있습니다.
3. **ServiceType·StartType 을 영어 글자로 거릅니다.** 7045 의 두 칸은 숫자가 아니라 현지화된 글자입니다. 조사한 PC 의 7045 175건 가운데 41건은 영어 ("user mode service", "kernel mode driver", "auto start", "demand start") 였습니다. 134건은 한국어 ("사용자 모드 서비스", "커널 모드 드라이버", "자동 시작", "요청 시 시작", "시스템 시작") 였습니다. 영어 41건은 모두 2026-06-26 18:01~18:07 UTC 6분 사이였습니다. 같은 PC 에서도 기록 당시 언어에 따라 섞입니다.
4. **7045 에서 설치자 칸을 찾습니다.** EventData 에는 없습니다. System 노드의 Security UserID 를 봅니다. 조사한 PC 에서는 S-1-5-18 이 130건, 사용자 SID 가 45건이었습니다. 사용자 SID 로 남은 45건 가운데 35건이 커널 모드 드라이버였습니다.
5. **두 이벤트의 칸 이름을 같다고 봅니다.** 7045 는 ImagePath·AccountName, 4697 은 ServiceFileName·ServiceAccount 입니다. 칸 이름으로 합치면 빠집니다.
6. **레지스트리 숫자를 그대로 읽습니다.** 도구가 Start·Type 값을 10진으로 보여 줄 수 있습니다. Type 0x110 은 272 로 보입니다.
7. **Automatic 과 Automatic Delayed 를 4697 로 가릅니다.** 문서 표에서 둘 다 2 입니다.

### 지우기와 조작

- **서비스와 실행 파일을 지웁니다.** 서비스 실행 파일을 지워도 7045 는 남습니다.
- **로그를 지웁니다.** System 로그를 지우면 104, 보안 로그를 지우면 1102 가 남습니다. [이벤트 로그 삭제 (1102·104)](1102-104.md)를 봅니다.
- **로그가 밀려납니다.** System 로그가 덮어쓰이면 7045 도 사라집니다. 밀려난 레코드가 파일 안에 남아 있을 수 있습니다. [파일 안에 남은 지운·손상 레코드](../../01-foundations/database-log-formats/evtx-evt-etl/chunk-slack-corrupted-evtx.md)를 봅니다.
- **설치 뒤 설정을 바꿉니다.** 두 이벤트는 바꾼 값을 남기지 않습니다. 시작 방식을 바꾸면 7040 이 남습니다.

## 직접 분석해 보기

### 헥스로 한 번

7045 의 원시 ID 를 나눠 봅니다. 아래 값은 메타데이터에서 읽은 원시 ID 를 풀어 본 예시입니다. 이벤트 레코드 안의 실제 저장 형식을 보여 주는 것이 아닙니다.

```
원시 ID  0x40001B85  (10진 1073748869)
윗 16비트  0x4000 = 16384   → XML 의 Qualifiers
아랫 16비트 0x1B85 = 7045   → XML 의 EventID
```

1. 0x40001B85 를 윗 16비트와 아랫 16비트로 나눕니다.
2. 윗 16비트 0x4000 은 10진 16384 입니다. XML 의 `Qualifiers='16384'` 와 같습니다.
3. 아랫 16비트 0x1B85 는 10진 7045 입니다.
4. 7000 의 원시 ID 0xC0001B58 도 같은 방법으로 나누면 아랫 16비트가 0x1B58 = 7000 입니다.

레지스트리의 Type 값도 16진으로 바꿔 봅니다. 도구가 272 로 보여 주면 16진으로 0x110 입니다. 4697 의 ServiceType 표에서 0x110 은 Interactive Own Process 입니다.

> 그림 자리: 원시 ID 32비트를 Qualifiers 와 EventID 로 나누는 그림

### 공개 도구로 한 번

Windows 에 들어 있는 PowerShell 의 `Get-WinEvent` 로 봅니다. 아래 `E:\case\` 는 예시 경로입니다.

```powershell
# 7045: 칸 값과 설치한 SID
Get-WinEvent -FilterHashtable @{ Path = 'E:\case\System.evtx'; ProviderName = 'Service Control Manager'; Id = 7045 } |
  ForEach-Object {
    $x = [xml]$_.ToXml()
    $d = @{}; $x.Event.EventData.Data | ForEach-Object { $d[$_.Name] = $_.'#text' }
    [pscustomobject]@{
      Time        = $_.TimeCreated
      UserSid     = $x.Event.System.Security.UserID
      ServiceName = $d.ServiceName
      ImagePath   = $d.ImagePath
      ServiceType = $d.ServiceType
      StartType   = $d.StartType
      AccountName = $d.AccountName
    }
  }

# 4697
Get-WinEvent -FilterHashtable @{ Path = 'E:\case\Security.evtx'; Id = 4697 }
```

칸 구성은 `(Get-WinEvent -ListProvider 'Service Control Manager').Events` 로 확인할 수 있으며, 이 명령은 분석 PC 의 메타데이터를 읽습니다. 도구가 7045 를 원시 ID 로 보여 주는지, ServiceType 글자를 바꿔 보여 주는지도 확인합니다. 방법은 [도구 결과 교차 검증](../../03-techniques/reporting/tool-validation.md)에서 다룹니다.

## 실습

**직접 만든 Windows 10·11 가상 머신**에서 해 봅니다. 각 단계의 시각을 적어 둡니다.

1. `auditpol /set /subcategory:{0CCE9211-69AE-11D9-BED3-505054503030} /success:enable` 로 보안 시스템 확장 감사를 켭니다.
2. `sc create` 로 무해한 테스트 서비스를 하나 만듭니다. 7045 와 4697 이 함께 남는지 봅니다. 두 이벤트의 칸 값을 나란히 적습니다.
3. 4697 의 버전과 ClientProcessId·ParentProcessId 칸이 채워지는지 봅니다.
4. 시작 방식을 "자동 (지연된 시작)" 으로 만들어 4697 의 ServiceStartType 이 2 로 남는지 봅니다.
5. 서비스의 실행 파일 경로를 바꿉니다. 이벤트가 새로 남는지, 레지스트리 ImagePath 와 7045 의 ImagePath 가 달라지는지 봅니다.
6. 화면 언어를 바꾼 뒤 서비스를 하나 더 만듭니다. 7045 의 ServiceType·StartType 글자가 바뀌는지 봅니다.
7. 옛 Windows 가상 머신에서도 7045 가 남는지 확인합니다. 7045 가 어느 Windows 부터 있는지는 이 페이지가 확인하지 못했습니다.

**NIST CFReDS 같은 공개 검체**에서는 다음을 풀어 봅니다.

1. System 로그의 7045 를 모두 뽑습니다. ImagePath 가 `%windir%`·Program Files 밖에 있는 서비스가 있습니까?
2. Security UserID 가 S-1-5-18 이 아닌 7045 가 있습니까? 그 SID 는 어느 사용자입니까?
3. 같은 시각대에 로그온 유형 3 로그온이 있습니까?
4. 7045 의 ImagePath 와 지금 레지스트리의 ImagePath 가 다른 서비스가 있습니까?
