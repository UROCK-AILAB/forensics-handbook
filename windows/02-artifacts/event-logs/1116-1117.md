# Windows Defender 탐지 (1116·1117)

## 한 줄 요약

Microsoft Defender 백신이 악성코드나 원치 않는 소프트웨어를 찾으면 운영 로그 (Operational) 에 1116 이 남고, 찾은 것에 조치를 하면 1117 이 남습니다. 두 이벤트는 같은 탐지 ID (Detection ID) 로 짝을 이룹니다. 칸에는 위협 이름, 경로, 탐지 출처, 관련 사용자, 조치 결과가 모두 문자열로 들어갑니다. 기록 계정은 SYSTEM 이므로 관련된 사람은 Detection User 칸에서 보고, 탐지 시각은 이벤트 기록 시각과 따로 UTC 문자열로 들어 있습니다.

## 무엇을 기록하나 · 왜 생기나

### 1116 — 찾았다

기호 이름은 MALWAREPROTECTION_STATE_MALWARE_DETECTED 이고, Microsoft 문서의 설명은 "The antimalware platform detected malware or other potentially unwanted software." 입니다. 문서는 사용자가 따로 할 일이 없다고 적으며, Defender 가 위협을 멈추고(suspend) 보통은 조치까지 합니다. 수준은 경고 (Warning) 였습니다 (확인 범위: Win11 25H2 한 대).

### 1117 — 조치했다

기호 이름은 MALWAREPROTECTION_STATE_MALWARE_ACTION_TAKEN 이고, 문서의 설명은 "The antimalware platform performed an action to protect your system …" 입니다. 1116 의 항목에 Action, Action Status, Error Code(HRESULT), Error Description 이 더해집니다. 수준은 정보 (Informational) 였습니다 (확인 범위: Win11 25H2 한 대).

문서가 적은 Action 값은 Clean, Quarantine, Remove, Allow, User defined, No action, Block 입니다.

Allow, No action, None 은 위협을 치료하지 않습니다. Allow 는 그 뒤의 탐지 이벤트를 막고, None 은 알림과 보호 기록을 계속 만듭니다. 변조 방지 (Tamper protection) 가 켜져 있으면 이 조치들을 설정할 수 없습니다.

ThreatSeverityDefaultAction 이 None 일 때 위협을 찾으면 1116 이 남고, 뒤따르는 1117 의 Action 이 Allow 이면 "찾았지만 치료하지 않음" 입니다.

문서는 탐지 뒤 Defender 가 되돌리는 설정도 적습니다. 기본 IE·Edge 설정, UAC 설정, Chrome 설정, 부팅 구성 데이터 (Boot Control Data), 레지스트리 편집기·작업 관리자 관련 레지스트리 설정, Windows Update·BITS·RPC 서비스, OS 파일입니다. 적용 OS 는 Vista SP1·SP2, Windows 7 이후, Server 2008~2016 으로 적혀 있습니다.

### 이웃 이벤트

같은 로그에서 함께 보는 이벤트입니다.

| ID | 기호 이름 | 뜻 |
|---|---|---|
| 1118 | MALWAREPROTECTION_STATE_MALWARE_ACTION_FAILED | 조치하다가 심각하지 않은 오류가 났습니다. 수준은 정보입니다 |
| 1119 | MALWAREPROTECTION_STATE_MALWARE_ACTION_CRITICALLY_FAILED | 조치하다가 심각한 오류가 났습니다. 수준은 오류 (Error) 입니다 |
| 1006 · 1007 · 1008 | MALWAREPROTECTION_MALWARE_DETECTED · _ACTION_TAKEN · _ACTION_FAILED | 1116·1117·1118 과 비슷한 탐지·조치 이벤트입니다 |
| 1015 | MALWAREPROTECTION_BEHAVIOR_DETECTED | 의심 행위를 찾았습니다. Fidelity Label, Target File Name 항목이 있습니다 |
| 1013 | MALWAREPROTECTION_MALWARE_HISTORY_DELETE | 탐지 기록을 지웠습니다 |
| 1120 | MALWAREPROTECTION_THREAT_HASH | 위협 파일의 해시입니다. ThreatFileHashLogging 정책을 설정했을 때만 남습니다 |
| 1121 | | 공격 표면 축소 (ASR) 규칙이 차단 모드로 동작했습니다 |

1006·1007 과 1116·1117 이 어떻게 다른지는 확인하지 못했고, 조사한 PC 에는 1006·1007 이 없었습니다.

## 위치와 버전별 차이

| 항목 | 내용 |
|---|---|
| 이벤트 뷰어 위치 | Applications and Services Logs > Microsoft > Windows > Windows Defender > Operational |
| 파일 | `%SystemRoot%\System32\Winevt\Logs\Microsoft-Windows-Windows Defender%4Operational.evtx` |
| 공급자 | Microsoft-Windows-Windows Defender |
| 공급자 GUID | `11cd958a-c507-4ef3-b3f2-5fd9dfbd2c78` |
| 로그 설정 | 켜짐, 최대 16MB, 순환 |

- 파일, 공급자 GUID, 로그 설정은 조사한 PC 에서 본 것입니다 (확인 범위: Win11 25H2 한 대).
- 조사한 PC 의 이 로그에는 5,364건이 있었습니다. 가장 오래된 것은 OS 설치 무렵(2026-06-26)이었습니다.
- Microsoft 문서의 적용 대상은 Microsoft Defender for Endpoint Plan 1·2 와 Microsoft Defender 백신 (Microsoft Defender Antivirus) 입니다.
- 조사한 PC 의 1116·1117 은 모두 이벤트 버전 0 이었습니다. 제품 버전은 4.18.26060.3008, 4.18.26070.9, 4.18.26080.4 였습니다.

## 구조

### 문서가 적은 항목

1116 의 항목은 Name, ID, Severity, Category, Path, Detection Origin, Detection Type, Detection Source, User, Process Name, Signature Version, Engine Version 입니다. 1117 에는 조치 항목이 더해집니다.

문서는 몇몇 항목의 값을 이렇게 적습니다.

| 항목 | 문서의 값 |
|---|---|
| Severity | Low, Moderate, High, Severe |
| Detection Origin | Unknown, Local computer, Network share, Internet, Incoming traffic, Outgoing traffic |
| Detection Type | Heuristics, Generic, Concrete, Dynamic signature |
| Detection Source | User, System, Real-time, IOAV(IE 다운로드·Outlook Express 첨부), NIS, IEPROTECT, ELAM, Remote attestation, AMSI |

### 실제 EventData 칸

공급자 템플릿을 보면 1116·1117·1118·1119 는 칸 42개를 함께 씁니다 (확인 범위: Win11 25H2 한 대). 모든 칸의 형식은 문자열 (UnicodeString) 입니다.

| 묶음 | 칸 |
|---|---|
| 제품 | Product Name, Product Version, Security intelligence Version, Engine Version |
| 탐지 | Detection ID, Detection Time, Threat ID, Threat Name, Severity ID, Severity Name, Category ID, Category Name, FWLink |
| 상태 | Status Code, Status Description, State |
| 출처 | Source ID, Source Name, Origin ID, Origin Name, Type ID, Type Name, Execution ID, Execution Name, Pre Execution Status |
| 대상·사람 | Process Name, Detection User, Path, Remediation User |
| 조치 | Action ID, Action Name, Error Code, Error Description, Post Clean Status, Additional Actions ID, Additional Actions String |
| 쓰지 않음 | Unused, Unused2, Unused3, Unused4, Unused5, Unused6 |

표는 이해하기 쉽게 묶은 것이고 실제 칸 순서는 이와 다릅니다. 화면 문구의 "User" 가 가리키는 칸은 이벤트마다 달라서, 1116 은 %20(Detection User), 1117·1118·1119 는 %39(Remediation User) 입니다. 곧 이벤트 뷰어의 "User" 줄은 1116 에서는 탐지와 관련된 사용자, 1117 에서는 조치한 사용자입니다.

### 이 PC 에서 본 값

조사한 PC 에는 1116 이 47건, 1117 이 33건 있었습니다. 분석·시험 중에 나온 탐지입니다 (확인 범위: Win11 25H2 한 대).

- 기록 계정 (System 의 Security UserID) 은 모두 `S-1-5-18`(SYSTEM) 이었습니다.
- 1116 의 Detection User 는 사용자 계정(`컴퓨터이름\사용자`), `NT AUTHORITY\SYSTEM`, 빈 값 가운데 하나였습니다.
- 1117 의 Remediation User 는 모두 `NT AUTHORITY\SYSTEM` 이었습니다.
- Threat Name 은 `HackTool:Win32/Mimikatz.I`, `Backdoor:JS/Chopper.GG!dha`, `Trojan:Win32/ClickFix.AAB!MTB`, `Ransom:PowerShell/FileFix.DZ!MTB` 같은 모양이었습니다.

숫자 ID 와 이름이 이렇게 짝지어 나왔습니다. 이름은 이 PC 의 표시 그대로입니다.

| 칸 | 본 값 |
|---|---|
| Severity ID | 4 = 높음(High), 5 = 심각(Severe) |
| Category ID | 6 = 백도어, 8 = 트로이, 34 = 도구, 50 = 랜섬웨어 |
| Source ID | 2 = 시스템, 3 = 실시간 보호 기능, 10 = AMSI |
| Origin ID | 0 = 알 수 없음, 1 = 로컬 컴퓨터 |
| Type ID | 0 = 구체적(Concrete), 8 = 빠른 경로(FastPath) |
| Execution ID | 0 = 알 수 없음, 1 = 일시 중단 |
| Action ID | 2 = 격리, 3 = 제거, 9 = 해당 없음. 1116 은 47건 모두 9 였습니다 |
| State | 1116 은 1. 1117 은 2(32건)·3(1건) |
| Status Code | 1116 은 1. 1117 은 3·4·103 |
| Error Code | 대부분 `0x00000000`. 1117 세 건은 `0x80508023`("이 장치에서 … 발견되지 않았습니다") |
| Additional Actions ID | 대부분 0(No additional actions required). 1117 한 건은 8("… 제거를 완료하려면 장치를 다시 시작하세요") |

이 표는 이 PC 에서 본 짝일 뿐입니다. 숫자 ID 의 공식 대응표는 확인하지 못했습니다.

### Path 칸의 앞머리

Path 칸의 값은 대상 종류를 가리키는 앞머리로 시작했습니다 (확인 범위: Win11 25H2 한 대).

| 앞머리 | 대상 |
|---|---|
| `file:_` | 파일 |
| `containerfile:_` | 압축 파일 같은 묶음 안의 파일 |
| `CmdLine:_` | 명령줄 |
| `amsi:_` | AMSI 가 검사한 내용 |

각 앞머리의 공식 설명은 확인하지 못했습니다.

### Process Name 칸

Source 가 시스템(2)인 탐지는 Process Name 이 `Unknown` 이었고, 실시간 보호(3)와 AMSI(10) 탐지에는 파일을 건드린 프로세스 이름이 `bash.exe`, `python.exe`, `powershell.exe` 처럼 들어 있었습니다.

## 증거로서 의미

| 증명하는 것 | 증명하지 못하는 것 |
|---|---|
| 탐지 시각에 Defender 가 이 경로에서 이 이름의 위협을 찾았습니다 (1116) | 그 파일이 실행됐다는 것. 탐지 출처와 Execution 칸을 따로 봅니다 |
| 어떤 기능이 찾았는지 (Source: 실시간 보호, AMSI, 시스템 검사 등) | 사용자가 그 파일을 일부러 받았거나 만들었다는 것 |
| 파일을 건드린 프로세스 이름 (실시간 보호·AMSI 탐지) | 1117 이 있으니 위협이 없어졌다는 것. Action 과 Error Code 를 봅니다 |
| Defender 가 한 조치와 그 결과 (1117) | 로그에 없으니 탐지도 없었다는 것. 문서는 Allow 가 그 뒤의 탐지 이벤트를 막는다고 적습니다 |
| 탐지와 관련된 계정 (1116 의 Detection User) | 계정 뒤의 사람이 누구인지 |

### 보고서 문장

아래 시각과 경로는 설명을 위해 만든 예입니다.

- 쓸 수 있는 문장: "Defender 운영 로그에는 탐지 시각 <시각> UTC 의 1116 이 있습니다. 실시간 보호 기능이 `C:\…\a.exe` 에서 위협 ○○ 을 찾았고, 그 파일을 건드린 프로세스는 `powershell.exe`, Detection User 는 ○○ 입니다. 같은 Detection ID 의 1117 은 격리 조치를 적고, Error Code 는 `0x00000000` 입니다."
- 쓰면 안 되는 문장: "○○ 이 악성코드를 실행했으나 백신이 삭제했다."

두 번째 문장은 실행과 결과를 단정합니다. 이벤트에는 탐지와 조치 기록만 있습니다.

## 시각 해석

한 탐지에 시각이 셋 있습니다.

| 시각 | 들어 있는 곳 | 형식 |
|---|---|---|
| 탐지 시각 | EventData 의 Detection Time | UTC 문자열, 밀리초까지, 끝에 Z (예: `2026-09-23T11:47:33.664Z`) |
| 1116 기록 시각 | `<TimeCreated SystemTime>` | UTC |
| 1117 기록 시각 | `<TimeCreated SystemTime>` | UTC |

짝을 이룬 1116·1117 은 Detection Time 이 같았습니다 (확인 범위: Win11 25H2 한 대). 표본 몇 건에서 1116 의 기록 시각은 Detection Time 보다 0.1초~11초 뒤였고, 1117 의 기록 시각은 25초~70초 뒤였습니다. 타임라인에는 Detection Time 을 탐지 시각으로 쓰고, 조치 시각은 1117 의 기록 시각으로 따로 적습니다.

- 문서는 1013 의 Time 이 탐지 기록을 지운 시각이라고 적습니다. 위협 이벤트에는 그 이름 대신 Action Time·Detection Time 을 쓴다고 적습니다.
- 현지 시각으로 바꿀 때는 [시간대 설정](../system-account/time-zone.md)을 씁니다.

## 함정과 한계

1. **영어 문자열로 거릅니다.** 이름 칸은 OS 표시 언어로 들어갑니다. 조사한 PC 에서는 Severity Name 이 "높음·심각", Action Name 이 "격리·제거·해당 없음" 처럼 한국어였습니다. 숫자 ID 칸은 언어와 상관없으므로 ID 로 거릅니다.
2. **1116 건수를 사건 수로 셉니다.** 1116 47건 가운데 46건이 1117 과 같은 Detection ID 였습니다. 1117 은 33건이었으므로, 한 Detection ID 에 1116 이 여러 번 남은 경우가 있습니다. Detection ID 로 묶어 셉니다.
3. **기록 계정을 사용자로 읽습니다.** 기록 계정은 모두 SYSTEM 입니다. 사람은 Detection User 에서 봅니다. 1117 의 "User" 는 조치한 계정이어서 SYSTEM 이 흔합니다.
4. **1117 을 "지웠다" 로 읽습니다.** Action 이 해당 없음이거나 Allow 일 수 있습니다. 조사한 PC 에서는 1117 세 건의 Error Code 가 `0x80508023`("발견되지 않았습니다") 이었습니다.
5. **조치가 끝났다고 봅니다.** Additional Actions 가 8 이면 제거를 마치려면 다시 시작해야 합니다. 다시 시작한 기록과 그 뒤의 상태를 따로 봅니다.
6. **이 페이지의 숫자 대응표를 공식 값으로 씁니다.** 한 PC 에서 본 짝입니다. 보고서에는 이름 칸의 원문을 함께 적습니다.
7. **Process Name 이 `Unknown` 이니 프로세스가 없었다고 봅니다.** 조사한 PC 에서는 Source 가 시스템(2)인 탐지에 `Unknown` 이 들어 있었습니다.
8. **1120 해시가 늘 있다고 봅니다.** ThreatFileHashLogging 정책을 설정했을 때만 남습니다. 해시는 격리 파일이나 다른 기록에서 찾습니다.
9. **Detection ID 로 DetectionHistory 파일을 바로 찾습니다.** 두 기록을 잇는 방법은 확인하지 못했습니다.

### 지우기와 조작

- **탐지 기록을 지웁니다.** 1013 이 남습니다.
- **조치를 Allow·No action·None 으로 바꿉니다.** 변조 방지가 켜져 있으면 이렇게 설정할 수 없습니다. 1117 의 Action 이 Allow 인 탐지를 찾아봅니다.
- **Defender 설정을 바꾸거나 끕니다.** 같은 로그의 설정 변경·끄기 이벤트(5001·5007·5013 등)는 [보안 프로그램을 끄거나 지웠나](../../04-scenarios/activity/anti-forensics/defense-evasion.md)에서 다룹니다.
- **로그를 지웁니다.** 지운 기록은 [이벤트 로그 삭제](1102-104.md)에서 찾습니다.

## 직접 분석해 보기

### 헥스로 한 번

Detection Time 은 FILETIME 이 아니라 문자열입니다. 로그 파일 안에서는 UTF-16LE 글자로 들어 있습니다.

아래는 조사한 PC 에서 본 Detection Time 을 형식대로 옮긴 예시입니다. 검체에서 뽑은 바이트가 아닙니다.

```
"2026-09-23T11:47:33.664Z"
→ 32 00 30 00 32 00 36 00 2D 00 30 00 39 00 2D 00 32 00 33 00
  54 00 31 00 31 00 3A 00 34 00 37 00 3A 00 33 00 33 00 2E 00
  36 00 36 00 34 00 5A 00
```

1. Defender 운영 로그 사본을 헥스 편집기로 엽니다.
2. 찾는 Detection ID(GUID 문자열)나 Threat Name 을 UTF-16LE 바이트로 바꿔 찾습니다.
3. 찾은 자리 근처에서 위 모양의 Detection Time 문자열을 읽습니다.
4. 도구 결과에 없는 자리에서 나왔다면, [이벤트 로그 형식](../../01-foundations/database-log-formats/evtx-evt-etl/index.md)에서 설명하는 구조로 그 자리가 레코드인지 확인합니다.

인코딩 자체는 [문자 인코딩](../../01-foundations/value-decoding/utf-16le-utf-8-cp949.md)에서 다룹니다.

### 공개 도구로 한 번

Windows 에 들어 있는 PowerShell 로 사본 파일에서 1116·1117 을 뽑아 Detection ID 로 묶을 수 있습니다. 칸 이름에 빈칸이 있으므로 이름을 따옴표로 감쌉니다.

```powershell
Get-WinEvent -Path '.\Microsoft-Windows-Windows Defender%4Operational.evtx' -FilterXPath "*[System[(EventID=1116 or EventID=1117)]]" -Oldest |
  ForEach-Object {
    $d = @{}
    ([xml]$_.ToXml()).Event.EventData.Data | ForEach-Object { $d[$_.Name] = $_.'#text' }
    [pscustomobject]@{
      RecordUtc     = $_.TimeCreated.ToUniversalTime()
      EventId       = $_.Id
      DetectionId   = $d['Detection ID']
      DetectionTime = $d['Detection Time']
      Threat        = $d['Threat Name']
      SourceId      = $d['Source ID']
      ActionId      = $d['Action ID']
      ErrorCode     = $d['Error Code']
      Process       = $d['Process Name']
      User          = $d['Detection User']
      Path          = $d['Path']
    }
  } | Sort-Object DetectionId, RecordUtc | Format-Table
```

- 같은 DetectionId 안에서 1116 과 1117 을 나란히 봅니다.
- EvtxECmd 맵 저장소에는 Defender 운영 로그 1116·1117 맵이 있습니다. 도구가 보여 주는 값은 XML 원문 한두 건과 맞춰 봅니다. 방법은 [도구 결과 교차 검증](../../03-techniques/reporting/tool-validation.md)에서 다룹니다.

## 실습

직접 만든 Windows 10·11 가상 머신에서 해 봅니다. 백신 시험용으로 널리 쓰는 무해한 EICAR 시험 파일을 씁니다. 각 단계의 시각을 UTC 로 적어 둡니다.

1. 시험 파일을 내려받습니다. 1116 과 1117 의 Detection ID 와 Detection Time 이 같은지 보십시오.
2. 두 이벤트의 기록 시각이 Detection Time 보다 몇 초 뒤인지 재어 보십시오.
3. 같은 파일을 압축 파일 안에 넣어 둡니다. Path 칸의 앞머리가 어떻게 바뀌는지 보십시오.
4. PowerShell 창에서 시험 문자열을 변수에 담아 봅니다. 탐지가 남는다면 Source 가 AMSI 인지, Path 앞머리가 무엇인지 보십시오.
5. 보호 기록에서 탐지 기록을 지워 봅니다. 1013 이 남는지 확인하십시오.
6. 표시 언어가 다른 가상 머신에서 1번을 되풀이합니다. 이름 칸과 숫자 ID 칸을 비교하십시오.

NIST CFReDS 같은 공개 검체에서 이벤트 로그를 꺼냈다면, 먼저 Defender 운영 로그에 1116 이 있는지 보십시오. 있으면 Detection ID 로 1117 을 찾아 Action 과 Error Code 를 확인하십시오.
