# 명시적 자격 증명·특수 권한 (4648·4672)

> 위치: 아티팩트 사전 > 이벤트 로그 > [로그온·로그오프 (Logon Events)](index.md)

## 한 줄 요약

4648 은 프로세스가 계정의 자격 증명을 직접 지정해 로그온을 시도할 때 남습니다. 4672 는 새 로그온 세션에 민감한 특수 권한이 하나라도 붙을 때 남습니다. 두 이벤트 모두 `SubjectLogonId` 로 4624 와 이을 수 있습니다. 둘 다 정상 운영 중에도 자주 생깁니다. 그래서 기록이 있다는 것만으로 이상하다고 보지 않습니다.

## 무엇을 기록하나 · 왜 생기나

두 이벤트 모두 공급자 `Microsoft-Windows-Security-Auditing` 이 `Security` 채널에 남깁니다.

| 이벤트 | 생기는 때 | 감사 하위 범주 | Task |
|---|---|---|---|
| 4648 | 프로세스가 계정의 자격 증명을 직접 지정해 로그온을 시도할 때 | 로그온 (Audit Logon) | 12544 |
| 4672 | 새 로그온 세션에 민감한 특수 권한이 하나라도 붙을 때 | 특수 로그온 (Audit Special Logon) | 12548 |

### 4648 명시적 자격 증명 (Explicit Credentials)

가장 흔한 경우는 예약 작업 같은 일괄 (batch) 구성이고, RUNAS 명령을 쓸 때도 생깁니다. Microsoft 문서는 4648 을 정상 운영 중에도 주기적으로 생기는 일상 이벤트라고 적습니다. 이 이벤트에는 자격 증명을 넣은 쪽 계정과 자격 증명이 쓰인 계정, 두 계정이 남습니다.

### 4672 특수 권한 (Special Privileges)

새 세션에 아래 13개 권한 가운데 하나라도 붙으면 생기며, SYSTEM(Local System) 계정이 로그온할 때마다 생기기 때문에 로그에 아주 많이 보입니다.

| 권한 이름 | 그룹 정책에 보이는 이름 |
|---|---|
| `SeTcbPrivilege` | Act as part of the operating system |
| `SeBackupPrivilege` | Back up files and directories |
| `SeCreateTokenPrivilege` | Create a token object |
| `SeDebugPrivilege` | Debug programs |
| `SeEnableDelegationPrivilege` | Enable computer and user accounts to be trusted for delegation |
| `SeAuditPrivilege` | Generate security audits |
| `SeImpersonatePrivilege` | Impersonate a client after authentication |
| `SeLoadDriverPrivilege` | Load and unload device drivers |
| `SeSecurityPrivilege` | Manage auditing and security log |
| `SeSystemEnvironmentPrivilege` | Modify firmware environment values |
| `SeAssignPrimaryTokenPrivilege` | Replace a process-level token |
| `SeRestorePrivilege` | Restore files and directories |
| `SeTakeOwnershipPrivilege` | Take ownership of files or other objects |

Microsoft 문서는 두 권한을 따로 설명합니다.

`SeSecurityPrivilege` 가 있는 사용자는 보안 로그를 보고 지울 수 있습니다. `SeDebugPrivilege` 는 다른 계정이 주인인 프로세스의 메모리를 디버그하거나 고칠 때 필요한데, Microsoft 는 이 권한을 Administrators 그룹에만 주라고 권합니다.

### 4624 의 관리자 권한 토큰 (Elevated Token)

4624 버전 2 에는 값이 "Yes" 또는 "No" 인 `ElevatedToken` 칸이 있습니다. "Yes" 면 그 세션은 권한이 올라간 상태이고 관리자 권한이 있으며, Microsoft 는 관리자 권한으로 한 로그온을 모두 보려면 `ElevatedToken` 이 "Yes" 인 4624 를 보라고 권합니다. 4672 와 `ElevatedToken` "Yes" 가 늘 함께 나오는지는 이번에 연 Microsoft 문서로 확인하지 못했습니다. 아래 실습으로 확인합니다.

- XML 에서 이 칸이 어떤 모양으로 들어 있는지는 [로그온 세션 잇기](logon-id-4624-4634-4647.md)에서 다룹니다.

## 위치와 버전별 차이

| 이벤트 | 이벤트 버전 | 최소 OS |
|---|---|---|
| 4648 | 0 | Vista · Server 2008 |
| 4672 | 0 | Vista · Server 2008 |

4648 문서는 이 이벤트가 어느 컴퓨터에 남는지 직접 적지 않고, 자격 증명을 쓴 대상은 `TargetServerName` 칸에 따로 적습니다. 4672 문서도 남는 컴퓨터를 직접 적지 않으며 `SubjectLogonId` 로 4624 와 잇는다는 설명만 있습니다. 두 이벤트를 어느 컴퓨터에서 찾을지, 그리고 4648 이 로그온 하위 범주에 속하면서도 다른 로그온 이벤트와 남는 쪽이 다를 수 있다는 점은 [기록이 남는 위치](pc.md)에서 다룹니다.
- 이 이벤트들이 남도록 감사가 켜져 있었는지는 [감사 정책과 로그 설정](../audit-policy-log-settings.md)에서 확인합니다.

## 구조

### 4648 의 칸

| 칸 (XML 이름) | 이벤트 뷰어의 이름 | 뜻 |
|---|---|---|
| `SubjectUserSid`, `SubjectUserName`, `SubjectDomainName` | Subject | 명시적 자격 증명으로 새 로그온 세션을 요청한 계정입니다 |
| `SubjectLogonId` | Subject 의 Logon ID | 요청한 계정의 로그온 ID 입니다. 같은 값의 4624 와 잇습니다 |
| `LogonGuid` | Subject 의 Logon GUID | 로그온 GUID 입니다 |
| `TargetUserName`, `TargetDomainName` | Account Whose Credentials Were Used | 자격 증명이 쓰인 계정의 이름과 도메인입니다 |
| `TargetLogonGuid` | Account Whose Credentials Were Used 의 Logon GUID | 자격 증명이 쓰인 계정 쪽 로그온 GUID 입니다 |
| `TargetServerName` | Target Server Name | 새 프로세스가 실행된 서버 이름입니다. 로컬에서 실행했으면 `localhost` 입니다 |
| `TargetInfo` | Additional Information | 문서에 자세한 설명이 없습니다 |
| `ProcessId`, `ProcessName` | Process ID, Process Name | 명시적 자격 증명으로 실행된 프로세스의 ID(16진)와 전체 경로입니다 |
| `IpAddress`, `IpPort` | Network Address, Port | 네트워크 주소와 포트입니다 |

- 두 로그온 GUID 는 도메인 컨트롤러의 4769, 같은 컴퓨터의 4624·4964 와 잇는 값입니다. 잡히지 않으면 모두 0 입니다.
- `ProcessId` 는 [프로세스 생성 (4688)](../4688.md)의 New Process ID 와 이을 수 있습니다.
- 주소는 IPv6 이거나 `::ffff:` 뒤에 IPv4 를 붙인 모양입니다. `::1` 과 `127.0.0.1` 은 이 컴퓨터 자신입니다.
- 대화형 로그온이면 포트는 0 입니다.
- XML 에는 자격 증명이 쓰인 계정의 SID 칸이 없습니다. 그런데 같은 문서의 권장 사항 표는 "Account Whose Credentials Were Used\Security ID" 를 언급합니다. 문서 안에서 서로 맞지 않습니다. 이 계정은 이름과 도메인으로만 확인합니다.

Microsoft 4648 문서의 예시 값은 아래와 같습니다.

| 칸 | 값 |
|---|---|
| `SubjectUserName` | `dadmin` |
| `LogonGuid` | 모두 0 |
| `TargetUserName` | `ladmin` |
| `TargetLogonGuid` | `{0887F1E4-39EA-D53C-804F-31D568A06274}` |
| `TargetServerName` | `localhost` |
| `ProcessName` | `C:\Windows\System32\svchost.exe` |
| `IpAddress` | `::1` |
| `IpPort` | `0` |

이 예시는 한 컴퓨터 안에서 `dadmin` 세션이 `ladmin` 의 자격 증명을 넣어 로그온을 시도한 기록입니다. Subject 쪽 로그온 GUID 는 비어 있고, 자격 증명 쪽 GUID 에만 값이 있습니다.

### 4672 의 칸

| 칸 (XML 이름) | 뜻 |
|---|---|
| `SubjectUserSid`, `SubjectUserName`, `SubjectDomainName` | 특수 권한을 받은 계정입니다 |
| `SubjectLogonId` | 권한이 붙은 세션의 로그온 ID 입니다. 4624 와 잇는 값입니다 |
| `PrivilegeList` | 붙은 권한 이름의 목록입니다. Microsoft 예시에서는 공백으로 나뉘어 있습니다 |

4672 의 Subject 는 로그온을 보고한 계정이 아니라 권한을 받은 계정이라서, 4624 의 Subject 와 뜻이 다릅니다. Microsoft 문서는 이 계정이 4624 의 New Logon 계정과 같다고 적지 않고 로그온 ID 로 잇는다는 설명만 하므로, 두 계정이 같은지는 값을 직접 맞춰 봅니다.
- 세션을 로그온 ID 로 잇는 순서는 [로그온 세션 잇기](logon-id-4624-4634-4647.md)에서 다룹니다.

## 증거로서 의미

| 증명하는 것 | 증명하지 못하는 것 |
|---|---|
| 기록 시각에 이 컴퓨터의 한 세션이 다른(또는 같은) 계정의 자격 증명을 지정해 로그온을 시도했습니다 (4648) | 그 로그온이 성공했는지 |
| 자격 증명을 넣은 프로세스의 경로와 ID (4648) | 사람이 자격 증명을 직접 입력했는지. 예약 작업 같은 일괄 구성도 4648 을 남깁니다 |
| 자격 증명을 쓸 대상 서버 이름 (4648) | 대상 서버에서 무엇을 했는지 |
| 기록 시각에 이 세션에 목록의 특수 권한이 붙었습니다 (4672) | 그 권한을 실제로 썼는지 |
| `ElevatedToken` 이 "Yes" 면 그 세션에 관리자 권한이 있었습니다 (4624) | 관리자 권한으로 어떤 작업을 했는지 |

### Microsoft 가 권하는 확인 항목

Microsoft 문서는 아래 조합을 살펴보라고 권합니다.

| 이벤트 | 살펴볼 조합 |
|---|---|
| 4648 | `ProcessName` 이 System32·Program Files 밖이거나, Temporary Internet Files 같은 곳에 있습니다 |
| 4648 | `ProcessName` 에 "mimikatz"·"cain.exe" 같은 문자열이 있습니다 |
| 4648 | Subject 계정이 알면 안 되는 계정의 자격 증명을 썼습니다 |
| 4648 | 자격 증명이 허용되지 않은 네트워크 주소에서 쓰였습니다 |
| 4672 | Subject 가 LOCAL SYSTEM·NETWORK SERVICE·LOCAL SERVICE 가 아니고, 이 권한을 받을 것으로 예상되는 관리자 계정도 아닙니다 |
| 4624 | 관리자 권한 로그온을 모두 보려면 `ElevatedToken` 이 "Yes" 인 기록을 봅니다 |

이 조합에 걸린다고 곧 침해라고 쓰지 않습니다. 걸린 기록마다 세션, 프로세스, 대상 컴퓨터 기록을 이어서 판단합니다.

### 보고서 문장

아래 시각은 설명을 위해 만든 예입니다. 계정·서버·프로세스는 Microsoft 문서의 예시 값입니다.

- 쓸 수 있는 문장: "이 PC 의 Security 로그에 2024-03-15 02:14:07 UTC 의 4648 이 있습니다. `dadmin` 세션에서 `ladmin` 계정의 자격 증명을 지정한 로그온 시도가 기록되어 있습니다. 대상 서버는 `localhost`, 프로세스는 `C:\Windows\System32\svchost.exe` 입니다."
- 쓰면 안 되는 문장: "`dadmin` 사용자가 `ladmin` 의 비밀번호를 알아내 관리자 권한으로 로그인했습니다."

두 번째 문장은 기록에 없는 사람, 의도, 성공 여부까지 적었습니다.

## 시각 해석

`TimeCreated SystemTime` 값은 끝에 `Z` 가 붙은 UTC 형식입니다. Microsoft 문서는 이 시각이 기록한 때인지 일이 일어난 때인지 따로 밝히지 않으므로 보고서에는 "기록 시각" 으로 적습니다. 4648 의 시각은 이 컴퓨터에서 로그온을 시도한 기록 시각이며, 대상 컴퓨터가 로그온을 받아들인 시각이 아닙니다. 대상 컴퓨터의 기록은 그 컴퓨터의 시계를 따르므로, 두 컴퓨터의 기록을 맞출 때는 [타임라인 작성](../../../03-techniques/analysis/timeline/index.md)에서 시계 차이를 보정합니다. 4672 는 같은 로그온 ID 의 4624 와 함께 한 세션으로 둡니다.

- 시스템 시각을 바꾼 기록은 [시간 변경](../4616-kernel-general.md)에서 찾습니다.

## 함정과 한계

1. **4648 이 있으면 공격이라고 봅니다.** Microsoft 는 4648 을 일상 이벤트라고 적습니다. 예약 작업과 RUNAS 도 이 이벤트를 남깁니다. 프로세스 경로와 두 계정의 관계를 먼저 봅니다.
2. **두 계정을 거꾸로 읽습니다.** Subject 는 자격 증명을 넣은 쪽 계정입니다. 자격 증명이 쓰인 계정은 `TargetUserName`·`TargetDomainName` 입니다.
3. **4648 을 성공한 로그온으로 읽습니다.** 4648 은 로그온 시도의 기록입니다. 성공했는지는 대상 컴퓨터의 4624 나 [로그온 실패와 실패 코드 (4625)](4625.md)로 확인합니다.
4. **자격 증명이 쓰인 계정의 SID 를 찾습니다.** XML 에는 그 칸이 없습니다. 이름과 도메인으로 [사용자 계정 (SAM)](../../system-account/sam.md)이나 [액티브 디렉터리 DB](../../credentials/ntds-dit.md)에서 계정을 찾습니다.
5. **`localhost` 를 원격 접속으로 읽습니다.** `TargetServerName` 이 `localhost` 면 새 프로세스가 이 컴퓨터에서 실행됐습니다. Microsoft 예시도 `localhost`, `::1`, 포트 0 입니다.
6. **로그온 GUID 로 늘 이을 수 있다고 봅니다.** 잡히지 않은 로그온 GUID 는 모두 0 입니다. Microsoft 예시에서도 Subject 쪽 GUID 는 0 이었습니다.
7. **`TargetInfo` 의 뜻을 단정합니다.** Microsoft 문서에는 이 칸의 자세한 설명이 없습니다. 값이 무엇을 뜻하는지는 실습으로 재현해 보고 적습니다.
8. **4672 를 모두 읽거나, 모두 버립니다.** SYSTEM 이 로그온할 때마다 4672 가 생깁니다. LOCAL SYSTEM·NETWORK SERVICE·LOCAL SERVICE 기록을 먼저 걸러 냅니다. 그 뒤 남은 계정을 관리자 계정 목록과 맞춥니다.
9. **4672 의 계정을 4624 의 New Logon 계정과 같다고 가정합니다.** Microsoft 문서는 로그온 ID 로 잇는다는 것만 적습니다. 같은 로그온 ID 의 4624 를 찾아 계정이 같은지 봅니다.
10. **권한이 붙은 것을 권한을 쓴 것으로 읽습니다.** 4672 는 세션에 권한이 붙었다는 기록입니다. 그 권한으로 무엇을 했는지는 [프로세스 생성 (4688)](../4688.md) 같은 다른 기록에서 찾습니다.
11. **원격 접속마다 출발 PC 에 4648 이 남는다고 봅니다.** `net use`·PsExec 같은 특정 도구를 쓸 때 4648 이 남는지는 이번에 연 자료로 확인하지 못했습니다. 조사하는 환경과 같은 버전에서 재현해 보고 판단합니다.

### 지우기와 조작

- **보안 로그를 지웁니다.** `SeSecurityPrivilege` 가 있는 사용자는 보안 로그를 지울 수 있습니다. 이 권한이 붙은 세션이 있었다면 [이벤트 로그 삭제](../1102-104.md) 흔적을 같이 찾습니다.
- **감사를 끕니다.** 특수 로그온 감사를 끄면 4672 가 남지 않습니다. 관리자 로그온이 있는데 4672 가 하나도 없으면 [감사 정책과 로그 설정](../audit-policy-log-settings.md)을 먼저 확인합니다.
- **프로세스 이름을 흔한 이름으로 바꿉니다.** 4648 의 `ProcessName` 은 전체 경로입니다. 파일 이름만 보지 말고 폴더까지 봅니다.
- 이런 흔적을 모아 읽는 순서는 [증거를 없애려 했나](../../../04-scenarios/activity/anti-forensics/index.md)에서 다룹니다.

## 직접 분석해 보기

### 헥스로 한 번

값이 레코드 안에 어떻게 놓이는지는 [로그온 유형 해석](logon-type.md)의 "헥스로 한 번" 에서 다룹니다. 로그온 ID 8바이트로 같은 세션의 레코드를 찾는 법은 [로그온 세션 잇기](logon-id-4624-4634-4647.md)의 "헥스로 한 번" 에서 다룹니다.

4648·4672 도 같은 방법을 씁니다.

1. 4624 의 `TargetLogonId` 를 바이트로 옮깁니다.
2. 같은 바이트가 들어 있는 레코드를 찾습니다.
3. 걸린 레코드가 4648·4672 인지, 걸린 자리가 `SubjectLogonId` 칸인지 템플릿으로 확인합니다.

### 공개 도구로 한 번

- 이벤트 뷰어의 "자세히 → XML 보기" 에서 `PrivilegeList`, `TargetServerName`, `ProcessName` 을 원문 그대로 봅니다.
- Windows 에 들어 있는 PowerShell 로 4648 을 표로 뽑을 수 있습니다. 아래는 사본 파일을 읽는 예입니다.

```powershell
Get-WinEvent -Path .\Security.evtx -FilterXPath "*[System[EventID=4648]]" -Oldest |
  ForEach-Object {
    $d = @{}
    ([xml]$_.ToXml()).Event.EventData.Data | ForEach-Object { $d[$_.Name] = $_.'#text' }
    [pscustomobject]@{
      TimeUtc  = $_.TimeCreated.ToUniversalTime()
      Subject  = "$($d['SubjectDomainName'])\$($d['SubjectUserName'])"
      LogonId  = $d['SubjectLogonId']
      UsedCred = "$($d['TargetDomainName'])\$($d['TargetUserName'])"
      Server   = $d['TargetServerName']
      Process  = $d['ProcessName']
      Ip       = $d['IpAddress']
    }
  } | Where-Object { $_.Process -notmatch '\\System32\\|\\Program Files' } | Format-Table
```

- 마지막 `Where-Object` 는 Microsoft 권장 사항처럼 System32·Program Files 밖의 프로세스만 남깁니다. 전체를 보려면 이 줄을 뺍니다.
- 4672 는 SYSTEM 기록을 걸러 낸 뒤 봅니다.

```powershell
Get-WinEvent -Path .\Security.evtx -FilterXPath "*[System[EventID=4672]]" -Oldest |
  ForEach-Object {
    $d = @{}
    ([xml]$_.ToXml()).Event.EventData.Data | ForEach-Object { $d[$_.Name] = $_.'#text' }
    [pscustomobject]@{
      TimeUtc    = $_.TimeCreated.ToUniversalTime()
      Sid        = $d['SubjectUserSid']
      User       = "$($d['SubjectDomainName'])\$($d['SubjectUserName'])"
      LogonId    = $d['SubjectLogonId']
      Privileges = ($d['PrivilegeList'].Trim() -split '\s+') -join ', '
    }
  } | Where-Object { $_.Sid -ne 'S-1-5-18' } | Format-Table -Wrap
```

- `S-1-5-18` 은 Microsoft 4624 예시의 Subject SID 입니다. 문서는 4624 를 보통 SYSTEM 계정이 남긴다고 적습니다. 이 SID 가 어느 계정인지, NETWORK SERVICE·LOCAL SERVICE 는 어떤 SID 인지는 [윈도 식별자 형식](../../../01-foundations/value-decoding/sid-guid-clsid-known-folder-id.md)에서 확인합니다. 확인한 SID 를 `Where-Object` 조건에 더합니다.
- 남은 기록의 `LogonId` 로 같은 세션의 4624 를 찾아 `ElevatedToken`·`LogonType` 을 함께 봅니다.
- 공개 도구가 `PrivilegeList` 를 한 줄로 합치거나 잘라 보여 주는지 XML 원문과 맞춰 봅니다. 방법은 [도구 결과 교차 검증](../../../03-techniques/reporting/tool-validation.md)에서 다룹니다.
- 많은 기록을 규칙으로 훑는 방법은 [이벤트 로그 규칙 검색](../../../03-techniques/analysis/sigma-rules.md)에서 다룹니다.

## 실습

직접 만든 Windows 10·11 가상 머신에서 해 봅니다. 각 단계의 시각을 적어 둡니다.

1. RUNAS 로 다른 로컬 계정을 지정해 명령 창을 엽니다. 4648 의 Subject, 자격 증명이 쓰인 계정, `TargetServerName`, `ProcessName` 을 적어 봅니다.
2. 다른 계정으로 도는 예약 작업을 만들고 실행합니다. 4648 이 남는지, 남는다면 `ProcessName` 이 무엇인지 봅니다.
3. 가상 머신 두 대를 준비합니다. 한 대에서 다른 계정의 자격 증명으로 상대의 공유 폴더에 접속합니다. 출발한 가상 머신에 4648 이 남는지, 남는다면 `TargetServerName` 이 무엇인지 봅니다. 위 함정 11번의 답이 여기서 나옵니다.
4. 관리자 계정으로 로그온합니다. 4672 의 `PrivilegeList` 와 같은 로그온 ID 의 4624 에 있는 `ElevatedToken` 을 봅니다.
5. 일반 계정으로 로그온합니다. 4672 가 생기는지, 4624 의 `ElevatedToken` 이 무엇인지 봅니다. 4번과 함께 보면 4672 와 `ElevatedToken` 이 늘 함께 나오는지 알 수 있습니다.

NIST CFReDS 같은 공개 검체의 `Security` 로그로도 풀어 봅니다.

1. 4672 가운데 SYSTEM·NETWORK SERVICE·LOCAL SERVICE 를 뺀 기록은 몇 건입니까? 어떤 계정이 남습니까?
2. 4648 의 `ProcessName` 을 종류별로 세어 봅니다. System32·Program Files 밖의 경로가 있습니까?
3. 4648 의 Subject 와 자격 증명이 쓰인 계정이 다른 기록을 찾아, 같은 로그온 ID 의 4624 와 이어 봅니다.
