# 도메인 인증 이벤트 (4768·4769·4776)

> 위치: 아티팩트 사전 > 이벤트 로그 > [로그온·로그오프 (Logon Events)](index.md)

## 한 줄 요약

도메인 인증 이벤트는 인증을 처리한 쪽 컴퓨터에 남는 기록입니다. 4768 은 키 배포 센터 (Key Distribution Center, KDC) 가 Kerberos 티켓 발급 티켓 (Ticket Granting Ticket, TGT) 을 발급할 때 남습니다. 4769 는 KDC 가 서비스 티켓 요청을 받을 때 남습니다. 두 이벤트는 도메인 컨트롤러 (Domain Controller) 에만 남습니다. 4776 은 NTLM 으로 자격 증명을 확인할 때, 그 자격 증명의 주인인 컴퓨터에 남습니다. 이 기록으로 어느 계정이 어느 주소나 컴퓨터에서 인증을 요청했는지 좁힙니다.

## 무엇을 기록하나 · 왜 생기나

세 이벤트 모두 공급자 `Microsoft-Windows-Security-Auditing` 이 `Security` 채널에 남깁니다. 세 이벤트 모두 성공과 실패를 함께 남깁니다.

| 이벤트 | 생기는 때 | 남는 곳 | 감사 하위 범주 | Task | 실패 표시 |
|---|---|---|---|---|---|
| 4768 | KDC 가 TGT 를 발급할 때마다 | 도메인 컨트롤러만 | Kerberos 인증 서비스 (Audit Kerberos Authentication Service) | 14339 | Result Code 가 0x0 이 아님 |
| 4769 | KDC 가 서비스 티켓 (TGS) 요청을 받을 때마다 | 도메인 컨트롤러만 | Kerberos 서비스 티켓 작업 (Audit Kerberos Service Ticket Operations) | 14337 | Failure Code 가 0x0 이 아님 |
| 4776 | NTLM 인증으로 자격 증명을 확인할 때마다 | 자격 증명의 주인인 컴퓨터. 도메인 계정은 도메인 컨트롤러, 로컬 계정은 그 컴퓨터 | 자격 증명 확인 (Audit Credential Validation) | 14336 | Error Code 가 0x0 이 아님 |

- 4768 의 Result Code 가 0x10·0x18 인 실패는 4768 로 남지 않습니다. Kerberos 사전 인증 실패 이벤트인 4771 로 남습니다.
- 4769 에서는 Failure Code 0x20(서비스 티켓 만료) 실패가 흔히 많이 보입니다. 이 실패는 보안상 의미가 거의 없습니다.
- 도메인 컨트롤러의 4776 에서는 NTLM 을 쓴 도메인 계정 인증 시도를 모두 볼 수 있고, 워크스테이션 잠금을 풀 때도 4776 이 생깁니다.
- 도메인 계정이 도메인 컨트롤러에 직접(로컬) 로그온할 때는 4776 이 생기지 않습니다. 계정이 저장된 컴퓨터에 로컬로 로그온하면 늘 NTLM 인증을 씁니다.
- 로컬 계정의 로그온을 볼 때는 4776 보다 4624 가 더 자세합니다. 4624 는 [로그온 세션 잇기](logon-id-4624-4634-4647.md)에서 다룹니다.

## 위치와 버전별 차이

| 이벤트 | 최소 OS | 필요한 서버 역할 | 이벤트 버전 |
|---|---|---|---|
| 4768 | Windows Server 2008 | Active Directory 도메인 컨트롤러 | 문서 머리는 0. 새 판 예시 XML 은 2 |
| 4769 | Windows Server 2008 | Active Directory 도메인 컨트롤러 | 새 판 예시 XML 은 2 |
| 4776 | Vista · Server 2008 | 없음 | 0 |

- Windows Server 2016 이후 도메인 컨트롤러는 2025년 1월 14일 이후의 보안 누적 업데이트를 받으면 4768·4769 의 새 판을 남깁니다.
- 4768 문서 머리에는 "Event Versions: 0" 이라고 적혀 있습니다. 그런데 같은 문서의 새 판 예시 XML 은 Version 이 2 입니다. 버전 1 은 문서에 나오지 않습니다.
- 한 컴퓨터가 어느 판을 남기는지는 레코드의 Version 값과 필드 목록으로 확인합니다.

| 이벤트 | 옛 판 필드 | 새 판에서 더해진 필드 |
|---|---|---|
| 4768 | `TargetUserName`, `TargetDomainName`, `TargetSid`, `ServiceName`, `ServiceSid`, `TicketOptions`, `Status`, `TicketEncryptionType`, `PreAuthType`, `IpAddress`, `IpPort`, `CertIssuerName`, `CertSerialNumber`, `CertThumbprint` | `ResponseTicket`, `AccountSupportedEncryptionTypes`, `AccountAvailableKeys`, `ServiceSupportedEncryptionTypes`, `ServiceAvailableKeys`, `DCSupportedEncryptionTypes`, `DCAvailableKeys`, `ClientAdvertizedEncryptionTypes`, `SessionKeyEncryptionType`, `PreAuthEncryptionType` |
| 4769 | `TargetUserName`, `TargetDomainName`, `ServiceName`, `ServiceSid`, `TicketOptions`, `TicketEncryptionType`, `IpAddress`, `IpPort`, `Status`, `LogonGuid`, `TransmittedServices` | `RequestTicketHash`, `ResponseTicketHash`, `AccountSupportedEncryptionTypes`, `AccountAvailableKeys`, `ServiceSupportedEncryptionTypes`, `ServiceAvailableKeys`, `DCSupportedEncryptionTypes`, `DCAvailableKeys`, `ClientAdvertizedEncryptionTypes`, `SessionKeyEncryptionType` |
| 4776 | `PackageName`, `TargetUserName`, `Workstation`, `Status` | 없음 |

한 번의 접속이 출발 PC, 도착 PC, 도메인 컨트롤러에 각각 무엇을 남기는지는 [기록이 남는 위치](pc.md)에서 다룹니다. 도메인 컨트롤러에서 이 감사가 켜져 있었는지는 [감사 정책과 로그 설정](../audit-policy-log-settings.md)에서 확인합니다.

## 구조

### 4768 의 필드

| 필드 (XML 이름) | 이벤트 뷰어의 이름 | 뜻 |
|---|---|---|
| `TargetUserName` | Account Name | TGT 를 요청한 계정입니다. 컴퓨터 계정은 `$` 로 끝납니다 (예: `WIN81$`) |
| `TargetSid` | User ID | 요청한 계정의 SID 입니다. 실패 이벤트에서는 NULL SID 입니다 |
| `ServiceName` | Service Name | 보통 `krbtgt` 입니다. 실패 이벤트에서는 보통 `krbtgt/CONTOSO` 처럼 `krbtgt/영역` 형식입니다 |
| `ServiceSid` | — | `krbtgt` 계정의 SID 입니다. `S-1-5-21-<도메인 식별자>-502` 형식입니다 |
| `TicketOptions` | Ticket Options | 티켓 옵션 비트입니다. 아래 표를 봅니다 |
| `Status` | Result Code | 결과 코드입니다. 성공이면 0x0 입니다 |
| `TicketEncryptionType` | Ticket Encryption Type | 티켓 암호화 형식입니다 |
| `PreAuthType` | Pre-Authentication Type | 사전 인증 (Pre-Authentication) 형식입니다 |
| `IpAddress` | Client Address | 요청을 보낸 컴퓨터의 IP 입니다 |
| `IpPort` | Client Port | 요청을 보낸 포트입니다. 자기 컴퓨터의 요청이면 0 입니다 |
| `CertIssuerName`, `CertSerialNumber`, `CertThumbprint` | 인증서 정보 | 스마트카드 로그온이면 인증서 발급자·일련번호·지문이 채워집니다 |

`IpAddress` 는 IPv6·IPv4 이거나 `::ffff:` 뒤에 IPv4 를 붙인 형식이고, `::1` 이면 도메인 컨트롤러 자신에서 인증한 것입니다.

### 4769 의 필드

| 필드 (XML 이름) | 이벤트 뷰어의 이름 | 뜻 |
|---|---|---|
| `TargetUserName` | Account Name | 티켓을 요청한 계정입니다. `dadmin@CONTOSO.LOCAL`, `WIN81$@CONTOSO.LOCAL` 처럼 `이름@전체 도메인 이름` 형식입니다. 비어 있을 수 있습니다 |
| `ServiceName` | Service Name | 서비스 티켓을 요청한 대상 계정이나 컴퓨터입니다. 비어 있을 수 있습니다 |
| `ServiceSid` | Service ID | 대상 계정·컴퓨터 개체의 SID 입니다. 실패 이벤트에서는 NULL SID 입니다 |
| `TicketOptions`, `TicketEncryptionType` | Ticket Options, Ticket Encryption Type | 4768 과 같은 표를 씁니다 |
| `IpAddress`, `IpPort` | Client Address, Client Port | 4768 과 같은 형식입니다 |
| `Status` | Failure Code | 실패 코드입니다. 성공이면 0x0 입니다 |
| `LogonGuid` | Logon GUID | 이 이벤트를 티켓이 발급된 대상 컴퓨터의 4624·4648·4964 와 잇는 값입니다. 잡히지 않으면 모두 0 입니다 |
| `TransmittedServices` | Transited Services | 제한된 Kerberos 위임 (Constrained Delegation) 을 썼을 때 요청된 SPN 목록입니다 |

- `TargetUserName` 은 계정의 UserPrincipalName 속성값이 아닙니다. SamAccountName 과 도메인 이름을 이어 만든 이름입니다.
- Microsoft 옛 판 예시의 `ServiceName` 은 컴퓨터 계정 `WIN2008R2$` 였습니다. 새 판 예시는 `krbtgt` 였습니다.
- `IpAddress` 가 `::1` 이면, Account Name 의 계정이 도메인 컨트롤러에 먼저 로그온한 뒤 요청한 것입니다.
- 일부 실패 코드는 `KdcExtraLogLevel` 레지스트리 값에 플래그를 켜야 남습니다. 0x01 은 SPN 을 모른다는 오류, 0x10 은 암호화 형식·잘못된 옵션 오류의 플래그입니다.

### 4776 의 필드

| 필드 (XML 이름) | 이벤트 뷰어의 이름 | 뜻 |
|---|---|---|
| `PackageName` | Authentication Package | 4776 에서는 늘 `MICROSOFT_AUTHENTICATION_PACKAGE_V1_0` 입니다 |
| `TargetUserName` | Logon Account | 자격 증명을 확인한 계정입니다 |
| `Workstation` | Source Workstation | 로그온 시도가 시작된 컴퓨터의 이름입니다 |
| `Status` | Error Code | 오류 코드입니다. 성공이면 0x0 입니다 |

- `TargetUserName` 에는 사용자 이름, `WIN81$` 같은 컴퓨터 계정, 잘 알려진 계정 이름이 들어갑니다. Local System 은 "Local", Local Service 는 "Local Service" 로 남습니다.
- `Workstation` 에는 출발 컴퓨터 이름만 남습니다. CLIENT-1 에서 SERVER-1 로 도메인 계정 인증을 하면 CLIENT-1 이 남고, 도착한 SERVER-1 은 이 이벤트에 없습니다. IP 주소 필드도 없습니다.
- Microsoft 예시는 계정 `dadmin`, Workstation `WIN81`, Status `0xc0000234` 인 실패 이벤트입니다. 이 예시의 Keywords 는 `0x8010000000000000` 이었습니다. 4624 성공 예시들의 Keywords 는 `0x8020000000000000` 이었습니다. .NET 의 `StandardEventKeywords` 에서 `0x0010000000000000` 은 감사 실패 (AuditFailure), `0x0020000000000000` 은 감사 성공 (AuditSuccess) 비트입니다. 맨 앞 `0x8000000000000000` 비트의 뜻은 공개 자료에 설명이 없습니다.

### 값 표

**티켓 옵션 (Ticket Options) — 흔한 값**

| 값 | 켜진 옵션 |
|---|---|
| `0x40810010` | Forwardable, Renewable, Canonicalize, Renewable-ok |
| `0x40810000` | Forwardable, Renewable, Canonicalize |
| `0x60810010` | Forwardable, Forwarded, Renewable, Canonicalize, Renewable-ok |

비트 번호는 MSB 0 방식입니다. 가장 왼쪽 비트가 0번입니다.

**결과 코드 (Result Code) — 4768 의 흔한 값**

| 코드 | 뜻 |
|---|---|
| 0x6 | 사용자 이름이 없습니다 |
| 0x7 | 서버 이름을 Active Directory 에서 찾지 못했습니다 |
| 0xC | 로그온 제한에 걸렸습니다 (워크스테이션·시간·스마트카드) |
| 0x12 | 계정이 사용 안 함·만료·잠김 상태입니다 |
| 0x17 | 비밀번호가 만료됐습니다 |
| 0x18 | 비밀번호가 틀렸습니다. 이 코드는 4771 에만 남습니다 |
| 0x25 | 시계 차이가 너무 큽니다 |

4768 문서는 0x17 을 4768 의 코드로 적습니다. 그런데 4769 문서의 같은 표는 0x17 이 "4768 에서는 생길 수 없고 4771 에서 생긴다" 고 적습니다. 두 문서가 서로 맞지 않으므로, 0x17 이 어느 이벤트에 남는지는 재현해 보고 판단합니다.

**티켓 암호화 형식 (Ticket Encryption Type)**

| 코드 | 형식 | 설명 |
|---|---|---|
| 0x1 | DES-CBC-CRC | Windows 7·Server 2008 R2 부터 기본으로 꺼져 있습니다 |
| 0x3 | DES-CBC-MD5 | Windows 7·Server 2008 R2 부터 기본으로 꺼져 있습니다 |
| 0x11 | AES128-CTS-HMAC-SHA1-96 | Server 2008·Vista 부터 지원합니다 |
| 0x12 | AES256-CTS-HMAC-SHA1-96 | Server 2008·Vista 부터 지원합니다 |
| 0x17 | RC4-HMAC | |
| 0x18 | RC4-HMAC-EXP | Server 2008·Vista 이전 OS 의 기본입니다 |
| 0xFFFFFFFF | — | 실패 이벤트입니다 |

새 판 4768 문서의 "Advertized Etypes" 표는 10진 23 을 0x18 RC4-HMAC-NT 로, 24 를 0x19 로 적습니다. 위 표의 0x17 RC4-HMAC 와 맞지 않습니다. 새 판의 암호화 형식 필드를 읽을 때는 값이 10진인지 16진인지 먼저 확인합니다.

## 증거로서 의미

| 증명하는 것 | 증명하지 못하는 것 |
|---|---|
| 기록 시각에 이 도메인 컨트롤러가 이 계정에 TGT 를 발급했거나 거부했습니다 (4768) | 그 계정을 쓴 사람이 누구인지 |
| 요청이 기록된 주소에서 왔습니다 (4768·4769) | 그 주소가 실제 출발 컴퓨터인지. 주소 변환 장비나 중계 서버를 거쳤을 수 있습니다 |
| 이 계정이 이 대상 계정·컴퓨터의 서비스 티켓을 요청했습니다 (4769) | 받은 티켓으로 대상 컴퓨터에 실제로 로그온했는지 |
| 이 계정의 NTLM 자격 증명 확인이 성공했거나 실패했습니다 (4776) | 어느 컴퓨터에 접속하려 했는지. 4776 에는 도착 컴퓨터가 없습니다 |
| 출발 컴퓨터가 알린 이름 (4776 의 `Workstation`) | 그 이름이 실제 출발 컴퓨터의 이름인지 |

실제로 로그온했는지는 대상 컴퓨터의 4624 로 확인합니다. 4769 의 로그온 GUID 가 0 이 아니면 대상 컴퓨터의 4624·4648 과 값으로 이을 수 있습니다.

### Microsoft 가 권하는 확인 항목

| 이벤트 | 살펴볼 조합 |
|---|---|
| 4768 | 사전 인증 형식이 0 입니다. "Do not require Kerberos preauthentication" 이 설정된 계정 말고는 없어야 합니다 |
| 4768·4769 | 티켓 암호화 형식이 0x11·0x12 가 아닙니다 (Vista·Server 2008 이후 환경) |
| 4768·4769 | 티켓 암호화 형식이 DES(0x1·0x3) 입니다 |
| 4768 | 짧은 시간에 Result Code 0x6 이 몰렸습니다. 계정 이름을 알아내려는 공격 신호일 수 있습니다 |
| 4768 | 짧은 시간에 Result Code 0x12 가 몰렸습니다. 이상 활동이나 비밀번호 대입 공격 신호일 수 있습니다 |
| 4768 | Client Port 가 0 보다 크고 1024 보다 작습니다 |
| 4776 | 로컬에서만 써야 하는 로컬 계정인데, `Workstation` 과 이벤트가 생긴 컴퓨터가 다릅니다 |

이 조합에 걸린다고 곧 공격이라고 쓰지 않습니다. 걸린 기록마다 출발 주소, 계정의 평소 쓰임, 대상 컴퓨터 기록을 이어서 판단합니다.

### 보고서 문장

아래 시각과 주소는 설명을 위해 만든 예입니다. 주소는 문서용 예약 주소입니다. 계정과 서비스 이름은 Microsoft 문서의 예시 값입니다.

- 쓸 수 있는 문장: "도메인 컨트롤러의 Security 로그에 2024-03-15 01:02:03 UTC 의 4769 가 있습니다. 계정 `dadmin@CONTOSO.LOCAL` 이 서비스 `WIN2008R2$` 의 티켓을 요청했고, 요청 주소는 `::ffff:192.0.2.10` 입니다. 실패 코드는 0x0 입니다."
- 쓰면 안 되는 문장: "dadmin 이 192.0.2.10 PC 에서 WIN2008R2 서버에 접속해 작업했습니다."

두 번째 문장은 기록에 없는 사람, 접속 성공, 작업까지 적었습니다.

## 시각 해석

`TimeCreated SystemTime` 값은 끝에 `Z` 가 붙은 UTC 형식입니다. Microsoft 문서는 이 시각이 기록한 때인지 일이 일어난 때인지 따로 밝히지 않으므로 보고서에는 "기록 시각" 으로 적습니다. 4768·4769 의 시각은 도메인 컨트롤러의 시계를 따르고, 출발 PC 와 도착 PC 의 기록은 각자의 시계를 따릅니다. 세 컴퓨터의 기록을 시간순으로 합칠 때는 컴퓨터마다 시계 차이를 보정하는데, 방법은 [타임라인 작성](../../../03-techniques/analysis/timeline/index.md)에서 다룹니다. 4768 의 Result Code 0x25 는 시계 차이가 너무 크다는 뜻이라서, 이 실패가 있으면 그 무렵 요청한 컴퓨터와 도메인 컨트롤러의 시계가 크게 달랐다고 볼 근거가 됩니다.

- 시스템 시각을 바꾼 기록은 [시간 변경](../4616-kernel-general.md)에서 찾습니다.

## 함정과 한계

1. **PC 에서 4768·4769 를 찾습니다.** 두 이벤트는 도메인 컨트롤러에만 남습니다. 도메인 계정의 인증 기록은 도메인 컨트롤러의 로그를 따로 수집해야 볼 수 있습니다.
2. **4776 에서 도착 컴퓨터와 IP 를 찾습니다.** 4776 에는 출발 컴퓨터 이름만 있습니다. IP 필드도 없습니다. 도착 컴퓨터는 그 컴퓨터의 4624 에서 찾습니다.
3. **4769 의 Account Name 을 UPN 으로 읽습니다.** 이 이름은 SamAccountName 과 도메인 이름을 이은 값입니다. 계정의 UPN 속성과 다를 수 있습니다.
4. **4768 에서 비밀번호 틀림을 찾습니다.** Result Code 0x10·0x18 은 4771 로 남습니다. 비밀번호 대입 공격을 볼 때는 4771 도 함께 봅니다.
5. **4769 의 실패를 모두 셉니다.** Failure Code 0x20(서비스 티켓 만료)은 흔히 많이 보이고 보안상 의미가 거의 없습니다. 먼저 걸러 냅니다.
6. **코드 표를 한 문서만 보고 믿습니다.** 0x17 결과 코드, RC4 암호화 형식 번호, 4768 의 이벤트 버전은 Microsoft 문서 안에서 서로 맞지 않습니다. 확정할 때는 같은 버전의 환경에서 재현합니다.
7. **기록이 없으면 실패도 없었다고 봅니다.** 일부 4769 실패 코드는 `KdcExtraLogLevel` 플래그를 켜야 남습니다. 감사 하위 범주가 꺼져 있어도 남지 않습니다.
8. **로그온 GUID 로 늘 이을 수 있다고 봅니다.** 잡히지 않은 로그온 GUID 는 모두 0 입니다. 이 경우 계정·시각·주소로 이어 보고, 그렇게 이었다고 보고서에 밝힙니다.
9. **4776 이 도메인 컨트롤러에만 남는다고 봅니다.** 로컬 계정의 4776 은 그 로컬 컴퓨터에 남습니다. 워크스테이션 잠금 해제 때도 생깁니다.
10. **도메인 컨트롤러에 직접 로그온한 기록을 4776 에서 찾습니다.** 도메인 계정이 도메인 컨트롤러에 로컬로 로그온하면 4776 이 생기지 않습니다.
11. **`::1` 을 외부 주소처럼 읽습니다.** 4768 의 `::1` 은 도메인 컨트롤러 자신에서 인증했다는 뜻입니다. 4769 의 `::1` 은 계정이 도메인 컨트롤러에 먼저 로그온한 뒤 요청했다는 뜻입니다.
12. **RC4(0x17) 티켓 요청을 곧 특정 공격으로 봅니다.** 이런 설명이 흔하지만 Microsoft 문서에는 없습니다. Microsoft 문서는 0x11·0x12 가 아닌 값을 살피라고만 권합니다. 판단은 [계정 탈취와 측면 이동](../../../04-scenarios/incident/credential-theft-lateral-movement/index.md)의 흐름을 따라 여러 기록으로 합니다.
13. **컴퓨터 계정 기록을 사람의 인증으로 봅니다.** `$` 로 끝나는 컴퓨터 계정도 TGT 와 서비스 티켓을 요청합니다. 사람 계정을 볼 때는 먼저 걸러 냅니다.

### 지우기와 조작

- **PC 의 로그를 지웁니다.** 4768·4769 는 도메인 컨트롤러에만 남으므로 PC 의 로그를 지워도 영향을 받지 않습니다. 도메인 계정의 4776 도 도메인 컨트롤러에 남습니다. PC 쪽 기록이 비어 있으면 도메인 컨트롤러 쪽을 봅니다.
- **도메인 컨트롤러의 로그를 지웁니다.** 지운 흔적은 [이벤트 로그 삭제](../1102-104.md)에서 찾습니다.
- **감사를 끕니다.** 도메인 컨트롤러의 감사 설정은 그룹 정책에 따라 다릅니다. [감사 정책과 로그 설정](../audit-policy-log-settings.md)을 먼저 확인합니다.
- **출발 컴퓨터 이름을 꾸밉니다.** 4776 의 `Workstation` 은 출발 쪽이 알린 이름입니다. 이름만으로 출발 컴퓨터를 단정하지 않습니다.

## 직접 분석해 보기

### 헥스로 한 번: 티켓 옵션 비트 풀기

티켓 옵션은 32비트 값입니다. 아래는 Microsoft 문서의 세 값을 비트로 풀어 본 예시입니다. 실제 기록에서 뽑은 값이 아닙니다.

```
0x40810010 = 0100 0000 1000 0001 0000 0000 0001 0000
0x40810000 = 0100 0000 1000 0001 0000 0000 0000 0000
0x60810010 = 0110 0000 1000 0001 0000 0000 0001 0000
             ↑ 0번 비트 (MSB 0 방식: 왼쪽부터 셉니다)
```

1. `0x40810010` 에서 켜진 비트는 1·8·15·27번입니다. 이 값은 Forwardable, Renewable, Canonicalize, Renewable-ok 입니다.
2. `0x40810000` 에서 켜진 비트는 1·8·15번입니다. 표에서 Renewable-ok 만 빠졌습니다. 그래서 27번 비트가 Renewable-ok 입니다.
3. `0x60810010` 에서는 2번 비트가 더 켜져 있습니다. 표에서 Forwarded 가 더해졌습니다. 그래서 2번 비트가 Forwarded 입니다.
4. 남은 1·8·15번은 Forwardable, Renewable, Canonicalize 입니다. 세 비트 가운데 어느 것이 어느 옵션인지는 Microsoft 문서의 비트 표에서 확인합니다.
5. 도구가 가장 오른쪽 비트를 0번으로 센다면 번호가 달라집니다. 31 에서 빼면 서로 바꿀 수 있습니다. 27번(MSB 0)은 4번(LSB 0)입니다.

값이 레코드 안에 바이트로 어떻게 놓이는지는 [로그온 유형 해석](logon-type.md)의 "헥스로 한 번" 에서 다룹니다.

### 공개 도구로 한 번

- 이벤트 뷰어의 "자세히 → XML 보기" 에서 `Status`, `TicketEncryptionType`, `IpAddress` 를 원문 그대로 봅니다.
- Windows 에 들어 있는 PowerShell 로 세 이벤트를 표로 뽑을 수 있습니다. 아래는 도메인 컨트롤러에서 가져온 사본 파일을 읽는 예입니다.

```powershell
Get-WinEvent -Path .\DC-Security.evtx -FilterXPath "*[System[(EventID=4768 or EventID=4769 or EventID=4776)]]" -Oldest |
  ForEach-Object {
    $d = @{}
    ([xml]$_.ToXml()).Event.EventData.Data | ForEach-Object { $d[$_.Name] = $_.'#text' }
    [pscustomobject]@{
      TimeUtc = $_.TimeCreated.ToUniversalTime()
      EventId = $_.Id
      Account = $d['TargetUserName']
      Service = $d['ServiceName']
      From    = if ($_.Id -eq 4776) { $d['Workstation'] } else { $d['IpAddress'] }
      Code    = $d['Status']
      EncType = $d['TicketEncryptionType']
    }
  } | Where-Object { $_.Account -notlike '*$*' } | Format-Table
```

- 마지막 `Where-Object` 는 `$` 가 들어 있는 컴퓨터 계정을 뺍니다.
- 위 확인 항목처럼 암호화 형식을 보려면 `Where-Object { $_.EncType -and $_.EncType -notin '0x11','0x12' }` 를 이어 붙입니다.
- 코드와 형식 값은 XML 에 보이는 모양 그대로 비교합니다. `-notin` 은 대소문자를 구분하지 않지만, 앞자리 0 이 다르면 (`0x12` 와 `0x00000012`) 다른 값으로 봅니다.
- python-evtx, EvtxECmd 같은 공개 도구도 이 필드들을 뽑아 줍니다. 도구가 코드를 문장으로 바꿔 보여 주면 원래 코드를 XML 과 맞춰 봅니다. 방법은 [도구 결과 교차 검증](../../../03-techniques/reporting/tool-validation.md)에서 다룹니다.
- 많은 기록을 규칙으로 검색하는 방법은 [이벤트 로그 규칙 검색](../../../03-techniques/analysis/sigma-rules.md)에서 다룹니다.

## 실습

도메인 컨트롤러 한 대와 도메인에 가입한 PC 두 대로 실습 환경을 만듭니다. 각 단계의 시각을 적어 둡니다.

1. PC-1 에 도메인 계정으로 로그온합니다. 도메인 컨트롤러의 4768 에서 Account Name, Client Address, 사전 인증 형식, 티켓 암호화 형식을 적어 봅니다.
2. 비밀번호를 한 번 틀리게 입력합니다. 도메인 컨트롤러에 4768 실패가 남는지, 4771 이 남는지 봅니다.
3. PC-1 에서 PC-2 의 공유 폴더에 컴퓨터 이름으로 접속합니다. 도메인 컨트롤러의 4769 에서 Service Name 을 봅니다. PC-2 의 4624 와 로그온 GUID 가 같은지 봅니다.
4. 같은 공유 폴더에 IP 주소로 접속합니다. 도메인 컨트롤러에 4769 가 남는지, 4776 이 남는지 봅니다.
5. PC-2 의 로컬 계정으로 PC-1 에서 PC-2 에 접속합니다. 4776 이 어느 컴퓨터에 남는지 봅니다. `Workstation` 에 무엇이 남는지도 봅니다.
6. PC-1 의 시계를 크게 틀어 놓고 도메인 계정으로 로그온합니다. 4768 의 Result Code 가 0x25 로 남는지 봅니다.

도메인 컨트롤러 이미지가 들어 있는 공개 시험 자료가 있으면 같은 질문으로 풀어 봅니다.

1. 사람 계정의 4768 을 Client Address 별로 세어 봅니다. 한 계정이 여러 주소에서 TGT 를 받았습니까?
2. 티켓 암호화 형식이 0x11·0x12 가 아닌 4769 가 있습니까? 어느 서비스에 대한 요청입니까?
3. 4776 의 `Workstation` 목록에 도메인에 없는 컴퓨터 이름이 있습니까?
