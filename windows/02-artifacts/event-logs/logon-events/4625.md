# 로그온 실패와 실패 코드 (4625)

## 한 줄 요약

이벤트 4625 는 로그온 시도가 실패할 때 보안 로그 (Security.evtx) 에 남습니다. 이 이벤트에는 시도에 쓴 계정 이름, 로그온 유형, 원격 주소, 실패 이유가 함께 적힙니다. 실패 이유는 실패 코드 (Status) 와 세부 코드 (Sub Status) 두 칸을 같이 읽어야 풀립니다. 이벤트는 로그온을 받은 컴퓨터에 남습니다. 시각은 UTC 입니다.

## 무엇을 기록하나 · 왜 생기나

Microsoft 문서는 이 이벤트가 모든 로그온 실패에 대해 남는다고 적습니다. 로그온 방식은 가리지 않습니다. 화면에서 직접 입력한 경우, 공유 폴더에 접속한 경우, 원격 데스크톱으로 들어온 경우가 모두 해당합니다.

실패하는 까닭은 여러 가지입니다.

- 비밀번호가 틀렸습니다.
- 없는 계정 이름을 썼습니다.
- 계정이 잠겼거나, 사용 안 함 상태이거나, 기한이 지났습니다.
- 그 계정에 허락되지 않은 방식이나 시간에 로그온하려 했습니다.

그래서 이 이벤트로 다음을 알 수 있습니다.

- 언제, 어떤 계정 이름으로 시도했는지
- 어떤 방식(로그온 유형)으로 시도했는지
- 원격 시도라면 어디서 왔다고 적혔는지
- 왜 실패했는지

성공한 로그온은 4624 로 따로 남습니다. 4624 와 로그오프를 잇는 방법은 [로그온 세션 잇기](/02-artifacts/event-logs/logon-events/logon-id-4624-4634-4647.md)에서 다룹니다. 로그온 유형 번호의 뜻은 [로그온 유형 해석](/02-artifacts/event-logs/logon-events/logon-type.md)에서 다룹니다. 이 페이지는 실패 이벤트의 칸과 실패 코드를 읽는 일만 다룹니다.

## 위치와 버전별 차이

### 파일과 감사 설정

| 항목 | 내용 |
|---|---|
| 로그 | 보안 (Security) |
| 파일 (Vista 이후) | `%SystemRoot%\System32\winevt\Logs\Security.evtx` |
| 공급자 | Microsoft-Windows-Security-Auditing |
| 감사 하위 범주 | 로그온 감사 (Audit Logon), 계정 잠금 감사 (Audit Account Lockout) |
| 이벤트 버전 | Microsoft 문서는 버전 0 하나만 적습니다 |
| 최소 OS | Windows Vista · Windows Server 2008 |

감사 정책이 실패를 기록하게 켜져 있어야 이 이벤트가 남습니다. 설정을 확인하는 방법은 [감사 정책과 로그 설정](/02-artifacts/event-logs/audit-policy-log-settings.md)에서 다룹니다. Microsoft 는 도메인 컨트롤러·구성원 서버·워크스테이션 모두에서 로그온 실패 감사를 켜라고 권합니다. EVTX 파일의 저장 구조는 [EVTX 파일 구조](/01-foundations/database-log-formats/evtx-evt-etl/file-header-chunk-record.md)에서 다룹니다.

### 어느 컴퓨터에 남나

이 이벤트는 로그온 시도를 받은 컴퓨터에 남습니다.

- 화면에서 직접 로그온하면, 그 컴퓨터에 남습니다.
- 공유 폴더처럼 네트워크로 접속하면, 자원이 있는 컴퓨터에 남습니다.
- 시도를 보낸 컴퓨터에는 4625 가 남지 않습니다.

도메인 계정으로 실패하면 도메인 컨트롤러에도 인증 실패가 따로 남습니다. 이 기록은 4625 가 아니라 Kerberos 사전 인증 실패(4771)나 NTLM 자격 증명 확인(4776) 같은 이벤트입니다. 자세한 내용은 [도메인 인증 이벤트](/02-artifacts/event-logs/logon-events/4768-4769-4776.md)와 [기록이 남는 위치](/02-artifacts/event-logs/logon-events/pc.md)를 봅니다.

### Windows 버전별 차이

| Windows | 로그 파일 | 로그온 실패 이벤트 |
|---|---|---|
| XP · 2003 | `SecEvent.Evt` (EVT 형식) | 실패 이유마다 이벤트 ID 가 다릅니다. 예: 529 (알 수 없는 사용자 이름 또는 잘못된 비밀번호), 530 (로그온 시간 제한 위반) |
| Vista · 2008 이후 | `Security.evtx` | 4625 하나입니다. 이유는 Status 와 Sub Status 로 나눕니다 |

옛 형식은 [구형 EVT 형식](/01-foundations/database-log-formats/evtx-evt-etl/windows-xp-2003.md)에서 다룹니다.

## 구조

### 칸 묶음

아래 XML 이름은 Microsoft 문서의 예시 이벤트에 나오는 이름입니다.

| 묶음 | XML 이름 | 뜻 | 읽을 때 주의 |
|---|---|---|---|
| 보고한 쪽 (Subject) | SubjectUserSid · SubjectUserName · SubjectDomainName · SubjectLogonId | 실패를 보고한 계정 | 시도한 사람이 아닙니다. 예시에서는 SYSTEM(S-1-5-18) 입니다 |
| 실패한 계정 | TargetUserSid · TargetUserName · TargetDomainName | 시도에 쓴 계정 | 이름은 입력한 그대로 남습니다. 예시의 SID 는 S-1-0-0 (Null SID) 입니다 |
| 실패 정보 | Status · FailureReason · SubStatus | 실패 이유 | 아래 표로 읽습니다 |
| 로그온 방식 | LogonType · LogonProcessName · AuthenticationPackageName | 로그온 유형, 로그온 프로세스, 인증 패키지 (Authentication Package) | 인증 패키지는 흔히 NTLM · Kerberos · Negotiate 입니다 |
| 인증 세부 | TransmittedServices · LmPackageName · KeyLength | Kerberos S4U 경유 서비스, NTLM 하위 버전, 세션 키 길이 | LmPackageName 은 NTLM 일 때만 찹니다. KeyLength 는 Kerberos 면 0 입니다 |
| 프로세스 | ProcessId · ProcessName | 로그온을 요청한 프로세스 | PID 는 16진수입니다 |
| 네트워크 | WorkstationName · IpAddress · IpPort | 시도한 쪽의 이름, 주소, 포트 | 127.0.0.1 이나 ::1 은 자기 자신입니다. 대화형 로그온의 포트는 0 입니다 |

TargetDomainName 으로 로컬 계정과 도메인 계정을 가립니다. 로컬 계정이면 이 칸에 컴퓨터 이름이 들어갑니다.

실패한 시도에는 새 로그온 세션이 생기지 않습니다. 이 이벤트의 로그온 ID 는 SubjectLogonId 하나이고, 보고한 쪽의 세션을 가리킵니다. 그래서 4624 처럼 로그온 ID 로 로그오프까지 이을 수 없습니다.

Microsoft 문서의 예시는 다음과 같습니다. 문서가 보여 주는 예시이며, 검체에서 나온 값이 아닙니다. 칸 일부만 옮겼습니다.

```xml
<EventID>4625</EventID>
<Keywords>0x8010000000000000</Keywords>
<TimeCreated SystemTime="2015-09-08T22:54:54.962511700Z" />
<Channel>Security</Channel>
<Data Name="SubjectUserSid">S-1-5-18</Data>
<Data Name="TargetUserSid">S-1-0-0</Data>
<Data Name="TargetUserName">Auditor</Data>
<Data Name="Status">0xc0000234</Data>
<Data Name="FailureReason">%%2307</Data>
<Data Name="SubStatus">0x0</Data>
<Data Name="LogonType">2</Data>
<Data Name="LogonProcessName">User32</Data>
<Data Name="AuthenticationPackageName">Negotiate</Data>
<Data Name="ProcessName">C:\Windows\System32\winlogon.exe</Data>
<Data Name="IpAddress">127.0.0.1</Data>
<Data Name="IpPort">0</Data>
```

Keywords 값 0x8010000000000000 은 감사 실패 (Audit Failure) 이벤트라는 표시입니다. 성공 이벤트와 이 값으로 가를 수 있습니다.

### 실패 코드 두 칸 읽기

Microsoft 문서는 Status 를 "로그온이 실패한 이유" 로, Sub Status 를 "추가 정보" 로 적습니다. 두 칸은 두 가지 모양으로 나옵니다.

| 모양 | 예 | 읽는 법 |
|---|---|---|
| Status 는 큰 분류, Sub Status 는 구체 이유 | Status 0xC000006D, Sub Status 0xC0000064 (Ultimate Windows Security 예시) | Sub Status 가 실제 이유입니다 |
| Status 가 곧 이유, Sub Status 는 0x0 | Status 0xC0000234, Sub Status 0x0 (Microsoft 예시) | Status 가 실제 이유입니다 |

그래서 Sub Status 가 0x0 이 아니면 Sub Status 를 먼저 봅니다. 0x0 이면 Status 를 봅니다. Status 만 보고 판단하면 안 됩니다. 0xC000006D 하나로는 이름이 틀렸는지 비밀번호가 틀렸는지 알 수 없습니다.

FailureReason 칸에는 `%%2307` 같은 번호가 들어 있습니다. 뷰어가 메시지 파일에서 이 번호에 맞는 문장을 찾아 보여 줍니다. 분석 PC 에 따라 문장이 안 나오거나 다르게 나올 수 있습니다. 판단은 Status 와 Sub Status 코드로 합니다. 메시지 파일은 [공급자와 메시지 파일](/01-foundations/database-log-formats/evtx-evt-etl/provider-message-table.md)에서 다룹니다.

### 실패 코드 표

이름과 뜻은 Microsoft 의 NTSTATUS 목록(MS-ERREF)과 4625 문서에서 옮겼습니다.

| 코드 | NTSTATUS 이름 | 뜻 | 해석할 때 |
|---|---|---|---|
| 0xC000006D | STATUS_LOGON_FAILURE | 이름이나 인증 정보가 틀렸습니다 | 큰 분류입니다. Sub Status 를 봅니다 |
| 0xC0000064 | STATUS_NO_SUCH_USER | 그런 계정이 없습니다 | 오타이거나 계정 이름을 짐작한 시도입니다. Microsoft 는 연달아 나오면 계정 이름 알아내기 (user enumeration) 공격의 신호일 수 있다고 적습니다 |
| 0xC000006A | STATUS_WRONG_PASSWORD | 이름은 맞고 비밀번호가 틀렸습니다 | 시도한 쪽이 실제로 있는 계정 이름을 썼다는 뜻입니다 |
| 0xC000006E | STATUS_ACCOUNT_RESTRICTION | 이름과 인증 정보는 맞지만 계정 제한에 걸렸습니다 | 구체적인 제한은 Sub Status 에서 찾습니다. 아래 함정 10번을 봅니다 |
| 0xC000006F | STATUS_INVALID_LOGON_HOURS | 허락된 시간 밖입니다 | 로그온 시간 제한이 걸린 계정입니다 |
| 0xC0000070 | STATUS_INVALID_WORKSTATION | 허락되지 않은 컴퓨터에서 시도했습니다 | Ultimate Windows Security 는 인증 정책 사일로 위반도 이 코드로 나온다고 적습니다 |
| 0xC0000071 | STATUS_PASSWORD_EXPIRED | 비밀번호 기한이 지났습니다 | |
| 0xC0000072 | STATUS_ACCOUNT_DISABLED | 사용 안 함 상태인 계정입니다 | 퇴사자 계정 같은 곳에 시도가 있었는지 봅니다 |
| 0xC0000193 | STATUS_ACCOUNT_EXPIRED | 계정 기한이 지났습니다 | |
| 0xC0000224 | STATUS_PASSWORD_MUST_CHANGE | 비밀번호를 바꿔야 로그온할 수 있습니다 | |
| 0xC0000234 | STATUS_ACCOUNT_LOCKED_OUT | 잘못된 시도가 많아 계정이 잠겼습니다 | 잠긴 동안에는 비밀번호가 맞아도 이 코드로 실패합니다 |
| 0xC000015B | STATUS_LOGON_TYPE_NOT_GRANTED | 그 로그온 유형의 권한이 없습니다 | 예: 원격 데스크톱 권한이 없는 계정의 원격 로그온 |
| 0xC0000133 | STATUS_TIME_DIFFERENCE_AT_DC | 도메인 컨트롤러와 시계 차이가 큽니다 | 시계 문제입니다. 시각 조작을 의심할 단서가 되기도 합니다 |
| 0xC000005E | STATUS_NO_LOGON_SERVERS | 로그온 서버를 쓸 수 없습니다 | Microsoft 는 보안 문제보다 인프라 문제일 때가 많다고 적습니다 |
| 0xC0000192 | STATUS_NETLOGON_NOT_STARTED | Netlogon 서비스가 켜지지 않았습니다 | 위와 같습니다 |
| 0xC0000413 | — | 인증 방화벽이 이 계정의 인증을 막았습니다 | Microsoft 4625 문서의 설명입니다 |
| 0xC0000225 | STATUS_NOT_FOUND | 대상을 찾지 못했습니다 | Ultimate Windows Security 는 윈도 버그로 보이며 위험 신호가 아니라고 적습니다 |

## 증거로서 의미

| 증명하는 것 | 증명하지 못하는 것 |
|---|---|
| 기록된 시각에 이 컴퓨터가 로그온 시도를 받았고, 그 시도가 실패했습니다 | 누가(어떤 사람이) 시도했는지 |
| 시도에 쓴 계정 이름과 도메인 이름 (입력한 그대로) | 그 계정의 주인이 시도했는지 |
| 실패 이유 코드 | 시도가 일부러 한 공격인지, 저장된 옛 비밀번호로 프로그램이 자동으로 다시 시도한 것인지 |
| 로그온 유형, 인증 패키지, 요청한 프로세스 | 워크스테이션 이름이 진짜 컴퓨터 이름인지 |
| 원격 시도라면 이 컴퓨터가 본 상대 IP 와 포트 | 그 IP 가 실제로 사람이 있던 곳인지 (NAT·VPN·중계 서버를 거칠 수 있습니다) |
| | 실패 뒤에 결국 로그온에 성공했는지 (4624 를 따로 봐야 합니다) |
| | 감사가 꺼져 있었거나 기록이 덮어써진 기간에 실패가 없었다는 것 |

### 보고서 문장

아래 시각·주소·개수는 설명을 위해 만든 예입니다. IP 는 문서용 예약 주소입니다.

- 쓸 수 있는 문장: "이 PC 의 Security.evtx 에는 2025-03-14 01:20:00 부터 01:25:00 UTC 사이 이벤트 4625 가 312건 있습니다. 모두 로그온 유형 3 이고, 원본 주소는 203.0.113.10 입니다. 계정 이름은 41개가 쓰였습니다. 이 가운데 Sub Status 0xC0000064(없는 계정)가 290건, 0xC000006A(비밀번호 틀림)가 22건입니다. 0xC000006A 는 모두 `admin` 계정입니다."
- 쓰면 안 되는 문장: "공격자가 203.0.113.10 에서 무차별 대입 공격으로 관리자 계정을 노렸다." 또는 "직원 A 가 비밀번호를 틀렸다."

두 번째 문장들은 기록에 없는 사람과 의도를 적습니다. 공격으로 판단하려면 간격, 계정 이름의 모양, 이후 4624 여부 같은 다른 근거를 함께 적습니다. 판단 절차는 [비밀번호 대입 공격이 있었나](/04-scenarios/incident/credential-theft-lateral-movement/brute-force.md)에서 다룹니다.

## 시각 해석

- 이벤트 XML 의 `TimeCreated SystemTime` 은 UTC 입니다. Microsoft 예시의 값도 끝에 `Z` 가 붙어 있습니다.
- EVTX 레코드 머리에도 기록 시각 (Written date and time) 이 FILETIME 으로 들어 있습니다. 이 값도 UTC 입니다.
- libevtx 명세는 레코드 머리의 기록 시각과 XML 의 TimeCreated 가 서로 맞지 않는 파일이 있다고 적습니다. 두 값이 다르면 둘 다 보고서에 적습니다.
- 시각은 이벤트를 남긴 컴퓨터의 시계를 따릅니다. 원격 시도라면 상대 컴퓨터의 시계와 다를 수 있습니다. 두 컴퓨터의 기록을 맞출 때는 [시간대·시계 오차 보정](/03-techniques/analysis/timeline/time-normalization.md)을 봅니다.
- 이벤트 뷰어 같은 도구는 분석 PC 의 현지 시각으로 바꿔 보여 주는 경우가 많습니다. 원래 값은 XML 에서 확인합니다.
- 시각은 인증이 실패로 끝나 기록된 때입니다. 사람이 입력을 시작한 때가 아닙니다.

FILETIME 계산은 [시각 값 형식](/01-foundations/value-decoding/filetime-unix-webkit-dos-ole.md)에서 다룹니다.

실패가 이어질 때는 간격을 봅니다. 사람이 손으로 치기 어려운 짧은 간격으로 수십·수백 건이 이어지면 프로그램이 보낸 시도일 가능성이 큽니다. 반대로 같은 계정·같은 출발지에서 일정한 간격으로 끝없이 이어지면, 옛 비밀번호를 저장한 서비스나 예약 작업일 수 있습니다. 간격만으로 단정하지 않고 다른 기록과 맞춰 봅니다.

## 함정과 한계

1. **보고한 쪽을 시도한 사람으로 읽습니다.** Subject 칸은 실패를 보고한 계정입니다. 로컬 로그온이면 흔히 SYSTEM 입니다. 시도에 쓴 계정은 TargetUserName 입니다.
2. **Status 만 봅니다.** 0xC000006D 는 큰 분류입니다. 이름이 틀렸는지 비밀번호가 틀렸는지는 Sub Status 에 있습니다.
3. **워크스테이션 이름을 믿습니다.** NTLM 인증에서 워크스테이션 이름은 시도하는 쪽이 보내는 값입니다(MS-NLMP). 보내지 않을 수도 있고, 아무 이름이나 보낼 수도 있습니다. Ultimate Windows Security 는 일부 Kerberos 로그온에서 이 칸이 비어 있다고 적습니다.
4. **IP 를 사람이 있던 곳으로 읽습니다.** 이 IP 는 이 컴퓨터가 본 상대 주소입니다. NAT·VPN·중계 서버 뒤의 실제 출발지는 다른 기록으로 찾습니다. Ultimate Windows Security 는 이 컴퓨터에서 시작한 로그온이면 실제 IP 대신 127.0.0.1 로 남는 때가 있다고 적습니다.
5. **원격 데스크톱 실패를 유형 10 에서만 찾습니다.** 원격 데스크톱 실패가 어떤 로그온 유형으로 남는지는 NLA 설정에 따라 다릅니다. [원격 데스크톱 해석 함정](/02-artifacts/event-logs/rdp-event-logs/1149-nla-3-10.md)을 봅니다.
6. **코드를 대소문자까지 맞춰 찾습니다.** XML 에는 `0xc0000234` 처럼 소문자로 들어 있습니다. 도구와 문서는 `0xC0000234` 처럼 대문자로 적습니다. 문자열로 거를 때는 대소문자를 가리지 않게 합니다.
7. **계정 이름 칸을 그대로 보고서에 옮깁니다.** 이 칸에는 입력한 문자열이 그대로 남습니다. 사용자가 이름 칸에 비밀번호를 잘못 친 경우 비밀번호가 남을 수 있습니다. 보고서에 옮길 때는 가립니다.
8. **실패를 곧 공격으로 봅니다.** 비밀번호를 바꾼 뒤 옛 비밀번호를 쥔 서비스·예약 작업·네트워크 드라이브 연결이 계속 실패를 만들 수 있습니다. 호출 프로세스, 로그온 유형, 반복 간격을 함께 봅니다.
9. **도메인 계정의 실패를 PC 에서만 찾습니다.** 도메인 컨트롤러에는 4771·4776 같은 다른 이벤트가 남습니다. [기록이 남는 위치](/02-artifacts/event-logs/logon-events/pc.md)를 봅니다.
10. **0xC000006E 를 "비밀번호가 맞았다" 는 증거로 씁니다.** NTSTATUS 설명은 이 코드를 "이름과 인증 정보는 맞지만 계정 제한에 걸렸다" 로 적습니다. 그러나 모든 인증 경로에서 비밀번호를 제한보다 먼저 확인하는지는 확인하지 못했습니다. 이 코드 하나로 단정하지 말고 같은 버전의 가상 머신에서 재현해 확인합니다(아래 실습).
11. **실패가 많은 로그를 끝까지 믿습니다.** 보안 로그는 크기 한도에 이르면 오래된 기록부터 덮어씁니다. 실패가 한꺼번에 쏟아지면 그 전 기록이 밀려날 수 있습니다. 로그 크기와 보관 방식은 [감사 정책과 로그 설정](/02-artifacts/event-logs/audit-policy-log-settings.md)에서 확인합니다.

### 지우기와 조작

- **로그를 통째로 지웁니다.** 보안 로그를 지우면 1102 가 남습니다. [이벤트 로그 삭제](/02-artifacts/event-logs/1102-104.md)와 [이벤트 로그를 지웠나](/04-scenarios/activity/anti-forensics/log-clearing.md)를 봅니다.
- **감사를 끕니다.** 실패 감사를 끄면 그 뒤로 4625 가 남지 않습니다. 기록이 없다는 사실만으로 시도가 없었다고 쓰지 않습니다. 정책 변경 흔적은 [감사 정책과 로그 설정](/02-artifacts/event-logs/audit-policy-log-settings.md)에서 다룹니다.
- **워크스테이션 이름을 꾸밉니다.** 위 함정 3번처럼 이름은 시도하는 쪽이 정합니다.
- **레코드 일부를 없앱니다.** 레코드 번호가 중간에 비거나, 청크 안에 지운 레코드가 남아 있을 수 있습니다. [파일 안에 남은 지운·손상 레코드](/01-foundations/database-log-formats/evtx-evt-etl/chunk-slack-corrupted-evtx.md)를 봅니다.
- **시스템 시각을 바꿉니다.** 4625 의 시각도 바뀐 시계를 따릅니다. [시간 변경](/02-artifacts/event-logs/4616-kernel-general.md)을 함께 봅니다.

## 직접 분석해 보기

### 헥스로 한 번

EVTX 레코드는 이진 XML 템플릿과 치환 값으로 나뉩니다. Status 같은 칸의 값은 치환 값 쪽에 들어 있습니다. 이진 XML 전체 구조는 [이진 XML 해석](/01-foundations/database-log-formats/evtx-evt-etl/binary-xml-template.md)에서 다룹니다. 여기서는 4625 의 실패 코드가 바이트로 어떻게 보이는지만 따라갑니다.

libevtx 명세에 따르면 치환 값 영역은 세 부분입니다.

1. 값 개수 (4바이트)
2. 값 설명 배열: 한 칸이 4바이트입니다. 값 크기 2바이트, 값 형식 1바이트, 빈 바이트 1바이트 순서입니다.
3. 값 데이터: 값 설명 배열과 같은 순서로 이어집니다.

이 페이지에 필요한 값 형식은 다음과 같습니다.

| 형식 번호 | 이름 | 4625 에서 쓰는 칸 |
|---|---|---|
| 0x01 | 문자열 (UTF-16LE, 끝 문자 없음) | TargetUserName · FailureReason 등 |
| 0x08 | 32비트 부호 없는 정수 | LogonType · KeyLength |
| 0x13 | SID | SubjectUserSid · TargetUserSid |
| 0x14 | 32비트 정수 (16진 표시) | Status · SubStatus |
| 0x15 | 64비트 정수 (16진 표시) | SubjectLogonId |

아래는 명세를 보고 만든 예시입니다. 값은 Microsoft 문서의 예시 이벤트(Status 0xc0000234, FailureReason %%2307, SubStatus 0x0, LogonType 2)에서 가져왔습니다. 검체에서 뽑은 바이트가 아닙니다. 네 칸이 EventData 의 순서대로 이어진다고 가정했습니다. 실제 순서는 템플릿이 정하므로 파일에서 확인합니다.

값 설명 배열 가운데 네 칸입니다.

```
04 00 14 00    크기 4,  형식 0x14 (16진 정수)   → Status
0C 00 01 00    크기 12, 형식 0x01 (문자열)      → FailureReason
04 00 14 00    크기 4,  형식 0x14               → SubStatus
04 00 08 00    크기 4,  형식 0x08 (정수)        → LogonType
```

값 데이터 가운데 같은 네 칸입니다.

```
34 02 00 C0                               → Status
25 00 25 00 32 00 33 00 30 00 37 00       → FailureReason
00 00 00 00                               → SubStatus
02 00 00 00                               → LogonType
```

1. Status 의 `34 02 00 C0` 를 리틀 엔디언으로 읽으면 0xC0000234 입니다. 계정 잠김입니다.
2. FailureReason 의 12바이트는 UTF-16LE 문자 6개입니다. `%%2307` 입니다. 끝 문자는 없습니다.
3. SubStatus 는 0x0 입니다. 그래서 Status 가 실제 이유입니다.
4. LogonType 은 2 입니다. 대화형 로그온입니다.

실패 이유가 다르면 SubStatus 자리가 바뀝니다.

| 경우 | Status 바이트 | SubStatus 바이트 |
|---|---|---|
| 비밀번호 틀림 (예) | `6D 00 00 C0` | `6A 00 00 C0` |
| 없는 계정 (Ultimate Windows Security 예시의 조합) | `6D 00 00 C0` | `64 00 00 C0` |

TargetUserSid 가 S-1-0-0 이면 SID 값은 12바이트 `01 01 00 00 00 00 00 00 00 00 00 00` 입니다. 앞에서부터 개정 번호 1, 하위 권한 개수 1, 권한 식별자 0(6바이트), 하위 권한 0(4바이트)입니다. SID 형식은 [윈도 식별자 형식](/01-foundations/value-decoding/sid-guid-clsid-known-folder-id.md)에서 다룹니다.

`6A 00 00 C0` 같은 4바이트만으로 비할당 영역을 찾으면 엉뚱한 곳도 많이 걸립니다. 레코드 서명 `2A 2A 00 00` 과 함께 확인합니다. 방법은 [레코드 카빙](/03-techniques/analysis/data-recovery/record-carving.md)에서 다룹니다.

> 그림 자리: 4625 레코드 하나에서 값 설명 배열의 Status·FailureReason·SubStatus·LogonType 네 칸과, 값 데이터의 해당 바이트를 선으로 이어 보여 주는 그림

### 공개 도구로 한 번

윈도에 들어 있는 이벤트 뷰어, 그리고 libevtx 의 `evtxexport`, python-evtx, EvtxECmd 같은 공개 도구로 4625 를 볼 수 있습니다. 여러 대의 로그를 규칙으로 훑을 때는 Sigma 규칙을 쓰는 도구를 흔히 씁니다([이벤트 로그 규칙 검색](/03-techniques/analysis/sigma-rules.md)).

도구를 쓸 때는 다음을 확인합니다.

- Status 와 Sub Status 를 원래 코드로 보여 주는지, 문장으로 바꿔 보여 주는지 확인합니다. 문장만 보여 주면 코드를 따로 확인합니다.
- 시각을 UTC 로 보여 주는지, 현지 시각으로 바꿔 보여 주는지 확인합니다.
- 청크에 남은 지운 레코드를 읽는지 확인합니다.
- 레코드 한두 개는 XML 원문이나 헥스와 맞춰 봅니다. 방법은 [도구 결과 교차 검증](/03-techniques/reporting/tool-validation.md)에서 다룹니다.

## 실습

**공개 샘플 EVTX-ATTACK-SAMPLES** (https://github.com/sbousseaden/EVTX-ATTACK-SAMPLES) 는 공격 기법별로 모은 EVTX 파일 모음입니다. `Credential Access` 폴더에서 두 파일을 씁니다.

1. `CA_4624_4625_LogonType2_LogonProc_chrome.evtx` 에서 4625 를 모두 찾으십시오. Status·Sub Status·로그온 유형·로그온 프로세스·호출 프로세스를 표로 적어 보십시오.
2. 1번의 조합에서 평범한 대화형 로그온 실패와 다른 점을 적어 보십시오. 같은 파일의 4624 와도 비교해 보십시오.
3. 1번 레코드 하나를 헥스로 열어 Status 와 Sub Status 의 4바이트를 직접 찾아 보십시오.
4. `kerberos_pwd_spray_4771.evtx` 에 4625 가 있는지 확인하십시오. 없다면 어느 컴퓨터의 로그인지, 왜 다른 이벤트로 남았는지 적어 보십시오.

**직접 만든 Windows 10·11 가상 머신**에서도 해 봅니다. 각 단계의 시각을 적어 둡니다.

1. 로컬 계정으로 비밀번호를 틀리고, 없는 이름으로도 한 번 시도합니다. 두 이벤트의 Status 와 Sub Status 를 비교합니다.
2. 계정을 사용 안 함으로 바꿉니다. 맞는 비밀번호와 틀린 비밀번호로 한 번씩 시도합니다. 두 이벤트의 코드가 같은지 봅니다. 위 함정 10번의 답이 여기서 나옵니다.
3. 계정 잠금 임계값을 정하고 잠길 때까지 틀립니다. 잠긴 뒤 맞는 비밀번호로 시도해 코드를 봅니다.
4. 다른 가상 머신에서 공유 폴더에 틀린 비밀번호로 접속합니다. 로그온 유형, 워크스테이션 이름, IP 가 어떻게 남는지 봅니다. 시도를 보낸 쪽 가상 머신에 무엇이 남는지도 봅니다.
5. 적어 둔 시각과 이벤트의 UTC 시각을 맞춰 봅니다.
