# 네이버 MYBOX (Naver MYBOX)

## 한 줄 요약

네이버 MYBOX 는 네이버의 클라우드 저장소이고, PC 에서는 동기화 앱이 사용자 프로필 아래에 DB 파일을 남기는 것으로 보입니다. 이 페이지를 쓸 때 MYBOX 관련 공개 자료는 하나도 확인하지 못했으므로, 아래 파일·표·칸 이름은 모두 검체에서 찾아볼 후보입니다. 보고서에 쓰기 전에 검체에서 이름과 뜻을 직접 확인합니다.

> **(구현)** 표시는 한 포렌식 분석 구현의 소스 코드에 들어 있던 파일·표·칸 이름입니다. 실제 검체나 공개 자료로 확인하지 않았고, 어느 앱 버전 것인지도 모릅니다. **(확인 못 함)** 은 공개 자료로 확인하지 못했다는 뜻입니다.

## 무엇을 기록하나 · 왜 생기나

구현에서 본 후보는 DB 세 종류입니다.

| 후보 | 담긴 것으로 보이는 기록 | 표시 |
|---|---|---|
| `sync_info.db` | 동기화하는 파일·폴더 목록과 파일 시각 | 구현 |
| `NDNetIOLog.db` | 파일 만들기·고치기·지우기·옮기기 기록과, 파일을 건드린 프로세스 이름 | 구현 |
| `ODSyncLog.db`, `NDSyncLog.db` | 동기화 폴더별 파일 목록 | 구현 |

포렌식에서 이 후보를 찾는 이유는 아래와 같습니다.

입출력 로그에 프로세스 이름 칸이 있다면 어떤 프로그램이 동기화 폴더의 파일을 건드렸는지 볼 수 있고, 지우기·옮기기 기록이 있다면 지금 폴더에 없는 파일의 흔적을 찾을 수 있습니다. 동기화 목록으로는 어느 파일이 클라우드와 맞춰지는 대상이었는지 봅니다.

## 위치와 버전별 차이

| 기록 | 위치 | 표시 |
|---|---|---|
| 프로그램 데이터 | `%LOCALAPPDATA%\MYBOX\Accounts\<계정 폴더>\` | 구현 |
| 각 DB 가 이 폴더 안 어디에 있는지 | — | 확인 못 함 |
| 기본 동기화 폴더 이름과 위치 | — | 확인 못 함 |

- `%LOCALAPPDATA%` 는 보통 `C:\Users\<사용자>\AppData\Local` 입니다.
- 계정 폴더 이름이 어떤 규칙으로 정해지는지는 확인하지 못했습니다.

| 이름 | 짐작 | 표시 |
|---|---|---|
| `ND` 로 시작하는 파일 (`NDNetIOLog.db`, `NDSyncLog.db`) | 예전 서비스 이름 N드라이브 시절의 이름으로 보입니다 | 확인 못 함 |
| `OD` 로 시작하는 파일 (`ODSyncLog.db`) | 새 형식의 이름으로 보입니다 | 확인 못 함 |

- N드라이브가 MYBOX 로 바뀐 시기는 확인하지 못했습니다. 한 PC 에 옛 이름과 새 이름 파일이 함께 있을 수 있다고 보고 둘 다 찾습니다.
- MYBOX 가 클라우드 파일 API 로 동기화 루트를 등록하는지, 가상 드라이브를 쓰는지는 확인하지 못했습니다. 확인하는 법은 [클라우드 동기화 공통 구조](cloud-files-api-syncrootmanager.md) 에 있습니다.

## 구조

아래 표와 칸은 모두 구현에서 본 이름입니다. 구현은 이 파일들을 표와 칸으로 읽었습니다. SQLite 파일인지는 검체에서 파일 머리로 먼저 확인합니다. SQLite 파일을 읽는 법은 [SQLite 데이터베이스](../../01-foundations/database-log-formats/sqlite/index.md) 에 있습니다.

### `sync_info.db` (구현)

| 표 | 칸 |
|---|---|
| `sync_table` | `path_component`, `file_size`, `local_base_path`, `creation_time`, `last_write_time`, `last_access_time`, `is_directory` |

시각 칸은 숫자입니다. 구현은 값의 크기로 Unix 초인지 밀리초인지 짐작해 바꿨습니다.

### `NDNetIOLog.db` (구현)

| 표 | 칸 |
|---|---|
| `tb_io_log` | `src_path`, `dest_path`, `process`, `size`, `io_date`, `param`, `iotype`, `actoin` |

`actoin` 은 칸 이름 철자가 틀린 그대로이며 `action` 이 아닙니다. `process` 칸은 파일을 건드린 프로세스 이름으로 짐작하고, `io_date` 는 문자열 날짜입니다. `param`, `iotype` 칸의 뜻은 확인하지 못했습니다.

구현이 `actoin` 값을 읽은 방식은 아래와 같습니다.

| `actoin` | 구현의 해석 |
|---|---|
| 0 | 만들기·고치기 |
| 1 | 지우기 |
| 2 | 옮기기 또는 이름 바꾸기 |

값 2 는 옮기기와 이름 바꾸기를 함께 뜻하는데, 구현은 `src_path` 와 `dest_path` 의 파일 이름이 같으면 옮기기, 다르면 이름 바꾸기로 갈랐습니다.

### `ODSyncLog.db`·`NDSyncLog.db` (구현)

이 DB 는 표 이름을 한 번 거쳐 찾습니다.

| 순서 | 표 | 칸 |
|---|---|---|
| 1 | `tb_sync_conf_info` | `tb_file_info` 칸이 동기화 폴더별 표 이름을 가리킵니다 |
| 2 | 1에서 찾은 표 | `file_name`(전체 경로), `dir_flag`, `file_time`, `file_size` |

`ODSyncLog.db` 는 새 이름, `NDSyncLog.db` 는 예전 이름으로 짐작합니다.

## 증거로서 의미

공개 자료가 없으므로, 아래는 검체에서 표와 칸의 뜻을 확인했다는 전제에서 씁니다.

### 증명하는 것

- `sync_table` 에 행이 있으면, 그 경로가 앱의 동기화 목록에 있었습니다.
- `tb_io_log` 에 행이 있으면, 앱이 그 파일의 변경을 적었습니다.
- `process` 칸이 프로세스 이름이라면, 어떤 프로그램 이름으로 파일을 건드렸는지 봅니다.
- `actoin` 이 1 인 행이 지우기라면, 지금 폴더에 없는 파일의 경로와 크기를 봅니다.
- `src_path` 와 `dest_path` 로 파일이 어디에서 어디로 갔는지 봅니다.

### 증명하지 못하는 것

- 프로세스 이름은 사람이 아닙니다. 누가 그 프로그램을 썼는지는 [그 시각에 PC 를 쓴 사람이 누구인가](../../04-scenarios/activity/user-attribution.md) 의 흐름으로 따로 따집니다.
- `tb_io_log` 가 로컬 파일 변경을 적는지, 클라우드 올리기를 적는지는 확인하지 못했습니다. 그래서 이 표만으로 파일이 클라우드로 올라갔다고 쓰지 않습니다.
- 구현의 해석(0·1·2 의 뜻, 옮기기와 이름 바꾸기 가르기)은 공개 자료로 확인한 것이 아닙니다. 보고서에는 원래 값을 함께 적습니다.
- 동기화 목록에 있다고 그 파일 내용이 PC 에 있었다고 단정하지 않습니다.

## 시각 해석

| 칸 | 형식 | 확인한 것 |
|---|---|---|
| `sync_table` 의 `creation_time`, `last_write_time`, `last_access_time` | 숫자 | 구현은 Unix 초·밀리초를 값 크기로 짐작했습니다. 단위와 시간대는 확인하지 못했습니다 |
| `tb_io_log` 의 `io_date` | 문자열 날짜 | 구현은 값을 한국 시간(UTC+9) 그대로 저장했습니다. UTC 인지 현지 시각인지는 확인하지 못했습니다 |
| 동기화 폴더별 표의 `file_time` | 확인 못 함 | 형식과 시간대를 확인하지 못했습니다 |

- 숫자 시각은 자릿수로 단위를 먼저 가립니다. 방법은 [시각 값 형식](../../01-foundations/value-decoding/filetime-unix-webkit-dos-ole.md) 에 있습니다.
- `io_date` 의 시간대는 시험으로 확인합니다. 시험 PC 에서 시각을 적어 두고 동기화 폴더에 파일을 하나 만든 뒤, 새로 생긴 행의 `io_date` 와 비교합니다.
- 검체 PC 의 시간대 설정은 [시간대 설정](../system-account/time-zone.md) 에서 확인합니다.

## 함정과 한계

- **공개 자료가 없습니다.** 이 페이지의 모든 이름은 한 구현에서 본 것입니다. 앱 버전이 다르면 이름이 다를 수 있습니다.
- **칸 이름 철자를 그대로 씁니다.** `action` 으로 조회하면 칸이 없다는 오류가 납니다. `actoin` 으로 씁니다.
- **도구가 보여 주는 "옮기기·이름 바꾸기" 는 해석입니다.** 원래 값은 `actoin` 2 하나입니다. `src_path` 와 `dest_path` 를 직접 보고 판단합니다.
- **표 이름을 한 번 거쳐 찾습니다.** `ODSyncLog.db`·`NDSyncLog.db` 에서 파일 목록 표 이름은 고정돼 있지 않은 것으로 보입니다. `tb_sync_conf_info` 를 먼저 읽습니다.
- **옛 이름과 새 이름 파일을 모두 찾습니다.** `ND` 파일만 보거나 `OD` 파일만 보면 기록 일부를 놓칠 수 있습니다.
- **시간대를 짐작하지 않습니다.** `io_date` 가 실제로 한국 시간인데 UTC 로 보고 다른 기록과 섞으면 9시간 어긋납니다.

## 직접 분석해 보기

### 헥스로 한 번

**숫자 시각의 단위 가리기.** 아래는 같은 순간(2024-01-01 00:00:00 UTC)을 두 단위로 적은 예시 값입니다. 특정 검체에서 옮긴 값이 아닙니다.

```
Unix 초 (10자리):      1704067200     = 0x65920080
Unix 밀리초 (13자리):  1704067200000  = 0x18CC251F400

초를 밀리초로 잘못 읽으면:  1970-01-20 근처
밀리초를 초로 잘못 읽으면:  수만 년 뒤
```

- 10자리 값이면 초, 13자리 값이면 밀리초로 먼저 읽어 봅니다.
- 바꾼 날짜가 앱을 깐 뒤의 날짜인지 확인합니다. 1970년 근처나 먼 미래로 나오면 단위를 잘못 고른 것입니다.
- SQLite 가 정수를 레코드 안에 어떻게 저장하는지는 [SQLite 데이터베이스](../../01-foundations/database-log-formats/sqlite/index.md) 에 있습니다. 헥스 편집기로 레코드를 직접 읽을 때는 그 페이지의 방법으로 값을 꺼낸 뒤 위처럼 자릿수를 봅니다.

### 공개 도구로 한 번

1. `%LOCALAPPDATA%\MYBOX\` 폴더 전체를 사본으로 뜹니다. DB 옆에 붙은 파일도 함께 뜹니다.
2. 폴더 안에서 확장자가 `.db` 인 파일을 모두 찾습니다. 후보 이름과 맞춰 봅니다.
3. SQLite 뷰어로 사본을 엽니다. 먼저 표 이름 목록을 봅니다.

```sql
SELECT name FROM sqlite_master WHERE type = 'table';
```

4. `tb_io_log` 가 있으면 후보 칸을 조회합니다.

```sql
SELECT io_date, actoin, src_path, dest_path, process, size
FROM tb_io_log
ORDER BY io_date;
```

5. `ODSyncLog.db` 나 `NDSyncLog.db` 가 있으면 파일 목록 표 이름부터 찾습니다.

```sql
SELECT tb_file_info FROM tb_sync_conf_info;
```

6. 5에서 나온 표 이름으로 `file_name`, `file_time`, `file_size` 를 조회합니다.

| 프리페치·AmCache | `process` 칸의 프로그램을 실행한 기록을 봅니다 | [프리페치](../execution/prefetch/index.md), [AmCache](../execution/amcache-hve/index.md) |
| USN 변경 저널 | 같은 시각 무렵 같은 경로의 파일 변경 기록을 봅니다 | [USN 변경 저널](../filesystem/usnjrnl.md) |
| 휴지통 | `actoin` 1 행의 파일이 휴지통에 있는지 봅니다 | [휴지통](../file-folder-usage/recycle-bin.md) |

반출 여부를 따지는 흐름은 [자료를 밖으로 빼돌렸나](../../04-scenarios/exfiltration/data-exfiltration/index.md) 에, 지운 파일을 따라가는 흐름은 [지운 파일의 흔적 찾기](../../04-scenarios/activity/deleted-file-traces.md) 에 있습니다.

## 실습

MYBOX 를 깐 시험 PC 를 직접 만들어 아래 질문을 풀어 봅니다. MYBOX 가 들어 있는 공개 검체를 찾으면 같은 질문을 풉니다.

1. `%LOCALAPPDATA%\MYBOX\` 아래 폴더 구조는 어떻습니까? `Accounts\<계정 폴더>` 가 있습니까?
2. 이 페이지의 후보 DB 가운데 실제로 있는 것은 무엇입니까? 후보에 없는 DB 는 무엇입니까?
3. 동기화 폴더에 파일을 만들고, 이름을 바꾸고, 다른 폴더로 옮기고, 지웁니다. `tb_io_log` 에 행이 몇 개 생깁니까? `actoin` 값은 각각 무엇입니까?
4. 3번에서 적어 둔 시각과 `io_date` 를 비교합니다. `io_date` 는 UTC 입니까, 한국 시간입니까?
5. `sync_table` 의 시각 칸은 몇 자리입니까? 초와 밀리초 가운데 어느 단위로 읽어야 파일을 만든 시각과 맞습니까?
6. `process` 칸에는 무엇이 적힙니까? 탐색기로 옮긴 파일과 다른 프로그램으로 저장한 파일의 값이 다릅니까?

## 참고 문헌

이 페이지를 쓸 때 열어 본 MYBOX 공개 자료는 없습니다. 이 페이지의 이름은 모두 검체로 확인할 후보입니다.
