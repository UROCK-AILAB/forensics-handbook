# PDF 증분 저장과 이전 판 복원 (Incremental Update)

PDF 는 고친 내용을 원래 파일 끝에 덧붙여 저장할 수 있습니다. 이 방식을 증분 저장 (incremental update) 이라고 합니다. 앞부분의 옛 객체는 지워지지 않고 남습니다. 그래서 알맞은 위치에서 파일을 자르면 고치기 전 판을 되살릴 수 있습니다.

> Word(Microsoft 365, 16.0.20326)로 내보낸 PDF 를 pypdf 6.19.0 의 증분 쓰기 (`incremental=True`) 로 고쳐 정보 사전의 `Author`·`ModDate` 를 바꾸면, 원래 내용은 그대로 두고 파일 끝에 새 정보 사전과 xref 가 붙습니다. 아래 값은 이 경우의 값입니다.

## 무엇을 기록하나 · 왜 생기나

ExifTool 은 PDF 메타데이터를 고칠 때 증분 저장 방식을 씁니다. 이 방식은 빠르고, 고친 내용을 되돌릴 수 있습니다.

ExifTool 이 덧붙인 수정 묶음 (PDF-update) 을 `-PDF-update:all=` 로 지우면 원래 파일을 되찾습니다. 옛 정보는 파일에서 실제로 지워지지 않으므로 보안 문제가 될 수 있습니다. 옛 정보를 영구히 지우려면 qpdf 로 파일을 다시 씁니다 (`qpdf --linearize`). 선형화 (linearized) 된 PDF 는 증분 저장 뒤 더는 선형화 상태가 아닙니다.

포렌식에서는 이 성질이 쓸모 있습니다. 누군가 메타데이터를 고쳤어도, 덧붙여 저장했다면 고치기 전 값이 파일 안에 남습니다.

정보 사전과 XMP 가 무엇을 담는지는 [PDF 정보 사전과 XMP (PDF Info·XMP)](pdf-info-xmp.md) 에서 다룹니다.

## 위치와 버전별 차이

PDF 파일 끝은 이런 모양입니다.

```
startxref
(교차 참조 표 또는 교차 참조 스트림 객체의 위치)
%%EOF
```

`startxref` 뒤의 수는 교차 참조 표 (`xref` 키워드로 시작) 나 교차 참조 스트림 객체의 위치이고, 교차 참조 스트림은 PDF 1.5 에서 들어왔습니다. 증분 저장을 하면 이 끝부분이 파일 뒤쪽에 한 벌 더 붙습니다.

값의 모양은 Windows 버전이 아니라 PDF 를 쓴 프로그램에 따라 달라집니다.

## 구조

### pypdf 로 고친 파일

원본 19,682바이트짜리 PDF 를 이렇게 고치면 파일은 20,446바이트가 됩니다.

```
[0 ~ 19,681]    원본 19,682바이트 그대로
                  └ 옛 18 0 obj (바꾸기 전 Author 등) 도 여기 그대로 남음
[덧붙은 부분]
18 0 obj        정보 사전을 새 값 (Author, ModDate) 으로 다시 정의
24 0 obj        새 교차 참조 스트림
                  /Type /XRef
                  /Index [ 18 1 ]      ← 바뀐 객체 18 하나만 담음
                  /Prev 19503          ← 원본의 마지막 startxref 값
                  /Info 18 0 R
                  /ID [원본과 같은 값 두 개]
startxref
20174
%%EOF
```

- 새 파일의 앞 19,682바이트는 원본과 바이트 단위로 같습니다.
- 덧붙은 부분은 같은 번호의 객체 `18 0 obj` 를 새 값으로 다시 정의합니다.
- 새 교차 참조 스트림의 `/Prev` 는 원본의 마지막 `startxref` 값을 가리킵니다.
- 고친 파일에서 읽은 정보 사전 값은 새 값입니다.
- 새 파일을 원본 길이 (19,682바이트) 에서 자르면 원본과 같은 파일이 됩니다.

### 한 번만 저장했는데 %%EOF 가 두 개

Word 의 "PDF 로 내보내기" 한 번으로 만든 파일에도 `%%EOF` 가 두 개 있습니다. 위 파일에서 끝 위치는 19,501 과 19,682 입니다.

두 번째 부분에는 비어 있는 옛 방식 교차 참조와 트레일러만 있습니다.

```
xref
0 0
trailer
<< /Size 24 /Root 1 0 R /Info 18 0 R /ID[…] /Prev 18866 /XRefStm 18578 >>
```

첫 `%%EOF` 에서 자른 파일도 pypdf 로 1쪽짜리 PDF 로 열립니다.

## 증거로서 의미

**증명하는 것**

- 덧붙은 부분에서 다시 정의된 객체가 있으면, 그 객체를 파일 끝에 덧붙여 고친 기록이 있습니다.
- 다시 정의된 객체와 앞부분의 옛 객체를 비교하면 무엇이 바뀌었는지 압니다. 위 파일에서는 옛 `Author` 와 새 `Author` 가 둘 다 남아 있습니다.
- 덧붙은 부분 앞에서 자른 사본은 덧붙이기 전 파일의 바이트를 보여 줍니다.

**증명하지 못하는 것**

- 몇 번 고쳤는지. `%%EOF` 개수는 편집 횟수가 아닙니다. 한 번 내보낸 파일에도 두 개가 있습니다.
- 잘라 낸 사본이 예전에 따로 저장된 판이라는 것. Word 가 한 번에 쓴 파일도 첫 `%%EOF` 에서 자르면 PDF 로 열립니다. 열리는 사본이 곧 사람이 저장한 이전 판은 아닙니다.
- 언제, 누가 덧붙였는지. pypdf 가 덧붙인 부분에서 시각을 알려 주는 값은 다시 정의한 정보 사전의 `ModDate` 뿐입니다. 이 값에는 고친 사람이 정한 값 (위 파일에서는 21:00:00) 이 그대로 들어갑니다.
- 덧붙은 부분이 없으면 고친 적이 없다는 것. qpdf 같은 도구로 파일을 처음부터 다시 쓰면 옛 판이 남지 않을 수 있습니다.

보고서 문장은 기록으로 확인되는 만큼만 씁니다.

- 쓰지 않을 문장: "피의자가 21:00 에 작성자를 조작했다."
- 쓸 문장: "result.pdf 에는 `%%EOF` 가 세 번 나온다. 마지막 부분에서 객체 18 (정보 사전) 이 다시 정의돼 있고, 이 객체의 `Author` 값은 앞부분 객체 18 의 값과 다르다. 다시 정의된 객체의 `ModDate` 값은 `D:20260923210000+09'00'` 이며, 이 값은 덧붙인 도구가 적은 값이다." (예시 문장입니다.)

## 시각 해석

- pypdf 가 덧붙인 부분에는 따로 시각 필드가 없습니다. 시각은 다시 정의한 정보 사전 안의 `ModDate` 뿐입니다.
- 그 `ModDate` 는 고친 도구가 넣은 값이며, 원하는 값을 그대로 넣을 수 있습니다.
- 정보 사전만 고치면 XMP 는 바뀌지 않아 `xmp:ModifyDate` 는 옛 값 그대로 남습니다. 이 어긋남은 [PDF 정보 사전과 XMP (PDF Info·XMP)](pdf-info-xmp.md) 에서 다룹니다.
- 파일이 디스크에서 언제 커졌는지는 [마스터 파일 테이블](../../filesystem/mft.md) 과 [USN 변경 저널](../../filesystem/usnjrnl.md) 에서 봅니다.

## 함정과 한계

- **`%%EOF` 개수로 편집 횟수를 세지 않습니다.** 한 번 내보낸 Word PDF 에도 두 개가 있습니다. 덧붙은 부분마다 실제로 다시 정의된 객체가 있는지 봅니다.
- **`/ID` 가 같아도 고친 파일일 수 있습니다.** pypdf 는 `/ID` 두 항목을 모두 원본 값 그대로 둡니다.
- **XMP 는 그대로일 수 있습니다.** pypdf 로 정보 사전만 고치면 XMP 는 바뀌지 않습니다.
- **선형화가 풀립니다.** 증분 저장 뒤에는 선형화 상태가 아닙니다. 선형화 표시가 있는데 끝에 덧붙은 부분이 있으면 따로 적어 둡니다.
- **다시 쓴 파일에는 옛 판이 없을 수 있습니다.** 옛 판이 없다는 사실만으로 고친 적이 없다고 보지 않습니다.
- **원본에 도구를 돌리지 않습니다.** ExifTool 의 `-PDF-update:all=` 처럼 파일을 바꾸는 명령은 사본에만 씁니다.
- **전자 서명된 PDF 는 따로 봅니다.** 서명과 증분 저장이 어떻게 얽히는지는 실제 데이터로 확인합니다.

## 직접 분석해 보기

### 헥스로 한 번

`%%EOF` 는 ASCII 로 `25 25 45 4F 46` 입니다. 헥스 편집기에서 이 바이트를 모두 찾습니다.

절차는 아래와 같습니다.

1. 원본의 해시를 구하고 사본을 만듭니다. 원본은 건드리지 않습니다.
2. 사본에서 `%%EOF` 가 나오는 위치를 모두 찾습니다.
3. 각 위치 바로 뒤에서 잘라 사본을 하나씩 만듭니다.
4. 마지막 `%%EOF` 에서 자른 사본이 원본 전체 길이와 같은지 봅니다. 다르면 `%%EOF` 뒤에 남은 바이트를 확인합니다.
5. 사본마다 PDF 로 열리는지 봅니다. 정보 사전·XMP·쪽 내용이 어떻게 다른지 비교합니다.
6. 덧붙은 부분마다 `n 0 obj` 로 다시 정의된 객체 번호를 적습니다. 같은 번호의 앞부분 객체와 비교하면 무엇이 바뀌었는지 압니다.
7. 덧붙은 부분의 교차 참조에서 `/Prev` 값을 적습니다. 앞 부분의 `startxref` 값과 같은지 봅니다.

### 공개 도구로 한 번

Python 으로 3단계를 할 수 있습니다. 원본을 읽기만 하고, 잘라 낸 파일은 새로 씁니다.

```python
data = open("original.pdf", "rb").read()
pos, n = 0, 0
while True:
    i = data.find(b"%%EOF", pos)
    if i < 0:
        break
    end = i + len(b"%%EOF")
    n += 1
    with open(f"cut_{n}_{end}.pdf", "wb") as f:
        f.write(data[:end])
    print(n, end)
    pos = end
print("원본 길이", len(data))
```

잘라 낸 사본은 pypdf 로 열어 봅니다.

```python
from pypdf import PdfReader

r = PdfReader("cut_1_19501.pdf")        # 앞 코드가 만든 파일 이름
print(len(r.pages), r.metadata)
```

- 다시 정의된 객체 번호는 `re.finditer(rb"(\d+) (\d+) obj", data)` 로 위치와 함께 모아 볼 수 있습니다. 같은 번호가 두 번 넘게 나오는 것을 고릅니다. 이 글자 검색 결과는 도구 결과와 맞춰 봅니다.
- ExifTool 로 고친 파일은 사본에 `-PDF-update:all=` 를 주면 원래 파일로 되돌아갑니다. 되돌린 사본과 잘라 낸 사본을 비교합니다.
- 결과가 서로 다르면 [도구 결과 교차 검증](../../../03-techniques/reporting/tool-validation.md) 을 따릅니다.

## 실습

공개 데이터셋 가운데 PDF 가 들어 있는 이미지를 고르거나, 가상 머신에서 직접 만듭니다.

1. 문서 편집기로 PDF 를 하나 내보냅니다. `%%EOF` 가 몇 개인가요? 덧붙은 부분에 다시 정의된 객체가 있나요?
2. 사본의 작성자를 pypdf 증분 쓰기나 ExifTool 로 바꿉니다. 덧붙은 부분에 무엇이 생겼나요?
3. 위 코드로 잘라 낸 사본을 만듭니다. 원본 길이에서 자른 사본의 해시가 원본 해시와 같나요?
4. 고친 파일을 qpdf 같은 도구로 다시 씁니다. 옛 `Author` 값이 파일에 남아 있나요?
5. 공개 데이터셋의 PDF 에서 `%%EOF` 가 둘 넘는 파일을 찾습니다. 덧붙은 부분마다 무엇이 바뀌었는지 표로 적습니다.
6. 결과로 보고서 문장을 하나 씁니다. "조작했다" 가 아니라 어느 객체가 어떻게 다시 정의됐는지를 씁니다.
