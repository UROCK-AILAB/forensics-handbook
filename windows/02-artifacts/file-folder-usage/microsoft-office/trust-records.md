# 신뢰 문서 기록 (Trust Records)

> 상위 페이지: [오피스 사용 흔적 (Microsoft Office)](index.md)

## 한 줄 요약

오피스 문서를 열고 경고 단추를 누르면 그 문서 경로가 레지스트리 `TrustRecords` 키에 값 이름으로 남습니다. 제한된 보기에서 [편집 사용] 만 눌러도 값이 생깁니다. 매크로를 켰는지는 값 데이터의 마지막 4바이트로 가릅니다.

> 이 페이지에서 "(관찰)" 을 붙인 내용은 PC 한 대에서 직접 본 것입니다. 확인 범위: Windows 11 Home 10.0.26200, Microsoft 365 앱 16.0.20326.20158 (클릭 투 런). 다른 버전과 설정에서는 다를 수 있습니다.

## 무엇을 기록하나 · 왜 생기나

Microsoft 는 신뢰 문서 (Trusted Document) 를 이렇게 설명합니다.

신뢰 문서는 사용자가 활성 콘텐츠를 켜서 신뢰한다고 표시한 파일이고, 메시지 표시줄의 [콘텐츠 사용] (Enable Content) 단추를 누르면 신뢰 문서가 됩니다. 신뢰 문서를 다시 열면 메시지 표시줄이 뜨지 않지만 파일을 옮기면 다시 경고가 뜹니다. 임시 인터넷 파일 폴더나 Temp 폴더처럼 안전하지 않은 위치에서 연 파일은 신뢰 문서로 만들 수 없고, 파일 > 옵션 > 보안 센터 > 보안 센터 설정 > 신뢰할 수 있는 문서 에서 신뢰 문서를 모두 지울 수 있습니다. 대상 앱은 Excel, Word, PowerPoint, Access, Visio 입니다 (2016~2024, Microsoft 365).

이 공식 문서에는 레지스트리 저장 위치가 나오지 않습니다. 저장 위치와 값의 뜻은 공개 연구 자료에서 가져왔습니다.

az4n6 블로그는 Word 로 이 기록을 시험했습니다. 결과는 아래와 같습니다.

제한된 보기 (Protected View) 에서 [편집 사용] (Enable Editing) 만 눌러도 매크로를 켜지 않은 채로 TrustRecords 에 값이 생겼고, 매크로를 켜면 값 데이터의 마지막 4바이트가 `FF FF FF 7F` 로 바뀌었습니다. 보안 센터에서 매크로 알림을 끈 상태면 악성 문서를 실행해도 값이 남지 않았으며, 문서를 지운 뒤에도 값이 남을 수 있습니다.

## 위치와 버전별 차이

```
HKCU\Software\Microsoft\Office\<버전>\<앱>\Security\Trusted Documents\TrustRecords
```

사용자마다 NTUSER.DAT 에 있습니다. RegRipper 는 Word, PowerPoint, Excel, Access 네 앱에서 이 키를 읽습니다. 버전 키가 어느 오피스 제품을 뜻하는지는 [허브 페이지](index.md) 에서 다룹니다.

| 버전 키 | 확인 범위 | 근거 |
|---|---|---|
| 14.0 (Word 2010) | 시험했습니다. | az4n6 |
| 15.0 (Word 2013) | 시험했습니다. | az4n6 |
| 16.0 | 글의 댓글에 같다는 말이 있습니다. 글쓴이가 직접 시험하지는 않았습니다. 관찰한 PC 에서는 Word·Excel·PowerPoint 에 값이 있었습니다. | az4n6 댓글, 관찰 |

az4n6 는 Excel·Access·PowerPoint 를 직접 시험하지 않았다고 적었습니다.

**부모 키의 `LastPurgeTime`.** 관찰한 PC 의 `Trusted Documents` 키 (TrustRecords 의 부모) 에는 `LastPurgeTime` (REG_DWORD) 값이 있었습니다. 값은 29812368 같은 수였습니다. 1970-01-01 부터 센 분으로 풀면 2026-09 가 나왔습니다. (관찰) 이 값의 뜻과 단위는 공식 설명을 확인하지 못했습니다.

## 구조

**값 이름.** 문서 경로입니다. 관찰한 PC 의 값 이름은 `%USERPROFILE%\…` 로 시작하는 로컬 경로이거나 `https://` 로 시작하는 주소였습니다. Word 15개, Excel 10개, PowerPoint 7개가 있었습니다. (관찰)

**값 데이터.** REG_BINARY 입니다. 공개 자료가 뜻을 밝힌 칸은 두 곳입니다.

| 위치 | 뜻 | 근거 |
|---|---|---|
| 처음 8바이트 | FILETIME 입니다. 매크로를 켠 시각이 아니라 문서를 만든 시각입니다. | RegRipper, az4n6 |
| 마지막 4바이트 | 매크로를 켜면 `FF FF FF 7F` (0x7FFFFFFF = 2,147,483,647) 로 바뀝니다. RegRipper 는 이 값이면 "Enable Content button clicked" 라고 표시합니다. | az4n6, RegRipper |

관찰한 PC 의 값 32개는 모두 길이가 24바이트였습니다. 아래 배치는 관찰로 짐작한 것입니다. 공식 명세는 확인하지 못했습니다. (관찰)

| 오프셋 | 크기 | 관찰한 내용 |
|---|---|---|
| 0 | 8 | FILETIME (UTC). 로컬 파일 4건은 파일 생성 시각과 초 단위까지 같았습니다. https 주소 기록은 모두 0 이었습니다. 로컬 기록에도 0 인 것이 있었습니다. |
| 8 | 8 | 64비트 정수. 32개 모두 0x0000004B6FE7A800 (324,000,000,000) 이었습니다. 100나노초 단위로 9시간입니다. 이 PC 의 시간대 UTC+9 와 같습니다. |
| 16 | 4 | 32비트 정수. 1970-01-01 UTC 부터 센 분으로 풀면 파일 생성 시각과 같거나 늦은 시각이 나왔습니다. 신뢰를 준 시각일 가능성이 있습니다. |
| 20 | 4 | 32개 모두 `01 00 00 00` 이었습니다. 매크로를 켠 기록 (`FF FF FF 7F`) 은 없었습니다. |

오프셋 8~19 의 뜻을 설명한 자료는 찾지 못했습니다.

**함께 보는 값.** 같은 `Security` 키의 `VBAWarnings` (REG_DWORD) 는 매크로 설정입니다.

| 값 | 뜻 |
|---|---|
| 1 | 모든 매크로 사용 |
| 2 | 알림과 함께 모두 끔 |
| 3 | 디지털 서명이 있는 매크로만 허용 |
| 4 | 알림 없이 모두 끔 |

사용자가 기본 설정을 바꾸지 않았으면 `VBAWarnings` 값이 없습니다. RegRipper 는 같은 키의 `blockcontentexecutionfrominternet`, `AccessVBOM`, `PackagerPrompt` 와 앱 `Options` 키의 `DontUpdateLinks` 도 보여 줍니다. `PackagerPrompt` 가 2 면 OLE 를 끈 상태입니다.

## 증거로서 의미

**증명하는 것**

- 그 사용자 프로필의 그 앱이 그 경로의 문서에 신뢰 기록을 남긴 적이 있습니다.
- 값이 생기는 동작으로 알려진 것은 [콘텐츠 사용] 과 제한된 보기의 [편집 사용] 입니다.
- 마지막 4바이트가 `FF FF FF 7F` 면 그 문서에서 매크로를 켠 기록입니다.
- 문서를 지운 뒤에도 값이 남을 수 있습니다. 그래서 지금 디스크에 없는 문서의 경로를 알려 줄 수 있습니다.

**증명하지 못하는 것**

- 값이 있다는 것만으로 매크로를 켰다는 것. [편집 사용] 만 눌러도 값이 생깁니다.
- 값이 없다는 것만으로 매크로를 켜지 않았다는 것. 매크로 알림을 끈 상태면 값이 남지 않습니다.
- 신뢰를 준 때. 처음 8바이트는 문서를 만든 시각입니다.
- 문서가 악성인지, 매크로가 무엇을 했는지.
- 단추를 누른 사람이 누구인지.

보고서 문장은 기록이 말하는 만큼만 씁니다.

- 쓰지 않을 문장: "사용자가 2024-03-11 05:05 UTC 에 invoice.docm 의 매크로를 실행했다."
- 쓸 문장: "사용자 kim 의 NTUSER.DAT, Word 의 TrustRecords 키에 `%USERPROFILE%\Downloads\invoice.docm` 값이 있다. 값 데이터의 마지막 4바이트는 FF FF FF 7F 이다. 공개 연구(az4n6)는 이 값을 문서에서 매크로를 켠 기록으로 본다. 처음 8바이트의 시각 2024-03-11 05:05:40 UTC 는 같은 연구에서 문서를 만든 시각으로 보는 값이며, 매크로를 켠 시각이 아니다." (예시 문장이며 숫자는 아래 헥스 예시와 같습니다.)

## 시각 해석

| 시각 | 형식 | 뜻 |
|---|---|---|
| 값 데이터 처음 8바이트 | FILETIME, UTC | 문서를 만든 시각입니다 (az4n6). 관찰에서 로컬 파일은 파일 생성 시각과 초까지 같았고, https 기록은 0 이었습니다. |
| 오프셋 16 의 4바이트 (관찰) | 1970-01-01 UTC 부터 센 분 | 신뢰를 준 시각일 가능성이 있습니다. 확인하지 못한 해석입니다. 분 단위라 초가 없습니다. |
| 부모 키의 `LastPurgeTime` (관찰) | 분 단위로 보입니다 | 뜻을 확인하지 못했습니다. |

- 처음 8바이트를 "매크로를 켠 시각" 으로 적으면 틀립니다. FILETIME 푸는 법은 [시각 값 형식](../../../01-foundations/value-decoding/filetime-unix-webkit-dos-ole.md) 에 있습니다.
- 오프셋 8 의 값이 시간대 차이라면, 기록을 남길 때의 시간대를 짐작하는 단서가 됩니다. 이 해석도 한 PC 관찰에서 나왔습니다. [시간대 설정](../../system-account/time-zone.md) 과 맞춰 봅니다.

## 함정과 한계

- **[편집 사용] 만으로 값이 생깁니다.** 값이 있다고 "매크로를 실행했다" 로 쓰지 않습니다.
- **알림을 끈 환경에서는 남지 않습니다.** 먼저 `VBAWarnings` 를 확인합니다. 값이 없으면 기본 설정입니다.
- **경로 기준 기록입니다.** 값 이름이 문서 경로입니다. 파일을 옮기면 다시 경고가 뜹니다. 같은 문서라도 경로가 다르면 따로 봅니다.
- **사용자가 모두 지울 수 있습니다.** 보안 센터에서 신뢰 문서를 모두 지울 수 있습니다. 지운 뒤 레지스트리에 무엇이 남는지는 확인하지 못했습니다. 부모 키의 `LastPurgeTime` 이 이 동작과 관련 있는지도 확인하지 못했습니다. 지운 값은 하이브 안의 빈 공간 ([레지스트리 하이브 구조](../../../01-foundations/database-log-formats/registry-hive/index.md)) 과 섀도 복사본 속 옛 NTUSER.DAT ([섀도 복사본 활용](../../../03-techniques/analysis/volume-shadow-copy-analysis.md)) 에서 찾아봅니다.
- **시험 범위가 좁습니다.** az4n6 는 Word 2010·2013 만 시험했습니다. 다른 앱과 16.0 은 검체와 같은 환경에서 따로 시험합니다.
- **24바이트 배치는 관찰입니다.** 오프셋 8~19 는 공식 명세가 없습니다.
- **처음 8바이트가 0 인 기록이 있습니다.** https 기록과 일부 로컬 기록이 0 이었습니다. (관찰) 0 을 1601-01-01 로 풀어 적지 않습니다.

## 직접 분석해 보기

### 헥스로 한 번

아래 바이트는 RegRipper·az4n6 가 밝힌 칸과 관찰한 24바이트 배치로 만든 예시입니다. 실제 검체에서 나온 값이 아닙니다.

값 이름 (예시): `%USERPROFILE%\Downloads\invoice.docm`

```
오프셋    00 01 02 03 04 05 06 07  08 09 0A 0B 0C 0D 0E 0F
00000000  00 2A F2 C2 71 73 DA 01  00 A8 E7 6F 4B 00 00 00   .*..qs.....oK...
00000010  D8 E8 B2 01 FF FF FF 7F                            ........
```

| 오프셋 | 바이트 | 뜻 |
|---|---|---|
| 0x00 | `00 2A F2 C2 71 73 DA 01` | 리틀 엔디언으로 0x01DA7371C2F22A00 입니다. 풀면 2024-03-11 05:05:40 UTC 입니다. 문서를 만든 시각입니다. |
| 0x08 | `00 A8 E7 6F 4B 00 00 00` | 0x4B6FE7A800 = 324,000,000,000 입니다. 100나노초 단위로 9시간입니다. (관찰 배치) |
| 0x10 | `D8 E8 B2 01` | 0x01B2E8D8 = 28,502,232 분입니다. 1970-01-01 UTC 에 더하면 2024-03-11 05:12 UTC 입니다. (관찰 배치) |
| 0x14 | `FF FF FF 7F` | 0x7FFFFFFF 입니다. 매크로를 켠 기록입니다. |

매크로를 켜지 않은 기록이면 둘째 줄이 `D8 E8 B2 01 01 00 00 00` 입니다. 관찰한 PC 의 값 32개가 모두 이 모양이었습니다. (관찰)

### 공개 도구로 한 번

RegRipper 의 msoffice 플러그인은 Word·PowerPoint·Excel·Access 의 TrustRecords 를 읽습니다. 처음 8바이트를 시각으로 풀고, 마지막 4바이트가 0x7FFFFFFF 면 "Enable Content button clicked" 를 붙입니다. 같은 플러그인이 `VBAWarnings` 같은 보안 설정도 보여 줍니다.

1. NTUSER.DAT 과 트랜잭션 로그 (.LOG1·.LOG2) 를 함께 뽑습니다.
2. msoffice 플러그인을 돌려 앱마다 값 목록을 봅니다.
3. 값 몇 개를 레지스트리 뷰어에서 헥스로 열어 길이와 마지막 4바이트를 직접 확인합니다.
4. 같은 `Security` 키의 `VBAWarnings` 를 확인합니다.
5. 도구 결과와 헥스 결과가 다르면 [도구 결과 교차 검증](../../../03-techniques/reporting/tool-validation.md) 을 따릅니다.

## 실습

NIST CFReDS 같은 공개 검체 가운데 오피스를 쓴 사용자 프로필이 있는 이미지를 고릅니다. 오피스를 설치한 가상 머신을 직접 만들어도 됩니다.

1. 앱마다 TrustRecords 값 수와 `VBAWarnings` 값을 적습니다.
2. 마지막 4바이트가 `FF FF FF 7F` 인 값이 있나요?
3. 값 이름의 경로가 지금 디스크에 있는지 봅니다. 없는 문서는 $MFT 와 휴지통에서 찾습니다.
4. 처음 8바이트 시각과 파일 생성 시각을 견줍니다. 같은가요?
5. 가상 머신에서 제한된 보기로 열리는 매크로 문서를 엽니다. [편집 사용] 만 누르고 값이 생기는지, 마지막 4바이트가 무엇인지 봅니다. 이어서 [콘텐츠 사용] 을 누르고 다시 봅니다.
6. 결과로 보고서 문장을 하나 씁니다. "매크로를 실행했다" 가 아니라 기록이 말하는 만큼만 씁니다.
