# 셸백 시각 해석 (처음 연 때·마지막 바뀐 때)

## 한 줄 요약

셸백 (ShellBags) 에서 읽을 수 있는 시각은 크게 두 종류입니다. 하나는 BagMRU 키마다 붙은 마지막 기록 시각입니다. 다른 하나는 값 안의 셸 아이템에 적힌 폴더 자신의 시각입니다. 어느 쪽도 폴더를 연 때를 모두 남기지는 않습니다. "처음 연 때" 와 "마지막으로 연 때" 는 키에 하위 폴더 항목이 있는지, 그 폴더가 MRUListEx 에서 몇 번째인지를 보고 좁혀서 추정합니다.

## 셸백에 남는 시각

| 시각 | 들어 있는 곳 | 형식·단위 | 기준 | 뜻 |
|---|---|---|---|---|
| BagMRU 키의 마지막 기록 시각 (Last Write Time) | BagMRU 키와 그 아래 번호 키마다 하나 | FILETIME, 100나노초 | UTC | 그 키의 값(번호 값·MRUListEx·NodeSlot 등)이 마지막으로 바뀐 때 |
| 셸 아이템의 수정 시각 | 번호 값 안의 파일 항목 셸 아이템 (File Entry Shell Item) | FAT 날짜·시각, 2초 단위 | 명세상 UTC | 항목을 기록할 때 그 폴더의 마지막 수정 시각 |
| 셸 아이템의 생성·접근 시각 | 같은 셸 아이템 안의 확장 블록 (Extension Block) 0xBEEF0004 | FAT 날짜·시각, 2초 단위 | 명세상 UTC | 항목을 기록할 때 그 폴더의 생성 시각과 마지막 접근 시각 |
| Bags 키의 마지막 기록 시각 | `Bags\<번호>` 아래 키 | FILETIME, 100나노초 | UTC | 그 폴더의 보기 설정 값이 마지막으로 바뀐 때 |

- 키 시각은 레지스트리가 적습니다. 셸 아이템 시각은 파일 시스템에서 가져온 값입니다. 출처가 다르므로 뜻도 다릅니다.
- 키 시각이 무엇에 바뀌는지는 [키 마지막 기록 시각](../../../01-foundations/database-log-formats/registry-hive/last-write-time.md) 에서 다룹니다. 이 페이지는 그 규칙이 셸백에서 무엇을 뜻하는지만 다룹니다.
- BagMRU·Bags 키의 위치와 연결 방식은 [저장 위치와 구조](ntuser-usrclass-bagmru-bags.md) 를 봅니다.
- 셸 아이템의 전체 구조는 [셸 아이템 (Shell Item·PIDL)](../../../01-foundations/shell-document-formats/shell-item-pidl.md) 을 봅니다.

여러 도구가 이 시각들을 조합해 "처음 연 때 (First Interacted)" 와 "마지막으로 연 때 (Last Interacted)" 같은 열을 만듭니다. 이 열은 레지스트리에 그대로 적힌 값이 아니라 도구가 규칙으로 계산한 값이며, 열 이름과 계산 규칙은 도구마다 다릅니다. 아래 "시각 해석" 절에서 그 규칙을 따라가 봅니다.

## 위치와 버전별 차이

셸백 키를 두는 하이브는 버전마다 다릅니다. Windows XP 는 NTUSER.DAT 에 두고, Vista 부터는 UsrClass.dat 에도 둡니다. 정확한 경로는 [저장 위치와 구조](ntuser-usrclass-bagmru-bags.md) 에 있습니다.

시각과 관련해 버전마다 달라지는 것은 확장 블록 0xBEEF0004 의 버전입니다. 아래 표는 libfwsi 명세를 따릅니다.

| 확장 블록 버전 | Windows | 생성·접근 시각 | NTFS 파일 참조 (MFT 번호·순번) |
|---|---|---|---|
| 3 | XP·2003 | 있음 | 없음 |
| 7 | Vista (SP0) | 있음 | 있음 |
| 8 | Server 2008·7·8.0 | 있음 | 있음 |
| 9 | 8.1·10 | 있음 | 있음 |

셸 아이템의 수정 시각 칸은 XP 이전 형식에도 있고, 명세는 Windows 11 을 따로 적지 않았습니다. Windows 8.1 부터 하이브 변경은 트랜잭션 로그에 먼저 쓰입니다. 그래서 가장 새 키 시각이 UsrClass.dat 의 .LOG1·.LOG2 에만 있을 수 있습니다. 반영 방법은 [트랜잭션 로그와 반영 안 된 변경](../../../01-foundations/database-log-formats/registry-hive/log1-log2.md) 을 봅니다.

## 구조 — 시각이 든 칸

BagMRU 의 번호 값에는 셸 아이템이 하나 들어 있습니다. 파일 시스템의 폴더는 파일 항목 셸 아이템으로 적힙니다. 내 PC·드라이브·네트워크 같은 항목은 셸 아이템 종류가 달라서 아래 시각 칸이 없거나 구조가 다릅니다. 외부 장치·네트워크·압축 폴더는 [외부 장치·네트워크·압축 폴더 탐색 흔적](removable-network-zip.md) 에서 다룹니다.

| 위치 | 오프셋 | 크기 | 칸 | 뜻 |
|---|---|---|---|---|
| 파일 항목 셸 아이템 | 0 | 2 | 크기 | 셸 아이템 전체 바이트 수 |
| 파일 항목 셸 아이템 | 2 | 1 | 종류 표시 (Class Type Indicator) | 0x70 으로 거른 값이 0x30 이면 파일 항목입니다. 0x01 이 켜져 있으면 폴더입니다 |
| 파일 항목 셸 아이템 | 8 | 4 | 마지막 수정 시각 | FAT 날짜·시각 |
| 확장 블록 0xBEEF0004 | 2 | 2 | 확장 블록 버전 | 위 버전 표 |
| 확장 블록 0xBEEF0004 | 4 | 4 | 서명 | 0xBEEF0004 |
| 확장 블록 0xBEEF0004 | 8 | 4 | 생성 시각 | FAT 날짜·시각 |
| 확장 블록 0xBEEF0004 | 12 | 4 | 마지막 접근 시각 | FAT 날짜·시각 |
| 확장 블록 0xBEEF0004 (버전 7 이상) | 20 | 8 | NTFS 파일 참조 | MFT 번호 6바이트 + 순번 2바이트 |

셸 아이템 칸의 오프셋은 셸 아이템 첫 바이트를 0 으로 센 값입니다. 확장 블록 칸의 오프셋은 확장 블록 첫 바이트를 0 으로 센 값입니다.

FAT 날짜·시각 (FAT Date and Time) 4바이트는 앞 2바이트가 날짜, 뒤 2바이트가 시각입니다. 둘 다 리틀 엔디언입니다.

| 칸 | 비트 | 뜻 |
|---|---|---|
| 날짜 | 0–4 | 일 (1–31) |
| 날짜 | 5–8 | 월 (1 = 1월) |
| 날짜 | 9–15 | 1980년부터 센 해 |
| 시각 | 0–4 | 초를 2로 나눈 값 |
| 시각 | 5–10 | 분 (0–59) |
| 시각 | 11–15 | 시 (0–23) |

초를 2로 나눠 적으므로 홀수 초는 남지 않습니다. 명세는 이 시각 값이 늘 채워지지는 않는다고 적었습니다. 값이 0 이면 날짜가 성립하지 않으므로 비어 있는 칸으로 봅니다. FAT 날짜·시각과 다른 시각 형식의 변환은 [시각 값 형식](../../../01-foundations/value-decoding/filetime-unix-webkit-dos-ole.md) 에서 다룹니다.

## 증거로서 의미

| 증명하는 것 | 증명하지 못하는 것 |
|---|---|
| 이 사용자 하이브에 그 폴더 항목이 기록된 적이 있습니다 | 폴더를 연 횟수. 연 때 전부 |
| 부모 키 시각에 MRUListEx 맨 앞 자식이 목록에 새로 들어오거나 맨 앞으로 올라왔습니다 | 맨 앞이 아닌 형제 폴더를 마지막으로 연 때 |
| MRUListEx 순서는 형제 폴더 가운데 어느 쪽이 더 나중에 맨 앞에 올랐는지 알려 줍니다 | 맨 앞 폴더를 그 뒤에 다시 열었는지 |
| 하위 폴더 항목이 없는 키의 시각은 그 키를 처음 만든 때일 가능성이 큽니다 (확인 범위: Windows 7) | 하위 폴더 항목이 생긴 키를 처음 만든 때 |
| 셸 아이템 시각은 항목을 기록할 때 그 폴더의 생성·수정·접근 시각입니다 | 셸 아이템 시각이 폴더를 연 때라는 것 |
| | 폴더 안의 파일을 열었는지. 폴더가 지금도 있는지 |
| | 사람이 직접 탐색기로 열었는지. 셸백이 생기는 조건은 [셸백 해석 함정](pitfalls.md) 을 봅니다 |

보고서에는 기록이 말하는 만큼만 씁니다. 아래 시각과 이름은 설명을 위한 예입니다.

- 쓸 수 있는 문장: "UsrClass.dat 의 BagMRU 아래 `Projects` 폴더 키는 2024-03-15 06:31:10 UTC 에 마지막으로 바뀌었습니다. 이 키의 MRUListEx 맨 앞 항목은 `Budget` 폴더입니다."
- 쓰면 안 되는 문장: "사용자는 2024-03-15 06:31:10 UTC 에 `Projects` 안의 모든 폴더를 열었습니다."
- 쓰면 안 되는 문장: "사용자는 `Report` 폴더를 2024-03-15 06:30:02 UTC 에 열었습니다." (셸 아이템의 수정 시각을 연 시각으로 읽은 경우)

## 시각 해석

### 키 시각이 바뀌는 때 (마지막 바뀐 때)

BagMRU 키 하나는 폴더 하나에 해당합니다. 그 키 안의 번호 값과 MRUListEx 는 그 폴더의 하위 폴더를 가리킵니다. 그래서 어떤 폴더를 열면 대개 그 폴더의 **부모** 폴더 키가 바뀝니다. 아래 표는 4n6k 의 실험(Windows 7)과 키 마지막 기록 시각의 일반 규칙을 따릅니다.

| 동작 | 바뀌는 키 시각 | 바뀌지 않는 키 시각 |
|---|---|---|
| 처음 보는 폴더를 열어 새 항목이 생김 | 부모 폴더 키(번호 값·MRUListEx 추가, 하위 키 생성). 새 키에는 만든 시각이 붙습니다 | 형제 폴더 키 |
| 처음 보는 폴더를 열어 새 항목이 생김 | 루트 BagMRU 키. 여기 있는 NodeSlots 값이 새 항목이 생길 때마다 바뀝니다 (확인 범위: Windows 7) | — |
| 기록된 형제 폴더를 다시 열어 맨 앞으로 올라감 | 부모 폴더 키 (MRUListEx 순서가 바뀜) | 연 폴더 자신의 키 |
| 이미 MRUListEx 맨 앞인 폴더를 다시 엶 | 없음. MRUListEx 를 다시 쓸 이유가 없습니다 (확인 범위: Windows 7. 4n6k 는 하위 폴더가 하나뿐인 경우로 시험했습니다) | 부모 폴더 키 |
| 셸백 키를 지움 (정리 도구 등) | 지운 키의 부모 키 | — |

키 안의 값이 하나라도 바뀌면 키 시각이 바뀌고, NodeSlot 같은 다른 값도 마찬가지입니다. 루트 키 시각은 마지막으로 새 폴더 항목이 생긴 때보다 앞설 수 없지만, 루트 키에는 다른 값도 있으므로 루트 키 시각이 곧 그때라고 단정하지는 않습니다.

- 루트 키 시각을 바로 아래 항목(내 PC 등)의 "마지막으로 연 때" 로 붙이면 안 됩니다. 어디서든 새 폴더 항목이 생기면 루트 키 시각이 바뀌므로, 바로 아래 항목이 방금 열린 것처럼 보입니다.
- 지운 셸백 항목을 찾는 방법은 [지운 폴더 흔적 찾기](deleted-folders.md) 를 봅니다.

> 그림 자리: BagMRU 트리에서 부모 키 하나와 자식 키 셋을 그립니다. 부모 키의 MRUListEx 맨 앞 칸에서 자식 하나로 화살표를 긋고, 부모 키 시각이 그 자식에게만 붙는다는 것을 보여 줍니다. 자식이 없는 키에는 "처음 만든 시각 그대로" 라고 표시합니다.

### 마지막으로 연 때: MRUListEx 맨 앞 자식에만 붙는다

부모 키 시각은 그 키가 마지막으로 바뀐 때입니다. 그 변경은 대개 MRUListEx 맨 앞 자식이 목록에 들어오거나 맨 앞으로 올라온 일입니다. 그래서 부모 키 시각은 **맨 앞 자식 하나에만** 붙일 수 있습니다.

맨 앞 자식의 "마지막으로 연 때" 는 정확히는 "맨 앞으로 마지막으로 올라온 때" 입니다. 이미 맨 앞인 폴더를 다시 열면 키가 바뀌지 않기 때문에 실제 마지막 방문은 그보다 뒤일 수 있습니다. 맨 앞이 아닌 자식이 맨 앞에 마지막으로 있던 때는 부모 키 시각보다 앞서지만 정확한 때는 알 수 없고, MRUListEx 순서로는 형제 폴더끼리 앞뒤만 알 수 있어서 앞에 있는 폴더가 더 나중에 맨 앞에 올랐습니다.

4n6k 는 2013년에 당시 공개 도구 두 개가 부모 키 시각을 모든 자식에게 똑같이 붙인다고 보고했습니다. 하위 폴더가 수백 개인 폴더라면 수백 개가 모두 같은 "마지막으로 연 때" 를 받게 됩니다.

MRUListEx 를 읽는 법은 [MRU 목록 읽는 법](../../../01-foundations/database-log-formats/registry-hive/mrulist-mrulistex.md) 에 있습니다.

### 처음 연 때: 하위 폴더 항목이 없는 키에서만 남는다

하위 폴더 항목이 없는 키에는 번호 값이 없습니다. MRUListEx 도 끝 표시 `FF FF FF FF` 만 있습니다. 4n6k 의 Windows 7 실험에서 이런 키는 만든 뒤로 바뀌지 않았습니다. 그래서 이 키의 시각은 그 폴더가 처음 기록된 때로 볼 수 있습니다.

그 폴더 아래에 하위 폴더 항목이 하나라도 생기면 키 시각이 옮겨 가고, 이때 처음 기록된 때는 키에서 사라집니다. 이 규칙은 관찰에 기댄 추정이므로 다른 Windows 버전에서 쓸 때는 같은 버전의 시험 시스템에서 먼저 확인합니다.

- 처음 기록된 때가 사라진 폴더는 다른 곳에서 범위를 좁힙니다. 섀도 복사본 안의 옛 UsrClass.dat 에서 그 항목이 처음 보이는 사본을 찾으면, 처음 기록된 때가 두 사본 사이로 좁혀집니다([섀도 복사본 활용](../../../03-techniques/analysis/volume-shadow-copy-analysis.md)).
- 셸 아이템의 시각들은 항목을 기록할 때 이미 있던 값입니다. 그래서 항목을 처음 기록한 때는 셸 아이템의 생성 시각보다 앞설 수 없습니다. 시계를 바꾸지 않았고 시각을 조작하지 않았다는 전제가 필요합니다.

### 가상 예로 한 번 읽기

아래는 규칙을 보여 주려고 만든 가상 예입니다. 경로는 줄였습니다.

```
키 (폴더)                 MRUListEx      번호 값   키 시각
…\BagMRU\…\0 (Projects)   1, 0           0, 1      T3
…\BagMRU\…\0\0 (Report)   FF FF FF FF    없음      T1
…\BagMRU\…\0\1 (Budget)   FF FF FF FF    없음      T2
```

1. `Projects` 키의 MRUListEx 는 1 이 맨 앞입니다. 값 1 은 `Budget` 입니다.
2. 그래서 T3 은 `Budget` 이 `Projects` 목록의 맨 앞에 마지막으로 올라온 때입니다.
3. `Report` 가 맨 앞에 마지막으로 있던 때는 T3 보다 앞섭니다. 정확한 때는 알 수 없습니다.
4. `Report` 와 `Budget` 은 하위 폴더 항목이 없습니다. 그래서 T1 과 T2 는 각각 처음 기록된 때로 볼 수 있습니다.
5. T2 와 T3 이 거의 같다면, `Budget` 을 처음 기록한 뒤로 `Projects` 키에 다른 변경이 없었다는 뜻입니다. 그 뒤에 `Budget` 을 다시 열었는지는 알 수 없습니다.
6. `Projects` 자신이 처음 기록된 때는 이 키에서 알 수 없습니다. `Projects` 는 하위 폴더 항목이 있기 때문입니다. `Projects` 가 부모 키의 맨 앞 자식이면, 부모 키 시각이 `Projects` 가 맨 앞에 마지막으로 올라온 때입니다.

### 셸 아이템 시각: 폴더의 시각이지 연 때가 아니다

셸 아이템 속 생성·수정·접근 시각은 항목을 기록할 때 파일 시스템이 알려 준 그 폴더의 시각을 옮겨 적은 값입니다. 4n6k 의 Windows 7 실험에서 이 시각은 항목을 만든 뒤 폴더를 다시 열어도 바뀌지 않았습니다.

- NTFS 에서 Windows 파일 API 가 돌려주는 시각은 $STANDARD_INFORMATION 쪽 시각입니다([두 벌의 시각](../../../01-foundations/disk-volume/ntfs/standard-information-file-name.md)).
- 폴더의 수정 시각은 폴더 안에 파일을 만들거나 지우거나 이름을 바꿀 때 바뀝니다. 그래서 셸 아이템의 수정 시각은 폴더 안 내용이 마지막으로 바뀐 때에 가깝습니다. 파일 시각의 변화 규칙은 [파일 시각 네 가지와 변화 규칙](../../../03-techniques/analysis/timeline/macb-timestamp-rules.md) 을 봅니다.
- 접근 시각은 파일 시스템 설정에 따라 늦게 갱신되거나 갱신되지 않습니다. Microsoft 문서는 NTFS 가 마지막 접근 시각 갱신을 최대 1시간까지 늦춘다고 적었습니다.
- FAT 볼륨은 접근 시각을 날짜로만 남깁니다. 그래서 FAT 볼륨 폴더의 셸 아이템 접근 시각은 날짜만 뜻이 있습니다. 4n6k 의 Windows 7 실험에서는 시·분 자리에 그 PC 의 시간대만큼 밀린 값이 보였습니다.
- 이 값은 기록 당시의 사본입니다. 그래서 지금 폴더 시각과 비교하면 기록 뒤에 폴더 시각이 바뀌었는지 볼 수 있습니다. 방법은 아래 "교차 검증" 절에 있습니다.

### UTC 와 현지 시각

- 키 시각은 FILETIME 이고 UTC 입니다.
- libfwsi 명세는 셸 아이템의 FAT 날짜·시각을 UTC 로 적었습니다. FAT 형식 자체에는 시간대 정보가 없습니다.
- FAT 볼륨은 디스크에 현지 시각을 적습니다. Microsoft 문서에 따르면 이 값을 UTC 로 바꿀 때 지금의 시간대·일광 절약 시간 설정을 씁니다. 그래서 FAT 볼륨 폴더의 시각은 한 시간 어긋날 수 있습니다.
- 현지 시각으로 바꿀 때는 그 PC 의 시간대 설정을 씁니다([시간대 설정](../../system-account/time-zone.md), [시간대·시계 오차 보정](../../../03-techniques/analysis/timeline/time-normalization.md)).
- 키 시각과 셸 아이템 시각을 비교할 때는 셸 아이템 쪽의 2초 단위를 감안합니다.

## 함정과 한계

셸백 전반의 함정은 [셸백 해석 함정](pitfalls.md) 에서 다룹니다. 아래는 시각에 관한 것만 모았습니다.

1. **부모 키 시각을 모든 자식에게 붙입니다.** 부모 키 시각은 MRUListEx 맨 앞 자식 하나에만 붙습니다.
2. **맨 앞 자식의 시각을 마지막 방문으로 단정합니다.** 이미 맨 앞인 폴더는 다시 열어도 키가 바뀌지 않습니다.
3. **셸 아이템 시각을 연 때로 읽습니다.** 셸 아이템 시각은 폴더 자신의 생성·수정·접근 시각입니다.
4. **하위 폴더 항목이 생긴 키의 시각을 처음 연 때로 읽습니다.** 처음 연 때는 하위 폴더 항목이 없는 키에서만 남습니다.
5. **트랜잭션 로그를 반영하지 않습니다.** Windows 8.1 부터 가장 새 키 시각이 로그에만 있을 수 있습니다.
6. **UTC 와 현지 시각을 섞습니다.** 도구가 분석 PC 의 시간대로 바꿔 보여 주는지 확인합니다. FAT 볼륨 폴더는 한 시간 차이도 생길 수 있습니다.
7. **셸 아이템 시각의 0 을 날짜로 바꿉니다.** 값이 비어 있는 칸입니다.
8. **키 시각을 조작하지 않았다고 가정합니다.** 키 시각은 API 로 바꿀 수 있습니다([키 마지막 기록 시각](../../../01-foundations/database-log-formats/registry-hive/last-write-time.md) 의 "조작과 흔적"). 셸백 정리 도구가 하위 키를 지우면 부모 키 시각이 지운 때로 바뀝니다.
9. **분석 중에 원본을 바꿉니다.** 분석 PC 에서 하이브를 불러와 열면 키 시각이나 파일이 바뀔 수 있습니다. 항상 사본에서 작업합니다.

## 직접 분석해 보기

### 헥스로 한 번

아래는 libfwsi 명세를 보고 만든 예시입니다. 실제 검체에서 뽑은 값이 아닙니다. Windows 8.1·10 형식(확장 블록 버전 9)으로, 이름이 `Report` 인 폴더를 적은 BagMRU 번호 값의 앞부분입니다.

```
셸 아이템 시작 기준
오프셋  00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F
00      54 00 31 00 00 00 00 00 6F 58 C1 33 10 00 52 45
10      50 4F 52 54 00 00 3E 00 09 00 04 00 EF BE 6F 58
20      87 33 6F 58 C1 33 2E 00 …
```

1. `54 00` 은 셸 아이템 크기입니다. 0x54 는 84바이트입니다.
2. `31` 은 종류 표시입니다. 0x70 으로 거르면 0x30 이므로 파일 항목입니다. 0x01 이 켜져 있으므로 폴더입니다.
3. 오프셋 0x08 의 `6F 58 C1 33` 이 마지막 수정 시각입니다. 앞 2바이트는 날짜 0x586F 이고 뒤 2바이트는 시각 0x33C1 입니다.
4. 날짜 0x586F 의 9–15비트는 44 입니다. 1980 에 더하면 2024년입니다. 5–8비트는 3 이므로 3월입니다. 0–4비트는 15 이므로 15일입니다.
5. 시각 0x33C1 의 11–15비트는 6 이므로 6시입니다. 5–10비트는 30 이므로 30분입니다. 0–4비트는 1 이므로 2초입니다.
6. 따라서 수정 시각은 2024-03-15 06:30:02 UTC 입니다.
7. 오프셋 0x0C 의 `10 00` 은 파일 속성 0x0010 입니다. 디렉터리라는 뜻입니다.
8. 오프셋 0x0E 부터는 짧은 이름 `REPORT` 와 끝 표시 0x00 입니다. 16비트 경계를 맞추려고 0x00 이 하나 더 붙었습니다.
9. 오프셋 0x16 부터 확장 블록입니다. `3E 00` 은 크기 62바이트입니다. `09 00` 은 버전 9 입니다. `04 00 EF BE` 는 서명 0xBEEF0004 입니다.
10. 셸 아이템 오프셋 0x1E(확장 블록 오프셋 8)의 `6F 58 87 33` 이 생성 시각입니다. 시각 0x3387 은 6시 28분 14초입니다. 생성 시각은 2024-03-15 06:28:14 UTC 입니다.
11. 셸 아이템 오프셋 0x22(확장 블록 오프셋 12)의 `6F 58 C1 33` 이 접근 시각입니다. 2024-03-15 06:30:02 UTC 입니다.
12. 셸 아이템 오프셋 0x26(확장 블록 오프셋 16)의 `2E 00` 은 긴 이름의 위치입니다. 그 뒤의 MFT 번호·순번과 긴 이름 `Report` 는 생략했습니다.

이 세 시각은 항목을 기록할 때 `Report` 폴더의 시각입니다. 폴더를 연 때가 아닙니다. 이 값만으로는 "이 항목은 2024-03-15 06:30:02 UTC 이후에 기록됐다" 는 것까지만 말할 수 있습니다. 이 항목을 담은 키의 시각을 읽는 방법은 [키 마지막 기록 시각](../../../01-foundations/database-log-formats/registry-hive/last-write-time.md) 의 헥스 예시를 봅니다.

### 공개 도구로 한 번

셸백을 읽는 공개 도구의 예로 RegRipper 의 셸백 플러그인, ShellBags Explorer·SBECmd, libfwsi 를 쓰는 plaso 가 있습니다. 도구를 쓸 때는 다음을 확인합니다.

- 부모 키 시각을 어느 자식에게 붙이는지 봅니다. 모든 자식에게 똑같이 붙이는지, MRUListEx 맨 앞 자식에게만 붙이는지 확인합니다. 4n6k 가 2013년에 지적한 뒤 고친 도구도 있으므로, 쓰는 판에서 직접 확인합니다.
- "처음 연 때" 같은 열을 어떤 키에서 채우는지 봅니다. 하위 폴더 항목이 있는 키의 시각을 처음 연 때로 보여 주면 틀린 값입니다.
- 셸 아이템 시각과 키 시각을 각각 UTC 로 보여 주는지 확인합니다.
- 트랜잭션 로그를 반영하고 읽었는지 확인합니다.
- 헥스로 읽은 값과 한두 항목을 맞춰 봅니다. 방법은 [도구 결과 교차 검증](../../../03-techniques/reporting/tool-validation.md) 을 봅니다.

## 실습

NIST CFReDS 에 공개된 Windows 검체(예: Data Leakage Case)의 사용자 UsrClass.dat 으로 풀어 봅니다.

1. UsrClass.dat 을 트랜잭션 로그 반영 전과 후로 각각 읽습니다. 시각이 달라지는 BagMRU 키가 있습니까?
2. 하위 폴더 항목이 둘 이상인 키를 하나 고릅니다. 그 키의 시각을 붙일 수 있는 자식은 어느 것입니까? 나머지 자식에 대해서는 무엇까지 말할 수 있습니까?
3. 하위 폴더 항목이 없는 키를 모아 처음 기록된 때 목록을 만듭니다. 셸 아이템의 생성 시각보다 앞서는 키 시각이 있습니까? 있다면 어떤 이유가 가능한지 적어 봅니다.
4. 셸 아이템의 MFT 번호·순번으로 $MFT 레코드를 찾습니다. 지금 생성 시각과 셸 아이템의 생성 시각이 같습니까?
5. 공개 도구 두 개로 같은 하이브를 읽습니다. "마지막으로 연 때" 열이 서로 다른 항목을 헥스로 확인합니다.
