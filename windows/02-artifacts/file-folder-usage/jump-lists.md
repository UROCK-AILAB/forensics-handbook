# 점프리스트 (Jump Lists)

## 한 줄 요약

점프리스트 (Jump Lists) 는 작업 표시줄이나 시작 메뉴에서 앱을 오른쪽 클릭하면 나오는 최근·고정 항목 목록입니다. 윈도는 이 목록을 사용자 프로필의 `Recent\AutomaticDestinations` 폴더와 `Recent\CustomDestinations` 폴더에 앱마다 파일 하나씩 저장합니다. 파일 안에는 항목마다 대상 파일의 LNK 데이터와 마지막 갱신 시각이 남습니다. 그래서 어떤 계정이 어떤 앱으로 어떤 파일을 다뤘는지 좁힐 수 있습니다.

## 무엇을 기록하나 · 왜 생기나

점프리스트는 Windows 7 에서 처음 생겼고, 사용자가 최근에 쓴 파일로 바로 가게 하려는 기능입니다. 목록은 앱의 작업 표시줄 단추와 시작 메뉴 항목에 붙습니다.

목록을 채우는 길은 두 가지입니다.

1. **자동 목록 (Automatic Destinations)** — 윈도가 모은 사용 기록입니다. 기록은 `SHAddToRecentDocs` 함수 호출로 쌓입니다. 탐색기에서 파일을 열 때는 셸이 앱 대신 이 함수를 부릅니다. 공통 파일 대화상자로 파일을 열거나, 저장하거나, 새로 만들 때도 셸이 부릅니다. 그래서 앱이 따로 코드를 넣지 않아도 기록이 쌓입니다.
2. **사용자 지정 목록 (Custom Destinations)** — 앱이 `ICustomDestinationList` 인터페이스로 직접 만든 목록입니다. 앱이 정한 범주와 작업 (Tasks) 이 들어갑니다.

`SHAddToRecentDocs` 는 앱 점프리스트의 최근 (Recent)·자주 사용 (Frequent) 목록을 갱신하고, 같은 호출이 사용자의 Recent 폴더에 바로가기 (LNK) 도 만듭니다. 다만 IShellLink 개체로 넘긴 항목은 Recent 폴더에 가지 않고 점프리스트에만 들어갑니다. Windows 7 부터는 "열기" 말고 다른 동사 (verb) 로 파일을 다뤄도 사용 기록이 생길 수 있지만, Windows 7 전에는 "열기" 만 기록을 만들었습니다. 폴더도 기록되는데, 탐색기의 점프리스트에만 나타나고 다른 앱의 점프리스트에는 나타나지 않습니다. 사용자는 항목을 고정 (pin) 하거나 목록에서 뺄 수 있습니다[2][3].

점프리스트 파일 하나에서 읽을 수 있는 것은 다음과 같습니다.

| 알 수 있는 것 | 어디에 남나 |
|---|---|
| 어느 앱의 목록인지 | 파일 이름 앞의 16자리 앱 식별자 (AppID) |
| 대상 파일·폴더의 경로 | DestList 항목의 경로, 번호 스트림 안 LNK |
| 목록에서 마지막으로 갱신된 시각 | DestList 항목의 시각 필드 |
| 고정 여부 | DestList 항목의 고정 상태 필드 |
| 그때 대상 파일의 시각·크기 | 번호 스트림 안 LNK 헤더 |
| 대상이 있던 볼륨 (종류·시리얼 번호·이름) 이나 네트워크 경로 | 번호 스트림 안 LNK |
| 대상이 있던 컴퓨터 이름과 링크 추적 식별자 | DestList 항목의 호스트 이름·드로이드 필드, LNK 의 추적 블록 |

## 위치와 버전별 차이

### 위치

| 종류 | 경로 | 형식 |
|---|---|---|
| 자동 목록 | `C:\Users\<사용자>\AppData\Roaming\Microsoft\Windows\Recent\AutomaticDestinations\<AppID>.automaticDestinations-ms` | OLE 복합 파일 (OLE Compound File) |
| 사용자 지정 목록 | `C:\Users\<사용자>\AppData\Roaming\Microsoft\Windows\Recent\CustomDestinations\<AppID>.customDestinations-ms` | 헤더·범주·LNK 를 이어 붙인 형식 |

두 폴더는 사용자 프로필 안에 있어서 어느 계정의 기록인지 가를 수 있습니다. 두 폴더의 부모인 `Recent` 폴더에는 [바로가기 파일 (LNK)](lnk.md) 이 따로 쌓입니다. 폴더가 `Roaming` 아래에 있으므로 로밍 프로필을 쓰는 환경에서는 다른 PC 에서 쌓인 항목이 함께 들어올 수 있습니다. 이 점은 구조로 보아 가능한 일입니다. 항목마다 호스트 이름 필드를 봅니다.

### AppID — 파일 이름 앞 16자리

파일 이름 앞 16자리 16진수는 앱을 가리키는 AppID 입니다. 계산 방법은 다음과 같습니다[1][6].

1. 실행 파일의 전체 경로를 대문자 UTF-16LE 로 바꿉니다.
2. 경로가 알려진 폴더 (Known Folder) 안에 있으면 그 폴더 식별자로 바꿔 씁니다.
3. 다항식 `0x92C64265D32139A4` 로 64비트 CRC 를 계산합니다.

앱이 AppUserModelID 를 따로 정했으면 경로 대신 그 값으로 계산합니다. 그래서 다음을 조심합니다.

- 같은 앱이라도 설치 경로가 다르면 AppID 가 다릅니다.
- 인터넷에 도는 AppID 목록은 특정 경로·버전에서 계산한 값입니다. 예를 들어 공개 목록에는 64비트 메모장이 `9b9cdc69c1c24e2b`, 32비트 메모장이 `918e0ecb43d17e23` 로 올라 있습니다[6]. 다른 환경에서는 값이 다를 수 있습니다.
- 목록에 없는 AppID 는 안쪽 LNK 의 대상 확장자와 경로로 앱을 짐작합니다. 보고서에는 짐작이라고 밝힙니다.

알려진 폴더 식별자는 [윈도 식별자 형식](../../01-foundations/value-decoding/sid-guid-clsid-known-folder-id.md) 에서 다룹니다.

### Windows 버전에 따라 달라지는 점

자동 목록 파일의 DestList 스트림 앞 4바이트는 형식 버전입니다. 버전에 따라 항목 구조가 다릅니다.

| Windows | 점프리스트 | DestList 형식 버전 | 근거 |
|---|---|---|---|
| XP · Vista | 없음 | — | 기능이 Windows 7 에서 생겼습니다 |
| 7 | 있음 | 1 | [1][5] |
| 8 · 8.1 | 있음 | 1 | Windows 10 전에는 1 입니다[5] |
| 10 | 있음 | 3 또는 4 | [1] |
| 11 | 있음 | 공개 자료 없음 | 헤더의 버전 값을 먼저 읽고 판단합니다 |

버전 1 항목은 경로가 항목 시작에서 114바이트 뒤에 있고, 버전 2 이상 항목은 130바이트 뒤에 있어서 그 사이에 16바이트가 늘었습니다. 이 변화 때문에 여러 도구가 Windows 10 파일을 잘못 읽은 일이 있습니다. 첫 항목만 보여 주거나 나머지를 조용히 버린 도구가 있었습니다[5].

## 구조

저장 형식 자체는 기반 구조 페이지에서 다룹니다. 복합 파일은 [OLE 복합 파일 (Compound File Binary)](../../01-foundations/shell-document-formats/compound-file-binary.md), LNK 는 [바로가기 형식 (Shell Link·LNK)](../../01-foundations/shell-document-formats/shell-link-lnk.md) 을 봅니다. 여기서는 점프리스트에만 있는 부분을 다룹니다. 오프셋과 필드 이름은 형식 명세를 따릅니다[1].

> 그림 자리: `.automaticDestinations-ms` 파일 하나를 복합 파일 디렉터리(Root Entry·DestList·번호 스트림 `1`·`2`·…·`1a`)로 펼치고, DestList 항목의 엔트리 번호가 같은 이름의 번호 스트림(LNK)을 가리키는 관계를 화살표로 보여 주는 그림

### 자동 목록 파일 (`.automaticDestinations-ms`)

파일은 OLE 복합 파일입니다. 안에는 스트림 (stream) 이 두 종류 있습니다.

- **DestList** — 최근·자주 사용 목록입니다. 32바이트 헤더 뒤에 크기가 제각각인 항목이 이어집니다. 파일이 비어 있으면 DestList 크기가 0 일 수 있습니다.
- **번호 스트림** — 이름이 `1`, `2`, `a`, `1a` 처럼 16진수입니다. 스트림 하나에 LNK 하나가 통째로 들어 있습니다.

DestList 항목의 엔트리 번호를 16진수로 쓰면 짝이 되는 번호 스트림의 이름이 됩니다. 예를 들어 엔트리 번호 1112 (0x458) 는 `458` 스트림을 가리킵니다[5].

#### DestList 헤더 (32바이트)

| 오프셋 | 크기 | 내용 |
|---|---|---|
| 0 | 4 | 형식 버전 (1·3·4) |
| 4 | 4 | 항목 수 |
| 8 | 4 | 고정 항목 수 |
| 12 | 4 | 뜻 미확인 (32비트 실수로 보임) |
| 16 | 4 | 마지막 엔트리 번호로 보임 |
| 20 | 4 | 뜻 미확인 (비어 있음) |
| 24 | 4 | 마지막 개정 번호로 보임 |
| 28 | 4 | 뜻 미확인 (비어 있음) |

#### DestList 항목

오프셋은 항목 시작에서 센 값입니다. 앞 112바이트는 두 버전이 같습니다.

| 오프셋 | 크기 | 내용 |
|---|---|---|
| 0 | 8 | 뜻 미확인 |
| 8 | 16 | 드로이드 볼륨 식별자 |
| 24 | 16 | 드로이드 파일 식별자 |
| 40 | 16 | 처음 (Birth) 드로이드 볼륨 식별자 |
| 56 | 16 | 처음 (Birth) 드로이드 파일 식별자 |
| 72 | 16 | 호스트 이름 (ASCII, 남는 자리는 0) |
| 88 | 4 | 엔트리 번호 |
| 92 | 4 | 뜻 미확인 (비어 있음) |
| 96 | 4 | 뜻 미확인 (32비트 실수로 보임) |
| 100 | 8 | 마지막 수정 시각 (FILETIME) |
| 108 | 4 | 고정 상태. `0xFFFFFFFF` (-1) 이면 고정 안 됨, 0 이상이면 고정 |

112바이트부터는 버전에 따라 다릅니다.

| 오프셋 | 크기 | 버전 1 | 오프셋 | 크기 | 버전 2 이상 |
|---|---|---|---|---|---|
| 112 | 2 | 경로 글자 수 | 112 | 4 | 뜻 미확인 (상태 값으로 보임) |
| 114 | 가변 | 경로 (UTF-16LE, 끝 NUL 없음) | 116 | 4 | 뜻 미확인 (접근 횟수로 보임) |
| | | | 120 | 8 | 뜻 미확인 (비어 있음) |
| | | | 128 | 2 | 경로 글자 수 |
| | | | 130 | 가변 | 경로 (UTF-16LE, 끝 NUL 없음) |
| | | | 경로 뒤 | 4 | 뜻 미확인 (정렬용 채움으로 보임) |

필드마다 알아 둘 점은 다음과 같습니다.

- **드로이드 (Droid)** 필드 네 개에는 NTFS 개체 식별자 (Object ID) 가 GUID 로 들어 있습니다. LNK 의 추적 블록 (TrackerDataBlock) 에 있는 같은 이름의 값과 성격이 같습니다. 링크 추적 서비스가 옮겨진 대상을 다시 찾을 때 쓰는 값입니다. 파일 쪽 식별자는 흔히 버전 1 UUID 입니다. 버전 1 UUID 에는 만든 시각과 6바이트 노드 값이 들어 있습니다. 노드 값은 MAC 주소일 수 있지만 반드시 그렇지는 않습니다. 개체 식별자를 모아 두는 NTFS 메타 파일은 [NTFS 메타 파일](../../01-foundations/disk-volume/ntfs/bitmap-secure-extend.md) 에서 다룹니다.
- **호스트 이름** 필드는 호스트 이름 또는 NetBIOS 이름이라고만 알려져 있습니다[1]. LNK 추적 블록의 같은 성격 필드는 대상이 마지막으로 있던 컴퓨터의 NetBIOS 이름입니다. 해석은 [바로가기 파일 (LNK)](lnk.md) 에서 다룹니다.
- **경로** 는 엄격한 UTF-16 이 아닙니다. 짝이 없는 대리 코드 (surrogate) 가 들어 있을 수 있습니다. 이런 값을 만나면 도구가 글자를 깨뜨리거나 오류를 낼 수 있습니다. 인코딩은 [문자 인코딩](../../01-foundations/value-decoding/utf-16le-utf-8-cp949.md) 에서 다룹니다.
- 경로는 파일이 아니라 폴더나 `.library-ms` 라이브러리 파일을 가리킬 수도 있습니다.
- 버전 2 이상의 116 오프셋 값은 접근 횟수로 보이지만 뜻이 확정되지 않았습니다[1].

### 사용자 지정 목록 파일 (`.customDestinations-ms`)

복합 파일이 아니며, 헤더 뒤에 범주 (category) 가 이어집니다.

| 부분 | 내용 |
|---|---|
| 헤더 | 형식 버전 (4바이트, 값 2), 범주 수 (4바이트), 뜻 미확인 4바이트 |
| 범주 종류 (4바이트) | 0 = 앱이 정한 범주, 1 = 알려진 범주, 2 = 사용자 작업 (User Tasks) |
| 종류 0 | 범주 이름 글자 수 (2바이트), 이름 (UTF-16LE), 항목 수 (4바이트), 항목들 |
| 종류 1 | 범주 식별자 (4바이트). 1 = 자주 사용 (KDC_FREQUENT), 2 = 최근 (KDC_RECENT) |
| 종류 2 | 항목 수 (4바이트), 항목들 |
| 범주 끝 | 서명 `0xBABFFBAB` (바이트로는 `AB FB BF BA`) |

항목 하나는 16바이트 클래스 식별자 (CLSID) 와 그 뒤의 셸 개체 데이터이고, LNK 항목의 클래스 식별자는 `00021401-0000-0000-C000-000000000046` 입니다. LNK 안의 파일 크기 필드로는 LNK 데이터의 길이를 잴 수 없으므로[1], LNK 경계는 서명 패턴으로 찾습니다. 방법은 아래 "직접 분석해 보기" 에서 다룹니다. 사용자 작업 범주에는 앱이 미리 정한 명령이 들어가며, 사용자가 무엇을 열었다는 기록이 아닙니다.

## 증거로서 의미

| 증명하는 것 | 증명하지 못하는 것 |
|---|---|
| 이 사용자 프로필에서 이 AppID 의 목록에 이 경로가 올라간 적이 있습니다 | 그 계정 앞에 실제로 누가 앉아 있었는지 |
| 기록된 시각 무렵에 이 항목이 마지막으로 갱신됐습니다 (시계가 맞다면) | 그보다 앞선 열기·저장의 시각 |
| 그때 대상이 이 경로·볼륨·네트워크 공유에 있었습니다 | 대상 파일이 지금도 있는지. 내용이 같은지 |
| 그때 대상 파일의 시각과 크기 (LNK 헤더) | 파일을 읽었는지, 고쳤는지, 복사했는지 |
| 사용자가 이 항목을 고정했는지 | 파일을 연 것인지 저장한 것인지 (둘 다 기록을 만듭니다) |
| 앱이 정한 작업·범주 목록 | 앱이 정한 작업을 사용자가 실행했는지 |

열기와 저장을 구분하지 못하는 이유는 공통 파일 대화상자로 열기·저장·새로 만들기를 하면 모두 같은 함수가 불리기 때문입니다. 목록에 없다는 사실로 쓰지 않았다고 단정하지 않습니다. 사용자가 항목을 뺄 수 있고, 앱이 공통 대화상자를 쓰지 않고 이 함수도 부르지 않으면 기록이 안 생깁니다. 화면에 보이는 목록과 파일 내용도 다릅니다. 화면에 보이는 개수는 해상도와 글꼴 크기 같은 조건에 따라 시스템이 정하고[3], 파일 하나에 DestList 항목이 673개 든 예도 있습니다[5].

### 보고서 문장

아래 경로와 값은 설명을 위해 만든 예입니다.

- 쓸 수 있는 문장: "사용자 A 프로필의 점프리스트 `<AppID>.automaticDestinations-ms` 에 `E:\Work\plan.docx` 항목이 있습니다. 이 항목은 2025-04-02 06:15:30 UTC 에 마지막으로 갱신됐습니다. 안쪽 LNK 에는 대상 볼륨이 이동식 드라이브로 기록돼 있습니다."
- 쓰면 안 되는 문장: "사용자 A 가 2025-04-02 15:15 에 USB 에 있던 plan.docx 를 열어 읽었습니다."

## 시각 해석

점프리스트 한 항목에는 뜻이 다른 시각이 여러 벌 있습니다.

| 시각 | 어디에 남나 | 무엇을 가리키나 | 형식 |
|---|---|---|---|
| DestList 항목 시각 | 항목 오프셋 100 | 이 항목이 목록에서 마지막으로 갱신된 때. 보통 이 앱으로 마지막으로 열거나 저장한 무렵으로 읽습니다 | FILETIME, UTC |
| LNK 헤더의 생성·접근·수정 시각 | 번호 스트림 | LNK 를 쓴 그때 대상 파일의 시각 | FILETIME, UTC |
| 드로이드 파일 식별자 안의 시각 | DestList 항목, LNK 추적 블록 | 대상 파일에 개체 식별자를 붙인 때 | 버전 1 UUID 시각 |
| 점프리스트 파일 자체의 NTFS 시각 | $MFT | 생성은 이 앱의 점프리스트가 처음 생긴 무렵으로 보이고, 수정은 마지막으로 다시 쓴 무렵 | FILETIME, UTC |

- DestList 시각의 필드 이름은 "마지막 수정 시각" 입니다[1]. 항목마다 한 번만 남습니다. 앞선 사용 시각은 덮어써집니다. 옛 시각은 [섀도 복사본](../../03-techniques/analysis/volume-shadow-copy-analysis.md) 에 남은 옛 파일에서 찾습니다.
- LNK 헤더의 세 시각은 파일을 연 시각이 아닙니다. 이 필드는 링크 대상의 생성·접근·수정 시각입니다. LNK 헤더의 수정 시각이 DestList 시각과 가까우면 그 무렵 파일을 저장했을 수 있습니다. 이 해석은 추정입니다.
- 헤더에 마지막 엔트리 번호 필드가 있어서 번호는 새 항목이 생길 때 차례로 붙는 것으로 보입니다. 이 필드의 뜻은 확정되지 않았으므로[1], 번호 순서를 처음 추가된 순서로 쓸 때는 추정이라고 밝힙니다.
- 모든 시각은 UTC 입니다. 현지 시각으로 바꿀 때는 [시간대 설정](../system-account/time-zone.md) 과 [시간대·시계 오차 보정](../../03-techniques/analysis/timeline/time-normalization.md) 을 따릅니다. FILETIME 계산은 [시각 값 형식](../../01-foundations/value-decoding/filetime-unix-webkit-dos-ole.md) 에서 다룹니다.
- 윈도가 점프리스트 파일을 제자리에서 고치는지, 새로 만들어 바꿔 끼우는지는 공개 자료에 나와 있지 않습니다. 파일을 지웠다가 다시 만든 경우도 있을 수 있습니다. 그래서 파일 생성 시각을 앱의 첫 사용 무렵으로 쓸 때는 추정이라고 밝힙니다. 파일의 두 벌 NTFS 시각은 [두 벌의 시각](../../01-foundations/disk-volume/ntfs/standard-information-file-name.md) 에서 다룹니다.

## 함정과 한계

1. **버전을 확인하지 않고 항목을 읽습니다.** 버전 2 이상 파일을 버전 1 틀로 읽으면 경로 위치가 16바이트 어긋납니다. 항목 경계도 어긋나서 두 번째 항목부터 모두 틀립니다. 헤더의 항목 수와 실제로 읽은 항목 수를 맞춰 봅니다.
2. **AppID 를 목록만 보고 앱 이름으로 바꿉니다.** AppID 는 설치 경로나 AppUserModelID 로 계산합니다. 목록의 이름은 계산한 사람의 환경을 따른 값입니다. 안쪽 LNK 의 대상과 맞는지 확인합니다.
3. **화면 목록과 파일을 같게 봅니다.** 파일에는 화면보다 훨씬 많은 항목이 있을 수 있습니다. 화면에 안 보인다고 파일에도 없다고 보지 않습니다.
4. **LNK 헤더 시각을 연 시각으로 씁니다.** 이 시각은 대상 파일의 시각이고, 열거나 저장한 무렵은 DestList 시각에서 찾습니다.
5. **사용자 작업을 사용자 행위로 읽습니다.** 사용자 지정 목록의 작업 범주는 앱이 정한 명령입니다. 범주 종류를 먼저 확인합니다.
6. **탐색기 점프리스트를 놓칩니다.** 폴더 항목은 탐색기의 점프리스트에만 남습니다. 폴더를 연 흔적을 찾을 때는 탐색기 쪽 파일을 따로 봅니다.
7. **Recent 폴더 LNK 와 개수가 같기를 기대합니다.** IShellLink 로 넘긴 항목은 점프리스트에만 들어갑니다. 반대로 셸 확장이 등록한 컨텍스트 메뉴 동사로 연 문서는 Recent 항목에는 나타나지만 앱 점프리스트에는 나타나지 않습니다 (Windows 7 기준)[2]. 두 기록의 개수가 달라도 이상하지 않습니다.
8. **수집한 사본의 파일 시각을 씁니다.** 복사 방법에 따라 사본의 NTFS 시각이 바뀔 수 있습니다. 파일 시각은 원본 볼륨의 [$MFT](../filesystem/mft.md) 에서 읽습니다.

### 지우기와 조작

- **정책으로 로그오프 때 지웁니다.** 로그오프할 때 최근 문서 기록을 지우는 정책 "Clear history of recently opened documents on exit" 이 있습니다. 레지스트리 값은 `HKCU\Software\Microsoft\Windows\CurrentVersion\Policies\Explorer` 의 `ClearRecentDocsOnExit` 입니다. 이 정책을 켜면 로그오프 때 점프리스트의 최근·자주 사용 항목이 지워집니다[4]. 고정 항목과 앱이 정한 작업은 지워지지 않습니다. 정책 값이 켜져 있으면 점프리스트가 비어 있는 이유가 설명됩니다.
- **앱이나 사용자가 목록을 비웁니다.** `SHAddToRecentDocs` 에 빈 값 (NULL) 을 넘기면 모든 사용 기록이 지워집니다[2]. 사용자는 항목을 하나씩 목록에서 뺄 수 있습니다. 앱은 `RemoveDestination`·`RemoveAllDestinations` 로 항목을 지울 수 있습니다.
- **파일째 지웁니다.** 점프리스트 파일이 생기고 지워진 기록은 [$UsnJrnl](../filesystem/usnjrnl.md) 과 $MFT 에 남을 수 있습니다. 옛 파일은 섀도 복사본에서 찾습니다. 지운 파일은 [파일 카빙](../../03-techniques/analysis/data-recovery/file-carving.md) 으로 복합 파일 서명 (`D0 CF 11 E0 A1 B1 1A E1`) 을 찾아 되살려 봅니다.
- **항목만 지웁니다.** 지운 항목의 LNK 데이터가 복합 파일 안 빈 섹터에 남는지는 공개 자료에 나와 있지 않습니다. 복합 파일 구조로 보아 남을 수 있으므로 빈 섹터와 스트림 끝 뒤 영역을 따로 봅니다.
- **파일 시각만 바꿉니다.** 파일 안의 DestList 시각은 그대로입니다. 두 시각을 비교하면 드러날 수 있습니다 ([시각 조작 탐지](../../03-techniques/analysis/timeline/timestomping.md)).

## 직접 분석해 보기

### 헥스로 한 번 — DestList

아래는 형식 명세[1]를 따라 만든 예시입니다. 실제 데이터에서 뽑은 값이 아닙니다. 복합 파일에서 `DestList` 스트림만 꺼낸 상태이고, 오프셋은 스트림 시작에서 센 값입니다. `..` 은 설명과 관계없어 줄인 바이트입니다. 0x28~0x67 의 드로이드 식별자 64바이트도 줄였습니다.

```
오프셋  00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F
0x00    04 00 00 00 01 00 00 00 00 00 00 00 .. .. .. ..
0x10    1A 00 00 00 00 00 00 00 .. .. .. .. 00 00 00 00
0x20    .. .. .. .. .. .. .. .. (드로이드 식별자 4개)
0x60    .. .. .. .. .. .. .. .. 50 43 2D 45 58 41 4D 50
0x70    4C 45 00 00 00 00 00 00 1A 00 00 00 .. .. .. ..
0x80    .. .. .. .. 00 AD 3E A2 96 A3 DB 01 FF FF FF FF
0x90    .. .. .. .. 03 00 00 00 00 00 00 00 00 00 00 00
0xA0    11 00 43 00 3A 00 5C 00 57 00 6F 00 72 00 6B 00
0xB0    5C 00 70 00 6C 00 61 00 6E 00 2E 00 64 00 6F 00
0xC0    63 00 78 00 00 00 00 00
```

1. 0x00 의 `04 00 00 00` 은 형식 버전 4 입니다. 그래서 항목을 버전 2 이상 틀로 읽습니다.
2. 0x04 의 `01` 은 항목 수 1 입니다. 0x08 의 `00` 은 고정 항목 수 0 입니다.
3. 0x10 의 `1A 00 00 00` 은 26 입니다. 마지막 엔트리 번호로 보이는 필드입니다.
4. 첫 항목은 헤더 바로 뒤인 0x20 에서 시작합니다.
5. 0x68 (항목 +72) 의 16바이트는 호스트 이름입니다. ASCII 로 읽으면 `PC-EXAMPLE` 입니다.
6. 0x78 (항목 +88) 의 `1A 00 00 00` 은 엔트리 번호 26 입니다. 16진수로 `1a` 이므로 짝이 되는 LNK 는 `1a` 스트림에 있습니다.
7. 0x84 (항목 +100) 의 8바이트 `00 AD 3E A2 96 A3 DB 01` 을 리틀 엔디언으로 읽으면 0x01DBA396A23EAD00 입니다. 10진으로는 133,880,481,300,000,000 입니다. 1601-01-01 00:00:00 UTC 부터 100나노초 단위로 센 값입니다. 날짜로 바꾸면 2025-04-02 06:15:30 UTC 입니다. 한국 시각 (UTC+9) 으로는 같은 날 15:15:30 입니다.
8. 0x8C (항목 +108) 의 `FF FF FF FF` 는 고정 안 됨입니다.
9. 0x94 (항목 +116) 의 `03 00 00 00` 은 접근 횟수로 보이는 필드입니다. 값은 3 입니다. 뜻이 확정되지 않았으므로 보고서에 사용 횟수로 쓰지 않습니다.
10. 0xA0 (항목 +128) 의 `11 00` 은 경로 글자 수 17 입니다. UTF-16LE 라서 34바이트를 읽습니다. 0xA2 부터 읽으면 `C:\Work\plan.docx` 입니다.
11. 경로 뒤 0xC4~0xC7 의 4바이트는 채움으로 보이는 자리입니다. 항목이 더 있다면 다음 항목은 0xC8 에서 시작합니다. 헤더의 항목 수만큼 읽었을 때 스트림 끝과 맞는지 봅니다.

이 파일을 버전 1 틀로 잘못 읽으면 0x90 (항목 +112) 을 경로 글자 수로 읽습니다. 그러면 엉뚱한 길이로 경로를 읽고, 다음 항목 위치도 어긋납니다.

그다음 `1a` 스트림을 꺼내면 LNK 가 나옵니다. 스트림은 LNK 헤더 크기 `4C 00 00 00` 과 LNK 클래스 식별자로 시작합니다. 그 뒤는 [바로가기 형식](../../01-foundations/shell-document-formats/shell-link-lnk.md) 페이지대로 읽습니다. 대상 경로를 담은 셸 아이템은 [셸 아이템](../../01-foundations/shell-document-formats/shell-item-pidl.md) 에서 다룹니다.

> 그림 자리: 위 DestList 예시에서 헤더(0x00~0x1F)·호스트 이름·엔트리 번호·시각·고정 상태·접근 횟수 추정 필드·경로를 색으로 나누고, 엔트리 번호 0x1A 가 `1a` 스트림으로 이어지는 모습을 보여 주는 그림

### 헥스로 한 번 — 사용자 지정 목록의 LNK 경계

사용자 지정 목록 파일에는 LNK 길이 필드가 없습니다. LNK 시작은 다음 20바이트 패턴으로 찾습니다[5]. 앞 4바이트는 LNK 헤더 크기 0x4C 이고, 뒤 16바이트는 LNK 클래스 식별자입니다.

```
4C 00 00 00 01 14 02 00 00 00 00 00 C0 00 00 00 00 00 00 46
```

- LNK 하나는 이 패턴에서 시작해 다음 패턴 바로 앞에서 끝납니다.
- 마지막 LNK 는 범주 끝 서명 `AB FB BF BA` 바로 앞에서 끝납니다.
- 항목마다 LNK 앞에 같은 클래스 식별자 16바이트가 한 번 더 붙습니다[1]. 이 16바이트는 LNK 데이터에 넣지 않습니다.

### 공개 도구로 한 번

JLECmd, JumpListsView 같은 공개 파서가 자동·사용자 지정 목록을 읽습니다. 복합 파일 도구로 스트림을 꺼낸 뒤 LNK 파서로 따로 읽는 방법도 있습니다. 도구를 쓸 때는 다음을 확인합니다.

- 헤더의 항목 수와 도구가 보여 준 항목 수가 같은지 확인합니다.
- 도구가 DestList 시각과 LNK 헤더 시각을 어떤 이름으로 보여 주는지 확인합니다. 둘을 바꿔 읽기 쉽습니다.
- 시각을 UTC 로 보여 주는지, 분석 PC 의 현지 시각으로 바꿔 보여 주는지 확인합니다.
- 도구가 붙여 주는 앱 이름은 AppID 목록에서 찾은 값입니다. 그 목록이 이 환경과 맞는지 따로 확인합니다.
- 파일 한두 개는 헥스로 읽은 값과 맞춰 봅니다. 방법은 [도구 결과 교차 검증](../../03-techniques/reporting/tool-validation.md) 을 봅니다.

## 실습

**NIST CFReDS Data Leakage Case** (https://cfreds-archive.nist.gov/data_leakage_case/data-leakage-case.html) 는 Windows 7 Ultimate SP1 PC 이미지를 줍니다. 이 사례에는 "이동식 매체 RM#2 에서 연 파일을 모두 나열하라 (문항 26)" 와 "회사 네트워크 드라이브에서 연 파일을 모두 나열하라 (문항 28)" 같은 문항이 있습니다. 점프리스트로 다음을 풀어 봅니다.

1. 사용자 프로필의 `AutomaticDestinations` 와 `CustomDestinations` 에 파일이 몇 개 있습니까? DestList 형식 버전은 무엇입니까? Windows 7 이므로 1 이 나오는지 확인합니다.
2. 각 파일의 AppID 는 어느 앱입니까? 공개 목록의 이름과 안쪽 LNK 의 대상 확장자가 맞는지 봅니다.
3. LNK 의 볼륨 정보가 이동식 드라이브인 항목은 무엇입니까? 그 볼륨 시리얼 번호가 USB 흔적의 장치와 맞습니까? (문항 26)
4. 대상이 네트워크 경로인 항목은 무엇입니까? (문항 28)
5. 한 항목을 골라 DestList 시각과 LNK 헤더의 세 시각을 나란히 적어 봅니다. 각 시각이 무엇을 뜻하는지 한 줄씩 씁니다.
6. Recent 폴더의 LNK 와 점프리스트 항목을 비교합니다. 한쪽에만 있는 항목이 있다면 이유를 설명해 봅니다.
7. 헤더의 항목 수와 도구가 보여 준 항목 수가 같습니까?
