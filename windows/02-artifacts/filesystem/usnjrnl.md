# USN 변경 저널 ($UsnJrnl)

## 한 줄 요약

USN 변경 저널 (USN Change Journal) 은 NTFS 볼륨에서 파일과 폴더가 바뀐 기록을 쌓는 파일입니다. 위치는 `$Extend\$UsnJrnl` 입니다(참고 1). 레코드마다 바뀐 파일의 이름, 파일 참조, 부모 폴더 참조, 시각(UTC), 바뀐 이유가 남습니다. `$LogFile` 보다 훨씬 긴 기간을 담지만 세부 내용은 적습니다(참고 4). 최대 크기에 닿으면 가장 오래된 레코드부터 버립니다.

## 무엇을 기록하나 · 왜 생기나

### 변경에 반응하려는 프로그램이 씁니다

파일 복제 서비스 (FRS), Windows Search 같은 프로그램이 파일 변경에 반응하려고 이 저널을 씁니다(참고 1). fsutil 문서는 Indexing Service, FRS, RIS, Remote Storage 가 저널을 켜고 쓴다고 적었고(참고 3), 저널은 볼륨마다 하나씩 있습니다(참고 2, 참고 3). 기본으로 켜져 있는지, 어느 Windows 부터 그런지는 이 페이지에서 확인하지 못했습니다. 검체에 `$Extend\$UsnJrnl` 이 있는지 직접 봅니다.

### 무엇이 남고 무엇이 안 남나

레코드에는 파일 이름과 부모 폴더 참조가 있지만 전체 경로 칸은 없고(참고 1), 무엇이 바뀌었는지를 뜻하는 이유 플래그가 있습니다(참고 1). 저널은 변경이 있었다는 사실과 이유만 남기며 변경을 되돌릴 만큼의 정보는 없습니다(참고 2). 이유 플래그 표에는 "파일을 읽었다" 를 뜻하는 값이 없습니다(참고 1).

## 위치와 버전별 차이

### 파일과 스트림

| 이름 | 내용 (참고 1) |
|---|---|
| `$Extend\$UsnJrnl` | 저널 파일입니다. MFT 항목 번호가 고정되지 않으므로 `$Extend` 폴더에서 이름으로 찾습니다 |
| `$UsnJrnl:$Max` | 최대 크기 같은 설정이 든 스트림입니다 (32바이트) |
| `$UsnJrnl:$J` | 변경 레코드가 쌓이는 희소 (sparse) 스트림입니다 |

`$Extend` 폴더와 다른 메타 파일은 [NTFS 메타 파일](../../01-foundations/disk-volume/ntfs/bitmap-secure-extend.md)에서 다룹니다. 희소 스트림은 [압축·희소 파일](../../01-foundations/disk-volume/ntfs/compressed-sparse.md)에서 다룹니다.

### `$Max` (32바이트)

| 오프셋 | 크기 | 칸 (참고 1) |
|---|---|---|
| 0 | 8 | 최대 크기 (바이트) |
| 8 | 8 | 할당 증분 (바이트) |
| 16 | 8 | 저널 ID (FILETIME) |
| 24 | 8 | 미상. 비어 있습니다 |

### 레코드 버전

- `fsutil usn readjournal` 은 레코드 주 버전 2~4 를 돌려줍니다. 옵션 minver 의 기본값은 2, maxver 의 기본값은 4 입니다(참고 3).
- 이 페이지의 레코드 표는 버전 2(USN_RECORD_V2)입니다. 버전 3·4 의 칸 배치는 이 페이지에서 확인하지 않았습니다. 주 버전이 2 가 아니면 아래 표로 읽지 않습니다.

### 실제 PC 한 대에서 본 값

`fsutil usn queryjournal C:` 로 확인한 값입니다. (확인 범위: Windows 11 25H2, 1.8TB 볼륨 한 대)

| 항목 | 값 |
|---|---|
| 최대 크기 (Maximum Size) | 0x2000000 (32MB) |
| 할당 증분 (Allocation Delta) | 0x800000 (8MB) |
| 지원 레코드 버전 | 2~4 |
| 쓰기 범위 추적 (Write range tracking) | Disabled |
| 저널 ID | 0x01dbb335d3b67025 (FILETIME 으로 풀면 2025-04-22 03:22:50 UTC) |

- 32MB·8MB 가 Windows 기본값인지는 확인하지 못했습니다. 한 대에서 본 값입니다.
- 이 저널 ID 가 저널을 만든 시각인지는 확인하지 못했습니다. 같은 PC 의 InstallDate 는 2026-06-26 이었습니다. 두 값이 달랐으므로 저널 ID 를 설치 시각이나 저널 생성 시각으로 단정하지 않습니다.

## 구조

### `$J` 가 쌓이고 지워지는 방식

새 레코드는 스트림 끝에 붙습니다(참고 2, 참고 3). 레코드의 USN 은 `$J` 스트림 안에서 그 레코드가 놓인 위치(오프셋)이고, 이 값을 레코드의 고유 번호로 씁니다(참고 1, 참고 2). 레코드는 블록 안에 64비트 경계에 맞춰 놓이고 블록에 남는 자리는 0 이며, 블록 크기는 4096 으로 보이지만 libyal 문서도 확정하지 않았습니다(참고 1).

최대 크기에 닿으면 가장 오래된 레코드를 지우고 그 자리를 희소 구간으로 바꾸기 때문에(참고 1) `$J` 의 앞부분이 비어 있습니다. 저널은 설정한 최대 크기보다 커질 수 있으며, 크기가 "최대 크기 + 할당 증분" 을 넘으면 다음 NTFS 체크포인트 때 잘라 냅니다(참고 3). NTFS 는 공간을 아끼려고 옛 레코드를 지울 수 있습니다(참고 2).

> 그림 자리: `$J` 를 가로 막대로 그리고, 왼쪽의 비어 있는 희소 구간과 오른쪽의 실제 레코드 구간을 나눈 그림. 레코드 하나의 USN 이 막대 시작에서 잰 거리라는 것을 화살표로 표시한다

### 레코드 (USN_RECORD_V2)

| 오프셋 | 크기 | 칸 (참고 1) | 분석에서 쓰는 곳 |
|---|---|---|---|
| 0 | 4 | 레코드 크기 | 다음 레코드로 넘어가기 |
| 4 | 2 | 주 버전 (2) | 버전 확인 |
| 6 | 2 | 부 버전 (0) | |
| 8 | 8 | 파일 참조 | [MFT](mft.md) 항목과 잇기 |
| 16 | 8 | 부모 폴더 참조 | 경로 세우기 |
| 24 | 8 | USN | `$J` 안 위치, 고유 번호 |
| 32 | 8 | 변경 시각 (FILETIME, UTC) | 시간표 |
| 40 | 4 | 변경 이유 (Reason) 플래그 | 무엇이 바뀌었나 |
| 44 | 4 | 출처 (Source) 플래그 | 운영체제·복제가 일으킨 변경 거르기 |
| 48 | 4 | 보안 설명자 ID | |
| 52 | 4 | 파일 속성 플래그 | |
| 56 | 2 | 이름 길이 (바이트) | |
| 58 | 2 | 이름 위치 | |
| 60 | 가변 | 이름 (UTF-16), 뒤에 0 채움 | 파일 이름 |

파일 참조는 MFT 항목 번호 6바이트와 순번 2바이트로 이뤄집니다. 읽는 법은 [마스터 파일 테이블](mft.md)에서 다룹니다.

### 변경 이유 (Reason) 플래그

아래 표는 libyal 문서에 실린 값만 옮겼습니다(참고 1). 표에 없는 비트가 켜져 있으면 Microsoft 의 구조체 문서를 따로 확인합니다.

| 값 | USN_REASON_ 뒤 이름 | 뜻 |
|---|---|---|
| 0x00000001 | DATA_OVERWRITE | 기본 데이터를 덮어씀 |
| 0x00000002 | DATA_EXTEND | 기본 데이터가 늘어남 |
| 0x00000004 | DATA_TRUNCATION | 기본 데이터가 잘림 |
| 0x00000010 | NAMED_DATA_OVERWRITE | 이름 있는 스트림을 덮어씀 |
| 0x00000020 | NAMED_DATA_EXTEND | 이름 있는 스트림이 늘어남 |
| 0x00000040 | NAMED_DATA_TRUNCATION | 이름 있는 스트림이 잘림 |
| 0x00000100 | FILE_CREATE | 파일을 만듦 |
| 0x00000200 | FILE_DELETE | 파일을 지움 |
| 0x00000400 | EA_CHANGE | 확장 속성이 바뀜 |
| 0x00000800 | SECURITY_CHANGE | 접근 권한이 바뀜 |
| 0x00001000 | RENAME_OLD_NAME | 레코드의 이름이 옛 이름 |
| 0x00002000 | RENAME_NEW_NAME | 레코드의 이름이 새 이름 |
| 0x00004000 | INDEXABLE_CHANGE | 색인 제외 속성이 바뀜 |
| 0x00008000 | BASIC_INFO_CHANGE | 읽기 전용·숨김 같은 속성이나 시각 가운데 하나 이상이 바뀜 |
| 0x00010000 | HARD_LINK_CHANGE | 하드 링크가 바뀜 |
| 0x00020000 | COMPRESSION_CHANGE | 압축 상태가 바뀜 |
| 0x00040000 | ENCRYPTION_CHANGE | 암호화 상태가 바뀜 |
| 0x00080000 | OBJECT_ID_CHANGE | 개체 ID 가 바뀜 |
| 0x00100000 | REPARSE_POINT_CHANGE | 리파스 포인트가 바뀜 |
| 0x00200000 | STREAM_CHANGE | 이름 있는 스트림을 더하거나 지우거나 이름을 바꿈 |
| 0x00400000 | TRANSACTED_CHANGE | 트랜잭션 NTFS (TxF) 로 바뀜 |
| 0x80000000 | CLOSE | 파일이 닫힘 |

### 출처 (Source) 플래그

| 값 | USN_SOURCE_ 뒤 이름 | 뜻 (참고 1) |
|---|---|---|
| 0x1 | DATA_MANAGEMENT | 사적인 데이터 스트림을 더함. 앱 데이터는 바뀌지 않음 |
| 0x2 | AUXILIARY_DATA | 운영체제가 일으킨 변경. 쓰기는 했지만 데이터는 바뀌지 않음 |
| 0x4 | REPLICATION_MANAGEMENT | 파일 복제가 일으킨 변경 |

### 플래그가 쌓이는 규칙

Microsoft 문서가 설명하는 규칙입니다(참고 2).

같은 종류의 변경이 여러 번 일어나도 플래그는 하나만 붙어서, 파일을 닫았다 다시 열지 않고 여러 번 쓰면 DATA_OVERWRITE 레코드 하나만 생깁니다. 새 종류의 변경이 생길 때마다 지금까지의 플래그에 새 플래그를 더해(OR) 새 레코드를 씁니다. 바꾸는 사용자가 그 파일을 혼자 쓰고 있었다면 파일을 닫을 때 CLOSE 가 붙은 마지막 레코드를 쓰는데, 이 레코드는 변경 요약이라서 앞 레코드들과 달리 변경 순서는 알려 주지 않습니다. 다음 사용자가 파일을 바꾸면 플래그 하나짜리 새 레코드부터 다시 시작합니다.

문서의 예는 다음과 같습니다. "쓰기 → 시각 설정 → 쓰기 → 자르기 → 쓰기 → 닫기" 순서로 다루면 레코드가 네 개 생깁니다.

| 순서 | 레코드의 이유 플래그 |
|---|---|
| 1 | DATA_OVERWRITE |
| 2 | DATA_OVERWRITE \| BASIC_INFO_CHANGE |
| 3 | DATA_OVERWRITE \| BASIC_INFO_CHANGE \| DATA_TRUNCATION |
| 4 | 3번과 같은 값 \| CLOSE |

두 번째·세 번째 쓰기는 새 레코드를 만들지 않습니다. 같은 종류의 변경이 이미 플래그에 들어 있기 때문입니다.

## 증거로서 의미

| 증명하는 것 | 증명하지 못하는 것 |
|---|---|
| 이 시각(UTC)에 이 이름·이 부모 폴더의 파일에 대해 이런 이유의 레코드를 썼습니다 | 누가 바꿨는지. 레코드에 계정이나 프로세스 칸이 없습니다 |
| 지운 파일의 이름과 부모 폴더 참조 (FILE_DELETE 레코드) | 무엇으로 바뀌었는지. 내용과 바뀌기 전 값은 남지 않습니다(참고 2) |
| 이름을 바꾼 파일의 옛 이름과 새 이름 (RENAME_OLD_NAME·RENAME_NEW_NAME) | CLOSE 요약 레코드 안에서 변경이 일어난 순서(참고 2) |
| 이름 있는 스트림을 더하거나 지운 기록 (STREAM_CHANGE) | 레코드 한 건이 사용자 행동 한 번이라는 것 |
| 접근 권한, 압축, 암호화 상태가 바뀐 기록 | 저널에 남은 가장 이른 레코드보다 앞선 일 |
| 파일 참조의 순번으로 어느 시점의 파일인지 | 파일을 읽기만 한 동작 |

### 보고서 문장

아래 이름과 시각은 설명을 위해 만든 예입니다.

- 쓸 수 있는 문장: "C: 볼륨의 USN 저널에 2025-05-20 06:30:00 UTC, 이름 `보고서.hwp`, 이유 FILE_DELETE·CLOSE 인 레코드가 있습니다. 이 레코드의 부모 폴더 참조는 MFT 39,982번 항목(순번 2)입니다."
- 쓰면 안 되는 문장: "사용자가 5월 20일 오후 3시 30분에 보고서.hwp 를 지웠다."

## 시각 해석

- 레코드 오프셋 32 의 변경 시각은 FILETIME 이고 UTC 입니다(참고 1). 계산법은 [시각 값 형식](../../01-foundations/value-decoding/filetime-unix-webkit-dos-ole.md)에서 다룹니다.
- 이 시각은 레코드를 쓴 시각이고, CLOSE 레코드의 시각은 파일을 닫을 때 쓴 요약 레코드의 시각입니다. 앞선 변경은 그보다 이르게 일어났을 수 있습니다.
- `$J` 에 남은 가장 이른 레코드가 이 기록의 시작점입니다. 그보다 앞의 변경은 `$J` 로 볼 수 없습니다.
- `$Max` 의 저널 ID 도 FILETIME 입니다(참고 1). 위 관찰처럼 설치 시각과 맞지 않을 수 있으므로 뜻을 단정하지 않습니다.
- 현지 시각으로 바꿀 때는 [시간대 설정](../system-account/time-zone.md)을 씁니다. 시계 오차 보정은 [시간대·시계 오차 보정](../../03-techniques/analysis/timeline/time-normalization.md)을 봅니다.
- `$MFT`·`$LogFile` 과 합쳐 시간표를 만드는 절차는 [파일시스템 타임라인](../../03-techniques/analysis/timeline/filesystem-timeline-mft-usnjrnl-logfile.md)에서 다룹니다.

## 함정과 한계

1. **`$J` 를 뽑는 방법에 따라 크기와 해시가 다릅니다.** 앞부분의 빈 구간을 0 으로 채워 뽑으면 논리 크기(수 GB)가 되고, 건너뛰면 실제 데이터만 남습니다. 어떻게 뽑았는지 기록합니다. (현장 관찰)
2. **레코드에는 경로가 없습니다.** 이름과 부모 폴더 참조만 있어서(참고 1) 경로는 MFT 로 세웁니다. 부모 폴더 항목이 다른 폴더에 다시 쓰였으면 경로가 틀어집니다. 부모 참조의 순번과 부모 항목의 지금 순번을 비교합니다.
3. **레코드 한 건은 행동 한 번이 아닙니다.** 한 번 열고 닫는 사이의 변경이 플래그로 쌓입니다(참고 2).
4. **BASIC_INFO_CHANGE 만으로 시각 변경을 말할 수 없습니다.** 이 플래그는 속성이 바뀌어도 붙고 시각이 바뀌어도 붙습니다(참고 1).
5. **출처 플래그가 켜진 레코드를 사용자 행동으로 읽습니다.** 운영체제나 복제가 일으킨 변경일 수 있습니다(참고 1).
6. **주 버전을 확인하지 않습니다.** 버전 3·4 레코드도 있습니다(참고 3). 버전 2 표로 읽으면 칸이 어긋날 수 있습니다.
7. **남은 기간을 짐작합니다.** 기간은 최대 크기와 볼륨 쓰임새에 따라 다릅니다. 검체의 `$Max` 와 가장 이른 레코드 시각을 직접 봅니다.

### 지우기와 조작

fsutil 문서가 설명하는 동작입니다(참고 3).

- `fsutil usn deletejournal {/d | /n} <볼륨>` 은 저널을 지우고 끕니다. `/d` 는 끄는 동안 바로 돌아오고, `/n` 은 다 끈 뒤에 돌아옵니다.
- 저널을 끄면 MFT 의 모든 레코드를 돌며 "마지막 USN" 값을 0 으로 만드는데, 몇 분 걸리고 재부팅 뒤에도 이어질 수 있습니다. 그동안 저널은 켜진 상태도 꺼진 상태도 아니고, 저널 작업은 오류를 냅니다.
- 이 "마지막 USN" 은 `$STANDARD_INFORMATION` 오프셋 64 의 USN 칸으로 보이지만, 둘이 같은 값이라는 문장은 문서에 없습니다.
- 저널을 지우면 FRS·Indexing Service 가 볼륨 전체를 다시 훑습니다.
- `fsutil usn createjournal m=<최대 크기> a=<할당 증분> <볼륨>` 은 저널을 만듭니다. 저널이 이미 있으면 두 값만 바꿉니다. 최대 크기를 줄이면 남는 기간도 짧아집니다.

분석할 때는 이렇게 봅니다.

- `$UsnJrnl` 이 없거나, 가장 이른 레코드가 수집 직전이면 저널을 지우거나 다시 만들었는지 따집니다.
- 다른 볼륨이나 [섀도 복사본](../../03-techniques/analysis/volume-shadow-copy-analysis.md)의 옛 `$J` 와 비교합니다.
- `$LogFile` 이 덮는 기간의 USN 레코드는 `$LogFile` 안에도 있습니다(참고 4). 저널을 지운 시점이 그 기간 안이면 `$LogFile` 에서 레코드를 더 찾을 수 있습니다.
- 명령 실행 흔적은 [PowerShell 명령 기록](../execution/consolehost-history-txt.md)과 [프로세스 생성](../event-logs/4688.md) 기록에서 찾습니다.
- 완전삭제 도구를 의심하면 [완전삭제 도구를 썼나](../../04-scenarios/activity/anti-forensics/wiping-tools.md)를 봅니다.

## 직접 분석해 보기

### 헥스로 한 번

아래 바이트는 libyal 명세의 USN_RECORD_V2 표를 보고 만든 예시입니다. 실제 검체에서 뽑은 값이 아닙니다.

```
오프셋  00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F
0x00    50 00 00 00 02 00 00 00 A3 F4 01 00 00 00 04 00
0x10    2E 9C 00 00 00 00 02 00 F0 C8 A5 13 02 00 00 00
0x20    00 24 A2 9C 50 C9 DB 01 00 02 00 80 00 00 00 00
0x30    0B 01 00 00 20 00 00 00 0E 00 3C 00 F4 BC E0 AC
0x40    1C C1 2E 00 68 00 77 00 70 00 00 00 00 00 00 00
```

1. 0x00 의 `50 00 00 00` 은 레코드 크기 0x50(80바이트)입니다. 80 은 8 의 배수이므로 64비트 경계에 맞습니다.
2. 0x04 의 `02 00` 은 주 버전 2, 0x06 의 `00 00` 은 부 버전 0 입니다. 그래서 위 V2 표로 읽습니다.
3. 0x08 의 `A3 F4 01 00 00 00 04 00` 은 파일 참조입니다. 앞 6바이트는 MFT 항목 0x01F4A3(128,163)번, 뒤 2바이트는 순번 4 입니다.
4. 0x10 의 `2E 9C 00 00 00 00 02 00` 은 부모 폴더 참조입니다. MFT 항목 0x9C2E(39,982)번, 순번 2 입니다.
5. 0x18 의 `F0 C8 A5 13 02 00 00 00` 은 USN 0x213A5C8F0, 10진으로 8,919,566,576 입니다. 이 레코드는 `$J` 스트림 안 8,919,566,576바이트 위치에 놓여 있습니다.
6. 0x20 의 `00 24 A2 9C 50 C9 DB 01` 은 변경 시각입니다. 리틀 엔디언으로 0x01DBC9509CA22400, 10진으로 133,921,962,000,000,000 입니다. 날짜로는 2025-05-20 06:30:00 UTC, 한국 시각 15:30:00 입니다.
7. 0x28 의 `00 02 00 80` 은 이유 플래그 0x80000200 입니다. FILE_DELETE(0x00000200)와 CLOSE(0x80000000)가 켜져 있습니다.
8. 0x2C 의 출처 플래그는 0 입니다. 켜진 값이 없습니다.
9. 0x30 은 보안 설명자 ID, 0x34 는 파일 속성 플래그입니다. 이 예시에서는 풀지 않습니다.
10. 0x38 의 `0E 00` 은 이름 길이 14바이트, 0x3A 의 `3C 00` 은 이름 위치 0x3C(60)입니다.
11. 0x3C 부터 14바이트는 UTF-16LE 이름입니다. `F4 BC` 는 U+BCF4 '보', `E0 AC` 는 U+ACE0 '고', `1C C1` 은 U+C11C '서' 입니다. 이어서 `.hwp` 가 옵니다. 이름은 `보고서.hwp` 입니다. 한글 이름 읽는 법은 [문자 인코딩](../../01-foundations/value-decoding/utf-16le-utf-8-cp949.md)에서 다룹니다.
12. 0x4A 부터 6바이트는 0 채움입니다.

그다음 할 일은 이렇습니다.

1. MFT 128,163번 항목의 순번을 봅니다. 파일을 지웠으므로 순번은 4 보다 커져 있을 것입니다. 항목이 다시 쓰이지 않았다면 이름과 시각이 남아 있을 수 있습니다.
2. MFT 39,982번 항목의 순번이 2 인지 봅니다. 2 이면 그 폴더의 이름과 부모를 따라 경로를 세웁니다.
3. 파일 참조가 같은 앞선 레코드를 찾습니다. 파일을 만든 레코드와 이름을 바꾼 레코드가 있는지 봅니다.

### 실행 중인 시스템에서

fsutil 로 확인합니다(참고 3).

- `fsutil usn queryjournal C:` — 저널 정보와 용량을 봅니다.
- `fsutil usn readjournal C: startusn=<USN>` — 지정한 위치부터 레코드를 읽습니다.
- `fsutil usn readdata <파일>` — 파일 하나의 USN 정보를 봅니다.
- `fsutil usn enumdata <파일 참조> <낮은 USN> <높은 USN> <볼륨>` — 두 경계 사이의 항목을 나열합니다.

`deletejournal`, `createjournal`, `enablerangetracking` 은 볼륨을 바꾸는 명령입니다. 증거 볼륨에서는 쓰지 않습니다.

### 공개 도구로 한 번

`$J` 를 표로 풀어 주는 공개 도구가 여럿 있습니다. 어느 도구를 쓰든 아래를 확인합니다.

- 주 버전 3·4 레코드를 읽는지 확인합니다.
- 출처 플래그를 칸으로 보여 주는지 확인합니다.
- 경로를 붙일 때 부모 참조의 순번을 비교하는지 확인합니다. 비교하지 않으면 틀린 경로가 나올 수 있습니다.
- 시각을 UTC 로 내는지 확인합니다.
- 레코드 몇 개는 헥스로 읽은 값과 맞춰 봅니다. 방법은 [도구 결과 교차 검증](../../03-techniques/reporting/tool-validation.md)을 봅니다.

## 실습

**직접 만든 Windows 10·11 가상 머신**에서 해 봅니다.

1. `fsutil usn queryjournal C:` 로 최대 크기와 할당 증분을 적습니다.
2. 텍스트 파일을 만들고, 내용을 두 번 고쳐 저장하고, 이름을 바꾸고, 지웁니다. 각 동작의 시각을 적어 둡니다.
3. 그 파일의 레코드를 모두 모아 보십시오. 레코드는 몇 개입니까? 이유 플래그가 위 "플래그가 쌓이는 규칙" 대로 쌓였습니까?
4. 이름을 바꾼 기록에서 옛 이름과 새 이름을 찾아보십시오.
5. `$J` 를 두 방법(빈 구간을 0 으로 채우기, 건너뛰기)으로 뽑아 크기와 해시를 비교해 보십시오.

**NIST CFReDS 같은 공개 검체의 Windows 디스크 이미지**로도 풀어 봅니다.

1. `$Max` 의 최대 크기와 할당 증분은 얼마입니까?
2. `$J` 에 남은 가장 이른 레코드와 가장 늦은 레코드의 시각은 언제입니까?
3. FILE_DELETE 레코드 가운데 MFT 에서 이미 다시 쓰인 항목을 가리키는 것을 찾아보십시오. 순번으로 어떻게 가려냈는지 적어 보십시오.
