# 지운 메시지 복구 (Recoverable Items·Free Blocks)

> 상위 허브: [아웃룩 (Outlook)](index.md)

## 한 줄 요약

Outlook 에서 지운 메시지는 두 곳에 남을 수 있습니다. 한 곳은 Exchange 서버 사서함의 숨은 복구 가능한 항목 (Recoverable Items) 폴더입니다. 다른 한 곳은 PST·OST 파일 안의 빈 공간입니다. 서버 쪽은 보존 규칙이 정해져 있지만(Exchange Online 기준), 파일 쪽은 빈 공간을 찾는 구조만 알려져 있어 실제로 되살아나는지는 실제 데이터로 확인합니다.

## 무엇을 기록하나 · 왜 생기나

### 지우는 세 단계

지우는 동작은 세 단계로 나뉩니다.

| 용어 | 동작 |
|---|---|
| 삭제 | 항목을 지운 편지함으로 옮깁니다 |
| 소프트 삭제 | 지운 편지함에서 다시 지우거나, Shift+Delete 로 바로 지웁니다. 항목은 Recoverable Items 폴더로 갑니다 |
| 하드 삭제 | 사서함 데이터베이스에서 지우도록 표시합니다 |

첫 단계의 지운 편지함은 보통 폴더라서 PST·OST 에서도 보이며, 이 페이지는 그다음 두 단계에서 항목이 어디에 남는지 다룹니다.

### 서버 쪽: Recoverable Items 폴더

Recoverable Items 폴더는 예전 Exchange 의 "덤프스터 (dumpster)" 를 대신합니다. 사서함은 IPM 하위 트리와 비 IPM 하위 트리로 나뉘는데, IPM 하위 트리에는 받은편지함·일정·보낸 편지함처럼 보이는 폴더가 있고 비 IPM 하위 트리에는 내부 데이터가 있습니다. Recoverable Items 는 비 IPM 쪽에 있어서 Outlook 과 웹 Outlook 에서 보이지 않습니다.

사서함을 다른 데이터베이스로 옮기면 이 폴더도 같이 갑니다. Exchange 검색이 이 폴더를 색인하기 때문에 eDiscovery 와 콘텐츠 검색으로 찾을 수 있습니다.

### 파일 쪽: PST·OST 안의 빈 공간 (Free Blocks)

PFF 파일은 파일 안의 어느 부분을 쓰고 있는지 표로 기록하고 쓰지 않는 부분은 빈 공간으로 기록합니다. 빈 공간을 찾는 표는 아래 "구조" 절에 있습니다.

지운 메시지 내용이 빈 블록에 남아 있다가 새 데이터에 덮이기 전까지 되살릴 수 있다는 설명이 흔합니다. 이 설명은 일반론이므로 실제로 되살아나는지는 실제 데이터로 확인합니다.

## 위치와 버전별 차이

### 서버 쪽 보존 기간과 한도 (Exchange Online)

| 항목 | 값 |
|---|---|
| 지운 항목 보존 기간 | 기본 14일, 최대 30일 |
| Managed Folder Assistant 가 지우는 때 | 기본 14일 뒤. 일정 항목만 120일 뒤 |
| Recoverable Items 한도 (기본) | 경고 20GB, 최대 30GB |
| Recoverable Items 한도 (보존 중) | 경고 90GB, 최대 100GB |
| Recoverable Items 한도 (보관 사서함을 켠 경우) | 경고 95GB, 최대 105GB |

- 경고 한도에 닿으면 먼저 들어온 항목부터(FIFO) 지웁니다.
- 기간을 어느 시점부터 세는지는 공개 문서에 나와 있지 않습니다.
- 이 값들은 Exchange Online 기준입니다. 온프레미스 Exchange 는 그 서버의 설정을 확인합니다.

### 파일 쪽 형식 차이

- 할당표 상태 필드의 위치는 32비트(ANSI) 헤더와 유니코드 헤더가 다릅니다. 아래 "구조" 절의 표를 봅니다.
- 첫 할당표 위치 `0x4400`·`0x4600` 이 4KB 페이지 형식(wVer 36)에서도 같은지는 실제 데이터로 확인합니다.

## 구조

### 서버 쪽: Recoverable Items 의 하위 폴더

| 하위 폴더 | 들어가는 것 | 사용자에게 |
|---|---|---|
| Deletions | 소프트 삭제한 항목(지운 편지함에서 다시 지웠거나 Shift+Delete 로 지운 항목) | "지운 항목 복구" 기능으로 볼 수 있습니다 |
| Versions | 보존 (In-Place Hold·Litigation Hold·보존 정책) 중일 때 원본과 고치기 전 사본 | |
| Purges | Litigation Hold 나 단일 항목 복구가 켜져 있을 때 하드 삭제된 항목 | 보이지 않습니다 |
| Audits | 사서함 감사 로그가 켜져 있을 때 감사 기록 | |
| DiscoveryHolds | In-Place Hold 나 보존 정책 조건에 맞는 하드 삭제 항목 | |
| Calendar Logging | 일정 변경 기록 | 보이지 않습니다 |
| SubstrateHolds | 보존 중 고치거나 지운 Teams 메시지의 원본 | |

폴더 사이에서 항목이 옮겨 가는 규칙은 다음과 같습니다.

- 사용자가 Deletions 에서 항목을 지우면 항목은 Purges 로 가고, 사용자는 더 이상 되살릴 수 없습니다. 단일 항목 복구가 켜져 있으면 보존 기간 동안 관리자가 eDiscovery 로 이 항목을 찾을 수 있습니다.
- 보존 (Hold) 중에는 DiscoveryHolds·Deletions·Purges 의 자동 삭제가 멈춥니다.
- 보존 중에 제목·본문·첨부·보낸 사람과 받는 사람·보낸 날짜와 받은 날짜를 고치면, 고치기 전 사본이 Versions 에 남습니다. 이 방식을 쓰기 시 복사 (copy-on-write) 라고 합니다. 임시 보관함 항목은 예외입니다.
- 사용자가 만든 폴더를 Shift+Delete 로 지우거나, 지운 편지함 안의 폴더를 지우면 폴더 자체는 하드 삭제되어 보존 중에도 되살릴 수 없습니다. 그 폴더 안의 항목은 Deletions 로 가고, 기본 14일 동안 되살릴 수 있습니다.

### 파일 쪽: 빈 공간을 기록하는 표

빈 공간을 기록하는 표는 다음과 같습니다.

| 표 | 페이지 형식 값 | 기록 단위 | 첫 표 위치 |
|---|---|---|---|
| 데이터 할당표 | `0x84` | 64바이트 블록마다 쓰임 여부 | 오프셋 `0x4400` |
| 페이지 할당표 | `0x83` | 512바이트 페이지마다 쓰임 여부 | 오프셋 `0x4600` |
| 빈 공간 지도 (free map) | `0x82` | 이어진 빈 데이터 블록 수 | |
| 빈 페이지 지도 | `0x85` | 빈 페이지 | |
| 밀도 목록 (density list) | `0x86` | 데이터 할당표를 채워진 정도 순서로 둔 목록 | |

헤더에는 할당표를 믿어도 되는지 알려 주는 상태 필드가 있습니다.

| 값 | 뜻 |
|---|---|
| `0x00` | 할당표가 하나 이상 틀립니다 |
| `0x01` | 옛 형식입니다. 더는 쓰지 않습니다 |
| `0x02` | 할당표가 모두 맞습니다 |

| 헤더 | 상태 필드 오프셋 |
|---|---|
| 32비트 (ANSI) | 200 (`0xC8`) |
| 유니코드 | 248 (`0xF8`) |

헤더 안 ROOT 에는 "남은 데이터 공간 크기" 필드도 있습니다. 이 필드로 빈 공간이 얼마나 되는지 봅니다. 필드 위치는 [데이터 파일 구조 (PST·OST)](pst-ost.md)의 ROOT 표에 있습니다.

## 증거로서 의미

### 서버 쪽

| 증명하는 것 | 증명하지 못하는 것 |
|---|---|
| Deletions 에 있는 항목은 소프트 삭제한 항목입니다. 지운 편지함에서 다시 지웠는지, Shift+Delete 로 바로 지웠는지는 폴더만으로 구분하지 못합니다 | Recoverable Items 에 없는 항목이 처음부터 없었다는 것. 보존 기간이 지났거나 한도 때문에 먼저 지워졌을 수 있습니다 |
| Purges 에 있는 항목은 Litigation Hold 나 단일 항목 복구가 켜진 상태에서 하드 삭제된 항목입니다 | 누가 지웠는지. 폴더 위치만으로는 알 수 없습니다. 감사 로그가 켜져 있었다면 Audits 를 봅니다 |
| Versions 에 사본이 있으면 보존 중에 그 항목의 제목·본문·첨부·주소·날짜 가운데 하나를 고친 것입니다 | 보존이 없던 기간에 고친 내용. 사본이 남지 않습니다 |
| Calendar Logging 에는 일정을 바꾼 기록이 남습니다 | 통째로 지운 사용자 폴더 자체. 보존 중에도 되살릴 수 없습니다 |

### 파일 쪽

| 증명하는 것 | 증명하지 못하는 것 |
|---|---|
| 할당표에서 빈 곳으로 표시된 부분은 파일이 지금 쓰지 않는 공간입니다 | 빈 공간에서 찾은 조각이 어느 메시지의 것인지. 조각만으로는 알기 어렵습니다 |
| 상태 필드가 `0x02` 이면 할당표를 믿고 빈 공간을 가려낼 수 있습니다 | 메시지를 언제 지웠는지. 빈 공간에는 지운 시각이 남지 않습니다 |
| | 빈 공간에 아무것도 없다고 해서 지운 메시지가 없었다는 것 |

### 보고서 문장

아래 폴더 이름과 날짜는 설명을 위해 만든 예입니다.

- 쓸 수 있는 문장: "콘텐츠 검색 결과, 이 사서함의 Recoverable Items\Purges 폴더에 제목이 '계약 조건' 인 메시지가 있습니다. 이 폴더에는 단일 항목 복구나 Litigation Hold 가 켜진 상태에서 하드 삭제된 항목이 들어갑니다."
- 쓰면 안 되는 문장: "사용자가 2025년 3월 증거를 없애려고 이 메일을 영구 삭제했습니다."

## 시각 해석

- 서버 쪽 보존 기간(기본 14일, 일정 120일)은 자동 삭제가 일어나는 기준인데, 기간을 어느 시점부터 세는지 알려져 있지 않으므로 "지운 지 며칠 지났으니 없다" 고 날짜를 계산해 단정하지 않습니다.
- 보존 중에는 자동 삭제가 멈춥니다. 보존을 언제 걸고 풀었는지 관리자에게 확인합니다.
- 빈 공간에서 찾은 조각 안의 시각 값은 메시지의 시각입니다. 지운 시각이 아닙니다. 형식은 UTC 기준 FILETIME 입니다([시각 값 형식](../../../01-foundations/value-decoding/filetime-unix-webkit-dos-ole.md)).
- PST·OST 가 경고 한도에 닿으면 파일을 줄이는 압축 (compaction) 이 시작됩니다. 파일 크기가 줄어든 때는 [USN 변경 저널](../../filesystem/usnjrnl.md)에서 찾아봅니다.

## 함정과 한계

1. **OST 에서 서버의 Recoverable Items 를 찾습니다.** 이 폴더는 서버 사서함의 비 IPM 쪽에 있습니다. OST 에 동기화되는지는 공개 문서에 나와 있지 않습니다. 서버 쪽 자료는 eDiscovery·콘텐츠 검색으로 따로 요청합니다([PST와 OST 차이](cached-mode-exchange.md)).
2. **Exchange Online 값을 온프레미스에 그대로 씁니다.** 이 페이지의 기간과 한도는 Exchange Online 기준입니다. 온프레미스는 그 서버의 설정을 확인합니다.
3. **보존 설정을 확인하지 않고 "14일이 지나 없다" 고 결론 냅니다.** 기간은 30일까지 늘릴 수 있습니다. 보존 중에는 자동 삭제가 멈춥니다. 한도에 닿으면 14일보다 먼저 지워질 수도 있습니다.
4. **폴더째 지운 경우 폴더도 되살아난다고 봅니다.** 폴더 자체는 하드 삭제되어 보존 중에도 되살릴 수 없습니다. 안의 항목만 Deletions 로 갑니다. 되살린 항목의 원래 폴더 이름은 다른 기록으로 확인합니다.
5. **파일 빈 공간 복구를 당연하게 약속합니다.** 빈 블록에 지운 메시지가 남는다는 설명은 일반론입니다. 압축이 빈 블록의 옛 내용을 지우는지도 알려져 있지 않습니다. 파일마다 결과가 다를 수 있다고 보고서에 적습니다.
6. **인코딩된 파일의 빈 공간을 글자로 검색합니다.** `bCryptMethod` 가 `0x01`·`0x02` 이면 블록 바이트가 원래 글자와 다릅니다. 빈 공간 조각도 그대로 검색하면 본문이 빠질 수 있습니다([데이터 파일 구조](pst-ost.md)의 인코딩 표).
7. **상태 필드가 `0x00` 인데 할당표를 믿습니다.** 할당표가 틀렸다는 뜻입니다. 빈 공간 판단이 틀릴 수 있으므로 파일 전체를 따로 살펴봅니다.
8. **도구의 "복구" 결과를 그대로 씁니다.** 공개 도구가 빈 블록·고아 항목에서 메시지를 되살리는지, 어떤 방법으로 하는지는 도구마다 다를 수 있습니다. 도구마다 결과를 비교합니다([도구 결과 교차 검증](../../../03-techniques/reporting/tool-validation.md)).

## 직접 분석해 보기

### 원시 바이트로 한 번

1. 헤더의 `wVer` 로 형식을 구분합니다([데이터 파일 구조](pst-ost.md)).
2. 할당표 상태 필드를 읽습니다. ANSI 는 오프셋 200, 유니코드는 248 입니다. `0x02` 이면 3번으로 갑니다. `0x00` 이면 할당표를 믿지 않고 파일 전체를 살펴봅니다.
3. ROOT 의 "남은 데이터 공간 크기" 필드를 읽습니다. 값이 클수록 볼 빈 공간이 많습니다.
4. 오프셋 `0x4400` 의 페이지로 갑니다. 첫 데이터 할당표입니다. 페이지 형식 값이 `0x84` 인지 확인합니다. 페이지 안에서 이 값이 놓이는 자리는 libpff 문서의 페이지 절을 봅니다.
5. 할당표가 빈 곳으로 표시한 64바이트 단위를 모아 따로 파일로 뽑습니다.
6. 뽑은 조각에서 메일 주소, 제목에 들어갔을 낱말을 검색합니다. 인코딩된 파일이면 5번에서 뽑은 조각을 먼저 되돌려야 하는지 확인합니다.

예: Windows 11 25H2 의 유니코드 PST 에서 오프셋 248 은 `0x02` 입니다.

> 그림 자리: PST 파일을 64바이트 칸으로 나눈 띠 위에 쓰는 칸과 빈 칸을 색으로 나누고, 데이터 할당표(0x4400)가 이 띠를 가리키는 모습을 보여 주는 그림

### 공개 도구로 한 번

- 서버 쪽: Microsoft 365 의 eDiscovery·콘텐츠 검색으로 Recoverable Items 를 검색합니다. 결과를 받을 때 어느 하위 폴더에서 나온 항목인지 함께 받습니다.
- 파일 쪽: libpff 같은 공개 파서로 PST 를 연 결과와, 위 순서로 직접 뽑은 빈 공간 검색 결과를 비교합니다. 파서가 보여 주지 않는 메시지가 빈 공간에서 나오면, 그 조각을 원래 파일의 위치와 함께 기록합니다.

빈 공간을 뽑아 검색하는 일반 절차는 [삭제 데이터 복구](../../../03-techniques/analysis/data-recovery/index.md)와 [파일 내용 검색](../../../03-techniques/analysis/content-search/index.md)에서 다룹니다.

## 실습

**직접 만든 가상 머신과 시험용 Exchange Online 계정으로** 해 봅니다.

1. 메일 셋을 각각 삭제, 소프트 삭제(Shift+Delete), 지운 편지함에서 다시 지우기로 지웁니다. Outlook 의 "지운 항목 복구" 에는 어느 메일이 보입니까?
2. "지운 항목 복구" 창에서 한 메일을 다시 지웁니다. 사용자 화면에서 사라집니까? 관리자 콘텐츠 검색으로는 찾아집니까?
3. 시험 사서함에 보존을 걸고 메일의 제목을 고쳐 봅니다. Versions 에 사본이 생깁니까? 임시 보관함 메일도 고쳐 보십시오.

**직접 만든 PST 로** 해 봅니다.

1. 새 PST 를 만들고 헤더의 `bCryptMethod` 를 확인합니다. 흔하지 않은 낱말을 넣은 메일 몇 통을 넣고 Outlook 을 닫은 뒤 파일을 복사합니다.
2. 메일을 지우고 지운 편지함도 비운 뒤 Outlook 을 닫습니다. 그 낱말이 파일에 원시 바이트로 남아 있습니까? 남았다면 할당표가 빈 곳으로 표시한 부분입니까?
3. PST 를 만들 때 인코딩을 고를 수 있으면 다른 값으로 같은 실험을 해 보십시오. 원시 검색 결과가 어떻게 다릅니까?
4. Outlook 이 파일을 열고 있는 동안 가상 머신을 강제로 끈 뒤, 할당표 상태 필드 값을 확인해 보십시오.
