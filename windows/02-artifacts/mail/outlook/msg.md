# 개별 메시지 파일 (MSG)

> 상위 허브: [아웃룩 (Outlook)](index.md)

## 한 줄 요약

`.msg` 파일은 Outlook 항목 하나를 파일 하나에 담은 형식으로, OLE 복합 파일 안에 저장소 (storage) 와 스트림 (stream) 으로 속성·수신자·첨부를 나눠 담습니다. 형식 명세는 Microsoft 의 [MS-OXMSG] 입니다. 저장소와 스트림의 수는 메시지마다 다르므로, 수를 세어 보면 수신자·첨부 수를 맞춰 볼 수 있습니다.

## 무엇을 기록하나 · 왜 생기나

명세의 제목은 "Outlook Item (.msg) File Format" 입니다. PST 가 폴더와 메시지를 통째로 담는 파일이라면, `.msg` 는 메시지 한 통을 떼어 낸 파일입니다. 파일의 최상위가 메시지 한 통 전체를 뜻합니다.

파일에는 다음이 들어 있습니다.

- 메시지의 속성 (제목·시각·보낸 사람 같은 값은 모두 속성입니다)
- 수신자마다의 정보
- 첨부마다의 정보와 내용
- 첨부가 다른 메시지일 때는 그 메시지 전체

속성의 번호와 값 형식은 [MAPI 속성](../../../01-foundations/app-mail-data/mapi-property.md)에서 다룹니다. 이 페이지는 속성이 파일 안 어디에 놓이는지를 다룹니다.

`.msg` 는 사용자가 저장한 곳 어디에나 있을 수 있고 정해진 폴더가 없으므로, 확장자와 파일 형식으로 디스크 전체를 찾습니다.

## 위치와 버전별 차이

- 파일 형식은 Windows 버전과 관계가 없고 명세의 판이 기준입니다. 이 글은 최상위 구조 절(2.3)의 2025-05-20 갱신본을 봤습니다.
- 문자열 속성이 ANSI 인지 유니코드인지에 따라 값의 형식 번호가 달라진다는 설명이 흔합니다. 이번에 명세 본문으로 확인하지 못했습니다. 문자열을 읽을 때는 [문자 인코딩](../../../01-foundations/value-decoding/utf-16le-utf-8-cp949.md)을 함께 봅니다.
- `.eml` 은 이름이 비슷하지만 다른 형식입니다. `.eml` 은 인터넷 메일 글자 형식입니다([인터넷 메일 형식](../../../01-foundations/app-mail-data/eml-mbox-rfc-5322-mime.md)).

## 구조

### 바탕: OLE 복합 파일

`.msg` 는 OLE 복합 파일 (Compound File) 구조를 씁니다. 명세 목차에도 "1.3.1 Compound Files" 절이 있습니다. 복합 파일은 파일 안에 폴더 같은 저장소와 파일 같은 스트림을 둡니다. 복합 파일 자체의 헤더와 디렉터리 읽는 법은 [OLE 복합 파일](../../../01-foundations/shell-document-formats/compound-file-binary.md)에서 다룹니다.

### 최상위에 들어가는 것

최상위에 드는 저장소·스트림의 수와 종류는 메시지 종류, 수신자·첨부 수, 들어 있는 속성에 따라 다릅니다. 명세가 적은 규칙은 다음과 같습니다.

| 들어가는 것 | 개수 |
|---|---|
| 수신자 저장소 | 수신자마다 1개 |
| 첨부 저장소 | 첨부마다 1개 |
| 이름 붙은 속성 대응 (named property mapping) 저장소 | 정확히 1개 |
| 속성 스트림 | 정확히 1개. 메시지의 모든 속성 항목이 들어 있습니다 |
| 길이가 바뀌는 속성의 스트림 | 속성마다 1개. 값이 들어 있습니다 |
| 길이가 고정된 다중값 속성의 스트림 | 속성마다 1개 |
| 길이가 바뀌는 다중값 속성의 스트림 | 값이 N개면 N+1개 |

### 명세의 절과 저장소 종류

명세 목차가 나누는 절은 다음과 같습니다.

| 절 | 내용 |
|---|---|
| 2.2.1 | 수신자 저장소 |
| 2.2.2 | 첨부 저장소 |
| 2.2.2.1 | 포함된 메시지 저장소. 첨부가 메시지일 때 씁니다 |
| 2.2.2.2 | 사용자 정의 첨부 저장소 |
| 2.2.3 | 이름 붙은 속성 대응 저장소. GUID·Entry·String 스트림이 들어 있습니다 |
| 2.4 | 속성 스트림 |
| 2.4.1 | 속성 스트림 헤더. 최상위, 포함된 메시지, 첨부·수신자에 따라 다릅니다 |
| 2.4.2.1 | 고정 길이 속성 항목 |

- 명세 2.2 "Storages" 절 페이지는 본문이 비어 있습니다. 세부 내용은 하위 절에 있습니다.
- 속성 스트림 헤더의 크기와 고정 길이 속성 항목의 크기는 이번에 확인하지 못했습니다. 바이트 단위로 읽을 때는 명세 2.4 절을 직접 엽니다.

> 그림 자리: 수신자 둘·첨부 하나(첨부가 다른 메시지)인 `.msg` 의 저장소·스트림 나무 구조. 최상위 속성 스트림, 이름 대응 저장소, 수신자 저장소 둘, 첨부 저장소 안의 포함된 메시지 저장소를 보여 주는 그림

### 저장소·스트림 이름

공개 파서와 분석 자료는 저장소·스트림에 아래 이름을 씁니다. 수신자 저장소 이름만 명세 2.2.1 절로 확인했습니다. 나머지는 명세 본문으로 확인하지 못한 이름입니다. 검체를 열어 실제 이름을 확인한 뒤 씁니다.

| 대상 | 이름 |
|---|---|
| 속성 스트림 | `__properties_version1.0` (확인하지 못함) |
| 수신자 저장소 | `__recip_version1.0_#00000000` 부터 하나씩 늘어납니다. 뒤 8자리는 16진수입니다(11번째 수신자는 `#0000000A`). 명세로 확인했습니다 |
| 첨부 저장소 | `__attach_version1.0_#XXXXXXXX` (확인하지 못함) |
| 이름 붙은 속성 대응 저장소 | `__nameid_version1.0` (확인하지 못함) |
| 값 스트림 | `__substg1.0_` 뒤에 속성 ID 4자리와 형식 4자리 (확인하지 못함) |
| 포함된 메시지 저장소 | `__substg1.0_3701000D` (확인하지 못함) |

명세 2.2.1 절은 `.msg` 파일 하나에 수신자 저장소를 2048개까지 둘 수 있다고 적습니다. 첨부 수의 상한은 확인하지 못했습니다.

## 증거로서 의미

| 증명하는 것 | 증명하지 못하는 것 |
|---|---|
| 이 파일 안에 이 속성 값·수신자·첨부를 담은 메시지 한 통이 있습니다 | 이 PC 의 사용자가 그 메시지를 보냈거나 받았다는 것 |
| 수신자 저장소 수만큼 수신자가, 첨부 저장소 수만큼 첨부가 들어 있습니다 | 파일 안 값이 원래 메시지와 같다는 것. 파일을 고치면 속성 값도 바뀝니다 |
| 파일이 그 경로에 있었습니다(파일 시스템 기록) | 파일을 언제, 어떤 동작으로 만들었는지. 이 페이지의 구조에는 만든 동작을 알려 주는 칸이 없습니다 |

속성 값이 사실인지는 서버 기록, 상대방의 메일, PST 안의 같은 메시지와 맞춰 봅니다.

### 보고서 문장

아래 파일 이름과 값은 설명을 위해 만든 예입니다.

- 쓸 수 있는 문장: "`D:\자료\견적.msg` 는 OLE 복합 파일이며, 수신자 저장소 2개와 첨부 저장소 1개가 있습니다. 첨부 저장소 안에는 포함된 메시지 저장소가 있습니다."
- 쓰면 안 되는 문장: "사용자는 이 견적 메일을 두 사람에게 보내고, 받은 메일을 첨부해 전달했습니다."

## 시각 해석

- 메시지를 보내고 받은 시각은 파일 안의 속성 값입니다. 어떤 속성인지는 [MAPI 속성](../../../01-foundations/app-mail-data/mapi-property.md), 값을 바꾸는 법은 [시각 값 형식](../../../01-foundations/value-decoding/filetime-unix-webkit-dos-ole.md)에서 다룹니다.
- 파일 시스템 시각은 `.msg` 파일이 그 볼륨에 생기고 바뀐 시각입니다. 메시지를 보낸 시각이 아닙니다([마스터 파일 테이블](../../filesystem/mft.md)).
- 두 시각을 나란히 적으면 "언제 오간 메시지를 언제 파일로 두었는지" 를 따로 말할 수 있습니다. 복사한 파일이면 파일 시스템 시각은 복사한 때를 따를 수 있으므로 [USN 변경 저널](../../filesystem/usnjrnl.md)로 한 번 더 확인합니다.
- `.msg` 안의 시각 속성과 파일 시스템 시각이 어떻게 어긋나는지는 이번에 자료로 확인하지 못했습니다. 아래 실습으로 직접 비교해 봅니다.

## 함정과 한계

1. **저장소·스트림 수를 정해진 값으로 여깁니다.** 수는 메시지 종류와 수신자·첨부 수, 들어 있는 속성에 따라 다릅니다. 다른 `.msg` 와 수가 다르다고 손상이나 조작으로 보지 않습니다.
2. **스트림 수로 다중값 속성의 값 개수를 셉니다.** 길이가 바뀌는 다중값 속성은 값이 N개면 스트림이 N+1개입니다. 스트림 수를 그대로 값 개수로 쓰면 하나가 많습니다.
3. **포함된 메시지를 놓칩니다.** 첨부가 메시지이면 첨부 저장소 안에 메시지 한 통이 통째로 들어 있습니다. 도구가 안쪽 메시지의 수신자·첨부까지 풀어내는지 확인합니다.
4. **이름 붙은 속성을 번호만 보고 해석합니다.** 이름 붙은 속성은 대응 저장소를 거쳐야 무슨 속성인지 압니다. 대응 저장소를 읽지 않은 도구는 뜻 없는 번호만 보여 줄 수 있습니다.
5. **`.msg` 와 `.eml` 을 같은 방법으로 읽습니다.** `.eml` 은 글자 형식이고, `.msg` 는 복합 파일입니다. 글자 검색만으로 `.msg` 의 본문을 찾으면 유니코드 문자열을 놓칠 수 있습니다([파일 내용 검색](../../../03-techniques/analysis/content-search/index.md)).
6. **확인하지 못한 이름을 그대로 믿습니다.** 위 "저장소·스트림 이름" 표에서 수신자 저장소 말고는 명세 본문으로 확인하지 못했습니다. 검체의 실제 이름과 다르면 검체를 따릅니다.

## 직접 분석해 보기

### 원시 바이트로 한 번

`.msg` 를 헥스로 읽는 첫 단계는 복합 파일의 헤더와 디렉터리를 읽는 일입니다. 그 방법은 [OLE 복합 파일](../../../01-foundations/shell-document-formats/compound-file-binary.md)에서 따라갑니다. 디렉터리 항목을 모두 적었다면 아래 순서로 맞춰 봅니다.

1. 최상위에 속성 스트림이 정확히 1개 있는지 봅니다.
2. 이름 붙은 속성 대응 저장소가 정확히 1개 있는지 봅니다. 그 안에 GUID·Entry·String 스트림이 있는지 봅니다.
3. 수신자 저장소의 수를 셉니다. 이 수가 수신자 수입니다.
4. 첨부 저장소의 수를 셉니다. 이 수가 첨부 수입니다.
5. 첨부 저장소 안에 포함된 메시지 저장소가 있으면, 그 안에서 1~4번을 다시 합니다.
6. 1·2번이 맞지 않으면 명세와 다른 파일입니다. 손상, 다른 프로그램이 만든 파일, 조작을 모두 의심하고 원인을 따로 찾습니다.

아래는 명세의 규칙으로 만든 나무 구조 예시입니다. 실제 검체에서 뽑은 것이 아닙니다. 이름 대신 역할을 적었습니다.

```
(최상위: 메시지 한 통)
├─ 속성 스트림 ··························· 1개
├─ 이름 붙은 속성 대응 저장소 ················ 1개
│   ├─ GUID 스트림
│   ├─ Entry 스트림
│   └─ String 스트림
├─ 수신자 저장소 #1
├─ 수신자 저장소 #2
├─ 첨부 저장소 #1
│   └─ 포함된 메시지 저장소 ················ 첨부가 메시지일 때
│       └─ (안쪽 메시지의 속성 스트림, 수신자·첨부 저장소 …)
├─ 길이가 바뀌는 속성의 스트림 ·············· 속성마다 1개
└─ 길이가 바뀌는 다중값 속성의 스트림 ········ 값 N개면 N+1개
```

### 공개 도구로 한 번

복합 파일을 여는 공개 도구라면 저장소·스트림 목록을 볼 수 있습니다. 파이썬의 `olefile` 을 예로 들면 아래처럼 목록을 뽑습니다.

```python
import olefile, sys

ole = olefile.OleFileIO(sys.argv[1])
for path in ole.listdir(streams=True, storages=True):
    print("/".join(path))
```

- 뽑은 목록에서 위 1~6번을 맞춰 봅니다.
- 메일 전용 파서를 쓰면 속성 값을 읽기 좋게 보여 줍니다. 그 결과의 수신자·첨부 수가 위에서 센 수와 같은지 확인합니다.
- 포함된 메시지까지 풀어내는지, 이름 붙은 속성을 이름으로 보여 주는지 확인합니다. 방법은 [도구 결과 교차 검증](../../../03-techniques/reporting/tool-validation.md)을 봅니다.

## 실습

**직접 만든 가상 머신에 클래식 Outlook 을 깔고** 해 봅니다.

1. 수신자 둘, 첨부 하나인 메일을 `.msg` 로 저장합니다. 위 파이썬 코드로 목록을 뽑아 수신자·첨부 저장소를 세어 보십시오. 수가 맞습니까?
2. 다른 메일을 첨부한 메일을 저장해 보십시오. 첨부 저장소 안에 무엇이 생깁니까?
3. 저장 형식 선택지가 있으면 바꿔 가며 저장해 보십시오. 스트림 이름 가운데 어느 부분이 달라집니까? 위 "저장소·스트림 이름" 표와 맞습니까?
4. 같은 메일을 두 번 저장해 두 파일의 해시를 비교해 보십시오. 같습니까? 다르다면 어느 바이트가 다릅니까?
5. 저장한 `.msg` 를 메일 파서로 열어 보낸 시각 속성을 적고, 파일 시스템의 만든 시각·수정 시각과 비교해 보십시오. 파일을 다른 폴더로 복사하면 어느 시각이 바뀝니까?

**공개 검체(NIST CFReDS 등)** 가운데 `.msg` 가 든 이미지에서도 해 봅니다.

1. 확장자로 찾은 `.msg` 가운데 복합 파일이 아닌 것이 있습니까?
2. 파일마다 수신자·첨부 수를 표로 만들고, 메일 파서가 보여 주는 수와 비교해 보십시오.
