# 설치 날짜 가늠하기 (Install Date)

Linux 에는 "설치 날짜" 를 담은 값이 따로 없어서, 파일 시스템을 만든 시각·설치 프로그램 로그·첫 패키지 기록·machine-id 같은 흔적을 모아 설치 무렵을 가늠합니다.

## 무엇을 기록하나 · 왜 생기나

설치 프로그램은 디스크를 나누고 파일 시스템을 만든 뒤 패키지를 풀어 넣고, 마지막으로 자기 로그를 설치한 시스템 안에 복사합니다. 이 과정에서 시각이 남는 곳이 여럿 생깁니다. ext4 슈퍼블록에는 파일 시스템을 만든 시각이 들어가고[1], 파일마다 아이노드에 생성 시각이 붙습니다[2]. Ubuntu 설치 프로그램 subiquity 는 `/var/log/installer/` 를, RHEL 설치 프로그램 anaconda 는 `/var/log/anaconda/` 를 대상 시스템에 남깁니다[5][6]. 패키지 관리자는 설치 중에 넣은 패키지부터 기록을 쌓고, `/etc/machine-id` 는 설치 과정이나 첫 부팅 때 생깁니다[9].

이 흔적들은 서로 다른 순간을 가리킵니다. 파일 시스템 생성은 설치 초반이고, 로그 복사는 설치 막바지이며, machine-id 는 설치 중이거나 첫 부팅 때입니다. 그래서 한 값만 보고 "설치일" 이라고 쓰지 않고, 여러 값이 같은 날에 모이는지를 봅니다. 시스템이 언제부터 쓰였는지, 사건 무렵에 새로 설치한 시스템인지, 이미지를 복제해 만든 서버인지를 가릴 때 이 쪽을 씁니다.

## 위치와 버전별 차이

| 흔적 | Ubuntu 24.04 LTS | RHEL 9 |
|---|---|---|
| 파일 시스템 생성 시각 | 루트가 ext4 면 슈퍼블록 `s_mkfs_time`[1] | 루트 파일 시스템 종류를 검체에서 확인. ext4 면 같은 필드, XFS 면 [XFS](../../01-foundations/filesystem/xfs.md) 쪽의 구조로 본다 |
| 설치 프로그램 로그 | `/var/log/installer/` (subiquity)[5] | `/var/log/anaconda/` (anaconda)[6] |
| 설치 설정 | `/var/log/installer/autoinstall-user-data`[5] | `/root/anaconda-ks.cfg`, `/root/original-ks.cfg`[6] |
| 패키지 기록 | `/var/log/dpkg.log*`, `/var/log/apt/history.*`, `/var/lib/dpkg/info/*.list`[14] | rpm 데이터베이스 `rpmdb.sqlite`[17], dnf 기록 `/var/lib/dnf/history.sqlite`[16] |
| 첫 부팅 무렵 | `/etc/machine-id`[9], 저널·wtmp 의 첫 부팅 | 같음 |

설치 프로그램 두 가지의 파일 목록은 upstream 코드 기준이고, 설치 매체의 판에 따라 목록이 다를 수 있습니다. 패키지 기록의 형식과 전체 위치는 [dpkg·apt 기록](../packages/dpkg-apt.md) 과 [rpm·dnf·yum 기록](../packages/rpm-dnf.md) 에서 다룹니다.

## 구조

### ext4 파일 시스템 생성 시각

ext4 슈퍼블록은 볼륨 시작에서 1024바이트 뒤에 있습니다[1]. 슈퍼블록 안 오프셋 0x108 의 `s_mkfs_time` 은 파일 시스템을 만든 시각이고, 에포크 기준 초를 담은 4바이트 리틀 엔디언 값입니다[1]. 오프셋 0x276 의 `s_mkfs_time_hi` 는 이 값의 위쪽 8비트입니다[1]. 슈퍼블록의 나머지 필드는 [ext4](../../01-foundations/filesystem/ext4/index.md) 쪽에서 다룹니다.

파일 하나의 생성 시각은 아이노드의 `i_crtime`(오프셋 0x90, 에포크 기준 초)과 `i_crtime_extra`(0x94)에 들어갑니다[2]. `i_crtime_extra` 의 아래 2비트는 초 값을 34비트로 늘리는 데 쓰고, 위 30비트는 나노초입니다[2]. 이 필드는 아이노드 크기가 128바이트보다 클 때만 있고, ext4 의 기본 아이노드 레코드 크기는 256바이트입니다[2]. 일반 `stat()` 으로는 생성 시각이 보이지 않지만, debugfs 는 보여 주고[2] `statx()` 는 `stx_btime` 으로 돌려줍니다[3].

### Ubuntu: subiquity 로그

subiquity 는 로그 폴더를 `/var/log/installer/` 로 정해 두고[5], 설치가 끝날 무렵 다음 순서로 대상 시스템에 옮깁니다[5].

1. 설치 환경의 `/var/log/cloud-init.log`, `/var/log/cloud-init-output.log` 가 있으면 `cp -a` 로 설치 환경의 `/var/log/installer` 에 넣습니다.
2. 설치 환경의 `/var/log/installer/` 전체를 `rsync -a` 로 대상 시스템의 `var/log/installer` 에 복사하고, 폴더 권한을 0770, 그룹을 adm 으로 맞춥니다.
3. 설치 환경의 `journalctl -b` 출력을 대상 폴더의 `installer-journal.txt` 로 새로 씁니다.

이 폴더에는 curtin 설치 로그 `curtin-install.log`, curtin 설정 폴더 `curtin-install/`, 장치 배치 `device-map.json` 류, 설치에 쓴 설정을 모은 `autoinstall-user-data` 가 들어갑니다[5]. `autoinstall-user-data` 는 비밀번호 해시가 들어 있어서 subiquity 가 모드 0400, 그룹 root 로 씁니다[5].

### RHEL: anaconda 로그

anaconda 는 설치 환경 `/tmp` 의 `anaconda.log`, `syslog`, `X.log`, `program.log`, `packaging.log`, `storage.log`, `ifcfg.log`, `lvm.log`, `dnf.librepo.log`, `hawkey.log`, `dbus.log` 를 `/var/log/anaconda/` 로 복사합니다[6]. 설치 매체 패키지 목록 `lorax-packages.log`, 킥스타트 스크립트 로그 `ks-script*.log`, 설치 환경의 `journalctl -b` 출력인 `journal.log` 도 같은 폴더로 가고, 복사한 파일은 모두 모드 0600 이 됩니다[6]. 설치 설정을 다시 만든 킥스타트는 `/root/anaconda-ks.cfg` 이고 첫 줄이 `# Generated by Anaconda` 뒤에 판 번호가 붙은 모양입니다[6]. 입력으로 받은 킥스타트는 `/root/original-ks.cfg` 로 복사합니다[6]. `nosave` 옵션을 쓰면 로그나 킥스타트를 남기지 않습니다[6].

anaconda 는 파일을 `shutil.copyfile` 로 복사합니다[6]. 이 함수는 내용만 복사하고 메타데이터는 옮기지 않으므로[7], 복사본의 시각은 원래 로그를 쓴 시각이 아니라 설치 막바지에 복사한 시각입니다.

### machine-id

`/etc/machine-id` 는 128비트 값을 16진 문자열로 담은 파일이고, 보통 설치나 첫 부팅 때 난수로 만든 뒤 바뀌지 않습니다[9]. 여러 대에 쓰는 이미지(컨테이너·클라우드)는 이 파일을 비워 두거나 빼 두고, 부팅할 때 값을 만들어 파일에 씁니다[9]. 파일이 없거나 `uninitialized` 가 들어 있으면 systemd 는 그 부팅을 첫 부팅으로 봅니다[9].

### os-release 의 BUILD_ID

`/etc/os-release` 의 `BUILD_ID=` 는 설치 기반이 된 시스템 이미지를 가리키는 문자열입니다[12]. 값이 `BUILD_ID="2013-03-20.3"` 처럼 날짜 모양일 수 있지만 이미지를 만든 쪽의 식별자라서 이 시스템을 설치한 날이 아닙니다[12]. 필드 전체는 [배포판과 버전](os-release.md) 쪽에 있습니다.

## 증거로서 의미

### 증명하는 것

- `s_mkfs_time` 은 이 볼륨에 파일 시스템을 만든 시각입니다[1]. 설치 프로그램으로 새로 나눈 디스크라면 설치 시작 무렵과 가깝습니다.
- 설치 프로그램 로그 폴더가 있으면 이 시스템을 그 설치 프로그램으로 설치했다는 뜻이고, 로그 안의 시각 줄이 설치 과정의 순서를 보여 줍니다.
- `installer-journal.txt`(subiquity)와 anaconda 가 복사한 파일은 설치 막바지에 대상 시스템에 새로 생긴 파일이라서, 이 파일들의 생성 시각은 설치가 끝나 가던 시점을 가리킵니다[5][6].
- dpkg.log 나 dnf 기록의 가장 이른 줄은 남아 있는 기록 가운데 가장 이른 패키지 작업입니다.

### 증명하지 못하는 것

- 하나로 확정된 설치 날짜를 증명하지 못합니다. 흔적마다 가리키는 순간이 다릅니다.
- 이미지를 복제한 가상 머신이나 클라우드 템플릿에서는 `s_mkfs_time` 이 템플릿을 만든 날일 수 있습니다. 이 값은 mkfs 를 실행한 시각이지 이 기계가 처음 켜진 시각이 아닙니다[1].
- 이미지에서 만든 시스템의 machine-id 는 설치 때가 아니라 그 인스턴스가 처음 부팅할 때 만든 값입니다[9]. 이미지에 빈 `/etc/machine-id` 를 넣어 두는 방식이면 파일의 생성 시각은 이미지를 만든 때일 가능성이 있습니다.
- 누가 설치했는지는 이 흔적들만으로 알 수 없습니다.

## 시각 해석

| 값 | 기준 | 바뀌는 때 |
|---|---|---|
| `s_mkfs_time` | 에포크 기준 초, UTC[1] | mkfs 를 실행할 때 |
| 아이노드 crtime | 에포크 기준 초 + 나노초, UTC[2] | 아이노드를 새로 만들 때. 파일을 새 이름으로 복사하면 복사한 때 |
| dpkg.log 줄 시각 | 시간대 표시 없는 현지 시각[13] | 패키지 작업 때 |
| apt `Start-Date:` | 시간대 표시 없는 현지 시각. dissect 는 대상 시스템 시간대로 해석[14] | apt 명령을 실행할 때 |
| yum.log 줄 시각 | 연도 없는 현지 시각. dissect 는 파일 시각으로 연도를 채움[14] | 패키지 작업 때 |
| rpm `INSTALLTIME` | 패키지 설치 시각[15]. 수집 결과에서 값 모양을 확인하고 사람이 읽는 시각으로 바꿔 다른 기록과 맞춰 본다 | 그 패키지를 설치할 때 |

현지 시각 기록을 UTC 로 옮길 때는 [호스트 이름·시간대·로캘](hostname-timezone.md) 쪽에서 구한 시간대를 씁니다. 에포크 값을 읽는 법은 [Linux 의 시각 값](../../01-foundations/value-decoding/time-values.md) 에 있습니다.

로그 파일을 복사한 방식에 따라 파일 시각의 뜻이 달라집니다. subiquity 가 cloud-init 로그를 옮길 때 쓰는 `cp -a` 는 원본의 접근 시각과 수정 시각을 되도록 보존합니다[8]. 하지만 이 파일들도 대상 시스템으로는 `rsync -a` 로 한 번 더 옮기므로[5], 대상 시스템에 있는 파일의 수정 시각이 원래 로그의 시각인지는 검체에서 파일의 수정 시각과 로그 안 마지막 줄 시각을 맞춰 보고 판단합니다. anaconda 가 `shutil.copyfile` 로 옮긴 파일은 수정 시각과 생성 시각 모두 복사한 때입니다[6][7].

## 함정과 한계

- 설치 때 시계가 틀려 있었으면 설치 로그·패키지 기록·파일 시각이 모두 같은 방향으로 어긋납니다. 저널의 첫 시계 동기화 메시지([부팅과 종료 기록](boot-shutdown.md))나 원격 로그처럼 바깥 기준과 한 번 대조합니다.
- 옛 dpkg.log 와 yum.log 는 로그 순환으로 지워졌을 수 있어서, 남은 파일의 첫 줄이 설치 때 줄이라는 보장이 없습니다([로그 순환](../../01-foundations/logging/logrotate.md)).
- dissect 는 dpkg 패키지의 설치 시각으로 `/var/lib/dpkg/info/패키지.list`(또는 `패키지:아키.list`)의 수정 시각을 그대로 씁니다[14]. 패키지를 다시 설치하거나 올리면 이 파일이 바뀔 가능성이 있으니 dpkg.log 줄과 대조합니다.
- 설치 로그 폴더는 지우기 쉽지만, 슈퍼블록과 패키지 기록까지 함께 맞춰 지우기는 어렵습니다. 한 흔적이 비어 있으면 나머지와 대조합니다.
- ext4 아이노드 생성 시각은 아이노드 크기가 128바이트인 파일 시스템에는 없습니다[2].
- 백업에서 되살렸거나 다른 디스크로 옮긴 시스템은 `s_mkfs_time` 과 파일 생성 시각이 옮긴 날로 바뀌어 있을 수 있습니다. 이때는 패키지 기록 안의 시각이 더 오래된 날을 가리킬 가능성이 있습니다.
- `autoinstall-user-data` 에는 비밀번호 해시가 들어 있으므로[5], 보고서에 원문을 그대로 옮기지 않습니다.
- `journalctl --list-boots` 는 남아 있는 저널 안의 부팅만 보여 주고[10], `last reboot` 는 wtmp 파일이 생긴 뒤의 부팅만 보여 줍니다[11]. 옛 저널이나 wtmp 가 지워졌으면 첫 부팅 기록이 남지 않으므로, 가장 이른 부팅이 늦다고 해서 시스템이 새것이라는 뜻은 아닙니다.

## 직접 분석해 보기

### 헥스로 한 번: s_mkfs_time

슈퍼블록이 볼륨 시작 +0x400 에 있으므로 `s_mkfs_time` 은 볼륨 시작에서 0x400 + 0x108 = 0x508 에 있습니다[1]. 아래는 명세로 만든 예시이고, 관계없는 바이트는 `..` 로 줄였습니다.

```
오프셋    00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F
00000500  .. .. .. .. .. .. .. .. 34 12 50 66 .. .. .. ..
```

0x508 부터 네 바이트 `34 12 50 66` 을 리틀 엔디언으로 읽으면 0x66501234 = 1716523572 이고, UTC 로 2024-05-24 04:06:12 입니다. 같은 볼륨의 0x676(0x400 + 0x276)에 있는 `s_mkfs_time_hi` 가 0 이 아니면 위쪽 8비트로 붙여 계산합니다[1]. 볼륨 이미지에서 이 네 바이트만 보려면 다음처럼 합니다.

```
xxd -s 0x508 -l 4 volume.img
date -u -d @1716523572
```

### 공개 도구로 한 번

- The Sleuth Kit 의 `fsstat` 은 ext4 에서 마지막 기록·점검·마운트 시각을 보여 주지만 파일 시스템 생성 시각 줄은 내지 않습니다[4]. 이 값은 위처럼 헥스로 읽습니다.
- `istat` 은 아이노드의 생성 시각을 `File Created:` 줄로 보여 줍니다[4]. `/etc/machine-id`, `/var/log/installer/installer-journal.txt`, `/var/log/anaconda/journal.log` 의 아이노드를 차례로 보면 첫 부팅과 설치 막바지 시각을 나란히 놓을 수 있습니다.
- dissect.target 의 messages 플러그인은 `/var/log/installer/` 안의 `syslog*`, `messages*`, `cloud-init.log*` 도 읽습니다[18]. 패키지 플러그인은 dpkg·apt·yum 기록을 대상 시스템 시간대로 해석합니다[14].
- plaso 의 dpkg 파서는 `2016-08-03 15:25:53 install base-passwd:amd64 <none> 3.5.33` 같은 줄을 현지 시각으로 읽습니다[13].
- rpm·dnf 가 있는 살아 있는 시스템에서는 UAC 가 `rpm -q -a --queryformat '%{INSTALLTIME}~%{NAME}~%{VERSION}-%{RELEASE}\n'`, `dnf history list` 를 받아 둡니다[15]. INSTALLTIME 이 가장 이른 패키지 묶음이 설치 때 들어간 패키지일 가능성이 있습니다.

## 실습

NIST CFReDS 같은 공개 저장소의 Linux 디스크 이미지로 다음을 풀어 봅니다.

1. 루트 볼륨 `s_mkfs_time` 은 UTC 로 언제인가?
2. 설치 프로그램 로그 폴더가 `/var/log/installer/` 와 `/var/log/anaconda/` 가운데 어디에 있는가? 그 안 가장 늦은 파일의 생성 시각은 언제인가?
3. dpkg.log 또는 dnf 기록의 가장 이른 줄은 언제이고, 1번 값과 몇 시간 차이 나는가?
4. `/etc/machine-id` 의 생성 시각은 설치 로그 복사 시각의 앞인가 뒤인가? 뒤라면 첫 부팅 때 만든 값일 가능성을 따져 본다.
5. 세 값이 서로 며칠 이상 벌어진다면 이미지 복제·복원·시계 오류 가운데 어느 설명이 맞는가?
