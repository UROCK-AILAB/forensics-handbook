# cron·anacron·at (cron)

cron 은 정해진 주기로, anacron 은 꺼져 있던 동안 놓친 하루·한 주·한 달 단위 작업을, at 은 한 번만 정해진 시각에 명령을 실행하며, 셋 모두 설정을 평범한 텍스트 파일로 남깁니다.

## 무엇을 기록하나 · 왜 생기나

예약 작업 (scheduled job) 은 관리자가 백업·로그 정리 같은 일을 맡기려고 만들고, 침입자는 재부팅 뒤에도 명령이 다시 돌게 하려고 만듭니다. 어느 쪽이든 "무엇을, 언제, 어느 계정으로" 돌릴지가 파일에 적히고[1][3][4], cron 은 잡을 시작할 때마다 syslog 로 한 줄을 남깁니다[1][3].

설정이 들어가는 길은 두 가지입니다. `crontab` 명령으로 사용자 crontab 을 설치하면 명령이 spool 디렉터리에 파일을 쓰고 로그를 남깁니다[1][3]. 반대로 `/etc/crontab`, `/etc/cron.d/` 같은 시스템 파일은 편집기로 직접 고치며, 데몬이 바뀐 것을 알아서 다시 읽습니다[1][2]. 그래서 같은 예약 작업이라도 어느 파일에 들어 있느냐에 따라 남는 흔적이 다릅니다.

Ubuntu 24.04 는 Debian 의 cron(vixie cron 3.0pl1 계열, 패키지 `3.0pl1-184ubuntu2`)을 쓰고[2], RHEL 9 는 cronie 를 씁니다[3]. at 은 두 배포판 모두 같은 원본 at 을 씁니다[4][5].

## 위치와 버전별 차이

| 항목 | Ubuntu 24.04 (Debian cron) | RHEL 9 (cronie) |
|---|---|---|
| 사용자 crontab | `/var/spool/cron/crontabs/사용자이름`[1] | `/var/spool/cron/사용자이름`[3] |
| 시스템 crontab | `/etc/crontab`. hourly·daily·weekly·monthly 네 줄이 기본으로 들어 있음[2] | `/etc/crontab`. 기본으로 비어 있음[3] |
| 조각 파일 | `/etc/cron.d/*`[1] | `/etc/cron.d/*`. 기본 파일 `0hourly`[3] |
| 주기 디렉터리 | `/etc/cron.{hourly,daily,weekly,monthly}`. `/etc/crontab` 이 `run-parts` 로 부름[2] | `/etc/cron.hourly` 는 `0hourly` 가 매시 01분에 부름. daily·weekly·monthly 는 anacron 이 부름[3] |
| 허용·거부 목록 | `/etc/cron.allow`, `/etc/cron.deny`[1] | 같음[9] |
| anacron 설정 | `/etc/anacrontab` (anacron 패키지가 있을 때) | `/etc/anacrontab`[3] |
| anacron 시각 파일 | `/var/spool/anacron/잡이름` | 같음[3] |
| at 잡 | 빌드 때 정함. `/var/spool/cron` 이 있으면 `/var/spool/cron/atjobs`, 출력은 `/var/spool/cron/atspool`[4] | `/var/spool/at`, 출력은 `/var/spool/at/spool`, 잡 번호 파일 `/var/spool/at/.SEQ`[5] |
| at 허용·거부 목록 | `/etc/at.allow`, `/etc/at.deny`[9] | 같음. `/etc/at.deny` 가 기본 설치됨[5] |
| cron 로그 | `/var/log/syslog`. 기본 설정의 `#cron.* /var/log/cron.log` 가 주석 처리돼 있음[6] | `/var/log/cron`. `/var/log/messages` 에는 `cron.none` 으로 빠짐[7] |

Ubuntu 의 at spool 위치는 at 을 빌드할 때 configure 가 정하므로[4], 실제 시스템에서 `/var/spool/cron/atjobs` 와 `/var/spool/at` 을 둘 다 봅니다.

Ubuntu `/etc/crontab` 의 daily·weekly·monthly 줄은 `test -x /usr/sbin/anacron ||` 로 시작하므로, anacron 이 설치돼 있으면 cron 은 이 세 줄을 건너뛰고 anacron 이 대신 돌립니다[2]. RHEL 9 에서는 매시 도는 `/etc/cron.hourly/0anacron` 이 `/var/spool/anacron/cron.daily` 의 날짜가 오늘이 아닐 때 anacron 을 부르고[3], 이 파일이 없을 때만 cronie 의 `dailyjobs` 가 run-parts 로 돌립니다[3].

두 cron 모두 저널에도 같은 메시지를 남기고, Ubuntu 의 `cron.service` 는 `SyslogFacility=cron` 입니다[2]. 저널 쪽 읽는 법은 [systemd 저널](../../01-foundations/logging/systemd-journal/index.md)을, syslog 파일의 줄 모양은 [syslog 형식과 rsyslog](../../01-foundations/logging/syslog-rsyslog.md)를 봅니다. systemd 타이머는 [systemd 서비스와 타이머](systemd-units.md)에서 따로 다룹니다.

## 구조

### crontab 한 줄

한 줄은 분·시·일·월·요일의 다섯 필드와 명령으로 이뤄집니다[1][3]. `/etc/crontab` 과 `/etc/cron.d/` 의 파일에는 요일과 명령 사이에 실행할 사용자 이름 필드가 하나 더 있고, 사용자 crontab 에는 이 필드가 없습니다[1][2]. 다섯 필드 대신 `@reboot`, `@yearly`, `@annually`, `@monthly`, `@weekly`, `@daily`, `@hourly` 를 쓸 수 있고, Debian cron 은 `@midnight` 도 받습니다[1][3]. `@reboot` 는 컴퓨터가 켜진 때가 아니라 cron 데몬이 시작한 때 한 번 돕니다[1].

명령 필드의 `%` 는 줄바꿈으로 바뀌고, 첫 `%` 뒤의 내용은 명령의 표준 입력으로 들어갑니다[1][3]. `SHELL=`, `PATH=`, `MAILTO=` 같은 환경 변수 줄도 둘 수 있고, cronie 는 표 하나의 시간대를 정하는 `CRON_TZ`, 무작위 지연 `RANDOM_DELAY`, 보내는 사람 `MAILFROM` 도 받습니다[1][3].

```
# /etc/cron.d/example (만든 예시)
SHELL=/bin/sh
*/10 * * * * root /usr/local/bin/sync-example.sh
@reboot      user1 /home/user1/.local/bin/agent-example
```

### Debian 사용자 crontab 의 머리 세 줄

Debian cron 의 `crontab` 명령은 사용자 crontab 을 설치할 때 파일 맨 위에 세 줄을 씁니다[1].

```
# DO NOT EDIT THIS FILE - edit the master and reinstall.
# (/tmp/crontab.Ab12Cd/crontab installed on Fri Jan  2 03:04:05 2026)
# (Cron version -- ...)
```

위 세 줄은 만든 예시입니다. 둘째 줄의 경로는 설치에 쓴 원본 파일입니다[1]. `crontab 파일이름` 으로 설치했으면 그 파일 경로가, `crontab -e` 로 편집했으면 `$TMPDIR`(없으면 `/tmp`) 아래 `crontab.XXXXXX/crontab` 임시 경로가 들어갑니다[1]. 시각은 `ctime()` 형식의 현지 시각입니다[1]. `crontab -l` 은 이 세 줄을 기본으로 숨기고, `CRONTAB_NOHEADER=N` 이면 보여 줍니다[1][2]. cronie 는 이 머리를 쓰는 코드가 주석 처리돼 있어 RHEL 9 의 사용자 crontab 에는 머리가 없습니다[3].

### anacrontab 과 시각 파일

anacrontab 한 줄은 `주기(일) 지연(분) 잡이름 명령` 이고, 주기 자리에 `@monthly` 같은 이름을 쓸 수 있습니다[3]. `START_HOURS_RANGE` 는 잡을 시작할 수 있는 시간대를, `RANDOM_DELAY` 는 지연에 더할 최대 무작위 분을 정합니다[3]. cronie 의 기본 `/etc/anacrontab` 은 `1 5 cron.daily nice run-parts /etc/cron.daily` 처럼 세 잡을 둡니다[3].

anacron 은 잡마다 `/var/spool/anacron/잡이름` 시각 파일을 두고, 내용은 `YYYYMMDD` 와 줄바꿈으로 된 9바이트입니다[3]. 날짜는 anacron 이 시작한 날의 현지 날짜이고, 파일은 잡이 끝났을 때 씁니다[3]. `anacron -u` 는 잡을 돌리지 않고 날짜만 오늘로 바꿉니다[3]. anacron 은 시각 파일을 지우지 않으므로 지금 설정에 없는 잡이름의 파일이 남아 있을 수 있습니다[3].

### at 잡 파일

at 잡 파일 이름은 `%c%5lx%8lx` 형식이고 빈칸은 `0` 으로 채웁니다[4]. 첫 글자는 큐 문자, 다음 5자리는 잡 번호(16진), 마지막 8자리는 실행 예정 시각을 Unix epoch 분(초 ÷ 60)으로 적은 16진 값입니다[4]. 잡 번호는 spool 의 `.SEQ` 파일에 `%05lx` 로 저장됩니다[4].

파일 내용은 셸 스크립트입니다. 첫 줄은 `#!/bin/sh`, 이어서 `# atrun uid=숫자 gid=숫자`, `# mail 사용자이름 0또는1`, `umask 8진수` 가 오고, 그 뒤에 제출할 때의 환경 변수 export, `cd 제출디렉터리`, 사용자가 입력한 명령이 차례로 들어갑니다[4]. at 은 제출한 사용자의 uid 로 잡 파일을 만들고, 내용을 다 쓴 뒤에야 소유자 실행 비트를 켭니다[4]. atd 는 실행 비트가 없는 파일을 아직 쓰는 중으로 보고 건너뜁니다[4].

실행할 때 atd 는 이름 첫 글자를 `=` 로 바꾼 하드 링크를 만들어 잠그고, 실행을 확정하면 원래 잡 파일을 unlink 합니다[4]. 파일 소유자와 `# atrun uid=` 값이 다르면 실행하지 않습니다[4]. 출력은 at spool 출력 디렉터리의 파일에 모으고, 잡이 끝나면 출력 파일과 `=` 잠금 파일을 지운 뒤 출력이 있거나 메일을 요청했으면 메일로 보냅니다[4].

### 로그 줄

두 cron 모두 syslog 의 cron facility 로 `(사용자) 이벤트 (내용)` 모양의 메시지를 남깁니다[1][3]. 잡을 돌리는 자식 프로세스는 프로그램 이름을 대문자로 바꾸므로 잡 실행 줄의 태그는 Debian cron 이 `CRON`, cronie 가 `CROND` 입니다[1][3].

```
CRON[23456]: (root) CMD (cd / && run-parts --report /etc/cron.hourly)
CROND[23456]: (user1) CMD (/home/user1/bin/job-example.sh)
crontab[23457]: (user1) REPLACE (user1)
```

(만든 예시, syslog 줄 머리의 시각·호스트 이름은 뺐음)

| 이벤트 | 남기는 쪽 | 뜻 |
|---|---|---|
| `CMD` | 두 cron | 잡 시작. 괄호 안은 명령 문자열[1][3] |
| `CMDOUT`, `CMDEND` | cronie | 잡 출력(`-s` 옵션 등), 잡 끝[3] |
| `LIST`, `DELETE`, `BEGIN EDIT`, `END EDIT`, `REPLACE` | `crontab` 명령 | 목록 보기, 지우기, 편집 시작·끝, 설치. 앞 괄호는 명령을 쓴 실제 사용자, 뒤 괄호는 대상 사용자[1][3] |
| `AUTH` | `crontab` 명령 | 허용·거부 목록 때문에 거부됨[1][3] |
| `RELOAD` | cronie | 바뀐 crontab 을 다시 읽음[3] |
| `BAD FILE MODE`, `WRONG FILE OWNER`, `NOT REGULAR`, `BAD LINK COUNT`, `ORPHAN` | cronie | 권한·소유자·파일 종류가 틀렸거나 계정이 없어 crontab 을 읽지 않음[3] |

Debian cron 은 `-L` 값으로 무엇을 남길지 정하고 기본값 1 은 잡 시작만 남깁니다(2 끝, 4 실패, 8 PID)[1]. Ubuntu 의 `cron.service` 는 `/usr/sbin/cron -f -P $EXTRA_OPTS` 로 실행하므로[2], 옵션을 바꿨는지는 `cron.service` 드롭인과 `/etc/default/cron` 을 봅니다.

anacron 은 cron facility 로 정보는 notice, 오류는 error 수준으로 남기고[3], `Anacron started on 2026-01-02`, ``Will run job `cron.daily' in 5 min.``, ``Job `cron.daily' started``, ``Job `cron.daily' terminated``, `Normal exit (1 job run)` 같은 문구를 씁니다(날짜·잡이름은 만든 예시)[3]. atd 는 `atd` 이름으로 cron facility 에 남기지만, 잡이 끝났을 때의 `pid ... exited with status ...` 줄은 디버그 빌드에서만 나옵니다[4]. 그래서 at 잡이 돌았는지는 atd 로그보다 spool 파일과 다른 흔적으로 봅니다.

cron 잡은 PAM 세션을 열기도 하므로, 같은 시각에 인증 로그에 `session opened for user root(uid=0) by ...` 같은 pam_unix 줄이 남을 수 있습니다[1][8]. 이 줄의 해석은 [인증 로그](../logins/auth-log.md)를 봅니다.

## 증거로서 의미

**증명하는 것**

- 설정 파일에 명령·주기·실행 계정이 적혀 있었다는 것. 사용자 crontab 은 파일 이름이, 시스템 crontab 은 사용자 필드가 실행 계정입니다[1][3].
- `CMD` 줄이 있으면 그 시각에 cron 이 그 계정으로 그 명령 문자열을 시작했다는 것[1][3].
- `REPLACE`·`END EDIT` 줄이 있으면 그 시각에 어느 사용자가 `crontab` 명령으로 누구의 crontab 을 바꿨다는 것[1][3].
- Debian 머리 세 줄이 있으면 `crontab` 명령으로 설치했고, 설치 원본 경로와 설치 시각(현지)이 무엇이었는지[1].
- at 잡 파일이 남아 있으면 실행 예정 시각, 제출한 uid·gid, 제출할 때의 작업 디렉터리와 환경 변수[4].
- anacron 시각 파일이 있으면 그 잡이 마지막으로 끝까지 돈 날(현지 날짜). 다만 `anacron -u` 로 돌리지 않고 날짜만 바꿨을 수도 있습니다[3].

**증명하지 못하는 것**

- 명령이 성공했는지. Debian cron 기본 설정은 시작만 남깁니다[1].
- 누가 파일을 편집했는지. 시스템 crontab 이나 spool 파일을 편집기로 직접 고치면 `crontab` 명령의 로그가 없고, root 는 어느 파일이든 고칠 수 있습니다.
- 머리 세 줄이 진짜인지. 텍스트라 누구나 써 넣을 수 있습니다.
- 이미 실행된 at 잡의 내용. 실행이 확정되면 잡 파일이 지워집니다[4].
- 파일에 있다고 실행됐는지. 아래 함정처럼 이름·권한 규칙에 걸려 읽히지 않은 파일일 수 있습니다[1][3].

보고서에는 "`/var/spool/cron/crontabs/user1` 에 10분마다 `/home/user1/bin/job-example.sh` 를 실행하는 줄이 있고, syslog 에 2026-01-02 03:10 부터 user1 계정의 CMD 기록이 있다"처럼 기록으로 확인되는 만큼만 씁니다(만든 예시).

## 시각 해석

| 값 | 무엇이 바뀔 때 바뀌나 | 시간대 |
|---|---|---|
| crontab 의 시각 필드 | 설정 값 | 데몬의 현지 시간대. Debian cron 은 `/etc/timezone` 을 쓰고 한 시간대만 다룸[1]. cronie 는 `CRON_TZ` 로 표마다 바꿀 수 있음[3] |
| cron 로그 줄 | 이벤트가 생길 때 | cronie 는 로그 시각을 데몬의 현지 시간대로 적음[3]. syslog 전통 형식이면 연도·시간대가 없음 |
| Debian 머리 `installed on` | `crontab` 으로 설치할 때 | 현지 시각, 연도 있음, 시간대 표기 없음[1] |
| at 파일 이름 끝 8자리 | 제출할 때 정함 | UTC epoch 분[4] |
| anacron 시각 파일 내용 | 잡이 끝날 때 씀 | anacron 이 시작한 날의 현지 날짜, 시·분 없음[3] |
| anacron 시각 파일 mtime | 잡이 끝날 때, `anacron -u` 를 돌릴 때[3] | 파일 시스템 시각 |
| spool 디렉터리 mtime | `crontab` 명령이 crontab 을 바꿀 때마다 갱신[1][3] | 파일 시스템 시각 |

서머타임처럼 시계가 3시간 미만 움직이면 Debian cron 은 시·분을 정해 둔 잡에 한해 앞으로 건너뛴 시각의 잡을 곧바로 돌리고, 뒤로 되돌아가 반복된 시각의 잡은 다시 돌리지 않습니다[1]. 시·분에 `*` 가 든 잡은 새 시각을 바로 따르고, 3시간 넘게 움직이면 모든 잡이 새 시각을 바로 따릅니다[1]. 로그 시각을 UTC 로 바꾸려면 [호스트 이름·시간대·로캘](../system-info/hostname-timezone.md)에서 시간대를 먼저 확인하고, mtime·ctime 같은 파일 시각은 [Linux 의 시각 값](../../01-foundations/value-decoding/time-values.md)을 봅니다.

## 함정과 한계

- **로그가 없다고 바뀌지 않은 것이 아님.** `LIST`·`REPLACE` 같은 이벤트는 `crontab` 명령만 남깁니다[1][3]. `/etc/crontab`, `/etc/cron.d/`, spool 파일을 직접 고치면 이 줄이 없으므로 파일 시각과 [셸 명령 기록](../execution/shell-history/index.md)을 봅니다.
- **Debian 에서 점이 든 이름은 무시됨.** `/etc/cron.d/` 와 `/etc/cron.{hourly,…}` 의 파일 이름은 영문자·숫자·`_`·`-` 만 쓸 수 있고, `backup.sh` 처럼 점이 든 파일은 실행되지 않습니다[1]. `/etc/cron.{hourly,…}` 의 파일은 실행 권한이 있고 root 소유이며 그룹·기타 쓰기 권한이 없어야 합니다[1]. 이 규칙은 Debian cron 의 것이라 RHEL 9 에 그대로 옮겨 적용하지 않습니다.
- **권한이 틀린 crontab.** Debian cron 은 `/etc/crontab` 과 `/etc/cron.d/` 파일이 root 소유이고 그룹·기타 쓰기 권한이 없기를 요구합니다[1]. cronie 는 crontab 이 일반 파일이나 일반 파일을 가리키는 심볼릭 링크가 아니거나, 소유자 말고 다른 사람에게 쓰기·실행 권한이 있으면 읽지 않고 `BAD FILE MODE` 같은 줄만 남깁니다(`-p` 옵션이면 검사하지 않음)[3]. 권한 비트 읽는 법은 [권한·확장 속성·ACL·Capabilities](../../01-foundations/filesystem/permissions-xattr.md)를 봅니다.
- **로그를 남기지 않는 줄.** cronie 에서 root 소유 crontab 의 줄이 `-` 로 시작하면 그 잡의 `CMD` 줄을 남기지 않습니다[3]. 로그에 없는 잡은 설정 파일에서 찾습니다.
- **anacron 쪽으로 옮겨 간 daily 잡.** anacron 이 있으면 cron.daily 스크립트의 실행 흔적은 `CMD` 줄이 아니라 anacron 로그와 시각 파일에 남습니다[2][3].
- **심볼릭 링크 crontab.** cronie 가 inotify 로 변경을 감시할 때는 심볼릭 링크로 된 crontab 의 변경을 알아채지 못해 SIGHUP 을 받아야 다시 읽습니다[3]. 파일 내용과 실제로 돈 명령이 다를 수 있습니다.
- **수집 정의의 빈틈.** ForensicArtifacts `LinuxCronLogs` 는 `/var/log/cron.log*` 만 정의하므로 RHEL 의 `/var/log/cron` 과 Ubuntu 의 `/var/log/syslog` 는 다른 정의로 모아야 합니다[9]. `LinuxAtJobs` 는 `/var/spool/at/*` 만 정의하고, Ubuntu 의 `/var/spool/cron/atjobs` 는 `LinuxCronTabs` 의 `/var/spool/cron/**` 로만 잡힙니다[9]. UAC 의 `job_scheduler.yaml` 은 `/var/spool/cron`, `/var/spool/anacron`, `/var/spool/at` 을 통째로 모으고, `/etc/crontab`·`/etc/cron.d` 는 이 정의에 없습니다[10].
- **파서가 필드를 잘못 나누는 경우.** Velociraptor `Linux.Sys.Crontab` 의 정규식은 모든 줄에 사용자 필드가 있다고 보므로, 사용자 crontab 줄은 명령의 첫 단어가 `User` 필드로 갑니다[11]. dissect.target `cronjobs` 는 `/etc/anacrontab` 도 다섯 필드 정규식으로 읽어 필드가 밀리고, 명령의 첫 단어가 실제 계정 이름이면 그 계정으로 추정하므로 계정이 잘못 붙을 수 있습니다[12]. 같은 정규식이라 `@reboot` 줄은 맞지 않아 경고로 빠지거나 필드가 밀린 레코드로 나올 수 있습니다[12]. dissect 는 at 잡과 anacron 시각 파일을 읽지 않습니다[12].

## 직접 분석해 보기

### 헥스로 한 번

at 잡 파일 이름 `a0000301c17418` 을 풀어 봅니다(명세로 만든 예시).

1. 첫 글자 `a` 는 큐 문자입니다[4].
2. 다음 5자리 `00003` 은 잡 번호 3 입니다[4].
3. 마지막 8자리 `01c17418` 은 16진수 29455384 이고, 60 을 곱하면 epoch 1767323040 초, 곧 2026-01-02 03:04:00 UTC 가 실행 예정 시각입니다[4].
4. 파일 소유자가 제출한 사용자이고, 첫 줄들의 `# atrun uid=… gid=…` 와 맞는지 봅니다[4].

anacron 시각 파일 `/var/spool/anacron/cron.daily` 의 내용입니다(명세로 만든 예시).

```
000000 32 30 32 36 30 31 30 32 0a                       >20260102.<
```

9바이트가 `YYYYMMDD` 와 줄바꿈이면 형식이 맞고, 2026-01-02(현지)에 시작한 anacron 이 cron.daily 를 끝낸 기록입니다[3]. 같은 파일의 mtime 은 잡이 끝난 시각이라 날짜가 하루 넘게 어긋나면 손으로 고친 흔적일 가능성이 있습니다.

### 공개 도구로 한 번

- **dissect.target `cronjobs`**: `/var/spool/cron`, `/var/spool/cron/crontabs`, `/etc/cron.d` 의 파일과 `/etc/crontab`, `/etc/anacrontab` 을 읽어 `minute`·`hour`·`day`·`month`·`weekday`·`command`·`source` 레코드와 환경 변수 레코드를 냅니다[12]. 위 함정의 필드 밀림을 알고 봅니다.
- **Velociraptor `Linux.Sys.Crontab`**: `CronTabs`(줄 파싱), `CronScripts`(`/etc/cron.{hourly,…}/*` 의 수정 시각과 내용), `Uploaded`(원본 수집) 세 소스를 냅니다[11].
- **라이브 시스템**: `atq` 는 at spool 의 파일 이름을 풀어 잡 번호, 탭, 실행 예정 시각(현지 시각), 큐 문자, 파일 소유자 순으로 찍습니다[4]. Debian 의 `crontab -l` 은 머리 세 줄을 숨기므로 파일 자체를 복사해 읽습니다[1].

## 실습

공개 Linux 디스크 이미지(NIST CFReDS 등)나 직접 만든 가상 머신 이미지로 아래 질문을 풀어 봅니다.

1. 배포판이 무엇이고, 사용자 crontab 은 `/var/spool/cron/crontabs/` 와 `/var/spool/cron/` 중 어디에 있는가?
2. `/etc/cron.d/` 와 `/etc/cron.{hourly,daily,weekly,monthly}/` 의 파일 가운데 패키지가 설치하지 않은 것은 무엇인가? 그 파일은 이름·권한 규칙상 실제로 실행될 수 있는가?
3. 사용자 crontab 에 Debian 머리 세 줄이 있는가? `installed on` 시각과 spool 디렉터리 mtime, syslog 의 `REPLACE` 줄 시각은 맞는가?
4. at spool 에 남은 잡이 있는가? 파일 이름의 실행 예정 시각(UTC)과 안의 `uid`, `cd` 경로는 무엇인가?
5. `/var/spool/anacron/` 의 날짜와 mtime 은 anacron 로그의 `Job ... terminated` 시각과 맞는가?
