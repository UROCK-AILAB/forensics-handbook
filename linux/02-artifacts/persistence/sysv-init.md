# init 스크립트와 rc.local (SysV init)

`/etc/init.d` 의 init 스크립트와 `rc.local` 은 systemd 이전부터 쓰던 부팅 때 실행 지점이고, 지금의 Ubuntu 24.04 와 RHEL 9 에서도 systemd 의 호환 생성기를 거쳐 부팅 때 실행될 수 있습니다.

## 무엇을 기록하나 · 왜 생기나

System V init (SysV init) 방식에서는 서비스마다 `/etc/init.d` 에 셸 스크립트를 두고, 실행 수준(runlevel)마다 `rcN.d` 디렉터리에 그 스크립트를 가리키는 링크를 둬서 부팅 때 무엇을 켤지 정했습니다. `rc.local` 은 관리자가 부팅 끝 무렵에 돌릴 명령을 적어 두는 파일입니다.

systemd 는 이 파일들을 직접 읽지 않고 생성기(generator) 두 개로 유닛을 만들어 씁니다. `systemd-sysv-generator` 는 부팅 때와 설정을 다시 읽을 때 `/etc/init.d/*` 스크립트마다 감싸는 `.service` 유닛을 만들고[2], `systemd-rc-local-generator` 는 `rc.local` 이 있고 실행 권한이 있을 때만 `rc-local.service` 를 부팅에 끌어들입니다[5][6]. 그래서 이 파일들은 스크립트 내용, 권한 비트, `rcN.d` 링크, 파일 시각이라는 형태로 "부팅 때 무엇을 돌리도록 해 두었나" 를 기록합니다. 스크립트가 실제로 돌았는지는 저널 쪽에서 봅니다.

한 번 넣어 두면 재부팅마다 실행되므로 지속성(persistence)을 노린 변경이 들어가는 자리이기도 합니다. systemd 유닛 자체는 [systemd 서비스와 타이머](systemd-units.md) 에서 다룹니다.

## 위치와 버전별 차이

스크립트 디렉터리, `rcN.d` 가 놓이는 곳, `rc.local` 경로는 systemd 를 빌드할 때 정하는 값이라 배포판마다 다릅니다[5][8].

| 항목 | Ubuntu 24.04 (systemd 255) | RHEL 9 (systemd 252) |
|---|---|---|
| init 스크립트 디렉터리 | `/etc/init.d`[12] | `/etc/rc.d/init.d`[13] |
| `rcN.d` 가 놓이는 곳 | `/etc` 아래 (`/etc/rc2.d` 등)[12] | `/etc/rc.d` 아래 (`/etc/rc.d/rc3.d` 등)[15] |
| `rc.local` 실제 파일 | `/etc/rc.local`[8] | `/etc/rc.d/rc.local`[13] |
| `/etc/rc.local` | 실제 파일 자리 | `rc.d/rc.local` 을 가리키는 심볼릭 링크[13] |
| 기본 `rc.local` | 설치돼 있는지 실제 시스템에서 확인 | systemd 패키지가 권한 `0644`(실행 권한 없음)로 설치[13][14] |
| `rc-local.service` 순서 | `After=network.target`[7] | `network-online.target` 뒤로 옮기는 배포판 패치가 들어가 있음[13] |

RHEL 9 가 설치하는 `rc.local` 에는 `#!/bin/bash` 와 주석(호환용 파일이라는 설명, 부팅 때 실행하려면 `chmod +x /etc/rc.d/rc.local` 을 하라는 안내) 말고는 명령 `touch /var/lock/subsys/local` 한 줄만 들어 있습니다[14]. 그래서 RHEL 9 시스템에서 이 파일에 실행 권한이 있거나 명령이 더 있다면 설치 뒤에 바뀐 것입니다.

systemd 판에 따라 이 호환 기능이 없을 수도 있습니다. systemd 259 에서 폐지를 예고했고, systemd 260 에서 `systemd-rc-local-generator`, `rc-local.service`, `systemd-sysv-generator`, `systemd-sysv-install` 을 지웠습니다[10]. 기준 판인 255·252 에는 모두 들어 있지만, systemd 260 이상을 쓰는 배포판에서는 `rc.local` 과 init 스크립트가 있어도 systemd 가 실행하지 않습니다.

같은 종류로 수집 도구가 함께 모으는 곳도 있습니다. xinetd 설정 `/etc/xinetd.conf`, `/etc/xinetd.d/**` 와 LSB 순서 설정 `/etc/insserv.conf`, `/etc/insserv.conf.d/**` 가 그렇고[1], 옛 Upstart 설정은 `/etc/init`, `/etc/xdg/upstart`, `/usr/share/upstart/sessions`, 사용자별 `~/.config/upstart` 에 있습니다[19].

## 구조

### init 스크립트와 생성된 유닛

`systemd-sysv-generator` 는 init 스크립트 디렉터리에서 일반 파일이면서 소유자 실행 권한(`S_IXUSR`)이 있는 것만 고릅니다[3]. 이름 끝의 `.sh` 를 떼고 `.service` 를 붙여 유닛 이름을 만들고, 같은 이름의 네이티브 유닛이 이미 있으면 그 스크립트는 건너뜁니다[3].

스크립트 안에서는 두 가지 머리말을 읽습니다[3].

- LSB 머리말: `### BEGIN INIT INFO` 와 `### END INIT INFO` 사이의 `Provides:`, `Required-Start:`, `Should-Start:`, `X-Start-Before:`, `X-Start-After:`, `Short-Description:`, `Description:`. LSB 기능 이름 `$remote_fs`, `$network`, `$named`, `$portmap`, `$time` 은 systemd 타깃 의존으로 바뀝니다[2].
- Red Hat 식 주석: `# description:` 과 `# pidfile:`.

만들어지는 유닛 파일의 첫 줄은 `# Automatically generated by systemd-sysv-generator` 이고, `SourcePath=` 에 원래 스크립트 경로가, `ExecStart=` 와 `ExecStop=` 에 `스크립트경로 start`, `스크립트경로 stop` 이 들어갑니다[3]. 설명을 읽어 냈다면 `Description=` 은 LSB 머리말이 있을 때 `LSB: `, 없을 때 `SYSV: ` 로 시작합니다[3]. 이 유닛은 `/run/systemd/generator.late` 에 생기므로[3][9] 전원을 끈 디스크 이미지에는 없습니다.

### rcN.d 링크 — 부팅 때 켤지 정하는 곳

생성기는 `rcN.d` 에서 이름이 `S` 와 두 자리 숫자로 시작하는 항목만 봅니다[3]. 넷째 글자부터를 서비스 이름으로 읽어서, 같은 이름의 init 스크립트가 있으면 그 유닛을 아래 타깃이 원하도록(`WantedBy`) 묶습니다[3].

| 디렉터리 | 묶이는 타깃 |
|---|---|
| `rc1.d` | `rescue.target` |
| `rc2.d`, `rc3.d`, `rc4.d` | `multi-user.target` |
| `rc5.d` | `graphical.target` |

`K` 로 시작하는 항목과 `rc0.d`, `rc6.d` 는 보지 않습니다[3]. 그래서 init 스크립트만 있고 `S` 링크가 없으면 유닛은 만들어져도 부팅 때 저절로 켜지지 않습니다. 반대로 `S` 링크의 이름만 맞으면 링크가 어디를 가리키는지와 상관없이 같은 이름의 스크립트가 묶입니다[3].

### rc.local 과 rc-local.service

`systemd-rc-local-generator` 는 `access(경로, X_OK)` 로 실행 가능 여부를 보고, 된다면 `multi-user.target.wants/rc-local.service` 링크를 생성기 출력 디렉터리(`/run/systemd/generator`)에 만듭니다[6][9]. 실행 권한이 없으면 `경로 is not marked executable, skipping.` 을 정보(info) 수준으로 남기고 건너뜁니다[6].

systemd 255 의 `rc-local.service` 는 `Description=` 이 `rc.local경로 Compatibility`, `ConditionFileIsExecutable=rc.local경로`, `Type=forking`, `ExecStart=rc.local경로 start`, `RemainAfterExit=yes` 입니다[7]. 옛 SysV 처럼 부팅 맨 마지막에 도는 것이 아니고 다른 서비스들과 나란히 돕니다[5][14].

## 증거로서 의미

### 증명하는 것

- 스크립트와 `rc.local` 에 어떤 명령이 적혀 있었는지.
- init 스크립트에 소유자 실행 권한이 있고 `rcN.d` 에 `S` 링크가 있으면, systemd 255·252 에서 부팅 때 그 스크립트를 돌리도록 설정돼 있었다는 것[3].
- `rc.local` 에 실행 권한이 있으면 부팅 때 `rc-local.service` 가 돌 조건이 갖춰져 있었다는 것[6][7].
- 저널에 `rc-local.service` 나 생성된 유닛의 시작 기록이 있으면 그 부팅에서 그 유닛이 시작됐다는 것. 저널 메시지 모양은 [systemd 서비스와 타이머](systemd-units.md) 에서 다룹니다.

### 증명하지 못하는 것

- 실행 권한이 없는 `rc.local`, 실행 권한이 없는 init 스크립트는 돌지 않으므로 내용만으로 실행됐다고 할 수 없습니다[3][6].
- 스크립트 안 명령이 성공했는지는 이 파일로 알 수 없습니다.
- 누가 파일을 만들었는지는 알 수 없습니다. 이 디렉터리 파일은 보통 root 소유라서 소유자로 사람을 가릴 수 없습니다.
- 지금 디스크에 있는 내용이 그때 돌았던 내용이라는 보장이 없습니다. 실행 뒤에 바꾸거나 지웠을 수 있습니다.

## 시각 해석

파일 시각은 1970-01-01 00:00:00 UTC 를 기준으로 잰 값이고, ext4 는 나노초까지 담습니다[16]. 값의 풀이는 [Linux 의 시각 값](../../01-foundations/value-decoding/time-values.md) 에서 다룹니다.

- mtime 은 내용을 쓸 때 바뀌고, 권한·소유자를 바꿀 때는 바뀌지 않습니다[16].
- ctime 은 내용을 쓸 때뿐만 아니라 권한·소유자·링크 수를 바꿀 때도 바뀝니다[16].

그래서 RHEL 9 의 기본 `rc.local` 에 `chmod +x` 만 했다면 mtime 은 그대로이고 ctime 만 켠 시각으로 바뀝니다. 켠 시각은 ctime 쪽에서 찾습니다. `rcN.d` 에 `S` 링크를 새로 만들거나 지우면 `rcN.d` 디렉터리의 mtime 이 바뀝니다[16]. `S` 링크 자체의 시각은 링크를 따라가지 않고 읽습니다.

실행 시각은 파일에 남지 않습니다. 저널의 `UNIT=rc-local.service` 나 생성된 유닛 이름으로 시작 기록을 찾습니다. 저널 시각의 해석은 [systemd 저널](../../01-foundations/logging/systemd-journal/index.md) 에서 다룹니다.

## 함정과 한계

- RHEL 9 의 `/etc/rc.local` 은 링크라서, 링크를 따라가지 않고 모으면 내용이 빠집니다[13]. ForensicArtifacts 의 `LinuxSysVInit` 는 `/etc/rc.d/rc.local` 을 따로 적지 않았고, `/etc/rc.local` 경로와 `/etc/rc*.d/*` 와일드카드로 모읍니다[1]. 수집할 때 실제 파일이 들어왔는지, 링크를 따라갔는지 확인합니다.
- RHEL 9 systemd 패키지는 `/etc/rc.d/rc.local` 에 `%verify(owner group)` 를 달아 두었습니다[13]. `%verify` 는 `rpm -V` 가 파일의 일부 속성을 검사하지 않게 하는 표시라서[21], 이 파일의 내용이나 권한을 바꿔도 `rpm -V` 결과에 나오지 않을 가능성이 있습니다. 내용과 권한은 파일에서 직접 봅니다. 패키지 검증 방법은 [패키지 파일 변조 확인](../packages/package-verify.md) 에서 다룹니다.
- `/etc/init.d` 에 있는 스크립트가 곧 실행되는 것은 아닙니다. 같은 이름의 네이티브 유닛이 있으면 생성기가 건너뛰고[3], 실행 권한이나 `S` 링크가 없으면 부팅 때 돌지 않습니다.
- 생성기가 만든 유닛과 `rc-local.service` 링크는 `/run` 아래에만 있어서 전원을 끈 이미지에는 없습니다[9]. 라이브 수집 때만 얻습니다.
- systemd 260 이상에서는 이 파일들이 무시됩니다[10]. 배포판의 systemd 판을 먼저 확인합니다.
- dissect.target 의 `services` 플러그인은 `/etc/rc.d/init.d` 와 `/etc/init.d` 의 파일 이름·경로와 mtime 만 내놓습니다[18]. 권한 비트, `rcN.d` 링크, `rc.local` 은 나오지 않습니다.

## 직접 분석해 보기

### 헥스로 한 번 — 권한과 시각

ext4 아이노드는 0x0 에 `i_mode`(2바이트), 0xC 에 `i_ctime`, 0x10 에 `i_mtime`(각 4바이트, 리틀 엔디언 epoch 초)을 둡니다[17]. `i_mode` 에서 0x8000 은 일반 파일, 0x40 은 소유자 실행 권한입니다[17]. 아래는 명세로 만든 예시로, `rc.local` 아이노드의 첫 0x14 바이트입니다.

```
오프셋  00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F
0000    ED 81 00 00 D0 01 00 00 80 95 A1 66 C0 EC A0 66
0010    00 86 31 66
```

- `i_mode` = 0x81ED → 0x8000(일반 파일) + 0755. 기본값이었다면 0x81A4(0644)이고, 차이인 0x49 가 소유자·그룹·다른 사용자의 실행 비트(0x40·0x08·0x01)입니다.
- `i_ctime` = 0x66A0ECC0 → 2024-07-24 12:00:00 UTC.
- `i_mtime` = 0x66318600 → 2024-05-01 00:00:00 UTC.

mtime 은 오래됐는데 ctime 만 최근이면 내용은 그대로 두고 권한이나 소유자를 바꾼 경우와 맞습니다. 아이노드 전체 구조와 나노초 필드는 [ext4](../../01-foundations/filesystem/ext4/index.md) 에서 다룹니다.

### 공개 도구로 한 번

이미지를 `/mnt/img` 에 읽기 전용으로 마운트했다고 두면(만든 예시) 다음 순서로 봅니다.

1. `ls -la --time=ctime /mnt/img/etc/rc.local /mnt/img/etc/rc.d/rc.local` 로 링크 여부, 권한, ctime 을 봅니다. `stat` 은 mtime·ctime 을 함께 보여 줍니다.
2. `ls -la /mnt/img/etc/rc?.d /mnt/img/etc/rc.d/rc?.d` 로 `S` 로 시작하는 링크를 모으고, 링크 이름에서 `S` 와 숫자 두 자리를 뗀 이름이 init 스크립트 디렉터리에 있는지 맞춰 봅니다.
3. init 스크립트 디렉터리에서 실행 권한이 있는 일반 파일을 고르고, 같은 이름의 유닛이 systemd 유닛 디렉터리에 있는지 확인합니다.
4. dissect.target 의 `services` 플러그인을 돌리면 `type` 이 `initd` 인 레코드로 스크립트 이름·경로와 mtime 이 나옵니다[18].

라이브 시스템이면 UAC 가 `service --status-all`, `chkconfig --list`, `runlevel` 출력과 `/etc`(shadow 파일 제외)를 모읍니다[19][20]. 이때 `/run/systemd/generator.late` 에서 생성된 유닛 파일도 함께 떠 둡니다.

저널에서는 systemd 255 생성기가 네이티브 유닛이 없는 SysV 스크립트를 만날 때 경고 수준으로 `MESSAGE_ID=a8fa8dacdb1d443e9503b8be367a6adb`, `SYSVSCRIPT=스크립트경로`, `UNIT=유닛이름` 을 남깁니다[3][11]. systemd 252 는 같은 경고를 `SysV service '경로' lacks a native systemd unit file.` 로 시작하는 문장으로만 남깁니다[4]. 이 경고가 저널에 남았는지는 이 값으로 찾아봅니다.

## 실습

NIST CFReDS 같은 공개 Linux 디스크 이미지로 다음을 풀어 봅니다.

1. 이미지의 배포판과 systemd 판은 무엇이고, 이 판에서 `rc.local` 과 init 스크립트 호환 기능이 남아 있나요?
2. `rc.local` 의 실제 파일 경로는 어디이고, 실행 권한이 있나요? mtime 과 ctime 은 각각 언제인가요?
3. init 스크립트 디렉터리에서 실행 권한이 있는 스크립트 가운데 `rcN.d` 에 `S` 링크가 있는 것은 무엇이고, 그중 같은 이름의 네이티브 유닛이 없는 것은 무엇인가요?
4. 그 스크립트들이 패키지 파일 목록에 있나요?
5. 저널에 `rc-local.service` 나 생성된 유닛의 시작 기록이 있다면, 첫 기록은 파일의 ctime 뒤인가요?
