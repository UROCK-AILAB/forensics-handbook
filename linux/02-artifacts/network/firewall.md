# 방화벽 (iptables·nftables·ufw·firewalld)

Linux 방화벽 규칙은 커널 메모리에 올라가 동작하고, 디스크에는 관리 도구가 남긴 저장 파일과 설정 파일, 그리고 LOG 규칙이 걸렸을 때 커널이 남긴 로그 줄이 남습니다.

## 무엇을 기록하나 · 왜 생기나

패킷을 거르는 일은 커널의 넷필터 (netfilter) 가 합니다. iptables·nftables 는 넷필터에 규칙을 넣는 명령이고, ufw 와 firewalld 는 그 위에서 규칙을 대신 만들어 주는 관리 도구입니다. 조사에서 방화벽을 보는 이유는 두 가지입니다. 하나는 어떤 포트를 열고 막았는지, 누가 규칙을 바꿨는지 같은 설정 변경의 흔적이고, 다른 하나는 LOG 규칙이 남긴 패킷 한 줄 한 줄의 통신 흔적입니다.

iptables 규칙은 기본으로 디스크에 저장되지 않습니다[1]. 재부팅 뒤에도 규칙을 쓰려면 `iptables-save` 결과를 어딘가에 두었다가 부팅 때 다시 넣어야 하고, 이 도구에는 정해진 저장 경로가 없습니다[1]. 그래서 디스크 이미지에서 찾은 규칙 파일은 "누군가 저장해 둔 규칙" 이지 "그 시각에 동작하던 규칙" 과 같지 않을 수 있습니다.

firewalld 도 설정을 두 층으로 나눕니다. 런타임 설정 (runtime configuration) 은 지금 동작하는 설정이고 영구적이지 않아서, 서비스를 다시 읽거나(reload) 다시 시작하거나 재부팅하면 영구 설정에 없는 부분은 사라집니다[4]. 영구 설정 (permanent configuration) 은 설정 파일에 저장되고, 부팅하거나 다시 읽을 때마다 새 런타임 설정이 됩니다[4]. `firewall-cmd --permanent` 없이 바꾼 규칙은 디스크에 남지 않는다는 뜻입니다.

## 위치와 버전별 차이

| 도구 | 디스크에 남는 것 | 위치 |
|---|---|---|
| iptables (IPv4) | `iptables-save` 결과 파일 | `/etc/iptables/rules.v4`, `/etc/sysconfig/iptables`, `/etc/iptables.rules`, `/etc/iptablesRule.v4`, `/etc/network/iptables.rules`[1] |
| ip6tables (IPv6) | `ip6tables-save` 결과 파일 | `/etc/iptables/rules.v6`, `/etc/iptablesRule.v6`, `/etc/sysconfig/ip6tables`[1] |
| ufw | 규칙 파일(iptables-save 형식) | `/etc/ufw/before.rules`, `user.rules`, `after.rules`, `before6.rules`, `user6.rules`, `after6.rules`, `/usr/share/ufw/user.rules`·`user6.rules`, `/usr/share/ufw/iptables/user.rules`·`user6.rules`, `/var/lib/ufw/user.rules`·`user6.rules`[1] |
| ufw | 설정 | `/etc/default/ufw`, `/etc/ufw/sysctl.conf`, `/etc/ufw/*.rules`, `/etc/ufw/applications.d/*`[2] |
| ufw | 로그 | `/var/log/ufw.log`[2] |
| firewalld | 패키지 기본 설정 | `/usr/lib/firewalld` 아래(영역은 `zones/영역.xml`)[4][6] |
| firewalld | 관리자가 바꾼 설정 | `/etc/firewalld` 아래(영역은 `zones/영역.xml`)[4][6] |
| firewalld | 전체 설정 | `/etc/firewalld/firewalld.conf`[5][7] |
| firewalld | 시작 인자 | `/etc/sysconfig/firewalld` 의 `FIREWALLD_ARGS=`[7] |
| firewalld | 자체 로그(디버그 메시지) | `/var/log/firewalld`[4] |
| nftables | 규칙 파일 | 패키지가 정함. 대상 시스템의 nftables 유닛 파일 `ExecStart` 가 읽는 파일로 확인 |
| 모든 도구 | LOG 규칙이 남긴 커널 줄 | 저널, rsyslog 파일([커널 로그](../system-info/kernel-log.md) 참고) |

`/usr/lib/firewalld` 의 파일은 패키지가 넣은 것이라 패키지를 업데이트하면 바뀐 내용이 사라집니다[4]. 관리자가 미리 정의된 영역을 고치려면 이 파일을 `/etc/firewalld` 의 같은 자리로 복사해서 고치고, `/etc/firewalld` 의 파일이 기본 파일보다 앞섭니다[4]. 그래서 `/etc/firewalld/zones/` 에 있는 파일은 누군가 그 영역을 바꿨거나 새 영역을 만들었다는 단서가 됩니다.

대상 시스템이 어느 도구를 썼는지는 위 경로 가운데 어느 것이 있는지와, 어떤 방화벽 서비스가 켜져 있었는지로 판별합니다. firewalld 유닛은 `WantedBy=multi-user.target` 이고 `iptables.service`, `ip6tables.service`, `ebtables.service`, `ipset.service` 와 함께 돌 수 없게(`Conflicts=`) 되어 있습니다[7]. 서비스가 켜진 흔적을 읽는 법은 [systemd 서비스와 타이머](../persistence/systemd-units.md) 에서 다룹니다.

firewalld 는 기본으로 nftables 를 백엔드로 쓰고(`FirewallBackend=nftables`), iptables 백엔드는 앞으로 없앨 예정입니다[5][7]. NetworkManager 도 공유 연결의 마스커레이드 (masquerade) 규칙을 넣을 때 `[main]` 절의 `firewall-backend` 로 iptables, nftables, none 가운데 하나를 고르고, 값을 비워 두면 스스로 감지해 고릅니다[12].

## 구조

### iptables-save 형식

iptables·ip6tables 저장 파일과 ufw 규칙 파일은 같은 형식입니다[1]. 아래는 형식을 보여 주려고 만든 예시입니다.

```
# Generated by iptables-save v1.8.10 on Tue Mar  5 12:00:00 2024
*filter
:INPUT DROP [1520:98311]
:FORWARD DROP [0:0]
:OUTPUT ACCEPT [4410:512034]
[35:2100] -A INPUT -s 198.51.100.0/24 -p tcp -m tcp --dport 22 -j ACCEPT
-A INPUT -i lo -j ACCEPT
COMMIT
```

| 줄 | 모양 | 뜻 |
|---|---|---|
| 머리 | `# Generated by iptables-save v판 on 시각` | 만든 프로그램(`iptables-save`, `ip6tables-save`)·판·저장 시각. 시각 형식은 `%a %b  %d %H:%M:%S %Y`[1] |
| 표 | `*filter`, `*nat` 등 | 뒤에 오는 줄이 속한 표[1] |
| 정책 | `:체인 정책 [패킷:바이트]` | 기본 체인의 기본 정책(ACCEPT·DROP)과 계수[1] |
| 규칙 | `[패킷:바이트] -A 체인 …` | 규칙 한 줄. 앞의 계수는 없을 수도 있음[1] |
| 끝 | `COMMIT` | 표 하나의 끝[1] |

정책 줄에는 계수가 반드시 있고, 규칙 줄에는 계수가 붙기도 하고 빠지기도 합니다[1]. 규칙 줄 계수가 0 이 아니면 저장하기 전에 그 규칙에 걸린 패킷이 있었다는 뜻으로 읽을 수 있습니다.

### firewalld 영역 파일

영역 파일 이름은 `영역이름.xml` 이고, 영역 이름은 17자까지입니다[6]. 맨 바깥 요소는 `<zone>` 이고 `version`, `target`(ACCEPT, `%%REJECT%%`, DROP), `ingress-priority`, `egress-priority` 속성을 둘 수 있습니다[6]. 안에는 영역에 묶인 `interface`·`source`, 허용한 `service`·`port`·`protocol`, `icmp-block`, `masquerade`, `forward-port`, `source-port`, 풍부한 규칙 (rich rule) 인 `rule` 요소가 들어갑니다[6][8][9]. 풍부한 규칙에는 자체 `log`·`nflog`·`audit` 요소가 들어갈 수 있습니다[9]. 아래는 요소 이름을 보여 주려고 만든 예시입니다.

```xml
<?xml version="1.0" encoding="utf-8"?>
<zone>
  <short>Public</short>
  <service name="ssh"/>
  <port port="8080" protocol="tcp"/>
  <source address="198.51.100.0/24"/>
</zone>
```

firewalld 는 영역 파일을 새로 쓰기 전에 기존 파일을 `영역이름.xml.old` 로 복사하고, 이때 `shutil.copy2` 를 써서 원래 파일의 수정 시각까지 옮깁니다[8]. `.old` 파일은 직전 설정의 사본이라 두 파일을 비교하면 마지막 변경에서 무엇이 바뀌었는지 볼 수 있습니다.

### firewalld.conf

업스트림 기본값 가운데 조사에 쓰이는 키는 아래와 같습니다[5][7].

| 키 | 기본값 | 뜻 |
|---|---|---|
| `DefaultZone` | `public` | 따로 정하지 않은 연결·인터페이스가 들어가는 영역 |
| `LogDenied` | `off` | 거부·버림 규칙 바로 앞에 로그 규칙을 넣을지. 값은 all, unicast, broadcast, multicast, off |
| `FirewallBackend` | `nftables` | 규칙을 넣을 백엔드 |
| `CleanupOnExit` | `yes` | firewalld 가 멈출 때 규칙을 비울지 |
| `FlushAllOnReload` | `yes` | 다시 읽을 때 런타임 설정을 모두 비울지 |

`LogDenied` 를 켜면 INPUT, FORWARD, OUTPUT 체인의 기본 거부·버림 규칙과 영역의 마지막 거부·버림 규칙 바로 앞에 로그 규칙이 들어갑니다[5]. 기본값이 off 이므로 firewalld 시스템에서 거부된 패킷 로그가 없는 것이 정상입니다.

### 커널 로그 줄 (LOG 대상)

LOG 규칙에 걸린 패킷은 커널 메시지 한 줄이 됩니다. 줄 모양은 커널의 `nf_log_syslog` 가 정합니다[10]. 아래는 형식에 맞춰 만든 IPv4 TCP 예시이고, `EXAMPLE-DROP: ` 은 지어낸 접두어입니다.

```
EXAMPLE-DROP: IN=eth0 OUT= MAC=00:00:5e:00:53:01:00:00:5e:00:53:02:08:00 SRC=203.0.113.5 DST=192.0.2.10 LEN=60 TOS=0x00 PREC=0x00 TTL=52 ID=5421 DF PROTO=TCP SPT=51514 DPT=22 WINDOW=64240 RES=0x00 SYN URGP=0
```

| 필드 | 뜻 |
|---|---|
| 접두어 | 규칙이 정한 문자열이 그대로 붙음. 뒤에 공백 없이 `IN=` 이 이어짐[10] |
| `IN=`, `OUT=` | 들어온 인터페이스, 나갈 인터페이스. 없으면 빈 값[10] |
| `PHYSIN=`, `PHYSOUT=` | 브리지를 거친 패킷의 실제 포트[10] |
| `MAC=` | 들어온 패킷일 때만. 링크 계층 헤더 바이트를 콜론으로 이음[10] |
| `MACSRC=`, `MACDST=`, `MACPROTO=` | 규칙에 MAC 풀이 옵션을 켰을 때 `MAC=` 대신 나옴[10] |
| `SRC=`, `DST=` | 출발·도착 IP[10] |
| `LEN= TOS= PREC= TTL= ID=` | IP 헤더 값. 뒤에 `CE`, `DF`, `MF` 표시가 붙을 수 있음[10] |
| `PROTO=TCP SPT= DPT=` | TCP 출발·도착 포트. 뒤에 `WINDOW=`, `RES=`, 플래그(`SYN`, `ACK`, `FIN`, `RST` 등), `URGP=`[10] |
| `SEQ= ACK=` | 규칙에 TCP 순서 번호 옵션을 켰을 때만[10] |
| `PROTO=UDP SPT= DPT= LEN=` | UDP[10] |
| `PROTO=ICMP TYPE= CODE=` | ICMP[10] |
| `UID= GID=` | 규칙에 UID 옵션을 켰고 소켓이 있을 때만. 로컬 프로세스의 사용자·그룹 번호[10] |
| `MARK=` | 패킷에 표시(mark)가 있을 때만[10] |

IPv6 줄은 `LEN= TC= HOPLIMIT= FLOWLBL=` 로 헤더를 적고, 프로토콜은 `PROTO=ICMPv6` 처럼 적습니다[10]. 예시의 `MAC=` 은 이더넷 헤더 순서대로 도착 MAC 6바이트, 출발 MAC 6바이트, 이더넷 형식 2바이트(`08:00` 은 IPv4)입니다.

## 증거로서 의미

**증명하는 것**

- 저장 파일이나 영역 파일에 적힌 규칙이 그 파일을 쓴 시점에 저장되어 있었다는 것. 어떤 포트를 열었는지, 기본 정책이 무엇이었는지, 특정 출발지만 허용했는지를 보여 줍니다.
- LOG 규칙의 줄이 있으면, 그 시각에 해당 인터페이스로 그 출발지·도착지·포트의 패킷이 그 규칙에 걸렸다는 것[10]. 접두어로 어느 규칙이 남긴 줄인지 확인합니다.
- `/etc/firewalld/zones/` 에 파일이 있거나 `.old` 파일이 있으면 그 영역을 누군가 바꿨거나 새로 만들었다는 것[4][8].
- 다른 프로그램이 넣은 규칙의 표지. wg-quick 은 iptables 규칙에 `-m comment --comment "wg-quick(8) rule for 인터페이스"` 주석을 달고, nft 를 쓰면 `wg-quick-인터페이스` 표를 만듭니다[13]. 이 표지로 WireGuard 사용 흔적을 찾는 법은 [VPN](vpn.md) 에서 다룹니다.

**증명하지 못하는 것**

- 저장 파일은 그 시각에 동작하던 규칙을 증명하지 않습니다. 런타임 규칙만 바꾸고 저장하지 않을 수 있기 때문입니다[1][4].
- 로그가 없다고 통신이 없었던 것은 아닙니다. LOG 규칙이 없으면 줄이 남지 않고, firewalld 의 `LogDenied` 는 기본 off 입니다[5][7]. 컨테이너처럼 기본 네트워크 이름공간 (network namespace) 이 아닌 곳의 패킷은 `nf_log_all_netns` 를 켜지 않으면 로그에 남지 않습니다[10][11].
- 로그 줄의 `UID=` 가 없으면 줄만으로 어느 프로세스·사용자의 통신인지 알 수 없습니다.
- 규칙 파일은 누가 바꿨는지 적지 않습니다. 바꾼 사람은 셸 기록, sudo 기록, 로그인 기록과 시각을 맞춰 추정합니다.

## 시각 해석

| 시각 | 바뀌는 때 | 시간대 |
|---|---|---|
| iptables-save 머리의 `on` 시각 | 파일을 저장할 때 | 시간대 표기가 없음. dissect 는 대상 시스템 시간대의 현지 시각으로 해석[1] |
| 규칙·설정 파일의 수정 시각 | 그 파일을 마지막으로 쓸 때 | 파일 시스템 시각 값(UTC 기준 epoch) |
| firewalld `영역.xml.old` 수정 시각 | 복사 때 원래 파일의 수정 시각을 그대로 옮김 | 같음[8] |
| 커널 로그 줄 앞 시각 | 저널이나 rsyslog 가 줄을 받을 때 붙임 | 받은 쪽의 형식을 따름 |

`.old` 파일의 수정 시각은 복사한 시각이 아니라 그 전 판이 마지막으로 쓰인 시각입니다[8]. 그래서 `영역.xml.old` 의 수정 시각은 직전 변경 시각, `영역.xml` 의 수정 시각은 마지막 변경 시각으로 읽을 수 있습니다. 파일 수정 시각은 규칙이 메모리에 올라간 시각이 아니라 파일을 쓴 시각입니다.

커널 줄에는 시각이 없고, 저널과 rsyslog 가 붙이는 시각의 차이와 연도가 없는 전통 syslog 형식은 [커널 로그](../system-info/kernel-log.md) 와 [syslog 형식과 rsyslog](../../01-foundations/logging/syslog-rsyslog.md) 에서 다룹니다. 시각 값 변환은 [Linux 의 시각 값](../../01-foundations/value-decoding/time-values.md) 에서 다룹니다.

## 함정과 한계

- firewalld 기본 백엔드가 nftables 이므로[5][7] `iptables -L` 결과만 보면 firewalld 가 넣은 규칙이 빠질 수 있습니다. `nft list ruleset` 결과를 함께 봅니다.
- ForensicArtifacts 의 `IPTablesRules` 는 `/sbin/iptables -L -n -v` 한 명령만 정의합니다[2]. 이 결과에는 nat 표와 nftables 규칙이 없습니다. UAC 는 `iptables -t nat -L -v -n` 과 `nft list ruleset` 까지 모읍니다[3].
- UAC 의 `ip6tables.yaml` 은 실행 조건이 `command_exists "ip6table"` 이고, 출력 파일 이름이 iptables 수집과 같은 `iptables_-L_-v_-n.txt` 입니다[3]. UAC 결과에 IPv6 규칙이 없거나 IPv4 결과를 덮어썼을 가능성이 있으므로 결과 폴더에서 두 파일의 내용을 확인합니다.
- dissect 의 iptables 플러그인은 정해진 경로만 보고, 첫 줄이 `# Generated by ip(6)tables-save` 머리이거나 `*filter` 를 담은 파일만 규칙 파일로 읽습니다[1]. 다른 경로에 두었거나 첫 줄에 주석을 단 파일은 빠지므로, `iptables-restore` 나 `nft -f` 를 부르는 유닛·스크립트에서 읽는 경로를 찾아 따로 봅니다.
- firewalld 의 `CleanupOnExit=yes` 는 서비스가 멈출 때 규칙을 비웁니다[5][7]. 서비스를 멈춘 뒤의 라이브 수집 결과에는 firewalld 규칙이 없을 수 있습니다.
- `/var/log/firewalld` 에는 디버그 메시지가 들어가고[4], `FIREWALLD_ARGS=` 에 `--debug` 가 없으면 내용이 적습니다[4][7]. 이 파일은 주 1회, 4개까지, 1MB 이상일 때 copytruncate 로 순환합니다[7]. 순환된 파일 이름은 [로그 순환](../../01-foundations/logging/logrotate.md) 에서 다룹니다.
- 사고 대응 도구도 규칙을 남깁니다. Velociraptor 의 `Linux.Remediation.Quarantine` 은 기본 이름 `vrr_quarantine_table` 인 inet 표에 inbound·outbound·forward 체인을 만들고, DNS(53, `127.0.0.53`)·DHCP(67, 68)·Velociraptor 서버 통신만 허용합니다[14]. 이 표가 있으면 대응 중 격리한 흔적이지 공격자가 넣은 규칙이 아닐 가능성이 있습니다.
- 공격자가 규칙을 지우거나 바꾼 뒤 저장 파일은 그대로 두면 디스크와 메모리의 규칙이 다릅니다. 라이브 수집 결과나 메모리 이미지가 있으면 저장 파일과 비교합니다.

## 직접 분석해 보기

### 원문으로 한 번

규칙 파일과 영역 파일은 모두 텍스트라서 헥스 대신 원문으로 읽습니다.

1. 이미지를 읽기 전용으로 붙이고 위 표의 경로를 모두 찾습니다. `/etc/firewalld/zones/*.xml` 과 `*.xml.old` 는 수정 시각과 함께 목록으로 남깁니다.
2. iptables-save 형식 파일은 머리 줄의 판과 저장 시각을 적고, `*표` 줄마다 정책 줄과 `-A` 규칙을 나눠 봅니다. `-j ACCEPT` 로 연 포트, 출발지를 좁힌 규칙(`-s`), 계수가 0 이 아닌 규칙을 먼저 봅니다.
3. firewalld 는 `/etc/firewalld/zones/영역.xml` 과 `.xml.old` 를 `diff` 로 비교하고, 같은 이름의 `/usr/lib/firewalld/zones/영역.xml` 과도 비교해 기본값에서 바뀐 부분을 구분합니다.
4. `/etc/firewalld/firewalld.conf` 에서 `DefaultZone`, `LogDenied`, `FirewallBackend` 를 기본값과 비교합니다.
5. LOG 규칙의 접두어(`--log-prefix` 값, 풍부한 규칙의 `log` 요소)를 모은 뒤, 그 문자열로 저널과 rsyslog 파일을 검색합니다. ufw 로그의 접두어도 `/etc/ufw/*.rules` 의 `--log-prefix` 값에서 확인합니다.

### 공개 도구로 한 번

- dissect.target 의 `iptables` 플러그인은 iptables-save·ufw 규칙 파일을 읽어 `ts`, `program`, `version`, `table`, `chain`, `type`(policy 또는 rule), `rule`, `packet_count`, `byte_count`, `source` 로 내놓습니다[1].
- UAC 는 라이브 시스템에서 `iptables -L -v -n`, `iptables -t nat -L -v -n`, `ip6tables -L -v -n`, `ip6tables -t nat -L -v -n`, `nft list ruleset`, `ufw status verbose`, `firewall-cmd --get-active-zones`·`--get-default-zone`·`--get-services`·`--list-all`·`--list-all-zones` 결과를 모읍니다[3]. 수집 절차는 [라이브 응답 수집](../../03-techniques/acquisition/live-response.md) 에서 다룹니다.
- Volatility 3 의 `linux.malware.netfilter` 플러그인은 메모리 이미지에서 넷필터 훅 (hook) 을 이름공간·프로토콜·훅별로 나열하고 처리 함수 주소, 모듈, `Is Hooked` 열을 보여 줍니다[15]. 규칙 내용이 아니라 훅에 걸린 함수를 보는 도구이고, 루트킷이 넷필터에 끼어든 흔적을 찾을 때 씁니다. 메모리 분석 전반은 [메모리 분석](../../03-techniques/analysis/memory-analysis.md) 에서 다룹니다.

## 실습

NIST CFReDS 등에 공개된 Linux 디스크·메모리 이미지로 다음 질문을 풀어 봅니다.

1. 대상 시스템에 있는 방화벽 관리 도구는 무엇이고, 어느 서비스가 켜져 있었나?
2. iptables-save 형식 파일이 있다면 머리 줄의 저장 시각과 파일 수정 시각은 서로 맞는가?
3. `/etc/firewalld/zones/` 에 있는 영역 파일은 `/usr/lib/firewalld/zones/` 의 같은 파일과 무엇이 다른가? `.old` 파일과 비교하면 마지막 변경은 무엇인가?
4. 저널이나 rsyslog 파일에 LOG 규칙 줄이 있다면, 가장 많이 막힌 출발지와 도착 포트는 무엇인가?
5. 라이브 수집 결과나 메모리 이미지가 있다면, 동작하던 규칙과 디스크의 저장 파일이 같은가?
