# XFS (XFS)

XFS 는 디스크를 할당 그룹 (Allocation Group, AG) 여러 개로 나눠 관리하는 파일 시스템이고, 모든 값을 빅 엔디언으로 적으며, V5 형식에서는 메타데이터 블록마다 체크섬·소유자·마지막으로 바꾼 로그 순서 번호를 함께 넣습니다[1][4].

ext4 와 개념은 비슷하지만 바이트 배치와 시각 형식이 다릅니다. 아이노드·시각·저널·지운 파일의 일반 개념은 ext4 페이지([아이노드와 익스텐트](ext4/inode-extent.md), [시각 값](ext4/timestamps.md), [저널](ext4/journal-jbd2.md), [지운 파일이 남기는 것](ext4/deleted-files.md))에서 다루고, 이 페이지는 XFS 에서 달라지는 점만 다룹니다.

## 이 형식을 쓰는 아티팩트

XFS 는 Red Hat 계열 배포판 시스템에서 자주 만납니다[10]. RHEL 9 설치 프로그램은 파일 시스템 종류를 `xfs` 로 두고, 기본 분할 방식은 LVM 입니다[6][7]. 그래서 RHEL 9 시스템에서는 XFS 가 [LVM 논리 볼륨](../disk-volume/lvm.md) 안에 들어 있는 경우가 많습니다.

| 배포판 | 설치 기본 파일 시스템 | 기본 분할 |
|---|---|---|
| Ubuntu 24.04 LTS | ext4(`/`, LVM 설치 때는 `/boot` 와 논리 볼륨 `ubuntu-lv`)[8] | 직접 설치 또는 LVM |
| RHEL 9 | xfs[6] | LVM. `/`(최소 1 GiB, 최대 70 GiB), `/home`, swap[6][7] |

XFS 볼륨 위의 모든 파일 흔적, 곧 로그 파일·셸 기록·설정 파일의 내용과 시각은 이 페이지의 아이노드 구조를 거쳐 읽습니다. 이미지 안 볼륨이 어느 마운트 지점에 붙는지는 `/etc/fstab` 의 UUID·레이블과 슈퍼블록의 `sb_uuid`·`sb_fname` 을 맞춰 정합니다[11]. 경로 규약은 [디렉터리 구조와 주요 경로](fhs-paths.md) 에서 다룹니다.

## 구조

온디스크 값은 빅 엔디언입니다[1]. 예외로 체크섬 필드인 슈퍼블록 `sb_crc`, 아이노드 `di_crc`, V5 트리 블록 머리 `bb_crc`, 로그 레코드 머리 `h_crc` 는 리틀 엔디언(`__le32`)입니다[1][2].

### 할당 그룹과 고정 위치

볼륨은 크기가 같은 할당 그룹 `sb_agcount` 개로 나뉘고, 그룹 하나의 크기는 `sb_agblocks` 블록입니다[1]. 디스크에서 위치가 정해진 메타데이터는 각 할당 그룹 머리의 네 개(슈퍼블록, AGF, AGI, AGFL)뿐이고, 나머지 메타데이터는 모두 동적으로 할당하므로 트리를 따라가서 찾아야 합니다[4]. 네 머리는 할당 그룹 첫 섹터부터 한 섹터씩 차례로 놓입니다[1].

| 순서 | 이름 | 마법 수 | 담는 것 |
|---|---|---|---|
| 섹터 0 | 슈퍼블록 | `0x58465342` `XFSB` | 볼륨 전체 설정. 모든 할당 그룹에 사본이 있고, 볼륨을 늘릴 때(growfs)가 아니면 0번 그룹 것만 갱신합니다 |
| 섹터 1 | AGF | `0x58414746` `XAGF` | 여유 공간 트리 뿌리 |
| 섹터 2 | AGI | `0x58414749` `XAGI` | 아이노드 트리 뿌리, 이름은 지웠지만 아직 참조되는 아이노드 목록 |
| 섹터 3 | AGFL | `0x5841464c` `XAFL` | 여유 목록(free list). V4 형식에는 마법 수가 없습니다[4] |

### 아이노드 번호에서 위치 구하기

XFS 아이노드 번호는 순번이 아니라 위치를 비트로 나눠 담은 값입니다. 아래쪽 `sb_inopblog` 비트가 블록 안 순번, 그 위 `sb_agblklog` 비트가 할당 그룹 안 블록 번호, 나머지 위쪽 비트가 할당 그룹 번호입니다[1].

```
블록 안 순번     = ino & ((1 << sb_inopblog) - 1)
그룹 안 블록 번호 = (ino >> sb_inopblog) & ((1 << sb_agblklog) - 1)
할당 그룹 번호    = ino >> (sb_inopblog + sb_agblklog)
바이트 위치       = (할당 그룹 번호 × sb_agblocks + 그룹 안 블록 번호) × sb_blocksize
                   + 블록 안 순번 × sb_inodesize
```

익스텐트에 적힌 블록 번호도 같은 방식으로 "할당 그룹 번호 << `sb_agblklog` | 그룹 안 블록 번호" 로 묶여 있습니다[1]. `sb_agblklog` 는 올림한 값이라 그대로 곱하면 안 되고, 위 식처럼 그룹 번호에 `sb_agblocks` 를 곱해 바이트 위치를 구합니다[1].

### 아이노드

아이노드는 앞쪽의 고정 머리(dinode core)와 그 뒤의 데이터 포크·속성 포크로 이뤄집니다[1]. 오프셋은 아이노드 시작 기준입니다[1].

| 오프셋 | 크기 | 이름 | 뜻 |
|---|---|---|---|
| 0x00 | 2 | `di_magic` | `0x494e` `IN` |
| 0x02 | 2 | `di_mode` | 파일 종류 + 권한 비트 |
| 0x04 | 1 | `di_version` | 아이노드 판(1·2, V5 볼륨은 3) |
| 0x05 | 1 | `di_format` | 데이터 포크 형식(아래 표) |
| 0x08 | 4 | `di_uid` | 소유자 UID |
| 0x0C | 4 | `di_gid` | 그룹 GID |
| 0x10 | 4 | `di_nlink` | 하드 링크 수 |
| 0x20 | 8 | `di_atime` | 마지막 접근 시각 |
| 0x28 | 8 | `di_mtime` | 데이터 수정 시각 |
| 0x30 | 8 | `di_ctime` | 아이노드 변경 시각 |
| 0x38 | 8 | `di_size` | 크기(바이트) |
| 0x40 | 8 | `di_nblocks` | 차지한 블록 수(데이터 + 트리 블록) |
| 0x4C | 4 | `di_nextents` | 데이터 포크 익스텐트 수 |
| 0x52 | 1 | `di_forkoff` | 속성 포크 위치(× 8 바이트) |
| 0x53 | 1 | `di_aformat` | 속성 포크 형식 |
| 0x5A | 2 | `di_flags` | 아이노드 플래그 |
| 0x5C | 4 | `di_gen` | 세대 번호 |
| 0x60 | 4 | `di_next_unlinked` | AGI 의 "지웠지만 열려 있는" 목록에서 다음 아이노드 |
| 0x64 | 4 | `di_crc` | 아이노드 체크섬(판 3부터, 리틀 엔디언) |
| 0x68 | 8 | `di_changecount` | 속성 변경 횟수 |
| 0x70 | 8 | `di_lsn` | 아이노드를 마지막으로 디스크에 쓴 로그 순서 번호 |
| 0x78 | 8 | `di_flags2` | 추가 플래그. 0x8 = bigtime 시각 형식 |
| 0x90 | 8 | `di_crtime` | 만든 시각(판 3만) |
| 0x98 | 8 | `di_ino` | 자기 아이노드 번호(판 3만) |
| 0xA0 | 16 | `di_uuid` | 볼륨 UUID(판 3만) |

고정 머리 크기는 판 1·2 가 100바이트(0x64), 판 3 이 176바이트(0xB0)입니다[1]. `di_crtime`·`di_ino`·`di_uuid` 는 아이노드를 만들 때만 쓰는 필드입니다[1]. `di_ctime` 정의 옆에는 "time created/inode modified" 라는 옛 설명이 남아 있지만, 만든 시각은 `di_crtime` 에 따로 적습니다[1].

`di_format` 값은 아래와 같습니다[1].

| 값 | 이름 | 데이터 포크 내용 |
|---|---|---|
| 0 | dev | 장치 번호 |
| 1 | local | 데이터를 아이노드 안에 바로 저장 |
| 2 | extents | 익스텐트 레코드 배열 |
| 3 | btree | 익스텐트 B+트리의 뿌리 |
| 4 | uuid | 정의만 있고 쓰지 않음 |
| 5 | meta_btree | 메타데이터용 트리 |

### 데이터 포크와 익스텐트 레코드

데이터 포크는 고정 머리 바로 뒤(판 3 이면 0xB0)에서 시작하고, 속성 포크는 데이터 포크 시작에서 `di_forkoff` × 8 바이트 뒤에 있습니다[1]. 익스텐트 레코드 하나는 빅 엔디언 64비트 두 개(`l0`, `l1`), 합쳐 128비트이고, 위쪽 비트부터 아래처럼 나뉩니다[1].

| 비트 수 | 이름 | 뜻 |
|---|---|---|
| 1 | 익스텐트 플래그 | 1 이면 보통 익스텐트가 아님 |
| 54 | `startoff` | 파일 안 논리 블록 번호 |
| 52 | `startblock` | 디스크 블록 번호(할당 그룹 번호와 그룹 안 번호를 묶은 값) |
| 21 | `blockcount` | 연속 블록 수 |

### 시각 형식

아이노드 시각 필드는 모두 8바이트이고, 형식은 두 가지입니다[1].

| 형식 | 조건 | 인코딩 | 기준 시점 | 범위 |
|---|---|---|---|---|
| 옛 형식 | `di_flags2` 에 0x8 없음 | 앞 4바이트 초(부호 있음), 뒤 4바이트 나노초 | 1970-01-01 00:00:00 UTC | 1901-12-13 20:45:52 ~ 2038-01-19 03:14:07 UTC |
| bigtime | `di_flags2` 0x8(볼륨은 `sb_features_incompat` 0x8) | 부호 없는 64비트 나노초 하나 | 1901-12-13 20:45:52 UTC | ~ 2486-07-02 20:20:24 UTC |

bigtime 값은 10^9 로 나눈 몫이 기준 시점부터의 초이고, 여기서 2^31(2147483648)을 빼면 Unix 초가 됩니다[1]. 두 형식 모두 UTC 기준이고 시간대 정보는 없습니다. Unix 초를 사람이 읽는 시각으로 바꾸는 일반 방법은 [Linux 의 시각 값](../value-decoding/time-values.md) 에서 다룹니다.

V4 형식은 메타데이터 체크섬, 강화된 검증, 2038년 이후 시각 저장이 없어 폐기가 정해졌습니다[3]. V4 마운트 지원을 끄는 커널 빌드 옵션은 2025년 9월부터 기본값이 "no" 이고, 2030년 9월에 코드에서 없앨 예정입니다[3].

### 그 밖의 마법 수

트리 블록마다 마법 수가 있어서, 블록 하나만 떼어 봐도 종류를 알 수 있습니다. V5 형식은 체크섬을 넣은 새 마법 수를 씁니다[1][4].

| 종류 | V4 | V5 |
|---|---|---|
| 익스텐트 트리(BMAP) | `BMAP` | `BMA3` |
| 여유 공간 트리(블록 번호순) | `ABTB` | `AB3B` |
| 여유 공간 트리(크기순) | `ABTC` | `AB3C` |
| 아이노드 트리 | `IABT` | `IAB3` |
| 빈 아이노드 트리 | `FIBT` | `FIB3` |
| 역방향 매핑(rmap) | 없음 | `RMB3` |
| 참조 횟수(reflink) | 없음 | `R3FC` |
| 긴 심볼릭 링크 블록 | 없음 | `XSLM` |

### 로그

XFS 는 메타데이터 변경을 먼저 로그에 쓰는 선기록 로그 (Write Ahead Logging) 방식입니다[5]. 아이노드와 쿼터 정보는 디스크 구조체가 아니라 메모리 안 구조체의 변경을 논리 형식으로 적고, 그 밖의 버퍼는 바뀐 바이트를 물리 형식으로 적습니다[5]. 내부 로그는 데이터 영역 안 `sb_logstart` 블록부터 `sb_logblocks` 블록을 차지합니다[1].

로그 레코드는 512바이트 머리로 시작합니다[2].

| 오프셋 | 크기 | 이름 | 뜻 |
|---|---|---|---|
| 0x00 | 4 | `h_magicno` | `0xFEEDBABE` |
| 0x04 | 4 | `h_cycle` | 로그를 몇 바퀴째 쓰는지 |
| 0x08 | 4 | `h_version` | 로그 판(1·2) |
| 0x0C | 4 | `h_len` | 레코드 길이 |
| 0x10 | 8 | `h_lsn` | 이 레코드의 로그 순서 번호 |
| 0x18 | 8 | `h_tail_lsn` | 아직 디스크에 반영되지 않은 가장 오래된 레코드 |
| 0x20 | 4 | `h_crc` | 체크섬(리틀 엔디언) |
| 0x28 | 4 | `h_num_logops` | 이 레코드 안 작업 수 |
| 0x12C | 4 | `h_fmt` | 레코드를 쓴 CPU 의 바이트 순서(1 = 리틀 엔디언 Linux, 2 = 빅 엔디언 Linux) |
| 0x130 | 16 | `h_fs_uuid` | 볼륨 UUID |

로그 순서 번호 (Log Sequence Number, LSN) 는 64비트이고, 위쪽 32비트가 바퀴 수(cycle), 아래쪽 32비트가 로그 안 블록 번호입니다[2]. 트랜잭션 머리의 마법 수는 `TRAN`(`0x5452414e`)이고, 로그 항목 종류는 `0x1236` 익스텐트 해제 의도(EFI), `0x1237` 해제 완료(EFD), `0x1238` IUNLINK, `0x123b` 아이노드, `0x123c` 버퍼, `0x123d` 쿼터, `0x123f` 아이노드 생성, `0x1246` 확장 속성 변경 의도 등입니다[2]. 로그 안의 아이노드(`xfs_log_dinode`)는 디스크 아이노드와 배치가 거의 같지만 빅 엔디언이 아니라 기록한 CPU 의 바이트 순서로 적습니다[1].

## 읽는 법

아래 헥스는 명세로 만든 예시입니다. 블록 4096바이트, 아이노드 512바이트, 할당 그룹 4개인 16 GiB 볼륨을 가정했습니다.

```
슈퍼블록 (볼륨 0번 바이트)
00000000  58 46 53 42 00 00 10 00  00 00 00 00 00 40 00 00   XFSB.........@..
00000050  00 00 00 01 00 10 00 00  00 00 00 04 00 00 00 00   ................
00000060  00 00 0A 00 B4 A5 02 00  02 00 00 08 64 61 74 61   ............data
00000070  00 00 00 00 00 00 00 00  0C 09 09 03 14 00 00 19   ................
000000D0  00 00 00 00 00 00 00 0D  00 00 00 0B 00 00 00 00   ................
```

1. 0x00 이 `XFSB` 이면 XFS 슈퍼블록입니다. 0x04 `00 00 10 00` 은 블록 4096바이트, 0x08 `00 00 00 00 00 40 00 00` 은 4,194,304 블록(16 GiB)입니다.
2. 0x54 `00 10 00 00` 은 할당 그룹 하나가 1,048,576 블록, 0x58 `00 00 00 04` 는 그룹 4개라는 뜻입니다.
3. 0x64 `B4 A5` 의 하위 4비트가 5 라서 V5 형식이고, 0x68 `02 00` 은 아이노드 512바이트, 0x6C 부터가 레이블 `data` 입니다.
4. 0x78~0x7C 의 `0C 09 09 03 14` 는 차례로 log2(블록 크기) 12, log2(섹터) 9, log2(아이노드) 9, log2(블록당 아이노드) 3, log2(그룹 블록 수) 20 입니다. 아이노드 번호를 풀 때 3 과 20 을 씁니다.
5. 0xD8 `00 00 00 0B` 는 ftype(0x1)·sparse inode(0x2)·bigtime(0x8) 이 켜진 볼륨이라는 뜻입니다. 이 볼륨의 아이노드 시각은 bigtime 으로 읽어야 합니다.

```
아이노드 (명세로 만든 예시, 판 3)
00000000  49 4E 81 A4 03 02 00 00  00 00 03 E8 00 00 03 E8   IN..............
00000010  00 00 00 01 00 00 00 00  00 00 00 00 00 00 00 00   ................
00000020  36 53 D7 51 F5 55 CD 15  36 53 D7 51 F5 55 CD 15   6S.Q.U..6S.Q.U..
00000070  00 00 00 00 00 00 00 00  00 00 00 00 00 00 00 08   ................
```

6. `IN` 뒤 `81 A4` 는 일반 파일·권한 0644, `03` 은 아이노드 판 3, `02` 는 익스텐트 형식입니다. UID·GID 는 `0x3E8`(1000)입니다.
7. 0x78 `di_flags2` 의 마지막 바이트 `08` 로 bigtime 임을 확인합니다.
8. 0x20 `di_atime` 값 `0x3653D751F555CD15` 는 3,914,709,248,123,456,789 나노초입니다. 10^9 로 나누면 3,914,709,248초와 123,456,789나노초이고, 2,147,483,648 을 빼면 Unix 초 1,767,225,600 이 됩니다. 곧 2026-01-01 00:00:00.123456789 UTC 입니다.

같은 8바이트를 옛 형식으로 읽으면 앞 4바이트 `0x3653D751` 이 1998-11-19 08:31:13 UTC 로 풀리고, 뒤 4바이트 나노초는 4,116,040,981 이 되어 10억을 넘습니다. 나노초 필드가 999,999,999 를 넘으면 bigtime 값을 옛 형식으로 읽고 있다는 신호입니다.

## 포렌식에서 중요한 점

**메타데이터를 쓴 순서.** V5 형식은 메타데이터 블록마다 CRC32c 체크섬, 볼륨 UUID, 블록 번호, 소유자(아이노드 또는 할당 그룹), 그 블록을 마지막으로 바꾼 트랜잭션의 LSN 을 넣습니다[4]. LSN 은 볼륨을 쓰는 동안 늘기만 하고, xfs_repair 를 돌릴 때만 처음으로 돌아갑니다[4]. 그래서 아이노드의 `di_lsn`, 슈퍼블록의 `sb_lsn`, 트리 블록의 LSN 을 비교하면 어느 메타데이터를 나중에 썼는지 순서를 알 수 있습니다. 예를 들어 어떤 블록을 담은 여유 공간 트리 블록이 그 블록 자체와 그 블록의 소유자보다 나중에 쓰였다면, 그 블록은 소유자에게서 빠졌어야 했을 가능성이 큽니다[4]. LSN 은 시각이 아니라 순서라서, 시각으로 바꾸려면 같은 LSN 대의 다른 기록과 맞춰 봐야 합니다.

**만든 시각.** 판 3 아이노드에는 `di_crtime` 이 있어서 파일을 만든 시각을 알 수 있습니다[1]. 판 1·2 아이노드(V4 볼륨)에는 이 필드가 없습니다.

**지웠지만 열려 있던 파일.** AGI 에는 항목 64개짜리 목록 `agi_unlinked` 가 있고, 이름은 지웠지만 아직 누군가 참조하고 있는 아이노드를 `di_next_unlinked` 로 이어 둡니다[1]. 라이브 상태에서 뜬 이미지나 비정상 종료한 볼륨에서 이 목록에 걸린 아이노드는, 프로세스가 연 채로 지운 파일일 가능성이 있습니다.

**로그.** 로그는 메타데이터 변경을 본 위치보다 먼저 적는 곳입니다[5]. 로그 안 아이노드 기록은 디스크 아이노드와 거의 같은 배치로 들어 있으므로[1], 본 위치의 아이노드가 바뀐 뒤에도 예전 시각·크기·소유자가 로그에 남아 있을 수 있습니다. 로그 레코드 `h_fmt` 로 그 안 아이노드의 바이트 순서를 먼저 확인합니다[2].

**지운 파일.** XFS 에서 파일을 지운 뒤 아이노드와 디렉터리 항목에 무엇이 남는지는 실제 데이터로 직접 확인합니다. 빈 아이노드 자리에 `IN` 마법 수와 익스텐트 레코드가 남아 있는지, 디렉터리 블록의 빈 공간에 예전 항목이 남아 있는지를 봅니다. The Sleuth Kit 의 XFS 코드는 할당되지 않은 파일을 읽으려고, 디렉터리가 아닌 파일의 아이노드 크기가 0 이면 데이터 포크에 남은 첫 익스텐트 레코드의 블록 수 × 블록 크기로 크기를 잡습니다[9]. 이 방식은 지운 아이노드에 익스텐트 레코드가 남아 있다고 가정하므로, 도구가 보여 준 크기와 내용은 헥스로 한 번 대조합니다. 복구 절차는 [지운 파일 되살리기](../../03-techniques/analysis/file-recovery.md) 에서 다룹니다.

**비정상 종료.** 깨끗하게 내리지 않은 볼륨을 로그 복구 없이 마운트하면 메타데이터가 서로 맞지 않을 수 있고, 일부 파일·디렉터리를 열지 못할 수 있습니다[3].

증명하는 것과 증명하지 못하는 것은 아래와 같습니다.

| 증명하는 것 | 증명하지 못하는 것 |
|---|---|
| 아이노드에 적힌 소유자 UID·GID, 크기, 네 가지 시각(판 3 은 만든 시각 포함) | 그 UID 를 실제로 쓴 사람. UID 와 계정 연결은 [UID·GID 와 사용자 이름 잇기](../value-decoding/uid-gid.md) 에서 다룹니다 |
| LSN 으로 본 메타데이터 블록끼리의 쓰기 순서 | LSN 만으로 알 수 있는 실제 시각 |
| AGI 목록에 걸린 아이노드가 지운 뒤에도 참조되고 있었다는 사실 | 어느 프로세스가 열고 있었는지 |
| 빈 아이노드 자리에 남은 `IN` 머리와 익스텐트 레코드 | 그 흔적이 지운 파일의 마지막 상태라는 것. 그 자리를 다시 쓴 파일의 값일 수 있습니다 |

## 함정

- bigtime 볼륨의 시각을 Unix 초로 바로 읽으면 기준 시점이 1901년이라 약 68년 어긋납니다. 앞 예시처럼 옛 형식으로 잘못 읽으면 전혀 다른 연도가 나옵니다[1]. 볼륨의 `sb_features_incompat` 0x8 과 아이노드 `di_flags2` 0x8 을 먼저 봅니다.
- 옛 형식 시각은 2038-01-19 03:14:07 UTC 를 넘길 수 없습니다[1]. V4 볼륨에서 그 뒤 시각이 보이면 도구가 값을 잘못 읽었는지부터 확인합니다.
- 체크섬 필드(`sb_crc`, `di_crc`, `bb_crc`, `h_crc`)는 리틀 엔디언이고, 로그 안 아이노드는 기록한 CPU 의 바이트 순서를 따릅니다[1][2]. 빅 엔디언 가정을 모든 바이트에 적용하면 이 부분을 틀리게 읽습니다.
- 아이노드 번호와 익스텐트의 블록 번호는 할당 그룹 번호를 비트로 묶은 값이라, 블록 크기를 곱하는 것만으로는 바이트 위치가 나오지 않습니다[1].
- `norecovery` 없이 마운트하면 로그 복구가 일어나 메타데이터가 바뀔 수 있습니다[3]. `norecovery` 옵션은 로그 복구 없이 마운트하며 읽기 전용일 때만 쓸 수 있고, `nouuid` 는 같은 UUID 중복 검사를 건너뜁니다. 두 옵션은 LVM 스냅숏을 읽기 전용으로 붙일 때 함께 씁니다[3]. 원본과 같은 UUID 의 사본을 분석 PC 에 붙일 때 `nouuid` 가 필요한 경우가 있습니다.
- xfs_repair 를 돌리면 LSN 이 초기화되어 쓰기 순서 비교가 끊깁니다[4]. 사본에서만 돌립니다.

## 도구

- xfs_info: 마운트 지점을 넣어 돌리고 출력에서 `crc=` 가 들어간 문자열로 V4 볼륨인지 확인합니다. 이 문자열이 아예 없으면 xfsprogs 를 최신 판으로 올려 다시 돌립니다[3].
- xfs_db: 메타데이터를 직접 살펴보는 도구이고, 손상 원인을 손으로 분석할 때 씁니다[4].
- The Sleuth Kit(fls·istat·icat): XFS 를 지원합니다. 시각은 옛 형식(`t_sec`·`t_nsec`)으로만 읽고 `di_crtime` 과 bigtime 을 처리하는 코드가 없으므로, bigtime 볼륨에서는 시각을 헥스로 다시 풉니다[9]. 데이터 포크 형식은 local·extents·btree 만 읽고 나머지는 "not supported" 를 출력합니다[9]. 디렉터리 데이터 블록은 V5 마법 수 `XDB3` 일 때만 블록 형식으로 풀고, 아니면 짧은 형식(shortform)으로 읽어 봅니다[9].
- dissect.xfs: Python 으로 XFS 를 읽는 라이브러리입니다[10]. dissect.target 은 이미지 안 XFS 볼륨의 UUID·레이블을 `/etc/fstab` 과 맞춰 마운트 지점에 붙입니다[11].

타임라인에 넣는 방법은 [타임라인 만들기](../../03-techniques/analysis/timeline.md), ext4·Btrfs 와의 비교는 [ext4](ext4/index.md)·[Btrfs](btrfs.md) 페이지에서 봅니다.
