# 페이지와 레코드 (B-tree·Record)

SQLite 데이터베이스 파일은 같은 크기의 페이지로 나뉘고, 표와 인덱스는 이 페이지들을 엮은 B-트리 (B-tree)에 들어가며, 행 하나는 칸마다 직렬 타입을 적은 레코드 (record)가 되어 셀 (cell) 안에 저장됩니다 [1].

## 파일 전체의 모양

파일 맨 앞 100바이트가 데이터베이스 헤더이고, 첫 16바이트는 문자열 `SQLite format 3\000` 입니다 [1]. 표와 인덱스는 모두 B-트리로 저장하고, 1번 페이지가 `sqlite_schema` 표의 루트 페이지입니다 [1]. 1번 페이지만은 100바이트 헤더 바로 뒤에서 B-트리 페이지 헤더가 시작하고, 나머지 페이지는 페이지 첫 바이트부터 B-트리 페이지 헤더입니다 [1].

`sqlite_schema` 표에는 DB 안의 표·인덱스·뷰·트리거가 한 행씩 들어 있어서, 어떤 표가 몇 번 페이지에서 시작하는지를 여기서 찾습니다 [1]. 이 표는 `sqlite_master` 라는 이름으로도 부를 수 있습니다 [1].

| 칸 | 내용 |
|---|---|
| type | `table`, `index`, `view`, `trigger` 가운데 하나 |
| name | 객체 이름. 자동으로 만든 인덱스는 `sqlite_autoindex_TABLE_N` 모양 |
| tbl_name | 이 객체가 딸린 표 이름 |
| rootpage | B-트리 루트 페이지 번호. 뷰·트리거는 0 또는 NULL |
| sql | 객체를 만든 `CREATE` 문. 자동 인덱스는 NULL |

## 데이터베이스 헤더 (100바이트)

여러 바이트로 된 정수는 모두 빅엔디언입니다 [1].

| 오프셋 | 크기 | 내용 |
|---|---|---|
| 0 | 16 | 매직 문자열 `SQLite format 3\000` |
| 16 | 2 | 페이지 크기. 512~32768 사이의 2의 거듭제곱이고, 값 1은 65536 |
| 18 | 1 | 쓰기 형식 버전. 1=레거시(롤백 저널), 2=WAL |
| 19 | 1 | 읽기 형식 버전. 뜻은 18과 같음 |
| 20 | 1 | 페이지 끝의 예약 바이트 수(보통 0) |
| 21 | 1 | 최대 페이로드 비율, 64로 고정 |
| 22 | 1 | 최소 페이로드 비율, 32로 고정 |
| 23 | 1 | 리프 페이로드 비율, 32로 고정 |
| 24 | 4 | 파일 변경 카운터. 수정한 뒤 잠금을 풀 때 늘어남 |
| 28 | 4 | DB 크기(페이지 수) |
| 32 | 4 | 첫 프리리스트 트렁크 페이지 번호(없으면 0) |
| 36 | 4 | 프리리스트 페이지 총수 |
| 40 | 4 | 스키마 쿠키. 스키마가 바뀔 때 늘어남 |
| 44 | 4 | 스키마 형식 번호(1~4) |
| 48 | 4 | 권장 캐시 크기 |
| 52 | 4 | 가장 큰 루트 B-트리 페이지 번호. auto-vacuum·incremental-vacuum일 때만 0이 아님 |
| 56 | 4 | 텍스트 인코딩. 1=UTF-8, 2=UTF-16le, 3=UTF-16be |
| 60 | 4 | user_version |
| 64 | 4 | 0이 아니면 incremental vacuum 모드 |
| 68 | 4 | application_id |
| 72 | 20 | 예약(0) |
| 92 | 4 | version-valid-for 번호. 24의 변경 카운터와 같을 때만 96의 값이 유효 |
| 96 | 4 | 마지막으로 이 DB를 수정한 SQLite의 `SQLITE_VERSION_NUMBER` |

페이지에서 실제로 쓸 수 있는 크기 U는 페이지 크기에서 20번 오프셋의 예약 바이트 수를 뺀 값이고, U는 480 이상이어야 합니다 [1]. 뒤에 나오는 오버플로 계산과 포인터 맵 계산은 모두 이 U를 씁니다.

18·19번 바이트가 2이면 WAL 모드라서 DB 파일만으로는 최신 상태가 아닐 수 있고, 그 이야기는 [WAL과 저널 (WAL·Journal)](wal-journal.md)에서 다룹니다. 32·36·52·64번 칸은 지운 레코드가 남아 있을지 가늠하는 단서이고, [지운 레코드 되살리기 (Freelist·Freeblock)](freelist-freeblock.md)에서 이어서 설명합니다.

## B-트리 페이지 헤더

B-트리 페이지 헤더는 리프 페이지에서 8바이트, 내부 페이지 (interior page)에서 12바이트입니다 [1].

| 오프셋 | 크기 | 내용 |
|---|---|---|
| 0 | 1 | 페이지 종류. `0x02`=인덱스 내부, `0x05`=표 내부, `0x0a`=인덱스 리프, `0x0d`=표 리프 |
| 1 | 2 | 첫 프리블록의 오프셋(없으면 0) |
| 3 | 2 | 셀 개수 |
| 5 | 2 | 셀 내용 영역이 시작하는 오프셋(0이면 65536) |
| 7 | 1 | 조각난 빈 바이트(fragment)의 합계, 최대 60 |
| 8 | 4 | 가장 오른쪽 자식 페이지 번호(내부 페이지만) |

헤더 바로 뒤에는 셀 포인터 배열이 옵니다. 셀마다 2바이트 오프셋이 하나씩 키 순서대로 놓이고, 이 오프셋이 가리키는 곳에 셀 본문이 있습니다 [1].

## 셀 형식

셀의 모양은 페이지 종류에 따라 다릅니다 [1].

| 페이지 종류 | 셀 구성 |
|---|---|
| 표 리프 (`0x0d`) | varint 전체 페이로드 크기, varint 정수 키(rowid), 페이로드 앞부분, 넘치면 4바이트 첫 오버플로 페이지 번호 |
| 표 내부 (`0x05`) | 4바이트 왼쪽 자식 페이지 번호, varint 정수 키 |
| 인덱스 리프 (`0x0a`) | varint 페이로드 크기, 페이로드, 넘치면 4바이트 오버플로 페이지 번호 |
| 인덱스 내부 (`0x02`) | 4바이트 왼쪽 자식 페이지 번호, varint 페이로드 크기, 페이로드, 넘치면 오버플로 페이지 번호 |

표의 실제 행은 표 리프 페이지에 있고, 표 내부 페이지에는 자식 페이지로 내려가는 번호와 키만 있습니다 [1].

varint는 1~9바이트 길이의 가변 길이 정수이고, 앞 8바이트는 하위 7비트씩, 9번째 바이트는 8비트를 모두 써서 64비트 부호 있는 정수를 만듭니다 [1].

### 오버플로

페이로드가 페이지 하나에 다 들어가지 않으면 앞부분만 셀에 두고 나머지를 오버플로 페이지로 넘깁니다. 표 리프 셀의 기준은 아래와 같고, P는 페이로드 크기입니다 [1].

```
X = U - 35
M = ((U - 12) * 32 / 255) - 23
K = M + ((P - M) % (U - 4))

P <= X  이면 페이로드 전부를 페이지 안에 둔다
P >  X  이고 K <= X 이면 K바이트를 페이지에 두고 나머지는 오버플로
그 밖에는 M바이트만 페이지에 두고 나머지는 오버플로
```

인덱스 셀은 X만 `((U - 12) * 64 / 255) - 23` 으로 바뀝니다 [1]. 오버플로 페이지는 첫 4바이트가 다음 오버플로 페이지 번호(마지막이면 0)이고 나머지가 내용입니다 [1].

## 레코드 형식

페이로드 안의 레코드는 헤더와 본문으로 나뉩니다. 헤더는 자기 자신까지 포함한 헤더 크기(varint)로 시작하고, 이어서 칸마다 직렬 타입 (serial type)이 varint로 하나씩 오며, 그 뒤에 칸 값이 같은 순서로 붙습니다 [1].

| 직렬 타입 | 뜻 | 본문 크기 |
|---|---|---|
| 0 | NULL | 0 |
| 1 | 8비트 정수 | 1 |
| 2 | 16비트 정수 | 2 |
| 3 | 24비트 정수 | 3 |
| 4 | 32비트 정수 | 4 |
| 5 | 48비트 정수 | 6 |
| 6 | 64비트 정수 | 8 |
| 7 | IEEE 754 64비트 실수 | 8 |
| 8 | 정수 0 (스키마 형식 4 이상) | 0 |
| 9 | 정수 1 (스키마 형식 4 이상) | 0 |
| 10, 11 | 예약 | — |
| 12 이상 짝수 N | BLOB | (N−12)/2 |
| 13 이상 홀수 N | TEXT | (N−13)/2 |

정수는 모두 빅엔디언 부호 있는 값입니다 [1]. 헤더의 직렬 타입만 읽어도 칸이 몇 개이고 칸마다 몇 바이트인지 알 수 있어서, 지워진 레코드를 카빙할 때 이 헤더 모양이 단서가 됩니다. 이 점은 [1]의 형식 정의에서 끌어낸 해석이고, 카빙 쪽 이야기는 [지운 레코드 되살리기 (Freelist·Freeblock)](freelist-freeblock.md)에 있습니다.

## 그 밖의 페이지

잠금 바이트 페이지 (lock-byte page)는 파일 오프셋 1,073,741,824~1,073,742,335 구간에 있는 페이지이고, 파일이 1,073,741,824바이트보다 클 때만 생기며 SQLite 코어가 읽지도 쓰지도 않습니다 [1].

포인터 맵 (ptrmap) 페이지는 헤더 52번 칸이 0이 아닌 auto-vacuum DB에만 있고, 첫 포인터 맵은 2번 페이지입니다 [1]. 항목 하나는 종류 1바이트와 페이지 번호 4바이트를 합한 5바이트이고, 페이지 하나에 U/5개가 들어갑니다 [1].

| 종류 값 | 뜻 |
|---|---|
| 1 | B-트리 루트 페이지 |
| 2 | 프리리스트 페이지 |
| 3 | 첫 오버플로 페이지 |
| 4 | 이어지는 오버플로 페이지 |
| 5 | 루트가 아닌 B-트리 페이지 |

## 읽는 법

### 헥스로 한 번

아래 바이트는 실제 검체가 아니라 명세 [1]에 맞춰 만든 예시입니다. 먼저 파일 맨 앞 32바이트이고, `NN` 과 `PP` 는 DB마다 달라지는 변경 카운터와 페이지 수 자리입니다.

```
오프셋  00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F
000000  53 51 4C 69 74 65 20 66 6F 72 6D 61 74 20 33 00   SQLite format 3.
000010  10 00 02 02 00 40 20 20 NN NN NN NN PP PP PP PP   .....@  ........
```

0x10의 `10 00` 은 페이지 크기 4096이고, 0x12·0x13의 `02 02` 는 WAL 모드, 0x14의 `00` 은 예약 바이트 없음이라서 U도 4096입니다. 0x15~0x17의 `40 20 20` 은 고정값 64·32·32입니다.

다음은 페이지 크기 4096인 DB에서 1번이 아닌 표 리프 페이지 하나를 페이지 시작 기준 오프셋으로 본 모습이고, 셀이 하나 들어 있습니다.

```
페이지 내 오프셋
0000  0D 00 00 00 01 0F F5 00 0F F5 ...
...
0FF5  09 05 04 13 02 00 61 62 63 01 2C
```

1. 0x0000의 `0D` 는 표 리프 페이지라서 페이지 헤더가 8바이트입니다.
2. `00 00` 은 프리블록 없음, `00 01` 은 셀 1개, `0F F5` 는 셀 내용 영역이 0x0FF5에서 시작한다는 뜻이고, `00` 은 조각 바이트 0입니다.
3. 헤더 바로 뒤 셀 포인터 배열의 `0F F5` 를 따라 0x0FF5로 갑니다.
4. 셀의 `09` 는 페이로드 9바이트, `05` 는 rowid 5입니다. 이 예시의 varint는 모두 한 바이트짜리입니다.
5. 페이로드의 `04` 는 레코드 헤더 4바이트이고, 이어지는 직렬 타입 `13`(19)은 3바이트 TEXT, `02` 는 16비트 정수, `00` 은 NULL입니다.
6. 본문 `61 62 63` 은 `abc`, `01 2C` 는 300이고, NULL 칸은 본문이 없습니다. 헤더 4바이트와 본문 5바이트를 더하면 페이로드 크기 9와 맞습니다.

페이로드 9바이트는 X = 4096 − 35보다 작아서 오버플로 없이 페이지 안에 다 들어갑니다.

### 공개 도구로 한 번

공개 도구 sqlite3 셸로 증거의 작업 사본을 열어 `sqlite_schema` 를 조회하면, 헥스에서 어느 페이지부터 봐야 하는지 알 수 있습니다.

```sql
SELECT type, name, tbl_name, rootpage FROM sqlite_schema;
```

셸 버전에 따라 `sqlite_schema` 라는 이름이 통하지 않으면 `sqlite_master` 로 바꿔 씁니다. WAL 모드 DB를 이렇게 열 때 생길 수 있는 변화는 [WAL과 저널 (WAL·Journal)](wal-journal.md)에서 먼저 확인합니다.

## 포렌식에서 중요한 점

헤더 96번 칸에는 마지막으로 DB를 수정한 SQLite의 버전 번호가 남지만, 92번 칸이 24번 변경 카운터와 같을 때만 유효한 값입니다 [1]. 24번 변경 카운터와 40번 스키마 쿠키는 수정과 스키마 변경이 있을 때 늘어나는 값이라서, 같은 DB의 두 사본을 비교할 때 어느 쪽이 나중 상태인지 가늠하는 데 참고할 수 있습니다(형식 정의에서 끌어낸 해석). 다만 WAL 모드에서는 변경 카운터가 트랜잭션마다 늘지 않을 수 있다고 명세가 밝히고 있어서 [1], WAL 모드 DB에서는 이 값만으로 앞뒤를 정하지 않습니다.

레코드가 지워지거나 페이지가 비워져도 페이지 구조와 레코드 헤더 모양이 남아 있으면 그 자리를 해석할 수 있고, 어디에 무엇이 남는지는 [지운 레코드 되살리기 (Freelist·Freeblock)](freelist-freeblock.md)에서 다룹니다.

## 함정

페이지 크기 칸의 값 1은 65536을 뜻하고, 페이지 헤더의 셀 내용 영역 시작 값 0도 65536을 뜻합니다 [1]. 두 경우 모두 값을 그대로 읽으면 크기가 엉뚱하게 나옵니다.

직렬 타입 8과 9는 본문 없이 정수 0과 1을 나타내지만 스키마 형식 4 이상에서만 쓰입니다 [1]. 레코드 헤더를 손으로 풀 때 본문 바이트 수를 잘못 세기 쉬운 부분입니다.

1GiB를 넘는 DB에서는 잠금 바이트 페이지를 SQLite가 쓰지 않아서 [1], 그 페이지를 다른 페이지처럼 B-트리 구조로 해석하지 않습니다.
