# WAL과 저널 (WAL·Journal)

SQLite는 트랜잭션을 안전하게 끝내려고 DB 파일 옆에 롤백 저널 (rollback journal)이나 WAL (Write-Ahead Log)을 두고, 롤백 저널에는 바뀌기 전의 페이지가, WAL에는 아직 DB 파일로 옮기지 않은 새 페이지와 같은 페이지의 여러 과거 버전이 남습니다 [1][2].

## 딸린 파일

DB 파일과 같은 디렉터리에 아래 이름으로 생깁니다 [1].

```
<DB이름>-journal   롤백 저널
<DB이름>-wal       WAL
<DB이름>-shm       WAL 인덱스
```

어느 파일이 생기는지는 저널 모드 (journal_mode)가 정하고, 모드마다 트랜잭션이 끝날 때 저널을 처리하는 방식이 다릅니다 [3].

| journal_mode | 트랜잭션이 끝날 때 | 파일에 남는 것 |
|---|---|---|
| DELETE (기본) | 저널 파일을 지움 | 파일 자체가 없어짐 |
| TRUNCATE | 저널을 0바이트로 자름 | 빈 파일 |
| PERSIST | 저널 헤더만 0으로 덮음 | 헤더 뒤의 본문(이전 페이지 내용)은 남음 |
| MEMORY | 저널을 메모리에만 둠 | 없음 |
| WAL | WAL 파일을 씀 | `-wal`, `-shm` |
| OFF | 저널을 쓰지 않음 | 없음 |

`journal_size_limit` 는 커밋이나 체크포인트 뒤에 남은 저널·WAL을 정해 둔 크기로 자르는 설정이고, 기본값 −1은 제한 없음입니다 [3].

WAL은 SQLite 3.7.0(2010-07-21)부터 쓸 수 있고 `PRAGMA journal_mode=WAL` 로 켭니다 [2]. 다른 저널 모드와 달리 WAL 설정은 DB 안에 남아서 다시 열어도 WAL 모드이고, 이때 DB 헤더 18·19번 바이트가 1에서 2로 바뀝니다 [2]. 헤더 필드 전체는 [페이지와 레코드 (B-tree·Record)](b-tree-record.md)에 있습니다. macOS의 Core Data 저장소가 WAL을 기본으로 쓰는 점은 [Core Data 저장소 (Core Data)](core-data.md)에서 다룹니다.

## 롤백 저널 구조

헤더는 32바이트이고, 섹터 경계까지는 0으로 채웁니다 [1].

| 오프셋 | 크기 | 내용 |
|---|---|---|
| 0 | 8 | 매직 `d9 d5 05 f9 20 a1 63 d7` |
| 8 | 4 | 이 구간의 페이지 레코드 수(−1이면 파일 끝까지) |
| 12 | 4 | 체크섬 계산용 난수(nonce) |
| 16 | 4 | 트랜잭션을 시작할 때의 DB 크기(페이지 수) |
| 20 | 4 | 섹터 크기 |
| 24 | 4 | 페이지 크기 |

헤더 뒤로는 페이지 레코드가 이어지고, 레코드 하나는 4바이트 페이지 번호와 트랜잭션 전 원래 페이지 내용, 4바이트 체크섬으로 되어 있습니다 [1]. 롤백 저널에 담기는 내용은 바뀐 뒤가 아니라 바뀌기 전의 페이지입니다.

트랜잭션이 끝나지 않은 채 멈춰 남은 저널을 핫 저널 (hot journal)이라고 하고, 다음에 누군가 DB를 열면 SQLite가 이 저널로 자동 롤백합니다 [1].

## WAL 구조

WAL 파일은 32바이트 헤더 뒤에 프레임이 이어지는 모양이고, 헤더 값은 빅엔디언입니다 [1].

| 오프셋 | 크기 | 내용 |
|---|---|---|
| 0 | 4 | 매직 `0x377f0682` 또는 `0x377f0683` |
| 4 | 4 | 형식 버전 3007000 |
| 8 | 4 | 페이지 크기 |
| 12 | 4 | 체크포인트 순번 |
| 16 | 4 | salt-1 |
| 20 | 4 | salt-2 |
| 24 | 4 | 체크섬-1 |
| 28 | 4 | 체크섬-2 |

매직의 끝자리는 체크섬을 계산할 때의 바이트 순서를 나타내서, `0682` 는 리틀엔디언, `0683` 은 빅엔디언입니다 [1].

프레임 하나는 24바이트 프레임 헤더와 페이지 하나로 되어 있습니다 [1].

| 오프셋 | 크기 | 내용 |
|---|---|---|
| 0 | 4 | 페이지 번호 |
| 4 | 4 | 커밋 프레임이면 커밋 뒤 DB 크기(페이지 수), 아니면 0 |
| 8 | 4 | salt-1 |
| 12 | 4 | salt-2 |
| 16 | 4 | 체크섬-1 |
| 20 | 4 | 체크섬-2 |

프레임이 유효하려면 프레임의 salt 두 개가 WAL 헤더의 salt와 같아야 하고, WAL 헤더 앞 24바이트와 각 프레임 헤더 앞 8바이트, 페이지 내용을 차례로 누적한 체크섬도 맞아야 합니다 [1]. 오프셋 4의 값이 0이 아닌 프레임이 커밋 프레임이고 트랜잭션의 경계입니다 [1].

같은 페이지가 WAL에 여러 번 들어갈 수 있고, 읽는 쪽은 자기가 본 끝 표시 이전의 마지막 사본을 씁니다 [2]. 한 페이지의 여러 과거 버전이 WAL에 나란히 남는 이유가 여기에 있습니다.

### 체크포인트와 WAL 재시작

체크포인트 (checkpoint)는 WAL의 내용을 DB 파일로 옮기는 작업입니다 [2]. 자동 체크포인트는 기본적으로 커밋 뒤 WAL이 1000페이지 이상이 될 때나 마지막 연결이 닫힐 때 일어나고, `wal_autocheckpoint` 로 기준을 바꾸거나 끌 수 있습니다 [2]. 모드는 PASSIVE, FULL, RESTART, TRUNCATE, NOOP이고 자동 체크포인트는 PASSIVE이며, TRUNCATE는 RESTART 뒤 WAL 파일을 0바이트로 자릅니다 [2][3].

체크포인트는 보통 WAL 파일을 자르지 않습니다(`journal_size_limit` 를 정한 경우는 예외) [2]. 완전한 체크포인트 뒤에 새 쓰기가 시작되면 salt-1을 1 올리고 salt-2를 새 난수로 바꾼 다음 WAL 앞부분부터 덮어쓰는데, 뒤쪽의 옛 프레임은 파일에 남아 있어도 salt가 달라 무효로 처리됩니다 [1][2]. 그래서 옛 salt로 된 프레임 안에 과거 데이터가 남아 있을 수 있습니다.

마지막 연결이 정상적으로 닫히면 SQLite는 체크포인트를 한 뒤 보통 `-wal` 과 `-shm` 을 지우고, 비정상 종료했거나 `SQLITE_FCNTL_PERSIST_WAL` 을 쓴 경우에는 두 파일이 남습니다 [2].

## WAL 인덱스 (-shm)

`-shm` 은 페이지 P에 대해 최대 프레임 M 이하에서 가장 큰 프레임을 빠르게 찾으려는 색인이고, mxFrame 값이 들어 있습니다 [1]. 일시적인 구조라서 충돌 뒤에는 WAL을 보고 다시 만들고, 복구에는 DB와 WAL만 있으면 됩니다 [1]. 여러 바이트 값은 빅엔디언이 아니라 그 시스템 고유의 바이트 순서로 저장합니다 [1].

## 읽는 법

### 헥스로 한 번

아래 바이트는 실제 데이터가 아니라 명세 [1]에 맞춰 만든 예시입니다. 페이지 크기 4096인 WAL의 앞부분이고, `KK` 는 체크포인트 순번, `S1`·`S2` 는 salt, `C1`·`C2` 는 체크섬 자리입니다.

```
오프셋  00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F
000000  37 7F 06 82 00 2D E2 18 00 00 10 00 KK KK KK KK
000010  S1 S1 S1 S1 S2 S2 S2 S2 C1 C1 C1 C1 C2 C2 C2 C2
000020  00 00 00 02 00 00 00 00 S1 S1 S1 S1 S2 S2 S2 S2
000030  C1 C1 C1 C1 C2 C2 C2 C2 (페이지 2의 내용 4096바이트)
...
001038  00 00 00 01 00 00 00 03 S1 S1 S1 S1 S2 S2 S2 S2
001048  C1 C1 C1 C1 C2 C2 C2 C2 (페이지 1의 내용 4096바이트)
```

1. 0x00의 `37 7F 06 82` 는 WAL 매직이고 체크섬은 리틀엔디언 순서로 계산합니다. `00 2D E2 18` 은 형식 버전 3007000, `00 00 10 00` 은 페이지 크기 4096입니다.
2. 0x10~0x17의 salt 두 개를 적어 둡니다. 프레임마다 이 값과 비교합니다.
3. 0x20에서 첫 프레임 헤더가 시작합니다. 페이지 번호 2이고 오프셋 4의 값이 0이라서 커밋 프레임이 아닙니다.
4. 프레임 하나가 24 + 4096바이트라서 다음 프레임은 0x1038에서 시작합니다. 페이지 번호 1이고 커밋 뒤 DB 크기 3이 적혀 있어서, 여기까지가 한 트랜잭션입니다.
5. salt가 헤더와 다른 프레임이 뒤에 나오면 이전 세대의 프레임이라서 SQLite는 쓰지 않지만, 과거 데이터를 찾는 분석에서는 따로 모아 둡니다.

프레임 안의 페이지는 DB 파일의 페이지와 같은 구조라서 [페이지와 레코드 (B-tree·Record)](b-tree-record.md)의 방법으로 풉니다.

## 포렌식에서 중요한 점

### 수집하고 여는 방법

DB 파일만 확보하면 WAL에 있던 최신 트랜잭션과 과거 버전을 놓치게 되어, `-wal` 과 `-shm`, `-journal` 을 DB와 함께 확보합니다. SQLite는 `-shm` 과 `-wal` 이 이미 있고 읽을 수 있거나, 디렉터리에 쓰기 권한이 있거나, `immutable` URI 파라미터로 열 때 읽기 전용 매체의 WAL DB를 읽을 수 있습니다 [2]. 증거 사본을 쓰기 가능한 곳에서 평범하게 열었다가 닫으면 체크포인트가 일어나 WAL이 DB 파일로 합쳐지고 `-wal` 이 지워질 수 있습니다 [2]. 롤백 저널 쪽도 같아서, 핫 저널이 있는 DB를 열면 자동 롤백으로 DB 내용이 바뀝니다 [1].

원본은 그대로 두고 해시를 남긴 뒤 작업 사본에서만 열고, 열기 전 상태의 `-wal` 과 `-journal` 은 헥스나 전용 도구로 먼저 따로 읽어 둡니다. 확보 절차 전반은 [맥 증거 확보 (Acquisition)](../../../03-techniques/process-acquisition/evidence-acquisition/index.md)에서 다룹니다.

### 무엇이 과거 데이터인가

롤백 저널에는 트랜잭션 전의 페이지 원본이 남고, PERSIST 모드에서는 헤더만 0으로 덮여 본문이 남습니다 [1][3]. WAL에는 같은 페이지의 여러 버전과 salt가 바뀐 옛 프레임이 남습니다 [1][2]. 이런 페이지에서 지운 레코드를 찾는 방법은 [지운 레코드 되살리기 (Freelist·Freeblock)](freelist-freeblock.md)에서 이어집니다.

WAL 헤더와 프레임 헤더, 저널 헤더의 필드에는 시각이 없습니다 [1]. 프레임 순서와 체크포인트 순번으로 앞뒤 순서는 알 수 있지만, 각 버전이 언제 쓰였는지는 페이지 안 레코드의 시각 열이나 파일 시스템 시각 같은 다른 기록으로 맞춰야 합니다.

## 함정

`-wal` 파일이 없다고 WAL 모드가 아니었다고 단정하지 않습니다. 정상 종료하면 SQLite가 보통 `-wal` 을 지우기 때문에 [2] DB 헤더 18·19번 바이트로 모드를 확인합니다.

WAL 파일이 크다고 옮기지 않은 데이터가 많다는 뜻은 아닙니다. 체크포인트는 보통 WAL을 자르지 않고 재시작 뒤에는 앞부분부터 덮어쓰기 때문에 [2], 파일 뒤쪽은 무효가 된 옛 프레임일 수 있습니다.

WAL 헤더의 매직 끝자리는 체크섬 계산 순서일 뿐이고 헤더 값 자체는 빅엔디언입니다 [1]. 반대로 `-shm` 은 시스템 고유 바이트 순서라서 [1], 두 파일을 같은 방식으로 읽으면 값이 틀어집니다.

PERSIST 모드의 저널은 헤더가 0이라서 매직으로 찾으면 걸리지 않지만 본문에는 이전 페이지가 남아 있습니다 [3].

## 도구

공개 도구 sqlite3 셸로 작업 사본을 열어 `PRAGMA journal_mode;` 로 현재 모드를 확인할 수 있습니다 [3]. WAL과 롤백 저널 안의 레코드를 따로 꺼내 보는 공개 도구 예로 FQLite가 있고 [4], 사용할 때의 주의점은 [지운 레코드 되살리기 (Freelist·Freeblock)](freelist-freeblock.md)에 정리했습니다.
