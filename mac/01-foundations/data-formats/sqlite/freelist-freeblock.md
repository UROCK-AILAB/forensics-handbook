# 지운 레코드 되살리기 (Freelist·Freeblock)

SQLite는 기본 설정에서 지운 내용을 0으로 덮지 않아서 [2], 빈 페이지 목록인 프리리스트 (freelist)와 페이지 안의 빈 공간인 프리블록 (freeblock), 저널과 WAL에 지운 레코드가 남을 수 있고, 남는 양은 `secure_delete` 와 `auto_vacuum` 설정에 따라 달라집니다.

## 지운 데이터가 남는 곳

| 위치 | 남을 수 있는 것 | 자세히 |
|---|---|---|
| 프리리스트 리프 페이지 | 쓰지 않게 된 페이지 전체의 이전 내용 | 이 페이지 |
| 프리블록·조각 | B-트리 페이지 안에서 비워진 셀 자리 | 이 페이지 |
| 롤백 저널 | 트랜잭션 전의 페이지 원본 | [WAL과 저널 (WAL·Journal)](wal-journal.md) |
| WAL | 같은 페이지의 여러 버전, salt가 바뀐 옛 프레임 | [WAL과 저널 (WAL·Journal)](wal-journal.md) |

페이지·셀·레코드의 기본 구조는 [페이지와 레코드 (B-tree·Record)](b-tree-record.md)에 있고, 이 페이지는 그 구조를 안다고 보고 빈 공간 쪽만 다룹니다.

## 프리리스트

프리리스트는 DB 안에서 쓰지 않는 페이지의 목록입니다 [1]. DB 헤더 32번 오프셋에 첫 트렁크 페이지 번호가, 36번 오프셋에 프리리스트 페이지 총수가 들어 있고 [1], sqlite3 셸에서는 `PRAGMA freelist_count;` 로 페이지 수를 볼 수 있습니다 [2].

프리리스트는 트렁크 페이지 (trunk page)가 사슬로 이어지고, 트렁크 페이지마다 리프 페이지 (leaf page) 번호를 적는 구조입니다 [1].

| 트렁크 페이지 오프셋 | 크기 | 내용 |
|---|---|---|
| 0 | 4 | 다음 트렁크 페이지 번호(마지막이면 0) |
| 4 | 4 | 이 페이지에 적힌 리프 페이지 번호의 개수 L |
| 8 | 4 × L | 리프 페이지 번호 |

명세는 프리리스트 리프 페이지에 담긴 정보가 없다고 정의하고, SQLite는 입출력을 줄이려고 이 페이지를 읽지도 쓰지도 않으며 내용도 정해 두지 않습니다 [1]. 이 정의대로라면 리프 페이지에는 프리리스트로 들어가기 전의 내용이 그대로 남아 있을 수 있고, 이 해석은 형식 정의에서 끌어낸 것입니다. 그래서 리프 페이지 첫 바이트가 B-트리 페이지 종류 값(`0x0d` 등)이면, 예전에 쓰던 B-트리 페이지로 보고 셀 포인터와 레코드를 풀어 볼 만합니다.

## 프리블록과 조각

프리블록은 B-트리 페이지 안의 빈 공간을 잇는 사슬이고, 첫 프리블록의 위치는 페이지 헤더 오프셋 1에 적혀 있습니다 [1]. 프리블록마다 4바이트 머리가 붙습니다 [1].

| 프리블록 오프셋 | 크기 | 내용 |
|---|---|---|
| 0 | 2 | 다음 프리블록의 오프셋(마지막이면 0) |
| 2 | 2 | 머리를 포함한 이 프리블록의 크기(최소 4) |

조각 (fragment)은 셀 내용 영역 안에 생긴 1~3바이트의 빈 틈이고, 페이지 안 조각의 합계는 페이지 헤더 오프셋 7에 최대 60까지 기록됩니다 [1].

프리블록 머리 뒤의 바이트는 비워지기 전 셀의 내용일 수 있지만, 레코드를 지웠을 때 셀의 어느 부분까지 남는지는 참고 문헌으로 확인하지 못했습니다. 레코드 헤더의 직렬 타입 줄이 남아 있으면 칸 수와 칸 길이를 맞춰 볼 수 있어서 이 모양이 카빙의 단서가 되고, 이 점은 [1]의 레코드 형식 정의에서 끌어낸 해석입니다.

## 남는 양을 정하는 설정

| 설정 | 값 | 지운 내용에 생기는 일 |
|---|---|---|
| `secure_delete` | 끔(기본) | 0으로 덮지 않음 |
| | 켬 | 지운 내용을 0으로 덮음. 컴파일 옵션 `SQLITE_SECURE_DELETE` 로 빌드하면 기본이 켬 |
| | FAST (2017-08-01 추가) | 입출력이 늘지 않을 때만 0으로 덮음. B-트리 페이지의 옛 내용은 지우지만 프리리스트 페이지에는 흔적이 남음 |
| `auto_vacuum` | NONE (0, 기본) | 프리리스트 페이지를 다시 쓰지만 파일 크기는 줄지 않음 |
| | FULL (1) | 커밋할 때마다 프리리스트 페이지를 파일 끝으로 옮겨 잘라 냄 |
| | INCREMENTAL (2) | `PRAGMA incremental_vacuum` 을 실행할 때만 잘라 냄 |

위 내용은 모두 [2]에서 확인했습니다. auto_vacuum을 NONE에서 FULL이나 INCREMENTAL로 바꾸는 일은 표를 만들기 전에만 할 수 있고 [2], FULL이면 프리리스트 페이지가 커밋 때마다 파일에서 잘려 나가서 그 흔적도 함께 사라집니다.

DB 헤더 52번 칸이 0이 아니면 auto-vacuum DB이고 64번 칸까지 0이 아니면 incremental 모드라서 [1], 헤더만 보고도 프리리스트 흔적이 남아 있을지 먼저 가늠할 수 있습니다. 반면 `secure_delete` 는 헤더 100바이트 어디에도 칸이 없어서 [1], 비워진 공간이 0으로 채워져 있는지를 직접 보고 판단합니다. macOS에 들어 있는 SQLite의 버전과 `secure_delete` 기본값은 참고 문헌으로 확인하지 못했습니다.

## 읽는 법

### 헥스로 한 번

아래 바이트는 실제 검체가 아니라 명세 [1]에 맞춰 만든 예시입니다. 먼저 프리리스트 트렁크 페이지의 앞부분입니다.

```
페이지 내 오프셋
0000  00 00 00 00 00 00 00 02 00 00 00 07 00 00 00 09
```

`00 00 00 00` 은 다음 트렁크 페이지가 없다는 뜻이고, `00 00 00 02` 는 리프 페이지 번호가 두 개라는 뜻이며, 그 번호는 7과 9입니다. 7번과 9번 페이지를 찾아가 첫 바이트가 B-트리 페이지 종류 값인지부터 봅니다.

다음은 표 리프 페이지의 헤더와 그 안의 프리블록입니다.

```
페이지 내 오프셋
0000  0D 0F A0 00 02 0F 80 00 ...
...
0FA0  00 00 00 10 xx xx xx xx xx xx xx xx xx xx xx xx
```

페이지 헤더의 `0F A0` 이 첫 프리블록 위치이고, 0x0FA0의 `00 00` 은 다음 프리블록 없음, `00 10` 은 머리를 포함해 16바이트라는 뜻입니다. `xx` 로 표시한 12바이트가 비워진 자리의 나머지이고, 여기서 레코드 헤더 모양을 찾습니다.

### 절차

1. 원본을 보존하고 DB와 `-journal`, `-wal`, `-shm` 을 함께 작업 사본으로 옮깁니다. 여는 순간 바뀔 수 있는 부분은 [WAL과 저널 (WAL·Journal)](wal-journal.md)에서 확인합니다.
2. DB 헤더 32·36번 칸으로 프리리스트가 있는지, 52·64번 칸으로 auto-vacuum인지 봅니다.
3. 첫 트렁크 페이지부터 사슬을 따라가며 리프 페이지 번호를 모두 적습니다.
4. 리프 페이지마다 이전 B-트리 페이지 모양이 남아 있는지 보고, 남아 있으면 셀 포인터와 레코드를 풉니다.
5. 사용 중인 B-트리 페이지마다 헤더 오프셋 1에서 시작해 프리블록 사슬을 따라가고, 조각 합계도 확인합니다.
6. `sqlite_schema` 의 `CREATE` 문으로 표마다 칸 수와 형식을 알아 두고, 빈 공간에서 그와 맞는 레코드 헤더를 찾습니다.
7. 저널과 WAL의 페이지에도 같은 방법을 쓰고, 공개 도구의 결과와 손으로 푼 결과를 맞춰 봅니다.

## 도구

sqlite3 셸의 `.recover` 명령은 손상된 DB에서 내용을 건져 SQL로 내보내고, 기본으로 프리리스트까지 훑어서 지워진 내용이 되살아날 수 있습니다 [3].

```
sqlite3 corrupt.db .recover >data.sql
```

프리리스트를 훑지 않으려면 `--ignore-freelist` 를 붙이고, 어느 표에 속하는지 알 수 없는 내용은 `lost_and_found` 표에 들어가며 표 이름은 `--lost-and-found` 로 바꿀 수 있습니다 [3]. 복구 기능의 소스는 `sqlite3recover.c`·`sqlite3recover.h` 와 `dbdata.c` 이고, `dbdata.c` 는 `SQLITE_ENABLE_DBPAGE_VTAB` 가 필요합니다 [3].

FQLite는 Hochschule Mittweida의 Dirk Pawlaszczyk 등이 만든 무료 오픈소스 도구이고, 프리리스트 페이지와 비할당 영역·프리블록, 롤백 저널과 WAL, 지워진 표에서 레코드를 복구합니다 [4]. Java/JavaFX로 만든 GUI 도구이고 macOS·Windows·Linux에서 쓸 수 있습니다. 최근 판은 JRE를 함께 담아 배포하고, 버전 2.0부터는 명령줄 모드를 없앴습니다 [4].

## 결과를 해석할 때

`.recover` 의 결과는 불완전하게 건져 낸 것이라서 값이나 타입이 바뀌거나 다른 표로 옮겨져 나올 수 있다고 SQLite 문서가 밝히고 있습니다 [3]. 되살린 레코드가 어느 표의 것인지는 칸 수와 칸 형식, 루트 페이지와의 관계로 따로 확인하고, `lost_and_found` 에 들어간 행은 소속을 단정하지 않습니다.

프리리스트와 프리블록에는 삭제 시각이 적히지 않습니다 [1]. 되살린 레코드는 그 내용이 한때 DB에 있었다는 것까지 보여 주지만, 언제 지워졌는지나 누가 지웠는지는 보여 주지 못합니다. 레코드 안에 시각 칸이 있어도 그 값은 앱이 레코드에 적어 둔 값일 뿐 삭제 시각이 아니라서 둘을 섞지 않습니다.

반대로 지운 레코드가 나오지 않았다고 삭제가 없었다고 볼 수도 없습니다. secure_delete와 auto_vacuum, 페이지 재사용 때문에 흔적이 덮이거나 잘려 나갔을 수 있습니다 [2].

보고서에는 "이 DB의 프리리스트 페이지에서 표 A의 칸 구성과 맞는 레코드를 되살렸고, 이 기록으로는 삭제 시각을 알 수 없다" 처럼 어디서 무엇이 나왔는지만 씁니다. 파일 시스템 수준의 삭제 파일 복구는 [삭제 데이터 복구 (Data Recovery)](../../../03-techniques/analysis/data-recovery/index.md)에서, 도구 결과를 검증하는 방법은 [도구 검증 (Tool Validation)](../../../03-techniques/reporting/tool-validation.md)에서 다룹니다. 사건에서 이 과정을 단계별로 밟는 방법은 [SQLite 레코드 되살리기 (SQLite)](../../../03-techniques/analysis/data-recovery/sqlite-records.md)에 있습니다.
