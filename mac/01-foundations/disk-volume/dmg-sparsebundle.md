# 디스크 이미지 형식 (DMG·Sparsebundle)

## 한 줄 요약

맥의 디스크 이미지는 파일 끝 512바이트에 "koly" 트레일러를 두는 UDIF(.dmg), 파일 앞 4096바이트 헤더에 밴드 색인을 두는 스파스 이미지(.sparseimage), 밴드 파일을 폴더에 나눠 담는 스파스 번들(.sparsebundle) 로 나뉘고, 이진 구조의 값은 빅 엔디언으로 적습니다.

## 이 형식을 쓰는 아티팩트

사용자 폴더나 외장 매체, 내려받은 파일 가운데 .dmg·.sparseimage·.sparsebundle 을 만나면, 그 안에 다시 파티션 표와 파일 시스템이 들어 있을 수 있습니다. 이미지를 풀어 원래 디스크 모양으로 되돌린 뒤에는 [파티션 구조](gpt-partitions.md), [APFS 구조](apfs/index.md), [HFS+ 구조](hfs-plus.md) 순서로 내려갑니다. 이미지 파일이 어디서 왔는지는 [이 파일은 어디서 왔나](../../04-scenarios/activity/file-origin.md)에서 다룹니다.

디스크 이미지의 형식 코드는 다음과 같습니다 [1].

| 형식 코드 | 확장자 | 설명 |
|---|---|---|
| UDIF (주석 표기 UDRW) | .dmg | 읽고 쓰는 이미지, 압축 안 함 |
| UDRO | .dmg | 읽기 전용, 압축 안 함 |
| UDZO | .dmg | zlib (DEFLATE) 압축 |
| UDBZ | .dmg | bzip2 압축 |
| UDCO | .dmg | ADC 압축 |
| ULFO | .dmg | LZFSE 압축 |
| ULMO | .dmg | LZMA 압축 |
| UDSP (SPARSE) | .sparseimage | 스파스 이미지 |
| UDSB (SPARSEBUNDLE) | .sparsebundle | 스파스 번들 |

읽고 쓰는 이미지는 식별자를 "UDIF" 로 쓰고, 형식 코드는 UDRW 입니다. 이 밖에 UDTO 는 CD/DVD 마스터, UFBI 는 장치 전체를 압축 없이 담은 UDIF 입니다. DC42 와 NDIF 계열 형식도 있습니다 [1].

## 구조

### UDIF (.dmg) 트레일러

UDIF 이미지는 파일 끝 512바이트에 "koly" 로 시작하는 트레일러를 둡니다. 오프셋은 트레일러 시작 기준입니다.

| 오프셋 | 크기 | 필드 |
|---|---|---|
| 0 | 4 | 시그니처 "koly" |
| 4 | 4 | 형식 버전 (4) |
| 8 | 4 | 트레일러 크기 (512) |
| 12 | 4 | 이미지 플래그 |
| 16 | 8 | RunningDataForkOffset |
| 24 | 8 | 데이터 포크 오프셋 |
| 32 | 8 | 데이터 포크 크기 |
| 40 | 8 | 리소스 포크 오프셋 |
| 48 | 8 | 리소스 포크 크기 |
| 56 | 4 | 세그먼트 번호 |
| 60 | 4 | 세그먼트 수 |
| 64 | 16 | 세그먼트 식별자 (UUID) |
| 80 | 136 | 데이터 체크섬 (형식·크기·값) |
| 216 | 8 | XML plist 오프셋 |
| 224 | 8 | XML plist 크기 |
| 352 | 136 | 마스터 체크섬 |
| 488 | 4 | 이미지 유형 |
| 492 | 8 | 섹터 수 |

크기 열의 일부는 다음 필드 오프셋과의 차이로 계산한 값입니다.

### XML plist 와 블록 표 (mish)

트레일러가 가리키는 XML plist 에는 `resource-fork` 딕셔너리가 있고, 그 안에 `blkx` 배열과 `plst` 배열이 들어 있습니다. 배열 항목마다 `Attributes` (16진 문자열), `CFName`, `Data` (base64), `ID` (10진 문자열), `Name` 키가 있습니다. plist 를 읽는 법은 [속성 목록 파일](../data-formats/plist/index.md)에서 다룹니다.

`blkx` 항목의 `Data` 를 base64 로 풀면 "mish" 로 시작하는 블록 표가 나옵니다.

| 오프셋 | 크기 | 필드 |
|---|---|---|
| 0 | 4 | 시그니처 "mish" |
| 4 | 4 | 버전 (1) |
| 8 | 8 | 시작 섹터 |
| 16 | 8 | 섹터 수 |
| 24 | 8 | 데이터 오프셋 |
| 36 | 4 | 블록 기술자 수 |
| 64 | 136 | 체크섬 |
| 200 | 4 | 조각 항목 수 (계산 값, 아래 설명) |
| 204 | 40 × 항목 수 | 조각 항목 배열 (계산 값) |

libmodi 문서의 표는 조각 항목 수를 오프셋 104, 배열을 108 에 적지만, 같은 표에서 오프셋 64 의 체크섬이 136바이트라서 이어지는 필드는 200 에서 시작해야 합니다. 위 표의 200·204 는 필드 크기로 계산한 값이라서, 실제 파일에서는 두 자리 가운데 어느 쪽 값이 조각 수와 맞는지 확인합니다.

조각 항목 하나는 40바이트이고 +0 유형(4바이트), +8 시작 섹터(8바이트), +16 섹터 수(8바이트), +24 데이터 오프셋(8바이트), +32 데이터 크기(8바이트) 순서입니다.

| 조각 유형 | 뜻 |
|---|---|
| 0x00000000 | 스파스 (0 으로 채움) |
| 0x00000001 | 압축 안 함 |
| 0x00000002 | 스파스 (Apple_Free) |
| 0x7FFFFFFE | 주석 |
| 0x80000004 | ADC |
| 0x80000005 | zlib |
| 0x80000006 | bzip2 |
| 0x80000007 | LZFSE |
| 0x80000008 | LZMA |
| 0xFFFFFFFF | 끝 |

`blkx` 항목의 `Name` 에 어떤 파티션 이름이 오는지는 실제 이미지로 확인해야 합니다.

### 스파스 이미지 (.sparseimage)

스파스 이미지는 4096바이트 헤더로 시작합니다. +0 에 "sprs", +4 에 버전, +8 에 밴드 하나의 섹터 수, +16 에 스파스가 아닌 원래 이미지 크기(섹터 단위) 가 있고, +64 부터 32비트 밴드 색인 배열이 이어집니다. 배열 항목에 적힌 밴드 색인은 1 부터 세고, 0 은 비어 있는 항목이며, 이미지에 없는 밴드는 풀 때 0 으로 채웁니다.

아래 계산식대로라면 배열의 몇 번째 항목인지가 파일 안 위치를 정하고, 항목에 적힌 밴드 색인이 원래 이미지 안 위치를 정합니다.

| 구하는 값 | 계산 |
|---|---|
| 파일 안 데이터 위치 | 0x1000 + (배열 색인 × 밴드당 섹터 수 × 512) |
| 원래 이미지 안 위치 | (밴드 색인 − 1) × 밴드당 섹터 수 × 512 |

### 스파스 번들 (.sparsebundle)

스파스 번들은 Mac OS X 10.5 에서 처음 나온 형식이고, 파일이 아니라 폴더라서 안에 다음 항목이 있습니다.

| 항목 | 내용 |
|---|---|
| `bands/` | 밴드 파일들 |
| `Info.plist` | 번들 설정 |
| `Info.bckup` | Info.plist 의 백업 |
| `token` | 빈 파일 |

| Info.plist 키 | 값 |
|---|---|
| `band-size` | 밴드 하나의 최대 크기 (바이트) |
| `size` | 미디어 크기 (바이트) |
| `diskimage-bundle-type` | `com.apple.diskimage.sparsebundle` |
| `bundle-backingstore-version` | 1 |
| `CFBundleInfoDictionaryVersion` | "6.0" |

밴드 파일 이름은 16진수 색인입니다. `0` 이 첫 밴드이고 `a` 가 색인 10, `f` 가 색인 15, `10` 이 색인 16 입니다. 밴드 파일 하나는 원래 이미지에서 색인 × `band-size` 위치부터 `band-size` 만큼을 맡는 것으로 보입니다.

## 읽는 법

아래 헥스는 명세로 만든 예시이고, 실제 이미지에서 나온 값이 아닙니다. `NN` 은 값이 들어갈 자리를 뜻합니다.

```text
UDIF 트레일러 (파일 끝 512바이트의 시작 기준)
오프셋  00 01 02 03  04 05 06 07  08 09 0A 0B  0C 0D 0E 0F
0000    6B 6F 6C 79  00 00 00 04  00 00 02 00  NN NN NN NN
        "k  o  l  y" 버전 4       크기 512     이미지 플래그
...
00D0                              NN NN NN NN  NN NN NN NN
                                  XML plist 오프셋 (오프셋 216)
00E0    NN NN NN NN  NN NN NN NN
        XML plist 크기 (오프셋 224)

mish 블록 표 (base64 를 푼 뒤)
오프셋  00 01 02 03  04 05 06 07  08 ...
0000    6D 69 73 68  00 00 00 01  NN ...
        "m  i  s  h" 버전 1       시작 섹터

스파스 이미지 (파일 시작)
오프셋  00 01 02 03  04 05 06 07  08 09 0A 0B
0000    73 70 72 73  NN NN NN NN  NN NN NN NN
        "s  p  r  s" 버전         밴드당 섹터 수
```

UDIF 한 개를 읽는 순서는 다음과 같습니다.

1. 파일 끝에서 512바이트를 읽어 "koly" 를 확인합니다. 확장자가 .dmg 여도 "koly" 가 없으면 UDIF 가 아니라서, 파일 앞 4바이트가 "sprs" 인지 등 다른 형식을 확인합니다.
2. 트레일러 오프셋 216·224 에서 XML plist 의 위치와 크기를 읽어 plist 를 꺼냅니다.
3. `resource-fork` 아래 `blkx` 배열의 항목마다 `Data` 를 base64 로 풀고, "mish" 와 버전 1 을 확인합니다.
4. mish 오프셋 200 의 항목 수만큼 오프셋 204 부터 40바이트씩 조각 항목을 읽습니다(위 오프셋 설명 참고).
5. 조각 유형에 따라 데이터를 풀어 시작 섹터 위치에 놓습니다. 스파스 유형은 0 으로 채우고, 주석은 건너뛰고, 0xFFFFFFFF 를 만나면 멈춥니다. 조각의 데이터 오프셋은 UDIF 이미지 파일 시작 기준 바이트 오프셋이고, 스파스 조각은 데이터 크기가 0 입니다 [1].

압축 조각을 푸는 법은 [압축 형식](../value-decoding/compression.md)에서 다룹니다. 스파스 번들은 `Info.plist` 에서 `band-size` 와 `size` 를 읽고, `bands/` 의 파일 이름을 16진수 색인으로 바꿔 차례로 이어 붙이며, 없는 색인 자리는 비워 둡니다.

## 포렌식에서 중요한 점

형식은 확장자가 아니라 구조로 판단합니다. .dmg 라는 이름만으로는 어떤 형식인지 알 수 없고, 파일 끝의 "koly" 로 UDIF 를, 파일 앞의 "sprs" 로 스파스 이미지를 가립니다. 보고서에도 확장자 대신 확인한 시그니처와 형식 코드를 적습니다.

스파스 조각(유형 0x00000000, 0x00000002) 은 이미지 파일에 데이터가 들어 있지 않고 풀 때 0 으로 채우는 영역입니다. 그래서 복원한 이미지에서 0 으로 채워진 넓은 영역을 보고 누군가 데이터를 지웠다고 판단하지 않고, 먼저 그 영역이 스파스 조각이었는지 블록 표에서 확인합니다. 스파스 번들에서도 쓰이지 않은 영역의 밴드 파일은 없을 수 있어서, 밴드 파일이 빠져 있다고 곧바로 삭제로 보지 않습니다.

스파스 번들은 밴드 파일마다 파일 시스템의 시각이 따로 남습니다. 이 때문에 어떤 밴드 파일이 언제 바뀌었는지가 이미지 안에서 언제 어느 영역에 썼는지를 추정하는 단서가 될 수 있습니다. 이 판단은 추론이라 보고서에는 추론이라고 밝혀 적습니다. 밴드 파일 시각을 타임라인에 올리는 법은 [타임라인 작성](../../03-techniques/analysis/timeline/index.md)에서 다룹니다. `Info.bckup` 은 `Info.plist` 의 백업이라서, 두 파일이 다르면 어느 한쪽이 나중에 바뀌었는지 살펴봅니다.

트레일러에는 세그먼트 번호와 세그먼트 수가 있어서, 세그먼트 수가 1 보다 크면 이미지가 여러 파일로 나뉘어 있는 것으로 보고 나머지 세그먼트를 모두 찾습니다. 데이터 체크섬과 마스터 체크섬도 있지만, 이미지 무결성은 확보할 때 따로 계산한 해시로 판단합니다. 해시를 기록하는 법은 [맥 증거 확보](../../03-techniques/process-acquisition/evidence-acquisition/index.md)에서 다룹니다.

## 함정

UDIF 와 스파스 이미지의 이진 구조는 빅 엔디언이라서, 리틀 엔디언으로 읽으면 오프셋과 크기가 엉뚱하게 나옵니다. 트레일러의 버전 4 와 크기 512 가 헥스에서 `00 00 00 04`, `00 00 02 00` 으로 보이는지로 바이트 순서를 먼저 확인합니다.

mish 의 오프셋 36 블록 기술자 수와 조각 항목 수는 다른 값이라서, 조각 배열을 읽을 때는 조각 항목 수를 씁니다. 요약 자료의 오프셋을 그대로 옮기지 말고 필드 크기로 다시 계산해 봅니다. 스파스 이미지에서 밴드 데이터의 파일 안 순서는 원래 이미지 순서와 다를 수 있어서, 파일 안 순서를 원래 순서로 착각하면 데이터가 뒤섞입니다. 반드시 밴드 색인 배열로 원래 위치를 다시 계산합니다.

타임 머신 백업은 [타임 머신](../../02-artifacts/filesystem/time-machine/index.md)에서 다룹니다.
