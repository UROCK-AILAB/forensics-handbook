# 파티션 구조 (GPT·APFS 파티션)

## 한 줄 요약

인텔 맥과 Apple silicon 맥의 디스크는 GUID 파티션 표 (GUID Partition Table, GPT) 로 나뉘고, 파티션마다 붙은 유형 GUID 로 APFS 컨테이너·HFS+·EFI 시스템 파티션 같은 용도를 가려내며, APFS 컨테이너 파티션은 첫 블록의 컨테이너 슈퍼블록에서 읽기 시작합니다.

## 이 형식을 쓰는 아티팩트

맥 디스크 이미지를 열면 가장 먼저 만나는 구조가 GPT 이고, 그 안의 파티션을 골라야 [APFS 구조](apfs/index.md)나 [HFS+ 구조](hfs-plus.md)로 내려갈 수 있습니다. 외장 디스크나 USB 저장 장치, 디스크 이미지 파일 안에도 파티션 표가 들어 있을 수 있어서, [USB 저장 장치](../../02-artifacts/external-devices/usb/index.md)와 [디스크 이미지 형식](dmg-sparsebundle.md)을 분석할 때도 이 페이지의 순서를 그대로 씁니다. 증거를 확보하는 단계에서 파티션 표를 함께 기록하는 법은 [맥 증거 확보](../../03-techniques/process-acquisition/evidence-acquisition/index.md)에서 다룹니다.

## 구조

### 디스크 앞뒤의 배치

LBA 0 에는 보호 MBR 이 있고, 디스크 전체를 덮는 유형 0xEE 파티션 하나로 이 디스크가 GPT 디스크라는 것을 알립니다. LBA 1 에는 시그니처 "EFI PART" 로 시작하는 GPT 헤더가 있고, 백업 헤더는 디스크 마지막 블록(LBA -1) 에 있습니다. LBA 를 바이트 위치로 바꿀 때는 디스크의 섹터 크기를 먼저 확인합니다.

| 헤더 오프셋 | 크기 | 필드 |
|---|---|---|
| 0 | 8 | 시그니처 "EFI PART" |
| 8 | 4 | 개정 번호 |
| 12 | 4 | 헤더 크기 (보통 92) |
| 16 | 4 | 헤더 CRC32 (이 칸을 0 으로 두고 헤더 크기만큼 계산) |
| 20 | 4 | 예약 (0) |
| 24 | 8 | 이 헤더의 LBA |
| 32 | 8 | 백업 헤더의 LBA |
| 40 | 8 | 첫 사용 가능 LBA |
| 48 | 8 | 마지막 사용 가능 LBA |
| 56 | 16 | 디스크 GUID |
| 72 | 8 | 파티션 항목 배열 시작 LBA |
| 80 | 4 | 파티션 항목 수 |
| 84 | 4 | 항목 하나의 크기 (보통 128) |
| 88 | 4 | 항목 배열 CRC32 |

여러 바이트로 된 값은 모두 리틀 엔디언이고, 헤더 뒤 나머지 블록은 0 으로 채웁니다.

### 파티션 항목

파티션 항목 하나는 128바이트이고 다음 순서로 되어 있습니다.

| 항목 오프셋 | 크기 | 필드 |
|---|---|---|
| 0 | 16 | 파티션 유형 GUID |
| 16 | 16 | 파티션 고유 GUID |
| 32 | 8 | 첫 LBA |
| 40 | 8 | 마지막 LBA |
| 48 | 8 | 속성 플래그 |
| 56 | 72 | 파티션 이름 (UTF-16LE, 36자) |

GUID 는 앞쪽 필드를 리틀 엔디언으로 적고 마지막 8바이트는 바이트 배열 그대로 적어서, 디스크에서 보면 엔디언이 섞인 것처럼 보입니다. 식별자를 읽는 일반 규칙은 [식별자 읽기](../value-decoding/uuid-uid.md)에서 다룹니다.

| Apple Boot (Recovery HD) | 426F6F74-0000-11AA-AA11-00306543ECAC |
| Apple Label | 4C616265-6C00-11AA-AA11-00306543ECAC |
| Apple TV Recovery | 5265636F-7665-11AA-AA11-00306543ECAC |
| Core Storage 컨테이너 (HFS+ 파일볼트) | 53746F72-6167-11AA-AA11-00306543ECAC |

APFS 컨테이너 GUID 는 APFS 명세의 `APFS_GPT_PARTITION_UUID` 와 같습니다. Apple GUID 가운데 여럿은 앞 4바이트를 ASCII 로 읽으면 뜻이 보입니다. 48465300 은 "HFS" 와 널 문자, 52414944 는 "RAID", 426F6F74 는 "Boot", 4C616265 는 "Labe", 53746F72 는 "Stor" 입니다.

### APFS 컨테이너 파티션 안

APFS 컨테이너는 GPT 파티션 하나에 들어가고, 한 컨테이너에는 볼륨을 `NX_MAX_FILE_SYSTEMS` = 100 개까지 둘 수 있습니다. 파티션의 블록 0 에는 컨테이너 슈퍼블록 (`nx_superblock_t`) 의 사본이 있고, 오프셋 32 의 `NX_MAGIC` 은 'BSXN' 이라 디스크에서는 "NXSB" 로 보입니다. 볼륨 슈퍼블록은 같은 오프셋 32 에 "APSB" 가 있습니다.

블록 0 의 사본은 최신일 수도 있고, 비정상 종료 뒤라면 옛 버전일 수도 있습니다. 그래서 블록 0 사본에서 체크포인트 설명 영역 (`nx_xp_desc_base`) 을 찾고, 그 영역에서 트랜잭션 ID 가 가장 크면서 정상인 슈퍼블록을 최신으로 씁니다 [2]. 체크포인트 영역은 링 버퍼이고, 이 사본들에는 과거 시점의 컨테이너 상태가 담겨 있습니다 [2].

퓨전 드라이브는 HDD 와 SSD 의 파티션이 각각 블록 0 에 컨테이너 슈퍼블록 사본을 두고, 두 사본의 `nx_fusion_uuid` 하위 127비트가 같습니다. 최상위 비트는 주 장치가 1, 2단계 장치가 0 이고, 퓨전이 아닌 컨테이너는 이 값이 0 입니다.

## 읽는 법

아래 헥스는 명세로 만든 예시이고, 특정 검체에서 나온 값이 아닙니다. `NN` 은 값이 들어갈 자리를 뜻합니다. 파티션 항목의 유형 GUID 바이트는 위 혼합 엔디언 규칙으로 APFS 컨테이너 GUID 를 바꿔 적은 것입니다.

```text
GPT 헤더 (LBA 1 시작 기준)
오프셋  00 01 02 03 04 05 06 07  08 09 0A 0B
0000    45 46 49 20 50 41 52 54  NN NN NN NN
        "E  F  I     P  A  R  T" 개정 번호

파티션 항목 하나 (항목 시작 기준)
오프셋  00 01 02 03 04 05 06 07  08 09 0A 0B 0C 0D 0E 0F
0000    EF 57 34 7C 00 00 AA 11  AA 11 00 30 65 43 EC AC
        유형 GUID = 7C3457EF-0000-11AA-AA11-00306543ECAC (APFS 컨테이너)
0010    NN NN NN NN NN NN NN NN  NN NN NN NN NN NN NN NN
        고유 GUID
0020    NN NN NN NN NN NN NN NN  NN NN NN NN NN NN NN NN
        첫 LBA                   마지막 LBA

APFS 컨테이너 파티션 블록 0
오프셋  20 21 22 23
0020    4E 58 53 42              "NXSB" (NX_MAGIC, 오프셋 32)
```

1. LBA 0 의 보호 MBR 에 유형 0xEE 파티션이 있는지 보고, LBA 1 에서 "EFI PART" 를 확인한 뒤 오프셋 16 의 헤더 CRC32 를 다시 계산해 맞춰 봅니다.
2. 헤더 오프셋 72·80·84 에서 항목 배열 위치, 항목 수, 항목 크기를 읽습니다.
3. 항목마다 유형 GUID 를 혼합 엔디언으로 풀어 위 표와 맞추고, 첫 LBA 와 마지막 LBA 로 파티션 범위를 정합니다.
4. APFS 컨테이너 파티션이면 파티션 첫 블록의 오프셋 32 에서 "NXSB" 를 확인하고, 체크포인트 설명 영역에서 최신 슈퍼블록을 고른 뒤 [APFS 구조](apfs/index.md)의 순서로 볼륨을 찾습니다. 시동 디스크의 시스템·데이터 볼륨을 짝짓는 법은 [볼륨 그룹과 펌링크](volume-group-firmlinks.md)에서 다룹니다.
5. LBA 1 의 헤더와 디스크 마지막 블록의 백업 헤더를 비교해서, 두 헤더가 가리키는 항목 배열이 같은지 확인합니다.

## 포렌식에서 중요한 점

GPT 는 디스크 앞뒤에 헤더를 하나씩 두어서, 앞쪽 헤더나 항목 배열이 손상되거나 지워져도 디스크 마지막 블록의 백업 헤더로 파티션 배치를 되살릴 수 있습니다. 두 헤더에서 "이 헤더의 LBA" 와 "백업 헤더의 LBA" 는 서로 뒤바뀌어 있어야 맞지만, 가리키는 항목 배열의 내용이나 항목 배열 CRC32 가 서로 다르면 파티션 표가 손상됐거나 한쪽만 고쳐졌을 가능성이 있으므로, 어느 쪽이 맞는지 파티션 안의 슈퍼블록 위치와 맞춰 봅니다. 헤더와 항목 배열에는 각각 CRC32 가 있어서, 저장된 값과 다시 계산한 값이 다르면 그 부분이 바뀌었다고 볼 수 있습니다.

어느 파티션에도 속하지 않은 공간은 파티션 목록만 따라가는 분석에서 빠지기 쉬워서, 지운 파티션이나 숨긴 데이터를 찾을 때 따로 훑어봅니다. 이 공간에서 "NXSB" 나 `'H+'` 같은 시그니처를 찾으면 예전 컨테이너나 볼륨의 흔적일 수 있습니다. 절차는 [삭제 데이터 복구](../../03-techniques/analysis/data-recovery/index.md)에서 다룹니다.

APFS 컨테이너의 체크포인트 영역은 링 버퍼라서 과거 시점의 컨테이너 상태가 남아 있습니다. 비정상 종료 뒤의 이미지라면 블록 0 사본이 최신이 아닐 수 있어서, 도구가 어느 슈퍼블록을 골랐는지 확인합니다. 퓨전 드라이브는 한 컨테이너가 두 장치에 걸쳐 있어서 한쪽 장치만 확보하면 컨테이너를 온전히 읽을 수 없고, `nx_fusion_uuid` 의 최상위 비트로 확보한 장치가 주 장치인지 2단계 장치인지 가립니다.

## 함정

GUID 를 디스크 바이트 순서 그대로 읽으면 7C3457EF 가 EF57347C 처럼 보여서 표의 값과 맞지 않습니다. 앞 4바이트·2바이트·2바이트는 뒤집고 마지막 8바이트는 그대로 둔다는 규칙을 먼저 적용한 뒤 비교합니다.

EFI 시스템 파티션 크기나 Apple silicon 내장 디스크의 컨테이너 구성 같은 기본 파티션 배치는 맥 모델마다 다를 수 있습니다. 파티션 수나 순서가 예상과 다르다고 곧바로 조작이라고 판단하지 않고, 같은 모델·같은 macOS 버전의 기준 이미지와 비교합니다. 라이브 대응에서 남긴 `diskutil list` 같은 명령 출력과 이미지를 맞출 때는 파티션 GUID 와 LBA 범위로 맞춥니다.

유형 GUID 는 파티션의 용도를 선언할 뿐이라서, 파티션 안에 정말 그 파일 시스템이 들어 있는지는 슈퍼블록이나 볼륨 헤더 시그니처로 따로 확인합니다.

## 도구

| 도구 | 쓰임 |
|---|---|
| 헥스 편집기 | "EFI PART" 헤더, 파티션 항목, "NXSB" 를 위 순서대로 직접 확인합니다 |
| Apple File System Reference (명세) | 컨테이너 슈퍼블록, 체크포인트, 퓨전 드라이브 규칙의 기준 |
| libyal libfsapfs 와 그 APFS 문서 | 컨테이너·볼륨 슈퍼블록 오프셋을 확인하고 APFS 컨테이너를 읽을 때 씁니다 |

도구 이름은 예로 든 것이고, 도구가 백업 헤더나 파티션 밖 공간을 어떻게 다루는지는 [도구 검증](../../03-techniques/reporting/tool-validation.md) 방식으로 확인합니다.
