# 도구 검증 (Tool Validation)

포렌식 도구와 절차가 기대대로 동작하는지 시험하고 그 한계를 알아내는 방법을 다룹니다. SWGDE 의 도구 시험 최소 요건(18-Q-001-2.1, 2024년 2.1판)을 뼈대로 도구 분류마다 시험 방법·주기·시험 주체를 정리하고, NIST CFTT 가 공개하는 시험 자료와 맥 조사에 적용할 때 챙길 점을 함께 봅니다.

## 언제 쓰나

이 일은 시험(testing)이라 부르고, 흔히 검증 시험(validation testing 또는 verification testing)이라고도 합니다 [2]. 시험은 도구나 절차가 기대대로 동작하는지 평가하고 도구의 한계를 알아내려고 하며, 사건 작업에 쓰기 전에 기본 시험을 합니다 [2]. 직접 시험해도 되고 역량 있는 다른 기관의 결과를 받아 써도 됩니다 [2]. 처리 속도, 사용 편의성, 해석용 소프트웨어, 사람이 충분히 훈련받았는지는 이 시험 요건에 들지 않습니다 [2].

시험의 목적은 도구와 절차가 바르게 동작한다는 신뢰를 쌓아 오류와 잘못된 해석의 위험을 줄이는 데 있습니다 [2]. 다만 소프트웨어와 하드웨어 버전이 너무 다양해서 모든 상황에서 기대대로 동작한다고 보장할 수는 없고, 조직은 시험을 덜 했을 때의 위험과 시험에 드는 자원을 함께 따집니다 [2]. 위험은 사람의 실수, 절차 오류, 장치·소프트웨어 오류에서 생기고, 조직은 도구의 신뢰성과 시험 이력을 보고 위험을 얼마나 받아들일지 정합니다 [2]. 시험 수준은 도구가 상용인지, 오픈소스인지, 자체 개발인지가 아니라 도구의 기능으로 정합니다 [2].

SWGDE 문서의 처음 판은 1.0(2018-11-20)이고, 이 페이지는 2.1판(2024-03-07)을 기준으로 합니다 [2]. 조직은 쓰임새와 운영상 필요, 정책에 따라 이 기준보다 높일 수 있습니다 [2].

## 시험 방법 세 가지

시험 방법은 셋으로 나뉩니다 [2].

| 방법 | 하는 일 | 주의할 점 |
|---|---|---|
| 알려진 데이터 세트 (Known Dataset) | 알려진 입력을 넣고 출력이 맞는지 봅니다 | 출력을 평가할 수 있을 만큼 입력을 알아야 하고 데이터 양도 충분해야 합니다. 실제 데이터가 꼭 더 낫지는 않고, 실험실에서 만든 데이터는 시험할 기능에 맞춰 만들 수 있습니다 |
| 비교 (Comparison) | 도구 둘 이상이 같은 결과를 내는지 봅니다 | 알려진 데이터 세트를 만들기 어렵거나 불가능할 때 최선일 수 있지만, 따로 만든 도구들에 같은 근본 문제가 있으면 오류를 놓칠 수 있습니다 |
| 경험적 (Empirical) | 출력을 다른 데이터와 대조하거나 손으로 확인합니다 | 예를 들어 비밀번호 복구 도구가 찾은 비밀번호로 파일이 열리면 기대한 결과를 낸 것으로 봅니다 |

## 절차

1. **도구를 분류합니다.** 도구 분류마다 시험 방법(Testing type), 주기(Frequency), 시험 주체(Tester)가 정해져 있습니다 [2]. 쓰는 도구를 아래 표의 어느 분류에 넣을지부터 정하고, 한 도구가 이미징과 검색을 함께 하면 기능마다 해당 분류를 따릅니다.

   | 분류 | 시험 방법 | 주기 | 주체와 비고 |
   |---|---|---|---|
   | 쓰기 방지 장치 (핵심) | 드라이브에 쓰기를 시도해 막히는지, 읽기를 방해하지 않는지 확인합니다. 읽기는 디스크 이미징 도구와 함께 시험하면 됩니다 | 도입 전, 수리 후, 소프트웨어·펌웨어 갱신 후 | 외부 시험 도구의 예로 CFTT Federated Testing 이 있습니다 |
   | 디스크 이미징 도구 (핵심) | 알려진 데이터 세트로 시험하고, 평소 절차에 쓰기 방지 장치를 쓰면 시험에도 넣습니다. 매체 전체나 대상 부분을 확보했는지, 실험실이 자주 만나는 매체 종류를 넣었는지, 이상한 점을 기록하고 이해했는지, 설정을 기록했는지 확인하고, 비트 단위 비교나 해시(예: MD5, SHA256) 비교로 검증합니다 | 도입 전, 수리 후, 주요 갱신 후. 작은 갱신이라도 릴리스 노트에 이미징 부분이 바뀌었다고 나오면 다시 시험합니다 | 실험실이 시험하고, 같은 주 버전이면 CFTT 같은 외부 기관 결과도 쓸 수 있습니다 |
   | 모바일 기기 이미징 도구 (핵심) | 기기 하드웨어가 데이터를 바꿀 수 있어서 해시만으로는 정확성을 판단할 수 없고, 주소록·사진·메시지 같은 알려진 내용으로 시험한 뒤 경험적 시험을 더합니다 | 소프트웨어는 주 버전마다, 하드웨어는 장치마다 | |
   | 클라우드 이미징 도구 (핵심) | 가능하면 알려진 데이터와 경험적 관찰을 함께 씁니다 | 쓸 때마다 | |
   | 해시 도구 (핵심) | 파일끼리 비교하거나 알려진 데이터로 시험하고, 입력에 이진 파일과 텍스트 파일을 모두 넣습니다 | 큰 도구 안에 든 해시 모듈은 릴리스 노트에 해시 모듈 변경이 나올 때 | |
   | 완전 삭제 도구 (핵심) | 전부 0 같은 알려진 패턴으로 지운 뒤 대상 전체에 그 패턴이 들어갔는지 헥스 편집기로 확인합니다 | | |
   | 기반 시스템·OS | 공급사 시험이면 충분하고 부팅되면 됩니다 | | Windows, Mac OS X, Linux 가 여기에 듭니다 |
   | 검색 도구 (분석) | 알려진 데이터로 시험하거나 결과를 손으로 확인하고, 파일 시스템 종류와 검색 위치(메타데이터, 슬랙, 압축 파일)를 고려합니다 | | 문자열 검색, 특정 MAC 시각 범위의 파일, 파일 형식, 연결된 이동식 저장장치 목록을 찾는 도구가 여기에 듭니다 |
   | 복구 도구 (분석) | 알려진 데이터로 시험합니다. 파일 카빙은 비할당 영역에 연속 파일과 조각난 파일을 하나 이상씩 두고, 파일 시스템 기반 삭제 파일 복구는 삭제된 연속 파일·조각난 파일·일부 덮어쓴 파일을 하나 이상씩 둡니다 | | |
   | 모음·요약 도구 (분석) | 타임라인이나 연결 그래프 같은 도구로, 알려진 데이터나 비교로 시험하거나 결과 일부를 손으로 확인합니다 | 도입 전, 주요 갱신 후 | |
   | 행정·보조 도구 | 공급사 시험 말고는 따로 시험하지 않습니다 | | 워드프로세서, 사건 관리 프로그램, 어떤 프로그램이 만든 파일을 그 프로그램으로 여는 경우가 여기에 듭니다 |
   | 자체 개발 도구 | 결과에 영향을 주면 기반 기술을 아는 다른 사람이나 기관이 시험하고, 가능하면 개발에 쓴 것과 다른 데이터 세트로 시험합니다 | 처음 쓸 때와 고칠 때마다 | 중요한 도구는 개발자가 아닌 사람이 시험합니다 |

   핵심 도구(Critical)는 원본이나 최선 증거에 직접 닿거나 무결성에 영향을 주는 도구입니다 [2].

2. **자체 스크립트가 시험 대상인지 가립니다.** 단순한 스크립트나 질의는 대개 시험할 필요가 없습니다 [2]. 감정 메모만으로는 다시 만들 수 없을 만큼 복잡하거나, 코드가 너무 커서 메모에 넣을 수 없거나, 결과를 손으로 확인할 수 없거나, 컴파일되어 있어 소스를 구하기 어려우면 시험이 필요하다는 신호로 봅니다 [2]. 맥 조사에서 SQLite 데이터베이스를 읽는 짧은 질의는 대개 앞쪽에 들고, 여러 형식을 풀어 합치는 파서는 뒤쪽에 들 가능성이 큽니다.
3. **외부 시험 결과를 찾습니다.** NIST CFTT 는 일반 도구 명세, 시험 절차, 시험 기준, 시험 세트, 시험 하드웨어를 만들어 컴퓨터 포렌식 소프트웨어 도구를 시험하는 방법론을 세우는 것을 목표로 둡니다 [3]. 미국 국토안보부 과학기술국(DHS S&T)의 Cyber Forensics 프로젝트가 NIST 와 함께 도구 시험 보고서를 공개하고 [2][3], 미 국방부 사이버범죄센터(DC3)도 dc3.mil 에 시험 보고서를 공개하지만 정부 도메인 사용자만 볼 수 있습니다 [2]. 공급사 대부분은 출시 전에 시험하고 이상한 점과 개선 사항을 논의하는 포럼도 둡니다 [2]. 외부 결과를 쓰면 그 시험 보고서를 참조로 남깁니다 [2].
4. **알려진 데이터 세트를 만듭니다.** 시험할 기능에 맞춰 입력을 설계하고, 기대 결과를 미리 적어 둡니다 [2]. 복구 도구라면 1단계 표의 조건처럼 연속 파일과 조각난 파일을 함께 넣고, 해시 도구라면 이진 파일과 텍스트 파일을 모두 넣습니다 [2]. 맥 아티팩트를 읽는 도구라면 시험할 macOS 버전의 아티팩트를 알려진 조작으로 만들어 넣으면 이 원칙에 맞습니다.
5. **시험하고 기록합니다.** 시험 결과에는 시험 목적과 범위(대상 도구·기법), 시험한 사람, 날짜, 시험 절차나 시나리오, 쓴 데이터 세트와 기대 결과, 결과와 이상한 점과 그 의미, 확인한 한계를 남깁니다 [2]. 공급사 시험 기록은 대개 구할 수 없습니다 [2].
6. **사건에서 쓸 때 영향과 기록을 챙깁니다.** 분석가는 수집 전에 도구가 시스템에 어떤 영향을 주는지 알아야 합니다 [1]. 이미징 도구 가운데 일부는 감사 기록과 보관 연속성 기록을 자동으로 남겨 감정 과정의 일관성과 결과의 정확성·재현성에 도움이 됩니다 [1]. 사건마다 도구 버전과 실행 명령을 적는 방법은 [포렌식 보고서 (Forensic Report)](forensic-report.md) 에서 다룹니다.
7. **다시 시험할 때를 정합니다.** 1단계 표의 주기(도입 전, 수리 후, 주요 갱신 후, 릴리스 노트에 해당 모듈 변경이 나올 때)를 달력이나 변경 관리 절차에 묶어 둡니다 [2].

## 도구

NIST CFTT 는 Federated Testing 을 내려받을 수 있는 CD iso 로 제공하고, 여기에는 공통 시험 방법 안내와 시험 보고서를 공유하는 기능이 들어 있습니다 [3]. CFTT 기술 정보 목록의 분야는 Cloud Data Extraction, Deleted File Recovery, Disk Imaging, Forensic File Carving, Forensic Media Preparation, Forensic String Search, Hardware Write Block, Mobile Devices, MS Windows Registry Tools, Software Write Block, SQLite 입니다 [3]. CFTT 페이지에서 CFReDS 와 Computer Forensics Tools & Techniques Catalog 로도 이어집니다 [3].

2018-03-23 기준으로 Federated Testing 은 디스크 이미징, 쓰기 방지, 모바일 기기 확보만 지원했고, 문자열 검색과 디스크 삭제는 추가할 예정이었습니다 [2]. 이 내용은 SWGDE 2024년 판에서도 바뀌지 않아서, 지금의 지원 범위는 CFTT 누리집에서 확인합니다.

완전 삭제 결과는 헥스 편집기로 확인하고, 이미징 결과는 비트 단위 비교나 해시 비교로 확인합니다 [2]. 공개 맥 분석 도구(예: mac_apt)를 쓸 때도 같은 기준을 적용하고, 도구마다 공개된 검증 보고서가 있는지 먼저 찾아보고 없으면 직접 시험합니다.

## 함정과 한계

시험 결과는 꼭 통과와 실패로 갈리지 않습니다. 어떤 결함은 심해서 도구를 쓸 수 없고, 어떤 결함은 특정 영역에서만 쓰임을 제한합니다 [2]. 검색 도구 시험은 핵심 기능이 되는지만 확인하고 도구의 한계는 보여 주지 않습니다 [2]. 복구 도구는 서로 다른 파일의 조각을 합칠 수 있어서, 감정인이 복구 결과를 직접 보고 앞뒤가 맞는지 확인합니다 [2]. 복구 절차 자체는 [삭제 데이터 복구 (Data Recovery)](../analysis/data-recovery/index.md) 에서 다룹니다.

도구 시험을 통과해도 대상 시스템의 상태 때문에 결과를 검증하지 못할 수 있습니다. 사용 중인 시스템에서 물리 장치 전체를 비트 단위로 복제하면 파일과 메모리가 계속 바뀌어 검증할 수 없고, 논리 영역 복제는 끝까지 하고 검증할 수 있습니다 [1]. 완전히 장악된 시스템에서는 루트킷이 커널 수준에서 동작을 바꿔 사용자 수준 도구에 거짓 데이터를 돌려줄 수 있어서, 포렌식 도구를 써도 정확성이 보장되지 않습니다 [1]. 이런 상황에서 무엇을 먼저 수집할지는 [라이브 대응 (Live Response)](../process-acquisition/live-response/index.md) 과 [메모리 분석 (Memory Forensics)](../analysis/memory-forensics/index.md) 을 봅니다.

기반 시스템과 OS 는 공급사 시험이면 충분하지만, 도구를 시험할 때는 도구가 작업용 컴퓨터의 기반 기술을 쓰는 부분을 알아채야 합니다 [2]. 맥에 적용하면 분석용 맥의 운영체제 기능을 빌려 이미지를 마운트하거나 파일을 읽는 도구는 분석용 맥의 macOS 버전도 시험 조건에 적어 두는 편이 안전합니다.

macOS 는 버전마다 아티팩트 형식이 바뀔 수 있어서, 이전 버전에서 시험한 도구가 새 버전의 데이터를 잘못 해석할 위험이 있어서, 주요 갱신 뒤에는 다시 시험합니다 [2]. 맥 아티팩트 다수가 SQLite 에 저장되고, CFTT 기술 분야 목록에 SQLite 가 있습니다 [3]. 저장 형식의 특성은 [SQLite 데이터베이스 (SQLite)](../../01-foundations/data-formats/sqlite/index.md) 에서 봅니다. CFTT 목록에는 macOS·APFS·Apple 전용 시험 보고서나 시험 데이터가 없어서 [3], 맥 아티팩트를 읽는 도구는 직접 시험합니다.

외부 시험 결과는 시기를 함께 봅니다. 2006년 무렵 CFTT 는 디스크 이미징 도구의 시험 절차를 만들었고, 시험을 거친 도구는 몇 개뿐이었습니다 [1]. 오래된 보고서는 지금 쓰는 버전과 맞는지 확인합니다. 포렌식용으로 만든 도구는 포렌식용 문서가 있는 경우가 많고 포렌식에서 쓰이면서 결함이 드러났을 가능성도 높지만, 문서는 거의 없어도 유용한 도구도 있습니다 [2].

## 결과를 어떻게 해석하나

시험 기록은 이 도구가 이 조건에서 이 기능을 기대대로 수행했다는 사실만 보여 줍니다. 시험하지 않은 파일 시스템, 매체 종류, macOS 버전, 기능에 대해서는 말해 주지 않아서, 확인한 한계와 시험 조건을 함께 읽습니다 [2]. 비교 시험에서 두 도구의 결과가 같아도 두 도구에 같은 근본 문제가 있으면 둘 다 틀릴 수 있고 [2], 알려진 데이터 세트나 손 확인으로 한 번 더 받치면 더 단단해집니다.

결함이 드러난 도구는 결함이 닿는 영역만 제한하고 나머지 기능을 쓸 수 있습니다 [2]. 이때 보고서에는 그 도구를 어느 범위에서 썼는지와 결함을 어떻게 피했는지를 적고, 외부 시험을 근거로 삼았다면 그 보고서를 참조로 붙입니다 [2]. 보고서에 들어갈 도구 정보의 형식은 [포렌식 보고서 (Forensic Report)](forensic-report.md) 를 따릅니다.
