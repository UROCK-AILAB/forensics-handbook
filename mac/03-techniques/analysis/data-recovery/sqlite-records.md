# SQLite 레코드 되살리기 (SQLite)

SQLite 데이터베이스 안의 freelist 페이지, 페이지 속 빈 블록(freeblock), WAL 파일의 옛 프레임, 롤백 저널에 남은 지운 레코드를 찾아 읽는 방법을 다룹니다.

## 언제 쓰나

메시지, 브라우저 기록, 메모처럼 macOS 의 많은 앱 기록이 SQLite 파일에 들어 있어서, 앱 화면이나 일반 조회에서 사라진 항목을 확인해야 할 때 씁니다. SQLite 는 지운 내용을 기본으로 0 으로 덮지 않고(secure_delete 는 보통 꺼져 있습니다) [2], 기본 설정(auto_vacuum 0)에서는 지워도 파일 크기가 그대로이고 빈 페이지는 freelist 로 가서 나중에 다시 쓰입니다 [2]. 그래서 지운 레코드가 파일이 남아 있는 동안 파일 안에 남는 경우가 많고, 파일 자체를 지운 경우는 [APFS에서 지운 파일 (APFS)](apfs-deleted-files.md) 이나 [카빙 (Carving)](carving.md) 으로 파일부터 되찾습니다.

파일 형식 전체는 [SQLite 데이터베이스 (SQLite)](../../../01-foundations/data-formats/sqlite/index.md) 에 있고, 이 페이지는 지운 데이터를 찾는 데 필요한 필드만 봅니다. 앱별 테이블 구성은 [메시지 (iMessage·SMS)](../../../02-artifacts/messengers/imessage/index.md), [메모 (Notes)](../../../02-artifacts/cloud-apps/notes.md), [사파리 (Safari)](../../../02-artifacts/browsers/safari/index.md) 처럼 각 아티팩트 페이지에서 봅니다.

## 지운 레코드가 남는 자리

### 파일 헤더에서 먼저 볼 필드

파일 헤더의 오프셋은 파일 처음 기준이고 값은 모두 빅 엔디언입니다 [1].

| 오프셋 | 크기 | 뜻 |
|---|---|---|
| 16 | 2 | 페이지 크기. 512~32768 사이 2의 거듭제곱이고, 값 1은 65536 |
| 24 | 4 | 파일 변경 카운터. 수정한 뒤 잠금을 풀 때마다 늘어남 |
| 32 | 4 | 첫 freelist 트렁크 페이지 번호(비었으면 0) |
| 36 | 4 | freelist 전체 페이지 수 |
| 52 | 4 | 0 이면 ptrmap 페이지가 없음(auto_vacuum 안 씀). 0 이 아니면 가장 큰 루트 페이지 번호 |
| 56 | 4 | 텍스트 인코딩. 1=UTF-8, 2=UTF-16le, 3=UTF-16be |
| 64 | 4 | 참이면 incremental_vacuum |

### freelist 페이지

freelist 트렁크 페이지는 4바이트 정수 배열이고, 첫 값은 다음 트렁크 페이지 번호(없으면 0), 둘째 값은 뒤따르는 리프 포인터 수 L, 그 뒤 L 개가 리프 페이지 번호입니다 [1]. freelist 리프 페이지에는 정보가 없고, SQLite 는 이 페이지를 읽지도 쓰지도 않습니다 [1]. 그래서 비었다고 표시만 되고 옛 테이블 페이지의 내용이 그대로 남아 있을 수 있습니다.

### 페이지 안의 freeblock 과 조각

B-트리 페이지 머리는 리프가 8바이트, 내부 페이지가 12바이트이고 필드는 다음과 같습니다 [1].

| 오프셋 | 크기 | 뜻 |
|---|---|---|
| 0 | 1 | 페이지 종류. 0x02 내부 인덱스, 0x05 내부 테이블, 0x0a 리프 인덱스, 0x0d 리프 테이블 |
| 1 | 2 | 첫 freeblock 오프셋(없으면 0) |
| 3 | 2 | 셀 개수 |
| 5 | 2 | 셀 내용 영역 시작(0 은 65536) |
| 7 | 1 | 조각난 빈 바이트 수 |
| 8 | 4 | 가장 오른쪽 자식 포인터(내부 페이지만) |

freeblock 은 앞 2바이트가 다음 freeblock 오프셋(마지막이면 0), 다음 2바이트가 4바이트 머리를 포함한 크기이고, 최소 4바이트입니다 [1]. 1~3바이트짜리 고립된 빈 자리는 조각(fragment)이라서 사슬로 이어지지 않고 그 합계만 머리 오프셋 7 에 적힙니다 [1].

테이블 리프 셀(0x0d)은 페이로드 전체 길이 varint, rowid varint, 페이로드 앞부분 순으로 이어지고, 페이로드가 넘치면 끝에 첫 오버플로 페이지 번호 4바이트가 붙습니다 [1]. 레코드는 머리 길이 varint(자기 자신 포함), 열마다 serial type varint, 본문 순이고, serial type 은 다음처럼 읽습니다 [1].

| serial type | 뜻 |
|---|---|
| 0 | NULL |
| 1~7 | 정수·실수(1~8바이트) |
| 8 | 정수 0 (스키마 형식 4 이상) |
| 9 | 정수 1 (스키마 형식 4 이상) |
| 12 이상 짝수 N | BLOB, (N-12)/2 바이트 |
| 13 이상 홀수 N | 문자열, (N-13)/2 바이트 |

셀이 freeblock 이 되면 freeblock 머리 4바이트가 셀 앞 4바이트 자리에 쓰여서, 페이로드 길이·rowid varint 와 레코드 머리 앞부분이 가려진 채 나머지가 남을 수 있습니다.

### WAL 파일

WAL 모드에서는 원본 DB 는 그대로 두고 변경을 -wal 파일에 덧붙이며, 커밋은 WAL 에 커밋 레코드를 붙이는 일입니다 [3]. WAL 내용을 DB 로 옮기는 일을 체크포인트라 하고, 기본 자동 체크포인트는 WAL 이 1000 페이지에 이를 때 돕니다 [3]. 체크포인트 뒤 WAL 은 보통 잘리지 않고 처음부터 덮어 쓰고(journal_size_limit 을 두면 잘립니다), 마지막 연결이 닫힐 때 보통 WAL 파일을 지우며, journal_mode=WAL 은 다시 열어도 유지되고, -shm 은 WAL 인덱스를 담는 공유 메모리 파일입니다 [3]. 처음부터 덮어 쓰는 방식이라 -wal 파일 뒤쪽에는 이미 DB 로 옮겨진 프레임이나 이전 세대의 프레임이 남을 수 있습니다.

WAL 헤더는 32바이트이고 빅 엔디언입니다 [1].

| 오프셋 | 크기 | 뜻 |
|---|---|---|
| 0 | 4 | 매직 0x377f0682 또는 0x377f0683 |
| 4 | 4 | 형식 버전(3007000) |
| 8 | 4 | 페이지 크기 |
| 12 | 4 | 체크포인트 순번 |
| 16 | 4 | salt-1 |
| 20 | 4 | salt-2 |
| 24 | 4 | checksum-1 |
| 28 | 4 | checksum-2 |

프레임마다 24바이트 머리가 붙고, 0 에 페이지 번호, 4 에 커밋 프레임이면 커밋 뒤 DB 크기(페이지 수)이고 아니면 0, 8·12 에 salt-1·salt-2, 16·20 에 checksum-1·checksum-2 가 옵니다 [1]. 프레임이 유효하려면 salt 두 값이 WAL 헤더와 같고 누적 체크섬이 맞아야 해서 [1], salt 가 헤더와 다른 프레임은 SQLite 가 무시하지만 조사하는 쪽에서는 이전 세대의 옛 페이지 사본으로 읽을 수 있습니다.

### 롤백 저널

WAL 이 아닌 모드에서 쓰는 롤백 저널은 8바이트 매직(0xd9 0xd5 0x05 0xf9 0x20 0xa1 0x63 0xd7)으로 시작하고, 8 에 페이지 수(-1 이면 전부), 12 에 체크섬 nonce, 16 에 원래 DB 크기(페이지 수), 20 에 섹터 크기, 24 에 페이지 크기가 옵니다 [1]. 그 뒤 레코드마다 페이지 번호(4바이트), 원래 페이지 내용, 체크섬(4바이트)이 이어져서 [1], 저널이 남아 있으면 트랜잭션 전의 페이지 내용을 볼 수 있습니다.

## 설정이 복구 가능성을 바꾼다

| 설정 | 값 | 지운 내용에 생기는 일 |
|---|---|---|
| secure_delete [2] | OFF (보통 기본) | 0 으로 덮지 않음 |
| secure_delete | ON | 지운 내용을 0 으로 덮음 |
| secure_delete | FAST | I/O 가 늘지 않을 때만 0 으로 덮어서, B-트리 페이지의 옛 내용은 지우지만 freelist 페이지에는 흔적이 남음 |
| auto_vacuum | 0 / NONE (기본) | 파일 크기 그대로, 빈 페이지는 freelist 로 가서 재사용 |
| auto_vacuum | 1 / FULL | 커밋마다 freelist 페이지를 파일 끝으로 옮기고 잘라냄 |
| auto_vacuum | 2 / INCREMENTAL | incremental_vacuum 을 불러야만 정리 |

secure_delete 의 기본값은 컴파일 옵션 SQLITE_SECURE_DELETE 가 정하고 [2], PRAGMA freelist_count 는 안 쓰는 페이지 수를 돌려줍니다 [2]. macOS 시스템 SQLite 의 secure_delete 기본값과 메시지·사진 같은 Apple 앱 DB 의 설정값은 실제 데이터로 확인해야 합니다. auto_vacuum 은 헤더 오프셋 52·64 의 값으로 확인하고, secure_delete 는 freeblock 과 freelist 페이지가 0 으로 채워져 있는지를 직접 보고 추정합니다.

## 헥스로 따라가기

아래는 명세로 만든 예시이고 실제 데이터에서 나온 값이 아닙니다. 페이지 크기 4096 의 테이블 리프 페이지에서 셀 하나를 지워 freeblock 이 생긴 상황입니다.

```
페이지 머리 (페이지 안 오프셋 0x0000)
0d 0f 40 00 01 0f 00 00
│  └─┬─┘ └─┬─┘ └─┬─┘ └ 조각난 빈 바이트 0
│    │     │     └ 셀 내용 영역 시작 0x0f00
│    │     └ 셀 개수 1
│    └ 첫 freeblock 오프셋 0x0f40
└ 페이지 종류 0x0d (리프 테이블)

지우기 전 0x0f40 의 셀 (13바이트)
0b 05 03 01 1b 2a 65 78 61 6d 70 6c 65
│  │  │  │  │  │  └ 문자열 "example"
│  │  │  │  │  └ 첫 칸 값 0x2a (42)
│  │  │  │  └ 둘째 칸 serial type 27 → (27-13)/2 = 7바이트 문자열
│  │  │  └ 첫 칸 serial type 1 → 1바이트 정수
│  │  └ 레코드 머리 길이 3
│  └ rowid 5
└ 페이로드 길이 11

지운 뒤 0x0f40 (freeblock)
00 00 00 0d 1b 2a 65 78 61 6d 70 6c 65
└─┬─┘ └─┬─┘
  │     └ freeblock 크기 13 (머리 4바이트 포함)
  └ 다음 freeblock 없음
```

지운 뒤에는 페이로드 길이, rowid, 레코드 머리 길이, 첫 열의 serial type 이 사라지고, 둘째 열의 serial type 0x1b 와 두 열의 본문이 남습니다. 0x1b 를 serial type 으로 읽으면 7바이트 문자열이라서 "example" 을 되찾을 수 있지만, 앞의 0x2a 가 1바이트 정수인지는 테이블 스키마의 열 구성과 맞춰 추정해야 하고, rowid 는 이 자리에서 되찾지 못합니다.

## 절차

1. **파일을 함께 확보합니다.** DB 와 -wal·-shm, 롤백 저널이 있으면 그것까지 한꺼번에 뜨고, 해시를 남긴 사본에서 작업합니다. 원본을 SQLite 로 그냥 열면 체크포인트가 돌아 WAL 이 바뀔 수 있어서 원본은 열지 않습니다. 수집 순서는 [맥 증거 확보 (Acquisition)](../../process-acquisition/evidence-acquisition/index.md) 를 따릅니다.
2. **헤더를 읽습니다.** 페이지 크기, freelist 트렁크 페이지 번호와 페이지 수, auto_vacuum 상태, 텍스트 인코딩을 적습니다 [1]. freelist 페이지 수가 0 이 아니고 auto_vacuum 을 쓰지 않으면 freelist 에 남은 페이지가 있습니다.
3. **freelist 를 따라갑니다.** 첫 트렁크 페이지에서 리프 페이지 번호를 모으고 다음 트렁크로 넘어가기를 0 이 나올 때까지 되풀이한 뒤 [1], 리프 페이지마다 첫 바이트가 B-트리 페이지 종류 값인지, 레코드 모양의 바이트가 있는지 봅니다.
4. **freeblock 사슬을 따라갑니다.** 사용 중인 B-트리 페이지마다 머리 오프셋 1 의 값으로 첫 freeblock 을 찾고 가서 다음 오프셋이 0 이 될 때까지 따라가며 [1], 각 freeblock 의 머리 뒤 바이트를 뽑습니다. 오프셋 7 의 조각 합계도 적어 두지만 1~3바이트라서 레코드로 읽기는 어렵습니다.
5. **레코드를 해석합니다.** 뽑은 바이트에서 serial type 과 본문 길이가 맞아떨어지는 자리를 찾아 위 표대로 읽고, 스키마의 열 수·자료형과 맞는 테이블을 고릅니다. 텍스트는 2단계에서 적은 인코딩으로 읽습니다.
6. **WAL 을 읽습니다.** 헤더의 salt 와 페이지 크기를 적고 프레임을 차례로 읽어, salt 가 같고 체크섬이 맞는 프레임과 그렇지 않은 프레임을 나눕니다 [1]. 같은 페이지 번호의 프레임이 여럿이면 버전별로 늘어놓고 DB 의 같은 페이지와 비교해 사라진 레코드를 찾습니다.
7. **롤백 저널이 있으면 읽습니다.** 헤더 뒤 레코드마다 페이지 번호와 원래 페이지 내용을 꺼내 DB 의 현재 페이지와 비교합니다 [1].
8. **도구로 한 번 더 봅니다.** 사본에 sqlite3 의 `.recover` 를 돌려 손으로 찾은 결과와 맞춰 봅니다(아래 도구 절).
9. **출처를 기록합니다.** 되살린 레코드마다 파일 이름, 페이지 번호, 페이지 안 오프셋, freelist·freeblock·WAL 프레임(salt 가 맞는지)·저널 가운데 어디서 나왔는지를 적습니다.

## 도구

sqlite3 명령줄 도구의 `.recover` 는 복구 확장을 써서 손상된 DB 에서 최대한 많은 내용을 뽑아 SQL 이나 새 DB 로 만들고, 어느 테이블 것인지 모르는 내용은 lost_and_found 테이블에 넣으며, 이 이름은 `--lost-and-found` 로 바꿀 수 있습니다 [4]. freelist 내용도 기본으로 되살리고 `--ignore-freelist` 로 끌 수 있습니다 [4].

```sh
sqlite3 사본.db ".recover" > 사본_recover.sql
```

`.recover` 는 덮어 쓴 데이터는 되살리지 못합니다. 또 지운 내용이 되살아날 수 있고, 값이 바뀌거나(48 이 49 로, 정수가 문자열로) 다른 테이블로 옮겨 가거나 제약 조건을 어길 수 있습니다 [4]. 그래서 `.recover` 결과는 지운 레코드 목록이 아니라 현재 내용과 되살린 내용이 섞인 결과로 보고, 결과 속 값은 5단계처럼 원래 바이트로 돌아가 확인합니다.

## 함정과 한계

secure_delete 가 ON 이면 지운 내용이 0 으로 덮여 있고, FAST 이면 B-트리 페이지는 비워지고 freelist 페이지에만 흔적이 남으며, auto_vacuum 이 FULL 이면 빈 페이지가 커밋마다 파일 끝에서 잘려 나갑니다 [2]. freelist 페이지는 나중에 다시 쓰이고 WAL 은 처음부터 덮어 쓰여서 [2][3], 앱을 오래 쓸수록 옛 흔적이 줄어든다고 보고 기대치를 정합니다.

freeblock 에서는 레코드 앞부분이 가려져 있을 수 있고, 페이로드가 오버플로 페이지로 넘친 레코드는 이어지는 페이지가 freelist 에 흩어져 있으면 조각을 잇기 어렵습니다. 마지막 연결이 닫힐 때 보통 WAL 파일을 지워서 [3] -wal 파일이 없다는 사실만으로 WAL 모드가 아니었다고 할 수 없고, 수집 시점에 앱이 실행 중이었는지를 함께 적어 둡니다.

## 결과를 어떻게 해석하나

되살린 레코드로는 "이 DB 파일 안에 한때 이런 값의 레코드가 쓰였다" 를 알 수 있습니다. 빈 자리에 있다는 사실만으로 사용자가 그 항목을 지웠다고 말할 수 없고, 앱이 스스로 정리하거나 값을 고치는 과정에서 옛 셀 자리가 남았을 가능성도 따집니다. 레코드 안의 시각 열은 그 레코드가 기록한 사건의 시각이지 지운 시각이 아니고, WAL 에서는 salt 가 같은 세대와 다른 세대를 나눠 앞뒤 순서만 말할 수 있습니다.

보고서에는 "이 앱 DB 사본의 12번 페이지 freeblock 에서 대화 내용을 담는 테이블의 열 구성과 맞는 레코드 조각을 찾았고, 문자열 열에 이 내용이 있다" 처럼 위치와 해석 근거를 함께 적습니다(페이지 번호는 문장 형식을 보여 주는 예입니다).
