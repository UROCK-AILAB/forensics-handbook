# 감사 로그 (OpenBSM Audit)

감사 로그 (OpenBSM Audit) 는 커널 감사 하위 시스템이 `/private/var/audit/` 에 남기는 BSM 바이너리 기록이고, macOS 11 부터 사용 중단 예정으로 바뀌어 macOS 14 부터는 꺼져 있으니, 분석 대상의 버전과 설정 파일부터 보고 기록이 남아 있을 만한지 가늠합니다 [1][2].

## 무엇을 기록하나 · 왜 생기나

감사 하위 시스템은 설정 파일 `/etc/security/audit_control` 에 적힌 이벤트 클래스에 맞는 사건을 감사 로그 파일에 씁니다 [1]. 어떤 사건을 남길지는 `flags` 항목이 정하고, 설정 파일 기본값은 `lo,aa` 입니다 [1]. 클래스 이름이 가리키는 사건의 정의는 클래스 정의 파일(`audit_class`)에 있으니, 기본 설정이 어떤 사건을 잡는지는 분석 대상의 설정 파일과 클래스 정의 파일을 함께 읽어 확인합니다.

통합 로그가 앱과 데몬이 스스로 남기는 메시지라면, 감사 로그는 설정한 클래스에 드는 사건을 운영체제 쪽에서 모아 적는 기록입니다. 통합 로그 쪽 로그인·인증 기록은 [통합 로그에서 찾을 것 (Unified Log Events)](unified-log-events/index.md)에서 다룹니다.

## 위치와 버전별 차이

감사 하위 시스템은 macOS 11.0 부터 사용 중단 예정(deprecated)이고 macOS 14.0 부터 꺼져(disabled) 있으며 앞으로 제거될 예정입니다. 대안은 EndpointSecurity API 입니다 [1].

| macOS 버전 | 상태 | 비고 |
|---|---|---|
| 10.15 Catalina | 사용 가능 | 11.0 부터 중단 예정이라는 공지로 미루어 본 것 [1]. 기본으로 켜져 있었는지는 실제 기기에서 확인 |
| 11 Big Sur ~ 13 Ventura | 사용 중단 예정, 아직 동작 | [1] |
| 14 Sonoma 이후 | 꺼짐 | [1]. 관리자가 다시 켤 수 있는지, 무엇이 꺼진 것인지는 실제 기기에서 확인 |
| 26 Tahoe | 실제 기기에서 확인 | 제거 예정이라는 공지만 있음 [1]. 실제로 제거됐는지는 실제 기기에서 확인 |

| 파일 | 경로 | 출처 |
|---|---|---|
| 설정 파일 | `/etc/security/audit_control` | [1] |
| 감사 로그 파일 | `/private/var/audit/` (`/var/audit/`) 아래, 이름 패턴 `[0-9]*.[0-9]*` | [2] |

로그 파일이 들어갈 폴더는 설정 파일의 `dir` 항목이 정하고 기본값이 `/var/audit` 라서 [1], 설정이 바뀐 기기라면 다른 폴더를 봐야 할 수 있습니다.

## 구조

### 설정 파일 audit_control

설정 파일은 `항목:값` 형식의 줄로 되어 있고, 항목과 기본 설정 파일 값은 아래와 같습니다 [1].

| 항목 | 뜻 | 기본 설정 파일 값 |
|---|---|---|
| `dir` | 감사 로그 파일을 두는 폴더. 여러 줄 쓸 수 있고, 바꾸면 감사 시스템을 다시 시작해야 함 | `/var/audit` |
| `flags` | 모든 사용자에게 적용할 감사 이벤트 클래스. 쉼표로 나누고 앞에 `+ - ^ ^+ ^-` 를 붙일 수 있음 | `lo,aa` |
| `naflags` | 특정 사용자에게 돌릴 수 없는 이벤트의 클래스 | `lo,aa` |
| `minfree` | 파일 시스템의 최소 여유 공간(%). 항목이 없으면 20% | `5` |
| `policy` | 전역 정책(`cnt, ahlt, argv, arge, seq, group, trail, path, zonename, perzone`) | `cnt,argv` |
| `filesz` | 로그 파일이 이 크기를 넘으면 새 파일로 넘김. 단위 B·K·M·G, 최소 512K | `2M` |
| `expire-after` | 오래된 로그를 지우는 기준. 나이(s·h·d·y)와 크기(B·K·M·G)를 AND·OR 로 조합 | `10M` |
| `host` | 감사 기록에 넣을 호스트 이름이나 IP. DNS 대신 `/etc/hosts` 를 권함 | 없음 |

기본 설정의 `policy` 에 든 `argv` 는 이름으로 짐작하면 명령 인자와 관련된 정책입니다. 켜져 있을 때 기록에 무엇이 들어가는지는 실제 기록으로 확인해야 합니다.

### 로그 파일 이름

파일 이름은 "시작 시각.끝 시각" 이고, 두 시각은 각각 `YYYYMMDDhhmmss` 형식입니다 [2]. 아래는 이 규칙으로 만든 예시이고, 실제 기기에서 나온 이름이 아닙니다.

```
20240101093000.20240101120000
```

앞의 14자리는 2024년 1월 1일 09:30:00, 뒤의 14자리는 같은 날 12:00:00 으로 읽습니다. 아직 닫히지 않은 파일의 끝 시각 자리에 무엇이 들어가는지는 실제 데이터로 확인합니다.

### 기록 형식

파일 안의 기록은 BSM 바이너리 형식이고, 텍스트나 XML 로 풀어 보는 도구 `praudit` 와 조건으로 걸러내는 도구 `auditreduce` 가 있습니다. 두 도구의 옵션과 출력 형식은 각 도구의 매뉴얼을 따릅니다.

## 증거로서 의미

**증명하는 것.** 감사 로그 파일이 남아 있으면, 파일 이름의 시작·끝 시각 사이에 감사 하위 시스템이 켜져서 기록을 썼다는 뜻입니다 [2]. 설정 파일은 그 맥이 어떤 클래스를 남기도록, 얼마나 오래 보관하도록 설정되어 있었는지 알려 주고 [1], 기본값과 다른 줄이 있으면 누군가 설정을 바꾼 흔적으로 봅니다.

**증명하지 못하는 것.** 감사 로그 파일이 없다고 해서 사건이 없었다는 뜻이 아닙니다. macOS 14 이후에는 하위 시스템이 꺼져 있고 [1], 켜져 있었더라도 `flags` 에 없는 클래스의 사건은 처음부터 남지 않습니다. 기본 설정에서는 크기 기준으로 오래된 파일을 지우니 [1], 남은 파일이 덮는 기간이 짧을 수 있습니다. 기록에 사용자 식별 정보가 담기더라도, 그 계정을 쓰던 사람이 누구인지는 다른 기록으로 맞춰야 합니다.

보고서에는 "`/private/var/audit/` 에 이 시각부터 이 시각까지를 덮는 감사 로그 파일이 있고, 설정 파일의 `flags` 값은 이것이다" 처럼 파일과 설정으로 확인되는 만큼만 씁니다.

## 시각 해석

파일 이름의 시각이 UTC 인지 현지 시각인지, 기록 안의 시각이 어떤 기준으로 적히는지는 실제 데이터로 확인해야 합니다. 파일 이름 시각과 파일 시스템 시각을 나란히 놓고 차이가 얼마인지 재어 보고, 분석 대상의 시간대는 [시간대와 시계 설정 (Time Zone·NTP)](../system-account/time-zone.md)에서 확인합니다. 여러 로그를 한 시간축에 놓는 방법은 [타임라인 작성 (Timeline)](../../03-techniques/analysis/timeline/index.md)에 있습니다.

## 함정과 한계

- **버전부터 봅니다.** macOS 14 이후 기기에서 감사 로그가 비어 있는 것은 공지된 동작에 맞습니다 [1]. 반대로 14 이후인데 새 파일이 계속 생겼다면 누군가 일부러 다시 켰을 가능성을 살펴보되, 같은 버전의 시험 기기에서 다시 켜지는지 재현해 보기 전에는 단정하지 않습니다.
- **설정 변경과 삭제.** `flags` 를 줄이거나 `expire-after` 를 줄이면 남는 기록이 줄어듭니다 [1]. 설정 파일의 파일 시스템 시각과 [파일 시스템 이벤트 (FSEvents)](../filesystem/fsevents/index.md)로 설정 파일과 `/private/var/audit/` 폴더가 언제 바뀌었는지 봅니다.
- **파일 사이의 빈틈.** 파일 이름에 시작과 끝 시각이 들어 있으니, 한 파일의 끝 시각과 다음 파일의 시작 시각 사이가 크게 비면 그 사이 파일이 지워졌거나 감사가 멈췄던 구간으로 의심해 볼 수 있습니다. 기본 설정의 크기 기준 삭제로도 앞쪽 파일이 사라지니, 맨 앞의 빈틈과 중간의 빈틈을 나눠 봅니다.
- **여러 폴더.** `dir` 는 여러 줄 쓸 수 있어서 [1], 설정 파일의 모든 `dir` 줄을 확인합니다.
- **도구 출력 해석.** `praudit` 출력의 필드 뜻은 도구 문서와 실제 출력을 대조한 뒤 보고서에 옮깁니다.

## 직접 분석해 보기

**헥스로 한 번.** 로그 파일 하나를 헥스 편집기로 열어 사람이 읽는 텍스트가 아니라 바이너리 기록이라는 점을 확인하고, 파일 이름의 시작·끝 시각을 위 예시처럼 풀어 적습니다. 기록 하나의 바이트 구성은 이 페이지에서 다루지 않으니 헥스로 필드를 풀지는 않고, 파일 크기가 설정 파일의 `filesz` 값 근처에서 끊기는지만 봅니다.

**공개 도구로 한 번.**

1. 이미지에서 `private/etc/security/audit_control` 과 `private/var/audit/` 폴더 전체를 꺼냅니다.
2. 설정 파일의 각 항목을 위 표의 기본값과 비교해 달라진 줄을 적습니다.
3. 로그 파일 이름을 시작 시각 순서로 늘어놓고, 파일 사이의 빈틈을 표로 만듭니다.
4. 분석용 맥이나 도구가 있는 환경에서 `praudit` 로 파일을 풀어 보고, 조사할 시간대만 `auditreduce` 로 걸러 냅니다. 옵션은 도구의 매뉴얼을 따릅니다.

> 그림 자리: 감사 로그 파일 이름을 시작 시각 순서로 늘어놓고, 파일 사이 빈틈을 표시한 시간 막대

## 실습

NIST CFReDS 처럼 공개된 맥 시험 이미지를 하나 골라 아래 질문을 풀어 봅니다.

1. 그 이미지의 macOS 버전으로 보면 감사 하위 시스템은 동작 중이었을까, 꺼져 있었을까?
2. `audit_control` 의 각 항목 가운데 기본값과 다른 것이 있는가?
3. `/private/var/audit/` 의 파일 이름으로 보면, 감사 로그가 덮는 가장 이른 시각과 가장 늦은 시각은 언제인가?
4. 파일 사이에 빈틈이 있다면, 그 구간에 다른 로그에서는 무슨 일이 보이는가?
