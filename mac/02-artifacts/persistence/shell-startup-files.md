# 셸 시작 파일 (zshrc·bash_profile)

셸 시작 파일 (Shell Startup Files)은 zsh·bash가 뜰 때마다 읽어서 그 안의 명령을 실행하는 텍스트 파일이고, 사용자가 터미널을 열거나 셸 스크립트가 돌 때 같이 실행되는 자리라서 사용자 몫의 자동 실행과 환경 조작을 찾을 때 확인합니다.

## 무엇을 기록하나 · 왜 생기나

셸은 시작할 때 정해진 파일을 차례로 읽어 환경 변수·경로·별칭 같은 설정을 적용하고, 파일 안에 적힌 명령은 무엇이든 그 셸의 권한으로 실행합니다. 원래는 사용자가 작업 환경을 맞추라고 둔 파일이지만, 한 줄만 끼워 넣어도 셸이 뜰 때마다 그 명령이 돌기 때문에 사고 조사에서는 자동 실행 위치로 봅니다.

macOS 10.15부터 새로 만드는 사용자 계정의 기본 셸은 zsh이고, 그 전에는 bash가 기본이었습니다 [1]. `.zprofile` 은 `.bash_profile` 에 해당하고 SSH 접속을 포함해 로그인 때 돌며, `.zshrc` 는 `.bashrc` 에 해당하고 새 터미널 세션마다 돕니다 [1]. 셸은 `chsh -s` 로 바꾸고, 바꿀 수 있는 셸의 경로는 `/etc/shells` 에 적힌 것 가운데 하나입니다 [1].

이 페이지는 시작 파일에 적힌 설정을 다루고, 셸에서 친 명령의 기록은 [터미널 명령 기록 (zsh_history·bash_sessions)](../execution/shell-history.md)에서 다룹니다.

## 위치와 버전별 차이

### 기본 셸

| macOS | 새로 만든 계정의 기본 셸 [1] |
|---|---|
| 10.14 이하 | bash |
| 10.15 이후 | zsh |

10.15부터 zsh가 기본인 것은 "새로 만든" 계정이라서, 10.14 이하에서 만들고 업그레이드한 계정은 bash로 남아 있을 수 있습니다. 그래서 macOS 버전만 보고 셸을 정하지 말고, 계정마다 로그인 셸이 무엇으로 설정돼 있는지를 [사용자 계정 (Local Accounts)](../system-account/user-accounts/index.md)의 계정 기록에서 확인한 뒤 그 셸의 시작 파일을 봅니다. 로그인 셸이 zsh여도 사용자가 bash를 따로 띄울 수 있어서, 두 셸의 파일을 모두 수집합니다.

### zsh가 읽는 순서

zsh는 시작 파일을 아래 순서로 읽습니다 [2]. `$ZDOTDIR` 이 정해져 있지 않으면 `HOME` 을 쓰므로 [2], 보통은 사용자 홈의 `~/.zshenv`, `~/.zprofile`, `~/.zshrc`, `~/.zlogin` 이 됩니다.

| 순서 | 파일 | 읽는 때 [2] |
|---|---|---|
| 1 | `/etc/zshenv` | 항상 (끌 수 없음) |
| 2 | `$ZDOTDIR/.zshenv` | 항상 |
| 3 | `/etc/zprofile` | 로그인 셸 |
| 4 | `$ZDOTDIR/.zprofile` | 로그인 셸 |
| 5 | `/etc/zshrc` | 대화형 셸 |
| 6 | `$ZDOTDIR/.zshrc` | 대화형 셸 |
| 7 | `/etc/zlogin` | 로그인 셸 |
| 8 | `$ZDOTDIR/.zlogin` | 로그인 셸 |

로그인 셸이 끝날 때는 `$ZDOTDIR/.zlogout` 을 읽고 이어서 `/etc/zlogout` 을 읽지만, 셸이 다른 프로세스를 `exec` 해서 끝나면 로그아웃 파일을 읽지 않습니다 [2].

`/etc/` 아래 파일은 그 맥의 모든 사용자에게 적용되고, `$ZDOTDIR`(보통 홈) 아래 파일은 그 사용자에게만 적용됩니다. 표에서 1·2번은 "항상" 읽으므로 대화형이 아닌 셸, 예를 들어 스크립트를 돌리는 셸에도 적용되고, 대화형 셸에서만 읽는 `.zshrc` 보다 적용 범위가 넓습니다 [2].

### bash

`.bash_profile` 과 `.bashrc` 는 각각 zsh의 `.zprofile`·`.zshrc` 에 해당합니다 [1]. 수집할 때는 `/etc/profile`, `~/.bash_profile`, `~/.bash_login`, `~/.profile`, `~/.bashrc` 다섯 파일을 모두 가져오고, 이 파일들을 읽는 순서는 bash 문서로, macOS에 기본으로 들어 있는 bash 버전은 실제 기기에서 따로 확인합니다.

## 구조

시작 파일은 셸 문법으로 쓴 텍스트 파일이고, 그 셸이 한 줄씩 실행합니다. 조사에서는 아래 두 종류의 줄을 봅니다.

첫째는 무언가를 실행하는 줄입니다. 다른 스크립트를 불러 읽는 줄, 백그라운드로 프로그램을 띄우는 줄, 네트워크에서 무언가를 받아 오는 줄이 여기에 들고, 불려 오는 파일도 같은 방식으로 따라가 읽어야 전체 그림이 나옵니다.

둘째는 뒤에 오는 동작을 바꾸는 줄입니다. `RCS`·`GLOBAL_RCS` 옵션은 기본으로 켜져 있고, 시작 파일을 읽는 도중에 꺼지면 그 뒤로 해당 종류의 시작 파일을 읽지 않습니다 [2]. `RCS` 가 꺼진 채 셸이 끝나면 명령 기록 파일도 저장하지 않습니다 [2]. 또 `~/.zshenv` 에서 `ZDOTDIR` 을 바꾸면 그 뒤의 사용자 시작 파일을 홈이 아닌 다른 폴더에서 읽게 됩니다 [2]. 이런 줄이 있으면 홈의 `.zshrc` 만 보고 끝내면 실제로 읽히는 파일을 놓칩니다.

`/etc/zshrc`·`/etc/zprofile` 처럼 macOS가 기본으로 넣어 두는 시스템 쪽 파일은 같은 macOS 버전의 깨끗한 설치본과 비교해서 바뀐 줄을 가려냅니다.

## 컴파일된 시작 파일 (.zwc)

zsh는 시작 파일을 평문 대신 미리 컴파일한 파일로 읽을 수 있어서, 평문 시작 파일만 읽으면 셸이 실제로 실행하는 내용을 놓칠 수 있습니다. 위 순서 표의 시작 파일과 로그아웃 파일은 모두 `zcompile` 내장 명령으로 미리 컴파일할 수 있고, 원래 파일 이름 뒤에 `.zwc` 를 붙인 컴파일 파일이 있으면서 원래 파일보다 새로우면 zsh는 원래 파일 대신 컴파일 파일을 읽습니다 [2]. `.zwc` 는 zsh 워드 코드 (zsh word code)의 줄임말입니다 [6]. 시작 파일 안에서 `source`(`.`) 로 불러 읽는 파일에도 같은 규칙이 있어서, `file.zwc` 가 `file` 보다 새롭고 `file` 을 컴파일한 것이면 `file.zwc` 에서 명령을 읽습니다 [6].

그래서 홈의 `.zshrc` 가 깨끗해 보여도, 옆에 있는 `.zshrc.zwc` 가 더 새로우면 셸이 뜰 때 실행되는 것은 `.zshrc.zwc` 의 내용입니다 [5]. 사용자 홈(또는 `$ZDOTDIR`)에서는 `.zshenv.zwc`, `.zprofile.zwc`, `.zshrc.zwc`, `.zlogin.zwc`, `.zlogout.zwc` 를 보고 [5], `/etc/` 의 시스템 시작 파일 옆에도 같은 이름의 `.zwc` 가 있는지 확인합니다 [2]. 평문 시작 파일을 수집하는 도구도 `.zwc` 는 따로 수집 대상에 넣지 않은 경우가 있으므로 [5], 시작 파일을 모을 때 같은 폴더의 같은 이름 `.zwc` 를 수집 목록에 직접 넣습니다. `.zwc` 확장자로 넓게 찾으면 시작 파일 말고도 함수 여러 개를 묶어 컴파일한 다이제스트 파일 (digest file)이 함께 나오는데 [6][8], 이 파일은 시작 파일과 별도로 목록에 적어 둡니다.

**어느 파일이 읽혔는지 판단하기.** 평문과 `.zwc` 의 수정 시각을 비교합니다. `.zwc` 가 더 새로우면 zsh는 `.zwc` 를 읽고, 평문이 더 새로우면 평문을 읽습니다 [2]. 평문이 더 새로운 경우에도 `.zwc` 에는 컴파일할 때의 내용이 남아 있어서, 누군가 평문을 고치거나 지운 뒤에도 그 전 코드를 되살리는 데 쓸 수 있습니다 [8]. 이 비교는 수집한 파일의 수정 시각이 원래 값 그대로일 때만 뜻이 있으므로, 시각을 보존하는 방법으로 수집하고 수정 시각은 바꿀 수 있는 값이라는 점을 감안해 [파일 시스템 이벤트 (FSEvents)](../filesystem/fsevents/index.md)에 남은 두 파일의 생성·변경 순서와 맞춰 봅니다.

**내용 확인하기.** `.zwc` 는 컴파일된 형식일 뿐 암호화한 파일이 아니라서 내용을 되살릴 수 있습니다 [5]. 수집한 사본을 분석용 기기에서 아래 순서로 봅니다.

1. `zsh -f -c 'zcompile -t evidence/.zshrc.zwc'` 로 파일을 살펴봅니다(`evidence/` 는 사본을 둔 폴더로, 만든 예시). `-t` 는 첫 줄에 이 파일을 컴파일한 zsh 버전과 읽는 방식(직접 읽기 또는 메모리 매핑)을 보여 주고, 그 아래에 컴파일에 들어간 원래 파일 이름을 나열합니다 [6]. `-f` 는 `RCS` 옵션을 끄는 것과 같아서, 이 셸은 분석용 기기의 `/etc/zshenv` 만 읽고 다른 시작 파일은 읽지 않습니다 [7].
2. `strings -a -n 4 evidence/.zshrc.zwc | grep -Ei 'https?://|curl|osascript|launchctl|base64'` 처럼 문자열을 뽑아 네트워크 주소, 다른 프로그램을 띄우는 명령, 인코딩된 값이 있는지 봅니다 [5].
3. 공개 도구 zwc-decompile 의 `zwc-decompile.py` 로 소스와 비슷한 zsh 코드를 되살립니다 [8]. 이 도구는 파일을 zsh로 실행하거나 `source` 하지 않고 파이썬으로 직접 파싱하며, `--strings` 를 붙이면 문자열 표도 함께 출력합니다 [8]. 주석과 원래 줄 배치는 컴파일할 때 사라지므로 결과는 원본 파일이 아니라 재구성한 코드이고, zsh 5.9 의 워드 코드 형식을 기준으로 만들어져 다른 버전에서 컴파일한 파일이면 경고를 냅니다 [8].
4. 되살린 코드를 같은 이름의 평문 시작 파일과 비교해 평문에 없는 줄을 골라내고, 그 줄은 위 "구조" 절의 두 종류 줄과 같은 방식으로 따라갑니다.

`.zwc` 가 있다는 것만으로 악성이라고 보지 않습니다. `zcompile` 은 원래 함수를 불러오거나 스크립트를 읽을 때 텍스트를 파싱하는 단계를 건너뛰어 빠르게 하려는 기능이라 [6], 사용자가 시작 속도 때문에 만들어 둔 파일일 수 있습니다. 판단은 컴파일된 내용이 평문과 다른지, 다르다면 무엇을 실행하는지로 합니다. 문자열 표에 어떤 주소나 명령이 있다는 것도 그 문자열이 파일에 들어 있다는 뜻일 뿐, 그 코드가 실제로 실행됐다는 뜻은 아닙니다 [8].

## 증거로서 의미

**증명하는 것.** 시작 파일에 어떤 줄이 있으면 수집한 시점에 그 셸이 뜰 때 그 명령을 실행하도록 설정돼 있었다는 뜻이고, 파일이 사용자 홈에 있는지 `/etc/` 에 있는지로 영향을 받는 계정의 범위를 말할 수 있습니다.

**증명하지 못하는 것.** 설정이 있다는 사실은 셸이 실제로 떴거나 명령이 실제로 돌았다는 뜻이 아닙니다. 파일을 누가 고쳤는지도 파일만으로는 알 수 없고, 사용자가 스스로 넣은 설정인지 다른 프로그램이 넣은 줄인지도 내용만으로 단정하지 않고, 낯선 줄은 곧바로 악성으로 적기 전에 그 줄이 부르는 파일의 정체를 먼저 확인합니다.

보고서에는 "이 사용자의 `.zshrc` 에 이 스크립트를 부르는 줄이 있었다" 처럼 쓰고, 실행 여부는 실행 흔적과 맞춘 뒤에 따로 씁니다.

## 시각 해석

시작 파일에는 줄마다 넣은 시각이 적히지 않습니다. 그래서 바뀐 시기는 파일 시스템 시각과 [파일 시스템 이벤트 (FSEvents)](../filesystem/fsevents/index.md)로 좁히고, 파일의 수정 시각은 "마지막으로 바뀐 때" 일 뿐 어느 줄이 그때 들어갔는지는 알려 주지 않는다는 점을 나눠서 씁니다. 어느 줄이 언제 들어갔는지는 [스냅숏과 백업 비교 (Snapshot·Time Machine Diff)](../../03-techniques/analysis/snapshot-diff.md)로 지난 판과 맞춰 봐야 좁혀집니다.

## 함정과 한계

지속성 위치를 정리한 자료가 셸 시작 파일을 빼놓는 일이 있습니다. 널리 쓰이는 지속성 정리 글과 수집 정의 가운데에도 셸 시작 파일을 지속성 위치로 다루지 않는 것이 있으므로 [3][4], 체크리스트나 수집 정의만 따라가면 이 파일들이 빠질 수 있습니다.

홈의 `.zshrc` 한 파일만 보는 실수가 흔합니다. `.zshenv` 는 대화형이 아닌 셸에도 적용되고, `/etc/` 쪽 파일은 모든 사용자에게 적용되며, `ZDOTDIR` 이 바뀌어 있으면 다른 폴더의 파일이 읽힙니다. 표의 여덟 파일과 로그아웃 파일 두 개, bash 쪽 파일을 모두 모은 뒤 실제 읽히는 순서대로 따라갑니다.

명령 기록이 비어 있을 때 곧바로 "기록을 지웠다" 고 보지 않습니다. 시작 파일에서 `RCS` 를 끄는 설정이 있으면 셸이 끝날 때 기록 파일을 저장하지 않으므로 [2], 기록이 없는 원인이 삭제인지 설정인지를 시작 파일에서 먼저 확인하고 [증거를 없애려 했나 (Anti-Forensics)](../../04-scenarios/activity/anti-forensics/index.md)의 다른 흔적과 함께 판단합니다.

터미널 앱이 새 창을 로그인 셸로 여는지, 터미널 세션 복원 파일이 따로 남는지는 실제 기기로 확인합니다. 그래서 "터미널을 열면 이 파일이 읽힌다" 를 보고서에 쓸 때는 `.zprofile` 은 로그인 때, `.zshrc` 는 새 터미널 세션마다 읽힌다는 범위 [1] 안에서만 씁니다.

## 직접 분석해 보기

### 헥스로 한 번

시작 파일은 텍스트라서 대부분 텍스트 편집기로 충분하지만, 한 번은 헥스 편집기로 열어 줄바꿈과 보이지 않는 문자를 확인합니다. 제어 문자나 긴 공백 뒤에 붙은 명령, 파일 끝에 줄바꿈 없이 이어 붙은 줄은 편집기 화면에서 잘 보이지 않다가 헥스에서 드러납니다.

### 공개 도구로 한 번

셸 시작 파일은 공개 수집 정의에 빠져 있을 수 있어서 [3][4], 수집 목록에 직접 넣습니다. 가져온 파일은 아래 순서로 봅니다.

1. 계정마다 로그인 셸을 확인하고, 그 사용자의 홈과 `/etc/` 에서 zsh·bash 시작 파일을 모두 모읍니다.
2. `~/.zshenv` 와 `/etc/zshenv` 에서 `ZDOTDIR` 을 바꾸는 줄이 있는지 먼저 보고, 있으면 그 폴더의 시작 파일도 모읍니다.
3. `grep` 같은 텍스트 검색 도구로 다른 파일을 불러 읽는 줄, 프로그램을 띄우는 줄, 네트워크 주소가 들어간 줄, `RCS` 를 끄는 줄을 찾습니다.
4. 불려 오는 파일을 따라가 같은 방식으로 읽고, 시스템 쪽 파일은 같은 버전의 설치본과 비교합니다.

실행 중인 시스템에서 확인할 때의 원칙은 [라이브 대응 (Live Response)](../../03-techniques/process-acquisition/live-response/index.md)을 따릅니다.

## 실습

NIST CFReDS 같은 공개 맥 이미지를 골라 아래 질문을 풀어 봅니다.

1. 이미지의 macOS 버전과 계정마다 설정된 로그인 셸을 적고, 기본 셸 표와 맞는지 봅니다.
2. 사용자마다 홈과 `/etc/` 의 zsh·bash 시작 파일이 있는지 적고, `ZDOTDIR` 을 바꾸는 줄이 있는지 봅니다.
3. 시작 파일에서 다른 파일을 불러 읽거나 프로그램을 띄우는 줄을 모두 뽑고, 불려 오는 파일이 이미지에 있는지 확인합니다.
4. 명령 기록 파일이 있는지, 없다면 시작 파일에 `RCS` 를 끄는 설정이 있는지 봅니다.
