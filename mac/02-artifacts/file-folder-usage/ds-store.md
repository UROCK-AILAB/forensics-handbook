# 폴더 보기 파일 (.DS_Store)

파인더는 자기가 손댄 폴더마다 숨김 파일 `.DS_Store` 를 두고 그 폴더를 어떤 보기로 열었는지, 아이콘을 어디에 두었는지, 파일마다 붙은 스포트라이트 설명과 크기 같은 값을 파일 이름별 레코드로 적어 두므로, 파인더가 그 폴더를 다룬 흔적과 그 안에 있던 파일 이름의 단서가 됩니다.

## 무엇을 기록하나 · 왜 생기나

파인더는 폴더와 파일을 어떻게 보여 줄지를 자기가 건드린 폴더마다 그 폴더의 `.DS_Store` 에 저장합니다 [1]. 그래서 이 파일에는 폴더 자체의 보기 설정(보기 방식, 창 크기와 배치, 배경)과 폴더 안 파일 하나하나에 대한 값(아이콘 위치, 스포트라이트 설명, 논리·물리 크기)이 함께 들어 있고, 레코드마다 어느 파일에 대한 값인지 파일 이름이 붙습니다 [1].

포렌식에서 이 파일을 여는 이유는 두 가지입니다. 하나는 파인더가 그 폴더를 다룬 적이 있다는 흔적이고, 다른 하나는 레코드에 붙은 파일 이름입니다. 휴지통 폴더의 `.DS_Store` 에는 되돌려 놓기에 쓰는 원래 위치까지 남는데, 이 부분은 [휴지통 (.Trash)](trash.md)에서 다룹니다.

파일이 지워진 뒤에도 그 파일의 레코드가 `.DS_Store` 에 남는지는 공개된 분석 자료가 없습니다. 조사에서 이 점을 근거로 삼으려면 같은 macOS 버전에서 파일을 만들고 지운 뒤 레코드가 어떻게 되는지 시험해 보고, 그 결과를 시험 조건과 함께 적습니다.

## 위치와 버전별 차이

`.DS_Store` 는 파인더가 다룬 폴더마다 하나씩 그 폴더 바로 안에 생기고, 이름이 점으로 시작하는 숨김 파일입니다 [1]. 네트워크 볼륨이나 USB 볼륨에는 이 파일을 만들지 않게 하는 설정이 있다고 알려져 있습니다.

알려진 버전 차이는 몇몇 레코드가 Snow Leopard 이후에 plist 로 바뀐 것 하나이고 [1], 10.15 Catalina 이후 버전끼리 형식이 달라졌다는 공개 자료는 없습니다.

| 구분 | 레코드 | 출처 |
|---|---|---|
| Snow Leopard 이후 plist 로 적는 레코드 | `bwsp`(창 크기·배치), `icvp`(아이콘 보기), `lsvp`·`lsvP`(목록 보기) | [1] |
| 10.15 Catalina 이후의 차이 | 공개 자료 없음 | — |

## 구조

`.DS_Store` 는 버디 할당자 (buddy allocator) 로 블록을 나눠 쓰는 파일이고, 그 블록 가운데 하나에 B-트리가 들어 있어 레코드를 담습니다 [1].

### 파일 머리와 할당자

| 오프셋 | 크기 | 값 | 뜻 |
|---|---|---|---|
| 0x00 | 4바이트 | `00 00 00 01` | 파일 맨 앞 값 |
| 0x04 | 4바이트 | `42 75 64 31` (`Bud1`) | 버디 할당자 매직 |

할당자 헤더에는 정보 블록 (bookkeeping block) 의 오프셋과 크기, 검증용으로 한 번 더 적은 오프셋, 뜻을 모르는 16바이트가 있습니다 [1]. 정보 블록에는 블록 개수와 블록 주소 배열, 디렉터리 개수와 디렉터리 항목, 크기별 빈 블록 목록 32개(2^0 부터 2^31 까지)가 들어 있습니다 [1]. 디렉터리 항목은 1바이트 길이와 이름, 4바이트 블록 번호로 이루어지고, 이름이 `DSDB` 인 항목이 B-트리 헤더가 든 블록을 가리킵니다 [1].

### B-트리

B-트리 헤더는 20바이트이고 정수 다섯 개가 차례로 들어 있습니다 [1].

| 순서 | 뜻 |
|---|---|
| 1 | 루트 노드의 블록 번호 |
| 2 | 내부 노드 층 수(트리 높이에서 1을 뺀 값) |
| 3 | 전체 레코드 수 |
| 4 | 전체 노드 수 |
| 5 | 늘 0x1000 |

노드는 P 값과 개수로 시작하고, P 가 0 이면 잎 노드입니다 [1]. 레코드를 모두 뽑으려면 루트에서 시작해 잎 노드까지 내려가며 차례로 읽습니다.

> 그림 자리: 파일 머리 → 할당자 헤더 → 정보 블록 → 디렉터리 항목 `DSDB` → B-트리 헤더 → 루트 노드 → 잎 노드의 레코드로 이어지는 흐름

### 레코드

레코드 하나는 아래 순서로 이어집니다 [1].

| 차례 | 크기 | 내용 |
|---|---|---|
| 1 | 4바이트 | 파일 이름 길이(글자 수) |
| 2 | 길이 × 2바이트 | 파일 이름. 빅엔디언 UTF-16 |
| 3 | 4바이트 | 구조 ID (4글자 코드) |
| 4 | 4바이트 | 자료형 (4글자 코드) |
| 5 | 자료형에 따라 다름 | 값 |

자료형은 아래 여덟 가지입니다 [1].

| 자료형 | 값 |
|---|---|
| `long` | 4바이트 정수 |
| `shor` | 4바이트. 앞 2바이트는 0 |
| `bool` | 1바이트 |
| `blob` | 길이 뒤에 바이트 |
| `type` | 4글자 코드 |
| `ustr` | 글자 수 뒤에 UTF-16 글자 |
| `comp` | 8바이트 정수 |
| `dutc` | 8바이트 정수. 1904년 맥 기준 시각부터 1/65536초 단위로 센 값 |

### 주요 구조 ID

주요 구조 ID 와 뜻은 아래와 같습니다 [1].

| 구조 ID | 자료형·값 | 뜻 |
|---|---|---|
| `Iloc` | `blob` (16바이트) | 아이콘 위치 |
| `bwsp` | 바이너리 plist | 창 크기와 배치 (Snow Leopard 이후) |
| `icvp` | plist | 아이콘 보기 설정 (Snow Leopard 이후) |
| `lsvp`, `lsvP` | plist | 목록 보기 설정 (Snow Leopard 이후) |
| `vstl` | `type` | 보기 방식. `icnv`, `clmv`, `Nlsv`, `Flwv` |
| `fwi0` | 16바이트 | 창 정보 |
| `icvo` | 18~26바이트 | 아이콘 보기 옵션 |
| `BKGD` | 12바이트 | 배경 |
| `pict` | — | 배경 그림의 별칭 |
| `cmmt` | `ustr` | 스포트라이트 설명 |
| `lg1S`, `logS` | `comp` | 논리 크기 |
| `ph1S`, `phyS` | `comp` | 물리 크기 |
| `modD`, `moDD` | `dutc` | 시각. 폴더에만 붙고, 둘 중 하나만 나오거나 둘 다 나옴 |
| `dscl` | `bool` | 목록 보기에서 하위 폴더를 펼쳐 둠 |
| `extn` | `ustr` | 확장자로 보이는 문자열. 다른 값일 때도 있음 |
| `vSrn` | `long` | 늘 1 |
| `ICVO`, `LSVO` | `bool` | 뜻 모름 |
| `info`, `icgo`, `dilc`, `lssp`, `GRP0` | — | 뜻 모름 |

plist 로 적힌 레코드는 [속성 목록 파일 (Property List)](../../01-foundations/data-formats/plist/index.md)의 방법으로 한 번 더 풀고, `pict` 의 별칭은 [파일 참조 데이터 (Alias·Bookmark)](../../01-foundations/value-decoding/alias-bookmark.md)에서 다룹니다. 휴지통에서만 보이는 `ptbL`, `ptbN` 은 형식 문서에는 없고 mac_apt 에만 나옵니다 [2].

## 증거로서 의미

**증명하는 것.** 어떤 폴더에 `.DS_Store` 가 있으면 파인더가 그 폴더를 다룬 적이 있다는 흔적이고 [1], 레코드에 붙은 파일 이름은 그 이름의 항목에 대해 파인더가 보기 정보를 적어 둔 적이 있다는 기록입니다. `cmmt` 레코드는 그 항목에 스포트라이트 설명이 붙어 있었다는 기록이고, `lg1S`·`ph1S` 같은 크기 레코드는 그때의 크기를 보여 줍니다 [1]. `vstl` 은 그 폴더의 보기 방식을, `dscl` 은 목록 보기에서 하위 폴더를 펼쳐 둔 상태를 보여 주지만 [1], 이 값이 사용자가 직접 보기를 바꿔야만 생기는지는 실제 데이터로 확인해야 합니다.

**증명하지 못하는 것.** 레코드에 이름이 있다고 그 파일이 지금도 그 폴더에 있다는 뜻은 아니고, 사용자가 그 파일을 열었다는 뜻도 아닙니다. 파일이 지워진 뒤 레코드가 남는지는 공개 자료가 없으므로, 폴더에 없는 이름이 레코드에 있을 때 "지운 파일" 이라고 단정하지 않고 다른 기록으로 확인합니다. 레코드에는 어느 사용자가 그 보기를 만들었는지 적혀 있지 않고, 폴더에 `.DS_Store` 가 없다고 해서 그 폴더를 쓰지 않았다고 말할 수도 없습니다. 이 파일은 파인더가 만들기 때문에 [1], 터미널이나 다른 앱으로만 다룬 폴더에는 이 파일이 없을 수 있습니다.

보고서에는 "피조사자가 이 파일을 봤다" 가 아니라 "이 폴더의 `.DS_Store` 에 이 이름으로 된 레코드가 있다" 처럼 적습니다.

## 시각 해석

레코드 안에서 시각으로 읽히는 값은 `modD`, `moDD` 이고 폴더에만 붙는데 [1], 이 값을 읽는 방법이 자료마다 다릅니다.

| 자료 | `modD`·`moDD` 를 읽는 방법 |
|---|---|
| 형식 문서 [1] | `dutc`. 1904년 맥 기준 시각부터 1/65536초 단위로 센 8바이트 정수 |
| mac_apt `TRASH` 플러그인 [2] | 리틀엔디언 8바이트 실수(`<d`)로 풀어 2001-01-01 기준 맥 절대 시각으로 읽음 (휴지통 `.DS_Store` 를 읽을 때) |

두 해석 가운데 어느 쪽이 맞는지 실제 파일로 검증한 공개 자료는 없습니다. 조사에서는 같은 8바이트를 두 방법으로 모두 풀어 보고, 폴더의 파일 시스템 시각과 비교해 말이 되는 쪽을 쓰되 보고서에는 어느 해석을 썼는지 밝힙니다. 기준점끼리의 관계는 [맥의 시각 값 (Mac Absolute Time·Unix·HFS)](../../01-foundations/value-decoding/mac-time-values.md)에 정리돼 있습니다.

그 밖의 레코드에는 시각이 없어서, `.DS_Store` 파일 자체의 파일 시스템 시각을 함께 봅니다. 다만 그 시각은 파일 전체를 마지막으로 쓴 때일 뿐이라서 어느 레코드가 그때 바뀌었는지는 알려 주지 않습니다.

## 함정과 한계

- **숨김 파일을 빼고 수집하는 경우.** 이름이 점으로 시작해서 숨김 파일을 건너뛰는 복사 방법으로는 빠집니다. 폴더마다 하나씩 흩어져 있으니 수집할 때 전체 볼륨에서 이름으로 찾습니다.
- **시각 해석을 하나로 단정하는 경우.** `modD`·`moDD` 는 앞 절처럼 해석이 둘로 갈립니다 [1][2].
- **뜻 모를 레코드.** `info`, `icgo`, `dilc`, `lssp`, `GRP0` 은 뜻이 알려지지 않은 값이라서 [1], 이 값에 해석을 붙이지 않습니다. `extn` 도 확장자가 아닌 값이 들어 있을 때가 있습니다 [1].
- **이름 맞추기.** 레코드의 파일 이름을 폴더 목록과 맞출 때 겉보기에 같은 이름이 바이트로는 다를 수 있으니, [유니코드 정규화 (NFD·NFC)](../../01-foundations/value-decoding/unicode-normalization.md)의 방법으로 정규화한 뒤 비교합니다.
- **지우기와 조작.** `.DS_Store` 는 보통 파일이라서 지우거나 다른 폴더의 것으로 바꿔 넣을 수 있고, 파일 안에는 그런 일이 있었다는 표시가 따로 남지 않습니다. 없어진 파일은 [삭제 데이터 복구 (Data Recovery)](../../03-techniques/analysis/data-recovery/index.md)나 스냅숏·백업에서 찾아봅니다.

## 직접 분석해 보기

원본 폴더에서 `.DS_Store` 를 작업 폴더로 복사한 뒤 사본을 엽니다.

### 헥스로 한 번

아래 바이트는 형식 문서 [1]의 설명에 맞춰 만든 예시이고, 실제 데이터에서 나온 값이 아닙니다. 첫 줄은 파일 맨 앞 8바이트이고, 둘째 줄부터는 이름이 `docs` 인 하위 폴더를 목록 보기에서 펼쳐 둔 `dscl` 레코드입니다.

```
파일 맨 앞 (예시)
00 00 00 01  42 75 64 31
             B  u  d  1

레코드 하나 (예시)
00 00 00 04                    파일 이름 길이 = 4글자
00 64 00 6F 00 63 00 73        "docs" (빅엔디언 UTF-16, 한 글자에 2바이트)
64 73 63 6C                    구조 ID "dscl"
62 6F 6F 6C                    자료형 "bool"
01                             값 = 참 (하위 폴더를 펼쳐 둠)
```

실제 파일에서 레코드를 찾을 때는 구조 ID 네 글자(예: `cmmt` = `63 6D 6D 74`, `Iloc` = `49 6C 6F 63`)를 헥스 검색하고, 그 앞쪽으로 거슬러 올라가 이름 길이와 UTF-16 이름을 읽습니다. 이름이 두 바이트씩 `00` 과 번갈아 나오는 모양이라서, 영문 이름은 헥스 창 오른쪽 글자 칸에서도 점과 글자가 번갈아 보입니다.

### 공개 도구로 한 번

파이썬 패키지 `ds_store` 는 B-트리를 따라가 레코드를 파일 이름·구조 ID·자료형·값으로 풀어 주고, mac_apt 도 이 패키지를 가져다 씁니다 [2].

```python
from ds_store import DSStore

with DSStore.open(".DS_Store", "r") as d:
    for entry in d:
        print(entry.filename, entry.code, entry.type, entry.value)
```

결과에서 폴더 목록에 없는 이름, `cmmt` 레코드, `modD`·`moDD` 레코드를 따로 골라 보고, 시각 레코드는 원래 8바이트를 두 방법으로 모두 풀어 봅니다.

## 실습

NIST CFReDS 같은 공개 시험 데이터 가운데 맥 이미지나 맥에서 쓴 외장 볼륨 이미지를 골라 아래 질문을 풀어 봅니다.

1. 사용자 홈 아래에서 `.DS_Store` 가 있는 폴더는 몇 개인가요? 없는 폴더와 비교하면 어떤 차이가 있나요?
2. 한 `.DS_Store` 의 맨 앞 8바이트가 `00 00 00 01 42 75 64 31` 인지 확인하고, B-트리 헤더에서 전체 레코드 수를 읽어 도구 결과의 레코드 수와 같은지 비교해 보세요.
3. 레코드에 붙은 파일 이름 가운데 지금 폴더에 없는 이름이 있나요? 있다면 FSEvents 에서 같은 이름을 찾아보세요.
4. `vstl` 값이 `icnv`, `clmv`, `Nlsv`, `Flwv` 가운데 무엇인지 폴더마다 모아 보세요.
5. `modD` 나 `moDD` 가 있다면 형식 문서 방식과 mac_apt 방식으로 각각 풀고, 폴더의 파일 시스템 수정 시각과 가까운 쪽이 어느 것인지 보세요.
