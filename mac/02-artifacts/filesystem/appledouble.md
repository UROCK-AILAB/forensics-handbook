# 애플더블 파일 (AppleDouble)

맥에서 확장 속성을 저장하지 못하는 볼륨으로 파일을 복사하면, 원래 파일 옆에 이름 앞에 `._` 를 붙인 애플더블 (AppleDouble) 파일이 생기고 그 안에 Finder 정보·리소스 포크·확장 속성이 들어갑니다. Finder로 만든 zip 파일에도 같은 형식의 데이터가 `__MACOSX` 폴더 아래에 들어갑니다. 그래서 USB 메모리나 zip 파일 하나만 확보해도 파일이 맥에서 왔다는 점, 복사한 시각, 파일에 붙어 있던 격리 속성과 다운로드 출처를 확인할 수 있습니다.

## 무엇을 기록하나 · 왜 생기나

맥 파일에는 파일 내용 말고도 Finder 정보, 리소스 포크, 확장 속성 (extended attribute, xattr) 같은 정보가 붙습니다. FAT32·exFAT처럼 이런 정보를 받을 자리가 없는 파일 시스템에서는 커널이 대신 애플더블 파일을 만들어 그 안에 정보를 적습니다 [2][5]. 파일 이름은 원래 이름 앞에 `._` 를 붙인 것이고, 원래 파일과 같은 폴더에 생깁니다 [4]. 볼륨 최상위 폴더 자체에 붙은 속성은 `._.` 라는 파일에 들어갑니다 [4]. 예를 들어 `me.jpg` 를 exFAT 볼륨으로 복사하면 숨김 파일 `._me.jpg` 가 함께 생깁니다 [2].

애플더블은 맥 파일을 다른 시스템으로 보내려고 만든 형식이고, 파일 내용(데이터 포크)은 원래 이름의 파일에, 나머지 정보는 헤더 파일 (AppleDouble Header file)에 따로 담습니다 [3]. 헤더 파일은 애플싱글 (AppleSingle) 형식과 같은 구조에서 데이터 포크 엔트리만 뺀 것입니다 [3].

zip 파일에서도 같은 일이 일어납니다. Finder에서 파일을 오른쪽 클릭해 "압축"으로 zip을 만들면, macOS는 파일의 확장 속성을 zip 안 `__MACOSX` 폴더에 함께 넣습니다 [1]. 내려받은 파일이라면 다운로드 출처가 담긴 속성도 들어가서, 받은 사람에게 원래 파일의 출처 URL이 넘어갈 수 있습니다 [1]. copyfile 라이브러리는 애플더블을 만들 때 격리 정보가 있으면 늘 함께 넣습니다 [5].

## 위치와 버전별 차이

| 생기는 곳 | 파일 이름 | 근거 |
|---|---|---|
| 확장 속성을 저장하지 못하는 볼륨(FAT32·exFAT 등)의 원래 파일 옆 | `._` + 원래 파일 이름 | [2][4][5] |
| 같은 볼륨의 최상위 폴더 | `._.` | [4] |
| Finder로 만든 zip 파일 안 | `__MACOSX` 폴더 아래 항목 | [1] |

형식은 1994년 RFC 1740 부록에 정의된 버전 2(`0x00020000`)이고 [3], 현재 xnu와 copyfile 소스도 같은 매직 번호와 버전을 씁니다 [4][5]. 아래 시각 해석은 HFS+ 볼륨에서 FAT32·exFAT으로 복사한 2016년 시험 결과라서 [2], APFS 볼륨에서 복사할 때도 시각이 같게 움직이는지는 실제 데이터로 확인합니다.

네트워크 공유도 서버가 확장 속성을 받지 못하면 같은 방식으로 `._` 파일이 생길 가능성이 있습니다. 공유 폴더에서 `._` 파일이 보이면 그 공유의 파일 시스템부터 확인합니다.

## 구조

모든 정수는 빅 엔디언입니다 [3][4]. 오프셋은 xnu와 copyfile의 구조체 정의를 따릅니다 [4][5].

### 애플더블 헤더

| 오프셋 | 크기 | 필드 | 값·뜻 |
|---|---|---|---|
| 0 | 4 | 매직 번호 | `00 05 16 07` (애플더블). 애플싱글은 `00 05 16 00` [3] |
| 4 | 4 | 버전 | `00 02 00 00` [3] |
| 8 | 16 | 채움 (filler) | RFC에서는 모두 0 [3]. copyfile이 만들면 `Mac OS X` 뒤에 공백 8개 [5] |
| 24 | 2 | 엔트리 개수 | 맥이 만든 파일은 2 [4][5] |
| 26 | 12 | 엔트리 0 | ID 9 (Finder 정보), 오프셋, 길이 |
| 38 | 12 | 엔트리 1 | ID 2 (리소스 포크), 오프셋, 길이 |
| 50 | 32 | Finder 정보 | 고정 크기 32바이트 [4] |
| 82 | 2 | 채움 | 뒤 구조를 맞추려는 2바이트 [4] |

엔트리 하나는 ID·오프셋·길이 세 필드(각 4바이트)이고, 오프셋은 파일 처음부터 센 값입니다 [3]. RFC가 정한 엔트리 ID에는 1 데이터 포크, 2 리소스 포크, 3 원래 이름, 8 파일 날짜, 9 Finder 정보 등이 있습니다 [3]. 맥이 만든 파일은 Finder 정보 엔트리를 첫째에, 리소스 포크 엔트리를 마지막에 둡니다 [4].

### 확장 속성 영역

확장 속성은 따로 엔트리를 두지 않고 Finder 정보 엔트리 안, 32바이트 Finder 정보 뒤에 이어서 들어갑니다 [4]. 그래서 Finder 정보 엔트리의 길이는 32보다 크고, 속성 헤더·속성 엔트리·속성 데이터를 모두 포함합니다 [4]. copyfile은 이 길이를 리소스 포크 시작 오프셋에서 50을 뺀 값으로 적습니다 [5].

| 오프셋 | 크기 | 필드 | 값·뜻 |
|---|---|---|---|
| 84 | 4 | 속성 헤더 매직 | `41 54 54 52` (`ATTR`) [4] |
| 88 | 4 | `debug_tag` | 정의상 원래 파일의 파일 ID [4]. copyfile은 0을 씀 [5] |
| 92 | 4 | `total_size` | 속성 헤더·엔트리·데이터가 끝나는 파일 오프셋 [4] |
| 96 | 4 | `data_start` | 속성 데이터 영역의 시작 오프셋 [4] |
| 100 | 4 | `data_length` | 속성 데이터 영역의 길이 [4] |
| 104 | 12 | 예약 | |
| 116 | 2 | `flags` | |
| 118 | 2 | `num_attrs` | 속성 개수 [4] |
| 120 | 가변 | 속성 엔트리 | 아래 표를 `num_attrs` 번 되풀이 |

| 엔트리 안 오프셋 | 크기 | 필드 | 뜻 |
|---|---|---|---|
| 0 | 4 | `offset` | 이 속성 값이 있는 파일 오프셋 |
| 4 | 4 | `length` | 속성 값 길이 |
| 8 | 2 | `flags` | |
| 10 | 1 | `namelen` | 이름 길이(끝의 NULL 포함) |
| 11 | `namelen` | `name` | NULL로 끝나는 UTF-8 속성 이름 |

엔트리 하나의 길이는 11 + `namelen` 을 4의 배수로 올린 값입니다 [4][5]. 속성 헤더와 엔트리는 파일 앞 64KB 안에 들어가야 하고, 속성 값은 그 뒤로 넘어갈 수 있습니다 [4].

속성 값은 쓴 앱이 정한 형식 그대로 들어갑니다. `com.apple.quarantine` 은 세미콜론으로 나눈 문자열이고, `com.apple.metadata:kMDItemWhereFroms` 는 `bplist` 로 시작하는 이진 plist입니다 [1]. 두 값의 해석은 [격리 확장 속성](quarantine/quarantine-xattr.md)과 [다운로드 출처 속성 (kMDItemWhereFroms)](where-froms.md)에 있습니다.

리소스 포크는 확장 속성 영역 뒤, 파일 끝에 옵니다 [4]. 커널이 만든 애플더블 파일은 호환성 때문에 "리소스 없음"을 뜻하는 빈 리소스 포크 헤더만 담는 경우가 있습니다 [5].

## 증거로서 의미

**증명하는 것.** `._` 파일이 있으면 같은 이름의 파일이 맥에서 확장 속성이나 Finder 정보를 달고 그 볼륨에 쓰였다는 뜻입니다 [2][4]. 복사 의도 (intent)가 COPY이면 격리 속성과 `com.apple.metadata:kMDItemWhereFroms` 속성이 모두 복사 대상이라서 [6], `._` 파일 안에 격리 속성과 다운로드 출처가 남아 있을 수 있습니다. 이 속성을 해석하면 원래 파일을 어느 앱으로 언제 받았는지, 어느 URL에서 받았는지를 맥 본체 없이 USB 메모리나 zip 파일만으로 확인할 수 있습니다. zip 파일 안의 `__MACOSX` 는 맥의 Finder 압축 기능이 만드는 폴더이고, 같은 형식으로 원래 파일의 속성을 담습니다 [1].

**증명하지 못하는 것.** `._` 파일의 생성 시각은 그 파일이 볼륨에 처음 쓰인 시각이라서, 누가 복사했는지나 어느 맥에서 복사했는지는 알려 주지 않습니다. 원래 파일과는 이름으로만 이어지므로, `._` 파일이 있다고 해서 원래 파일이 지금도 있다거나 내용이 복사 당시와 같다고 볼 수 없습니다 [4]. 반대로 `._` 파일이 없다고 맥에서 복사하지 않았다고 보지 않습니다. 원래 파일에 저장할 속성이 없었을 수도 있고, 다른 시스템에서 `._` 파일만 지웠을 수도 있습니다.

보고서에는 "이 USB 볼륨에 `._report.pdf` 가 있고, 생성 시각은 이 시각이며, 그 안의 격리 속성에는 이 앱 이름과 시각이 적혀 있다"처럼 파일과 속성에 적힌 값만 옮깁니다.

## 시각 해석

HFS+ 볼륨에서 FAT32·exFAT 볼륨으로 파일을 복사하면 원래 파일의 생성·수정 시각은 원본 값을 물려받고, 접근 시각만 복사한 때로 바뀝니다 [2]. FAT32의 접근 시각은 날짜만 남습니다 [2][7]. 반면 함께 생긴 `._` 파일은 생성·수정·접근 시각이 모두 복사한 시각입니다 [2]. 그래서 원래 파일의 시각이 편집이나 열람으로 바뀐 뒤에도 `._` 파일의 생성 시각으로 복사한 시각을 확인할 수 있습니다 [2]. 이 결과는 한 사람이 2016년에 시험한 것이고, 시험한 사람도 결과가 일정하지 않은 경우가 있다고 밝혔습니다 [2].

FAT32·exFAT 볼륨에서 파일을 열거나 Finder에서 정보 가져오기를 하면 원래 파일과 `._` 파일의 접근 시각이 함께 바뀝니다 [2]. 복사 시각은 접근 시각이 아니라 생성 시각으로 읽습니다.

시각의 기준은 볼륨 형식에 따라 다릅니다. FAT은 시각을 컴퓨터의 현지 시각으로 적고 [7], exFAT은 현지 시각과 함께 UTC와의 차이를 15분 단위로 적는 `CreateUtcOffset`·`LastModifiedUtcOffset`·`LastAccessedUtcOffset` 필드가 있습니다 [8]. 이 필드의 `OffsetValid` 비트가 0이면 적힌 차이 값이 유효하지 않다는 뜻입니다 [8]. FAT32 볼륨의 `._` 파일 시각을 UTC로 바꿀 때는 복사한 맥의 시간대를 따로 확인해야 합니다([시간대와 시계 설정](../system-account/time-zone.md)).

`._` 파일 안의 격리 속성에 적힌 시각은 파일을 받은 때의 시각이고 복사 시각과 다릅니다. 이 시각은 16진수 유닉스 시각이라 UTC 기준입니다([격리 확장 속성](quarantine/quarantine-xattr.md)).

## 함정과 한계

**`._` 파일은 원래 파일의 속성 저장소입니다.** 커널이 원래 파일의 속성 저장소로 쓰는 파일이라 맥에 볼륨을 붙이면 `xattr` 명령이 `._` 파일을 읽어 원래 파일의 속성으로 보여 줍니다 [4]. 이미지에서 파일 목록을 뽑을 때는 `._` 파일을 따로 골라내 원래 파일과 짝을 짓습니다.

**짝이 없는 `._` 파일도 있습니다.** 두 파일은 이름으로만 이어지므로 [4], 다른 운영체제에서 원래 파일만 지우거나 이름을 바꾸면 `._` 파일만 남을 수 있습니다. 이때 `._` 파일 이름과 그 안의 속성이 지워진 파일의 이름과 출처를 알려 주는 단서가 됩니다.

**도구가 계산하는 엔트리 길이를 확인합니다.** Velociraptor 아티팩트는 속성 엔트리 길이를 `value + value - int(int=value / 4) * 4` 로 계산하는데 [1], 이 값은 11 + `namelen` 이 홀수이면 xnu가 정한 "4의 배수로 올림"과 다릅니다 [4]. 속성이 둘 이상인 파일은 둘째 엔트리부터 어긋날 수 있으므로 결과를 헥스로 한 번 맞춰 봅니다.

**격리 속성의 출처를 복사한 볼륨의 출처로 읽지 않습니다.** `._` 파일의 격리 속성은 원래 맥에서 파일을 받았을 때의 기록이고, 그 볼륨에 복사한 기록이 아닙니다.

## 직접 분석해 보기

### 헥스로 한 번

아래 헥스는 xnu와 copyfile 구조체 정의대로 만든 값입니다(만든 예시). `com.apple.quarantine` 속성 하나(값 `0081;65920080;Chrome;`, 21바이트)만 든 `._` 파일입니다.

```text
0000  00 05 16 07 00 02 00 00 4D 61 63 20 4F 53 20 58  |........Mac OS X|
0010  20 20 20 20 20 20 20 20 00 02 00 00 00 09 00 00  |        ........|
0020  00 32 00 00 00 7B 00 00 00 02 00 00 00 AD 00 00  |.2...{..........|
0030  00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00  |................|
0040  00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00  |................|
0050  00 00 00 00 41 54 54 52 00 00 00 00 00 00 00 AD  |....ATTR........|
0060  00 00 00 98 00 00 00 15 00 00 00 00 00 00 00 00  |................|
0070  00 00 00 00 00 00 00 01 00 00 00 98 00 00 00 15  |................|
0080  00 00 15 63 6F 6D 2E 61 70 70 6C 65 2E 71 75 61  |...com.apple.qua|
0090  72 61 6E 74 69 6E 65 00 30 30 38 31 3B 36 35 39  |rantine.0081;659|
00A0  32 30 30 38 30 3B 43 68 72 6F 6D 65 3B           |20080;Chrome;|
```

1. 처음 4바이트 `00 05 16 07` 로 애플더블임을 확인합니다. 0x18의 `00 02` 가 엔트리 개수 2입니다.
2. 0x1A부터 엔트리 0은 ID 9, 오프셋 0x32(50), 길이 0x7B(123)이고, 엔트리 1은 ID 2, 오프셋 0xAD(173), 길이 0입니다. Finder 정보 엔트리 길이 123은 173에서 50을 뺀 값입니다.
3. 0x54(84)에서 `ATTR` 을 확인하고, 0x5C의 `total_size` 0xAD, 0x60의 `data_start` 0x98, 0x64의 `data_length` 0x15, 0x76의 `num_attrs` 1을 읽습니다.
4. 0x78(120)의 첫 엔트리에서 값 오프셋 0x98, 길이 0x15, 이름 길이 0x15(21)와 이름 `com.apple.quarantine` 을 읽습니다. 엔트리 길이는 11 + 21 = 32이고 이미 4의 배수입니다.
5. 0x98부터 21바이트가 속성 값입니다. 2번 필드 `65920080` 은 2024-01-01 00:00:00 UTC입니다(만든 예시).

### 공개 도구로 한 번

1. zip 파일은 풀지 말고 `unzip -l` 처럼 목록만 보는 명령으로 `__MACOSX` 아래 항목이 있는지 먼저 봅니다.
2. Velociraptor의 `MacOS.Forensics.AppleDoubleZip` 아티팩트를 돌리면 `__MACOSX` 아래 항목마다 속성 이름과 값을 뽑고, `bplist` 로 시작하는 값은 plist로 풀어 줍니다 [1]. 기본 검색 경로는 `/Users/*/Downloads/*.zip` 이고, 맥에서 만든 zip은 다른 시스템으로 옮겨 가므로 다른 운영체제에서 확보한 zip에도 쓸 수 있습니다 [1].
3. USB 볼륨의 `._` 파일도 형식이 같아서, 이 아티팩트가 내보내는 `ParseAppleDouble` 함수로 읽을 수 있습니다 [1][4]. 풀린 이진 plist는 [속성 목록 파일 (Property List)](../../01-foundations/data-formats/plist/index.md)의 방법으로 읽습니다.
4. 결과에서 속성이 둘 이상인 파일 하나를 골라 위 헥스 절차로 엔트리 위치를 맞춰 봅니다.

`._` 파일 생성 시각이 USB 볼륨이 맥에 붙어 있던 시간대 안에 드는지 보고, 같은 이름이 장치 쪽 FSEvents에 있는지 맞춰 봅니다. 유출 조사에서 이 흔적을 쓰는 순서는 [USB 저장 장치로 (USB)](../../04-scenarios/exfiltration/data-exfiltration/usb.md)에, 파일 출처를 따라가는 순서는 [이 파일은 어디서 왔나 (File Origin)](../../04-scenarios/activity/file-origin.md)에 있습니다.

## 실습

NIST CFReDS 같은 공개 자료 가운데 맥과 USB 메모리가 함께 들어 있는 이미지를 골라 아래 질문을 풀어 봅니다.

1. USB 볼륨에서 `._` 파일을 모두 찾아 원래 파일과 짝을 지을 때, 짝이 없는 `._` 파일이 있나요?
2. `._` 파일의 생성 시각과 원래 파일의 생성 시각이 다른 파일을 골라, 어느 쪽이 복사한 시각인지 설명할 수 있나요?
3. `._` 파일에 격리 속성이 있다면 그 UUID가 맥 쪽 격리 이벤트 DB에도 있나요?
4. FAT32 볼륨이라면 `._` 파일의 생성 시각을 UTC로 바꾸려면 무엇을 더 확인해야 하나요?
