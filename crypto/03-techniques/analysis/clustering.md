# 주소 묶기와 그 한계 (Address Clustering)

주소 묶기는 여러 블록체인 주소를 "같은 주체가 쓰는 주소" 로 한데 묶는 추정 작업입니다. 따라가야 할 주소 수는 크게 줄지만 묶음이 실제로 한 사람의 것인지는 블록체인만으로 확인할 수 없습니다. 실제 소유자를 기록한 시뮬레이션에서 널리 쓰는 규칙 조합의 평균 오류율은 41~65% 였습니다[6][7]. 이 페이지는 비트코인과 이더리움에서 쓰는 묶기 규칙, 결과를 조사에 쓰는 순서, 그리고 보고서에 어디까지 쓸 수 있는지를 다룹니다.

## 언제 쓰나

[비트코인 거래 따라가기](bitcoin-tracing.md)나 [이더리움 거래 따라가기](ethereum-tracing.md)에서 흐름이 여러 주소로 흩어져 하나씩 따라가기 어려울 때, 또는 상용 분석 도구가 "이 주소는 ○○ 묶음에 속한다" 고 표시한 결과를 해석해야 할 때 씁니다. 어느 거래소의 입금 주소인지, 한 사람이 쓴 주소가 몇 개인지 추정할 때도 씁니다.

묶기 결과는 수사 방향을 잡는 보조 자료입니다. 암호화폐 포렌식에서 묶기 결과는 단독 증거로 쓰지 않고, 거래 행동과 체인 밖 정보로 보강합니다[7]. 기기에서 나온 지갑 데이터나 거래소 회신처럼 소유를 직접 보여 주는 자료가 있으면 그것이 먼저입니다.

## 절차

### 1. 기기 자료로 확정된 주소부터 모읍니다

묶기 규칙을 쓰기 전에, 추정이 아닌 근거로 한 지갑에 속하는 주소를 먼저 정리합니다. 확장 공개 키 (extended public key) 하나로 그 아래의 강화되지 않은 (non-hardened) 자식 공개 키를 모두 다시 계산할 수 있어서[13], 기기에서 찾은 확장 공개 키에서 계산한 주소는 규칙으로 추정한 주소가 아니라 그 지갑 계정의 주소입니다. 계산 범위와 주소 형식을 빠뜨리면 주소를 놓치므로, 계산 방법은 [비트코인 거래 따라가기](bitcoin-tracing.md)의 확장 공개 키 단계와 [복구 문구와 파생 경로](../../01-foundations/wallets/seed-derivation.md)를 따릅니다. 공개 조회 도구가 확장 공개 키에서 세그윗 주소를 계산하지 못해 거래를 빠뜨리는 경우도 있습니다[12].

이 목록은 뒤에서 규칙으로 만든 묶음을 검산하는 기준으로도 씁니다.

### 2. 비트코인에서 쓸 규칙을 고릅니다

비트코인 묶기 규칙은 크게 두 종류입니다. 한 트랜잭션의 입력 주소들을 묶는 공통 입력 소유 (common-input-ownership) 규칙과, 출력 가운데 거스름돈 (change) 주소를 골라 입력과 묶는 거스름돈 규칙입니다. 공통 입력 소유 규칙은 비트코인 백서에서 처음 나왔고, 거스름돈 규칙은 알려진 변형만 20가지가 넘습니다[1].

| 규칙 | 조건 | 묶는 대상 | 흔들리는 경우 |
|---|---|---|---|
| 공통 입력 소유 | 입력이 2개 이상 | 모든 입력 주소 | 코인조인 (CoinJoin)처럼 여러 사람이 입력을 모은 트랜잭션[1][2] |
| 코인조인을 뺀 공통 입력 소유 | 입력이 2개 이상이고, 코인조인 판별 규칙에 걸리지 않음 | 모든 입력 주소 | 판별 규칙이 못 잡은 공동 트랜잭션[1] |
| 거스름돈 기본형 | 출력 주소가 2개이고, 그중 처음 쓰이는 주소가 정확히 하나 | 그 새 주소를 거스름돈으로 봄 | 도박 사이트·채굴 풀처럼 한 트랜잭션으로 여러 사람에게 지급하는 경우[2] |
| 거스름돈 (Meiklejohn 정교화) | 코인베이스가 아니고, 처음 나타나는 출력 주소가 하나뿐이며, 입력 주소가 출력에 다시 나오지 않음 | 그 새 주소를 거스름돈으로 봄 | 지갑이 거스름돈 주소를 여러 개 만들거나 일부러 재사용한 경우[2] |
| 주소 재사용 | 전에 쓰인 출력 주소는 거스름돈보다 받는 사람 주소일 가능성이 높음 | 그 출력을 거스름돈 후보에서 뺌 | 지갑이 일부러 주소를 재사용하는 경우[2] |
| 시간 근접 | 시각이 가까운 트랜잭션은 관련 있음 | 트랜잭션 사이를 이음 | 믹서가 일부러 시간 간격을 둔 경우[2] |
| 입금 주소 모으기 | 입력 a 개 이상(연구 설정 a=25), 출력 1개 | 모든 입력 주소를 한 사용자(서비스)로 봄 | 공통 입력 소유 규칙의 특수한 경우라 한계도 같음[1] |

공통 입력 소유 규칙은 여러 사용자가 한 트랜잭션에 참여하는 기능이 일반 지갑에 없다는 가정에 기댑니다[2]. 입금 주소 모으기 트랜잭션과 일괄 지급 트랜잭션의 모양은 [거래소와 가상자산사업자](../../01-foundations/ecosystem/exchanges.md)에서, 코인조인과 믹서의 모양은 [믹서와 추적을 어렵게 하는 방법](../../01-foundations/ecosystem/mixers.md)에서 다룹니다.

거스름돈 규칙은 도구마다 이름과 조건이 다릅니다. BlockSci 가 제공하는 거스름돈 규칙은 아래와 같고, 규칙끼리 결과가 서로 어긋날 수 있습니다[3].

| BlockSci 규칙 | 거스름돈 후보로 보는 출력 |
|---|---|
| `address_reuse` | 입력 주소가 출력에 다시 나오면 그 출력 |
| `address_type` | 입력이 모두 한 주소 형식이면 같은 형식의 출력 |
| `optimal_change` | 어느 입력보다도 작은 출력 (입력이 1개면 모든 출력이 해당될 수 있음) |
| `power_of_ten_value` | 금액이 10의 거듭제곱 배수가 아닌 출력 |
| `client_change_address_behavior` | 그 주소에 처음 값을 보내는 출력 |
| `locktime` | 이미 쓰였고, 그 트랜잭션과 locktime 동작이 맞는 출력 (Bitcoin Core 는 수수료 가로채기(fee sniping)를 막으려고 locktime 을 현재 블록 높이로 둠). 아직 안 쓰인 출력도 후보로 돌려줌 |
| `peeling_chain` | 필링 체인을 이어 가는 출력 |

`locktime` 과 `peeling_chain` 은 출력이 나중에 쓰였는지에 따라 결과가 바뀌는 동적 규칙이고, 나머지는 트랜잭션 하나만 보고 판단하는 정적 규칙입니다[3]. 많은 규칙이 후보를 여러 개 내므로 BlockSci 는 후보가 하나일 때만 결과를 주는 `.unique_change` 를 두고, 규칙 하나를 다듬지 않고 그대로 묶기에 쓰지 말라고 권합니다[3].

주소 형식이 같은지를 보는 조건은 새 규칙에도 쓰입니다. 2025년 연구의 새 규칙은 출력 6개 이하 트랜잭션 가운데 코인베이스가 아니고, 입력 주소가 출력에 다시 나오지 않으며, 입력 주소 형식이 모두 같고, 출력이 모두 새 주소이고, 입력과 같은 형식인 출력이 하나뿐일 때 그 출력을 일회성 거스름돈으로 봅니다[7].

### 3. 이더리움에서 쓸 규칙을 고릅니다

이더리움은 계정 모델이라 한 트랜잭션에 보내는 계정과 받는 계정이 하나씩이고, 비트코인의 다중 입력·거스름돈 규칙을 그대로 쓸 수 없습니다[10]. 대신 아래 규칙을 씁니다[10].

**입금 주소 재사용.** 거래소는 고객마다 입금 주소를 만들고, 받은 금액을 거래소 본 주소로 옮깁니다[10]. 입금 주소는 고객마다 만들어서, 같은 입금 주소로 보낸 여러 주소는 같은 사람의 것일 가능성이 높습니다[10]. 입금 주소를 판별할 때는 받은 금액과 옮긴 금액의 차이 한도(amax)와 받은 뒤 옮기기까지의 블록 수 한도(tmax)를 정합니다. 2019-09-07 의 블록 8,500,000 까지 자료로 추정한 값은 금액 차이 95백분위 0.0083 ETH, 시간 95백분위 3,185블록(약 13시간)이었고, 연구는 amax 0.01 ETH, tmax 3,200블록을 썼습니다[10]. 토큰은 수수료를 토큰으로 낼 수 없어서 금액 차이가 보통 0 입니다[10]. 거래소끼리 오간 돈이 섞이지 않도록 알려진 거래소 주소와 블록을 채굴한 주소는 빼고, 거래소 주소 하나로만 옮기는 입금 주소만 썼습니다[10]. 입금 주소 판별을 거래소 자료와 맞추는 방법은 [거래소 자료 분석](exchange-analysis.md)에서 다룹니다.

**에어드롭 여러 번 참여.** 한 사람이 여러 주소로 같은 에어드롭에 참여하면 받은 토큰을 한 주소로 모으는 경우가 많습니다[10]. 그래서 같은 수량을 나눠 준 에어드롭에서 받은 수량 그대로 한 주소로 옮긴 수령 주소들을 묶고, 모은 주소가 거래소나 탈중앙 거래소(DEX) 계약이면 뺍니다[10].

**자기 승인.** ERC-20 토큰의 승인(Approval)이 활성 외부 소유 계정(EOA) 사이에 있으면, 자기 주소끼리 승인했다고 보고 소유자와 지출자를 묶습니다[10]. 승인을 받은 지출자 가운데 거래소 주소는 뺍니다[10]. 한 지출자를 1만 개 넘는 소유자가 승인한 경우처럼 한 사람으로 볼 수 없는 경우가 있어, 연구는 소유자·지출자를 각각 10개 이하로 제한해 7,107개 주소에서 4,599개 주체를 얻었습니다[10].

입금 주소 규칙에서 주소가 1,000개 넘게 묶인 주체 4개는 실제로 있을 가능성이 낮다고 보고 버렸습니다[10]. 세 규칙을 합치면 블록 8,500,000 까지 활성 외부 소유 계정의 17.9%(9,562,153개)가 묶이고, 입금 주소 규칙이 가장 많은 주소를 묶습니다[10].

### 4. 묶음을 만들고 합쳐지는 과정을 기록합니다

묶기 도구는 보통 유니온-파인드 (Union-Find) 구조로 주소를 합칩니다. GraphSense 의 묶기 모듈은 트랜잭션마다 입력 주소 ID 목록을 받아 같은 트랜잭션의 입력을 한 묶음으로 합칩니다[5]. 합치기는 이어져서, 아래처럼 두 트랜잭션이 주소 하나를 함께 쓰면 서로 만난 적 없는 주소까지 한 묶음이 됩니다[5].

```text
(만든 예시)
트랜잭션 1 의 입력: 주소 A, 주소 B   → {A, B}
트랜잭션 2 의 입력: 주소 B, 주소 C   → {A, B, C}
결과: A 와 C 는 같은 트랜잭션에 함께 나온 적이 없지만 같은 묶음
```

이 성질 때문에 잘못 묶인 트랜잭션 한 건이 큰 묶음 두 개를 하나로 합칠 수 있습니다. BlockSci 는 묶음 붕괴 (cluster collapse) 위험 때문에 거스름돈 주소를 기본으로 묶지 않습니다[4]. BlockSci 의 기본 묶기는 다중 입력 규칙을 쓰면서 코인조인 트랜잭션을 건너뛰려 합니다[4]. GraphSense 의 묶기 모듈은 주소를 해석하고 거르는 일을 상위 코드에 맡기므로[5], 코인조인을 뺐는지는 이 모듈을 부르는 상위 코드의 설정에서 확인합니다.

조사에서는 묶음이 커진 지점마다 어느 트랜잭션이 어느 규칙으로 두 묶음을 합쳤는지 남깁니다. 나중에 한 건이 잘못으로 드러나면 그 합치기만 되돌릴 수 있습니다.

### 5. 묶음을 검산합니다

만든 묶음을 1단계에서 확정한 주소 목록과 비교합니다. 기기에서 확인한 주소가 서로 다른 묶음으로 갈라져 있으면 규칙이 놓친 연결이 있고, 기기와 관계없는 거래소 주소나 큰 서비스 주소가 섞여 있으면 잘못 합쳐진 곳이 있습니다. 거래소 본 주소는 여러 고객의 돈이 모이는 곳이라[10] 사용자 묶음에 들어가면 안 됩니다.

지갑 지문 (wallet fingerprint)도 검산에 쓸 수 있습니다. 지문으로 공통 입력 묶음에 관계없는 주소가 섞였는지 확인하거나 거스름돈 판별을 도울 수 있고, 한 서비스의 지문은 약 40개 트랜잭션으로도 만들 수 있습니다[9]. 다만 지문과 맞는 트랜잭션이 곧 그 서비스의 것은 아니어서 결과는 확률로만 읽습니다[9]. 지문의 구성은 [믹서와 추적을 어렵게 하는 방법](../../01-foundations/ecosystem/mixers.md)에서 다룹니다.

### 6. 묶음에 붙은 이름을 따로 확인합니다

묶음에 거래소 이름 같은 라벨을 붙이는 기능은 외부에서 받은 주소 태그를 쓰는 방식입니다[4]. 공개된 라벨 출처는 빠진 것이 많거나, 주체 정보가 없거나, 소유자가 확인하지 않은 경우가 많습니다[7]. 라벨은 출처와 조회 날짜를 적어 옮기고, 거래소 회신처럼 소유를 확인한 자료가 나오면 그것으로 바꿉니다.

## 도구

- **BlockSci:** 비트코인과 여러 다른 체인에서 다중 입력 묶기와 거스름돈 규칙을 제공하고, 거스름돈 규칙을 합집합·교집합·차집합으로 조합할 수 있습니다[3][4]. 2020년 11월에 개발과 지원을 멈춰서, 암호화폐가 바뀌면 호환되지 않을 수 있습니다[4]. 묶기 모듈은 규칙 기반 묶기를 시험하는 단순한 구현이라 결과가 실제로 맞다고 가정하면 안 됩니다[4].
- **GraphSense (`graphsense-clustering`):** Rust 로 만든 병렬 유니온-파인드로 비트코인 등 UTXO 체인에 다중 입력 규칙을 적용합니다[5].
- **Neo4j:** 믹서 거래 연구에서 블록체인 데이터를 그래프 데이터베이스에 넣고 경로를 질의하는 데 썼습니다[2].
- **확장 공개 키 조회 도구:** 규칙이 아니라 키 파생으로 주소를 모읍니다. 도구마다 계산하는 주소 형식과 범위가 달라 결과가 빠질 수 있습니다[12].

상용 분석 도구의 묶음과 위험 점수도 같은 규칙을 바탕으로 하지만 어떤 규칙과 매개변수를 썼는지 공개하지 않는 경우가 많습니다. 결과를 옮길 때는 도구 이름·버전·조회 날짜를 적습니다.

## 함정과 한계

**줄어든 비율을 정확도로 읽는 경우.** 블록 700,000 까지 874.6M 개 스크립트에 공통 입력 소유 규칙을 쓰면 따져 볼 대상 수가 절반으로 줄고, 거스름돈 규칙은 약 15%, 둥근 금액·입력 강제 합치기·입금 주소 규칙은 각각 5~10% 줄입니다[1]. 코인조인을 뺀 공통 입력 소유·거스름돈·둥근 금액·입력 강제 합치기 규칙 네 가지를 함께 쓰면 약 70% 줄어 약 2억 5천만 개 묶음이 됩니다[1]. 이 숫자는 얼마나 줄었는지일 뿐 얼마나 맞는지가 아닙니다. 여러 유형의 사용자를 대표하는 정답 데이터가 없어서 규칙 선택은 주로 확신에 기댑니다[1].

**오류율이 시뮬레이션마다 다른 경우.** 정답이 없는 문제를 피하려고 소유자를 기록하는 시뮬레이터로 오류율을 잰 연구가 있습니다. 실제 묶음 R 과 규칙으로 만든 묶음 H 에 대해 정확도를 `|H∩R| / |R|`, 오류율을 1−정확도로 두고 규칙으로 만든 묶음마다 구해 평균합니다[6]. 두 연구의 결과가 다릅니다.

| 연구 | 시뮬레이션 기준 | 일회성 거스름돈 | 다중 입력 | 다중 입력 + 일회성 거스름돈 |
|---|---|---|---|---|
| Gong 등 2022 | 첫 716,548블록의 분포, 기본 설정 | 90.3612% | 46.5040% | 41.2528% |
| Gong 등 2025 | 첫 823,786블록의 분포, 노드 50·100개와 트랜잭션 5천~2만 건의 6가지 설정 평균 | — | — | 64.6805% |

2025년 연구는 차이를 사용자 행동 변화로 설명합니다. 여러 곳에 지급하는 트랜잭션의 비율이 줄고 한 곳으로 옮기는 트랜잭션의 비율이 늘었습니다[7]. 같은 연구에서 다른 규칙(H1)을 더하면 4.8798% 나아졌고, 새 규칙을 더하면 H1 을 더한 결과보다 6.1274% 더 나아졌으며, 모두 합치면 기본보다 14.3249% 나아졌습니다[7]. 시뮬레이션은 실제 상황을 다 담지 못하고, 사용자 행동이 바뀌면 고정된 규칙은 효과가 떨어집니다[7]. 보고서에 오류율을 쓸 때는 어느 연구의 어떤 조건에서 나온 값인지 함께 씁니다.

**주소 재사용이 줄어드는 경우.** 2023년 주소 재사용률은 2014년 이후 가장 낮았고, 1~2월 9.23% 에서 BRC-20 이 활성화된 뒤 7.63% 로 더 떨어졌습니다[7]. 같은 기간 P2WPKH·P2TR 출력이 늘었습니다[7]. 재사용에 기대는 규칙은 최근 트랜잭션일수록 근거가 약해집니다.

**분석 시점까지의 정보로만 판단하는 경우.** "재사용되지 않은 주소" 같은 조건은 알고 있는 트랜잭션 범위 안에서만 판단됩니다. 분석 시점 뒤에 처음 재사용되는 주소는 그 시점에는 새 주소로 보입니다[1]. 같은 묶음도 언제 계산했는지에 따라 달라지므로 계산에 쓴 블록 높이를 기록합니다.

**필링 체인을 믹서로 단정하는 경우.** 자기 거스름돈으로 이어지는 필링 체인을 찾은 연구는 원래 13,025,575개였던 사슬 가운데 사슬 안 트랜잭션의 버전·주소 형식·locktime·sequence 범주·세그윗 여부가 같은 것만 남겨 5,598,367개로 줄였습니다[8]. 짧은 사슬에는 끝 다음이 모으기 트랜잭션인지, 간격이 10블록·1시간 이내인지 같은 조건을 더해 최종 624,573개로 좁혔습니다[8]. 그래도 모두 믹서가 만든 사슬이라고 확신할 수 없고, 일회성 거스름돈으로 이어진 사슬은 이 방법으로 찾지 못합니다[8]. 필링 체인을 따라가는 방법은 [비트코인 거래 따라가기](bitcoin-tracing.md)에서 다룹니다.

**이더리움 입금 주소 규칙이 속는 경우.** 누군가 돈을 받자마자 같은 금액을 알려진 거래소 주소로 보내면, 그 주소가 입금 주소로 판정되어 돈을 보낸 주소들의 묶음에 끼어듭니다[10]. 이 규칙은 한 단계 전달만 보고, 알려지지 않은 거래소 주소가 있으면 큰 묶음이 생길 수 있어 거래소 주소 목록이 필요합니다[10]. 정답 라벨이 없어 이더리움 묶기도 오류율을 재기가 매우 어렵습니다[10].

**기계 학습 판정의 근거 데이터.** 널리 쓰인 Elliptic 비트코인 데이터셋(2019)은 특징을 만든 방법이 완전히 공개되지 않아 다시 만들기 어렵습니다[11]. 일부 특징이 미래 시점의 주소 활동까지 담은 통계라 학습·시험 데이터 사이에 정보가 샙니다[11]. 이런 데이터로 학습한 모델의 성능은 부풀려졌을 수 있습니다[11]. "위험 주소" 판정을 옮길 때는 판정에 쓴 데이터가 공개됐는지부터 확인합니다.

## 결과를 어떻게 해석하나

**증명하는 것.** 한 비트코인 트랜잭션의 입력이 모두 유효하게 서명됐다는 것은 체인에서 확인되고, 각 입력을 잠근 키의 보유자가 서명에 참여했다는 뜻입니다. 하지만 코인조인처럼 여러 사람이 함께 서명할 수 있어서 같은 사람이라는 뜻은 아닙니다[1][2]. 기기에서 찾은 확장 공개 키에서 계산한 주소는 그 키 아래의 주소라는 것이 파생 규칙으로 확인됩니다[13][14].

**증명하지 못하는 것.** 규칙으로 만든 묶음이 한 사람이나 한 조직의 것이라는 것은 증명되지 않습니다. 실제 체인에는 정답 자료가 없어 오류율을 재기 어렵고[1][10], 시뮬레이션에서는 규칙과 조건에 따라 평균 오류율이 41~90% 로 나왔습니다[6][7]. 묶음에 붙은 거래소 이름 같은 라벨이 맞는지도 라벨 출처를 따로 확인해야 합니다[7]. 법정에서 과학적 증거를 받아들이는 기준 가운데 하나인 Daubert 기준은 알려진 오류율을 따지므로, 오류율을 제시하지 못하는 묶기 결과는 증거로서 약하다는 문제 제기가 있습니다[6][7].

**보고서 문장.** 묶음을 사실처럼 쓰지 않고, 어떤 규칙으로 어떤 트랜잭션에서 묶었는지를 씁니다. 예: "주소 bc1q…a1(만든 예시)과 bc1q…b2(만든 예시)는 TXID cc33…(만든 예시)의 입력으로 함께 쓰였다. 공통 입력 소유 규칙에 따르면 두 주소는 같은 주체의 것으로 추정되지만, 이 트랜잭션에 여러 사람이 참여했는지는 체인 자료만으로 알 수 없다. 이 기기의 지갑 파일에서 나온 확장 공개 키로 계산한 주소 목록에는 bc1q…a1 만 있다." 보고서 전체의 구성은 [암호화폐 포렌식 보고서](../reporting/forensic-report.md)에서 다룹니다.
