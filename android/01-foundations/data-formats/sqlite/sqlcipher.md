# 암호화된 SQLite (SQLCipher)

## 한 줄 요약

SQLCipher 는 Zetetic 이 만든, SQLite 에 암호화를 더한 라이브러리이고, 페이지마다 AES-256 CBC 로 암호화해서 키가 없으면 파일 전체가 무작위 데이터처럼 보입니다 [1]. 이 페이지는 암호화된 DB 를 알아보는 법과 파일 구조, 버전마다 다른 기본 설정을 다루고, 키를 얻는 방법은 다루지 않습니다.

## 이 형식을 쓰는 곳

SQLCipher 는 앱이 자기 설치 파일에 따로 넣어 쓰는 라이브러리입니다. 어느 앱이 SQLCipher 를 쓰는지, 키를 어디에 두는지는 앱마다 달라 분석 대상 앱에서 확인합니다. 앱이 자기 SQLite 라이브러리를 따로 넣으면 플랫폼 SQLite 의 빌드 옵션(secure_delete·자동 정리)을 따르지 않는다는 점은 [지운 레코드 되살리기](freelist-freeblock.md)에 정리했습니다. 앱 데이터 폴더에서 DB 파일을 찾는 법은 [앱 데이터 폴더 구조](../../storage/app-data-layout.md)에서 다룹니다.

## 구조

SQLCipher 는 페이지 단위로 따로 암호화하고, 기본 페이지 크기는 4096바이트입니다 [1][2]. 평문 SQLite 와 비교하면 아래가 다릅니다.

| 부분 | 평문 SQLite | SQLCipher (기본 설정) |
|---|---|---|
| 파일 첫 16바이트 | 매직 `SQLite format 3\000` | 16바이트 난수 salt. 매직이 보이지 않음 [1][2] |
| 페이지 본문 | 평문 | AES-256 CBC 암호문 [1] |
| 페이지 끝 | 머리 오프셋 20 에 적힌 예약 공간(보통 0) | 페이지를 쓸 때마다 만든 새 난수 IV 와, 암호문·IV 에 대한 HMAC-SHA512 [1] |
| 롤백 저널·WAL | 평문 페이지 사본 | DB 키로 암호화한 페이지. 문(statement) 저널도 암호화 [1] |

페이지 끝에 IV 와 HMAC 을 두는 자리는 SQLite 파일 머리 오프셋 20 의 예약 공간과 이어지고, 이 필드의 뜻은 [페이지와 레코드](b-tree-record.md)에 있습니다 [3].

키는 비밀번호에서 PBKDF2-HMAC-SHA512 로 만들고, 기본 반복 횟수는 256,000회이며 `PRAGMA kdf_iter` 로 바꿀 수 있습니다 [1][2]. KDF 는 기본 PBKDF2_HMAC_SHA512 외에 SHA256·SHA1 을, HMAC 은 기본 HMAC_SHA512 외에 SHA256·SHA1 을 지원합니다 [2]. 비밀번호 대신 원시 키를 줄 수도 있고, 원시 키와 salt 를 함께 주는 형식은 16진 96글자(키 32바이트와 salt 16바이트)입니다 [1][2].

### 머리 일부를 평문으로 두는 설정

SQLCipher 4.0.0 에서 추가된 `cipher_plaintext_header_size` 를 쓰면 파일 머리 일부를 암호화하지 않고 남겨, 파일이 SQLite 로 보이게 합니다. 이때 salt 는 파일에 없어서 앱이 따로 보관합니다. 이 설정은 주로 iOS 공유 컨테이너에 있는 WAL DB 에 씁니다 [2]. 이 설정을 쓴 파일은 첫 16바이트에 매직이 보여도 본문은 암호문일 수 있습니다.

## 버전마다 다른 기본 설정

SQLCipher 는 주 버전마다 기본 설정이 다르고, 4.0.1 에서 추가된 `cipher_compatibility` 에 1~4 를 주면 그 버전의 기본값으로 DB 를 엽니다. `cipher_migrate` 는 1·2·3 버전의 DB 를 4 버전 기본값으로 바꿉니다 [2].

| 항목 | 4.x 기본값 [1][2] | 3.x→4.x 바꾸기 예시에서 옛 DB 를 여는 값 [2] |
|---|---|---|
| 페이지 크기 | 4096 | 1024 |
| KDF 반복 횟수 | 256,000 | 64,000 |
| HMAC | HMAC_SHA512 | HMAC_SHA1 |
| KDF | PBKDF2_HMAC_SHA512 | PBKDF2_HMAC_SHA1 |

오른쪽 칸은 바꾸기 예시에 나온 값이라 3.x 의 기본값과 다를 수 있습니다. HMAC 은 SQLCipher 2.0 에서 들어왔고, 1.1.x 와 맞추려면 `cipher_use_hmac` 로 끕니다 [2]. 같은 앱이라도 설치 시기에 따라 DB 를 만든 SQLCipher 버전이 다를 수 있어서, 키를 알더라도 설정이 맞지 않으면 열리지 않는다는 점을 기억해 둡니다.

## 알아보는 법

암호화된 DB 는 전체가 무작위 데이터처럼 보입니다 [1]. 첫 16바이트에 `SQLite format 3` 매직이 없고 파일 크기가 페이지 크기의 배수인 파일은 SQLCipher 같은 암호화 DB 후보로 봅니다. 이 판별 기준은 구조에서 끌어낸 해석입니다.

아래는 명세로 만든 비교 예시이고, 실제 파일의 값이 아닙니다. 위는 평문 SQLite, 아래는 SQLCipher 기본 설정 파일의 첫 줄입니다.

```
평문       53 51 4c 69 74 65 20 66 6f 72 6d 61 74 20 33 00   SQLite format 3.
SQLCipher  ?? ?? ?? ?? ?? ?? ?? ?? ?? ?? ?? ?? ?? ?? ?? ??   16바이트 난수 salt (파일마다 다름)
```

매직이 없는 파일이 모두 암호화 DB 는 아닙니다. 손상된 SQLite 파일, 다른 방식으로 파일 전체를 암호화한 DB, 압축 파일도 같은 모습일 수 있어서, 후보로 표시한 뒤 앱 쪽 근거(앱이 넣은 라이브러리, 설정 파일)와 함께 판단합니다. 파일 시스템 수준의 암호화는 이와 다른 층의 이야기이고 [저장 공간 암호화](../../storage/encryption/index.md)에서 다룹니다.

## 포렌식에서 중요한 점

키가 있을 때는 공식 API 의 `sqlcipher_export` 로 평문 DB 를 내보내 일반 SQLite 로 분석할 수 있습니다 [2]. 키를 얻는 방법은 이 핸드북의 범위가 아닙니다. 내보낸 평문 DB 는 살아 있는 행만 담은 새 파일이라서, 원래 파일의 빈 페이지와 freeblock 흔적은 옮겨 오지 않습니다. 지운 레코드를 찾으려면 원래 파일을 페이지 단위로 복호한 사본에서 [지운 레코드 되살리기](freelist-freeblock.md)의 방법을 씁니다. 이 부분은 구조에서 끌어낸 해석입니다.

WAL 과 롤백 저널도 같은 키로 암호화돼 있어서 [1], 주 파일과 곁 파일을 함께 확보해야 한다는 원칙은 평문 DB 와 같습니다. 확보와 곁 파일 이야기는 [WAL과 저널](wal-journal.md)에 있습니다.

키가 없어 열지 못한 DB 도 기록할 가치가 있습니다. 파일 이름, 크기, 수정 시각, 곁 파일의 유무와 크기는 암호화와 상관없이 파일 시스템에서 읽을 수 있고, "이 앱의 암호화된 DB 가 마지막으로 바뀐 시각이 이렇게 기록돼 있다" 정도는 말할 수 있습니다. 수정 시각은 파일 시스템 값이라 바뀔 수 있고, 이 값으로 내용은 알 수 없습니다.

## 함정

- 첫 16바이트에 매직이 보인다고 평문이라고 단정하지 않습니다. `cipher_plaintext_header_size` 를 쓴 파일은 머리 일부만 평문입니다.
- 키가 맞아도 페이지 크기·KDF 반복 횟수·HMAC·KDF 알고리즘 가운데 하나가 다르면 열리지 않습니다. 버전 차이를 먼저 의심합니다.
