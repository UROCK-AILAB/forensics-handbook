# 페이지와 레코드 (B-tree·Record)

## 한 줄 요약

SQLite 파일은 크기가 같은 페이지로 나뉘고, 표와 색인은 페이지를 나무 모양으로 이은 B-tree 에, 행 하나는 머리와 본문으로 된 레코드 (Record) 에 담깁니다. 이 페이지는 파일 머리 100바이트에서 시작해 셀 하나를 헥스로 풀어 읽기까지를 다룹니다. SQLite 파일이 어디에 쓰이는지와 곁에 붙는 파일 이야기는 [SQLite 데이터베이스](index.md) 허브에 정리했습니다.

## 페이지

SQLite 데이터베이스는 파일 하나로 되어 있고, 파일 전체를 같은 크기의 페이지 (Page) 로 나눠 씁니다. 페이지 크기는 512부터 32768 사이의 2의 거듭제곱이고, 머리에 1 이 적혀 있으면 65536 을 뜻합니다 [1]. 페이지 번호는 1번부터 세서, N번 페이지는 파일 오프셋 (N−1)×페이지 크기에서 시작합니다.

Android 플랫폼 SQLite 는 새 DB 를 만들 때 /data 파일 시스템의 블록 크기(`StatFs("/data").getBlockSize()`)를 기본 페이지 크기로 쓰고, `debug.sqlite.pagesize` 속성이 있으면 그 값으로 바꿉니다(현행 AOSP 기준) [2]. 블록 크기는 기기마다 다를 수 있고 앱이 페이지 크기를 따로 정할 수도 있어서, 분석할 때는 파일 머리에 적힌 값을 읽어 씁니다.

파일이 1 GiB(1073741824바이트)보다 크면 그 오프셋에 걸친 페이지 하나는 잠금용 페이지 (Lock-byte Page) 이고, SQLite 는 이 페이지에 데이터를 쓰지 않습니다 [1].

## 파일 머리 (100바이트)

파일 머리 (Database Header) 는 1번 페이지 맨 앞 100바이트에만 있습니다. 1번 페이지의 B-tree 페이지 머리는 이 머리 뒤 오프셋 100 에서 시작하고, 다른 페이지의 B-tree 페이지 머리는 오프셋 0 에서 시작합니다 [1]. 분석에 쓰는 칸은 아래와 같습니다.

| 오프셋 | 크기 | 뜻 |
|---|---|---|
| 0 | 16 | 매직 문자열 `SQLite format 3\000` |
| 16 | 2 | 페이지 크기(빅엔디언). 65536 은 2바이트에 들어가지 않아 `00 01` 로 적음 |
| 18 | 1 | 쓰기 형식 버전. 1 은 롤백 저널, 2 는 WAL |
| 19 | 1 | 읽기 형식 버전. 뜻은 18 과 같음 |
| 20 | 1 | 페이지마다 끝에 비워 두는 예약 공간 바이트 수(보통 0) |
| 24 | 4 | 파일 변경 카운터. DB 를 바꾼 뒤 잠금을 풀 때 올라감 |
| 28 | 4 | 머리에 적힌 DB 크기(페이지 수) |
| 32 | 4 | 첫 freelist 트렁크 페이지 번호(없으면 0) |
| 36 | 4 | freelist 페이지 총수 |
| 40 | 4 | 스키마 쿠키. 스키마가 바뀔 때 올라감 |
| 52 | 4 | 자동 정리용 가장 큰 루트 페이지 번호. 0 이면 포인터 맵 페이지가 없음 |
| 56 | 4 | 글자 인코딩. 1 은 UTF-8, 2 는 UTF-16le, 3 은 UTF-16be |
| 60 | 4 | user_version. 앱이 `PRAGMA user_version` 으로 읽고 씀 |
| 64 | 4 | 0 이 아니면 incremental vacuum |
| 68 | 4 | application ID |
| 92 | 4 | version-valid-for 번호 |
| 96 | 4 | 마지막으로 이 파일을 쓴 SQLite 라이브러리의 버전 번호(SQLITE_VERSION_NUMBER) |

오프셋 28 의 DB 크기는 값이 0 이 아니고 오프셋 24 값과 오프셋 92 값이 같을 때만 믿을 수 있습니다 [1]. 오프셋 18·19 는 WAL 여부를, 오프셋 32·36·52·64 는 지운 페이지가 어떻게 관리되는지를 알려 줍니다. WAL 쪽은 [WAL과 저널](wal-journal.md)에서, 빈 페이지 쪽은 [지운 레코드 되살리기](freelist-freeblock.md)에서 이어 설명합니다. 오프셋 20 의 예약 공간은 SQLCipher 가 페이지마다 IV 와 HMAC 을 두는 자리라서 [암호화된 SQLite](sqlcipher.md)와 이어집니다.

아래는 명세로 만든 예시이고, 특정 검체에서 나온 값이 아닙니다. 페이지 크기 4096, WAL 모드, 예약 공간 0 인 파일의 앞부분입니다.

```
오프셋  00 01 02 03 04 05 06 07 08 09 0a 0b 0c 0d 0e 0f
0000    53 51 4c 69 74 65 20 66 6f 72 6d 61 74 20 33 00   SQLite format 3.
0010    10 00 02 02 00 ..                                 페이지 크기 0x1000=4096, 쓰기·읽기 버전 2(WAL), 예약 0
```

## B-tree 페이지

표와 색인은 각각 B-tree 하나에 들어가고, B-tree 의 페이지마다 맨 앞에 페이지 머리가 있습니다. 페이지 머리 오프셋 0 의 한 바이트가 페이지 종류를 알려 줍니다 [1].

| 값 | 페이지 종류 |
|---|---|
| 2 (0x02) | 색인 내부 페이지 |
| 5 (0x05) | 표 내부 페이지 |
| 10 (0x0a) | 색인 잎 페이지 |
| 13 (0x0d) | 표 잎 페이지 |

페이지 머리는 잎 페이지가 8바이트, 내부 페이지가 12바이트입니다 [1].

| 오프셋 | 크기 | 뜻 |
|---|---|---|
| 0 | 1 | 페이지 종류 |
| 1 | 2 | 첫 freeblock 위치(없으면 0) |
| 3 | 2 | 셀 수 |
| 5 | 2 | 셀 내용 영역 시작 위치(0 이면 65536) |
| 7 | 1 | 조각난 빈 바이트 수 |
| 8 | 4 | 가장 오른쪽 자식 페이지 번호(내부 페이지만) |

페이지 머리 바로 뒤에는 셀 포인터 배열이 옵니다. 셀마다 2바이트 오프셋이 하나씩 있고, 파일에 놓인 순서가 아니라 키 순서로 늘어섭니다 [1]. 셀 자체는 페이지 뒤쪽의 셀 내용 영역에 있어서, 셀 포인터 배열 끝과 셀 내용 영역 시작 사이가 아직 쓰지 않은 공간이 됩니다.

셀의 짜임은 페이지 종류마다 다릅니다 [1].

| 페이지 종류 | 셀 안의 순서 |
|---|---|
| 표 잎 (0x0d) | 페이로드 전체 길이(varint) → rowid(varint) → 페이로드 앞부분 → 넘침이 있으면 첫 넘침 페이지 번호(4바이트) |
| 표 내부 (0x05) | 왼쪽 자식 페이지 번호(4바이트) → 키(varint) |
| 색인 잎 (0x0a) | 페이로드 길이(varint) → 페이로드 앞부분 → 넘침이 있으면 첫 넘침 페이지 번호 |
| 색인 내부 (0x02) | 왼쪽 자식 페이지 번호(4바이트) → 색인 잎과 같은 내용 |

행 내용은 표 잎 페이지에만 들어 있고, 표 내부 페이지에는 자식 페이지로 가는 길잡이만 있습니다.

### 넘침 페이지

페이로드가 한 페이지에 다 들어가지 않으면 앞부분만 셀에 두고 나머지를 넘침 페이지 (Overflow Page) 로 보냅니다. 넘침 페이지는 앞 4바이트가 다음 넘침 페이지 번호(마지막이면 0)이고 나머지가 내용입니다 [1].

넘칠지 말지는 쓸 수 있는 크기 U(페이지 크기 − 예약 공간)로 정합니다. 표 잎은 X = U−35, 색인은 X = ((U−12)×64/255)−23 이고, 페이로드가 X 이하면 전부 페이지 안에 둡니다. 넘칠 때 페이지 안에 얼마를 남길지는 M = ((U−12)×32/255)−23 을 함께 써서 정합니다 [1]. 긴 문자열이나 BLOB 을 되살릴 때 이 계산이 틀리면 내용이 중간에서 끊겨 보입니다.

### 포인터 맵 페이지

포인터 맵 (Pointer Map) 페이지는 머리 오프셋 52 값이 0 이 아닐 때만 있고, 첫 포인터 맵은 2번 페이지입니다. 항목 하나는 5바이트로, 종류 1바이트와 부모 페이지 번호 4바이트로 되어 있습니다 [1].

| 종류 | 뜻 |
|---|---|
| 1 | B-tree 루트 페이지 |
| 2 | freelist 페이지 |
| 3 | 넘침 사슬의 첫 페이지 |
| 4 | 넘침 사슬의 이후 페이지 |
| 5 | 루트가 아닌 B-tree 페이지 |

## 레코드

레코드는 머리와 본문으로 되어 있습니다. 머리는 머리 전체 길이(자기 자신 포함, varint)로 시작하고, 뒤이어 칸마다 직렬 타입 (Serial Type) varint 가 하나씩 옵니다. 본문에는 칸 값이 같은 순서로 붙어 있습니다 [1].

| 직렬 타입 | 값 | 본문 바이트 수 |
|---|---|---|
| 0 | NULL | 0 |
| 1 · 2 · 3 · 4 | 부호 있는 정수 | 1 · 2 · 3 · 4 |
| 5 | 부호 있는 정수 | 6 |
| 6 | 부호 있는 정수 | 8 |
| 7 | IEEE 754 실수 | 8 |
| 8 | 정수 0 (스키마 형식 4 이상) | 0 |
| 9 | 정수 1 (스키마 형식 4 이상) | 0 |
| 10 · 11 | 내부용 예약 | — |
| 12 이상 짝수 N | BLOB | (N−12)/2 |
| 13 이상 홀수 N | 문자열(끝에 NUL 없음) | (N−13)/2 |

정수는 빅엔디언으로 적습니다. varint 는 1~9바이트 빅엔디언 정수로, 앞 바이트들은 최상위 비트가 1이고 마지막 바이트는 최상위 비트가 0이며, 9바이트째는 8비트를 모두 값으로 씁니다 [1]. Android 플랫폼 SQLite 는 `SQLITE_DEFAULT_FILE_FORMAT=4` 로 빌드해서(현행 AOSP 기준) [3], 플랫폼 라이브러리로 새로 만든 DB 에는 직렬 타입 8·9 가 나올 수 있습니다.

표에 INTEGER PRIMARY KEY 칸이 있으면 그 칸은 rowid 의 별칭이 되고, 레코드 안에는 NULL 로 적힙니다. 실제 값은 셀의 rowid 에서 읽습니다 [1]. 되살린 레코드에서 첫 칸이 NULL 로 보이면 이 경우일 수 있습니다.

스키마 표(sqlite_schema, 옛 이름 sqlite_master)는 1번 페이지에서 시작하고, 칸은 type, name, tbl_name, rootpage, sql 다섯 개입니다. rootpage 는 그 표나 색인의 루트 페이지 번호이고, 뷰와 트리거는 0 입니다 [1]. sql 칸에 표를 만든 문장이 그대로 남아 있어서, 되살린 레코드의 칸 순서와 타입을 맞춰 볼 때 기준으로 씁니다.

## 읽는 법

아래 순서로 손으로 따라가면 도구가 보여 준 행이 파일의 어디에서 나왔는지 확인할 수 있습니다.

1. 첫 16바이트가 매직 문자열인지 보고, 오프셋 16 에서 페이지 크기를, 오프셋 20 에서 예약 공간을, 오프셋 56 에서 글자 인코딩을 읽습니다.
2. 1번 페이지(오프셋 100 부터)의 sqlite_schema 를 풀어 찾는 표의 rootpage 와 sql 을 얻습니다.
3. rootpage 번호로 페이지 오프셋을 계산해 페이지 머리의 종류 바이트를 봅니다. 0x05 면 셀의 왼쪽 자식 번호와 가장 오른쪽 자식 번호를 따라 내려가고, 0x0d 에 닿을 때까지 되풀이합니다.
4. 표 잎 페이지에서 셀 수만큼 셀 포인터를 읽고, 포인터가 가리키는 오프셋에서 셀을 풉니다.
5. 셀의 레코드 머리로 칸마다 직렬 타입을 읽고 본문을 자릅니다. 페이로드가 X 보다 크면 넘침 페이지를 이어 붙입니다.

아래는 명세로 만든 예시 셀입니다. rowid 1 인 행이고, 칸은 문자열 `hi` 와 정수 5 두 개입니다.

```
06          페이로드 길이 6
01          rowid 1
03          레코드 머리 길이 3 (자기 자신 포함)
11          첫 칸 직렬 타입 0x11 = 17 → 홀수, (17−13)/2 = 2바이트 문자열
01          둘째 칸 직렬 타입 1 → 1바이트 정수
68 69       "hi"
05          5
```

## 포렌식에서 중요한 점

주 파일에 보이는 내용이 DB 의 최신 상태라고 단정하지 않습니다. 오프셋 18·19 가 2 면 WAL 모드이고, 커밋했지만 아직 주 파일로 옮기지 않은 페이지가 -wal 파일에 따로 있을 수 있습니다. 반대로 지운 행의 흔적은 freelist 페이지, 페이지 안의 freeblock, 셀 포인터 배열과 셀 내용 영역 사이 공간에 남을 수 있어서, 도구가 보여 주는 "살아 있는 행" 만으로는 파일 전체를 본 것이 아닙니다. 이 두 갈래는 각각 [WAL과 저널](wal-journal.md)과 [지운 레코드 되살리기](freelist-freeblock.md)에서 다룹니다.

첫 16바이트에 매직 문자열이 없는 파일은 손상됐거나 암호화됐을 수 있습니다. 판별은 [암호화된 SQLite](sqlcipher.md)에서 이어 봅니다.

## 함정

- 페이지 크기 칸의 1 은 65536 이고, 셀 내용 영역 시작 칸의 0 도 65536 입니다. 그대로 1·0 으로 계산하면 오프셋이 모두 어긋납니다.
- 넘침 기준 U 는 페이지 크기에서 예약 공간을 뺀 값입니다. 예약 공간이 0 이 아닌 파일에서 페이지 크기를 그대로 쓰면 넘침 계산이 틀립니다.
- 문자열에는 끝 NUL 이 없고, 머리 오프셋 56 의 인코딩이 UTF-16 이면 바이트를 두 개씩 읽습니다.
- 셀 포인터 배열은 키 순서라서, 셀 내용 영역의 물리 순서를 행이 들어온 순서로 읽으면 안 됩니다.

## 도구

공개 도구는 헥스 편집기와 SQLite 클라이언트 두 가지면 충분합니다. 클라이언트로 행을 보고, 중요한 행 몇 개는 위의 읽는 법으로 헥스에서 같은 값을 찾아 도구 결과를 검증합니다. 클라이언트가 파일을 열 때 WAL 을 합치거나 파일을 바꿀 수 있어서 늘 사본에서 작업하고, 그 이유는 [WAL과 저널](wal-journal.md)에 적었습니다. 도구 결과를 검증하는 절차는 [도구 검증](../../../03-techniques/reporting/tool-validation.md)에서 다룹니다.
