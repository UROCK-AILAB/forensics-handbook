# 작성 원칙

이 핸드북의 모든 글이 따르는 기준입니다.

## 성격

- **벤더 중립**입니다. 특정 제품의 사용법이 아니라, 아티팩트가 무엇을 기록하고 어떻게 해석하는지를 설명합니다.
- 독자는 SQLite·ext4 같은 기초 개념을 아는 사람입니다. 공부하는 사람과 현업 분석가 둘 다입니다.
- 도구는 공개 도구를 예로 들되, 도구 하나에 기대지 않습니다. 가능하면 헥스로 직접 한 번 따라갑니다.

## 문장

- "~합니다" 체로 씁니다.
- 한 문장에는 한 가지 생각만 담습니다. 이어지는 내용은 "~이고", "~라서", "~지만" 으로 이어 한 흐름으로 씁니다. 짧은 문장을 뚝뚝 끊어 늘어놓지 않습니다.
- 글머리표는 서로 무관한 항목을 나열할 때만 씁니다. 이유·순서·조건처럼 앞뒤가 이어지는 내용은 문단으로 씁니다. 사실 한 줄이 항목 하나인 목록으로 페이지를 채우지 않습니다.
- 설명하는 문장에서 "설명은 ~에서 끝나지 않는다" 처럼 사물을 주어로 삼지 않습니다. "~뿐만 아니라 ~까지 다룹니다" 처럼 씁니다.
- 말로 안 쓰는 한자어·번역투는 풀어 씁니다.
- 용어는 처음 나올 때 "한국어 (English)" 로 한 번 적고, 그 뒤에는 한국어로 씁니다.
- 평가어("완벽한", "강력한")를 쓰지 않습니다.

### 규칙 — 영어 문장을 그대로 옮기지 않는다

영어와 한국어는 문장을 짜는 방식이 다르다. 영어 구조를 그대로 옮기면 문법은 맞아도 읽는 사람이 번역서라는 것을 안다. 아래 4가지를 **쓰는 문장마다** 확인한다. (아래 예시는 문장 짜임만 보여 준다. 글은 "~합니다" 체로 쓴다.)

**1) 사물이 무엇을 "가지고 있다" 고 쓰지 않는다.**

| 틀림 | 옳음 |
|---|---|
| 이 규칙은 더 넓은 범위를 가지고 있다. | 이 규칙은 범위가 더 넓다. |
| 그녀는 아름다운 목소리를 가지고 있다. | 그녀는 목소리가 아름답다. |
| 그는 그러한 본능을 가지고 있다. | 그에게는 그런 본능이 있다. |
| 이 레코드는 세 개의 시각 값을 가지고 있다. | 이 레코드에는 시각 값이 세 개 있다. |

**2) "~에 의해 ~되다" 로 쓰지 않는다.** 행위자가 있으면 행위자를 주어로 쓰고, 없으면 "~가 바뀐다" 처럼 사물이 저절로 그렇게 되는 것으로 쓴다.

| 틀림 | 옳음 |
|---|---|
| 색깔이 빛에 의해 변한다. | 빛에 따라 색깔이 변한다. |
| 결정은 부모에 의해 만들어진다. | 결정은 부모가 한다. |
| 엄청난 노력이 기울여졌다. | 엄청난 노력을 기울였다. |
| 이 값은 운영체제에 의해 기록된다. | 운영체제가 이 값을 기록한다. |

**3) 명사를 늘어놓지 말고 동사로 푼다.** 영어는 명사로 뭉치고 한국어는 동사로 푼다.

| 틀림 | 옳음 |
|---|---|
| 성능의 향상을 위한 방법의 제안 | 성능을 높이는 방법을 제안한다 |
| 변이에 대한 연구를 수행했다. | 변이를 연구했다. |
| 실행 흔적의 확인을 위한 분석의 수행 | 실행 흔적을 확인하려고 분석한다 |

**4) 주어를 억지로 넣지 않는다.** 영어는 문법상 주어를 채워야 해서 we, you, it 을 넣지만 한국어는 그러지 않는다. 정말 사람을 가리킬 때만 남긴다.

| 틀림 | 옳음 |
|---|---|
| 우리는 데이터로 범람한다. | 데이터가 범람하고 있다. |
| 우리는 이 키에서 실행 횟수를 볼 수 있다. | 이 키에서 실행 횟수를 볼 수 있다. |
| 당신은 먼저 사본을 만들어야 한다. | 먼저 사본을 만든다. |

### 규칙 — 쓰지 않는 말

어렵거나, 번역투이거나, 예스럽거나, 뜻이 둘로 읽히는 말입니다. 오른쪽처럼 바꿉니다.

| 쓰지 않는 말 | 바꿀 말 | 그대로 둬도 되는 경우 |
|---|---|---|
| X 가 맞습니다, ~가 핵심입니다 | X 를 쓰면 됩니다, 할 일을 바로 씁니다 | — |
| 기록이 말하다, 말해 주다, 말하지 않다 (사물을 사람처럼) | ~로 알 수 있다, ~에 나와 있다, ~로 확인된다 | 사람이 주어일 때 |
| 검체 | 실제 기기, 실제 데이터, 분석 대상, 이미지, 증거물 | — |
| 칸 (필드·열이라는 뜻) | DB 는 "열", 레코드·로그·JSON 은 "필드" | 진짜 표의 칸, 빈칸, 입력칸 |
| 가리다 (구분한다는 뜻) | 구분합니다, 판별합니다, 확인합니다, 골라냅니다 | 값을 감춘다는 뜻, 가리키다, 가려내다, 가리지 않고 |
| 세우다 (표·순서·구간·경로를) | 시간순으로 합치다, 정렬하다, 경로를 되살리다, 구간을 찾다, 표로 정리하다 | 계획·가설·대책을 세우다 |
| 쪽 (페이지라는 뜻) | 페이지 | 방향·편(서버 쪽, 양쪽), 인쇄 쪽수 |
| 갈래 | 분류, 범주, 종류 | — |
| 꼴 (형식이라는 뜻) | 형식, 모양 | — |
| 견주다 | 비교하다 | — |
| 벽시계 (wall clock) | 실제 시각 시계, 시스템 시계 | — |
| 살아 있는 시스템 (live) | 실행 중인 시스템 | 삭제되지 않았다는 뜻 |
| 셉니다 (따로 다룬다는 뜻) | 따로 봅니다, 따로 분류합니다 | 실제로 개수를 셀 때 |
| 이름으로 보아, 까닭 | 이름으로 보면, 이유·"그래서 ~" | — |
| 영어 비유(~위에 서 있다, ~앞에서는) | ~덕분에, ~할 때는 | — |

## 정확성

- **버전에 따라 다른 것은 그 자리에 버전을 적습니다.** 예: "Windows 10 1803 에서는 ~". 페이지 머리에 확인 날짜나 확인 방법을 적지 않고, "(확인 범위: …)", "(관찰)" 같은 괄호도 붙이지 않습니다. 직접 시험한 결과는 "~했습니다" 로 보고하지 않고 "~하면 ~됩니다" 처럼 조건이 붙은 사실로 씁니다.
- **Android 버전과 제조사를 밝힙니다.** 버전마다 다르면 표로 정리합니다.
- **모르면 쓰지 않습니다.** 오프셋·패키지 이름·DB 표 이름·파일 경로는 확인한 것만 씁니다. 글쓴이가 무엇을 찾지 못했는지, 어떤 자료를 열지 못했는지 같은 작업 과정은 쓰지 않습니다.
- **사실은 우리 글로 곧바로 씁니다.** "○○ 글은 ~라고 적었습니다", "~에 따르면" 처럼 출처를 옮겨 전하지 않고, 사실을 쓴 뒤 끝에 참고 문헌 번호를 답니다. 출처끼리 결과가 다를 때, 특정 시험 조건의 결과일 때만 출처를 본문에 밝힙니다.
- 헥스 예시는 명세로 만든 예시라고 밝힙니다. 특정 기기에서 나온 숫자·해시를 지어내지 않습니다.
- 참고 문헌에는 **실제로 열어 본 자료만** 넣습니다.

## 증거로서의 해석

- 모든 아티팩트 글에 **증명하는 것 / 증명하지 못하는 것**을 나눠 씁니다.
- 시각은 무엇이 바뀔 때 바뀌는지, UTC 인지 현지 시각인지 밝힙니다.
- 흔한 오해와 안티포렌식(지우기·조작)에 어떻게 남는지를 씁니다.
- 보고서에 쓸 문장은 "파일을 보냈다" 가 아니라 "이 시간대에 이 앱이 이만큼 송신한 기록이 있다" 처럼 기록으로 확인되는 만큼만 씁니다.

## 링크

- 다른 페이지는 그 페이지가 있는 폴더 기준 상대 경로로 링크합니다. 예: `../sqlite/index.md`. GitHub 저장소 화면과 GitHub Pages 둘 다에서 풀립니다
- 같은 사실은 한 페이지에만 쓰고 나머지는 링크합니다. 저장 형식 설명은 기반 구조 페이지로 링크합니다.
- 그림이 필요한 곳은 `> 그림 자리: (무엇을 보여 줄지)` 로 표시합니다.
