# 도구 검증 (Tool Validation)

도구 검증은 포렌식 도구와 절차가 알려진 데이터를 바꾸지 않고 정확히 가져와 보여 주는지, 어디까지 믿고 쓸 수 있는지를 사건에 쓰기 전에 시험하고 그 결과를 기록하는 일입니다.

## 언제 쓰나

NIST 가 정리한 이전 도구 시험에서는 기기에 있는 데이터를 가져오지 못하거나, 화면에 보이는 데이터와 보고서 출력이 다르거나, 보고서나 화면 출력이 잘리는 문제가 드러났습니다[1]. 복구한 데이터를 해석·변환하다 틀리거나 관련 데이터를 다 가져오지 못한 경우도 있었고, 새 버전이 일부 기능에서 이전 버전보다 못한 경우도 있었습니다[1].

도구 자체에도 오류가 있을 수 있어서, 구현 버그가 있거나 도구가 따르는 파일 구조 명세가 틀렸거나 낡았을 수 있고, 다른 프로그램이 만든 입력 파일의 구조가 잘못됐을 수도 있습니다[1]. 모바일 도구 실험에서는 데이터 형식과 표시 오류가 흔했습니다[1]. NIST 는 도구가 쓸 만한지 검증하고 업데이트나 새 버전이 나오면 다시 검증하라고 권하며, 그 결과로 도구가 적절한지, 부족한 점을 어떻게 메울지, 다른 버전을 쓸지를 정합니다[1].

SWGDE 18-Q-001 은 이런 시험을 흔히 검증 (Validation) 또는 확인 (Verification) 시험이라고 부르고, 도구·절차가 기대대로 동작하는지와 한계가 무엇인지를 알아보려고 한다고 적습니다[3]. 언제 시험하는지는 다음과 같습니다.

| 상황 | 시험 여부 | 출처 |
|---|---|---|
| 도구를 쓰기 시작하기 전 | 시험 | [3] |
| 하드웨어 도구를 수리한 뒤 | 시험 | [3] |
| 주요 업데이트·개정 뒤 | 시험. 소프트웨어는 주요 버전마다 한 번이면 대체로 충분 | [3] |
| 기기 지원 추가·기능 추가·버그 수정 같은 잦은 변경 | 대개 다시 시험하지 않아도 됨. 배포 노트를 보고 기관이 중요하다고 판단하거나 기관 정책이 요구하면 시험 | [3] |
| 하드웨어 장비 | 장비마다 시험 | [3] |
| 자체 개발 도구 | 처음 쓸 때와 개정할 때마다 시험 | [3] |
| 사건 기기에 절차를 쓰기 전 | 같은 모델 기기로 시험 | [1] |

사건에 따라 특정 모델을 따로 시험할 수 있고[3], NIST 는 실제 사건 전에 시험용 기기로 여러 도구를 써 보기를 강하게 권합니다[1].

## 기준 문서

| 문서 | 연도 | 다루는 것 | 읽을 때 주의 |
|---|---|---|---|
| NIST SP 800-101 Rev.1[1] | 2014 | 모바일 포렌식 지침, 도구 선택 기준과 절차 검증 | Android 10 이상으로 출시되는 기기에 파일 단위 암호화 (File-Based Encryption, FBE)가 의무가 되기 전 문서 |
| NIST CFTT 모바일 기기 도구 규격 2.0[2] | 2016 | 모바일 수집 도구의 필수·선택 요건 | FBE 의무화 전 문서 |
| SWGDE 18-Q-001 2.1판[3] | 2024-03-07 | 도구 종류별 최소 시험 요건 | 현재판 |

FBE 가 수집 범위에 주는 영향은 [저장 공간 암호화](../../01-foundations/storage/encryption/index.md)에 있습니다.

## 도구를 고르는 기준

NIST 가 드는 도구 선택 기본 요건은 여섯 가지입니다[1].

| 요건 | 뜻 |
|---|---|
| 쓰기 편함 (Usability) | 조사자에게 쓸모 있는 형태로 보여 준다 |
| 빠짐없음 (Comprehensive) | 유죄·무죄 증거를 모두 찾을 수 있게 데이터를 전부 보여 준다 |
| 정확함 (Accuracy) | 출력 품질이 검증돼 있다 |
| 결정적 (Deterministic) | 같은 명령과 입력이면 같은 출력을 낸다 |
| 확인 가능 (Verifiable) | 중간 변환·표시 결과를 볼 수 있어 정확성을 확인할 수 있다 |
| 시험됨 (Tested) | 기기에 있는 알려진 데이터가 바뀌지 않고 정확히 보고되는지 확인돼 있다 |

## 절차

NIST 는 검증을 포괄적인 시험 데이터를 정하고, 수집 절차로 그 데이터를 가져오고, 결과를 평가하는 세 단계로 설명합니다[1]. 절차를 만들고 검증하는 단계로는 DOJ 2008 지침을 인용해 과제 정의, 해결책 제안, 같은 시험 기기에서 통제된 조건으로 각 해결책 시험, 결과 평가, 절차 확정을 들고 이 과정을 기록하라고 적습니다[1]. 절차는 결과가 유효하고 독립적으로 다시 만들 수 있는지를 시험해야 합니다[1]. 아래 단계는 두 설명을 합친 것입니다.

1. **과제를 정합니다.** 어떤 도구·절차로 어떤 데이터를 가져오려는지 정합니다. CFTT 는 도구 문서가 가져올 수 있다고 밝힌 데이터 객체, 즉 지원 데이터 객체 (Supported Data Objects)를 기준으로 시험합니다[2]. 도구가 스스로 주장한 범위가 시험 범위의 출발점입니다.
2. **알려진 데이터 세트를 만듭니다.** SWGDE 는 모바일 이미저 시험에 알려진 데이터 세트를 반드시 쓰고, 주소록·사진·영상·메시지·소셜 미디어처럼 흔히 만나는 데이터 종류를 대표하게 짜라고 적습니다[3]. 실제 데이터가 꼭 더 나은 것은 아니고, 실험실에서 만든 데이터가 중요한 조건을 겨냥하기에 좋습니다[3]. 압수 기기를 써도 되지만 관련 내용을 기록하고 개인 정보가 새지 않게 합니다[3]. CFTT 가 내부 메모리 시험에 쓰는 데이터 종류는 아래 "CFTT 모바일 기기 도구 규격" 에 있습니다.
3. **시험 기기를 고정합니다.** CFTT 시험에서는 원본 기기와 UICC 에 알려진 데이터 세트를 채운 뒤, 네트워크 연결로 데이터가 바뀌지 않게 기기를 보호 상태로 보관합니다[2]. 시험 기록에는 시험 기기의 `Build.FINGERPRINT` 와 `Build.VERSION.SECURITY_PATCH` 를 적어 둘 수 있습니다[5]. 같은 모델이라도 빌드가 바뀌면 도구 동작이 달라질 수 있다고 보고 적어 두는 값인데, 이 판단은 직접 확인한 것이 아니고, 새 버전 도구가 오히려 못했던 사례[1]와 소프트웨어·하드웨어 판이 워낙 다양해 모든 상황에서 기대대로 동작한다고 보장할 수 없다는 SWGDE 의 설명[3]에서 끌어냈습니다. 두 값이 무엇을 뜻하는지는 [포렌식 보고서](forensic-report.md)의 기기 식별 정보 표에 있습니다.
4. **시험 환경을 준비합니다.** CFTT 는 시험할 도구마다 다른 포렌식 프로그램이 없는 전용 컴퓨터에 설치합니다[2].
5. **통제된 조건으로 수집합니다.** CFTT 규격은 원본 증거를 바꾸지 않는다는 원칙을 핵심으로 삼고, 드라이버 설치처럼 기기 설정을 바꾸지 않고는 수집할 수 없다면 그 절차를 기록합니다[2]. 해결책이 여럿이면 같은 시험 기기에서 각각 시험합니다[1].
6. **결과를 평가합니다.** 알려진 데이터가 빠짐없이, 바뀌지 않고 나오는지 봅니다. 요즘 도구는 검증에 도움이 될 자세한 추출 로그를 잘 주지 않아서, NIST 는 여러 도구의 출력을 비교해 결과가 일관된지 보라고 권하고 시간이 걸려도 반드시 해야 한다고 적습니다[1]. SWGDE 는 알려진 데이터 시험에 경험적 시험을 더하고, 추출이 덜 됐을 가능성과 이상 현상, 도구 한계에 주의하라고 적습니다[3]. 시험 종류는 아래 표에 있습니다.
7. **결과를 기록합니다.** SWGDE 6장이 드는 기록 항목은 시험 목적과 범위(어떤 도구·기법인지), 시험한 사람, 날짜, 시험 절차 또는 시나리오, 쓴 데이터 세트와 기대 결과, 결과와 이상 현상과 그 의미, 확인된 한계입니다[3]. 제3자 시험을 쓰면 그 보고서와 결과를 참조로 적고, 공급사 시험 기록은 보통 구할 수 없습니다[3].
8. **절차를 확정하고 교육합니다.** 확정한 절차는 사건에 쓰고, 조사자는 쓰는 도구와 절차에 대해 최신 교육을 받아야 합니다[1].

SWGDE 부록 A 는 시험 종류를 셋으로 나눕니다[3].

| 시험 종류 | 방법 | 주의 |
|---|---|---|
| 알려진 데이터 세트 시험 | 알려진 입력을 주고 출력이 맞는지 본다 | 실험실에서 만든 데이터로 중요한 조건을 겨냥할 수 있다 |
| 비교 시험 | 두 도구 이상이 같은 결과를 내는지 본다 | 따로 만든 도구끼리도 같은 원인의 문제가 있을 수 있어, 알려진 데이터 시험보다 놓치는 오류가 있을 수 있다 |
| 경험적 시험 | 출력이 기대한 데이터 형식과 맞는지, 손으로 확인되는지처럼 다른 자료와 맞춰 본다 | 알려진 데이터 시험에 더해서 쓴다 |

## CFTT 모바일 기기 도구 규격

CFTT(Computer Forensics Tool Testing)는 DHS·NIJ·NIST 의 공동 사업으로, 포렌식 도구가 정확한 결과를 낸다는 것을 측정할 수 있게 보증하려고 도구 규격과 시험 방법을 만들고 그 규격에 맞춰 도구를 시험합니다[2]. 모바일 기기 도구 규격 2.0 은 피처폰·스마트폰·태블릿·UICC 의 내부 메모리를 수집하는 소프트웨어·하드웨어 도구에 적용됩니다[2]. 규격의 요건은 시험 단언 (Test Assertion)으로 풀어 쓰는데, 시험 단언은 시험 뒤에 확인할 수 있는 일반 조건이고 하나 이상의 시험 사례(시험 절차와 기대 결과)로 나타납니다[2]. 짝 문서는 "Mobile Device Tool Test Assertions and Test Plan Version 2.0" 입니다[2].

| 구분 | 번호 | 내용[2] |
|---|---|---|
| 필수 | MDT-CR-01 | 지원 기기를 권장 연결 방식(케이블·블루투스 등)으로 알아본다 |
| 필수 | MDT-CR-02 | 추출 중 기기와 연결 오류가 나면 사용자에게 알린다 |
| 필수 | MDT-CR-03 | 지원 데이터 객체를 바꾸지 않고 논리 추출한다 |
| 선택 | MDT-RO-01~03 | 물리 추출: 지원 기기를 물리 추출하고, 추출 중 연결 오류를 알리고, 부트로더·JTAG·ISP 로 읽을 수 있는 메모리를 바꾸지 않고 추출한다 |
| 선택 | MDT-RO-04~06 | UICC 추출: 지원 UICC 를 알아보고, 리더와의 연결 오류를 알리고, UICC 메모리의 지원 데이터 객체를 모두 가져온다 |
| 선택 | MDT-RO-07 | 인증 수단 우회. 이 핸드북은 우회 방법을 다루지 않는다 |

필수 요건은 모든 도구가 충족해야 하고, 선택 요건은 도구에 그 기능이 있을 때만 적용합니다[2]. 규격은 파일 시스템 파티션 같은 논리 저장소에 있는 연락처·통화 기록·문자·파일 같은 논리 객체를 비트 단위로 복사하는 방식을 논리 수집으로, 내부 메모리를 비트 단위로 수집하는 방식을 물리 수집으로 정의합니다[2]. 수집 방식의 실무 차이는 [모바일 증거 확보](../acquisition/mobile-acquisition/index.md)에 있습니다.

내부 메모리 시험에 쓰는 데이터 종류는 다음과 같습니다[2].

| 분류 | 데이터 종류 |
|---|---|
| 식별자 | 가입자·단말 식별자(IMEI, MEID/ESN) |
| 개인 정보 관리 | PIM 데이터(연락처·일정·메모) |
| 통신 | 통화 기록(수신·발신·부재), 문자(SMS, MMS), 인스턴트 메시지, 메일, 소셜 미디어 데이터 |
| 파일 | 단독 파일(오디오·그림·영상), 전자 문서 |
| 앱·웹 | 제3자 앱 데이터, 웹 활동(기록·북마크) |
| 위치 | GPS·위치(위도·경도) |

## 도구 종류별 시험 요점

SWGDE 는 도구 종류마다 시험 방법을 따로 적습니다[3].

| 도구 종류 | 시험 방법 | 주의 |
|---|---|---|
| 모바일 이미저 (5.1.2.2) | 알려진 데이터 세트에 경험적 시험을 더한다. 흔한 데이터와 흔한 폰 종류에 집중한다 | 모든 폰에서 모든 데이터를 가져오는 도구는 없고, 모든 기기 종류와 OS 변형을 다 시험할 필요도 없다 |
| 디스크 이미저 | 원본과 수집본을 비트 단위로 비교하거나 해시(MD5, SHA256 등)를 비교한다 | 시험에 쓴 설정을 기록한다 |
| 해시 도구 (5.1.3) | 파일 사이 비교나 알려진 데이터로 시험하고, 입력에 바이너리와 텍스트 파일을 모두 넣는다 | 큰 도구에 든 해시 기능은 배포 노트에 해시 모듈이 바뀌었다고 나올 때 시험한다 |
| 검색 도구 (5.3.1) | 알려진 데이터 세트나 결과 수동 확인 | 도구의 한계까지 알 수는 없지만 핵심 기능이 동작하는지는 확인된다 |
| 복구 도구 (5.3.2) | 알려진 데이터 세트로 시험하고 조각난 파일을 어떻게 다루는지 본다 | 다른 파일의 조각을 합칠 수 있어서, 복구한 파일을 직접 열어 앞뒤가 맞는지 확인한다 |
| 모으기·요약 도구 (5.3.3) | 타임라인·연결 그래프 등을 알려진 데이터, 비교, 결과 일부 수동 확인으로 시험한다 | |
| 보조 도구 (5.5) | 워드 프로세서·사건 관리 소프트웨어 등은 공급사 시험 외에 따로 시험하지 않아도 된다 | |
| 자체 개발 도구 (5.6) | 결과에 영향을 줄 수 있으면 그 기술을 아는 다른 사람이나 기관이 시험한다 | 간단한 스크립트·질의는 대개 시험하지 않아도 된다 |

모바일 기기는 저장 장치 내부 동작 때문에 데이터가 바뀔 수 있어서, SWGDE 는 해시만으로 모바일 이미지가 맞다고 판단할 수 없다고 적습니다[3]. 연달아 수집한 두 이미지의 전체 해시가 왜 다른지와 보고서에 무엇을 적는지는 [포렌식 보고서](forensic-report.md)의 무결성 값 절에 있습니다.

자체 개발 도구는 조사자 메모만으로 다시 만들 수 없을 만큼 복잡하거나, 코드가 메모에 넣기엔 크거나, 결과를 손으로 확인할 수 없거나, 컴파일돼 있어 소스를 구하기 어려울 때 시험이 필요합니다[3]. 중요한 도구는 개발자가 아닌 사람이 시험하고, 가능하면 개발에 쓴 것과 다른 데이터 세트로 시험합니다[3]. 삭제 데이터 복구와 콘텐츠 검색의 방법 자체는 [삭제 데이터 복구](../analysis/data-recovery/index.md)와 [콘텐츠 검색](../analysis/content-search.md)에 있습니다.

## 도구

시험은 기관 안에서 해도 되고, 다른 역량 있는 기관의 결과를 받아 써도 됩니다[3]. SWGDE 는 CFTT 의 일반 규격·시험 절차·기준·시험 세트·시험 하드웨어를 써 볼 만한 방법으로 들고, 모바일 이미저는 기관 자신이나 CFTT, 또는 같은 주요 버전을 시험한 다른 제3자가 시험한다고 적습니다[3].

시험 보고서는 기관 자체, 공급사, NIST CFTT 를 포함한 제3자가 냅니다[3]. NIST 연합 시험 (Federated Testing)을 쓰면 기관이 NIST 가 만든 시험을 직접 돌릴 수 있는데, 2018-03-23 기준으로 디스크 이미징, 쓰기 방지, 모바일 기기 수집에만 있었습니다[3]. 미국 국방부 사이버범죄센터(DC3)도 시험 보고서를 내지만 정부 도메인 사용자만 볼 수 있습니다[3]. CFTT 보고서를 인용할 때는 시험한 도구 버전과 규격 판이 지금 쓰는 것과 같은지 확인합니다.

공개 도구로 비교 시험을 하는 방법도 있습니다. 같은 추출본을 ALEAPP 같은 공개 파서[4]와 다른 도구로 각각 처리해 결과를 맞춰 보면 SWGDE 가 말하는 비교 시험에 해당한다고 볼 수 있습니다[3]. 비교 시험이 놓칠 수 있는 오류는 위 시험 종류 표에 있습니다. ALEAPP 의 입력 형식과 출력은 [포렌식 보고서](forensic-report.md)의 도구 절에 있습니다.

## 함정과 한계

CFTT 시험은 도구가 주장한 지원 데이터 객체를 기준으로 하기 때문에[2], 시험을 통과한 도구라도 시험하지 않은 앱이나 도구가 지원한다고 밝히지 않은 데이터까지 정확히 가져온다고 볼 수는 없습니다. SWGDE 도 모바일 이미저를 빠짐없이 시험하는 일은 현실적이지 않다고 적습니다[3].

소프트웨어·하드웨어 판이 너무 다양해서 모든 상황에서 도구가 기대대로 동작한다고 보장할 수 없고, 그래서 기관은 위험과 시험 비용을 저울질해야 합니다[3].

시험 기기는 켜져 있는 동안 사용자 조작과 무관하게 기록을 계속 바꿉니다. 관찰 기기에서는 `dumpsys batterystats` 출력이 98027줄이었고 그 가운데 Battery History 에 상태 변화 줄이 수만 개 쌓여 있었으며, `dumpsys usagestats` 에도 `FOREGROUND_SERVICE_START`, `FOREGROUND_SERVICE_STOP`, `STANDBY_BUCKET_CHANGED` 같은 이벤트가 계속 기록돼 있었습니다. 같은 시험 기기를 두 번 수집해 비교할 때는 이런 기록이 바뀐다는 점을 감안하고, 전체 해시가 아니라 알려진 데이터 항목 단위로 대조합니다. 두 기록의 구조는 [배터리 사용 기록](../../02-artifacts/app-usage/batterystats.md)과 [앱 사용 기록](../../02-artifacts/app-usage/usagestats/index.md)에 있습니다.

공개된 Android 기준 이미지(알려진 데이터 세트)의 이름과 출처는 이 핸드북에서 아직 확인하지 않았습니다. 기준 이미지가 없더라도 기관이 시험 기기에 알려진 데이터를 직접 채워 시험할 수 있고, SWGDE 도 실험실에서 만든 데이터가 중요한 조건을 겨냥하기 좋다고 적습니다[3].

## 결과를 어떻게 해석하나

시험 결과는 합격·불합격 둘로 나뉘지 않습니다[3]. 심각한 결함이 있으면 도구를 쓰면 안 되지만, 어떤 결함은 특정 영역에서만 도구의 쓰임을 제한합니다[3]. 예를 들어 한 도구가 메시지는 정확히 가져오지만 특정 데이터 종류에서 표시 오류를 보였다면, 그 데이터 종류에는 다른 도구나 수동 확인을 쓰도록 절차에 적어 두는 식입니다. 이렇게 확인된 한계는 시험 기록에 남기고, 그 도구로 만든 [포렌식 보고서](forensic-report.md)의 "검사에 쓴 장비와 설정" 에도 적습니다.

시험 기록의 문장도 관찰한 만큼만 씁니다. "이 도구는 정확하다" 라고 쓰지 않고, "이 도구 버전은 이 빌드의 시험 기기에서 알려진 데이터 세트의 해당 항목을 바꾸지 않고 모두 보고했다. 시험하지 않은 앱 데이터는 이 결과로 판단할 수 없다" 처럼 도구 버전, 시험 기기 빌드, 데이터 세트, 범위를 함께 적습니다.
