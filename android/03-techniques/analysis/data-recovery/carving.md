# 파일 카빙 (Carving)

파일 시스템의 기록을 쓰지 않고 저장 영역의 블록을 차례로 읽으며 알려진 파일 서명과 맞춰 파일을 다시 잘라 내는 기법이고, Android 내부 저장소에서는 암호화 때문에 쓸 수 있는 곳이 좁습니다.

## 언제 쓰나

카빙은 평문 블록이 저장 장치에 남아 있어야 성립합니다. 공개 도구 PhotoRec 같은 카빙 도구는 파일 시스템을 거치지 않고 그 밑의 데이터를 블록 단위로 읽으면서 알려진 파일 서명과 맞춰 봅니다 [1]. Android 10 이후 출시 기기의 내부 저장소(`/data`)는 파일 기반 암호화 (File-Based Encryption, FBE) 로 파일 내용이 암호화되고(AES-256-XTS 또는 Adiantum), 공용 저장 공간인 `/sdcard`(= `/data/media/<사용자ID>`)도 자격 증명 암호화 (CE) 영역입니다 [2]. 그래서 `/data` 의 물리 이미지를 그대로 카빙해서는 파일 서명이 보이지 않습니다. 암호화와 TRIM 이 복구를 어떻게 막는지는 [TRIM과 암호화가 주는 한계](trim-encryption.md) 페이지에 있습니다.

그래서 카빙을 쓸 만한 곳은 아래처럼 나뉩니다.

| 대상 | 카빙 가능성 | 근거 |
|---|---|---|
| 암호화하지 않은 휴대용 SD 카드(FAT·exFAT) | PhotoRec 류 도구가 다루는 파일 시스템이라 카빙 대상이 됨 | [1]. 휴대용 SD 카드의 암호화 여부는 실제 기기로 확인 |
| 내부 저장소로 쓰는 SD 카드(adoptable) | FBE 와 메타데이터 암호화가 항상 걸림 | [3] |
| 내부 저장소 `/data` 물리 이미지(Android 10 이후 출시 기기) | 파일 내용이 암호문이라 서명이 보이지 않음 | [2] |
| 논리 수집으로 얻은 개별 파일 안(DB 의 BLOB, 캐시 파일 등) | 파일 안에서 다른 파일의 서명을 찾을 수 있음 | 파일 시스템을 거쳐 읽은 평문 파일 안을 찾는 것이라 저장 장치 층 암호화와 따로 봄 |

DB 파일 안에 남은 지운 레코드는 카빙이 아니라 SQLite 구조를 따라 찾는 편이 정확하고, 그 방법은 [SQLite 레코드 되살리기](sqlite-records.md) 페이지에 있습니다.

## 절차

1. **대상이 평문인지 먼저 확인합니다.** 이미지가 어느 저장 영역에서 나왔는지, 그 영역이 FBE·메타데이터 암호화 대상인지 확인합니다. 암호문 영역이면 카빙 결과가 나오지 않는 것이 정상이라서, 이 단계에서 카빙을 할지 말지 정합니다.
2. **원본은 읽기 전용으로 다룹니다.** PhotoRec 은 SD 카드 같은 메모리 카드와 DD raw·E01 이미지를 읽을 수 있고 [1], 이미지로 떠 둔 사본에서 작업합니다. 이미지를 뜨는 방법은 [모바일 증거 확보](../../acquisition/mobile-acquisition/index.md) 페이지에 있습니다.
3. **블록 크기를 정합니다.** PhotoRec 은 먼저 슈퍼블록에서 블록(클러스터) 크기를 읽고, 읽을 수 없으면 처음 찾은 파일들로 추정합니다 [1]. 도구가 정한 값은 결과와 함께 적어 둡니다.
4. **서명과 맞춰 봅니다.** 블록마다 앞 바이트를 알려진 파일 서명과 비교합니다. PhotoRec 은 480개가 넘는 확장자(약 300개 파일 계열)를 알아봅니다 [1].
5. **결과를 정리합니다.** 되살린 파일에는 원래 이름과 시각이 없고, 조각난 파일은 온전히 살아나지 않을 수 있습니다 [1]. 파일마다 이미지 안의 시작 오프셋, 크기, 해시를 적고, 열리지 않거나 중간이 깨진 파일은 따로 표시합니다.
6. **다른 기록과 맞춰 봅니다.** 되살린 사진은 파일 안의 메타데이터를 [카메라 사진과 메타데이터](../../../02-artifacts/media/dcim-exif.md) 방식으로 읽고, [미디어 저장소](../../../02-artifacts/media/mediastore/index.md) 와 [섬네일 캐시](../../../02-artifacts/media/thumbnails.md) 에 같은 파일의 흔적이 있는지 찾아봅니다.

## 헥스로 따라가기

아래는 명세로 만든 예시이고, 실제 기기에서 뽑은 값이 아닙니다. JPEG 파일은 `ff d8 ff e0` 로 시작하는 경우가 있습니다 [1].

```
블록 0x0003a000: ff d8 ff e0 …    JPEG 서명 → 여기서 파일 하나를 잘라 내기 시작
블록 0x0003b000: 00 00 00 00 …    서명 없음 → 앞 파일의 이어지는 블록일 수 있음
```

카빙 도구는 이렇게 블록 앞머리의 서명으로 파일이 시작하는 자리를 잡습니다. 두 번째 블록처럼 서명이 없는 블록이 앞 파일의 뒷부분인지는 파일 시스템 정보 없이는 알 수 없어서, 조각난 파일은 이어 붙이는 과정에서 틀어질 수 있습니다.

## F2FS 에서 알아 둘 점

F2FS 는 NAND 플래시용 로그 구조 파일 시스템이고, 고친 데이터를 제자리가 아닌 새 자리에 씁니다(out-of-place write). 그래서 옛 블록이 영역 곳곳에 남을 수 있습니다 [4]. 영역은 2MB 세그먼트 단위로 나뉘고, 아래 순서로 배치됩니다 [4].

| 영역 | 담는 것 |
|---|---|
| 슈퍼블록 | 파티션 기본 정보와 F2FS 기본 설정. 파티션 앞에 두 벌을 둠 |
| 체크포인트 (CP) | 파일 시스템 정보, 유효한 NAT·SIT 판의 비트맵, 고아 inode 목록. 두 벌(shadow copy)을 둠 |
| SIT | 세그먼트별 유효 블록 수와 블록 유효 비트맵 |
| NAT | 노드 블록의 위치 |
| SSA | 메인 영역 블록의 소유자 정보 |
| 메인 영역 | 파일과 디렉터리의 데이터, 그 색인(노드 블록) |

약 3.4KB 보다 작은 파일은 inline_data 로 inode 블록 안에 바로 저장될 수 있고, 디렉터리 항목도 inline_dentry 로 inode 안에 둘 수 있습니다 [4]. 이런 파일이 블록 앞머리 서명으로 찾는 카빙에 잡히는지는 실제 기기로 확인합니다. F2FS 는 필요할 때와 백그라운드에서 청소 (garbage collection) 를 하고, 청소할 세그먼트를 greedy 방식이나 cost-benefit 방식으로 고릅니다 [4]. 청소하면 옛 블록이 비워지거나 다시 쓰일 수 있어서, 옛 블록이 남는다는 성질만 보고 복구를 기대하지는 않습니다.

PhotoRec 이 다루는 파일 시스템은 FAT, NTFS, exFAT, ext2/3/4, HFS+ 이고 F2FS 는 목록에 없습니다 [1]. `/data` 가 F2FS 인지 ext4 인지는 기기마다 달라서 실제 기기로 확인합니다. 파일 시스템 구조는 [파일 시스템](../../../01-foundations/storage/filesystems/index.md) 페이지에 있습니다.

## 도구

PhotoRec 은 카빙 도구의 한 예이고, 다른 공개 도구도 서명과 블록을 맞춘다는 원리는 같습니다. 도구마다 알아보는 파일 종류와 조각난 파일을 다루는 방식이 달라서, 한 도구의 결과만으로 "되살릴 파일이 없다" 고 결론 내리지 않습니다. 도구 결과를 검증하는 방법은 [도구 검증](../../reporting/tool-validation.md) 페이지에 있습니다.

## 함정과 한계

카빙으로 되살린 파일에는 이름과 시각이 사라져서 [1], 어느 폴더에 있었는지, 언제 만들고 지웠는지는 파일만으로 알 수 없습니다. 조각난 파일은 앞부분만 열리거나 다른 파일의 블록이 섞여 나올 수 있어서, 결과 파일을 하나씩 열어 보고 깨진 곳을 확인합니다.

암호문 영역에서 나온 결과가 비어 있는 것은 정상이고, 이것만으로 사용자가 데이터를 지웠다거나 지우지 않았다고 말할 수 없습니다. 반대로 암호문 영역을 카빙했는데 서명이 우연히 맞는 조각이 나오면 거짓 결과일 수 있어서, 열어서 내용이 이어지는지 확인합니다.

## 결과를 어떻게 해석하나

되살린 파일은 그 바이트가 이미지의 해당 오프셋에 있었다는 것을 증명합니다. 파일 안에 든 메타데이터(예: 사진의 EXIF)는 파일을 만든 쪽이 적은 값이라 그대로 읽을 수 있지만, 저장 장치에 언제 쓰였고 언제 지워졌는지는 증명하지 못합니다. 같은 파일이 지금도 남아 있는 사본일 수도 있어서, 해시로 현재 파일과 겹치는지 먼저 확인합니다.

보고서에는 "사진을 지웠다" 가 아니라 "SD 카드 이미지의 이 오프셋에서 JPEG 서명으로 시작하는 파일을 되살렸고, 현재 파일 시스템에서 같은 해시의 파일을 찾지 못했다" 처럼 찾은 자리와 대조 결과만 씁니다.
