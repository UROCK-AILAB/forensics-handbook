# SQLite 레코드 되살리기 (SQLite)

## 한 줄 요약

파일은 남아 있고 안의 행만 지운 SQLite 데이터베이스에서, 페이지 안의 빈 공간과 빈 페이지 목록 (freelist), 롤백 저널 (rollback journal), WAL 에 남은 옛 바이트를 찾아 지운 레코드를 다시 읽어 내는 기법입니다.

## 언제 쓰나

앱이 SQLite 에 저장하는 기록에서 사용자가 항목 몇 개를 지웠고, DB 파일은 논리 수집이나 파일 시스템 수집으로 확보했을 때 씁니다. Android 에서는 저장 장치 층의 복구가 암호화와 TRIM 때문에 어렵고(자세한 내용은 [TRIM과 암호화가 주는 한계](trim-encryption.md) 페이지에 있습니다), 실무에서 되살릴 수 있는 곳은 주로 아직 살아 있는 파일 안의 잔재입니다 [1][2][3].

SQLite 파일 형식 전체의 설명은 [SQLite 데이터베이스](../../../01-foundations/data-formats/sqlite/index.md) 페이지에 있고, 이 페이지는 지운 레코드가 남는 자리와 Android 플랫폼 설정이 그 자리를 얼마나 지우는지만 다룹니다. 플랫폼 설정은 현행 AOSP 기준(`platform/external/sqlite` 의 main 가지)이고, 어느 Android 버전부터 그렇게 됐는지는 버전마다 다를 수 있어 검체에서 확인합니다.

## 지운 레코드가 남는 자리

SQLite 파일 안에서 지운 레코드의 바이트가 남을 수 있는 자리는 여섯 곳입니다 [1].

| 자리 | 찾는 법 | 남을 수 있는 것 |
|---|---|---|
| 페이지 안의 할당 안 된 공간 | 셀 포인터 배열이 끝나는 곳부터 셀 내용 영역이 시작하는 곳(페이지 머리말 오프셋 5)까지 | 예전에 셀이 있던 자리의 바이트 |
| freeblock | 페이지 머리말 오프셋 1 에 적힌 첫 freeblock 에서 시작해 체인을 따라감 | 지운 셀 자리의 바이트. 앞 4바이트는 freeblock 머리말 자리 |
| 조각 (fragment) | 셀 내용 영역에 따로 떨어진 1~3바이트 빈 곳. 합계만 페이지 머리말 오프셋 7 에 있음 | 레코드의 아주 작은 조각 |
| freelist 페이지 | DB 머리말 오프셋 32 의 첫 trunk 페이지에서 시작 | 통째로 비운 페이지의 옛 내용 |
| 롤백 저널 | 같은 폴더의 `<DB 이름>-journal` | 고치기 전 페이지의 원본 |
| WAL | 같은 폴더의 `<DB 이름>-wal`, 색인은 `<DB 이름>-shm` | 같은 페이지의 여러 판, 지난 체크포인트의 남은 프레임 |

freeblock 은 페이지 안의 빈 조각을 잇는 체인입니다. 첫 2바이트에 다음 freeblock 의 오프셋(마지막이면 0)을, 다음 2바이트에 이 4바이트 머리말을 포함한 크기를 적고, 가장 작은 freeblock 이 4바이트입니다 [1]. 머리말 4바이트가 들어선 자리에는 원래 바이트가 남지 않습니다.

freelist 는 trunk 페이지를 이은 목록입니다. trunk 페이지의 첫 4바이트는 다음 trunk 페이지 번호이고, 다음 4바이트는 뒤따르는 leaf 페이지 번호의 개수입니다. SQLite 는 leaf 페이지에 정보가 없다고 보고 읽지도 쓰지도 않아서, secure_delete 가 꺼져 있으면 leaf 페이지에 예전 내용이 그대로 남을 수 있습니다 [1][2].

롤백 저널에는 DB 페이지를 고치기 전에 그 페이지의 원래 내용을 먼저 적습니다. 저널 머리의 매직은 `d9 d5 05 f9 20 a1 63 d7` 이고, 페이지 레코드는 페이지 번호(4바이트), 원래 페이지 내용, 체크섬(4바이트) 순서입니다 [1].

WAL 은 32바이트 머리말 뒤에 프레임이 이어지는 파일이고, 프레임 하나는 24바이트 프레임 머리말과 페이지 한 장으로 이뤄집니다. WAL 은 앞에서 뒤로만 자라서 같은 페이지의 여러 판이 프레임으로 겹쳐 있을 수 있고, 체크포인트 뒤에는 새 프레임이 앞에서부터 옛 프레임을 덮어서 파일 뒤쪽에 옛 프레임이 남을 수 있습니다 [1]. WAL 모드는 한 번 켜면 연결을 닫았다 다시 열어도 DB 에 남습니다 [2].

## 읽을 때 쓰는 값

모든 정수는 빅엔디언입니다 [1].

| 자리 | 오프셋 | 크기 | 뜻 |
|---|---|---|---|
| DB 머리말 (100바이트) | 16 | 2 | 페이지 크기(512~65536, 2의 거듭제곱) |
| | 24 | 4 | 파일 변경 카운터 |
| | 28 | 4 | 페이지 수 |
| | 32 | 4 | 첫 freelist trunk 페이지 번호(없으면 0) |
| | 36 | 4 | freelist 페이지 총수 |
| | 52 | 4 | auto-vacuum 용 가장 큰 루트 페이지 번호(auto-vacuum 이 아니면 0) |
| | 64 | 4 | incremental vacuum 여부 |
| B-tree 페이지 머리말 (8 또는 12바이트) | 0 | 1 | 페이지 종류(2 내부 인덱스, 5 내부 테이블, 10 리프 인덱스, 13 리프 테이블) |
| | 1 | 2 | 첫 freeblock 오프셋 |
| | 3 | 2 | 셀 수 |
| | 5 | 2 | 셀 내용 영역 시작(0 이면 65536) |
| | 7 | 1 | 조각난 빈 바이트 수 |
| | 8 | 4 | 내부 페이지의 오른쪽 끝 포인터 |

페이지 안은 (1번 페이지만) 100바이트 DB 머리말, 페이지 머리말, 셀 포인터 배열, 할당 안 된 공간, 셀 내용 영역, 예약 영역 순서로 놓입니다 [1].

레코드는 머리말 길이 varint 로 시작하고, 칸마다 serial type varint 가 이어진 뒤 본문이 옵니다. 지운 레코드를 빈 공간에서 찾을 때는 이 serial type 이 이어지는 모양을 단서로 씁니다 [1].

| serial type | 본문 |
|---|---|
| 0 | NULL(본문 없음) |
| 1~6 | 정수. 1·2·3·4·6·8바이트 |
| 7 | 실수 8바이트 |
| 8, 9 | 상수 0, 1(본문 없음) |
| 12 이상 짝수 | BLOB, (N-12)/2 바이트 |
| 13 이상 홀수 | TEXT, (N-13)/2 바이트 |

## Android 플랫폼 SQLite 의 기본 설정

Android 프레임워크가 쓰는 플랫폼 SQLite 라이브러리는 빌드 파일(`dist/Android.bp`)에서 컴파일 옵션으로 기본값을 바꿉니다 [3]. 복구와 관계있는 옵션은 아래와 같습니다(현행 AOSP 기준).

| 컴파일 옵션 | SQLite 기본값 | 복구에 주는 영향 |
|---|---|---|
| `-DSQLITE_SECURE_DELETE` | secure_delete 꺼짐 | 플랫폼 라이브러리로 연 DB 는 secure_delete 가 기본으로 켜져서, 지운 내용을 0 으로 덮음 [2][3] |
| `-DSQLITE_DEFAULT_AUTOVACUUM=1` | auto_vacuum 0(NONE) | 새로 만든 DB 가 FULL 이 되어, 커밋마다 freelist 페이지를 파일 끝으로 옮기고 잘라 냄 [2][3] |
| `-DSQLITE_DEFAULT_JOURNAL_SIZE_LIMIT=1048576` | -1(한도 없음) | 커밋하거나 WAL 을 리셋할 때 저널·WAL 파일이 1MiB 보다 크면 1MiB 까지 잘라 냄 [2][3] |
| `-DSQLITE_TEMP_STORE=3` | — | 임시 파일을 모두 RAM 에 둠 [3] |
| `-DSQLITE_ENABLE_FTS3`·`FTS3_BACKWARDS`·`FTS4` | — | 전문 검색 가상 테이블을 쓸 수 있음 [3] |

그래서 플랫폼 기본값 그대로 만든 DB 는 페이지 안의 지운 내용이 0 으로 덮이고 빈 페이지도 커밋마다 파일에서 잘려 나가며, 흔적이 남기 쉬운 곳은 WAL 쪽입니다. 롤백 저널은 저널 모드에 따라 달라서, DELETE 모드는 트랜잭션이 끝날 때마다 저널 파일을 지우고 TRUNCATE 모드는 길이 0 으로 잘라 내며, PERSIST 모드만 머리말을 0 으로 덮고 파일을 남깁니다 [2]. 그래서 DELETE·TRUNCATE 모드의 DB 에서는 저널 파일 안에 옛 페이지가 남지 않습니다. secure_delete 는 일반 테이블에만 작동하고, 가상 테이블이 shadow 테이블에 저장하는 경우(FTS 등)에는 가상 테이블에서 지워도 shadow 테이블에 흔적이 남을 수 있습니다 [2]. 플랫폼 라이브러리가 FTS3·FTS4 를 켜 두었기 때문에, 검색 색인 테이블이 있는 DB 는 따로 살펴봅니다.

예외도 있습니다. SQLCipher 같은 암호화 SQLite 처럼 앱이 자기 SQLite 라이브러리를 따로 넣으면 이 컴파일 옵션을 따르지 않고, 앱이 PRAGMA 로 secure_delete 와 auto_vacuum 을 바꿀 수도 있습니다 [2][3]. auto_vacuum 은 테이블을 만들기 전에만 정할 수 있고 나중에 바꾸려면 VACUUM 이 필요해서, 기본값이 바뀌기 전에 만든 오래된 DB 는 NONE 일 수 있습니다 [2]. 앱마다 설정이 다를 수 있으므로, 플랫폼 기본값만 보고 판단하지 말고 DB 머리말을 직접 읽어 확인합니다. 머리말 오프셋 52 가 0 이 아니면 auto-vacuum 이 켜진 DB 이고, 오프셋 64 로 incremental 인지 가립니다 [1]. DB 머리말에는 secure_delete 를 적는 칸이 없어서, 파일만 보고 켜져 있었는지 판단할 수 없습니다 [1].

`settings global` 에 `sqlite_compatibility_wal_flags` 키가 있는 기기도 있습니다. 이 키가 무엇을 조절하는지와 플랫폼의 기본 저널 모드는 공개된 분석 자료가 없어 검체로 확인해야 합니다.

## 절차

1. **DB 와 딸린 파일을 함께 확보합니다.** 저널과 WAL, WAL 색인은 DB 이름 뒤에 `-journal`, `-wal`, `-shm` 을 붙인 이름으로 같은 폴더에 있습니다 [1]. 세 파일이 있으면 모두 함께 복사하고, 이후 작업은 사본으로 합니다.
2. **DB 머리말을 읽습니다.** 페이지 크기(오프셋 16), 첫 freelist trunk 페이지(32), freelist 페이지 총수(36), auto-vacuum 여부(52, 64)를 적어 둡니다. auto-vacuum 이 FULL 이면 freelist 가 비어 있는 경우가 많고, 이때는 저널과 WAL 에 무게를 둡니다.
3. **freelist 를 따라갑니다.** trunk 페이지에서 다음 trunk 번호와 leaf 번호 배열을 읽어 leaf 페이지 목록을 만들고, 각 leaf 페이지를 B-tree 페이지로 읽어 봅니다.
4. **페이지마다 빈 공간을 훑습니다.** 페이지 머리말에서 첫 freeblock 오프셋, 셀 수, 셀 내용 영역 시작, 조각 바이트 수를 읽습니다. freeblock 체인과 할당 안 된 공간을 모두 뽑아 냅니다.
5. **레코드 모양을 맞춥니다.** 뽑은 바이트에서 머리말 길이 varint 뒤에 serial type 이 이어지는 자리를 찾고, 살아 있는 테이블의 칸 수·칸 종류와 맞는지 확인합니다.
6. **저널과 WAL 을 읽습니다.** 저널에서는 페이지 번호별로 고치기 전 페이지를 꺼냅니다. WAL 에서는 프레임마다 salt 가 WAL 머리말과 같은지, 누적 체크섬이 맞는지 확인해서 현재 유효한 프레임과 지난 체크포인트에서 남은 프레임을 가려냅니다 [1]. 같은 페이지 번호의 프레임이 여럿이면 판마다 레코드를 비교합니다.
7. **되살린 레코드의 자리를 적습니다.** 파일 이름, 페이지 번호, 페이지 안 오프셋, 어느 자리(freeblock·freelist·저널·WAL 프레임 번호)에서 나왔는지를 레코드와 함께 기록합니다.

## 헥스로 따라가기

아래는 명세 [1] 에 맞춰 만든 예시이고, 실제 검체에서 뽑은 값이 아닙니다.

DB 머리말의 오프셋 0x20(32)부터 8바이트와 0x34(52)부터 4바이트입니다.

```
0x20: 00 00 00 05  00 00 00 02    첫 freelist trunk 페이지 5, freelist 페이지 총 2장
0x34: 00 00 00 00                 가장 큰 루트 페이지 번호 0 → auto-vacuum 아님
```

페이지 크기가 4096바이트인 DB 의 어느 리프 테이블 페이지 머리말과, 그 페이지의 첫 freeblock 입니다.

```
페이지 머리말 0x000: 0d 00 0f 40 00 03 0f 10 00
                     0d       페이지 종류 13(리프 테이블)
                     0f 40    첫 freeblock 오프셋 0x0f40
                     00 03    셀 3개
                     0f 10    셀 내용 영역 시작 0x0f10
                     00       조각 바이트 0
freeblock   0xf40:   0f 80 00 18
                     0f 80    다음 freeblock 오프셋 0x0f80
                     00 18    이 freeblock 크기 24바이트(머리말 4바이트 포함)
```

0x0f44 부터 20바이트가 지운 셀의 남은 바이트이고, 여기서 아래 같은 레코드 모양을 찾습니다(셀 앞쪽의 길이·rowid 는 빼고 레코드 부분만 적었습니다).

```
04 01 19 08  2a  68 65 6c 6c 6f 21
04           레코드 머리말 길이 4바이트
01           칸 1: 1바이트 정수
19           칸 2: serial type 25 → TEXT (25-13)/2 = 6바이트
08           칸 3: 상수 0
2a           칸 1 값 42
68 … 21      칸 2 값 "hello!"
```

WAL 파일 머리말의 앞 12바이트입니다.

```
37 7f 06 82  00 2d e2 18  00 00 10 00
             매직 0x377f0682, 형식 버전 3007000, 페이지 크기 4096
```

## 도구

지운 레코드를 찾아 주는 공개 도구로 FQLite, Undark 등이 있고, 도구마다 freeblock·freelist·저널·WAL 중 읽는 범위가 다를 수 있습니다. 도구를 쓰기 전에 지운 행이 어디에 남는지 알고 있는 시험용 DB 를 만들어 도구 결과와 맞춰 보고, 그 방법은 [도구 검증](../../reporting/tool-validation.md) 페이지에 있습니다. 도구가 찾아 준 레코드는 위의 헥스 절차로 한 건 이상 직접 확인합니다.

## 함정과 한계

플랫폼 기본값으로 만든 DB 에서는 결과가 비어 나오는 것이 흔하고, 결과가 비었다고 해서 지운 기록이 없었다는 뜻이 되지는 않습니다. secure_delete 로 0 이 된 자리와 auto_vacuum 으로 잘려 나간 페이지에는 되살릴 바이트가 남지 않습니다. secure_delete 에는 FAST 설정도 있는데, I/O 가 늘지 않을 때만 0 으로 덮어서 B-tree 페이지의 옛 내용은 지우지만 freelist 페이지에는 흔적이 남습니다 [2].

저널과 WAL 은 크기가 1MiB 를 넘으면 커밋이나 WAL 리셋 때 잘려 나가고(플랫폼 기본값), WAL 은 체크포인트 뒤 앞에서부터 다시 덮어 쓰기 때문에 오래된 프레임일수록 남을 가능성이 낮습니다 [1][2][3].

저널의 옛 페이지와 WAL 의 옛 프레임에서 나온 행은 지운 행일 수도 있지만, 값을 고치기 전의 판일 수도 있습니다. 같은 rowid 의 행이 현재 테이블에 살아 있는지 먼저 확인하고, 살아 있으면 "삭제" 가 아니라 "이전 값" 으로 다룹니다.

freeblock 의 앞 4바이트와 1~3바이트 조각에는 온전한 레코드가 남지 않아서, 레코드 머리가 잘린 채로 나오는 경우가 있습니다. 이때 칸 경계를 추정해서 채운 값은 추정이라고 표시합니다.

## 결과를 어떻게 해석하나

되살린 레코드는 그 바이트가 한때 이 DB 파일의 해당 자리에 있었다는 것을 증명합니다. 저널에서 나왔다면 그 페이지를 고치기 전 내용이었다는 것까지 말할 수 있습니다 [1].

언제 지웠는지, 누가 어떤 동작으로 지웠는지는 증명하지 못합니다. 앱이 오래된 항목을 스스로 정리했을 수도 있고 사용자가 지웠을 수도 있어서, 삭제 동작은 앱 사용 기록 같은 다른 기록과 맞춰 봅니다. 레코드 안에 시각 칸이 있으면 그 시각은 레코드가 만들어지거나 고쳐진 때를 가리킬 뿐 지운 때가 아니고, 시각 값을 읽는 법은 [시각 값](../../../01-foundations/value-decoding/time-values.md) 페이지에 있습니다.

보고서에는 "메시지를 지웠다" 가 아니라 "이 DB 의 WAL 프레임 12에 담긴 페이지 판에 현재 테이블에 없는 행이 있고, 그 행의 내용은 다음과 같다" 처럼 나온 자리와 내용만 씁니다(프레임 번호는 예시입니다). 앱별 DB 의 해석은 [앱 데이터 분석](../app-data-analysis/index.md) 과 각 앱 페이지에 있습니다.
