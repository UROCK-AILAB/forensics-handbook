# 네이버 지도 (NAVER Map)

네이버 지도 (NAVER Map, 패키지 com.nhn.android.nmap) 는 주요 데이터베이스 파일을 암호화해 저장하고, 그 암호 키(passphrase)를 안드로이드 키 저장소 (Android Keystore) 에 보관합니다 [2][3]. 그래서 같은 국내 지도 앱인 [티맵 (TMAP)](tmap.md) 이나 [카카오맵 (KakaoMap)](kakaomap.md) 과 달리 앱 폴더를 복사해도 주요 DB 를 SQLite 로 바로 열 수 없고, 공개 도구 ALEAPP 에도 이 앱을 읽는 모듈이 없습니다 [1][2].

## 무엇을 기록하나 · 왜 생기나

지도 앱을 쓰면 사용자가 이동한 경로와 목적지의 위치 정보가 시간 정보와 함께 남고, 이 기록으로 사용자가 언제 어디로 가려 했는지를 추적할 수 있습니다 [2]. 네이버 지도의 암호화된 주요 DB 안에도 위치 정보와 관련된 기록이 들어 있습니다 [2].

앱 화면은 발견, 예약, 대중교통, 내비게이션, 저장 탭으로 나뉩니다 [3]. 검색창 하나로 장소·버스·지하철·주소를 찾고, 관심 장소를 지도 위에 저장해 친구와 공유하며, "MY" 에서는 지도·리뷰·예약과 관련된 사용자 기록을 모아 봅니다 [3]. 이 기능 목록은 어떤 흔적을 찾아볼지 정하는 데 쓰고, 기기에 그 기록이 파일로 남았다는 근거로 쓰지 않습니다. 저장한 장소나 리뷰처럼 친구와 공유하는 기록은 네이버 계정 쪽에도 남아 있을 가능성이 있습니다.

## 위치와 버전별 차이

| 항목 | 내용 | 근거 |
|---|---|---|
| 패키지 이름 | com.nhn.android.nmap, 개발자 NAVER Corp. | Play 상세 페이지 [3] |
| 지원 Android 버전 | 앱 v5.0 은 Android 8.0 이상 | Play 상세 페이지 [3] |
| 주요 DB 파일 | 암호화해 저장, 암호 키는 키 저장소에 보관 | 2022년 분석 [2] |
| DB 파일 이름·표·열 | 앱 판마다 바뀔 수 있어 실제 데이터로 확인(아래 절차) | — |
| ALEAPP 전용 모듈 | 없음(2026-09-28 main 가지의 모듈 목록 기준) | [1] |

암호화 여부는 2022년 논문이 그 무렵의 앱을 분석한 결과라서 [2], 다른 판을 다룰 때는 아래 "구조" 절의 3단계처럼 파일 앞머리를 보고 다시 확인합니다. 앱 v6.3 부터는 통화 기록과 SMS 권한을 쓰지 않아서 [3], 같은 앱이라도 판에 따라 남는 흔적이 달라질 수 있습니다.

앱 데이터 영역은 루팅되지 않은 기기에서 adb 일반 권한으로 읽을 수 없는 곳이고, 짜임새는 [앱 데이터 폴더 구조](../../01-foundations/storage/app-data-layout.md) 페이지에서 다룹니다. 앱 폴더 밖의 [공용 저장 공간 (Shared Storage·/sdcard)](../../01-foundations/storage/shared-storage.md) 도 함께 살핍니다.

## 구조 — 직접 찾는 절차

DB 파일 이름과 표 구조는 기기마다 아래 순서로 직접 확인해 기록합니다. 일반 절차는 [앱 데이터 분석 (App Data Analysis)](../../03-techniques/analysis/app-data-analysis/index.md) 페이지에 있습니다.

1. 설치된 앱 목록에서 com.nhn.android.nmap 을 찾고, 그 APK 의 앱 이름과 서명자를 확인해 네이버 지도가 맞는지 확인합니다. 앱 목록은 [설치된 앱 (packages.xml)](../app-usage/packages/index.md), APK 이름과 서명 읽기는 [APK 정보 (AndroidManifest·서명)](../embedded-metadata/apk.md) 페이지에서 다룹니다.
2. 그 패키지의 앱 데이터 폴더에서 `databases`, `shared_prefs`, `files`, `cache` 같은 하위 폴더를 살펴보고, 파일마다 크기와 수정 시각을 적어 둡니다.
3. 파일 앞머리 바이트로 형식을 구분합니다. 평문 SQLite 는 맨 앞 16바이트가 `SQLite format 3\000` 입니다. `databases` 안의 파일인데 이 문자열이 없고 앞머리부터 무작위 데이터처럼 보이면 암호화된 DB 일 가능성이 있습니다. 암호화된 SQLite 를 알아보는 법은 [암호화된 SQLite (SQLCipher)](../../01-foundations/data-formats/sqlite/sqlcipher.md) 페이지에 있습니다.
4. 평문으로 열리는 SQLite 파일이면 표 목록을 뽑고, 이름이나 열에 검색어·장소 이름·좌표·시각이 들어 있을 만한 표를 고릅니다. 열 이름은 `PRAGMA table_info` 로 확인합니다.
5. 고른 표에서 좌표로 보이는 열과 시각으로 보이는 열을 찾아 아래 "시각 해석" 과 "직접 분석해 보기" 대로 단위를 판별합니다.
6. 앱 안에서 직접 검색·저장·길찾기를 해 본 시험 기기와 비교해, 어느 표가 어느 동작 때 바뀌는지 확인한 뒤에야 보고서에 표의 뜻을 씁니다.

키 저장소는 키를 기기 밖으로 꺼내기 어렵게 만든 시스템이라서, 앱 폴더 복사본만으로는 암호화된 DB 의 내용을 읽기 어렵습니다. 키 저장소의 성격은 [키 저장소와 보안 하드웨어 (Keystore·TEE·StrongBox)](../../01-foundations/storage/encryption/keystore-tee.md) 페이지에서 다룹니다. 이런 DB 는 "암호화된 DB 파일이 있고 크기와 수정 시각이 이렇다" 까지만 보고서에 씁니다.

6단계를 거치지 않은 해석은 "이 표에 이런 값이 있다" 까지만 씁니다. 시험 기기를 이용해 도구와 해석을 확인하는 방법은 [도구 검증 (Tool Validation)](../../03-techniques/reporting/tool-validation.md) 페이지에 있습니다.

## 증거로서 의미

**증명하는 것**

6단계까지 확인한 표라면, 검색 기록은 그 시각에 앱에서 무엇을 찾아봤는지, 저장한 장소는 어떤 장소를 저장했는지, 길찾기 기록은 어디로 가는 길을 찾았는지를 알려 줄 수 있습니다. 6단계를 거치지 않은 표는 "이 앱 폴더에 이런 문자열과 좌표가 있다" 는 사실만 증명합니다. 암호화된 DB 파일의 수정 시각으로는 그 무렵 앱이 DB 에 무언가를 썼다는 것까지 알 수 있습니다.

**증명하지 못하는 것**

검색하거나 길을 찾은 기록은 그곳에 실제로 갔다는 증거가 아닙니다. 저장한 장소는 계정 동기화로 다른 기기에서 넘어왔을 수도 있으니, 이 기기에서 저장했다고 단정하지 않습니다. 평문 파일에 기록이 없다는 사실도 앱을 쓰지 않았다는 뜻이 아니고, 위치 기록이 암호화된 DB 에만 들어 있을 수 있습니다 [2].

## 시각 해석

시각 필드의 단위는 파일마다 다를 수 있으니, 값의 자릿수로 먼저 어림합니다. 요즘 날짜를 유닉스 시각으로 적으면 초는 10자리, 밀리초는 13자리, 마이크로초는 16자리쯤 됩니다. 자릿수로 고른 단위로 바꾼 날짜가 앱 설치 시각과 수집 시각 사이에 들어오는지 맞춰 보고, 문자열로 적힌 날짜라면 시간대 표기가 붙어 있는지 확인합니다. 유닉스 시각은 UTC 기준이라서 보고서에는 현지 시각으로 옮겨 적습니다. 값을 바꾸는 법은 [시각 값](../../01-foundations/value-decoding/time-values.md), 현지 시각으로 옮기는 기준은 [시간대와 시각 설정 (Time Zone)](../system-account/time-zone.md) 페이지에 있습니다.

암호화된 DB 파일은 안의 시각 값을 읽을 수 없으니, 파일 시스템의 수정 시각만 씁니다. 이 시각은 앱이 DB 에 마지막으로 쓴 때이고, 사용자가 마지막으로 검색한 때와 같다고 볼 수 없습니다.

## 함정과 한계

첫째, 공개 도구 결과에 네이버 지도 항목이 없다고 해서 기록이 없는 것이 아닙니다. ALEAPP 에는 이 앱을 읽는 모듈이 없고 [1], 주요 DB 는 암호화돼 있어서 [2] 범용 SQLite 도구로는 열리지 않습니다.

둘째, 인터넷에 떠도는 파일 이름이나 표 이름을 확인 없이 옮기지 않습니다. 앱 판마다 저장 방식이 바뀔 수 있습니다.

셋째, 네이버 앱이나 네이버 계정을 쓰는 다른 앱에서 지도를 연 기록은 네이버 지도 앱 폴더에 없을 수 있습니다. 네이버 앱 쪽은 [네이버 앱 (NAVER)](../browsers/naver.md) 페이지에서 다룹니다.

넷째, 서버에 남는 기록은 기기 분석으로 얻을 수 없습니다. 클라우드 쪽 확보 절차는 [클라우드 데이터 (Google Takeout 등)](../../03-techniques/acquisition/cloud-data.md) 페이지에서 다룹니다.

## 직접 분석해 보기

### 헥스로 한 번

위 3단계에서 파일을 헥스 편집기로 열어 앞머리를 보고 형식을 구분합니다. 형식별 앞머리 모양은 [SQLite 데이터베이스](../../01-foundations/data-formats/sqlite/index.md), [설정 XML과 SharedPreferences](../../01-foundations/data-formats/shared-preferences.md), [프로토콜 버퍼 (Protocol Buffers)](../../01-foundations/data-formats/protobuf.md), [LevelDB와 IndexedDB](../../01-foundations/data-formats/leveldb-indexeddb.md) 페이지에 있습니다.

평문 파일에서 좌표 필드로 보이는 정수가 있으면, 국내 좌표인지로 단위를 판별할 수 있습니다. 아래는 계산으로 만든 예시이고 실제 기기에서 나온 값이 아닙니다.

```
37566500     → ÷ 10^6 = 37.566500    (E6 로 읽으면 국내 위도 범위)
375665000    → ÷ 10^7 = 37.5665000   (E7 로 읽으면 국내 위도 범위)
37.5665      → 실수 그대로 도 단위
```

같은 필드의 값을 여러 개 바꿔 봤을 때 국내 위도(대략 33~39도)와 경도(대략 124~132도) 안으로 들어오는 나눗수가 그 필드의 단위일 가능성이 높지만, 도 단위가 아닌 다른 좌표계일 수도 있어서 시험 기기로 확인합니다.

### 공개 도구로 한 번

전용 모듈이 없으니 SQLite 브라우저나 프로토콜 버퍼 디코더 같은 범용 도구로 평문 파일을 하나씩 엽니다. 여러 파일에서 좌표·검색어를 한꺼번에 찾을 때는 [콘텐츠 검색 (Content Search)](../../03-techniques/analysis/content-search.md) 방법을 씁니다. 암호화된 DB 안의 문자열은 이 검색에 걸리지 않으니, 검색 결과가 없다고 기록이 없다고 판단하지 않습니다.

## 실습

공개 이미지에 네이버 지도가 들어 있는 경우는 드물 수 있으니, 필요하면 직접 준비한 시험 기기로 풀어 봅니다.

1. 설치된 앱 목록에서 com.nhn.android.nmap 의 앱 이름과 서명자는 무엇이고, 앱 버전은 몇입니까?
2. 그 패키지의 `databases` 폴더에서 맨 앞 16바이트가 `SQLite format 3\000` 인 파일과 아닌 파일은 각각 몇 개입니까?
3. 시험 기기에서 장소 하나를 검색한 전후로 어느 파일의 크기나 수정 시각이 바뀌었고, 그 파일은 평문입니까, 암호화돼 있습니까?
4. 평문 파일에서 시각으로 보이는 필드의 자릿수로 단위를 어림한 뒤, 바꾼 시각이 실제로 검색한 시각과 맞습니까?
