# 흐름 기록 분석 (nfdump)

라우터·방화벽·스위치가 내보낸 흐름 기록 (flow record) 에는 패킷 내용이 없지만, 어느 주소와 포트 사이에 언제 얼마만큼 오갔는지가 긴 기간에 걸쳐 남습니다. 이 페이지는 nfdump 로 흐름 파일을 시간과 주소로 거르고, 쪼개진 기록을 합치고, 상위 통계를 뽑아 보고서에 쓸 수 있는 만큼만 해석하는 절차를 다룹니다. NetFlow·IPFIX·sFlow 형식 자체는 [흐름 기록](../../01-foundations/records/flow-records.md) 페이지에 있습니다.

## 언제 쓰나

흐름 기록은 패킷 내용을 담지 않아 같은 기간의 캡처보다 훨씬 작으므로, 캡처보다 오래 보관할 수 있습니다. 그래서 캡처가 없는 기간에 특정 내부 PC 가 어느 외부 주소와 통신했는지, 사건 전후로 평소보다 많이 보냈는지, 같은 외부 주소에 여러 PC 가 붙었는지를 확인할 때 흐름 기록부터 봅니다.

nfdump 는 nfcapd(NetFlow v1·v5/v7·v9·IPFIX 수집기), sfcapd(sFlow 수집기), nfpcapd(패킷에서 흐름을 만드는 도구)가 만든 바이너리 파일을 읽습니다[1][2][3]. 조사 대상 조직이 다른 수집기를 쓰면 그 제품의 내보내기 기능으로 CSV 를 받아 같은 절차를 따르면 되고, 이 페이지의 판단 기준(시각의 뜻, 샘플링, 쪼개진 흐름)은 그대로 적용됩니다. 캡처 파일만 있고 흐름 기록이 없으면 nfpcapd 로 캡처에서 흐름 파일을 만들어 같은 방법으로 볼 수 있습니다(4단계 끝 참고).

## 절차

아래 명령은 nfdump 1.7.10 설명서 기준입니다[1]. 경로·주소·시각은 모두 만든 예시입니다.

1. **수집 조건부터 확인합니다.** 흐름 파일은 수집기가 정해진 간격마다 새 파일로 바꿔 가며 저장하는데, 기본 간격은 300초이고 이름은 `nfcapd.YYYYMMddhhmm` 형식입니다[2]. 예를 들어 `nfcapd.202609150900` 은 2026-09-15 09:00 부터 받은 흐름이 든 파일입니다(만든 예시). 수집기를 `-Z` 로 띄우면 파일 이름 끝에 현지 시간대 오프셋이 붙습니다[2]. 수집기를 `-e` 로 띄우면 간격이 끝날 때마다 nfexpire 에 정한 최대 보존 기간·최대 용량에 따라 파일을 지우므로[2], 보존 기간 밖의 파일이 없는 것은 통신이 없었다는 뜻이 아닙니다. 파일이 온전한지와 내보낸 장비 목록은 아래처럼 확인합니다.

   ```
   nfdump -r /evidence/flows -I                   # 파일 하나의 흐름 통계, 폴더면 전체 요약
   nfdump -v /evidence/flows/nfcapd.202609150900  # 파일 일관성 검사와 레코드 수
   nfdump -E /evidence/flows/nfcapd.202609150900  # 내보낸 장비·샘플러 목록, 장비별 순서 오류 수
   ```

   `-E` 결과의 순서 오류 (sequence errors) 는 장비가 보낸 내보내기 패킷 일부를 수집기가 받지 못했다는 뜻이라서, 그 장비의 기록에 빠진 부분이 있을 수 있습니다[1][4]. 샘플러 목록이 나오면 샘플링 환경이므로 5단계의 양을 해석할 때 따로 봅니다.

2. **시간 범위로 거릅니다.** 옛 옵션 `-t` 대신 `first seen`·`last seen` 필터를 씁니다[1]. 시각은 ISO8601 형식으로 밀리초까지 적을 수 있고, `2026-09-15T09` 처럼 뒤를 생략하면 `2026-09-15T09:00:00.000` 으로 채워집니다(연도는 꼭 있어야 합니다)[1].

   ```
   nfdump -r /evidence/flows 'last seen >= 2026-09-15T09:00:00 and first seen <= 2026-09-15T10:00:00'
   ```

   `first seen >= 시작 and last seen <= 끝` 으로 쓰면 창 안에서 시작하고 끝난 흐름만 남아, 시작 전에 열려 창 안까지 이어진 긴 흐름이 빠집니다. 조사 창과 조금이라도 겹치는 흐름을 모두 보려면 위처럼 "끝난 시각이 창 시작 뒤, 시작한 시각이 창 끝 앞" 으로 씁니다. 필터에 적은 시각을 UTC 로 읽는지 분석 PC 의 현지 시각으로 읽는지는 시각을 아는 레코드 하나로 확인합니다. 그 레코드를 6단계의 `%tsr`(epoch 초)와 함께 뽑고, 시각 필터를 걸었을 때 걸리는지 맞춰 봅니다.

   `-r` 에 폴더를 주면 하위 폴더까지 모두 읽되 운영체제가 나열하는 순서로 처리하고, 옛 옵션 `-R` 은 알파벳 순서로 읽습니다[1]. 시각 순서가 중요하면 결과를 `-O tstart` 로 정렬합니다[1].

3. **관심 주소와 포트로 좁힙니다.** 필터 문법은 tcpdump 와 비슷하고 키워드는 대소문자를 구분하지 않습니다[1]. 자주 쓰는 요소는 다음과 같습니다[1].

   | 필터 | 뜻 |
   |---|---|
   | `host 10.0.5.23`, `src ip ...`, `dst ip ...` | 출발지나 목적지 IP(`host` 는 `ip` 와 같은 뜻) |
   | `ip in [ 203.0.113.10, 198.51.100.0/24 ]` | IP·CIDR 목록. 주소가 수백~수천 개면 `or` 로 잇는 것보다 빠름 |
   | `net 10.0.5.0/24` | 네트워크 대역 |
   | `dst port 443`, `port in [ 22, 3389 ]` | 포트 비교와 목록 |
   | `proto tcp`, `flags S and not flags AFRPU` | 프로토콜, TCP 플래그(A·S·F·R·P·U, X 는 전부) |
   | `bytes > 100M`, `packets > 1k`, `duration > 60000` | 양과 지속 시간(지속 시간은 밀리초, K·M·G·T 배율 사용 가능) |
   | `router ip 192.0.2.1` | 기록을 보낸 장비 |

   침해 지표 주소가 많으면 필터를 파일로 만들어 `-f` 로 넘깁니다. 파일 안에서는 `#` 뒤가 주석이고 `@include` 로 다른 파일을 끌어올 수 있으며, 명령줄에 필터를 함께 적으면 파일보다 명령줄 필터가 우선합니다[1].

4. **쪼개진 기록을 합칩니다.** 장비는 오래 이어지는 흐름을 일정 시간마다 중간에 내보내므로[4], 연결 하나가 여러 레코드로 나뉘어 있습니다. `-a` 는 프로토콜·출발지 IP·목적지 IP·출발지 포트·목적지 포트 다섯 값이 같은 레코드를 합치고, `-A` 로 합치는 기준을 바꿀 수 있습니다[1]. `-b` 는 방향이 반대인 두 흐름까지 한 레코드로 합쳐 들어온 양과 나간 양을 따로 보여 줍니다[1].

   ```
   nfdump -r /evidence/flows -b -O tstart 'host 10.0.5.23 and host 203.0.113.10'
   nfdump -r /evidence/flows -a -A srcip,dstip -P 'bytes > 100M' 'src net 10.0.0.0/8'
   ```

   `-P` 는 합치거나 통계를 낸 뒤에 거르는 필터라서, 두 번째 명령은 "내부 주소에서 한 목적지로 합계 100MB 넘게 보낸 쌍" 만 남깁니다[1]. 흐름 수(`%fl`)는 장비가 따로 보내지 않으면 받은 레코드마다 1이고 합칠 때마다 더해지므로, 합쳐진 레코드 개수이지 연결 수가 아닙니다[1].

   캡처 파일만 있으면 `nfpcapd -r 캡처파일 -w 폴더` 로 흐름 파일을 만듭니다. 이때 읽을 수 있는 것은 마이크로초 단위의 옛 pcap 형식뿐이고 pcapng 와 나노초 pcap 은 읽지 못합니다[3]. 형식 변환은 [큰 캡처 파일 다루기](../acquisition/large-captures.md) 페이지를 봅니다. nfpcapd 의 기본 만료 값은 활성 300초·비활성 60초(`-e 300,60`)입니다[3].

5. **상위 통계를 뽑습니다.** `-s` 로 원하는 요소의 상위 N 개를 보고, `/bytes` 처럼 정렬 기준을 붙입니다. 정렬 기준을 주지 않으면 흐름 수로 정렬하고, 기본으로 10개를 보여 주며 `-n 0` 이면 제한이 없습니다[1].

   ```
   nfdump -r /evidence/flows -s dstip/bytes -n 20 'src ip 10.0.5.23'
   nfdump -r /evidence/flows -s record/bytes -A srcip,dstip
   nfdump -r /evidence/flows -s dstport:p/flows
   ```

   첫 번째는 한 PC 가 가장 많이 보낸 목적지, 두 번째는 가장 많이 주고받은 IP 쌍, 세 번째는 전송 프로토콜별로 나눈 목적지 포트 순위입니다[1]. 흐름 기록에 JA3·JA4 값이 들어 있으면 `-s ja3`·`-s ja4` 로도 묶을 수 있습니다[1]. 지문의 뜻은 [TLS 지문](../../02-artifacts/fingerprints/ja3-ja4.md) 페이지에 있습니다.

6. **결과를 내보냅니다.** 보고서나 다른 도구로 넘길 때는 시각을 epoch 로 함께 뽑아 두면 시간대 혼동이 없습니다[1].

   ```
   nfdump -r /evidence/flows -N -O tstart -o 'csv:%tsr,%ter,%trr,%pr,%sa,%sp,%da,%dp,%pkt,%byt,%fl' 'host 10.0.5.23'
   ```

   `-N` 은 단위를 붙이지 않은 숫자를 찍고, `-o json` 은 JSON 배열, `-o ndjson` 은 한 줄에 객체 하나를 씁니다[1]. 기본 출력 형식(`line`)은 IPv6 주소를 16자로 줄여 보여 주므로 전체 주소가 필요하면 `-6` 을 붙입니다[1]. 거른 결과를 `-w` 로 바이너리 파일에 저장해 두면 같은 부분 집합을 다시 nfdump 로 읽을 수 있습니다[1].

## 도구

| 도구 | 하는 일 |
|---|---|
| nfdump | 흐름 파일 읽기, 거르기, 합치기, 통계, 형식 변환[1] |
| nfcapd | NetFlow v1·v5/v7·v9·IPFIX 수신과 파일 저장, 기본 UDP 9995[2] |
| sfcapd | sFlow 수신[2] |
| nfpcapd | 인터페이스나 pcap 파일에서 흐름 파일 생성[3] |
| Security Onion | Elastic "NetFlow Records" 통합으로 수신해 NetFlow 대시보드로 보여 줌, 수신 포트 기본값 UDP 2055[5] |

수신 포트 기본값이 nfcapd 는 9995, Security Onion 은 2055 로 서로 다릅니다[2][5]. 실제로 기록이 어디로 갔는지는 내보내는 장비의 설정에 적힌 수집기 주소와 포트로 확인합니다. 클라우드의 VPC 흐름 로그는 [클라우드 핸드북 VPC 흐름 로그](https://urock-ailab.github.io/forensics-handbook/cloud/02-artifacts/aws/vpc-flow-logs.html) 페이지에 있습니다.

## 함정과 한계

**흐름 기록 하나가 연결 하나가 아닙니다.** 장비는 TCP FIN·RST 를 보거나, 일정 시간 패킷이 없거나(비활성 시간 초과), 오래 이어지는 흐름의 보고 주기가 되거나(활성 시간 초과), 메모리 부족 같은 내부 사정이 생기면 흐름을 내보냅니다[4]. IPFIX 에서는 이 이유가 `flowEndReason`(요소 번호 136) 필드에 0x01 비활성 시간 초과, 0x02 활성 시간 초과, 0x03 흐름 끝 감지, 0x04 강제 종료, 0x05 자원 부족으로 남습니다[6]. 합치지 않고 레코드 수를 세면 연결 수가 부풀고, 레코드 하나의 지속 시간만 보면 실제 연결 시간보다 짧게 읽힙니다.

**방향은 추측입니다.** `-B` 는 `-b` 처럼 합치면서 TCP·UDP 에서 출발지 포트가 목적지 포트보다 작고 출발지 포트가 1024 미만, 목적지 포트가 1024 초과이면 방향을 뒤집는 편의 옵션입니다[1]. 서버가 높은 포트를 쓰면 틀리므로, 누가 먼저 연결했는지는 TCP 플래그나 [Zeek 로그](../../02-artifacts/zeek/zeek-logs/index.md)의 conn.log 로 확인합니다.

**샘플링된 양은 추정값입니다.** 샘플링을 하는 장비는 N 개 중 한 패킷만 세고, 그 비율이 NetFlow v9 의 `SAMPLING_INTERVAL`(34)에, 방식이 `SAMPLING_ALGORITHM`(35, 1 결정적·2 무작위)에 남습니다[4]. nfcapd 는 이 비율을 패킷·바이트 수에 곱해 저장하므로 SNMP 같은 다른 계수와 값이 다를 수 있습니다[2]. 장비가 비율을 알리지 않으면 nfcapd 의 `-s` 값(기본 1, 샘플링 없음)을 쓰고, 음수로 주면 장비가 알린 값을 덮어씁니다[2]. 그래서 수집기 설정을 모르면 저장된 바이트 수가 실제 양인지 곱한 값인지 판단할 수 없습니다.

**계산된 속도 값은 한 방향만 봅니다.** 필터의 `bps` 는 8 × 들어온 바이트 ÷ 지속 시간, `pps` 는 들어온 패킷 ÷ 지속 시간, `bpp` 는 들어온 바이트 ÷ 들어온 패킷입니다[1]. 양방향으로 합친 레코드에서 되돌아온 쪽 양은 `out bytes`·`out packets` 로 따로 걸러야 합니다[1].

**필터의 호스트 이름은 지금 풀립니다.** `ip` 필터에 IP 대신 이름을 쓰면 nfdump 가 분석하는 시점에 DNS 로 이름을 IP 로 바꿉니다[1]. 사건 당시와 지금의 주소가 다를 수 있으므로, 당시 주소는 [DNS 분석](dns-analysis.md) 결과에서 얻어 IP 로 넣습니다.

**파일 이름의 시각은 흐름의 시각이 아닙니다.** 파일 이름은 그 파일에 저장하기 시작한 시각이라서[2], 활성 시간 초과로 늦게 내보낸 긴 흐름은 시작 시각이 이름보다 앞섭니다. 파일 이름만 보고 조사 창에 해당하는 파일을 고르면 앞뒤 흐름이 빠지므로, 앞뒤 파일까지 넉넉히 읽고 2단계처럼 필터로 거릅니다.

**장비를 거치지 않은 통신은 없습니다.** 흐름 기록은 내보내는 장비를 지나간 트래픽만 담습니다. 같은 스위치 안의 PC 끼리, 또는 다른 인터넷 출구로 나간 통신은 기록이 없어도 일어났을 수 있습니다. 어디서 보는지에 따라 무엇이 남는지는 [어디서 캡처하나](../../01-foundations/capture/capture-points.md) 페이지와 같은 원리입니다.

## 결과를 어떻게 해석하나

### 증명하는 것 / 증명하지 못하는 것

흐름 기록으로 증명할 수 있는 것은 "내보낸 장비가 이 시간대에 이 주소·포트 사이에서 이만큼의 패킷과 바이트를 보았다" 는 요약입니다. 여기에 더해 흐름에서 본 TCP 플래그 전체, 들어오고 나간 인터페이스 번호, 기록을 보낸 장비 주소가 남으므로 어느 경로로 지나갔는지도 알 수 있습니다[1][4].

증명하지 못하는 것은 다음과 같습니다. 내용·URL·파일 이름은 없습니다. 샘플링 환경에서는 정확한 양을 알 수 없습니다. 레코드 수는 연결 수가 아닙니다. 포트로 추측한 방향은 누가 먼저 연결했는지를 증명하지 않습니다. 기록이 없다고 해서 통신이 없었다는 뜻도 아닌데, 장비를 거치지 않았거나, 순서 오류로 빠졌거나, 보존 기간이 지나 지워졌을 수 있기 때문입니다. NAT 뒤에서는 기록의 주소가 실제 PC 주소가 아닐 수 있으며, 변환 전후 주소를 잇는 방법은 [IP 주소·포트·NAT 해석](../../01-foundations/records/ip-nat.md) 페이지에 있습니다.

### 시각

nfdump 가 보여 주는 시각은 세 종류입니다[1].

| 태그 | 뜻 | 기준 |
|---|---|---|
| `%ts`·`%tsr`·`%tsg` | 흐름 첫 패킷 시각(first seen) | 내보낸 장비의 시계 |
| `%te`·`%ter`·`%teg` | 흐름 마지막 패킷 시각(last seen) | 내보낸 장비의 시계 |
| `%tr`·`%trr`·`%trg` | 수집기가 레코드를 받은 시각 | 수집기의 시계 |

`r` 로 끝나는 태그는 1970-01-01 기준 epoch 초(소수), `g` 로 끝나는 태그는 GMT 입니다[1]. GMT 태그가 따로 있으므로 `%ts` 는 분석 PC 의 시간대로 표시될 가능성이 있고, 같은 레코드를 `%tsr` 과 `%tsg` 로 함께 뽑아 보면 확인됩니다. `%tr` 은 흐름이 일어난 시각이 아니라 받은 시각이라서, `%te` 와의 차이는 장비가 흐름을 붙잡아 둔 시간(시간 초과 설정)과 전송 지연을 보여 줍니다.

첫·마지막 패킷 시각은 장비 시계에 기대어 계산됩니다. NetFlow v9 에서 `FIRST_SWITCHED`(22)·`LAST_SWITCHED`(21)는 절대 시각이 아니라 장비가 켜진 뒤 흐른 밀리초(sysUptime)이고, 내보내기 패킷 머리의 `sysUpTime`(부팅 뒤 밀리초)과 `UNIX Secs`(패킷이 장비를 떠난 시각, 1970 UTC 기준 초)를 함께 써야 절대 시각이 나옵니다[4]. 아래는 명세로 만든 예시 머리 20바이트입니다.

```
00 09 00 01  00 36 EE 80  6A A8 8C D8  00 00 00 2A  00 00 00 00
버전=9       sysUpTime    UNIX Secs    순서 번호     Source ID
count=1      =3,600,000ms =1789431000  =42           =0
```

`UNIX Secs` 1789431000 은 2026-09-15 00:10:00 UTC 입니다. 이 패킷에 든 흐름의 `FIRST_SWITCHED` 가 3,000,000 이면 첫 패킷은 내보내기 600초 전인 00:00:00 UTC, `LAST_SWITCHED` 가 3,590,000 이면 마지막 패킷은 10초 전인 00:09:50 UTC 입니다(만든 예시). 장비 시계가 틀리면 이 계산 결과가 모두 같은 만큼 어긋나므로, 장비 시계 설정과 NTP 동기화 기록을 함께 확보합니다. 순서 번호는 내보내기 패킷마다 1씩 늘어나서 건너뛴 번호가 있으면 받지 못한 패킷이 있다는 뜻이고[4], 수집기에 저장된 파일에서는 nfdump `-E` 의 장비별 순서 오류 수로 확인합니다[1]. 여러 소스의 시각을 맞추는 방법은 [네트워크 기록의 시각](../../01-foundations/records/timestamps.md)과 [네트워크 타임라인](timeline.md) 페이지에 있습니다.

### 양과 모양으로 읽기

흐름 기록만으로도 통신의 모양은 드러납니다. 흐름당 바이트, 흐름당 패킷, 패킷당 바이트, 지속 시간, 일정 구간(1·5·20초)마다의 바이트·패킷·흐름 수를 변수로 삼아 DNS 터널을 찾은 연구가 있습니다[7]. 약 300명이 쓰는 대학 캠퍼스 일부 네트워크에 iodine 터널을 흘린 조건에서, 원시 흐름을 쓰는 탐지기(흐름당 바이트가 5000을 넘고 지속 시간이 55초를 넘으면 경보를 내는 규칙에, 패킷당 바이트 분포의 변화를 보는 규칙을 더한 것)가 모든 터널 사용을 잡았고 오탐은 12건(8건은 탐지 지연 탓)이었습니다[7]. 정상 DNS 는 구간마다의 바이트·패킷·흐름 수에서 낮과 밤의 차이가 뚜렷해서, 이 값에 기준을 둘 때는 시간대별로 달리 두어야 했습니다[7]. 다른 환경에 쓰려면 기준값과 구간 크기를 그 환경에 맞춰 다시 정해야 합니다[7]. 이 숫자를 그대로 가져다 쓰기보다, 같은 조직의 평소 흐름과 비교해 튀는 구간을 찾는 방법으로 씁니다. 일정한 간격으로 되풀이되는 연결은 [비컨 찾기](beaconing.md) 페이지를 봅니다.

### 보고서 문장 예

흐름 기록으로 쓸 수 있는 문장은 "기록된 만큼" 입니다(만든 예시).

- 쓸 수 있음: "경계 방화벽(192.0.2.1)이 내보낸 흐름 기록에, 2026-09-15 00:00:00 부터 00:09:50 UTC 사이 내부 주소 10.0.5.23 에서 203.0.113.10 의 TCP 443 으로 약 1.2GB 를 보낸 흐름이 있습니다. 이 장비는 샘플링을 쓰지 않도록 설정되어 있었습니다."
- 쓸 수 없음: "10.0.5.23 사용자가 회사 파일을 외부 서버에 올렸습니다."

두 번째 문장을 쓰려면 단말 기록, 프록시 로그, 패킷 캡처 같은 다른 근거가 필요합니다. 방화벽 허용·차단 기록과 맞춰 보는 방법은 [방화벽 로그](../../02-artifacts/devices/firewall-logs.md) 페이지에, 보고서 전체 형식은 [네트워크 포렌식 보고서](../reporting/forensic-report.md) 페이지에 있습니다.
